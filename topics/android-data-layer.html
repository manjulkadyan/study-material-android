10.1 Networking

HTTP Basics

HTTP is a stateless request/response protocol running over TCP/IP — every call is independent, no session memory, and every Android network call goes over HTTP or HTTPS.

Methods and semantics:

Method Safe Idempotent Has Body Use
GETYesYesNoFetch resource
POSTNoNoYesCreate resource
PUTNoYesYesReplace resource
PATCHNoNoYesPartial update
DELETENoYesNoRemove resource
HEADYesYesNoFetch headers only

Status code families:

  • 1xx — Informational (100 Continue, 101 Switching Protocols)
  • 2xx — Success (200 OK, 201 Created, 204 No Content)
  • 3xx — Redirection (301 Moved Permanently, 304 Not Modified)
  • 4xx — Client errors (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests)
  • 5xx — Server errors (500 Internal, 503 Service Unavailable, 504 Gateway Timeout)

Headers that matter on Android:

  • Content-Type: application/json — request/response body type
  • Authorization: Bearer <token> — auth header
  • Cache-Control — caching directives
  • ETag / If-None-Match — conditional requests for cache validation
  • Last-Modified / If-Modified-Since — time-based conditional requests
  • Accept-Encoding: gzip — OkHttp adds this automatically; saves 60–80% bandwidth
  • Connection: keep-alive — persistent connections (HTTP/1.1 default)

HTTP/2 benefits: multiplexed streams over single TCP connection (no head-of-line blocking at HTTP layer), header compression (HPACK), server push. OkHttp supports HTTP/2 automatically when server supports it.

Android implications: All network operations must be off the main thread. NetworkOnMainThreadException is thrown if you try. OkHttp uses a thread pool internally; Retrofit bridges to coroutines/RxJava.

REST Principles

REST is an architectural style, not a protocol — it's Roy Fielding's set of six constraints that, when followed, produce a scalable, loosely coupled web API. The constraints are:

  1. Client-Server: Separation of UI from data storage
  2. Stateless: Each request contains all context — no server-side session
  3. Cacheable: Responses must declare themselves cacheable or not
  4. Uniform Interface: Standard resource identification (URI), manipulation through representations, self-descriptive messages, HATEOAS (often skipped in practice)
  5. Layered System: Client doesn't know if it's talking to an origin server or proxy
  6. Code on Demand (optional): Server can send executable code

Resource modeling:

GET    /users/{id}          — fetch user
POST   /users               — create user
PUT    /users/{id}          — replace user
PATCH  /users/{id}          — partial update
DELETE /users/{id}          — delete user
GET    /users/{id}/orders   — sub-resource

Trade-offs vs GraphQL:

  • REST: multiple round-trips for nested data (N+1), simple caching
  • GraphQL: single round-trip, precise data fetching, complex caching (no HTTP caching by default)

JSON Serialization

JSON serialization is the process of converting between Kotlin/Java objects and JSON strings — and on Android there are two dominant modern approaches, plus one legacy one to know about:

Gson (Google, legacy):

val gson = Gson()
val json = gson.toJson(user)       // serialize
val user = gson.fromJson(json, User::class.java)  // deserialize

Problems: uses reflection, no null safety for Kotlin, poor performance on large payloads.

Moshi (Square, modern):

val moshi = Moshi.Builder()
    .addLast(KotlinJsonAdapterFactory())  // reflection adapter, or use codegen
    .build()
val adapter = moshi.adapter(User::class.java)
val json = adapter.toJson(user)
val user = adapter.fromJson(json)

Codegen with @JsonClass(generateAdapter = true) — faster than reflection, null-safe, Kotlin-idiomatic.

Kotlinx.serialization (JetBrains, newest):

@Serializable
data class User(val id: Int, val name: String)

val json = Json.encodeToString(User(1, "Alice"))
val user = Json.decodeFromString<User>(json)

Compile-time code generation, no reflection, first-class Kotlin support, excellent performance.

Key serialization concerns on Android:

  • Unknown fields: Moshi ignores by default; @JsonClass codegen does too. Gson silently ignores. Important for API versioning.
  • Null vs missing field: JSON null vs field absence — Kotlin default parameters handle absence; explicit null annotations handle null.
  • Custom adapters: For Date, BigDecimal, sealed classes, polymorphism.
  • Performance: Reflection-based is 2–5x slower than codegen; matters for lists with 1000+ items.

Retrofit + Moshi:

val retrofit = Retrofit.Builder()
    .baseUrl("https://api.example.com/")
    .addConverterFactory(MoshiConverterFactory.create(moshi))
    .client(okHttpClient)
    .build()

OkHttp

OkHttp is the HTTP client that lives underneath Retrofit — it manages connections, the request/response lifecycle, and the interceptor chain that lets you inject middleware at every call.

Internals:

  • Dispatcher: Manages async call execution. Default: 64 max concurrent requests, 5 per host. Backed by ExecutorService.
  • ConnectionPool: Reuses TCP connections. Default: 5 connections, 5-minute keep-alive.
  • Cache: Disk-backed HTTP cache using DiskLruCache.
  • Interceptor chain: Each interceptor calls chain.proceed() to pass to the next. Application interceptors run before caching; network interceptors run after.

Basic setup:

val okHttpClient = OkHttpClient.Builder()
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(30, TimeUnit.SECONDS)
    .writeTimeout(30, TimeUnit.SECONDS)
    .cache(Cache(cacheDir, 10 * 1024 * 1024)) // 10MB cache
    .addInterceptor(loggingInterceptor)
    .addInterceptor(authInterceptor)
    .authenticator(tokenRefreshAuthenticator)
    .build()

Call lifecycle:

  1. client.newCall(request) creates a RealCall
  2. call.enqueue(callback) dispatches to Dispatcher thread pool
  3. Interceptor chain executes: application interceptors → cache → network interceptors → server
  4. Response flows back through the chain

Failure modes:

  • ConnectException — cannot reach host
  • SocketTimeoutException — timeout hit
  • SSLHandshakeException — TLS failure
  • UnknownHostException — DNS failure
  • Response with error status code — NOT an exception in OkHttp; must check response.isSuccessful

Retrofit

Retrofit is a type-safe HTTP client that turns annotated Kotlin interfaces into working HTTP calls, using OkHttp as the transport layer underneath.

Interface definition:

interface UserApi {
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: String): User

    @GET("users")
    suspend fun getUsers(
        @Query("page") page: Int,
        @Query("limit") limit: Int
    ): PagedResponse<User>

    @POST("users")
    suspend fun createUser(@Body user: CreateUserRequest): User

    @PATCH("users/{id}")
    suspend fun updateUser(
        @Path("id") id: String,
        @Body update: UpdateUserRequest
    ): User

    @DELETE("users/{id}")
    suspend fun deleteUser(@Path("id") id: String): Response<Unit>

    @GET("users")
    suspend fun getUsersRaw(): Response<List<User>>  // wrap in Response<T> for status code access

    @Multipart
    @POST("uploads")
    suspend fun uploadFile(
        @Part file: MultipartBody.Part,
        @Part("description") description: RequestBody
    ): UploadResponse

    @Headers("Cache-Control: no-cache")
    @GET("feed")
    suspend fun getFeed(): List<FeedItem>
}

Suspend functions: Retrofit 2.6+ natively supports suspend fun with coroutines. The call runs on a background thread managed by OkHttp's Dispatcher; no manual thread switching needed.

Response<T> vs plain T:

  • T directly: Retrofit throws HttpException for non-2xx; good for simple cases
  • Response<T>: gives access to status code, headers, raw body; handle non-2xx yourself

Retrofit internals: Uses CallAdapter to convert OkHttp Call<T> to coroutine/RxJava. Uses Converter (Moshi/Gson/etc.) to serialize/deserialize bodies. Generates proxy objects via Java Proxy.newProxyInstance using the interface annotations.

Dynamic URLs:

@GET
suspend fun getFromUrl(@Url url: String): SomeResponse

Interceptors

Interceptors are middleware in the OkHttp chain — each one receives a Chain, can inspect or modify the request, calls chain.proceed() to pass it along, and can then inspect or modify the response on the way back.

Two types:

  • addInterceptor (application interceptors): Runs once, even for cached responses. Good for: auth headers, logging, retry logic.
  • addNetworkInterceptor (network interceptors): Runs only for actual network calls, not for cached responses. Good for: request/response body rewriting, monitoring actual bytes sent/received.

Logging interceptor:

val logging = HttpLoggingInterceptor().apply {
    level = if (BuildConfig.DEBUG) 
        HttpLoggingInterceptor.Level.BODY 
    else 
        HttpLoggingInterceptor.Level.NONE
}

Critical: Never log request/response bodies in production — bodies can contain tokens, PII, PHI.

Auth header interceptor:

class AuthInterceptor(private val tokenProvider: TokenProvider) : Interceptor {
    override fun intercept(chain: Chain): Response {
        val token = tokenProvider.getAccessToken() // synchronous, from memory/prefs
        val request = chain.request().newBuilder()
            .header("Authorization", "Bearer $token")
            .build()
        return chain.proceed(request)
    }
}

Retry interceptor:

class RetryInterceptor(private val maxRetries: Int = 3) : Interceptor {
    override fun intercept(chain: Chain): Response {
        var attempt = 0
        var response: Response
        do {
            if (attempt > 0) {
                Thread.sleep(2.0.pow(attempt).toLong() * 100) // exponential backoff
            }
            response = chain.proceed(chain.request())
            attempt++
        } while (!response.isSuccessful && isRetryable(response.code) && attempt < maxRetries)
        return response
    }

    private fun isRetryable(code: Int) = code == 503 || code == 504 || code == 429
}

Order matters: Interceptors are called in the order added. Typical order: logging → auth → retry.

Authentication and Token Refresh

Most APIs hand you a short-lived access token and a long-lived refresh token. When the access token expires and you get a 401, the client has to silently obtain a new one and replay the original request — all without the user noticing.

The race condition problem: If 3 requests fire simultaneously and all get 401, you don't want 3 concurrent token refresh calls — that's wasteful and may break some OAuth providers (refresh tokens are often single-use).

Safe single-flight token refresh with OkHttp Authenticator:

class TokenRefreshAuthenticator(
    private val tokenRepository: TokenRepository,
    private val authApi: AuthApi
) : Authenticator {

    // Mutex ensures only one refresh happens at a time
    private val refreshMutex = Mutex()

    override fun authenticate(route: Route?, response: Response): Request? {
        // If we've already retried once for this request chain, give up
        if (response.request.header("Authorization-Retried") != null) {
            return null // return null to propagate 401 to caller
        }

        // runBlocking is acceptable here — Authenticator is called from OkHttp's
        // IO thread pool, never the main thread
        val newToken = runBlocking {
            refreshMutex.withLock {
                // Double-check: another thread may have already refreshed
                val currentToken = tokenRepository.getAccessToken()
                val requestToken = response.request
                    .header("Authorization")
                    ?.removePrefix("Bearer ")

                if (currentToken != null && currentToken != requestToken) {
                    // Token was already refreshed by another thread — reuse it
                    currentToken
                } else {
                    // We need to actually refresh
                    try {
                        val refreshToken = tokenRepository.getRefreshToken()
                            ?: return@withLock null
                        val refreshResponse = authApi.refresh(RefreshRequest(refreshToken))
                        tokenRepository.saveTokens(refreshResponse.accessToken, refreshResponse.refreshToken)
                        refreshResponse.accessToken
                    } catch (e: Exception) {
                        tokenRepository.clearTokens()
                        null // triggers logout
                    }
                }
            }
        } ?: return null // null = don't retry, propagate 401

        return response.request.newBuilder()
            .header("Authorization", "Bearer $newToken")
            .header("Authorization-Retried", "true")
            .build()
    }
}

Key details:

  • Authenticator is only invoked on 401 Unauthorized (not 403).
  • Returning null from authenticate() stops retrying and propagates the 401.
  • The Mutex (from kotlinx.coroutines) is a non-reentrant coroutine-safe lock.
  • The "double-check" idiom (compare stored token to the one that failed) avoids a redundant refresh when two requests get 401 simultaneously.
  • runBlocking is intentional here — Authenticator.authenticate() is a synchronous interface.
  • For the authApi client used inside the authenticator, use a separate OkHttpClient without the authenticator to avoid infinite loops.

Alternative: Interceptor-based approach (less standard but used when 401 doesn't reliably trigger Authenticator):

class TokenRefreshInterceptor(
    private val tokenRepository: TokenRepository,
    private val authApi: AuthApi
) : Interceptor {
    private val refreshMutex = Mutex()

    override fun intercept(chain: Chain): Response {
        val response = chain.proceed(chain.request())
        if (response.code != 401) return response

        response.close() // Must close before proceeding again

        val newToken = runBlocking {
            refreshMutex.withLock {
                val current = tokenRepository.getAccessToken()
                val failed = chain.request().header("Authorization")?.removePrefix("Bearer ")
                if (current != null && current != failed) {
                    current
                } else {
                    val refresh = tokenRepository.getRefreshToken() ?: return@withLock null
                    try {
                        val r = authApi.refresh(RefreshRequest(refresh))
                        tokenRepository.saveTokens(r.accessToken, r.refreshToken)
                        r.accessToken
                    } catch (e: Exception) {
                        null
                    }
                }
            }
        } ?: return response

        return chain.proceed(
            chain.request().newBuilder()
                .header("Authorization", "Bearer $newToken")
                .build()
        )
    }
}

Failure modes:

  • Refresh token is also expired → clear tokens, emit logout event (use a SharedFlow or similar event bus).
  • Infinite loop if the auth endpoint itself returns 401 → guard with separate OkHttpClient or check URL.
  • Race condition if Mutex is not used → multiple refreshes, tokens overwritten with stale data.

Timeouts

Timeouts are limits on how long OkHttp is willing to wait at each phase of an HTTP call — connect, read, and write are each configurable independently.

Three timeout types:

  • connectTimeout: Time to establish TCP connection. Default: 10s. Set to 10–15s.
  • readTimeout: Time to wait for data between bytes from server. Default: 10s. For long-polling or streaming, increase significantly.
  • writeTimeout: Time to upload request body. Default: 10s. Increase for file uploads.
  • callTimeout (OkHttp 3.11+): End-to-end timeout for entire call including retries and redirects.

Per-request timeout override:

// OkHttp supports per-call timeouts via the Call API
val call = okHttpClient.newBuilder()
    .readTimeout(60, TimeUnit.SECONDS)
    .build()
    .newCall(request)

With Retrofit, use a custom CallAdapter or create dedicated client instances for long operations.

Failure modes:

  • SocketTimeoutException — read or write timeout hit
  • ConnectException — connect timeout hit (or refused)
  • Setting timeouts too high → users wait forever; too low → flaky on slow connections
  • File uploads need higher write timeout; video playback needs higher read timeout

Retries

Retries are automatic re-attempts of a failed request — the goal is to recover from transient failures transparently, without the user ever seeing an error.

What to retry:

  • 5xx (except 501) — transient server failures
  • 429 Too Many Requests — rate limit (respect Retry-After header)
  • Network errors (IOException) — connection drops, DNS failures
  • Never retry 4xx except 429 — 400/401/403/404 are client errors; retrying won't help

Exponential backoff with jitter:

class RetryInterceptor(
    private val maxAttempts: Int = 3,
    private val initialDelayMs: Long = 100
) : Interceptor {

    override fun intercept(chain: Chain): Response {
        val request = chain.request()
        var attempt = 0
        var lastResponse: Response? = null

        while (attempt < maxAttempts) {
            if (attempt > 0) {
                lastResponse?.close()
                val delayMs = initialDelayMs * (1L shl (attempt - 1)) + Random.nextLong(0, 100)
                Thread.sleep(delayMs)
            }
            try {
                val response = chain.proceed(request)
                if (response.isSuccessful || !shouldRetry(response.code)) {
                    return response
                }
                lastResponse = response
            } catch (e: IOException) {
                if (attempt == maxAttempts - 1) throw e
            }
            attempt++
        }
        return lastResponse!!
    }

    private fun shouldRetry(code: Int) = code == 429 || code in 500..599 && code != 501
}

Idempotency and retries: Only retry idempotent operations automatically. For POST (non-idempotent creates), require explicit user confirmation or use a client-generated idempotency key.

OkHttp built-in retries: OkHttp itself retries on connection failures (not on HTTP errors). This is controlled by retryOnConnectionFailure(true) (default). It does NOT retry on 5xx.

Caching

HTTP caching means storing responses locally so you can skip the network entirely for data you've already fetched recently.

HTTP cache headers:

  • Cache-Control: max-age=300 — cache for 5 minutes
  • Cache-Control: no-cache — revalidate with server before using
  • Cache-Control: no-store — never cache
  • Cache-Control: public — any cache may store
  • Cache-Control: private — only client cache
  • ETag: "abc123" — version token; client sends If-None-Match: "abc123" → server returns 304 if unchanged
  • Last-Modified: Thu, 01 Jan 2026 00:00:00 GMT — time-based equivalent

OkHttp cache setup:

val cache = Cache(
    directory = File(context.cacheDir, "http_cache"),
    maxSize = 50L * 1024 * 1024 // 50 MB
)

val client = OkHttpClient.Builder()
    .cache(cache)
    .build()

Force cache / force network:

// Only use cache, fail if not cached
request.newBuilder()
    .cacheControl(CacheControl.FORCE_CACHE)
    .build()

// Only use network, ignore cache
request.newBuilder()
    .cacheControl(CacheControl.FORCE_NETWORK)
    .build()

Offline-mode pattern:

class CacheInterceptor(private val context: Context) : Interceptor {
    override fun intercept(chain: Chain): Response {
        val request = if (!context.isNetworkAvailable()) {
            chain.request().newBuilder()
                .cacheControl(CacheControl.Builder()
                    .onlyIfCached()
                    .maxStale(7, TimeUnit.DAYS)
                    .build())
                .build()
        } else {
            chain.request()
        }
        return chain.proceed(request)
    }
}

Trade-offs:

  • HTTP cache is appropriate for GET requests with stable data
  • For mutable data (feed, user profile), prefer Room as the cache (offline-first) over HTTP cache
  • HTTP cache is transparent to the app; Room cache is explicit and controllable

Pagination

Pagination is the pattern of fetching a large dataset in manageable chunks rather than pulling everything at once — critical for feeds, search results, or any list that could grow unbounded.

Three pagination strategies:

1. Offset/Limit (page-based):

GET /posts?page=2&limit=20

Problem: If items are inserted/deleted between pages, you get duplicate or skipped items.

2. Cursor-based (keyset):

GET /posts?after=cursor_opaque_string&limit=20

The cursor encodes the last item's sort key (e.g., base64(id + timestamp)). Stable for real-time feeds. Cannot jump to arbitrary pages.

3. Timestamp-based:

GET /posts?before=2026-01-01T00:00:00Z&limit=20

Variant of cursor; natural for time-ordered feeds.

Paging 3 library (the standard Android approach):

// PagingSource for network-only
class PostPagingSource(
    private val api: PostApi
) : PagingSource<String, Post>() {

    override fun getRefreshKey(state: PagingState<String, Post>): String? {
        return state.anchorPosition?.let { anchor ->
            state.closestItemToPosition(anchor)?.id
        }
    }

    override suspend fun load(params: LoadParams<String>): LoadResult<String, Post> {
        return try {
            val cursor = params.key
            val response = api.getPosts(cursor = cursor, limit = params.loadSize)
            LoadResult.Page(
                data = response.items,
                prevKey = null, // can't go back
                nextKey = response.nextCursor
            )
        } catch (e: Exception) {
            LoadResult.Error(e)
        }
    }
}

// RemoteMediator for network + Room cache (covered in 10.3)
// ViewModel
val pager = Pager(
    config = PagingConfig(pageSize = 20, enablePlaceholders = false),
    pagingSourceFactory = { PostPagingSource(api) }
).flow.cachedIn(viewModelScope)

Error Mapping

Error mapping is the practice of converting raw HTTP and network exceptions into domain-specific sealed class errors that the UI layer can actually reason about. Without it, ViewModels receive raw HttpException, IOException, SocketTimeoutException — networking implementation details that have no business in the UI.

Domain error model:

sealed class NetworkError {
    object NoInternet : NetworkError()
    object Timeout : NetworkError()
    data class ServerError(val code: Int, val message: String) : NetworkError()
    data class Unauthorized(val message: String) : NetworkError()
    object NotFound : NetworkError()
    data class Unknown(val throwable: Throwable) : NetworkError()
}

Error mapping function:

fun Throwable.toNetworkError(): NetworkError = when (this) {
    is UnknownHostException, is ConnectException -> NetworkError.NoInternet
    is SocketTimeoutException -> NetworkError.Timeout
    is HttpException -> when (code()) {
        401 -> NetworkError.Unauthorized(message())
        404 -> NetworkError.NotFound
        in 500..599 -> NetworkError.ServerError(code(), message())
        else -> NetworkError.ServerError(code(), message())
    }
    else -> NetworkError.Unknown(this)
}

Parsing error response bodies:

// Server returns: {"error": "validation_failed", "details": "Email is invalid"}
data class ApiError(val error: String, val details: String?)

fun HttpException.parseErrorBody(moshi: Moshi): ApiError? {
    return try {
        val body = response()?.errorBody()?.string() ?: return null
        moshi.adapter(ApiError::class.java).fromJson(body)
    } catch (e: Exception) {
        null
    }
}

Result type pattern:

sealed class Result<out T> {
    data class Success<T>(val data: T) : Result<T>()
    data class Error(val error: NetworkError) : Result<Nothing>()
}

// Repository usage
suspend fun getUser(id: String): Result<User> = try {
    Result.Success(api.getUser(id))
} catch (e: Exception) {
    Result.Error(e.toNetworkError())
}

Alternatively, Kotlin's built-in kotlin.Result<T> or Arrow's Either<Error, Success> serve the same purpose.

Idempotency

An operation is idempotent when performing it multiple times produces exactly the same result as performing it once — which determines whether it's safe to automatically retry on failure.

HTTP idempotency:

  • GET, PUT, DELETE, HEAD: idempotent
  • POST, PATCH: NOT idempotent by default

Client-side idempotency key for POST:

// Client generates a unique key for each logical operation
val idempotencyKey = UUID.randomUUID().toString()

@POST("orders")
suspend fun createOrder(
    @Header("Idempotency-Key") key: String,
    @Body order: CreateOrderRequest
): Order

If the network fails after the server processes the request (but before the response arrives), the client can retry with the same key — the server recognizes the duplicate and returns the original result without creating a second order.

Android scenarios where idempotency matters:

  • Payment/booking APIs — user taps "Book" twice due to slow response
  • File uploads — upload failed mid-way, retry should not create a duplicate entry
  • Form submissions — user navigates back and resubmits

Avoiding duplicate requests in the UI:

class BookingViewModel : ViewModel() {
    private var bookingJob: Job? = null

    fun book() {
        if (bookingJob?.isActive == true) return // guard
        bookingJob = viewModelScope.launch {
            _state.update { it.copy(isLoading = true) }
            // ... make request
        }
    }
}

TLS Basics

TLS is the encryption layer that turns HTTP into HTTPS — and on Android 9 and above, cleartext HTTP is blocked by default via android:usesCleartextTraffic="false", so HTTPS is effectively mandatory.

TLS handshake steps (simplified):

  1. Client → Server: ClientHello (supported TLS versions, cipher suites, random nonce)
  2. Server → Client: ServerHello + Certificate + (optional) CertificateRequest
  3. Client validates certificate against trusted CAs
  4. Key exchange (ECDHE or similar) → shared secret
  5. Both sides derive session keys from shared secret
  6. Encrypted communication begins

Android trusted CAs: Android maintains a system CA store. Apps trust all system CAs by default. Enterprise apps can add custom CAs via network_security_config.xml.

TLS configuration in OkHttp:

// Restrict to TLS 1.2+ and strong cipher suites
val spec = ConnectionSpec.Builder(ConnectionSpec.MODERN_TLS)
    .tlsVersions(TlsVersion.TLS_1_3, TlsVersion.TLS_1_2)
    .cipherSuites(
        CipherSuite.TLS_AES_128_GCM_SHA256,
        CipherSuite.TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
    )
    .build()

val client = OkHttpClient.Builder()
    .connectionSpecs(listOf(spec))
    .build()

network_security_config.xml (Android 7+):

<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>
    <domain-config>
        <domain includeSubdomains="true">api.example.com</domain>
        <pin-set expiration="2027-01-01">
            <pin digest="SHA-256">AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=</pin>
            <pin digest="SHA-256">BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB=</pin>
        </pin-set>
    </domain-config>
</network-security-config>

Certificate Pinning

Certificate pinning means hard-coding the expected public key hash of your server into the app and refusing any TLS connection that doesn't match — even if the certificate is otherwise valid and CA-signed.

Why it matters: Prevents man-in-the-middle attacks where an attacker has compromised a CA or installed a corporate proxy certificate. Critical for apps handling financial or health data.

Two types:

  • Certificate pinning: Pin the entire certificate (brittle — breaks on cert renewal)
  • Public key pinning: Pin the public key from the certificate (survives cert renewals if the key pair is retained)

OkHttp CertificatePinner:

val certificatePinner = CertificatePinner.Builder()
    .add("api.example.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .add("api.example.com", "sha256/BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB=") // backup pin
    .build()

val client = OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build()

How to get the pin:

openssl s_client -connect api.example.com:443 | \
    openssl x509 -pubkey -noout | \
    openssl pkey -pubin -outform der | \
    openssl dgst -sha256 -binary | \
    base64

Failure modes:

  • Pin mismatch → SSLPeerUnverifiedException — entire HTTPS call fails
  • Certificate renewal without updating pin → app-wide outage
  • Corporate proxies / debugging proxies (Charles, mitmproxy) → pinning fails intentionally

Mitigation strategies:

  • Always include at least two pins (primary + backup)
  • Set an expiration date and rotate pins before renewal
  • Implement a remote kill switch to disable pinning via a trusted configuration endpoint fetched without pinning
  • Use network_security_config.xml for declarative pinning (framework enforced, survives ProGuard)

Debug builds: Typically disable pinning or add the debug certificate pin to avoid blocking local proxies.

Interview Angles: Networking

Q: How do you handle token refresh safely?

"There are two problems to solve simultaneously. The first is a 401 triggering multiple concurrent refresh calls — if three requests all fail at once, you don't want three parallel hits to the auth server. The second is re-using a stale token after another thread already refreshed it. I solve both with OkHttp's Authenticator interface combined with a Mutex. The Authenticator is only invoked on a 401. The Mutex serializes access so only one refresh actually happens. And there's a double-check inside the lock: I compare the stored token to the token that failed — if they're already different, another thread refreshed while I was waiting, so I just reuse the new token and skip the network call. That combination eliminates both races."

Q: How do you model network errors?

"The rule I follow is: never let HttpException or IOException escape the data layer. At the repository boundary I map all exceptions to a sealed class NetworkError using a Kotlin extension function on Throwable. For server errors with structured bodies, I parse the errorBody() from HttpException. The ViewModel gets a Result<T> or Either<NetworkError, T> — never a raw exception — which means the UI logic can just pattern-match on human-readable cases like NoInternet, Timeout, Unauthorized, ServerError, without caring about HTTP internals."

Q: How do you avoid duplicate requests?

"There are three layers I use. First, a ViewModel-level guard — before launching a new coroutine job, I check if one is already active and bail out if so; that handles double-taps and fast navigation. Second, for non-idempotent POST requests, I generate a UUID per logical operation and include it as an Idempotency-Key header — the server can then recognize a retry and return the original result without creating a duplicate. Third, for search and autocomplete, I apply debounce() in the StateFlow pipeline so rapid keystrokes only trigger one network call."

Q: How do you handle pagination?

"I use Paging 3. For a pure-network list, I write a PagingSource that fetches from the API. For a network-plus-local-cache setup, I use RemoteMediator alongside a Room-backed PagingSource — the RemoteMediator fetches from the network and writes to Room, and the PagingSource reads from Room, so the DB is always the source of truth. The PagingConfig controls pageSize, initialLoadSize, and prefetchDistance. In the ViewModel I expose .flow.cachedIn(viewModelScope) so the paged data survives config changes. In Compose I collect with collectAsLazyPagingItems() and handle the LoadState for loading, error, and empty states."

Q: Retry strategy for failed requests?

"My default is exponential backoff with jitter in an Interceptor. I retry 5xx errors — except 501, which means 'not implemented' and will never succeed on retry — and network IOException. For 429 I respect the Retry-After header. I cap at three attempts. The critical rule is that I never auto-retry non-idempotent POST requests unless they carry an idempotency key, because retrying a POST that the server already processed would create a duplicate. For background sync specifically, I delegate to WorkManager, which handles retries with BackoffPolicy.EXPONENTIAL and survives process death."

10.2 Persistence

SQLite Basics

SQLite is a lightweight relational database embedded directly in every Android device — a single on-disk file, accessed through the android.database.sqlite package, with no separate server process.

Key characteristics:

  • Single writer at a time (WAL mode allows concurrent reads)
  • ACID transactions
  • Dynamically typed (type affinity, not strict enforcement)
  • No network overhead; reads/writes directly to a file in data/data/<package>/databases/

WAL mode (Write-Ahead Logging): Room enables WAL by default since Room 2.2. In WAL mode, writes go to a .wal file and are periodically checkpointed into the main database. Allows concurrent reads during writes (much better performance for read-heavy apps).

Raw SQLite pattern (rarely used directly; Room is preferred):

val db = context.openOrCreateDatabase("app.db", Context.MODE_PRIVATE, null)
db.execSQL("CREATE TABLE IF NOT EXISTS users (id TEXT PRIMARY KEY, name TEXT)")
val cursor = db.rawQuery("SELECT * FROM users WHERE id = ?", arrayOf(userId))
cursor.use {
    while (it.moveToNext()) {
        val id = it.getString(it.getColumnIndex("id"))
    }
}

Problems with raw SQLite: manual cursor management, no compile-time query validation, no type safety, tedious migrations.

Room

Room is the Jetpack persistence library — it sits on top of SQLite and gives you compile-time query verification, type-safe DAOs, migration scaffolding, and first-class support for Flow and LiveData.

Setup:

// build.gradle.kts
implementation("androidx.room:room-runtime:2.6.1")
implementation("androidx.room:room-ktx:2.6.1")
ksp("androidx.room:room-compiler:2.6.1")

The three core components:

  1. @Entity — maps to a database table
  2. @Dao — Data Access Object; defines SQL queries as Kotlin functions
  3. @Database — the database holder; creates/opens the SQLite file

Database declaration:

@Database(
    entities = [UserEntity::class, PostEntity::class],
    version = 3,
    exportSchema = true  // exports schema JSON; required for migration testing
)
@TypeConverters(DateConverter::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun userDao(): UserDao
    abstract fun postDao(): PostDao

    companion object {
        @Volatile private var instance: AppDatabase? = null

        fun getInstance(context: Context): AppDatabase =
            instance ?: synchronized(this) {
                instance ?: Room.databaseBuilder(
                    context.applicationContext,
                    AppDatabase::class.java,
                    "app_database"
                )
                .addMigrations(MIGRATION_1_2, MIGRATION_2_3)
                .fallbackToDestructiveMigration() // ONLY in dev; never in production
                .build().also { instance = it }
            }
    }
}

Room compilation: The @Database annotation processor generates AppDatabase_Impl, validates all @Query annotations at compile time (SQL syntax, column names, return types), generates efficient boilerplate. This compile-time validation is the single biggest advantage over raw SQLite.

Entity

An @Entity is a Kotlin data class that maps directly to a SQLite table — each property becomes a column, and Room's annotation processor generates all the schema DDL at compile time.

@Entity(
    tableName = "users",
    indices = [
        Index(value = ["email"], unique = true),
        Index(value = ["last_name", "first_name"])
    ],
    foreignKeys = [
        ForeignKey(
            entity = TeamEntity::class,
            parentColumns = ["id"],
            childColumns = ["team_id"],
            onDelete = ForeignKey.CASCADE  // or SET_NULL, RESTRICT, NO_ACTION
        )
    ]
)
data class UserEntity(
    @PrimaryKey val id: String,              // String PKs: use UUIDs
    @ColumnInfo(name = "first_name") val firstName: String,
    @ColumnInfo(name = "last_name") val lastName: String,
    val email: String,
    @ColumnInfo(name = "team_id") val teamId: String?,
    @ColumnInfo(name = "created_at") val createdAt: Long,  // Store dates as epoch ms
    @Ignore val transientField: String = "" // not persisted
)

Type converters: Room stores only primitives, Strings, ByteArray, and Boxed primitives natively. For complex types:

class DateConverter {
    @TypeConverter fun fromDate(date: Date?): Long? = date?.time
    @TypeConverter fun toDate(ms: Long?): Date? = ms?.let { Date(it) }
}

Embedded objects:

data class Address(val street: String, val city: String)

@Entity
data class UserEntity(
    @PrimaryKey val id: String,
    @Embedded val address: Address  // columns: street, city stored directly in users table
)

DAO

A DAO (Data Access Object) is an interface annotated with @Dao where you declare your SQL operations as abstract Kotlin functions — Room generates the entire implementation at compile time.

@Dao
interface UserDao {
    // Simple queries
    @Query("SELECT * FROM users WHERE id = :id")
    suspend fun getUserById(id: String): UserEntity?

    @Query("SELECT * FROM users WHERE team_id = :teamId ORDER BY last_name ASC")
    suspend fun getUsersByTeam(teamId: String): List<UserEntity>

    // Reactive queries (return Flow)
    @Query("SELECT * FROM users ORDER BY last_name ASC")
    fun getAllUsersFlow(): Flow<List<UserEntity>>

    @Query("SELECT * FROM users WHERE id = :id")
    fun getUserByIdFlow(id: String): Flow<UserEntity?>

    // Insert operations
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertUser(user: UserEntity)

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertUsers(users: List<UserEntity>)

    // Update
    @Update
    suspend fun updateUser(user: UserEntity): Int  // returns rows affected

    // Delete
    @Delete
    suspend fun deleteUser(user: UserEntity)

    @Query("DELETE FROM users WHERE id = :id")
    suspend fun deleteUserById(id: String)

    @Query("DELETE FROM users")
    suspend fun deleteAllUsers()

    // Upsert (Room 2.5+)
    @Upsert
    suspend fun upsertUser(user: UserEntity)

    // Partial updates with POJO
    @Query("UPDATE users SET email = :email WHERE id = :id")
    suspend fun updateEmail(id: String, email: String)

    // Count
    @Query("SELECT COUNT(*) FROM users")
    suspend fun count(): Int

    // JOIN query returning custom POJO
    @Query("""
        SELECT u.*, t.name as team_name 
        FROM users u 
        LEFT JOIN teams t ON u.team_id = t.id 
        WHERE u.id = :userId
    """)
    suspend fun getUserWithTeam(userId: String): UserWithTeam?
}

OnConflictStrategy:

  • REPLACE: delete old row, insert new (triggers DELETE + INSERT, may break foreign key cascades)
  • IGNORE: keep old row, ignore new (returns -1 for the rowId)
  • ABORT (default): throw exception

Transactions

A database transaction groups multiple operations into one atomic unit — they all succeed together or all roll back together. Room provides the @Transaction annotation to declare this, plus database.withTransaction {} for cross-DAO operations.

@Dao
interface UserDao {
    @Transaction
    suspend fun replaceAllUsers(users: List<UserEntity>) {
        deleteAllUsers()
        insertUsers(users)
    }

    @Insert
    suspend fun insertUsers(users: List<UserEntity>)

    @Query("DELETE FROM users")
    suspend fun deleteAllUsers()
}

Database-level transaction (when spanning multiple DAOs):

suspend fun syncUsersAndTeams(
    users: List<UserEntity>,
    teams: List<TeamEntity>
) {
    database.withTransaction {
        database.teamDao().insertAll(teams)
        database.userDao().insertUsers(users)  // users reference teams via FK
    }
}

database.withTransaction is a Room extension that wraps the lambda in a SQLite transaction. Any exception inside will roll back the transaction.

Why transactions matter:

  • Atomicity: If an app process is killed mid-sync, partial state is not visible
  • Performance: Inserting 1000 rows in a single transaction is 10–50x faster than 1000 individual inserts (avoids 1000 journal writes)
  • Consistency: Foreign key constraints are checked at transaction commit, not per-insert

Migrations

A migration is how you evolve the database schema across app versions without losing user data — Room validates every migration against a generated schema snapshot, so if your SQL is wrong you find out at build time, not in production.

Room migration mechanics:

  1. Increment the version in @Database
  2. Write a Migration object with the SQL ALTER/CREATE/DROP statements
  3. Register with addMigrations()
  4. Room validates the final schema against the generated schema JSON
val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL("ALTER TABLE users ADD COLUMN profile_image_url TEXT")
    }
}

val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(database: SupportSQLiteDatabase) {
        // SQLite doesn't support DROP COLUMN directly (before API 35)
        // Must recreate the table
        database.execSQL("""
            CREATE TABLE users_new (
                id TEXT NOT NULL PRIMARY KEY,
                first_name TEXT NOT NULL,
                last_name TEXT NOT NULL,
                email TEXT NOT NULL
            )
        """)
        database.execSQL("""
            INSERT INTO users_new (id, first_name, last_name, email)
            SELECT id, first_name, last_name, email FROM users
        """)
        database.execSQL("DROP TABLE users")
        database.execSQL("ALTER TABLE users_new RENAME TO users")
    }
}

Multi-version migration: Room supports jumping multiple versions:

val MIGRATION_1_3 = object : Migration(1, 3) { ... }
// Room will use 1→3 directly if available, falling back to 1→2→3

Auto-migrations (Room 2.4+):

@Database(
    ...,
    version = 4,
    autoMigrations = [
        AutoMigration(from = 3, to = 4)  // simple addColumn works automatically
    ]
)

For complex changes (renames, drops), use @AutoMigrationSpec:

@RenameColumn(tableName = "users", fromColumnName = "name", toColumnName = "full_name")
class Migration3to4Spec : AutoMigrationSpec

Testing migrations:

@RunWith(AndroidJUnit4::class)
class MigrationTest {
    @get:Rule val helper = MigrationTestHelper(
        InstrumentationRegistry.getInstrumentation(),
        AppDatabase::class.java
    )

    @Test
    fun migrate1To2() {
        helper.createDatabase(TEST_DB, 1).apply {
            execSQL("INSERT INTO users VALUES('1', 'Alice', 'Smith', 'alice@test.com')")
            close()
        }
        val db = helper.runMigrationsAndValidate(TEST_DB, 2, true, MIGRATION_1_2)
        // validate data is preserved
        val cursor = db.query("SELECT profile_image_url FROM users WHERE id = '1'")
        assertThat(cursor.moveToFirst()).isTrue()
        assertThat(cursor.getString(0)).isNull()
    }
}

fallbackToDestructiveMigration(): Only for development. In production, a missing migration drops and recreates the database — all user data is lost. Never use in production.

Indexes

A database index is a B-tree structure that speeds up queries on specific columns — the trade-off is extra storage and slightly slower writes, because each insert or update has to maintain the index tree as well as the table.

@Entity(
    tableName = "posts",
    indices = [
        Index(value = ["user_id"]),                        // index for FK lookups
        Index(value = ["created_at"]),                     // index for time-based queries
        Index(value = ["user_id", "created_at"]),          // composite index for filtered + sorted
        Index(value = ["slug"], unique = true)             // unique constraint via index
    ]
)
data class PostEntity(
    @PrimaryKey val id: String,
    val userId: String,
    val slug: String,
    val title: String,
    val createdAt: Long
)

When to add indexes:

  • Foreign key columns (always — SQLite does not auto-index FKs unlike PostgreSQL)
  • Columns used in WHERE clauses of frequent queries
  • Columns used in ORDER BY (especially for large tables)
  • Columns used in JOIN conditions

When indexes hurt:

  • INSERT/UPDATE/DELETE are slower (must update index B-tree)
  • Extra storage per row
  • Full table scans are faster for tables with < ~100 rows

EXPLAIN QUERY PLAN (use in debug mode to verify index usage):

val cursor = db.query("EXPLAIN QUERY PLAN SELECT * FROM posts WHERE user_id = '1'", null)
// Output should show "SEARCH posts USING INDEX idx_posts_user_id"
// Not "SCAN posts" which is a full table scan

Foreign Keys and Relations

Foreign keys enforce referential integrity at the database level — a child row simply cannot reference a parent that doesn't exist, and Room can cascade deletes or set nulls automatically when a parent is removed.

// Enable foreign keys — not enabled by default in SQLite!
val db = Room.databaseBuilder(...)
    .addCallback(object : RoomDatabase.Callback() {
        override fun onOpen(db: SupportSQLiteDatabase) {
            db.execSQL("PRAGMA foreign_keys = ON")
        }
    })
    .build()

Relations in Room: Room does not support SQL JOINs in @Query returning entity objects directly. Instead, use data classes with @Relation:

data class UserWithPosts(
    @Embedded val user: UserEntity,
    @Relation(
        parentColumn = "id",
        entityColumn = "user_id"
    )
    val posts: List<PostEntity>
)

@Dao
interface UserDao {
    @Transaction
    @Query("SELECT * FROM users WHERE id = :userId")
    suspend fun getUserWithPosts(userId: String): UserWithPosts?
}

@Transaction is required on @Relation queries — Room makes two separate queries (one for users, one for posts) and merges them in memory; the transaction ensures consistency.

Many-to-many:

@Entity(primaryKeys = ["user_id", "tag_id"])
data class UserTagCrossRef(
    @ColumnInfo(name = "user_id") val userId: String,
    @ColumnInfo(name = "tag_id") val tagId: String
)

data class UserWithTags(
    @Embedded val user: UserEntity,
    @Relation(
        parentColumn = "id",
        entityColumn = "id",
        associateBy = Junction(UserTagCrossRef::class,
            parentColumn = "user_id",
            entityColumn = "tag_id")
    )
    val tags: List<TagEntity>
)

Flow from Room

When a Room DAO method returns Flow<T>, it emits the current query result immediately and then automatically re-emits every time the underlying table changes — which means the UI never has to poll; it just collects and stays current.

@Dao
interface UserDao {
    @Query("SELECT * FROM users ORDER BY last_name ASC")
    fun getAllUsers(): Flow<List<UserEntity>>
}

How it works internally: Room uses InvalidationTracker — a table observer that detects when tables are modified by tracking statement IDs. When a tracked table changes, it notifies all observing Flow collectors, which re-execute their query.

Combining Room Flow with network data:

class UserRepository(
    private val userDao: UserDao,
    private val userApi: UserApi
) {
    // Expose Room Flow — UI always shows local data
    val users: Flow<List<User>> = userDao.getAllUsers()
        .map { entities -> entities.map { it.toUser() } }

    // Refresh from network — writes to Room, triggers Flow
    suspend fun refresh() {
        val remoteUsers = userApi.getUsers()
        userDao.insertUsers(remoteUsers.map { it.toEntity() })
    }
}

Important: Room queries on Flow run on the I/O dispatcher internally. But if you're collecting and doing other work, use .flowOn(Dispatchers.IO) explicitly in the repository, and collect on the main thread in the ViewModel.

One-shot vs reactive:

  • suspend fun DAO functions: one-shot, coroutine-based
  • Flow<T> DAO functions: reactive, long-lived observation
  • Use Flow for anything the UI displays live; use suspend fun for write operations

DataStore

DataStore is the modern replacement for SharedPreferences — it does the same key-value job but uses coroutines and Flow throughout, so all I/O is async, off the main thread, and errors surface properly instead of silently failing.

Two variants:

Preferences DataStore — for untyped key-value data (analogous to SharedPreferences):

val Context.dataStore by preferencesDataStore(name = "settings")

// Keys
val DARK_MODE_KEY = booleanPreferencesKey("dark_mode")
val USER_ID_KEY = stringPreferencesKey("user_id")
val THEME_KEY = intPreferencesKey("theme")

// Read (returns Flow — always up-to-date)
val isDarkMode: Flow<Boolean> = context.dataStore.data
    .map { prefs -> prefs[DARK_MODE_KEY] ?: false }

// Write
suspend fun setDarkMode(enabled: Boolean) {
    context.dataStore.edit { prefs ->
        prefs[DARK_MODE_KEY] = enabled
    }
}

Proto DataStore — for typed, schema-validated data using Protocol Buffers:

// user_settings.proto
syntax = "proto3";
message UserSettings {
    bool dark_mode = 1;
    string user_id = 2;
    int32 theme = 3;
}
object UserSettingsSerializer : Serializer<UserSettings> {
    override val defaultValue = UserSettings.getDefaultInstance()
    override suspend fun readFrom(input: InputStream): UserSettings =
        UserSettings.parseFrom(input)
    override suspend fun writeTo(t: UserSettings, output: OutputStream) =
        t.writeTo(output)
}

val Context.userSettingsDataStore by dataStore(
    fileName = "user_settings.pb",
    serializer = UserSettingsSerializer
)

// Read
val settings: Flow<UserSettings> = context.userSettingsDataStore.data

// Write
suspend fun setDarkMode(enabled: Boolean) {
    context.userSettingsDataStore.updateData { current ->
        current.toBuilder().setDarkMode(enabled).build()
    }
}

SharedPreferences Legacy

SharedPreferences is the original Android key-value store — it writes to XML files and is still common in legacy codebases, but it has enough problems that all new code should use DataStore instead.

Q: Room migration strategy.

"Whenever I change the schema, I increment the @Database version by one and write a Migration object with the raw SQL — ALTER TABLE for adding a column, and the full recreate pattern for dropping or renaming a column because SQLite doesn't support DROP COLUMN before API 35. I register the migration with addMigrations(). "DataStore is strictly better on every axis that matters. It's async, Flow-based, thread-safe, and surfaces IOException through the Flow error channel instead of silently swallowing it. There's zero ANR risk because I/O never touches the main thread. SharedPreferences.commit() blocks the calling thread and can cause ANRs, and apply() is async but gives you no way to know if it failed. Q: When use database vs file vs DataStore?

  • Room: Structured relational data with queries, sorting, filtering — user data, feed items, appointments. Anything with rows and columns.
  • DataStore: User preferences, settings, lightweight app state — small, keyed values without structure.
  • File: Binary data — images, PDFs, downloads, audio. Not queryable; addressed by path/URI.
  • SharedPreferences: Legacy only; migrate away.

Q: How do you design offline cache?

"I use Room as the single source of truth. Network responses are written to Room; the ViewModel never holds its own copy of data — it just observes a Room Flow. Cache invalidation is also free — I just write to Room and every observer gets the new data without any explicit notification code."

Q: How do you handle schema changes?

"I write a Migration for every version increment, no exceptions, because users may have builds several versions behind. For adding a column, ALTER TABLE is fine. FROM old_name, drop the original, then rename the new table. I test every migration path with MigrationTestHelper — create the database at version N, run the migration, then assert the data survived and the schema matches."

10.3 Offline-First Design

Single Source of Truth

The single source of truth is the principle that one place — typically Room — is the definitive data source for the UI, and the network is just a mechanism to push updates into that place, never a direct source.

Why it matters:

  • The UI always reads from the local DB, so there are no loading spinners for data you've already cached.
  • State is predictable — there are no race conditions between a network response landing and what the UI is displaying.
  • Offline support is natural — the local DB always has something to show, even with no connectivity.
  • Error handling is simpler — network failures update DB state or surface a flag, rather than being wired directly into UI state.

Implementation pattern:

Network Response → Repository → Room DB → Flow → ViewModel → UI
                                   ↑
                         (UI reads ONLY from here)

The ViewModel never holds a copy of data; it only transforms what comes from the Room Flow. The repository orchestrates: fetch from network → write to Room → Room Flow notifies UI.

Contrast with non-SSOT pattern (anti-pattern):

// BAD: two sources of data → UI can show inconsistent state
viewModelScope.launch {
    _state.update { it.copy(users = dao.getAll()) }  // initial load from DB
    val fresh = api.getUsers()
    _state.update { it.copy(users = fresh) }          // overwrite with network
}

The SSOT approach instead: write fresh data to DB, let the DB Flow update the state.

Cache Invalidation

Cache invalidation is the problem of knowing when locally cached data is stale enough to warrant a fresh network fetch — and it turns out there are several complementary strategies, each appropriate in different situations.

Strategies:

1. TTL (Time-To-Live):

    @PrimaryKey val id: String,
    val content: String,
    val fetchedAt: Long = System.currentTimeMillis()
)

fun FeedItemEntity.isStale(ttlMs: Long = 5 * 60 * 1000): Boolean {
    return System.currentTimeMillis() - fetchedAt > ttlMs
}

// Repository: refresh if stale
suspend fun getFeed(): Flow<List<FeedItem>> {
    val cached = feedDao.getAll().first()
    if (cached.isEmpty() || cached.first().isStale()) {
        fetchAndStore()
    }
    return feedDao.getAllFlow().map { ... }
}

2. ETag/Last-Modified (server-driven):

// Store ETag with cached data
val etag = response.header("ETag")
feedDao.saveEtag(etag)

// Next request: send If-None-Match header
val cachedEtag = feedDao.getEtag()
val request = Request.Builder()
    .url(url)
    .header("If-None-Match", cachedEtag ?: "")
    .build()

// 304 → use cache; 200 → update cache with new ETag

3. Event-driven invalidation:

// Push notification or WebSocket event triggers refresh
class PushNotificationHandler {
    fun onFeedUpdated() {
        coroutineScope.launch { feedRepository.refresh() }
    }
}

4. Manual pull-to-refresh: User-initiated invalidation. Always appropriate as a fallback.

Stale-while-revalidate pattern: Show cached data immediately; trigger refresh in background; update UI when new data arrives (Room Flow handles the update automatically).

Sync Strategy

A sync strategy is how you keep local data in sync with the server — especially important when the user has made mutations while offline that now need to reach the server.

Read sync — server to local — is straightforward: fetch and overwrite. Write sync — local to server — is more complex because local changes need to reach the server eventually, and failures have to be handled.

Full sync (simple, high bandwidth):

suspend fun fullSync() {
    val remoteData = api.getAllItems()
    database.withTransaction {
        dao.deleteAll()
        dao.insertAll(remoteData.map { it.toEntity() })
    }
}

Good for small datasets. Bad for large datasets or frequent updates.

Delta sync (incremental):

// Server returns only items changed since a timestamp
suspend fun deltaSync(lastSyncTime: Long) {
    val delta = api.getChangedItems(since = lastSyncTime)
    database.withTransaction {
        dao.upsertAll(delta.updated.map { it.toEntity() })
        dao.deleteByIds(delta.deleted)
        preferences.setLastSyncTime(System.currentTimeMillis())
    }
}

Requires server support. More complex but scalable.

Two-phase sync (for write conflicts):

  1. Push local changes → server
  2. Pull server changes → local
  3. Merge conflicts

Sync triggers:

  • App foreground: immediate sync on resume
  • Periodic: WorkManager PeriodicWorkRequest (minimum 15 minutes)
  • Event-driven: FCM push notification triggers sync
  • Network reconnection: ConnectivityManager.NetworkCallback
// Network reconnection trigger

    override fun onAvailable(network: Network) {
        coroutineScope.launch { syncRepository.sync() }
    }
}
connectivityManager.registerDefaultNetworkCallback(networkCallback)

Conflict Resolution

A conflict exists when a resource has been modified both locally while offline and independently on the server — and the two versions are now inconsistent with each other.

Conflict detection:

  • Server-side versioning: each entity carries a version integer or updatedAt timestamp. The client sends the version it last saw, and the server rejects the request if the stored version is different.
  • Optimistic locking: a PUT /items/1 body includes {"version": 5, ...}. The server returns 409 Conflict if the stored version is no longer 5.

Resolution strategies:

1. Last-write-wins (LWW): The most recent write (by timestamp) wins. Simple but can silently discard changes. Appropriate for user settings, preferences.

2. Server-wins: On conflict, discard local changes and use server data. Simple; appropriate when server data is authoritative (financial transactions).

fun resolveConflict(local: ItemEntity, remote: ItemEntity): ItemEntity = remote

3. Client-wins: Local changes always win. Rare; appropriate only when client is the single writer.

4. Merge: For field-level conflicts (e.g., user updates name, server updates email independently) — merge non-conflicting fields. Requires CRDT or OT for true merge.

fun mergeItems(local: ItemEntity, remote: ItemEntity): ItemEntity {
    return remote.copy(
        name = if (local.nameModifiedAt > remote.nameModifiedAt) local.name else remote.name,
        email = if (local.emailModifiedAt > remote.emailModifiedAt) local.email else remote.email
    )
}

5. User-assisted: Show conflict UI and let the user choose. Appropriate for document editors (Google Docs model).

Android pattern with Room:

@Entity
data class ItemEntity(
    @PrimaryKey val id: String,
    val content: String,
    val serverVersion: Int,
    val isDirty: Boolean,  // true = modified locally, not yet synced
    val localModifiedAt: Long
)

suspend fun sync() {
    val dirtyItems = dao.getDirtyItems()
    dirtyItems.forEach { item ->
        try {
            val response = api.updateItem(item.id, item.toRequest(), expectedVersion = item.serverVersion)
            dao.upsert(response.toEntity().copy(isDirty = false))
        } catch (e: HttpException) {
            if (e.code() == 409) {
                val serverItem = api.getItem(item.id)
                val resolved = resolveConflict(item, serverItem.toEntity())
                dao.upsert(resolved)
            }
        }
    }
}

Optimistic Updates

An optimistic update means applying a user action immediately to the local database and UI before the server has confirmed it — then reconciling once the server responds. The reason to do this is that it eliminates perceived latency for common operations like likes, bookmarks, and deletes. The UI feels instantaneous.

Pattern:

class BookmarkViewModel(
    private val bookmarkRepository: BookmarkRepository
) : ViewModel() {

    fun toggleBookmark(postId: String, currentlyBookmarked: Boolean) {
        viewModelScope.launch {
            // 1. Optimistically update local DB immediately
            bookmarkRepository.setBookmarked(postId, !currentlyBookmarked)

            // 2. Send to server
            try {
                bookmarkRepository.syncBookmark(postId, !currentlyBookmarked)
            } catch (e: Exception) {
                // 3. Rollback on failure
                bookmarkRepository.setBookmarked(postId, currentlyBookmarked)
                _events.emit(BookmarkEvent.SyncFailed)
            }
        }
    }
}
// Repository
suspend fun setBookmarked(postId: String, bookmarked: Boolean) {
    bookmarkDao.setBookmarked(postId, bookmarked)  // immediate local write → UI updates via Flow
}

suspend fun syncBookmark(postId: String, bookmarked: Boolean) {
    if (bookmarked) {
        api.addBookmark(postId)
    } else {
        api.removeBookmark(postId)
    }
}

Failure modes:

  • Network failure → rollback required
  • Server rejects action (e.g., 403 — not authorized) → rollback + show error
  • Server returns different state (e.g., post was deleted) → update local DB with server response

Complex operations: For multi-step operations (booking a slot), optimistic updates are riskier. Use explicit loading states instead.

Retry Queue

A retry queue is a persistent store of failed mutations that should be retried once connectivity is restored. The key word is persistent — if the app is killed while offline, any in-memory queue is lost, so the queue must live in Room to survive process death.

@Entity(tableName = "pending_operations")
data class PendingOperationEntity(
    @PrimaryKey val id: String = UUID.randomUUID().toString(),
    val operationType: String,  // "BOOKMARK_ADD", "POST_CREATE", etc.
    val payload: String,        // JSON-serialized operation data
    val createdAt: Long = System.currentTimeMillis(),
    val attempts: Int = 0,
    val lastAttemptAt: Long? = null
)

@Dao
interface PendingOperationDao {
    @Query("SELECT * FROM pending_operations ORDER BY created_at ASC")
    suspend fun getAll(): List<PendingOperationEntity>

    @Insert
    suspend fun insert(op: PendingOperationEntity)

    @Delete
    suspend fun delete(op: PendingOperationEntity)

    @Query("UPDATE pending_operations SET attempts = attempts + 1, last_attempt_at = :now WHERE id = :id")
    suspend fun incrementAttempts(id: String, now: Long = System.currentTimeMillis())
}
class RetryQueueProcessor(
    private val dao: PendingOperationDao,
    private val handlers: Map<String, OperationHandler>
) {
    suspend fun processQueue() {
        val pending = dao.getAll()
        pending.forEach { op ->
            if (op.attempts >= MAX_ATTEMPTS) {
                dao.delete(op)
                return@forEach
            }
            try {
                handlers[op.operationType]?.handle(op.payload)
                dao.delete(op)
            } catch (e: Exception) {
                dao.incrementAttempts(op.id)
            }
        }
    }
}

NetworkBoundResource Pattern

NetworkBoundResource is a pattern from the Google Architecture Blueprints — pre-Paging-3 era — that coordinates cache and network in a single Flow: it always shows local data first, fetches fresh data from the network in parallel if needed, and writes the result back to the local cache.

Modern Kotlin implementation using Flow:

fun <LocalType, RemoteType> networkBoundResource(
    query: () -> Flow<LocalType>,           // DB query
    fetch: suspend () -> RemoteType,        // Network call
    saveFetchResult: suspend (RemoteType) -> Unit,  // Write to DB
    shouldFetch: (LocalType) -> Boolean = { true }, // Cache validity check
    onFetchFailed: (Throwable) -> Unit = {}
): Flow<Resource<LocalType>> = flow {

    emit(Resource.Loading())

    val data = query().first()

    val flow = if (shouldFetch(data)) {
        emit(Resource.Loading(data))  // Show cached data while fetching
        try {
            saveFetchResult(fetch())
            query().map { Resource.Success(it) }
        } catch (t: Throwable) {
            onFetchFailed(t)
            query().map { Resource.Error(t, it) }  // Show error + stale cached data
        }
    } else {
        query().map { Resource.Success(it) }
    }

    emitAll(flow)
}

sealed class Resource<T>(val data: T? = null, val error: Throwable? = null) {
    class Success<T>(data: T) : Resource<T>(data)
    class Error<T>(error: Throwable, data: T? = null) : Resource<T>(data, error)
    class Loading<T>(data: T? = null) : Resource<T>(data)
}

Usage in repository:

fun getFeed(): Flow<Resource<List<FeedItem>>> = networkBoundResource(
    query = { feedDao.getAllFlow().map { it.map(FeedItemEntity::toFeedItem) } },
    fetch = { api.getFeed() },

        database.withTransaction {
            feedDao.deleteAll()
            feedDao.insertAll(remote.map(RemoteFeedItem::toEntity))

        cached.isEmpty() || cached.firstOrNull()?.isStale() == true
    }
)

WorkManager for Sync

WorkManager is the Jetpack library for deferrable, guaranteed background work — work that must survive process death and device reboots and still run eventually. It is the right choice for sync because it gives you four things that nothing else provides together: guaranteed execution even if the app is killed, respect for battery optimization and Doze mode, constraint support (run only when connected to the network, charging, etc.), and built-in exponential backoff retry.

Sync worker:

class SyncWorker(
    context: Context,
    params: WorkerParameters,
    private val syncRepository: SyncRepository
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        return try {
            syncRepository.sync()
            Result.success()
        } catch (e: Exception) {
            if (runAttemptCount < 3) {
                Result.retry()  // WorkManager will retry with exponential backoff
            } else {
                Result.failure(workDataOf("error" to e.message))
            }
        }
    }

    companion object {
        fun buildRequest(): PeriodicWorkRequest {
            val constraints = Constraints.Builder()
                .setRequiredNetworkType(NetworkType.CONNECTED)
                .build()

            return PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
                .setConstraints(constraints)
                .setBackoffCriteria(BackoffPolicy.EXPEDITED, 10, TimeUnit.SECONDS)
                .build()
        }
    }
}

Pagination with Local Cache

RemoteMediator is Paging 3's mechanism for combining a Room-backed PagingSource with network fetching — Room is the source of truth for what the UI displays, and RemoteMediator is responsible for populating and refreshing Room as the user scrolls.

Architecture:

UI → PagingData (from Room PagingSource)
           ↑
       Room DB ← RemoteMediator (fetches from network, writes to Room)

RemoteMediator implementation:

@OptIn(ExperimentalPagingApi::class)
class FeedRemoteMediator(
    private val database: AppDatabase,
    private val api: FeedApi
) : RemoteMediator<Int, FeedItemEntity>() {

    override suspend fun initialize(): InitializeAction {
        val lastRefresh = database.remoteKeyDao().getLastRefresh()
        return if (System.currentTimeMillis() - (lastRefresh ?: 0) < CACHE_TIMEOUT) {
            InitializeAction.SKIP_INITIAL_REFRESH
        } else {
            InitializeAction.LAUNCH_INITIAL_REFRESH
        }
    }

    override suspend fun load(
        loadType: LoadType,
        state: PagingState<Int, FeedItemEntity>
    ): MediatorResult {
        return try {
            val page = when (loadType) {
                LoadType.REFRESH -> 1
                LoadType.PREPEND -> return MediatorResult.Success(endOfPaginationReached = true)
                LoadType.APPEND -> {
                    val lastPage = database.remoteKeyDao().getLastPage()
                        ?: return MediatorResult.Success(endOfPaginationReached = false)
                    lastPage + 1
                }
            }

            val response = api.getFeed(page = page, pageSize = state.config.pageSize)

            database.withTransaction {
                if (loadType == LoadType.REFRESH) {
                    database.feedDao().clearAll()
                    database.remoteKeyDao().clearAll()
                }
                database.feedDao().insertAll(response.items.map { it.toEntity() })
                database.remoteKeyDao().insert(
                    RemoteKey(page = page, lastRefresh = System.currentTimeMillis())
                )
            }

            MediatorResult.Success(endOfPaginationReached = response.items.size < state.config.pageSize)
        } catch (e: IOException) {
            MediatorResult.Error(e)
        } catch (e: HttpException) {
            MediatorResult.Error(e)
        }
    }

    companion object {
        const val CACHE_TIMEOUT = 30 * 60 * 1000L // 30 minutes
    }
}

Q: Design an offline-first feed.

"Room is the single source of truth. The ViewModel exposes a StateFlow derived from a Room Flow, and the UI only ever reads from that — it has no idea whether the data came from the network or the cache. "I mark every local mutation with isDirty = true in Room at the point of write. On success I mark the row isDirty = false. On failure I increment an attempts counter and retry with exponential backoff. Because the queue lives in Room, it survives process death — so even if the user force-closes the app mid-sync, the pending operations are still there when they reopen it. If attempts exceed the maximum I surface an error to the user rather than silently discarding the change."

Q: What happens when server and local data conflict?

"I detect conflicts with optimistic locking — every write includes a version field, and the server returns 409 Conflict if the stored version doesn't match. On a 409, the resolution depends on the business domain: for user preferences, last-write-wins by timestamp is usually fine; for financial or booking data, the server wins because it's the authoritative record; for profile fields that the user edited independently, a field-level merge is possible if I track a modifiedAt timestamp per field. After resolution, whatever the canonical state is gets written to Room and emits through the Flow. For genuinely complex conflicts I surface it to the user — show them both versions and let them choose."

Q: How do you avoid stale data?

"I layer several strategies. First, every Room entity has a fetchedAt timestamp, and the repository checks it on load — if it's expired, it triggers a refresh in the background while still showing the cached data immediately. Second, I use ETag-based revalidation when the server supports it: send If-None-Match with the cached ETag, and if nothing changed the server returns a 304 with near-zero bandwidth cost. Third, FCM push notifications can trigger an immediate refresh when the server knows data has changed. Fourth, pull-to-refresh as a user-initiated fallback. And fifth, I refresh on onResume() or when the lifecycle hits STARTED, so the feed is never stale just because the user left the app for a few minutes. The model that ties all of this together is stale-while-revalidate: show cached data immediately, refresh in the background, and let Room's Flow deliver the update automatically when it arrives."
