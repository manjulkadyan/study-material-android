10.1 Networking

HTTP Basics

🎤 Say it out loud (~30–45s): "HTTP is a stateless request/response protocol over TCP — each call carries everything the server needs, there's no session memory between requests. On Android the thing I always call out is that networking can never touch the main thread or you get a NetworkOnMainThreadException, and that error status codes like 404 or 500 aren't exceptions in OkHttp — the request succeeded, so I still have to check isSuccessful. The other nuance interviewers probe is idempotency: GET/PUT/DELETE are safe to retry, but POST isn't, which is why retry logic has to be method-aware."

HTTP is a stateless request/response protocol running over TCP/IP — every call is independent, no session memory, and every Android network call goes over HTTP or HTTPS.

Methods and semantics:

Method Safe Idempotent Has Body Use
GETYesYesNoFetch resource
POSTNoNoYesCreate resource
PUTNoYesYesReplace resource
PATCHNoNoYesPartial update
DELETENoYesNoRemove resource
HEADYesYesNoFetch headers only

Status code families:

  • 1xx — Informational (100 Continue, 101 Switching Protocols)
  • 2xx — Success (200 OK, 201 Created, 204 No Content)
  • 3xx — Redirection (301 Moved Permanently, 304 Not Modified)
  • 4xx — Client errors (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests)
  • 5xx — Server errors (500 Internal, 503 Service Unavailable, 504 Gateway Timeout)

Headers that matter on Android:

  • Content-Type: application/json — request/response body type
  • Authorization: Bearer <token> — auth header
  • Cache-Control — caching directives
  • ETag / If-None-Match — conditional requests for cache validation
  • Last-Modified / If-Modified-Since — time-based conditional requests
  • Accept-Encoding: gzip — OkHttp adds this automatically; saves 60–80% bandwidth
  • Connection: keep-alive — persistent connections (HTTP/1.1 default)

HTTP/2 benefits: multiplexed streams over single TCP connection (no head-of-line blocking at HTTP layer), header compression (HPACK), server push. OkHttp supports HTTP/2 automatically when server supports it.

Under the hood

An HTTP request is fundamentally just text written onto a TCP socket — a request line, CRLF-delimited headers, a blank line, then the optional body. HTTP/1.1 keeps the socket open (keep-alive) so the next request reuses the same TCP+TLS handshake, but responses on one connection are strictly serialized, which is HTTP-layer head-of-line blocking. HTTP/2 fixes this by framing: the single connection is split into a binary frame layer carrying interleaved HEADERS and DATA frames tagged with stream IDs, so many logical requests multiplex concurrently, and HPACK compresses headers against a shared dynamic table so repeated headers (cookies, auth) cost only an index reference.

GET /users/42 HTTP/1.1\r\n
Host: api.example.com\r\n
Authorization: Bearer eyJ...\r\n
Accept-Encoding: gzip\r\n
\r\n                          <- blank line ends headers, no body for GET

Because the gzip is transparent (OkHttp adds Accept-Encoding: gzip and inflates the response itself), Content-Length reflects the compressed bytes on the wire while your code sees the decompressed stream.

Android implications: All network operations must be off the main thread. NetworkOnMainThreadException is thrown if you try. OkHttp uses a thread pool internally; Retrofit bridges to coroutines/RxJava.

REST Principles

🎤 Say it out loud (~30–45s): "REST is an architectural style, not a protocol — Fielding's six constraints, the big ones being statelessness, a uniform resource-oriented interface, and cacheability. In practice I model URIs as nouns and let HTTP verbs carry the action, so GET /users/42 and DELETE /users/42 instead of RPC-style endpoints. The honest nuance is that almost nobody implements HATEOAS — the hypermedia constraint — so most 'RESTful' APIs are really REST-ish, and the real trade-off versus GraphQL is round-trips: REST gives you dead-simple HTTP caching but N+1 fetches for nested data."

REST is an architectural style, not a protocol — it's Roy Fielding's set of six constraints that, when followed, produce a scalable, loosely coupled web API. The constraints are:

  1. Client-Server: Separation of UI from data storage
  2. Stateless: Each request contains all context — no server-side session
  3. Cacheable: Responses must declare themselves cacheable or not
  4. Uniform Interface: Standard resource identification (URI), manipulation through representations, self-descriptive messages, HATEOAS (often skipped in practice)
  5. Layered System: Client doesn't know if it's talking to an origin server or proxy
  6. Code on Demand (optional): Server can send executable code

Resource modeling:

GET    /users/{id}          — fetch user
POST   /users               — create user
PUT    /users/{id}          — replace user
PATCH  /users/{id}          — partial update
DELETE /users/{id}          — delete user
GET    /users/{id}/orders   — sub-resource

Trade-offs vs GraphQL:

  • REST: multiple round-trips for nested data (N+1), simple caching
  • GraphQL: single round-trip, precise data fetching, complex caching (no HTTP caching by default)

Under the hood

REST isn't enforced by any library — it's a discipline layered on top of plain HTTP, so "under the hood" REST is just HTTP semantics used correctly. The constraints map directly to mechanics: statelessness means no server affinity, so a load balancer can route consecutive requests from the same client to different backend instances with no sticky-session table — that's what makes horizontal scaling cheap. Cacheability is implemented entirely through HTTP headers (Cache-Control, ETag, Last-Modified), letting any intermediary — CDN, proxy, or OkHttp's Cache — serve a 304 Not Modified without hitting origin. The "uniform interface" is why a generic client like Retrofit can talk to any REST API: the contract is the HTTP method + URI + media type, not a per-server RPC stub. GraphQL breaks the caching constraint precisely because every query is a POST to a single /graphql endpoint, so the URL is no longer a cache key and HTTP intermediaries can't reason about it.

JSON Serialization

🎤 Say it out loud (~30–45s): "JSON serialization converts between objects and JSON text, and on Android the modern choices are Moshi and kotlinx.serialization, with Gson as the legacy option I'm trying to migrate off. The key reason I avoid Gson is that it's reflection-based and Kotlin-unaware — it'll happily put null into a non-null Kotlin field and bypass the type system, blowing up later with an NPE. Moshi codegen and kotlinx.serialization both generate adapters at compile time, so they're faster and respect nullability and default values, which is what actually protects me when an API adds or drops a field."

JSON serialization is the process of converting between Kotlin/Java objects and JSON strings — and on Android there are two dominant modern approaches, plus one legacy one to know about:

Gson (Google, legacy):

val gson = Gson()
val json = gson.toJson(user)       // serialize
val user = gson.fromJson(json, User::class.java)  // deserialize

Problems: uses reflection, no null safety for Kotlin, poor performance on large payloads.

Moshi (Square, modern):

val moshi = Moshi.Builder()
    .addLast(KotlinJsonAdapterFactory())  // reflection adapter, or use codegen
    .build()
val adapter = moshi.adapter(User::class.java)
val json = adapter.toJson(user)
val user = adapter.fromJson(json)

Codegen with @JsonClass(generateAdapter = true) — faster than reflection, null-safe, Kotlin-idiomatic.

Kotlinx.serialization (JetBrains, newest):

@Serializable
data class User(val id: Int, val name: String)

val json = Json.encodeToString(User(1, "Alice"))
val user = Json.decodeFromString<User>(json)

Compile-time code generation, no reflection, first-class Kotlin support, excellent performance.

Key serialization concerns on Android:

  • Unknown fields: Moshi ignores by default; @JsonClass codegen does too. Gson silently ignores. Important for API versioning.
  • Null vs missing field: JSON null vs field absence — Kotlin default parameters handle absence; explicit null annotations handle null.
  • Custom adapters: For Date, BigDecimal, sealed classes, polymorphism.
  • Performance: Reflection-based is 2–5x slower than codegen; matters for lists with 1000+ items.

Retrofit + Moshi:

val retrofit = Retrofit.Builder()
    .baseUrl("https://api.example.com/")
    .addConverterFactory(MoshiConverterFactory.create(moshi))
    .client(okHttpClient)
    .build()

Under the hood

The split that explains everything is reflection vs codegen. Gson and Moshi's KotlinJsonAdapterFactory walk your class at runtime with java.lang.reflect/kotlin-reflect, reading field metadata and using Field.setAccessible(true) to write values directly — which is why Gson can violate Kotlin's non-null contract: it never calls the constructor, so the compiler-injected Intrinsics.checkNotNull null check never runs, and a JSON null silently lands in a non-null field. Moshi codegen (@JsonClass(generateAdapter = true)) and kotlinx.serialization instead run an annotation processor / compiler plugin at build time that emits a concrete adapter class (e.g. UserJsonAdapter) with hand-written fromJson/toJson that read tokens off a streaming JsonReader and call the real constructor — so nullability and default-parameter handling are baked in, and there's no reflection cost per object.

// What Moshi codegen emits (simplified): a streaming, reflection-free reader
override fun fromJson(reader: JsonReader): User {
    var id: Int? = null; var name: String? = null
    reader.beginObject()
    while (reader.hasNext()) when (reader.selectName(NAMES)) {
        0 -> id = intAdapter.fromJson(reader)
        1 -> name = stringAdapter.fromJson(reader)
        -1 -> { reader.skipName(); reader.skipValue() }  // unknown field skipped
    }
    reader.endObject()
    return User(id ?: throw JsonDataException("id missing"), name ?: ...)
}

kotlinx.serialization goes further: its compiler plugin generates a KSerializer plus an integer bitmask tracking which fields were present in the JSON, so it can distinguish "absent" (use the default) from "explicit null" without reflection at all.

OkHttp

🎤 Say it out loud (~30–45s): "OkHttp is the actual HTTP engine under Retrofit — it owns the connection pool, the disk cache, and the interceptor chain. The two pieces I lean on are connection reuse, where it keeps a pool of warm TCP/TLS connections so I'm not paying handshake cost on every call, and the Dispatcher, which caps concurrency at 64 total and 5 per host. The gotcha I always mention is that a 4xx or 5xx response is still a successful Response object — OkHttp only throws for transport-level failures like timeouts or DNS, so I have to check response.isSuccessful myself."

OkHttp is the HTTP client that lives underneath Retrofit — it manages connections, the request/response lifecycle, and the interceptor chain that lets you inject middleware at every call.

Internals:

  • Dispatcher: Manages async call execution. Default: 64 max concurrent requests, 5 per host. Backed by ExecutorService.
  • ConnectionPool: Reuses TCP connections. Default: 5 connections, 5-minute keep-alive.
  • Cache: Disk-backed HTTP cache using DiskLruCache.
  • Interceptor chain: Each interceptor calls chain.proceed() to pass to the next. Application interceptors run before caching; network interceptors run after.

Basic setup:

val okHttpClient = OkHttpClient.Builder()
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(30, TimeUnit.SECONDS)
    .writeTimeout(30, TimeUnit.SECONDS)
    .cache(Cache(cacheDir, 10 * 1024 * 1024)) // 10MB cache
    .addInterceptor(loggingInterceptor)
    .addInterceptor(authInterceptor)
    .authenticator(tokenRefreshAuthenticator)
    .build()

Call lifecycle:

  1. client.newCall(request) creates a RealCall
  2. call.enqueue(callback) dispatches to Dispatcher thread pool
  3. Interceptor chain executes: application interceptors → cache → network interceptors → server
  4. Response flows back through the chain

Failure modes:

  • ConnectException — cannot reach host
  • SocketTimeoutException — timeout hit
  • SSLHandshakeException — TLS failure
  • UnknownHostException — DNS failure
  • Response with error status code — NOT an exception in OkHttp; must check response.isSuccessful

Under the hood

A RealCall runs the request through a fixed, ordered list of interceptors assembled in getResponseWithInterceptorChain(), ending with built-in ones you never see: the RetryAndFollowUpInterceptor (re-routes and follows redirects/auth challenges), BridgeInterceptor (adds Host, Accept-Encoding: gzip, cookies), CacheInterceptor (serves/validates from DiskLruCache), ConnectInterceptor (opens or borrows a socket from the pool), and finally CallServerInterceptor (writes the request bytes and reads the response). The RealInterceptorChain is the mechanism: each interceptor receives an immutable chain index and calls proceed(), which constructs the next chain node — that's why every interceptor is guaranteed to run exactly one downstream proceed().

RealCall.execute()
 └─ RealInterceptorChain.proceed(request)   // index 0
     ├─ [your application interceptors]      // see uncached request
     ├─ RetryAndFollowUpInterceptor
     ├─ BridgeInterceptor                     // gzip, cookies, Content-Length
     ├─ CacheInterceptor                      // may short-circuit with 304/cached body
     ├─ ConnectInterceptor                    // ConnectionPool: reuse or new socket
     ├─ [your network interceptors]           // only run if we actually hit the wire
     └─ CallServerInterceptor                 // socket write + read

The ConnectionPool keys idle connections by route (host + proxy + TLS config) and reaps them with a background cleanup task after the 5-minute keep-alive; HTTP/2 connections are special-cased so multiple concurrent calls to the same host share one socket via stream multiplexing instead of taking separate pool slots.

Retrofit

🎤 Say it out loud (~30–45s): "Retrofit turns an annotated Kotlin interface into a working HTTP client — I describe endpoints declaratively and it generates the implementation at runtime via a dynamic proxy. Under the hood it's a thin layer over OkHttp: a Converter handles serialization and a CallAdapter bridges OkHttp's Call to coroutines or RxJava. The thing I'm deliberate about is the return type — a bare User makes Retrofit throw HttpException on any non-2xx, whereas Response<User> hands me the status code and headers so I can handle errors gracefully instead of catching exceptions."

Retrofit is a type-safe HTTP client that turns annotated Kotlin interfaces into working HTTP calls, using OkHttp as the transport layer underneath.

Interface definition:

interface UserApi {
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: String): User

    @GET("users")
    suspend fun getUsers(
        @Query("page") page: Int,
        @Query("limit") limit: Int
    ): PagedResponse<User>

    @POST("users")
    suspend fun createUser(@Body user: CreateUserRequest): User

    @PATCH("users/{id}")
    suspend fun updateUser(
        @Path("id") id: String,
        @Body update: UpdateUserRequest
    ): User

    @DELETE("users/{id}")
    suspend fun deleteUser(@Path("id") id: String): Response<Unit>

    @GET("users")
    suspend fun getUsersRaw(): Response<List<User>>  // wrap in Response<T> for status code access

    @Multipart
    @POST("uploads")
    suspend fun uploadFile(
        @Part file: MultipartBody.Part,
        @Part("description") description: RequestBody
    ): UploadResponse

    @Headers("Cache-Control: no-cache")
    @GET("feed")
    suspend fun getFeed(): List<FeedItem>
}

Suspend functions: Retrofit 2.6+ natively supports suspend fun with coroutines. The call runs on a background thread managed by OkHttp's Dispatcher; no manual thread switching needed.

Response<T> vs plain T:

  • T directly: Retrofit throws HttpException for non-2xx; good for simple cases
  • Response<T>: gives access to status code, headers, raw body; handle non-2xx yourself

Retrofit internals: Uses CallAdapter to convert OkHttp Call<T> to coroutine/RxJava. Uses Converter (Moshi/Gson/etc.) to serialize/deserialize bodies. Generates proxy objects via Java Proxy.newProxyInstance using the interface annotations.

Dynamic URLs:

@GET
suspend fun getFromUrl(@Url url: String): SomeResponse

Under the hood

Retrofit.create() calls Proxy.newProxyInstance, which generates a synthetic class implementing your interface; every method call is funneled into a single InvocationHandler.invoke(). On first call for a method, Retrofit parses its annotations into a cached ServiceMethod/HttpServiceMethod (URL template, parameter handlers, the Converter, and the matching CallAdapter), so the reflection cost is paid once per method and memoized. The suspend support is a compiler trick, not magic: the Kotlin compiler rewrites a suspend fun getUser(): User into a JVM method with a hidden trailing Continuation parameter and an erased Object return type. Retrofit detects that last Continuation argument and adapts OkHttp's async enqueue callback into continuation.resume(...) / resumeWithException(...), which is how the coroutine is resumed off the OkHttp dispatcher thread.

api.getUser("42")
  → Proxy InvocationHandler.invoke(method, args)
  → loadServiceMethod(method)          // cached ServiceMethod (parsed once)
  → HttpServiceMethod.invoke(args)
  → builds okhttp3.Request via Converter + parameter handlers
  → CallAdapter wraps Call; suspend variant suspendCancellableCoroutine { call.enqueue { resume } }

The @Path/@Query/@Body annotations become ParameterHandler objects that each know how to apply one argument to the RequestBuilder in order — @Path does URL-segment substitution with encoding, @Query appends to the query string, and @Body runs the argument through the response converter to produce the request RequestBody.

Interceptors

🎤 Say it out loud (~30–45s): "Interceptors are middleware in OkHttp's chain — each one gets the request, can mutate it, calls chain.proceed(), and can then inspect the response coming back. The distinction I always draw is application versus network interceptors: an application interceptor runs exactly once even if the response is served from cache, which makes it the right place for auth headers and logging, while a network interceptor only fires on actual wire traffic. The big gotcha is that interceptors are synchronous and run on OkHttp's pool, so I never do blocking token refresh inside one — that's what the Authenticator is for, since it reacts to a 401 and isn't part of the chain."

Interceptors are middleware in the OkHttp chain — each one receives a Chain, can inspect or modify the request, calls chain.proceed() to pass it along, and can then inspect or modify the response on the way back.

Two types:

  • addInterceptor (application interceptors): Runs once, even for cached responses. Good for: auth headers, logging, retry logic.
  • addNetworkInterceptor (network interceptors): Runs only for actual network calls, not for cached responses. Good for: request/response body rewriting, monitoring actual bytes sent/received.

Logging interceptor:

val logging = HttpLoggingInterceptor().apply {
    level = if (BuildConfig.DEBUG) 
        HttpLoggingInterceptor.Level.BODY 
    else 
        HttpLoggingInterceptor.Level.NONE
}

Critical: Never log request/response bodies in production — bodies can contain tokens, PII, PHI.

Auth header interceptor:

class AuthInterceptor(private val tokenProvider: TokenProvider) : Interceptor {
    override fun intercept(chain: Chain): Response {
        val token = tokenProvider.getAccessToken() // synchronous, from memory/prefs
        val request = chain.request().newBuilder()
            .header("Authorization", "Bearer $token")
            .build()
        return chain.proceed(request)
    }
}

Retry interceptor:

class RetryInterceptor(private val maxRetries: Int = 3) : Interceptor {
    override fun intercept(chain: Chain): Response {
        var attempt = 0
        var response: Response
        do {
            if (attempt > 0) {
                Thread.sleep(2.0.pow(attempt).toLong() * 100) // exponential backoff
            }
            response = chain.proceed(chain.request())
            attempt++
        } while (!response.isSuccessful && isRetryable(response.code) && attempt < maxRetries)
        return response
    }

    private fun isRetryable(code: Int) = code == 503 || code == 504 || code == 429
}

Order matters: Interceptors are called in the order added. Typical order: logging → auth → retry.

Under the hood

The "chain" is a linked walk through OkHttp's interceptor list implemented by RealInterceptorChain: calling chain.proceed(request) builds a new chain instance with index + 1 and invokes the next interceptor's intercept(), returning its Response up the stack. This is why ordering is positional — your application interceptors sit at the front of the list (before the built-in cache and connect interceptors), so they see the logical request and the final response regardless of whether the body came from DiskLruCache or the network, while network interceptors are inserted after ConnectInterceptor and only execute when a real socket is in play. The chain is strictly synchronous and single-threaded per call — intercept() blocks the OkHttp dispatcher thread until proceed() returns — so a retry interceptor's Thread.sleep parks a pooled worker, and any blocking I/O (like a network token refresh) inside an interceptor stalls that thread.

proceed(req) at index i  →  interceptors[i].intercept(chainAtIndex i+1)
                                     │
                                     └─ (interceptor body) ─ chain.proceed(req') ─┐
                                                                                  ▼
                                                          proceed(req') at index i+1 ...

Auth refresh is deliberately not done in the chain: OkHttp's Authenticator is a separate callback the RetryAndFollowUpInterceptor invokes only after it sees a 401, letting it attach fresh credentials and replay the request — which avoids racing multiple interceptor copies trying to refresh a token at once.

Authentication and Token Refresh

🎤 Say it out loud (~30–45s): "When an access token expires the server hands back a 401, and I want to silently refresh and replay the original request so the user never sees an error. I'd hang that off OkHttp's Authenticator, because it's the framework's built-in 401 hook — it re-runs my code and lets me return a new request to retry. The gotcha interviewers always probe is the thundering-herd race: if several requests 401 at once you can fire several refreshes and burn a single-use refresh token, so I guard the refresh with a Mutex plus a double-check that compares the stored token against the one that failed, so only the first caller actually hits the auth endpoint."

Most APIs hand you a short-lived access token and a long-lived refresh token. When the access token expires and you get a 401, the client has to silently obtain a new one and replay the original request — all without the user noticing.

The race condition problem: If 3 requests fire simultaneously and all get 401, you don't want 3 concurrent token refresh calls — that's wasteful and may break some OAuth providers (refresh tokens are often single-use).

Safe single-flight token refresh with OkHttp Authenticator:

class TokenRefreshAuthenticator(
    private val tokenRepository: TokenRepository,
    private val authApi: AuthApi
) : Authenticator {

    // Mutex ensures only one refresh happens at a time
    private val refreshMutex = Mutex()

    override fun authenticate(route: Route?, response: Response): Request? {
        // If we've already retried once for this request chain, give up
        if (response.request.header("Authorization-Retried") != null) {
            return null // return null to propagate 401 to caller
        }

        // runBlocking is acceptable here — Authenticator is called from OkHttp's
        // IO thread pool, never the main thread
        val newToken = runBlocking {
            refreshMutex.withLock {
                // Double-check: another thread may have already refreshed
                val currentToken = tokenRepository.getAccessToken()
                val requestToken = response.request
                    .header("Authorization")
                    ?.removePrefix("Bearer ")

                if (currentToken != null && currentToken != requestToken) {
                    // Token was already refreshed by another thread — reuse it
                    currentToken
                } else {
                    // We need to actually refresh
                    try {
                        val refreshToken = tokenRepository.getRefreshToken()
                            ?: return@withLock null
                        val refreshResponse = authApi.refresh(RefreshRequest(refreshToken))
                        tokenRepository.saveTokens(refreshResponse.accessToken, refreshResponse.refreshToken)
                        refreshResponse.accessToken
                    } catch (e: Exception) {
                        tokenRepository.clearTokens()
                        null // triggers logout
                    }
                }
            }
        } ?: return null // null = don't retry, propagate 401

        return response.request.newBuilder()
            .header("Authorization", "Bearer $newToken")
            .header("Authorization-Retried", "true")
            .build()
    }
}

Key details:

  • Authenticator is only invoked on 401 Unauthorized (not 403).
  • Returning null from authenticate() stops retrying and propagates the 401.
  • The Mutex (from kotlinx.coroutines) is a non-reentrant coroutine-safe lock.
  • The "double-check" idiom (compare stored token to the one that failed) avoids a redundant refresh when two requests get 401 simultaneously.
  • runBlocking is intentional here — Authenticator.authenticate() is a synchronous interface.
  • For the authApi client used inside the authenticator, use a separate OkHttpClient without the authenticator to avoid infinite loops.

Alternative: Interceptor-based approach (less standard but used when 401 doesn't reliably trigger Authenticator):

class TokenRefreshInterceptor(
    private val tokenRepository: TokenRepository,
    private val authApi: AuthApi
) : Interceptor {
    private val refreshMutex = Mutex()

    override fun intercept(chain: Chain): Response {
        val response = chain.proceed(chain.request())
        if (response.code != 401) return response

        response.close() // Must close before proceeding again

        val newToken = runBlocking {
            refreshMutex.withLock {
                val current = tokenRepository.getAccessToken()
                val failed = chain.request().header("Authorization")?.removePrefix("Bearer ")
                if (current != null && current != failed) {
                    current
                } else {
                    val refresh = tokenRepository.getRefreshToken() ?: return@withLock null
                    try {
                        val r = authApi.refresh(RefreshRequest(refresh))
                        tokenRepository.saveTokens(r.accessToken, r.refreshToken)
                        r.accessToken
                    } catch (e: Exception) {
                        null
                    }
                }
            }
        } ?: return response

        return chain.proceed(
            chain.request().newBuilder()
                .header("Authorization", "Bearer $newToken")
                .build()
        )
    }
}

Failure modes:

  • Refresh token is also expired → clear tokens, emit logout event (use a SharedFlow or similar event bus).
  • Infinite loop if the auth endpoint itself returns 401 → guard with separate OkHttpClient or check URL.
  • Race condition if Mutex is not used → multiple refreshes, tokens overwritten with stale data.

Under the hood

Authenticator is not an interceptor — it lives in a different stage of the call. OkHttp's RetryAndFollowUpInterceptor runs the request, and only when it sees a 401 (or 407 for proxies, which routes to proxyAuthenticator) does it call Authenticator.authenticate() to build a follow-up request. If you return a non-null Request, OkHttp loops back and re-executes the entire interceptor chain with it; if you return null, the 401 response is returned to the caller untouched. OkHttp caps these follow-ups at MAX_FOLLOW_UPS = 20, which is the framework-level loop guard, but you should still add your own (the Authorization-Retried header above) because the auth endpoint itself could 401 and chew through all 20.

The Mutex is the real mechanism behind single-flight. kotlinx.coroutines' Mutex is not a JVM monitor — it's a suspending lock backed by a CAS on an internal state field plus a lock-free queue of waiting continuations. The first coroutine wins the CAS and runs the refresh; the others suspend (no thread blocked) and resume in FIFO order after unlock(), at which point the double-check sees the freshly stored token and skips the network call.

RealCall.execute()
  └─ RetryAndFollowUpInterceptor   ← sees 401, calls authenticator, loops (max 20)
       └─ BridgeInterceptor        ← adds Host, gzip, cookies
            └─ CacheInterceptor
                 └─ ConnectInterceptor
                      └─ CallServerInterceptor  ← writes/reads socket → Response(code=401)

Timeouts

🎤 Say it out loud (~30–45s): "OkHttp doesn't have one timeout — it has separate timeouts for each phase: connect to establish the TCP and TLS handshake, write to upload the body, and read which is the gap between bytes from the server, not the total response time. That last point trips people up: readTimeout resets on every chunk, so a slow trickle never trips it, which is why for a hard upper bound you want callTimeout, the end-to-end limit covering retries and redirects. I tune them per workload — long read timeout for streaming, long write timeout for file uploads — usually by spinning a dedicated client off newBuilder() so I don't bloat the global one."

Timeouts are limits on how long OkHttp is willing to wait at each phase of an HTTP call — connect, read, and write are each configurable independently.

Three timeout types:

  • connectTimeout: Time to establish TCP connection. Default: 10s. Set to 10–15s.
  • readTimeout: Time to wait for data between bytes from server. Default: 10s. For long-polling or streaming, increase significantly.
  • writeTimeout: Time to upload request body. Default: 10s. Increase for file uploads.
  • callTimeout (OkHttp 3.11+): End-to-end timeout for entire call including retries and redirects.

Per-request timeout override:

// OkHttp supports per-call timeouts via the Call API
val call = okHttpClient.newBuilder()
    .readTimeout(60, TimeUnit.SECONDS)
    .build()
    .newCall(request)

With Retrofit, use a custom CallAdapter or create dedicated client instances for long operations.

Failure modes:

  • SocketTimeoutException — read or write timeout hit
  • ConnectException — connect timeout hit (or refused)
  • Setting timeouts too high → users wait forever; too low → flaky on slow connections
  • File uploads need higher write timeout; video playback needs higher read timeout

Under the hood

connect/read/write timeouts are pushed down to the underlying socket: OkHttp sets Socket.setSoTimeout() and uses Okio's Timeout/AsyncTimeout on the source and sink. These are per-I/O-operation timers — each read() on the socket arms a timer for readTimeout, and a single byte arriving disarms and re-arms it. That's why a server dribbling one byte every 9 seconds never trips a 10s read timeout: the clock is between bytes, not over the whole body.

callTimeout is implemented completely differently. It's not a socket option — it's an AsyncTimeout scheduled on a watchdog thread when RealCall starts. When that deadline elapses the watchdog calls cancel() on the call, which closes the connection and surfaces as an InterruptedIOException ("timeout"). Because it wraps the entire chain, it's the only timeout that bounds redirects, the Authenticator retry loop, and connection acquisition combined.

// Conceptually, per-operation socket timeouts vs. a single wall-clock cap:
socket.soTimeout = readTimeoutMillis      // re-armed on every read()
AsyncTimeout.scheduleAt(now + callTimeout) // one-shot, cancels the whole RealCall

Retries

🎤 Say it out loud (~30–45s): "My rule is: retry only what's transient and only what's safe. Transient means 5xx, 429, and IOExceptions like dropped connections — never a 4xx like 400 or 401, because retrying a client error just hammers the server with the same broken request. Safe means idempotent: GET is fine to retry blindly, but a POST that creates a resource I won't auto-retry unless the server honors a client-generated idempotency key, otherwise I create duplicates. And I always use exponential backoff with jitter — without the random jitter, a fleet of clients that all failed at once retries in lockstep and synchronizes into a thundering herd that takes the server down again."

Retries are automatic re-attempts of a failed request — the goal is to recover from transient failures transparently, without the user ever seeing an error.

What to retry:

  • 5xx (except 501) — transient server failures
  • 429 Too Many Requests — rate limit (respect Retry-After header)
  • Network errors (IOException) — connection drops, DNS failures
  • Never retry 4xx except 429 — 400/401/403/404 are client errors; retrying won't help

Exponential backoff with jitter:

class RetryInterceptor(
    private val maxAttempts: Int = 3,
    private val initialDelayMs: Long = 100
) : Interceptor {

    override fun intercept(chain: Chain): Response {
        val request = chain.request()
        var attempt = 0
        var lastResponse: Response? = null

        while (attempt < maxAttempts) {
            if (attempt > 0) {
                lastResponse?.close()
                val delayMs = initialDelayMs * (1L shl (attempt - 1)) + Random.nextLong(0, 100)
                Thread.sleep(delayMs)
            }
            try {
                val response = chain.proceed(request)
                if (response.isSuccessful || !shouldRetry(response.code)) {
                    return response
                }
                lastResponse = response
            } catch (e: IOException) {
                if (attempt == maxAttempts - 1) throw e
            }
            attempt++
        }
        return lastResponse!!
    }

    private fun shouldRetry(code: Int) = code == 429 || code in 500..599 && code != 501
}

Idempotency and retries: Only retry idempotent operations automatically. For POST (non-idempotent creates), require explicit user confirmation or use a client-generated idempotency key.

OkHttp built-in retries: OkHttp itself retries on connection failures (not on HTTP errors). This is controlled by retryOnConnectionFailure(true) (default). It does NOT retry on 5xx.

Under the hood

OkHttp's native retry lives in RetryAndFollowUpInterceptor and only fires on connection-level IOExceptions, gated by recover(). recover() returns false (rethrows) for things that won't get better by retrying: a ProtocolException, a non-SocketTimeoutException after the request body was already sent, certain TLS handshake failures (SSLPeerUnverifiedException), or when there's no further Route to try. When there are multiple DNS results or proxy routes, RouteSelector hands the next candidate to the retry, which is why a single enqueue() can transparently fail over to a second IP — it never re-runs your application interceptors, so your code doesn't see it.

A custom RetryInterceptor like the one above sits in the application interceptor layer, so each chain.proceed() re-runs the whole network stack and is the only place you can retry on HTTP status codes. The bit-shift 1L shl (attempt - 1) is just 2^(attempt-1) — exponential growth — and Random.nextLong(0, 100) is the jitter that de-correlates clients. Note this implementation uses Thread.sleep, which is fine because OkHttp dispatches the call on its Dispatcher's ExecutorService thread, never the main thread; doing the same in a coroutine should use delay() so it suspends instead of pinning a thread.

backoff:  100ms · 2^0 + jitter → ~100–200ms
          100ms · 2^1 + jitter → ~200–300ms
          100ms · 2^2 + jitter → ~400–500ms
jitter prevents N clients that failed at T0 from all retrying at exactly T0+200ms

Caching

🎤 Say it out loud (~30–45s): "OkHttp ships a full HTTP cache that's driven by response headers — Cache-Control max-age for freshness and ETag/Last-Modified for revalidation — and it's completely transparent to the app, so a GET that's still fresh never touches the network. The key distinction I draw is fresh vs. stale-but-revalidatable: when something expires, OkHttp doesn't refetch blindly, it sends a conditional If-None-Match and the server can answer 304 Not Modified with no body, saving bandwidth. The trap is using HTTP caching for mutable data like a user feed — for offline-first I reach for Room as the source of truth instead, because HTTP caching is opaque and I can't query or selectively invalidate it."

HTTP caching means storing responses locally so you can skip the network entirely for data you've already fetched recently.

HTTP cache headers:

  • Cache-Control: max-age=300 — cache for 5 minutes
  • Cache-Control: no-cache — revalidate with server before using
  • Cache-Control: no-store — never cache
  • Cache-Control: public — any cache may store
  • Cache-Control: private — only client cache
  • ETag: "abc123" — version token; client sends If-None-Match: "abc123" → server returns 304 if unchanged
  • Last-Modified: Thu, 01 Jan 2026 00:00:00 GMT — time-based equivalent

OkHttp cache setup:

val cache = Cache(
    directory = File(context.cacheDir, "http_cache"),
    maxSize = 50L * 1024 * 1024 // 50 MB
)

val client = OkHttpClient.Builder()
    .cache(cache)
    .build()

Force cache / force network:

// Only use cache, fail if not cached
request.newBuilder()
    .cacheControl(CacheControl.FORCE_CACHE)
    .build()

// Only use network, ignore cache
request.newBuilder()
    .cacheControl(CacheControl.FORCE_NETWORK)
    .build()

Offline-mode pattern:

class CacheInterceptor(private val context: Context) : Interceptor {
    override fun intercept(chain: Chain): Response {
        val request = if (!context.isNetworkAvailable()) {
            chain.request().newBuilder()
                .cacheControl(CacheControl.Builder()
                    .onlyIfCached()
                    .maxStale(7, TimeUnit.DAYS)
                    .build())
                .build()
        } else {
            chain.request()
        }
        return chain.proceed(request)
    }
}

Trade-offs:

  • HTTP cache is appropriate for GET requests with stable data
  • For mutable data (feed, user profile), prefer Room as the cache (offline-first) over HTTP cache
  • HTTP cache is transparent to the app; Room cache is explicit and controllable

Under the hood

The cache is a DiskLruCache on disk: each entry is keyed by an MD5 hash of the request URL and stored as two files — one for the serialized headers/metadata, one for the raw response body — with a journal file tracking the LRU ordering so eviction stays under maxSize. CacheInterceptor is the decision point. On each call it runs CacheStrategy, which compares the cached response's freshness lifetime (from max-age/Expires minus current age) against now and produces one of three outcomes: serve the cached response directly (a cache hit, network request is null), make a conditional network request, or go fully to the network.

The 304 path is where the savings come from. When an entry is stale but carries a validator, CacheStrategy builds a request with If-None-Match: <etag> (or If-Modified-Since). If the server replies 304 Not Modified, OkHttp discards the empty network body, merges the new headers onto the stored entry, refreshes its timestamps, and returns the cached body — so the bytes never re-download. FORCE_CACHE sets onlyIfCached and synthesizes a 504 Unsatisfiable Request if nothing is cached; FORCE_NETWORK sets no-cache so the validation/serve-from-disk branch is skipped entirely.

CacheStrategy outcomes:
  networkRequest == null && cacheResponse != null  → HIT, return from DiskLruCache
  networkRequest != null && cacheResponse != null  → CONDITIONAL GET (If-None-Match)
                                                       └─ 304 → return cached, refresh headers
                                                       └─ 200 → replace entry
  networkRequest != null && cacheResponse == null   → MISS, full network fetch
  networkRequest == null && cacheResponse == null   → 504 (onlyIfCached, nothing stored)

Pagination

🎤 Say it out loud (~30–45s): "Pagination fetches a big list in chunks instead of all at once. The decision I always call out is offset vs. cursor: offset/limit is simple and lets you jump to an arbitrary page, but it's unstable — if rows are inserted or deleted while the user scrolls, items shift and you get duplicates or skips. Cursor-based (keyset) pagination encodes the last item's sort key, so it's stable for live feeds at the cost of not being able to random-access a page. On Android I'd reach for Paging 3 with a PagingSource, and RemoteMediator when I want it backed by Room for offline; the library handles prefetch, in-flight de-duplication, and exposing load states to the UI so I'm not reinventing that."

Pagination is the pattern of fetching a large dataset in manageable chunks rather than pulling everything at once — critical for feeds, search results, or any list that could grow unbounded.

Three pagination strategies:

1. Offset/Limit (page-based):

GET /posts?page=2&limit=20

Problem: If items are inserted/deleted between pages, you get duplicate or skipped items.

2. Cursor-based (keyset):

GET /posts?after=cursor_opaque_string&limit=20

The cursor encodes the last item's sort key (e.g., base64(id + timestamp)). Stable for real-time feeds. Cannot jump to arbitrary pages.

3. Timestamp-based:

GET /posts?before=2026-01-01T00:00:00Z&limit=20

Variant of cursor; natural for time-ordered feeds.

Paging 3 library (the standard Android approach):

// PagingSource for network-only
class PostPagingSource(
    private val api: PostApi
) : PagingSource<String, Post>() {

    override fun getRefreshKey(state: PagingState<String, Post>): String? {
        return state.anchorPosition?.let { anchor ->
            state.closestItemToPosition(anchor)?.id
        }
    }

    override suspend fun load(params: LoadParams<String>): LoadResult<String, Post> {
        return try {
            val cursor = params.key
            val response = api.getPosts(cursor = cursor, limit = params.loadSize)
            LoadResult.Page(
                data = response.items,
                prevKey = null, // can't go back
                nextKey = response.nextCursor
            )
        } catch (e: Exception) {
            LoadResult.Error(e)
        }
    }
}

// RemoteMediator for network + Room cache (covered in 10.3)
// ViewModel
val pager = Pager(
    config = PagingConfig(pageSize = 20, enablePlaceholders = false),
    pagingSourceFactory = { PostPagingSource(api) }
).flow.cachedIn(viewModelScope)

// UI
val lazyItems = viewModel.pager.collectAsLazyPagingItems()
LazyColumn {
    items(lazyItems) { item ->
        PostItem(item)
    }
    lazyItems.apply {
        when {
            loadState.refresh is LoadState.Loading -> LoadingSpinner()
            loadState.append is LoadState.Loading -> PageLoadingSpinner()
            loadState.append is LoadState.Error -> RetryButton { retry() }
        }
    }
}

Under the hood

Paging 3 is built around a PageFetcher that owns the active PagingSource and emits a stream of PagingData. As the UI scrolls, collectAsLazyPagingItems() reports the accessed index back through a PagingDataPresenter; when that index gets within prefetchDistance of either edge of the loaded window, the fetcher invokes your suspend load() with LoadParams.Append or LoadParams.Prepend, carrying the nextKey/prevKey you returned from the previous page. It serializes these so only one append and one prepend are ever in flight, which is the in-flight de-duplication you get for free. With enablePlaceholders = true, it knows total count and emits null items for unloaded positions; with it off, the list simply grows.

cachedIn(viewModelScope) is what makes the stream survive configuration changes: it multicasts the PagingData through a SharedFlow-style operator tied to the scope, so a rotation re-collects the already-loaded pages instead of re-hitting the network from page one. Invalidation (a Room write, or you calling invalidate()) tears down the current PagingSource, calls getRefreshKey() to find an anchor near the user's scroll position, and constructs a fresh source loading around that key — which is why getRefreshKey returns the item id near anchorPosition rather than a page number.

scroll near end (index ≥ loaded - prefetchDistance)
   → PageFetcher.load(Append, key = lastPage.nextKey)
        → your PagingSource.load()  → LoadResult.Page(data, nextKey)
              → appended to PagingData → diffed → emitted to LazyColumn
invalidate() → getRefreshKey(state) → new PagingSource centered on that key

Error Mapping

🎤 Say it out loud (~30–45s): "Error mapping is about not letting networking internals leak into the UI. Raw HttpException, IOException, SocketTimeoutException are transport details — my ViewModel and UI should reason about a domain sealed class like NoInternet, Timeout, Unauthorized, ServerError. So at the repository boundary I catch and map exceptions into that sealed type, usually wrapped in a Result. The detail I make sure to handle is parsing the error body: Retrofit's HttpException only gives you the status code and a generic message, so to surface the server's actual validation message I have to read errorBody().string() — and that stream can only be consumed once, so I read it carefully and tolerate it being empty."

Error mapping is the practice of converting raw HTTP and network exceptions into domain-specific sealed class errors that the UI layer can actually reason about. Without it, ViewModels receive raw HttpException, IOException, SocketTimeoutException — networking implementation details that have no business in the UI.

Domain error model:

sealed class NetworkError {
    object NoInternet : NetworkError()
    object Timeout : NetworkError()
    data class ServerError(val code: Int, val message: String) : NetworkError()
    data class Unauthorized(val message: String) : NetworkError()
    object NotFound : NetworkError()
    data class Unknown(val throwable: Throwable) : NetworkError()
}

Error mapping function:

fun Throwable.toNetworkError(): NetworkError = when (this) {
    is UnknownHostException, is ConnectException -> NetworkError.NoInternet
    is SocketTimeoutException -> NetworkError.Timeout
    is HttpException -> when (code()) {
        401 -> NetworkError.Unauthorized(message())
        404 -> NetworkError.NotFound
        in 500..599 -> NetworkError.ServerError(code(), message())
        else -> NetworkError.ServerError(code(), message())
    }
    else -> NetworkError.Unknown(this)
}

Parsing error response bodies:

// Server returns: {"error": "validation_failed", "details": "Email is invalid"}
data class ApiError(val error: String, val details: String?)

    return try {
        val body = response()?.errorBody()?.string() ?: return null
        moshi.adapter(ApiError::class.java).fromJson(body)
    } catch (e: Exception) {
        null
    }
}

Result type pattern:

sealed class Result<out T> {
    data class Success<T>(val data: T) : Result<T>()
    data class Error(val error: NetworkError) : Result<Nothing>()
}

// Repository usage

    Result.Success(api.getUser(id))
} catch (e: Exception) {
    Result.Error(e.toNetworkError())
}

Alternatively, Kotlin's built-in kotlin.Result<T> or Arrow's Either<Error, Success> serve the same purpose.

Under the hood

A Retrofit HttpException is thrown by Retrofit itself, not by OkHttp: when a suspend Retrofit method or a Call returns a response with a non-2xx code, Retrofit wraps the failed retrofit2.Response in HttpException, copying out code() and message() (the HTTP status line reason phrase) eagerly while keeping a reference to the full Response. The body of a failed call is held as errorBody(), an OkHttp ResponseBody backed by a BufferedSource reading from the socket. Calling .string() reads the whole buffer and then closes it — the source is one-shot, so a second .string() throws IllegalStateException: closed. That's the subtlety the parsing helper above is guarding against by reading exactly once.

The connectivity exceptions map cleanly because they come from distinct layers: UnknownHostException is thrown by the DNS resolver (InetAddress.getAllByName) when a hostname can't resolve, ConnectException from the TCP connect() syscall when there's no route or the port is refused, and SocketTimeoutException from the socket read/write timers described earlier. Because Kotlin's sealed class is closed at compile time, the when over NetworkError in the UI is exhaustive without an else, so adding a new error variant forces every consumer to handle it — the compiler turns "did I handle this failure?" into a build error rather than a runtime surprise.

socket read → 503 status line
  → OkHttp Response(code=503, body=ResponseBody)
    → Retrofit sees !isSuccessful → throw HttpException(response)
      → repository catch → toNetworkError() → NetworkError.ServerError(503, ...)
        → ViewModel exhaustive `when` → UI state
errorBody().string() consumes + closes the BufferedSource (one read only)

Idempotency

🎤 Say it out loud (~30–45s): "Idempotency means doing the operation N times lands you in the same state as doing it once, which is exactly the property that tells me whether a retry is safe. GET, PUT, and DELETE are idempotent by definition; POST and PATCH aren't, so I never blindly retry them. The trick for making a POST safe to retry is a client-generated idempotency key — a UUID per logical operation that the server dedupes on — so if the network drops after the server committed but before I got the response, I retry with the same key and get the original result instead of a second order."

An operation is idempotent when performing it multiple times produces exactly the same result as performing it once — which determines whether it's safe to automatically retry on failure.

HTTP idempotency:

  • GET, PUT, DELETE, HEAD: idempotent
  • POST, PATCH: NOT idempotent by default

Client-side idempotency key for POST:

// Client generates a unique key for each logical operation
val idempotencyKey = UUID.randomUUID().toString()

@POST("orders")
suspend fun createOrder(
    @Header("Idempotency-Key") key: String,
    @Body order: CreateOrderRequest
): Order

If the network fails after the server processes the request (but before the response arrives), the client can retry with the same key — the server recognizes the duplicate and returns the original result without creating a second order.

Android scenarios where idempotency matters:

  • Payment/booking APIs — user taps "Book" twice due to slow response
  • File uploads — upload failed mid-way, retry should not create a duplicate entry
  • Form submissions — user navigates back and resubmits

Avoiding duplicate requests in the UI:

class BookingViewModel : ViewModel() {
    private var bookingJob: Job? = null

    fun book() {
        if (bookingJob?.isActive == true) return // guard
        bookingJob = viewModelScope.launch {
            _state.update { it.copy(isLoading = true) }
            // ... make request
        }
    }
}

Under the hood

Idempotency isn't enforced by the HTTP protocol — it's a contract the server must honor. With an idempotency key, the server typically persists a record keyed by (key, request-fingerprint) inside the same transaction that commits the side effect. On a retry it looks up that key: if a completed result exists it short-circuits and replays the stored response, and if a request with that key is still in flight it returns a 409/conflict or blocks. The hard part is atomicity — the key record and the business write must commit together, otherwise a crash between them reopens the duplicate window.

1st POST  ──► server: BEGIN TX; insert order; insert idem_key=K; COMMIT ──► 201 (lost on network)
retry POST(K) ──► server: SELECT idem_key=K → HIT ──► replay stored 201, no new order

TLS Basics

🎤 Say it out loud (~30–45s): "TLS is the layer that gives HTTPS confidentiality, integrity, and server authentication. The handshake negotiates a cipher suite, the server presents a certificate chain that the client validates back to a trusted root CA, and then an ephemeral key exchange like ECDHE derives the symmetric session keys. On Android 9+ cleartext HTTP is blocked by default, so HTTPS is effectively mandatory, and the thing interviewers probe is that the chain has to validate to the system trust store — a self-signed or expired cert fails validation even though the bytes are still encrypted."

TLS is the encryption layer that turns HTTP into HTTPS — and on Android 9 and above, cleartext HTTP is blocked by default via android:usesCleartextTraffic="false", so HTTPS is effectively mandatory.

TLS handshake steps (simplified):

  1. Client → Server: ClientHello (supported TLS versions, cipher suites, random nonce)
  2. Server → Client: ServerHello + Certificate + (optional) CertificateRequest
  3. Client validates certificate against trusted CAs
  4. Key exchange (ECDHE or similar) → shared secret
  5. Both sides derive session keys from shared secret
  6. Encrypted communication begins

Android trusted CAs: Android maintains a system CA store. Apps trust all system CAs by default. Enterprise apps can add custom CAs via network_security_config.xml.

Under the hood

The asymmetric crypto (the certificate's RSA/ECDSA key) is used only to authenticate the server and protect the key exchange — it never encrypts the bulk traffic. ECDHE has both sides exchange ephemeral public keys and independently compute the same shared secret, which is then fed through a key-derivation function (HKDF in TLS 1.3) to produce the symmetric AEAD keys used for the rest of the session; because the DH keys are ephemeral, capturing the server's private key later still can't decrypt a recorded session — that's forward secrecy. On Android, certificate validation runs through the platform's X509TrustManager (via Conscrypt, Android's BoringSSL-backed JSSE provider), which walks the chain checking signatures, validity dates, and hostname, terminating at a root in the system store. TLS 1.3 also collapses the handshake to a single round trip by having the client guess the key-share in the ClientHello.

ECDHE:  client (a, g^a)  ⇄  server (b, g^b)   →  both derive g^ab  →  HKDF → AEAD session keys
auth:   server signs handshake transcript with cert private key; client verifies chain → system root CA

Certificate Pinning

🎤 Say it out loud (~30–45s): "Pinning means I hard-code the expected public-key hash of my server and reject any TLS connection that doesn't match, even if the cert is otherwise valid and CA-signed — that defends against a compromised CA or a corporate MITM proxy. I always pin the public key, not the whole certificate, so it survives cert renewals as long as the key pair is reused, and I ship at least two pins plus a backup. The big gotcha is operational: a pin mismatch is an app-wide outage, so I pin with an expiration, rotate ahead of renewal, and keep a remote kill switch. I prefer declaring it in network_security_config so it's framework-enforced and survives obfuscation."

Certificate pinning means hard-coding the expected public key hash of your server into the app and refusing any TLS connection that doesn't match — even if the certificate is otherwise valid and CA-signed.

Why it matters: Prevents man-in-the-middle attacks where an attacker has compromised a CA or installed a corporate proxy certificate. Critical for apps handling financial or health data.

Two types:

  • Certificate pinning: Pin the entire certificate (brittle — breaks on cert renewal)
  • Public key pinning: Pin the public key from the certificate (survives cert renewals if the key pair is retained)

OkHttp CertificatePinner:

val certificatePinner = CertificatePinner.Builder()
    .add("api.example.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .add("api.example.com", "sha256/BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB=") // backup pin
    .build()

val client = OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build()

How to get the pin:

openssl s_client -connect api.example.com:443 | \
    openssl x509 -pubkey -noout | \
    openssl pkey -pubin -outform der | \
    openssl dgst -sha256 -binary | \
    base64

Failure modes:

  • Pin mismatch → SSLPeerUnverifiedException — entire HTTPS call fails
  • Certificate renewal without updating pin → app-wide outage
  • Corporate proxies / debugging proxies (Charles, mitmproxy) → pinning fails intentionally

Mitigation strategies:

  • Always include at least two pins (primary + backup)
  • Set an expiration date and rotate pins before renewal
  • Implement a remote kill switch to disable pinning via a trusted configuration endpoint fetched without pinning
  • Use network_security_config.xml for declarative pinning (framework enforced, survives ProGuard)

Debug builds: Typically disable pinning or add the debug certificate pin to avoid blocking local proxies.

Under the hood

The pin is a SHA-256 hash of the certificate's SubjectPublicKeyInfo (SPKI) — the DER-encoded public key plus its algorithm identifier, not the whole certificate — which is why a renewed cert that reuses the same key pair keeps the same pin. Pinning runs as an extra check layered on top of normal chain validation: OkHttp's CertificatePinner lets the standard X509TrustManager validate the chain to a system root first, then for the matched hostname it hashes the SPKI of each cert in the verified chain and requires at least one to equal a configured pin, throwing SSLPeerUnverifiedException otherwise. Because any cert in the chain can satisfy a pin, teams often pin an intermediate CA's key for safer rotation. When declared in network_security_config.xml, the framework's NetworkSecurityTrustManager enforces the same check for every HTTPS stack in the process (OkHttp, HttpURLConnection, WebView), which is why declarative pinning survives ProGuard renaming of your code.

verified chain: [leaf]→[intermediate]→[root]
for each cert: SHA-256( DER(SubjectPublicKeyInfo) ) → base64
connection OK iff ∃ cert whose hash ∈ configured pin-set, else SSLPeerUnverifiedException

Interview Angles: Networking

Q: How do you handle token refresh safely?

"There are two problems to solve simultaneously. The first is a 401 triggering multiple concurrent refresh calls — if three requests all fail at once, you don't want three parallel hits to the auth server. The second is re-using a stale token after another thread already refreshed it. I solve both with OkHttp's Authenticator interface combined with a Mutex. The Authenticator is only invoked on a 401. The Mutex serializes access so only one refresh actually happens. And there's a double-check inside the lock: I compare the stored token to the token that failed — if they're already different, another thread refreshed while I was waiting, so I just reuse the new token and skip the network call. That combination eliminates both races."

Q: How do you model network errors?

"The rule I follow is: never let HttpException or IOException escape the data layer. At the repository boundary I map all exceptions to a sealed class NetworkError using a Kotlin extension function on Throwable. For server errors with structured bodies, I parse the errorBody() from HttpException. The ViewModel gets a Result<T> or Either<NetworkError, T> — never a raw exception — which means the UI logic can just pattern-match on human-readable cases like NoInternet, Timeout, Unauthorized, ServerError, without caring about HTTP internals."

Q: How do you avoid duplicate requests?

"There are three layers I use. First, a ViewModel-level guard — before launching a new coroutine job, I check if one is already active and bail out if so; that handles double-taps and fast navigation. Second, for non-idempotent POST requests, I generate a UUID per logical operation and include it as an Idempotency-Key header — the server can then recognize a retry and return the original result without creating a duplicate. Third, for search and autocomplete, I apply debounce() in the StateFlow pipeline so rapid keystrokes only trigger one network call."

Q: How do you handle pagination?

"I use Paging 3. For a pure-network list, I write a PagingSource that fetches from the API. For a network-plus-local-cache setup, I use RemoteMediator alongside a Room-backed PagingSource — the RemoteMediator fetches from the network and writes to Room, and the PagingSource reads from Room, so the DB is always the source of truth. The PagingConfig controls pageSize, initialLoadSize, and prefetchDistance. In the ViewModel I expose .flow.cachedIn(viewModelScope) so the paged data survives config changes. In Compose I collect with collectAsLazyPagingItems() and handle the LoadState for loading, error, and empty states."

Q: Retry strategy for failed requests?

"My default is exponential backoff with jitter in an Interceptor. I retry 5xx errors — except 501, which means 'not implemented' and will never succeed on retry — and network IOException. For 429 I respect the Retry-After header. I cap at three attempts. The critical rule is that I never auto-retry non-idempotent POST requests unless they carry an idempotency key, because retrying a POST that the server already processed would create a duplicate. For background sync specifically, I delegate to WorkManager, which handles retries with BackoffPolicy.EXPONENTIAL and survives process death."

10.2 Persistence

SQLite Basics

🎤 Say it out loud (~30–45s): "SQLite is a serverless, embedded relational database — it's just a single file in the app's private storage accessed in-process, with full ACID transactions. The two things I always call out: it's single-writer, so write contention serializes, though WAL mode lets readers run concurrently with a writer; and its typing is dynamic — columns have type affinity rather than strict enforcement, so a TEXT column can actually hold an integer. In practice I never touch raw SQLite directly because of manual cursor management and no compile-time query checking — I let Room sit on top."

SQLite is a lightweight relational database embedded directly in every Android device — a single on-disk file, accessed through the android.database.sqlite package, with no separate server process.

Key characteristics:

  • Single writer at a time (WAL mode allows concurrent reads)
  • ACID transactions
  • Dynamically typed (type affinity, not strict enforcement)
  • No network overhead; reads/writes directly to a file in data/data/<package>/databases/

WAL mode (Write-Ahead Logging): Room enables WAL by default since Room 2.2. In WAL mode, writes go to a .wal file and are periodically checkpointed into the main database. Allows concurrent reads during writes (much better performance for read-heavy apps).

Raw SQLite pattern (rarely used directly; Room is preferred):

val db = context.openOrCreateDatabase("app.db", Context.MODE_PRIVATE, null)
db.execSQL("CREATE TABLE IF NOT EXISTS users (id TEXT PRIMARY KEY, name TEXT)")
val cursor = db.rawQuery("SELECT * FROM users WHERE id = ?", arrayOf(userId))
cursor.use {
    while (it.moveToNext()) {
        val id = it.getString(it.getColumnIndex("id"))
    }
}

Problems with raw SQLite: manual cursor management, no compile-time query validation, no type safety, tedious migrations.

Under the hood

SQLite stores the whole database as a tree of fixed-size pages (default 4 KB) in one file; tables and indexes are B-trees rooted at page numbers tracked in the sqlite_master schema table, so a primary-key lookup is a B-tree descent rather than a scan. A Cursor doesn't materialize all rows up front — SQLiteCursor backs a CursorWindow, a chunk of shared (ashmem) memory holding a window of rows, and moveToNext() past the window's edge re-queries to fill the next batch; that's why leaking a cursor leaks native memory and why you wrap it in use {}. In the default rollback-journal mode a writer copies original pages into a -journal file and takes an exclusive lock, blocking everyone; WAL inverts this — the writer appends new page images to a -wal file while readers keep reading the last committed snapshot from the main file, and a periodic checkpoint folds the WAL back in. Type affinity means the declared column type is only a preference: SQLite stores each value with its own storage class and coerces toward the column's affinity, so strictness is the application's job (or STRICT tables in newer SQLite).

file = [page 1: sqlite_master B-tree root][page 2..N: table/index B-tree pages]
read path: rawQuery → compile to bytecode (VDBE) → B-tree walk → rows into CursorWindow (ashmem)
WAL: writer appends to db-wal; readers see last-committed snapshot; checkpoint merges wal→db

Room

🎤 Say it out loud (~30–45s): "Room is Jetpack's persistence library sitting on top of SQLite, and its headline feature is that it verifies your SQL at compile time — the annotation processor actually parses every @Query against the schema, so a typo'd column name is a build error, not a runtime crash. You declare @Entity, @Dao, and @Database, and Room generates the implementation that does the cursor-to-object mapping for you. The nuance I mention is that returning a Flow from a DAO gives you observable queries that re-emit on table changes, and that fallbackToDestructiveMigration is a dev-only convenience — in production you ship real Migration objects, because destructive migration drops the user's data."

Room is the Jetpack persistence library — it sits on top of SQLite and gives you compile-time query verification, type-safe DAOs, migration scaffolding, and first-class support for Flow and LiveData.

Setup:

// build.gradle.kts
implementation("androidx.room:room-runtime:2.6.1")
implementation("androidx.room:room-ktx:2.6.1")
ksp("androidx.room:room-compiler:2.6.1")

The three core components:

  1. @Entity — maps to a database table
  2. @Dao — Data Access Object; defines SQL queries as Kotlin functions
  3. @Database — the database holder; creates/opens the SQLite file

Database declaration:

@Database(
    entities = [UserEntity::class, PostEntity::class],
    version = 3,
    exportSchema = true  // exports schema JSON; required for migration testing
)
@TypeConverters(DateConverter::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun userDao(): UserDao
    abstract fun postDao(): PostDao

    companion object {
        @Volatile private var instance: AppDatabase? = null

        fun getInstance(context: Context): AppDatabase =
            instance ?: synchronized(this) {
                instance ?: Room.databaseBuilder(
                    context.applicationContext,
                    AppDatabase::class.java,
                    "app_database"
                )
                .addMigrations(MIGRATION_1_2, MIGRATION_2_3)
                .fallbackToDestructiveMigration() // ONLY in dev; never in production
                .build().also { instance = it }
            }
    }
}

Room compilation: The @Database annotation processor generates AppDatabase_Impl, validates all @Query annotations at compile time (SQL syntax, column names, return types), generates efficient boilerplate. This compile-time validation is the single biggest advantage over raw SQLite.

Under the hood

The room-compiler is a KSP/annotation processor that, at build time, actually compiles each @Query string against an in-memory model of your schema (it bundles SQLite's own grammar), so column and table names are resolved before the app ever runs — that's the compile-time verification. For each abstract class it generates concrete code: AppDatabase_Impl wires up the DAOs and a RoomOpenHelper that checks the stored user_version pragma against the @Database(version=…) and runs the matching Migration objects (each migration is raw SQL you write; Room only verifies the resulting schema matches the exported JSON). UserDao_Impl contains the hand-rolled cursor code — bind args, run the query, read each CursorWindow column by index into your entity. Observable Flow/LiveData queries are backed by the InvalidationTracker: Room installs SQLite triggers on the relevant tables that write into an internal room_table_modification_log, and after any write transaction commits it checks that log and re-runs affected queries, which is how a Flow re-emits when the underlying table changes.

build time:  @Query "SELECT * FROM users WHERE id=:id"  ──parse vs schema──► UserDao_Impl (cursor mapping) or COMPILE ERROR
runtime open: RoomOpenHelper reads PRAGMA user_version → runs Migration_1_2, Migration_2_3 → validates schema == exported JSON
observe:     write COMMIT → triggers update room_table_modification_log → InvalidationTracker → re-run Flow query → re-emit

🎤 Say it out loud (~30–45s): "An entity is just a Kotlin data class annotated with @Entity — Room's annotation processor reads it at compile time and generates the actual CREATE TABLE DDL, so each property becomes a column. An @Entity is a Kotlin data class that maps directly to a SQLite table — each property becomes a column, and Room's annotation processor generates all the schema DDL at compile time.

Under the hood

Room runs as a kapt/KSP annotation processor during compilation. It reflects over the entity's properties (using the Kotlin metadata / javax.lang.model element model), maps each Kotlin type to one of SQLite's four storage classes via column affinity (INTEGER, REAL, TEXT, BLOB — there is no native date or boolean type), and emits the CREATE TABLE string. A Boolean is stored as INTEGER 0/1; a Long epoch is stored as INTEGER. The non-null Kotlin types become NOT NULL constraints in the DDL. At read time, the generated DAO code pulls values out of an android.database.Cursor by column index and invokes your registered @TypeConverter to rehydrate complex types. @Embedded produces no nesting — the processor splices the embedded class's columns directly into the parent table.

DAO

🎤 Say it out loud (~30–45s): "A DAO is an interface or abstract class annotated with @Dao where I declare queries as method signatures, and Room generates the implementation at compile time — including parsing and verifying my SQL against the real schema so a typo'd column name is a build error, not a crash. The gotcha I watch for is the return type: a suspend function runs the query once, but returning a Flow makes it observable — Room sets up an invalidation tracker so the flow re-emits whenever any row in the touched tables changes."

A DAO (Data Access Object) is an interface annotated with @Dao where you declare your SQL operations as abstract Kotlin functions — Room generates the entire implementation at compile time.

@Dao
interface UserDao {
    // Simple queries
    @Query("SELECT * FROM users WHERE id = :id")
    suspend fun getUserById(id: String): UserEntity?

    @Query("SELECT * FROM users WHERE team_id = :teamId ORDER BY last_name ASC")
    suspend fun getUsersByTeam(teamId: String): List<UserEntity>

    // Reactive queries (return Flow)
    @Query("SELECT * FROM users ORDER BY last_name ASC")
    fun getAllUsersFlow(): Flow<List<UserEntity>>

    @Query("SELECT * FROM users WHERE id = :id")
    fun getUserByIdFlow(id: String): Flow<UserEntity?>

    // Insert operations
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertUser(user: UserEntity)

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertUsers(users: List<UserEntity>)

    // Update
    @Update
    suspend fun updateUser(user: UserEntity): Int  // returns rows affected

    // Delete
    @Delete
    suspend fun deleteUser(user: UserEntity)

    @Query("DELETE FROM users WHERE id = :id")
    suspend fun deleteUserById(id: String)

    @Query("DELETE FROM users")
    suspend fun deleteAllUsers()

    // Upsert (Room 2.5+)
    @Upsert
    suspend fun upsertUser(user: UserEntity)

    // Partial updates with POJO
    @Query("UPDATE users SET email = :email WHERE id = :id")
    suspend fun updateEmail(id: String, email: String)

    // Count
    @Query("SELECT COUNT(*) FROM users")
    suspend fun count(): Int

    // JOIN query returning custom POJO
    @Query("""
        SELECT u.*, t.name as team_name 
        FROM users u 
        LEFT JOIN teams t ON u.team_id = t.id 
        WHERE u.id = :userId
    """)
    suspend fun getUserWithTeam(userId: String): UserWithTeam?
}

OnConflictStrategy:

  • REPLACE: delete old row, insert new (triggers DELETE + INSERT, may break foreign key cascades)
  • IGNORE: keep old row, ignore new (returns -1 for the rowId)
  • ABORT (default): throw exception

Under the hood

Room generates a UserDao_Impl class that implements the interface. Each @Query is parsed and type-checked at compile time against the schema, then compiled into a RoomSQLiteQuery (a prepared SQLiteStatement with bound ? parameters — your :id becomes a positional bind argument, which is also why Room is injection-safe). For a one-shot suspend function, the generated code wraps the cursor read in CoroutinesRoom.execute(...), hopping onto the database's Executor (a dedicated background dispatcher) so it never touches the SQLite connection on the main thread. For a Flow return, Room registers an InvalidationTracker.Observer on the tables the query reads. SQLite triggers (installed on those tables) write into a shadow room_table_modification_log; on the next transaction commit, the tracker compares table versions and, if a watched table changed, re-runs the query and emits the fresh result downstream. That is table-level granularity — any write to users re-emits, even if the specific row you care about didn't change.

@Query("SELECT * FROM users WHERE id = :id") -> compile time
  ├─ SQL parsed & validated vs schema (bad column = build error)
  ├─ becomes RoomSQLiteQuery: "SELECT * FROM users WHERE id = ?"  bind(1, id)
  └─ Flow variant: InvalidationTracker observer on table "users"
       writes -> SQLite trigger -> modification log -> re-query -> emit

Transactions

🎤 Say it out loud (~30–45s): "A transaction groups several operations so they commit or roll back as one atomic unit — I annotate a DAO method with @Transaction, or for work spanning multiple DAOs I use db.withTransaction { }. Two things I always mention: it's not just about atomicity, it's a huge performance win because batching inserts means one fsync to the journal instead of one per row; and the suspend-aware withTransaction pins the whole block to a single connection on a transaction-scoped dispatcher, so you must not switch dispatchers or do unrelated suspending I/O inside it or you can deadlock or lose the transaction context."

A database transaction groups multiple operations into one atomic unit — they all succeed together or all roll back together. Room provides the @Transaction annotation to declare this, plus database.withTransaction {} for cross-DAO operations.

@Dao
interface UserDao {
    @Transaction
    suspend fun replaceAllUsers(users: List<UserEntity>) {
        deleteAllUsers()
        insertUsers(users)
    }

    @Insert
    suspend fun insertUsers(users: List<UserEntity>)

    @Query("DELETE FROM users")
    suspend fun deleteAllUsers()
}

Database-level transaction (when spanning multiple DAOs):

suspend fun syncUsersAndTeams(
    users: List<UserEntity>,
    teams: List<TeamEntity>
) {
    database.withTransaction {
        database.teamDao().insertAll(teams)
        database.userDao().insertUsers(users)  // users reference teams via FK
    }
}

database.withTransaction is a Room extension that wraps the lambda in a SQLite transaction. Any exception inside will roll back the transaction.

Why transactions matter:

  • Atomicity: If an app process is killed mid-sync, partial state is not visible
  • Performance: Inserting 1000 rows in a single transaction is 10–50x faster than 1000 individual inserts (avoids 1000 journal writes)
  • Consistency: Foreign key constraints are checked at transaction commit, not per-insert

Under the hood

Underneath, Room calls SQLite's beginTransaction() / setTransactionSuccessful() / endTransaction(). With Write-Ahead Logging (WAL, Room's default journal mode), each transaction appends changed pages to a -wal file and only forces a durability fsync at commit — so 1000 inserts in one transaction is one durability barrier instead of 1000, which is where the order-of-magnitude speedup comes from. The coroutine withTransaction extension is the subtle part: it acquires a connection, stores it in a TransactionElement inside the coroutine context, and dispatches the block on a transaction-scoped dispatcher backed by that single connection's thread. Every suspending DAO call inside inherits that element and reuses the same connection, which is mandatory because SQLite transactions are per-connection. If you withContext(Dispatchers.IO) to a different thread/connection mid-block, those statements execute outside the transaction. Because Room's transaction executor is a bounded pool, blocking inside the block while also trying to start a nested transaction can exhaust it and deadlock.

withTransaction {
  BEGIN (connection C, thread T) ── stored as TransactionElement in coroutine ctx
    insert(teams)   ┐ all run on C/T, pages appended to -wal
    insert(users)   ┘
  success -> COMMIT -> single fsync of -wal
}  (exception anywhere -> endTransaction without success -> ROLLBACK)

Migrations

🎤 Say it out loud (~30–45s): "A migration is how I evolve the schema across app versions without nuking user data: I bump the @Database version and supply a Migration object with the raw ALTER/CREATE SQL. The safety net is that Room exports a JSON schema snapshot at build time and, after my migration runs, validates the live schema against the expected one — so a mismatched column type or a forgotten index fails loudly instead of silently corrupting data. The classic gotcha is fallbackToDestructiveMigration, which drops and recreates everything — fine in dev, catastrophic in production."

A migration is how you evolve the database schema across app versions without losing user data — Room validates every migration against a generated schema snapshot, so if your SQL is wrong you find out at build time, not in production.

Room migration mechanics:

  1. Increment the version in @Database
  2. Write a Migration object with the SQL ALTER/CREATE/DROP statements
  3. Register with addMigrations()
  4. Room validates the final schema against the generated schema JSON
val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL("ALTER TABLE users ADD COLUMN profile_image_url TEXT")
    }
}

val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(database: SupportSQLiteDatabase) {
        // SQLite doesn't support DROP COLUMN directly (before API 35)
        // Must recreate the table
        database.execSQL("""
            CREATE TABLE users_new (
                id TEXT NOT NULL PRIMARY KEY,
                first_name TEXT NOT NULL,
                last_name TEXT NOT NULL,
                email TEXT NOT NULL
            )
        """)
        database.execSQL("""
            INSERT INTO users_new (id, first_name, last_name, email)
            SELECT id, first_name, last_name, email FROM users
        """)
        database.execSQL("DROP TABLE users")
        database.execSQL("ALTER TABLE users_new RENAME TO users")
    }
}

    }
}

fallbackToDestructiveMigration(): Only for development. In production, a missing migration drops and recreates the database — all user data is lost. Never use in production.

Under the hood

The user_version PRAGMA is an integer stored in the SQLite file header; SQLite itself does nothing with it, but Room reads it on open to decide whether to migrate. When the on-disk user_version is lower than the @Database version, Room's RoomOpenHelper looks up a path through the registered migrations (a graph search — it picks a direct edge like 1→3 if one exists, otherwise chains 1→2→3), runs each migration's migrate() inside a transaction, then bumps user_version. The validation step compares an identityHash of the live schema against the hash baked into the build-time schema JSON (the file Room exports when you set room.schemaLocation); a mismatch throws IllegalStateException. Auto-migrations are simply Migration objects whose body Room generates at compile time by diffing two exported schema JSONs — which is why anything ambiguous (a rename looks like a drop+add to a diff) needs an @AutoMigrationSpec to disambiguate. The table-recreate dance in MIGRATION_2_3 exists because legacy SQLite (pre-3.35 / API < 35) had no DROP COLUMN, so the only safe rewrite is create-new, copy, drop-old, rename.

open db -> read PRAGMA user_version (e.g. 1), target = 3
  find migration path: [1->3] if present else [1->2, 2->3]
  for each migration: BEGIN; migrate(); COMMIT
  validate: identityHash(live schema) == hash(schema_3.json) ? ok : crash
  set PRAGMA user_version = 3

Indexes

🎤 Say it out loud (~30–45s): "An index is a separate B-tree keyed on one or more columns that lets SQLite binary-search to matching rows instead of scanning the whole table — so it turns an O(n) filter into roughly O(log n). The trade-off is that every insert, update, and delete now has to maintain that extra tree and it costs storage, so I index the columns I actually filter, sort, or join on — and critically, foreign keys, because SQLite, unlike Postgres, does not auto-index them. I verify with EXPLAIN QUERY PLAN that I see SEARCH ... USING INDEX rather than SCAN."

A database index is a B-tree structure that speeds up queries on specific columns — the trade-off is extra storage and slightly slower writes, because each insert or update has to maintain the index tree as well as the table.

@Entity(
    tableName = "posts",
    indices = [
        Index(value = ["user_id"]),                        // index for FK lookups
        Index(value = ["created_at"]),                     // index for time-based queries
        Index(value = ["user_id", "created_at"]),          // composite index for filtered + sorted
        Index(value = ["slug"], unique = true)             // unique constraint via index
    ]
)
data class PostEntity(
    @PrimaryKey val id: String,
    val userId: String,
    val slug: String,
    val title: String,
    val createdAt: Long
)

When to add indexes:

  • Foreign key columns (always — SQLite does not auto-index FKs unlike PostgreSQL)
  • Columns used in WHERE clauses of frequent queries
  • Columns used in ORDER BY (especially for large tables)
  • Columns used in JOIN conditions

When indexes hurt:

  • INSERT/UPDATE/DELETE are slower (must update index B-tree)
  • Extra storage per row
  • Full table scans are faster for tables with < ~100 rows

EXPLAIN QUERY PLAN (use in debug mode to verify index usage):

val cursor = db.query("EXPLAIN QUERY PLAN SELECT * FROM posts WHERE user_id = '1'", null)
// Output should show "SEARCH posts USING INDEX idx_posts_user_id"
// Not "SCAN posts" which is a full table scan

Under the hood

In SQLite, both the table and each index are stored as B-tree pages inside the same database file. A normal rowid table is a B-tree keyed by the integer rowid; an index is a separate B-tree whose keys are the indexed column values followed by the row's rowid, so a lookup binary-searches the index tree, finds the rowid, then does a second seek into the table tree to fetch the full row. That second hop is why a covering composite index — one that contains every column the query needs — can be faster: SQLite reads everything straight from the index and skips the table entirely. The query planner picks an index using sqlite_stat1 statistics (populated by ANALYZE); without stats it falls back to heuristics, which is occasionally why it ignores an index you expected. Composite indexes obey the left-prefix rule: an index on (user_id, created_at) accelerates filters on user_id alone or user_id + created_at, but does nothing for a query that filters only on created_at. A unique index additionally enforces the constraint by rejecting a duplicate key insert at write time.

INDEX idx(user_id, created_at):
  B-tree keyed [user_id, created_at, rowid]
  query: WHERE user_id='1' ORDER BY created_at
    -> SEARCH using index (binary search to user_id='1', already sorted by created_at)
    -> for each match: seek rowid into table tree for SELECT *  (skipped if covering)
  query: WHERE created_at > X  -> left-prefix not satisfied -> SCAN

Foreign Keys and Relations

🎤 Say it out loud (~30–45s): "Foreign keys enforce referential integrity at the database level — a child can't point at a parent that doesn't exist, and I can declare onDelete = CASCADE or SET_NULL so the DB cleans up automatically. The number-one gotcha is that SQLite has foreign keys off by default, so you must enable PRAGMA foreign_keys = ON per connection. For reading related data, Room doesn't hydrate JOINs into object graphs — I use @Relation with @Embedded, and that method must be @Transaction because Room runs separate queries per relation and stitches them in memory."

Foreign keys enforce referential integrity at the database level — a child row simply cannot reference a parent that doesn't exist, and Room can cascade deletes or set nulls automatically when a parent is removed.

// Enable foreign keys — not enabled by default in SQLite!
val db = Room.databaseBuilder(...)
    .addCallback(object : RoomDatabase.Callback() {
        override fun onOpen(db: SupportSQLiteDatabase) {
            db.execSQL("PRAGMA foreign_keys = ON")
        }
    })
    .build()

Relations in Room: Room does not support SQL JOINs in @Query returning entity objects directly. Instead, use data classes with @Relation:

data class UserWithPosts(
    @Embedded val user: UserEntity,
    @Relation(
        parentColumn = "id",
        entityColumn = "user_id"
    )
    val posts: List<PostEntity>
)

@Dao
interface UserDao {
    @Transaction
    @Query("SELECT * FROM users WHERE id = :userId")
    suspend fun getUserWithPosts(userId: String): UserWithPosts?
}

@Transaction is required on @Relation queries — Room makes two separate queries (one for users, one for posts) and merges them in memory; the transaction ensures consistency.

Many-to-many:

@Entity(primaryKeys = ["user_id", "tag_id"])
data class UserTagCrossRef(
    @ColumnInfo(name = "user_id") val userId: String,
    @ColumnInfo(name = "tag_id") val tagId: String
)

data class UserWithTags(
    @Embedded val user: UserEntity,
    @Relation(
        parentColumn = "id",
        entityColumn = "id",
        associateBy = Junction(UserTagCrossRef::class,
            parentColumn = "user_id",
            entityColumn = "tag_id")
    )
    val tags: List<TagEntity>
)

Under the hood

Foreign key enforcement is a runtime SQLite feature gated by the foreign_keys PRAGMA, which is connection-scoped and defaults to OFF for backward compatibility — that's why it goes in onOpen (which fires per connection) rather than being declared once. When enabled, on a parent delete SQLite walks the child tables and applies the declared action (CASCADE deletes children, SET_NULL nulls the FK column), and it checks constraints; with WAL/immediate enforcement a violating write fails immediately. For @Relation, Room generates code that does not emit a JOIN — a JOIN would duplicate the parent row once per child, which doesn't map cleanly to a User owning a List<Post>. Instead it runs the parent query, collects the parent keys, then issues a second SELECT ... WHERE user_id IN (?, ?, ...) for the children and buckets them into a LongSparseArray/HashMap keyed by the relation column before assembling the objects in memory. Wrapping both queries in @Transaction guarantees they observe a single consistent snapshot, so a concurrent insert can't make the parent and child sets disagree. A many-to-many Junction adds a third query against the cross-ref table to resolve the key mapping.

getUserWithPosts(userId):  (no JOIN)
  Q1: SELECT * FROM users WHERE id = ?          -> parent rows + keys {id}
  Q2: SELECT * FROM posts WHERE user_id IN (?)  -> children
      bucket children into map<user_id, List<Post>>
  assemble UserWithPosts in memory
  (@Transaction => Q1 and Q2 see one consistent snapshot)

Flow from Room

🎤 Say it out loud (~30–45s): "When a Room DAO returns a Flow, I get the query result immediately and then an automatic re-emission every time any tracked table changes — so the UI never polls, it just collects and stays current. The nuance interviewers like to probe is that Room observes at table granularity, not row granularity, so a write to an unrelated row in the same table still triggers a re-query; that's why you keep queries lean and let distinctUntilChanged filter out no-op emissions downstream."

When a Room DAO method returns Flow<T>, it emits the current query result immediately and then automatically re-emits every time the underlying table changes — which means the UI never has to poll; it just collects and stays current.

@Dao
interface UserDao {
    @Query("SELECT * FROM users ORDER BY last_name ASC")
    fun getAllUsers(): Flow<List<UserEntity>>
}

How it works internally: Room uses InvalidationTracker — a table observer that detects when tables are modified by tracking statement IDs. When a tracked table changes, it notifies all observing Flow collectors, which re-execute their query.

Combining Room Flow with network data:

class UserRepository(
    private val userDao: UserDao,
    private val userApi: UserApi
) {
    // Expose Room Flow — UI always shows local data
    val users: Flow<List<User>> = userDao.getAllUsers()
        .map { entities -> entities.map { it.toUser() } }

    // Refresh from network — writes to Room, triggers Flow
    suspend fun refresh() {
        val remoteUsers = userApi.getUsers()
        userDao.insertUsers(remoteUsers.map { it.toEntity() })
    }
}

Important: Room queries on Flow run on the I/O dispatcher internally. But if you're collecting and doing other work, use .flowOn(Dispatchers.IO) explicitly in the repository, and collect on the main thread in the ViewModel.

One-shot vs reactive:

  • suspend fun DAO functions: one-shot, coroutine-based
  • Flow<T> DAO functions: reactive, long-lived observation
  • Use Flow for anything the UI displays live; use suspend fun for write operations

Under the hood

The generated DAO implementation wraps the query in CoroutinesRoom.createFlow(...), which builds a Flow backed by a callbackFlow/channel and registers an InvalidationTracker.Observer for the tables named in the query. The tracker doesn't watch rows — it installs temporary SQLite triggers (AFTER INSERT/UPDATE/DELETE) that write the modified table's id into an internal room_table_modification_log table. After each transaction commits, InvalidationTracker.refreshVersionsAsync() runs a query against that log on the I/O executor, computes the set of invalidated table ids, and fires the matching observers, which send a signal down the channel that causes the collector to re-run the query suspendingly.

INSERT INTO users ...                 -- app write
  → AFTER INSERT trigger fires
      → INSERT INTO room_table_modification_log (table_id=<users>)
  → txn commits
      → refreshVersionsAsync(): SELECT changed table_ids from log
          → observer for "users" notified
              → channel.trySend(Unit)
                  → Flow collector re-executes SELECT, emits new List

Because invalidation is table-scoped, any write to users re-triggers the Flow even if the visible result is identical — chaining .distinctUntilChanged() collapses those into a single emission downstream.

DataStore

🎤 Say it out loud (~30–45s): "DataStore is the modern replacement for SharedPreferences — same key-value job, but coroutine- and Flow-based, so all I/O is async, off the main thread, and errors surface through the Flow instead of being silently swallowed. The detail I always mention is that it's not a drop-in: there's no synchronous read, every read is a Flow and every write a suspend function, and it serializes all writes through a single actor so you get transactional, last-write-wins consistency. I reach for Preferences DataStore for loose key-value and Proto DataStore when the shape evolves and I want compile-time type safety."

DataStore is the modern replacement for SharedPreferences — it does the same key-value job but uses coroutines and Flow throughout, so all I/O is async, off the main thread, and errors surface properly instead of silently failing.

Two variants:

Preferences DataStore — for untyped key-value data (analogous to SharedPreferences):

val Context.dataStore by preferencesDataStore(name = "settings")

// Keys
val DARK_MODE_KEY = booleanPreferencesKey("dark_mode")
val USER_ID_KEY = stringPreferencesKey("user_id")
val THEME_KEY = intPreferencesKey("theme")

// Read (returns Flow — always up-to-date)
val isDarkMode: Flow<Boolean> = context.dataStore.data
    .map { prefs -> prefs[DARK_MODE_KEY] ?: false }

// Write
suspend fun setDarkMode(enabled: Boolean) {
    context.dataStore.edit { prefs ->
        prefs[DARK_MODE_KEY] = enabled
    }
}

Proto DataStore — for typed, schema-validated data using Protocol Buffers:

// user_settings.proto
syntax = "proto3";
message UserSettings {
    bool dark_mode = 1;
    string user_id = 2;
    int32 theme = 3;
}
object UserSettingsSerializer : Serializer<UserSettings> {
    override val defaultValue = UserSettings.getDefaultInstance()
    override suspend fun readFrom(input: InputStream): UserSettings =
        UserSettings.parseFrom(input)
    override suspend fun writeTo(t: UserSettings, output: OutputStream) =
        t.writeTo(output)
}

val Context.userSettingsDataStore by dataStore(
    fileName = "user_settings.pb",
    serializer = UserSettingsSerializer
)

// Read
val settings: Flow<UserSettings> = context.userSettingsDataStore.data

// Write
suspend fun setDarkMode(enabled: Boolean) {
    context.userSettingsDataStore.updateData { current ->
        current.toBuilder().setDarkMode(enabled).build()
    }
}

DataStore vs SharedPreferences:

Aspect SharedPreferences DataStore

Error handlingSilent failuresThrows IOException via Flow

When to use each:

  • SharedPreferences: Only when modifying legacy code that already uses it; migrate incrementally.
  • Preferences DataStore: Simple key-value user settings, feature flags, lightweight state.
  • Proto DataStore: Structured settings that evolve over time; need type safety and schema.
  • Room: Anything with relational structure, queries, or collections.

Under the hood

DataStore is built on a SingleProcessDataStore that funnels every read and write through one internal actor coroutine (a SimpleActor draining a message queue), which is what guarantees ordering and atomicity without locks on the caller. The data Flow is a flow { ... } that emits the in-memory cached state plus updates broadcast over an internal MutableStateFlow/channel; on first collection it reads the file once. A write via updateData reads current state, applies your transform, and then writes to a temporary file that is fsync'd and atomically rename()d over the real file — so a crash mid-write can't corrupt the store (rename is atomic at the filesystem level). Cross-process changes are detected via a file lock plus checking the file's version, which is why the default SingleProcessDataStore is explicitly single-process.

updateData { transform }
  → actor enqueues the write
      → read current data (from cache)
      → newData = transform(current)
      → serializer.writeTo(newData, tmpFile)
      → tmpFile.fsync()
      → tmpFile.renameTo(realFile)   // atomic swap
      → downstreamFlow.emit(newData) // all collectors observe new value

Because the file is rewritten in full on every write, DataStore is meant for small payloads — not large or high-frequency data, which belongs in Room.

SharedPreferences Legacy

🎤 Say it out loud (~30–45s): "SharedPreferences is the original key-value store backed by an XML file. The thing I flag is that the entire file is parsed into an in-memory HashMap on first access, and that first load can block — getSharedPreferences returns immediately but the first getter blocks on the load latch. apply() writes the in-memory map synchronously then flushes to disk on a background thread, while commit() blocks the caller on disk I/O and can ANR. It's fine to maintain in legacy code, but I migrate to DataStore when I touch it."

SharedPreferences is the original Android key-value store — it writes to XML files and is still common in legacy codebases, but it has enough problems that all new code should use DataStore instead.

val prefs = context.getSharedPreferences("app_prefs", Context.MODE_PRIVATE)

// Read
val userId = prefs.getString("user_id", null)
val count = prefs.getInt("count", 0)

// Write
prefs.edit()
    .putString("user_id", "abc123")
    .putInt("count", 42)
    .apply()  // async write; prefer this over commit()
    // .commit()  // synchronous; blocks calling thread; only for critical data before process kill

Failure modes:

  • commit() on main thread → ANR risk
  • Not safe for concurrent writes from multiple threads — race conditions
  • No mechanism for observing changes in coroutines (must use OnSharedPreferenceChangeListener with manual lifecycle)
  • XML parsing overhead — loads entire file on first access

Migration to DataStore:

val migration = SharedPreferencesMigration(context, "old_prefs_name")
val Context.dataStore by preferencesDataStore(
    name = "new_prefs",
    produceMigrations = { context ->
        listOf(SharedPreferencesMigration(context, "old_prefs_name"))
    }
)

Under the hood

The framework implementation is SharedPreferencesImpl. On creation it spawns a background thread that parses the XML file into a HashMap<String, Object> held in memory; getters block on a loaded latch until that parse finishes, then read straight from the map. An edit() returns an EditorImpl that buffers your changes in a local map. On apply(), it first commits the changes to the in-memory map synchronously (so subsequent reads see them immediately), then enqueues the disk write to a single background thread via QueuedWork — and that pending write is force-drained on Activity.onPause/Service lifecycle transitions, which is a hidden source of jank if many apply() calls are queued. commit() does the same memory update but performs the disk write on the calling thread and returns its boolean success.

apply():
  memoryMap.putAll(editedValues)   // synchronous, visible to readers now
  QueuedWork.enqueue { writeToDiskAtomically() }   // background thread
  → write to <name>.xml.bak, fsync, rename over <name>.xml

commit():
  memoryMap.putAll(editedValues)
  writeToDiskAtomically()          // ON CALLING THREAD → ANR if main
  return success

The disk write itself is atomic via a backup file (.bak) and rename, but there is no transactional read API and no built-in coroutine observation — which is precisely what DataStore adds.

Under the hood

Scoped storage is enforced by the platform's MediaProvider and the lower-level filesystem-in-userspace (FUSE) layer: in Android 11+, the external volume is mounted through a FUSE daemon so that even raw File access to other apps' media is intercepted and permission-checked against MediaStore rather than relying on the old READ/WRITE_EXTERNAL_STORAGE permission. 10.3 Offline-First Design

Single Source of Truth

🎤 Say it out loud (~30–45s): "Single source of truth means one place — usually Room — is the definitive source the UI reads from, and the network is just a mechanism to push updates into that place, never something the UI reads directly. The payoff is that cache invalidation becomes free: I write fresh data to the DB, the DB Flow notifies every observer, and the UI updates with no explicit notification wiring. The anti-pattern interviewers want me to call out is the ViewModel holding its own copy and overwriting it with a network result — that creates two sources of truth and a race between the cached value and the fresh one."

The single source of truth is the principle that one place — typically Room — is the definitive data source for the UI, and the network is just a mechanism to push updates into that place, never a direct source.

Why it matters:

  • The UI always reads from the local DB, so there are no loading spinners for data you've already cached.
  • State is predictable — there are no race conditions between a network response landing and what the UI is displaying.
  • Offline support is natural — the local DB always has something to show, even with no connectivity.
  • Error handling is simpler — network failures update DB state or surface a flag, rather than being wired directly into UI state.

Implementation pattern:

Network Response → Repository → Room DB → Flow → ViewModel → UI
                                   ↑
                         (UI reads ONLY from here)

The ViewModel never holds a copy of data; it only transforms what comes from the Room Flow. The repository orchestrates: fetch from network → write to Room → Room Flow notifies UI.

Contrast with non-SSOT pattern (anti-pattern):

// BAD: two sources of data → UI can show inconsistent state
viewModelScope.launch {
    _state.update { it.copy(users = dao.getAll()) }  // initial load from DB
    val fresh = api.getUsers()
    _state.update { it.copy(users = fresh) }          // overwrite with network
}

The SSOT approach instead: write fresh data to DB, let the DB Flow update the state.

Under the hood

There's no special framework machinery here — SSOT is an architectural discipline that leans on the reactive primitives underneath. The mechanism that makes it work is Room's InvalidationTracker firing the observing Flow after a committed write, combined with stateIn/StateFlow in the ViewModel acting as the conflation point so the UI only ever holds one current value. Because every mutation path terminates in a single DB write and every read path originates from a single DB Flow, the data forms a unidirectional cycle with exactly one writer surface and one observable source — eliminating the two-writer race the anti-pattern creates.

                 write
network ──► repo ──────► Room (the ONE source)
                          │ InvalidationTracker fires
                          ▼
                        Flow ──► stateIn() ──► StateFlow ──► UI
       (no UI→network read path; UI only collects the StateFlow)

The conceptual guarantee: state changes are serialized through the DB transaction log, so "latest committed write wins" is the only ordering the UI can ever observe — there is no second in-memory copy to drift out of sync.

Cache Invalidation

🎤 Say it out loud (~30–45s): "Cache invalidation is deciding when local data is stale enough to refetch, and there's no single right answer — I usually combine strategies. TTL is cheap and client-only; ETag/Last-Modified lets the server tell me 'nothing changed' with a 304 so I save bandwidth; event-driven via push lets me invalidate the instant something changes server-side. The gotcha interviewers probe is that with Room I lean on stale-while-revalidate — I render the cached data immediately and refresh in the background, because making the user stare at a spinner defeats the point of caching."

Cache invalidation is the problem of knowing when locally cached data is stale enough to warrant a fresh network fetch — and it turns out there are several complementary strategies, each appropriate in different situations.

Strategies:

1. TTL (Time-To-Live):

@Entity
data class FeedItemEntity(
    @PrimaryKey val id: String,
    val content: String,
    val fetchedAt: Long = System.currentTimeMillis()
)

fun FeedItemEntity.isStale(ttlMs: Long = 5 * 60 * 1000): Boolean {
    return System.currentTimeMillis() - fetchedAt > ttlMs
}

Under the hood

ETag-based revalidation is conditional-request HTTP defined in RFC 7232. The server computes a validator (an opaque ETag string — typically a hash or version of the representation) and the client echoes it back in If-None-Match. The origin compares it to the current validator and, if they match, returns 304 Not Modified with empty body — saving payload transfer but still costing a round trip. OkHttp's Cache automates this entirely: it stores responses keyed by URL on disk (a journaled DiskLruCache), and on a cache hit that's stale it issues the conditional request for you, splicing the cached body onto a fresh 304's headers.

1st request:  GET /feed                          → 200, ETag: "abc123", body stored on disk
later (stale): GET /feed  If-None-Match: "abc123" → 304 (no body)  → OkHttp serves disk copy

The Room "Flow auto-updates" mechanism is separate: Room registers an InvalidationTracker that installs SQLite triggers on the queried tables. Sync Strategy

🎤 Say it out loud (~30–45s): "A sync strategy is how I keep local and server data consistent, and I split it into read sync — server to local, which is basically fetch-and-overwrite — and write sync, which is harder because offline mutations have to reach the server eventually and survive failures. For small datasets I'll do a full sync; for anything large I want delta sync where the server returns only what changed since a timestamp. The nuance interviewers want is the trigger story: I don't just sync on a timer — WorkManager periodic work is capped at 15 minutes, so I also sync on app foreground, on FCM push, and on a ConnectivityManager network-available callback."

A sync strategy is how you keep local data in sync with the server — especially important when the user has made mutations while offline that now need to reach the server.

Read sync — server to local — is straightforward: fetch and overwrite. Write sync — local to server — is more complex because local changes need to reach the server eventually, and failures have to be handled.

Full sync (simple, high bandwidth):

suspend fun fullSync() {
    val remoteData = api.getAllItems()
    database.withTransaction {
        dao.deleteAll()
        dao.insertAll(remoteData.map { it.toEntity() })
    }
}

Good for small datasets. Bad for large datasets or frequent updates.

Delta sync (incremental):

    database.withTransaction {
        dao.upsertAll(delta.updated.map { it.toEntity() })
        dao.deleteByIds(delta.deleted)
        preferences.setLastSyncTime(System.currentTimeMillis())
    }
}

Requires server support. More complex but scalable.

  1. Push local changes → server
  2. Pull server changes → local
  3. Merge conflicts

Under the hood

database.withTransaction { } is what makes a sync atomic. Room opens a SQLite transaction (BEGIN), runs your block, then COMMITs — or ROLLBACKs if the block throws. Critically, it uses a coroutine-aware transaction: it acquires a dedicated thread from the transaction executor and pins the suspending block to it via a TransactionElement in the coroutine context, so all the DAO calls inside run on the same connection that holds the lock. Without this, a deleteAll() followed by a crashing insertAll() would wipe your cache and leave it empty.

The 15-minute floor on PeriodicWorkRequest is a hard JobScheduler constraint, not a WorkManager choice — MIN_PERIODIC_INTERVAL_MILLIS is 900000ms. Conflict Resolution

🎤 Say it out loud (~30–45s): "A conflict is when the same resource was edited both locally offline and on the server, so the two diverged. Detection is usually optimistic locking — each entity carries a version or updatedAt, the client sends the version it last saw, and the server returns 409 if its stored version moved on. For resolution I pick a policy by domain: last-write-wins for preferences, server-wins for anything authoritative like payments, field-level merge when edits touch different fields, and user-assisted for documents. The thing I call out is that LWW silently drops data — it's only acceptable when losing a write is genuinely fine."

A conflict exists when a resource has been modified both locally while offline and independently on the server — and the two versions are now inconsistent with each other.

Conflict detection:

  • Server-side versioning: each entity carries a version integer or updatedAt timestamp. The client sends the version it last saw, and the server rejects the request if the stored version is different.
  • Optimistic locking: a PUT /items/1 body includes {"version": 5, ...}. The server returns 409 Conflict if the stored version is no longer 5.

Resolution strategies:

1. Last-write-wins (LWW): The most recent write (by timestamp) wins. Simple but can silently discard changes. Appropriate for user settings, preferences.

2. Server-wins: On conflict, discard local changes and use server data. Simple; appropriate when server data is authoritative (financial transactions).

fun resolveConflict(local: ItemEntity, remote: ItemEntity): ItemEntity = remote

3. Client-wins: Local changes always win. Rare; appropriate only when client is the single writer.

4. Merge: For field-level conflicts (e.g., user updates name, server updates email independently) — merge non-conflicting fields. Requires CRDT or OT for true merge.

fun mergeItems(local: ItemEntity, remote: ItemEntity): ItemEntity {
    return remote.copy(
        name = if (local.nameModifiedAt > remote.nameModifiedAt) local.name else remote.name,
        email = if (local.emailModifiedAt > remote.emailModifiedAt) local.email else remote.email
    )
}

5. User-assisted: Show conflict UI and let the user choose. Appropriate for document editors (Google Docs model).

Android pattern with Room:

@Entity
data class ItemEntity(
    @PrimaryKey val id: String,
    val content: String,
    val serverVersion: Int,
    val isDirty: Boolean,  // true = modified locally, not yet synced
    val localModifiedAt: Long
)

suspend fun sync() {
    val dirtyItems = dao.getDirtyItems()
    dirtyItems.forEach { item ->
        try {
            val response = api.updateItem(item.id, item.toRequest(), expectedVersion = item.serverVersion)
            dao.upsert(response.toEntity().copy(isDirty = false))
        } catch (e: HttpException) {
            if (e.code() == 409) {
                val serverItem = api.getItem(item.id)
                val resolved = resolveConflict(item, serverItem.toEntity())
                dao.upsert(resolved)
            }
        }
    }
}

Under the hood

Optimistic locking is enforced atomically on the server with a compare-and-swap, not a read-then-write. The canonical implementation is a conditional UPDATE: UPDATE items SET ..., version = version + 1 WHERE id = ? AND version = ?. SQL row locking makes that single statement atomic, so the affected-row count tells you whether you won: 1 row means success, 0 rows means someone else already incremented the version — that's the 409. Doing a separate SELECT version then UPDATE would re-introduce a race window between the two.

True field-level merge needs more than timestamps because wall-clock comparison across devices is unreliable (clock skew, no global ordering). CRDTs solve this with data structures whose merge operation is commutative, associative, and idempotent — e.g., a Last-Writer-Wins register tagged with a Lamport/hybrid-logical clock, or an OR-Set for collections — so any two replicas that have seen the same set of updates converge to the same state regardless of arrival order. Operational Transformation (the older Google Docs approach) instead transforms each incoming operation against concurrent ones so intent is preserved.

Lamport clock: each node keeps a counter; on any event counter++ ;
on receiving a message, counter = max(local, received) + 1
→ gives a total order that respects causality without synced wall clocks

Optimistic Updates

🎤 Say it out loud (~30–45s): "An optimistic update means I write the user's action to the local DB and UI immediately, before the server confirms, then reconcile when the response lands. It kills perceived latency for likes, bookmarks, deletes — the UI feels instant. The whole game is the failure path: I have to remember the previous state so I can roll back on a network error or a 403, and if the server returns a different state than I assumed I overwrite local with the server's truth. I keep it for single idempotent actions — for multi-step things like booking a slot, the rollback gets hairy, so I'd use an explicit loading state instead."

An optimistic update means applying a user action immediately to the local database and UI before the server has confirmed it — then reconciling once the server responds. The reason to do this is that it eliminates perceived latency for common operations like likes, bookmarks, and deletes. The UI feels instantaneous.

Pattern:

class BookmarkViewModel(
    private val bookmarkRepository: BookmarkRepository
) : ViewModel() {

    fun toggleBookmark(postId: String, currentlyBookmarked: Boolean) {
        viewModelScope.launch {
            // 1. Optimistically update local DB immediately
            bookmarkRepository.setBookmarked(postId, !currentlyBookmarked)

            // 2. Send to server
            try {
                bookmarkRepository.syncBookmark(postId, !currentlyBookmarked)
            } catch (e: Exception) {
                // 3. Rollback on failure
                bookmarkRepository.setBookmarked(postId, currentlyBookmarked)
                _events.emit(BookmarkEvent.SyncFailed)
            }
        }
    }
}
// Repository
suspend fun setBookmarked(postId: String, bookmarked: Boolean) {
    bookmarkDao.setBookmarked(postId, bookmarked)  // immediate local write → UI updates via Flow
}

suspend fun syncBookmark(postId: String, bookmarked: Boolean) {
    if (bookmarked) {
        api.addBookmark(postId)
    } else {
        api.removeBookmark(postId)
    }
}

Failure modes:

  • Network failure → rollback required
  • Server rejects action (e.g., 403 — not authorized) → rollback + show error
  • Server returns different state (e.g., post was deleted) → update local DB with server response

Complex operations: For multi-step operations (booking a slot), optimistic updates are riskier. Use explicit loading states instead.

Under the hood

What makes the UI flip "instantly" is the Room → Flow → recomposition pipeline, and it's worth knowing where the latency actually goes. The DAO write hits SQLite, Room's InvalidationTracker fires the table-modification trigger, the observing Flow re-queries and emits on a background dispatcher, and collectAsStateWithLifecycle writes the new value into a Compose MutableState. That state write calls into the Snapshot system, which records the change and notifies the Recomposer; the affected composables are scheduled and re-run on the next frame. So "immediate" is really "next frame" (~16ms at 60fps) — fast enough to feel instant, but it is still asynchronous, which is why the rollback must re-issue another write rather than mutate UI directly.

The rollback correctness hinges on capturing currentlyBookmarked as a value before the optimistic write. If you instead re-read state inside the catch block, a second concurrent toggle could have changed it, and you'd roll back to the wrong value. This is the classic compare-the-snapshot-you-saw pattern.

toggle() → DAO write (new) ──┐
                            ├─ Flow emits → Compose State → recompose (frame N)
network fails ──────────────┘
catch → DAO write (old, captured) → Flow emits → recompose (frame N+k)

Retry Queue

🎤 Say it out loud (~30–45s): "A retry queue is a durable list of failed mutations I replay once connectivity comes back. The word that matters is durable — if I keep it in memory and the process gets killed while offline, those writes are gone, so the queue lives in Room to survive process death. I record an operation type, a serialized payload, and an attempt count, cap retries with a max-attempts so I don't loop forever on a poison message, and drain it from a WorkManager job gated on a network constraint. The subtlety is that handlers must be idempotent, because a retry can fire after the server already succeeded but the response was lost."

A retry queue is a persistent store of failed mutations that should be retried once connectivity is restored. The key word is persistent — if the app is killed while offline, any in-memory queue is lost, so the queue must live in Room to survive process death.

@Entity(tableName = "pending_operations")
data class PendingOperationEntity(
    @PrimaryKey val id: String = UUID.randomUUID().toString(),
    val operationType: String,  // "BOOKMARK_ADD", "POST_CREATE", etc.

    val attempts: Int = 0,
    val lastAttemptAt: Long? = null
)

@Dao

    @Query("SELECT * FROM pending_operations ORDER BY created_at ASC")
    suspend fun getAll(): List<PendingOperationEntity>

    @Insert
    suspend fun insert(op: PendingOperationEntity)

    @Delete
    suspend fun delete(op: PendingOperationEntity)

class RetryQueueProcessor(
    private val dao: PendingOperationDao,
    private val handlers: Map<String, OperationHandler>
) {
    suspend fun processQueue() {
        val pending = dao.getAll()
        pending.forEach { op ->
            if (op.attempts >= MAX_ATTEMPTS) {
                dao.delete(op)
                return@forEach
            }
            try {
                handlers[op.operationType]?.handle(op.payload)
                dao.delete(op)
            } catch (e: Exception) {
                dao.incrementAttempts(op.id)
            }
        }
    }
}

WorkManager integration (see below): The queue processor is triggered by WorkManager on network availability.

Under the hood

Durability here is really SQLite's write-ahead-log guarantee. When Room commits the @Insert, SQLite (in WAL mode, Room's default) appends the change to the -wal file and fsyncs; once that fsync returns the row survives a process kill or power loss, because on next open SQLite replays the WAL into the main db. That's why the queue outlives process death where an in-memory ArrayList would not.

The retry cadence is driven by WorkManager's own backoff machinery. When a CoroutineWorker returns Result.retry(), WorkManager reschedules with exponential (or linear) backoff starting at WorkRequest.MIN_BACKOFF_MILLIS (10s), and JobScheduler only dispatches it when the attached NetworkType.CONNECTED constraint is satisfied — so you're not polling, the system wakes you when a network appears. The MAX_ATTEMPTS guard plus monotonically increasing attempts column is what prevents a "poison" payload (e.g., a permanently-rejected 400) from being retried forever. Idempotency is the unstated requirement: the client-generated id (a UUID) doubles as an idempotency key the server can dedupe on, so a replay after a lost-but-successful response doesn't create a duplicate.

worker fails → Result.retry() → backoff = 10s, 20s, 40s... (capped)
              ↑ JobScheduler holds until NetworkType.CONNECTED is met

NetworkBoundResource Pattern

🎤 Say it out loud (~30–45s): "NetworkBoundResource is the classic Google pattern for coordinating cache and network behind a single Flow — it emits the local data immediately, decides whether the cache is stale, fetches in the background if so, writes the result back to the DB, and then re-emits from the DB so the database stays the single source of truth. The subtle part is that the UI subscribes only to the DB query, not the network — the network write is what drives the emission, so you never bind directly to the fetch result. The gotcha interviewers love is error handling: on a failed fetch you still emit the stale cached data alongside the error, rather than dropping the user into an empty error screen."

NetworkBoundResource is a pattern from the Google Architecture Blueprints — pre-Paging-3 era — that coordinates cache and network in a single Flow: it always shows local data first, fetches fresh data from the network in parallel if needed, and writes the result back to the local cache.

Modern Kotlin implementation using Flow:

fun <LocalType, RemoteType> networkBoundResource(
    query: () -> Flow<LocalType>,           // DB query
    fetch: suspend () -> RemoteType,        // Network call
    saveFetchResult: suspend (RemoteType) -> Unit,  // Write to DB
    shouldFetch: (LocalType) -> Boolean = { true }, // Cache validity check
    onFetchFailed: (Throwable) -> Unit = {}
): Flow<Resource<LocalType>> = flow {

    emit(Resource.Loading())

    val data = query().first()

    val flow = if (shouldFetch(data)) {
        emit(Resource.Loading(data))  // Show cached data while fetching
        try {
            saveFetchResult(fetch())
            query().map { Resource.Success(it) }
        } catch (t: Throwable) {
            onFetchFailed(t)
            query().map { Resource.Error(t, it) }  // Show error + stale cached data
        }
    } else {
        query().map { Resource.Success(it) }
    }

    emitAll(flow)
}

sealed class Resource<T>(val data: T? = null, val error: Throwable? = null) {
    class Success<T>(data: T) : Resource<T>(data)
    class Error<T>(error: Throwable, data: T? = null) : Resource<T>(data, error)
    class Loading<T>(data: T? = null) : Resource<T>(data)
}

Usage in repository:

Under the hood

The whole pattern is built on cold Flow semantics and the flow { } builder. flow { } returns a cold flow whose block runs anew inside each collector's coroutine when collect is called — nothing executes until collection. Inside that block, query().first() opens the DB flow, suspends until the first value arrives, then cancels the upstream subscription, giving you a one-shot read of the current cache. The terminal emitAll(flow) is the key mechanism: it forwards every emission of the inner query().map { ... } flow into the outer collector. Because that inner flow is a Room-observable query, Room's InvalidationTracker registers an Observer on the affected tables; when saveFetchResult commits its withTransaction, Room's update hook fires, the tracker marks the tables dirty, and the observable query re-runs and re-emits — which is exactly how the post-fetch DB write "pushes" a fresh Resource.Success to the UI without the collector ever touching the network result directly.

collect()
  └─ flow { } block starts (per-collector)
       emit(Loading)               -> reaches collector immediately
       query().first()             -> reads current cache, then cancels query
       if shouldFetch:
         emit(Loading(cache))
         fetch() (suspends on network)
         saveFetchResult()         -> DB transaction commit
                                      -> Room InvalidationTracker marks table dirty
         emitAll(query().map{...})  -> observable query re-runs on each table change

Suspension is cooperative: fetch() parks the coroutine at a suspension point (a state-machine COROUTINE_SUSPENDED return from the compiler-generated continuation) without blocking the underlying thread, so the dispatcher's thread is free while the network is in flight.

class SyncWorker(
    context: Context,
    params: WorkerParameters,
    private val syncRepository: SyncRepository
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        return try {
            syncRepository.sync()
            Result.success()
        } catch (e: Exception) {
            if (runAttemptCount < 3) {
                Result.retry()  // WorkManager will retry with exponential backoff
            } else {
                Result.failure(workDataOf("error" to e.message))
            }
        }
    }

    companion object {
        fun buildRequest(): PeriodicWorkRequest {
            val constraints = Constraints.Builder()
                .setRequiredNetworkType(NetworkType.CONNECTED)
                .build()

            return PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
                .setConstraints(constraints)
                .setBackoffCriteria(BackoffPolicy.EXPEDITED, 10, TimeUnit.SECONDS)
                .build()
        }
    }
}

Under the hood

WorkManager is a façade over a persisted work graph plus a platform scheduler. When you enqueue, it serializes the request into its own Room database (androidx.work.workdb) — the WorkSpec table holds the worker class name, constraints, backoff policy, current State, and run_attempt_count; dependency rows model beginWith().then() chains. Persisting to Room is what makes work survive process death and reboot: a BOOT_COMPLETED RescheduleReceiver re-reads the DB on restart. WorkManager then delegates to a Scheduler chosen by API level — JobScheduler on API 23+ (each WorkSpec becomes a JobInfo whose constraints map onto JobScheduler constraints), and the GreedyScheduler for in-process, unconstrained immediate work. Constraints are watched by ConstraintController/ConstraintTracker objects (network via ConnectivityManager callbacks, charging via battery broadcasts); the work only moves to RUNNING once all controllers report satisfied.

       └─ Scheduler chosen by API:
            API 23+  -> JobScheduler (WorkSpec -> JobInfo + constraints)
            in-proc  -> GreedyScheduler (immediate, ProcessLifecycle-aware)
       └─ ConstraintTrackers gate RUNNING (network/charging/idle/storage)
       └─ Result.retry() -> state RETRY, run_attempt_count++,
                            next run = backoff(policy, attempt) [10s..5h clamp]

A CoroutineWorker runs doWork() on a Job tied to a Dispatchers.Default-backed scope; Result.retry() flips the WorkSpec to ENQUEUED/RETRY, increments run_attempt_count, and computes the next delay from the BackoffPolicy (linear or exponential), clamped between a 10-second floor and a 5-hour ceiling. Periodic work is never "exactly" periodic — JobScheduler batches and defers jobs to honor Doze maintenance windows and App Standby buckets, with an enforced minimum interval of 15 minutes.

Pagination with Local Cache

🎤 Say it out loud (~30–45s): "Paging 3 with RemoteMediator is how you do offline-capable infinite scroll where Room is the single source of truth. The PagingSource reads pages straight out of Room, and RemoteMediator's only job is to keep Room topped up — Paging calls its load with APPEND when the user scrolls near the end, and I fetch the next page and write it back in a transaction. The cursor for 'what page is next' lives in a RemoteKeys table because the network page numbers are separate from Room's positional keys. The gotcha is that there are two independent load states — loadState.source for Room and loadState.mediator for the network — so an offline error surfaces in the mediator state while the source keeps happily serving cached pages."

RemoteMediator is Paging 3's mechanism for combining a Room-backed PagingSource with network fetching — Room is the source of truth for what the UI displays, and RemoteMediator is responsible for populating and refreshing Room as the user scrolls.

Architecture:

UI → PagingData (from Room PagingSource)
           ↑
       Room DB ← RemoteMediator (fetches from network, writes to Room)

RemoteMediator implementation:

@OptIn(ExperimentalPagingApi::class)
class FeedRemoteMediator(
    private val database: AppDatabase,
    private val api: FeedApi
) : RemoteMediator<Int, FeedItemEntity>() {

    override suspend fun initialize(): InitializeAction {
        val lastRefresh = database.remoteKeyDao().getLastRefresh()
        return if (System.currentTimeMillis() - (lastRefresh ?: 0) < CACHE_TIMEOUT) {
            InitializeAction.SKIP_INITIAL_REFRESH
        } else {
            InitializeAction.LAUNCH_INITIAL_REFRESH
        }
    }

    override suspend fun load(
        loadType: LoadType,
        state: PagingState<Int, FeedItemEntity>
    ): MediatorResult {
        return try {
            val page = when (loadType) {
                LoadType.REFRESH -> 1
                LoadType.PREPEND -> return MediatorResult.Success(endOfPaginationReached = true)
                LoadType.APPEND -> {
                    val lastPage = database.remoteKeyDao().getLastPage()
                        ?: return MediatorResult.Success(endOfPaginationReached = false)
                    lastPage + 1
                }
            }

            val response = api.getFeed(page = page, pageSize = state.config.pageSize)

            database.withTransaction {
                if (loadType == LoadType.REFRESH) {
                    database.feedDao().clearAll()
                    database.remoteKeyDao().clearAll()
                }
                database.feedDao().insertAll(response.items.map { it.toEntity() })
                database.remoteKeyDao().insert(
                    RemoteKey(page = page, lastRefresh = System.currentTimeMillis())
                )
            }

            MediatorResult.Success(endOfPaginationReached = response.items.size < state.config.pageSize)
        } catch (e: IOException) {
            MediatorResult.Error(e)
        } catch (e: HttpException) {
            MediatorResult.Error(e)
        }
    }

    companion object {
        const val CACHE_TIMEOUT = 30 * 60 * 1000L // 30 minutes
    }
}

RemoteKey table: Stores the page cursor for each list type, so RemoteMediator.load(APPEND) knows what page to fetch next. Can also store nextCursor for cursor-based pagination.

Offline behavior: When the network is unavailable, RemoteMediator.load() returns MediatorResult.Error. The PagingSource still serves Room data. The UI should handle the LoadState.Error in loadState.mediator vs loadState.source separately.

Under the hood

Pager.flow is a cold flow of PagingData; each PagingData wraps a PageFetcherSnapshot driven by a PageFetcher. When you annotate a DAO method to return PagingSource<Int, FeedItemEntity>, Room's annotation processor generates a LimitOffsetPagingSource subclass — its load() issues a SELECT ... LIMIT ? OFFSET ? plus a COUNT(*) query, and it registers with Room's InvalidationTracker so that any write to feed_items invalidates the active source. Invalidation is the linchpin: when RemoteMediator commits its withTransaction, the tracker fires, the current PagingSource is marked invalid, the PageFetcher tears it down and asks the pagingSourceFactory for a fresh one, and the new pages flow to the UI — that's why writing to Room is all the mediator has to do. The two LoadState machines (source from the PagingSource, mediator from RemoteMediator) are combined into a CombinedLoadStates so the UI can distinguish a DB read error from a network refresh error.

list scrolled near end (within prefetchDistance)
  └─ PageFetcherSnapshot detects boundary
       └─ source PagingSource.load(APPEND)  -> SELECT ... LIMIT/OFFSET from Room
       └─ if near end of cached data: RemoteMediator.load(APPEND)
             reads RemoteKeys -> next page number
             api.getFeed(page) -> network
             withTransaction { insertAll; remoteKeys.insert }
             -> InvalidationTracker fires
             -> PagingSource invalidated -> factory builds new source
             -> fresh pages emitted via PagingData

load() is suspending and is called sequentially by the paging machinery — Paging will not issue a second load for the same LoadType while one is in flight, which is why the mediator doesn't need its own mutex around the page cursor. cachedIn(viewModelScope) makes the otherwise-cold PagingData flow a multicast, shareable conflated stream so a config change (re-collection) replays the already-loaded pages instead of refetching from page 1.

Interview Angles: Offline-First

Q: Design an offline-first feed.

"Room is the single source of truth. The ViewModel exposes a StateFlow derived from a Room Flow, and the UI only ever reads from that — it has no idea whether the data came from the network or the cache. The repository has two operations: observe() returns the Room Flow, and refresh() hits the network and writes to Room, which automatically re-emits through the Flow. For paginated feeds I use Paging 3 with RemoteMediator — it keeps Room populated as the user scrolls, so the UI is always driven by Room pages. Background freshness comes from WorkManager, which periodically triggers a sync when the device has connectivity. For cache invalidation I use a fetchedAt timestamp on entities, or ETags if the server supports them. For mutations like likes and bookmarks, I write optimistically to Room immediately and then sync to the network in the background with a Room-backed retry queue, so mutations survive process death."

Q: How do you sync local changes?

"I mark every local mutation with isDirty = true in Room at the point of write. When connectivity is restored — either via a ConnectivityManager.NetworkCallback or a WorkManager job that runs under a NetworkType.CONNECTED constraint — I query all dirty rows and send them to the server one by one. On success I mark the row isDirty = false. On failure I increment an attempts counter and retry with exponential backoff. Because the queue lives in Room, it survives process death — so even if the user force-closes the app mid-sync, the pending operations are still there when they reopen it. If attempts exceed the maximum I surface an error to the user rather than silently discarding the change."

Q: What happens when server and local data conflict?

"I detect conflicts with optimistic locking — every write includes a version field, and the server returns 409 Conflict if the stored version doesn't match. On a 409, the resolution depends on the business domain: for user preferences, last-write-wins by timestamp is usually fine; for financial or booking data, the server wins because it's the authoritative record; for profile fields that the user edited independently, a field-level merge is possible if I track a modifiedAt timestamp per field. After resolution, whatever the canonical state is gets written to Room and emits through the Flow. For genuinely complex conflicts I surface it to the user — show them both versions and let them choose."

Q: How do you avoid stale data?

"I layer several strategies. First, every Room entity has a fetchedAt timestamp, and the repository checks it on load — if it's expired, it triggers a refresh in the background while still showing the cached data immediately. Second, I use ETag-based revalidation when the server supports it: send If-None-Match with the cached ETag, and if nothing changed the server returns a 304 with near-zero bandwidth cost. Third, FCM push notifications can trigger an immediate refresh when the server knows data has changed. Fourth, pull-to-refresh as a user-initiated fallback. And fifth, I refresh on onResume() or when the lifecycle hits STARTED, so the feed is never stale just because the user left the app for a few minutes. The model that ties all of this together is stale-while-revalidate: show cached data immediately, refresh in the background, and let Room's Flow deliver the update automatically when it arrives."
