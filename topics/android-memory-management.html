6.1 JVM/ART Memory Basics

Stack vs Heap

Definition

The stack and heap are the two distinct memory regions the JVM uses, and understanding the difference matters a lot for Android because it determines both lifetime and thread safety.

Dimension Stack Heap
What lives therePrimitive local variables, method frames, object referencesAll object instances and arrays
AllocationAutomatic, LIFO, at method entryExplicit new (or Kotlin object literals), GC-managed
LifetimeExactly the enclosing method callUntil no live reference remains
SizeSmall, fixed per thread (Android default ~8 KB–1 MB per thread)Large, expandable up to the process memory limit
Thread safetyEach thread has its own stack — no sharingShared across all threads — concurrency required
SpeedVery fast (just SP register increment)Slower (allocation, possible GC)

Android / ART internals

  • ART uses a generational heap split into Young (allocation), Old (long-lived), and Large Object Space (objects > ~12 KB).
  • Stack frames for Dalvik bytecode methods are laid out by the ART interpreter or JIT/AOT-compiled native frames.
  • Stack overflow (deep recursion) throws StackOverflowError, not OutOfMemoryError.

Interview angles

Q: "If I declare val x = 5 inside a function, where does it live?"

"The value 5 lives in the current thread's stack frame — the stack is just the scratch space for whatever method is currently executing. Now if instead I write val obj = MyClass(), the reference obj is still on the stack, but the actual MyClass instance is allocated on the heap. The stack holds the pointer; the heap holds the object."

Q: "Can two threads share a stack variable?"

"No. Each thread has its own independent stack, so stack variables are private to the thread running that method. Threads can only share state through the heap — which is exactly why you need synchronization any time two threads read and write the same mutable heap object."

Object Allocation

Internals

ART allocates new objects in the Thread-Local Allocation Buffer (TLAB) — a small region carved out of Young space for each thread. TLAB allocation is near-free because it is just a pointer bump. When the TLAB fills, ART does a minor GC (Young collection), which is fast — roughly 2 to 5 ms — but still causes a brief pause.

When an object survives enough minor GCs it is promoted to Old generation, where it lives until a major GC.

Kotlin allocation pitfalls

// BAD: creates a lambda object on every call
list.forEach { it.process() }

// BETTER: if called in a tight loop, extract to a named function reference
val fn: (Item) -> Unit = { it.process() }
list.forEach(fn)

Boxing: Kotlin's Int, Long, etc. compile to primitive JVM types when possible, but generics always box — List<Int> stores Integer objects. Prefer IntArray / LongArray / SparseArray in performance-critical paths.

References and Reachability

Reachability (GC root tracing)

The key concept here is reachability. The GC starts from GC roots — currently-executing stack frames, static fields, JNI global references, and synchronization monitors — and traces every reference chain outward. Any object reachable by following references from a root is live and will not be collected. Anything the GC cannot reach from any root is eligible for collection.

GC Roots
  ├── Thread stack frames
  ├── Static fields (dangerous — they live until ClassLoader unload)
  ├── JNI global refs
  └── System classes
        └── → object A → object B → object C   (all live)

The important implication is that if you cut the reference chain — for example, by setting a static field to null — the entire sub-graph below it becomes eligible for collection.

Garbage Collection

ART GC algorithms

ART ships multiple collectors selectable at runtime:

Collector Pauses Use case
CMS (Concurrent Mark-Sweep)Short stop-the-world pausesDefault for most allocation
Generational CC (Concurrent Copying)Very shortBackground/foreground switching
Semi-spaceCompacting, longer pauseAfter transition to background

The Android lifecycle integration matters here: when an app moves to background at onStop, ART may trigger a compacting GC using the semi-space collector. That is expensive — roughly 50 to 100 ms — but acceptable because the user is not watching the screen at that point.

GC phases (simplified)

There are essentially three phases. First, Mark — the GC traces from GC roots and marks all reachable objects. Second, Sweep — it reclaims the memory of everything that was not marked. Third, in the Concurrent Mark-Sweep variant, most of that marking and sweeping runs concurrently alongside your app threads, but brief stop-the-world pauses still occur at the start of the mark phase and at the end for a final remark pass.

Reference Strengths: Strong / Weak / Soft / Phantom

Strong reference (default)

val activity: Activity = this  // strong — Activity will NOT be GC'd while this lives

A strong reference is the default — the GC will never collect an object as long as a strong reference to it exists.

Weak reference

import java.lang.ref.WeakReference

class MyCache {
    private val ref = WeakReference(someExpensiveObject)

    fun get() = ref.get()  // returns null if GC collected it
}

A weak reference tells the GC: "collect this at the next GC cycle once no strong references remain." There are two main uses in Android. First, caches and listener registrations where you don't want the cache to prevent GC. Second, holding a WeakReference<Activity> inside a Handler or background thread so that finishing the Activity does not keep it alive just because the handler still has a reference.

Soft reference

import java.lang.ref.SoftReference

val cached = SoftReference(loadBitmap())
val bmp = cached.get() ?: loadBitmap()  // reload if GC'd

A soft reference means "keep this alive as long as there's memory to spare, but collect it before throwing OOM." The GC will only collect the referent when memory is actually tight. The trade-off is that LruCache with explicit eviction is usually better, because soft references hand too much control to the GC — you cannot predict what gets evicted when.

Phantom reference

val queue = ReferenceQueue<MyObject>()
val ref = PhantomReference(obj, queue)
// obj = null  (must explicitly clear strong ref)

// In a cleanup thread:
val enqueued = queue.poll()  // non-null after GC finalizes obj

Phantom references are enqueued after the referent's finalizer runs (or would have run) and its memory is about to be reclaimed. Calling get() always returns null — you can never resurrect the object. The use case is deterministic resource cleanup as an alternative to finalize(). ART's internal Cleaner, used for native memory bookkeeping, is built on phantom references. You rarely need this in app code, but mentioning it shows depth.

Reference summary table

Type GC collects when? get() returns null? Main use
StrongNever (while reference exists)NoNormal object ownership
SoftLow memoryAfter GCMemory-sensitive caches
WeakNext GC cycleAfter GCNon-owning associations
PhantomAfter finalizationAlwaysPre-reclaim cleanup hooks

Finalizers Are Problematic

What a finalizer is

// Java-style; Kotlin discourages this
class Broken {
    protected fun finalize() {
        closeResource()  // DON'T do this
    }
}

Why finalizers are dangerous

There are five reasons to avoid them. First, non-deterministic timing — the GC decides when to call finalize(), so resources may be held for unpredictable durations. Second, resurrection risk — a finalizer can make the object reachable again by storing this in a static field, which forces a second GC cycle before actual collection. Third, the FinalizerDaemon bottleneck — ART runs all finalizers on a single background thread. A slow or blocking finalizer stalls finalization of every other object, growing the finalization queue indefinitely. Fourth, OOM under finalizer pressure — if objects are created faster than FinalizerDaemon can finalize them, the heap fills up and throws OutOfMemoryError. And fifth, there is no guarantee of execution — the JVM spec says finalizers are not guaranteed to run before process exit.

Correct alternative

Use Closeable / AutoCloseable with the use { } extension — it calls close() automatically on exit, even when an exception is thrown:

FileInputStream("file.txt").use { stream ->
    // stream.close() called automatically on exit, even on exception
}

Or Kotlin's kotlin.io.use / Closeable.use extension.

Allocation Pressure, GC Pauses, and Object Churn

Definitions

Allocation pressure means creating objects faster than the GC can reclaim them, which forces frequent GC cycles. GC pauses are brief stop-the-world pauses where all app threads halt so the GC can safely walk the heap — even a 5 ms pause can drop a frame at 60 fps given a 16 ms budget. Object churn is creating many short-lived objects rapidly — they fill Young gen and trigger frequent minor GCs.

Why this causes jank

Frame budget (60 fps) = 16 ms
GC minor pause       = 2–5 ms
GC major pause       = 10–50 ms (semi-space / compacting)

A major GC during a frame guarantees a dropped frame. Minor GCs are shorter but they add up, and the key insight is that the allocation pattern is entirely within your control — the GC is not.

Common causes in Android

// BAD: creates a new String on every bind call in RecyclerView
fun bind(item: Item) {
    label.text = "Item: " + item.id  // String concatenation → new objects
}

// BETTER:
fun bind(item: Item) {
    label.text = itemLabel(item.id)  // pre-computed or formatted lazily
}

Other churn sources:

  • Lambda captures inside onDraw() or onBindViewHolder()
  • ArrayList resizing (each resize copies the backing array)
  • Autoboxing Int → Integer in HashMap<Int, V> (use SparseArray<V> instead)
  • Creating Paint or Rect objects inside onDraw() (allocate once as class fields)

Mitigation

  • Object pools (Pools.SimplePool)
  • Pre-allocated scratch buffers
  • @Reusable Dagger scopes for stateless helpers
  • Avoid allocation inside tight loops and rendering code

onTrimMemory

Definition

ComponentCallbacks2.onTrimMemory(level: Int) is the system's way of asking your process to reduce its memory footprint. It is available in Activity, Fragment, Service, Application, and ViewModel, and the level argument tells you how urgently the system needs memory back.

Levels

Level constant Value Meaning
TRIM_MEMORY_UI_HIDDEN20App moved to background; release UI resources
TRIM_MEMORY_RUNNING_MODERATE5System is under moderate memory pressure; app is running
TRIM_MEMORY_RUNNING_LOW10System is low on memory; app is running
TRIM_MEMORY_RUNNING_CRITICAL15System is critically low; process may be killed soon
TRIM_MEMORY_BACKGROUND40Process is in LRU cache; release as much as possible
TRIM_MEMORY_MODERATE60Process in middle of LRU; system wants memory
TRIM_MEMORY_COMPLETE80Process is near top of LRU kill list; release everything possible

Correct usage

class MyApplication : Application() {
    override fun onTrimMemory(level: Int) {
        super.onTrimMemory(level)
        when {
            level >= ComponentCallbacks2.TRIM_MEMORY_COMPLETE -> {
                // Release all caches
                imageCache.evictAll()
                dataCache.clear()
            }
            level >= ComponentCallbacks2.TRIM_MEMORY_BACKGROUND -> {
                // Release UI caches
                imageCache.trimToSize(imageCache.size() / 2)
            }
            level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> {
                // App moved to background — release thumbnail caches, etc.
                thumbnailCache.evictAll()
            }
        }
    }
}

The trade-off is that releasing too aggressively slows re-entry because cold data must reload, whereas releasing too conservatively risks process kill. The rule of thumb is: target UI_HIDDEN for transient UI caches, and COMPLETE for everything else.

6.2 Android Memory Leaks

A memory leak is what happens when an object that should be eligible for GC is kept alive by an unintended reference chain rooted at a GC root. The object's memory is never reclaimed, and over time the heap grows until you hit OOM or the process gets killed.

The distinction between a leak and high memory usage is worth being precise about. High memory usage means the app legitimately holds a lot of data — caches, large datasets. A leak means memory that should have been freed is still held. Both can cause OOM, but leaks grow monotonically whereas high memory usage is bounded.

Activity Referenced by Singleton

The problem

// WRONG
object NetworkManager {
    var activityContext: Activity? = null  // Activity lives forever
}

class MainActivity : Activity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        NetworkManager.activityContext = this  // leak!
    }
}

NetworkManager is a GC root because it is reachable via a static field of its companion object. That means the Activity instance — with all its Views, Drawables, bitmaps, and the entire View hierarchy — can never be collected as long as the process lives.

Fix

Use Application context for singletons. If Activity is truly needed — for example, to show a dialog — hold only a WeakReference and null it on onDestroy.

object NetworkManager {
    private var _context: Context? = null
    // Or: accept Context.applicationContext at init
    fun init(appContext: Context) { _context = appContext }
}

Static Reference to Context

// WRONG
companion object {
    lateinit var appContext: Context   // fine if app context
    lateinit var activity: Activity    // LEAK if Activity
}

Static fields in Kotlin compile to fields on the companion object's backing class, which is loaded by the application ClassLoader — itself a GC root. Assigning an Activity to a static field creates a strong reference chain straight from a GC root to the Activity, so the Activity can never be collected.

The safe alternative is application.applicationContext — it lives for the entire process lifetime anyway, so holding it statically is not a leak.

Non-Static Inner Class Holding Outer Activity

// WRONG — Kotlin nested class is non-static by default
class MyActivity : Activity() {

    inner class MyTask : AsyncTask<Void, Void, String>() {  // holds implicit ref to MyActivity
        override fun doInBackground(vararg params: Void?) = heavyWork()
        override fun onPostExecute(result: String) {
            this@MyActivity.updateUI(result)  // implicit capture
        }
    }
}

An inner class — inner class in Kotlin, non-static nested in Java — holds an implicit reference to the enclosing instance. If MyTask outlives MyActivity, for example because the task is still running after the user presses Back, the Activity is leaked.

Fix: use a static nested class with a WeakReference

class MyActivity : Activity() {

    private var task: MyTask? = null

    override fun onDestroy() {
        super.onDestroy()
        task?.cancel(true)
        task = null
    }

    // Static nested — no implicit outer reference
    private class MyTask(activity: MyActivity) : AsyncTask<Void, Void, String>() {
        private val ref = WeakReference(activity)

        override fun doInBackground(vararg params: Void?) = heavyWork()

        override fun onPostExecute(result: String) {
            ref.get()?.updateUI(result)  // safe — Activity may be null
        }
    }
}

In modern Kotlin, the right answer is to use coroutines tied to lifecycleScope rather than AsyncTask entirely.

Handler and Delayed Messages

The problem

// WRONG
class MainActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // Lambda captures `this` (MainActivity)
        handler.postDelayed({
            doSomething()  // implicit capture of MainActivity
        }, 30_000L)
    }
}

The reference chain here is what traps the Activity. handler.postDelayed enqueues a Message in the main MessageQueue. That Message holds a reference to its Runnable. The Runnable lambda captures this (the Activity). The MessageQueue is attached to the main Looper, which is a GC root. So the full chain is: MessageQueue → Message → Runnable → Activity. Even after onDestroy, the Activity is kept alive for the full 30-second delay.

Fix: WeakReference pattern

class MainActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())
    private val activityRef = WeakReference(this)

    private val delayedTask = Runnable {
        activityRef.get()?.doSomething()  // no-op if Activity is gone
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler.postDelayed(delayedTask, 30_000L)
    }

    override fun onDestroy() {
        super.onDestroy()
        handler.removeCallbacks(delayedTask)  // CRITICAL: remove pending messages
    }
}

The key rule is: always call handler.removeCallbacksAndMessages(null) — or remove specific callbacks — in onDestroy.

Coroutine Running Beyond Lifecycle

// WRONG — GlobalScope coroutine captures Activity
class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        GlobalScope.launch {  // never cancelled
            val data = fetchData()
            runOnUiThread { updateUI(data) }  // MainActivity captured; Activity leaked
        }
    }
}

GlobalScope lives for the entire process lifetime. The coroutine's continuation captures the surrounding object — this@MyActivity — and after onDestroy, the coroutine is still suspended waiting for fetchData(), holding the Activity alive the whole time.

Fix: use lifecycleScope

class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycleScope.launch {  // cancelled automatically on onDestroy
            val data = fetchData()
            updateUI(data)
        }
    }
}

lifecycleScope is a CoroutineScope tied to the Activity's Lifecycle. When the Activity is destroyed, all launched coroutines are cancelled automatically. For ViewModels, use viewModelScope.

One subtlety worth knowing: even with lifecycleScope, a coroutine running during onStop that is expected to finish quickly is fine. The issue is long-running or indefinitely-suspended work that holds a reference to the Activity across destruction.

Callback/Listener Not Unregistered

// WRONG
class MyFragment : Fragment() {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        locationManager.requestLocationUpdates(provider, 0, 0f, locationListener)
        // locationListener holds a reference to this Fragment
    }
    // Never removed → Fragment and its entire view hierarchy are leaked
}

The general principle is that any external object — a system service, a singleton, a third-party library — that holds a listener reference keeps the containing class alive. The fix is always symmetric registration and unregistration.

Fix: symmetric register/unregister

override fun onStart() {
    super.onStart()
    locationManager.requestLocationUpdates(provider, 0, 0f, locationListener)
}

override fun onStop() {
    super.onStop()
    locationManager.removeUpdates(locationListener)
}

The rule is to pair registration with the matching lifecycle callback: onStart/onStop for things only needed in the foreground, onResume/onPause for things only needed when visible, and onCreate/onDestroy for process-wide resources.

BroadcastReceiver Not Unregistered

// WRONG
class MyActivity : AppCompatActivity() {
    private val receiver = MyBroadcastReceiver()

    override fun onCreate(savedInstanceState: Bundle?) {
        registerReceiver(receiver, IntentFilter(Intent.ACTION_BATTERY_CHANGED))
        // Activity destroyed but receiver still registered → Activity leaked via Context
    }
}

Fix

override fun onStart() { registerReceiver(receiver, filter) }
override fun onStop()  { unregisterReceiver(receiver) }

Alternatively, use a LifecycleObserver to auto-unregister when the lifecycle reaches the appropriate state.

Adapter / ViewHolder Leaks

RecyclerView.Adapter holding stale data

class MyAdapter(private val items: MutableList<Item>) : RecyclerView.Adapter<MyViewHolder>() {
    // 'items' may be a list from a ViewModel or repository.
    // If the Adapter lives longer than the Fragment (e.g., stored in a singleton),
    // 'items' (and transitively any Context captured in ViewHolder) is leaked.
}

The pattern to follow is that adapters should be owned by the Fragment or Activity, not by ViewModels or singletons. Use DiffUtil and ListAdapter so the adapter holds only the diffed snapshot, not a live mutable reference into the data layer.

ViewHolder holding View context

Every View holds a reference to the Context that created it — the Activity. If a ViewHolder is stored somewhere beyond the RecyclerView's lifecycle, the entire Activity is reachable through that View.

Dialog / Window Leaks

// WRONG — dialog holds Activity window token
class MyActivity : AppCompatActivity() {
    private var dialog: AlertDialog? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        dialog = AlertDialog.Builder(this)  // 'this' is Activity
            .setMessage("Loading...")
            .create()
        dialog?.show()
        // If dialog is not dismissed before Activity finishes,
        // Android WindowManager throws (or leaks the window).
    }
}

Fix

override fun onDestroy() {
    super.onDestroy()
    dialog?.dismiss()
    dialog = null
}

Use DialogFragment for dialogs that need to survive configuration changes — it handles the show/dismiss lifecycle correctly so the window token situation is managed for you.

Bitmap / Cache Leaks

Before API 26, bitmaps were backed by native memory with a small Java header. Since API 26, both the header and pixel data live in native memory, but the Bitmap object itself is still tracked by the Java GC. The trap is that if you accumulate bitmaps in a static cache without bounds, native memory grows unbounded while the Java heap looks perfectly healthy.

Always use a bounded LruCache or delegate to Glide/Coil — see §6.4 for details.

WebView Leaks

WebView is notoriously hard to clean up, and the order of operations matters:

// Pattern to minimize WebView leaks
override fun onDestroy() {
    webViewContainer.removeAllViews()  // detach from hierarchy first
    webView.destroy()                  // release native resources
    webView = null
    super.onDestroy()
}

There are three additional mitigations worth knowing. First, inflate WebView with applicationContext rather than the Activity, to avoid keeping Activity context inside WebView's internal state. Second, if the leak is severe, run WebView in a separate process. Third, never store WebView in a static field.

Fragment View Binding Leaks

The problem

The root of this leak is that a Fragment has two distinct lifecycles: the Fragment lifecycle and the Fragment View lifecycle. The view is destroyed at onDestroyView while the Fragment itself may remain alive on the back stack. If you hold a ViewBinding reference in a Fragment instance variable, the binding keeps the entire View hierarchy alive after onDestroyView.

// WRONG
class MyFragment : Fragment() {
    private var binding: MyFragmentBinding? = null  // nullable but never nulled

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        binding = MyFragmentBinding.inflate(inflater, container, false)
        return binding!!.root
    }
    // binding retains all Views after onDestroyView → leak
}

Correct fix: null the binding in onDestroyView

class MyFragment : Fragment(R.layout.my_fragment) {
    private var _binding: MyFragmentBinding? = null
    private val binding get() = _binding!!

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        _binding = MyFragmentBinding.bind(view)
        binding.button.setOnClickListener { /* ... */ }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null  // CRITICAL: break reference to View hierarchy
    }
}

After _binding = null, no strong reference from the Fragment instance to the View hierarchy remains, so the Views can now be GC'd.

Long-Running Thread Holding Activity

// WRONG
class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        Thread {                        // captures 'this' via lambda
            val result = longWork()
            runOnUiThread { show(result) }  // still holds Activity ref
        }.start()
    }
}

A Thread object is a GC root while it is alive — running or blocked. Its Runnable lambda captures the Activity. Even if the user navigates away, the thread and the Activity both stay alive until longWork() finishes.

Fix

Use lifecycleScope.launch(Dispatchers.IO) so the coroutine is cancelled automatically on onDestroy. If you must use raw threads:

private var workerThread: Thread? = null

override fun onDestroy() {
    workerThread?.interrupt()  // signal thread to stop
    workerThread = null
    super.onDestroy()
}

Book Deep-Dive

Thread-Related Memory Leaks

A Thread is a GC root until it terminates, so any object captured in the thread's Runnable — directly or indirectly — is kept alive for the thread's entire lifetime. There are three strategies for dealing with this. First, prefer lifecycleScope or viewModelScope where cancellation is automatic. Second, use an interrupt flag — call thread.interrupt() and check Thread.currentThread().isInterrupted in long loops. Third, pass a WeakReference<Activity> instead of the Activity directly.

Static Inner Classes

In Java, every non-static inner class holds a hidden this$0 reference to its enclosing instance. In Kotlin, inner class has exactly the same behavior. Declaring the class as private class without the inner keyword in Kotlin — or as static class in Java — removes that hidden reference entirely.

// Kotlin: static nested (no outer reference)
class Outer {
    private class Worker : Runnable {
        // No access to Outer members unless passed explicitly
        override fun run() { /* ... */ }
    }
}

// Kotlin: inner class (has outer reference)
class Outer {
    inner class Worker : Runnable {
        override fun run() { this@Outer.someMethod() }  // can access Outer
    }
}

Weak References Pattern

The canonical leak-safe pattern for cases where an inner object — a Handler, an AsyncTask, a Thread — needs to call back to an outer Activity is to pass a WeakReference and check for null before using it:

class WeakHandler(activity: Activity) : Handler(Looper.getMainLooper()) {
    private val ref = WeakReference(activity)

    override fun handleMessage(msg: Message) {
        val act = ref.get() ?: return  // Activity gone — ignore
        when (msg.what) {
            MSG_UPDATE -> act.updateUI(msg.obj as String)
        }
    }
}

class MainActivity : AppCompatActivity() {
    private lateinit var handler: WeakHandler

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler = WeakHandler(this)
    }

    override fun onDestroy() {
        handler.removeCallbacksAndMessages(null)  // drain queue
        super.onDestroy()
    }
}

Stopping Worker Threads

There are three options, listed here in order of preference:

  1. Cooperative cancellation via flag:
   @Volatile private var running = true

   val thread = Thread {
       while (running) {
           processNextItem()
       }
   }

   fun stopWorker() { running = false }
  1. Interrupt:
   thread.interrupt()
   // In worker:
   while (!Thread.currentThread().isInterrupted) { ... }
  1. HandlerThread.quit() / quitSafely():
   val handlerThread = HandlerThread("worker").also { it.start() }
   val workerHandler = Handler(handlerThread.looper)

   fun cleanup() {
       handlerThread.quitSafely()  // processes pending messages, then stops
   }

Never use Thread.stop() — it is deprecated and unsafe because it can leave shared state in a corrupt condition.

Retaining Worker Threads (across config changes)

The right approach here is to let a ViewModel own the thread or coroutine scope, because ViewModel survives configuration changes:

class MyViewModel : ViewModel() {
    private val workerJob = SupervisorJob()
    val scope = CoroutineScope(Dispatchers.IO + workerJob)

    override fun onCleared() {
        workerJob.cancel()  // cancels all children
    }
}

Never store a worker thread in onRetainNonConfigurationInstance or setRetainInstance(true) — both are deprecated.

Cleaning Up Message Queues

Before destroying any component that owns a Handler, drain its queue:

// Remove all pending callbacks and messages
handler.removeCallbacksAndMessages(null)

// Or remove specific Runnable:
handler.removeCallbacks(myRunnable)

// Or remove by message.what code:
handler.removeMessages(MSG_CODE)

Failing to drain the queue means pending messages can fire after the Activity is destroyed, causing NullPointerException or silently wasting work.

6.3 Context Leaks

Activity Context vs Application Context

Context is an abstract class. The two concrete subclasses that matter most for leaks are Activity — including the host Activity referenced by a Fragment — and Application. Understanding which one to use in a given situation is one of the most common Android interview topics.

Property Activity Context Application Context
LifetimeFrom onCreate to onDestroyEntire process lifetime
Theme/style accessFull access (Activity theme)Application theme only (may be wrong theme)
UI operationsRequired for dialogs, window tokens, some ViewsNot suitable
Safe for singletonsNo — singleton outlives ActivityYes — same lifetime as process
GC riskHigh if held beyond onDestroyNone (lives as long as process)

When Application Context Is Safe

Use applicationContext for any of the following: initializing singletons such as Retrofit, Room, OkHttp, or image loaders; accessing system services where no UI is involved like getSystemService(CONNECTIVITY_SERVICE) or getSystemService(NOTIFICATION_SERVICE); string and resource access in non-UI code; starting Service or BroadcastReceiver intents; and SharedPreferences access in a repository or data layer.

class MyRepository @Inject constructor(
    @ApplicationContext private val context: Context  // Dagger qualifier
) {
    fun prefs() = context.getSharedPreferences("prefs", Context.MODE_PRIVATE)
}

Dagger's @ApplicationContext qualifier ensures the repository always receives application.applicationContext and never accidentally an Activity.

When Activity Context Is Required

Activity context is required in five situations. First, inflating layouts — the View needs the Activity context to pick up the correct theme and display metrics. Second, creating dialogs with AlertDialog.Builder(activityContext) — dialogs need the Activity's window token. Third, starting Activities when FLAG_ACTIVITY_NEW_TASK is absent — using application context requires that flag. Fourth, some system services where LayoutInflater.from(context) uses the context theme, and using application context gives the wrong theme. Fifth, registerForActivityResult and permission requests — these are bound to the Activity lifecycle.

The rule of thumb is simple: if it touches the screen or a window, use Activity context.

Singleton Must Not Hold Activity

This is the most common source of large memory leaks. A single Activity instance contains its full View hierarchy — potentially hundreds of View objects, Drawables, Bitmaps, and text layouts — so leaking one Activity can mean tens of megabytes of memory that never comes back.

// WRONG
class AnalyticsManager private constructor() {
    var currentActivity: Activity? = null  // LEAK
    companion object { val instance = AnalyticsManager() }
}

// RIGHT — use WeakReference if you truly need the Activity temporarily
class AnalyticsManager private constructor() {
    private var activityRef: WeakReference<Activity>? = null

    fun attachActivity(activity: Activity) {
        activityRef = WeakReference(activity)
    }

    fun detachActivity() {
        activityRef = null
    }

    fun currentActivity(): Activity? = activityRef?.get()
}

The even better answer is to redesign so the singleton never needs an Activity reference at all. Use event buses, callbacks, or LiveData/Flow to communicate back to the UI layer.

Views Must Not Outlive Activity

// WRONG — View stored in a static or longer-lived object
object ViewCache {
    var cachedHeader: View? = null
}

Every View holds a reference to the Context — specifically the Activity — through which it was created, accessible as view.context. Storing a View in a singleton or any object that outlives the Activity leaks the entire Activity through that reference.

If you need to preserve layout state across recreation, store the data — Parcelable or serializable state — in a ViewModel, not the Views themselves.

6.4 Bitmap and Image Memory

Bitmap Memory Size

Formula

bytes = width × height × bytes_per_pixel
Config Bytes per pixel Notes
ARGB_88884Default; best quality
RGB_5652No alpha; acceptable for photos
ARGB_44442Deprecated, poor quality
ALPHA_81Masks only
HARDWARE0 (GPU memory)API 26+; not CPU-accessible

The numbers add up fast. A 4000×3000 photo at ARGB_8888 uses 4000 × 3000 × 4 = 48 MB per image. Loading even a few full-resolution phone camera shots can OOM most devices.

Historical note

Before API 26 (Oreo), bitmap pixel data was stored in a special native heap separate from both the Java heap and the regular native heap. That meant the Java OutOfMemoryError would not trigger even as you allocated hundreds of megabytes of bitmap data — the OOM came from the native allocator with confusing stack traces. Since API 26, pixel data lives in the normal native heap tracked by malloc, and ART applies back-pressure correctly.

Downsampling

Downsampling is the technique of loading a smaller version of an image before decoding it, which reduces memory proportionally to the sample size.

fun decodeSampledBitmap(res: Resources, resId: Int, reqWidth: Int, reqHeight: Int): Bitmap {
    // First pass: decode with inJustDecodeBounds = true to get dimensions
    val options = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeResource(res, resId, options)

    // Calculate inSampleSize
    options.inSampleSize = calculateInSampleSize(options, reqWidth, reqHeight)
    options.inJustDecodeBounds = false

    return BitmapFactory.decodeResource(res, resId, options)
}

fun calculateInSampleSize(options: BitmapFactory.Options, reqWidth: Int, reqHeight: Int): Int {
    val (height, width) = options.run { outHeight to outWidth }
    var inSampleSize = 1
    if (height > reqHeight || width > reqWidth) {
        val halfHeight = height / 2
        val halfWidth = width / 2
        while (halfHeight / inSampleSize >= reqHeight && halfWidth / inSampleSize >= reqWidth) {
            inSampleSize *= 2
        }
    }
    return inSampleSize
}

inSampleSize must be a power of 2. Setting inSampleSize = 4 means a quarter of the linear dimensions, which is 1/16 the pixels and therefore 1/16 the memory.

The trade-off is that a lower inSampleSize gives a sharper image but uses more memory. The rule is to always match inSampleSize to the display size, not the source size — there is no point decoding a 4K image to show it in a 48 dp thumbnail.

Image Caching and LruCache

Two-level cache pattern

Request → Memory cache (fast, limited) → Disk cache (slower, larger) → Network/Disk decode

LruCache (in-memory)

LruCache evicts the least-recently-used entry automatically whenever the cache exceeds its configured capacity.

val maxMemory = (Runtime.getRuntime().maxMemory() / 1024).toInt()
val cacheSize = maxMemory / 8  // Use 1/8th of available memory

val memoryCache = object : LruCache<String, Bitmap>(cacheSize) {
    override fun sizeOf(key: String, bitmap: Bitmap): Int {
        // Return size in kilobytes
        return bitmap.byteCount / 1024
    }
}

// Add
memoryCache.put(key, bitmap)

// Get
val cached: Bitmap? = memoryCache.get(key)

The 1/8 fraction is a typical rule of thumb: too large and you cause memory pressure on the rest of the app; too small and you get frequent cache misses.

DiskLruCache (on-disk)

DiskLruCache — from the AOSP samples, also shipped internally by Glide — caches encoded images in JPEG or PNG format on disk. It survives process restarts, is size-bounded, and is slower than a memory cache but much cheaper than a network round-trip.

Glide / Coil / Picasso

All three of these libraries handle the same core set of concerns: URL-to-bitmap loading, downsampling to display size, memory cache, disk cache, lifecycle awareness, placeholder and error drawables, and request cancellation.

Library Language Lifecycle-aware Compose support Notes
GlideJavaYes (custom)YesMost widely used, very configurable
CoilKotlinYes (LifecycleOwner)NativeCoroutines-first, smaller binary
PicassoJavaPartialLimitedSimpler API, less actively developed

Coil example (Compose)

// build.gradle: implementation("io.coil-kt:coil-compose:2.x")
AsyncImage(
    model = ImageRequest.Builder(LocalContext.current)
        .data("https://example.com/image.jpg")
        .crossfade(true)
        .size(300, 300)          // downsample to display size
        .memoryCachePolicy(CachePolicy.ENABLED)
        .diskCachePolicy(CachePolicy.ENABLED)
        .build(),
    contentDescription = "Profile photo",
    modifier = Modifier.size(48.dp)
)

Glide example

Glide.with(fragment)
    .load(url)
    .override(Target.SIZE_ORIGINAL)   // or specific px
    .placeholder(R.drawable.loading)
    .error(R.drawable.broken)
    .into(imageView)

The reason to use a library rather than rolling your own is that manual bitmap loading in RecyclerView requires at least four non-trivial things: cancellation on view recycle, downsampling to the display size, two-level caching, and worker-thread management. All of those are already solved correctly by these libraries.

Hardware Bitmaps

API 26 introduced Bitmap.Config.HARDWARE. A hardware bitmap stores pixel data only in GPU memory, which means it is immutable, it cannot be read back to the CPU — calls to getPixel() or copyPixelsToBuffer() throw — and it cannot be drawn with a software Canvas. The upside is that it is faster to draw because it skips the CPU-to-GPU upload step on each frame.

val options = BitmapFactory.Options().apply {
    inPreferredConfig = Bitmap.Config.HARDWARE
}
val bitmap = BitmapFactory.decodeResource(resources, R.drawable.photo, options)
// bitmap.config == Bitmap.Config.HARDWARE

Avoid hardware bitmaps when you need to read pixels back — for image editing — when drawing with a software Canvas such as for accessibility overlays or some Drawables, or when sharing the bitmap via Parcelable across processes.

Glide and Coil can be configured to prefer hardware bitmaps:

// Glide
Glide.with(context).asBitmap().load(url)
    .apply(RequestOptions().format(DecodeFormat.PREFER_ARGB_8888))  // or PREFER_RGB_565
    .into(target)

RecyclerView Image Cancellation

When a ViewHolder is recycled, the previous image load must be cancelled. Otherwise a slow load started for item #3 could complete and set its image on item #27, which has since been reused — giving the user the wrong image.

class ImageViewHolder(val binding: ItemImageBinding) : RecyclerView.ViewHolder(binding.root) {

    fun bind(url: String) {
        // Coil: request is tagged to the ImageView;
        // loading a new URL automatically cancels the previous one
        binding.image.load(url) {
            placeholder(R.drawable.placeholder)
        }
    }

    fun recycle() {
        // Explicitly cancel and clear (not always needed with Coil/Glide but explicit is safer)
        binding.image.dispose()
    }
}

With Glide, call Glide.with(fragment).clear(imageView) to cancel and clear. With Coil, calling imageView.dispose() is explicit, but simply calling imageView.load(newUrl) handles cancellation of the previous request implicitly.

Avoiding OOM

There are eight rules to avoid bitmap OOM. First, always downsample to display size — never load a 4K image into a 48 dp thumbnail view. Second, use a library like Coil or Glide — they handle all of the above automatically. Third, set a bounded memory cache, and maxMemory / 8 is a reasonable starting point. Fourth, use Bitmap.Config.RGB_565 for non-transparent images where quality allows, which cuts memory in half compared to ARGB_8888. Fifth, recycle bitmaps when done — bitmap.recycle() — especially pre-API 26. Sixth, handle onTrimMemory in your Application or image loader to evict caches under memory pressure. Seventh, prefer hardware bitmaps on API 26 and above for display-only images. And eighth, never load images on the main thread — StrictMode will warn you, and an OOM blocking the main thread also triggers an ANR.

6.5 Leak Detection and Profiling

Android Studio Memory Profiler

The Memory Profiler shows a real-time heap allocation graph broken down by Java heap, native heap, graphics, stack, code, and others. It shows total allocations per time window, lets you trigger GC manually, and supports heap dump capture and analysis.

The workflow is: run the app, open the Profiler tab, select Memory, and click on the graph to start observing. A sawtooth pattern — allocation, then GC, then plateau — is normal. A growing floor after each GC cycle is the signal that something is leaking. Rotating the device or navigating back and checking whether the heap drops back to baseline is a quick first check. If it does not, capture a heap dump to confirm.

Heap Dump

A heap dump is a snapshot of all live objects on the heap at a specific point in time, stored in .hprof format. You can capture one three ways: clicking "Dump Java Heap" in the Memory Profiler, calling Debug.dumpHprofData(filePath) programmatically, or running adb shell am dumpheap <pid> /data/local/tmp/heap.hprof.

When analyzing in Android Studio, the workflow has three steps. First, the class list view — sort by "Retained Size" descending to find the largest retained objects. Second, the instance list — click a class to see all live instances; multiple Activity instances of the same class with no more user interaction is a clear leak signal. Third, the references tree — for a suspicious instance, expand "References" to trace the reference chain back to the GC root.

There are five things to look for specifically in a heap dump. First, multiple instances of a single Activity class — there should be at most one after pressing Back. Second, Activity instances reachable from static fields. Third, Bitmap objects with large byteCount accumulated in a static cache. Fourth, Fragment instances with a non-null mView field after expected destruction. Fifth, Handler objects that hold references back to Activities.

Allocation Tracking

Allocation tracking records each allocation event with its stack trace during a recording window. Use it when you see frequent GC events but no permanent leak — in that case you are looking for allocation pressure and churn, not retained objects.

The workflow in the Memory Profiler is: click "Record allocations", use the app, then click "Stop". Sort by "Allocations" or "Shallow Size" and look for allocations in rendering paths — onDraw, onBindViewHolder, draw.

Common findings include String concatenation inside onBindViewHolder, ArrayList or HashMap churn in data processing loops, and lambda objects created fresh inside setOnClickListener on every bind call.

LeakCanary

LeakCanary is Square's open-source automatic leak detection library for debug builds.

How it works (internals)

LeakCanary works in five steps. First, the detection trigger: LeakCanary installs an ActivityLifecycleCallbacks — plus Fragment and ViewModel equivalents — and when an Activity is destroyed it adds the instance to a KeyedWeakReference list and schedules a check. Second, the reachability check: after a roughly 5-second delay, it triggers GC and checks whether the WeakReference was cleared. If the reference was not cleared, the object is still alive and is likely leaked. Third, the heap dump: LeakCanary calls Debug.dumpHprofData() to capture a snapshot. Fourth, path analysis: it uses its internal HPROF parser, Shark, to find the shortest strong-reference path from a GC root to the leaked object. Fifth, notification: it shows a notification with the full leak trace and the exact field names at each step in the reference chain.

Setup

// build.gradle (app module) — debug only
debugImplementation("com.squareup.leakcanary:leakcanary-android:2.x")
// No Application code needed — LeakCanary auto-installs via ContentProvider

Reading a LeakCanary trace

┬───
│ GC Root: static field
│
├─ com.example.MySingleton
│    Leaking: NO (static)
│    ↓ MySingleton.activityRef
├─ com.example.MainActivity
│    Leaking: YES (Activity.mDestroyed is true)
│    ↓ MainActivity.this$0 [inner class ref]
╰→ com.example.MainActivity$1 instance
     Leaking: YES

Read it bottom-up: MainActivity$1, an anonymous inner class, is the retained object. It holds a reference back to MainActivity through this$0. MainActivity was already destroyed. And MySingleton.activityRef is the GC root that is keeping the entire chain alive.

Trade-offs

LeakCanary is debug-only — never ship it to production because heap dumps are expensive. False positives are rare but possible, for instance when framework code legitimately holds a reference briefly. And there is roughly a 5 to 10 second delay between Activity destruction and the notification, because the library waits to ensure the GC had a chance to run.

Android Vitals

Android Vitals is Google Play Console's production crash, ANR, and memory data aggregated from opted-in real devices.

The metrics most relevant to memory are ANR rate — because GC pauses blocking the main thread can trigger ANRs — crash rate from OutOfMemoryError and NullPointerException from GC'd weak references, stuck partial wake locks and excessive wakeups which are symptoms of resource leaks.

For a memory investigation, the workflow is: filter crashes by OutOfMemoryError to see which code paths OOM in production. The crash details include a stack trace and the device model and RAM tier, which lets you correlate leaks with low-RAM devices. The LowMemoryKills metric — available via the Play Console API — counts how often the OS killed your process for low memory, which is an actionable signal for how well your onTrimMemory handling is working.

dumpsys meminfo

adb shell dumpsys meminfo <package-name> prints a memory summary for a running process.

Perfetto

Perfetto is the system-wide tracing infrastructure that replaced Systrace on API 28 and above.

There are three memory-relevant probes. First, heapprofd, the heap profiler — it samples native malloc allocations with full stack traces at very low overhead, with a default sampling interval of 4096 bytes, and it shows you exactly where native memory grows. ``bash adb shell perfetto --out /data/misc/perfetto-traces/trace \ -c - --txt <<EOF buffers: { size_kb: 63488 } data_sources: { config { name: "android.heapprofd" heapprofd_config { sampling_interval_bytes: 4096 process_cmdline: "com.example.app" } } } duration_ms: 15000 EOF ``

Second, android.java_hprof — a Java heap snapshot that is like a heap dump but streamed directly into a Perfetto trace. Third, track_event — custom trace events you add to your own code with Trace.beginSection and Trace.endSection.

Open the trace at ui.perfetto.dev. The Memory track shows RSS and PSS over time, and zooming in shows individual allocation events from heapprofd.

Use Perfetto over the Memory Profiler for system-wide analysis — for example, to check whether GPU, media, or system_server is consuming memory — for production-close profiling at lower overhead, or when investigating native memory leaks that do not show up in Java heap dumps.
