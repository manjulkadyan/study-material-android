6.1 JVM/ART Memory Basics

Stack vs Heap

🎤 Say it out loud (~30–45s): "The stack and heap are two different memory regions with different lifetimes and ownership. The stack is per-thread scratch space — method frames, primitives, and object references — and it's automatically freed when the method returns, so it's super fast and inherently thread-safe. The heap is where every object actually lives; it's shared across all threads and reclaimed by the garbage collector once nothing references the object. The gotcha interviewers love is that a reference can sit on the stack while the object it points to lives on the heap — so 'where does the variable live' depends on whether it's a primitive or a reference."

Definition

The stack and heap are the two distinct memory regions the JVM uses, and understanding the difference matters a lot for Android because it determines both lifetime and thread safety.

Dimension Stack Heap
What lives therePrimitive local variables, method frames, object referencesAll object instances and arrays
AllocationAutomatic, LIFO, at method entryExplicit new (or Kotlin object literals), GC-managed
LifetimeExactly the enclosing method callUntil no live reference remains
SizeSmall, fixed per thread (Android default ~8 KB–1 MB per thread)Large, expandable up to the process memory limit
Thread safetyEach thread has its own stack — no sharingShared across all threads — concurrency required
SpeedVery fast (just SP register increment)Slower (allocation, possible GC)

Under the hood

Each JVM/ART thread gets its own native stack, and within it the runtime maintains a chain of frames — one per active method call. A frame holds the method's local variable array (slots indexed 0..n), an operand stack the bytecode pushes/pops against, and a reference to the constant pool. Dalvik bytecode is register-based, so locals map to virtual registers (v0, v1, …) rather than a pure operand stack like classic JVM bytecode. References on the stack are just pointers (32- or 64-bit, subject to compressed-oop-style optimizations) into the heap; the object header on the heap carries the class pointer and lock/hash word.

Thread A stack (grows downward)        ART managed heap (shared)
┌──────────────────────────┐          ┌───────────────────────────┐
│ frame: render()          │          │ [hdr|class=Button|fields] │
│   v0 = 5  (primitive)    │          │ [hdr|class=String |chars] │
│   v1 = ref ─────────────────────────▶ ...                        │
│ frame: onDraw()          │          └───────────────────────────┘
└──────────────────────────┘

Android / ART internals

  • ART uses a generational heap split into Young (allocation), Old (long-lived), and Large Object Space (objects > ~12 KB).
  • Stack frames for Dalvik bytecode methods are laid out by the ART interpreter or JIT/AOT-compiled native frames.
  • Stack overflow (deep recursion) throws StackOverflowError, not OutOfMemoryError.

Interview angles

Q: "If I declare val x = 5 inside a function, where does it live?"

"The value 5 lives in the current thread's stack frame — the stack is just the scratch space for whatever method is currently executing. Now if instead I write val obj = MyClass(), the reference obj is still on the stack, but the actual MyClass instance is allocated on the heap. The stack holds the pointer; the heap holds the object."

Q: "Can two threads share a stack variable?"

"No. Each thread has its own independent stack, so stack variables are private to the thread running that method. Threads can only share state through the heap — which is exactly why you need synchronization any time two threads read and write the same mutable heap object."

Object Allocation

🎤 Say it out loud (~30–45s): "On ART, allocation is usually almost free because each thread bumps a pointer inside its own Thread-Local Allocation Buffer carved out of Young space — no locking, no global contention. The cost shows up later as GC pressure: when the TLAB or Young space fills, you pay a minor collection, and objects that survive get promoted to Old gen. The thing that bites people in Kotlin is hidden allocation — lambdas captured in hot loops, autoboxing in generic collections like List<Int> — so in performance-critical paths I reach for IntArray or SparseArray to avoid churning the allocator."

Internals

ART allocates new objects in the Thread-Local Allocation Buffer (TLAB) — a small region carved out of Young space for each thread. TLAB allocation is near-free because it is just a pointer bump. When the TLAB fills, ART does a minor GC (Young collection), which is fast — roughly 2 to 5 ms — but still causes a brief pause.

When an object survives enough minor GCs it is promoted to Old generation, where it lives until a major GC.

Kotlin allocation pitfalls

// BAD: creates a lambda object on every call
list.forEach { it.process() }

// BETTER: if called in a tight loop, extract to a named function reference
val fn: (Item) -> Unit = { it.process() }
list.forEach(fn)

Boxing: Kotlin's Int, Long, etc. compile to primitive JVM types when possible, but generics always box — List<Int> stores Integer objects. Prefer IntArray / LongArray / SparseArray in performance-critical paths.

Under the hood

The "pointer bump" is literally that: the TLAB tracks a top and end cursor, and allocation does if (top + size <= end) { obj = top; top += size } — a CAS-free fast path because the buffer is thread-local. Only when the bump would overflow end does ART take the slow path: request a new TLAB, run a Young GC, or fall back to the Large Object Space for big arrays. At the bytecode level, MyClass() compiles to a new-instance op followed by invoke-direct to <init>; a non-capturing Kotlin lambda compiles to a singleton (INSTANCE field), but a capturing lambda compiles to a fresh class instance constructed on every evaluation, which is the allocation you see in the "BAD" example. Generic boxing is the compiler emitting Integer.valueOf(...) (which caches only −128..127) to satisfy the erased Object-typed slots of a List.

TLAB fast path:
  top ──▶ [ free region ] ──▶ end
  alloc(n): candidate = top; if candidate+n <= end -> top = candidate+n; return candidate
                              else -> slow path (refill TLAB / GC / LOS)

References and Reachability

🎤 Say it out loud (~30–45s): "Garbage collection isn't about reference counting — it's about reachability. The GC starts from a fixed set of GC roots, like active stack frames, static fields, and JNI globals, and traces every reference chain outward; anything it can reach is live, anything it can't is collectable. The practical upshot for Android leaks is that a single root holding a chain to your Activity keeps the whole graph alive — so the fix is always to cut the chain, like nulling a static field or clearing a listener, and the entire sub-graph below it becomes eligible for collection."

Reachability (GC root tracing)

The key concept here is reachability. The GC starts from GC roots — currently-executing stack frames, static fields, JNI global references, and synchronization monitors — and traces every reference chain outward. Any object reachable by following references from a root is live and will not be collected. Anything the GC cannot reach from any root is eligible for collection.

GC Roots
  ├── Thread stack frames
  ├── Static fields (dangerous — they live until ClassLoader unload)
  ├── JNI global refs
  └── System classes
        └── → object A → object B → object C   (all live)

The important implication is that if you cut the reference chain — for example, by setting a static field to null — the entire sub-graph below it becomes eligible for collection.

Under the hood

Tracing is a graph traversal (mark phase of mark-sweep): the GC seeds a work queue/mark-stack with the roots, then pops each object, reads its reference fields using the class's reference map (computed from field layout / GC type info), and pushes any unmarked referents — marking each by flipping a bit in a side mark-bitmap (ART keeps marks out-of-line so it doesn't dirty object headers). To enumerate stack roots precisely, ART walks each thread's frames at a safepoint and consults stack maps that say which registers/slots currently hold references. Static fields are reachable because they're stored in the Class object, which is itself rooted by its ClassLoader — which is exactly why a static field pinning an Activity never gets collected until the classloader unloads (effectively never for the app classloader). Cutting one edge doesn't free anything immediately; it just means the next trace won't reach that sub-graph, so it gets swept.

mark-stack = [root1, root2, ...]
while stack not empty:
    o = pop()
    for ref in references_of(o):        // via class reference map
        if not marked(ref):
            mark(ref); push(ref)
// anything still unmarked after this == unreachable == sweepable

Garbage Collection

ART GC algorithms

🎤 Say it out loud (~30–45s): "ART doesn't use one collector — it picks based on app state. While you're in the foreground it favors a concurrent collector so pauses are tiny and the UI stays smooth, and when the app goes to background it can run a heavier compacting collection that defragments the heap and hands memory back to the system. The nuance is that compaction is the expensive one — tens of milliseconds — but it's deliberately scheduled for when the user isn't looking, so it doesn't cost you frames."

ART ships multiple collectors selectable at runtime:

Collector Pauses Use case
CMS (Concurrent Mark-Sweep)Short stop-the-world pausesDefault for most allocation
Generational CC (Concurrent Copying)Very shortBackground/foreground switching
Semi-spaceCompacting, longer pauseAfter transition to background

The Android lifecycle integration matters here: when an app moves to background at onStop, ART may trigger a compacting GC using the semi-space collector. That is expensive — roughly 50 to 100 ms — but acceptable because the user is not watching the screen at that point.

Under the hood

The modern default (Android 8+) is Concurrent Copying (CC) using a region-based heap with read barriers. CC evacuates live objects from "from-space" regions into "to-space" while mutator threads keep running; the read barrier intercepts field loads so a thread that reads a reference to an object mid-copy gets forwarded to the new copy (via a forwarding address in the header) instead of the stale one. Because it copies survivors compactly, it both reclaims and defragments in one pass, which is why fragmentation is much less of a problem than under plain mark-sweep. Only short stop-the-world windows are needed — to flip spaces and re-scan dirty cards/roots. The expensive background compaction is ART deciding the foreground/background trade-off has flipped: it's worth a longer pause to shrink the heap footprint (madvise(MADV_DONTNEED) on freed regions) so the kernel can reclaim physical pages from a backgrounded process.

GC phases (simplified)

🎤 Say it out loud (~30–45s): "Conceptually it's mark, then sweep: trace from the roots to mark everything reachable, then reclaim whatever wasn't marked. The reason it feels smooth on Android is that most of that work runs concurrently with your app threads — the only stop-the-world moments are a brief initial root scan and a final remark to catch references that mutated while marking was running. That final remark is why a write barrier exists: it records mutations so the concurrent marker doesn't miss a newly-created edge."

There are essentially three phases. First, Mark — the GC traces from GC roots and marks all reachable objects. Second, Sweep — it reclaims the memory of everything that was not marked. Third, in the Concurrent Mark-Sweep variant, most of that marking and sweeping runs concurrently alongside your app threads, but brief stop-the-world pauses still occur at the start of the mark phase and at the end for a final remark pass.

Under the hood

Concurrent marking has a correctness hazard: if the app mutates the object graph while the GC is tracing, a freshly-stored reference to a not-yet-marked object could be missed and wrongly collected. ART solves this with a write barrier backed by a card table — the heap is divided into ~card-sized chunks, and any reference store dirties the corresponding card byte. At the final stop-the-world remark, the GC only needs to re-scan dirty cards (plus thread roots) rather than the whole heap, which keeps the pause bounded. Sweeping under mark-sweep walks the allocation bitmap and frees unmarked spans back to the free-list allocator (RosAlloc/DlMalloc); under the copying collector there is no separate sweep — reclamation is implicit once from-space regions are evacuated and discarded.

[STW] initial root scan ─▶ [concurrent] mark graph (mutators run, write barrier dirties cards)
   ─▶ [STW] remark dirty cards + roots ─▶ [concurrent] sweep / reclaim from-space

Reference Strengths: Strong / Weak / Soft / Phantom

Strong reference (default)

🎤 Say it out loud (~30–45s): "A strong reference is the normal kind — the plain assignment — and as long as one exists the GC will never collect the object. That's the whole basis of leaks: an unintended strong reference from something long-lived, like a static or a running thread, to something short-lived, like an Activity, is exactly what keeps the Activity pinned in memory after it should have been destroyed."
val activity: Activity = this  // strong — Activity will NOT be GC'd while this lives

A strong reference is the default — the GC will never collect an object as long as a strong reference to it exists.

Under the hood

A strong reference is just an ordinary reference field/slot — there is no wrapper object and no special handling. During tracing the GC follows it unconditionally, so a strongly-reachable object is always marked live. The Reference machinery (weak/soft/phantom) is the exception path: those are real heap objects (java.lang.ref.Reference subclasses) whose referent field the GC treats specially. Strong refs skip all of that, which is why they're both the fastest and the easiest to leak with.

Weak reference

🎤 Say it out loud (~30–45s): "A weak reference lets you point at an object without keeping it alive — if the only references left are weak, the GC clears them on its next pass and get() starts returning null. In Android I use it for non-owning associations: caches, listener registries, or wrapping an Activity inside a Handler or background task so finishing the screen actually lets it be collected. The catch is you must null-check every get(), because the object can vanish between calls."
import java.lang.ref.WeakReference

class MyCache {
    private val ref = WeakReference(someExpensiveObject)

    fun get() = ref.get()  // returns null if GC collected it
}

A weak reference tells the GC: "collect this at the next GC cycle once no strong references remain." There are two main uses in Android. First, caches and listener registrations where you don't want the cache to prevent GC. Second, holding a WeakReference<Activity> inside a Handler or background thread so that finishing the Activity does not keep it alive just because the handler still has a reference.

Under the hood

A WeakReference is a heap object holding a referent field that the GC knows about. During the mark phase the collector does not trace through weak referents; after marking finishes, it visits all discovered weak references whose referent is unmarked (i.e., not strongly reachable) and atomically clears the referent field to null, then enqueues the reference on its ReferenceQueue if one was registered. That clearing-after-marking ordering is precisely why get() can flip from non-null to null between two calls — and why every dereference needs a null guard.

Soft reference

🎤 Say it out loud (~30–45s): "A soft reference is a memory-sensitive cache hint — the GC keeps it as long as memory is comfortable and only clears it when it's about to run out, ideally before throwing OOM. I'm usually cautious recommending them on Android, though, because you hand eviction policy to the GC and can't predict what disappears when; an LruCache with an explicit size budget gives you deterministic control, so that's almost always the better cache primitive."
import java.lang.ref.SoftReference

val cached = SoftReference(loadBitmap())
val bmp = cached.get() ?: loadBitmap()  // reload if GC'd

A soft reference means "keep this alive as long as there's memory to spare, but collect it before throwing OOM." The GC will only collect the referent when memory is actually tight. The trade-off is that LruCache with explicit eviction is usually better, because soft references hand too much control to the GC — you cannot predict what gets evicted when.

Under the hood

Soft references share the same Reference machinery as weak references, but the collector applies a clearing policy rather than clearing them eagerly. Each SoftReference effectively tracks a last-access timestamp (updated on get()), and the runtime keeps softly-reachable objects until it's under memory pressure, then clears them — typically least-recently-used first — to try to satisfy an allocation before declaring OutOfMemoryError. So the lifetime is non-deterministic and policy-driven, which is exactly the unpredictability that makes an explicit LruCache (you choose the byte budget and eviction order) preferable for image/object caches.

Phantom reference

🎤 Say it out loud (~30–45s): "A phantom reference is the most exotic — its get() always returns null, so you can never resurrect the object; its only job is to notify you via a ReferenceQueue after the object has been finalized and is about to be reclaimed. It's the modern, deterministic replacement for finalize() for cleaning up native resources, and it's what ART's own Cleaner is built on. You rarely write it in app code, but knowing the queue-based reclaim hook shows you understand the reference hierarchy end to end."
val queue = ReferenceQueue<MyObject>()
val ref = PhantomReference(obj, queue)
// obj = null  (must explicitly clear strong ref)

// In a cleanup thread:
val enqueued = queue.poll()  // non-null after GC finalizes obj

Phantom references are enqueued after the referent's finalizer runs (or would have run) and its memory is about to be reclaimed. Calling get() always returns null — you can never resurrect the object. The use case is deterministic resource cleanup as an alternative to finalize(). ART's internal Cleaner, used for native memory bookkeeping, is built on phantom references. You rarely need this in app code, but mentioning it shows depth.

Under the hood

PhantomReference.get() is hard-coded to return null — the API guarantees you can never re-obtain a strong reference, which removes the resurrection hazard that finalizers have. The GC processes references in a strict order: it clears soft (if needed) and weak referents and enqueues them, runs/finalizes objects with finalizers, and only then — once an object is truly unreachable and post-finalization — enqueues its phantom reference onto the registered ReferenceQueue. The memory itself isn't reclaimed until the phantom is enqueued and your cleanup code processes the queue (historically phantom referents weren't cleared automatically, so you clear() or drop the reference). java.lang.ref.Cleaner packages this pattern: it registers a phantom reference plus a cleanup Runnable and a dedicated thread drains the queue to run native-resource cleanups deterministically.

Finalizers Are Problematic

What a finalizer is

🎤 Say it out loud (~30–45s): "A finalizer is a method the GC calls right before reclaiming an object, meant as a last-chance hook to release resources. In practice it's an anti-pattern — Kotlin and effective-Java both steer you away from it — because the timing is non-deterministic and there's no guarantee it ever runs. I treat seeing finalize() in code as a smell and reach for Closeable/use instead."
// Java-style; Kotlin discourages this
class Broken {
    protected fun finalize() {
        closeResource()  // DON'T do this
    }
}

Under the hood

When the JVM/ART first allocates an object whose class overrides finalize(), the runtime registers it with the finalizer subsystem (in ART, a FinalizerReference is created). This has real cost: finalizable objects can't be reclaimed in the GC cycle that first finds them unreachable. Instead the GC discovers them unreachable, hands them to a single FinalizerDaemon thread, which invokes finalize(), and only a subsequent GC cycle can actually free the memory — so every finalizable object survives at least two collections. Overriding finalize() also disables some allocation fast paths and bloats the bookkeeping the collector must maintain.

Why finalizers are dangerous

There are five reasons to avoid them. First, non-deterministic timing — the GC decides when to call finalize(), so resources may be held for unpredictable durations. Second, resurrection risk — a finalizer can make the object reachable again by storing this in a static field, which forces a second GC cycle before actual collection. Third, the FinalizerDaemon bottleneck — ART runs all finalizers on a single background thread. A slow or blocking finalizer stalls finalization of every other object, growing the finalization queue indefinitely. Fourth, OOM under finalizer pressure — if objects are created faster than FinalizerDaemon can finalize them, the heap fills up and throws OutOfMemoryError. And fifth, there is no guarantee of execution — the JVM spec says finalizers are not guaranteed to run before process exit.

Under the hood

Android adds a hard guard the desktop JVM doesn't: a FinalizerWatchdogDaemon thread times each finalize() call, and if one exceeds a timeout (historically ~10 s) it kills the process with a TimeoutException-style fatal error. So a blocking finalizer doesn't just slow things down — it can crash the app. Mechanically, the single FinalizerDaemon polls a ReferenceQueue of FinalizerReferences, calls each finalize(), and clears the reference; because it's serial, throughput is bounded by the slowest finalizer, and allocation-vs-finalization rate mismatch lets the queue (and heap) grow until OOM. Resurrection works because the daemon holds a temporary strong reference to this while running finalize(), so the method can re-publish that reference to a root — after which the object is reachable again and the next GC must re-discover it.

Correct alternative

🎤 Say it out loud (~30–45s): "The right pattern is explicit, deterministic cleanup: implement Closeable/AutoCloseable and let Kotlin's use { } close it on the way out — including on exceptions — the same way try-with-resources works in Java. That gives you a precise lifetime instead of waiting on the GC. If you genuinely need a GC-tied safety net for native memory, you reach for Cleaner with a phantom reference, not finalize()."

Use Closeable / AutoCloseable with the use { } extension — it calls close() automatically on exit, even when an exception is thrown:

FileInputStream("file.txt").use { stream ->
    // stream.close() called automatically on exit, even on exception
}

Or Kotlin's kotlin.io.use / Closeable.use extension.

Under the hood

use is an inline extension function, so there's no lambda allocation and no separate try-with-resources bytecode magic — the compiler inlines the body into the call site. Conceptually it expands to a try { block(this) } catch (e) { ... } finally { close() }, and it carefully preserves any primary exception: if the block throws and close() also throws, the close exception is attached via Throwable.addSuppressed(...) rather than masking the original. This is the JVM's try-with-resources contract expressed as a Kotlin inline function, giving deterministic, exception-safe release at a precise lexical scope instead of at some unknown future GC.

// roughly what the compiler inlines:
val stream = FileInputStream("file.txt")
var thrown: Throwable? = null
try { /* block */ } catch (e: Throwable) { thrown = e; throw e }
finally {
    if (thrown == null) stream.close()
    else try { stream.close() } catch (c: Throwable) { thrown.addSuppressed(c) }
}

Allocation Pressure, GC Pauses, and Object Churn

🎤 Say it out loud (~30–45s): "Allocation pressure is when I create objects faster than the GC can reclaim them, which forces frequent collections; even a short stop-the-world pause can blow my 16 ms frame budget at 60 fps. The thing I always emphasize is that I can't control the GC, but I fully control my allocation pattern — so the fix is to stop churning short-lived objects in hot paths like onBindViewHolder and onDraw, not to try to tune the collector. The gotcha an interviewer probes is that it's usually death by a thousand minor GCs, not one big major GC — tiny allocations in tight loops add up to visible jank."

Definitions

Allocation pressure means creating objects faster than the GC can reclaim them, which forces frequent GC cycles. GC pauses are brief stop-the-world pauses where all app threads halt so the GC can safely walk the heap — even a 5 ms pause can drop a frame at 60 fps given a 16 ms budget. Object churn is creating many short-lived objects rapidly — they fill Young gen and trigger frequent minor GCs.

Why this causes jank

Frame budget (60 fps) = 16 ms
GC minor pause       = 2–5 ms
GC major pause       = 10–50 ms (semi-space / compacting)

A major GC during a frame guarantees a dropped frame. Minor GCs are shorter but they add up, and the key insight is that the allocation pattern is entirely within your control — the GC is not.

Common causes in Android

// BAD: creates a new String on every bind call in RecyclerView
fun bind(item: Item) {
    label.text = "Item: " + item.id  // String concatenation → new objects
}

// BETTER:
fun bind(item: Item) {
    label.text = itemLabel(item.id)  // pre-computed or formatted lazily
}

Other churn sources:

  • Lambda captures inside onDraw() or onBindViewHolder()
  • ArrayList resizing (each resize copies the backing array)
  • Autoboxing Int → Integer in HashMap<Int, V> (use SparseArray<V> instead)
  • Creating Paint or Rect objects inside onDraw() (allocate once as class fields)

Mitigation

  • Object pools (Pools.SimplePool)
  • Pre-allocated scratch buffers
  • @Reusable Dagger scopes for stateless helpers
  • Avoid allocation inside tight loops and rendering code

Under the hood

ART uses a generational, concurrent collector (the default is Concurrent Copying / CC). Small objects are bump-allocated into a thread-local allocation buffer (TLAB), so an allocation is normally just a pointer increment — cheap until the region fills and a GC is triggered. The CC collector does most marking and copying concurrently with app threads, but it still inserts short stop-the-world pauses to flip the from-space/to-space roots and to handle the read barrier hand-off, which is where your frame-time hit comes from. String concatenation like "Item: " + item.id compiles to a StringBuilder allocation plus a toString() that allocates a fresh String and its backing char[]/byte[] — three objects per call. Autoboxing Int into a HashMap allocates an Integer wrapper per key (outside the small -128..127 IntegerCache range), which is exactly the garbage SparseArray avoids by storing primitive int keys in a parallel array.

TLAB allocation (fast path):   ptr += objectSize;  if (ptr > end) → slow path → GC
"a " + n  ⇒  new StringBuilder().append("a ").append(n).toString()
            ⇒ StringBuilder + char[] + String  (3 allocations)

onTrimMemory

🎤 Say it out loud (~30–45s): "onTrimMemory is the system telling my process to give memory back, and the level argument tells me how urgently — from UI_HIDDEN when I just went to the background, up to COMPLETE when I'm near the top of the LRU kill list. I use it to drop caches proportionally: thumbnail and UI caches at UI_HIDDEN, then everything at the critical levels. The nuance I'd raise is it's a trade-off — release too aggressively and re-entry is slow because I reload cold data, release too little and the OOM killer takes my whole process, so it's a graceful-degradation knob, not a guarantee."

Definition

ComponentCallbacks2.onTrimMemory(level: Int) is the system's way of asking your process to reduce its memory footprint. It is available in Activity, Fragment, Service, Application, and ViewModel, and the level argument tells you how urgently the system needs memory back.

Levels

Level constant Value Meaning
TRIM_MEMORY_UI_HIDDEN20App moved to background; release UI resources
TRIM_MEMORY_RUNNING_MODERATE5System is under moderate memory pressure; app is running
TRIM_MEMORY_RUNNING_LOW10System is low on memory; app is running
TRIM_MEMORY_RUNNING_CRITICAL15System is critically low; process may be killed soon
TRIM_MEMORY_BACKGROUND40Process is in LRU cache; release as much as possible

Correct usage

class MyApplication : Application() {
    override fun onTrimMemory(level: Int) {
        super.onTrimMemory(level)
        when {
            level >= ComponentCallbacks2.TRIM_MEMORY_COMPLETE -> {
                // Release all caches
                imageCache.evictAll()
                dataCache.clear()
            }
            level >= ComponentCallbacks2.TRIM_MEMORY_BACKGROUND -> {
                // Release UI caches
                imageCache.trimToSize(imageCache.size() / 2)
            }
            level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> {
                // App moved to background — release thumbnail caches, etc.
                thumbnailCache.evictAll()
            }
        }
    }
}

The trade-off is that releasing too aggressively slows re-entry because cold data must reload, whereas releasing too conservatively risks process kill. The rule of thumb is: target UI_HIDDEN for transient UI caches, and COMPLETE for everything else.

Under the hood

The callback originates in ActivityManagerService (AMS), which tracks every process's adj (out-of-memory adjustment score / oom_adj) and LRU position. When system memory crosses thresholds, AMS calls into the app process over Binder (ApplicationThread.scheduleTrimMemory), which posts to the main thread and fans the level out to all registered ComponentCallbacks2. The _RUNNING_* levels are delivered while your app is foreground/visible; the _UI_HIDDEN, _BACKGROUND, _MODERATE, and _COMPLETE levels track your slide down the cached-process LRU list. This is distinct from the kernel's lowmemorykiller/LMKD path — onTrimMemory is a cooperative request to shed memory before LMKD escalates to sending SIGKILL based on oom_score_adj. Note the values are not monotonic by urgency (UI_HIDDEN is 20 but RUNNING_CRITICAL is 15), which is why you branch on specific constants rather than treating the int as a simple severity scale.

AMS (oom_adj, LRU rank) ──Binder──▶ ApplicationThread.scheduleTrimMemory(level)
   ▶ main-thread dispatch ▶ every ComponentCallbacks2.onTrimMemory(level)
If app ignores it ▶ adj rises ▶ LMKD picks highest oom_score_adj ▶ SIGKILL

6.2 Android Memory Leaks

A memory leak is what happens when an object that should be eligible for GC is kept alive by an unintended reference chain rooted at a GC root. The object's memory is never reclaimed, and over time the heap grows until you hit OOM or the process gets killed.

The distinction between a leak and high memory usage is worth being precise about. High memory usage means the app legitimately holds a lot of data — caches, large datasets. A leak means memory that should have been freed is still held. Both can cause OOM, but leaks grow monotonically whereas high memory usage is bounded.

Activity Referenced by Singleton

🎤 Say it out loud (~30–45s): "The classic leak is a singleton holding an Activity. The singleton is reachable from a static field, which is a GC root, so anything it references — including an Activity and its entire view tree, drawables, and bitmaps — can never be collected for the life of the process. The fix is to pass the application context to singletons instead of an Activity, and if I genuinely need the Activity, hold it in a WeakReference and null it in onDestroy. The gotcha is that the leak isn't the Activity object alone — it's the whole window's worth of bitmaps hanging off it, which is why one leaked Activity can be megabytes."

The problem

// WRONG
object NetworkManager {
    var activityContext: Activity? = null  // Activity lives forever
}

class MainActivity : Activity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        NetworkManager.activityContext = this  // leak!
    }
}

NetworkManager is a GC root because it is reachable via a static field of its companion object. That means the Activity instance — with all its Views, Drawables, bitmaps, and the entire View hierarchy — can never be collected as long as the process lives.

Fix

Use Application context for singletons. If Activity is truly needed — for example, to show a dialog — hold only a WeakReference and null it on onDestroy.

object NetworkManager {
    private var _context: Context? = null
    // Or: accept Context.applicationContext at init
    fun init(appContext: Context) { _context = appContext }
}

Under the hood

A Kotlin object declaration compiles to a final class with a private static final INSTANCE field initialized in a static initializer (<clinit>). Static fields of a loaded class are part of the JVM/ART GC root set, so NetworkManager.INSTANCE is permanently reachable and never collected. When you assign this into its activityContext field you splice the Activity onto that root. During GC the mark phase traverses object references transitively from roots: NetworkManager.INSTANCE → activityContext → mWindow → DecorView → child views → Drawable → Bitmap. Because every node on that path is strongly reachable, ART's collector marks them all live and skips reclamation — that's mechanically why the leak retains the whole view hierarchy, not just the Activity header. A WeakReference participates as a weak edge: the GC clears it during the reference-processing phase if the referent has no remaining strong path, so the Activity can still be collected.

Static Reference to Context

🎤 Say it out loud (~30–45s): "A static field pointing at an Activity is a guaranteed leak because the class object is loaded by the app classloader, which is a GC root, so the Activity is strongly reachable for the entire process lifetime. The key distinction I draw is that the application context in a static field is totally fine — it already lives as long as the process, so there's nothing to leak. The trap is using lateinit var activity for convenience; the same pattern is safe for app context and fatal for an Activity or a View."
// WRONG
companion object {
    lateinit var appContext: Context   // fine if app context
    lateinit var activity: Activity    // LEAK if Activity
}

Static fields in Kotlin compile to fields on the companion object's backing class, which is loaded by the application ClassLoader — itself a GC root. Assigning an Activity to a static field creates a strong reference chain straight from a GC root to the Activity, so the Activity can never be collected.

The safe alternative is application.applicationContext — it lives for the entire process lifetime anyway, so holding it statically is not a leak.

Under the hood

A Kotlin companion object is itself a nested singleton; properties declared in it compile to static fields on the enclosing class (with a synthetic Companion holder for the methods, or @JvmStatic/backing fields on the outer class). Either way the field lives in the class's static storage. ART keeps a class loaded as long as its defining ClassLoader is reachable, and the boot/app classloaders are never unloaded during normal app execution — so the field root is effectively permanent. The reason applicationContext is safe is identity: getApplicationContext() returns the single Application instance, which the framework already holds via ActivityThread.mAllApplications and the LoadedApk for the lifetime of the process. Holding another reference to an object that is already permanently reachable adds no retention. An Activity, by contrast, is meant to be released at onDestroy; the framework drops its own references (ActivityThread.mActivities token is cleared), so your static field becomes the sole surviving strong path that defeats collection.

AppClassLoader (GC root) ─▶ MyClass.class ─▶ static field `activity` ─▶ Activity (never freed)
AppClassLoader (GC root) ─▶ static field `appContext` ─▶ Application (already lives forever → no leak)

Non-Static Inner Class Holding Outer Activity

🎤 Say it out loud (~30–45s): "A non-static inner class — inner in Kotlin — captures an implicit reference to its outer instance, so if that inner object outlives the Activity, like a background task still running after Back is pressed, the Activity leaks. The fix is a static nested class plus a WeakReference to the Activity, so there's no implicit edge and the reference can be cleared. The thing I'd flag is that in modern Kotlin I wouldn't write this at all — I'd use a coroutine on lifecycleScope, which is cancelled automatically when the lifecycle is destroyed, so the leak window never exists."
// WRONG — Kotlin nested class is non-static by default
class MyActivity : Activity() {

    inner class MyTask : AsyncTask<Void, Void, String>() {  // holds implicit ref to MyActivity
        override fun doInBackground(vararg params: Void?) = heavyWork()
        override fun onPostExecute(result: String) {
            this@MyActivity.updateUI(result)  // implicit capture
        }
    }
}

An inner class — inner class in Kotlin, non-static nested in Java — holds an implicit reference to the enclosing instance. If MyTask outlives MyActivity, for example because the task is still running after the user presses Back, the Activity is leaked.

Fix: use a static nested class with a WeakReference

class MyActivity : Activity() {

    private var task: MyTask? = null

    override fun onDestroy() {
        super.onDestroy()
        task?.cancel(true)
        task = null
    }

    // Static nested — no implicit outer reference
    private class MyTask(activity: MyActivity) : AsyncTask<Void, Void, String>() {
        private val ref = WeakReference(activity)

        override fun doInBackground(vararg params: Void?) = heavyWork()

        override fun onPostExecute(result: String) {
            ref.get()?.updateUI(result)  // safe — Activity may be null
        }
    }
}

In modern Kotlin, the right answer is to use coroutines tied to lifecycleScope rather than AsyncTask entirely.

Under the hood

The compiler implements the "implicit outer reference" as a real synthetic field. A Kotlin inner class (or a non-static nested class in Java) gets a hidden field — this$0 in JVM bytecode — that is assigned the enclosing instance in the constructor, and every reference to an outer member compiles to this$0.member. That synthetic field is an ordinary strong reference, indistinguishable to the GC from any other field, which is why the inner object pins the Activity. Marking a nested class non-inner in Kotlin (the default) or static in Java omits the this$0 field entirely, so no edge exists. The same mechanism applies to lambdas: a lambda that touches this or an outer member is compiled to a class (or invokedynamic-generated object) capturing those values as fields, so a "harmless" lambda can leak exactly like an inner class. The coroutine alternative works because lifecycleScope is a CoroutineScope whose Job is cancelled in the lifecycle's onDestroy; cancellation throws CancellationException at the next suspension point, the continuation is dropped, and its captured references become unreachable.

Java/Kotlin source:  inner class MyTask  ──compiles to──▶  class MyTask { final MyActivity this$0; }
                     this@MyActivity.x    ──compiles to──▶  this$0.x   (strong reference → leak)

Handler and Delayed Messages

🎤 Say it out loud (~30–45s): "When I postDelayed a lambda that captures the Activity, that work sits in the main thread's MessageQueue until it fires. The Looper is a GC root, so the chain Looper → MessageQueue → Message → Runnable → Activity keeps the Activity alive for the entire delay — 30 seconds in the example — even after onDestroy. The fix is to remove the callbacks in onDestroy with removeCallbacksAndMessages(null), and ideally hold the target through a WeakReference so a stale message is a no-op. The gotcha interviewers like is that the Message object pool itself isn't the leak — it's that the queued Message strongly references your Runnable's captured this."

The problem

// WRONG
class MainActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // Lambda captures `this` (MainActivity)
        handler.postDelayed({
            doSomething()  // implicit capture of MainActivity
        }, 30_000L)
    }
}

The reference chain here is what traps the Activity. handler.postDelayed enqueues a Message in the main MessageQueue. That Message holds a reference to its Runnable. The Runnable lambda captures this (the Activity). The MessageQueue is attached to the main Looper, which is a GC root. So the full chain is: MessageQueue → Message → Runnable → Activity. Even after onDestroy, the Activity is kept alive for the full 30-second delay.

Fix: WeakReference pattern

class MainActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())
    private val activityRef = WeakReference(this)

    private val delayedTask = Runnable {
        activityRef.get()?.doSomething()  // no-op if Activity is gone
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler.postDelayed(delayedTask, 30_000L)
    }

    override fun onDestroy() {
        super.onDestroy()
        handler.removeCallbacks(delayedTask)  // CRITICAL: remove pending messages
    }
}

The key rule is: always call handler.removeCallbacksAndMessages(null) — or remove specific callbacks — in onDestroy.

Under the hood

Handler.postDelayed wraps your Runnable in a Message: it sets msg.callback = runnable, msg.target = handler, and computes msg.when = SystemClock.uptimeMillis() + delay, then inserts it into the MessageQueue's single-linked list ordered by when. The queue is owned by the thread's Looper, and Looper.loop() is itself invoked from ActivityThread.main() on the main thread, so the main Looper (a thread-local held for the process lifetime) is a live GC root. Until when arrives, the message is neither dispatched nor recycled, so the strong chain Looper → MessageQueue → Message.callback → Runnable → captured this keeps the Activity reachable. Handler itself also back-references via the lambda's captured outer instance. removeCallbacks walks the queue and unlinks matching messages (clearing msg.callback/msg.target and returning the Message to the static recycling pool via recycleUnchecked), which severs the chain. A WeakReference makes the still-queued message harmless because dispatch finds ref.get() == null and does nothing.

Looper(main, GC root) ─▶ MessageQueue ─▶ Message{ when, target=Handler, callback=Runnable }
                                                      └─▶ Runnable captures this$0 ─▶ Activity
removeCallbacks ⇒ unlink Message ⇒ recycleUnchecked() ⇒ chain broken

Coroutine Running Beyond Lifecycle

🎤 Say it out loud (~30–45s): "The classic bug is launching in GlobalScope from an Activity — the coroutine's continuation captures this, and since GlobalScope lives for the whole process, a suspended coroutine waiting on a network call keeps the destroyed Activity alive. The fix is to launch in a lifecycle-aware scope like lifecycleScope or viewModelScope so cancellation is automatic on onDestroy. The nuance interviewers probe is that cancellation is cooperative — your suspending calls have to be cancellable, and a tight CPU loop that never suspends won't actually stop until you check isActive or call ensureActive()."
// WRONG — GlobalScope coroutine captures Activity
class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        GlobalScope.launch {  // never cancelled
            val data = fetchData()
            runOnUiThread { updateUI(data) }  // MainActivity captured; Activity leaked
        }
    }
}

GlobalScope lives for the entire process lifetime. The coroutine's continuation captures the surrounding object — this@MyActivity — and after onDestroy, the coroutine is still suspended waiting for fetchData(), holding the Activity alive the whole time.

Fix: use lifecycleScope

🎤 Say it out loud (~30–45s): "lifecycleScope is a CoroutineScope whose Job is bound to the Activity's Lifecycle, so when the lifecycle hits DESTROYED the scope's Job is cancelled and every child coroutine with it. For ViewModels I reach for viewModelScope, which is cancelled in onCleared. The thing to remember is that this only protects against the scope outliving the owner — if I capture a View or Context inside the block and the coroutine genuinely needs to outlive the screen, I still have a leak, so I keep references narrow and let structured concurrency tear it all down."
class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycleScope.launch {  // cancelled automatically on onDestroy
            val data = fetchData()
            updateUI(data)
        }
    }
}

lifecycleScope is a CoroutineScope tied to the Activity's Lifecycle. When the Activity is destroyed, all launched coroutines are cancelled automatically. For ViewModels, use viewModelScope.

One subtlety worth knowing: even with lifecycleScope, a coroutine running during onStop that is expected to finish quickly is fine. The issue is long-running or indefinitely-suspended work that holds a reference to the Activity across destruction.

Under the hood

The Kotlin compiler turns a suspend function into a state machine: each suspension point becomes a label, and local variables that must survive the suspension are hoisted into fields of a generated Continuation (a subclass of ContinuationImpl). That continuation object holds the captured this reference — which is exactly why an outer Activity stays reachable. lifecycleScope is backed by LifecycleCoroutineScopeImpl, which registers a LifecycleEventObserver; on ON_DESTROY it calls coroutineContext.cancel(), propagating a CancellationException down the Job tree. Cancellation flips the Job to a cancelling state and resumes each suspended continuation with that exception at its next suspension point — which is why blocking, non-suspending work is uninterruptible.

GlobalScope.launch { fetchData() }   → Job's parent = GlobalScope (never cancelled)
lifecycleScope.launch { fetchData() } → Job's parent tied to Lifecycle.Job
   Lifecycle → DESTROYED → Job.cancel() → CancellationException at next suspend point

Callback/Listener Not Unregistered

🎤 Say it out loud (~30–45s): "Any long-lived object I hand a listener to — a system service like LocationManager, a singleton, a third-party SDK — now holds a strong reference back to my Activity or Fragment, and if I never unregister, the whole view hierarchy leaks. My rule is symmetric registration: whatever I register in onStart I unregister in onStop. The gotcha is that anonymous listeners and lambdas implicitly capture the outer this, so even a 'stateless'-looking callback pins the screen; modern code sidesteps this with repeatOnLifecycle or a DefaultLifecycleObserver that does the cleanup for me."
// WRONG
class MyFragment : Fragment() {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        locationManager.requestLocationUpdates(provider, 0, 0f, locationListener)
        // locationListener holds a reference to this Fragment
    }
    // Never removed → Fragment and its entire view hierarchy are leaked
}

The general principle is that any external object — a system service, a singleton, a third-party library — that holds a listener reference keeps the containing class alive. The fix is always symmetric registration and unregistration.

Fix: symmetric register/unregister

🎤 Say it out loud (~30–45s): "I pair the register and unregister calls to the matching lifecycle bracket — onStart/onStop for foreground-only work, onResume/onPause for visible-only, onCreate/onDestroy for process-scoped resources. The subtle part is choosing the right bracket: registering in onStart but unregistering in onDestroy means the listener stays live across onStop, burning battery and still risking a leak if the system kills the view but keeps the instance, so the brackets have to be symmetric and at the same lifecycle level."
override fun onStart() {
    super.onStart()
    locationManager.requestLocationUpdates(provider, 0, 0f, locationListener)
}

override fun onStop() {
    super.onStop()
    locationManager.removeUpdates(locationListener)
}

The rule is to pair registration with the matching lifecycle callback: onStart/onStop for things only needed in the foreground, onResume/onPause for things only needed when visible, and onCreate/onDestroy for process-wide resources.

Under the hood

System services like LocationManager are thin client-side proxies that talk to a system server process over Binder. When you call requestLocationUpdates, the framework wraps your listener in a ListenerTransport/ILocationListener stub and stores it in a HashMap<Object, ListenerTransport> keyed by your listener instance — a strong reference held inside LocationManager, which itself is a process-wide singleton obtained from Context. That map entry is the GC root that keeps your Fragment reachable. removeUpdates looks the listener up in that map and drops the entry, breaking the chain. An anonymous inner class compiled for the listener carries a synthetic this$0 field pointing at the enclosing Fragment, which is the actual leaked path.

LocationManager (singleton)
  └─ mListeners: HashMap<Listener, ListenerTransport>   ← strong ref
       └─ your listener (anon class)  →  this$0 = Fragment  →  View tree → Context

BroadcastReceiver Not Unregistered

🎤 Say it out loud (~30–45s): "A registered BroadcastReceiver is tracked by the ActivityManager through your Context, so if I register one in onCreate and never unregister, the receiver — and the Activity it was registered against — stays referenced after destruction. I register in onStart and unregister in onStop, or use a LifecycleObserver to do it automatically. Beyond the leak, the platform actually logs an IntentReceiverLeaked exception when an Activity is torn down with a receiver still registered, so it's a noisy, observable bug, not a silent one."
// WRONG
class MyActivity : AppCompatActivity() {
    private val receiver = MyBroadcastReceiver()

    override fun onCreate(savedInstanceState: Bundle?) {
        registerReceiver(receiver, IntentFilter(Intent.ACTION_BATTERY_CHANGED))
        // Activity destroyed but receiver still registered → Activity leaked via Context
    }
}

Fix

override fun onStart() { registerReceiver(receiver, filter) }
override fun onStop()  { unregisterReceiver(receiver) }

Alternatively, use a LifecycleObserver to auto-unregister when the lifecycle reaches the appropriate state.

Under the hood

Context.registerReceiver routes through ContextImpl, which asks the ActivityManagerService (AMS) to register an IIntentReceiver Binder stub. On the client side, LoadedApk maintains a ReceiverDispatcher cache — an ArrayMap keyed by Context then by receiver — so the dispatcher (and through it your receiver and its Activity context) is held strongly until unregisterReceiver removes it. When an Activity is destroyed with a receiver still registered, ActivityThread detects the dangling entry and logs android.app.IntentReceiverLeaked via StrictMode. Using a LocalBroadcastManager keeps everything in-process, but the same register/unregister symmetry still applies.

   destroyed Activity still keyed here  →  IntentReceiverLeaked logged on teardown

Adapter / ViewHolder Leaks

RecyclerView.Adapter holding stale data

🎤 Say it out loud (~30–45s): "An adapter is a view-layer object, so it should be owned by the Fragment or Activity, never by a ViewModel or singleton — if it outlives the screen, the items list and any Context captured in a ViewHolder leak with it. I use ListAdapter with DiffUtil so the adapter holds an immutable snapshot via submitList rather than a live reference into the data layer. The thing to flag is that even the right ownership leaks if I forget to clear recyclerView.adapter = null in a Fragment's onDestroyView, because the RecyclerView keeps recycled ViewHolders — and their View Context — referenced."
class MyAdapter(private val items: MutableList<Item>) : RecyclerView.Adapter<MyViewHolder>() {
    // 'items' may be a list from a ViewModel or repository.
    // If the Adapter lives longer than the Fragment (e.g., stored in a singleton),
    // 'items' (and transitively any Context captured in ViewHolder) is leaked.
}

The pattern to follow is that adapters should be owned by the Fragment or Activity, not by ViewModels or singletons. Use DiffUtil and ListAdapter so the adapter holds only the diffed snapshot, not a live mutable reference into the data layer.

Under the hood

RecyclerView keeps a Recycler with two tiers: a per-RecyclerView mCachedViews (default cap 2) of detached-but-not-rebound ViewHolders, and a shared RecycledViewPool keyed by view type. Each cached ViewHolder.itemView is a View whose mContext field points at the Activity that inflated it, so any retained ViewHolder transitively retains the Activity. ListAdapter runs DiffUtil on a background executor and swaps an immutable list reference, so the adapter never aliases your mutable source. Setting recyclerView.adapter = null triggers setAdapterInternal, which calls the pool's clear() and detaches cached holders, releasing those View→Context references.

ViewHolder holding View context

🎤 Say it out loud (~30–45s): "Every View stores a reference to the Context that inflated it, and for an Activity-inflated view that Context is the Activity. So if a ViewHolder — which wraps a View — gets stashed anywhere beyond the RecyclerView's own caches, the entire Activity and its window are reachable through itemView.getContext(). That's why I never hold ViewHolders in static fields or pass them to long-lived objects; the cheap mental check is 'this View knows its Activity.'"

Every View holds a reference to the Context that created it — the Activity. If a ViewHolder is stored somewhere beyond the RecyclerView's lifecycle, the entire Activity is reachable through that View.

Under the hood

A View is constructed with a Context argument that it stores in its final mContext field; for layouts inflated by an Activity that context is the Activity (an Application context only appears when explicitly used). Once attached, the View also gains a mAttachInfo referencing the ViewRootImpl and window. So the retention chain from a stray ViewHolder is ViewHolder.itemView → mContext (Activity) and, while attached, → ViewRootImpl → Window. A static or singleton reference to that holder becomes a GC root, and LeakCanary will report the path terminating at the Activity instance.

static field → ViewHolder → itemView (View) → mContext → Activity (+ Window via ViewRootImpl)

Dialog / Window Leaks

🎤 Say it out loud (~30–45s): "An AlertDialog built with the Activity as its Context attaches to that Activity's window token, so if the Activity finishes while the dialog is showing I either leak the window or hit a WindowManager$BadTokenException. I dismiss and null the dialog in onDestroy, but the cleaner answer is DialogFragment, which ties the dialog's show/dismiss to the fragment lifecycle and survives configuration changes. The subtlety is that you must use an Activity context, not an Application context, to show a dialog — the Application context has no window token — so you can't just dodge the leak by swapping contexts."
// WRONG — dialog holds Activity window token
class MyActivity : AppCompatActivity() {
    private var dialog: AlertDialog? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        dialog = AlertDialog.Builder(this)  // 'this' is Activity
            .setMessage("Loading...")
            .create()
        dialog?.show()
        // If dialog is not dismissed before Activity finishes,
        // Android WindowManager throws (or leaks the window).
    }
}

Fix

override fun onDestroy() {
    super.onDestroy()
    dialog?.dismiss()
    dialog = null
}

Use DialogFragment for dialogs that need to survive configuration changes — it handles the show/dismiss lifecycle correctly so the window token situation is managed for you.

Under the hood

dialog.show() calls WindowManager.addView with a WindowManager.LayoutParams whose token is the host Activity's window token (an IBinder from the Activity's ViewRootImpl). The system WindowManagerService indexes the window by that token, and the Dialog holds the Activity Context strongly through its decor view. If the Activity's window is destroyed first, the global WindowManagerGlobal still holds the dialog's view, producing the leak, and re-showing against a dead token throws WindowManager$BadTokenException. DialogFragment hooks onStart/onStop to call show/dismiss and re-creates the dialog after a configuration change, so the token is always live and the view is removed from WindowManagerGlobal before the Activity tears down.

   Activity finishes first → token dead → BadTokenException / leaked window in WindowManagerGlobal

Bitmap / Cache Leaks

🎤 Say it out loud (~30–45s): "The tricky thing about bitmaps is the memory accounting moved across versions — before API 26 the pixels lived in native memory with a small Java header, and from API 26 (Android O) both header and pixels are in native memory but the Bitmap Java object still tracks them. So if I stuff bitmaps into an unbounded static cache, native memory climbs toward an OOM while the Java heap looks totally healthy and a normal heap dump won't show the problem. The fix is a bounded LruCache sized in bytes, or just delegating to Glide or Coil, which manage both the bitmap pool and lifecycle-aware request cancellation for me."

Before API 26, bitmaps were backed by native memory with a small Java header. Since API 26, both the header and pixel data live in native memory, but the Bitmap object itself is still tracked by the Java GC. The trap is that if you accumulate bitmaps in a static cache without bounds, native memory grows unbounded while the Java heap looks perfectly healthy.

Always use a bounded LruCache or delegate to Glide/Coil — see §6.4 for details.

Under the hood

A Bitmap is a small Java object wrapping a native SkBitmap/SkPixelRef. Pre-API-26 the pixels sat in a separate native allocation freed via recycle() or an NativeAllocationRegistry; from API 26 the runtime registers the native pixel buffer with ART's NativeAllocationRegistry so GC pressure accounts for it, but the bytes are not on the managed heap — so a managed heap dump under-reports them. LruCache is just a LinkedHashMap in access order with a sizeOf override (you return bitmap.allocationByteCount); when size() exceeds maxSize it evicts the eldest entry and calls entryRemoved. Glide/Coil add a BitmapPool that reuses byte buffers via inBitmap to cut allocation churn, and tie request lifetimes to the Lifecycle so off-screen loads are cancelled.

   └─ native SkPixelRef (pixel bytes)  ← NOT on managed heap (API 26+)
unbounded static cache → native memory ↑↑ while Java heap looks flat → native OOM

WebView Leaks

🎤 Say it out loud (~30–45s): "WebView is one of the worst leak offenders because it holds a ton of native state tied to whatever Context inflated it. The trick is order of operations on destroy — detach it from the view hierarchy first, then call destroy(), then null your reference, and never put it in a static field. If I really need to be safe, I inflate it with the application context so it never grabs the Activity, and for the nuclear option I run it in its own process so any leaked native state dies when that process does."

WebView is notoriously hard to clean up, and the order of operations matters:

// Pattern to minimize WebView leaks
override fun onDestroy() {
    webViewContainer.removeAllViews()  // detach from hierarchy first
    webView.destroy()                  // release native resources
    webView = null
    super.onDestroy()
}

There are three additional mitigations worth knowing. First, inflate WebView with applicationContext rather than the Activity, to avoid keeping Activity context inside WebView's internal state. Second, if the leak is severe, run WebView in a separate process. Third, never store WebView in a static field.

Under the hood

A WebView is a thin Java/Kotlin facade over the Chromium rendering engine. Construction spins up native objects (the renderer's AwContents, ContentViewCore, settings, and a BrowserContext) that hold a JNI reference back to the Java-side Context you passed in. Chromium also registers process-wide singletons and component callbacks the first time a WebView is created, so even a destroyed-but-not-detached WebView can stay reachable. webView.destroy() is what tears down the native pair and unregisters those callbacks — but it asserts the view is already detached, which is why removeAllViews() must come first. Running WebView in :webview style separate process means the entire WebViewRenderProcess is sandboxed; when that process is killed, all the leaked native heap is reclaimed by the OS regardless of Java-side reachability.

Fragment View Binding Leaks

The problem

🎤 Say it out loud (~30–45s): "A Fragment has two lifecycles — the Fragment itself and its View. When the Fragment goes onto the back stack its view is destroyed at onDestroyView, but the Fragment instance keeps living. So if I stash the ViewBinding in a Fragment field and never clear it, that binding pins the whole inflated view tree in memory even though it's off-screen. The fix is to null the binding in onDestroyView. The subtle gotcha is that the Fragment can be re-attached and re-create its view later, so the field has to be nullable and re-assigned, not a lateinit val."

The root of this leak is that a Fragment has two distinct lifecycles: the Fragment lifecycle and the Fragment View lifecycle. The view is destroyed at onDestroyView while the Fragment itself may remain alive on the back stack. If you hold a ViewBinding reference in a Fragment instance variable, the binding keeps the entire View hierarchy alive after onDestroyView.

// WRONG
class MyFragment : Fragment() {
    private var binding: MyFragmentBinding? = null  // nullable but never nulled

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        binding = MyFragmentBinding.inflate(inflater, container, false)
        return binding!!.root
    }
    // binding retains all Views after onDestroyView → leak
}

Under the hood

A generated ViewBinding is just a holder object: its constructor walks the inflated hierarchy with findViewById and stores a hard reference to the root plus every id'd child view. Those View objects in turn hold mContext (the Activity), mParent, and listener references, so one binding field transitively pins the entire subtree. Meanwhile FragmentManager keeps the Fragment instance in its mActive/back-stack collections across onDestroyView, and the Fragment is a GC root for as long as it's tracked there. The Fragment's view-lifecycle LifecycleOwner (getViewLifecycleOwner()) is recreated on each onCreateView, which is precisely why the binding must be re-assigned per view-creation rather than held once — the old binding belongs to a dead view lifecycle.

Correct fix: null the binding in onDestroyView

🎤 Say it out loud (~30–45s): "The standard pattern is a backing _binding that's nullable plus a non-null binding accessor for convenience. I set _binding in onViewCreated and set it back to null in onDestroyView — that single line breaks the only strong reference from the surviving Fragment to the dead view tree, so the GC can collect it. The thing people forget is that the non-null get() = _binding!! accessor will throw if you touch it after onDestroyView, for example from a coroutine or callback that outlives the view, so view-touching work has to be scoped to viewLifecycleOwner."
class MyFragment : Fragment(R.layout.my_fragment) {
    private var _binding: MyFragmentBinding? = null
    private val binding get() = _binding!!

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        _binding = MyFragmentBinding.bind(view)
        binding.button.setOnClickListener { /* ... */ }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null  // CRITICAL: break reference to View hierarchy
    }
}

After _binding = null, no strong reference from the Fragment instance to the View hierarchy remains, so the Views can now be GC'd.

Under the hood

MyFragmentBinding.bind(view) skips inflation and only runs findViewById against the already-inflated root that the Fragment(@LayoutRes) constructor inflated for you, so it's cheaper than inflate. Setting _binding = null doesn't free anything immediately — it just removes the one strong edge in the object graph; reclamation happens whenever the next GC traces reachability and finds the view subtree unreachable. This is exactly the leak LeakCanary's FragmentAndViewModelClearedReferenceWatcher watches for: it installs a watch on the binding/viewLifecycleOwner after onDestroyView and reports a leak if the object is still reachable after a forced GC plus a delay.

Long-Running Thread Holding Activity

🎤 Say it out loud (~30–45s): "A running thread is itself a GC root, and the lambda I hand to Thread { } captures this — the Activity — so the Activity can't be collected until the thread finishes, even after the user navigates away. The fix is to use a lifecycle-aware scope like lifecycleScope so cancellation is automatic at onDestroy. If I'm stuck with a raw thread, I have to interrupt it explicitly and check isInterrupted in the loop — interrupt only works cooperatively, it won't kill a thread mid-CPU-work."
// WRONG
class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        Thread {                        // captures 'this' via lambda
            val result = longWork()
            runOnUiThread { show(result) }  // still holds Activity ref
        }.start()
    }
}

A Thread object is a GC root while it is alive — running or blocked. Its Runnable lambda captures the Activity. Even if the user navigates away, the thread and the Activity both stay alive until longWork() finishes.

Fix

Use lifecycleScope.launch(Dispatchers.IO) so the coroutine is cancelled automatically on onDestroy. If you must use raw threads:

private var workerThread: Thread? = null

override fun onDestroy() {
    workerThread?.interrupt()  // signal thread to stop
    workerThread = null
    super.onDestroy()
}

Under the hood

A live thread is a root in the GC's root set because the runtime (ART) enumerates all running thread stacks and their associated Thread objects as roots during the mark phase — anything reachable from a thread's stack frames or its target Runnable survives. The Kotlin Thread { ... } lambda compiles to a synthetic class implementing Runnable; because it references the enclosing Activity (via runOnUiThread/show), the compiler adds a captured field holding this, creating the strong edge. Thread.interrupt() does not forcibly stop anything — it sets an internal interrupt flag and, if the thread is parked in a blocking call (sleep, wait, join, interruptible I/O), throws InterruptedException; a thread busy in a tight CPU loop ignores it entirely unless it polls isInterrupted. lifecycleScope works because it's a CoroutineScope tied to the Activity's Lifecycle; the lifecycle observer calls cancel() on ON_DESTROY, which propagates CancellationException to suspending children at their next suspension point.

Book Deep-Dive

Thread-Related Memory Leaks

🎤 Say it out loud (~30–45s): "The core fact is that a thread stays a GC root until it terminates, so everything its Runnable captures lives as long as the thread does. I attack this three ways: prefer structured-concurrency scopes like lifecycleScope or viewModelScope where cancellation is wired to lifecycle automatically; use a cooperative interrupt flag for raw long-running loops; or if I truly must hold an Activity reference, hold it as a WeakReference and null-check on use so the GC can still reclaim it."

A Thread is a GC root until it terminates, so any object captured in the thread's Runnable — directly or indirectly — is kept alive for the thread's entire lifetime. There are three strategies for dealing with this. First, prefer lifecycleScope or viewModelScope where cancellation is automatic. Second, use an interrupt flag — call thread.interrupt() and check Thread.currentThread().isInterrupted in long loops. Third, pass a WeakReference<Activity> instead of the Activity directly.

Under the hood

Captured locals become fields on the synthetic Runnable class the Kotlin/Java compiler emits for the lambda or anonymous class; effectively-final locals are copied in, and the enclosing instance is stored as a synthetic outer reference. A WeakReference is special-cased by ART: weak references are recorded in the heap's reference-processing queue during marking and are not treated as keeping their referent alive, so if the only path to the Activity is through WeakReference.get(), the collector clears the reference (and may enqueue it) and reclaims the Activity. That's why the weak-ref pattern still requires a null check — get() can return null the moment the referent has been collected.

Static Inner Classes

🎤 Say it out loud (~30–45s): "In both Java and Kotlin, a non-static inner class — inner class in Kotlin — secretly holds a reference to its outer instance, the this$0 field. So an inner Runnable or Handler pins the whole Activity. The fix is to make it a static nested class — which in Kotlin is just a regular nested class without the inner keyword — so there's no implicit outer reference, and you pass in only what you actually need, ideally weakly. The gotcha people hit is that Kotlin's default nested class is already static; you have to opt in to the leak with inner."

In Java, every non-static inner class holds a hidden this$0 reference to its enclosing instance. In Kotlin, inner class has exactly the same behavior. Declaring the class as private class without the inner keyword in Kotlin — or as static class in Java — removes that hidden reference entirely.

// Kotlin: static nested (no outer reference)
class Outer {
    private class Worker : Runnable {
        // No access to Outer members unless passed explicitly
        override fun run() { /* ... */ }
    }
}

// Kotlin: inner class (has outer reference)
class Outer {
    inner class Worker : Runnable {
        override fun run() { this@Outer.someMethod() }  // can access Outer
    }
}

Under the hood

When you compile an inner/non-static inner class, the compiler synthesizes a field — this$0 in javac's naming — initialized in the constructor with the enclosing instance, and rewrites every implicit outer-member access into this$0.member. In bytecode the inner class's constructor gains an extra leading parameter of the outer type, and the outer class passes this when it instantiates it. A static nested class simply has no such parameter or field, so there is no edge in the object graph back to the outer instance. Kotlin inverts Java's default: a plain class Worker nested in Outer is compiled with no outer reference (static-equivalent), and only the inner modifier adds the synthetic outer field.

Weak References Pattern

🎤 Say it out loud (~30–45s): "When an inner object that can outlive the Activity — a Handler, an old AsyncTask, a thread — needs to call back into the Activity, I wrap the Activity in a WeakReference and get() plus null-check before touching it. If the Activity's already gone, I just bail. The classic case is a Handler on the main looper: a queued Message holds its target Handler, so a non-static Handler keeps the Activity alive until the message fires — wrapping the reference weakly plus draining the queue in onDestroy closes both holes."

The canonical leak-safe pattern for cases where an inner object — a Handler, an AsyncTask, a Thread — needs to call back to an outer Activity is to pass a WeakReference and check for null before using it:

class WeakHandler(activity: Activity) : Handler(Looper.getMainLooper()) {
    private val ref = WeakReference(activity)

    override fun handleMessage(msg: Message) {
        val act = ref.get() ?: return  // Activity gone — ignore
        when (msg.what) {
            MSG_UPDATE -> act.updateUI(msg.obj as String)
        }
    }
}

class MainActivity : AppCompatActivity() {
    private lateinit var handler: WeakHandler

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler = WeakHandler(this)
    }

    override fun onDestroy() {
        handler.removeCallbacksAndMessages(null)  // drain queue
        super.onDestroy()
    }
}

Under the hood

Every Message enqueued in the MessageQueue stores a target field pointing at the Handler that will dispatch it, and a delayed message sits in the queue (ordered by its when timestamp) until due. Because the main thread's Looper and its MessageQueue live for the entire process, a pending message transitively roots its Handler and, if the Handler is non-static, the enclosing Activity — that's the leak. The WeakReference breaks the Handler→Activity edge so the Activity is collectable, but the Handler and its queued messages still exist; that's why removeCallbacksAndMessages(null) in onDestroy is the complementary fix — it walks the queue and unlinks/recycles every Message whose target is this Handler, returning them to the Message object pool.

Stopping Worker Threads

🎤 Say it out loud (~30–45s): "There's a clear preference order. Best is cooperative cancellation — a @Volatile boolean the loop checks each iteration. Next is interrupt(), which is good for waking a thread out of a blocking call but only works if the worker actually checks isInterrupted or handles InterruptedException. For message-loop threads I use HandlerThread.quitSafely(), which drains pending work then stops. The one rule that's non-negotiable: never call Thread.stop() — it's deprecated because it can kill the thread mid-mutation and leave shared state corrupted with locks half-released."

There are three options, listed here in order of preference:

  1. Cooperative cancellation via flag:
   @Volatile private var running = true

   val thread = Thread {
       while (running) {
           processNextItem()
       }
   }

   fun stopWorker() { running = false }
  1. Interrupt:
   thread.interrupt()
   // In worker:
   while (!Thread.currentThread().isInterrupted) { ... }
  1. HandlerThread.quit() / quitSafely():
   val handlerThread = HandlerThread("worker").also { it.start() }
   val workerHandler = Handler(handlerThread.looper)

   fun cleanup() {
       handlerThread.quitSafely()  // processes pending messages, then stops
   }

Never use Thread.stop() — it is deprecated and unsafe because it can leave shared state in a corrupt condition.

Under the hood

The @Volatile modifier matters here for correctness, not just style: it forces reads/writes of running through main memory (a memory barrier on the JMM), so the worker thread actually observes the writer thread's false instead of caching a stale value in a register. interrupt() sets the thread's interrupt status flag and, for a thread blocked in an interruptible call, the runtime clears the flag and raises InterruptedException. HandlerThread.quit() calls Looper.quit(), which sets the MessageQueue to a quitting state and discards all pending messages; quitSafely() instead lets already-due messages drain but rejects new/future-dated ones, then MessageQueue.next() returns null and Looper.loop() exits, terminating the thread cleanly. Thread.stop() was deprecated because it throws ThreadDeath at an arbitrary instruction boundary, unwinding the stack and releasing every held monitor — leaving guarded objects visible to other threads in a half-updated, inconsistent state.

Retaining Worker Threads (across config changes)

🎤 Say it out loud (~30–45s): "When work needs to survive a rotation, I let a ViewModel own the coroutine scope, because the ViewModel outlives the Activity recreation — it's retained across configuration changes and only torn down in onCleared. So I cancel the scope's SupervisorJob in onCleared and everything cleans up. What I never do is the old onRetainNonConfigurationInstance or setRetainInstance(true) — both are deprecated, and retaining a raw thread that way risks holding the old Activity reference across the recreation."

The right approach here is to let a ViewModel own the thread or coroutine scope, because ViewModel survives configuration changes:

class MyViewModel : ViewModel() {
    private val workerJob = SupervisorJob()
    val scope = CoroutineScope(Dispatchers.IO + workerJob)

    override fun onCleared() {
        workerJob.cancel()  // cancels all children
    }
}

Never store a worker thread in onRetainNonConfigurationInstance or setRetainInstance(true) — both are deprecated.

Under the hood

A ViewModel survives configuration changes because its ViewModelStore is handed off through Activity.onRetainNonConfigurationInstance() internally — the framework stashes the store in a NonConfigurationInstances object that the next Activity instance picks up, so the same ViewModel object is reattached rather than recreated. The framework only calls onCleared() when the host is finishing for real (not rotating), which is detected via isChangingConfigurations(). A SupervisorJob is chosen over a regular Job so that one failing child cancels only itself, not its siblings; calling cancel() on it propagates cancellation down the parent-child job tree, throwing CancellationException at each child's suspension points. viewModelScope is just this exact pattern provided out of the box — a SupervisorJob plus Dispatchers.Main.immediate, cancelled for you in onCleared.

Cleaning Up Message Queues

🎤 Say it out loud (~30–45s): "Before I destroy anything that owns a Handler, I drain its queue — usually removeCallbacksAndMessages(null) to clear everything, or the targeted variants by Runnable or what code. If I don't, a message scheduled with postDelayed can fire after onDestroy, touching a dead view or null binding and either crashing with an NPE or just wasting work. The subtlety is that the pending message keeps the Handler — and a non-static Handler keeps the Activity — alive in the meantime, so draining is both a correctness and a leak fix."

Before destroying any component that owns a Handler, drain its queue:

// Remove all pending callbacks and messages
handler.removeCallbacksAndMessages(null)

// Or remove specific Runnable:
handler.removeCallbacks(myRunnable)

// Or remove by message.what code:
handler.removeMessages(MSG_CODE)

Failing to drain the queue means pending messages can fire after the Activity is destroyed, causing NullPointerException or silently wasting work.

Under the hood

MessageQueue is a singly-linked list of Message objects ordered by their when field; postDelayed inserts at the position matching SystemClock.uptimeMillis() + delay. removeCallbacksAndMessages(null) walks that list and unlinks every node whose target == thisHandler (the null argument means "match any token"), then recycles each removed Message back to the global pool via Message.recycleUnchecked(). The overloads differ by predicate: removeCallbacks matches on the callback Runnable field, removeMessages matches on the what int. None of this stops a message that's already been dequeued and is mid-dispatchMessage — there's an inherent race, which is the deeper reason view-touching callbacks should also null-check or be lifecycle-scoped rather than relying on draining alone.

6.3 Context Leaks

Activity Context vs Application Context

🎤 Say it out loud (~30–45s): "Context is abstract; the two subclasses that bite you are the Activity context, which lives only from onCreate to onDestroy, and the Application context, which lives for the whole process. The rule is: never hand an Activity context to anything that outlives the Activity — a singleton, a long-lived cache, a static field — or you pin the whole Activity and its view tree. Use the Application context for those. The flip side gotcha is you can't just always use the app context: dialogs, inflation with the right theme, and window tokens need the Activity context, because the app context carries the application theme, not the Activity's."

Context is an abstract class. The two concrete subclasses that matter most for leaks are Activity — including the host Activity referenced by a Fragment — and Application. Understanding which one to use in a given situation is one of the most common Android interview topics.

Property Activity Context Application Context
LifetimeFrom onCreate to onDestroyEntire process lifetime
Theme/style accessFull access (Activity theme)Application theme only (may be wrong theme)
UI operationsRequired for dialogs, window tokens, some ViewsNot suitable
Safe for singletonsNo — singleton outlives ActivityYes — same lifetime as process
GC riskHigh if held beyond onDestroyNone (lives as long as process)

Under the hood

Activity extends ContextThemeWrapper, which extends ContextWrapper — a decorator delegating to a base ContextImpl. The Application is also a ContextWrapper over its own ContextImpl. Crucially, an Activity is a Context and also holds the window, the view-root, and the themed Resources.Theme, so an Activity context transitively reaches the entire decor view hierarchy. getApplicationContext() returns the single process-wide Application instance, which has no window or theme overlay — that's why LayoutInflater or AlertDialog.Builder given the app context render with the base application theme and dialogs fail to obtain a valid window token. When something with a longer lifetime (a static, a singleton, an object on a never-ending thread) holds the Activity context, the Activity object stays in the GC root-reachable set, so neither it nor its inflated views can be collected — that's the textbook Context leak.

When Application Context Is Safe

🎤 Say it out loud (~30–45s): "The app context is the safe default any time there's no UI and the consumer lives a long time: initializing singletons like Retrofit, Room, or an image loader; grabbing non-UI system services like connectivity or notifications; resource and string access in non-UI layers; starting services and broadcasts; and SharedPreferences in a repository. In a Dagger/Hilt codebase I lean on the @ApplicationContext qualifier so injection can never accidentally smuggle an Activity into a singleton-scoped object — that's the gotcha the qualifier exists to prevent."

Use applicationContext for any of the following: initializing singletons such as Retrofit, Room, OkHttp, or image loaders; accessing system services where no UI is involved like getSystemService(CONNECTIVITY_SERVICE) or getSystemService(NOTIFICATION_SERVICE); string and resource access in non-UI code; starting Service or BroadcastReceiver intents; and SharedPreferences access in a repository or data layer.

class MyRepository @Inject constructor(
    @ApplicationContext private val context: Context  // Dagger qualifier
) {
    fun prefs() = context.getSharedPreferences("prefs", Context.MODE_PRIVATE)
}

Dagger's @ApplicationContext qualifier ensures the repository always receives application.applicationContext and never accidentally an Activity.

Under the hood

getSystemService returns managers that themselves cache a Context; for window-related services (like the deprecated direct use of WINDOW_SERVICE or layout inflation) that cached context matters, but for process-scoped services like connectivity or notifications the manager is effectively a singleton wrapper over a system Binder proxy, so passing the app context avoids tying it to an Activity. @ApplicationContext is a Dagger/Hilt @Qualifier annotation: at compile time the annotation processor generates a Provider bound to application.applicationContext, so the dependency graph resolves that exact instance — the qualifier disambiguates it from a @ActivityContext binding so a @Singleton-scoped object physically cannot be wired to an Activity-scoped context (Dagger would fail the scope check at compile time). getSharedPreferences keys its in-memory cache by name on the ContextImpl's package info, which is shared process-wide, so the same prefs file is returned regardless of which context retrieves it — another reason the app context is the correct, leak-free choice here.

When Activity Context Is Required

🎤 Say it out loud (~30–45s): "Activity context is required anytime the work touches the screen or a window — inflating layouts so they pick up the right theme and display metrics, building dialogs that need the Activity's window token, starting Activities without the NEW_TASK flag, and lifecycle-bound things like registerForActivityResult. My rule of thumb is: if it touches a window, use Activity context; otherwise prefer application context so I don't accidentally hold a reference past the Activity's lifetime. The gotcha an interviewer probes is the theme one — application context carries the app theme, not the Activity's, so a LayoutInflater built from it silently renders with the wrong styling."

Activity context is required in five situations. First, inflating layouts — the View needs the Activity context to pick up the correct theme and display metrics. Second, creating dialogs with AlertDialog.Builder(activityContext) — dialogs need the Activity's window token. Third, starting Activities when FLAG_ACTIVITY_NEW_TASK is absent — using application context requires that flag. Fourth, some system services where LayoutInflater.from(context) uses the context theme, and using application context gives the wrong theme. Fifth, registerForActivityResult and permission requests — these are bound to the Activity lifecycle.

The rule of thumb is simple: if it touches the screen or a window, use Activity context.

Under the hood

A Context is an abstract handle; the concrete instances differ in what they wrap. An Activity is a ContextWrapper whose base is a ContextImpl carrying a Resources.Theme resolved from the Activity's <activity> theme, plus a mToken (an IBinder Window token issued by the WindowManagerService). The Application's ContextImpl has the application theme and no window token. So addView/dialog show paths call into WMS with that token to attach a surface to the right window; an app context has no token and WMS rejects it (BadTokenException) — or for startActivity, ActivityManagerService requires FLAG_ACTIVITY_NEW_TASK because there's no task to inherit. LayoutInflater.from(context) simply reads context.getTheme(), which is why the identity of the context — not just "any context" — determines styling.

Activity (ContextWrapper) ─► ContextImpl { Theme=ActivityTheme, mToken=WindowToken }
Application (ContextWrapper) ─► ContextImpl { Theme=AppTheme,      mToken=null }
                                                              │
                       inflate/dialog/window ── needs token ──┘ (null → BadTokenException)

Singleton Must Not Hold Activity

🎤 Say it out loud (~30–45s): "A process-lifetime singleton holding an Activity is the classic large leak — the singleton outlives the Activity, so the GC can never collect it, and you're stranding the entire View tree, its Drawables and Bitmaps, which can be tens of megabytes. If I genuinely need a transient Activity reference I'd wrap it in a WeakReference and null it out, but the better answer is to redesign so the singleton talks back through a callback, event bus, or a Flow/LiveData and never holds the Activity at all. The subtle part is that it's not just the Activity object — it's every object the View hierarchy transitively reaches."

This is the most common source of large memory leaks. A single Activity instance contains its full View hierarchy — potentially hundreds of View objects, Drawables, Bitmaps, and text layouts — so leaking one Activity can mean tens of megabytes of memory that never comes back.

// WRONG
class AnalyticsManager private constructor() {
    var currentActivity: Activity? = null  // LEAK
    companion object { val instance = AnalyticsManager() }
}

// RIGHT — use WeakReference if you truly need the Activity temporarily
class AnalyticsManager private constructor() {
    private var activityRef: WeakReference<Activity>? = null

    fun attachActivity(activity: Activity) {
        activityRef = WeakReference(activity)
    }

    fun detachActivity() {
        activityRef = null
    }

    fun currentActivity(): Activity? = activityRef?.get()
}

The even better answer is to redesign so the singleton never needs an Activity reference at all. Use event buses, callbacks, or LiveData/Flow to communicate back to the UI layer.

Under the hood

ART's garbage collector is a tracing collector: it starts from GC roots and keeps anything reachable. A Kotlin object / companion object singleton is held by a static field on its class, and loaded classes are pinned by their ClassLoader (a GC root) for the life of the process. So a strong reference chain ClassLoader → AnalyticsManager.INSTANCE → currentActivity → DecorView → ... → every child View → each View.mContext (the Activity again) is fully reachable; the destroyed Activity's mark bit stays set every GC cycle and it's never reclaimed. A WeakReference instead stores the referent in a slot the collector clears during the reference-processing phase once no strong path exists, so get() returns null after collection. LeakCanary detects exactly this: after onDestroy it watches the Activity via a WeakReference + ReferenceQueue, forces a GC, and if the ref wasn't enqueued it computes the shortest strong path back to a GC root.

Views Must Not Outlive Activity

🎤 Say it out loud (~30–45s): "Every View keeps a hard reference to the Context it was inflated with — almost always the Activity — exposed as view.context. So caching a View in anything that outlives the Activity, like a static field or a singleton, leaks the whole Activity through that back-reference. If I need to survive configuration changes or recreation, I persist the data — Parcelable state or a ViewModel — and rebuild the Views, never stash the Views themselves. The trap is that it looks cheap, 'just one header view,' but that View transitively pins the entire hierarchy and its Activity."
// WRONG — View stored in a static or longer-lived object
object ViewCache {
    var cachedHeader: View? = null
}

Every View holds a reference to the Context — specifically the Activity — through which it was created, accessible as view.context. Storing a View in a singleton or any object that outlives the Activity leaks the entire Activity through that reference.

If you need to preserve layout state across recreation, store the data — Parcelable or serializable state — in a ViewModel, not the Views themselves.

Under the hood

View.mContext is assigned in the View(Context) constructor and never changes; LayoutInflater passes the Activity context down to every inflated child, and a ViewGroup holds its children in mChildren, each child holding mParent. The result is a densely connected object graph rooted at the DecorView, all sharing the same Activity context. When the static ViewCache.cachedHeader field (a GC root via its class) points at any node in that graph, tracing reaches mContext and re-pins the Activity. ViewModel survives recreation by a different mechanism entirely — it's retained in the ViewModelStore carried across config changes via onRetainNonConfigurationInstance, and onCleared() fires only on true finish — which is precisely why it should hold serializable state, not View references, so nothing leaks across the recreation boundary.

ViewCache.cachedHeader ─► HeaderView.mContext ─► Activity ─► Window ─► DecorView ─► (whole tree)
        (GC root)                                   leaked along with everything it reaches

6.4 Bitmap and Image Memory

Bitmap Memory Size

Formula

🎤 Say it out loud (~30–45s): "Bitmap memory is just width times height times bytes-per-pixel — it's independent of the on-disk file size, which is the thing people forget. A 4000×3000 photo at the default ARGB_8888 is four bytes a pixel, so about 48 megabytes decoded in RAM even if the JPEG was a couple hundred KB. So the levers are: decode at display resolution with inSampleSize, and drop to RGB_565 when you don't need alpha to halve it. On API 26+ I'd reach for HARDWARE config when the bitmap is display-only, since the pixels live in GPU memory and stay off the Java heap."
bytes = width × height × bytes_per_pixel
Config Bytes per pixel Notes
ARGB_88884Default; best quality
RGB_5652No alpha; acceptable for photos
ARGB_44442Deprecated, poor quality
ALPHA_81Masks only
HARDWARE0 (GPU memory)API 26+; not CPU-accessible

The numbers add up fast. A 4000×3000 photo at ARGB_8888 uses 4000 × 3000 × 4 = 48 MB per image. Loading even a few full-resolution phone camera shots can OOM most devices.

Under the hood

The decoder allocates a flat, uncompressed pixel buffer — rowBytes × height, where rowBytes is width × bytesPerPixel rounded up for alignment — so memory scales with pixel dimensions, never with the compressed encoding. The Config selects the in-memory pixel layout: ARGB_8888 packs 8 bits per channel into a 32-bit word; RGB_565 packs red/green/blue into 16 bits with no alpha. HARDWARE is special — the decoded pixels are uploaded into a GPU-backed GraphicBuffer/AHardwareBuffer that the renderer samples directly, so it consumes graphics memory rather than Java/native heap and getPixel() throws because the CPU can't read it. Skia (BitmapFactory → nativeDecode) does the actual decode into the chosen target.

ARGB_8888:  [A:8][R:8][G:8][B:8]  = 4 bytes/px
RGB_565:        [R:5][G:6][B:5]   = 2 bytes/px   (no alpha)
buffer size = rowBytes(aligned) × height   ── unrelated to JPEG/PNG file size

Historical note

Before API 26 (Oreo), bitmap pixel data was stored in a special native heap separate from both the Java heap and the regular native heap. That meant the Java OutOfMemoryError would not trigger even as you allocated hundreds of megabytes of bitmap data — the OOM came from the native allocator with confusing stack traces. Since API 26, pixel data lives in the normal native heap tracked by malloc, and ART applies back-pressure correctly.

Downsampling

🎤 Say it out loud (~30–45s): "Downsampling decodes a reduced-resolution version of an image instead of the full thing. I do a two-pass decode: first with inJustDecodeBounds = true to read the dimensions without allocating pixels, compute inSampleSize, then decode for real. inSampleSize is a power of two, and because it scales both linear dimensions, a sample size of 4 is 1/16 the pixels and 1/16 the memory. The key judgment is sampling to the display size, not the source — there's no reason to decode a 4K image to fill a 48dp thumbnail."

Downsampling is the technique of loading a smaller version of an image before decoding it, which reduces memory proportionally to the sample size.

fun decodeSampledBitmap(res: Resources, resId: Int, reqWidth: Int, reqHeight: Int): Bitmap {
    // First pass: decode with inJustDecodeBounds = true to get dimensions
    val options = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeResource(res, resId, options)

    // Calculate inSampleSize
    options.inSampleSize = calculateInSampleSize(options, reqWidth, reqHeight)
    options.inJustDecodeBounds = false

    return BitmapFactory.decodeResource(res, resId, options)
}

fun calculateInSampleSize(options: BitmapFactory.Options, reqWidth: Int, reqHeight: Int): Int {
    val (height, width) = options.run { outHeight to outWidth }
    var inSampleSize = 1
    if (height > reqHeight || width > reqWidth) {
        val halfHeight = height / 2
        val halfWidth = width / 2
        while (halfHeight / inSampleSize >= reqHeight && halfWidth / inSampleSize >= reqWidth) {
            inSampleSize *= 2
        }
    }
    return inSampleSize
}

inSampleSize must be a power of 2. Setting inSampleSize = 4 means a quarter of the linear dimensions, which is 1/16 the pixels and therefore 1/16 the memory.

The trade-off is that a lower inSampleSize gives a sharper image but uses more memory. The rule is to always match inSampleSize to the display size, not the source size — there is no point decoding a 4K image to show it in a 48 dp thumbnail.

Under the hood

inJustDecodeBounds = true makes the native decoder parse only the image header (the JPEG/PNG dimension markers) and populate outWidth/outHeight/outMimeType without allocating any pixel buffer — the decode returns null. On the real pass, Skia reads inSampleSize and subsamples while decoding: it never materializes the full-resolution bitmap, so peak memory is bounded by the output size, not the source. The decoder rounds a non-power-of-two inSampleSize down to the nearest power of two internally, which is why specifying one directly is conventional. For sizes between powers of two, decoders that support inScaled/inTargetDensity can post-scale, but pure inSampleSize is the cheapest path because the rejected pixels are never decoded in the first place.

Pass 1 (inJustDecodeBounds=true): parse header → outWidth/outHeight, allocate 0 bytes, return null
Pass 2 (inSampleSize=4):          decode every 4th pixel each axis → 1/16 pixels → 1/16 memory

Image Caching and LruCache

🎤 Say it out loud (~30–45s): "I use a two-level cache: a fast in-memory LruCache in front of a size-bounded disk cache, falling back to network or decode on a full miss. For the memory tier I size it as a fraction of Runtime.maxMemory() — about an eighth is the usual rule of thumb — and I override sizeOf to measure in real bitmap bytes, not entry count, since bitmaps vary wildly in size. The disk tier holds encoded JPEG/PNG so it survives process death and dodges the network round-trip. The gotcha is sizeOf units: maxSize and sizeOf must use the same unit or eviction misbehaves."

Two-level cache pattern

Request → Memory cache (fast, limited) → Disk cache (slower, larger) → Network/Disk decode

LruCache (in-memory)

LruCache evicts the least-recently-used entry automatically whenever the cache exceeds its configured capacity.

val maxMemory = (Runtime.getRuntime().maxMemory() / 1024).toInt()
val cacheSize = maxMemory / 8  // Use 1/8th of available memory

val memoryCache = object : LruCache<String, Bitmap>(cacheSize) {
    override fun sizeOf(key: String, bitmap: Bitmap): Int {
        // Return size in kilobytes
        return bitmap.byteCount / 1024
    }
}

// Add
memoryCache.put(key, bitmap)

// Get
val cached: Bitmap? = memoryCache.get(key)

The 1/8 fraction is a typical rule of thumb: too large and you cause memory pressure on the rest of the app; too small and you get frequent cache misses.

Under the hood

LruCache is backed by a LinkedHashMap constructed in access order (accessOrder = true). Every get removes and re-inserts the entry at the tail, so iteration order tracks recency; on each put it runs trimToSize, which evicts from the head (the least-recently-used end) until size() <= maxSize. size() is the running sum of sizeOf over all entries — which is why your sizeOf unit must match the maxSize unit (here, kilobytes). It's fully synchronized for thread safety. Note that LruCache only bounds count of bytes you report and holds entries with strong references — it does not interact with the GC or SoftReference (older SoftReference bitmap caches were abandoned because ART clears soft refs too aggressively and unpredictably).

LinkedHashMap(accessOrder=true):  [LRU head] A → B → C → D [MRU tail]
get(B):                           A → C → D → B            (B moved to tail)
put(E) and size>maxSize:          evict A (head), repeat trimToSize until size ≤ maxSize

DiskLruCache (on-disk)

DiskLruCache — from the AOSP samples, also shipped internally by Glide — caches encoded images in JPEG or PNG format on disk. It survives process restarts, is size-bounded, and is slower than a memory cache but much cheaper than a network round-trip.

Under the hood

DiskLruCache keeps the bytes in per-key files on disk and tracks state in an append-only journal (a text file of DIRTY/CLEAN/READ/REMOVE lines). On open it replays the journal to rebuild an in-memory access-ordered map of entries and their sizes; writes go through an Editor that stages to a .tmp file and atomically renames into place on commit, so a crash mid-write leaves a recoverable DIRTY record rather than a corrupt entry. When total on-disk size exceeds the bound, a background thread trims LRU entries by deleting their files and appending REMOVE lines; the journal is periodically rebuilt/compacted once it grows past a threshold. This is why it survives process death — the durable state is the files plus the journal, not in-RAM structure.

Glide / Coil / Picasso

🎤 Say it out loud (~30–45s): "These libraries all solve the same hard problem: turning a URL into a correctly-sized, cached bitmap without leaking or OOM-ing. They downsample to the view, keep a two-level memory and disk cache, tie the request to a lifecycle so it cancels automatically, and manage worker threads for you. The nuance I'd flag is that the big win isn't just caching — it's request cancellation on view recycle in lists, which is the thing people get wrong when they roll their own."

All three of these libraries handle the same core set of concerns: URL-to-bitmap loading, downsampling to display size, memory cache, disk cache, lifecycle awareness, placeholder and error drawables, and request cancellation.

Coil example (Compose)

🎤 Say it out loud (~30s): "Coil's AsyncImage is coroutine-native, so the request is scoped to the composition and cancels when the composable leaves. I build an ImageRequest, pass an explicit size so it downsamples to my view instead of decoding full resolution, and let the memory and disk cache policies do the rest.         .data("https://example.com/image.jpg")

Under the hood

Coil's AsyncImage launches the request from a rememberCoroutineScope-style scope tied to the composable's lifecycle via AsyncImagePainter, which holds the request as remembered state and cancels the underlying coroutine in onForgotten when the painter leaves composition. The ImageRequest flows through an interceptor chain (EngineInterceptor last) that checks the in-memory MemoryCache (an LRU-backed LinkedHashMap keyed by URL + transformations + size), then the disk DiskLruCache, then the network. Downsampling happens in BitmapFactoryDecoder, which reads the bitmap bounds with inJustDecodeBounds = true, computes inSampleSize as a power of two, and decodes a smaller bitmap directly so the full-resolution image never lands in memory.

             -> NetworkFetcher -> BitmapFactoryDecoder (inSampleSize) -> Bitmap

Glide example

🎤 Say it out loud (~30s): "Glide's API binds the load to a lifecycle owner — Glide.with(fragment) — so it automatically pauses on stop and resumes on start and cancels on destroy. I give it the URL, a placeholder and an error drawable, and a target view. The thing interviewers probe is the with() argument: passing the Activity or Fragment instead of the application context is what gives you the lifecycle-aware cancellation; passing application context disables it."
Glide.with(fragment)
    .load(url)
    .override(Target.SIZE_ORIGINAL)   // or specific px
    .placeholder(R.drawable.loading)
    .error(R.drawable.broken)
    .into(imageView)

Under the hood

Glide.with(fragment) attaches an invisible RequestManagerFragment (or a SupportRequestManagerFragment/lifecycle observer) to the host so Glide receives onStart/onStop/onDestroy callbacks; on stop it pauses pending requests, on destroy it clears them. .into(imageView) wraps the view in a ViewTarget that stashes the running Request in the view's tag via setTag. When you call into again on the same view, Glide reads that tag, cancels the prior request, and clears the resource — this is the implicit cancellation that makes list recycling safe. Glide's LruResourceCache plus a BitmapPool (which recycles old bitmap allocations into inBitmap for reuse) minimizes GC churn from decoding.

The reason to use a library rather than rolling your own is that manual bitmap loading in RecyclerView requires at least four non-trivial things: cancellation on view recycle, downsampling to the display size, two-level caching, and worker-thread management. All of those are already solved correctly by these libraries.

Hardware Bitmaps

🎤 Say it out loud (~30–45s): "A hardware bitmap, added in API 26 with Bitmap.Config.HARDWARE, keeps the pixels only in GPU memory as a graphic buffer rather than on the Java or native heap. That makes it cheaper to draw because there's no per-frame CPU-to-GPU upload, and it keeps pressure off your heap. The catch is it's immutable and CPU-opaque — getPixel, software Canvas drawing, and cross-process Parcelable all fail — so it's display-only. If I need to read or edit pixels, I decode to ARGB_8888 instead."

API 26 introduced Bitmap.Config.HARDWARE. A hardware bitmap stores pixel data only in GPU memory, which means it is immutable, it cannot be read back to the CPU — calls to getPixel() or copyPixelsToBuffer() throw — and it cannot be drawn with a software Canvas. The upside is that it is faster to draw because it skips the CPU-to-GPU upload step on each frame.

val options = BitmapFactory.Options().apply {
    inPreferredConfig = Bitmap.Config.HARDWARE
}
val bitmap = BitmapFactory.decodeResource(resources, R.drawable.photo, options)
// bitmap.config == Bitmap.Config.HARDWARE

Avoid hardware bitmaps when you need to read pixels back — for image editing — when drawing with a software Canvas such as for accessibility overlays or some Drawables, or when sharing the bitmap via Parcelable across processes.

Glide and Coil can be configured to prefer hardware bitmaps:

// Glide
Glide.with(context).asBitmap().load(url)
    .apply(RequestOptions().format(DecodeFormat.PREFER_ARGB_8888))  // or PREFER_RGB_565
    .into(target)

Under the hood

A hardware bitmap is backed by an Android HardwareBuffer (an AHardwareBuffer, which wraps a graphics allocation such as a GraphicBuffer/gralloc buffer), not by a byte[] on the Java heap or a malloc'd region on the native heap. Because the buffer lives in shared graphics memory, the GPU can sample it directly during rendering, and the system can also map a single buffer into multiple processes via the file-descriptor it carries. The immutability and CPU-read restrictions exist because the memory isn't guaranteed to be CPU-addressable or linearly laid out — it may be tiled/swizzled for the GPU — so getPixel throws an IllegalStateException rather than returning garbage. There's also a hard ceiling on the number of simultaneous hardware bitmaps because each consumes a file descriptor and a gralloc buffer; exceeding the process FD limit forces the framework to fall back to software-backed bitmaps.

ARGB_8888 bitmap:  pixels in native heap (mutable, CPU-readable)
HARDWARE bitmap:   pixels in HardwareBuffer / gralloc (GPU memory, FD-backed, opaque to CPU)

RecyclerView Image Cancellation

🎤 Say it out loud (~30–45s): "In a list, ViewHolders get reused, so a slow load kicked off for row 3 can finish after that holder is now showing row 27 and stamp the wrong image — the classic 'flickering wrong avatar' bug. The fix is to cancel the in-flight request when the holder rebinds or recycles. With Coil and Glide this is mostly automatic: loading a new URL into the same view cancels the previous request because the request is tagged to the view. I still call dispose() or clear() in onViewRecycled to be explicit and to release the bitmap reference."

When a ViewHolder is recycled, the previous image load must be cancelled. Otherwise a slow load started for item #3 could complete and set its image on item #27, which has since been reused — giving the user the wrong image.

class ImageViewHolder(val binding: ItemImageBinding) : RecyclerView.ViewHolder(binding.root) {

    fun bind(url: String) {
        // Coil: request is tagged to the ImageView;
        // loading a new URL automatically cancels the previous one
        binding.image.load(url) {
            placeholder(R.drawable.placeholder)
        }
    }

    fun recycle() {
        // Explicitly cancel and clear (not always needed with Coil/Glide but explicit is safer)
        binding.image.dispose()
    }
}

With Glide, call Glide.with(fragment).clear(imageView) to cancel and clear. With Coil, calling imageView.dispose() is explicit, but simply calling imageView.load(newUrl) handles cancellation of the previous request implicitly.

Under the hood

Both libraries store the active request on the target view itself via the view tag mechanism (View.setTag(id, request)). When load/into runs again on a recycled view, the library reads the stored disposable/request from the tag and cancels it before starting the new one — for Coil that means cancelling the request's coroutine Job, for Glide it means calling Request.clear() and returning the bitmap to the BitmapPool. The reason the wrong-image bug exists at all is that RecyclerView calls onBindViewHolder on the same holder instance for different positions, and a background decode that completes later has no idea the holder moved on — so the cancellation has to be keyed to the view, not the position. Explicitly cancelling in onViewRecycled also drops the strong reference from the completed callback to the ImageView, which helps the bitmap and any captured context get collected promptly.

holder bound to row 3  -> request A started, tagged on ImageView
holder recycled -> row 27 -> load() reads tag, cancels request A, starts request B
request A (if not cancelled) would resolve and call into a stale ImageView -> wrong image

Avoiding OOM

🎤 Say it out loud (~30–45s): "Bitmap OOM almost always comes down to decoding images bigger than you display — a single full-res photo can be tens of megabytes once it's an ARGB_8888 bitmap. So rule one is downsample to the view size, and rule two is just use Coil or Glide because they do that plus bounded caching automatically. Beyond that I bound the memory cache to something like maxMemory/8, respond to onTrimMemory to evict under pressure, and never decode on the main thread — an OOM there is also an ANR. The subtle one people forget pre-API-26 is recycling bitmaps you own, since their pixels lived on the native heap and weren't reclaimed by a normal GC."

There are eight rules to avoid bitmap OOM. First, always downsample to display size — never load a 4K image into a 48 dp thumbnail view. Second, use a library like Coil or Glide — they handle all of the above automatically. Third, set a bounded memory cache, and maxMemory / 8 is a reasonable starting point. Fourth, use Bitmap.Config.RGB_565 for non-transparent images where quality allows, which cuts memory in half compared to ARGB_8888. Fifth, recycle bitmaps when done — bitmap.recycle() — especially pre-API 26. Sixth, handle onTrimMemory in your Application or image loader to evict caches under memory pressure. Seventh, prefer hardware bitmaps on API 26 and above for display-only images. And eighth, never load images on the main thread — StrictMode will warn you, and an OOM blocking the main thread also triggers an ANR.

Under the hood

A bitmap's memory cost is width × height × bytesPerPixel, where ARGB_8888 is 4 bytes and RGB_565 is 2 — so a 4000×3000 photo is ~48 MB at ARGB_8888 regardless of the file's compressed size on disk. Downsampling works through BitmapFactory.Options.inSampleSize: the decoder reads only the header with inJustDecodeBounds = true, you compute a power-of-two sample factor, and the second decode subsamples pixels so the large image is never fully materialized. The location of those pixels changed at API 26 (Android 8.0): before O, bitmap pixel data lived in the native heap, separate from the Java/Dalvik object, which is why recycle() mattered and why leaks were easy to miss in the Java heap profiler; from O onward, pixels moved back into the managed heap (or into a HardwareBuffer for hardware bitmaps) and are reclaimed by ordinary GC, making recycle() largely unnecessary. onTrimMemory callbacks are dispatched by ActivityManager with levels like TRIM_MEMORY_RUNNING_LOW and TRIM_MEMORY_UI_HIDDEN; a well-behaved LruCache shrinks maxSize or calls evictAll() in response, and the framework consults the per-app heap limit (ActivityManager.getMemoryClass()) — exceeding it throws OutOfMemoryError even when device RAM is free.

file.jpg (2 MB compressed)  --decode-->  4000x3000 x 4 bytes = ~48 MB ARGB_8888 bitmap
with inSampleSize = 8       --decode-->  500x375 x 4 bytes   = ~0.75 MB

6.5 Leak Detection and Profiling

Android Studio Memory Profiler

🎤 Say it out loud (~30–45s): "The Memory Profiler gives me a live heap graph split into Java, native, graphics, code, and stack, plus the ability to force a GC and capture heap dumps. What I'm actually reading is the shape: a sawtooth of allocate-then-collect is healthy, but a floor that keeps rising after each GC means something is retained that shouldn't be. My fast first test is to rotate or navigate back and forth and check whether the heap returns to baseline — if it doesn't, I capture a heap dump to find the retaining reference."

The Memory Profiler shows a real-time heap allocation graph broken down by Java heap, native heap, graphics, stack, code, and others. It shows total allocations per time window, lets you trigger GC manually, and supports heap dump capture and analysis.

The workflow is: run the app, open the Profiler tab, select Memory, and click on the graph to start observing. A sawtooth pattern — allocation, then GC, then plateau — is normal. A growing floor after each GC cycle is the signal that something is leaking. Rotating the device or navigating back and checking whether the heap drops back to baseline is a quick first check. If it does not, capture a heap dump to confirm.

Under the hood

The profiler collects data through two mechanisms: a JVMTI agent attached to the app process for allocation tracking, and periodic sampling of the process's memory state via the kernel and ART. The category breakdown maps to real accounting — "Java" is the ART managed heap, "native" is malloc/C++ allocations (read from /proc/<pid>/smaps-style accounting), "graphics" is GPU/EGL and gralloc buffers, "code" is .dex/.so and mmapped files. When you press "Force GC," Android Studio sends a command that triggers ART's concurrent collector (a generational, concurrent copying/mark-sweep collector), so the post-GC floor reflects only objects still reachable from a GC root. That's exactly why a rising post-GC floor is diagnostic: anything the collector couldn't reclaim is, by definition, still strongly reachable from somewhere — a static field, a live thread, a registered listener — which is the leak.

Heap Dump

🎤 Say it out loud (~30–45s): "A heap dump is a full snapshot of every live object on the managed heap at one instant, written as an .hprof file. I sort by retained size to find what's holding the most memory, then for a suspect — say two instances of an Activity that should be a singleton after Back — I walk the references tree from the instance back to its GC root. That shortest path to a root is the smoking gun: it tells me exactly which static field, handler, or listener is pinning the object."

A heap dump is a snapshot of all live objects on the heap at a specific point in time, stored in .hprof format. You can capture one three ways: clicking "Dump Java Heap" in the Memory Profiler, calling Debug.dumpHprofData(filePath) programmatically, or running adb shell am dumpheap <pid> /data/local/tmp/heap.hprof.

When analyzing in Android Studio, the workflow has three steps. First, the class list view — sort by "Retained Size" descending to find the largest retained objects. Second, the instance list — click a class to see all live instances; multiple Activity instances of the same class with no more user interaction is a clear leak signal. Third, the references tree — for a suspicious instance, expand "References" to trace the reference chain back to the GC root.

There are five things to look for specifically in a heap dump. First, multiple instances of a single Activity class — there should be at most one after pressing Back. Second, Activity instances reachable from static fields. Third, Bitmap objects with large byteCount accumulated in a static cache. Fourth, Fragment instances with a non-null mView field after expected destruction. Fifth, Handler objects that hold references back to Activities.

Under the hood

The .hprof file is a binary format (Android's variant of the JVM HPROF format, which hprof-conv or Studio normalizes) that serializes every object as a record: its class, identity hash, field values, and the object IDs it references — effectively the entire object reference graph frozen at dump time. "Retained size" is a graph computation, not a single object's size: it's the total memory that would be freed if that object were collected, computed from the dominator tree, where object X dominates Y if every path from a GC root to Y passes through X. "Shallow size" is just the object's own fields. To find a leak, the analyzer searches for the shortest path from the suspect instance to a GC root — roots being JNI globals, live thread stacks, system classes, and static fields of loaded classes — because as long as such a path exists, the concurrent collector will never reclaim the object. LeakCanary automates exactly this by watching destroyed objects with a WeakReference, forcing a GC, and if the referent survives, dumping the heap and computing that shortest-path-to-root for you.

GC Root (static APP.cache) ──▶ LruCache ──▶ Entry ──▶ MainActivity (should be dead!)
                                                          └─ retained size includes its whole view tree

Allocation Tracking

🎤 Say it out loud (~30–45s): "Allocation tracking records every allocation and its stack trace over a window, so I reach for it when I see lots of GC activity but no growing retained set — that's churn, not a leak. I record, exercise the app, stop, then sort by allocation count or shallow size and look in hot paths like onBindViewHolder or onDraw. The gotcha is that allocation pressure causes jank without ever looking like a 'leak' — the heap stays flat but the GC is constantly running, so the profiler graph alone won't tell you; you have to read the call sites."

Allocation tracking records each allocation event with its stack trace during a recording window. Use it when you see frequent GC events but no permanent leak — in that case you are looking for allocation pressure and churn, not retained objects.

The workflow in the Memory Profiler is: click "Record allocations", use the app, then click "Stop". Sort by "Allocations" or "Shallow Size" and look for allocations in rendering paths — onDraw, onBindViewHolder, draw.

Common findings include String concatenation inside onBindViewHolder, ArrayList or HashMap churn in data processing loops, and lambda objects created fresh inside setOnClickListener on every bind call.

Under the hood

ART implements allocation tracking by switching the allocation entrypoints to instrumented versions: when tracking is enabled, the runtime points each thread's TLS allocation stub at a slow-path allocator that, after carving the object out of the thread-local allocation buffer (TLAB), records an entry into a fixed-size circular AllocRecordObjectMap. Each record captures the class, the byte size, the thread, and a walked stack trace (depth-bounded). Because every allocation now takes the instrumented path instead of the fast inline bump-pointer in the TLAB, the app runs noticeably slower while recording — which is why this is a debug-only, windowed tool. The records are streamed to the profiler over JDWP/the perfa agent and aggregated by call site.

fast path (normal):   TLAB bump pointer → return object   (a few instructions)
tracking path (on):   allocate → walk stack → append AllocRecord → return object

LeakCanary

LeakCanary is Square's open-source automatic leak detection library for debug builds.

How it works (internals)

🎤 Say it out loud (~30–45s): "LeakCanary watches objects that should die — destroyed Activities, Fragments, ViewModels — by wrapping each in a KeyedWeakReference and registering it with a ReferenceQueue. After a destroy plus an idle delay it forces a GC; if the weak ref hasn't been enqueued, the object survived when it shouldn't have, so it dumps the heap and runs Shark to find the shortest strong path from a GC root. The nuance interviewers like is that it relies on WeakReference semantics and the ReferenceQueue — it's not polling object state, it's asking the GC 'did you collect this yet?' and treating 'no' as the leak signal."

LeakCanary works in five steps. First, the detection trigger: LeakCanary installs an ActivityLifecycleCallbacks — plus Fragment and ViewModel equivalents — and when an Activity is destroyed it adds the instance to a KeyedWeakReference list and schedules a check. Second, the reachability check: after a roughly 5-second delay, it triggers GC and checks whether the WeakReference was cleared. If the reference was not cleared, the object is still alive and is likely leaked. Third, the heap dump: LeakCanary calls Debug.dumpHprofData() to capture a snapshot. Fourth, path analysis: it uses its internal HPROF parser, Shark, to find the shortest strong-reference path from a GC root to the leaked object. Fifth, notification: it shows a notification with the full leak trace and the exact field names at each step in the reference chain.

Under the hood

The mechanism is built on java.lang.ref.WeakReference plus a ReferenceQueue. Each watched object is wrapped in a KeyedWeakReference(referent, key, queue); when the GC determines the referent is only weakly reachable, it clears the reference and enqueues it onto the ReferenceQueue. LeakCanary drains that queue and removes the matching key from its set of "still watched" objects. The check runs on an idle handler (after IdleHandler fires and a delay), then calls Runtime.gc()/System.gc() and re-drains the queue. Anything still in the watched set after GC is a retained instance. Shark then memory-maps the HPROF file and walks the object graph as records — class dumps, instance dumps, and root records — computing the dominator path with a breadth-first shortest-path search from GC roots so it can name the exact field at each hop.

watch(activity) → KeyedWeakReference(activity, key, queue)
GC runs        → if only weakly reachable: clear ref + enqueue onto ReferenceQueue
check          → drain queue → key still present? → RETAINED → dump heap → Shark path

Setup

// build.gradle (app module) — debug only
debugImplementation("com.squareup.leakcanary:leakcanary-android:2.x")
// No Application code needed — LeakCanary auto-installs via ContentProvider

Read it bottom-up: MainActivity$1, an anonymous inner class, is the retained object. It holds a reference back to MainActivity through this$0. MainActivity was already destroyed. And MySingleton.activityRef is the GC root that is keeping the entire chain alive.

Trade-offs

LeakCanary is debug-only — never ship it to production because heap dumps are expensive. False positives are rare but possible, for instance when framework code legitimately holds a reference briefly. And there is roughly a 5 to 10 second delay between Activity destruction and the notification, because the library waits to ensure the GC had a chance to run.

Android Vitals

🎤 Say it out loud (~30–45s): "Android Vitals is the production memory-and-stability data Google Play aggregates from opted-in real devices, so it's how I see leaks I can't reproduce locally. For memory I care about the ANR rate — long GC pauses on the main thread show up as ANRs — plus OutOfMemoryError crashes and the LowMemoryKills metric, which tells me how often the OS killed my process. The thing people miss is the device dimension: Vitals lets me bucket OOMs by RAM tier and model, so I can prove a leak only bites on low-RAM devices rather than guessing."

Android Vitals is Google Play Console's production crash, ANR, and memory data aggregated from opted-in real devices.

The metrics most relevant to memory are ANR rate — because GC pauses blocking the main thread can trigger ANRs — crash rate from OutOfMemoryError and NullPointerException from GC'd weak references, stuck partial wake locks and excessive wakeups which are symptoms of resource leaks.

For a memory investigation, the workflow is: filter crashes by OutOfMemoryError to see which code paths OOM in production. The crash details include a stack trace and the device model and RAM tier, which lets you correlate leaks with low-RAM devices. The LowMemoryKills metric — available via the Play Console API — counts how often the OS killed your process for low memory, which is an actionable signal for how well your onTrimMemory handling is working.

Under the hood

Vitals data flows from the on-device DropBoxManager and the platform crash/ANR pipeline. When your process hits an uncaught OutOfMemoryError, RuntimeInit reports it through the activity manager, which records a crash entry; ANRs are detected by the system when the main thread fails to service input/broadcast within the watchdog window (commonly ~5s for input), at which point the system captures the traces of every thread into an ANR report. Low-memory kills come from the Linux Low Memory Killer / lmkd daemon, which kills processes by oom_adj score under memory pressure; the kill reason is surfaced via ActivityManager.getHistoricalProcessExitReasons() (API 30+) as REASON_LOW_MEMORY and rolled up into the LowMemoryKills metric. GMS Core batches these reports and uploads them for opted-in users, where the backend aggregates by app version, device model, and RAM bucket.

Under the hood

dumpsys meminfo doesn't measure memory itself — it asks each process's ActivityThread (via a binder call into the app, with a fallback to reading /proc/<pid>/smaps) to walk its virtual memory mappings and categorize them. PSS is computed from smaps by summing each mapping's private pages plus its shared pages divided by the number of processes mapping them, which is why summing PSS across processes roughly approximates physical RAM without double-counting shared libraries. Pages are classified as dirty (modified, backed by swap/anonymous, must be written out to reclaim) versus clean (unmodified file-backed pages that can be dropped and re-read for free). The "Graphics" line is gathered from the GPU memory accounting (dmabuf / gralloc buffers) rather than the heap.

Pss(mapping) = Private_Dirty + Private_Clean + (Shared_Dirty + Shared_Clean) / sharing_count

Perfetto

🎤 Say it out loud (~30–45s): "Perfetto is the system-wide tracing stack that replaced Systrace from API 28 on, and for memory I use three probes: heapprofd for sampled native malloc profiling with stacks, android.java_hprof for a Java heap snapshot streamed into the trace, and track_event for my own Trace.beginSection markers. I pick it over the Memory Profiler when I need system-wide context — GPU, media, system_server — or low-overhead, production-close native leak hunting. The key nuance is that heapprofd is sampled, not exhaustive — it samples roughly every 4 KB allocated — so it's statistically accurate for finding where memory grows but won't catch every tiny allocation."

Perfetto is the system-wide tracing infrastructure that replaced Systrace on API 28 and above.

There are three memory-relevant probes. First, heapprofd, the heap profiler — it samples native malloc allocations with full stack traces at very low overhead, with a default sampling interval of 4096 bytes, and it shows you exactly where native memory grows. ``bash adb shell perfetto --out /data/misc/perfetto-traces/trace \ -c - --txt <<EOF buffers: { size_kb: 63488 } data_sources: { config { name: "android.heapprofd" heapprofd_config { sampling_interval_bytes: 4096 process_cmdline: "com.example.app" } } } duration_ms: 15000 EOF ``

Second, android.java_hprof — a Java heap snapshot that is like a heap dump but streamed directly into a Perfetto trace. Third, track_event — custom trace events you add to your own code with Trace.beginSection and Trace.endSection.

Open the trace at ui.perfetto.dev. The Memory track shows RSS and PSS over time, and zooming in shows individual allocation events from heapprofd.

Use Perfetto over the Memory Profiler for system-wide analysis — for example, to check whether GPU, media, or system_server is consuming memory — for production-close profiling at lower overhead, or when investigating native memory leaks that do not show up in Java heap dumps.

Under the hood

heapprofd works by interposing on the allocator: the central traced service tells the traced_perf/heapprofd daemon to attach to the target, and the target's libc scudo/jemalloc allocator routes allocations through a sampling hook. It uses Poisson sampling keyed to the sampling_interval_bytes — roughly one sampled allocation per 4096 bytes of allocation on average — and for each sampled allocation it unwinds the native stack (out-of-process, using the daemon, to keep target overhead low) and attributes the bytes to that call stack. Because it's sampled, reported sizes are scaled up to estimate the true total. Trace data is written into ring buffers in shared memory and committed to the output file; the whole system uses a producer/consumer protocol where app and system processes are producers and traced is the central tracing service. android.java_hprof instead triggers an ART heap walk and serializes the object graph into the same protobuf trace stream rather than a standalone .hprof file.

6.2 — Android Memory Leaks

🎤 Say it out loud (~30–45s): "An Android memory leak is almost always an object that outlives its useful life because something reachable from a GC root still points at it — most commonly an Activity or its View tree. The classic offenders are non-static inner classes capturing the outer this, Handlers whose pending messages sit in the MessageQueue, and Fragment view bindings held past onDestroyView. The nuance interviewers probe is that the leak isn't the reference itself, it's the lifetime mismatch — so the fix is either to break the reference at the right lifecycle callback or to hold it weakly so GC can reclaim it."
Question Answer
How can Handler leak Activity?postDelayed lambda captures Activity; MessageQueue (GC root) holds the message for the delay duration. Fix: WeakReference + removeCallbacksAndMessages.
Why can non-static inner classes leak?Hold implicit this$0 reference to outer class. If the inner class outlives the outer, the outer is leaked. Fix: private class (static nested) + explicit WeakReference if back-reference needed.
How do you avoid Fragment binding leaks?Null _binding in onDestroyView(). Never use binding after onDestroyView.
How do you detect memory leaks?LeakCanary (debug), Memory Profiler (heap dump + growing floor), dumpsys meminfo.
Memory leak vs high memory usageLeak: memory that should be free is not, grows monotonically. High usage: bounded, legitimate data retention.
How to clean message queuehandler.removeCallbacksAndMessages(null) in onDestroy.

Under the hood

The "implicit reference" the answer mentions is a synthetic field the Kotlin/Java compiler generates: a non-static inner class gets a hidden field (this$0 in JVM bytecode) initialized in its constructor to the enclosing instance, and every captured local becomes a val$x field. A lambda passed to postDelayed is compiled the same way — it captures the enclosing class instance to call its methods. At runtime the leak chain is concrete: the static thread-local Looper is a GC root, it owns the MessageQueue, each queued Message holds a target Handler and a callback Runnable, and the Runnable's synthetic field pins the Activity. ART's reachability-based GC will never collect the Activity while that chain holds, regardless of how many finish() calls happened.

Thread (GC root) → ThreadLocal<Looper> → MessageQueue → Message.callback (Runnable)
                                                       → Runnable.this$0 → Activity → View tree → Bitmaps

removeCallbacksAndMessages(null) walks the queue and unlinks every Message whose target == this handler, then recycles them to the Message pool — severing the chain so the next GC pass reclaims the Activity. A WeakReference works differently: ART tracks it specially and clears the referent during GC's reference-processing phase once nothing strongly reaches it.

6.3 — Context Leaks

🎤 Say it out loud (~30–45s): "A Context leak is a special case of an Activity leak — an Activity Context drags the entire themed View hierarchy, Drawables, and Bitmaps with it, so retaining one is expensive. My rule is: anything that lives longer than a screen — repositories, singletons, caches — gets the Application context, which lives for the whole process. The gotcha is that you can't just always use the Application context: theming, layout inflation, and dialog/window-token operations genuinely need the Activity Context, so the skill is matching Context lifetime to the consumer's lifetime."
Question Answer
Which Context should a repository use?applicationContext — never Activity context. Inject with @ApplicationContext.
Why is storing Activity in singleton dangerous?Singleton is a GC root; Activity (with full View hierarchy, Drawables, Bitmaps) can never be GC'd.
When is Activity context required?Dialog creation, layout inflation with theme, starting Activities without NEW_TASK flag, some window/token operations.

Under the hood

Activity extends ContextThemeWrapper, which extends ContextWrapper — all three ultimately delegate to a ContextImpl created per Activity, but the Activity itself adds the Window, WindowManager token, and a themed Resources.Theme. That's why a dialog or LayoutInflater needs the Activity Context: it reads theme attributes resolved against that Activity's theme and attaches the inflated views to the Activity's window token. The Application context is a single ContextImpl whose lifetime equals the process, holding only the application-level theme.

The reason a singleton reference is fatal is reachability: a Kotlin object or DI-scoped singleton is itself rooted (the classloader holds the class, the class holds the static instance), so anything it references is permanently reachable.

object FeatureManager {
    var ctx: Context? = null   // if assigned an Activity, leaks the whole screen for the process lifetime
}
// Safe: inject the application Context, which would have leaked nothing because it's already process-scoped
class Repo @Inject constructor(@ApplicationContext private val ctx: Context)

Hilt's @ApplicationContext qualifier resolves to the singleton-component-bound Application context precisely so injected long-lived objects can't accidentally capture an Activity.

6.4 — Bitmap and Image Memory

🎤 Say it out loud (~30–45s): "Bitmaps are usually the single biggest memory consumer because a decoded image costs width × height × bytes-per-pixel regardless of the compressed file size — a 4000×3000 ARGB_8888 photo is ~48 MB in RAM even if the JPEG is 2 MB. So the core move is downsampling to the display size with inSampleSize and reusing a two-level cache. In practice I delegate to Coil or Glide because they tie loads to the lifecycle and cancel on recycle. The gotcha interviewers love is RecyclerView image flicker — you must cancel the previous async load on view recycle or a stale image lands in a reused row."
Question Answer
How do you avoid OOM with images?Downsample to display size (inSampleSize), use LruCache, delegate to Coil/Glide, handle onTrimMemory.
Why use image loading libraries?They handle downsample, two-level cache, lifecycle cancellation, worker threads, placeholder/error states automatically.
How does image caching work?Memory cache (LruCache, fast) → disk cache (DiskLruCache, slower) → network. Hit memory first, fall back to disk, then network.
What is a hardware bitmap?Bitmap.Config.HARDWARE — pixel data in GPU memory. Faster to draw, immutable, cannot be read by CPU.
How do you prevent wrong images in RecyclerView?Cancel previous load on recycle: Coil imageView.dispose() / imageView.load(newUrl), Glide Glide.with(...).clear(imageView).

Under the hood

Since Android 8.0 (API 26) a Bitmap's pixel buffer lives in the native heap, not the Java/Dalvik heap (pre-8.0 it sat in Java heap and pressured the GC). The Java Bitmap object is a thin handle; native memory is freed when the handle is finalized or recycle() runs. This is why dumpsys meminfo reports large image apps under "Graphics" / native rather than "Dalvik Heap". inSampleSize works during decode: BitmapFactory with inSampleSize = 4 reads only every 4th pixel in each dimension, allocating a buffer 1/16 the size — so it never materializes the full-resolution buffer in the first place. Setting inJustDecodeBounds = true does a header-only pass to read outWidth/outHeight so you can compute the right sample size before allocating anything.

A HARDWARE bitmap is uploaded into a GPU texture (GraphicBuffer/AHardwareBuffer); the GPU draws it without a CPU upload each frame, which is why it's faster but unreadable by the CPU and can exhaust the per-process file-descriptor limit if you hold thousands. LruCache itself is just a LinkedHashMap in access-order mode plus a sizeOf accounting hook; when size() exceeds maxSize it evicts the eldest (least-recently-accessed) entry via trimToSize.

6.5 — Detection and Profiling

🎤 Say it out loud (~30–45s): "My investigation funnel goes from coarse to fine. In production I start with Android Vitals to see OOM crash rates and affected devices; locally I reproduce and watch the Memory Profiler for a heap floor that keeps rising after forced GCs — a rising floor is the leak signature versus normal sawtooth. Then I capture a heap dump, sort by retained size, and look for the smoking gun: multiple instances of the same Activity, Fragments with live views, or oversized static caches. The nuance is that the Java heap profiler is blind to native allocations — for native or bitmap-heavy leaks I reach for Perfetto's heapprofd."
Question Answer
How would you investigate OOM?Android Vitals for production OOM crashes; Memory Profiler for live heap; heap dump to find large retained objects; LeakCanary for Activity/Fragment leaks.
How would you find a leak?LeakCanary (automatic); or Memory Profiler — observe growing heap floor after GC, capture heap dump, find multiple Activity instances, trace reference chain to GC root.
What would you check in a heap dump?Sort by Retained Size; look for multiple Activity instances, large Bitmap arrays in static caches, Fragment instances with live views, Handler instances referencing Activities.
When to use Perfetto?Native memory leaks (heapprofd), system-wide memory analysis, production-close profiling, or when Java heap profiler misses native allocations.
What does dumpsys meminfo show?PSS breakdown by category (Native Heap, Dalvik Heap, Graphics, Stack). Private Dirty is the most actionable number — growing private dirty = leak or unbounded cache.

Under the hood

LeakCanary's automation is mechanical: it installs an ObjectWatcher that, via lifecycle callbacks, wraps each destroyed Activity/Fragment/ViewModel in a KeyedWeakReference tied to a ReferenceQueue. After a destroy it triggers GC and checks whether the weak ref was enqueued; if the referent is still reachable after a delay, it dumps the heap with Debug.dumpHprofData() and runs Shark to compute the shortest strong reference path from a GC root to the leaked object — that path is the leak trace you read in the report.

A heap dump is an HPROF file: a binary record stream of class definitions, instance dumps with field values, and the root set (JNI globals, thread stacks, static fields, etc.). "Retained size" is what the profiler computes by building the dominator tree — the total memory that becomes unreachable if a given object is collected — which is why sorting by it surfaces the true culprit rather than a leaf.

PSS (Proportional Set Size) = private pages + (shared pages / number of sharers)
Private Dirty = pages only this process owns AND has modified → cannot be paged out or shared

Private Dirty is the most actionable line because it represents memory the OS can reclaim only by killing the process; a monotonic climb there is the same leak signature as the Memory Profiler's rising floor. Perfetto's heapprofd hooks malloc/free at the native allocator level via sampling, so it captures C/C++ and bitmap-buffer allocations that never appear in the Java HPROF dump.
