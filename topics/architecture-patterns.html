7.1 MVC, MVP, MVVM, MVI

MVC — and "Massive Activity"

🎤 Say it out loud (~30s): "MVC splits responsibilities into Model, View, and Controller, but on Android the framework gives you nothing to enforce that split — the Activity ends up being the Controller, the View, and a dumping ground for everything else. The gotcha interviewers want is why it rots: there's no protocol forcing a clean interface, so logic flows to the path of least resistance, which is always the Activity, and you get a 2,000-line 'Massive Activity'."

Definition

Model-View-Controller is the oldest of the mainstream patterns. The Model holds data and business logic, the View renders the UI, and the Controller sits in the middle — it receives user input, tells the Model to change, and tells the View to update.

Android Reality

🎤 Say it out loud (~30s): "In practice the Activity or Fragment is the Controller, but it also inflates layouts, owns the view hierarchy, gets lifecycle callbacks, and does I/O. Because setContentView() and onClick() live in the same class, the View and Controller collapse into one. The nuance is that a giant Activity isn't a skill problem — it's the predictable end state of a pattern with no architectural constraint."

In a naive Android MVC implementation the Activity or Fragment plays the Controller role — but it also inflates the layout, receives lifecycle callbacks, handles permissions, starts animations, and does I/O. Nothing in the framework enforces separation, so everything funnels into the Activity. This is the "Massive Activity" anti-pattern.

A 2,000-line Activity is not a sign of bad programmers; it is a sign that MVC has no architectural constraint preventing the Controller from absorbing its neighbours' responsibilities. The View and Controller collapse into a single class because setContentView() and onClick() live in the same place.

Under the hood

There is no "Controller" type in the Android SDK — the role is purely conceptual. Activity extends Context and is instantiated by the framework via Instrumentation.newActivity() (reflection on the class name from the manifest), then driven through ActivityThread's message loop: performLaunchActivity → onCreate → onStart → onResume. Because the Activity is simultaneously a Context, a Window owner (PhoneWindow/DecorView), and a LifecycleOwner, it has direct field access to the view tree, system services, and resources. Nothing structurally separates "handle input" from "render UI," so the compiler happily lets one class reference both — that's the mechanism behind the Massive Activity.

ActivityThread.handleLaunchActivity
  → Instrumentation.newActivity(cl, className, intent)   // reflective instantiation
  → activity.attach(context, ...)                        // wires in Window, Context
  → Instrumentation.callActivityOnCreate → onCreate()    // setContentView() inflates DecorView

Problems

🎤 Say it out loud (~30s): "The big four are: it's untestable because the Controller is an Activity needing a live runtime; it's tightly coupled because the Controller directly references both Model and View; it has a lifecycle mismatch since the Controller dies on rotation and forces save/restore boilerplate; and there's no clear ownership. The throughline is that every problem stems from the Activity being the Controller."
  • Untestable: the Controller is an Activity, which requires a live Android runtime to run.
  • Tight coupling: the Controller directly references both Model and View; swapping either requires touching the Controller.
  • Lifecycle mismatch: the Controller is torn down on configuration change, forcing state restoration boilerplate.
  • No ownership: when everyone is responsible for everything, nothing has a clear owner.

Under the hood

The "untestable" problem is concrete at the JVM level: instantiating an Activity with new gives you an object whose Context, resources, and Window are all null because the framework's attach() was never called — any method touching them throws NullPointerException. That's why running Activity logic off-device requires either a real device/emulator (the full ActivityThread pipeline) or Robolectric, which ships a shadow object graph that fakes the android.jar stubs (the SDK android.jar you compile against contains only method stubs that throw new RuntimeException("Stub!") at runtime). The lifecycle mismatch is real teardown: on configuration change the framework calls onDestroy() and creates a brand-new instance, so any state held in Controller fields is garbage-collected unless serialized into the Bundle passed to onSaveInstanceState.

Interview Angles

Q: Why does MVC become messy in Android? "The framework offers no separation between View and Controller. The Activity is both the entry point for user events and the owner of the UI hierarchy, and there is no protocol forcing a clean interface between them. So logic migrates to the path of least resistance — and that path is always the Activity."

Q: What is "Massive Activity"? "It's an Activity that has grown to encompass networking, business logic, UI manipulation, persistence, and lifecycle handling — everything MVC left unassigned ends up there. It's the natural end state of unconstrained MVC on Android."

MVP — Passive View and Presenter

🎤 Say it out loud (~30s): "MVP introduces a strict View interface so the Presenter holds pure presentation logic with no Android imports — that makes it JUnit-testable with a mocked view. The catch interviewers probe is the lifecycle leak: the Presenter holds a reference to the Activity, so an async callback returning after onDestroy will call methods on a dead view unless you null it out or detach in onDestroy."

Definition

Model-View-Presenter fixes MVC's biggest problem by introducing a strict contract between the View and the Presenter via an interface. The View is deliberately passive — it forwards user events to the Presenter and blindly applies whatever the Presenter tells it to display. The Presenter owns all presentation logic and has no dependency on Android framework classes, which means it's testable with plain JUnit.

// The View contract — implemented by the Activity/Fragment
interface LoginView {
    fun showLoading()
    fun hideLoading()
    fun showError(message: String)
    fun navigateToHome()
}

// The Presenter — pure Kotlin, no android imports
class LoginPresenter(
    private val authRepository: AuthRepository,
    private val view: LoginView   // <-- holds a View reference
) {
    fun onLoginClicked(email: String, password: String) {
        view.showLoading()
        authRepository.login(email, password) { result ->
            view.hideLoading()
            when (result) {
                is Success -> view.navigateToHome()
                is Failure -> view.showError(result.message)
            }
        }
    }
}

// The Activity
class LoginActivity : AppCompatActivity(), LoginView {
    private lateinit var presenter: LoginPresenter

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        presenter = LoginPresenter(AuthRepository(), this)  // passes 'this' as view
        binding.loginButton.setOnClickListener {
            presenter.onLoginClicked(binding.emailField.text.toString(), binding.passwordField.text.toString())
        }
    }

    override fun showLoading() { binding.progress.isVisible = true }
    override fun hideLoading() { binding.progress.isVisible = false }
    override fun showError(message: String) { Toast.makeText(this, message, Toast.LENGTH_SHORT).show() }
    override fun navigateToHome() { startActivity(Intent(this, HomeActivity::class.java)) }
}

Under the hood

The View interface is what decouples the Presenter at the bytecode level. When the Presenter calls view.showLoading(), the compiler emits an invokeinterface opcode against LoginView, not an invokevirtual against LoginActivity — so the concrete type is resolved by dynamic dispatch at runtime through the object's vtable/itable. That indirection is precisely why a test can supply a Mockito/MockK proxy: the mock is a dynamically generated class implementing LoginView, and invokeinterface dispatches to it identically to a real Activity. The Presenter .class file carries zero references to android.*, so it loads and runs on a plain JVM with no android.jar on the classpath.

Lifecycle Leak Risk

🎤 Say it out loud (~30s): "The Presenter strongly references the View, which is the Activity. If a network call returns during a rotation, the Presenter calls into an Activity that's already destroyed — best case a wasted UI update, worst case it pins the destroyed Activity in memory, a classic leak. I fix it by nulling the view in detachView()/onDestroy() and using view?.method() so stale callbacks become silent no-ops."

The Presenter holds a direct reference to the View, which is the Activity. If an async operation completes after the Activity is destroyed — say a network call returns during a configuration change — the Presenter calls methods on a dead Activity. The three common mitigations are:

  1. Nullable view: call view?.showError(...). Null the reference in onDestroy.
  2. WeakReference: WeakReference<LoginView>. Slightly more ergonomic; slightly more fragile.
  3. Detach on lifecycle: expose attachView(view) / detachView() and call detachView() in onDestroy().
class LoginPresenter(private val authRepository: AuthRepository) {
    private var view: LoginView? = null

    fun attachView(v: LoginView) { view = v }
    fun detachView() { view = null }

    fun onLoginClicked(email: String, password: String) {
        view?.showLoading()
        authRepository.login(email, password) { result ->
            view?.hideLoading()  // safe: view may be null if Activity destroyed
            when (result) {
                is Success -> view?.navigateToHome()
                is Failure -> view?.showError(result.message)
            }
        }
    }
}

Under the hood

The leak is a GC-reachability problem. A destroyed Activity should become garbage once the framework drops its references, but if the Presenter (held by, say, a retained object or a static/singleton, or captured in an in-flight callback's closure) keeps a strong field pointing at the Activity, that Activity stays reachable from a GC root and is never collected — along with its entire DecorView tree and bitmaps. The lambda { result -> ... } passed to authRepository.login is compiled into a synthetic class whose fields capture this (the Presenter), and the Presenter's view field reaches the Activity; so until the network future completes, the closure is a live retention path. WeakReference breaks the path by letting the collector reclaim the referent and return null from .get(); explicit detachView() breaks it by overwriting the strong field with null at a deterministic point (onDestroy).

Interview Angles

Q: MVP vs MVVM — which do you prefer and why? "MVVM is almost always the right choice for new code. The ViewModel is lifecycle-aware — it survives configuration changes without any manual detach/attach plumbing — and it exposes observable state that the View drives reactively. With MVP, you're managing the lifecycle contract entirely by hand; MVVM offloads that to the Jetpack ViewModel component. MVP's main remaining advantage is familiarity in codebases that are already heavily invested in it, but rewriting working MVP code is usually not worth the churn."

Q: How does Presenter communicate with the View? "Through the View interface. The Presenter calls methods on the interface, and the Activity or Fragment is the concrete implementation. That indirection is what makes the Presenter unit-testable — in a test I just pass in a mock LoginView and I never need an Activity at all."

Q: How do you avoid leaking the Activity? "I null out the view reference in detachView() or onDestroy(), and I use view?.method() everywhere so calls on a null reference are silent no-ops. The alternative is storing the View in a WeakReference, which is slightly more ergonomic but slightly more fragile — I prefer the explicit null check."

MVVM — ViewModel, StateFlow, Immutable State

🎤 Say it out loud (~30s): "MVVM puts all UI state in a lifecycle-aware ViewModel that exposes it as observable streams; the View just observes and re-renders, and crucially the ViewModel holds no reference to the View. The two things interviewers always probe: it survives config changes for free because it lives in a retained ViewModelStore, and you must never put a Context or View in it or you leak the Activity."

Definition

Model-View-ViewModel separates UI state management from the UI itself. The ViewModel owns all UI state and exposes it as observable streams. The View — whether that's an Activity, Fragment, or Composable — observes state and re-renders; it never mutates state directly. The Model is the data and domain layer underneath.

Why ViewModel Survives Configuration Change

🎤 Say it out loud (~30s): "The ViewModel isn't owned by the Activity instance — it lives in a ViewModelStore that the Activity hands off across re-creation via onRetainNonConfigurationInstance. So on rotation the Activity is destroyed and rebuilt, but it reattaches to the same store and gets the same ViewModel back. The nuance is that onCleared() only fires on a real finish — back press or finish() — not on a config change, which is exactly the distinction isChangingConfigurations() captures."

ViewModel is stored in a ViewModelStore owned by the ViewModelStoreOwner, which is the Activity. That ViewModelStore is retained across configuration changes via onRetainNonConfigurationInstance() — the ViewModel instance stays alive in a store that outlives the Activity instance. Only when the Activity finishes permanently — through a back press or a call to finish() — does the ViewModelStore clear and onCleared() fire.

// The ViewModel — no Context, no View references
class LoginViewModel(
    private val authRepository: AuthRepository
) : ViewModel() {

    // Mutable state kept private — only ViewModel can write
    private val _uiState = MutableStateFlow<LoginUiState>(LoginUiState.Idle)
    // Immutable view — View only observes this
    val uiState: StateFlow<LoginUiState> = _uiState.asStateFlow()

    // One-time events via SharedFlow (not StateFlow — see below)
    private val _events = MutableSharedFlow<LoginEvent>(extraBufferCapacity = 1)
    val events: SharedFlow<LoginEvent> = _events.asSharedFlow()

    fun onLoginClicked(email: String, password: String) {
        viewModelScope.launch {
            _uiState.value = LoginUiState.Loading
            authRepository.login(email, password)
                .onSuccess {
                    _uiState.value = LoginUiState.Success
                    _events.emit(LoginEvent.NavigateToHome)
                }
                .onFailure { e ->
                    _uiState.value = LoginUiState.Error(e.message ?: "Unknown error")
                }
        }
    }
}

// Immutable sealed UI state
sealed interface LoginUiState {
    data object Idle : LoginUiState
    data object Loading : LoginUiState
    data object Success : LoginUiState
    data class Error(val message: String) : LoginUiState
}

// One-time navigation events
sealed interface LoginEvent {
    data object NavigateToHome : LoginEvent
}
// The Composable — observes, never mutates
@Composable
fun LoginScreen(viewModel: LoginViewModel = hiltViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    val context = LocalContext.current

    // Consume one-time events
    LaunchedEffect(Unit) {
        viewModel.events.collect { event ->
            when (event) {
                is LoginEvent.NavigateToHome -> { /* navigate */ }
            }
        }
    }

    when (uiState) {
        is LoginUiState.Idle -> LoginForm(onLoginClicked = viewModel::onLoginClicked)
        is LoginUiState.Loading -> CircularProgressIndicator()
        is LoginUiState.Success -> { /* handled via event */ }
        is LoginUiState.Error -> ErrorMessage((uiState as LoginUiState.Error).message)
    }
}

Under the hood

ComponentActivity implements ViewModelStoreOwner. The ViewModelStore is just a HashMap<String, ViewModel> keyed by a canonical key (the ViewModel class name, or a Hilt/qualified key). On a configuration change the framework calls Activity.retainNonConfigurationInstances(), which packages the ViewModelStore into a NonConfigurationInstances blob; ActivityThread holds that blob while the old Activity is destroyed and the new one is constructed, then the new ComponentActivity retrieves it in getLastNonConfigurationInstance() and reinstalls the same store — same ViewModel objects, same identity. ViewModelProvider.get() does a store.get(key): a hit returns the existing instance, a miss runs the Factory and store.puts it. On a genuine finish, ComponentActivity observes its own Lifecycle hitting ON_DESTROY while isChangingConfigurations() is false, and calls viewModelStore.clear(), which loops every entry calling ViewModel.clear() → your onCleared() and cancels viewModelScope (a CoroutineScope whose Job is cancelled here).

rotate:   onDestroy(isChangingConfigurations=true)  → store survives via NonConfigurationInstances → reattached
back/finish: onDestroy(isChangingConfigurations=false) → viewModelStore.clear() → onCleared() + viewModelScope cancel

Immutable State — Why It Matters

🎤 Say it out loud (~30s): "Exposing read-only StateFlow means the View physically cannot corrupt state — all writes funnel through one mutation point in the ViewModel. The payoff beyond safety is debuggability and Compose correctness: because each state is an immutable value, Compose can do structural equality to decide what to recompose, and every state transition is a self-contained snapshot I can log."
  • The View cannot accidentally corrupt ViewModel state because the exposed StateFlow is read-only.
  • Every state transition happens in the ViewModel under controlled conditions — inside a coroutine, at a single mutation point.
  • Compose can compare previous and new state to decide what to recompose, but that only works with value equality, which immutable data classes provide.
  • You can log every state transition, and each log entry is a complete, self-contained picture of the UI at that moment — which makes debugging dramatically easier.

Under the hood

MutableStateFlow deduplicates by comparing the incoming value to the current one with equals() before emitting — so for a data class, the auto-generated structural equals()/hashCode() (the compiler emits these from the constructor vals) means setting the same logical value is a no-op and won't wake collectors. asStateFlow() returns a ReadonlyStateFlow wrapper that exposes only the read API, so the View has no .value setter at compile time. On the Compose side, recomposition skipping depends on parameters being @Stable/@Immutable: the Compose compiler plugin tags a class as stable when all its public properties are stable and immutable, then generates code that compares old vs new arguments with equals() and skips the recomposition if they're equal. A var field or a raw List (vs ImmutableList) is inferred unstable, defeating that comparison and forcing recomposition every time.

What Should NOT Be in a ViewModel

🎤 Say it out loud (~30s): "Nothing that carries a Context or touches the view tree — no Activity, Fragment, View, Binding, or NavController. The reason is concrete: the ViewModel outlives the Activity across rotation, so holding any of those pins a destroyed Activity in memory. The ViewModel should be pure Kotlin — repositories, use cases, and viewModelScope coroutines."
  • Context (unless AndroidViewModel is justified — prefer passing primitives or injecting abstractions).
  • References to Activity, Fragment, View, or Binding.
  • Navigation logic that requires Android SDK types.
  • Heavy I/O done without a coroutine scope (use viewModelScope).
  • Business logic that belongs in a Use Case / Interactor.

Under the hood

This is the inverse of the survival mechanism: because the same ViewModel object spans multiple Activity instances, a strong field referencing Activity #1 keeps it GC-reachable after rotation creates Activity #2 — you now have two DecorView trees alive, and LeakCanary will flag the retained instance. AndroidViewModel is the sanctioned exception because it stores the Application context, which is a process-lifetime singleton (ContextImpl for the app), so retaining it leaks nothing. viewModelScope is an extension property backed by a CloseableCoroutineScope stored in the ViewModel's tag map with a SupervisorJob() + Dispatchers.Main.immediate; ViewModel.clear() invokes its close(), cancelling the Job so in-flight coroutines stop rather than continuing to touch released state.

StateFlow vs LiveData

🎤 Say it out loud (~30s): "Both survive config changes inside a ViewModel and both conflate. LiveData is lifecycle-aware out of the box and tolerates nulls — a Java-era API; StateFlow is Kotlin-idiomatic, requires a non-null initial value, but isn't lifecycle-aware on its own, so I collect it with collectAsStateWithLifecycle or repeatOnLifecycle to avoid wasting work while the UI is in the background. For new Kotlin/Compose code I default to StateFlow."

Under the hood

LiveData is lifecycle-aware because observe(owner, observer) registers a LifecycleBoundObserver that subscribes to the owner's Lifecycle; it only dispatches when the owner is at least STARTED and auto-removes the observer at ON_DESTROY, and it tracks a per-observer version counter so a re-STARTED observer gets the latest value exactly once. StateFlow has none of that — it's a plain hot flow that always has a value and emits on the collecting coroutine's dispatcher; "lifecycle awareness" comes from collectAsStateWithLifecycle/repeatOnLifecycle(STARTED), which cancels and restarts the collecting coroutine on stop/start so collection genuinely pauses. Conflation differs too: StateFlow conflates by definition (a slow collector skips intermediate values and only sees the latest), and it uses equals() to drop duplicate emissions, whereas LiveData posts via postValue which conflates by overwriting a pending value on the main-thread handler.

StateFlow vs SharedFlow for Events

🎤 Say it out loud (~30s): "I model one-time events — navigation, toasts — as SharedFlow with replay = 0, never StateFlow. StateFlow always replays its latest value to any new collector, so after a rotation a new collector would re-fire 'NavigateToHome' and bounce the user. SharedFlow with no replay fires once; the equally valid alternative is a Channel consumed as a flow, which gives single-delivery semantics."

Use SharedFlow — not StateFlow — for one-time events like navigation or toasts. The reason is that StateFlow replays its last value to every new collector, so a new collector after a config change would re-trigger a "NavigateToHome" event and send the user to the wrong screen. SharedFlow with replay = 0 fires once and that's it. The alternative is a Channel<Event> consumed as a Flow, which also gives you single-delivery semantics.

Under the hood

StateFlow is conceptually a SharedFlow with replay = 1 plus conflation and an always-present value — that mandatory replay buffer of 1 is exactly what re-emits the last event to a fresh collector. A plain SharedFlow(replay = 0) keeps no replay cache, so a value emitted while nobody is collecting is simply dropped, and a collector that subscribes later sees only values emitted after it subscribed — fan-out, not replay. The subtle gotcha: MutableSharedFlow.emit() suspends if there are no subscribers and no buffer (the event would otherwise be lost), so events are commonly given extraBufferCapacity = 1 (with tryEmit) to make emission non-suspending. A Channel differs semantically: it's a fan-out queue with at-most-one receiver per element (not broadcast), backed by a buffer with a configurable onBufferOverflow, which is why it naturally yields exactly-once delivery to a single consumer.

Interview Angles

Q: Why ViewModel? "Config-change survival without any manual save/restore plumbing. The ViewModel lives across Activity re-creation, so UI state — the search query, the scroll position, the in-flight network request — persists automatically. You don't have to serialize anything into a Bundle and restore it in onCreate."

Q: What should not be inside ViewModel? "Anything that carries a Context or a View — Activity, Fragment, View, Binding, NavController. Holding those creates a memory leak because the ViewModel outlives the Activity instance. The ViewModel should be pure Kotlin: repositories, use cases, and coroutines only."

Q: How does MVVM help testing? "The ViewModel is pure Kotlin with no framework dependencies, so I can test it with plain JUnit. I inject mock repositories, call the ViewModel methods, and assert on the emitted StateFlow values. No Activity, no Instrumentation, no Robolectric."

Q: ViewModel vs Presenter? "Both separate presentation logic from the View, but there are four key differences. First, the ViewModel survives config changes natively because the framework retains it across Activity re-creation; a Presenter has no such mechanism and you have to do the detach/attach dance manually. Second, the ViewModel exposes observable streams and the View drives itself reactively; a Presenter calls methods on the View interface imperatively. Third, the ViewModel holds no reference to the View at all; a Presenter does, which is where the leak risk comes from. And fourth, the ViewModel is a Jetpack component with built-in lifecycle integration; a Presenter is a plain object you wire up yourself."

Q: How do you expose UI state? "I use a single immutable data class or sealed interface representing the complete screen state, exposed as a StateFlow<UiState>. One-time events — navigation, toasts — go into a separate SharedFlow<Event>. The key thing I avoid is multiple independent StateFlow or LiveData fields that can produce contradictory combinations. If isLoading and error are separate fields, there's nothing stopping a bug from setting both to true at once, which is a state the UI never has a consistent answer for."

MVI / UDF — Intent, Reducer, State, Side Effects

🎤 Say it out loud (~30s): "MVI enforces strict unidirectional data flow: View emits Intents, a reducer maps the current State plus an Intent to a new State, and the View renders that single source of truth. Because every change passes through one pure reducer, state is predictable and time-travel debuggable. The gotcha is side effects — navigation, toasts — can't live in State because State replays, so they go through a separate one-shot effect stream."

Definition

Model-View-Intent and Unidirectional Data Flow are closely related ideas. The key principle is that data always flows in one direction: View → Intent/Action → Reducer → State → View. There is exactly one source of truth — the current State — and the only way to change it is to pass an Intent through the Reducer. That constraint is what makes the system predictable.

User gesture
    │
    ▼
 Intent/Action  (what happened: "LoginClicked(email, pass)")
    │
    ▼
  Reducer       (pure function: (State, Intent) → State)
    │
    ▼
   State        (immutable snapshot of the entire screen)
    │
    ▼
   View         (renders the State; generates new Intents)

Under the hood

UDF maps cleanly onto StateFlow mechanics: the "single source of truth" is one MutableStateFlow<State> whose .value is replaced atomically. MutableStateFlow.update { } runs your reducer lambda inside a compare-and-set loop — it reads the current value, computes the new state via your pure function, and compareAndSets it; if another thread changed the value in between, the CAS fails and the lambda re-runs, which is what makes concurrent dispatches safe without locks. Because the reducer returns a new immutable instance (via copy()), StateFlow then runs equals() against the old value and notifies collectors only on a real change. The "one direction" is enforced socially/structurally (the View only has the read-only flow + a dispatch() entry point), not by the runtime — there's no opcode preventing a sloppy View from mutating, only the read-only StateFlow type.

Kotlin Example: MVI with ViewModel

// 1. Intents — everything the user can do
sealed interface LoginIntent {
    data class LoginClicked(val email: String, val password: String) : LoginIntent
    data object DismissError : LoginIntent
    data object ForgotPasswordClicked : LoginIntent
}

// 2. State — complete, immutable snapshot of the screen
data class LoginState(
    val email: String = "",
    val password: String = "",
    val isLoading: Boolean = false,
    val error: String? = null,
    val isLoggedIn: Boolean = false
)

// 3. Side Effects — one-time outputs that are NOT state
sealed interface LoginSideEffect {
    data object NavigateToHome : LoginSideEffect
    data object NavigateToForgotPassword : LoginSideEffect
}

// 4. ViewModel acts as the store; reduce() is the reducer
class LoginViewModel(
    private val authRepository: AuthRepository
) : ViewModel() {

    private val _state = MutableStateFlow(LoginState())
    val state: StateFlow<LoginState> = _state.asStateFlow()

    private val _sideEffects = MutableSharedFlow<LoginSideEffect>()
    val sideEffects: SharedFlow<LoginSideEffect> = _sideEffects.asSharedFlow()

    fun dispatch(intent: LoginIntent) {
        when (intent) {
            is LoginIntent.LoginClicked -> login(intent.email, intent.password)
            is LoginIntent.DismissError -> reduce { copy(error = null) }
            is LoginIntent.ForgotPasswordClicked -> viewModelScope.launch {
                _sideEffects.emit(LoginSideEffect.NavigateToForgotPassword)
            }
        }
    }

    private fun login(email: String, password: String) {
        viewModelScope.launch {
            reduce { copy(isLoading = true, error = null) }
            authRepository.login(email, password)
                .onSuccess {
                    reduce { copy(isLoading = false, isLoggedIn = true) }
                    _sideEffects.emit(LoginSideEffect.NavigateToHome)
                }
                .onFailure { e ->
                    reduce { copy(isLoading = false, error = e.message) }
                }
        }
    }

    // Convenience: atomically update state
    private fun reduce(block: LoginState.() -> LoginState) {
        _state.update { it.block() }
    }
}

Under the hood

dispatch() compiles into a tableswitch/when over the sealed hierarchy; the Kotlin compiler knows the sealed interface subtypes at compile time, so an exhaustive when needs no else branch and emits an efficient type-dispatch. The reduce { copy(...) } call is where immutability is cheap: data class copy() generates a constructor call that shares references to unchanged fields and only swaps the named ones, so a "new state" is a shallow object whose unchanged List/String fields are the same references — no deep clone, so allocation cost is one small object per transition. _state.update {} wraps the reducer in the CAS loop described above, guaranteeing the read-modify-write is atomic even if login()'s coroutine and a DismissError dispatch interleave on different dispatchers.

What Is a Reducer?

🎤 Say it out loud (~30s): "A reducer is a pure function — current State plus an Intent in, new State out, with no I/O, no mutation, no side effects. That purity is the whole point: it makes every transition deterministic and trivially unit-testable, because you just call reduce(state, intent) and assert on the return value with no coroutines or mocks. The async work stays outside the reducer — the reducer only ever computes the next state."

A reducer is a pure function — (CurrentState, Intent) → NewState. It takes the current state and an intent describing what happened, and returns the new state without mutating the old one, without side effects, and without any I/O. That purity is what makes every state transition predictable and trivially testable.

// Pure reducer (no side effects — async is handled outside)
fun reduce(state: LoginState, intent: LoginIntent): LoginState = when (intent) {
    is LoginIntent.DismissError -> state.copy(error = null)
    is LoginIntent.LoginClicked -> state.copy(isLoading = true, error = null)
    // ... etc
}

Under the hood

"Pure" has a precise bytecode consequence: the function reads only its two parameters and allocates one return value — it touches no fields outside its arguments, performs no invoke on I/O APIs, and has no observable effect besides the returned object. That referential transparency is why a test JVM can call it a million times with no setup: there's no dispatcher, no Context, no mock graph, just stack frames in and an object out. It also means the function is thread-safe by construction (no shared mutable state), which is what lets the update {} CAS loop re-invoke it safely on retry. The deliberate separation — async happens in the coroutine, the reducer only computes — keeps the suspending machinery (the compiler-generated state machine and Continuation) out of the unit under test.

Side Effects

🎤 Say it out loud (~30s): "A side effect is anything that escapes the State→View loop — navigation, a toast, an analytics event, a file write. I can't encode those as State because State is re-emitted to every new collector, so a rotation would replay it and re-navigate. I model them as a separate SharedFlow with replay = 0 that fires once and is consumed once."

A side effect is anything that escapes the State → View cycle — navigation, showing a toast, triggering analytics, writing to a file. Side effects cannot be represented as State because State is re-emitted to every new collector, which means a config change would re-trigger navigation and send the user somewhere they didn't ask to go. The right approach is to model them separately as a SharedFlow<SideEffect> that fires once and is consumed once.

Under the hood

The replay distinction is structural, as covered above: StateFlow carries a mandatory replay = 1 buffer, so a fresh collector after a configuration change immediately receives the latest value — fatal for an effect like NavigateToHome. A SharedFlow(replay = 0) holds no replay cache, so a NavigateToHome emitted to an active collector is delivered to that collector and then forgotten; a collector that re-subscribes after rotation sees nothing. On the consumer side, collecting effects inside LaunchedEffect(Unit) ties the collecting coroutine to the composition's lifecycle — it's launched once when the node enters composition and cancelled when it leaves — so each emitted effect is handled exactly once rather than re-run on every recomposition.

Predictable State and Easier Debugging

🎤 Say it out loud (~30s): "Because every change funnels through one reduce(), I get three things cheaply: a full audit trail by logging each (intent, before, after) triple; deterministic tests that feed a sequence of intents and assert the sequence of states; and time-travel debugging, since replaying the recorded intents against the initial state reproduces any bug exactly. That determinism is the real reason teams pay MVI's boilerplate tax."

Because every state change passes through a single reduce(), three things become straightforward that are hard in other patterns. First, you can log every (intent, state_before, state_after) triple and have a complete audit trail of how the UI got to where it is. Second, you can write a test that feeds a sequence of intents and asserts the sequence of states — it's fully deterministic because the reducer is a pure function. And third, you can time-travel debug: record every intent that fired, replay them against the initial state, and reproduce any bug exactly.

Under the hood

Time-travel replay is sound only because the reducer is pure and the state is immutable: replaying intent list [i0, i1, …, in] from a captured initialState is a left-fold — intents.fold(initialState) { acc, i -> reduce(acc, i) } — and a pure fold over the same inputs is guaranteed to produce the same outputs, because nothing in the reducer reads wall-clock time, random values, or external mutable state. Immutability is what makes the recorded state_before snapshots trustworthy: since copy() never mutates the prior instance, every logged state is a frozen value that can't be retroactively changed by a later transition. The only thing that can't be replayed deterministically is the side-effect channel (network results, timestamps) — which is precisely why MVI quarantines those outside the reducer.

MVI Boilerplate Warning

🎤 Say it out loud (~30s): "MVI's cost is real ceremony — every action is a sealed type, every change is a copy(), every effect is another sealed type. For a one-toggle screen that's pure overhead, so I don't reach for it by default. I reserve it for screens with many interdependent state fields or where state consistency is critical enough to justify the structure."

MVI adds real ceremony: every user action becomes a sealed class, every state change is a copy(), every side effect is another sealed class. For a simple screen — one toggle, one button — that's overkill. Reserve MVI for screens with many concurrent state transitions, or where state consistency is critical enough to justify the extra structure.

Under the hood

The ceremony has a measurable footprint. Each sealed interface subtype is its own .class file; a data object compiles to a singleton (a INSTANCE static field with private constructor), while a data class Intent generates a constructor plus synthetic equals/hashCode/toString/componentN/copy methods — so a screen with 15 intents and 8 effects is ~23 extra classes and their generated methods, which counts against the 64K-method DEX limit on large apps (mitigated by R8/multidex). The copy() per transition allocates a short-lived object that dies young, so it lands in the generational GC's young space and is collected cheaply, but on a high-frequency stream (e.g., per-frame scroll state) that allocation churn is the thing to watch. None of this matters for a toggle — which is the point of the warning: the structure pays off only when the state space is genuinely complex.

Second, when I need strict auditability of state transitions, like in a finance or health context. And third, when I want time-travel debugging. 7.2 Clean Architecture

Separation of Concerns and the Dependency Rule

🎤 Say it out loud (~30s): "Separation of concerns means each layer knows only what it must — the UI never touches the database directly. The Dependency Rule says source-code dependencies point inward only: outer layers depend on inner ones, never the reverse. The mechanism interviewers want is dependency inversion — the Domain defines the repository interface and the Data layer implements it, so the high-level policy never depends on the network or DB details."

Separation of concerns means each layer knows only what it needs to know. The UI does not reach into the database. The database does not know ViewModels exist.

The Dependency Rule (Robert C. Martin): source code dependencies must point inward only. Inner circles know nothing about outer circles. Outer circles depend on inner circles — never the reverse.

      ┌─────────────────────────────────┐
      │        Presentation Layer       │  ← depends on Domain
      │   (ViewModel, Composable, UI)   │
      └───────────────┬─────────────────┘
                      │
      ┌───────────────▼─────────────────┐
      │          Domain Layer           │  ← depends on nothing
      │  (Use Cases, Entities, Repo IF) │
      └───────────────┬─────────────────┘
                      │
      ┌───────────────▼─────────────────┐
      │           Data Layer            │  ← depends on Domain (implements its interfaces)
      │ (Repository impl, API, Room DB) │
      └─────────────────────────────────┘

The Data layer implements interfaces defined in the Domain layer — that's dependency inversion in action. High-level policy, the Domain, does not depend on low-level detail like the network or the database; both the Domain and the Data layer depend on the abstractions that sit between them.

Under the hood

The Dependency Rule is enforceable at the module level, not just by convention. If Domain, Data, and Presentation are separate Gradle modules and Domain declares no dependency on Data in its build.gradle, then the compiler literally cannot resolve a Data type from Domain code — the symbol isn't on the compilation classpath, so it's a compile error, not a code-review nit. At runtime, dependency inversion works through the same invokeinterface dispatch as MVP: the Domain's UseCase holds a field typed as the Repository interface it owns, and DI (Hilt/Dagger) binds the concrete RepositoryImpl from the Data module at the composition root. So the call repository.getUser() emits an invokeinterface against the Domain-owned abstraction and dispatches at runtime to the Data-layer implementation — the compiled Domain .class files contain zero references to Room, Retrofit, or any Data class, which is the literal meaning of "dependencies point inward."

compile graph:   Presentation ──▶ Domain ◀── Data        (Domain has no outgoing edges)
runtime binding:  UseCase → Repository(interface)  ⟵bound by DI⟶  RepositoryImpl(Room/Retrofit)

Layers: Presentation, Domain, Data

🎤 Say it out loud (~30–45s): "I think of the app as three layers: presentation renders UI and holds lifecycle-safe state, domain holds framework-free business rules, and data implements the I/O. The key discipline is the dependency direction — presentation depends on domain, data depends on domain, but domain depends on nothing Android. The nuance an interviewer probes is that the domain layer is optional; Google's own guidance says so, and I only add it when business logic is complex or reused, otherwise the ViewModel can talk to the repository directly."

Presentation Layer

🎤 Say it out loud (~30s): "The presentation layer is just UI plus state — a ViewModel orchestrates use cases and maps domain models into UI models, and Composables or Fragments render that state and dispatch events. The gotcha I call out is that UI models are deliberately not domain entities: I pre-format strings and shape data for display so the UI stays dumb and survives configuration changes through the ViewModel."

Responsibility: render UI, handle user events, and manage lifecycle-safe state.

  • ViewModel — orchestrates use case calls, maps domain models to UI models.
  • Composables and Fragments — render state, dispatch events.
  • UI models — different from domain entities; optimised for display, with things like pre-formatted strings already in place.
  • Navigation logic.

Under the hood

A ViewModel survives configuration changes because ViewModelStore outlives the Activity instance. When an Activity is recreated, the framework retains the ViewModelStore via NonConfigurationInstances (returned from onRetainNonConfigurationInstance() / the ComponentActivity retained-instance machinery), so the same ViewModel object is handed to the new Activity. ViewModelProvider keys instances by class name in a HashMap inside the store; onCleared() only fires when the store itself is cleared (real finish, not rotation).

Domain Layer

🎤 Say it out loud (~30s): "The domain layer is pure Kotlin — entities, use cases, and repository interfaces — with zero Android imports. The important inversion is that the contract lives here and the data layer implements it, so the domain dictates terms instead of depending on Retrofit or Room. The thing interviewers like to hear is why it's pure: it makes business rules unit-testable on the JVM with no instrumentation, and it lets you swap the whole data stack without touching a single business rule."

Responsibility: encapsulate business rules independently of any framework or infrastructure detail.

  • Entities — core business models such as Doctor or Appointment. No Android imports — pure Kotlin.
  • Use Cases / Interactors — single-responsibility operations like GetAvailableSlotsUseCase or BookAppointmentUseCase. Each use case encapsulates exactly one business operation.
  • Repository interfaces — defined here, implemented in the Data layer. The domain dictates the contract; the data layer fulfils it.
// Domain entity — pure Kotlin
data class Doctor(
    val id: String,
    val name: String,
    val specialty: String,
    val rating: Float
)

// Repository interface — defined in Domain, implemented in Data
interface DoctorRepository {
    suspend fun getDoctors(specialty: String): Result<List<Doctor>>
    suspend fun getDoctorById(id: String): Result<Doctor>
}

// Use case — orchestrates business logic
class GetDoctorsBySpecialtyUseCase(
    private val doctorRepository: DoctorRepository
) {
    suspend operator fun invoke(specialty: String): Result<List<Doctor>> {
        require(specialty.isNotBlank()) { "Specialty must not be blank" }
        return doctorRepository.getDoctors(specialty)
            .map { doctors -> doctors.sortedByDescending { it.rating } }
    }
}

Under the hood

"Pure Kotlin, no Android imports" is enforceable at the build-graph level, not just by convention. If the domain lives in a separate Gradle module that applies kotlin("jvm") (a plain JVM library) instead of com.android.library, then android.* classes aren't even on its compile classpath — referencing Context or Bundle won't compile. The suspend keyword on the interface methods compiles each function to take an extra hidden Continuation parameter (CPS transform) and return Any?, so the contract is async-ready without any RxJava/coroutine type leaking into the signature shape.

:domain  -> apply kotlin("jvm")        // android.jar NOT on classpath
:data    -> apply com.android.library  // depends on :domain, has Retrofit/Room
:app     -> depends on :domain + :data // DI wires impl to interface

Data Layer

🎤 Say it out loud (~30s): "The data layer implements the repository interfaces and owns every I/O concern — Retrofit, Room, DataStore — plus the DTOs and DB entities that are shaped for the wire and the schema. Its job is to coordinate sources and map them to domain models. The detail I always mention is that this is where caching and fallback policy lives: the repository decides network-first versus cache-first and hides that from everyone above it."

Responsibility: implement the repository contracts and manage all I/O concerns — networking, database, file system.

  • Repository implementations — implement the domain's interfaces.
  • Remote data sources — Retrofit services, GraphQL clients.
  • Local data sources — Room DAOs, SharedPreferences, DataStore.
  • DTOs — data transfer objects shaped for the network API (often auto-generated from Swagger/OpenAPI).
  • Entities — database entities shaped for Room schema.
  • Mappers — convert between DTOs/entities and domain models.
// Data layer: implements the domain interface
class DoctorRepositoryImpl(
    private val remoteDataSource: DoctorRemoteDataSource,
    private val localDataSource: DoctorLocalDataSource,
    private val mapper: DoctorMapper
) : DoctorRepository {

    override suspend fun getDoctors(specialty: String): Result<List<Doctor>> {
        return try {
            val dtos = remoteDataSource.fetchDoctors(specialty)
            val doctors = dtos.map { mapper.toDomain(it) }
            localDataSource.saveDoctors(doctors.map { mapper.toEntity(it) })
            Result.success(doctors)
        } catch (e: Exception) {
            // Fallback to cache
            val cached = localDataSource.getDoctors(specialty)
            if (cached.isNotEmpty()) Result.success(cached.map { mapper.toDomain(it) })
            else Result.failure(e)
        }
    }
}

Under the hood

Retrofit doesn't write the network code you'd expect — at runtime it builds a java.lang.reflect.Proxy (or invokes a generated ServiceMethod) for the interface, parses each method's annotations and @SerializedName once, and caches the resulting ServiceMethod in a ConcurrentHashMap. Room's @Dao is the opposite: its kapt/KSP annotation processor generates a concrete XxxDao_Impl at compile time that builds SupportSQLiteStatements and binds parameters, so the SQL is validated against the schema during the build, not at runtime. The DTO-vs-entity split exists precisely because these two layers have different shape constraints — the JSON parser keys off serialization annotations and the SQLite codegen keys off @ColumnInfo — and the mapper is what keeps both sets of annotations out of the domain model.

Use Cases / Interactors

🎤 Say it out loud (~30–45s): "A use case is one business operation — one class with a single public entry point, idiomatically operator fun invoke, so the call site reads like calling a function. I reach for them to keep ViewModels thin, to reuse a single operation across screens, and to get pure-JVM testability. The honest nuance is they're a tool, not a mandate: a use case that just delegates straight to the repository is pure indirection, so I skip it for trivial passthroughs."

A use case is a single business operation — one class, one public method, conventionally operator fun invoke(). That's not a hard rule from Clean Architecture; it's an idiomatic Kotlin convention that makes use cases feel like callable functions, which keeps the call sites clean.

Why Use Cases?

🎤 Say it out loud (~30s): "There are four payoffs: they stop fat ViewModels from absorbing business logic, they let me reuse the same operation from a search and a profile ViewModel, they're trivially testable with a mock repository and no Android runtime, and they enforce single responsibility — one operation per class. The one I'd flag is reusability is the strongest argument; if a piece of logic is only ever used in one place, the testability win alone may not justify the class."

There are four reasons to introduce use cases. First, they prevent fat ViewModels — without them, ViewModels orchestrate business logic directly, they grow, and they become hard to test and impossible to reuse. Second, reusability: GetDoctorsBySpecialtyUseCase can be called from a search screen ViewModel and a profile screen ViewModel without duplicating the logic in both. Third, testability: a use case takes plain Kotlin inputs, returns plain Kotlin outputs, and can be tested with a mock repository — no Android runtime needed. And fourth, single responsibility: one use case equals one business operation, which makes it easy to reason about and easy to change in isolation.

Under the hood

operator fun invoke isn't magic — the Kotlin compiler maps the expression useCase("cardiology") to a normal method call useCase.invoke("cardiology"), where invoke is just a method with a special name the resolver recognizes. Because it's suspend, the compiler applies the CPS transform: invoke actually compiles to take a hidden Continuation and returns Any?, and the function body becomes a state machine class (an invokeSuspend with a label int) so each suspension point can resume without blocking a thread. That's why a "thin" use case wrapping one repository call still allocates that state-machine object on each invocation — a real (if tiny) cost behind the "pure delegation is free" assumption.

When Are Use Cases Not Worth It?

🎤 Say it out loud (~30s): "For a plain CRUD read with no rules — like fetching a static settings list — a use case is just a passthrough that adds a layer without earning it, so I let the ViewModel call the repository directly. Worth knowing on this team: we call them 'Interactors,' which is just our synonym for use case — same concept, different label."

For a simple CRUD operation with no business logic — say, "get a list of settings items," which is just a passthrough to the repository — the use case adds a layer of indirection without pulling its weight. The Zocdoc Android codebase uses "Interactor" as a synonym for use case; both terms describe the same concept.

Testing a Use Case

🎤 Say it out loud (~30s): "I test a use case as pure Kotlin: mock the repository with MockK, run inside runTest, and assert on the transformed output — here, that doctors come back sorted by rating. The detail I'd add is runTest gives me a virtual clock and a test dispatcher, so any delays inside the suspend function are skipped and the test is deterministic, not wall-clock-bound."
class GetDoctorsBySpecialtyUseCaseTest {
    private val repository: DoctorRepository = mockk()
    private val useCase = GetDoctorsBySpecialtyUseCase(repository)

    @Test
    fun `returns doctors sorted by rating descending`() = runTest {
        val unsorted = listOf(
            Doctor("1", "Dr. A", "cardiology", rating = 3.5f),
            Doctor("2", "Dr. B", "cardiology", rating = 4.9f),

}

Under the hood

runTest installs a TestCoroutineScheduler backed by a StandardTestDispatcher and runs the body on a virtual clock: calls to delay() don't sleep, they enqueue a resumption at a virtual time and the scheduler fast-forwards, so a "1 second" delay completes instantly. MockK's coEvery { ... } works by generating a proxy/subclass of the interface (via its bytecode-generation backend) whose getDoctors records the stubbed answer; coEvery differs from every only in that it runs the matcher block inside a coroutine so it can match suspend calls. runTest also fails the test if any child coroutine is still unfinished when the body returns, which is what catches leaked or never-completing coroutines.

Mappers

🎤 Say it out loud (~30s): "Mappers translate between each layer's representation — DTO to domain, domain to DB entity, and back. The payoff is that my domain model stays clean of @SerializedName and @ColumnInfo, the translation is unit-testable on its own, and API field names like providerId never leak upward. The trade-off I acknowledge is the boilerplate, which is why I keep mappers as plain functions and reserve them for real shape mismatches, not identical 1:1 copies."

Mappers translate between the data representations of each layer. Having explicit mapper classes does three things: it keeps domain models free of serialization annotations like @SerializedName or @ColumnInfo; it makes the mapping logic testable in isolation; and it prevents API field names from leaking into the domain.

class DoctorMapper {
    fun toDomain(dto: DoctorDto): Doctor = Doctor(
        id = dto.providerId,          // rename from API field name
        name = "${dto.firstName} ${dto.lastName}",
        specialty = dto.primarySpecialty,
        rating = dto.averageRating?.toFloat() ?: 0f
    )

    fun toEntity(domain: Doctor): DoctorEntity = DoctorEntity(
        id = domain.id,
        name = domain.name,
        specialty = domain.specialty,
        rating = domain.rating,
        cachedAt = System.currentTimeMillis()
    )

    fun toDomain(entity: DoctorEntity): Doctor = Doctor(
        id = entity.id,
        name = entity.name,
        specialty = entity.specialty,
        rating = entity.rating
    )
}

Under the hood

The two toDomain overloads compile to distinct JVM methods — the bytecode signatures differ by parameter type (toDomain(DoctorDto) vs toDomain(DoctorEntity)), and Kotlin resolves the call statically at compile time, so there's no runtime dispatch cost to the overloading. The string-template "${dto.firstName} ${dto.lastName}" doesn't do repeated + concatenation; the compiler lowers it to a StringBuilder.append(...) chain (or an invokedynamic makeConcat call on newer toolchains). The reason annotations "don't leak" is structural: @SerializedName/@ColumnInfo have RetentionPolicy.RUNTIME and live on the DTO/entity fields where Gson/Moshi and Room's codegen read them via reflection or generated adapters — the mapper produces a Doctor whose fields carry none of that metadata, so reflection-based serializers have nothing to act on.

Dependency Inversion

🎤 Say it out loud (~30–45s): "Dependency inversion is the spine of this whole architecture: the domain owns the abstraction — the DoctorRepository interface — and the data layer depends on that abstraction by implementing it, so the high-level policy doesn't depend on low-level detail. At runtime Hilt or Dagger binds the concrete impl to the interface. The practical wins are that the domain has zero knowledge of Retrofit or Room, swapping the network library only touches data, and tests inject a fake repository with no networking at all. The nuance is the 'inversion' is about which module owns the interface — putting it in domain, not data, is what flips the arrow."

The Domain layer defines interfaces like DoctorRepository. The Data layer provides concrete implementations like DoctorRepositoryImpl. At runtime, the DI framework — Hilt or Dagger — wires the implementation to the interface. The practical consequences are that the Domain layer has zero knowledge of Retrofit, Room, or any data technology; swapping the network library requires changing only the Data layer; and tests can inject a fake repository without touching any networking code.

Under the hood

Dagger/Hilt resolve bindings entirely at compile time, not via runtime reflection. The annotation processor builds a directed graph of @Provides/@Binds declarations and @Inject constructors, validates it (missing or duplicate bindings are build errors), then generates Factory classes — e.g. DoctorRepositoryImpl_Factory with a static create(...) and get() — plus a DaggerXxxComponent that wires them together. A @Binds of DoctorRepository to DoctorRepositoryImpl generates no body at all; it just makes the component return the impl's factory where the interface is requested. So the JVM-level dependency arrow from the call site points at the interface type, while the generated component is the only place that knows the concrete class — which is exactly the inversion, realized in generated code.

:data     class DoctorRepositoryImpl       --implements-->  DoctorRepository
:app      @Binds bind(impl): DoctorRepository
          -> DaggerComponent (generated) returns impl factory for the interface

Is the Domain Layer Always Required?

🎤 Say it out loud (~30–45s): "No — and I'd point out Google's own architecture guidance explicitly marks the domain layer as optional. I add it when business logic is genuinely complex, like eligibility or pricing, when the same operation is reused across ViewModels, or when team size demands clear ownership boundaries. I skip it for thin CRUD screens, prototypes, or any use case that would be a one-line delegate. The trap I name out loud is over-engineering: a pure passthrough use case has identical test coverage to the repository call it wraps, so it's indirection with no payoff."

No — and Google's official Android documentation explicitly calls the domain layer optional. It's worth adding when the business logic is complex enough to warrant isolation, like eligibility checks or pricing calculations; when the same operation is reused across multiple ViewModels; or when the team is large enough that you need clear ownership boundaries.

Skip it when the screen is a thin CRUD form and the ViewModel calls the repository directly, when you're building a small app or a prototype, or when the use case would be a one-liner that just delegates straight to the repository.

Over-engineering warning: adding use cases that are pure delegation — class GetDoctorsUseCase { suspend operator fun invoke() = repository.getDoctors() } — creates indirection without any value. The test coverage of that use case is identical to the test coverage of the repository call in the ViewModel. Add a layer only when it pulls its weight.

Under the hood

The cost of an unnecessary domain layer is measurable beyond style. Each extra module participates in the build graph: Gradle must configure it, run kapt/KSP and kotlinCompile tasks for it, and Dagger must generate a factory and a binding for every use case — so a flood of pure-delegation use cases inflates annotation-processing time and the size of the generated DaggerComponent. At runtime each delegating invoke still allocates a coroutine state-machine object and adds a stack frame on every call. None of that buys additional behavior to test, which is why the over-engineering warning holds: the bytecode of useCase() -> repository.getDoctors() is strictly more work than calling the repository directly, with no new branch to cover.

Avoiding Over-Engineering

🎤 Say it out loud (~30–45s): "I start with two layers — a ViewModel and a Repository — and only introduce a Domain layer with use cases once business logic genuinely earns it. My heuristic is the rule of three: if the same logic shows up in three places, I extract it; if it's used once, it stays in the ViewModel. The nuance interviewers probe is that abstraction isn't free — every extra class is more indirection a new engineer has to trace, so I treat premature layering as a real cost, not a virtue."
  • Start with two layers: Presentation — the ViewModel — plus Data — the Repository. Add the Domain layer only when business logic complexity genuinely justifies it.
  • Use the "rule of three": if the same logic appears in three places, extract a use case. If it only appears once, leave it in the ViewModel.
  • Complexity is a cost. Every class is one more file to navigate and one more abstraction to explain to a new engineer.

Under the hood

Each abstraction layer is not free at runtime either. A use case that just forwards to a repository compiles to an extra class with its own constructor, an extra megamorphic-prone virtual call, and — if DI-provided — an extra entry in the Dagger/Hilt object graph that must be instantiated. The JIT can often inline trivial single-call forwarders, but the bytecode, the DEX method-count contribution (relevant against the 64K method reference limit per DEX file), and the build-time annotation-processing cost are all real.

7.3 Repository Pattern

Abstraction and Single Source of Truth

🎤 Say it out loud (~30–45s): "A repository hides every data source behind a domain-friendly API — the caller asks 'give me doctors by specialty' and never knows if that's network, cache, or DB. The single-source-of-truth idea is that one owner — usually the Room database — is canonical: I write all remote data into the DB and the UI reads only from the DB. The payoff is consistent reads with no network-vs-DB races, offline-by-default, and the network demoted to a sync mechanism. The gotcha is you must expose a reactive read — a Flow off the DAO — so writes automatically push fresh data to the UI."

A repository is a class that abstracts all data sources behind a domain-friendly API. The ViewModel or use case just asks "give me doctors by specialty" — it never knows or cares whether that comes from the network, a cache, a database, or some combination of all three.

Single source of truth means one canonical owner of data. For most apps, that's the local database. The repository writes all remote data into the DB, and the UI reads exclusively from the DB. The three consequences of that are: the UI always sees consistent data with no race conditions between network and DB reads; offline reads just work because the DB always has something; and the network becomes a sync mechanism rather than a direct read path.

interface DoctorRepository {
    fun getDoctors(specialty: String): Flow<List<Doctor>>  // returns Flow, not suspend
    suspend fun refreshDoctors(specialty: String)           // triggers network sync
}

class DoctorRepositoryImpl(
    private val remoteDataSource: DoctorRemoteDataSource,
    private val localDataSource: DoctorLocalDataSource,
    private val mapper: DoctorMapper
) : DoctorRepository {

    // Room emits a new list every time the DB changes
    override fun getDoctors(specialty: String): Flow<List<Doctor>> =
        localDataSource.getDoctorsFlow(specialty)
            .map { entities -> entities.map(mapper::toDomain) }

    // Called by ViewModel.init or pull-to-refresh
    override suspend fun refreshDoctors(specialty: String) {
        val dtos = remoteDataSource.fetchDoctors(specialty)
        localDataSource.saveDoctors(dtos.map(mapper::toEntity))
        // DB write triggers Flow emission above — UI updates automatically
    }
}

Under the hood

Room's Flow-returning DAO query doesn't poll. At compile time, the Room annotation processor generates an implementation that registers an InvalidationTracker.Observer against the tables the query touches. Room installs SQLite triggers on those tables that write into an internal room_table_modification_log; on any INSERT/UPDATE/DELETE the tracker is notified, it diffs the table-version set, and re-runs the query on the configured Executor, emitting a fresh list into the Flow. That's why a write inside refreshDoctors automatically re-emits to collectors — the invalidation is table-scoped, not row-scoped.

saveDoctors() --INSERT--> SQLite trigger --> room_table_modification_log
   --> InvalidationTracker --> re-run query --> Flow.emit(newList) --> UI

Repository vs Data Source

🎤 Say it out loud (~30–45s): "A data source owns exactly one I/O concern — the remote source only knows networking, the local one only knows Room, and neither knows the other exists. The repository is the coordinator that makes policy: when to fetch, when to cache, how to map, what to return. So data sources do the raw I/O and the repository makes the decisions. The reason I keep them separate is testability — I can fake either data source independently, and the repository's policy logic gets unit-tested without touching a real network or DB."

Data sources are single-responsibility: DoctorRemoteDataSource knows how to make network calls and that's all — it knows nothing about the local DB. DoctorLocalDataSource wraps Room and knows nothing about the network. The repository is the coordinator that decides which to call and when.

Under the hood

The boundary is enforced by the type system and DI graph, not by convention alone. The remote data source typically wraps a Retrofit interface — at runtime Retrofit builds a java.lang.reflect.Proxy whose InvocationHandler reads the method annotations (@GET, @Query), builds an OkHttp Call, and adapts the return type via the registered CallAdapter (e.g., the suspend adapter that bridges Call to a coroutine Continuation). The local data source wraps Room's generated DAO _Impl. Because each is injected behind an interface, the repository holds only the interface reference, so the linker never couples the two concerns — swapping in a fake is just a different binding in the Dagger graph.

Caching and Refresh Strategies

Cache-First

🎤 Say it out loud (~30–45s): "Cache-first emits whatever I already have immediately, then fetches fresh data in the background and emits again, so the user sees something instantly and an update lands a moment later. The key gotcha is error handling: a network failure should only surface to the UI if I have nothing cached — otherwise I swallow it and let the stale-but-present data stand. In production I'd usually back this with the DB-as-source-of-truth so the second emission comes from a DB write rather than emitting the network result directly."

Return cached data immediately, refresh in the background, and let the UI observe the DB via Flow.

fun getDoctors(specialty: String): Flow<List<Doctor>> = flow {
    // 1. Emit cached data immediately
    val cached = localDataSource.getDoctors(specialty)
    if (cached.isNotEmpty()) emit(cached.map(mapper::toDomain))

    // 2. Fetch fresh data
    try {
        val fresh = remoteDataSource.fetchDoctors(specialty)
        localDataSource.saveDoctors(fresh.map(mapper::toEntity))
        emit(fresh.map(mapper::toDomain))
    } catch (e: Exception) {
        if (cached.isEmpty()) throw e  // rethrow only if no cached data
    }
}

Under the hood

flow { ... } builds a cold SafeFlow; nothing runs until a terminal collect. When collected, the builder's lambda runs as a suspending function whose emit calls invoke the collector's emitValue on the collector's coroutine context — that's the basis of Flow's sequential, back-pressure-free contract. Each suspension point (fetchDoctors, saveDoctors) is compiled by the Kotlin compiler into a state-machine Continuation: the function is split at suspend boundaries into states, locals are hoisted into the continuation object, and resumption re-enters via invokeSuspend with the prior label. If the collector's scope is cancelled mid-fetch, a CancellationException propagates at the next suspension point.

Network-First (with fallback)

🎤 Say it out loud (~30–45s): "Network-first hits the network first and only falls back to cache when the call fails — I use it when freshness matters more than instant render, like a detail screen. The subtle part is being precise about which exceptions trigger fallback: I catch IOException for genuine connectivity failures, not a blanket Exception, because an HTTP 4xx or a parse error is a real bug I don't want masked by silently serving stale data."

Try the network first; if it fails, fall back to the cache.

suspend fun getDoctor(id: String): Doctor {
    return try {
        val dto = remoteDataSource.fetchDoctor(id)
        val entity = mapper.toEntity(mapper.toDomain(dto))
        localDataSource.saveDoctor(entity)
        mapper.toDomain(dto)
    } catch (e: IOException) {
        localDataSource.getDoctor(id)
            ?.let(mapper::toDomain)
            ?: throw e
    }
}

Under the hood

IOException here is the seam OkHttp uses to signal transport-level failure — socket timeouts, DNS failures, and connection resets all surface as IOException (or subclasses like SocketTimeoutException), whereas a completed HTTP response with a non-2xx code does not throw at the OkHttp layer; Retrofit's converter or your code throws HttpException for that. So catching IOException specifically falls back only on "couldn't reach the server," and lets server-rejection errors propagate. The Kotlin try/catch around a suspend body compiles into the continuation state machine with the catch installed as an exception handler spanning the suspended states, so a failure resumed via resumeWith(Result.failure) lands in the catch correctly.

TTL-Based Refresh

🎤 Say it out loud (~30–45s): "TTL-based refresh stamps each cache write with a timestamp and only re-fetches once the data is older than my time-to-live window — it's a cheap way to bound staleness without refetching on every read. The gotcha is the clock: System.currentTimeMillis() is wall-clock time that can jump backward via NTP or user changes, so for strict elapsed-time decisions I'd lean toward a monotonic source like elapsedRealtime, and I'd make sure the timestamp is persisted alongside the data, not held in memory."

Cache results with a timestamp and re-fetch only when the cache is stale.

suspend fun getDoctors(specialty: String): List<Doctor> {
    val cacheAge = localDataSource.getCacheAge(specialty)
    val isStale = cacheAge == null || System.currentTimeMillis() - cacheAge > CACHE_TTL_MS
    if (isStale) {
        val dtos = remoteDataSource.fetchDoctors(specialty)
        localDataSource.saveDoctors(dtos.map(mapper::toEntity), timestamp = System.currentTimeMillis())
    }
    return localDataSource.getDoctors(specialty).map(mapper::toDomain)
}

Under the hood

System.currentTimeMillis() reads the wall clock (CLOCK_REALTIME), which is settable and can step in either direction; SystemClock.elapsedRealtime() reads a monotonic counter (CLOCK_BOOTTIME) that includes deep sleep and never goes backward — that's why elapsed-time logic should prefer it. Persisting the timestamp matters because the cache and its TTL marker must be written atomically: in Room you'd do this in a single @Transaction, which wraps the SQLite statements in BEGIN/COMMIT so a crash between the data write and the timestamp write can't leave the cache looking fresh-but-empty or stale-but-populated inconsistently.

Model Mapping: DTO → Entity → Domain

🎤 Say it out loud (~30–45s): "I keep three distinct model types: a DTO that mirrors the API JSON, an Entity that mirrors the Room schema, and a pure-Kotlin domain model the rest of the app uses. Explicit mappers convert between them so a network field rename or a column change stays contained in one layer instead of rippling through the codebase. The pushback I get is 'isn't this boilerplate?' — and my answer is that the coupling you avoid is worth it; the domain model should never carry a @SerializedName or a @ColumnInfo, because the moment it does, your business logic is hostage to your wire format."

There are three distinct model types, each serving a distinct purpose:

Under the hood

These annotations drive code generation/reflection at different layers, which is exactly why mixing them couples your model to two masters. Moshi's codegen (@JsonClass(generateAdapter = true)) produces a JsonAdapter at compile time via KSP/kapt that reads @Json/@SerializedName-style name mappings to map JSON keys to constructor parameters; Room's processor reads @Entity/@ColumnInfo to emit CREATE TABLE SQL and Cursor-binding code in the DAO _Impl. A combined class would force one POJO's field names and nullability to satisfy both the wire contract and the DB schema simultaneously. Mappers are usually trivial pure functions, so the JIT can inline them and escape-analysis can often stack-allocate the short-lived intermediates, making the runtime cost negligible.

Offline-First Architecture

🎤 Say it out loud (~30–45s): "Offline-first means the app is fully usable with no connectivity and reconciles when it comes back. The backbone is Room as the canonical store with a Flow off the DAO so the UI reacts to DB changes, WorkManager for deferred background sync, optimistic local writes that roll back on failure, and an explicit conflict-resolution policy — last-write-wins, server-wins, or field-level merge. The hardest part interviewers dig into is conflict resolution: you have to decide deliberately, because 'just let the server win' silently discards a user's offline edits."

Offline-first means the app functions fully without connectivity and syncs when connectivity returns. There are five key components. First, the local DB as the canonical store — all reads come from Room; the network only populates or updates the DB. Second, observing the DB with Flow — localDataSource.getDoctorsFlow() emits whenever data changes, so the UI reacts to DB changes rather than to network responses directly. Third, WorkManager for background sync — it schedules periodic refreshes even when the app is in the background. Fourth, optimistic updates — write user actions to the DB immediately, show the result, sync to the server in the background, and roll back on failure. And fifth, conflict resolution — define a merge strategy such as last-write-wins, server-wins, or field-level merge for when offline writes collide with server state.

// WorkManager sync task — called by OS even when app is backgrounded
class SyncDoctorsWorker(
    ctx: Context,
    params: WorkerParameters,
    private val repository: DoctorRepository
) : CoroutineWorker(ctx, params) {

    override suspend fun doWork(): Result {
        return try {
            repository.refreshDoctors(inputData.getString("specialty") ?: "")
            Result.success()
        } catch (e: Exception) {
            if (runAttemptCount < 3) Result.retry() else Result.failure()
        }
    }
}

Under the hood

WorkManager doesn't keep your process alive or run a thread of its own — it persists each enqueued request as a row in its internal Room database (androidx.work.* tables) and delegates actual execution to a scheduler chosen at runtime: JobScheduler (the JobService/JobInfo API) on API 23+, or AlarmManager + a broadcast receiver as the fallback. Because requests are persisted, they survive process death and reboot (a BOOT_COMPLETED receiver re-registers pending jobs). CoroutineWorker.doWork() runs on Dispatchers.Default inside a coroutine bound to the worker's lifecycle; returning Result.retry() increments the persisted runAttemptCount and reschedules per the configured BackoffPolicy (default exponential, 30s minimum), and constraints like network availability are evaluated by the underlying scheduler before doWork is ever invoked.

7.4 Dependency Injection

Constructor vs Field Injection

🎤 Say it out loud (~30–45s): "I default to constructor injection because it makes every dependency explicit, lets me hold them as vals, and means I can't construct the object in an invalid state. Field injection is the exception, not a preference — I only reach for it on framework-instantiated classes like Activities and Fragments, where the OS calls the constructor so Hilt has to inject fields after the object already exists. The gotcha there is lateinit var: touch it before injection happens and you get an UninitializedPropertyAccessException."

Constructor Injection (Preferred)

🎤 Say it out loud (~30–45s): "Constructor injection just means the dependencies come in as constructor parameters, so the compiler enforces that you can't forget one. I get immutable val references that are safe to share across threads, and testing is trivial — I just pass mocks or fakes straight in, no framework needed. With Hilt I annotate the constructor with @Inject and the generated factory wires it up."

Dependencies are passed through the constructor — this is the purest form of DI:

class LoginViewModel(
    private val authRepository: AuthRepository,    // injected via constructor
    private val analyticsLogger: AnalyticsLogger
) : ViewModel()

Advantages:

  • Dependencies are explicit and visible at the call site.
  • The class cannot be instantiated without providing all dependencies — it's impossible to forget one.
  • Easy to swap in tests: LoginViewModel(mockk(), mockk()).
  • Immutable references with val — thread-safe by construction.
  • Works naturally with Hilt's @HiltViewModel.

Under the hood

When you annotate a constructor with @Inject, Dagger/Hilt's annotation processor (running at compile time via KSP or the legacy kapt) generates a Factory class that implements Provider<T>. That factory's get() method calls the constructor directly, passing in each parameter by invoking its provider. There's no reflection at runtime — it's all plain generated Java/Kotlin calling new LoginViewModel(...). These factories are linked together into the component's directed acyclic graph, so resolving a dependency is just a chain of get() calls.

LoginViewModel_Factory.get()
  └─ new LoginViewModel(
         authRepositoryProvider.get(),   // resolves AuthRepository binding
         analyticsLoggerProvider.get())  // resolves AnalyticsLogger binding

Field Injection

🎤 Say it out loud (~30–45s): "Field injection is when the DI framework sets @Inject lateinit var fields after the object is built, instead of through the constructor. I only use it where I have no control over construction — Android system components the OS instantiates for me. The trade-offs are real: the dependencies are invisible in the signature, the fields are mutable lateinit, and you can hit an UninitializedPropertyAccessException if you read one before Hilt's inject() call runs in onCreate."

Dependencies are annotated with @Inject on fields; the DI framework populates them after construction.

@AndroidEntryPoint
class LoginActivity : AppCompatActivity() {
    @Inject lateinit var analyticsLogger: AnalyticsLogger  // field injection
}

When field injection is necessary: Android framework classes — Activity, Fragment, Service, BroadcastReceiver — are instantiated by the OS, so you cannot control their constructors. Hilt therefore uses field injection for @AndroidEntryPoint classes. For everything else, prefer constructor injection.

Disadvantages of field injection:

  • lateinit var — accessing the field before injection throws UninitializedPropertyAccessException.
  • Dependencies are not visible in the constructor signature, which makes the class harder to understand at a glance.
  • Harder to use in unit tests because you have to manually set the field rather than just passing arguments.

Under the hood

Field injection requires a MembersInjector<T> instead of a Factory<T>. The processor generates a class with an injectMembers(instance) method that assigns each @Inject field by calling a generated injectFieldName static helper. For @AndroidEntryPoint, Hilt rewrites your class (via a Gradle bytecode-transform plugin) so it extends a generated Hilt_LoginActivity base, whose onCreate calls into the generated component to run injectMembers before super.onCreate(). The lateinit var compiles to a plain non-null field initialized to null; the generated getter inserts a null check that throws UninitializedPropertyAccessException if read before assignment — which is exactly why ordering relative to Hilt's injection point matters.

OS → Activity.<init>()            // fields are null here
Hilt_LoginActivity.onCreate()
  └─ generatedComponent.inject(this)   // MembersInjector runs, fields assigned
LoginActivity.onCreate()          // now safe to read analyticsLogger

Interface Binding

🎤 Say it out loud (~30–45s): "Interface binding is how I keep callers depending on an abstraction instead of a concrete class — I declare an interface in the domain layer and bind the implementation with a @Binds method in a module. I prefer @Binds over @Provides here because it's abstract, generates no factory body, and just tells the graph 'when someone asks for AuthRepository, hand them the Impl.' The subtle bit is that the implementation still needs its own @Inject constructor so Hilt knows how to build it."

Interface binding wires a concrete implementation to an interface so that callers depend on the abstraction rather than the implementation. In Hilt, you do this with a @Binds method in a @Module.

// The interface (defined in Domain)
interface AuthRepository {
    suspend fun login(email: String, password: String): Result<User>
}

// The implementation (defined in Data)
class AuthRepositoryImpl @Inject constructor(
    private val apiService: AuthApiService,
    private val userDao: UserDao
) : AuthRepository {
    override suspend fun login(email: String, password: String): Result<User> { ... }
}

// Hilt module: tells the graph "when someone asks for AuthRepository, give them AuthRepositoryImpl"
@Module
@InstallIn(SingletonComponent::class)
abstract class AuthModule {
    @Binds
    @Singleton
    abstract fun bindAuthRepository(impl: AuthRepositoryImpl): AuthRepository
}

Under the hood

@Binds is special precisely because it has no body. The processor doesn't generate a factory that creates anything — instead it records a binding-graph edge that says "the key AuthRepository is satisfied by the existing AuthRepositoryImpl provider." At resolution time the generated component just returns the AuthRepositoryImpl_Factory.get() result directly, with no extra wrapper allocation. That's why @Binds methods must be abstract and live in an abstract class or interface module — there's nothing to execute. Contrast with @Provides, where the processor generates a factory that actually invokes your method body. So @Binds is a pure compile-time aliasing operation: zero runtime cost beyond the underlying impl's own creation.

key: AuthRepository  ──(alias)──▶  AuthRepositoryImpl_Factory
                                       └─ needs AuthApiService, UserDao

Scopes

🎤 Say it out loud (~30–45s): "A scope guarantees a single shared instance for the lifetime of a component — @Singleton for the whole app, @ViewModelScoped per ViewModel, and so on. Unscoped bindings hand out a fresh object on every injection. The classic mistake interviewers probe is scope mismatch: if a @Singleton holds something tied to an Activity, you leak the Activity for the life of the process. Hilt actually catches most of these at compile time because a component can only depend on bindings from itself or its parents."

A scope determines how long a provided dependency lives and ensures that all injections within that scope receive the same instance — rather than a new object on every injection.

@ActivityRetainedScopedActivityRetainedComponentActivity lifetime, survives config change

    @Provides

    @Singleton

            .client(client)

// ViewModelScoped: one instance per ViewModel, cleared when ViewModel is cleared

    @Provides
    @ViewModelScoped
    fun provideLoginPresenterHelper(): LoginPresenterHelper = LoginPresenterHelper()
}

Why scoping matters: without @Singleton, each injection creates a new instance. Two classes that both inject OkHttpClient would get different clients, wasting resources and breaking connection pooling. Scoping ensures shared resources are truly shared.

Common mistake: scoping a dependency to a wider scope than its own dependencies allow. If a @Singleton NetworkModule holds a reference to an @ActivityScoped dependency, the Activity leaks into the singleton and is never garbage-collected. Hilt catches this mistake at compile time.

Under the hood

A scope is implemented as a memoizing wrapper around the underlying factory. The processor wraps a scoped binding's Provider in DoubleCheck — a double-checked-locking lazy holder that computes the value once on first get(), stores it in a volatile field, and returns that same reference forever after. Unscoped bindings get the raw factory with no DoubleCheck, so every get() allocates. The "instance" of a scope is literally the generated component object: SingletonComponent is created once in Application, ActivityRetainedComponent is stored in a retained ViewModel (which is how it survives config changes), and each scoped instance is a field cached inside its component. Compile-time scope validation comes from Dagger checking that a binding installed in a child component never gets cached in a longer-lived parent.

// Roughly what the processor generates for a @Singleton binding:
private volatile Object okHttpClient = new MemoizedSentinel();
OkHttpClient okHttpClient() {
    Object local = okHttpClient;
    if (local instanceof MemoizedSentinel) {
        synchronized (local) {
            local = okHttpClient;
            if (local instanceof MemoizedSentinel) {
                local = NetworkModule.provideOkHttpClient();  // runs ONCE
                okHttpClient = local;
            }
        }
    }
    return (OkHttpClient) local;
}

Qualifiers and Modules

🎤 Say it out loud (~30–45s): "Qualifiers solve the ambiguous-binding problem — when two providers share a type like String, I tag each with a custom @Qualifier annotation so Dagger can tell them apart by key. Without one you get a duplicate-binding compile error. Modules are just the containers that group binding declarations, and I organize them by concern — network, database, repository — so the graph stays readable and @InstallIn controls which component they live in."

Qualifiers distinguish multiple bindings of the same type. Without them, Hilt would have no way to tell two String providers apart and the build would fail with an ambiguous binding error.

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class BaseUrl

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class ApiKey

@Module

object AppConfigModule {

    @Singleton

    @Provides
    @Singleton
    @ApiKey
    fun provideApiKey(): String = BuildConfig.API_KEY
}

// Usage:
class ApiClient @Inject constructor(
    @BaseUrl private val baseUrl: String,

NetworkModule       — OkHttpClient, Retrofit, API services

Under the hood

Dagger identifies every binding by a composite key of (qualifier-annotation, type), not by type alone. So @BaseUrl String and @ApiKey String are two distinct keys in the graph — that's why they don't collide. The @Retention(BINARY) matters because the qualifier annotation must survive into the .class files for the annotation processor to read it during compilation, but it doesn't need to be present at runtime via reflection (so RUNTIME is overkill). Modules themselves carry no runtime state for @Provides object modules — the processor reads each module's methods to discover bindings and emits the corresponding factories; @InstallIn simply tells Dagger which generated component class should own those bindings. A duplicate-binding error is literally Dagger finding two entries hashing to the same key while building the graph.

Testing with Fakes

🎤 Say it out loud (~30–45s): "DI is what makes testing clean — because dependencies come in from outside, I can swap real implementations for test doubles. For pure unit tests I just construct the class and pass fakes directly, no framework involved. For instrumented tests that go through Hilt, I use @TestInstallIn to replace a whole module. I lean toward fakes over mocks for DI replacement because a fake is a real working implementation, so it's more stable; I reach for mocks when I specifically need to verify interactions."

DI enables replacing real implementations with fakes in tests. There are two strategies:

1. Constructor injection — pass fakes directly

🎤 Say it out loud (~30s): "With constructor injection I don't need Hilt at all in a unit test — I just new up the class with fakes. That's the biggest practical payoff of preferring constructor over field injection: my ViewModel test is plain JVM code with no instrumentation, no graph, no @HiltAndroidTest overhead."
@Test
fun `login success updates state to Success`() = runTest {
    val fakeRepo = FakeAuthRepository(shouldSucceed = true)
    val viewModel = LoginViewModel(fakeRepo, FakeAnalyticsLogger())

    viewModel.onLoginClicked("user@example.com", "password")

    assertEquals(LoginUiState.Success, viewModel.uiState.value)
}

2. Hilt test modules — replace binding in instrumented tests

🎤 Say it out loud (~30s): "When the test has to run through the real graph, I use @TestInstallIn with a replaces argument to swap out a production module for a fake one. Hilt regenerates a test component that uses my fake binding instead of the real one across the whole test. The nuance is replaces must point at the exact module being uninstalled, and this only works in @HiltAndroidTest instrumented or Robolectric tests, not plain JVM unit tests."
// Replace the real AuthRepository binding in tests
@Module
@TestInstallIn(components = [SingletonComponent::class], replaces = [AuthModule::class])
abstract class FakeAuthModule {
    @Binds
    @Singleton
    abstract fun bindAuthRepository(impl: FakeAuthRepository): AuthRepository
}

Fake vs Mock: A fake is a simplified but working implementation of an interface — for example, an in-memory list standing in for a database. A mock is a test double that records calls and can be configured to return specific values. Fakes tend to be more stable for DI replacement because they have real behaviour; mocks are better when you specifically want to verify interaction sequences.

Under the hood

@TestInstallIn works by generating a separate test component hierarchy at compile time. Hilt's processor sees the replaces list and physically omits the named production modules from the generated DaggerXxx_TestComponent, splicing in the test module instead — so there's no runtime monkey-patching; it's a different generated graph that the test runner activates via HiltTestApplication. For per-test overrides, @BindValue is even more dynamic: the processor generates a field on the test class and a binding that reads that field, so the value is resolved when the component is built in the @Before injection step. Either way, the substitution is resolved before any of your code runs — Hilt never swaps bindings while the app is live.

Hilt Basics

🎤 Say it out loud (~30–45s): "Hilt is a layer on top of Dagger 2 that gives you a standard set of components already wired to the Android lifecycle, so you skip the boilerplate of hand-writing components and injection calls. You annotate the Application with @HiltAndroidApp to generate the root, mark entry points like Activities with @AndroidEntryPoint, and use @HiltViewModel plus hiltViewModel() in Compose. It's still fully compile-time and built on Dagger underneath — Hilt is opinion and convention, not a new runtime."

Hilt is built on Dagger 2 and eliminates the vast majority of its boilerplate by providing predefined components that are already tied to the Android lifecycle.

Under the hood

DI vs Service Locator

🎤 Say it out loud (~30–45s): "Both decouple a class from concrete types, but the difference is who does the lookup. With DI the framework hands you dependencies through your constructor, so they're visible in the signature and trivially swappable in tests. With a service locator the class reaches into a global registry itself — ServiceLocator.get<T>() — which hides its real dependencies and reintroduces global mutable state. The gotcha interviewers love is that service locator looks like DI but it's actually the opposite of inversion of control: the dependency is still pulled, not pushed, so it's generally treated as an anti-pattern."

Both patterns decouple consumers from concrete types, but they differ fundamentally in who performs the lookup.

Dependency Injection Service Locator
Who resolves dependencies?The framework (Hilt/Dagger) at construction timeThe class itself, by calling a registry
Dependencies visible?Yes — constructor signatureNo — hidden inside the class
TestabilityHigh — swap implementations at constructionLow — must configure global registry
CouplingLoose — class doesn't know about the containerTight — class calls ServiceLocator.get<T>()
Exampleclass Foo @Inject constructor(val bar: Bar)val bar = ServiceLocator.get<Bar>()

Service locator is considered an anti-pattern in most contexts. It hides dependencies, makes classes harder to test, and creates implicit global state — all the things DI is designed to avoid.

Under the hood

A service locator is typically a singleton holding a Map<Class<*>, Provider<*>> (or Map<KClass, () -> Any>); a get<T>() call hashes the type token and returns the registered provider's result. Because that map is process-global mutable state, resolution failures surface only at runtime when the lookup misses. Dagger/Hilt instead resolve the graph at compile time: the annotation processor walks @Inject constructors, builds a directed acyclic graph, and code-generates concrete Factory/Provider classes (e.g. Foo_Factory) plus a component that wires them — so a missing or cyclic binding is a compilation error, not a NullPointerException in production.

Service Locator:  class --> ServiceLocator.get(T) --> Map<KClass, Provider> [runtime lookup, can miss]
Dependency Inj.:  Component --> Foo_Factory.get() --> new Foo(bar)         [graph verified at compile time]

Hilt vs Manual Dagger vs Manual DI

🎤 Say it out loud (~30–45s): "These are three points on a spectrum of automation. Manual DI is just hand-wiring constructors in an AppContainer — totally transparent, zero build cost, but it scales linearly with the graph and gives you no scoping. Dagger generates that wiring for you with compile-time validation and scoping, and Hilt is Dagger plus a set of opinionated, lifecycle-aware components for Android. My default is Hilt for any real app; the trade-off I'd call out is the kapt/KSP annotation-processing cost on build time, which is why a tiny prototype or a test container might just hand-wire fakes instead."

Manual DI means hand-wired constructor injection with no framework at all:

// Application class manually wires the dependency graph
class AppContainer(context: Context) {
    val db = Room.databaseBuilder(context, AppDatabase::class.java, "app-db").build()
    val userDao = db.userDao()
    val authApiService = Retrofit.Builder().build().create(AuthApiService::class.java)
    val authRepository: AuthRepository = AuthRepositoryImpl(authApiService, userDao)
    fun makeLoginViewModel() = LoginViewModel(authRepository)
}

Pros: no annotation processing, fully transparent, fast build. Cons: all wiring is manual — it scales poorly, there's no scoping support, and boilerplate grows roughly linearly with the graph size.

When to use what:

  • Hilt for almost all new Android apps. It reduces boilerplate, integrates with the Jetpack lifecycle, and has first-party support from Google.
  • Manual Dagger 2 for large legacy codebases already invested in Dagger, or apps with unusual component graphs like multi-process setups or shared libraries.
  • Manual DI for small projects, prototypes, or when teaching. Also useful for test containers where you want to wire fakes without the overhead of the Hilt test infrastructure.

Under the hood

Hilt is a thin layer of code generation on top of Dagger, not a separate runtime. At compile time the Hilt processor generates a fixed hierarchy of Dagger components keyed to Android lifecycles — SingletonComponent, ActivityRetainedComponent, ActivityComponent, ViewModelComponent, etc. — and a generated Hilt_MainActivity base class that field-injects via a getGeneratedComponentManager() lookup. @AndroidEntryPoint rewrites your Activity's superclass through a bytecode/Gradle transform so the OS-constructed class still receives injection. Dagger itself emits no reflection: every binding becomes a generated Provider, and @Singleton/scoped bindings are wrapped in DoubleCheck — a double-checked-locking memoizing provider — so the instance is created once and cached. Manual DI has none of this generation; the graph is literally the val initialization order in your container, resolved eagerly at object construction.

// Roughly what Dagger generates for a scoped binding

// .get() lazily creates once, then returns the cached instance on every later call

Interview Angles

Q: Why use DI? "DI inverts control over dependency creation. The consumer doesn't construct its own dependencies — they're provided from outside. That decouples the consumer from the concrete type, enables substitution — fakes in tests, different implementations at runtime — and centralises configuration in one place rather than scattered across the codebase."

Q: Constructor injection vs field injection — which do you prefer? "Constructor injection whenever possible. The dependency is explicit in the signature, enforced at compile time, and naturally val so it's immutable. Field injection is unavoidable for Android framework classes like Activity and Fragment because the OS constructs them and you don't control the constructor. Everywhere else — ViewModels, repositories, use cases, data sources — I use constructor injection."

Q: What is scoping? "Scoping ensures that all injections within a given component receive the same instance. @Singleton means one instance for the life of the app. @ViewModelScoped means one instance per ViewModel lifecycle. Without scoping, every injection creates a new instance — and that's expensive for stateful objects like database connections or HTTP clients."

Q: How does DI improve testing? "Because dependencies are injected rather than constructed internally, tests can substitute any real dependency with a fake or a mock. There's no global state and no static factory to configure — I just pass a different object to the constructor. That makes tests fast because there's no real I/O, and reliable because there's no shared mutable state between tests."

Q: Hilt vs manual DI? "Hilt provides scoping, lifecycle integration, and boilerplate elimination at the cost of annotation processing time and coupling to the framework. Manual DI is transparent and framework-free but scales poorly in large apps. Hilt is the right default for any app of meaningful size; I'd use manual DI for small prototypes or in situations where annotation processing is a hard constraint."

7.5 Modularization

Module Types and Roles

🎤 Say it out loud (~30–45s): "I organize a multi-module app into three tiers: a thin :app module that just wires everything together, :feature modules that are self-contained user-facing flows, and :core modules holding shared infrastructure like network, data, ui, and domain. The rule that keeps it healthy is one-directional dependencies — features depend on core, core never depends on features, and crucially features don't depend on each other. The gotcha is keeping :app thin: it's tempting to leak feature logic into it, but its only job is composition — navigation graph and DI component wiring."

A well-modularized Android app organises code into modules with clear, non-overlapping responsibilities and explicit dependency declarations.

:app                  — application module; ties everything together; thin
:feature:search       — one user-facing feature
:feature:booking      — another user-facing feature
:feature:profile      — another user-facing feature
:core:ui              — shared Compose components, themes, design tokens
:core:network         — Retrofit setup, auth interceptors, base API types
:core:data            — shared repositories, Room database
:core:domain          — shared domain models, interfaces
:core:analytics       — FEM/analytics infrastructure
:core:testing         — test utilities, fakes, base test classes

Under the hood

Each Gradle module compiles to its own artifact (an .aar for Android library modules, .jar for pure Kotlin/JVM ones) with its own classpath and its own R class. Gradle models the build as a task graph of per-module compileKotlin/compileJava tasks; module boundaries are what let it parallelize and cache those tasks independently. The api vs implementation configuration in a module's build.gradle.kts decides what leaks downstream: implementation dependencies stay off the consumer's compile classpath (they're only on the runtime classpath), so a transitive change there can't force a downstream recompile. That's also why a feature module declaring :core:domain as api re-exposes those types, while implementation keeps them private — the choice directly shapes the compile-time dependency graph the build cache hashes against.

API vs Implementation Separation

🎤 Say it out loud (~30–45s): "For a big feature I split it into an :api module with just the public contract — interfaces, models, navigation routes — and an :impl module with the ViewModels, Composables, and data layer. Other features depend only on :api, and :app is the single thing that depends on :impl to wire DI. The payoff is twofold: I get a hard compile-time boundary so booking literally can't call search's internal ViewModel, and I get faster builds because changing search's implementation never recompiles booking — only changing the :api contract does."

For large feature modules, split the module into :feature:search:api and :feature:search:impl.

  • :feature:search:api: the public contract — interfaces, domain models, navigation routes. Other features that need to navigate to search or consume search results depend only on :api.
  • :feature:search:impl: the private implementation — ViewModels, Composables, Retrofit services, Room tables. Only :app depends on :impl, to wire DI.
:feature:booking:impl → :feature:search:api   (to navigate to search)
:app                  → :feature:search:impl  (to register DI module)
:app                  → :feature:booking:impl

The benefits are: booking recompiles when search:api changes, but NOT when search:impl changes; changes to search's internal implementation never force a recompile of booking; and the boundary is enforced — booking cannot call internal search ViewModel methods even if someone wants to.

Under the hood

The mechanism that makes this work is ABI-based incremental compilation keyed on the application binary interface. When :search:impl compiles, the Kotlin/Gradle infrastructure computes a hash of its public ABI — class signatures, method signatures, public constants — but not method bodies. Because booking only sees :search:api on its compile classpath, edits inside an :impl method body change the .class byte stream but leave the ABI hash that booking was compiled against untouched, so Gradle marks :booking's compile task UP-TO-DATE and skips it. The boundary is enforced because :impl's classes are simply never on :booking's compile classpath — an attempt to reference an internal ViewModel is an unresolved-reference compile error, not a convention. (Kotlin internal visibility reinforces this at the module level: internal symbols are name-mangled in bytecode and invisible to other modules.)

Dependency Direction and Avoiding Cycles

🎤 Say it out loud (~30–45s): "The dependency rule maps straight onto modules: features point at core, core never points back, and features never point at each other directly. When two features genuinely need to talk, I don't let them depend on each other — I either pull the shared concept down into :core:domain, define an interface there that one implements and the other calls, or wire the interaction up in :app since it already sees both. The thing to know is Gradle will hard-fail the build on a dependency cycle, so cycles never really survive — the real discipline is preventing the accidental edge with lint or a dependency-guard check."

The dependency rule maps directly to modules: feature modules depend on core modules; core modules never depend on feature modules; and feature modules never depend on each other, except through :api contracts wired by :app.

CORRECT:
:feature:booking → :core:data → :core:domain

WRONG — cycle:
:feature:booking → :feature:search
:feature:search  → :feature:booking   ← CYCLE

How to prevent cycles: there are four approaches. First, architecture lint rules — Gradle or tools like Dependency Guard can fail the build on unexpected dependencies. Second, extract shared concepts to core — if booking and search share a domain concept, move it to :core:domain. Third, event bus or shared interface — if search must notify booking, define a SearchCompletedListener interface in :core:domain; booking implements it; search calls it; neither knows about the other's implementation. And fourth, decouple via :app — the :app module can wire feature interactions directly because it depends on both features.

Detecting cycles: ./gradlew :app:dependencies and tools like gradle-dependency-graph-generator visualise the full graph. Gradle will fail the build entirely on a cycle, so they rarely survive long.

Under the hood

Gradle builds an internal directed graph of project dependencies during the configuration phase and resolves each configuration (e.g. compileClasspath) by topological sort. A cycle makes a topological ordering impossible — there's no module it can compile first — so Gradle throws a CircularReferenceException/circular-dependency error before any compilation starts. The "interface in :core:domain" trick works because it inverts the dependency edge using the Dependency Inversion Principle: both search and booking end up pointing down at the shared abstraction in core rather than sideways at each other, turning a would-be cycle into two acyclic edges.

Cycle (no valid build order):      booking → search → booking
Inverted via core abstraction:     booking → core:domain ← search   (acyclic; both depend downward)

Build Speed

🎤 Say it out loud (~30–45s): "Modularization's biggest concrete win is incremental compilation — Gradle only recompiles the modules whose inputs actually changed and pulls everything else from cache, so a one-feature edit can drop a build from minutes to under a minute. Under that sit four levers: the build cache hashing module inputs to reuse outputs, parallel compilation of independent modules, the configuration cache skipping the configuration phase, and ABI stability so dependents don't recompile when only an implementation body changes. The nuance is that all of this depends on clean boundaries — one api dependency or one god-module quietly serializes the graph and the cache hit rate collapses."

Modularization's primary concrete engineering benefit is incremental compilation. Gradle compiles a module only when its sources or its direct dependencies have actually changed.

Full app compile time without modules:  ~8 minutes
After unrelated feature change:          ~8 minutes (entire :app recompiles)

With modules:
Change in :feature:booking:               recompile :feature:booking + :app
All other modules:                        cache hit — skipped
Effective compile time:                  ~45 seconds

There are four key mechanisms. The Gradle build cache hashes module inputs and caches the output .jar — if nothing in :core:domain changed, the cached .jar is reused with no compilation at all. Parallel compilation lets independent modules compile at the same time via org.gradle.parallel=true. The configuration cache (org.gradle.configuration-cache=true) skips the Gradle configuration phase on repeated builds. And ABI stability means that if a module's public API doesn't change, none of its dependents recompile even when the module's implementation changes internally.

Under the hood

The build cache key is a SHA hash computed over a task's complete set of declared inputs — source files, classpath artifacts, compiler args, and the JVM/Kotlin toolchain version. On a cache hit Gradle restores the task's outputs from the local (~/.gradle/caches) or a shared remote cache and never invokes the compiler; this is why a task can be reported FROM-CACHE rather than UP-TO-DATE. Parallelism is bounded by the dependency graph and the worker count (org.gradle.workers.max): only modules with no unfinished dependency edge can run concurrently, so a single highly-depended-on module becomes a serialization bottleneck — every dependent must wait for it. The configuration cache goes further by serializing the resolved task graph itself to disk, letting Gradle skip re-running every build.gradle.kts script on the next invocation as long as no build inputs (env vars, files read at configuration time) changed.

Feature-Based vs Layer-Based

🎤 Say it out loud (~30s): "These are two ways to slice a multi-module app. Feature-based gives each module a vertical slice — all the layers for one feature — which maximizes cohesion and team ownership. Layer-based slices horizontally by architectural layer, which reads cleanly but kills build parallelism and ownership. In practice I go hybrid: feature modules on top, shared :core:* modules underneath, because pure feature-based still forces you to extract shared infrastructure anyway."

Feature-Based (Vertical Slices)

🎤 Say it out loud (~30s): "In feature-based modularization each module owns the full stack for one feature — ViewModel, Composable, repository, data source. The win is cohesion: a change to search touches only :feature:search, and a team can own it end to end. The catch is shared infrastructure — network setup, the Room database — which you either duplicate or hoist into a :core module, so you almost never stay purely feature-based."

Each module contains all layers for one feature — ViewModel, Composable, repository, data source, DTO.

:feature:search     — SearchViewModel, SearchScreen, SearchRepository, SearchApiService
:feature:booking    — BookingViewModel, BookingScreen, BookingRepository, BookingApiService

Pros: high cohesion within the feature; natural team ownership; changing a feature touches one module. Cons: shared infrastructure like network setup and the Room database either duplicates across features or requires a :core:* module anyway.

Under the hood

Gradle models the build as a directed acyclic graph of project tasks. With vertical slices, sibling feature modules have no dependency edge between them, so Gradle's task scheduler can compile :feature:search and :feature:booking in parallel across worker processes (org.gradle.parallel). Each module also produces its own compilation classpath, so a change confined to one feature only invalidates that module's compileKotlin task outputs; the build cache restores everything else from prior outputs keyed by an input hash.

:feature:search ─┐
                 ├─► :app   (no edge between the two features → parallel compile)
:feature:booking ┘

Layer-Based (Horizontal Slices)

🎤 Say it out loud (~30s): "Layer-based puts all ViewModels in :presentation, all use cases in :domain, all repositories in :data. It looks architecturally pure and the dependency direction is easy to police, but it creates a serial compile chain — presentation depends on domain depends on data — and nobody can really own 'all the data sources for the entire app.' Adding one feature touches three modules, so I avoid it at scale."

Each module contains one architectural layer for all features.

:presentation   — all ViewModels and Composables
:domain         — all use cases and entities
:data           — all repositories and data sources

Pros: clean separation of concerns by layer; architecture rules are easy to enforce. Cons: low cohesion — adding a feature touches three modules; poor ownership alignment (who owns :data?); and poor build parallelism because :presentation depends on :domain which depends on :data, creating a serial compilation chain.

Under the hood

Because the layer modules form a linear dependency chain, Gradle must topologically order their compile tasks: :data's compileKotlin must finish before :domain's can start (it needs the class files on its classpath), and :domain before :presentation. Even with org.gradle.parallel=true, the scheduler cannot overlap them — parallelism only helps independent nodes in the task graph. A change deep in :data also invalidates the ABI (the public API surface) seen by :domain and :presentation, so Kotlin's incremental compiler must recheck both downstream modules.

:data ──► :domain ──► :presentation   (strictly serial — no overlap possible)

Hybrid (Recommended for Large Apps)

🎤 Say it out loud (~30s): "The hybrid is what I actually ship: feature modules at the top for ownership and parallel builds, with cross-cutting concerns pulled down into :core:* modules like network, UI, domain, and data. For big features I split :api from :impl so other modules compile against a stable contract and don't recompile when the implementation changes. It's the structure Now in Android uses, and it balances cohesion against shared-infrastructure reuse."

Feature-based at the top level, with shared core layers extracted into :core:* modules.

:feature:search:api / :feature:search:impl
:feature:booking:api / :feature:booking:impl
:core:domain
:core:data
:core:ui
:core:network

Under the hood

The :api/:impl split exploits Gradle's distinction between the compile classpath and the runtime classpath. Other modules depend only on :feature:search:api (interfaces and data classes), so changes inside :impl don't alter the ABI those modules compiled against — Gradle marks the downstream compileKotlin tasks UP-TO-DATE and skips them. The concrete :impl is added to the runtime classpath (or wired by :app via DI), and Gradle's ABI-aware incremental compilation compares the extracted public-API fingerprint, not file timestamps, to decide what to recompile.

Dynamic Feature Modules

🎤 Say it out loud (~30s): "Dynamic Feature Modules let you ship part of the app on demand instead of in the base APK, downloaded later through Play's SplitInstallManager. The thing interviewers probe is the inverted dependency — a DFM depends on :app, not the reverse — and the runtime cost: the code isn't present until it's installed, so every entry point has to check install state, and DI gets hairy because Hilt needs a custom component. I treat them as a last resort for large optional features, not a default."

Dynamic Feature Modules enable on-demand delivery — the user downloads and installs parts of the app after the initial install, which reduces the base APK size.

// In :feature:onboarding (a DFM):
// build.gradle.kts
plugins { id("com.android.dynamic-feature") }
android { ... }
dependencies { implementation(project(":app")) }  // DFM depends on base app, reverse of normal

The implications are worth understanding before reaching for them. DFM code is not available at app start if it hasn't been downloaded yet, so all calls must go through SplitInstallManager. Navigation to DFM screens requires checking install state first. DFMs complicate DI — Hilt supports them via @DefineComponent plus @InstallIn(customComponent), but it's non-trivial. They're best suited to large optional features like AR try-on or full offline maps, where the size reduction justifies the significant added complexity. Testing DFM install flows also requires specific test infrastructure that most teams don't already have.

Under the hood

A DFM is packaged as a separate split APK inside the Android App Bundle (.aab); the Play Store generates and serves it independently of the base split. When you request it, SplitInstallManager downloads the split and the framework calls SplitCompat.install(), which patches the running app's ClassLoader and resource table so the new classes.dex and resources resolve at runtime — this is why a class reference into an uninstalled DFM throws ClassNotFoundException and why entry points must be reflective or interface-based. The reversed dependency edge (implementation(project(":app"))) exists because the base APK is loaded first and is on the DFM's classpath; the DFM cannot be on the base's compile classpath or the base couldn't build without it.

base.apk (app) ──loaded first──► ClassLoader
        ▲                              │ SplitCompat.install() patches in:
        │ implementation(project)      ▼
feature-onboarding.apk (split, fetched on demand)  →  new dex + resources

Convention Plugins

🎤 Say it out loud (~30s): "Convention plugins move shared Gradle setup — compileSdk, Kotlin options, common dependencies — into one reusable plugin so each module applies a single line instead of copy-pasting 50. The big win is consistency: I bump compileSdk in one place and every module follows, and no module can drift onto a stale SDK. People sometimes ask buildSrc versus an included build-logic build — I prefer the included build because changing it doesn't invalidate the whole project's build classpath."

Convention plugins — also called build logic plugins — centralise Gradle configuration and eliminate copy-paste across build.gradle.kts files.

// buildSrc/src/main/kotlin/AndroidFeatureConventionPlugin.kt
class AndroidFeatureConventionPlugin : Plugin<Project> {
    override fun apply(target: Project) {
        with(target) {
            pluginManager.apply("com.android.library")
            pluginManager.apply("org.jetbrains.kotlin.android")
            pluginManager.apply("com.google.dagger.hilt.android")

            extensions.configure<LibraryExtension> {
                compileSdk = 35
                defaultConfig.minSdk = 26
                compileOptions {
                    sourceCompatibility = JavaVersion.VERSION_17
                    targetCompatibility = JavaVersion.VERSION_17
                }
            }

            dependencies {
                "implementation"(project(":core:ui"))
                "implementation"(project(":core:domain"))
                "testImplementation"(project(":core:testing"))
                // ... common deps
            }
        }
    }
}
// :feature:search:impl/build.gradle.kts
plugins { id("zocdoc.android.feature") }  // single line replaces 50 lines of boilerplate

dependencies {
    implementation(project(":feature:search:api"))  // feature-specific only
}

Benefits: version updates to compileSdk, minSdk, or Kotlin happen in one place; new modules get the correct configuration by applying a single plugin; and consistency is enforced — no module can accidentally slip onto a different SDK version.

Under the hood

A convention plugin is just a class implementing Plugin<Project>; at configuration time Gradle calls its apply(target) and the body imperatively mutates that project's model — applying other plugins, configuring the LibraryExtension, and adding dependencies — exactly as if you'd typed it in the module's own script. Code in buildSrc is compiled into a synthetic build automatically placed on every script's classpath, so editing it invalidates the configuration cache for the whole build. An includeBuild("build-logic") composite build instead exposes the plugin through a gradlePluginPortal-style marker, so only modules that actually apply the plugin are affected — which is why large projects (and Now in Android) favor build-logic over buildSrc.

When Does Modularization Become Over-Engineering?

🎤 Say it out loud (~30s): "Modularization is a tool with real costs — Gradle config overhead, DI wiring, interface indirection, navigation boilerplate — so it's over-engineering when those costs exceed the payoff. The tells are modules with a handful of files, PRs that touch every module anyway, and a small team that doesn't need ownership boundaries. On a small app, Gradle's per-module configuration time can actually exceed the compile time you saved, so I start with three to five modules and split only when a real pressure — team boundary, compile pain, or on-demand delivery — shows up."

There are six signs you've over-modularized. First, modules with only 1–3 files — the boundary adds more cognitive overhead than it saves. Second, most changes touch all modules — if every PR reaches :core:domain, :core:data, :feature:X, and :app, the modules are too fine-grained and you should consider merging. Third, the team is small — 2 or 3 engineers don't need module ownership boundaries. Fourth, circular dependency pressure — if you keep wanting to add cross-module dependencies, the boundary is in the wrong place. Fifth, the build is not bottlenecked on compilation — on small apps the Gradle configuration overhead can easily exceed the compilation time savings. And sixth, navigation becomes a maze — excessive api/impl splits, interface indirection for simple screen transitions, and Hilt component hierarchies for DFMs can add complexity that dwarfs any benefit on a small codebase.

Guideline: start with 3–5 modules — :app, :core:network, :core:ui, and one :feature:* — and split features into their own modules only when a team boundary emerges, compile times become painful, or a feature is a natural candidate for on-demand delivery.

Under the hood

Every Gradle module incurs fixed overhead in the configuration phase: the build script is evaluated, plugins are applied, and a task graph node set is created for that project — work that happens on every invocation unless the configuration cache hits. Past a few hundred modules this per-project cost grows linearly and can dominate wall-clock time on incremental builds, which is the mechanism behind "the build is not bottlenecked on compilation." Modularization only pays off when it shrinks the set of compileKotlin tasks actually invalidated by a typical change; if most changes still fan out to every module, the dependency graph hasn't reduced invalidation scope and you've added configuration overhead for no caching benefit.

Interview Angles

Q: How would you modularize a large Android app? "I'd start with a hybrid approach: feature modules for each user-facing feature — :feature:search, :feature:booking — shared :core:* modules for network, UI, domain, data, and testing, and a thin :app module that wires navigation and DI. Within large feature modules I'd separate :api — the public contract — from :impl — the private implementation — to keep recompilation scope as narrow as possible."

Q: Feature-based vs layer-based — which do you choose? "Feature-based, with shared infrastructure extracted to core modules. Layer-based creates serial build chains and poor team ownership — nobody owns 'all the data sources for the whole app.' Features are the natural unit of ownership, and they're also the natural unit of on-demand delivery if you ever need Dynamic Feature Modules."

Q: How do you prevent dependency cycles? "The architectural rule is that feature modules depend on core modules, and feature modules never depend on each other except through :api contracts wired by :app. I enforce that with Gradle build linting or Dependency Guard. Whenever I feel the urge to add a cross-feature dependency, that's a signal the shared concept belongs in :core:domain."

Q: How does modularization improve build time? "Gradle's incremental build and build cache only recompile modules whose inputs changed. If I touch :feature:booking, Gradle recompiles only :feature:booking and :app — every other module uses its cached output. Without modules, any change forces a recompile of the entire :app module."

Q: When does modularization become over-engineering? "When the cost of maintaining module boundaries — Gradle configuration, interface indirection, DI wiring, navigation boilerplate — exceeds the benefit in build speed, team ownership, and test isolation. The typical indicators are modules with fewer than around 10 files, small teams that don't need ownership boundaries, and build times that were never a bottleneck in the first place."
