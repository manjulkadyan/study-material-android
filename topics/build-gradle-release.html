12.1 Gradle Basics

Project vs Module

🎤 Say it out loud (~30–45s): "A Gradle project is the whole build rooted at settings.gradle.kts, and a module — Gradle calls it a subproject — is an independently buildable unit you declare with include. The reason we split into modules isn't aesthetics: each module is its own compilation unit, so a change in :feature:search doesn't force :core:network to recompile. The gotcha interviewers probe is that modularization is only a win if your dependency graph stays acyclic and you keep api leakage in check — otherwise you get recompile cascades and you've paid the complexity cost for nothing."

Definition

A Gradle project is the top-level build — the root build.gradle(.kts) and settings.gradle(.kts) files represent it. A Gradle module (Gradle calls them "subprojects") is an independently buildable unit declared in settings.gradle.kts via include(":moduleName").

How it works

settings.gradle.kts
  rootProject.name = "MyApp"
  include(":app")
  include(":feature:search")
  include(":core:network")

Each module has its own build.gradle.kts. The root project aggregates them. Gradle resolves the dependency graph by walking include declarations and evaluating each module's build script.

Under the hood

settings.gradle.kts is evaluated first by the Settings object during the initialization phase, before any build.gradle.kts is touched. Each include(":a:b") creates a ProjectDescriptor and maps the path to a directory (default a/b). Gradle then builds an in-memory Project object tree and runs the configuration phase, evaluating every project's build script to register tasks and wire dependencies into a single TaskExecutionGraph (the DAG). Modules are nodes in a project-dependency graph; Gradle topologically sorts it, which is exactly why a cycle is fatal — there is no valid linear order to execute.

init phase:    Settings → ProjectDescriptor tree
config phase:  each Project.evaluate() → tasks + dependency edges
exec phase:    topological sort of TaskExecutionGraph → run

Android implications

  • :app is almost always the only com.android.application module.
  • Libraries are com.android.library modules.
  • Pure Kotlin/Java logic (no Android SDK) can be org.jetbrains.kotlin.jvm — these build fastest because they skip Android resource/manifest processing.
  • Modules can depend on each other: :app → :feature:search → :core:network.

Trade-offs

Monolithic (single module) Multi-module
Simple setupComplex dependency graph
Full recompile on any changeIncremental compilation per module
Slower CI builds as codebase growsParallelisable builds
Easier initial navigationHigher initial investment

Failure modes

  • Circular dependencies: Gradle will throw Circular dependency between the following tasks. Break cycles by extracting shared code into a :core module.
  • Accidentally including a module that doesn't have a build.gradle → Project directory ... does not exist.

Android Gradle Plugin (AGP)

🎤 Say it out loud (~30–45s): "AGP is the Gradle plugin that bolts Android onto generic Gradle — it's what knows about aapt2, manifest merging, DEX-ing, variants, signing, and AAB packaging. When you apply com.android.application, it registers hundreds of tasks behind friendly lifecycle names like assembleDebug. The thing interviewers always check is the version coupling: AGP, the Gradle wrapper, the Kotlin Gradle plugin, and the JDK all have to line up — AGP 8 needs Gradle 8 and JDK 17 — and a mismatch surfaces as a cryptic NoSuchMethodError, not a clear message."

Definition

AGP is the Gradle plugin that layers Android-specific build logic on top of standard Gradle — it handles resource compilation with aapt2, manifest merging, DEX compilation, APK/AAB packaging, signing, lint, and instrumented test support.

How it works

// root build.gradle.kts
plugins {
    id("com.android.application") version "8.4.0" apply false
    id("com.android.library")     version "8.4.0" apply false
    id("org.jetbrains.kotlin.android") version "1.9.24" apply false
}

AGP registers hundreds of Gradle tasks behind assembleDebug, bundleRelease, etc. It consumes android { } DSL blocks and wires source sets, build variants, and outputs.

AGP → Gradle → JDK compatibility matrix

Always check the AGP release notes before upgrading. A version mismatch — for example, AGP 8.x paired with Gradle 7.x — causes immediate build failure. AGP 8.x requires Gradle 8.x and JDK 17 or higher.

Key AGP responsibilities

  1. aapt2 — compiles XML resources, produces R.java/R.txt
  2. Manifest merger — merges library manifests into the app manifest
  3. d8/r8 — Kotlin/Java bytecode → DEX (release: R8 with shrink/obfuscate)
  4. Resource shrinking (shrinkResources)
  5. APK/AAB assembly and signing

Under the hood

AGP is itself a Gradle plugin written against Gradle's Plugin<Project> API plus internal Variant/Component APIs. When applied, it reads the android { } extension (a Gradle ExtensionContainer object), enumerates the build-type × flavor matrix, and programmatically registers a task per variant — aapt2 compile/link tasks, merge* tasks, the dexBuilder/d8/r8 tasks, package and sign tasks — wiring their inputs and outputs so Gradle's up-to-date and caching machinery can track them. The NoSuchMethodError failure mode happens because AGP and the Kotlin Gradle Plugin both link against Gradle's internal (non-stable) APIs; if AGP calls a Gradle method that a mismatched Gradle/KGP version removed or changed signature on, the JVM resolves the call at runtime and throws.

apply AGP → read android{} extension
          → expand variants (buildType × flavor)
          → for each variant: register aapt2 / merge / d8|r8 / package / sign tasks
          → expose lifecycle tasks (assemble*, bundle*) depending on them

Failure modes

  • Version mismatch between AGP and Kotlin Gradle Plugin → obscure NoSuchMethodError at build time.
  • AGP's minimum SDK enforcement: if a library requires minSdk 21 and your app has minSdk 19, the manifest merger will fail.
  • aapt2 errors are often resource ID conflicts from merged libraries.

Gradle Tasks

🎤 Say it out loud (~30–45s): "A Gradle task is a unit of work with declared inputs, outputs, and an action, and tasks form a DAG that Gradle executes in dependency order. The power comes from incremental builds: Gradle fingerprints each task's inputs and outputs, and if nothing changed it skips the task as UP-TO-DATE or pulls it FROM-CACHE. The classic gotcha is non-deterministic inputs — if a task reads System.currentTimeMillis() or forgets its @Input/@OutputFile annotations, Gradle can't fingerprint it correctly, so it either never goes up-to-date or silently serves stale outputs."

Definition

A Gradle task is a unit of work with declared inputs, outputs, and an action. Tasks form a DAG — a directed acyclic graph — and Gradle executes them in dependency order.

Key concepts

  • UP-TO-DATE: Gradle checks input/output fingerprints. If nothing changed, the task is skipped. This is the cornerstone of incremental builds.
  • FROM-CACHE: Output was fetched from the build cache rather than re-executed.
  • Task configuration vs execution: Configuration phase wires the task graph. Execution phase runs actions. Doing heavy work at configuration time is a common performance anti-pattern.

Common AGP tasks

Task What it does
preBuildEntry point, dependency checks
compile{Variant}KotlinKotlin → JVM bytecode
compile{Variant}JavaWithJavacJava → JVM bytecode
merge{Variant}ResourcesMerges resources from all modules
merge{Variant}AssetsMerges assets
package{Variant}Packages DEX + resources into APK/AAB
assemble{Variant}Lifecycle task that triggers full APK build
bundle{Variant}Produces AAB
lint{Variant}Runs Android Lint
test{Variant}UnitTestRuns JVM unit tests

Custom tasks

// build.gradle.kts
abstract class GenerateVersionTask : DefaultTask() {
    @get:OutputFile
    abstract val outputFile: RegularFileProperty

    @TaskAction
    fun generate() {
        outputFile.get().asFile.writeText("VERSION=${project.version}")
    }
}

tasks.register<GenerateVersionTask>("generateVersion") {
    outputFile.set(layout.buildDirectory.file("version.txt"))
}

Under the hood

Up-to-date checking is built on input/output snapshots, not timestamps. For each task, Gradle hashes the declared inputs — file contents (a hash per file, combined into a fingerprint), input properties, and the task's own implementation/classpath — and stores them with the previous execution in .gradle. Before running, it recomputes those hashes; if they match the prior run AND the output fingerprints are unchanged, it reports UP-TO-DATE and skips the action entirely. The build cache extends this: the input fingerprint becomes a cache key, and the task's outputs are stored as an archive keyed by that hash (locally or in a remote cache), so a matching key on any machine yields FROM-CACHE. This is precisely why @Input/@OutputFile annotations matter — they tell Gradle what to put in the fingerprint. An unannotated input is invisible to hashing (stale-output risk); a volatile value like currentTimeMillis() makes the fingerprint differ every run (never cacheable). register is also lazy — the task is configured only if it ends up in the graph, unlike eager create.

inputs (files+props+impl) ──hash──▶ fingerprint ──┐
                                                   ├─ == previous? & outputs intact? → UP-TO-DATE
prev run fingerprint  ◀── stored in .gradle ───────┘
fingerprint as key ──▶ build cache lookup ──▶ hit → FROM-CACHE (unpack outputs)

Failure modes

  • Tasks that read System.currentTimeMillis() or random values as outputs break UP-TO-DATE checks — outputs always differ.
  • Forgetting @Input/@Output annotations on custom tasks → Gradle cannot fingerprint correctly → stale outputs.
  • Task ordering vs dependency: mustRunAfter doesn't create a dependency — if Task B mustRunAfter Task A but nothing depends on B, A won't run. Use dependsOn for hard dependencies.

Build Variants, Build Types, Product Flavors

Build Types

🎤 Say it out loud (~30–45s): "A build type controls how the same code is compiled and packaged — debuggability, minification, signing config, and id/version suffixes — with debug and release as the defaults. The mental model I use: build type is the how, flavor is the what. A subtlety is that initWith lets a custom type like staging inherit from debug and then override pieces, which is cleaner than copy-pasting the whole block, and applicationIdSuffix lets you install debug and release side by side."

Definition: A build type controls how the code is compiled and packaged. The two default types are debug and release.

android {
    buildTypes {
        debug {
            isDebuggable = true
            applicationIdSuffix = ".debug"
            versionNameSuffix = "-DEBUG"
        }
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
            signingConfig = signingConfigs.getByName("release")
        }
        create("staging") {
            initWith(getByName("debug"))
            applicationIdSuffix = ".staging"
        }
    }
}

What build type controls: debuggability, minification, signing config, application ID suffix, version name suffix.

Under the hood

applicationIdSuffix does not just change the installed package name — AGP appends it to the applicationId that gets written into the merged AndroidManifest.xml and the final DEX/resource table, which is what makes two build types installable on the same device as distinct apps. isDebuggable = true flips the android:debuggable manifest flag, which ART honors by disabling certain JIT/AOT optimizations and allowing a debugger to attach (JDWP). isMinifyEnabled = true inserts the R8 task into the variant's task chain between compilation and DEX, and signingConfig selects which key AGP uses in the apksigner/zipalign step that produces the final signed artifact.

Product Flavors

🎤 Say it out loud (~30–45s): "A product flavor controls what goes into the build — different endpoints, branding, or feature sets — like a free vs paid tier, or prod vs staging. Flavors live in dimensions, and AGP produces the Cartesian product: every combination of one flavor per dimension, crossed with each build type, becomes a variant. The gotcha is variant explosion — three dimensions of two flavors each is eight combos times two build types equals sixteen variants — and that library modules need missingDimensionStrategy if they don't declare every dimension the app does."

Definition: A product flavor controls what is in the build — different API endpoints, feature sets, or branding for different market segments.

android {
    flavorDimensions += listOf("environment", "payment")

    productFlavors {
        create("prod") {
            dimension = "environment"
            buildConfigField("String", "BASE_URL", "\"https://api.zocdoc.com\"")
        }
        create("staging") {
            dimension = "environment"
            buildConfigField("String", "BASE_URL", "\"https://staging.api.zocdoc.com\"")
            applicationIdSuffix = ".staging"
        }
        create("free") {
            dimension = "payment"
        }
        create("paid") {
            dimension = "payment"
        }
    }
}

Flavor dimensions: When multiple dimensions exist, every combination of one flavor per dimension × each build type creates a variant: prodFreeDebug, prodFreeRelease, stagingPaidDebug, etc.

Under the hood

buildConfigField causes AGP to generate a BuildConfig.java per variant during the generate{Variant}BuildConfig task; each field becomes a public static final constant compiled into bytecode, so BuildConfig.BASE_URL is resolved at compile time, not read from a file at runtime. Flavor resolution is implemented through Gradle's variant-aware dependency management: each variant publishes a set of attributes (the flavor of each dimension plus the build type), and when :app depends on a library, Gradle's attribute-matching engine selects the library variant whose attributes match. missingDimensionStrategy supplies a default attribute value for a dimension the library never declared, which is why its absence produces No matching variant of project :core found — the matcher has an unsatisfiable attribute.

Build Variants

🎤 Say it out loud (~30–45s): "A build variant is exactly one flavor combination plus one build type — stagingPaidDebug, say — and AGP generates a dedicated source set, BuildConfig, output artifact, and full task chain for each. What's worth knowing is how sources merge: AGP layers variant-specific over build-type over flavor over main, with higher priority winning. That layering is what lets you, for example, swap in a fake network module just for debug without touching production code."

A build variant is one flavor combination plus one build type. Gradle creates a variant-specific source set, output APK/AAB, and compile/assemble tasks for each combination.

Variant matrix (2 env flavors × 2 payment flavors × 2 build types = 8 variants):
  prodFreeDebug
  prodFreeRelease
  prodPaidDebug
  prodPaidRelease
  stagingFreeDebug
  ...

How flavors work under the hood

  1. AGP creates a SourceSet for each flavor, each build type, and each combination.
  2. Source sets are merged in priority order: buildType > flavor > main.
  3. Resources, manifests, and Java/Kotlin sources from higher-priority sets override lower ones.
  4. BuildConfig fields are generated per variant.

Under the hood

For each variant AGP builds a merged view from the contributing source sets and feeds it to the compilers. Java/Kotlin sources from different source sets are additive — they're concatenated into one compilation unit, so two source sets defining the same fully-qualified class is a duplicate-class compile error, not an override. Resources, by contrast, are merged by the merge{Variant}Resources task: it walks source sets in priority order and the highest-priority definition of a given name+type wins, silently shadowing lower ones (a same-priority duplicate is a hard error). Manifests are combined by the manifest merger using node markers and tools: rules. Because every variant gets its own compile/dex/package task chain keyed by the merged inputs, adding a flavor dimension multiplies the number of task chains Gradle must configure and potentially execute — that's the literal source of variant-count build-time growth.

Trade-offs

  • Each additional flavor dimension multiplies the variant count — 3 dimensions × 2 flavors each = 8 combos × 2 build types = 16 variants. Build times grow.
  • Use missingDimensionStrategy in library modules that don't have all flavor dimensions to tell AGP which flavor to fall back to.

Failure modes

  • Forgot to add missingDimensionStrategy in a library module → No matching variant of project :core found build error.
  • Resource conflicts when two source sets define the same resource name with conflicting values — AGP merge picks highest priority silently, which can cause subtle runtime differences.

Source Sets

🎤 Say it out loud (~30–45s): "A source set is just a named bundle of source directories — Kotlin/Java, res, assets, and a manifest — tied to a variant or one of its components. Android gives you main plus one per build type, per flavor, and per combination, and they merge by priority: variant-specific beats build-type beats flavor beats main. The practical use is injecting different code per variant — a fake NetworkModule in debug/, the real google-services.json in release/ — and the gotcha is that for code a duplicate class across source sets is an error, while for resources the higher-priority one just silently wins."

Definition: A source set is a named collection of source directories — Java/Kotlin, resources, assets, and manifest — associated with a specific variant or one of its components.

Default source set layout

app/src/
  main/           ← base source set
    java/
    kotlin/
    res/
    assets/
    AndroidManifest.xml
  debug/          ← debug build type source set
  release/        ← release build type source set
  prod/           ← prod flavor source set
  staging/        ← staging flavor source set
  prodDebug/      ← prod+debug combined source set

Custom source set paths

android {
    sourceSets {
        getByName("main") {
            java.srcDirs("src/main/kotlin", "src/generated/kotlin")
            res.srcDirs("src/main/res", "src/main/res-overrides")
        }
    }
}

Priority (highest wins)

variant-specific > build-type > flavor > main

For resources, duplicate resource names at the same priority level are a build error. At different priority levels, the higher one wins silently.

Under the hood

A source set is represented by AGP as an AndroidSourceSet object holding AndroidSourceDirectorySets (one each for java, kotlin, res, assets, manifest, jniLibs, etc.) — these are just configurable lists of directories, which is why srcDirs(...) can point them anywhere. The directory naming convention (debug/, prodDebug/) is pure convention: AGP derives the expected folder names from the variant's build type and flavor names and registers those paths automatically; renaming a flavor renames the expected directory. At build time the resolved per-variant set is the ordered concatenation of every contributing source set, and the priority ordering you see is literally the order in which those directories are presented to the resource merger and prepended to the compiler's source roots. Nothing physically moves on disk — the merge is a virtual, in-memory composition done by the relevant merge*/compile* task.

Use cases

  • Put mock NetworkModule.kt in debug/ so debug builds wire a fake API.
  • Put real google-services.json in release/ and a dummy one in debug/.
  • Override strings/drawables per flavor for white-labeling.

Dependency Configurations

implementation

🎤 Say it out loud (~30–45s): "implementation puts a dependency on this module's own compile classpath but hides it from consumers — they see my public ABI, not my internal Retrofit dependency. The big payoff is incremental compilation: if Retrofit changes internally but my module's public API doesn't, Gradle won't recompile any downstream module. That's why the default advice is implementation everywhere and only reach for api when a type genuinely leaks into your public signatures."

Definition: The dependency is on the compile classpath of this module only — it is not exposed to consumers of this module.

dependencies {
    implementation("com.squareup.retrofit2:retrofit:2.9.0")
}

How it works: Consumers of this module see the compiled ABI (public API), but Retrofit is hidden from their compile classpath. Consumers can still use Retrofit at runtime if they declare it themselves.

Key benefit: If Retrofit changes internally but the module's own public API doesn't change, Gradle will NOT recompile downstream modules. This is the primary mechanism for incremental compilation gains in a multi-module project.

Under the hood

The distinction is realized through Gradle's outgoing-variant configurations. Every module publishes two relevant configurations: apiElements (consumed at compile time by downstream modules) and runtimeElements (consumed at runtime). An implementation dependency is added to the implementation bucket, which feeds only runtimeElements — it never appears in apiElements, so it's literally absent from the consumer's compile classpath. On top of that, Gradle tracks the ABI fingerprint (public method/field signatures) of upstream modules; the Kotlin/Java incremental compiler skips recompiling a consumer when an upstream change doesn't alter that ABI. Since an implementation dependency's internals can't be part of your ABI (consumers can't reference them), changes there can't trigger downstream recompilation.

module :core:network
  ├─ apiElements      → exposed at compile time to consumers
  └─ runtimeElements  → exposed at runtime
implementation dep ─▶ runtimeElements only  (hidden from consumer compile classpath)
api dep            ─▶ apiElements + runtimeElements (leaks to consumers)

api

🎤 Say it out loud (~30–45s): "api is like implementation but it transitively exposes the dependency to consumers — anyone depending on my module gets it on their compile classpath automatically. You only want this when the dependency's types actually appear in your public API signatures, like returning an OkHttpClient. The cost interviewers want you to name is the recompile cascade: change an api dependency and every downstream module recompiles, so over-using api silently erodes the whole point of modularization."

Definition: The dependency is on the compile classpath of this module and is transitively exposed to all consumers.

// In :core:network
dependencies {
    api("com.squareup.okhttp3:okhttp:4.12.0") // OkHttp types leak into consumer APIs
}

How it works: Any module depending on :core:network sees OkHttp on its compile classpath automatically. If OkHttp updates, Gradle must recompile all downstream modules.

When to use api

Use api only when the dependency's types appear in the module's own public API signatures (method parameters, return types, public fields). If you expose OkHttpClient in a public function, consumers need it on their classpath to compile.

Under the hood

api dependencies are placed in the api bucket, which Gradle wires into both apiElements and runtimeElements of the publishing module. When a consumer resolves its compile classpath, Gradle transitively pulls everything from upstream apiElements, so OkHttp's types are present and resolvable. The recompile cascade follows from ABI tracking: because an api dependency's types can legally appear in your public signatures, a change to that dependency can change your module's effective ABI, so Gradle must conservatively assume downstream consumers may be affected and recompile them. This transitivity is also what pollutes consumer classpaths — they can now accidentally import okhttp3.* even if they never declared OkHttp.

compileOnly

🎤 Say it out loud (~30–45s): "compileOnly puts a dependency on the compile classpath but does not package it into the output — perfect for annotations like javax.inject that are only needed at compile time, or APIs the platform itself provides at runtime, which is exactly how android.jar is wired. The trap: if you mark something compileOnly whose classes are actually needed at runtime, you'll compile fine and then crash with NoClassDefFoundError once you hit that code path on device."

Definition: On the compile classpath but not packaged into the output. Used for compile-time annotations or APIs that the platform provides at runtime.

dependencies {
    compileOnly("javax.annotation:javax.annotation-api:1.3.2")
    compileOnly("com.google.dagger:dagger:2.51") // when using kapt for code gen only
}

Android use cases: javax.inject annotations, provided annotations for annotation processors, APIs available on Android platform (android.jar is automatically compileOnly).

Under the hood

compileOnly artifacts are added to the compileClasspath configuration but deliberately excluded from runtimeClasspath, so the DEX/packaging step never sees them and they don't ship in the APK. This works for annotations because many have @Retention(SOURCE) or CLASS retention — they're consumed by the compiler/annotation processor and either discarded or left only as metadata, never needed by the running VM. android.jar is the canonical case: AGP adds it as a bootclasspath-style compile-only dependency so your code can reference android.app.Activity, but the actual implementation lives in the framework on the device. The failure mode is direct: a compileOnly library's class is absent from runtimeClasspath, so the class loader (ART's PathClassLoader walking the DEX files) can't find it, and the first reference throws NoClassDefFoundError/ClassNotFoundException.

Failure mode: If you compileOnly a library whose classes are needed at runtime, you get ClassNotFoundException or NoClassDefFoundError at runtime.

runtimeOnly

🎤 Say it out loud (~30–45s): "runtimeOnly is the mirror image of compileOnly — the dependency is packaged into the output but kept off the compile classpath, so you can't reference its types directly in code. It's for pluggable implementations chosen at runtime, like an SLF4J logging backend or a JDBC driver. It's pretty rare in Android app modules and shows up more in plain JVM modules where you wire the implementation via service loading or reflection."

Definition: Not on the compile classpath, but packaged into the output. Used for implementations selected at runtime — SLF4J backends, JDBC drivers, and similar.

dependencies {
    runtimeOnly("org.slf4j:slf4j-android:1.7.36")
}

Rare in Android app modules, more common in JVM modules.

Under the hood

runtimeOnly adds the artifact to runtimeClasspath (and thus into the packaged output) but excludes it from compileClasspath, so the compiler can't see the types — that's intentional, because the consumer is expected to discover the implementation indirectly. The common mechanism is java.util.ServiceLoader: a façade like SLF4J calls ServiceLoader.load(...), which reads META-INF/services/ provider files from whatever is on the runtime classpath and instantiates the backend by reflection. Because nothing in your source references the backend directly, keeping it off the compile classpath prevents accidental hard coupling while still shipping the bytecode so the loader can find it at runtime.

kapt

🎤 Say it out loud (~30–45s): "kapt runs Java annotation processors against Kotlin code, but Java APs can't read Kotlin directly, so kapt first generates Java stubs — signature-only representations of your Kotlin classes — runs the processors against those, then feeds the generated sources back for a final Kotlin compile. That stub-generation round is the expensive part and it doesn't play well with incremental compilation, which is the whole reason the ecosystem moved to KSP."

Definition: Runs an annotation processor through the Kotlin Annotation Processing Tool. The processor runs after Kotlin compilation and generates Java/Kotlin source files.

plugins {
    id("kotlin-kapt")
}
dependencies {
    implementation("com.google.dagger:dagger:2.51")
    kapt("com.google.dagger:dagger-compiler:2.51")
}

How it works: KAPT creates stubs (Java-compatible representation of Kotlin classes), runs Java annotation processors against those stubs, then feeds the generated sources back into the Kotlin compiler. Two compilation rounds: stubs + Java AP → generated sources → final Kotlin compile.

Under the hood

KAPT exists because the standard javax.annotation.processing API (and javax.lang.model mirror types) only understands Java source/elements, not Kotlin. KAPT runs the Kotlin compiler in a special mode that emits Java stub files — classes with correct signatures but empty/throwing method bodies — then launches a real javac annotation-processing round over those stubs so existing processors like Dagger's see familiar TypeElement/ExecutableElement models. Generated sources are collected and then compiled in the final Kotlin/Java passes. The cost is twofold: stub generation requires fully resolving and re-emitting your Kotlin as Java for the whole compilation unit, and because the AP round operates on regenerated stubs, KAPT's incremental support is coarse — small Kotlin edits often invalidate the stubs and force broad reprocessing.

Kotlin sources ─▶ KAPT stub gen ─▶ Java stubs ─▶ javac annotation processing ─▶ generated sources
                                                                                       │
                          final compile ◀──────────────────────────────────────────────┘

Performance cost: Stub generation is expensive. KAPT cannot benefit from Kotlin incremental compilation as effectively as KSP.

ksp

🎤 Say it out loud (~30–45s): "KSP is a first-class Kotlin compiler plugin API for annotation processing — it operates directly on Kotlin's symbol/resolution model with no Java stub-generation step, which is why it's roughly twice as fast as kapt and supports proper incremental processing. Room, Moshi, and Hilt all ship KSP processors now. The migration nuance is that KSP gives processor authors a Kotlin-native API, so each library had to write a dedicated KSP processor — you can't just point kapt config at it."

Definition: Kotlin Symbol Processing is a first-class Kotlin compiler plugin API for building annotation processors that work directly on the Kotlin IR, with no stub generation step.

plugins {
    id("com.google.devtools.ksp") version "1.9.24-1.0.20"
}
dependencies {
    implementation("com.google.dagger:hilt-android:2.51")
    ksp("com.google.dagger:hilt-android-compiler:2.51")
    implementation("androidx.room:room-runtime:2.6.1")
    ksp("androidx.room:room-compiler:2.6.1")
}

Under the hood

KSP runs as a Kotlin compiler plugin and exposes its own abstraction layer — KSClassDeclaration, KSFunctionDeclaration, Resolver — backed by the compiler's already-resolved symbol table, so processors read Kotlin declarations (nullability, suspend, properties, default args) without any Java stub round. Processors implement SymbolProcessor and run in rounds: each round returns the symbols it couldn't yet process (deferred) and can generate new files via a CodeGenerator, which records the originating source files. That dependency tracking is what enables true incremental processing — when a source file changes, KSP only reprocesses the symbols and regenerates the outputs whose recorded dependencies were touched, instead of re-running over rebuilt stubs. The net effect is fewer compiler invocations and finer-grained invalidation, hence the roughly 2× speedup over KAPT.

KSP advantages over KAPT: Up to 2× faster, supports incremental processing, no stub generation step, works natively with Kotlin types. Room, Moshi, Hilt all support KSP.

Under the hood

The catalog is not a runtime construct — it is consumed entirely at configuration time. When a build with a libs.versions.toml is present, Gradle parses the TOML and synthesizes a Java class (commonly LibrariesForLibs) whose methods correspond to your dependency aliases; the libs you type in the DSL is an instance of that generated extension registered on the project. Aliases with dashes/dots are split into a nested accessor tree, so retrofit-converter-gson becomes libs.retrofit.converter.gson returning a Provider<MinimalExternalModuleDependency>. Because the accessors are generated from the TOML, a typo can only fail at configuration time (unresolved symbol) — it can never reach execution. The catalog model itself is also a build input, so changing a version in the TOML invalidates the relevant configuration/cache entries.

Convention Plugins

🎤 Say it out loud (~30–45s): "A convention plugin is just a regular Gradle plugin that bundles the build configuration I'd otherwise copy-paste into every module — compileSdk, Java/JVM target, lint, common dependencies. I write it once in buildSrc or a :build-logic included build and apply it by id, so bumping compileSdk across 50 modules is a one-line change. The senior nuance is where I put it: buildSrc is auto-discovered but sits on every module's classpath, so touching it invalidates the whole project; an included build is more setup but only recompiles affected modules and is fully configuration-cache friendly, so for a large repo I reach for :build-logic."

Definition: A convention plugin is a Gradle plugin — typically written in buildSrc or an included build (:build-logic) — that encapsulates common build configuration shared across multiple modules.

The problem they solve

Without convention plugins, each module's build.gradle.kts repeats the same boilerplate:

// Repeated in every module:
plugins { id("com.android.library"); id("org.jetbrains.kotlin.android") }
android {
    compileSdk = 34
    defaultConfig { minSdk = 21 }
    compileOptions { sourceCompatibility = JavaVersion.VERSION_17; targetCompatibility = JavaVersion.VERSION_17 }
    kotlinOptions { jvmTarget = "17" }
}

In a 50-module project, updating compileSdk from 34 to 35 means editing 50 files.

Solution: convention plugin in buildSrc

// buildSrc/src/main/kotlin/android-library-convention.gradle.kts
plugins {
    id("com.android.library")
    id("org.jetbrains.kotlin.android")
}

android {
    compileSdk = 35
    defaultConfig { minSdk = 21 }
    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_17
        targetCompatibility = JavaVersion.VERSION_17
    }
    kotlinOptions { jvmTarget = "17" }
}
// Any library module's build.gradle.kts
plugins {
    id("android-library-convention") // ← one line replaces 15
}

dependencies {
    implementation(libs.retrofit.core) // module-specific deps still here
}

Why convention plugins at a senior level

  1. DRY: There is one place to update compileSdk, the Java version, and lint rules — change it once and every module picks it up.
  2. Enforce standards: Lint checks, detekt, and code coverage thresholds are applied uniformly across every module without relying on copy-paste discipline.
  3. Composability: You layer multiple plugins — android-library-convention plus hilt-convention plus testing-convention — so each module declares only what it needs.
  4. Testable: Convention plugins can themselves have unit tests, just like any other Gradle code.

Failure modes

  • buildSrc changes invalidate the entire project's configuration cache → every module recompiles. For active development on build logic, prefer :build-logic.
  • Version catalog not accessible in buildSrc plugins without explicitly wiring versionCatalogs extensions.

Under the hood

A precompiled script plugin (android-library-convention.gradle.kts) is compiled by the kotlin-dsl plugin into a real Plugin<Project> class before any consuming build runs — the file name (with dots) becomes the plugin id. So applying id("android-library-convention") is identical to applying a hand-written class … : Plugin<Project>: Gradle instantiates it and calls apply(project), which mutates that project's ExtensionContainer (e.g., the android {} extension) and DependencyHandler. The buildSrc-vs-included-build cost difference is a classpath fact: buildSrc's output jar is injected into the build-script classpath of every project, so any change there changes that shared classpath and Gradle conservatively invalidates all task and configuration-cache entries. An includeBuild("build-logic") is a separate Gradle build whose published plugin artifacts are resolved per-consumer, so its task graph and outputs are tracked independently and only the modules that actually apply the changed plugin recompile.

buildSrc change ──▶ shared buildscript classpath changes ──▶ ALL projects invalidated
:build-logic change ──▶ only consumers of the changed plugin recompile

Interview Angles 12.1

Q: api vs implementation — explain the difference and when to use each.

"implementation keeps a dependency on the compile classpath of the declaring module only — consumers cannot see or use it at compile time. api exposes the dependency transitively to all consumers, so it lands on their compile classpath too.

The rule I follow is: start with implementation everywhere, and only switch to api when the dependency's types actually appear in the module's public API — method signatures, return types, public fields. If my module has a fun createClient(): OkHttpClient, then consumers need OkHttp on their classpath to compile their call sites, and api is correct there.

The performance implication is the critical part. When a dependency declared with api changes, Gradle has to recompile every downstream module. implementation restricts that cascade to just the module where the change happened. In a 50-module project, one accidental api on a low-level library can mean the entire project recompiles every time that library updates — so the default should always be implementation."

Q: How do product flavors work?

"Flavors let you produce multiple variants of the app from a single codebase. You organize them into dimensions — say environment and tier — and AGP takes every combination: one flavor per dimension times each build type gives you your full variant matrix.

Each flavor gets its own source set directory, and those sets overlay each other in a fixed priority order: variant-specific overrides build type, build type overrides flavor, flavor overrides main. So you can drop a file into the prod/ source set and it will shadow the main/ version only for prod builds. BuildConfig fields declared in a flavor are baked into the generated BuildConfig.java at compile time, so each variant gets its own constants. Flavor-specific dependencies work the same way — prodImplementation(\"…\") only wires that dependency for the prod flavor."

12.2 Build Performance

Configuration Cache

🎤 Say it out loud (~30–45s): "The configuration cache serializes the result of the configuration phase — the fully built task graph — to disk, so on a warm run Gradle skips re-evaluating every build script and jumps straight to execution. On a big modular project that's 10–30 seconds saved per invocation, and it stacks with the build cache. The catch is it imposes a strict contract: tasks can't touch Project or other live build state at execution time, and they must capture only serializable inputs — so non-compliant plugins are the usual blocker, which is why I run with problems=warn first and read the HTML report before flipping it to fail."

Definition: Gradle's configuration cache stores the result of the configuration phase — the task graph construction — to disk so it can be reused on subsequent builds without re-evaluating build scripts.

How it works

Without configuration cache:

  1. Gradle evaluates every build.gradle.kts (configuration phase).
  2. Constructs the task graph.
  3. Executes selected tasks.

Steps 1+2 happen on every build invocation, even ./gradlew tasks. For a 50-module project, configuration can take 10–30 seconds alone.

With configuration cache enabled, steps 1+2 are serialized to .gradle/configuration-cache/ on the first run. Subsequent runs deserialize the cached task graph and jump straight to execution — saving the full configuration time.

Enabling

// gradle.properties
org.gradle.configuration-cache=true
org.gradle.configuration-cache.problems=warn  # or "fail" for strict mode

Or per-run: ./gradlew assembleDebug --configuration-cache

Requirements and constraints

Configuration cache imposes strict rules on tasks: they cannot access Project at execution time (only at configuration time), must not capture non-serializable types, must declare all inputs/outputs. Many third-party plugins violate these rules.

AGP compatibility: AGP 8.1+ has full configuration cache support. Most Android-first plugins (Firebase App Distribution, Play Publisher) reached full compatibility in 2023–2024.

Trade-offs

Pro Con
Skips 10–30s configuration phase on warm runsFirst run is slightly slower (serialization)
Works with --build-cache for full reuseIncompatible plugins cause build failures
Dramatically speeds up CI on repeated runsSerialization/deserialization adds overhead on tiny projects

Failure modes

  • Plugin captures Project reference in a task action → Cannot serialize object of type 'DefaultProject' error.
  • Dynamic build script logic that reads environment variables at execution time → configuration cache considers these undeclared inputs, may produce stale results.
  • Workaround for incompatible plugins: --configuration-cache-problems=warn to identify, then report to plugin maintainers.

Debugging

Run ./gradlew assembleDebug --configuration-cache and examine the HTML report at build/reports/configuration-cache/ — it lists all incompatibilities.

Under the hood

The cache key is a fingerprint of everything that influenced configuration: the requested task names, the build-script classpath, the values of read system properties and environment variables, and the content of files read during configuration. If any of those change on a later run, Gradle gets a cache miss and re-runs configuration; this is exactly why reading an env var at execution time is unsafe — it was never recorded as a configuration input. On a hit, Gradle deserializes a graph of Task instances with their input/output state already populated and proceeds directly to execution scheduling, skipping script evaluation entirely. The serializer is what enforces the contract: it walks each task's captured fields, and a live Project (or other non-serializable build service) fails the graph because the whole point is that no configuration-time-only state may survive into the execution of a cached graph. The cache also enables eager parallelism — once the graph is materialized, Gradle can begin scheduling work without waiting on script evaluation.

inputs: [task requests] + [buildscript classpath] + [env vars/sysprops read] + [files read]
        └──── hashed ────▶ cache key
hit  ▶ deserialize Task graph (inputs/outputs restored) ▶ execute
miss ▶ run configuration phase ▶ serialize graph ▶ store under key

Build Cache

🎤 Say it out loud (~30–45s): "The build cache keys each task's outputs by a hash of its inputs — task type, input files, classpath, properties. If that key already exists locally or on a remote node, Gradle copies the outputs in instead of running the task. The thing people conflate is UP-TO-DATE versus build cache: UP-TO-DATE only asks whether this checkout's outputs are still current, whereas the build cache lets you reuse outputs across machines and even after a clean. The failure mode to watch is non-deterministic outputs — embedded timestamps or absolute paths — because those poison the key and you get misses on every build."

Definition: The build cache stores task outputs keyed by a hash of the task's inputs. If the inputs hash to a key already in the cache, Gradle fetches the outputs from cache instead of re-executing the task.

How it works

Gradle computes a cache key as a hash of the task class, task inputs, and classpath. If that key exists in the local or remote cache, outputs are restored. This is different from UP-TO-DATE: UP-TO-DATE checks whether the outputs on disk are unchanged; the build cache allows reuse across machines and clean checkouts.

Local vs Remote cache

  • Local cache: ~/.gradle/caches/build-cache/ on developer machines. Survives ./gradlew clean.
  • Remote cache: HTTP endpoint (e.g., Gradle Enterprise, self-hosted gradle-cache-node). Enables CI-to-developer and PR-to-PR cache reuse.

Enabling

// gradle.properties
org.gradle.caching=true

Remote cache configuration:

// settings.gradle.kts
buildCache {
    remote(HttpBuildCache::class) {
        url = uri("https://gradle-cache.internal.example.com/cache/")
        isPush = System.getenv("CI") != null  // only CI pushes to remote
    }
}

Android-specific cacheable tasks

Most compilation tasks (compileKotlin, compileJava, aapt2Compile) are cache-enabled in AGP 7+. Resource merging and manifest merging are partially cacheable.

Trade-offs

Pro Con
Dramatic speed-up after cleanRemote cache infra cost
Cross-machine reuseCache poisoning risk if key collision (extremely rare)
Works with --no-daemon on CIIncremental compilation often already handles warm local builds

Failure modes

  • Non-deterministic task outputs (timestamps embedded in outputs, random UUIDs) → cache misses on every run. Use --rerun-tasks + ./gradlew help --scan to diagnose.
  • Kotlin compiler embeds absolute paths in some metadata → cache misses across machines with different workspace paths. Mitigated in recent KGP versions via path normalization.
  • Tasks with @CacheableTask but undeclared path-sensitive inputs → false cache hits → stale outputs.

Under the hood

Only tasks annotated @CacheableTask participate, and each input property carries normalization metadata (@PathSensitive, @InputFiles, etc.) that tells Gradle how to hash it. The build cache key is a Merkle-style hash: Gradle hashes the task implementation (class + its classpath), then each input — for files it hashes content under the declared path sensitivity, so @PathSensitive(RELATIVE) deliberately ignores absolute locations and lets two machines with different workspace roots produce the same key. The combined hash is the cache entry's name; the entry itself is a tarball of the declared @OutputFile/@OutputDirectory artifacts. A hit simply unpacks that tarball into the output locations — no task action runs. This is why embedded timestamps and unnormalized absolute paths are fatal: they change the hashed content of an input (or are baked into an output that becomes a future input), so the key never repeats. UP-TO-DATE is a cheaper, local-only check that compares the current input/output snapshot against the last build's snapshot in the project's .gradle state — it never consults the shared store.

key = hash( taskType+classpath ) ⊕ hash( each input @ declared PathSensitivity )
entry = tar( @OutputFile / @OutputDirectory )
hit  ▶ untar outputs into place (action skipped)
miss ▶ run action ▶ tar outputs ▶ store under key (local and/or remote)

Parallel Builds

🎤 Say it out loud (~30–45s): "Parallel builds let Gradle run tasks that have no dependency between them on separate worker threads at the same time. In a modular Android project the win is mostly cross-module — :feature:search and :feature:appointments can compile concurrently once their shared :core deps are built. The honest caveat is that :app sits at the bottom of the graph and has to wait for everything above it, so deep or skinny dependency chains cap your speedup no matter how many cores you have — and bumping org.gradle.workers.max too high on a RAM-constrained CI box just trades parallelism for OOM kills."

Definition: With parallel builds enabled, Gradle executes independent tasks across multiple worker threads simultaneously.

Enabling

// gradle.properties
org.gradle.parallel=true
org.gradle.workers.max=8  # default: number of CPU cores

How it works

Gradle builds the task execution graph and identifies tasks with no dependency relationship. It dispatches these to a worker pool. In a multi-module project, if :feature:search and :feature:appointments both depend only on :core:network (already built), they compile in parallel.

Under the hood

Gradle models the build as a DAG of tasks and acquires/releases resource leases before running each one: a global worker lease (bounded by org.gradle.workers.max) plus a project lock. Historically a project was locked while one of its tasks ran, so intra-project parallelism was limited and most concurrency came from running tasks in different projects at once — which is why modularization, not single-module work, unlocks the speedup. The Worker API goes further by letting a single task fan its own work units out to the shared worker pool (in-process, or in a forked daemon for classpath isolation). The scheduler is greedy over the DAG: a task becomes eligible the moment all its dependency edges are satisfied and it can acquire the needed leases, so a long pole like :app — which depends transitively on everything — serializes the tail of the build regardless of free cores. Each worker consumes heap, so total memory scales with maxWorkers; oversubscribing on a small CI box triggers GC thrash or OOM rather than faster builds.

DAG:  :core:network ─┬─▶ :feature:search ──────┐
                     └─▶ :feature:appointments ─┴─▶ :app   (long pole)
scheduler: run a task when (all deps done) AND (worker lease + project lock acquired)
workers bounded by org.gradle.workers.max ; each worker holds heap → OOM if oversubscribed

Android implications

  • Most benefit comes from parallel module compilation, not parallel tasks within a single module.
  • The :app module must wait for all its dependencies — it's the bottleneck. Deep dependency chains limit parallelism.
  • Annotation processors (KAPT) run serially per module; parallelism helps by running multiple modules' KAPT steps simultaneously.

Incremental Annotation Processing

🎤 Say it out loud (~30–45s): "Incremental annotation processing means a processor only re-runs against the files that changed instead of the whole source set — and processors declare their category as ISOLATING or AGGREGATING so Gradle knows how to scope that. The gotcha is that aggregation poisons the well: a single AGGREGATING processor, or one non-incremental processor in the module, forces a full reprocessing pass for everything in that module on any change, even a one-line comment edit. So when I'm optimizing build time I hunt for the one processor that's silently downgrading the whole module to the slow path."

Definition: Annotation processors that support incremental processing only re-run against the source files that changed, not against the entire source set.

How it works

An annotation processor declares itself as incremental (ISOLATING, AGGREGATING, or DYNAMIC):

  • ISOLATING: The processor output for file X depends only on file X. If X changes, only X is reprocessed. Most processors (Room entity processors, Dagger component processors) are isolating.
  • AGGREGATING: Output depends on multiple source files (e.g., a processor that generates a registry of all @Module classes). Any source change triggers full reprocessing.
  • DYNAMIC: Processor decides at runtime whether it's isolating or aggregating. Rare.

How to check

./gradlew :app:compileDebugKotlin --info 2>&1 | grep -i "incremental"
# Look for: "Annotation processor 'com.google.dagger.internal.codegen.ComponentProcessor' is 'ISOLATING'"
# vs: "not incremental" — this is the slow path

Under the hood

A processor opts in by writing a properties resource at META-INF/gradle/incremental.annotation.processors inside its jar, mapping each processor's fully-qualified class name to a category. At configuration/compile time Gradle reads that file; if any processor on the classpath is absent from it, Gradle treats the entire processing round as non-incremental. Gradle then tracks an origin relationship: for ISOLATING, it records that generated file G and its outputs originate from exactly one source file X, so it can delete G and re-run just X when X changes. For AGGREGATING, the processor is allowed to read any number of source files, so Gradle records that its outputs depend on the whole annotated set and re-runs it whenever any annotated element changes. Generated files are fingerprinted in the build's incremental state so stale outputs are pruned rather than left to cause duplicate-symbol errors.

ISOLATING:    edit X.kt  → delete outputs originating from X → reprocess X only
AGGREGATING:  edit X.kt  → reprocess all annotated sources (registry must be rebuilt)
not declared: edit X.kt  → whole module's annotation processing re-runs from scratch

Android implications

  • Hilt/Dagger: mostly isolating in recent versions. @Module aggregation is inherently aggregating.
  • Room: entity processing is isolating; DAO processing is often isolating.
  • Moshi: isolating.
  • Non-incremental processors force a full recompilation on every change — even a one-line comment edit.

Failure modes

  • A single non-incremental processor in the module forces full annotation processing for all processors in that module.
  • KAPT cannot do incremental processing as effectively as KSP because stub generation itself is not always incremental.

KSP vs KAPT

This is a high-frequency interview topic. Know it deeply.

KAPT: Kotlin Annotation Processing Tool

🎤 Say it out loud (~30–45s): "KAPT bolts the Java annotation-processing pipeline onto Kotlin by first generating Java stubs — signatures with no bodies — for every Kotlin class, then running the javac-based processors against those stubs, then feeding the generated code back for a real Kotlin compile. The killer cost is that stub generation can be 30 to 50 percent of compile time, and because stubs only approximate Kotlin, processors see java.lang.String instead of kotlin.String and lose precise nullability. It's now in maintenance mode, so I treat KAPT as legacy and migrate off it wherever a KSP processor exists."

How it works:

  1. Kotlin compiler runs a stub-generation pass: generates .java stubs for all Kotlin classes (method signatures, field declarations, no bodies).
  2. Java annotation processors run against the stubs using javac's AP infrastructure.
  3. Generated Java/Kotlin sources are fed back into the Kotlin compiler as additional sources.
  4. Full Kotlin compilation runs.

Problems with KAPT:

  • Stub generation is slow: For a large module, generating stubs can take as long as the actual compilation.
  • Two compilation rounds: Kotlin stubs → AP generates sources → Kotlin compiles generated sources.
  • Limited incrementality: Stubs don't encode enough information for fine-grained incremental processing.
  • Kotlin type fidelity: Stubs approximate Kotlin types as Java; processors see java.lang.String, not kotlin.String; nullability annotations are approximations.
  • Deprecated: Google has announced KAPT as maintenance-mode. KSP is the recommended path.

Under the hood

KAPT runs the Kotlin compiler frontend far enough to resolve declarations, then emits Java source stubs into a kaptStubs directory — each stub is a .java file with full type signatures but method bodies replaced by throw new RuntimeException("Stub!");. It then spins up javac configured purely as an annotation-processing host (-proc:only), with the stubs as the source path, so the processors run through the standard javax.annotation.processing.Processor SPI against javac's Elements/Types mirror — which is exactly why processors see erased, Java-flavored types and why round-based generation works. Generated sources are collected and handed back to kotlinc for the real compile. The two-frontend-pass structure (resolve-for-stubs, then compile-for-real) is the structural reason KAPT roughly doubles frontend work compared to a plain Kotlin compile.

.kt sources ──kotlinc frontend──▶ Java stubs (bodies = throw "Stub!")
                                      │
                                      ▼
                              javac -proc:only ──▶ generated .java/.kt
                                      │
                                      ▼
            .kt sources + generated ──kotlinc full compile──▶ .class

KSP: Kotlin Symbol Processing

🎤 Say it out loud (~30–45s): "KSP is a Kotlin compiler plugin that hands processors a structured view of the compiler's own symbol resolution — so instead of inspecting fake Java stubs, a SymbolProcessor walks KSClassDeclaration and KSFunctionDeclaration with full Kotlin fidelity: real nullability, extension functions, type aliases, value classes. There's no stub-generation pass, which is where most of the speedup comes from — typically up to 2x — and it has first-class incremental support because processors declare their symbol dependencies. The one nuance is that KSP deliberately exposes a lazy, resolution-on-demand API, so calling .resolve() on types eagerly can claw back some of the speed you came for."

How it works:

  • KSP is a Kotlin compiler plugin that exposes a structured API over the Kotlin compiler's symbol table (IR).
  • Processors implement SymbolProcessor and access KSDeclaration, KSClassDeclaration, KSFunctionDeclaration, etc. directly.
  • No stub generation step. The processor sees native Kotlin types with full nullability, extension functions, type aliases.
  • Incremental processing support built-in: processors declare which symbols they depend on; the KSP runtime only re-invokes them when those symbols change.

KSP advantages

Dimension KAPT KSP

IncrementalityLimitedFull (ISOLATING/AGGREGATING per processor)
Kotlin type fidelityApproximated via stubsNative (nullability, inline classes, etc.)
Multi-round processingSupported but slowSupported
Maintenance trajectoryDeprecated (maintenance mode)Active development, Google-endorsed

Under the hood

KSP registers as a kotlin-compiler-plugin and hooks the compiler's analysis phase via a SymbolProcessorProvider; it builds its own abstraction (Resolver, KSNode tree) on top of the compiler's binding context rather than exposing the raw IR or PSI. The API is intentionally lazy: a KSTypeReference is just a reference until you call .resolve(), which triggers actual type resolution — KSP tracks which symbols a processor touched during resolution to build the incremental dependency graph. That graph is what powers per-processor ISOLATING/AGGREGATING incrementality: KSP records, per round, the input sources each output was derived from, persists it across builds, and on the next build replays only the affected subset. Because it reads resolved Kotlin symbols directly, nullability, value/inline classes, variance, and type aliases survive intact — none of the lossy Java-mirror translation KAPT performs.

class MyProcessor(private val codeGen: CodeGenerator) : SymbolProcessor {
    override fun process(resolver: Resolver): List<KSAnnotated> {
        val symbols = resolver.getSymbolsWithAnnotation("com.x.MyAnn")
        // .resolve() here is what forces type resolution AND records the
        // incremental dependency on that symbol — overusing it costs speed
        symbols.filterIsInstance<KSClassDeclaration>().forEach { decl ->
            decl.getAllProperties().forEach { it.type.resolve() }
        }
        return symbols.filterNot { it.validate() }.toList() // deferred to next round
    }
}

Failure modes / gotchas

  • KSP and KAPT cannot both process the same annotation for the same library — if you add both kapt("room-compiler") and ksp("room-compiler"), Room generates duplicate files.
  • Processor written only for KAPT cannot be used with KSP without a KSP port by the library author.
  • KSP ksType.makeNotNullable() behavior can differ subtly from KAPT's stub behavior — test generated code after migration.

Modularization

🎤 Say it out loud (~30–45s): "Modularization splits the codebase into Gradle modules — typically a layered set of :feature and :core modules — so a change recompiles only the changed module and its dependents, sibling modules build in parallel, and unchanged modules get restored from the build cache. The two things an interviewer probes are dependency direction and granularity: features depend on core, never on each other, and you can absolutely over-modularize — two hundred tiny modules push so much work into Gradle's configuration phase that you lose the build-time win you were chasing. So I treat the module count as a tuning knob, not a 'more is better' axis."

Definition: Modularization means splitting the app's code into multiple Gradle modules — :core:*, :feature:*, :app — so each can compile independently, enabling parallel builds and scoped incremental recompilation.

Why modularization improves build time

  1. Incremental compilation scope: A change to :feature:search only recompiles :feature:search and its dependents — :feature:appointments and :core:network are untouched.
  2. Parallel compilation: Sibling modules that share a common dependency compile simultaneously once that dependency is built.
  3. Build cache reuse: Unchanged modules are restored from cache — local or remote — rather than recompiled from source.
  4. Annotation processing isolation: A slow ksp step in :feature:search no longer blocks :feature:appointments from compiling.

Module layering (typical large-app architecture)

:app                          ← Android application, DI wiring, navigation host
:feature:search               ← Search UI, ViewModel, Interactor
:feature:appointments
:feature:profile
:core:network                 ← Retrofit, OkHttp, base API config
:core:database                ← Room, DAOs, entities
:core:design                  ← Compose components, theme, tokens
:core:analytics               ← FEM, event models
:core:common                  ← Extension functions, utilities (no Android deps)

Dependency direction rule: Dependencies flow :feature:* → :core:* → :core:common. Feature modules never depend on other feature modules directly — shared logic lives in :core, and cross-feature navigation goes through contracts or interfaces.

Trade-offs

Pro Con
Faster incremental buildsSetup complexity
Enables parallel compilationHarder to refactor shared code
Feature isolationCircular dependency risk
Enables dynamic feature modulesNavigation contracts across modules

Under the hood

Gradle models the build as a directed acyclic graph of tasks; each module contributes tasks (:feature:search:compileDebugKotlin, etc.) with declared inputs and outputs, and Gradle topologically sorts them and runs independent branches concurrently up to org.gradle.workers.max. The reason implementation vs api matters here is the compile classpath: with implementation, a module's dependency is on the consumer's runtime classpath but not its compile classpath, so changing that transitive dependency's ABI does not invalidate the consumer's compile task — this is what prunes the recompilation cascade. The build cache keys each task by a hash of its inputs (source fingerprints, classpath ABI hashes, compiler args); an unchanged module's task produces the same key and its outputs are restored from the local or remote cache instead of executing. The flip side is that every module must be evaluated during the configuration phase to build the task graph, which is why module count trades off against configuration time.

configuration phase: evaluate all build.gradle → build task DAG  (cost ∝ module count)
execution phase:     run task DAG, independent branches in parallel
                     each task: inputs hash → cache key → HIT (restore) or MISS (execute)
ABI change in :core:network (api dep)  → invalidates downstream compile tasks
ABI change behind 'implementation'     → downstream compile tasks stay UP-TO-DATE

Failure modes

  • Over-modularization: 200 tiny modules → Gradle configuration time dominates. Sweet spot is roughly 20–80 modules for a large app.
  • All features depend on a single fat :core module → changes to :core trigger full rebuild. Split :core further.
  • Circular dependencies: :feature:A depends on :feature:B which depends on :feature:A → build error. Resolve by extracting shared contract to :core.

Avoiding Unnecessary Dependencies

🎤 Say it out loud (~30–45s): "The core idea is to declare only what you use and at the narrowest scope — implementation instead of api, test libs in testImplementation, and compileOnly for annotation-only artifacts that don't need to ship. The build-time reason this matters is the ABI cascade: an api dependency leaks onto consumers' compile classpaths, so a version bump anywhere in that chain invalidates everyone's compile tasks. The nuance interviewers like is that api isn't always wrong — if a module's public types genuinely expose another library's types in their signatures, you need api; the skill is keeping that surface deliberately small."

Definition: Keeping dependencies lean means only declaring what you actually need and always using the narrowest scope — implementation over api, and test-only dependencies in testImplementation.

Practical steps

  1. Audit with ./gradlew :app:dependencies: Look for transitive leaks (unnecessary api declarations).
  2. Remove unused transitive api: Change to implementation.
  3. Move test dependencies: implementation("mockk") → testImplementation("mockk").
  4. Use compileOnly for annotation-only libraries: javax.inject doesn't need to ship.
  5. Avoid fat utility modules: Split :core:utils into :core:date, :core:string, :core:network-utils so only needed pieces are compiled.

Build time impact

Each dependency added to the compile classpath increases:

  • Classpath scanning time during annotation processing
  • Kotlin type resolution time
  • Risk of classpath conflicts

Dependency exclusion

    implementation("com.example:library:1.0") {
        exclude(group = "org.json", module = "json") // already provided by Android
    }
}

Under the hood

Gradle resolves dependencies per configuration — implementation, api, compileOnly, runtimeOnly are configurations with different visibility. The Java/Android plugins wire these so that api dependencies are exposed transitively to consumers via the apiElements outgoing variant (landing on the consumer's compile classpath), while implementation flows only through runtimeElements (runtime classpath, not compile). Gradle also computes a compile-avoidance ABI hash: when a dependency changes, Gradle compares the new ABI (public signatures) against the cached one; if only method bodies changed, downstream compile tasks stay UP-TO-DATE. But that avoidance only protects you for dependencies that aren't on the compile classpath in the first place — which is precisely why api is costly: it puts the dependency where any ABI change forces recompilation of every consumer. compileOnly keeps the artifact off the runtime classpath entirely (it won't be packaged into the APK/DEX), which is correct for annotation/source-only libraries like javax.inject.

api dep:         producer apiElements  ──▶ consumer COMPILE classpath  (ABI change → recompile consumers)
implementation:  producer runtimeElements ─▶ consumer RUNTIME classpath (ABI change → consumers stay UP-TO-DATE)
compileOnly:     consumer COMPILE classpath only, NOT packaged into DEX

Gradle Profiling

🎤 Say it out loud (~30–45s): "Gradle profiling is about measuring before optimizing — I never guess at build-time fixes. My go-to is a build scan, which gives a per-task timeline and breaks every task into UP-TO-DATE, cache-hit, or executed, so I can see whether time is going to configuration, kapt, resource merging, or dexing. For rigorous before/after comparisons I use the gradle-profiler to run repeated warm and cold scenarios and get statistically meaningful numbers, because a single build is too noisy — daemon warm-up and OS file caching alone can swing a run by seconds."

Definition: Gradle profiling is the practice of using tools and techniques to measure exactly where build time is being spent before you try to fix it.

--scan (Gradle Build Scan)

./gradlew assembleDebug --scan

Uploads a build profile to scans.gradle.com. Shows timeline of task execution, which tasks were slowest, UP-TO-DATE vs cache-hit vs executed breakdown, dependency resolution time, and memory usage. Essential for diagnosing build performance regressions.

--profile

./gradlew assembleDebug --profile

Generates an HTML report at build/reports/profile/. Lighter-weight than --scan, stays local. Shows configuration time per project and execution time per task.

--benchmark with the Gradle Profiler

The Gradle Profiler can run multiple warm/cold build scenarios and produce statistical results. Useful for measuring the impact of configuration changes (e.g., "does enabling configuration cache save 8 seconds?").

gradle-profiler --benchmark --project-dir . --scenario-file scenarios.conf

What to look for

  1. Long configuration time → convention plugins or buildSrc changes → consider :build-logic included build.
  2. kapt tasks dominating → migrate to KSP.
  3. mergeDebugResources slow → many resource directories, complex resource merging from libraries.
  4. Module X always full-recompile → undeclared task inputs, or api leaking a frequently-changing dependency.
  5. dexBuilder slow → desugaring for low minSdk. Increase minSdk for debug builds to 21+ to skip desugaring.
// Speed up debug builds by skipping desugaring
android {
    defaultConfig { minSdk = 21 }
    buildTypes {
        debug {
            // no minSdk override needed if defaultConfig is already 21+
        }
    }
}

org.gradle.daemon=true and JVM warm-up

The Gradle Daemon keeps the JVM warm between builds, avoiding JVM startup overhead (300–500ms). Always enabled by default for developer builds. On CI, use --no-daemon for reproducibility unless you have persistent agents that benefit from a warm JVM.

Under the hood

The build scan and --profile reports are driven by Gradle's internal build operations and the listener APIs (TaskExecutionListener, BuildOperationListener) — Gradle instruments each phase (initialization, configuration, execution) and each task with start/end events, then categorizes a task's outcome as EXECUTED, UP-TO-DATE (inputs unchanged), FROM-CACHE (output restored via cache key), SKIPPED, or NO-SOURCE. --scan serializes those operations and uploads them; --profile renders them locally. The daemon matters for profiling because it's a long-lived JVM that preserves JIT-compiled hot paths and Gradle's in-memory caches (the configuration model, file-system watching state) across invocations — which is exactly why the first build after starting a daemon is slower than subsequent ones, and why a profiler must distinguish cold (fresh daemon, OS cache cleared) from warm scenarios to produce comparable numbers.

build phases instrumented by build operations:
  initialization → settings.gradle, included builds
  configuration  → evaluate every project's build.gradle (the phase config-cache skips on hit)
  execution      → run task DAG; per task outcome: EXECUTED | UP-TO-DATE | FROM-CACHE | SKIPPED
daemon: persistent JVM → keeps JIT + Gradle in-memory state warm between builds

Interview Angles 12.2

Q: How do you reduce build time in a large Android app?

"I think about this as a layered approach — there are about ten levers, and they compound. Starting from the cheapest:

  1. Enable parallel builds (org.gradle.parallel=true) and size the worker pool to available CPUs.
  2. Enable the configuration cache — this saves the full configuration phase on warm runs, which alone can be 10–30 seconds on a large project.
  3. Enable the build cache — restores task outputs from local or remote cache, so even after a clean you're not recompiling from scratch.
  4. Migrate KAPT to KSP — eliminates stub generation and enables incremental processing, which is often the single biggest win.
  5. Modularize — scope recompilation to changed modules and let sibling modules build in parallel.
  6. Use implementation everywhere, not api — cuts the recompilation cascade when a low-level dependency changes.
  7. Increase debug minSdk to 21 — skips legacy DEX desugaring.
  8. Move build logic to :build-logic instead of buildSrc — buildSrc changes invalidate the entire project's configuration cache; :build-logic does not.
  9. Profile with --scan first — always identify the slowest tasks before guessing what to optimize.
  10. Remote build cache — enables CI-to-developer reuse, especially valuable after a branch switch or fresh checkout."

Q: Why can annotation processors slow builds?

"KAPT annotation processors require a full stub generation pass before they even start: Kotlin code gets compiled to Java stubs so that Java-based processors can inspect it. That adds a full extra compile-like step per module. And processors are often non-incremental — meaning they're AGGREGATING — so any source change triggers full reprocessing of the entire module. In a module with 500 Kotlin files, editing one line means regenerating stubs for all 500, then running the processor over all of them. That's why KAPT can eat 30–50% of total compile time.

KSP eliminates this entirely: it runs processors directly against the Kotlin compiler's own symbol table, no stubs needed, and it supports fine-grained incremental processing — processors only re-run on the files that actually changed."

Q: KSP vs KAPT?

"The short version is: KSP is up to 2× faster, fully incremental, gives processors native Kotlin type access without any stub approximation, and it's the direction Google has officially endorsed — KAPT is now in maintenance mode. For any library that already supports KSP — Room, Hilt, Moshi — I always prefer KSP. The only reason to keep KAPT around is for libraries that haven't yet published a KSP processor."

APK vs AAB

APK (Android Package)

🎤 Say it out loud (~30–45s): "An APK is the actual installable artifact — a ZIP archive holding the DEX bytecode, the compiled resources.arsc, native .so libraries, assets, and the manifest, all signed so the device can verify it. The thing to call out is that a universal APK packs every ABI, density, and language for all devices, so it's bloated — that's exactly the problem AABs were introduced to solve, and it's also why side-loading or any non-Play distribution still needs a full APK."

Definition: An APK is the installable artifact for Android. It bundles compiled DEX bytecode, compiled resources (resources.arsc), native libraries (.so), assets, and AndroidManifest.xml into a single file that devices install directly.

How APKs are built

Kotlin/Java source
  → d8/r8 → .dex files
XML resources
  → aapt2 compile → flat files
  → aapt2 link → resources.arsc + R.java
Native code
  → NDK → .so files
All artifacts
  → apkbuilder → unsigned.apk
  → apksigner / jarsigner → signed.apk

Universal APK: A single APK containing resources, native code, and screen densities for every device. Large file size. Required for side-loading and for builds that don't go through the Play Store.

Split APKs (Dynamic Delivery pre-cursor): AGP can split one build into multiple APKs by ABI, screen density, or language. Manually managing splits is complex.

Under the hood

An APK is just a ZIP file with a specific layout, and the OS treats it as one. At install time PackageManager/installd copies it to /data/app/<pkg>-<hash>/, and the DEX is processed by dex2oat (ART's ahead-of-time compiler) into an .oat/.art file for faster startup — modern ART uses a hybrid of AOT plus JIT plus profile-guided compilation. The resources.arsc is a flat binary table mapping resource IDs (a packed 0xPPTTEEEE int: package/type/entry) to per-configuration values, which is how Resources resolves the right drawable or string for the device config at runtime. The Zip's entries must be 4-byte aligned (zipalign) so the OS can mmap uncompressed resources directly instead of copying them into RAM.

app.apk (ZIP)
├── classes.dex, classes2.dex ...   # DEX bytecode (multidex)
├── resources.arsc                  # compiled resource table (ID → value/config)
├── res/                            # compiled binary XML + assets referenced by arsc
├── lib/arm64-v8a/*.so              # native libs per ABI
├── assets/                         # raw files (AssetManager)
├── AndroidManifest.xml             # binary XML
└── META-INF/                       # signatures (v1); v2+ block sits before central dir

AAB (Android App Bundle)

🎤 Say it out loud (~30–45s): "An AAB is an upload-only format — you can't install it on a device directly. You ship Google one bundle, and Play's Dynamic Delivery generates a tailored APK set per device, stripping out the ABIs, densities, and languages that device doesn't need, which typically cuts download size dramatically. The gotcha interviewers probe is that because Play re-splits and re-signs, you need Play App Signing, and to test an AAB locally you have to run it through bundletool to materialize an installable APK set."

Definition: An AAB is an upload artifact for the Google Play Store — it is not directly installable on a device. It contains all app code and resources in a modular format (base/, feature modules), and the Play Store's Dynamic Delivery infrastructure generates device-optimized APKs from it at delivery time.

How AABs work

  1. Developer uploads the AAB to Play Console.
  2. Play's servers generate a device-specific APK set for each device class: only the correct ABI (arm64-v8a vs x86), the correct screen density (xxxhdpi vs hdpi), and the correct language strings are packaged.
  3. Users download a smaller, optimized APK tailored to their device.

AAB size advantage

An app with arm64, x86, x86_64 native code, 5 screen densities, and 20 languages:

  • Universal APK: ~150 MB
  • Device-specific APK from AAB: ~30 MB (only what the device needs)

AAB requirements

  • Required for new apps on Google Play since August 2021.
  • AABs must be signed with the same key as the distribution certificate on Play.
  • Cannot be side-loaded (for testing, use bundletool to extract a local APK set).

Dynamic Feature Modules

AABs enable on-demand feature delivery: large features (e.g., AR module, PDF viewer) can be delivered as dynamic feature modules downloaded only when the user needs them, reducing initial install size.

Under the hood

An AAB is a ZIP in a protobuf-based format: the manifest is AndroidManifest.xml in protobuf (aapt2's proto resource format, not the binary-XML used in APKs), resources live in resources.pb, and code/resources are organized into modules (base/, plus feature modules) each declaring split dimensions. The AAB itself is not signed for distribution — Play's server runs bundletool to produce an APK set: one base APK plus split APKs keyed by config (config.arm64_v8a, config.xxhdpi, config.en). On install, the device receives the base plus only the matching splits, and Android's split-APK mechanism loads them as one logical package (this is the same machinery as Split APKs, surfaced through Play). The device tells Play its capabilities via the Play Store app's device spec, so the server's bundletool invocation is effectively build-apks --device-spec=<that device>.

app.aab (ZIP, proto format)        Play server (bundletool)         device download
├── base/                          ─────────────────────────►       base.apk
│   ├── manifest/ (proto)          generates an APK set:      +     config.arm64_v8a.apk
│   ├── dex/, res/, assets/        base + per-config splits   +     config.xxhdpi.apk
│   └── resources.pb                                          +     config.en.apk
├── feature_x/  (dynamic module)                              (feature delivered on-demand)
└── BUNDLE-METADATA/  (mapping.txt, etc.)

App Signing

🎤 Say it out loud (~30–45s): "Every APK and AAB has to be signed with a developer key — Android records the signing certificate at first install and refuses any update signed with a different key, which is how it guarantees updates come from the same author. The big senior-level point is to enroll in Play App Signing: you sign with an upload key you can rotate if it leaks, while Google holds the real distribution key. Losing the distribution key without that enrollment is catastrophic — you can never update the app again and have to ship under a new package name."

Definition: Before an APK or AAB can be installed or uploaded to the Play Store, it must be cryptographically signed with a developer key. Android verifies that signature at install time and on every subsequent update.

Keystore and keys

  • A keystore (.jks or .keystore) is an encrypted container holding one or more key pairs.
  • A key alias identifies a specific key within the keystore.
  • The key includes a private key (for signing) and a self-signed certificate (for verification).
  • Key validity: best practice is 25+ year validity for Play Store publishing keys (certificate must outlast app updates).

Signing configuration in Gradle

android {
    signingConfigs {
        create("release") {
            storeFile = file(System.getenv("KEYSTORE_PATH") ?: "keystore/release.jks")
            storePassword = System.getenv("KEYSTORE_PASSWORD")
            keyAlias = System.getenv("KEY_ALIAS")
            keyPassword = System.getenv("KEY_PASSWORD")
        }
    }
    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")
        }
    }
}

Google Play App Signing (GPAS)

With GPAS, you upload an AAB signed with an upload key. Google re-signs it with the distribution key (which Google holds) before delivering to devices.

Benefits:

  • If the upload key is compromised, you can request a key rotation from Google.
  • The actual distribution key never leaves Google's secure infrastructure.
  • Required for new apps, strongly recommended for existing ones.

Key loss

If you lose the signing key and haven't enrolled in GPAS, you cannot publish updates to your app. The only option is to publish a new app with a different package name. This is catastrophic. Always back up signing keys in multiple secure locations (e.g., HSM, encrypted S3 bucket with strict access controls, password manager).

v1 vs v2 vs v3 signatures

  • v1 (JAR signing): Signs individual entries. Android 1.0+.
  • v2 (APK Signature Scheme v2): Signs the entire APK binary. Faster verification. Android 7.0+.
  • v3 (APK Signature Scheme v3): Adds key rotation support. Android 9.0+.
  • v4: For incremental installs (ADB). Android 11+.

AGP enables v1+v2 by default; v3 is opt-in for key rotation. Play requires v1+v2 for compatibility with older Android versions.

Under the hood

Signing is asymmetric cryptography: a SHA-256 digest of the content is signed with the RSA/EC private key, and the public certificate ships inside the APK so any verifier can check it — there's no CA chain of trust, the certificate is self-signed and identity is "same cert as last time." v1 (JAR) hashes each ZIP entry and stores manifests in META-INF/, which is why it doesn't protect the ZIP metadata and is slow (the device must read every entry). v2/v3 insert an APK Signing Block between the ZIP entries and the central directory, signing a digest computed over the whole file in 1 MB chunks (a Merkle-style tree), so verification is one pass and tamper-evident across the entire archive. v3 extends the block with a proof-of-rotation linked list where the old key signs the new key, letting Android accept an update whose signer changed because it can follow the chain back to the originally trusted cert. The accepted certificate's hash is what Android persists in PackageManager's packages.xml and checks on every update.

APK layout for v2/v3 verification:
[ ZIP entries ][ APK Signing Block ][ Central Directory ][ End of CD ]
                      │
                      └── digests over 1MB chunks of the other 3 sections,
                          signed by private key; v3 adds rotation lineage

ProGuard / R8

🎤 Say it out loud (~30–45s): "R8 is the default release-build tool that replaced ProGuard — it does shrinking, optimization, obfuscation, and DEX compilation in a single pass, taking .class files straight to .dex, which is why it's faster than the old ProGuard-then-D8 pipeline. It's driven by the same proguard-rules.pro keep-rule syntax, so it's backwards compatible. The gotcha is full mode, the default since AGP 8 — it optimizes far more aggressively, including assuming things are non-null, so anything touched by reflection or JNI needs explicit keep rules or it'll get stripped or broken."

Definition: R8 is the code shrinker, optimizer, and obfuscator used in Android release builds, replacing ProGuard. It performs four operations in a single pass: tree-shaking (shrinking), optimization, obfuscation, and DEX compilation.

How R8 works (single-pass)

ProGuard was a separate Java tool that ran after d8 DEX compilation. R8 is a compiler: it takes .class files and outputs .dex directly, applying shrinking, optimization, and obfuscation in the same compilation pass. That single-pass approach is what makes R8 faster than the ProGuard + D8 pipeline it replaced.

Enabling R8

android {
    buildTypes {
        release {
            isMinifyEnabled = true       // enables R8 (shrink + obfuscate)
            isShrinkResources = true     // enables resource shrinking (requires minifyEnabled)
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
        }
    }
}

proguard-android-optimize.txt includes the default Android-specific keep rules (Activity, Service, View constructors, etc.) plus optimizations. proguard-android.txt skips optimizations — use -optimize version for release.

R8 in full mode

// gradle.properties
android.enableR8.fullMode=true

R8 full mode is more aggressive: it applies more optimizations and stricter class inlining. Can break code that relies on reflection without explicit keep rules. In AGP 8.0+, full mode is the default.

Under the hood

R8 parses all .class bytecode into its own intermediate representation, then walks the call graph from the keep rules (the "roots") to build a set of live classes/methods/fields. Reachability is what drives shrinking — anything the graph never reaches is dropped. Optimizations then run over the IR: aggressive inlining, devirtualization (turning virtual invoke-virtual/invoke-interface into direct calls when there's a single implementer), class merging, and outlining of repeated bytecode sequences into shared helpers to save DEX size. In full mode, R8 stops honoring some implicit ProGuard assumptions — most notably it assumes a class/member not kept is not reachable via reflection, and it propagates non-null and constant information aggressively, so a field only ever set by Gson reflection can be optimized to null. Finally R8 lowers the optimized IR straight to DEX, applying register allocation and the invoke-* opcode selection itself rather than handing .class files to a separate D8 step.

.class (all modules + libs)
   │  parse → R8 IR
   ▼
build live set from keep rules (roots) ── unreachable nodes pruned (SHRINK)
   │
   ▼
optimize IR: inline / devirtualize / merge / outline / propagate constants
   │
   ▼
rename live symbols → a,b,c (OBFUSCATE)  + emit mapping.txt
   │
   ▼
lower to DEX: register alloc + opcode selection (no separate D8)

Obfuscation

🎤 Say it out loud (~30–45s): "Obfuscation renames classes, methods, and fields to short meaningless identifiers like a, b, aa — it raises the bar for reverse engineering and shrinks the binary because short names compress and pack better. But I'm always careful to frame it as a speed bump, not security: string literals, endpoints, and control flow are all still recoverable by decompilers. The operationally critical part is the mapping.txt R8 emits — without archiving it per release, your production crash stack traces are permanently unreadable."

Definition: Obfuscation means renaming class names, method names, and field names to short meaningless identifiers like a, b, c, aa, and so on. The goal is to make reverse engineering harder and to reduce binary size, since shorter names compress better.

How obfuscation works

R8 generates a mapping file (mapping.txt) that records every original name → obfuscated name. At build time:

  • com.example.MyUserRepository → a.b.c
  • fun getUserById(id: Long): User → fun a(a: Long): b

This mapping file is critical for crash symbolication (see below).

What obfuscation does NOT protect

  • String literals are not obfuscated.
  • The app's binary can still be decompiled — the class and method names are meaningless, but the control flow is still there.
  • API endpoints embedded in code remain visible.
  • Determined reverse engineers can still analyze the logic.

Obfuscation is a speed bump, not a security guarantee.

Keep rules for obfuscation

Any class or member accessed via reflection, JNI, or serialization must be explicitly kept — R8 cannot statically analyze reflection, so it will remove things it can't see being called.

# Keep data class used with Gson (reflection-based serialization)
-keep class com.example.api.response.** { *; }

# Keep Parcelable implementations
-keep class * implements android.os.Parcelable {
    public static final android.os.Parcelable$Creator *;
}

# Keep enum names (used in serialization)
-keepclassmembers enum * {
    public static **[] values();
    public static ** valueOf(java.lang.String);
}

# Keep custom exception classes (for catch blocks)
-keep public class * extends java.lang.Exception

# Keep specific class but allow method renaming
-keepnames class com.example.MyClass

Under the hood

Obfuscation is a rename pass over the live symbol set, but the renaming is constrained by JVM/DEX rules R8 must preserve: it can't rename anything overriding a framework or library method (the override relationship must keep the same descriptor), and it reuses names across unrelated scopes — a can name a class, a field, and a method simultaneously because the DEX format resolves each by its kind plus enclosing type, and method dispatch keys on the full descriptor (name + parameter/return types). This is also why overloads collapse: two methods with different signatures can both become a(...) since the descriptor still disambiguates them, which shrinks the string pool that DEX uses for all identifiers. The mapping.txt is the inverse table R8 records so the rename is reversible at symbolication time; the obfuscated DEX itself contains none of the original names except those held by keep rules. Strings stay untouched because they're entries in the DEX string_ids data pool, not symbols R8 considers renameable — only type/method/field identifiers participate.

DEX identifier pools (all renamed independently by R8):
  type_ids     → Lcom/example/UserRepo;  becomes  La/b/c;
  method_ids   → resolved by (defining type, name, proto/descriptor)
  field_ids    → resolved by (defining type, name, type)
  string_ids   → literal strings — NOT obfuscated
mapping.txt = reverse map (obfuscated → original) kept off-device

Shrinking (Code and Resource)

Code Shrinking (Tree-Shaking)

🎤 Say it out loud (~30–45s): "Code shrinking is tree-shaking: R8 starts from the entry points — everything declared in the manifest plus keep rules — builds a reachability graph, and deletes any class or method nothing reaches. The big wins come from huge transitive dependencies where you only use a sliver of the library. The catch is that R8 can't see reflection or JNI calls, so anything reached only that way looks dead and gets removed unless you explicitly keep it — that's the classic source of release-only crashes."

How it works: R8 builds a call graph from the app's entry points (Activities, Services, BroadcastReceivers — all declared in AndroidManifest.xml). It follows every reachable method call and class instantiation. Anything not reachable is removed from the output DEX.

Size impact: Removing unused code from large transitive dependencies (e.g., a library that includes its own JSON parser which you never use) can reduce APK size by 20–50%.

What R8 keeps by default (from proguard-android-optimize.txt):

  • All classes referenced in AndroidManifest.xml
  • All public classes with public/protected constructors taking Context (entry points)
  • Classes annotated with @Keep
  • Native method signatures

Under the hood

The reachability analysis is essentially a mark-and-sweep over the type/method/field graph: keep rules and the manifest seed a worklist of "roots," R8 marks each reachable node and enqueues everything it references (called methods, instantiated types, read fields, supertypes/interfaces it must keep for verification), and repeats to a fixpoint. Whatever stays unmarked is swept from the output DEX. Reflection breaks this because a call like Class.forName("com.example.Foo") is just a string argument — there's no edge in the graph from caller to Foo, so Foo stays unmarked and is removed; the same applies to native methods whose implementations live in C++ and whose Java side is only reached via JNI name lookup. R8 ships consumer rules bundled inside many AARs (META-INF/proguard/) precisely so library authors can declare these invisible edges on your behalf, which is why most well-behaved libraries don't need manual keep rules.

roots = manifest components + @Keep + keep rules + JNI signatures
worklist ← roots
while worklist not empty:
    n ← pop
    mark(n)
    enqueue n's static edges: called methods, new'd types,
            read/written fields, supertypes/interfaces
# reflection / JNI create NO static edge → target left unmarked → swept

Resource Shrinking

🎤 Say it out loud (~30–45s): "Resource shrinking runs after code shrinking — once R8 knows which R.id constants survive, the resource shrinker drops drawables, layouts, and strings nothing references. By default it runs in safe mode and keeps anything it's unsure about, because resources are often loaded dynamically by name via getIdentifier, which it can't trace. The subtle detail is that 'removed' resources aren't truly deleted from resources.arsc — they're replaced with tiny dummy stubs so the resource table's ID offsets stay valid."

How it works: After code shrinking, AGP's resource shrinker analyzes which resource IDs are referenced in the remaining code. Unreferenced resources (images, layouts, strings) are removed from resources.arsc and replaced with tiny dummy files (not truly deleted to preserve alignment).

Enabling

buildTypes {
    release {
        isMinifyEnabled = true       // required for resource shrinking
        isShrinkResources = true
    }
}

Safe mode vs strict mode

Resource shrinker defaults to "safe" mode — it keeps resources it's uncertain about (e.g., resources loaded via Resources.getIdentifier("my_image_", "drawable", packageName)). Strict mode (android.defaultConfig.shrinkResources = true with tools:shrinkMode="strict" in res/raw/keep.xml) removes more but requires explicit keep rules for dynamic resource loading.

<!-- res/raw/keep.xml -->
<resources xmlns:tools="http://schemas.android.com/tools"
    tools:keep="@layout/l_used*_a,@layout/l_used_b*"
    tools:discard="@layout/unused"
    tools:shrinkMode="strict" />

Under the hood

The resource shrinker builds a reference graph too, but across resources: it parses the surviving DEX for integer R constants, scans resources.arsc and compiled binary-XML resources for resource-to-resource references (a layout referencing @drawable/x, a style referencing another style), and computes the transitively reachable set. The "safe mode" heuristic is a string scan — if it finds any string constant that looks like a resource name, it assumes getIdentifier-style dynamic lookup and keeps everything matching, because a missing resource at runtime is a crash. Crucially it can't physically delete entries from resources.arsc without renumbering every resource ID (those IDs are baked into the DEX as constants), so it instead rewrites the unused entries to point at a tiny placeholder file and zeroes their value — the ID slot survives, the payload shrinks. tools:shrinkMode="strict" turns off the name-matching heuristic so only graph-reachable resources survive, trading safety for more removal.

Optimization (R8 only)

Beyond shrinking, R8 performs code optimizations:

  • Inlining short methods
  • Class merging (merging companion objects into their outer class)
  • Constant propagation
  • Dead branch elimination (if (BuildConfig.DEBUG) { ... } is removed in release builds when DEBUG = false)
  • Enum optimization (converting enums to int constants where possible)

Mapping Files and Crash Symbolication

🎤 Say it out loud (~30–45s): "When R8 obfuscates, it emits mapping.txt — a text file mapping every renamed class, method, and field back to its original name and line numbers. That file is the only way to turn a production stack trace full of a.b.c back into readable code, so I archive one per versionCode; lose it and crashes from that build are unreadable forever. In practice I wire it into the crash reporter — upload the mapping to Sentry keyed by a build UUID, and it de-obfuscates automatically instead of me running retrace by hand."

Definition: The mapping.txt file produced by R8 is a line-oriented text file that maps every obfuscated identifier back to its original name and source file line number. Without it, production crash stack traces are permanently unreadable.

Location

app/build/outputs/mapping/release/mapping.txt

What mapping.txt contains

# Format: original -> obfuscated:
com.example.UserRepository -> a.b.c:
    long userId -> a
    com.example.User getUser(long) -> a
        5:5:void <init>() -> <init>
        10:12:com.example.User getUser(long) -> a

Crash symbolication workflow

  1. R8 produces an obfuscated stack trace in production:
   FATAL EXCEPTION: main
   java.lang.NullPointerException: ...
       at a.b.c.a(Unknown Source:3)
       at d.e.f.a(Unknown Source:12)
  1. Use retrace (shipped with AGP / Android Studio) to de-obfuscate:
   # Using the standalone retrace tool
   java -jar retrace.jar mapping.txt crash_log.txt

   # Using AGP's retrace wrapper
   ./gradlew retrace --stacktrace-file=crash_log.txt --mapping-file=mapping.txt
  1. De-obfuscated output:
   java.lang.NullPointerException: ...
       at com.example.UserRepository.getUser(UserRepository.kt:3)
       at com.example.HomeViewModel.loadUser(HomeViewModel.kt:12)

Sentry and crash symbolication

Sentry (and other crash reporters) support automatic symbolication. The workflow has three steps:

  1. Upload the mapping.txt to Sentry on each release via the Sentry CLI or Gradle plugin:
   sentry-cli upload-proguard --android mapping.txt
  1. Sentry stores the mapping against a build UUID that the Sentry SDK embeds in the release APK.
  2. When a crash comes in, Sentry automatically de-obfuscates the stack trace using the stored mapping — no manual retrace step needed.

Important: Store mapping.txt for every release. Without it, production crashes from that build are permanently unreadable. Archive mapping files to S3 or similar long-term storage keyed by versionCode.

Line number obfuscation

By default, R8 collapses multiple original lines to single lines in the mapping file, which can make stack traces less precise. To preserve accurate line numbers:

-keepattributes SourceFile,LineNumberTable
-renamesourcefileattribute SourceFile

This keeps line numbers accurate while still obfuscating the source file name shown in stack traces — you'll see SourceFile:line instead of UserRepository.kt:line. For most crash tooling, having accurate line numbers is sufficient.

Under the hood

retrace is a pure reverse lookup: a stack frame prints class.method(SourceFile:lineNumber), and retrace resolves the obfuscated class to its original, then uses the from:to: line ranges in mapping.txt to map the runtime line back to the original source line — which is also how it can un-collapse inlined frames, because R8 records inlining ranges in the mapping so an inlined call can be expanded back into multiple original frames. The "Unknown Source:N" you see when SourceFile/LineNumberTable aren't kept happens because the DVM/ART StackTraceElement carries the line number from the DEX debug_info but no file name; R8 can still resolve it through the line-range table even without the original file name, which is exactly the trick the -renamesourcefileattribute rule exploits. The Sentry-style automation works by R8/AGP embedding a stable UUID into the build (and the mapping is uploaded under that UUID); the SDK stamps each event with it, so the server picks the exact mapping for that build rather than guessing.

mapping.txt line-range entry:
    10:12:com.example.User getUser(long) -> a
    └ runtime lines 10–12 in method `a` ⇒ original getUser(long), original lines 10–12
retrace(frame "a.b.c.a(SourceFile:11)") → com.example.UserRepository.getUser(UserRepository.kt:11)
inlining ranges in the same file let one runtime frame expand into several source frames

Play Console Rollout and Staged Rollout

🎤 Say it out loud (~30–45s): "Staged rollout lets me push a release to a slice of production — say 10% — watch crash-free rate and ANRs, then expand or halt. The key detail is that the selection is deterministic per Google account, so a user in the 10% bucket stays in when I bump to 20%, and the cohort only grows. The gotcha interviewers love is that you can't truly 'roll back' — Play requires a strictly increasing versionCode, so a rollback is really publishing the old binary as a brand-new higher-versionCode release, which is why the real fast kill switch is a server-side feature flag, not Play Console."

Definition: Play Console staged rollout lets you release a new version of your app to a percentage of your user base first, monitor crash rates and reviews, and then gradually expand or halt the rollout based on what you see.

How staged rollout works

  1. In Play Console → Production → Create new release → upload AAB.
  2. Set rollout percentage (e.g., 10%).
  3. Users in the rollout receive the new version via Play Store auto-update.
  4. Play uses a deterministic selection: the same user always sees the same rollout decision (based on a hash of their Google account). A user who receives 10% rollout will receive 20% rollout when you expand.
  5. Monitor: Crash-free users rate, ANRs, reviews, ratings, Play-measured vitals.
  6. Expand to 25% → 50% → 100% or halt/rollback.

Play Tracks

Track Purpose Testers
Internal testingDev/QA team, instant publishUp to 100 opted-in
Closed testing (Alpha)Expanded testing, controlledSpecific users/groups
Open testing (Beta)Public opt-inAnyone who opts in
ProductionAll usersStaged or full

Rollback mechanics

You cannot "push back" a released version. Rolling back means publishing the previous APK version as a new release — the same versionCode trick does not work, because Play requires a strictly increasing versionCode. For fast rollback, always keep the previous signed AAB and a CI/CD pipeline that can publish it in minutes.

Alternatively, if the bad behavior is behind a feature flag, you can disable it server-side without shipping any new release at all.

Play Console monitoring during rollout

  • Android vitals: Crash rate, ANR rate. Play displays a threshold; exceeding it flags your release.
  • Rating/review: A spike in 1-star reviews signals user-facing issues.
  • Pre-launch report: Automated Robo test and crawl on Firebase Test Lab before you promote.

Staged rollout limitations

  • Staged rollout only applies to the production track.
  • Users on beta/alpha tracks always get the latest beta/alpha version (no percentage control there).
  • Users who manually go to Play Store and press Update always get the latest available regardless of rollout percentage.

Under the hood

The rollout decision is not made on-device and isn't random per check — Play's distribution backend computes a stable bucket for each (app, account) pair and the Play Store client honors it during its auto-update poll. Because the bucket is derived from a hash of the account identity rather than re-rolled, the population is monotonic: expanding the percentage can only add users, never swap them, which keeps the observed cohort coherent for vitals analysis. Android vitals themselves are aggregated server-side from DropBoxManager/ActivityManager crash and ANR reports that the framework collects on-device and uploads via Play services; the "crash-free users" rate you watch is a backend rollup of those reports keyed by versionCode. There is no per-device flag the framework reads to decide "am I in the rollout" — staging is purely a delivery-time gate on which APK splits the device is offered.

Account ID --hash--> stable bucket in [0,100)
   bucket < rolloutPercent  ->  offered new versionCode
   bucket >= rolloutPercent ->  stays on old versionCode
expanding percent only lowers the threshold => cohort grows, never churns

Feature Flags and Remote Config

🎤 Say it out loud (~30–45s): "Feature flags let me decouple deploy from release — I merge code to main and ship it dark, then turn it on for 1% independently of the Play release cadence, and flip it off server-side as a kill switch within minutes if it misbehaves. With Firebase Remote Config the critical detail is that fetch is asynchronous and cached, so on a cold start before the first fetch completes the app reads the bundled XML defaults — which means my defaults must always be the safe, off state for anything risky. The nuance interviewers probe is the fetch throttle: in production the minimum fetch interval defaults to several hours, so you can't expect a flag flip to propagate instantly to a device that just fetched."

Definition: Feature flags — also called feature toggles — let you enable or disable features at runtime without shipping a new app release. Remote Config extends this by allowing flag values to be configured from the server side.

Why feature flags for risky features

  1. Decouple deploy from release: Merge code to main and ship it to all users, but behind a flag that's false. Turn it on for 1% of users first, independently of the Play Store release cadence.
  2. Kill switch: If a feature causes crashes in production, flip the flag server-side to false — it takes effect within minutes, with no waiting for app review or staged rollout completion.
  3. A/B testing: Run an experiment with control and treatment groups from the same binary.
  4. Gradual rollout independent of Play Store: Roll out by percentage using your own backend instead of relying solely on Play's mechanism.

Risk mitigation strategy for risky features

  1. Put the feature behind a feature flag that defaults to false in production.
  2. Enable it for QA and internal users on the internal test track first.
  3. Enable for opted-in beta users on the open beta track.
  4. Production staged rollout: 1% → 5% → 20% → 50% → 100%.
  5. Monitor crash rates, ANRs, and business metrics at each stage before expanding.
  6. If metrics degrade at any stage, flip the flag to false server-side immediately, then investigate.

Remote config fetch latency

Remote config values are fetched asynchronously and cached locally. If the app launches before a fetch completes, it falls back to the default values from remote_config_defaults.xml. That is the safe state — defaults should always be the conservative, off setting for any risky feature.

Under the hood

Remote Config keeps three separate value stores on-device: a defaults map (seeded from your XML), a fetched store (the most recent values pulled from the server but not yet live), and the active store (what getBoolean/getString actually read). fetch() does an HTTP request and writes into the fetched store; activate() atomically copies fetched → active. fetchAndActivate() chains the two. Crucially, a getter never blocks on the network — it reads the active store synchronously, and the resolution order is active value → default → static type default (false/0/""). Each fetched value also carries a source enum (REMOTE, DEFAULT, STATIC) you can inspect. The minimumFetchIntervalInSeconds is a client-side throttle: if you call fetch() again inside the window, the SDK short-circuits and returns the cached result without a network round-trip, which is why production uses hours and debug uses 0. Values persist across process death in app-private storage, so a returning user already has the last-activated flags before the first fetch of the new session even starts.

getBoolean("flag")
  -> active store has key?   yes -> return it (source REMOTE/DEFAULT)
  -> no -> static type default (false)   (source STATIC)

fetch(): network -> fetched store   (throttled by minFetchInterval)
activate(): fetched store --atomic copy--> active store

Versioning

🎤 Say it out loud (~30–45s): "Every Android app has two version identifiers: versionCode, an integer Play uses purely for update ordering, and versionName, the human-readable string shown to users — they're completely independent. The one rule that bites people is that versionCode must strictly increase for every upload to Play, which is exactly why a 'rollback' has to be a new, higher versionCode publishing the old code. Definition: Android apps have two version identifiers. versionCode is an integer the Play Store uses for update ordering. versionName is the human-readable string shown to users.

android {
    defaultConfig {
        versionCode = 1042            // integer, monotonically increasing
        versionName = "4.2.1"         // user-visible string
    }
}

versionCode rules

  • Must be a positive integer.
  • Play Store requires each release to have a higher versionCode than the previous. Play uses versionCode to determine update ordering.
  • No relation to versionName — you can have versionCode = 1042 and versionName = "4.2.1".
  • Maximum value: 2,100,000,000 (Android limit).

versionName conventions

Common schemes:

  • Semantic versioning: MAJOR.MINOR.PATCH (e.g., 4.2.1)
  • Date-based: 2024.06.18
  • Automatic from CI: combine Git commit count or timestamp.

Automating versionCode in CI

// build.gradle.kts
val ciVersionCode = System.getenv("BUILD_NUMBER")?.toIntOrNull()
android {
    defaultConfig {
        versionCode = ciVersionCode ?: 1
        versionName = "4.2.${ciVersionCode ?: 0}"
    }
}

BuildConfig versioning

BuildConfig.VERSION_CODE and BuildConfig.VERSION_NAME are generated constants available at runtime, useful for including in analytics events, crash reports, and support tooling.

Under the hood

versionCode and versionName are not Gradle inventions — they are manifest attributes (android:versionCode, android:versionName) that AGP merges into the final AndroidManifest.xml, then aapt2 encodes them into the binary resource table of the APK. At install time PackageManagerService reads versionCode out of the parsed manifest into the PackageInfo/ApplicationInfo it tracks; an update is only accepted if the incoming package's versionCode is greater than or equal to the installed one (Play enforces strictly greater on the store side). The integer is actually stored as a 32-bit value, which is the origin of the ~2.1 billion ceiling — and modern AGP splits it into versionCode (lower bits) plus versionCodeMajor (upper bits) for apps that exhaust the range. BuildConfig.VERSION_CODE/VERSION_NAME are a separate artifact: AGP generates a BuildConfig.java per variant with these as public static final fields, so they're baked into the compiled bytecode as constants — meaning the runtime value comes from the build, not from re-reading the manifest at startup.

build.gradle versionCode/versionName
   |
   +--> merged AndroidManifest.xml (android:versionCode/Name)
   |         |--> aapt2 -> binary resource table in APK
   |         |--> PackageManagerService: update allowed iff newCode > installedCode
   |
   +--> generated BuildConfig.{VERSION_CODE,VERSION_NAME} (static final consts)

Q: What does R8 do?

"R8 is a combined shrinker, optimizer, obfuscator, and DEX compiler that runs in a single pass on every release build. There are four things it does.

First, tree-shaking: it builds a call graph starting from every entry point declared in your manifest — Activities, Services, BroadcastReceivers — and walks every reachable method and class. Anything that isn't reachable gets removed entirely. That kills dead code from both your own modules and from third-party libraries that you only use a fraction of.

Second, optimization: it inlines short methods, merges classes, propagates constants, eliminates dead branches — so an if (BuildConfig.DEBUG) block is literally removed from the release binary when DEBUG is false — and converts enums to int constants where possible. These all improve runtime performance and shrink the binary further.

Third, obfuscation: it renames classes, methods, and fields to short identifiers like a and b. That produces mapping.txt, which is what you use to de-obfuscate crash stack traces later. It also reduces binary size because shorter names compress better, and it raises the cost of reverse engineering.

Fourth, DEX compilation: it converts JVM bytecode to Dalvik/ART DEX format, replacing the separate d8 step that debug builds use.

R8 replaced ProGuard in AGP 3.4. The key advantage is that single pass — combining all four operations is faster than running ProGuard then D8 in sequence, and R8 has much deeper integration with the Kotlin toolchain."

Q: How do you debug obfuscated crashes?

"There are four steps. First, retrieve the obfuscated stack trace from your crash tool — Sentry, Crashlytics, whatever you use. Second, find the mapping.txt for the exact build that crashed; you match it by versionCode and build timestamp, which is why you archive mapping files for every release. Third, run retrace:

java -jar retrace.jar mapping.txt obfuscated_crash.txt

And fourth, read the de-obfuscated output — you get back the original class names, method names, and line numbers.

The best practice is to automate all of this. Both the Sentry Gradle plugin and the Crashlytics Gradle plugin can upload mapping.txt at build time so the tool de-obfuscates crashes automatically without you needing to run retrace manually.

The one catastrophic case is when you've lost the mapping.txt for a build. At that point, the crash is permanently unreadable — you can only correlate symptoms with the code changes in that version range. That's why every serious team stores mapping files in long-term storage keyed by versionCode, whether that's S3 or an artifact repository."

Q: Why use staged rollout?

"Staged rollout exists to limit the blast radius of bugs that make it through QA. There are four reasons I always use it.

First, risk containment: a crash affecting 1% of users is recoverable, a crash affecting 100% is a P0 incident. Staging gives you the window to detect and halt before you've hit the full audience.

Second, real-world signals: synthetic tests in CI cover known scenarios, but real users surface edge cases that testing simply cannot replicate — specific device models, OS versions, carrier configurations, locale-specific content.

Third, time to investigate: a 10% rollout that bumps crash rate by 0.5% gives the team time to diagnose and fix. By the time you'd expand to 100%, you either have a fix ready or you've already halted.

Fourth, business metric validation: for feature changes specifically, you can monitor conversion rate or session length or whichever KPI matters at 10% before you commit to full rollout."

Q: How do you safely release risky features?

"I think about this as a layered strategy — there are seven layers, and each one adds an independent safety net.

First, the feature flag at rest: merge the code to main behind a flag that's false in production defaults. The code ships in every release but stays dormant until you enable it.

Second, internal testing: enable the flag for the dev and QA team via the debug panel or a BuildConfig override, and validate against real production infrastructure.

Third, alpha and beta tracks on Play: enable via remote config for opted-in beta users to collect real-world feedback with a small, self-selected audience.

Fourth, production staged rollout: start at 1–5% on Play Console and monitor crash-free sessions, ANR rate, and business metrics for 24–48 hours before expanding.

Fifth, the remote kill switch: if metrics degrade at any stage, you flip the flag server-side to false — that takes effect within minutes, which is far faster than any hotfix release cycle.

Sixth, a hotfix pipeline: have CI/CD ready to publish a previous signed AAB or a targeted hotfix within 30 minutes in case the feature flag alone isn't enough.

And seventh, observability: instrument the feature with structured logging keyed to the flag state so you can split your dashboards between flag-on and flag-off users and see exactly what's changing."
