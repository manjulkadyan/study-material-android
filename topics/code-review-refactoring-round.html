17. Code Review & Refactoring Round

A complete, self-contained prep kit for the Android code-review / refactoring interview round, distilled from 20 real take-home / refactoring repositories reviewed as part of this study set. Each section is grounded in concrete findings; case-study repositories referenced below live in the companion code-review/ workspace (each with its own SOLUTION.md). Use the right-hand outline to jump between the eight parts.

17.1 The Code-Review Method

The "code review / refactoring" round is not a quiz about whether you can spot GlobalScope. It is a role-play: the interviewer hands you a PR (or an intentionally-bad app) and watches how a senior engineer thinks, prioritizes, and communicates. This module gives you a repeatable process so you don't freeze, don't rat-hole on nits, and don't miss the merge-blocker sitting on line 6.

1. The reviewer mindset — what interviewers actually score

Interviewers are (silently) filling in a rubric with roughly four axes. Optimize for all four, not just the first.

Axis Weak signal Strong signal
Correctness / depth"The networking could be better.""MyNewsActivity.kt:41 ignores the return of inputStream.read(buffer); for an asset larger than the initial available() this truncates the buffer and JSONObject(...) throws — I'd use bufferedReader().use { readText() }."
PrioritizationLists 30 findings in file order, nits mixed with crashes.Leads with the ANR + the leaked secret, explicitly defers naming nits to "non-blocking."
Communication"This is wrong." / rewrites silently.States symptom → cause → fix → why, asks a question when intent is unclear, praises what's good.
PragmatismDemands a full Clean Architecture rewrite for a 60-line take-home.Scopes the fix to the round's goal, distinguishes "must fix to merge" from "would do next sprint."

Three mindset rules that separate seniors from juniors:

  1. **Reason about runtime behavior, not style.** The best findings predict a concrete failure: a crash, an ANR, a leak, a wrong pixel, a leaked key. Style opinions are cheap; behavioral predictions are expensive and impressive.
  2. Prioritize out loud. Say "let me do a fast triage pass first, then go deep." Interviewers can't score prioritization they can't hear.
  3. Be the author's ally, not their judge. You are trying to get this PR mergeable, not to prove you're smarter. That framing changes your tone (see §4) and it's exactly what they're watching for in a teammate.

When there's no code to review. Repo 18 (../18-android-taming-bad-code/SOLUTION.md) is an empty Gradle Java-library stub — src/main/java/Library.java returns a constant true, no manifest, no android{} block. Repo 17 (../17-android-bad-code-smell/SOLUTION.md) is an IntelliJ plugin, not an app, so MVVM/Compose criteria don't apply. First establish that the subject exists and what kind of thing it is. Saying "before I review, let me confirm the scope — this isn't actually an Android app" is a senior move, not a dodge.

2. The time-boxed review pass (a repeatable checklist)

Do two passes. A fast breadth pass to build a map and catch blockers, then a deep pass on the hot spots. In a 45–60 min round budget roughly: 5 min orient, 15 min breadth triage, 20 min deep dive, 10 min write-up/verdict.

Pass order (highest signal-per-minute first)

Work outside-in: build config → entry points → threading/lifecycle → data/networking → parsing/models → tests → UI/resources → hygiene. Earlier stages gate later ones (a project that doesn't compile makes UI nits moot).

[ 0 ] BUILD / MANIFEST      does it even compile & run? toolchain, secrets, permissions
[ 1 ] ENTRY POINTS          Activity/Fragment/Composable/App — where does control start?
[ 2 ] THREADING / LIFECYCLE main-thread I/O, scope choice, cancellation, config change
[ 3 ] DATA / NETWORKING     client construction, error/status handling, timeouts
[ 4 ] PARSING / MODELS      nullability vs real API, manual parse, date types
[ 5 ] TESTS                 do they exist, compile, and actually exercise the code?
[ 6 ] RESOURCES / UI        layout constraints, adapters/DiffUtil, theming, strings
[ 7 ] HYGIENE               dead code, naming, unused deps, VCS junk

The checklist (tick these against any Android PR)

[0] Build / manifest / secrets — catches the "dead on arrival" blockers

  • [ ] Does it compile? (Repo 11 MainActivity.java:32-33 references a MainPresenterImpl that doesn't exist; Repo 15 MainScreen.kt:14 calls UserManager() no-arg against a 3-arg ctor; Repo 20 uses Gson with no Gson dependency.)
  • [ ] Any secret committed? Grep for keys. (Repo 01 common/Constants.kt:6 — API_NEWS_TOKEN in git history + APK. Repo 13 data/PhotoApi.kt:12 — Pixabay key as a default query param.)
  • [ ] Manifest sanity: is every Activity/Application registered? Cleartext allowed? Permissions present for the APIs used? (Repo 10 PetsApp never registered → LeakCanary silently never installs; Repo 20 getDeviceId() on minSdk 26 with no READ_PHONE_STATE → SecurityException.)
  • [ ] Toolchain: jcenter(), kotlin-android-extensions, removed APIs (AsyncTask, org.apache.http).

[1] Entry points — build the mental map

  • [ ] Open the Activity/Fragment/@Composable. What does it own? A "god" entry point that does I/O + parse + adapter + nav is your architecture headline. (Repo 04 MyNewsActivity.kt; Repo 07 MainActivity.java:30-147; Repo 09 RestaurantsActivity.kt:37-128.)

[2] Threading / lifecycle — the highest-frequency crash/ANR category

  • [ ] Any blocking I/O on the main thread? (Repo 04 MyNewsActivity.kt:36-47 reads a file + parses JSON in onResume(); Repo 13 MainActivity.kt:38-47 Thread.sleep(2000) in a click handler; Repo 16 KeywordDao.kt:8-50 synchronous SQLite on main.)
  • [ ] Scope choice: viewModelScope/lifecycleScope, or GlobalScope/hand-rolled? Is it cancelled? (Repo 03 ReviewsFragment.kt:62, Repo 08 MainViewModel.kt:16 GlobalScope; Repo 01 NewsListViewModel.kt:23-24 CoroutineScope(Dispatchers.Main + Job()) never cancelled.)
  • [ ] Config change: does rotation re-fetch or lose state? (Repo 02 LaunchedEffect(Unit) re-fetches on rotation.)

[3] Data / networking

  • [ ] Where is the HTTP client built? Inline per-call, or a singleton? (Repo 01 NewsRepository.kt:16-25 builds Retrofit inline.)
  • [ ] Error + status handling: is non-2xx handled? Is there a try/catch and an error UI state? (Repo 08 MainViewModel.kt:16-28 no try/catch; Repo 16 KakaoLocationImpl.kt:26-35 swallows non-2xx.)
  • [ ] Timeouts, cleartext, dead endpoints. (Repo 07/10 api.myjson.com is shut down; Repo 05/11/20 use cleartext http://.)

[4] Parsing / models

  • [ ] Do model nullabilities match the real API? (Repo 08 News.kt:6-15 non-null author/urlToImage + publishedAt: Date vs newsapi.org nulls/ISO-8601 → Gson NPE.)
  • [ ] Manual parse that throws on a missing key? (Repo 07 MediaEntity.java:19-28 getString/getInt per field.)

[5] Tests

  • [ ] Do they compile and run offline? (Repo 03 TestCoroutineRule.kt uses removed TestCoroutineScope.)
  • [ ] Is the mock actually injected and asserted, or a tautology? (Repo 01 GetNewListUsecaseTest.kt:36 mocks the repo but the use case news its own; Repo 08 MainViewModelTest.kt:36-50 asserts is ArrayList<News>.)

[6] Resources / UI

  • [ ] Layout constraints correct? (Repo 08 activity_main.xml:10-17 RecyclerView 0dp height, no bottom constraint → zero-height list.)
  • [ ] notifyDataSetChanged() vs DiffUtil/ListAdapter; stable keys; theming; hardcoded strings.

[7] Hygiene — mention briefly, never lead with it

  • [ ] Dead code, unused deps (Glide and Coil in Repo 13), .idea/ in VCS (Repo 04), magic constants, naming.

Announce the pass you're running: "I'll start with build and entry points, then threading." It shows method and buys you thinking time.

3. Severity taxonomy — how to triage under pressure

Assign every finding a severity. The label is your prioritization, and stating it is half the score.

Severity Definition Merge decision Examples from these repos
Merge-blocker (Critical)Crashes, data loss/corruption, security leak, doesn't compile, ANR, guaranteed wrong behavior. Ships → users hit it.Must fix before merge.Leaked API key (01/Constants.kt:6); main-thread file I/O ANR (04:36-47); guaranteed NPE after login (06/ProductsListActivity.java:41-55); non-compiling (11, 15, 20); unchecked cast crash (08/DetailActivity.kt:22).
MajorReal risk or clear correctness/architecture defect, but not guaranteed on the happy path. Testability gaps live here.Should fix before merge; negotiable with a follow-up ticket if truly out of scope.No error/loading UI (03, 08); hand-rolled un-cancelled scope (01:23-24); GlobalScope (03, 08); mock never injected (01, 08); no repository/ViewModel layer.
MinorWorks today but fragile, non-idiomatic, or a maintenance trap.Fix if cheap; fine as a follow-up.notifyDataSetChanged() instead of DiffUtil; Serializable instead of @Parcelize (08/News.kt:15); stringly-typed type (09).
NitPure style/preference, no behavioral impact.Never blocks. Prefix nit: and offer, don't demand.Magic number 6371 (09:81), Hungarian mList/mMap (11:15-17), hardcoded UI strings.

How to decide the line between Major and Blocker: ask "will a user or the CI hit this on a normal run?" If yes → blocker. A NetworkOnMainThreadException (05/MainActivity.java:34-56) fires on every launch → blocker. A missing else in a when that today never receives that value → major/minor depending on how reachable it is.

Triage under time pressure: if the clock is short, spend your words on blockers + the single biggest architectural theme, then batch the rest: "There's also a cluster of hygiene issues — magic numbers, hardcoded strings, notifyDataSetChanged — I'd sweep those but none block merge." Naming that you saw them without enumerating each is itself a prioritization signal.

4. Writing PR feedback that lands

Structure every substantive comment as: Symptom → Cause → Suggested fix → Why

NewsListViewModel.kt:23 — [blocker] scope leak. This ViewModel launches on a hand-rolled CoroutineScope(Dispatchers.Main + Job()) that's never cancelled in onCleared(), so an in-flight request outlives the screen and can touch a dead ViewModel. Suggest viewModelScope, which is cancelled for you when the ViewModel clears. Happy to pair on it.

Tone rules

  • Praise the good, specifically. It builds trust and shows you read carefully. Repo 08 gets a real one: the API key goes through ApiKeyInterceptor reading BuildConfig.NEWS_API_KEY from local.properties — call that out.
  • Question when intent is unclear; demand only when behavior is objectively wrong. "Is country meant to be user-selectable? setCountry() looks dead and it's hardcoded to us" (Repo 01) is a question. "This crashes on cancel — data is nullable" (Repo 14 MainActivity.kt:34) is a demand.
  • Give the fix, not just the complaint. A finding without a suggested direction reads as gatekeeping.
  • Attach severity labels ([blocker], [major], nit:) so the author can triage your review the way you triaged their code.

Example comments — bad vs good

1. Leaked secret (Repo 01, common/Constants.kt:6)

  • ❌ "Never hardcode API keys!!" — scolding, no fix, no severity.
  • ✅ "[blocker] Constants.kt:6 — the newsapi.org key is committed here, so it's in git history and the shipped APK. Move it to local.properties → BuildConfig (or inject via an interceptor as we already do elsewhere), and rotate the key, since the current one must be treated as compromised."

2. Main-thread I/O (Repo 04, MyNewsActivity.kt:36-47)

  • ❌ "Don't do I/O on the main thread." — true but generic; no runtime consequence, no fix.
  • ✅ "[blocker] MyNewsActivity.kt:36 — assets.open(...).read() + JSONObject(...) run on the main thread inside onResume(). On a large asset or slow device this ANRs, and there's no try/catch so any I/O error crashes. Move the read+parse into a repository on Dispatchers.IO, expose a StateFlow<UiState>, and collect it in the Activity."

3. Ignored read return (Repo 04, MyNewsActivity.kt:41) — the depth flex

  • ❌ "Use readText()."
  • ✅ "[major] :41 — inputStream.read(buffer) returns the number of bytes actually read, which isn't guaranteed to equal available(); for a larger asset this leaves the tail of buffer as zero bytes and JSONObject throws. assets.open(\"news.json\").bufferedReader().use { it.readText() } sidesteps the whole class of bug."

4. Mock never injected (Repo 01, GetNewListUsecaseTest.kt:36)

  • ❌ "This test is wrong."
  • ✅ "[major] GetNewListUsecaseTest.kt:36 — the mock repo is created but GetNewsListUsecase news its own NewsRepository() internally, so the mock is never exercised; the test passes by accident (and the delay(1000) suggests it's hitting the real network). Once the repo is constructor-injected, whenever(repo.getNews(...))... will actually drive the test. See ../06-testing-di.md."

5. Question, not demand (Repo 01, NewsListViewModel.kt:29)

  • ✅ "nit/question: country is hardcoded to \"us\" and setCountry() looks unused — was source/country selection dropped from scope, or is this a TODO? Not blocking, just want to make sure the brief's requirement isn't silently lost."

6. Praise (Repo 08)

  • ✅ "Nice — routing the key through ApiKeyInterceptor + BuildConfig.NEWS_API_KEY keeps it out of source. Worth copying this pattern to the other modules."

5. A fully worked mini-review — OneFootball (Repo 04)

This is what a complete PR review looks like end-to-end. Subject: the entire app lives in ../04-onefootball-coding_challenge_android/app/src/main/java/com/onefootball/MyNewsActivity.kt (see SOLUTION.md).

Review summary

Verdict: Request changes — not mergeable as-is. The app renders the happy path, but the data load runs entirely on the main thread with no error handling, which is both an ANR and a guaranteed-crash risk, and all logic lives in one Activity so nothing is testable. I've flagged 3 merge-blockers and 2 major items below, plus a batch of minors. The RecyclerView + Coil wiring itself is clean, and the JSONArray.forEach extension is a nice touch — the issues are about where the work happens, not the UI.

Inline comments

[blocker] MyNewsActivity.kt:36-47 — main-thread file I/O + parse (ANR) with no error handling. onResume() opens the asset, reads it, and parses JSON synchronously on the UI thread; there's no try/catch, so any I/O or schema error crashes instead of showing an error state. And because it's in onResume(), it re-runs every time the screen resurfaces. Move to a repository on Dispatchers.IO:

// AFTER — repository
class NewsRepository(private val assets: AssetManager, private val moshi: Moshi) {
    suspend fun loadNews(): List<News> = withContext(Dispatchers.IO) {
        val json = assets.open("news.json").bufferedReader().use { it.readText() }
        moshi.adapter(NewsFeed::class.java).fromJson(json)?.news.orEmpty()
    }
}
// ViewModel exposes StateFlow<UiState>; Activity collects it in onCreate, not onResume.

[blocker] :41 — inputStream.read(buffer) return value ignored → truncated read. read() may return fewer bytes than available(); the remainder of buffer stays zeroed and JSONObject(jsonString!!) throws. The bufferedReader().use { readText() } above eliminates it. (See snippet S3 in the evidence pack.)

[blocker] :86-90 — unguarded startActivity(ACTION_VIEW). If a device has no browser (or news_link is malformed), this throws ActivityNotFoundException. Guard it:

val intent = Intent(Intent.ACTION_VIEW, Uri.parse(news.newsLink))
if (intent.resolveActivity(context.packageManager) != null) context.startActivity(intent)
else Toast.makeText(context, R.string.no_browser, Toast.LENGTH_SHORT).show()

[major] whole file — God Activity, untestable. MyNewsActivity owns I/O, parsing, the adapter, the view holder, and an extension function. There's no ViewModel/repository/DI seam, so none of it can be unit-tested (ExampleUnitTest.kt is still assertEquals(4, 2+2)). Extract NewsRepository (interface) + MyNewsViewModel(viewModelScope) + Hilt. This also fixes the onResume() re-fetch. Full target design in ../03-architecture-mvvm-clean.md.

[major] :38-45 — parse throws on any schema drift. getString("title") etc. throw JSONException on a missing key; combined with the missing try/catch this is a crash. Moshi with @Json names + nullable fields degrades gracefully. See ../05-networking-parsing.md.

nit: :96 notifyDataSetChanged() — prefer ListAdapter + DiffUtil for correct animations and less redraw. nit: news_item.xml:23,45 hardcodes UI strings; move to strings.xml. nit: .idea/ is committed; add it to .gitignore. None block merge.

Merge blockers (the "must-fix" list I'd paste at the top)

  1. :36-47 main-thread I/O + no error handling (ANR + crash).
  2. :41 ignored read() return (truncated-read crash).
  3. :86-90 unguarded startActivity (ActivityNotFoundException).

Alternate worked example: Medibank (Repo 01) is the best case for the "DI present but fake" + leaked secret story — lead its summary with the Constants.kt:6 key and the bypassed Hilt graph (GetNewsListUsecase.kt:24 news its own repo). See ../01-medibank-ventures-code-review-exercise-android/SOLUTION.md and snippet S16 in .evidence.md.

6. Assessing production readiness & stating a verdict

Close every review with one explicit verdict. Interviewers want a decision, not a shrug. Use a three-way scale and justify it in one sentence tied to the blocker count.

Verdict Criterion
✅ Ready / ApproveZero blockers; majors have owned follow-up tickets.
⚠️ Approve with changes / Needs changesNo blockers, but majors must land first (Repo 08 is the canonical "close but not quite").
❌ Request changes / Not ready≥1 merge-blocker: crashes, leaks, doesn't compile, ANR (Repos 01, 03, 10, 11, 17, 20).

A production-readiness statement should touch, in order: does it run → is it safe (secrets, crashes) → is it correct against the brief → is it maintainable/tested. Template:

"Not ready. One security blocker (committed API key) and two crash/ANR blockers mean it can't ship. The architecture (no DI/repository, logic in the Activity) makes it hard to change safely and impossible to unit-test. I'd unblock the three criticals first, then treat the layering + tests as fast-follow. The Compose UI and the modern dependency choices are a solid base to build on."

Two calibration notes from these repos:

  • "Learning repo" is not a verdict you get to give in the round. 13 of the 20 are intentionally-flawed teaching starters, but the interviewer still expects you to review them as if they were a PR. Say "if this were a real PR, I'd request changes because…" — that's what INDEX.md's mergeBlockerCount encodes.
  • Distinguish "by design" from "defect." A pair-programming starter (Repo 03) is supposed to be rough; note that, then review it anyway. Don't excuse a leaked key because "it's just an exercise."

Self-check

17.2 Flaw Catalog

This is the module you keep open during the round. When you spot something in the supplied app, jump to the matching category, confirm the symptom, and lift the recommended fix. Each entry follows the same template so you can scan fast:

  • Symptom — what you literally see in the code.
  • Impact — why a reviewer blocks on it (crash / ANR / leak / security / untestable).
  • Spot it fast — the grep/scan heuristic to find it in seconds.
  • Before / After — real snippet from a repo, plus the recommended fix.
  • Seen in — every repo that exhibits it.

Related modules go deeper on specific axes: architecture layering → 03-architecture-mvvm-clean.md; coroutine/lifecycle mechanics → 04-concurrency-lifecycle.md; HTTP/JSON → 05-networking-parsing.md; tests/DI seams → 06-testing-di.md. This catalog is the index of symptoms; those modules are the depth.

How to use this in the round

  1. First pass — crashes & security. Scan for the Crashes/Correctness (§C) and Security (§S) entries. These are auto-blockers; naming even two of them establishes credibility.
  2. Second pass — architecture & concurrency. §A and §L tell the reviewer whether the whole thing is testable and lifecycle-safe.
  3. Third pass — networking, parsing, UI, tests, smells. §N, §P, §U, §T, §CS round out the review.
  4. Always phrase a finding as symptom → impact → fix, with a file:line. That is the difference between "I'd use MVVM" and a hire.

Legend for severity used below: BLOCKER (crash/security/data-loss — do not merge), HIGH (leak/ANR/untestable), MEDIUM (correctness/UX), LOW (hygiene/style).

§A — Architecture

The single most common finding across all 20 repos: business logic, networking, and state live directly in an Activity / Fragment / Composable. See 03-architecture-mvvm-clean.md for the full target design; here we catalog the smells that reveal the absence of layering.

A1 — God Activity / Fragment / Composable

  • Severity: HIGH
  • Symptom: One class (often onCreate/onResume/onCreateView/a single subscribe lambda) does I/O, parsing, mapping, filtering, adapter wiring, and view binding.
  • Impact: Nothing is unit-testable (no seams), state is lost on rotation, and every change risks the whole screen. This is the root cause most other flaws hang off.
  • Spot it fast: Open the Activity/Fragment. If it imports Retrofit/HttpURLConnection/JSONObject and references RecyclerView/setContent, it's a god class. Count the lines in the largest method.
  • Before — 04-onefootball-coding_challenge_android/.../MyNewsActivity.kt:36-47 does file I/O + parse + adapter all in onResume():
override fun onResume() {
    super.onResume()
    var inputStream = assets.open("news.json")   // I/O
    val size = inputStream.available()
    val buffer = ByteArray(size)
    inputStream.read(buffer)
    inputStream.close()
    jsonString = buffer.toString(Charset.defaultCharset())
    val items = parseJsonString(jsonString!!)    // parsing
    myAdapter.setNewsItems(items)                // view binding
}
  • After — push each responsibility to a layer; the Activity only renders UiState:
// Activity
viewModel.uiState.flowWithLifecycle(lifecycle).onEach { render(it) }.launchIn(lifecycleScope)
// ViewModel
val uiState = repository.news()
    .map { NewsUiState.Content(it) }
    .catch { emit(NewsUiState.Error(it.message)) }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), NewsUiState.Loading)
// Repository (off-main-thread I/O + parse — see A/§L)
class NewsRepository(private val assets: AssetManager, private val moshi: Moshi) {
    suspend fun news(): List<News> = withContext(Dispatchers.IO) {
        val json = assets.open("news.json").bufferedReader().use { it.readText() }
        moshi.adapter<NewsResponse>().fromJson(json)!!.articles
    }
}
  • Seen in: 04-onefootball (MyNewsActivity.kt), 07-newsapp (MainActivity.java:30-147, extends ListActivity), 09-better-android-refactor-code-class (RestaurantsActivity.kt:37-128, one 90-line subscribe lambda), 10-petapp-android (PetListFragment), 06-halan (ProductsListActivity.java:36-102), 11-dirty-code-exercise (MainActivity.java onCreate), 03-getyourguide (ReviewsFragment.onCreateView), 02-mcrmobile (MainActivity.kt / VehiclesFragment.kt).

A2 — "DI present but fake" (the trap case)

  • Severity: BLOCKER (untestable + misleading)
  • Symptom: Hilt/Dagger annotations and modules exist, but consumers still new their dependencies, or a @Provides method builds a throwaway object. The graph looks wired but isn't.
  • Impact: Zero injection benefit — you can't substitute a fake in tests, and the "architecture" is decorative. This is a classic senior-signal finding: interviewers plant it to see if you read past the annotations.
  • Spot it fast: Search for = NewsRepository( / = SomethingImpl( inside a class that also has an @Inject constructor. Read every @Provides body — if it constructs and returns the same thing it's supposed to inject, it's fake.
  • Before — 01-medibank.../GetNewsListUsecase.kt:24 bypasses the injected graph:

    operator fun invoke(token: String, country: String): Flow<Resource<List<Article>>> {
        val newsRepository = NewsRepository()   // <-- news up its own repo; injection defeated
        ...
    }
}
// NewsRepository.kt:16-25 then builds Retrofit/OkHttp/Moshi inline (not a singleton)
// RepositoryModule.kt:13-16 has a nonsensical circular provider; Logger provider is unused
  • After — inject the repo, provide it once, delete the fake provider:

}
class GetNewsListUseCase @Inject constructor(private val repo: NewsRepository) {

@Provides @Singleton

    .baseUrl(Constants.BASE_URL).client(client)

  • Seen in: 01-medibank (canonical case — GetNewsListUsecase.kt:24, NewsRepository.kt:16-25, RepositoryModule.kt:13-16), 16-kakao (Hilt + Room on classpath, entirely unused; manual getInstance(context) factories), 15-refactoring-testing-android-lab (MainScreen.kt wires the graph inside a composable, never assembled), 13-android-refactoring-start-code (declared Retrofit PhotoApi never called; fake data returned instead).

A3 — No repository / domain seam (transport bleeds into UI)

  • Severity: HIGH
  • Symptom: The view/ViewModel calls the API interface (api.getReviews()) or builds Retrofit itself; there is no Repository type to fake.
  • Impact: Cannot test the ViewModel without a network; mapping logic is scattered; changing the API shape ripples into the UI.
  • Spot it fast: Grep for Retrofit.Builder() and the @GET/@POST interface name — see who calls it directly.
  • Before — 03-getyourguide/.../ReviewsFragment.kt:62-64 calls the API straight from the composable; RetrofitBuilder.kt:15 builds it inline.
  • After — insert a ReviewsRepository interface between API and ViewModel; ViewModel depends on the interface (see A1 After, and 06-testing-di.md for the fake).
  • Seen in: 03-getyourguide, 01-medibank, 08-pair-programming-exercise (ViewModel builds its own API via DependencyProvider), 13-android-refactoring-start-code, 20-refactoring-android (KApplication.java:14 hard-wires new ILoginActionImpl(this)).

A4 — MVP presenter leaks the Activity

  • Severity: HIGH
  • Symptom: A presenter holds a strong reference to the View/Activity and has no detach()/dispose tied to lifecycle.
  • Impact: Memory leak when the presenter outlives the Activity (rotation, back-stack); callbacks fire into a dead view.
  • Before — 12-refactoring-android-app-series/Episode1/.../BooksActivityPresenter.java:10-16 keeps view forever; 10-petapp-android AsyncTask callbacks fire after fragment detach into nulled mContext/mListener.
  • After — hold a nullable view, add detach() in onDestroy, or migrate to ViewModel + viewModelScope so the framework handles lifecycle.
  • Seen in: 12-refactoring-android-app-series, 10-petapp-android, 16-kakao (observeForever never removed — see L6).

§L — Concurrency / Lifecycle

The second-biggest bucket. See 04-concurrency-lifecycle.md for the coroutine/dispatcher deep dive; catalog entries here are the tells.

L1 — GlobalScope.launch (leaks, uncancellable)

  • Severity: HIGH
  • Symptom: GlobalScope.launch { ... } for network/DB work — often with @DelicateCoroutinesApi opted in to silence the warning.
  • Impact: Not tied to any lifecycle → work continues after the screen dies (leak), can't be cancelled, and results may touch a destroyed view. Inside a composable it re-fires on every recomposition.
  • Spot it fast: Grep GlobalScope and @DelicateCoroutinesApi. Both are red flags.
  • Before — 03-getyourguide/.../ReviewsFragment.kt:62-65 — inside setContent, so it re-launches on each recomposition:
setContent {
    var data by remember { mutableStateOf<ReviewResponse?>(null) }
    GlobalScope.launch {              // leaks + refires every recomposition
        val response = api.getReviews()
        data = response
    }
    ...
}
  • After — hoist into a ViewModel with viewModelScope; the composable only reads state:
class ReviewsViewModel(private val repo: ReviewsRepository) : ViewModel() {
    private val _state = MutableStateFlow<ReviewsUiState>(ReviewsUiState.Loading)
    val state = _state.asStateFlow()
    init { load() }
    fun load() = viewModelScope.launch {
        _state.value = runCatching { repo.getReviews() }
            .fold({ ReviewsUiState.Content(it) }, { ReviewsUiState.Error(it.message ?: "") })
    }
}
// composable: val state by viewModel.state.collectAsStateWithLifecycle()
  • Seen in: 03-getyourguide (ReviewsFragment.kt:62), 08-pair-programming-exercise (MainViewModel.kt:16 — viewModelScope imported but unused).

L2 — Hand-rolled CoroutineScope never cancelled

  • Severity: HIGH
  • Symptom: A ViewModel creates its own CoroutineScope(Dispatchers.Main + Job()) and launches into it, but onCleared() never cancels the Job.
  • Impact: Scope leak — coroutines outlive the ViewModel. Also wrong dispatcher default (Main).
  • Spot it fast: Grep CoroutineScope( inside a ViewModel; then check onCleared() exists and calls .cancel().
  • Before — 01-medibank.../NewsListViewModel.kt:23-24,38:
private val customJob = Job()
private val customScope = CoroutineScope(Dispatchers.Main + customJob)  // never cancelled
fun getNews() {
    customScope.launch { getNewsListUseCase(...).collect { _news.value = it } }
}
// no onCleared() -> customJob leaks
  • After — use the framework-managed scope:
fun getNews() = viewModelScope.launch {           // auto-cancelled in onCleared()
    getNewsListUseCase(country.value).collect { _news.value = it }
}
  • Seen in: 01-medibank (NewsListViewModel.kt:23-24,38).

L3 — Main-thread blocking I/O / parsing → ANR

  • Severity: BLOCKER (ANR)
  • Symptom: File reads, JSON parse, DB access, or synchronous HTTP on the UI thread (in onCreate/onResume/click handler).
  • Impact: Frozen UI, ANR dialog, NetworkOnMainThreadException on modern SDKs, StrictMode death on stricter setups.
  • Spot it fast: In lifecycle callbacks, look for assets.open, File, openConnection, JSONObject(, writableDatabase, Thread.sleep, DefaultHttpClient.
  • Before — 13-android-refactoring-start-code/.../MainActivity.kt:38-47 sleeps on the main thread in a click handler; 04-onefootball MyNewsActivity.kt:36-47 reads+parses in onResume; 05-agilevent MainActivity.java:52-56 runs synchronous DefaultHttpClient in onCreate:
// 13-android-refactoring-start-code — main-thread block
button.setOnClickListener {
    progressBar.visibility = View.VISIBLE   // never actually renders — main thread is blocked next line
    Thread.sleep(2000)                      // ANR
    val photos = getPhotos()                // synchronous fake fetch
    ...
}
  • After — move work to a background dispatcher; only touch UI on Main:
viewModel.search(query)   // ViewModel does withContext(Dispatchers.IO) { repo.search(query) }
// UI observes a Loading/Content/Error state and shows the spinner correctly
  • Seen in: 04-onefootball (MyNewsActivity.kt:36-47), 05-agilevent (MainActivity.java:52-56), 13-android-refactoring-start-code (MainActivity.kt:38-47), 16-kakao (KeywordDao.kt:8-9,14-50 — DB on main thread), 07-newsapp (parse on UI thread via postDelayed(...,0)).

L4 — Deprecated AsyncTask for everything

  • Severity: HIGH
  • Symptom: All I/O runs through AsyncTask (deprecated since API 30), often with no lifecycle awareness.
  • Impact: Leaks the Activity, callbacks fire after detach, serial executor bottleneck; deprecated API.
  • Before — 20-refactoring-android/.../ILoginActionImpl.java:49,103,141,174, 06-halan/LoginTask.java, 10-petapp JsonRequestAsyncTask.
  • After — coroutines + repository (suspend fun on Dispatchers.IO), or in Java a bounded ExecutorService + Handler(Looper.getMainLooper()) with a lifecycle-aware cancel.
  • Seen in: 20-refactoring-android, 06-halan, 10-petapp-android, 05-agilevent (imports AsyncTask but never uses it — does the blocking call inline instead).

L5 — Background-thread startActivity / UI mutation

  • Severity: BLOCKER (crash)
  • Symptom: onPostExecute/UI navigation invoked from doInBackground, or UI touched off the main thread.
  • Impact: CalledFromWrongThreadException; also the framework's real callback path never runs.
  • Before — 06-halan/.../LoginTask.java:66,74: doInBackground calls this.onPostExecute(true) itself (bg thread startActivity), then unconditionally return false; so the framework's onPostExecute never navigates.
  • After — return the real result from doInBackground; navigate in the framework onPostExecute (main thread); put the extra the consumer actually reads:
if (success) {
    Intent i = new Intent(context, ProductsListActivity.class);
    i.putExtra("RESPONSE", result);   // the missing extra ProductsListActivity reads (see C3)
    context.startActivity(i);          // no FLAG_ACTIVITY_NEW_TASK for in-app nav
}
  • Seen in: 06-halan (LoginTask.java:66,74).

L6 — observeForever without removal + config-change refetch

  • Severity: HIGH
  • Symptom: observeForever called in init/onCreate and never paired with removeObserver; or a LaunchedEffect(Unit) / onCreate fetch that re-runs on every rotation.
  • Impact: Observer leak; duplicated network calls; state lost on rotation.
  • Before — 16-kakao/.../SearchViewModel.kt:22-24 calls observeForever on a per-call KakaoLocationImpl instance, never removed; 02-mcrmobile uses LaunchedEffect(Unit) inside non-rememberSaveable state so it re-fetches on rotation; 07-newsapp raw Thread+Handler capture the Activity and refetch on rotation.
  • After — use viewModelScope + StateFlow (survives rotation, no manual observer); in Compose, collect from a ViewModel StateFlow, don't launch effects keyed on Unit for one-shot loads.
  • Seen in: 16-kakao (SearchViewModel.kt:22-24), 02-mcrmobile (LaunchedEffect(Unit)), 07-newsapp (MainActivity.java:36,86-146).

§C — Crashes / Correctness

Highest-value category in a review round — these are unconditional blockers. Name them first.

C1 — Unchecked intent-extra cast / null extra

  • Severity: BLOCKER
  • Symptom: intent.getSerializableExtra(...) as News or getParcelableExtra treated as non-null.
  • Impact: NPE / ClassCastException when the extra is absent or the wrong type.
  • Spot it fast: Grep getSerializableExtra, getParcelableExtra, as casts on intent reads.
  • Before — 08-pair-programming-exercise/.../DetailActivity.kt:22:
val newsSelected = intent.getSerializableExtra("newsSelected") as News   // NPE/CCE on null
  • After:
val news = intent.getParcelableExtraCompat<News>(EXTRA_NEWS) ?: run { finish(); return }
  • Seen in: 08-pair-programming-exercise (DetailActivity.kt:22), 14-refactoring-to-kotlin-android (ChangePersonDataActivity.kt:18 treats nullable getParcelableExtra as non-null).

C2 — Non-null bundle / extras dereferenced

  • Severity: BLOCKER
  • Symptom: getIntent().getExtras() (nullable) dereferenced without a null check.
  • Impact: NPE on any launch without the expected extra (deep link, process death, refactor).
  • Before — 07-newsapp/.../DetailViewActivity.java:27-28 derefs getExtras() directly; 14-refactoring-to-kotlin-android/MainActivity.kt:34: onActivityResult(..., data: Intent) typed non-null, but Android passes null on cancel.
  • After — data: Intent? and null-guard every extras read:
override fun onActivityResult(requestCode: Int, resultCode: Int, data: Intent?) {
    super.onActivityResult(requestCode, resultCode, data)
    val updated = data?.getParcelableExtra<Person>(PERSON) ?: return
    ...
}
  • Seen in: 07-newsapp (DetailViewActivity.java:27-28), 14-refactoring-to-kotlin-android (MainActivity.kt:34), 06-halan (ProductDetailsActivity.java:41-56).

C3 — Extra never put, then read (guaranteed NPE)

  • Severity: BLOCKER
  • Symptom: Producer screen forgets to putExtra(...); consumer reads that key and dereferences the result.
  • Impact: 100% crash on the happy path — the app never works.
  • Before — 06-halan: LoginTask never puts the RESPONSE extra, so ProductsListActivity.java:41-55 reads a null bundle and does loginResponse.profile.image → NPE right after login.
  • After — put the extra the consumer reads (see L5 After), and null-guard on read.
  • Seen in: 06-halan (ProductsListActivity.java:41-55).

C4 — Swallowed exception → later NPE

  • Severity: BLOCKER
  • Symptom: catch { } / catch { printStackTrace() } leaves a variable null, which is dereferenced downstream.
  • Impact: NPE far from the real cause; silent failure with no user feedback.
  • Before — 05-agilevent/.../MainActivity.java:66: exception swallowed, response stays null, then dereferenced.
  • After — return a safe default / error state from the catch, and null-guard before use:
if (c.getResponseCode() != 200) return new CommitModel();   // explicit guard
  • Seen in: 05-agilevent (MainActivity.java:66), 07-newsapp (NewsEntity.java:39 swallows JSONException, aborting the media loop), 16-kakao (onFailure only printStackTrace).

C5 — Deprecated adapterPosition / NO_POSITION index

  • Severity: MEDIUM (crash under race)
  • Symptom: list[adapterPosition] or getItem(adapterPosition) in a click listener without checking NO_POSITION (-1).
  • Impact: IndexOutOfBoundsException when the item is removed/animating at click time.
  • Before — 02-mcrmobile/.../VehiclesFragment.kt:52-62 (vehicles[adapterPosition] + requireContext() in click); 13-android-refactoring-start-code/PhotoAdapter.kt:45 (getItem(adapterPosition) can be -1).
  • After — use bindingAdapterPosition and guard:
holder.itemView.setOnClickListener {
    val pos = holder.bindingAdapterPosition
    if (pos != RecyclerView.NO_POSITION) onClick(getItem(pos))
}
  • Seen in: 02-mcrmobile (VehiclesFragment.kt:52-62), 13-android-refactoring-start-code (PhotoAdapter.kt:45).

C6 — Wrong data bound / user-visible text bug

  • Severity: MEDIUM
  • Symptom: The wrong field is displayed, or strings concatenated without separators.
  • Impact: Visibly wrong UI — an easy, concrete finding.
  • Before — 02-mcrmobile/.../VehiclesFragment.kt:69: model + " " + model (should be brand + " " + model); 19-android-ejemplo/Buses.java:13-25: missing separators render "...gasesSistema de Audio.".
  • After — bind the correct field / add separators (prefer a formatted string resource: getString(R.string.vehicle_label, brand, model)).
  • Seen in: 02-mcrmobile (VehiclesFragment.kt:69), 19-android-ejemplo (Buses.java:13-25).

C7 — Parallel arrays indexed by position (no bounds guard)

  • Severity: BLOCKER (AIOOBE)
  • Symptom: Two arrays (TITLES[], DETAILS[]) kept in sync by index, accessed by list position with no bounds check.
  • Impact: ArrayIndexOutOfBoundsException; fragile data coupling (edit one array, forget the other).
  • Before — 19-android-ejemplo/.../DetailsFragment.java:40 + Buses.java.
  • After — one model list:
public final class Bus { public final String code; public final int passengers; /* + flags */ }
// bind: text.setText(getString(R.string.bus_details, bus.passengers));
  • Seen in: 19-android-ejemplo (DetailsFragment.java:40, Buses.java).

C8 — Unguarded implicit intent (ACTION_VIEW)

  • Severity: MEDIUM (crash)
  • Symptom: startActivity(Intent(ACTION_VIEW, uri)) with no resolver check.
  • Impact: ActivityNotFoundException when no app handles the URI.
  • Before — 04-onefootball/.../MyNewsActivity.kt:86-90.
  • After:

if (intent.resolveActivity(packageManager) != null) startActivity(intent)
else Toast.makeText(this, R.string.no_browser, Toast.LENGTH_SHORT).show()
  • Seen in: 04-onefootball (MyNewsActivity.kt:86-90).

C9 — Does-not-compile / missing symbols

  • Severity: BLOCKER
  • Symptom: References to classes/constants that don't exist; missing dependency for a used type.
  • Impact: The project doesn't build — nothing else matters. Establish this first (see 01-code-review-method.md — "does it build?").
  • Before — 11-dirty-code-exercise/MainActivity.java:32-33 references MainPresenterImpl/marvel_updating (don't exist); 15-refactoring-testing-android-lab/MainScreen.kt:14 calls UserManager() no-arg though ctor needs (validator, repository, emailService); 20-refactoring-android/HttpEngine.java uses Gson/TypeToken with no Gson dependency declared, plus HttpUrlConnection/KeyRep.Type typos and missing classes (EncryptUtil, ErrorEvent, CouponPriceUtil, CouponBO.TYPE_*).
  • After — supply the missing type / dependency / constructor args; fix the signature mismatch.
  • Seen in: 11-dirty-code-exercise, 15-refactoring-testing-android-lab, 20-refactoring-android.

C10 — when/switch over continuous or exhaustive-looking values

  • Severity: MEDIUM
  • Symptom: when over a Double using overlapping Int ranges; switch(status) handling only 200 with no default.
  • Impact: Wrong branch chosen; error statuses silently ignored.
  • Before — 14-refactoring-to-kotlin-android/whenWeather.kt:8-9 (in -50..0, in 0..15 overlap at 0, and Int ranges never match a Double); 06-halan/LoginTask.java:63-67 (switch(status) only 200).
  • After — use Double comparisons / add an else / default that surfaces an error state.
  • Seen in: 14-refactoring-to-kotlin-android, 06-halan, 20-refactoring-android (200-only status).

C11 — Missing return after a validation failure

  • Severity: BLOCKER (logic)
  • Symptom: A guard logs/reports an error but doesn't return, so execution continues.
  • Impact: Invalid request still fires; downstream state corrupted.
  • Before — 20-refactoring-android/.../ILoginActionImpl.java:165-169: listCoupon reports failure but omits return, firing the request anyway.
  • After — return immediately after reporting the failure.
  • Seen in: 20-refactoring-android (ILoginActionImpl.java:165-169).

C12 — NPE in model getters / !! in comparators

  • Severity: MEDIUM
  • Symptom: Getter dereferences nullable fields; comparator uses !! and integer subtraction.
  • Impact: NPE; also Int overflow in a - b comparators.
  • Before — 11-dirty-code-exercise/Marvel.java:16-18 (getThumbnailURL() derefs thumbnail.path/.extension); 09-better.../Restaurant.kt:14-16 (p0!!.distance - p1!!.distance).
  • After:
val sorted = filtered.sortedBy { it.distance }   // null-safe, no overflow
  • Seen in: 11-dirty-code-exercise, 09-better-android-refactor-code-class.

§N — Networking

See 05-networking-parsing.md for the full HTTP/OkHttp/Retrofit treatment. Catalog tells:

N1 — Retrofit/HTTP client built inline (not a singleton)

  • Severity: HIGH
  • Symptom: Retrofit.Builder() inside a repository/fragment; no shared OkHttp; no timeouts/logging/interceptors.
  • Impact: Wasteful (new connection pool each time), untestable, inconsistent config, no timeouts → hangs.
  • Before — 01-medibank/NewsRepository.kt:16-25, 03-getyourguide/RetrofitBuilder.kt:15, 02-mcrmobile DependencyContainer (default client, no timeouts).
  • After — provide OkHttpClient and Retrofit as singletons through DI with explicit timeouts + a logging interceptor (debug only).
  • Seen in: 01-medibank, 03-getyourguide, 02-mcrmobile, 11-dirty-code-exercise.

N2 — No error handling on the call

  • Severity: BLOCKER
  • Symptom: No try/catch, no non-2xx check; failure crashes or spins forever.
  • Impact: App crash on any timeout/4xx/parse error; infinite spinner; no error UI.
  • Before — 08-pair-programming-exercise/MainViewModel.kt:16-28 (no try/catch; failure sets news.value=null into a non-null showNews(ArrayList<News>)); 16-kakao/KakaoLocationImpl.kt:26-35 (non-2xx ignored, onFailure only prints).
  • After — wrap in runCatching/try-catch, map to UiState.Error, check response.isSuccessful.
  • Seen in: 08-pair-programming-exercise, 16-kakao, 03-getyourguide, 07-newsapp, 09-better (.subscribe({...}, {}) empty error consumer at RestaurantsActivity.kt:126).

N3 — Dead / cleartext endpoint, no timeout/status/retry

  • Severity: BLOCKER (app non-functional / insecure)
  • Symptom: Hardcoded dead URL (e.g. api.myjson.com, GitHub API v2), http:// cleartext, no timeout, no disconnect, only 200 handled.
  • Impact: App shows empty list forever; cleartext blocked by modern targetSdk; connection leaks.

§P — Parsing / Models

See 05-networking-parsing.md. The recurring theme: models lie about nullability, and hand-rolled parsing is brittle.

P1 — Non-null model fields vs real API nulls

  • Severity: BLOCKER
  • Symptom: DTO declares author: String, publishedAt: Date non-null, but the API returns null/ISO-8601 strings.
  • Impact: Gson NPE / JsonSyntaxException on real responses; app crashes off the happy path.
  • Before — 08-pair-programming-exercise/News.kt:6-15:
class News(val author: String, val urlToImage: String, val publishedAt: Date, ...) : Serializable
  • After — nullable fields, String (or a Moshi/Gson adapter) for dates, @Parcelize:
@Parcelize
data class News(
    val source: Source, val author: String?, val title: String, val description: String?,
    val url: String, val urlToImage: String?, val publishedAt: String?, val content: String?
) : Parcelable
  • Seen in: 08-pair-programming-exercise (News.kt:6-15), 01-medibank (Article.kt:11,12 non-null title/url from nullable ArticleDto.kt:20-24, .orEmpty() → blank WebView).

P2 — Crash-prone date parsing, recomputed per frame

  • Severity: HIGH
  • Symptom: LocalDateTime.parse(str, ofPattern("...z")) in a composable/bind; strict pattern throws on offset/Z/fractional seconds; recomputed on every recomposition.
  • Impact: DateTimeParseException crash; wasted work per frame.
  • Before — 03-getyourguide/.../ReviewsFragment.kt:105-108:
val dateText = LocalDateTime.parse(
    review.created,
    DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ssz")   // throws on Z/offset/fractional
).format(DateTimeFormatter.ofPattern("MMM dd, yyyy"))
  • After — tolerant parse in the mapping layer, never crash the row:
fun String.toDisplayDate(): String =
    runCatching { OffsetDateTime.parse(this) }
        .map { it.format(DateTimeFormatter.ofPattern("MMM dd, yyyy")) }
        .getOrDefault("")
  • Seen in: 03-getyourguide (ReviewsFragment.kt:105-108).

P3 — Fragile manual JSON parsing (getString/getInt per field)

  • Severity: HIGH
  • Symptom: JSONObject.getString("key")/getInt("key") for every field; one missing key throws and aborts the loop. inputStream.read(buffer) return value ignored (truncation).
  • Impact: JSONException on any schema drift; corrupted/partial data; truncated reads.
  • Before — 07-newsapp/MediaEntity.java:19-28; 04-onefootball/MyNewsActivity.kt:41 ignores read() return.
  • After — use opt* with defaults and iterate defensively (or switch to Moshi/Gson with @Json):
url = o.optString("url", null); height = o.optInt("height", 0); caption = o.optString("caption", "");
JSONArray media = o.optJSONArray("multimedia");
if (media != null) for (int i = 0; i < media.length(); i++) {
    JSONObject m = media.optJSONObject(i);
    if (m != null) list.add(new MediaEntity(m));   // one bad item doesn't abort the rest
}

And for the read: assets.open("news.json").bufferedReader().use { it.readText() }.

  • Seen in: 07-newsapp (MediaEntity.java:19-28, NewsEntity.java:39), 04-onefootball (MyNewsActivity.kt:41,49-64).

P4 — Serializable instead of @Parcelize; hand-rolled Parcelable

  • Severity: LOW (perf/maintenance)
  • Symptom: Intent extras use Serializable; or a hand-written Parcelable with manual read/write order.
  • Impact: Slow reflection-based serialization; hand-rolled Parcelable has a write/read-order maintenance trap.
  • Before — 08-pair-programming-exercise/News.kt:15 (Serializable), 14-refactoring-to-kotlin-android/Person.kt (hand-rolled Parcelable).
  • After — @Parcelize data class ... : Parcelable.
  • Seen in: 08-pair-programming-exercise, 14-refactoring-to-kotlin-android.

P5 — Stringly-typed enums; type-unsafe mapping in impl

  • Severity: MEDIUM
  • Symptom: type: String with a when/switch over string literals and no else; parsing coordinates with unguarded toDouble().
  • Impact: Silent no-match; crashes on unexpected value.
  • Before — 09-better/RestaurantsAdapter.kt:45-61 (when over "TAKE_AWAY"/"EAT_IN"… no else); 16-kakao/KakaoLocationImpl.kt:38-48 (it.x.toDouble() throws on non-numeric).
  • After — model as an enum carrying its resources:

    TAKE_AWAY(R.drawable.take_away, R.string.type_take_away),
    EAT_IN(R.drawable.eat_in, R.string.type_eat_in),
    DRIVE_THROUGH(R.drawable.drive_through, R.string.type_drive_through);
}
  • Seen in: 09-better-android-refactor-code-class, 16-kakao.

P6 — equals called on a possibly-null receiver

  • Severity: MEDIUM (NPE)
  • Symptom: nullableVar.equals("0") (Java) instead of "0".equals(nullableVar).
  • Before — 20-refactoring-android/ApiResponse.java:19.
  • After — "0".equals(event) (literal as receiver), or Objects.equals(...).
  • Seen in: 20-refactoring-android.

§T — Testability / Tests

See 06-testing-di.md for the full testing/DI playbook. The catalog tells that a test is theater, not verification:

T1 — Mock created but never injected (test hits real network)

  • Severity: BLOCKER (false confidence)
  • Symptom: mock() created in setUp, but the subject-under-test constructs its own real dependency, so the mock is never used. The test passes by accident, sometimes hitting the live network.
  • Impact: The test proves nothing; it's flaky and slow, and lulls reviewers into trusting untested code.
  • Before — 08-pair-programming-exercise/MainViewModelTest.kt:36-50:
newsAPI = mock()
mainViewModel = MainViewModel()   // builds its own real Retrofit; the mock is orphaned

  • After — inject the mock via the constructor and assert real behavior:
mainViewModel = MainViewModel(newsAPI)   // inject the mock

Assert.assertEquals(NewsUiState.Success(articles), mainViewModel.state.getOrAwaitValue())
  • Seen in: 08-pair-programming-exercise (MainViewModelTest.kt:36-50), 01-medibank (GetNewListUsecaseTest.kt:36 — mocks the repo but the use case news up its own; also uses delay(1000) instead of a TestDispatcher).

  • Severity: HIGH

T3 — Tests that hit the live network / use disabled assert

  • Impact: Flaky, slow, network-dependent; assert-based tests silently never fail.
  • Before — 07-newsapp/APIAvailabilityTest.java:14-26 (live net + assert keyword), 10-petapp/ApiAvailabilityUnitTest.java (real HTTP to dead endpoints).

T4 — Test infra that won't compile / misplaced tests

  • Severity: HIGH
  • Symptom: Uses removed APIs (TestCoroutineScope, ApplicationTestCase); test files in src/main (shipped in the APK); mocking a Kotlin object.
  • Impact: Tests don't run; test code ships to production; Mockito can't mock a final object.

  • Severity: HIGH
  • Symptom: All logic in a lambda/Activity; nothing to instantiate in isolation; only placeholder tests exist.
  • Impact: Can't test without an emulator and a network.
  • Before/After — introduce a repository interface + inject it; extract pure functions (mapping, distance math) that are trivially unit-testable.
  • Seen in: 04, 02, 09, 11, 13, 14, 19, 20 (all placeholder tests + no seams). Positive counter-example: 12-refactoring-android-app-series actually tests both presenter branches (but uses deprecated junit.framework.Assert and brittle size()==3).

S1 — Committed API key / secret (the headline finding)

  • Severity: BLOCKER
  • Symptom: An API key hardcoded in a source constant, committed to VCS and baked into the APK.
  • Impact: Secret is leaked in git history and every shipped APK (decompilable). Rotating it is the only fix — and it must never have been committed.
  • Spot it fast: Grep for const val.*=.*"[A-Za-z0-9]{20,}", apiKey, TOKEN, Constants.kt/Constants.java.
  • Before — 01-medibank/.../common/Constants.kt:6:

17.3 Architecture: MVVM, MVP & Clean

Every single one of the 20 exercise repos fails on architecture. It is the most common finding category (14 distinct instances in the evidence pack) and it is almost always the headline deliverable of a refactor exercise. If you get architecture right, most of the concurrency, testability, and error-handling findings fall out for free. This module is the spine of the whole kit.

1. The patterns, in one screen

The interviewer wants you to (a) name the pattern the code uses, (b) name the pattern it should use, and (c) justify the difference in terms of testability, lifecycle safety, and separation of concerns. Here is the vocabulary you must be fluent in.

Pattern State lives in View knows about Testable off-device? Survives config change? Typical smell that flags it
MVC (Android's accidental default)The Activity/Fragment is the controllerEverythingNoNo"god Activity/Fragment"
MVPPresenterView via an interfaceYes (presenter is plain Java/Kotlin)Only if presenter is retainedPresenter holds a strong Activity ref, no detach()
MVVMViewModel (+ observable state)Nothing about the ViewModel's internalsYesYes (ViewModel outlives config change)Logic in the composable/Activity, GlobalScope, state lost on rotation
MVISingle immutable UiState, reduced from IntentsOne render(state) sinkYesYesAd-hoc LiveData per field instead of one state object

Clean Architecture is orthogonal to the above — it's about layering (presentation / domain / data) and dependency direction, and it composes with MVVM or MVP. You can have "MVVM but no layers" (logic dumped in the ViewModel) or "layered but no MVVM." The good answer is usually MVVM + a repository + (optionally) use cases.

How to say it in the room

"This is effectively MVC — the Activity is the controller, view, and model all at once. I'd move to MVVM so state survives rotation and the logic becomes unit-testable, and I'd introduce a repository so the ViewModel doesn't know about Retrofit."

That one sentence hits pattern name → why → concrete first step. That is what "senior" sounds like.

3. Layering: presentation / domain / data

Clean Architecture in Android is three layers with a strict dependency direction: presentation → domain → data, where domain is the pure center that depends on nothing Android.

┌─────────────── presentation ───────────────┐
│  Activity/Fragment/Composable  ·  ViewModel │  (Android, coroutines, UiState)
└───────────────────┬─────────────────────────┘
                    │ calls  ▼
┌─────────────────── domain ──────────────────┐
│  UseCase / Interactor  ·  domain models      │  (pure Kotlin, no Android imports)
│  Repository *interfaces*                     │
└───────────────────┬─────────────────────────┘
                    │ implemented by  ▼
┌──────────────────── data ───────────────────┐
│  RepositoryImpl · Retrofit/Room · DTOs · map │  (Android, network, DB)
└──────────────────────────────────────────────┘

Key rules the reviewer checks:

  • The ViewModel must not import Retrofit/OkHttp/Room. It talks to a repository interface. In ../01-medibank-ventures-code-review-exercise-android/ the repo builds Retrofit inline (NewsRepository.kt:16-25) and the use case does NewsRepository() (GetNewsListUsecase.kt:24) — the layering exists on paper (Hilt is configured) but is bypassed. This is the "DI present but fake" trap; details in ./06-testing-di.md.
  • The repository interface lives in domain; its impl lives in data. That's what lets you swap a FakeRepository in tests. In ../03-getyourguide-android-challenge/ there is no repository at all — ReviewsFragment.onCreateView builds Retrofit and calls the API directly, so nothing is testable.
  • DTOs ≠ domain models. Data layer parses ArticleDto (nullable fields, @Json names); domain exposes a clean Article. Map at the boundary. Medibank maps nullable DTO fields into non-null domain fields with .orEmpty() (Article.kt:11,12 vs ArticleDto.kt:20-24) — a blank url silently yields a blank WebView. Parsing/model detail: ./05-networking-parsing.md.

Do you always need use cases?

No — and saying so is a senior signal. Use cases (interactors) earn their place when there's real domain logic to encapsulate or reuse: ../09-better-android-refactor-code-class/ filters restaurants, computes Haversine distance, sorts, and maps — that's a GetNearbyRestaurantsUseCase, not something to smear across an Activity lambda (RestaurantsActivity.kt:37-128). For a screen that just fetches-and-shows (OneFootball, GetYourGuide), a ViewModel → Repository is enough; a pass-through use case is ceremony. Say: "I'd add use cases where there's domain logic to test in isolation; for a straight fetch I'd let the ViewModel call the repository directly."

4. UDF, state hoisting, and modeling UiState

Unidirectional Data Flow (UDF): state flows down (ViewModel → UI) and events flow up (UI → ViewModel). The UI is a pure function of state; the ViewModel is the single source of truth. This is the mental model behind both Compose and modern View-based screens.

State hoisting (Compose term, but the idea is universal): a composable should be stateless and receive its state + callbacks from above, so the owner of the state is the ViewModel, not the widget. ../02-mcrmobile-Android-Refactoring/ and ../03-getyourguide-android-challenge/ violate this by putting remember/network/state inside the leaf composable, so state dies on rotation.

Model UiState as a sealed class

The single most reusable architecture artifact for this interview. A screen has exactly one state at a time — model it as a sealed hierarchy, expose it as one StateFlow, and the UI does an exhaustive when:

sealed interface NewsUiState {
    data object Loading : NewsUiState
    data class Content(val articles: List<Article>) : NewsUiState
    data class Error(val message: String) : NewsUiState
    data object Empty : NewsUiState            // optional but shows you thought about it
}

class NewsViewModel(private val repo: NewsRepository) : ViewModel() {
    private val _state = MutableStateFlow<NewsUiState>(NewsUiState.Loading)
    val state: StateFlow<NewsUiState> = _state.asStateFlow()

    init { load() }

    fun load() = viewModelScope.launch {                       // lifecycle-scoped — see ./04
        _state.value = NewsUiState.Loading
        _state.value = runCatching { repo.getNews() }
            .fold(
                onSuccess = { if (it.isEmpty()) NewsUiState.Empty else NewsUiState.Content(it) },
                onFailure = { NewsUiState.Error(it.message ?: "Something went wrong") },
            )
    }
}
// Compose: state down, events up. The screen renders state; it owns none.
@Composable
fun NewsScreen(state: NewsUiState, onRetry: () -> Unit) = when (state) {
    NewsUiState.Loading      -> LoadingSpinner()
    NewsUiState.Empty        -> EmptyMessage()
    is NewsUiState.Content   -> NewsList(state.articles)
    is NewsUiState.Error     -> ErrorMessage(state.message, onRetry)
}

Why the interviewer loves this:

  • It forces you to handle Loading and Error, which is the #1 missing behavior across the kit — GetYourGuide has "an infinite spinner or crash" because there is no Error state at all (ReviewsFragment.kt:63), and Pair-Programming crashes on failure because it sets news.value = null into a non-null ArrayList<News> (MainViewModel.kt:17/26).
  • data object Loading/Empty and is Content/Error make the UI when exhaustive — add a state and the compiler finds every screen that must handle it.
  • It's trivially testable: assert state.value transitions Loading → Content / Loading → Error. (Turbine example in ./06-testing-di.md.)

Note vs Resource<T> / Result: Medibank uses a generic Resource sealed class — fine, but a per-screen UiState is usually clearer because it can carry screen-specific fields (e.g. isRefreshing, query). Mention both; prefer per-screen UiState for the presentation layer and Result/runCatching at the repository boundary.

The refactor, one dependency-inverting step at a time

Step 0 — establish the seam (interface first). Decide the boundary before moving code. The ViewModel will depend on this, not on assets:

// domain
interface NewsRepository { suspend fun getNews(): List<News> }

Step 1 — push I/O + parsing into a data-layer repository, off the main thread. This kills the ANR, the truncation bug, and the missing exception handling in one move:

// data
class AssetNewsRepository(
    private val assets: AssetManager,
    private val io: CoroutineDispatcher = Dispatchers.IO,   // injectable → testable, see ./06
) : NewsRepository {
    override suspend fun getNews(): List<News> = withContext(io) {
        val json = assets.open("news.json").bufferedReader().use { it.readText() }  // no truncation
        NewsParser.parse(json)                              // pure function → unit-testable
    }
}

Step 2 — introduce the ViewModel with UiState. State now survives rotation and loads once, not every resume:

class NewsViewModel(private val repo: NewsRepository) : ViewModel() {
    private val _state = MutableStateFlow<NewsUiState>(NewsUiState.Loading)
    val state: StateFlow<NewsUiState> = _state.asStateFlow()
    init { load() }                                          // load once, not in onResume
    fun load() = viewModelScope.launch {
        _state.value = runCatching { repo.getNews() }
            .fold({ NewsUiState.Content(it) }, { NewsUiState.Error(it.message ?: "…") })
    }
}

Step 3 — the Activity becomes a thin, dumb observer. It owns no logic and no mutable state:

class MyNewsActivity : AppCompatActivity() {
    private val vm: NewsViewModel by viewModels { /* factory or Hilt */ }
    private val adapter = NewsAdapter()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        findViewById<RecyclerView>(R.id.newsRecyclerView).adapter = adapter
        lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {     // collector detail → ./04
                vm.state.collect { render(it) }
            }
        }
    }
    private fun render(state: NewsUiState) { /* show spinner / list / error */ }
}

Step 4 — extract the adapter/viewholder to their own files, and prefer ListAdapter + DiffUtil over notifyDataSetChanged().

Step 5 — wire the graph. Provide AssetNewsRepository via Hilt (@Provides) or a ViewModelProvider.Factory. See ./06-testing-di.md.

The scorecard: main-thread I/O gone, crash-on-error gone (now an Error state), truncation gone, reload-per-resume gone, state survives rotation, and the parser + repository + ViewModel are all unit-testable without a device — from one 110-line file. That is the entire exercise.

6. Config-change survival — why state belongs in the ViewModel

When the device rotates (or locale/dark-mode/keyboard changes), Android destroys and recreates the Activity/Fragment. Anything held in an Activity field, a composable's remember, or a fragment's local var is gone. This is the root cause behind a cluster of findings:

  • ../02-mcrmobile-Android-Refactoring/ — LaunchedEffect(Unit) in the composable re-fires the network call on every rotation, and there's no rememberSaveable/ViewModel, so results are lost.
  • ../03-getyourguide-android-challenge/ — state lives in onCreateView; rotation wipes the loaded reviews and refetches (via a leaking GlobalScope no less).
  • ../13-android-refactoring-start-code/ — MainViewModel is an empty stub (MainViewModel.kt:6-7); all state is in the Activity, so rotation wipes the search results.
  • ../07-newsapp-Ques_NewsApp_Android_challenge/ — a raw Thread + Handler refetch on rotation and leak the Activity.

Why ViewModel is the correct home: it is scoped to the ViewModelStoreOwner and survives configuration changes — the same instance is handed back to the recreated Activity. So state placed in the ViewModel (the loaded list, the current query, the UiState) is intact after rotation, and in-flight viewModelScope work keeps running instead of being cancelled-and-restarted. It's only cleared in onCleared() when the owner is finally finished (real back-press, not rotation).

The layered rule of thumb:

  • UI-transient / large data → ViewModel (list results, UiState, in-flight jobs).
  • Small UI state that must survive process death, not just rotation → SavedStateHandle (a query string, selected tab). ViewModel alone does not survive process death; SavedStateHandle (backed by onSaveInstanceState) does.
  • Never rely on setRetainInstance(true) (deprecated) — that's the old hack PetApp used, and it doesn't cancel work.

Interview one-liner: "State that must outlive a rotation goes in the ViewModel; state that must outlive process death goes in SavedStateHandle. It should never live in the Activity."

Two ways to organize the source tree — the reviewer may ask which you prefer.

package-by-LAYER                     package-by-FEATURE
────────────────                     ──────────────────
com.app/                             com.app/
 ├─ data/                             ├─ news/
 │   ├─ NewsRepository                │   ├─ NewsRepository
 │   ├─ ReviewsRepository             │   ├─ NewsViewModel
 │   └─ ...                           │   ├─ NewsScreen
 ├─ domain/                           │   └─ NewsUiState

 │   ├─ ReviewsViewModel              │   ├─ ReviewsViewModel
 │   └─ ...                           │   └─ ReviewsScreen
 └─ di/                               └─ core/ (shared: network, di, ui)
  • Package-by-layer groups by technical role (all repositories together, all ViewModels together). Fine for a tiny sample; Medibank uses it. It scales badly: a single feature's files are scattered, and it invites accidental cross-feature coupling.
  • Package-by-feature groups by domain concept — everything for "news" in one package. It scales, keeps changes localized, makes a feature easy to delete or move to its own module, and enforces boundaries.

../09-better-android-refactor-code-class/ makes this concrete: its refactor arc ends on the 24-packages-by-feature-solution branch (see the branch list in ../09-better-android-refactor-code-class/SOLUTION.md) — the final step after splitting responsibilities is reorganizing package-by-feature. ../02-mcrmobile-Android-Refactoring/ is a middle ground: it splits by build module (compose/, xml/) which is coarse feature separation.

Balanced answer: "For anything beyond a toy, I default to package-by-feature — it localizes change and is the natural precursor to modularization. Within a feature I still keep the layer split (data/domain/ui). Package-by-layer at the top level only works while the app is small."

17.4 Concurrency & Lifecycle

This module is the single most cited failure category across the 20 review repos: 13 concurrency/lifecycle defects (tied with only Crashes/Correctness for the top spot). It is also the category interviewers probe hardest, because it separates "makes the happy path work" from "understands Android." Master the four questions below and you can diagnose almost every case in the evidence pack:

  1. What thread is this running on? (main-thread rule / ANR)
  2. Who owns this coroutine, and when does it get cancelled? (scopes / structured concurrency)
  3. What happens on rotation / recomposition? (config-change survival)
  4. How does the UI observe state, and is that observation lifecycle-safe? (StateFlow/LiveData collection)

Architecture layering (where the ViewModel/repository live) is covered in ./03-architecture-mvvm-clean.md; networking/parsing details in ./05-networking-parsing.md; testing dispatchers in ./06-testing-di.md. This module stays on threading, scopes, cancellation, and lifecycle.

1. The main-thread rule & ANR

Android has exactly one UI thread ("main"). Two hard rules:

  • Only the main thread may touch the UI. Touching a View/Compose state from a background thread throws CalledFromWrongThreadException.
  • The main thread must never block. If it is blocked for ~5s (input) / ~10s (broadcast), the system raises an ANR ("Application Not Responding"). Even sub-second blocking causes jank and dropped frames (16.6ms budget at 60fps).

What blocks the main thread, in order of frequency in the repos:

Blocking op Repo evidence

File / disk I/O + JSON parse on main thread04-onefootball MyNewsActivity.kt:36-47

Cautionary case A — OneFootball: file I/O + parse in onResume()

04-onefootball-coding_challenge_android/app/src/main/java/com/onefootball/MyNewsActivity.kt:36-47:

override fun onResume() {
    super.onResume()
    var inputStream = assets.open("news.json")   // disk I/O on MAIN thread
    val size = inputStream.available()
    val buffer = ByteArray(size)
    inputStream.read(buffer)                      // + return value ignored → truncation bug
    inputStream.close()
    jsonString = buffer.toString(Charset.defaultCharset())
    val items = parseJsonString(jsonString!!)     // JSON parse on MAIN thread; !! can NPE; no try/catch
    myAdapter.setNewsItems(items)
}

Three interview talking points in one method:

  • Thread: assets.open + read + JSONObject(...) parse are all synchronous on the main thread → ANR on a large asset.
  • Lifecycle: it's in onResume(), which fires on every return-to-foreground (e.g. after a phone call, notification-shade dismiss), so the work re-runs needlessly. onCreate would run once; the data doesn't change, so even onCreate is the wrong place — it belongs in a ViewModel that survives config changes.
  • Robustness: no try/catch; parseJsonString(jsonString!!) crashes on any I/O or schema error. (Parsing detail in ./05-networking-parsing.md.)

Fix — push I/O off-main via a repository on Dispatchers.IO, expose state, load once:

class NewsRepository(private val assets: AssetManager, private val moshi: Moshi) {
    suspend fun loadNews(): List<News> = withContext(Dispatchers.IO) {   // off main thread
        val json = assets.open("news.json").bufferedReader().use { it.readText() }  // read fully, auto-close
        moshi.adapter(NewsFeed::class.java).fromJson(json)?.news.orEmpty()
    }
}

class NewsViewModel(private val repo: NewsRepository) : ViewModel() {
    private val _state = MutableStateFlow<UiState>(UiState.Loading)
    val state: StateFlow<UiState> = _state.asStateFlow()
    init { load() }                                  // ONCE, survives rotation — not per onResume
    fun load() = viewModelScope.launch {
        _state.value = runCatching { repo.loadNews() }
            .fold({ UiState.Content(it) }, { UiState.Error(it) })
    }
}

bufferedReader().use { readText() } also fixes the ignored-read()-return truncation bug for free — see ../04-onefootball-coding_challenge_android/SOLUTION.md and evidence snippet S3.

2. Dispatchers: pick the right thread pool

Dispatchers are the coroutine equivalent of thread pools. You almost never create your own; you withContext(...) onto the right one.

Dispatcher Backing Use for
Dispatchers.MainThe single UI threadTouching Views/LiveData, updating Compose state. Default for viewModelScope/lifecycleScope.
Dispatchers.IOLarge elastic pool (~64 threads)Blocking I/O: disk, DB, File, okhttp sync calls, assets.open.

Rules of thumb:

  • Retrofit suspend functions already switch to a background thread — you do not wrap them in withContext(Dispatchers.IO). Room suspend/Flow DAOs do too. The withContext(IO) wrapper is for manual blocking I/O (like OneFootball's assets.open, or the raw HttpURLConnection in the Java repos).
  • Keep the switch inside the lowest layer (repository/data source), not the ViewModel. The ViewModel launches on Main; the repository does withContext(IO). That way callers never have to remember.
  • 09-better-android-refactor-code-class shows the Default mistake in RxJava terms: heavy distance math + list transforms run inside observeOn(AndroidSchedulers.mainThread()) (RestaurantsActivity.kt:70-110) — CPU work on the UI thread. It should be subscribeOn/observeOn(Schedulers.computation()) upstream, only the final bind on main. (RxJava threading — §8.)
// Repository owns the thread switch; ViewModel stays on Main
class RestaurantsRepository(private val api: Api) {
    suspend fun nearby(location: LatLng): List<Restaurant> = withContext(Dispatchers.Default) {
        api.fetch()                     // (already background if suspend Retrofit)
            .map { it.toDomain() }
            .filter { it.isOpenNow() }
            .sortedBy { it.distanceTo(location) }   // CPU-bound → Default, not Main
    }
}

3. Scopes: viewModelScope, lifecycleScope, repeatOnLifecycle

A CoroutineScope ties a coroutine's lifetime to a component. When the component dies, the scope is cancelled and every child coroutine stops. Getting the scope right is what makes work cancellable and leak-free. Getting it wrong is the #1 concurrency finding in the pack.

The three scopes you should actually use

// 1. In a ViewModel — cancelled automatically in onCleared()
class MyViewModel : ViewModel() {
    fun load() = viewModelScope.launch { /* survives config change; dies with the ViewModel */ }
}

// 2. In an Activity/Fragment for UI-only work tied to the component lifecycle
class MyFragment : Fragment() {
    fun onClick() = lifecycleScope.launch { /* cancelled in onDestroy */ }
}

// 3. Collecting a Flow safely in a View-based UI (see §6)
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.state.collect { render(it) }   // collection auto-stops in onStop, restarts in onStart
    }
}

viewModelScope uses Dispatchers.Main.immediate + a SupervisorJob by default, and is cancelled in ViewModel.onCleared(). That single fact fixes most of the bugs below.

Anti-pattern 1 — GlobalScope.launch

GlobalScope is application-lifetime. Coroutines launched there are never cancelled by any component, so:

  • If the coroutine holds a reference to a View/Activity/Fragment (directly or via a callback), you leak it until the coroutine completes.
  • If it updates UI state, it may fire after the screen is gone.
  • In Compose, launching it during composition re-fires on every recomposition.

03-getyourguide — ReviewsFragment.kt:62-65 (the canonical case):

setContent {
    var data by remember { mutableStateOf<ReviewResponse?>(null) }
    GlobalScope.launch {              // ← launched during composition
        val response = api.getReviews()
        data = response
    }
    data?.let { /* render */ }
    if (data == null) { CircularProgressIndicator(...) }
}

Three defects: (1) GlobalScope → not cancelled when the screen leaves, leaks the composition; (2) it's inside setContent, so it re-launches a new network call on every recomposition; (3) no error branch — a failure leaves data == null forever → infinite spinner.

08-pair-programming-exercise — MainViewModel.kt:11,16: GlobalScope.launch used even though viewModelScope is already imported (@DelicateCoroutinesApi then propagates through the class). The fix is a one-word change:

// BEFORE
GlobalScope.launch { news.value = repo.getNews("apple") }
// AFTER
viewModelScope.launch { _state.value = repo.getNews("apple") }

The @DelicateCoroutinesApi/@OptIn annotation is itself a code smell flare: the compiler is telling you GlobalScope is delicate. If you see that opt-in, look for the scope bug.

Anti-pattern 2 — hand-rolled CoroutineScope(...) never cancelled

Creating your own CoroutineScope(Dispatchers.Main + Job()) inside a ViewModel is a leak unless you cancel it in onCleared() — and nobody ever does.

01-medibank — NewsListViewModel.kt:23-24,38:

// BEFORE — a private Job()-backed scope, never cancelled in onCleared()
private val customScope = CoroutineScope(Dispatchers.Main + Job())
fun getNews() = customScope.launch { /* ... */ }
// AFTER — let the framework own the lifetime
fun getNews() = viewModelScope.launch {
    getNewsListUseCase(country.value).collect { _news.value = it }
}

Why it matters: when the Activity is destroyed and the ViewModel is cleared, customScope's Job is still active. Any in-flight coroutine keeps running and keeps the ViewModel (and whatever it captured) alive. viewModelScope cancels in onCleared() — free correctness. See ../01-medibank-ventures-code-review-exercise-android/SOLUTION.md and snippet S2.

Anti-pattern 3 — observeForever never removed

Not a coroutine, but the same class of bug in LiveData form. 16-kakao — SearchViewModel.kt:22-24 calls observeForever on a per-call KakaoLocationImpl instance and never removeObservers it, and there is no onCleared() cleanup → the observer (and its ViewModel) leaks. Fix: use viewModelScope + a StateFlow, or at minimum pair every observeForever with a removeObserver in onCleared().

4. Structured concurrency, cancellation & exception handling

Structured concurrency means every coroutine has a parent, and a parent doesn't complete until its children do. The scope is the structure. Consequences you must know:

  • Cancellation is cooperative. A coroutine only stops at a suspension point or when it checks isActive/ensureActive(). A tight CPU loop with no suspension won't cancel. Blocking calls (Thread.sleep) don't respond to cancellation — that's part of why 13-android-refactoring-start-code's Thread.sleep(2000) (MainActivity.kt:38-47) is doubly wrong: it blocks the main thread and ignores cancellation. Use delay() (suspending, cancellable) instead.
  • CancellationException is special. It's how cancellation propagates. Never swallow it. A bare catch (e: Exception) around a suspend call will eat cancellation and break structured concurrency:
// WRONG — swallows CancellationException, coroutine "won't die"
try { repo.load() } catch (e: Exception) { showError(e) }
// RIGHT — rethrow cancellation
try { repo.load() }
catch (e: CancellationException) { throw e }
catch (e: Exception) { showError(e) }
// BETTER — runCatching in the newer stdlib rethrows CancellationException for you (Kotlin 1.6+ coroutines)
_state.value = runCatching { repo.load() }.fold(::Content, ::Error)

try/catch vs CoroutineExceptionHandler

  • try/catch is for a specific launch { }/suspend call where you want a local error result. Prefer it in ViewModels — you usually want to turn the failure into a UiState.Error. This is the fix for the pack's "no error handling" cases (03-getyourguide ReviewsFragment.kt:63, 08-pair MainViewModel.kt:16-28).
  • CoroutineExceptionHandler is a last-resort net installed on the scope for uncaught exceptions from launch (it does not catch exceptions from async, whose exception surfaces at await()). Use it for cross-cutting logging, not per-call error UI.
private val handler = CoroutineExceptionHandler { _, e -> Log.e("VM", "uncaught", e) }
fun load() = viewModelScope.launch(handler) { /* ... */ }

supervisorScope / SupervisorJob

In a plain coroutineScope, if one child fails, the failure cancels the parent and all siblings. In a supervisorScope, a child's failure is isolated — siblings keep running. Use it when you fan out independent work and want partial success:

// Load profile + products concurrently; a products failure shouldn't nuke the profile
suspend fun loadDashboard() = supervisorScope {
    val profile = async { runCatching { repo.profile() } }
    val products = async { runCatching { repo.products() } }
    Dashboard(profile.await().getOrNull(), products.await().getOrElse { emptyList() })
}

viewModelScope already uses a SupervisorJob, so one failed launch in a ViewModel doesn't tear down the whole scope — but sibling asynces inside a single launch still need supervisorScope for isolation. This is the principled answer to 06-halan/10-petapp "one failed call breaks the whole screen."

5. Config-change survival (rotation)

The recurring rotation bug: state lives in the Activity/Fragment/Composable, so rotation destroys and re-creates it, wiping data and re-firing network calls.

Evidence:

  • 02-mcrmobile — LaunchedEffect(Unit) re-fetches the network on every rotation (no ViewModel, state not hoisted).
  • 03-getyourguide — all state in onCreateView; lost on config change.
  • 07-newsapp — raw Thread + Handler capture the Activity and refetch on rotation (MainActivity.java:36,86-146).
  • 13-android-refactoring-start-code — MainViewModel is an empty stub, so all results live in the Activity and rotation wipes them (MainViewModel.kt:6-7).

The correct layering: ViewModel survives config changes (it's retained across the Activity re-creation), so put your StateFlow/LiveData there and launch work in viewModelScope. That alone fixes rotation for in-flight and completed work.

  • Views: re-observe the ViewModel in onCreate/onViewCreated; the retained ViewModel replays its latest state.
  • Compose: hoist state to a viewModel(); use LaunchedEffect(key) with a stable key (not Unit if you need it to survive — actually Unit runs once per composition-entry; the real fix is that the ViewModel holds the state so recreation doesn't re-trigger the fetch). Transient UI state that must survive process death uses rememberSaveable / SavedStateHandle.
  • Anti-patterns: setRetainInstance(true) (deprecated) as used by 10-petapp to hold state, and the old AsyncTask-in-Activity model that leaks on rotation (10-petapp callbacks fire after fragment detach with nulled mContext/mListener).
// Compose: ViewModel-owned state survives rotation; no re-fetch on recreation
@Composable
fun ReviewsScreen(vm: ReviewsViewModel = viewModel()) {
    val state by vm.state.collectAsStateWithLifecycle()   // lifecycle-aware collection
    when (val s = state) {
        is Loading -> Spinner()
        is Content -> ReviewList(s.reviews)
        is Error   -> ErrorView(s.message, onRetry = vm::load)
    }
}

Prefer StateFlow in new code (all the coroutine-based repos here should). Expose a read-only StateFlow, back it with a private MutableStateFlow:

private val _state = MutableStateFlow<UiState>(UiState.Loading)
val state: StateFlow<UiState> = _state.asStateFlow()

Model state as a sealed UI state, not three loose fields (data == null as a proxy for "loading" is exactly what breaks 03-getyourguide and 08-pair):

sealed interface UiState {
    data object Loading : UiState
    data class Content(val items: List<News>) : UiState
    data class Error(val cause: Throwable) : UiState
}

Collecting safely

The StateFlow trap: a plain lifecycleScope.launch { flow.collect {} } keeps collecting even when the app is backgrounded — wasting work and risking updates to a stopped UI. Use repeatOnLifecycle (Views) or collectAsStateWithLifecycle() (Compose):

// Views — the ONLY correct pattern for collecting a hot flow in a Fragment
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {   // suspends collection in onStop, resumes in onStart
        viewModel.state.collect { render(it) }
    }
}
// Compose
val state by viewModel.state.collectAsStateWithLifecycle()

LiveData doesn't need this — observe(viewLifecycleOwner) { } is already lifecycle-aware (that's its main advantage in legacy screens). Note 08-pair uses a deprecated Observer overload — the modern call passes a LifecycleOwner.

For one-off events (navigation, snackbars) don't use StateFlow (it re-emits the last value on rotation → double navigation). Use a Channel→receiveAsFlow() or a SharedFlow(replay = 0).

7. Migrating AsyncTask (deprecated) → coroutines

AsyncTask was deprecated in API 30. It's leak-prone (holds an implicit Activity ref), has no built-in cancellation guarantees, and its threading is easy to misuse. The Java repos are full of it: 06-halan (LoginTask), 07-newsapp (raw Thread+Handler), 10-petapp (JsonRequestAsyncTask), 20-refactoring-android (ILoginActionImpl.java:49,103,141,174 — all networking).

The classic AsyncTask bugs to call out in review:

  • Callback after detach: onPostExecute runs after the Activity/Fragment is gone → NPE / stale UI (10-petapp nulls mContext/mListener and still fires).
  • Wrong-thread navigation: 06-halan LoginTask.java:66 calls onPostExecute(true) from doInBackground → startActivity on a background thread.
  • Captured Activity leaks on rotation (07-newsapp MainActivity.java:36).

Mapping

onPreExecute()code before the withContext, on Main
doInBackground()withContext(Dispatchers.IO) { ... }
onProgressUpdate()emit to a Flow / update a StateFlow

// BEFORE (Java, leaks Activity, fires after detach)
private class LoadTask extends AsyncTask<Void, Void, Result> {
    protected Result doInBackground(Void... v) { return httpFetch(); }
    protected void onPostExecute(Result r) { textView.setText(r.title); }  // may run post-detach
}
// AFTER (Kotlin ViewModel)
fun load() = viewModelScope.launch {                 // cancelled in onCleared → no post-detach callback
    _state.value = UiState.Loading
    _state.value = runCatching { withContext(Dispatchers.IO) { repo.fetch() } }
        .fold({ UiState.Content(it) }, { UiState.Error(it) })
}

If the repo is still Java and a coroutine rewrite is out of scope for a timed exercise, the minimum fix is: remove StrictMode.penaltyDeath()-tripping main-thread work, keep the AsyncTask but (a) make it static + hold a WeakReference, (b) null-check the view in onPostExecute, (c) add timeouts/status checks/finally { disconnect() }. See snippet S4 for the Java-side hardening in 05-agilevent.

This module is the network boundary: how bytes leave the device, how JSON becomes typed models, and how failures become UI state instead of crashes. Across the 20 review repos this is one of the densest failure clusters — 12 distinct networking findings and 9 parsing/model findings. The good news: the fixes are formulaic. If you can recite the "correct" shape below and point at why each repo deviates, you own this part of the round.

Scope boundaries (stay in lane):

1. The canonical "good" network layer

Before critiquing broken code, anchor on the target. Every repo below is graded against this shape. A senior review answer starts by describing this and then names each deviation.

// 1) DTOs — nullable exactly where the wire is nullable (see §4)

Six things this has that almost none of the repos have: timeouts, a logging interceptor gated on DEBUG, an auth interceptor pulling the key from BuildConfig, a single base-URL source, a non-2xx branch, and a try/catch boundary that returns a typed result. Learn to scan for the absence of each.

2. Inline Retrofit-in-Fragment / repo — the #1 networking smell

The most common finding: Retrofit is built inside the class that uses it (a Fragment, an Activity, or a plain repository with no DI), instead of being a singleton assembled once and injected.

2a. GetYourGuide — Retrofit built inline, base URL + path hardcoded, no error handling

../03-getyourguide-android-challenge/app/src/main/java/com/getyourguide/interview/RetrofitBuilder.kt:

object RetrofitBuilder {
  fun <T> build(apiInterface: Class<T>): T =
    Retrofit.Builder()
      .addConverterFactory(MoshiConverterFactory.create())
      .client(OkHttpClient.Builder().addInterceptor(HttpLoggingInterceptor().setLevel(Level.BASIC)).build())
      .baseUrl("https://travelers-api.getyourguide.com/")   // hardcoded literal
      .build()
      .create(apiInterface)
}

And the API surface bakes pagination into the path — ../03-getyourguide-android-challenge/app/src/main/java/com/getyourguide/interview/ReviewsApi.kt:7:

@GET("activities/141648/reviews?offset=0&limit=60")   // activity id + offset + limit are hardcoded in the path string
suspend fun getReviews(): ReviewResponse

What's wrong:

  • No timeouts. OkHttpClient.Builder().build() gets the defaults (10s connect, 10s read) — acceptable, but there's no explicit, reviewable policy. More important, the client is rebuilt on every build() call, so no connection pool / cache is ever shared.
  • Logging always on at Level.BASIC — not gated on BuildConfig.DEBUG, so it ships in release.
  • Hardcoded literals for base URL, activity id (141648), and paging. Those belong in @Query/@Path params or BuildConfig, not a string in the annotation.
  • The call has no error boundary. getReviews() returns the raw DTO (ReviewResponse, not Response<T>), and the caller (ReviewsFragment.kt:62-65) invokes it in a GlobalScope.launch with no try/catch:
GlobalScope.launch {
  val response = api.getReviews()   // any IOException / non-2xx / parse error throws here
  data = response                   // → uncaught → crash, or infinite spinner keyed on data == null
}

Any timeout, 4xx/5xx, or JSON mismatch throws an uncaught exception on a coroutine nobody supervises → the app crashes or hangs forever on the spinner (which is keyed on data == null). See ../03-getyourguide-android-challenge/SOLUTION.md.

2b. Medibank — repository builds its own Retrofit, ignoring the constant it already defines

../01-medibank-ventures-code-review-exercise-android/.../data/repository/NewsRepository.kt:16-25:

This is worse than GetYourGuide because the repo has a Constants.BASE_URL = "https://newsapi.org/v2/" (common/Constants.kt:5) and ignores it, duplicating the literal. It also passes the API token as a method parameter rather than an interceptor, so the secret is threaded through the whole call stack. And this class is constructed with NewsRepository() (no-arg) from GetNewsListUsecase.kt:24, defeating the Hilt graph that's already configured — the classic "DI present but fake" case. Why inline-in-Fragment/repo is wrong — the review one-liner

"The Retrofit/OkHttp client is an expensive, thread-safe object with a connection pool and dispatcher; it must be a single application-scoped instance. Building it inside a Fragment/repository means (1) a new client + pool per screen (wasteful, no reuse), (2) no seam to inject a MockWebServer or fake API in tests, and (3) cross-cutting config — timeouts, auth, logging — is copy-pasted per call site and drifts. Hoist it to a @Singleton provider and inject the API interface."

Other inline offenders to name-drop: ../11-dirty-code-exercise/SOLUTION.md (Retrofit builder + auth map in MainActivity.onCreate), ../02-mcrmobile-Android-Refactoring/SOLUTION.md (DependencyContainer uses the default OkHttp client — no timeouts/logging/retry).

3. Error handling: wrap every call in a Result / sealed type

The single most repeated crash: a network call with no try/catch, so an IOException, a non-2xx HttpException, or a JsonDataException propagates uncaught. Repos: GetYourGuide (§2a), Pair Programming, Halan, Kakao, News App, Agilevent.

The failure — Pair Programming

../08-pair-programming-exercise/.../main/MainViewModel.kt:16-28 (per ../08-pair-programming-exercise/SOLUTION.md): the fetch has no try/catch; on any failure it sets news.value = null, which is then fed into showNews(ArrayList<News>) — a non-null parameter — in MainActivity.kt:40. So a failed request is a guaranteed NPE. Two bugs compound: no error catching and a type that can't represent "no data."

The fix — one ApiResult sealed type + a safeApiCall boundary

sealed interface ApiResult<out T> {
    data class Success<T>(val data: T) : ApiResult<T>
    data class Error(val kind: ErrorKind, val cause: Throwable) : ApiResult<Nothing>
}

enum class ErrorKind { NETWORK, HTTP, PARSE, UNKNOWN }

suspend fun <T> safeApiCall(block: suspend () -> T): ApiResult<T> =
    try {
        ApiResult.Success(block())
    } catch (e: CancellationException) {
        throw e                                        // NEVER swallow cancellation — rethrow it
    } catch (e: IOException) {
        ApiResult.Error(ErrorKind.NETWORK, e)          // timeout, no connectivity, socket reset
    } catch (e: HttpException) {
        ApiResult.Error(ErrorKind.HTTP, e)             // non-2xx surfaced by Retrofit
    } catch (e: JsonDataException) {                   // Moshi; Gson: JsonSyntaxException
        ApiResult.Error(ErrorKind.PARSE, e)            // schema mismatch, null-into-nonnull
    } catch (e: Exception) {
        ApiResult.Error(ErrorKind.UNKNOWN, e)
    }

Two rules that separate a senior answer from a junior one:

  1. Rethrow CancellationException first. A bare catch (e: Exception) swallows the cancellation that viewModelScope/lifecycleScope throws to stop the coroutine, breaking structured concurrency (the coroutine "completes successfully" instead of cancelling). This is subtle and interviewers love it. (Concurrency depth → 04.)
  2. Distinguish network vs HTTP vs parse. The UI wants different copy for "you're offline" (NETWORK), "server said 401" (HTTP), and "we couldn't read the response" (PARSE). Collapsing everything to a generic "error" is a lost opportunity, but any typed result beats an uncaught throw.

The repository returns ApiResult; the ViewModel folds it into UiState.Error (that mapping is 03). For the concise version when time is tight, Kotlin's stdlib runCatching { ... }.fold(...) is acceptable — see snippet S1 in the evidence pack — but it catches Throwable (including CancellationException), so in production code prefer the explicit try/catch above.

Silent-catch is the same bug wearing a disguise

The mirror image of "no try/catch" is "catch that does nothing." Both leave the user staring at a blank screen:

  • ../09-better-android-refactor-code-class/.../RestaurantsActivity.kt:126 — .subscribe({...}, {}) — empty RxJava error consumer, all failures dropped.
  • ../02-mcrmobile-Android-Refactoring/SOLUTION.md — catch { printStackTrace() }, no error UI.
  • ../16-kakao-android-map-refactoring/.../KakaoLocationImpl.kt:26-35 — onFailure only printStackTrace(); non-2xx ignored entirely.
  • ../07-newsapp-Ques_NewsApp_Android_challenge/.../MainActivity.java:94-96 — errors swallowed via printStackTrace, empty list forever.

Review phrasing: "printStackTrace() is not error handling — it's error hiding. Every catch must either recover or surface a state the UI can render."

Don't forget the non-2xx branch

Retrofit only throws for suspend functions returning a bare type when the body fails to deserialize; if you return Response<T>, a 404/500 comes back as response.isSuccessful == false with a null body — it does not throw. Many repos check only status 200 and treat everything else as either success or silence:

  • ../06-halan-fixing-refactoring_challenge-task/.../LoginTask.java:63-67 — switch(status) handles only 200, no default.
  • ../20-refactoring-android/.../HttpEngine.java — only 200 = success; ../20-refactoring-android/SOLUTION.md.
  • ../05-agilevent-android-job-application-challenge-2/.../MainActivity.java:66 — response stays null after a swallowed exception, then dereferenced → NPE.

Always: if (!response.isSuccessful) return error; val body = response.body() ?: return error.

4. JSON models: nullability discipline

The single highest-frequency parse crash is a non-null Kotlin field mapped from a wire value that is actually nullable. The wire lies; the type system trusts it; a real response arrives with null; the converter throws.

The textbook case — Pair Programming News.kt

../08-pair-programming-exercise/.../data/model/News.kt:6-15 (verbatim):

class News(
    val source: Source,
    val author: String,        // newsapi.org returns null here constantly
    val title: String,
    val description: String,   // nullable on the wire
    val url: String,
    val urlToImage: String,    // nullable on the wire
    val publishedAt: Date,     // ISO-8601 STRING on the wire, not a Date (see §5)
    val content: String        // nullable on the wire
): Serializable

newsapi.org's /v2/everything returns null for author, description, urlToImage, and content on many articles. With Gson these become null assigned into non-null Kotlin properties — Gson uses reflection/Unsafe and won't complain at parse time, so you get a News object with null in a String slot, and the NPE fires later when something reads author.length. With Moshi codegen it fails at parse with a JsonDataException: Non-null value 'author' was null. Either way: crash.

Fix (evidence-pack S7):

@Parcelize                                    // Parcelable, not Serializable (§7)
data class News(
    val source: Source,
    val author: String?,                      // nullable exactly where the API is nullable
    val title: String,                        // title/url are reliably present → keep non-null
    val description: String?,
    val url: String,
    val urlToImage: String?,
    val publishedAt: String?,                 // raw string; parse in the mapping layer
    val content: String?,
) : Parcelable

The Medibank variant — nullable DTO papered over with .orEmpty()

../01-medibank-ventures-code-review-exercise-android/SOLUTION.md: ArticleDto.kt:20-24 is correctly nullable, but the domain Article.kt:11,12 has non-null title/url, and the mapper coerces with .orEmpty(). That doesn't crash — it produces a blank URL, which loads a blank WebView. The lesson: nullability isn't just a crash concern; silently substituting "" moves the failure downstream into a confusing UX bug. Better: if url is genuinely required, drop the article (filter it out) or model it as invalid — don't fabricate an empty string.

The rule

Model the DTO to match the wire exactly — nullable where the API can send null, non-null only where the contract guarantees presence. Keep DTO nullable and enforce your own invariants in the mapper (drop/require/default deliberately), where a bad value is a data decision, not a crash. Never assume a field is present because "it always was in my test payload."

5. Date/time parsing pitfalls (ISO-8601 vs Date)

Two failure modes, both live in the repos:

  1. Wrong static type. Pair Programming's publishedAt: Date (§4). Gson maps ISO-8601 to java.util.Date only via a registered DateFormat, and the default format is EEE MMM dd HH:mm:ss zzz yyyy — not ISO-8601 — so "2021-01-15T10:30:00Z" throws JsonSyntaxException. The fix is to keep the DTO field a String and parse in the mapping layer.
  2. A brittle formatter pattern. GetYourGuide, ../03-getyourguide-android-challenge/.../ReviewsFragment.kt:105-108 (verbatim):
val dateText = LocalDateTime.parse(
  review.created,
  DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ssz")   // 'z' = zone name; brittle
).format(DateTimeFormatter.ofPattern("MMM dd, yyyy"))

Three problems: (a) LocalDateTime has no offset/zone — parsing a string with Z or +02:00 into it throws DateTimeParseException; (b) the pattern 'z' doesn't match ISO Z or numeric offsets or fractional seconds; (c) it's recomputed on every recomposition because it's not remembered or moved to the mapping layer.

Fix (evidence-pack S9) — parse tolerantly, once, in the mapper:

// For ISO-8601 with offset (2021-01-15T10:30:00Z or +02:00): use OffsetDateTime / Instant, which
// understand the full ISO_OFFSET_DATE_TIME grammar including 'Z' and fractional seconds.
fun String.toDisplayDate(): String =
    runCatching { OffsetDateTime.parse(this) }               // ISO by default, no custom pattern
        .map { it.format(DateTimeFormatter.ofPattern("MMM dd, yyyy")) }
        .getOrDefault("")                                     // a bad date never crashes the row

Rules: never model a timestamp as Date in a DTO (keep the raw String); use Instant/OffsetDateTime + the built-in ISO_* formatters rather than hand-rolled ofPattern; do the parse in a mapping/domain layer once, not per row or per recomposition; and wrap it so a malformed timestamp degrades to "" instead of taking down the list.

6. Secrets: never commit API keys

The violation — Medibank

../01-medibank-ventures-code-review-exercise-android/.../common/Constants.kt:6 (verbatim):

object Constants {
    const val BASE_URL = "https://newsapi.org/v2/"
    const val API_NEWS_TOKEN = "d5d3fe8e9870498b9f57818b216507d8"   // committed secret — in git history AND the APK
    const val WEB_URL_KEY = "newsUrl"
}

This key is (1) in every clone of the git history forever, (2) trivially extractable from the shipped APK via strings, and (3) can't be rotated without a code change + release. Same pattern in ../13-android-refactoring-start-code/.../data/PhotoApi.kt:12 (Pixabay key as a default @Query param) and ../11-dirty-code-exercise/.../MainActivity.java:25-30 (fake Marvel auth hardcoded over cleartext).

The fix — local.properties → BuildConfig → interceptor

local.properties (gitignored by default in every Android project):

NEWS_API_KEY=d5d3fe8e9870498b9f57818b216507d8

app/build.gradle.kts:

android {
    defaultConfig {
        val key = project.rootProject.file("local.properties")
            .takeIf { it.exists() }
            ?.let { java.util.Properties().apply { load(it.inputStream()) } }
            ?.getProperty("NEWS_API_KEY").orEmpty()
        buildConfigField("String", "NEWS_API_KEY", "\"$key\"")
    }
    buildFeatures { buildConfig = true }
}

Then attach it via an interceptor so no call site ever touches the raw key.

The positive counter-example — Pair Programming does this correctly

../08-pair-programming-exercise/.../data/ApiKeyInterceptor.kt (verbatim) — cite this in a review as "here is the right pattern":

class ApiKeyInterceptor : Interceptor {
    companion object { private const val API_KEY = "apiKey" }

    override fun intercept(chain: Interceptor.Chain): Response {
        val originalHttpUrl = chain.request().url()
        val url = originalHttpUrl.newBuilder()
            .addQueryParameter(API_KEY, BuildConfig.NEWS_API_KEY)   // key from BuildConfig, not source
            .build()
        val request = chain.request().newBuilder().url(url).build()
        return chain.proceed(request)
    }
}

(Nitpicks worth noting even here: the semicolons are un-idiomatic Kotlin, and query-param keys are logged by any HttpLoggingInterceptor.Level.BASIC+, so a header — addHeader("X-Api-Key", ...) — is marginally better for secrets and can be redacted with HttpLoggingInterceptor.redactHeader.) ../16-kakao-android-map-refactoring/SOLUTION.md is another positive: keys read from local.properties via getApiKey(...).

Full review move: "The key is committed at Constants.kt:6 — it's in git history and the APK. This is a security finding, not a style nit: rotate the key immediately, move it to local.properties/CI secrets exposed via BuildConfig, add it through an interceptor. Pair Programming's ApiKeyInterceptor is the reference implementation."

An auth interceptor is also where you attach bearer tokens and 401-refresh logic (via OkHttp Authenticator) — but keep secrets out of logs.

7. Bonus model smell — Serializable for intent extras

Pair Programming's News : Serializable (News.kt:15) is also passed through an Intent and read with an unchecked cast at DetailActivity.kt:22: intent.getSerializableExtra("newsSelected") as News → NullPointerException/ClassCastException on a null extra. Several Java repos hand-roll HTTP. This is where a refactor exercise (not just review) lives, so know the mechanical translation.

The legacy patterns and what's wrong

  • ../07-newsapp-Ques_NewsApp_Android_challenge/.../MainActivity.java:90 — raw HttpURLConnection on a bare Thread, dead endpoint api.myjson.com, no timeout, no status check, no retry, no disconnect(), getString/getInt manual parse that throws on any missing key.

The migration recipe

  1. Define a Retrofit interface with suspend methods returning Response<Dto>; put path/query params in @Path/@Query instead of string-concatenated URLs.

See evidence-pack S4 for the Java AsyncTask version. But in a Kotlin/Gradle repo, "migrate to Retrofit" is the correct answer, not "add timeouts to the raw connection."

Bundled-asset JSON is the same category — OneFootball

Not every parse is a network call. OneFootball reads a bundled news.json asset on the main thread with an ignored read() return and no try/catch — ../04-onefootball-coding_challenge_android/.../MyNewsActivity.kt:36-47. The inputStream.read(buffer) at :41 ignores its return value → possible truncated read → parse crash (evidence-pack S3):

// BEFORE (main thread, ignores read() count, uncaught exceptions, manual org.json extraction)
var inputStream = assets.open("news.json")
val buffer = ByteArray(inputStream.available())
inputStream.read(buffer)                       // return value ignored → truncation
val items = parseJsonString(buffer.toString(Charset.defaultCharset()))   // throws, uncaught

// AFTER — read fully & safely off the main thread, then Moshi
val json = assets.open("news.json").bufferedReader().use { it.readText() }   // use{} closes the stream
val items = moshi.adapter<NewsResponse>().fromJson(json).orEmpty()           // in a repo, on Dispatchers.IO

Two reusable lessons: InputStream.read(byte[]) is not guaranteed to fill the buffer — always loop or use readText()/readBytes(); and manual org.json extraction per field (getString/getInt) is fragile — getString on a missing key throws JSONException, which the News App repo then swallows in a way that aborts the whole media loop (../07-newsapp-Ques_NewsApp_Android_challenge/.../NewsEntity.java:39, MediaEntity.java:19-28). If you're forced to keep org.json, use opt* with defaults and iterate defensively (evidence-pack S6). Otherwise, a converter-backed model deletes the whole class of bugs.

17.6 Testing & DI

Across all 20 repos, "there are tests" almost always meant assertEquals(4, 2+2). Where there were real-looking tests, they were subtly broken: the mock was never wired, the assert was a tautology, the rule wouldn't compile, or the singleton couldn't be mocked. This module teaches you to (a) spot fake confidence in a PR and (b) write tests that actually fail when the code is wrong — which only works if the code is injectable.

The one-liner that ties this whole module together:

Untestable code and fake DI are the same defect viewed from two ends. A ViewModel or use case that constructs its own dependencies (NewsRepository(), DependencyProvider.getApi(), new ApiImpl()) cannot be tested with a double, so the "test" quietly runs against the real network and passes by accident. Fix the DI and the test becomes real for free.

2. Testing a ViewModel with coroutines (the reference recipe)

This is the pattern interviewers most want to see you write from memory. Modern (kotlinx-coroutines-test ≥ 1.6, current API):

@OptIn(ExperimentalCoroutinesApi::class)
class MainCoroutineRule(
  val dispatcher: TestDispatcher = StandardTestDispatcher()
) : TestWatcher() {
  override fun starting(description: Description) { Dispatchers.setMain(dispatcher) }
  override fun finished(description: Description) { Dispatchers.resetMain() }
}
@OptIn(ExperimentalCoroutinesApi::class)
class ReviewsViewModelTest {
  @get:Rule val mainRule = MainCoroutineRule()

  private val repo: ReviewsRepository = mockk()

  @Test
  fun `emits Loading then Content on success`() = runTest {
    coEvery { repo.getReviews() } returns listOf(review)
    val vm = ReviewsViewModel(repo)                 // <-- dependency INJECTED

    vm.state.test {                                  // Turbine
      assertEquals(ReviewsUiState.Loading, awaitItem())
      assertEquals(ReviewsUiState.Content(listOf(review)), awaitItem())
    }
  }

  @Test
  fun `emits Error when repository throws`() = runTest {
    coEvery { repo.getReviews() } throws IOException("boom")
    val vm = ReviewsViewModel(repo)
    vm.state.test {
      assertEquals(ReviewsUiState.Loading, awaitItem())
      assertThat(awaitItem()).isInstanceOf(ReviewsUiState.Error::class.java)
    }
  }
}

Key pieces, and why each matters:

  • runTest { } — replaces runBlocking; provides a TestScope with a virtual clock, so delay(1000) completes instantly (see the anti-pattern in §3). It also fails the test if any child coroutine is still running at the end (leak detection).
  • Dispatchers.setMain(testDispatcher) in a rule — viewModelScope uses Dispatchers.Main, which throws on the JVM ("no Main dispatcher") unless you install one. The rule does setMain/resetMain around every test.
  • StandardTestDispatcher — queues coroutines; they run only when you advanceUntilIdle() / runCurrent() or when runTest drains at the end. Use it to assert intermediate states (like Loading). UnconfinedTestDispatcher runs eagerly/inline — convenient when you don't care about ordering, but it hides ordering bugs. Default to StandardTestDispatcher and reach for Unconfined only when eager execution simplifies a specific test.
  • Turbine's .test { awaitItem() } — the clean way to assert a sequence of StateFlow/Flow emissions. For LiveData, use the getOrAwaitValue() helper (seen in 08).
  • Inject dispatchers into the ViewModel/repo (class Repo(private val io: CoroutineDispatcher = Dispatchers.IO)) so tests can pass the test dispatcher instead of the real Dispatchers.IO. Dispatcher mechanics live in ./04-concurrency-lifecycle.md.

2a. The GetYourGuide TestCoroutineRule that won't compile — and the fix

03-getyourguide-android-challenge/app/src/test/java/com/getyourguide/interview/TestCoroutineRule.kt:5-6,32-34,47 ships a rule built entirely on APIs that were removed in kotlinx-coroutines-test 1.6 (the repo pulls 1.7.x), so it does not compile:

// BEFORE — uses removed TestCoroutineScope / TestCoroutineDispatcher / cleanupTestCoroutines
@ExperimentalCoroutinesApi
class TestCoroutineRule : TestRule, TestCoroutineScope by TestCoroutineScope() {   // removed type
  val dispatcher = coroutineContext[ContinuationInterceptor] as TestCoroutineDispatcher  // removed type
  override fun apply(base: Statement, description: Description) = object : Statement() {
    override fun evaluate() {
      Dispatchers.setMain(dispatcher)
      base.evaluate()
      cleanupTestCoroutines()          // removed API
      Dispatchers.resetMain()
    }
  }
}

TestCoroutineScope, TestCoroutineDispatcher, and cleanupTestCoroutines() were deprecated in 1.6 and deleted in 1.7. The fix is the MainCoroutineRule in §2 (a TestWatcher over a TestDispatcher), and using runTest in the test body — runTest now owns the scope, virtual clock, and end-of-test leak check that the old rule tried to hand-roll:

// AFTER — compiles against coroutines-test 1.7+, no removed symbols
@OptIn(ExperimentalCoroutinesApi::class)
class MainCoroutineRule(val dispatcher: TestDispatcher = StandardTestDispatcher()) : TestWatcher() {
  override fun starting(description: Description) { Dispatchers.setMain(dispatcher) }
  override fun finished(description: Description) { Dispatchers.resetMain() }
}

Interview tell: if a test-infra file imports kotlinx.coroutines.test.TestCoroutineScope or TestCoroutineDispatcher, say out loud: "this is pre-1.6 API, removed in 1.7 — replace with TestScope/TestDispatcher + runTest." It signals you track the coroutine-test API churn.

3. Test anti-patterns harvested from the repos

3a. Mock never injected — the SUT constructs its own dependency

Review script: trace the mock. Find the mock()/mockk(), then find where the SUT is constructed. If the mock isn't passed into that constructor (or set via an injectable seam), the test is inert. Say: "the mock is never on the object's dependency path — this test exercises the real implementation."

3b. Tautological / vacuous asserts

Two flavors seen:

  • assertEquals(4, 2+2) — the auto-generated ExampleUnitTest left as the only test in 04, 02, 09, 11, 13, 14, 19, 20. It asserts the JVM can add. Zero coverage of the app.
  • assertTrue(... is ArrayList<News>) — 08 MainViewModelTest.kt:48-49. Because of type erasure this is effectively is ArrayList<*>; it can't even check the element type, and it says nothing about contents. A test that can't fail for a wrong result is worse than no test — it advertises coverage that doesn't exist. Assert the actual value: assertEquals(expectedArticles, vm.state...).

3c. Live-network / not-really-unit tests

  • 07 APIAvailabilityTest.java:14-26 opens a real HTTP connection and asserts with the Java assert keyword — which is disabled by default at JVM launch, so the "assertions" never execute and the test can never fail. Double-broken.
  • 10 ApiAvailabilityUnitTest.java opens real connections to dead endpoints (api.myjson.com).

A unit test must be deterministic and offline. Network belongs in a Retrofit-against-MockWebServer integration test (see ./05-networking-parsing.md), never in a plain unit test, and never with the disabled assert keyword — use a JUnit assertion.

3d. delay(1000) / Thread.sleep inside a test

Medibank GetNewListUsecaseTest.kt:103 does delay(1000) inside runBlocking to "wait for" the flow to collect. That's a real one-second wall-clock wait, and it's a flaky race — 1s may or may not be enough. Replace with runTest (virtual clock: delay is skipped instantly) plus deterministic collection via Turbine or advanceUntilIdle():

// BEFORE
@Test fun testUseCase() = runBlocking {
  ...
  launch { result.collect { resource.add(it) } }
  delay(1000)                                    // real 1s wait, racey
  assertEquals(Resource.Loading, resource.first())
}
// AFTER — no sleeping, no race
@Test fun testUseCase() = runTest {
  useCase.invoke("us").test {
    assertEquals(Resource.Loading, awaitItem())
    assertEquals(Resource.Success(articleList), awaitItem())
    awaitComplete()
  }
}

3e. Structural test-hygiene smells

  • Tests in src/main — 15 ships MainScreenTest.kt and : UserManagerTest.kt under app/src/main/java/.... They compile into the production APK (bloat + leaking test deps to release), and being in main they never run under ./gradlew test. Note the file literally named ": UserManagerTest.kt" (leading colon/space — an invalid, never-discovered name). Unit tests go in src/test/, instrumentation/Compose-UI tests in src/androidTest/.
  • Deprecated assert frameworks — 12 uses junit.framework.Assert and hand-rolled fakes despite Mockito being on the classpath; brittle magic asserts like size() == 3. (Credit where due: 12 is the one repo that actually tests both branches of its presenter — the positive counter-example.)
  • Removed base classes — 07 ApplicationTest extends the removed ApplicationTestCase; won't compile on modern tooling.

4. Fakes vs mocks — pick the right test double

Mock (MockK/Mockito) Fake (hand-written working impl)
What it isRecords/stubs interactions; you script return values per callA real, simplified implementation (in-memory map, canned list)
Best forVerifying interactions (was logAudit() called?), one-off stubbed returnsRepositories/APIs/DAOs with stateful behavior reused across many tests
CostCheap per test, but brittle: couples test to call signaturesSlightly more upfront code, but robust and readable
Failure modeOver-mocking → tests that assert the code called the methods you already know it calls (see 08's tautology)Fake drifts from real contract if not kept in sync

Rule of thumb: fake the things you read state from (repositories, APIs, DAOs); mock the things you verify calls to (analytics, audit logger, navigator). For a repository test double, a fake is usually clearer:

// A fake repo — no framework, trivially reusable, can model errors
class FakeReviewsRepository(
  private var result: Result<List<Review>> = Result.success(emptyList())
) : ReviewsRepository {
  fun willReturn(reviews: List<Review>) { result = Result.success(reviews) }
  fun willFail(t: Throwable) { result = Result.failure(t) }
  override suspend fun getReviews(): List<Review> = result.getOrThrow()
}
@Test fun `content on success`() = runTest {
  val repo = FakeReviewsRepository().apply { willReturn(listOf(review)) }
  ReviewsViewModel(repo).state.test {
    awaitItem()                                  // Loading
    assertEquals(ReviewsUiState.Content(listOf(review)), awaitItem())
  }
}

For faking the network boundary specifically, prefer MockWebServer over mocking Retrofit interfaces — it exercises real JSON deserialization and status handling. That's covered in ./05-networking-parsing.md.

4a. The un-mockable Kotlin object — Medibank's cousin in the testing lab

)

5. DI: why manual providers/singletons kill testability, and how Hilt fixes it

Every "mock never injected" and "can't mock the object" defect above is a DI defect wearing a testing costume. The through-line:

Anti-patterns seen in the repos:

  • SUT constructs its own dependency: Medibank GetNewsListUsecase.kt:24 NewsRepository(); 08 MainViewModel() builds its API via DependencyProvider; 20 new ApiImpl() / new ILoginActionImpl(this); 13 empty Application, no repo abstraction.
  • Global singletons / object: 15's Database/EmailService objects; 16's getInstance(context) manual singletons leaking Activity Context.
  • Manual ViewModelFactory threading Context through: 16 MapViewModelFactory.

Why it hurts:

  1. No seam → a test can't substitute a fake → tests either don't exist or run against real I/O.
  2. Hidden coupling → the class secretly depends on Retrofit/OkHttp/Context; you can't reason about it or reuse it.
  3. Lifecycle bugs → manual singletons that capture Context/Activity leak (16's getInstance(context), 12's presenter holding a strong Activity ref).

5a. Hilt basics (the minimum you must be able to write)

// 1. Application entry point
@HiltAndroidApp class NewsApp : Application()

// 2. Constructor injection — the class declares its real dependencies; no more `new`
class NewsRepository @Inject constructor(private val api: NewsApiService) {
  suspend fun getNews(country: String) = withContext(Dispatchers.IO) { api.getTopHeadlines(country) }
}
class GetNewsListUseCase @Inject constructor(private val repo: NewsRepository) { /* uses repo */ }

// 3. Module for things you don't own / need config (Retrofit, OkHttp, Room)
@Module @InstallIn(SingletonComponent::class)
object NetworkModule {
  @Provides @Singleton
  fun provideRetrofit(client: OkHttpClient): Retrofit = Retrofit.Builder()
    .baseUrl(BuildConfig.BASE_URL).client(client)
    .addConverterFactory(MoshiConverterFactory.create()).build()

  @Provides @Singleton
  fun provideApi(retrofit: Retrofit): NewsApiService = retrofit.create(NewsApiService::class.java)
}

// 4. ViewModel injection — no manual factory
@HiltViewModel
class NewsListViewModel @Inject constructor(
  private val getNews: GetNewsListUseCase
) : ViewModel() { /* viewModelScope.launch { ... } */ }
  • @Inject constructor — Hilt builds the object and supplies its params. This is the seam: in tests you just call the constructor with fakes/mocks yourself (no Hilt needed for unit tests).
  • @Module + @Provides — teach Hilt how to build types you can't annotate (Retrofit, OkHttpClient, interfaces). Use @Binds for interface→impl.
  • @InstallIn(SingletonComponent::class) + @Singleton — scope/lifetime.
  • @HiltViewModel + hiltViewModel() (Compose) / by viewModels() (Views) — no hand-rolled ViewModelFactory (kills 16's manual-factory finding).

The payoff for testing: because every dependency arrives through a constructor, unit tests never touch Hilt — they instantiate the SUT directly with test doubles. Hilt only re-enters for instrumentation tests (@HiltAndroidTest + HiltAndroidRule + @TestInstallIn to swap modules).

5b. Medibank — "configured Hilt but fake graph" (the trap to name)

Medibank is the canonical teaching case: it has Hilt on the classpath and has modules — but the graph is fake, so it buys none of Hilt's benefits.

// BEFORE (the fake graph)

Talking out loud (pair-programming rounds)

In a pair round the interviewer is scoring your process, not your silence. Bad candidates read in silence for 8 minutes then say "this is bad." Strong candidates externalize a loop. Use this script:

1. Orient (30–60s). Say what you're looking at and how you'll attack it.

"Single-Activity app, all logic in MyNewsActivity. I'll skim top to bottom for lifecycle and threading first, then correctness, then style. Let me start in onResume."

2. Narrate the scan as a running commentary. Every time you form a hypothesis, say it before you confirm it.

"This is assets.open … in onResume … on the main thread. That's a red flag — file I/O on the UI thread is an ANR risk, and it re-runs on every resume. Let me confirm nothing hops threads … no, no dispatcher. So P0: main-thread I/O."

3. Prioritize out loud. Explicitly rank as you go so the interviewer hears your judgment.

"I'm calling that a blocker. The hardcoded strings I noticed are a nit — I'll park them and come back if we have time."

4. Ask before you commit to a direction. In a pair, alignment beats speed.

"I see three things I'd refactor: the scope, the error handling, and the date parse. I'd start by hoisting the network call into a ViewModel because it fixes the leak and gives us a place for error state. Does that ordering work for you, or would you rather see the crash fixed first?"

5. Think in tradeoffs, not absolutes. Seniority shows in "it depends."

"I'd reach for StateFlow over LiveData here since we're Compose-first, but LiveData would be fine and needs less test setup. I'll go StateFlow."

6. When stuck, say what you're doing. Silence reads as being lost.

"I want to check how the extra is passed — give me ten seconds to find where the Intent is built."

7. Land the plane. Before time's up, summarize.

"So: two blockers — the GlobalScope leak and no error handling; one correctness bug in the date parse; the rest is architecture debt. With more time I'd add a repository interface and a ViewModel state test."

Anti-patterns that cost points: narrating every keystroke ("now I type val"); silent reading; only listing negatives with no positives; rewriting everything instead of the one thing asked; arguing with a redirect instead of taking it and moving.

Interviewer Q&A

Practice saying each answer aloud in under 60 seconds. Ground every claim in a concrete case — that's what separates a senior answer from a textbook recital.

Q1. "How would you make this testable?"

Answer. Introduce seams: an interface for the data source, constructor injection for dependencies, and a pure function for parsing/mapping. Right now logic is welded to the Android framework — e.g. OneFootball parses inside MyNewsActivity using assets/org.json, so there's nothing to unit-test without a device. I'd extract NewsRepository (interface) + a pure NewsParser + a ViewModel that takes the repository in its constructor. Then I test the parser with plain JUnit, the ViewModel with a fake repository and a TestDispatcher. Talking points: interface at the boundary; constructor over field injection; pure functions for logic; fakes over mocks for your own interfaces. See 06-testing-di.md.

Q2. "Where's the ANR risk here?"

Answer. Anywhere blocking work runs on the main thread. Three canonical shapes in these repos: file I/O — OneFootball reads and parses news.json in onResume (MyNewsActivity.kt:36-47); network — Agilevent does a synchronous DefaultHttpClient call in onCreate (MainActivity.java:52-56); artificial blocking — the ImageSearch repo does Thread.sleep(2000) in a click handler (13/MainActivity.kt:38-47); and DB/disk — Kakao opens writableDatabase and reads synchronously on the main thread (16/KeywordDao.kt:8-50). Fix: move to Dispatchers.IO via a coroutine in a ViewModel, or Room suspend/Flow for the DB. Talking points: the 5-second window; StrictMode as a detector; withContext(Dispatchers.IO).

Q3. "GlobalScope vs viewModelScope — why does it matter?"

Answer. GlobalScope is unbounded and not tied to any lifecycle, so its coroutines leak and can outlive the screen, and — as in GetYourGuide, ReviewsFragment.kt:62 — if you launch it inside setContent it re-fires on every recomposition. viewModelScope is cancelled automatically in onCleared(), so the work dies with the ViewModel. Pair Programming (08/MainViewModel.kt:16) even imports viewModelScope and then uses GlobalScope anyway. The fix is always: launch in viewModelScope (or lifecycleScope for UI-only work), never GlobalScope. Talking points: structured concurrency; cancellation propagation; @DelicateCoroutinesApi is a warning, not a suggestion. See 04-concurrency-lifecycle.md.

Q4. "How do you handle API nulls / a field that might be missing?"

Answer. Model the wire shape as nullable, then map to a clean domain model at a boundary. Pair Programming's News.kt:6-15 declares author/urlToImage/content non-null and publishedAt: Date, so Gson NPEs or throws on the real newsapi.org response that returns nulls and ISO-8601 strings. Make DTO fields nullable (author: String?), keep dates as String (or use an adapter), and map to a domain type where you decide defaults explicitly — not with a silent .orEmpty() that turns a null URL into a blank WebView, like Medibank's Article.kt. For manual parsing (News App MediaEntity.java), use optString/optInt with defaults instead of getString/getInt that throw. Talking points: DTO ↔ domain separation; nullable at the edge, non-null in the core; tolerant parsing. See 05-networking-parsing.md.

Q5. "MVVM vs MVP — which and why?"

Answer. For new Android I default to MVVM with a ViewModel + unidirectional state (StateFlow<UiState>), because the ViewModel survives config changes and integrates natively with Compose and lifecycle-aware collection — no manual view detach. MVP still works (the Books repo, 12, uses a presenter with view/repository interfaces and a real presenter test), but its classic weakness shows there too: the presenter holds a strong Activity reference with no detach/dispose (BooksActivityPresenter.java:10-16) → leak. MVVM sidesteps that. I'd use MVP only in a legacy codebase already built on it. Talking points: state survival across rotation; view-detach discipline in MVP; UDF; both are testable if you keep the view behind an interface.

Q6. "How do you decide what to fix first?"

Answer. By blast radius. P0 = things that crash, ANR, leak, or leak secrets — user- or security-impacting and non-negotiable. P1 = correctness bugs (wrong data shown, requirement unmet). P2 = architecture/testability. P3 = style/hygiene. Concretely, in Medibank I'd fix the committed API key and the fake DI before I touch Color.Blue hardcoding. In OneFootball the ANR and the guaranteed crash come before "split the adapter into its own file." I state the ranking out loud so the interviewer hears the judgment, and I park nits explicitly rather than silently skipping them. Talking points: crash/ANR/leak/security first; requirement gaps count as bugs; time-box the nits. See 01-code-review-method.md.

Q7. "This uses Hilt — so DI is fine, right?"

Answer. Not necessarily — presence isn't correctness. Medibank has Hilt fully configured but the graph is theatre: the use case does NewsRepository() directly (GetNewsListUsecase.kt:24), the repo builds Retrofit inline (NewsRepository.kt:16-25), and the module provider is circular/nonsensical (RepositoryModule.kt:13-16). Nothing is actually injected, so nothing is swappable in a test — which is exactly why its use-case test passes without ever exercising the mock. I always trace the graph: is the dependency received via constructor, or constructed inside? Kakao is the analogue — Hilt and Room on the classpath, entirely unused in favor of manual factories. Talking points: constructed-vs-injected; DI's payoff is test seams; classpath presence ≠ usage.

Q8. "What's wrong with catching an exception and calling printStackTrace()?"

Answer. It hides failures from both the user and your telemetry. GetYourGuide, MCR, Kakao, and News App all swallow network errors with printStackTrace() (or an empty Rx error consumer in 09/RestaurantsActivity.kt:126), so a failed fetch shows an infinite spinner or an empty list with no way to recover. Errors should become an explicit UiState.Error the UI renders (with retry) and should be logged to your crash/analytics pipeline. Silent catch is only acceptable when you genuinely have a fallback value and you comment why. Talking points: error UiState + retry; log to Crashlytics/Timber; never catch (e: Exception) {}.

Q9. "How would you fix the crash on a null Intent extra / result?"

Answer. Never treat framework-provided extras as non-null. Pair Programming does intent.getSerializableExtra("newsSelected") as News (DetailActivity.kt:22) — crashes on null or wrong type. The Kotlin refactor repo declares onActivityResult(..., data: Intent) non-null, but Android passes null on cancel (14/MainActivity.kt:34). Fix: use a nullable type (data: Intent?), a null-safe getter (getParcelableExtraCompat<News>(KEY) ?: return), a constant key shared between writer and reader (the 14 repo writes PERSON and reads the literal "PERSON"), and prefer @Parcelize/Parcelable over Serializable. Talking points: nullable at the boundary; shared key constants; Parcelable over Serializable; type-safe nav args.

Q10. "AsyncTask everywhere — how would you modernize it?"

Answer. AsyncTask is deprecated and leak-prone — it captures the enclosing Activity/Fragment and its callbacks fire after detach (PetApp, 10, NPEs on nulled mContext/mListener; Halan calls onPostExecute inside doInBackground, running startActivity on a background thread). In Kotlin I'd replace it with coroutines: suspend functions in a repository on Dispatchers.IO, launched from viewModelScope, results as StateFlow. In a Java codebase that can't adopt coroutines yet, at minimum make it a static inner class holding a WeakReference and check for detach, or use ExecutorService + Handler — but the real answer is coroutines/Flow. Talking points: lifecycle capture; detach-time callbacks; coroutines + repository as the target.

Q11. "Where do you put the API key / how do you handle secrets?"

Answer. Never in source. Medibank commits the key in Constants.kt:6 — it's now in git history and the APK. The correct pattern is exactly what Pair Programming does right: read it from local.properties/CI into BuildConfig, then inject it via an OkHttp ApiKeyInterceptor. Kakao does the same via getApiKey(...) → BuildConfig/resValue. And once a key has been committed, rotating it is part of the fix — scrubbing the file isn't enough because it's in history. Talking points: local.properties → BuildConfig; interceptor injection; rotate leaked keys; .gitignore hygiene.

Q12. "This test passes — is it a good test?"

Answer. Passing isn't the bar; exercising the right code is. Two failure modes in these repos: the mock is never injected — Medibank (GetNewListUsecaseTest.kt:36) and Pair Programming (MainViewModelTest.kt:36-50) both create a mock but the subject constructs its own real dependency, so the test hits the network and passes by accident; and tautological assertions — Pair Programming asserts the result is ArrayList<News>, which is always true. A good test injects a fake, drives one behavior, and asserts a specific expected value (a UiState.Success(expected)), and it controls time with a TestDispatcher instead of delay(1000). Talking points: inject the double; assert specifics not types; runTest + TestDispatcher; test the error branch too (Turbine for Flow). See 06-testing-di.md.

Q13. "How would you prevent the list from re-fetching on rotation?"

Answer. Hoist the fetch above the Activity's lifecycle. MCR re-fetches because LaunchedEffect(Unit) runs on each recomposition/recreation and there's no state holder; OneFootball reloads in onResume; News App refetches on rotation because the raw Thread lives in the Activity. Move the load into a ViewModel that fetches once in init (or a guarded load()), expose StateFlow, and collect it with collectAsStateWithLifecycle. The ViewModel survives rotation, so the data is cached across config changes for free. Talking points: ViewModel survives config change; LaunchedEffect(Unit) ≠ once-ever; SavedStateHandle for process death.

Q14. "notifyDataSetChanged() everywhere — does it matter?"

Answer. Yes — it rebinds every visible row, drops animations and scroll position, and is O(n) even for a one-item change. It shows up in 02/04/06/08/09. The fix is ListAdapter + DiffUtil: submitList(newList) diffs off the main thread and rebinds only what changed. Watch the companion trap: adapterPosition/bindingAdapterPosition can be NO_POSITION (-1) after a change, and indexing list[position] or getItem(-1) then crashes (MCR VehiclesFragment.kt:52, ImageSearch PhotoAdapter.kt:45) — guard for RecyclerView.NO_POSITION in click listeners. Talking points: DiffUtil/ListAdapter; stable keys; NO_POSITION guard.

Q15. "Would you merge this PR? Justify in one sentence."

Answer. State a verdict, then the single most important reason. "No — a synchronous main-thread network call in onCreate crashes the app on launch, so nothing else matters until that's off-thread" (Agilevent). Or "No — the API key is committed to source and history, which is a security incident regardless of code quality" (Medibank). The interviewer wants a decisive call plus evidence, not "well, it depends." If it's genuinely close, say what the one change is that would flip you to yes. Talking points: decisive verdict; lead with the top blocker; name the flip condition.

Q16. "You have 20 minutes and this whole app is a mess. What do you do?"

Answer. Triage, don't boil the ocean. First 5 min: read for the P0s — anything that crashes, ANRs, or leaks a secret. Next 10: fix or precisely document those, and pick the one structural change with the highest leverage (usually hoisting logic out of the Activity into a ViewModel, because it unblocks threading, error state, and testing at once). Last 5: write the punch list of everything I didn't get to, ranked, so the reviewer knows I saw it. Explicitly say "I'm parking the styling and the toolchain bump" so skipping them reads as a choice, not a miss. Talking points: P0 sweep first; one high-leverage refactor; a ranked "not done" list; verbalize your parking decisions.

Q17. "The app reads from a WebView — any concerns?"

Answer. Yes — unvalidated URLs are an injection/redirect surface. PetApp (10) loads an arbitrary JSON-provided content_url into a WebView and its shouldOverrideUrlLoading re-loads any URL with no allowlist. I'd validate the scheme/host against an allowlist, disable JavaScript unless required, avoid addJavascriptInterface with untrusted content, and never load http://. Medibank's news links similarly flow into a WebView — those should at least be https and origin-checked. Talking points: URL allowlist; disable JS by default; no addJavascriptInterface for remote content; https only.

Q18. "What did the candidate do right?" (or: "Is anything here good?")

Answer. Always have this ready — it signals you review fairly. OneFootball uses a proper data class, RecyclerView + ViewHolder, and Coil for images. Pair Programming injects its API key correctly via a BuildConfig interceptor. Kakao reads keys from local.properties and debounces search input. Better-Android (09) actually gets Rx threading right and disposes its CompositeDisposable in onDestroy. Calling these out shows I'm evaluating the code, not just pattern-matching for bugs — and it makes the blocking feedback land better. Talking points: fairness; specific positives by file; feedback lands better when balanced.

    data class Error(val message: String) : UiState<Nothing>
}

class ReviewsViewModel(private val repo: ReviewsRepository) : ViewModel() {
    private val _state = MutableStateFlow<UiState<List<Review>>>(UiState.Loading)
    val state: StateFlow<UiState<List<Review>>> = _state.asStateFlow()

    init { load() }

    fun load() = viewModelScope.launch {
        _state.value = UiState.Loading
        _state.value = runCatching { repo.getReviews() }
            .fold({ UiState.Content(it) }, { UiState.Error(it.message ?: "Something went wrong") })
    }
}

Compose side renders the three states — no data == null spinner heuristic, no crash on failure.

6. Interview Talking-Points / Soft-Skills One-Pager

How to prioritize (say this framing)

"I'll triage into blockers (crashes, ANRs, security, data loss), major (architecture/testability/error handling), and minor (naming, style, dead code). I'll fix or flag blockers first."

Concrete blocker examples to name: main-thread I/O ANR (04), guaranteed crash-on-null (08, 06), leaked secret (01), doesn't compile (11/15/20).

How to state a verdict

Use one of three, and commit:

  • ❌ Not ready / request changes — has blockers. "I'd request changes: the hardcoded key and the main-thread parse are merge blockers."
  • ⚠️ Approve with comments — no blockers, but majors. "Approve once the GlobalScope→viewModelScope and error-state changes land."
  • ✅ Approve — clean (rare in these exercises).

Always: verdict → top 3 reasons → what would change your mind.

How to disagree / handle pushback

  • Anchor on impact, not taste: "This isn't style — getExtras() returns null on a cancelled result, so this NPEs 100% of the time." (07/14)
  • Concede cheaply: "Fair, the enum is a nice-to-have; the null-safety is the must-fix."
  • Offer the trade: "If we're tight on time, keep the manual parse but at least wrap it in try/catch and add the IO dispatcher."
  • Ask before assuming: for 18 (empty scaffold) the right move was "there's no subject code — can you confirm the repo/branch?" — not inventing findings.

Narration habits that score points

  • Read the entry class first, out loud: "Everything's in MyNewsActivity — that's my architecture finding."
  • Cite file:line. "MainViewModel.kt:16, GlobalScope."
  • Separate correctness ("this crashes") from quality ("this is hard to test").
  • State the fix, not just the flaw. Every finding = problem → impact → fix.
  • Time-box aloud: "I'll spend 2 more minutes on tests then summarize."
