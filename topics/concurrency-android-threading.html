3.1 Java Thread Basics

Process vs Thread

A process is an isolated program instance — it gets its own memory space, file descriptors, and OS resources, and the kernel schedules it independently. Processes cannot share memory without explicit IPC.

A thread is an execution unit that lives inside a process. All threads in a process share the same heap and static fields, but each has its own stack, program counter, and register set. Creating a thread is much cheaper than forking a process, but the shared address space is exactly what makes multi-threading dangerous.

On Android, every Application normally runs in a single process (unless android:process is set on a component). Inside that process, the runtime starts several threads automatically — the main thread, GC threads, Binder threads, and so on.

// Cheapest way to observe threads in Android
Thread.currentThread().name  // "main", "pool-1-thread-1", etc.
android.os.Process.myPid()   // Linux PID of the process
android.os.Process.myTid()   // Linux TID of the calling thread

Thread Lifecycle States

NEW ──► RUNNABLE ──► RUNNING ──► TERMINATED
                  ▲        │
                  │        ▼
               BLOCKED / WAITING / TIMED_WAITING
State Meaning
NEWThread object created, start() not yet called
RUNNABLEReady to run; may or may not be on-CPU
RUNNING(JVM abstraction) scheduler gave it CPU time
BLOCKEDWaiting to acquire an intrinsic monitor lock
WAITINGParked indefinitely via wait(), join(), LockSupport.park()
TIMED_WAITINGSame but with a timeout (sleep, wait(ms), join(ms))
TERMINATEDrun() returned or threw an uncaught exception

The key transition gotcha is this: a thread in WAITING cannot be scheduled until another thread calls notify()/notifyAll() or unpark(). A thread in BLOCKED is actively competing for a lock with other threads — it's ready to run, it just can't get in.

Context Switching

The OS scheduler preempts threads on time-slice boundaries or when a thread blocks. Switching means saving the current thread's registers and stack pointer, loading the next thread's saved state, and updating the TLB. On Android (Linux scheduler — CFS, Completely Fair Scheduler), threads are scheduled by priority (nice value). android.os.Process.setThreadPriority() maps to nice values.

The cost implication is that context switches carry CPU cache eviction overhead. Too many threads means too many switches, which means contention for CPU caches and a real slowdown in throughput. That is exactly why thread pools exist.

Race Conditions

A race condition occurs when program correctness depends on the relative timing of operations across two or more threads, and that timing is not controlled.

Classic example — two threads each doing balance += deposit:

Thread A reads balance (100)
Thread B reads balance (100)
Thread A writes 100 + 50 = 150
Thread B writes 100 + 75 = 175   // A's update is lost!

The final value should be 225 but is 175. The compound "read-modify-write" operation is the hazard.

Critical Sections

A critical section is a block of code that accesses shared mutable state and must be executed by at most one thread at a time. The goal of every synchronization mechanism is to enforce mutual exclusion over critical sections while minimizing the time threads spend waiting.

Shared Mutable State

There are three factors that create thread-safety problems. First, the data is shared — accessible from multiple threads. Second, it is mutable — the value can change. Third, there is no synchronization — no mechanism forces ordered, exclusive access.

There are three solution paths. Either do not share the data and confine it to one thread (thread confinement). Or do not mutate it and use immutable or read-only data structures. Or synchronize access using locks, atomics, or lock-free algorithms.

Thread Safety, Visibility, Atomicity, Ordering

Thread safety means a class behaves correctly when accessed from multiple threads, regardless of scheduling, without additional synchronization by the caller.

Visibility is the guarantee that when thread A writes a variable, thread B actually sees that write. Without a happens-before relationship, the JMM allows threads to cache variables in registers or local CPU caches, so there is no such guarantee by default.

Atomicity means an operation completes in a single, indivisible step from the perspective of other threads. Reading or writing a 32-bit int or reference is atomic per JMM, but long and double on 32-bit JVMs are not guaranteed atomic because they require two separate 32-bit writes. Compound operations like i++ are never atomic even for int.

Ordering is the rule that the JMM allows the compiler and CPU to reorder instructions, as long as the result is equivalent within a single thread. Another thread may observe a different order unless happens-before edges — from locks, volatile, or final fields — prevent it.

Concurrency vs Parallelism

Concurrency is about structure — designing a program so that multiple logical tasks can overlap in time. A single-core machine can run concurrent code by interleaving.

Parallelism is about execution — two or more tasks literally running at the same moment on multiple cores.

On Android, a single-core device can be fully concurrent (async IO, handler messages) but not parallel. A multi-core device can do both.

Why Does a Bug Disappear Under a Debugger?

Debuggers slow thread execution, insert memory barriers via breakpoints (the int3 trap flushes caches), and change timing. A race that only triggers in a narrow timing window often disappears when execution speed changes — that is a Heisenbug. The cure is proper synchronization, not relying on timing.

3.2 Locks and Synchronization

Intrinsic Lock (Monitor Lock)

Every Java object has exactly one intrinsic lock, also called a monitor lock. When a thread enters a synchronized block or method on that object, it acquires the lock. When it exits — normally or via exception — it releases the lock. The lock has two effects. First, mutual exclusion: only one thread holds the lock at a time. Second, visibility: acquiring a lock flushes the thread's local cache, and releasing it flushes writes back to main memory, creating a happens-before edge.

Java Monitor

A monitor bundles three things: a mutex for mutual exclusion, a wait set for threads parked via wait(), and ownership tracking for which thread holds it and its reentry count.

The JVM implements monitors using object headers (mark word). When uncontended, HotSpot uses biased locking — a single CAS. Under contention it inflates to a full OS mutex (futex on Linux).

synchronized Method vs Block

// Method — locks on `this` (or the Class object for static)
public synchronized void deposit(int amount) {
    balance += amount;
}

// Block — explicit lock object, narrower scope
public void deposit(int amount) {
    synchronized (lock) {
        balance += amount;
    }
}

Prefer the block form because there are three advantages. First, you can choose a more appropriate lock object — typically a private Object lock = new Object() rather than this. Second, you can narrow the synchronized region, keeping non-shared work outside the lock. Third, you avoid accidentally exposing the lock, since clients of this can also call synchronized(account){} and interfere.

Mutual Exclusion

Mutual exclusion — mutex — guarantees that at most one thread executes a critical section at a time. In Java, holding the intrinsic lock of an object provides mutual exclusion over all synchronized blocks on that same object.

Reentrant Locks

Java's intrinsic lock is reentrant: a thread that already holds a lock can acquire it again without deadlocking, because the JVM tracks a reentry count. This matters when a synchronized method calls another synchronized method on the same object.

java.util.concurrent.locks.ReentrantLock provides explicit, reentrant locking with extra features. There are four worth knowing: tryLock(timeout) to avoid blocking forever; lockInterruptibly() to respond to thread interruption while waiting; Condition objects for multiple wait sets per lock instead of the single wait set a monitor gives you; and a fairness option that queues waiting threads in FIFO order.

val lock = ReentrantLock()
val notFull = lock.newCondition()
val notEmpty = lock.newCondition()

fun produce(item: Int) {
    lock.lock()
    try {
        while (buffer.size == MAX) notFull.await()
        buffer.add(item)
        notEmpty.signal()
    } finally {
        lock.unlock()  // always in finally
    }
}

Deadlock

A deadlock occurs when two or more threads are permanently blocked, each waiting for a lock held by another.

There are four necessary conditions — called the Coffman conditions — and all four must hold simultaneously. First, mutual exclusion: resources are held exclusively. Second, hold-and-wait: a thread holds a lock while waiting for another. Third, no preemption: locks cannot be forcibly taken away. Fourth, circular wait: A waits for B and B waits for A, or a longer cycle.

Classic example:

// Thread 1
synchronized (lockA) { synchronized (lockB) { /* work */ } }

// Thread 2
synchronized (lockB) { synchronized (lockA) { /* work */ } }

Prevention strategies:

  • Lock ordering: always acquire locks in the same global order.
  • Lock timeout: use tryLock(timeout) and back off if acquisition fails.
  • Lock leveling: assign numerical levels to locks; always acquire in ascending order.
  • Single lock: if possible, use one coarse-grained lock.
  • Avoid holding locks while calling foreign code (callbacks, listeners).

Livelock

A livelock is when threads are not blocked but are continuously changing state in response to each other without making any progress. The analogy is two people in a corridor stepping aside simultaneously — each mirrors the other's move and neither passes.

Starvation

Starvation is when a thread cannot gain access to a resource because other threads are always preferred. Common causes are unfair schedulers, high-priority threads monopolizing a lock, or a caller that always uses notify() instead of notifyAll().

The fix is to use a fair lock (ReentrantLock(fair=true)) and always prefer notifyAll() over notify().

Lock Contention and Granularity

Contention occurs when multiple threads frequently try to acquire the same lock simultaneously, causing queueing and reduced throughput.

Granularity is the scope of data protected by a single lock. A coarse-grained lock covers the whole object — simple but high contention. A fine-grained lock covers one data element (lock striping in ConcurrentHashMap is a good example) — low contention, but more complex and more prone to deadlock.

The rule of thumb is: start coarse, measure, then refine. Premature lock splitting introduces bugs.

3.3 Volatile and Atomic Classes

volatile — Visibility, Not Compound Atomicity

The volatile keyword in Java/Kotlin does three things: it ensures every read comes from main memory rather than a register or cache; it ensures every write goes directly to main memory; and it establishes a happens-before relationship so that a write to a volatile field happens-before every subsequent read of that field. What it does NOT provide is atomicity for compound operations.

volatile is sufficient in two situations: a boolean flag written by one thread and read by others (such as @Volatile var cancelled = false), and a single-writer, multi-reader reference swap where you are swapping an immutable config object.

volatile is not enough when the operation is compound. count++ is actually three steps — read, increment, write — so two threads can both read the same value and both write oldValue + 1, losing one increment. The same problem applies to check-then-act patterns like if (!initialized) initialize(), where two threads can both see false and both call initialize(). Any read-modify-write sequence has this hazard.

AtomicInteger, AtomicBoolean, AtomicReference

java.util.concurrent.atomic classes use CAS — Compare-And-Swap — CPU instructions to achieve lock-free, thread-safe operations on single variables.

val counter = AtomicInteger(0)
counter.incrementAndGet()           // atomic i++, returns new value
counter.getAndAdd(5)                // atomic i += 5, returns old value
counter.compareAndSet(10, 20)       // if current == 10, set to 20; returns bool

val flag = AtomicBoolean(false)
flag.compareAndSet(false, true)     // safe initialization gate

val ref = AtomicReference<Config>(initialConfig)
ref.set(newConfig)                  // atomic reference swap

AtomicLong, AtomicIntegerArray, and AtomicReferenceArray cover arrays.

LongAdder and LongAccumulator give better throughput under high contention because they maintain multiple cells that are summed on read, so there is no single hot CAS location.

Compare-And-Swap (CAS)

CAS is a single CPU instruction (CMPXCHG on x86): if the memory location currently holds expected, replace it with update and return whether the swap succeeded.

CAS(addr, expected, update):
  if *addr == expected:
    *addr = update
    return true
  return false

AtomicInteger's incrementAndGet in pseudo-code:

loop:
  old = read(counter)
  new = old + 1
  if CAS(counter, old, new): return new
  // else: another thread modified counter, retry

This is an optimistic spin loop. Under low contention it is faster than a mutex. Under very high contention the spin loops waste CPU — prefer LongAdder.

The ABA problem is worth knowing: CAS only checks value equality, so if a value changes from A to B and back to A, CAS cannot detect the round trip. The solution is AtomicStampedReference or AtomicMarkableReference, both of which include a version stamp alongside the value.

Decision Matrix

Scenario Use
Read/write single flag (1 writer)@Volatile var
Increment counter from many threadsAtomicInteger
High-contention counter (stats)LongAdder
CAS-based conditional reference swapAtomicReference
Multiple related fields must be consistentsynchronized or ReentrantLock

3.4 Wait/Notify and Producer-Consumer

The Monitor Wait Set

Every Java object has a wait set. Calling wait() on an object requires holding that object's intrinsic lock. When called, there are four steps: the current thread releases the lock; the thread is placed in the object's wait set and suspended; when another thread calls notify() or notifyAll(), the thread moves from the wait set back to the blocked state, competing for the lock again; and when the lock is re-acquired, wait() returns.

The important contrast is with sleep(), which does NOT release any lock. A sleeping thread holds all its locks.

Spurious Wakeups

The JVM specification allows wait() to return even if no notify() was called — that is a spurious wakeup. Always check the condition in a loop:

// WRONG
synchronized (lock) {
    if (!conditionMet()) lock.wait();
    // proceed — might be spurious
}

// CORRECT
synchronized (lock) {
    while (!conditionMet()) lock.wait();
    // condition is definitely true now
}

Guarded Block

A guarded block is a wait-in-a-loop pattern that protects a critical operation behind a condition check:

synchronized (queue) {
    while (queue.isEmpty()) queue.wait();
    Item item = queue.remove();
    queue.notifyAll();
}

Producer-Consumer with wait/notify

class BoundedBuffer<T>(private val capacity: Int) {
    private val buffer = ArrayDeque<T>()

    @Synchronized
    fun put(item: T) {
        while (buffer.size == capacity) (this as Object).wait()
        buffer.addLast(item)
        (this as Object).notifyAll()
    }

    @Synchronized
    fun take(): T {
        while (buffer.isEmpty()) (this as Object).wait()
        val item = buffer.removeFirst()
        (this as Object).notifyAll()
        return item
    }
}

Use notifyAll() rather than notify() unless you know only one thread can act on the notification. The rule of thumb is: always use notifyAll to be safe, even if it is slightly less efficient.

BlockingQueue — Prefer This Over Manual Wait/Notify

java.util.concurrent.BlockingQueue encapsulates the producer-consumer pattern correctly, and you should prefer it over rolling your own wait/notify logic:

val queue = LinkedBlockingQueue<Work>(100)  // bounded

// Producer
queue.put(work)     // blocks if full, uninterruptible
queue.offer(work, 500, TimeUnit.MILLISECONDS)  // timeout variant

// Consumer
val work = queue.take()          // blocks if empty
val work2 = queue.poll(500, TimeUnit.MILLISECONDS)

The main implementations are: ArrayBlockingQueue — fixed-size, backed by array, single lock; LinkedBlockingQueue — optionally bounded, with separate head and tail locks for higher throughput; SynchronousQueue — zero capacity, where each put must pair with a take (a handoff); PriorityBlockingQueue — unbounded, ordered by priority; and DelayQueue — elements only become available after a configured delay, useful for scheduled tasks.

BlockingQueue is preferred because it handles spurious wakeups, lock ordering, and condition management internally, so you cannot get those details wrong.

3.5 Executors and Task Execution

Why Not new Thread() Per Task?

There are four problems. First, thread creation overhead — stack allocation and an OS kernel thread. Second, there is no upper bound on concurrency, which means memory exhaustion under load. Third, there is no lifecycle management, no exception handling, and no monitoring. Fourth, there is thread teardown cost when the work is done.

Executor and ExecutorService

interface Executor {
    void execute(Runnable command);
}

interface ExecutorService extends Executor {
    Future<?> submit(Runnable task);
    <T> Future<T> submit(Callable<T> task);
    void shutdown();        // no new tasks; finish current
    List<Runnable> shutdownNow();  // interrupt in-progress, return queued
    boolean awaitTermination(long timeout, TimeUnit unit);
}

Thread Pool Types

// Fixed: exactly N threads, LinkedBlockingQueue (unbounded by default)
val fixed = Executors.newFixedThreadPool(4)

// Cached: grows as needed, idle threads expire in 60s; good for many short tasks
val cached = Executors.newCachedThreadPool()

// Single: exactly 1 thread, tasks serialized
val single = Executors.newSingleThreadExecutor()

// Scheduled: delays and periodic tasks
val scheduled = Executors.newScheduledThreadPool(2)
scheduled.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS)

Use ThreadPoolExecutor directly when you need full control:

ThreadPoolExecutor(
    corePoolSize = 4,          // always-alive threads
    maximumPoolSize = 8,       // max threads when queue is full
    keepAliveTime = 60L,       // idle thread timeout
    unit = TimeUnit.SECONDS,
    workQueue = LinkedBlockingQueue(100),   // bounded queue
    threadFactory = { r -> Thread(r, "worker-${counter.incrementAndGet()}") },
    handler = ThreadPoolExecutor.CallerRunsPolicy()  // backpressure policy
)

Callable and Future

val executor = Executors.newFixedThreadPool(4)
val future: Future<Int> = executor.submit(Callable {
    heavyComputation()
})

// Later...
try {
    val result = future.get(5, TimeUnit.SECONDS)   // blocks until done or timeout
} catch (e: TimeoutException) {
    future.cancel(true)  // interrupt the task
} catch (e: ExecutionException) {
    throw e.cause!!      // unwrap the original exception
}

isDone(), isCancelled(), and cancel(mayInterruptIfRunning) are the non-blocking query methods.

Cancellation

future.cancel(true) sets the interrupt flag on the executing thread. The task must cooperate by checking Thread.interrupted() or by calling methods that throw InterruptedException — such as sleep, wait, or queue.take.

while (!Thread.currentThread().isInterrupted()) {
    // process chunk
}

Backpressure and Queue Sizing

When producers submit tasks faster than consumers execute them, the queue grows. With an unbounded queue (LinkedBlockingQueue() no-arg), this eventually causes OutOfMemoryError. With a bounded queue, the chosen rejection policy kicks in:

Policy Behavior
AbortPolicy (default)Throws RejectedExecutionException
CallerRunsPolicyCaller thread runs the task (natural backpressure)
DiscardPolicySilently drops the task
DiscardOldestPolicyDrops the oldest queued task, retries submit

Sizing guidance:

  • CPU-bound tasks: N_cores + 1 threads (the extra 1 covers when a thread page-faults or is preempted).
  • IO-bound tasks: N_cores * (1 + wait_time / service_time). If threads spend 90% waiting, use roughly 10x cores.
  • Mixed: profile first; start with N_cores * 2 and tune from there.

Thread Starvation

Starvation in an executor happens when a long-running task occupies a thread and shorter tasks wait indefinitely. In a single-thread executor, one hung task blocks everything. In a fixed pool, a thread that calls future.get() on another task submitted to the same pool can deadlock the entire pool — all threads end up waiting for tasks that have no available thread to execute them. This is thread-pool deadlock.

3.6 Android Application Threads

Main Thread (UI Thread)

Android apps start with one main thread per process. The main thread does five things: it runs the Looper's message loop; dispatches InputEvents; drives Choreographer for frame rendering (calling View.draw, View.measure, View.layout, and onDraw); delivers lifecycle callbacks like onCreate and onResume; and processes BroadcastReceiver.onReceive.

The key constraint is that the UI toolkit is not thread-safe — only the thread that created a view hierarchy can update it. Calling view.setText(...) from a background thread causes CalledFromWrongThreadException.

ANR (Application Not Responding)

ANR triggers in three situations: the main thread does not process a user input event within 5 seconds; onReceive() does not complete within 10 seconds for a foreground broadcast or 60 seconds for background; or Service.onStartCommand() does not return within 20 seconds.

All of these happen because the main thread's MessageQueue is blocked. The common causes are synchronous network or disk IO on the main thread, large database queries, holding a lock that another thread is waiting for, a long while loop, or waiting for a Binder call to a dead process.

For debugging, adb shell kill -3 <pid> dumps thread stacks to logcat, and StrictMode.setThreadPolicy() catches disk and network violations on the main thread in debug builds.

Binder Threads

Binder is Android's high-performance IPC mechanism. Each process has a thread pool of roughly 15 Binder threads maintained by the Binder driver. Remote calls arrive on one of these threads, not the main thread. There are three implications: Service.onBind() may be called on a Binder thread; AIDL interface implementations run on Binder threads so they must be thread-safe; and synchronous Binder calls from the main thread block the main thread until the remote returns.

Background Threads

Background threads are all threads other than main and Binder — any thread the app creates via Thread, Executor, HandlerThread, coroutines, and so on. They can perform any work but cannot touch UI directly. Results must be posted back to the main thread via Handler, runOnUiThread, LiveData.postValue, or withContext(Dispatchers.Main).

Linux Process and Scheduling

Android runs on Linux, where each thread is a Linux task. The Linux CFS (Completely Fair Scheduler) assigns CPU time based on virtual runtime and nice value. Android maps thread priorities to Linux nice values:

Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND)  // nice +10
Process.setThreadPriority(Process.THREAD_PRIORITY_DEFAULT)     // nice 0
Process.setThreadPriority(Process.THREAD_PRIORITY_URGENT_DISPLAY) // nice -8

Background threads should use THREAD_PRIORITY_BACKGROUND or lower so they do not compete with the UI thread for CPU time.

Debugging Main-Thread Freezes

There are five tools. StrictMode catches disk and network violations in debug builds. Systrace and Perfetto show the frame timeline and exactly where main thread time is spent. The Android Studio Profiler CPU view gives you the thread timeline and method traces. ANR traces at /data/anr/anr_* contain thread dumps captured at the moment of the ANR. And adb shell kill -3 <pid> forces a thread dump without killing the process.

3.7 Handler / Looper / MessageQueue

Architecture Overview

Thread A                Thread B (UI thread)
   │                         │
   │                     ┌───┴───┐
   │                     │Looper │◄── loop() blocks here
   │                     └───┬───┘
   │                         │
   │                     ┌───┴──────┐
   └──── handler.post() ─►│MessageQueue│
                          └───┬──────┘
                              │ (next Message dequeued)
                           Handler.handleMessage()
                               or Runnable.run()

Looper

A Looper provides a message loop for a thread. There is only one Looper per thread. The main thread has one set up by the framework (ActivityThread.main()). Background threads do not have one by default.

// Manually set up a Looper on a background thread (rarely needed — use HandlerThread)
class MyThread : Thread() {
    lateinit var handler: Handler
    override fun run() {
        Looper.prepare()
        handler = Handler(Looper.myLooper()!!) { msg ->
            // handle message
            true
        }
        Looper.loop()  // blocks until quit() is called
    }
}

Looper.loop() blocks, dispatching messages one at a time. When a Message is available at or after its when timestamp, the Looper pops it and dispatches it to the Handler that sent it.

MessageQueue

MessageQueue is a priority queue ordered by delivery time (Message.when). Under the hood it is a singly-linked list of Message objects sorted by timestamp. Looper.loop() calls MessageQueue.next(), which blocks via nativePollOnce() — epoll on Linux — until the next message is due.

MessageQueue.addIdleHandler() lets you register callbacks that fire when the queue is empty. Libraries like Glide and Choreographer use this for work that should not delay frames.

Handler

A Handler is bound to a specific thread's Looper at construction time, so posting from any thread enqueues work on that Looper's thread.

// Posting from a background thread to the main thread
val mainHandler = Handler(Looper.getMainLooper())
mainHandler.post { textView.text = result }          // Runnable, ASAP
mainHandler.postDelayed({ doSomething() }, 3000L)    // Runnable, 3 seconds later
mainHandler.postAtTime({ doSomething() }, uptimeMs)  // Runnable, at absolute uptime

// Sending a Message (used for typed dispatch)
val msg = mainHandler.obtainMessage(MSG_UPDATE, data)
mainHandler.sendMessage(msg)
mainHandler.sendMessageDelayed(msg, 1000L)

post(Runnable) internally creates a Message with Message.callback set to the runnable. sendMessage(Message) sets Message.target to the handler and enqueues it.

Handler construction — Kotlin idiomatic:

// Callback-based (avoids subclassing)
val handler = Handler(Looper.getMainLooper()) { message ->
    when (message.what) {
        MSG_DONE -> { updateUi(message.obj as Result) ; true }
        else -> false
    }
}

HandlerThread

HandlerThread is a Thread subclass that sets up a Looper for you and exposes it after start(). It is the idiomatic way to get a background thread with a message loop:

val ht = HandlerThread("network-callback")
ht.start()
val bgHandler = Handler(ht.looper)

// When done:
ht.quitSafely()  // drains pending messages then stops
// ht.quit()     // stops immediately, may drop messages

Android uses HandlerThread internally for CameraDevice, Bluetooth, and IntentService (now deprecated).

Memory Leaks from Delayed Messages

A very common leak pattern:

class MyActivity : AppCompatActivity() {
    // LEAK: non-static/anonymous handler holds implicit reference to Activity
    val handler = Handler(Looper.getMainLooper())

    override fun onResume() {
        // Delayed message enqueued; activity may finish before it fires
        handler.postDelayed({ updateUI() }, 60_000L)
    }
}

The Handler holds a reference to this via the Runnable closure or callback. The MessageQueue holds the pending Message, which holds the Handler, which holds the Activity. The Activity cannot be garbage collected until that message fires or is removed.

Fix:

override fun onDestroy() {
    super.onDestroy()
    handler.removeCallbacksAndMessages(null)  // remove ALL pending messages/runnables
}

Alternatively, use a WeakReference<Activity> in the callback, or switch to lifecycle-aware coroutines which handle this automatically.

Communicating with the UI Thread

There are four modern idioms, all preferred over raw Handler. Activity.runOnUiThread { } internally posts to the main handler. View.post { } posts once the view's window is attached. LiveData.postValue() is thread-safe and deduplicates rapid updates. And withContext(Dispatchers.Main) { } is the coroutine-based approach.

3.8 Kotlin Coroutines on Android

What Is a Coroutine?

A coroutine is a suspendable computation. Unlike a thread, it does not block an OS thread when suspended — it saves its execution state (local variables, program counter) on the heap and releases the thread to do other work. When the suspension point completes, the coroutine is resumed, possibly on a different thread.

Coroutines are implemented via Continuation Passing Style transformation: the compiler rewrites suspend fun foo() into a state machine that passes a Continuation callback at each suspension point.

suspend Functions

A suspend function can be paused at suspension points — calls to other suspend functions or to suspendCoroutine/suspendCancellableCoroutine. It can only be called from another suspend function or a coroutine builder.

suspend fun fetchUser(id: String): User {
    return withContext(Dispatchers.IO) {   // suspension point
        userApi.getUser(id)
    }
}

The key rule is that suspend by itself does NOT make a function non-blocking. A suspend function that does synchronous CPU work blocks whatever thread it runs on. Use withContext(Dispatchers.Default) or Dispatchers.IO to actually offload the work.

Coroutine Builders

There are three builders. launch is fire-and-forget — it returns a Job and exceptions propagate to the scope's exception handler. Uncaught exceptions crash the parent scope unless it is backed by a SupervisorJob.

async is for concurrent computation that returns a result — it returns Deferred<T>. Exceptions are stored and rethrown when you call await().

runBlocking bridges blocking and suspending code by blocking the calling thread until the block completes. Use it only in main() or tests — never in production Android code, because it would block the calling thread.

// In tests:
@Test
fun testFetch() = runBlocking {
    val result = repository.fetchUser("123")
    assertEquals("Alice", result.name)
}

CoroutineScope

Every coroutine runs inside a CoroutineScope. The scope tracks all coroutines launched within it and provides cancellation propagation — when the scope is cancelled, all its children are cancelled.

// ViewModel provides viewModelScope
class MyViewModel : ViewModel() {
    fun load() {
        viewModelScope.launch {
            val data = repository.getData()   // suspend; non-blocking
            _state.value = data
        }
    }
    // viewModelScope is automatically cancelled in onCleared()
}

There are three standard scopes on Android. viewModelScope is tied to the ViewModel lifecycle. lifecycleScope is tied to a Lifecycle owner like an Activity or Fragment. GlobalScope should be avoided because it is not tied to any lifecycle and will leak coroutines.

Coroutine Context

A CoroutineContext is a map of context elements — Job, CoroutineDispatcher, CoroutineName, CoroutineExceptionHandler. Child coroutines inherit the parent's context but can override individual elements:

launch(Dispatchers.IO + CoroutineName("fetch-user")) {
    // runs on IO dispatcher, named for debugging
}

Dispatchers

Dispatcher Underlying thread pool Use case
Dispatchers.MainAndroid main threadUI updates, Compose, LiveData
Dispatchers.IOShared pool, up to 64 threads (or N_cores if larger)Blocking IO, network, file, database
Dispatchers.DefaultShared pool, N_cores threadsCPU-intensive computation
Dispatchers.UnconfinedCaller's thread, then resumes whereverRarely; testing or trivial bridges
CustomYour Executor.asCoroutineDispatcher()Dedicated background thread, Binder thread

Dispatcher injection for testability:

class UserRepository(
    private val api: UserApi,
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {
    suspend fun getUser(id: String): User = withContext(ioDispatcher) {
        api.fetchUser(id)
    }
}

// In tests:
val repo = UserRepository(mockApi, StandardTestDispatcher(testScheduler))

Structured Concurrency

Structured concurrency is the discipline that coroutines must complete before the scope that launched them completes. There are four consequences. A parent coroutine waits for all children before completing. Cancelling a parent cancels all children. A child failure propagates to the parent unless the scope uses a SupervisorJob. And coroutines cannot escape their scope's lifetime.

This makes reasoning about concurrent code dramatically simpler — there is no orphaned background work to worry about.

Job vs SupervisorJob

With a regular Job, when a child fails, the exception propagates to the parent, which then cancels all siblings and itself — one failure kills all siblings.

With a SupervisorJob, a child's failure does not propagate to the parent or siblings. Each child is independent. Use a SupervisorJob for top-level scopes where independent operations should not kill each other.

// viewModelScope uses SupervisorJob internally
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)

scope.launch { operationA() }  // if this throws, operationB keeps running
scope.launch { operationB() }

coroutineScope vs supervisorScope

Both are suspend functions that create a new child scope and neither returns until all children complete.

With coroutineScope, if any child throws, all siblings are cancelled and the exception propagates out. With supervisorScope, children are independent — one failure does not cancel siblings.

suspend fun loadDashboard() = coroutineScope {
    val user = async { fetchUser() }     // if this fails, everything fails
    val posts = async { fetchPosts() }
    DashboardData(user.await(), posts.await())
}

suspend fun loadOptional() = supervisorScope {
    val primary = async { fetchPrimary() }   // failure doesn't kill secondary
    val secondary = async { fetchSecondary() }
    // handle each result independently
}

withContext

withContext(context) switches the coroutine to a new context — typically a different dispatcher — for the duration of the block, then switches back:

suspend fun saveToDb(item: Item) {
    withContext(Dispatchers.IO) {
        db.insert(item)          // runs on IO thread
    }
    // back on the original dispatcher here
}

withContext does not start a new coroutine scope. It is semantically equivalent to async { ... }.await() but more efficient because it avoids the Deferred allocation.

Exception Handling

// Option 1: try/catch at the call site
viewModelScope.launch {
    try {
        val result = repository.fetch()
        _state.value = result
    } catch (e: IOException) {
        _error.value = e.message
    }
}

// Option 2: CoroutineExceptionHandler (for launch only, not async)
val handler = CoroutineExceptionHandler { _, e ->
    Log.e(TAG, "Unhandled exception", e)
}
viewModelScope.launch(handler) { dangerousWork() }

There are two important nuances. First, async does NOT invoke the CoroutineExceptionHandler — the exception is stored in the Deferred and rethrown when you call await(), so wrap await() in a try/catch.

Second, CancellationException is thrown when a coroutine is cancelled and it must NOT be caught and swallowed:

try {
    delay(1000)
} catch (e: Exception) {
    if (e is CancellationException) throw e  // re-throw!
    handleError(e)
}

Cancellation Cooperation

Coroutines are cancelled cooperatively — the runtime sets a flag and the coroutine must check it. All suspend functions in kotlinx.coroutines check for cancellation automatically. CPU-intensive work must check manually:

suspend fun processLargeList(list: List<Item>) {
    list.forEach { item ->
        ensureActive()        // throws CancellationException if cancelled
        // or: yield()        // checks cancellation AND yields scheduler
        process(item)
    }
}

The isActive property on CoroutineScope or Job is available for a non-throwing check.

Main-Safety

A function is main-safe if it can be called from the main thread without blocking it. The pattern is that every layer — ViewModel, Repository, DataSource — wraps its own heavy work in the appropriate dispatcher using withContext, rather than pushing that responsibility up to the caller.

// Repository is responsible for its own main-safety
class PhotoRepository(private val db: PhotoDao, private val api: PhotoApi) {
    suspend fun getPhotos(): List<Photo> = withContext(Dispatchers.IO) {
        db.getAll().ifEmpty { api.fetchAll().also { db.insertAll(it) } }
    }
}

// ViewModel just calls and updates state — no dispatcher needed here
class PhotoViewModel(private val repo: PhotoRepository) : ViewModel() {
    fun load() = viewModelScope.launch {
        _photos.value = repo.getPhotos()   // main-safe: repo handles dispatcher
    }
}

Testing Coroutines

@OptIn(ExperimentalCoroutinesApi::class)
class UserViewModelTest {
    @get:Rule val mainDispatcherRule = MainDispatcherRule()
    // MainDispatcherRule replaces Dispatchers.Main with TestCoroutineDispatcher

    @Test
    fun `load user updates state`() = runTest {
        val vm = UserViewModel(fakeRepository)
        vm.loadUser("1")
        advanceUntilIdle()   // runs all pending coroutines
        assertEquals(expectedUser, vm.state.value)
    }
}

// MainDispatcherRule
class MainDispatcherRule(
    private val dispatcher: TestDispatcher = UnconfinedTestDispatcher()
) : TestWatcher() {
    override fun starting(description: Description) = Dispatchers.setMain(dispatcher)
    override fun finished(description: Description) = Dispatchers.resetMain()
}

There are two test dispatchers. StandardTestDispatcher does not run tasks until you explicitly call advanceUntilIdle() or advanceTimeBy(), which gives you precise control over execution order. UnconfinedTestDispatcher runs tasks eagerly on the calling thread, which makes it simpler for tests that just need to observe state.

3.9 Flow, StateFlow, SharedFlow, Channel

Cold vs Hot Streams

A cold stream — Flow — does nothing until collected. Each collector gets its own independent execution of the producer, like calling a function fresh each time.

A hot stream — StateFlow, SharedFlow, Channel — produces values regardless of whether there are collectors. Multiple collectors share the same stream of values.

Flow — Cold Stream

fun fetchPages(): Flow<Page> = flow {
    var page = 1
    while (true) {
        emit(repository.getPage(page++))   // suspend, respects backpressure
    }
}

// Collect — starts the producer
viewModelScope.launch {
    fetchPages().collect { page ->
        // process page
    }
}

Flow is sequential by default — the producer and collector run in the same coroutine, and emit suspends until the collector processes the value.

Flow Operators

flow
    .map { transform(it) }                   // 1:1 transform
    .filter { it.isValid }                   // conditional pass-through
    .combine(otherFlow) { a, b -> a + b }    // zip latest from both flows
    .flatMapLatest { query ->                // cancel previous, start new on each emission
        searchApi.search(query)
    }
    .debounce(300)                           // suppress emissions within 300ms window
    .distinctUntilChanged()                  // suppress if same as previous value
    .catch { e -> emit(defaultValue) }       // handle upstream exceptions
    .retry(3) { e -> e is IOException }      // retry upstream on matching exception
    .stateIn(                                // convert to StateFlow
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5000),
        initialValue = emptyList()
    )
    .shareIn(                                // convert to SharedFlow
        scope = viewModelScope,
        started = SharingStarted.Eagerly,
        replay = 1
    )
    .collectLatest { value ->               // cancels previous collector block on new emission
        render(value)
    }

The three flatMap variants differ in how they handle concurrent inner flows. flatMapLatest cancels the previous inner flow when a new value arrives — use this for search queries. flatMapMerge runs all inner flows concurrently up to the concurrency limit. flatMapConcat runs them sequentially, one at a time.

For stateIn, there are three SharingStarted options. Eagerly starts immediately and never stops. Lazily starts on the first collector and never stops. WhileSubscribed(stopTimeoutMillis) stops N milliseconds after the last collector cancels and restarts when a new one arrives — for ViewModel-to-UI flows, 5000 ms is the recommended value because it survives a configuration change.

StateFlow — Hot State Holder

StateFlow is a hot flow that always holds exactly one current value. It is the replacement for LiveData in Kotlin codebases.

private val _state = MutableStateFlow<UiState>(UiState.Loading)
val state: StateFlow<UiState> = _state.asStateFlow()

// Update state
_state.value = UiState.Success(data)         // main thread
_state.update { current -> current.copy(...) } // atomic update

// Collect in Compose
val uiState by viewModel.state.collectAsStateWithLifecycle()

There are four key properties: it always has a current value (initial value required at construction); it only emits when the value actually changes, so distinctUntilChanged is baked in; new collectors immediately receive the current value since the replay is effectively 1; and the value setter is thread-safe using atomic CAS.

SharedFlow — Hot Broadcast

SharedFlow is for events that should reach multiple collectors, with a configurable replay cache.

private val _events = MutableSharedFlow<UiEvent>(
    replay = 0,            // new collectors don't get old events
    extraBufferCapacity = 1,
    onBufferOverflow = BufferOverflow.DROP_OLDEST
)
val events: SharedFlow<UiEvent> = _events.asSharedFlow()

// Emit
viewModelScope.launch { _events.emit(UiEvent.ShowSnackbar("Saved")) }
// or tryEmit (non-suspending, drops if buffer full)
_events.tryEmit(UiEvent.Navigate(Screen.Home))

For modeling one-time events: SharedFlow(replay=0) means the event fires once and only collectors active at that moment receive it. An alternative pattern is consumeAsFlow() via Channel. Avoid StateFlow for events because new collectors will replay the last event, which is almost never what you want for a navigation or snackbar command.

Channel — One-to-One Communication

Channel is a non-broadcast, coroutine-based primitive for producer-consumer patterns. Each value is consumed by exactly one collector — unlike SharedFlow, which broadcasts to all active collectors.

val channel = Channel<Work>(capacity = Channel.BUFFERED)

// Producer
launch { channel.send(work) }   // suspends if buffer full

// Consumer
launch { for (work in channel) process(work) }  // suspends if empty
// or
launch { channel.consumeEach { process(it) } }

channel.close()  // signals completion

There are four capacity modes. RENDEZVOUS (capacity 0) means the sender suspends until the receiver is ready — like SynchronousQueue. BUFFERED gives a small buffer of 64 by default. UNLIMITED never suspends on send. CONFLATED keeps only the last value.

For the Channel versus SharedFlow decision: use Channel when exactly one consumer should handle each event, such as a navigation command consumed by one Fragment. Use SharedFlow when multiple UI components should all react, such as a toast that could be visible in two places.

Lifecycle-Aware Collection

The problem with collecting a Flow inside a plain lifecycleScope.launch block is that collection continues when the UI is in the background (STOPPED), wasting resources and potentially updating invisible UI.

The solution is repeatOnLifecycle:

// In Fragment or Activity
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        // This block starts when STARTED, cancels when STOPPED
        // Restarts when STARTED again
        viewModel.state.collect { render(it) }
    }
}

repeatOnLifecycle is the correct way to collect Flows in the UI layer. It automatically cancels the inner block when the lifecycle drops below the target state and restarts it when the lifecycle rises again.

In Compose:

@Composable
fun MyScreen(viewModel: MyViewModel = hiltViewModel()) {
    // Lifecycle-aware: stops collecting when composable leaves composition/goes to background
    val uiState by viewModel.state.collectAsStateWithLifecycle()
    // render uiState
}

collectAsStateWithLifecycle is the Compose-specific equivalent of repeatOnLifecycle(STARTED) and requires androidx.lifecycle:lifecycle-runtime-compose.

For the launchIn versus repeatOnLifecycle choice: lifecycleScope.launchIn(this) combined with flowWithLifecycle() is an alternative for single flows, while repeatOnLifecycle is preferred for multiple flows or more complex collection logic.

3.10 Background Work

Categorizing Work

Category Definition Appropriate API
Immediate asyncMust run now, result needed soon, tied to app processCoroutines (viewModelScope, lifecycleScope)
DeferrableCan run later, at system's discretionWorkManager
PersistentMust complete even after process death or rebootWorkManager (deferrable) or Foreground Service (immediate persistent)
Exact timingMust run at a specific timeAlarmManager (with care)
Ongoing user-visibleLong-running, user-visible progressForeground Service

WorkManager

WorkManager is the recommended API for deferrable, persistent background work. It uses JobScheduler on API 23 and above, falling back to AlarmManager plus BroadcastReceiver on older devices. It survives process death and device restarts because constraints are re-registered at boot.

// Define a worker
class SyncWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        return try {
            repository.sync()
            Result.success()
        } catch (e: Exception) {
            if (runAttemptCount < 3) Result.retry() else Result.failure()
        }
    }
}

// Build a request
val request = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)
            .setRequiresBatteryNotLow(true)
            .build()
    )
    .setInputData(workDataOf("key" to "value"))
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
    .addTag("sync")
    .build()

// Enqueue
WorkManager.getInstance(context).enqueue(request)

// Unique work — only one sync at a time
WorkManager.getInstance(context)
    .enqueueUniqueWork("sync", ExistingWorkPolicy.REPLACE, request)

// Observe
WorkManager.getInstance(context)
    .getWorkInfoByIdLiveData(request.id)
    .observe(lifecycleOwner) { info ->
        if (info?.state == WorkInfo.State.SUCCEEDED) { /* done */ }
    }

Periodic Work

val periodicRequest = PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
    .setConstraints(networkConstraint)
    .build()

WorkManager.getInstance(context)
    .enqueueUniquePeriodicWork(
        "periodic-sync",
        ExistingPeriodicWorkPolicy.KEEP,  // or REPLACE, UPDATE
        periodicRequest
    )

The minimum period is 15 minutes, OS-enforced. KEEP means the existing scheduled work is left alone and no new request is enqueued.

Chained Work

WorkManager.getInstance(context)
    .beginWith(listOf(cleanupRequest, prepareRequest))  // parallel first step
    .then(uploadRequest)                                // sequential second step
    .then(notifyRequest)                                // sequential third step
    .enqueue()

Output of one worker flows to the input of the next via Data. If any worker returns Result.failure(), the chain stops unless subsequent workers are configured to handle failure input.

Expedited Work

For time-sensitive tasks that must start immediately but still need to survive process death:

val expeditedRequest = OneTimeWorkRequestBuilder<CriticalWorker>()
    .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
    .build()

On Android 12 and above, the worker runs with expedited job quota. On older versions it falls back to running as a foreground service.

Cancellation

WorkManager.getInstance(context).cancelWorkById(request.id)
WorkManager.getInstance(context).cancelAllWorkByTag("sync")
WorkManager.getInstance(context).cancelUniqueWork("periodic-sync")

Workers receive cancellation through CoroutineWorker's coroutine scope — the scope is cancelled, so all cooperative suspension points exit via CancellationException.

JobScheduler

JobScheduler is the Android framework API that WorkManager is built on. You would interact with it directly only when you need platform-specific features not exposed by WorkManager, which is rare. Jobs survive process death because they are registered with the system server.

val jobScheduler = getSystemService(JobScheduler::class.java)
val jobInfo = JobInfo.Builder(JOB_ID, ComponentName(this, SyncJobService::class.java))
    .setRequiredNetworkType(JobInfo.NETWORK_TYPE_ANY)
    .setPersisted(true)   // survives reboot
    .build()
jobScheduler.schedule(jobInfo)

One gotcha: JobService.onStartJob() runs on the main thread, so you must offload work to a background thread manually.

Foreground Services

Use a Foreground Service for long-running work that must continue while the app is in the background and where the user must be aware it is running via a persistent notification:

class MusicService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = buildNotification()
        startForeground(NOTIFICATION_ID, notification)
        playMusic()
        return START_STICKY   // restart if killed
    }
}

// Start (Android 9+)
ContextCompat.startForegroundService(context, Intent(context, MusicService::class.java))

Android 12 and above require declaring foregroundServiceType in the manifest — for example mediaPlayback, location, or camera. Android 14 enforces type-specific runtime permissions on top of that.

For the WorkManager versus Foreground Service decision: use WorkManager when the work is deferrable and the result can be delivered later or is network-triggered. Use a Foreground Service when the work is immediate and ongoing and the user is actively engaged — music playback, navigation, or an upload in progress.

AlarmManager

Use AlarmManager for work that must run at a precise time, even if the device is in Doze mode — use setExactAndAllowWhileIdle or setAlarmClock. It is not for deferrable work because the system cannot batch it.

val alarmManager = getSystemService(AlarmManager::class.java)
val pendingIntent = PendingIntent.getBroadcast(
    context, requestCode, Intent(context, AlarmReceiver::class.java),
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)
alarmManager.setExactAndAllowWhileIdle(
    AlarmManager.ELAPSED_REALTIME_WAKEUP,
    SystemClock.elapsedRealtime() + delayMs,
    pendingIntent
)

Android 12 and above require the SCHEDULE_EXACT_ALARM permission. Android 13 changes it to a user-grantable permission. Use exact alarms sparingly — they drain battery.

BroadcastReceiver Limitations

Statically registered receivers in the manifest are subject to background execution limits from Android 8 onward. Most implicit broadcasts are no longer delivered to them. Runtime-registered receivers do receive broadcasts while the app is running.

onReceive() runs on the main thread and must complete in roughly 10 seconds or an ANR will fire. Never start long-running work directly from onReceive — instead kick off a WorkManager job. JobIntentService is deprecated; WorkManager is the correct replacement.

Doze Mode and App Standby

Doze mode activates when the device is off the charger, stationary, and screen off for a period. Android then restricts network access, JobScheduler jobs, alarms (except setAlarmClock), and sync adapters. Only setExactAndAllowWhileIdle alarms fire during Doze.

App Standby Buckets bucket apps by usage frequency — Active, Working Set, Frequent, Rare, Restricted. Apps in the Rare bucket may have their jobs deferred significantly. WorkManager respects these buckets automatically.

Retry and Backoff

Returning Result.retry() from a Worker schedules a retry using the configured backoff policy:

OneTimeWorkRequestBuilder<MyWorker>()
    .setBackoffCriteria(
        BackoffPolicy.EXPONENTIAL,   // or LINEAR
        WorkRequest.MIN_BACKOFF_MILLIS,  // minimum 10 seconds
        TimeUnit.MILLISECONDS
    )
    .build()

BackoffPolicy.EXPONENTIAL doubles the delay each attempt, capped at 5 hours. LINEAR adds a fixed increment each time.

WorkManager vs Coroutine Decision

The core decision rule is: if the work must survive process death or a device reboot, use WorkManager. If it can die with the process, a coroutine in the appropriate scope is simpler.

Criterion Coroutine WorkManager
Must survive process death?NoYes
Must survive device reboot?NoYes (with setPersisted equivalent)
Can be deferred by system?NoYes
Tied to user-visible work?NoNo (unless expedited)
One-shot network request in ViewModelYesNo
Upload file, retry if network dropsNoYes
Sync data in background periodicallyNoYes

Debugging Background Work

There are four useful adb commands:

# Inspect WorkManager database
adb shell content query --uri content://androidx.work.diagnostics.WorkDiagnosticsProvider

# Dump job scheduler state
adb shell dumpsys jobscheduler

# Trigger Doze mode manually
adb shell dumpsys deviceidle force-idle

# Trigger app standby bucket
adb shell am set-standby-bucket <package> rare

WorkManager also exposes a built-in diagnostic tool accessible at runtime:

WorkManager.getInstance(context).getWorkInfosByTagLiveData("sync")
// or observe all work:
WorkManager.getInstance(context).getWorkInfosLiveData(WorkQuery.fromStates(WorkInfo.State.RUNNING))

Quick-Reference: Interview Cheat Sheet

Race Condition

Two threads read-modify-write a shared variable without synchronization, so one update is lost.

Thread-Safe

A class is thread-safe if its invariants hold under concurrent access without external synchronization by the caller.

Intrinsic Lock

Every Java object has one. synchronized on that object acquires it and provides both mutual exclusion and visibility.

Deadlock Prevention

Lock ordering: always acquire multiple locks in the same canonical order across all threads.

volatile vs AtomicInteger

volatile gives visibility only — count++ is still a race. AtomicInteger.incrementAndGet() is a single CAS, so it is atomic and visible.

wait() vs sleep()

wait() releases the monitor and parks the thread in the wait set. sleep() does not release any lock.

Why Not GlobalScope?

It is not bound to any lifecycle, so coroutines survive ViewModel and Activity destruction, causing leaks and unexpected behavior.

Structured Concurrency

A parent scope cannot complete until all children complete. Cancellation and exceptions propagate through the parent-child hierarchy automatically.

Job vs SupervisorJob

With a Job, one child failing cancels all siblings. With a SupervisorJob, each child is independent.

StateFlow vs SharedFlow

StateFlow always has a current value, replays it to new collectors, and has distinctUntilChanged built in — use it for state. SharedFlow has configurable replay and no built-in dedup — use it for events and broadcasts.

repeatOnLifecycle vs launchWhenStarted

launchWhenStarted is deprecated: it suspends collection but the coroutine stays alive, leaking resources. repeatOnLifecycle(STARTED) completely cancels and restarts the inner block, actually freeing resources when the UI goes to background.

WorkManager vs Coroutine

If the work must survive process death or device reboot, use WorkManager. Otherwise, a coroutine in the appropriate scope is simpler.

WorkManager vs Foreground Service

WorkManager is deferrable, battery-optimized, and system-scheduled. A Foreground Service is for immediate, ongoing, user-visible work that requires a persistent notification. When you need both persistence and immediacy, use WorkManager's expedited API, which runs as a Foreground Service under the hood on older API levels.
