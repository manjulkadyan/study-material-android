3.1 Java Thread Basics

Process vs Thread

🎤 Say it out loud (~30–45s): "A process is an isolated instance with its own address space, file descriptors, and OS resources, while a thread is a unit of execution inside a process that shares the heap and static fields but has its own stack and program counter. Threads are far cheaper to create than processes, but that shared address space is exactly what makes them dangerous — there's no memory isolation, so unsynchronized access corrupts state. On Android each app is usually one process with many runtime threads already running: main, GC, and Binder threads."

A process is an isolated program instance — it gets its own memory space, file descriptors, and OS resources, and the kernel schedules it independently. Processes cannot share memory without explicit IPC.

A thread is an execution unit that lives inside a process. All threads in a process share the same heap and static fields, but each has its own stack, program counter, and register set. Creating a thread is much cheaper than forking a process, but the shared address space is exactly what makes multi-threading dangerous.

On Android, every Application normally runs in a single process (unless android:process is set on a component). Inside that process, the runtime starts several threads automatically — the main thread, GC threads, Binder threads, and so on.

// Cheapest way to observe threads in Android
Thread.currentThread().name  // "main", "pool-1-thread-1", etc.
android.os.Process.myPid()   // Linux PID of the process
android.os.Process.myTid()   // Linux TID of the calling thread

Under the hood

On ART a java.lang.Thread maps 1:1 to a native OS thread — a Linux pthread created via pthread_create, which underneath issues the clone(2) syscall with flags like CLONE_VM | CLONE_FILES | CLONE_THREAD so the new task shares the address space and FD table with its peers. A process by contrast is a clone/fork without those sharing flags, giving copy-on-write separate memory. The thread's Linux TID (gettid) is what Process.myTid() returns, and the kernel's scheduler operates on these tasks, not on the JVM's abstract Thread objects.

Process (PID)
 ├─ shared: heap, static fields, code, FD table   ← one address space
 └─ Thread (TID)  Thread (TID)  Thread (TID)
     own: stack, PC, registers, kernel task_struct

Thread Lifecycle States

🎤 Say it out loud (~30–45s): "A Java thread moves NEW → RUNNABLE → terminated, and while runnable it can park into BLOCKED, WAITING, or TIMED_WAITING. The subtlety interviewers probe is the difference between BLOCKED and WAITING: a BLOCKED thread is actively contending for a monitor lock and is otherwise ready, whereas a WAITING thread is parked indefinitely and can't be scheduled until someone calls notify, signals it, or unparks it. The other gotcha is that a thread is single-use — once it's TERMINATED you can't call start again."
NEW ──► RUNNABLE ──► RUNNING ──► TERMINATED
                  ▲        │
                  │        ▼
               BLOCKED / WAITING / TIMED_WAITING
State Meaning
NEWThread object created, start() not yet called
RUNNABLEReady to run; may or may not be on-CPU
RUNNING(JVM abstraction) scheduler gave it CPU time
BLOCKEDWaiting to acquire an intrinsic monitor lock
WAITINGParked indefinitely via wait(), join(), LockSupport.park()
TIMED_WAITINGSame but with a timeout (sleep, wait(ms), join(ms))
TERMINATEDrun() returned or threw an uncaught exception

The key transition gotcha is this: a thread in WAITING cannot be scheduled until another thread calls notify()/notifyAll() or unpark(). A thread in BLOCKED is actively competing for a lock with other threads — it's ready to run, it just can't get in.

Under the hood

Thread.State is a pure JVM/JLS abstraction — there's no RUNNING enum value (it's folded into RUNNABLE), because from the JVM's view "ready to run" and "on-CPU" are both the kernel scheduler's business. ART tracks a separate internal thread state on its native Thread struct (e.g. kRunnable, kBlocked, kWaiting, kTimedWaiting, kSuspended) that the GC and debugger care about, and maps it onto the public enum. Underneath, a RUNNABLE thread is a Linux task in run state R, while BLOCKED/WAITING/TIMED_WAITING correspond to the kernel S (interruptible sleep) state parked on a futex. A Thread can't be restarted because start() checks the internal started/state field and throws IllegalThreadStateException once it has left NEW.

Context Switching

🎤 Say it out loud (~30–45s): "A context switch is when the scheduler saves one thread's CPU state — registers, stack pointer, program counter — and loads another's, either on a time-slice boundary or when a thread blocks. It's not free: beyond the kernel bookkeeping you pay for cache and TLB eviction, so the new thread starts cold. That's why spawning hundreds of threads hurts throughput and why we use bounded thread pools — past the core count you mostly buy switching overhead, not parallelism."

The OS scheduler preempts threads on time-slice boundaries or when a thread blocks. Switching means saving the current thread's registers and stack pointer, loading the next thread's saved state, and updating the TLB. On Android (Linux scheduler — CFS, Completely Fair Scheduler), threads are scheduled by priority (nice value). android.os.Process.setThreadPriority() maps to nice values.

The cost implication is that context switches carry CPU cache eviction overhead. Too many threads means too many switches, which means contention for CPU caches and a real slowdown in throughput. That is exactly why thread pools exist.

Under the hood

A switch is a kernel-mode operation: on a timer interrupt or blocking syscall the CPU traps into the kernel, the scheduler picks the next runnable task via CFS (which orders tasks by virtual runtime weighted by nice), and a low-level context_switch/switch_to swaps the register file, stack pointer, and address-space pointer (CR3 on x86). Swapping address spaces flushes much of the TLB; the new thread's working set is also cold in L1/L2, so the real cost is mostly micro-architectural, not the instruction count. Java thread priorities (1–10) are translated by ART into Linux nice values via setpriority/set_sched, which only bias CFS's choices — they don't give hard real-time guarantees.

Race Conditions

🎤 Say it out loud (~30–45s): "A race condition is when correctness depends on the relative timing of operations across threads and nothing controls that timing. The canonical one is a read-modify-write like balance += x: two threads both read the old value, both compute, and one write clobbers the other, so an update is lost. The key insight is that the += looks atomic in source but is actually three separate steps at the bytecode level, and the scheduler can interleave them — you fix it with a lock, an atomic, or by confining the state."

A race condition occurs when program correctness depends on the relative timing of operations across two or more threads, and that timing is not controlled.

Classic example — two threads each doing balance += deposit:

Thread A reads balance (100)
Thread B reads balance (100)
Thread A writes 100 + 50 = 150
Thread B writes 100 + 75 = 175   // A's update is lost!

The final value should be 225 but is 175. The compound "read-modify-write" operation is the hazard.

Under the hood

balance += deposit is not one operation at the bytecode level — for a field it compiles to roughly getfield (load), iadd (compute), putfield (store), and on a local/static the analogue is iload/iadd/istore. The JVM/ART is free to interleave any other thread's bytecode between those instructions, and the CPU may additionally keep balance in a register so each thread works on its own stale copy. There's no implicit lock and no happens-before edge, so even the final visibility of either write isn't guaranteed. java.util.concurrent.atomic types close the gap with a single CAS instruction (cmpxchg) that does compare-and-set indivisibly.

Critical Sections

🎤 Say it out loud (~30–45s): "A critical section is a region of code that touches shared mutable state and must be run by at most one thread at a time. Every synchronization primitive — synchronized, ReentrantLock, semaphores — exists to enforce mutual exclusion over critical sections. The design goal is to make the section as small as possible: you want it long enough to protect the invariant but short enough that threads aren't queueing behind a lock doing work that didn't need protecting."

A critical section is a block of code that accesses shared mutable state and must be executed by at most one thread at a time. The goal of every synchronization mechanism is to enforce mutual exclusion over critical sections while minimizing the time threads spend waiting.

Under the hood

A critical section has no special bytecode of its own — it's whatever instructions sit between a lock acquire and release. With synchronized that's the span between MONITORENTER and MONITOREXIT; with ReentrantLock it's the code between lock() and unlock(), enforced only by convention (hence the try/finally). The mutual-exclusion guarantee comes entirely from the surrounding lock's monitor or AQS state, plus the memory barriers those acquire/release operations emit, which is what turns "only one at a time" into "and the next thread sees the previous one's writes."

Shared Mutable State

🎤 Say it out loud (~30–45s): "Thread-safety problems need three ingredients at once: the data is shared across threads, it's mutable, and access isn't synchronized. Remove any one and the problem disappears, which gives you three strategies — confine the state to a single thread, make it immutable, or synchronize access with locks or atomics. I reach for confinement or immutability first because they're cheaper and harder to get wrong than locking."

There are three factors that create thread-safety problems. First, the data is shared — accessible from multiple threads. Second, it is mutable — the value can change. Third, there is no synchronization — no mechanism forces ordered, exclusive access.

There are three solution paths. Either do not share the data and confine it to one thread (thread confinement). Or do not mutate it and use immutable or read-only data structures. Or synchronize access using locks, atomics, or lock-free algorithms.

Under the hood

Immutability is enforced by the JMM's final-field semantics: when a constructor finishes, the JVM emits a freeze (a StoreStore barrier on the writer side) so that any thread observing the reference through a properly published object is guaranteed to see the correctly-initialized final fields without extra synchronization. Thread confinement leans on the fact that each thread has its own stack — locals never escape — and on ThreadLocal, which on ART is backed by a per-Thread ThreadLocalMap keyed by weak references to the ThreadLocal object, so there is literally no shared storage to race on.

Thread Safety, Visibility, Atomicity, Ordering

🎤 Say it out loud (~30–45s): "These are the four pillars. Thread safety means a class is correct under concurrent access with no extra caller synchronization. Visibility is whether one thread's write is seen by another — not guaranteed without a happens-before edge, because the JMM lets threads cache values. Atomicity is whether an operation is indivisible — single int and reference reads/writes are atomic, but long/double on 32-bit aren't, and i++ never is. Ordering is that the compiler and CPU can reorder instructions unless volatile, locks, or final fields establish a happens-before edge."

Thread safety means a class behaves correctly when accessed from multiple threads, regardless of scheduling, without additional synchronization by the caller.

Visibility is the guarantee that when thread A writes a variable, thread B actually sees that write. Without a happens-before relationship, the JMM allows threads to cache variables in registers or local CPU caches, so there is no such guarantee by default.

Atomicity means an operation completes in a single, indivisible step from the perspective of other threads. Reading or writing a 32-bit int or reference is atomic per JMM, but long and double on 32-bit JVMs are not guaranteed atomic because they require two separate 32-bit writes. Compound operations like i++ are never atomic even for int.

Ordering is the rule that the JMM allows the compiler and CPU to reorder instructions, as long as the result is equivalent within a single thread. Another thread may observe a different order unless happens-before edges — from locks, volatile, or final fields — prevent it.

Under the hood

These four are formalized by the Java Memory Model, whose primitive is the happens-before partial order; visibility and ordering are really the same guarantee viewed from two angles. A volatile write is implemented with a StoreStore+StoreLoad barrier sequence (and the read with LoadLoad+LoadStore), which on ARM lowers to dmb/load-acquire/store-release instructions and prevents both compiler hoisting and CPU store-buffer reordering. The non-atomic long/double rule exists because the JLS only mandates atomic 32-bit accesses; a 64-bit value can be written as two 32-bit putfield-style stores, so a reader can observe a torn high/low half — declaring the field volatile forces a single atomic 64-bit access.

Concurrency vs Parallelism

🎤 Say it out loud (~30–45s): "Concurrency is about structure — composing a program so multiple logical tasks can be in progress and overlap in time, even on one core via interleaving. Parallelism is about execution — tasks literally running simultaneously on multiple cores. The line interviewers like is Rob Pike's: concurrency is dealing with many things at once, parallelism is doing many things at once. On a single-core phone you can be fully concurrent with async IO and Handler messages but never truly parallel."

Concurrency is about structure — designing a program so that multiple logical tasks can overlap in time. A single-core machine can run concurrent code by interleaving.

Parallelism is about execution — two or more tasks literally running at the same moment on multiple cores.

On Android, a single-core device can be fully concurrent (async IO, handler messages) but not parallel. A multi-core device can do both.

Under the hood

Whether concurrent code actually runs in parallel is decided below the language by the kernel scheduler and the number of online CPU cores it can dispatch runnable tasks onto. On a single core, "concurrency" is just time-slicing — the scheduler rotates tasks on context-switch boundaries so they interleave but never overlap. Higher-level constructs reflect this: a Kotlin coroutine dispatcher like Dispatchers.Default multiplexes many coroutines (concurrency) over a thread pool sized to availableProcessors() (the parallelism ceiling), while Android's main Looper gives concurrency with zero parallelism — one thread draining a single MessageQueue.

Why Does a Bug Disappear Under a Debugger?

🎤 Say it out loud (~30–45s): "Because the debugger changes timing. Breakpoints, single-stepping, and the trap instruction slow execution and effectively flush caches and serialize memory, so a race that only fires in a tiny timing window stops reproducing. That's a Heisenbug — observing it changes it. The takeaway is that the bug isn't gone; the cure is real synchronization that establishes happens-before, never relying on the lucky timing the debugger happened to introduce."

Debuggers slow thread execution, insert memory barriers via breakpoints (the int3 trap flushes caches), and change timing. A race that only triggers in a narrow timing window often disappears when execution speed changes — that is a Heisenbug. The cure is proper synchronization, not relying on timing.

Under the hood

A breakpoint is implemented by patching the target instruction with a one-byte trap (int3 / 0xCC on x86, a BRK on ARM); hitting it raises an exception that transfers control to the debugger and parks the thread, which serializes execution and gives other threads time to "catch up," masking the race window. On ART, attaching a debugger via JDWP also disables JIT optimizations and forces interpreted execution for affected methods, so aggressive reorderings and register caching that exposed the visibility bug no longer happen. Single-stepping additionally suspends all-but-one thread at safepoints, collapsing the interleavings that produced the failure.

3.2 Locks and Synchronization

Intrinsic Lock (Monitor Lock)

🎤 Say it out loud (~30–45s): "Every Java object has exactly one intrinsic lock, also called its monitor. Entering a synchronized block or method acquires it and exiting — even via exception — releases it, so you get mutual exclusion: one thread at a time. Crucially it also gives a memory guarantee — acquiring establishes a happens-before edge with the previous release, so the writes the last holder made are visible to me. People remember the mutual exclusion and forget the visibility half, but both come from the same lock."

Every Java object has exactly one intrinsic lock, also called a monitor lock. When a thread enters a synchronized block or method on that object, it acquires the lock. When it exits — normally or via exception — it releases the lock. The lock has two effects. First, mutual exclusion: only one thread holds the lock at a time. Second, visibility: acquiring a lock flushes the thread's local cache, and releasing it flushes writes back to main memory, creating a happens-before edge.

Under the hood

The intrinsic lock lives in the object header's mark word — there is no separate lock object allocated up front. ART represents the lock state inline in that word and starts it as a lightweight "thin lock" holding the owning thread's id plus a recursion count, acquired with a single CAS. Only under genuine contention does it inflate to a "fat" monitor: ART allocates a Monitor object backed by an OS-level mutex/condition variable (a Linux futex), and the mark word is rewritten to point at it. The happens-before/visibility guarantee comes from the acquire and release each emitting full memory barriers around that mark-word transition.

Java Monitor

🎤 Say it out loud (~30–45s): "A monitor is the construct that bundles three things onto an object: a mutex for mutual exclusion, a wait set where threads that called wait park until notified, and ownership tracking — which thread holds it and the reentry count. That ownership count is what makes the lock reentrant. wait/notify operate on the wait set, and the gotcha is they must be called while holding the monitor or you get IllegalMonitorStateException."

A monitor bundles three things: a mutex for mutual exclusion, a wait set for threads parked via wait(), and ownership tracking for which thread holds it and its reentry count.

The JVM implements monitors using object headers (mark word). When uncontended, HotSpot uses biased locking — a single CAS. Under contention it inflates to a full OS mutex (futex on Linux).

Under the hood

The mark word doubles as the lock word, so the JVM avoids a per-object allocation for the common uncontended case. HotSpot historically used three tiers — biased (no atomics, just a stamped thread id), thin/lightweight (a CAS into a stack-allocated lock record), and fat/inflated (an ObjectMonitor with an OS mutex and the wait/entry queues); ART uses an analogous thin-to-fat scheme. Note that biased locking was deprecated and disabled by default in modern HotSpot (JDK 15+) because the cost of revoking a bias under unexpected contention outweighed the savings. wait()/notify() require the calling thread to own the monitor precisely because they manipulate that monitor's internal wait set, which the JVM guards by checking ownership and throwing IllegalMonitorStateException otherwise.

synchronized Method vs Block

🎤 Say it out loud (~30–45s): "Both take the same intrinsic lock; the difference is what object and what scope. A synchronized method implicitly locks on this — or the Class object if it's static — over the whole method. A synchronized block lets me choose the lock object and narrow the region. I prefer the block form with a private final lock object, because locking on this is a leak: any client holding my reference can synchronize on it and either deadlock me or starve my own threads."
// Method — locks on `this` (or the Class object for static)
public synchronized void deposit(int amount) {
    balance += amount;
}

// Block — explicit lock object, narrower scope
public void deposit(int amount) {
    synchronized (lock) {
        balance += amount;
    }
}

Prefer the block form because there are three advantages. First, you can choose a more appropriate lock object — typically a private Object lock = new Object() rather than this. Second, you can narrow the synchronized region, keeping non-shared work outside the lock. Third, you avoid accidentally exposing the lock, since clients of this can also call synchronized(account){} and interfere.

Under the hood

The two forms compile differently. A synchronized block emits explicit MONITORENTER at the top and MONITOREXIT at the bottom, plus a compiler-generated exception handler that runs a second MONITOREXIT on any abnormal exit so the monitor is never leaked. A synchronized method emits no monitor opcodes at all — instead the ACC_SYNCHRONIZED flag is set in the method's access_flags, and the JVM/ART acquires the receiver's monitor (or the Class object's monitor for static) implicitly on method entry and releases it on return or throw. Functionally identical lock, but the method form is invisible in the bytecode body and always spans the whole method.

Mutual Exclusion

🎤 Say it out loud (~30–45s): "Mutual exclusion — mutex — is the property that at most one thread is inside a critical section at a time. In Java you get it by holding an object's intrinsic lock: all synchronized blocks keyed on the same object are mutually exclusive with each other. The thing to be precise about is that exclusion is per-lock-object, not per-block — two synchronized blocks on different objects don't exclude each other at all, which is a common source of 'I added synchronized and it still races' bugs."

Mutual exclusion — mutex — guarantees that at most one thread executes a critical section at a time. In Java, holding the intrinsic lock of an object provides mutual exclusion over all synchronized blocks on that same object.

Under the hood

At the metal, mutual exclusion bottoms out in an atomic read-modify-write the CPU guarantees indivisible — a compare-and-swap (cmpxchg/LDREX/STREX) on the lock word. Only one core can win the CAS that flips the word from unlocked to owned; losers either spin briefly or, once the monitor inflates, block on a Linux futex (FUTEX_WAIT) so they consume no CPU while parked, and the releaser issues FUTEX_WAKE. Because exclusion is enforced on a specific lock word, two threads guarding the same invariant with different lock objects both win their respective CAS operations and proceed concurrently — the exclusion simply doesn't apply across distinct monitors.

Reentrant Locks

🎤 Say it out loud (~30–45s): "Reentrant means a thread that already holds a lock can acquire it again without deadlocking, because the lock tracks an owner and a hold count instead of a simple boolean. Java's intrinsic lock is reentrant, which is what lets one synchronized method call another on the same object. ReentrantLock is the explicit version with extras I actually reach for: tryLock with a timeout, lockInterruptibly, multiple Conditions per lock, and an optional fairness mode — at the cost of remembering to unlock in a finally."

Java's intrinsic lock is reentrant: a thread that already holds a lock can acquire it again without deadlocking, because the JVM tracks a reentry count. This matters when a synchronized method calls another synchronized method on the same object.

java.util.concurrent.locks.ReentrantLock provides explicit, reentrant locking with extra features. There are four worth knowing: tryLock(timeout) to avoid blocking forever; lockInterruptibly() to respond to thread interruption while waiting; Condition objects for multiple wait sets per lock instead of the single wait set a monitor gives you; and a fairness option that queues waiting threads in FIFO order.

val lock = ReentrantLock()
val notFull = lock.newCondition()
val notEmpty = lock.newCondition()

fun produce(item: Int) {
    lock.lock()
    try {
        while (buffer.size == MAX) notFull.await()
        buffer.add(item)
        notEmpty.signal()
    } finally {
        lock.unlock()  // always in finally
    }
}

Under the hood

ReentrantLock does not use any object monitor — it's built on AbstractQueuedSynchronizer (AQS), which holds a single volatile int state and a FIFO CLH-style wait queue of parked threads. Acquire is a CAS that bumps state from 0 to 1 and stamps the exclusiveOwnerThread; reentry just increments state (so the hold count can exceed 1), and unlock decrements it, only releasing when it returns to 0. Contended threads are parked/unparked with LockSupport.park/unpark, which on ART maps to futex waits — no busy spinning. Fairness is a tiny policy difference in tryAcquire: a fair lock checks hasQueuedPredecessors() and refuses to barge ahead of the queue, whereas the default unfair lock attempts an immediate CAS first. Each Condition is its own separate wait queue inside the same AQS, which is how one lock exposes multiple wait sets.

Deadlock

🎤 Say it out loud (~30–45s): "Deadlock is when two or more threads are permanently blocked, each waiting on a lock the other holds. It requires all four Coffman conditions simultaneously — mutual exclusion, hold-and-wait, no preemption, and a circular wait — so breaking any one prevents it. In practice the cheapest break is global lock ordering: always acquire locks in the same order so a cycle can't form. tryLock with a timeout breaks no-preemption, and not holding a lock while calling foreign code avoids the surprise cycles."

A deadlock occurs when two or more threads are permanently blocked, each waiting for a lock held by another.

There are four necessary conditions — called the Coffman conditions — and all four must hold simultaneously. First, mutual exclusion: resources are held exclusively. Second, hold-and-wait: a thread holds a lock while waiting for another. Third, no preemption: locks cannot be forcibly taken away. Fourth, circular wait: A waits for B and B waits for A, or a longer cycle.

Classic example:

// Thread 1
synchronized (lockA) { synchronized (lockB) { /* work */ } }

// Thread 2
synchronized (lockB) { synchronized (lockA) { /* work */ } }

Prevention strategies:

  • Lock ordering: always acquire locks in the same global order.
  • Lock timeout: use tryLock(timeout) and back off if acquisition fails.
  • Lock leveling: assign numerical levels to locks; always acquire in ascending order.
  • Single lock: if possible, use one coarse-grained lock.
  • Avoid holding locks while calling foreign code (callbacks, listeners).

Under the hood

At runtime a deadlock is a cycle in the resource-allocation graph: each blocked thread sits in a futex wait owned by another, and the kernel will never wake them because the wake condition (the other's release) can never occur — no thread is runnable, so the scheduler simply never schedules them. Intrinsic monitors offer no escape because synchronized provides no timeout or interruption; that "no preemption" property is baked into the opcode. This is exactly why ReentrantLock.tryLock(timeout) and lockInterruptibly() exist — they let a thread give up a futex wait and back off, attacking the no-preemption condition. The JVM's thread dump (jstack / Thread.getAllStackTraces) can detect these cycles by inspecting each thread's held-vs-waited monitors and explicitly reports "Found one Java-level deadlock."

Livelock

🎤 Say it out loud (~30–45s): "Livelock is the cousin of deadlock where threads aren't blocked — they're actively running and changing state — but they keep responding to each other in a way that makes no forward progress. The corridor analogy is two people repeatedly stepping the same direction to let each other pass. It's nastier than deadlock because CPU looks busy and a thread dump shows everyone RUNNABLE; the fix is to break the symmetry, usually with randomized backoff so the threads stop mirroring each other."

A livelock is when threads are not blocked but are continuously changing state in response to each other without making any progress. The analogy is two people in a corridor stepping aside simultaneously — each mirrors the other's move and neither passes.

Under the hood

Livelock typically arises in optimistic / retry-based schemes rather than blocking locks — e.g. a CAS loop where two threads' compare-and-swaps keep failing because each invalidates the other's snapshot, or a tryLock-then-release-and-retry deadlock-avoidance loop where both threads back off in lockstep. Unlike a futex-blocked deadlocked thread (kernel S state, 0% CPU), livelocked threads stay RUNNABLE and burn CPU, so it shows up as high utilization with no throughput. The standard cure is to inject asymmetry — randomized/exponential backoff (the same idea as Ethernet's collision backoff) so the threads desynchronize and one wins.

Starvation

🎤 Say it out loud (~30–45s): "Starvation is when a thread perpetually loses the race for a resource because others are always preferred — by an unfair lock, by higher-priority threads monopolizing the CPU, or by repeated notify that keeps waking the wrong waiter. It's a liveness failure but not a total stall; the system makes progress, just not for that thread. The mitigations are a fair lock to enforce FIFO ordering and preferring notifyAll over notify so no waiter is permanently skipped."

Starvation is when a thread cannot gain access to a resource because other threads are always preferred. Common causes are unfair schedulers, high-priority threads monopolizing a lock, or a caller that always uses notify() instead of notifyAll().

The fix is to use a fair lock (ReentrantLock(fair=true)) and always prefer notifyAll() over notify().

Under the hood

Starvation is a side effect of how the underlying primitives choose a winner. A default unfair ReentrantLock (and the intrinsic monitor) lets a just-arriving thread barge ahead via an immediate CAS instead of joining the AQS queue tail — great for throughput, bad for the thread that keeps getting jumped. notify() wakes exactly one arbitrary thread from the monitor's wait set (the JVM picks; order is unspecified), so a particular waiter can be skipped forever, whereas notifyAll() moves the whole wait set to the entry set so every thread eventually re-checks its condition. Thread-priority starvation comes from CFS: a higher-priority (lower nice) thread accumulates virtual runtime more slowly and is repeatedly chosen, so on a saturated core the low-priority thread rarely runs.

Lock Contention and Granularity

🎤 Say it out loud (~30–45s): "Contention is when many threads frequently fight for the same lock, so they queue up and throughput collapses. Granularity is how much state one lock protects — coarse-grained is one lock for the whole object: simple but contended; fine-grained splits state across many locks, like lock striping in ConcurrentHashMap: low contention but more complex and more deadlock-prone. My rule is start coarse, measure where the contention actually is, then split — premature lock splitting just buys you subtle bugs."

Contention occurs when multiple threads frequently try to acquire the same lock simultaneously, causing queueing and reduced throughput.

Granularity is the scope of data protected by a single lock. A coarse-grained lock covers the whole object — simple but high contention. A fine-grained lock covers one data element (lock striping in ConcurrentHashMap is a good example) — low contention, but more complex and more prone to deadlock.

The rule of thumb is: start coarse, measure, then refine. Premature lock splitting introduces bugs.

Under the hood

Contention has a concrete cost progression: an uncontended thin-lock CAS is nearly free, but once two threads collide the lock inflates to a fat OS monitor and losers block on a futex, paying syscall + context-switch + cache-coldness costs on every hand-off. Cache-coherence traffic matters too — the lock word and the guarded data bounce between cores' caches (MESI invalidations), so even brief critical sections serialize the memory bus. Lock striping (e.g. legacy ConcurrentHashMap's segment array, or per-bin locking in the modern CAS-based implementation) spreads accesses across N independent lock words so threads hitting different keys win different CAS operations and never serialize — the trade-off being more lock words to reason about and a real risk of cross-stripe deadlock if you ever need two at once.

3.3 Volatile and Atomic Classes

volatile — Visibility, Not Compound Atomicity

🎤 Say it out loud (~30–45s): "volatile is about visibility and ordering, not atomicity. It guarantees that a write is flushed to main memory and that subsequent reads see the latest value, plus it sets up a happens-before edge — so it's perfect for a single cancellation flag or a one-writer reference swap. But it does nothing for compound operations: count++ is a read-modify-write, so two threads can both read the same value and clobber each other. The interview trap is claiming volatile makes ++ thread-safe — it doesn't; you need an atomic or a lock for that."

The volatile keyword in Java/Kotlin does three things: it ensures every read comes from main memory rather than a register or cache; it ensures every write goes directly to main memory; and it establishes a happens-before relationship so that a write to a volatile field happens-before every subsequent read of that field. What it does NOT provide is atomicity for compound operations.

volatile is sufficient in two situations: a boolean flag written by one thread and read by others (such as @Volatile var cancelled = false), and a single-writer, multi-reader reference swap where you are swapping an immutable config object.

volatile is not enough when the operation is compound. count++ is actually three steps — read, increment, write — so two threads can both read the same value and both write oldValue + 1, losing one increment. The same problem applies to check-then-act patterns like if (!initialized) initialize(), where two threads can both see false and both call initialize(). Any read-modify-write sequence has this hazard.

Under the hood

The compiler marks the field with the ACC_VOLATILE flag in the class file, which tells the JIT/runtime to surround accesses with memory barriers instead of caching the value in a register. On the typical JMM-to-hardware lowering, a volatile write is followed by a StoreLoad-style fence and a volatile read is preceded by a load-acquire fence:

volatile write x:
    StoreStore barrier
    store x
    StoreLoad barrier      // most expensive; prevents reordering with later loads

volatile read x:
    load x
    LoadLoad / LoadStore barrier   // acquire semantics

These fences disable both compiler reordering and CPU store-buffer/cache reordering, which is exactly what creates the happens-before edge. There is no lock and no read-modify-write atomicity — the hardware just refuses to reorder or stale-cache the single load/store.

AtomicInteger, AtomicBoolean, AtomicReference

🎤 Say it out loud (~30–45s): "The java.util.concurrent.atomic classes give me lock-free, thread-safe updates to a single variable using compare-and-swap under the hood. So incrementAndGet() is a genuinely atomic ++, and compareAndSet() lets me do conditional updates without a mutex. The thing I'd flag is that each atomic protects exactly one variable — if I need several fields to stay mutually consistent, I still need a lock. And under really heavy contention I'd reach for LongAdder, which spreads writes across multiple cells instead of hammering one hot CAS location."

java.util.concurrent.atomic classes use CAS — Compare-And-Swap — CPU instructions to achieve lock-free, thread-safe operations on single variables.

val counter = AtomicInteger(0)
counter.incrementAndGet()           // atomic i++, returns new value
counter.getAndAdd(5)                // atomic i += 5, returns old value
counter.compareAndSet(10, 20)       // if current == 10, set to 20; returns bool

val flag = AtomicBoolean(false)
flag.compareAndSet(false, true)     // safe initialization gate

val ref = AtomicReference<Config>(initialConfig)
ref.set(newConfig)                  // atomic reference swap

AtomicLong, AtomicIntegerArray, and AtomicReferenceArray cover arrays.

LongAdder and LongAccumulator give better throughput under high contention because they maintain multiple cells that are summed on read, so there is no single hot CAS location.

Under the hood

The atomic's value is stored in a volatile field, and the mutation methods route through Unsafe/VarHandle intrinsics that the JIT lowers to a single atomic CPU instruction. incrementAndGet() is implemented as a CAS retry loop, while raw compareAndSet() maps directly to one instruction:

AtomicInteger.value : volatile int        // visibility
compareAndSet(e,u)  -> Unsafe.compareAndSetInt
                    -> LOCK CMPXCHG (x86) or LDREX/STREX retry (ARM)
incrementAndGet()   -> do { v=getVolatile(); } while(!CAS(v, v+1)); return v+1

LongAdder instead keeps a base value plus a striped Cell[] array padded to avoid false sharing; threads hash to different cells so concurrent writers rarely touch the same cache line, and sum() adds the base and all cells (a non-atomic snapshot, which is fine for statistics).

Compare-And-Swap (CAS)

🎤 Say it out loud (~30–45s): "CAS is an optimistic, lock-free primitive: I read the current value, compute a new one, and atomically swap only if the location still holds what I expected — otherwise I retry. It maps to a single hardware instruction like CMPXCHG, so under low contention it beats a mutex because there's no blocking or context switch. Under heavy contention the retry loop can burn CPU spinning. And the classic gotcha is the ABA problem — the value goes A→B→A and CAS can't tell it changed — which you fix with a versioned reference like AtomicStampedReference."

CAS is a single CPU instruction (CMPXCHG on x86): if the memory location currently holds expected, replace it with update and return whether the swap succeeded.

CAS(addr, expected, update):
  if *addr == expected:
    *addr = update
    return true
  return false

AtomicInteger's incrementAndGet in pseudo-code:

loop:
  old = read(counter)
  new = old + 1
  if CAS(counter, old, new): return new
  // else: another thread modified counter, retry

This is an optimistic spin loop. Under low contention it is faster than a mutex. Under very high contention the spin loops waste CPU — prefer LongAdder.

The ABA problem is worth knowing: CAS only checks value equality, so if a value changes from A to B and back to A, CAS cannot detect the round trip. The solution is AtomicStampedReference or AtomicMarkableReference, both of which include a version stamp alongside the value.

Under the hood

The atomicity comes from the CPU, not software. On x86 the CMPXCHG instruction is made atomic with the LOCK prefix, which asserts cache-line ownership (cache-line locking via the MESI coherence protocol, or in the worst case a bus lock). On ARM/RISC there is no single compare-and-swap; the runtime emits a load-linked/store-conditional pair:

x86:   LOCK CMPXCHG   — one instruction, atomic compare-then-write

ARM:   retry:
         LDREX r, [addr]      ; load-exclusive, sets a monitor on the line
         CMP   r, expected
         BNE   fail
         STREX status, update, [addr]  ; succeeds only if line untouched
         CBNZ  status, retry           ; another writer raced → retry

Because the check is purely on the bit pattern, CAS is blind to A→B→A transitions — AtomicStampedReference works around this by CAS-ing a (reference, stamp) pair so the stamp increments even when the reference returns to its old value.

Decision Matrix

🎤 Say it out loud (~30–45s): "My rule of thumb scales with the operation. A single flag with one writer is just @Volatile. A counter hit by many threads is an AtomicInteger, and a high-contention stats counter is LongAdder. A conditional reference swap is an AtomicReference with compareAndSet. The key dividing line: the moment I need two or more fields to stay mutually consistent, no single atomic covers that — I escalate to synchronized or a ReentrantLock, because atomics only protect one variable at a time."
Scenario Use
Read/write single flag (1 writer)@Volatile var
Increment counter from many threadsAtomicInteger
High-contention counter (stats)LongAdder
CAS-based conditional reference swapAtomicReference
Multiple related fields must be consistentsynchronized or ReentrantLock

Under the hood

The matrix is really ordered by escalating synchronization cost. volatile is the cheapest — just memory fences, no atomicity. Single-variable atomics add a CAS instruction (one hot cache line). LongAdder trades a slightly more expensive read for striped, contention-free writes. Locks are the heaviest because they can park the thread on a monitor (a kernel futex transition under contention), but they are the only option that can make a multi-field update appear atomic — atomics and volatile each guard exactly one memory location.

3.4 Wait/Notify and Producer-Consumer

The Monitor Wait Set

🎤 Say it out loud (~30–45s): "wait() is how a thread voluntarily gives up the monitor and sleeps until another thread signals a condition. The critical detail is that you must already hold the object's intrinsic lock to call wait(), and wait() atomically releases that lock as it parks the thread — that's what lets the other thread make progress and eventually notify(). Contrast that with sleep(), which holds onto every lock it owns, so a sleeping thread inside a synchronized block blocks everyone else."

Every Java object has a wait set. Calling wait() on an object requires holding that object's intrinsic lock. When called, there are four steps: the current thread releases the lock; the thread is placed in the object's wait set and suspended; when another thread calls notify() or notifyAll(), the thread moves from the wait set back to the blocked state, competing for the lock again; and when the lock is re-acquired, wait() returns.

The important contrast is with sleep(), which does NOT release any lock. A sleeping thread holds all its locks.

Under the hood

Each object header points (lazily, when contended) to a monitor structure with two distinct queues: an entry set (threads blocked trying to acquire the lock) and a wait set (threads that called wait()). wait() releases the monitor, moves the caller into the wait set, and parks it; notify() migrates one arbitrary waiter from the wait set into the entry set, and notifyAll() migrates all of them. Crucially, a notified thread does not run immediately — it must re-contend for the monitor in the entry set and only returns from wait() once it re-acquires the lock.

monitor:
  owner       -> current lock holder (one thread)
  entry set   -> [blocked threads competing for the lock]
  wait set    -> [parked threads that called wait()]

wait():   release lock, add self to wait set, park
notify(): move ONE waiter: wait set -> entry set
notifyAll(): move ALL waiters: wait set -> entry set

Spurious Wakeups

🎤 Say it out loud (~30–45s): "The JVM spec explicitly permits wait() to return without any matching notify() — that's a spurious wakeup. So I never guard a wait() with an if; I always loop: while (!condition) wait(). The loop matters for two reasons — spurious wakeups, and the fact that by the time a notified thread re-acquires the lock another thread may have already consumed the condition. Re-checking on every wakeup is the only correct pattern."

The JVM specification allows wait() to return even if no notify() was called — that is a spurious wakeup. Always check the condition in a loop:

// WRONG
synchronized (lock) {
    if (!conditionMet()) lock.wait();
    // proceed — might be spurious
}

// CORRECT
synchronized (lock) {
    while (!conditionMet()) lock.wait();
    // condition is definitely true now
}

Under the hood

Spurious wakeups are not a JVM bug — they leak through from the OS layer. JVM monitors are typically implemented on top of POSIX condition variables (pthread_cond_wait) or futexes, and those primitives are documented to wake occasionally without a signal (e.g. a thread can be woken by a signal-handler interruption and the kernel chooses to return rather than re-sleep). Rather than paying to suppress these, the spec pushes the cost onto the caller via the mandatory re-check loop. The loop also handles the legitimate race where a different woken thread consumed the condition first, so even a "real" notify can require waiting again.

Guarded Block

🎤 Say it out loud (~30–45s): "A guarded block is the canonical wait-loop idiom: acquire the monitor, while the condition isn't satisfied, wait(); once it is, do the protected work and then notifyAll() so anyone blocked on the opposite condition can proceed. It's the building block for producer-consumer — the guard prevents you from removing from an empty queue or adding to a full one, and the loop absorbs spurious wakeups and lost races."

A guarded block is a wait-in-a-loop pattern that protects a critical operation behind a condition check:

synchronized (queue) {
    while (queue.isEmpty()) queue.wait();
    Item item = queue.remove();
    queue.notifyAll();
}

Under the hood

The whole block executes while owning the queue's monitor, so the while-check and the remove() are one indivisible critical section — no other thread can slip in between the check and the act. When the guard isn't met, wait() atomically drops the lock and parks the thread in the wait set, so a producer can enter the same monitor and add an item. The trailing notifyAll() wakes threads waiting on any condition tied to this object (both "not empty" and "not full" waiters share one wait set), which is precisely why a single condition variable forces notifyAll rather than notify.

Producer-Consumer with wait/notify

🎤 Say it out loud (~30–45s): "A bounded buffer is the textbook producer-consumer: producers wait while it's full, consumers wait while it's empty, and each side notifyAlls after it changes the buffer. I deliberately use notifyAll over notify here because producers and consumers share one monitor and one wait set — a plain notify could wake the wrong kind of thread and stall the system. In real code I'd skip all of this and use a BlockingQueue, which gets the locking and conditions right for me."
class BoundedBuffer<T>(private val capacity: Int) {
    private val buffer = ArrayDeque<T>()

    @Synchronized
    fun put(item: T) {
        while (buffer.size == capacity) (this as Object).wait()
        buffer.addLast(item)
        (this as Object).notifyAll()
    }

    @Synchronized
    fun take(): T {
        while (buffer.isEmpty()) (this as Object).wait()
        val item = buffer.removeFirst()
        (this as Object).notifyAll()
        return item
    }
}

Use notifyAll() rather than notify() unless you know only one thread can act on the notification. The rule of thumb is: always use notifyAll to be safe, even if it is slightly less efficient.

Under the hood

There is exactly one monitor (the buffer instance) and therefore one wait set holding both blocked producers and blocked consumers. Because notify() wakes a single arbitrary waiter, it can wake a producer when only consumers can make progress (the "lost wakeup" / signal-hijacking hazard), leaving the system stuck. notifyAll() avoids this by waking everyone so each re-evaluates its own while guard, at the cost of a thundering-herd re-contention on the lock. This is exactly the limitation that ReentrantLock with two Condition objects (notFull, notEmpty) solves — you can then signal only the relevant queue, which is how ArrayBlockingQueue is actually built.

BlockingQueue — Prefer This Over Manual Wait/Notify

🎤 Say it out loud (~30–45s): "In practice I never hand-roll wait/notify — I use a BlockingQueue, which encapsulates the producer-consumer pattern correctly. put() blocks when full, take() blocks when empty, and the spurious-wakeup and condition handling is done for me. The decisions I actually make are which implementation and what bound: ArrayBlockingQueue for a fixed array with one lock, LinkedBlockingQueue for two-lock throughput, SynchronousQueue for direct handoff. The big trap is leaving it unbounded — that just relocates an overload into an OutOfMemoryError."

java.util.concurrent.BlockingQueue encapsulates the producer-consumer pattern correctly, and you should prefer it over rolling your own wait/notify logic:

val queue = LinkedBlockingQueue<Work>(100)  // bounded

// Producer
queue.put(work)     // blocks if full, uninterruptible
queue.offer(work, 500, TimeUnit.MILLISECONDS)  // timeout variant

// Consumer
val work = queue.take()          // blocks if empty
val work2 = queue.poll(500, TimeUnit.MILLISECONDS)

The main implementations are: ArrayBlockingQueue — fixed-size, backed by array, single lock; LinkedBlockingQueue — optionally bounded, with separate head and tail locks for higher throughput; SynchronousQueue — zero capacity, where each put must pair with a take (a handoff); PriorityBlockingQueue — unbounded, ordered by priority; and DelayQueue — elements only become available after a configured delay, useful for scheduled tasks.

BlockingQueue is preferred because it handles spurious wakeups, lock ordering, and condition management internally, so you cannot get those details wrong.

Under the hood

These implementations are built on ReentrantLock + Condition, not raw wait/notify. ArrayBlockingQueue uses one lock with two conditions (notEmpty, notFull), so put signals exactly the consumers and take signals exactly the producers. LinkedBlockingQueue gets higher throughput by using two separate locks — a putLock at the tail and a takeLock at the head — letting one producer and one consumer operate concurrently, coordinated by an AtomicInteger count. SynchronousQueue holds no elements at all; it parks the offerer and the taker and rendezvouses them via a Treiber-stack/queue of waiting threads, so a put literally hands the item to a take.

ArrayBlockingQueue:   1 lock, conditions { notEmpty, notFull }
LinkedBlockingQueue:  putLock (tail) + takeLock (head), AtomicInteger count
SynchronousQueue:     no storage; direct producer<->consumer handoff

3.5 Executors and Task Execution

Why Not new Thread() Per Task?

🎤 Say it out loud (~30–45s): "Spawning a raw thread per task doesn't scale. Each thread costs a real OS kernel thread plus a stack (often ~512KB–1MB), there's no upper bound so a burst can exhaust memory, and you get no lifecycle, exception handling, or monitoring. You also pay creation and teardown cost for work that's often shorter than the thread setup itself. An executor amortizes all of that by reusing a bounded pool of worker threads fed from a queue."

There are four problems. First, thread creation overhead — stack allocation and an OS kernel thread. Second, there is no upper bound on concurrency, which means memory exhaustion under load. Third, there is no lifecycle management, no exception handling, and no monitoring. Fourth, there is thread teardown cost when the work is done.

Under the hood

A JVM thread is a thin wrapper over an OS-scheduled native thread (created via pthread_create/clone on Linux), and each reserves a contiguous stack region governed by -Xss. Creating one is a syscall plus page-table and scheduler bookkeeping; destroying one reclaims that. Beyond a few hundred threads the OS scheduler spends increasing time context-switching (saving/restoring registers and blowing CPU caches/TLBs), so throughput actually drops with more threads. A pool fixes this by paying the creation cost once and parking idle workers on the queue's take() rather than tearing them down.

Executor and ExecutorService

🎤 Say it out loud (~30–45s): "Executor is the minimal interface — just execute(Runnable) — decoupling what runs from how/where it runs. ExecutorService extends it with results and lifecycle: submit returns a Future, and you get shutdown() for a graceful drain versus shutdownNow() which interrupts running tasks and returns the un-started queue. The detail I'd call out is that submitting after shutdown() triggers the rejection policy, and you should always awaitTermination to confirm the pool actually drained."
interface Executor {
    void execute(Runnable command);
}

interface ExecutorService extends Executor {
    Future<?> submit(Runnable task);
    <T> Future<T> submit(Callable<T> task);
    void shutdown();        // no new tasks; finish current
    List<Runnable> shutdownNow();  // interrupt in-progress, return queued
    boolean awaitTermination(long timeout, TimeUnit unit);
}

Under the hood

submit() doesn't hand your Runnable/Callable straight to a thread — it wraps it in a FutureTask (which holds the result/exception and a state machine) and enqueues that, returning the FutureTask as the Future. A worker later dequeues and runs it, storing the return value or any thrown exception inside the task; that's why future.get() can re-throw the task's exception wrapped in ExecutionException. shutdown() flips an internal state flag so the queue stops accepting work and drains naturally, whereas shutdownNow() additionally calls Thread.interrupt() on every worker and returns the still-queued tasks that never started.

Thread Pool Types

🎤 Say it out loud (~30–45s): "The Executors factories are presets over ThreadPoolExecutor. Fixed gives me N permanent threads, cached grows unboundedly and reaps idle threads after 60s, single serializes everything on one thread, and scheduled handles delays and periodic work. The catch I always mention: newFixedThreadPool and newSingleThreadExecutor use an unbounded LinkedBlockingQueue, and newCachedThreadPool has an unbounded thread count — both can OOM under load, which is why for production I configure ThreadPoolExecutor directly with a bounded queue and a rejection policy."
// Fixed: exactly N threads, LinkedBlockingQueue (unbounded by default)
val fixed = Executors.newFixedThreadPool(4)

// Cached: grows as needed, idle threads expire in 60s; good for many short tasks
val cached = Executors.newCachedThreadPool()

// Single: exactly 1 thread, tasks serialized
val single = Executors.newSingleThreadExecutor()

// Scheduled: delays and periodic tasks
val scheduled = Executors.newScheduledThreadPool(2)
scheduled.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS)

Use ThreadPoolExecutor directly when you need full control:

ThreadPoolExecutor(
    corePoolSize = 4,          // always-alive threads
    maximumPoolSize = 8,       // max threads when queue is full
    keepAliveTime = 60L,       // idle thread timeout
    unit = TimeUnit.SECONDS,
    workQueue = LinkedBlockingQueue(100),   // bounded queue
    threadFactory = { r -> Thread(r, "worker-${counter.incrementAndGet()}") },
    handler = ThreadPoolExecutor.CallerRunsPolicy()  // backpressure policy
)

Under the hood

Every factory is just a ThreadPoolExecutor (or ScheduledThreadPoolExecutor) with preset arguments, and the submit path follows one fixed algorithm:

on submit:
  1. if poolSize < corePoolSize       -> start a new core thread
  2. else if workQueue.offer(task)    -> enqueue it
  3. else if poolSize < maximumPoolSize -> start a new (non-core) thread
  4. else                              -> reject via RejectedExecutionHandler

This explains the presets' behavior: newFixedThreadPool(N) sets core == max == N with an unbounded LinkedBlockingQueue, so step 2 always succeeds and step 3 never fires — the queue grows forever. newCachedThreadPool sets core = 0, max = Integer.MAX_VALUE with a SynchronousQueue (zero capacity), so step 2 fails immediately and step 3 spawns a thread per task — unbounded threads. ScheduledThreadPoolExecutor swaps in a DelayedWorkQueue (a heap ordered by next-run time) so workers block until the earliest task is due.

Callable and Future

🎤 Say it out loud (~30–45s): "Callable is like Runnable but it returns a value and can throw a checked exception; submitting one gives me a Future handle. future.get() blocks until the result is ready — I always use the timed overload so I can't hang forever — and it re-throws the task's failure wrapped in an ExecutionException, which I unwrap via .cause. I can also poll with isDone() or cancel(true) to interrupt. The nuance: the work runs whether or not anyone ever calls get(); get() only retrieves the already-computed outcome."
val executor = Executors.newFixedThreadPool(4)
val future: Future<Int> = executor.submit(Callable {
    heavyComputation()
})

// Later...
try {
    val result = future.get(5, TimeUnit.SECONDS)   // blocks until done or timeout
} catch (e: TimeoutException) {
    future.cancel(true)  // interrupt the task
} catch (e: ExecutionException) {
    throw e.cause!!      // unwrap the original exception
}

isDone(), isCancelled(), and cancel(mayInterruptIfRunning) are the non-blocking query methods.

Under the hood

The returned Future is concretely a FutureTask with an internal volatile int state machine (NEW → COMPLETING → NORMAL/EXCEPTIONAL, or CANCELLED/INTERRUPTED). When the worker runs it, the result or thrown exception is stored in an outcome field and the state is CAS-advanced. get() reads state; if the task isn't finished it adds the calling thread to a Treiber-stack of waiters and parks it via LockSupport.park(). On completion the running worker walks that waiter stack and unpark()s everyone. If outcome holds a Throwable, get() wraps it in ExecutionException — the original is the .cause.

Cancellation

🎤 Say it out loud (~30–45s): "Cancellation in Java is cooperative, not preemptive. future.cancel(true) just sets the interrupt flag on the running thread — the task has to actually notice it, either by checking Thread.currentThread().isInterrupted() in its loop or by calling a blocking method like sleep, wait, or queue.take that throws InterruptedException. A tight CPU loop that never checks the flag won't stop. And a common bug is swallowing InterruptedException without restoring the interrupt status, which hides the cancellation from the rest of the stack."

future.cancel(true) sets the interrupt flag on the executing thread. The task must cooperate by checking Thread.interrupted() or by calling methods that throw InterruptedException — such as sleep, wait, or queue.take.

while (!Thread.currentThread().isInterrupted()) {
    // process chunk
}

Under the hood

Each Thread carries a single boolean interrupt status flag. cancel(true) calls Thread.interrupt(), which sets that flag; if the thread is currently parked inside a blocking call registered with an interrupt (sleep, wait, park, BlockingQueue.take, lockInterruptibly), the runtime clears the flag and throws InterruptedException to unwind it. There is no asynchronous stop — the JVM removed Thread.stop() precisely because forcibly killing a thread leaves locks and shared state corrupted. That is why catching InterruptedException should normally re-set the flag with Thread.currentThread().interrupt() so callers higher up can still see it.

Backpressure and Queue Sizing

🎤 Say it out loud (~30–45s): "Backpressure is what happens when producers outrun consumers. With an unbounded queue the backlog just grows until you OOM, so I use a bounded queue and pick a rejection policy: CallerRunsPolicy is my favorite because it makes the submitting thread run the task, which naturally throttles the producer. For sizing, CPU-bound work wants about cores + 1 threads since more just adds context-switch overhead, while IO-bound work scales with how long threads sit waiting — roughly cores * (1 + wait/compute). When unsure, I profile rather than guess."

When producers submit tasks faster than consumers execute them, the queue grows. With an unbounded queue (LinkedBlockingQueue() no-arg), this eventually causes OutOfMemoryError. With a bounded queue, the chosen rejection policy kicks in:

Policy Behavior
AbortPolicy (default)Throws RejectedExecutionException
CallerRunsPolicyCaller thread runs the task (natural backpressure)
DiscardPolicySilently drops the task
DiscardOldestPolicyDrops the oldest queued task, retries submit

Sizing guidance:

  • CPU-bound tasks: N_cores + 1 threads (the extra 1 covers when a thread page-faults or is preempted).
  • IO-bound tasks: N_cores * (1 + wait_time / service_time). If threads spend 90% waiting, use roughly 10x cores.
  • Mixed: profile first; start with N_cores * 2 and tune from there.

Under the hood

The rejection handler is invoked synchronously on the submitting thread the moment the submit algorithm reaches step 4 (queue full and maximumPoolSize reached), or whenever a task is submitted after shutdown(). CallerRunsPolicy provides true backpressure because it executes task.run() inline on the caller, so while the caller is busy running that task it physically cannot submit more — the producer's rate self-limits to the consumer's rate. The sizing formulas come from Little's Law: a CPU-bound task keeps a core busy ~100% of the time, so extra threads beyond cores + 1 only add context-switch overhead, whereas an IO-bound task releases the core while blocked, so you need cores * (1 + wait/compute) threads to keep all cores doing useful work during those waits.

Thread Starvation

🎤 Say it out loud (~30–45s): "Starvation is when tasks can't get a thread to run on. The nasty version is thread-pool deadlock: if a task running in the pool calls future.get() on another task submitted to the same pool, it occupies a worker while waiting for a task that has no free worker to run on. In a fixed pool, enough of these and every thread is blocked waiting for work that can never be scheduled. The fix is to never have pool tasks block on other tasks in the same pool — use a separate pool, or restructure so dependent work composes asynchronously."

Starvation in an executor happens when a long-running task occupies a thread and shorter tasks wait indefinitely. In a single-thread executor, one hung task blocks everything. In a fixed pool, a thread that calls future.get() on another task submitted to the same pool can deadlock the entire pool — all threads end up waiting for tasks that have no available thread to execute them. This is thread-pool deadlock.

Under the hood

The deadlock arises because a blocked worker still owns its thread — parking inside future.get() does not return the thread to the pool. With a fixed pool of N, if N tasks all block waiting on subtasks, there are zero free workers, those subtasks sit in the queue forever, and the dependency cycle can never resolve. This is structurally identical to a classic resource deadlock where threads are the finite resource. Frameworks like ForkJoinPool mitigate it with work-stealing and a managed-blocker mechanism that can spin up a compensation thread when a worker blocks, which is also why coroutine and reactive models prefer composing dependent work asynchronously (thenCompose/flatMap) instead of blocking a pooled thread on another task's result.

3.6 Android Application Threads

Main Thread (UI Thread)

🎤 Say it out loud (~30–45s): "Every Android process starts with a single main thread, and it's responsible for everything the user perceives — input dispatch, frame rendering via Choreographer, lifecycle callbacks, and broadcast delivery. The reason the UI toolkit is single-threaded is that making every view operation thread-safe would mean locking on every draw and measure, which would be slow and deadlock-prone; instead Android confines all UI work to one thread. So if I touch a view from a background thread, I get a CalledFromWrongThreadException, and the fix is to marshal the result back to the main thread."

Android apps start with one main thread per process. The main thread does five things: it runs the Looper's message loop; dispatches InputEvents; drives Choreographer for frame rendering (calling View.draw, View.measure, View.layout, and onDraw); delivers lifecycle callbacks like onCreate and onResume; and processes BroadcastReceiver.onReceive.

The key constraint is that the UI toolkit is not thread-safe — only the thread that created a view hierarchy can update it. Calling view.setText(...) from a background thread causes CalledFromWrongThreadException.

Under the hood

The main thread isn't special at the OS level — it's an ordinary Linux thread. What makes it the "UI thread" is that ActivityThread.main() calls Looper.prepareMainLooper() and then Looper.loop(), turning it into a message-processing loop that never returns for the life of the process.

ActivityThread.main()
   ├─ Looper.prepareMainLooper()   // creates Looper, stores in ThreadLocal<Looper>
   └─ Looper.loop()                // infinite loop: MessageQueue.next() → dispatch

The thread-confinement check is enforced by ViewRootImpl.checkThread(), which compares Thread.currentThread() against the thread that created the ViewRootImpl and throws CalledFromWrongThreadException on mismatch. There's no lock on the view hierarchy precisely because correctness is guaranteed by confinement instead.

ANR (Application Not Responding)

🎤 Say it out loud (~30–45s): "An ANR is the system telling the user the app's main thread is stuck. The thresholds I keep in mind are roughly 5 seconds for an unprocessed input event, 10 seconds for a foreground broadcast's onReceive, and 20 seconds for a service's onStartCommand. Every one of these is really the same root cause — the main thread's MessageQueue isn't getting drained because something is blocking it: synchronous IO, a held lock, or a long loop. So the cure is always the same: get the blocking work off the main thread."

ANR triggers in three situations: the main thread does not process a user input event within 5 seconds; onReceive() does not complete within 10 seconds for a foreground broadcast or 60 seconds for background; or Service.onStartCommand() does not return within 20 seconds.

All of these happen because the main thread's MessageQueue is blocked. The common causes are synchronous network or disk IO on the main thread, large database queries, holding a lock that another thread is waiting for, a long while loop, or waiting for a Binder call to a dead process.

For debugging, adb shell kill -3 <pid> dumps thread stacks to logcat, and StrictMode.setThreadPolicy() catches disk and network violations on the main thread in debug builds.

Under the hood

ANR detection lives in the system process, not in your app. When the framework hands work to your app (e.g. dispatches an input event or starts a broadcast), ActivityManagerService arms a delayed "timeout" message on its own handler. If your app posts back the "I finished" acknowledgement before that timeout fires, the system cancels the timeout; if not, the timeout message runs and triggers the ANR dialog plus a trace dump.

System server arms timeout ──► your main thread must drain its
                                MessageQueue and ACK in time
   ack received  → removeMessages(timeout)   // no ANR
   timeout fires → dump /data/anr/, show "App isn't responding"

The key insight: the watchdog isn't measuring "is the app busy," it's measuring "did the main thread's loop service its queue fast enough." A main thread stuck inside one Message's dispatch can't pull the next message — including the framework's own input messages — so it appears unresponsive.

Binder Threads

🎤 Say it out loud (~30–45s): "Binder is Android's IPC mechanism, and incoming remote calls don't land on my main thread — they arrive on one of the threads in a per-process Binder thread pool, which is around 15 threads. That has real consequences: AIDL implementations and onBind can run concurrently on Binder threads, so they must be thread-safe; and a synchronous Binder call I make from the main thread blocks the main thread until the remote side returns, which is a classic hidden ANR source."

Binder is Android's high-performance IPC mechanism. Each process has a thread pool of roughly 15 Binder threads maintained by the Binder driver. Remote calls arrive on one of these threads, not the main thread. There are three implications: Service.onBind() may be called on a Binder thread; AIDL interface implementations run on Binder threads so they must be thread-safe; and synchronous Binder calls from the main thread block the main thread until the remote returns.

Under the hood

The Binder thread pool is managed by the kernel Binder driver together with IPCThreadState in native code. Threads block in an ioctl(BINDER_WRITE_READ) syscall waiting for incoming transactions; when a transaction arrives, the driver wakes an idle pool thread to execute the target's onTransact(). The pool grows lazily up to a cap (ProcessState::setThreadPoolMaxThreadCount, default ~15) as concurrent requests demand.

Caller process              Kernel binder driver        Your process
  transact() ───────────────► copy via mmap'd buffer ──► wake pool thread
                                                          → onTransact()
                                                          → AIDL stub.onCall()

Because any of these pool threads can run your stub concurrently, shared state touched in AIDL methods needs synchronization — the framework gives you no per-call serialization unless you add it (e.g. post onto a single HandlerThread).

Background Threads

🎤 Say it out loud (~30–45s): "Background threads are everything that isn't the main thread or a Binder thread — anything I spin up via Thread, an Executor, a HandlerThread, or a coroutine dispatcher. They can do any heavy lifting, but they can't touch the view hierarchy. So the pattern is: do the work off-main, then hop back to the main thread to publish results — via Handler.post, runOnUiThread, LiveData.postValue, or withContext(Dispatchers.Main)."

Background threads are all threads other than main and Binder — any thread the app creates via Thread, Executor, HandlerThread, coroutines, and so on. They can perform any work but cannot touch UI directly. Results must be posted back to the main thread via Handler, runOnUiThread, LiveData.postValue, or withContext(Dispatchers.Main).

Under the hood

"Hopping back to the main thread" is always implemented by enqueuing a Message (or a Runnable wrapped in one) onto the main thread's MessageQueue. Activity.runOnUiThread checks whether you're already on the main thread and runs the block inline if so, otherwise it calls mHandler.post(action). withContext(Dispatchers.Main) resumes the continuation through HandlerDispatcher, which likewise posts to the main Handler. LiveData.postValue posts a single coalescing runnable, so a burst of postValue calls before the main thread drains the queue collapses into one delivery of the latest value.

bg thread  ──► mainHandler.post { … }  ──► main MessageQueue ──► main thread runs it

So there's no magic cross-thread "callback" — every UI-thread handoff is just another message on the same queue the loop is already draining.

Linux Process and Scheduling

🎤 Say it out loud (~30–45s): "Under Android, every thread is a Linux task scheduled by the Completely Fair Scheduler, which allocates CPU by virtual runtime weighted by the thread's nice value. Android exposes this through Process.setThreadPriority, mapping its priority constants to Linux nice values — background is +10, default 0, urgent display is around -8. The practical rule is to set my background threads to THREAD_PRIORITY_BACKGROUND so they get a smaller CPU share and don't starve the UI thread during rendering."

Android runs on Linux, where each thread is a Linux task. The Linux CFS (Completely Fair Scheduler) assigns CPU time based on virtual runtime and nice value. Android maps thread priorities to Linux nice values:

Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND)  // nice +10
Process.setThreadPriority(Process.THREAD_PRIORITY_DEFAULT)     // nice 0
Process.setThreadPriority(Process.THREAD_PRIORITY_URGENT_DISPLAY) // nice -8

Background threads should use THREAD_PRIORITY_BACKGROUND or lower so they do not compete with the UI thread for CPU time.

Under the hood

Process.setThreadPriority calls down to setpriority(2) (and, for some constants, into cgroup scheduling) on the calling or target tid. A higher nice value means lower priority: CFS tracks each task's accumulated virtual runtime and always runs the task with the smallest vruntime, but vruntime accrues faster for high-nice (low-priority) tasks, so they're scheduled less often.

nice -8  ──► large CPU weight  ──► vruntime grows slowly ──► runs more
nice +10 ──► small CPU weight  ──► vruntime grows fast    ──► runs less

Android additionally places throttled work in the bg_non_interactive cgroup, which caps the total CPU share of all background-priority threads collectively — so a runaway background thread can't starve the foreground even if you forget to tune individual priorities.

Debugging Main-Thread Freezes

🎤 Say it out loud (~30–45s): "When the main thread freezes, I reach for a layered toolkit: StrictMode flags accidental disk or network IO on the main thread in debug builds; Systrace or Perfetto give me a frame timeline showing exactly where main-thread time goes; the Android Studio CPU profiler gives method traces; and if it's already ANR'd, /data/anr/anr_* holds the captured thread dumps. For a live hang I can also force a dump without killing the process with kill -3."

There are five tools. StrictMode catches disk and network violations in debug builds. Systrace and Perfetto show the frame timeline and exactly where main thread time is spent. The Android Studio Profiler CPU view gives you the thread timeline and method traces. ANR traces at /data/anr/anr_* contain thread dumps captured at the moment of the ANR. And adb shell kill -3 <pid> forces a thread dump without killing the process.

Under the hood

kill -3 sends SIGQUIT, which the ART runtime installs a handler for; the handler walks every thread's stack and writes a dump rather than terminating the process (the JVM's traditional SIGQUIT behavior). StrictMode works by instrumenting framework entry points — BlockGuard policy hooks in the IO and Binder paths check the current thread's StrictMode policy and log or crash on a violation. Systrace/Perfetto rely on Trace.beginSection/endSection (atrace) markers that the framework already emits around measure, layout, draw, and Binder transactions, which is why you can see exactly which phase stalled.

SIGQUIT ─► ART signal handler ─► dump all thread stacks ─► logcat / tombstone

3.7 Handler / Looper / MessageQueue

Architecture Overview

🎤 Say it out loud (~30–45s): "The whole system is three cooperating pieces: a Looper owns a MessageQueue and spins in loop() pulling messages off it; a Handler is the producer-and-consumer endpoint bound to one Looper that you post work to; and the MessageQueue is the ordered buffer in between. Any thread can call handler.post, but the work always runs on the Looper's thread — that's how this safely serializes cross-thread communication onto a single thread like the UI thread."
Thread A                Thread B (UI thread)
   │                         │
   │                     ┌───┴───┐
   │                     │Looper │◄── loop() blocks here
   │                     └───┬───┘
   │                         │
   │                     ┌───┴──────┐
   └──── handler.post() ─►│MessageQueue│
                          └───┬──────┘
                              │ (next Message dequeued)
                           Handler.handleMessage()
                               or Runnable.run()

Looper

🎤 Say it out loud (~30–45s): "A Looper turns an ordinary thread into a message loop: it owns a MessageQueue and spins in loop(), pulling messages off and dispatching each to its target Handler. There's exactly one Looper per thread, stored in a thread-local, and the main thread gets one created for free in ActivityThread.main(). A background thread has none by default — I'd have to call Looper.prepare() and Looper.loop() myself, though in practice I use HandlerThread so I don't get that boilerplate wrong."

A Looper provides a message loop for a thread. There is only one Looper per thread. The main thread has one set up by the framework (ActivityThread.main()). Background threads do not have one by default.

// Manually set up a Looper on a background thread (rarely needed — use HandlerThread)
class MyThread : Thread() {
    lateinit var handler: Handler
    override fun run() {
        Looper.prepare()
        handler = Handler(Looper.myLooper()!!) { msg ->
            // handle message
            true
        }
        Looper.loop()  // blocks until quit() is called
    }
}

Looper.loop() blocks, dispatching messages one at a time. When a Message is available at or after its when timestamp, the Looper pops it and dispatches it to the Handler that sent it.

Under the hood

Looper.prepare() constructs a Looper (which constructs its MessageQueue) and stores it in a static ThreadLocal<Looper> — that's the mechanism enforcing one Looper per thread, and why Looper.myLooper() returns the calling thread's instance. Looper.loop() is essentially an infinite loop calling MessageQueue.next() and then msg.target.dispatchMessage(msg):

public static void loop() {
    final Looper me = myLooper();          // from ThreadLocal
    final MessageQueue queue = me.mQueue;
    for (;;) {
        Message msg = queue.next();        // blocks (may park in nativePollOnce)
        if (msg == null) return;           // queue.quit() returned null → exit loop
        msg.target.dispatchMessage(msg);   // target is the sending Handler
        msg.recycleUnchecked();            // return Message to the object pool
    }
}

dispatchMessage checks msg.callback first (a post-ed Runnable), else the Handler's mCallback, else handleMessage. The loop only exits when next() returns null, which happens after quit()/quitSafely() — that's why loop() "blocks until quit."

MessageQueue

🎤 Say it out loud (~30–45s): "The MessageQueue is an ordered buffer of messages, sorted by their when delivery timestamp — internally a singly-linked list, not a heap. The clever part is next() doesn't busy-wait: when the queue is empty or the head message isn't due yet, it parks in nativePollOnce, which is an epoll wait on a native file descriptor with a timeout equal to the delay until the next message — so a sleeping app burns no CPU. There's also an idle-handler hook that fires when the queue runs dry, which framework code uses for deferrable work."

MessageQueue is a priority queue ordered by delivery time (Message.when). Under the hood it is a singly-linked list of Message objects sorted by timestamp. Looper.loop() calls MessageQueue.next(), which blocks via nativePollOnce() — epoll on Linux — until the next message is due.

MessageQueue.addIdleHandler() lets you register callbacks that fire when the queue is empty. Libraries like Glide and Choreographer use this for work that should not delay frames.

Under the hood

next() computes how long until the head message is due (when - SystemClock.uptimeMillis()) and passes that as the timeout to nativePollOnce(ptr, timeoutMillis). Native code blocks in epoll_wait on a Linux eventfd/pipe; the thread wakes either when the timeout expires (a delayed message is now due) or when enqueueMessage writes a byte to the fd via nativeWake (a new message jumped the head, so the wait must recompute).

empty queue            → timeout = -1 (infinite) → epoll_wait parks until wake
head due in 500ms      → timeout = 500           → wakes when due or on enqueue
head due now / past    → timeout = 0             → returns the head immediately

Idle handlers run inside next() only when there is no message ready to return; each IdleHandler.queueIdle() returning false is removed after one fire. Note "priority queue ordered by time" is a logical description — the implementation is an insertion-sorted singly-linked list keyed on when (FIFO among equal timestamps), plus a synchronization-barrier mechanism that lets async messages (used by Choreographer for vsync) skip ahead of normal ones.

Handler

🎤 Say it out loud (~30–45s): "A Handler is bound to a specific Looper at construction — so whichever thread that Looper runs on is where the work executes, regardless of which thread calls post. That's the bridge: a background thread builds a result and calls mainHandler.post, and the Runnable runs on the main thread. Under the covers post(Runnable) and sendMessage(Message) do the same thing — both enqueue a Message whose target is the Handler; post just stashes the Runnable in Message.callback."

A Handler is bound to a specific thread's Looper at construction time, so posting from any thread enqueues work on that Looper's thread.

// Posting from a background thread to the main thread
val mainHandler = Handler(Looper.getMainLooper())
mainHandler.post { textView.text = result }          // Runnable, ASAP
mainHandler.postDelayed({ doSomething() }, 3000L)    // Runnable, 3 seconds later
mainHandler.postAtTime({ doSomething() }, uptimeMs)  // Runnable, at absolute uptime

// Sending a Message (used for typed dispatch)
val msg = mainHandler.obtainMessage(MSG_UPDATE, data)
mainHandler.sendMessage(msg)
mainHandler.sendMessageDelayed(msg, 1000L)

post(Runnable) internally creates a Message with Message.callback set to the runnable. sendMessage(Message) sets Message.target to the handler and enqueues it.

Handler construction — Kotlin idiomatic:

// Callback-based (avoids subclassing)
val handler = Handler(Looper.getMainLooper()) { message ->
    when (message.what) {
        MSG_DONE -> { updateUi(message.obj as Result) ; true }
        else -> false
    }
}

Under the hood

Every enqueue path funnels through one method: post, postDelayed, sendMessage, and sendMessageDelayed all compute an absolute when = SystemClock.uptimeMillis() + delay and call enqueueMessage(queue, msg, when), which sets msg.target = this before inserting into the MessageQueue in when order.

// Handler.enqueueMessage (simplified)
private boolean enqueueMessage(MessageQueue queue, Message msg, long when) {
    msg.target = this;                 // so loop() knows where to dispatch
    if (mAsynchronous) msg.setAsynchronous(true);
    return queue.enqueueMessage(msg, when);  // inserts sorted; nativeWake if head changed
}

The delay is always converted to an absolute uptime timestamp at enqueue time — it's measured against SystemClock.uptimeMillis() (which does not advance during deep sleep), so postDelayed is not a wall-clock guarantee and can be pushed later if the thread is busy when the message comes due. obtainMessage pulls a Message from the recycling pool rather than allocating, which is why you should prefer it over Message().

HandlerThread

🎤 Say it out loud (~30–45s): "HandlerThread is the idiomatic way to get a background thread that owns a message loop — it subclasses Thread, calls Looper.prepare() and Looper.loop() for me in run(), and exposes the Looper once it's started. I build a Handler against ht.looper and now every task I post is serialized on that one thread, which is great for things that must not run concurrently. When I'm done I call quitSafely() so it drains pending work before stopping."

HandlerThread is a Thread subclass that sets up a Looper for you and exposes it after start(). It is the idiomatic way to get a background thread with a message loop:

val ht = HandlerThread("network-callback")
ht.start()
val bgHandler = Handler(ht.looper)

// When done:
ht.quitSafely()  // drains pending messages then stops
// ht.quit()     // stops immediately, may drop messages

Android uses HandlerThread internally for CameraDevice, Bluetooth, and IntentService (now deprecated).

Under the hood

HandlerThread.run() does Looper.prepare(), then synchronizes on the instance to publish mLooper and call notifyAll(), then runs Looper.loop(). The getLooper() accessor blocks on that same monitor (wait()) until run() has actually created and published the Looper — which is why you must call start() before touching ht.looper, and why accessing it is thread-safe despite the Looper being created on another thread.

start() → run(): prepare() → mLooper set → notifyAll() → loop()
getLooper(): while (mLooper == null && isAlive()) wait();  return mLooper

quit() calls MessageQueue.quit(false), which discards all pending messages and makes next() return null immediately. quitSafely() calls quit(true), which removes only messages scheduled in the future and still delivers any already-due messages before next() returns null — that's the "drain then stop" semantics.

Memory Leaks from Delayed Messages

🎤 Say it out loud (~30–45s): "This is the classic Handler leak. An anonymous or inner Handler/Runnable holds an implicit reference to the enclosing Activity. When I postDelayed something long-lived, the MessageQueue holds that Message, the message references the Handler as its target, and the Handler references the Activity — so the Activity can't be garbage-collected until the message fires or I remove it. If the user leaves the screen before then, that's a leaked Activity. The fix is removeCallbacksAndMessages(null) in onDestroy, or a WeakReference, or just lifecycle-scoped coroutines."

A very common leak pattern:

class MyActivity : AppCompatActivity() {
    // LEAK: non-static/anonymous handler holds implicit reference to Activity
    val handler = Handler(Looper.getMainLooper())

    override fun onResume() {
        // Delayed message enqueued; activity may finish before it fires
        handler.postDelayed({ updateUI() }, 60_000L)
    }
}

The Handler holds a reference to this via the Runnable closure or callback. The MessageQueue holds the pending Message, which holds the Handler, which holds the Activity. The Activity cannot be garbage collected until that message fires or is removed.

Fix:

override fun onDestroy() {
    super.onDestroy()
    handler.removeCallbacksAndMessages(null)  // remove ALL pending messages/runnables
}

Alternatively, use a WeakReference<Activity> in the callback, or switch to lifecycle-aware coroutines which handle this automatically.

Under the hood

The retention chain is real and walkable: the main thread's Looper is a process-lifetime GC root; its MessageQueue strongly references the queued Message; Message.target strongly references the Handler; and an anonymous Handler/Runnable declared inside the Activity holds a synthetic this$0 field pointing at the enclosing Activity instance.

[main Looper]  (GC root, lives forever)
   └─► MessageQueue
        └─► Message (when = now + 60s)
             ├─► target  ─► Handler (anonymous → outer Activity via this$0)
             └─► callback ─► Runnable (lambda capturing Activity)
                                └─► Activity  ← cannot be collected for 60s

removeCallbacksAndMessages(null) walks the queue and unlinks every Message whose target is this Handler (the null token means "match any"), breaking the chain immediately. removeCallbacks(runnable) / removeMessages(what) remove specific entries. Note that messages already dequeued and mid-dispatch can't be removed — so the safest scope is removing in onDestroy plus keeping delays short. Lifecycle-aware coroutines avoid the problem because cancelling the scope removes the pending continuations rather than leaving them parked in the queue.

Communicating with the UI Thread

🎤 Say it out loud (~30–45s): "In modern code I rarely use a raw Handler to get back to the UI thread — I reach for higher-level idioms that all sit on top of it. runOnUiThread posts to the main handler (or runs inline if I'm already there); View.post defers until the view is attached to a window, which is handy for measure-dependent work; LiveData.postValue is thread-safe and coalesces rapid updates; and withContext(Dispatchers.Main) is the coroutine way. They all ultimately enqueue a message on the main MessageQueue."

There are four modern idioms, all preferred over raw Handler. Activity.runOnUiThread { } internally posts to the main handler. View.post { } posts once the view's window is attached. LiveData.postValue() is thread-safe and deduplicates rapid updates. And withContext(Dispatchers.Main) { } is the coroutine-based approach.

Under the hood

Each idiom resolves to a message on the main MessageQueue, but with a subtle difference in when it runs:

runOnUiThread{}        → if on main: run inline; else mHandler.post(r)
View.post{}            → if attached: attachInfo.mHandler.post(r)
                         else: queued in ViewRootImpl run-queue, flushed at next traversal
LiveData.postValue(v)  → mainHandler.post(coalescing runnable); only latest v survives
withContext(Main){}    → Dispatchers.Main (HandlerDispatcher) posts the continuation

View.post before attachment is special: there's no Looper association yet, so the Runnable is held in the view's HandlerActionQueue and replayed once dispatchAttachedToWindow gives the view its handler — that's why it's the correct place to read a freshly-laid-out view's dimensions. LiveData.postValue's coalescing works by storing the pending value in a field guarded by a lock and only posting a runnable if one isn't already pending, so N rapid postValue calls yield at most one (latest-wins) main-thread delivery — which is exactly why you can lose intermediate values compared to setValue.

3.8 Kotlin Coroutines on Android

What Is a Coroutine?

🎤 Say it out loud (~30–45s): "A coroutine is a suspendable computation — it's not a thread. When it suspends, instead of blocking an OS thread it saves its state on the heap and frees the thread to do other work, then resumes later, possibly on a different thread. That's why I can run thousands of coroutines on a handful of threads. Under the hood the compiler rewrites my suspend functions into a state machine using Continuation-Passing Style, so there's no magic — just callbacks and saved state."

A coroutine is a suspendable computation. Unlike a thread, it does not block an OS thread when suspended — it saves its execution state (local variables, program counter) on the heap and releases the thread to do other work. When the suspension point completes, the coroutine is resumed, possibly on a different thread.

Coroutines are implemented via Continuation Passing Style transformation: the compiler rewrites suspend fun foo() into a state machine that passes a Continuation callback at each suspension point.

Under the hood

The compiler transforms each suspend fun into a function that takes an extra Continuation parameter and returns Any? (it may return either the real result or the sentinel COROUTINE_SUSPENDED). The body becomes a state machine where every suspension point is a numbered label; local variables that must survive a suspension are hoisted into fields of a generated ContinuationImpl subclass.

suspend fun foo(): T
        ↓ (CPS transform)
Object foo(Continuation<? super T> $cont)
  - $cont stores the current label and saved locals
  - at each suspension point: save state, set next label,
    if the callee returns COROUTINE_SUSPENDED, foo also returns it
  - on resume, the saved $cont re-invokes foo(), the switch jumps
    to the saved label, and execution continues from there

suspend Functions

🎤 Say it out loud (~30–45s): "A suspend function is just a function that's allowed to pause at suspension points and resume later without blocking the thread. The big gotcha interviewers love is that suspend alone doesn't move work off the calling thread — if I do synchronous CPU or blocking IO inside a suspend function, it blocks whatever thread called it. To actually offload, I wrap the work in withContext(Dispatchers.IO) or Default. The compiler enforces the rule that suspend functions can only be called from other suspend functions or a coroutine builder."

A suspend function can be paused at suspension points — calls to other suspend functions or to suspendCoroutine/suspendCancellableCoroutine. It can only be called from another suspend function or a coroutine builder.

suspend fun fetchUser(id: String): User {
    return withContext(Dispatchers.IO) {   // suspension point
        userApi.getUser(id)
    }
}

The key rule is that suspend by itself does NOT make a function non-blocking. A suspend function that does synchronous CPU work blocks whatever thread it runs on. Use withContext(Dispatchers.Default) or Dispatchers.IO to actually offload the work.

Under the hood

The suspend modifier is purely a compile-time contract that allows the CPS transform. At the bytecode level there's no separate "suspend" call mechanism — fetchUser(id) compiles to fetchUser(id, $continuation). The lowest-level primitive is suspendCoroutine/suspendCancellableCoroutine, which hands you the Continuation; calling continuation.resumeWith(Result) is what re-enters the state machine. If the callee actually suspends, it returns COROUTINE_SUSPENDED up the call chain so the thread can be released; if it completes synchronously, it returns the value and execution continues without ever yielding the thread.

Coroutine Builders

🎤 Say it out loud (~30–45s): "launch is fire-and-forget — it returns a Job and an uncaught exception propagates to the scope and cancels it. async is for concurrent results — it returns a Deferred, and its exception is held until I call await(). runBlocking bridges the blocking and suspending worlds by actually blocking the calling thread, so I only use it in main() or tests, never in production Android code. The nuance is exception timing: launch throws eagerly into the scope, async defers until await."

There are three builders. launch is fire-and-forget — it returns a Job and exceptions propagate to the scope's exception handler. Uncaught exceptions crash the parent scope unless it is backed by a SupervisorJob.

async is for concurrent computation that returns a result — it returns Deferred<T>. Exceptions are stored and rethrown when you call await().

runBlocking bridges blocking and suspending code by blocking the calling thread until the block completes. Use it only in main() or tests — never in production Android code, because it would block the calling thread.

// In tests:
@Test
fun testFetch() = runBlocking {
    val result = repository.fetchUser("123")
    assertEquals("Alice", result.name)
}

Under the hood

launch and async are extension functions on CoroutineScope. Each constructs a coroutine object (StandaloneCoroutine for launch, DeferredCoroutine for async) whose Job is registered as a child of the scope's Job, then calls start, which schedules the initial continuation on the dispatcher. launch returns the Job; async's Deferred extends Job and additionally stores the completion result. runBlocking creates a BlockingCoroutine with an event loop and parks the current thread (LockSupport.park) until the coroutine completes, draining queued continuations on that same thread — which is exactly why it must not run on the Android main thread.

CoroutineScope

🎤 Say it out loud (~30–45s): "A CoroutineScope is the lifetime boundary for coroutines — every coroutine I launch is a child of the scope's Job, so when the scope is cancelled all its children are cancelled. On Android I lean on viewModelScope, which auto-cancels in onCleared, and lifecycleScope tied to an Activity or Fragment. I avoid GlobalScope because it isn't tied to any lifecycle, so it leaks coroutines and the work outlives the screen."

Every coroutine runs inside a CoroutineScope. The scope tracks all coroutines launched within it and provides cancellation propagation — when the scope is cancelled, all its children are cancelled.

// ViewModel provides viewModelScope
class MyViewModel : ViewModel() {
    fun load() {
        viewModelScope.launch {
            val data = repository.getData()   // suspend; non-blocking
            _state.value = data
        }
    }
    // viewModelScope is automatically cancelled in onCleared()
}

There are three standard scopes on Android. viewModelScope is tied to the ViewModel lifecycle. lifecycleScope is tied to a Lifecycle owner like an Activity or Fragment. GlobalScope should be avoided because it is not tied to any lifecycle and will leak coroutines.

Under the hood

A CoroutineScope is essentially just a holder for a CoroutineContext, and the most important element in that context is its Job. When you call scope.launch, the new coroutine's Job is attached to the scope's Job via attachChild, building the parent-child tree. scope.cancel() calls Job.cancel(), which walks that tree cancelling every child. viewModelScope is a lazily-created CloseableCoroutineScope(SupervisorJob() + Dispatchers.Main.immediate) stored on the ViewModel; onCleared() calls coroutineContext.cancel(). GlobalScope has no Job lifecycle owner, so nothing ever cancels its children.

Coroutine Context

🎤 Say it out loud (~30–45s): "A CoroutineContext is an indexed set of elements — the Job, the Dispatcher, a CoroutineName, an exception handler — and you combine them with the + operator. Children inherit the parent's context but can override individual elements. The subtlety is that the Job is special: the child gets a new child Job, not the parent's, which is what wires up structured concurrency."

A CoroutineContext is a map of context elements — Job, CoroutineDispatcher, CoroutineName, CoroutineExceptionHandler. Child coroutines inherit the parent's context but can override individual elements:

launch(Dispatchers.IO + CoroutineName("fetch-user")) {
    // runs on IO dispatcher, named for debugging
}

Under the hood

CoroutineContext is an immutable, persistent map keyed by element Keys; each Element is itself a context with a single entry. The + operator builds a CombinedContext linked list and folds duplicate keys (right wins). Lookups use get(key). When a builder runs, it computes the new child context as parentContext + builderContext + Job, where a fresh child Job is always installed — so the child never shares the parent's Job object, only points to it as parent. The Dispatcher is found in this context as a ContinuationInterceptor, which the machinery uses to wrap each continuation before resuming it.

Dispatchers

🎤 Say it out loud (~30–45s): "A dispatcher decides which thread a coroutine runs and resumes on. Main is the Android UI thread, IO is a large elastic pool for blocking calls like network and disk, and Default is sized to the CPU cores for compute. Mechanically a dispatcher is just a ContinuationInterceptor that intercepts each continuation and posts its resume to the right thread. I always inject the dispatcher rather than hard-coding it, so tests can swap in a TestDispatcher."

Dispatchers.MainAndroid main threadUI updates, Compose, LiveData
Dispatchers.IOShared pool, up to 64 threads (or N_cores if larger)Blocking IO, network, file, database

class UserRepository(
    private val api: UserApi,
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {
    suspend fun getUser(id: String): User = withContext(ioDispatcher) {

    }
}

// In tests:

Under the hood

A CoroutineDispatcher is a ContinuationInterceptor: its interceptContinuation wraps the coroutine's continuation in a DispatchedContinuation, and dispatch(context, block) posts the resume Runnable onto the target executor. Dispatchers.Main on Android dispatches via a Handler on the main Looper; Default and IO share one pool of worker threads (CoroutineScheduler) but with different parallelism limits — IO lets blocking tasks elastically grab more threads while Default is capped at CPU count. Main.immediate skips re-dispatch when already on the main thread. Because dispatching is just continuation interception, switching dispatchers with withContext is the act of resuming the next continuation on a different thread.

Structured Concurrency

🎤 Say it out loud (~30–45s): "Structured concurrency means a coroutine's lifetime is bounded by the scope that launched it — the parent can't complete until all its children complete. So cancelling the parent cancels the children, a child's failure propagates up unless I'm using a SupervisorJob, and there's no orphaned background work that outlives its scope. That's the whole reason coroutines are easier to reason about than raw callbacks or thread pools: leaks and lost exceptions become structurally impossible."

Structured concurrency is the discipline that coroutines must complete before the scope that launched them completes. There are four consequences. A parent coroutine waits for all children before completing. Cancelling a parent cancels all children. A child failure propagates to the parent unless the scope uses a SupervisorJob. And coroutines cannot escape their scope's lifetime.

This makes reasoning about concurrent code dramatically simpler — there is no orphaned background work to worry about.

Under the hood

Structured concurrency is implemented entirely through the Job tree. Each launched coroutine's Job is attached to its parent via attachChild, producing a ChildHandle. A parent Job cannot reach the Completed state until all child Jobs complete — internally the JobSupport state machine counts active children and stays in a Completing state while any remain. Cancellation propagates downward (parent cancel → cancelChildren), while uncaught failures propagate upward (childCancelled → parent cancels), unless the parent is a SupervisorJob, whose childCancelled returns false to stop upward propagation.

Job vs SupervisorJob

🎤 Say it out loud (~30–45s): "With a regular Job, a child failure propagates up and cancels the parent and all siblings — one failure takes everything down. A SupervisorJob breaks that upward propagation, so each child fails independently without killing its siblings. I use a SupervisorJob for long-lived top-level scopes — like a screen scope running several independent operations — where one failing request shouldn't tear down the others. That's also exactly why viewModelScope uses a SupervisorJob internally."

With a regular Job, when a child fails, the exception propagates to the parent, which then cancels all siblings and itself — one failure kills all siblings.

With a SupervisorJob, a child's failure does not propagate to the parent or siblings. Each child is independent. Use a SupervisorJob for top-level scopes where independent operations should not kill each other.

// viewModelScope uses SupervisorJob internally
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)

scope.launch { operationA() }  // if this throws, operationB keeps running
scope.launch { operationB() }

Under the hood

Both are Job implementations; the only behavioral difference is in the childCancelled(cause) hook. A regular Job (JobImpl) returns true, meaning "I handled the child's failure by cancelling myself" — which then cancels all other children. SupervisorJobImpl overrides childCancelled to return false, signalling that the child must handle its own exception (via a CoroutineExceptionHandler or, for async, at await). Note this only works at the scope boundary: supervisorScope/SupervisorJob does NOT stop a failure from propagating if you nest a normal launch whose own child throws — the supervisor only governs its direct children.

coroutineScope vs supervisorScope

🎤 Say it out loud (~30–45s): "Both are suspend functions that create a new child scope and suspend until every child inside finishes — so they're how I do structured concurrency inside a single suspend function. The difference is failure semantics: with coroutineScope, if any child throws, all siblings are cancelled and the exception rethrows out of the block; with supervisorScope, children are independent so one failure doesn't cancel the others. I reach for coroutineScope for all-or-nothing parallel work and supervisorScope when partial results are acceptable."

Both are suspend functions that create a new child scope and neither returns until all children complete.

With coroutineScope, if any child throws, all siblings are cancelled and the exception propagates out. With supervisorScope, children are independent — one failure does not cancel siblings.

suspend fun loadDashboard() = coroutineScope {
    val user = async { fetchUser() }     // if this fails, everything fails
    val posts = async { fetchPosts() }
    DashboardData(user.await(), posts.await())
}

suspend fun loadOptional() = supervisorScope {
    val primary = async { fetchPrimary() }   // failure doesn't kill secondary
    val secondary = async { fetchSecondary() }
    // handle each result independently
}

Under the hood

coroutineScope { } is a suspend function that calls suspendCoroutineUninterceptedOrReturn and installs a ScopeCoroutine whose Job becomes the parent of everything launched inside. It inherits the caller's context (and thus its dispatcher and Job as parent) and only resumes the outer continuation once all children have completed. supervisorScope does the same but installs a SupervisorCoroutine whose childCancelled returns false. Because the scope's Job is a child of the calling coroutine's Job, a failure that does propagate out of coroutineScope is rethrown synchronously at the call site rather than going to a CoroutineExceptionHandler.

withContext

🎤 Say it out loud (~30–45s): "withContext switches the coroutine to a different context — usually a dispatcher — for the duration of the block, then switches back automatically when the block returns. It doesn't start a new coroutine; it's roughly async { }.await() but cheaper because it skips the Deferred allocation. The reason it doesn't 'leak' the dispatcher is structured: the context change is scoped to the block, so once it returns I'm back on the original dispatcher, and exceptions propagate straight to the caller."

withContext(context) switches the coroutine to a new context — typically a different dispatcher — for the duration of the block, then switches back:

suspend fun saveToDb(item: Item) {
    withContext(Dispatchers.IO) {
        db.insert(item)          // runs on IO thread
    }
    // back on the original dispatcher here
}

withContext does not start a new coroutine scope. It is semantically equivalent to async { ... }.await() but more efficient because it avoids the Deferred allocation.

Under the hood

withContext computes a merged context (oldContext + newContext) and, if the dispatcher actually changed, allocates a DispatchedCoroutine and re-dispatches the continuation onto the new dispatcher; when the block completes it dispatches the result back onto the original dispatcher before resuming the caller. The reason the dispatcher doesn't "leak" is that the caller's own continuation still carries the original ContinuationInterceptor — withContext only re-routes the resume of its own block, so resumption after the block lands on the original thread. If the target context equals the current one, withContext has a fast path that runs the block inline with no dispatch at all.

Exception Handling

🎤 Say it out loud (~30–45s): "For launch-style code I either try/catch at the call site or install a CoroutineExceptionHandler as a last-resort handler at the top of the scope. The two traps interviewers probe: async does not invoke the exception handler — the exception is stored in the Deferred and only thrown at await(), so I wrap await in try/catch. And CancellationException is special — it's how cancellation works, so if I catch a broad exception I must rethrow it, otherwise I break cooperative cancellation."
// Option 1: try/catch at the call site
viewModelScope.launch {
    try {
        val result = repository.fetch()
        _state.value = result
    } catch (e: IOException) {
        _error.value = e.message
    }
}

// Option 2: CoroutineExceptionHandler (for launch only, not async)
val handler = CoroutineExceptionHandler { _, e ->
    Log.e(TAG, "Unhandled exception", e)
}
viewModelScope.launch(handler) { dangerousWork() }

There are two important nuances. First, async does NOT invoke the CoroutineExceptionHandler — the exception is stored in the Deferred and rethrown when you call await(), so wrap await() in a try/catch.

Second, CancellationException is thrown when a coroutine is cancelled and it must NOT be caught and swallowed:

try {
    delay(1000)
} catch (e: Exception) {
    if (e is CancellationException) throw e  // re-throw!
    handleError(e)
}

Under the hood

When a coroutine completes exceptionally, JobSupport distinguishes CancellationException (normal cancellation — does not propagate to the handler) from other throwables (a real failure). For a real failure it calls childCancelled up the tree; if propagation reaches a root coroutine with no parent to handle it, the machinery looks up the CoroutineExceptionHandler element in the context and invokes it, falling back to a global handler / thread UncaughtExceptionHandler. async's DeferredCoroutine instead stores the exception in its completed state and only re-throws it from await()'s getCompletionExceptionOrNull, which is why the handler never fires for async. Because cancellation is signalled by throwing CancellationException at suspension points, swallowing it leaves the Job thinking it's still active and breaks structured cancellation.

Cancellation Cooperation

🎤 Say it out loud (~30–45s): "Coroutine cancellation is cooperative: cancelling sets the Job to a cancelling state, but the coroutine only actually stops when it hits a suspension point that checks for it. All the kotlinx.coroutines suspend functions like delay check automatically and throw CancellationException. But a tight CPU loop with no suspension points will keep running, so I have to cooperate manually — call ensureActive() or yield(), or check the isActive flag. That's the classic 'why won't my coroutine cancel' bug."

Coroutines are cancelled cooperatively — the runtime sets a flag and the coroutine must check it. All suspend functions in kotlinx.coroutines check for cancellation automatically. CPU-intensive work must check manually:

suspend fun processLargeList(list: List<Item>) {
    list.forEach { item ->
        ensureActive()        // throws CancellationException if cancelled
        // or: yield()        // checks cancellation AND yields scheduler
        process(item)
    }
}

The isActive property on CoroutineScope or Job is available for a non-throwing check.

Under the hood

Job.cancel() transitions the Job's state from Active to Cancelling and stores a CancellationException as the cancel cause. Cooperating suspend functions check this on resume: when a continuation backed by a cancellable coroutine is resumed, the machinery sees the cancelled state and throws the stored CancellationException instead of continuing — that's why suspension points are the only places cancellation can take effect. ensureActive() is a non-suspending check that reads Job.isActive and throws the cancel cause if inactive; yield() additionally re-dispatches to give other work a turn. A loop with zero suspension points never reaches a check, so it runs to completion regardless of cancellation.

Main-Safety

🎤 Say it out loud (~30–45s): "Main-safe means a suspend function can be called from the main thread without ever blocking it. The principle I follow is that each layer owns its own main-safety — the repository or data source wraps its blocking work in the right dispatcher via withContext, rather than making every caller remember to switch threads. So my ViewModel can just call the repository from viewModelScope and update state, and never has to think about dispatchers."

A function is main-safe if it can be called from the main thread without blocking it. The pattern is that every layer — ViewModel, Repository, DataSource — wraps its own heavy work in the appropriate dispatcher using withContext, rather than pushing that responsibility up to the caller.

// Repository is responsible for its own main-safety
class PhotoRepository(private val db: PhotoDao, private val api: PhotoApi) {
    suspend fun getPhotos(): List<Photo> = withContext(Dispatchers.IO) {
        db.getAll().ifEmpty { api.fetchAll().also { db.insertAll(it) } }
    }
}

// ViewModel just calls and updates state — no dispatcher needed here
class PhotoViewModel(private val repo: PhotoRepository) : ViewModel() {
    fun load() = viewModelScope.launch {
        _photos.value = repo.getPhotos()   // main-safe: repo handles dispatcher
    }
}

Under the hood

Main-safety is just disciplined use of withContext dispatching. When getPhotos() is called on the main thread, execution runs inline until it hits withContext(Dispatchers.IO), which re-dispatches the inner block's continuation onto an IO worker thread (the main thread is freed at that suspension point). When the block completes, withContext dispatches the result back to Dispatchers.Main before resuming the caller, so _photos.value = ... runs on the main thread. Note that suspend-based libraries like Room and Retrofit are already main-safe internally — they perform their own dispatch — so wrapping their suspend APIs in another withContext(IO) is redundant; the manual withContext matters for your own blocking code.

Testing Coroutines

🎤 Say it out loud (~30–45s): "For testing I run inside runTest, which gives me a virtual clock so delay is skipped and I control time with advanceUntilIdle or advanceTimeBy. I swap Dispatchers.Main with a TestDispatcher via a JUnit rule that calls Dispatchers.setMain/resetMain. The choice is between StandardTestDispatcher, which queues tasks so I can assert ordering deterministically, and UnconfinedTestDispatcher, which runs eagerly when I just want to observe final state."
@OptIn(ExperimentalCoroutinesApi::class)
class UserViewModelTest {
    @get:Rule val mainDispatcherRule = MainDispatcherRule()
    // MainDispatcherRule replaces Dispatchers.Main with TestCoroutineDispatcher

    @Test
    fun `load user updates state`() = runTest {
        val vm = UserViewModel(fakeRepository)
        vm.loadUser("1")
        advanceUntilIdle()   // runs all pending coroutines
        assertEquals(expectedUser, vm.state.value)
    }
}

// MainDispatcherRule
class MainDispatcherRule(
    private val dispatcher: TestDispatcher = UnconfinedTestDispatcher()
) : TestWatcher() {
    override fun starting(description: Description) = Dispatchers.setMain(dispatcher)
    override fun finished(description: Description) = Dispatchers.resetMain()
}

There are two test dispatchers. StandardTestDispatcher does not run tasks until you explicitly call advanceUntilIdle() or advanceTimeBy(), which gives you precise control over execution order. UnconfinedTestDispatcher runs tasks eagerly on the calling thread, which makes it simpler for tests that just need to observe state.

Under the hood

runTest runs the body on a TestScope backed by a TestCoroutineScheduler — a virtual clock with a priority queue of scheduled tasks keyed by virtual time. delay(n) doesn't really sleep; it schedules a resumption at currentTime + n, and advanceTimeBy/advanceUntilIdle simply pop tasks off the queue and run them, advancing the virtual clock instantly. TestDispatchers share that one scheduler so all coroutines stay coordinated. StandardTestDispatcher enqueues every task (nothing runs until you advance), whereas UnconfinedTestDispatcher runs each task eagerly until its first suspension. Dispatchers.setMain swaps the Main dispatcher factory for the test dispatcher so production code using viewModelScope (which is Main.immediate) runs on the test scheduler too.

3.9 Flow, StateFlow, SharedFlow, Channel

Cold vs Hot Streams

🎤 Say it out loud (~30–45s): "The split is about who controls execution. A cold stream like Flow doesn't run its producer block until someone collects, and it re-runs fresh and independently for every collector — like calling a function each time. A hot stream like StateFlow, SharedFlow, or Channel produces values whether or not anyone is listening, and collectors share one source. The practical consequence interviewers probe is that two collectors on a cold flow hit the network twice, whereas on a hot flow they share emissions — so I pick cold for per-request pipelines and hot for shared state or events."

A cold stream — Flow — does nothing until collected. Each collector gets its own independent execution of the producer, like calling a function fresh each time.

A hot stream — StateFlow, SharedFlow, Channel — produces values regardless of whether there are collectors. Multiple collectors share the same stream of values.

Under the hood

A cold Flow is essentially a suspend lambda wrapped in an object: its collect takes a FlowCollector and runs the producer block right then, calling collector.emit(value) for each item. Because nothing is stored, calling collect twice executes the block twice. Hot streams instead hold shared mutable state (a current value, a replay cache, or a queue) that lives independently of any collector, so emission and collection are decoupled.

Flow — Cold Stream

🎤 Say it out loud (~30–45s): "A Flow built with the flow { } builder is sequential and cold — the block runs only on collect, and producer and collector share the same coroutine by default. The subtle part is backpressure: emit is a suspend call, so when I emit, the producer suspends until the collector finishes processing that value. That means I get implicit backpressure for free without any explicit buffering. If I want them to run concurrently I add a buffer() operator, which inserts a channel between them."
fun fetchPages(): Flow<Page> = flow {
    var page = 1
    while (true) {
        emit(repository.getPage(page++))   // suspend, respects backpressure
    }
}

// Collect — starts the producer
viewModelScope.launch {
    fetchPages().collect { page ->
        // process page
    }
}

Flow is sequential by default — the producer and collector run in the same coroutine, and emit suspends until the collector processes the value.

Under the hood

emit and collect are linked by suspension. collect invokes the producer block passing a FlowCollector whose emit directly invokes the supplied collector lambda; since emit is suspend, the producer cannot continue until the downstream lambda returns. This is why backpressure is implicit — there's no buffer, the producer simply suspends at the emit point until the consumer is ready.

producer: emit(A) ──suspends──▶ consumer processes A ──returns──▶ producer resumes ──▶ emit(B) ...

Flow Operators

🎤 Say it out loud (~30–45s): "Operators are intermediate and lazy — they wrap the upstream Flow and only do work once a terminal operator like collect runs. The ones interviewers dig into are the flatMap family — flatMapLatest cancels the previous inner flow, which is exactly what you want for typeahead search — and flowOn, which changes the dispatcher of the upstream only, not the collector. I'd also mention stateIn/shareIn for turning a cold flow hot with a sharing policy like WhileSubscribed(5000) so it survives config changes."
flow
    .map { transform(it) }                   // 1:1 transform
    .filter { it.isValid }                   // conditional pass-through
    .combine(otherFlow) { a, b -> a + b }    // zip latest from both flows
    .flatMapLatest { query ->                // cancel previous, start new on each emission
        searchApi.search(query)
    }
    .debounce(300)                           // suppress emissions within 300ms window
    .distinctUntilChanged()                  // suppress if same as previous value
    .catch { e -> emit(defaultValue) }       // handle upstream exceptions
    .retry(3) { e -> e is IOException }      // retry upstream on matching exception
    .stateIn(                                // convert to StateFlow
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5000),
        initialValue = emptyList()
    )
    .shareIn(                                // convert to SharedFlow
        scope = viewModelScope,
        started = SharingStarted.Eagerly,
        replay = 1
    )
    .collectLatest { value ->               // cancels previous collector block on new emission
        render(value)
    }

The three flatMap variants differ in how they handle concurrent inner flows. flatMapLatest cancels the previous inner flow when a new value arrives — use this for search queries. flatMapMerge runs all inner flows concurrently up to the concurrency limit. flatMapConcat runs them sequentially, one at a time.

For stateIn, there are three SharingStarted options. Eagerly starts immediately and never stops. Lazily starts on the first collector and never stops. WhileSubscribed(stopTimeoutMillis) stops N milliseconds after the last collector cancels and restarts when a new one arrives — for ViewModel-to-UI flows, 5000 ms is the recommended value because it survives a configuration change.

Under the hood

Intermediate operators return a new Flow that decorates the upstream — they don't trigger execution, so the chain stays cold until a terminal operator collects it. flowOn works by inserting a channel boundary: upstream emissions run on the specified dispatcher and are passed through a channel to the downstream, so it changes context for everything above it only. flatMapLatest and collectLatest cancel and relaunch the inner/downstream coroutine when a new value arrives, while stateIn/shareIn launch a single sharing coroutine in the given scope that collects upstream once and fans out to a StateFlow/SharedFlow.

StateFlow — Hot State Holder

🎤 Say it out loud (~30–45s): "StateFlow is a hot, conflated state holder that always has exactly one current value, which is why it needs an initial value at construction and is my go-to LiveData replacement for screen state. It conflates rapid updates and only emits when the new value isn't equal to the previous one — so distinctUntilChanged is baked in, and a new collector instantly gets the current value. The gotcha that follows from equals-based dedupe is that mutating a list in place without producing a new object won't emit, so I always emit immutable copies via update { }."

StateFlow is a hot flow that always holds exactly one current value. It is the replacement for LiveData in Kotlin codebases.

private val _state = MutableStateFlow<UiState>(UiState.Loading)
val state: StateFlow<UiState> = _state.asStateFlow()

// Update state
_state.value = UiState.Success(data)         // main thread
_state.update { current -> current.copy(...) } // atomic update

// Collect in Compose
val uiState by viewModel.state.collectAsStateWithLifecycle()

There are four key properties: it always has a current value (initial value required at construction); it only emits when the value actually changes, so distinctUntilChanged is baked in; new collectors immediately receive the current value since the replay is effectively 1; and the value setter is thread-safe using atomic CAS.

Under the hood

StateFlow is a conflated state holder: it stores a single current value and, on every set, compares the new value to the old with equals. If they're equal it emits nothing; if different it updates and signals collectors. Conceptually it behaves like a SharedFlow with replay = 1, onBufferOverflow = DROP_OLDEST, plus distinct-until-changed. Because conflation can collapse intermediate values, a fast A → B → A sequence may surface as just A to a slow collector — StateFlow guarantees the latest, not every intermediate, value. The value setter uses an atomic compare-and-set so updates are thread-safe.

SharedFlow — Hot Broadcast

🎤 Say it out loud (~30–45s): "SharedFlow is a fully configurable hot broadcast — no initial value, and I tune replay, extraBufferCapacity, and onBufferOverflow. It fans every emission out to all active collectors, which makes it the natural fit for one-shot events when I set replay = 0 so a freshly subscribed collector doesn't get stale events. The nuance is the difference between emit, which suspends when the buffer is full, and tryEmit, which is non-suspending and returns false rather than blocking — and that with replay = 0 and no collectors, an event is simply dropped."

SharedFlow is for events that should reach multiple collectors, with a configurable replay cache.

private val _events = MutableSharedFlow<UiEvent>(
    replay = 0,            // new collectors don't get old events
    extraBufferCapacity = 1,
    onBufferOverflow = BufferOverflow.DROP_OLDEST
)
val events: SharedFlow<UiEvent> = _events.asSharedFlow()

// Emit
viewModelScope.launch { _events.emit(UiEvent.ShowSnackbar("Saved")) }
// or tryEmit (non-suspending, drops if buffer full)
_events.tryEmit(UiEvent.Navigate(Screen.Home))

For modeling one-time events: SharedFlow(replay=0) means the event fires once and only collectors active at that moment receive it. An alternative pattern is consumeAsFlow() via Channel. Avoid StateFlow for events because new collectors will replay the last event, which is almost never what you want for a navigation or snackbar command.

Under the hood

SharedFlow maintains a replay cache (size replay) plus an extra buffer (extraBufferCapacity); a new collector first receives whatever is in the replay cache, then live emissions. When the buffer fills, behavior depends on onBufferOverflow: SUSPEND makes emit suspend the producer until space frees up (true backpressure), while DROP_OLDEST/DROP_LATEST discard a value so emission never suspends. tryEmit is the non-suspending entry point — it succeeds only if it can add without suspending (i.e. there's buffer room or a drop policy applies), otherwise returns false. With replay = 0 and no active collectors, emitted values have nowhere to go and are effectively dropped.

Channel — One-to-One Communication

🎤 Say it out loud (~30–45s): "A Channel is a hot, coroutine-safe queue where each element goes to exactly one receiver — unlike SharedFlow, which broadcasts the same value to every collector. The default RENDEZVOUS channel has zero buffer, so send suspends until a receiver is ready, giving precise hand-off backpressure. I'd reach for a Channel for producer-consumer work distribution or single-consumer events like a navigation command, and call out that it's the building block hot flows use internally and that you should close() it to signal completion."

Channel is a non-broadcast, coroutine-based primitive for producer-consumer patterns. Each value is consumed by exactly one collector — unlike SharedFlow, which broadcasts to all active collectors.

val channel = Channel<Work>(capacity = Channel.BUFFERED)

// Producer
launch { channel.send(work) }   // suspends if buffer full

// Consumer
launch { for (work in channel) process(work) }  // suspends if empty
// or
launch { channel.consumeEach { process(it) } }

channel.close()  // signals completion

There are four capacity modes. RENDEZVOUS (capacity 0) means the sender suspends until the receiver is ready — like SynchronousQueue. BUFFERED gives a small buffer of 64 by default. UNLIMITED never suspends on send. CONFLATED keeps only the last value.

For the Channel versus SharedFlow decision: use Channel when exactly one consumer should handle each event, such as a navigation command consumed by one Fragment. Use SharedFlow when multiple UI components should all react, such as a toast that could be visible in two places.

Under the hood

A Channel is a hot queue with a configurable capacity. send adds an element and receive removes one, with each element delivered to exactly one receiver — there is no broadcast. With RENDEZVOUS (capacity 0) there is no storage at all: send suspends until a receive is waiting, so the two coroutines hand the value off directly. Buffered/unlimited modes store elements until received; CONFLATED keeps only the latest. Backpressure is explicit: send suspends when the buffer is full (except UNLIMITED/conflated). This rendezvous/queue machinery is exactly what flowOn, buffer, and callbackFlow use to bridge coroutines.

Lifecycle-Aware Collection

🎤 Say it out loud (~30–45s): "Collecting a flow in a plain lifecycleScope.launch keeps running while the UI is in the background, wasting work and updating invisible views. The fix is repeatOnLifecycle(STARTED), which cancels the collection coroutine when the lifecycle drops below STARTED and restarts it when it comes back — so I get a fresh subscription each time the screen is visible. In Compose the equivalent is collectAsStateWithLifecycle. I'd note that repeatOnLifecycle cancels and re-collects, which is why a WhileSubscribed(5000) upstream is nice — it doesn't tear down the shared pipeline during a quick rotation."

The problem with collecting a Flow inside a plain lifecycleScope.launch block is that collection continues when the UI is in the background (STOPPED), wasting resources and potentially updating invisible UI.

The solution is repeatOnLifecycle:

// In Fragment or Activity
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        // This block starts when STARTED, cancels when STOPPED
        // Restarts when STARTED again
        viewModel.state.collect { render(it) }
    }
}

repeatOnLifecycle is the correct way to collect Flows in the UI layer. It automatically cancels the inner block when the lifecycle drops below the target state and restarts it when the lifecycle rises again.

In Compose:

@Composable
fun MyScreen(viewModel: MyViewModel = hiltViewModel()) {
    // Lifecycle-aware: stops collecting when composable leaves composition/goes to background
    val uiState by viewModel.state.collectAsStateWithLifecycle()
    // render uiState
}

collectAsStateWithLifecycle is the Compose-specific equivalent of repeatOnLifecycle(STARTED) and requires androidx.lifecycle:lifecycle-runtime-compose.

For the launchIn versus repeatOnLifecycle choice: lifecycleScope.launchIn(this) combined with flowWithLifecycle() is an alternative for single flows, while repeatOnLifecycle is preferred for multiple flows or more complex collection logic.

Under the hood

repeatOnLifecycle is a suspend function that registers a lifecycle observer and, each time the lifecycle reaches the target state, launches a new coroutine running the block; when the state drops below the target it cancels that coroutine. So collecting inside it means a brand-new collect (and thus a fresh upstream subscription) on every STARTED transition — the old one is fully cancelled, not paused. collectAsStateWithLifecycle wraps the same machinery, calling repeatOnLifecycle internally and feeding emissions into a Compose State. Because each restart re-subscribes, pairing it with a stateIn(WhileSubscribed(5000)) upstream keeps the shared producer alive across brief gaps like rotation instead of restarting it.

3.10 Background Work

Categorizing Work

🎤 Say it out loud (~30–45s): "The first thing I do is categorize the work, because the API falls out of that. If it must run now and can die with the process, it's a coroutine in the right scope. If it's deferrable but must run eventually — even across reboot — that's WorkManager. If it's user-visible and ongoing, like playback, that's a foreground service. And if it needs exact timing, that's AlarmManager, used sparingly. Picking the wrong category is the classic mistake — like using WorkManager for an exact alarm or a foreground service for a deferrable sync."
Category Definition Appropriate API
Immediate asyncMust run now, result needed soon, tied to app processCoroutines (viewModelScope, lifecycleScope)
DeferrableCan run later, at system's discretionWorkManager
PersistentMust complete even after process death or rebootWorkManager (deferrable) or Foreground Service (immediate persistent)
Exact timingMust run at a specific timeAlarmManager (with care)
Ongoing user-visibleLong-running, user-visible progressForeground Service

Under the hood

Each category maps to a different framework mechanism. Coroutines live entirely in your process — nothing is persisted, so when the process dies the work is gone. WorkManager persists requests to a Room database and hands scheduling to the system, so the OS can run them later even after a restart. Foreground services keep the process at foreground priority so the OOM killer leaves it alone while a visible notification is shown. AlarmManager registers a wakeup with the AlarmManagerService in system_server, which is the only one of these that can wake a Doze-idle device at a precise time.

WorkManager

🎤 Say it out loud (~30–45s): "WorkManager is the recommended API for deferrable, guaranteed background work — syncing, uploading, log shipping — work that must run eventually even if the app is killed or the device reboots. It persists the request in a database and, on modern APIs, schedules it through JobScheduler, honoring constraints like network or charging. The nuance interviewers probe is that it's not for immediate or exact-time work — for that I'd reach for a coroutine, a foreground service, or rarely an exact alarm."

WorkManager is the recommended API for deferrable, persistent background work. It uses JobScheduler on API 23 and above, falling back to AlarmManager plus BroadcastReceiver on older devices. It survives process death and device restarts because constraints are re-registered at boot.

// Define a worker
class SyncWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        return try {
            repository.sync()
            Result.success()
        } catch (e: Exception) {
            if (runAttemptCount < 3) Result.retry() else Result.failure()
        }
    }
}

// Build a request
val request = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)
            .setRequiresBatteryNotLow(true)
            .build()
    )
    .setInputData(workDataOf("key" to "value"))
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
    .addTag("sync")
    .build()

// Enqueue
WorkManager.getInstance(context).enqueue(request)

// Unique work — only one sync at a time
WorkManager.getInstance(context)
    .enqueueUniqueWork("sync", ExistingWorkPolicy.REPLACE, request)

// Observe
WorkManager.getInstance(context)
    .getWorkInfoByIdLiveData(request.id)
    .observe(lifecycleOwner) { info ->
        if (info?.state == WorkInfo.State.SUCCEEDED) { /* done */ }
    }

Under the hood

WorkManager is a layer on top of the platform scheduler, not a separate scheduler itself. When you enqueue a request it is written into an internal Room database (the WorkSpec table), which is what gives it durability across process death and reboot. A Greedy/SystemJobScheduler then translates the request into the appropriate framework primitive:

enqueue(request)
   │
   ▼
[Room DB: WorkSpec persisted]   ← survives kill / reboot
   │
   ▼
[WorkManager scheduler picks an implementation]
   ├── API 23+  → JobScheduler (SystemJobScheduler)
   └── API <23  → AlarmManager + BroadcastReceiver (SystemAlarmScheduler)
   │
   ▼
[Constraints met → JobSchedulerService runs the job → CoroutineWorker.doWork()]

A RescheduleReceiver listens for BOOT_COMPLETED (and similar) so unfinished work is re-registered with the scheduler after a reboot. The worker itself runs on a WorkManager-managed Executor; CoroutineWorker bridges that to a coroutine on Dispatchers.Default.

Periodic Work

🎤 Say it out loud (~30–45s): "Periodic work is for recurring background jobs — a roughly-every-15-minutes sync, say. The key nuance is the 15-minute floor is OS-enforced and the timing is approximate, not exact: the system batches periodic jobs with other apps' work and Doze to save battery, so the interval is a minimum, not a guarantee. If someone needs precise recurring timing they're asking the wrong API — that's a job for an alarm, not periodic work."
val periodicRequest = PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
    .setConstraints(networkConstraint)
    .build()

WorkManager.getInstance(context)
    .enqueueUniquePeriodicWork(
        "periodic-sync",
        ExistingPeriodicWorkPolicy.KEEP,  // or REPLACE, UPDATE
        periodicRequest
    )

The minimum period is 15 minutes, OS-enforced. KEEP means the existing scheduled work is left alone and no new request is enqueued.

Under the hood

A periodic request becomes a recurring JobScheduler job with setPeriodic(), where the system clamps the period to its own minimum (15 minutes) and decides when within each interval to actually run, batching it with other deferred jobs. Because periodic work cannot be chained and its timing is approximate, the framework treats each run as an independent execution; WorkManager re-enqueues the next interval after doWork() returns. The Doze maintenance window and App Standby bucket both influence when the interval's run is permitted to fire, which is why a "15-minute" job can drift well past 15 minutes on an idle, infrequently-used device.

Chained Work

🎤 Say it out loud (~30–45s): "WorkManager lets me express a dependency graph — run these two in parallel, then this one, then notify — and it guarantees ordering and passes output Data from one worker into the next. The thing to call out is failure semantics: if any worker in the chain returns failure, the rest of the chain is cancelled, so chaining is really for steps that only make sense as an all-or-nothing pipeline."
WorkManager.getInstance(context)
    .beginWith(listOf(cleanupRequest, prepareRequest))  // parallel first step
    .then(uploadRequest)                                // sequential second step
    .then(notifyRequest)                                // sequential third step
    .enqueue()

Output of one worker flows to the input of the next via Data. If any worker returns Result.failure(), the chain stops unless subsequent workers are configured to handle failure input.

Under the hood

A chain is stored as a dependency graph in the same Room database, with each WorkSpec recording its prerequisites in a Dependency table. WorkManager only schedules a worker with the underlying JobScheduler once all of its prerequisites have reached SUCCEEDED; the output Data of a prerequisite is persisted and merged (via an InputMerger, by default OverwritingInputMerger) into the next worker's input. Because the graph lives in the database, a chain survives process death mid-way — already-completed nodes stay completed and only the remaining nodes are rescheduled. A failure() marks its dependents FAILED so they are never scheduled.

Expedited Work

🎤 Say it out loud (~30–45s): "Expedited work is for tasks that need to start almost immediately but still want WorkManager's durability — think kicking off a critical upload right after a user action. On Android 12+ it runs against an expedited job quota; below that it falls back to a foreground service. The nuance is the quota is finite, so I have to provide an OutOfQuotaPolicy saying what happens when the quota is exhausted — either drop to a normal request or fail."

For time-sensitive tasks that must start immediately but still need to survive process death:

val expeditedRequest = OneTimeWorkRequestBuilder<CriticalWorker>()
    .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
    .build()

On Android 12 and above, the worker runs with expedited job quota. On older versions it falls back to running as a foreground service.

Under the hood

The mechanism differs by API level. On API 31+, expedited work maps to a JobScheduler expedited job (setExpedited(true)), which the system runs promptly but only while the app has remaining expedited-job quota — quota that replenishes based on the app's standby bucket. When quota is exhausted, the OutOfQuotaPolicy decides between demoting to an ordinary deferrable request or failing outright. On older APIs WorkManager implements the same intent by promoting the worker into a short-lived foreground service (calling setForeground/getForegroundInfo), which is why an expedited worker generally must supply foreground info to avoid an exception.

Cancellation

🎤 Say it out loud (~30–45s): "I can cancel work by id, by tag, or by unique name. With CoroutineWorker cancellation is cooperative — WorkManager cancels the worker's coroutine scope, so the work unwinds through CancellationException at the next suspension point. The thing to remember is that blocking, non-cooperative code won't stop on its own; you have to check isStopped or use suspending calls for cancellation to actually take effect."
WorkManager.getInstance(context).cancelWorkById(request.id)
WorkManager.getInstance(context).cancelAllWorkByTag("sync")
WorkManager.getInstance(context).cancelUniqueWork("periodic-sync")

Workers receive cancellation through CoroutineWorker's coroutine scope — the scope is cancelled, so all cooperative suspension points exit via CancellationException.

Under the hood

Cancellation flips the WorkSpec state to CANCELLED in the Room database and tells the underlying scheduler to drop the corresponding JobScheduler job (or AlarmManager alarm). For work already executing, WorkManager calls ListenableWorker.onStopped() and, for a CoroutineWorker, cancels the Job backing its CoroutineScope. That is why cancellation is cooperative: a coroutine only actually stops at a suspension point or an explicit isStopped/isActive check — tight CPU loops that never suspend keep running until they finish or the process is killed.

JobScheduler

🎤 Say it out loud (~30–45s): "JobScheduler is the API 21+ framework scheduler that WorkManager sits on top of for API 23 and above. It registers jobs with the system server so they survive process death, and the system batches them with other apps' jobs to save battery. I'd rarely touch it directly — only for platform features WorkManager doesn't expose — and one classic gotcha is that onStartJob runs on the main thread, so I still have to move real work off it myself."

JobScheduler is the Android framework API that WorkManager is built on. You would interact with it directly only when you need platform-specific features not exposed by WorkManager, which is rare. Jobs survive process death because they are registered with the system server.

val jobScheduler = getSystemService(JobScheduler::class.java)
val jobInfo = JobInfo.Builder(JOB_ID, ComponentName(this, SyncJobService::class.java))
    .setRequiredNetworkType(JobInfo.NETWORK_TYPE_ANY)
    .setPersisted(true)   // survives reboot
    .build()
jobScheduler.schedule(jobInfo)

One gotcha: JobService.onStartJob() runs on the main thread, so you must offload work to a background thread manually.

Under the hood

JobScheduler.schedule() is a binder call into the JobSchedulerService running in system_server, which owns all jobs across every app. That service stores JobInfo (persisting it to disk when setPersisted(true), gated on the RECEIVE_BOOT_COMPLETED permission), evaluates each job's constraints — network type, charging, idle, content URIs — and only when they are all satisfied does it bind to your JobService and invoke onStartJob() on your app's main thread. Your service signals completion with jobFinished(), releasing the wakelock the system held for the run. The system deliberately batches eligible jobs together and aligns them with Doze maintenance windows to amortize the cost of waking the device.

Foreground Services

🎤 Say it out loud (~30–45s): "A foreground service is for long-running work the user is actively aware of — music playback, navigation, an in-progress upload — and it must post a persistent notification. It keeps the process at foreground priority so it isn't killed. The modern nuance is the platform tightened this a lot: from Android 12 you declare a foregroundServiceType, and Android 14 enforces type-specific runtime permissions, so you can't just spin one up for arbitrary deferrable work."

Use a Foreground Service for long-running work that must continue while the app is in the background and where the user must be aware it is running via a persistent notification:

class MusicService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = buildNotification()
        startForeground(NOTIFICATION_ID, notification)
        playMusic()
        return START_STICKY   // restart if killed
    }
}

// Start (Android 9+)
ContextCompat.startForegroundService(context, Intent(context, MusicService::class.java))

Android 12 and above require declaring foregroundServiceType in the manifest — for example mediaPlayback, location, or camera. Android 14 enforces type-specific runtime permissions on top of that.

For the WorkManager versus Foreground Service decision: use WorkManager when the work is deferrable and the result can be delivered later or is network-triggered. Use a Foreground Service when the work is immediate and ongoing and the user is actively engaged — music playback, navigation, or an upload in progress.

Under the hood

startForegroundService() tells ActivityManagerService to start the service with a grace window (about 5 seconds) within which you must call startForeground() and post a notification, or the system throws ForegroundServiceDidNotStartInTimeException. While in the foreground state the process is given foreground (or "perceptible") OOM-adjustment priority, so the low-memory killer ranks it near the top and is unlikely to reap it. The mandatory notification is the OS's way of keeping background work user-visible. From API 26, background execution limits forbid starting a background service from the background at all, which is exactly why startForegroundService plus a prompt startForeground() call became the required path; API 31 added the foregroundServiceType declaration and API 34 ties each type to its own runtime permission and allowed start-reasons.

AlarmManager

🎤 Say it out loud (~30–45s): "AlarmManager is the API for work that must fire at a precise wall-clock or elapsed time, even through Doze — that's setExactAndAllowWhileIdle or setAlarmClock. It is deliberately not for deferrable work because the system can't batch exact alarms, so they cost battery. The nuance interviewers like is the permission story: Android 12 introduced SCHEDULE_EXACT_ALARM and Android 13 made it user-grantable, so exact alarms are now something you justify, not sprinkle around."

Use AlarmManager for work that must run at a precise time, even if the device is in Doze mode — use setExactAndAllowWhileIdle or setAlarmClock. It is not for deferrable work because the system cannot batch it.

val alarmManager = getSystemService(AlarmManager::class.java)
val pendingIntent = PendingIntent.getBroadcast(
    context, requestCode, Intent(context, AlarmReceiver::class.java),
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)
alarmManager.setExactAndAllowWhileIdle(
    AlarmManager.ELAPSED_REALTIME_WAKEUP,
    SystemClock.elapsedRealtime() + delayMs,
    pendingIntent
)

Android 12 and above require the SCHEDULE_EXACT_ALARM permission. Android 13 changes it to a user-grantable permission. Use exact alarms sparingly — they drain battery.

Under the hood

Alarms are held by the AlarmManagerService in system_server, which programs the kernel alarm timer (/dev/alarm historically, now timerfd/CLOCK_BOOTTIME_ALARM) so a *_WAKEUP alarm can wake the device from sleep. Inexact alarms are coalesced into batches and aligned with maintenance windows so the SoC wakes once for many alarms; exact alarms break that batching, which is the battery cost. During Doze the service suppresses ordinary alarms entirely and only releases setExactAndAllowWhileIdle (rate-limited to roughly once every 9 minutes per app) and setAlarmClock alarms. When an alarm fires the system holds a brief wakelock while it dispatches the PendingIntent — typically a broadcast — to your app.

BroadcastReceiver Limitations

🎤 Say it out loud (~30–45s): "Since Android 8, manifest-declared receivers no longer get most implicit system broadcasts — that was the background-execution-limits crackdown — so for those you need a runtime-registered receiver while the app is alive. And onReceive runs on the main thread with about a 10-second budget before an ANR, so I never do real work there; I just enqueue a WorkManager job. JobIntentService, the old bridge for this, is deprecated."

Statically registered receivers in the manifest are subject to background execution limits from Android 8 onward. Most implicit broadcasts are no longer delivered to them. Runtime-registered receivers do receive broadcasts while the app is running.

onReceive() runs on the main thread and must complete in roughly 10 seconds or an ANR will fire. Never start long-running work directly from onReceive — instead kick off a WorkManager job. JobIntentService is deprecated; WorkManager is the correct replacement.

Under the hood

Broadcasts are dispatched by ActivityManagerService, which delivers each one to your receiver's onReceive() on the main thread and holds a wakelock for the duration. If the call doesn't return within roughly 10 seconds the system raises a broadcast-timeout ANR, so any real work must be handed off — goAsync() buys a little more time, but enqueuing a WorkManager job is the durable answer. The Android 8 background-execution limits changed delivery itself: the AMS no longer matches implicit broadcasts against manifest-registered receivers (with a short exemption list), because waking dozens of background processes for every system event was a major battery and memory drain. Explicit broadcasts and runtime-registered receivers are unaffected.

Doze Mode and App Standby

🎤 Say it out loud (~30–45s): "Doze and App Standby are the two big battery-saving regimes. Doze kicks in when the device is unplugged, still, and screen-off — it suspends network and wakelocks and batches deferred jobs and alarms into periodic maintenance windows, with only setExactAndAllowWhileIdle and alarm-clock alarms allowed through. App Standby instead buckets apps by how often you use them and throttles a rarely-used app's jobs harder. The takeaway is WorkManager respects all of this automatically, which is exactly why you don't fight it with raw threads."

Doze mode activates when the device is off the charger, stationary, and screen off for a period. Android then restricts network access, JobScheduler jobs, alarms (except setAlarmClock), and sync adapters. Only setExactAndAllowWhileIdle alarms fire during Doze.

App Standby Buckets bucket apps by usage frequency — Active, Working Set, Frequent, Rare, Restricted. Apps in the Rare bucket may have their jobs deferred significantly. WorkManager respects these buckets automatically.

Under the hood

Doze is driven by the DeviceIdleController in system_server, which uses signals like motion sensors, charging state, and screen state to step the device through light- and deep-idle states. In deep Doze it defers JobScheduler jobs and inexact alarms, holds network access, and ignores wakelocks, then periodically opens a maintenance window during which all the deferred work is allowed to run in one batch before the device drops back to idle — windows that grow less frequent the longer the device stays idle.

unplugged + stationary + screen off
        │
        ▼
   [idle] ──► [maintenance window: deferred jobs/alarms/syncs run] ──► [idle] ──► ...
                  (windows get rarer the longer idle lasts)

Allowed through idle: setExactAndAllowWhileIdle (rate-limited), setAlarmClock,
high-priority FCM messages.

App Standby is tracked separately: the system assigns each app a bucket (Active → Working Set → Frequent → Rare → Restricted) from usage patterns and applies progressively tighter quotas on jobs, alarms, and expedited-job allowance. WorkManager reads through to JobScheduler, so it inherits both the Doze deferral and the bucket quotas without extra code.

Retry and Backoff

🎤 Say it out loud (~30–45s): "When a worker returns Result.retry(), WorkManager reschedules it according to the backoff policy I set — exponential or linear, with a 10-second minimum. Exponential doubles each attempt and both are capped at about 5 hours. The nuance is the retry isn't immediate or guaranteed-on-time: the reschedule still goes through the system scheduler, so constraints, Doze, and standby buckets all gate when the next attempt actually runs."

Returning Result.retry() from a Worker schedules a retry using the configured backoff policy:

OneTimeWorkRequestBuilder<MyWorker>()
    .setBackoffCriteria(
        BackoffPolicy.EXPONENTIAL,   // or LINEAR
        WorkRequest.MIN_BACKOFF_MILLIS,  // minimum 10 seconds
        TimeUnit.MILLISECONDS
    )
    .build()

BackoffPolicy.EXPONENTIAL doubles the delay each attempt, capped at 5 hours. LINEAR adds a fixed increment each time.

Under the hood

Each retry increments the persisted runAttemptCount on the WorkSpec, and WorkManager computes the next delay from the backoff policy and that count — EXPONENTIAL roughly as initialDelay * 2^(attempt-1), LINEAR as initialDelay * attempt, both clamped between the 10-second minimum and the 5-hour maximum. The recomputed WorkSpec is re-handed to the underlying JobScheduler with that minimum-latency, so the retry is still a normal scheduled job: its constraints must be satisfied and Doze or a low standby bucket can push the actual execution later than the nominal backoff delay. Because the attempt count lives in the database, the backoff schedule survives process death.

WorkManager vs Coroutine Decision

🎤 Say it out loud (~30–45s): "My one-line rule: if the work must survive process death or reboot, it's WorkManager; if it can safely die with the process, a coroutine in the right scope is simpler and cheaper. A viewModelScope network call for the current screen is a coroutine. An upload that has to retry across network drops, or a periodic background sync, is WorkManager. The mistake to avoid is reaching for WorkManager for in-screen async work — that adds a persisted, system-scheduled job where a coroutine would do."

The core decision rule is: if the work must survive process death or a device reboot, use WorkManager. If it can die with the process, a coroutine in the appropriate scope is simpler.

Criterion Coroutine WorkManager
Must survive process death?NoYes
Must survive device reboot?NoYes (with setPersisted equivalent)
Can be deferred by system?NoYes
Tied to user-visible work?NoNo (unless expedited)
One-shot network request in ViewModelYesNo
Upload file, retry if network dropsNoYes
Sync data in background periodicallyNoYes

Under the hood

The difference is entirely about where the work's state lives. A coroutine's continuation lives only in process memory tied to a CoroutineScope (like viewModelScope), so when the process is killed the continuation and any in-flight work vanish — there is nothing on disk to resume. WorkManager writes a WorkSpec to its Room database and registers a JobScheduler job with system_server, so the state outlives the process and a BOOT_COMPLETED receiver can reschedule it after a reboot. That durability has a cost — a database write, a binder call to the scheduler, and the worker running on a managed executor rather than your scope — which is why a coroutine is the right, lighter tool whenever the work doesn't need to survive the process.

Debugging Background Work

🎤 Say it out loud (~30–45s): "For debugging I lean on a few adb tools: dumpsys jobscheduler to see the actual jobs and why they're pending, and dumpsys deviceidle force-idle plus am set-standby-bucket to simulate Doze and a rare bucket so I can reproduce deferral instead of waiting for it. From code I observe WorkInfo via the LiveData/Flow APIs to watch state transitions. The point I'd make is that background work bugs are usually about when the system lets it run, so reproducing Doze and buckets locally is the key skill."

There are four useful adb commands:

# Inspect WorkManager database
adb shell content query --uri content://androidx.work.diagnostics.WorkDiagnosticsProvider

# Dump job scheduler state
adb shell dumpsys jobscheduler

# Trigger Doze mode manually
adb shell dumpsys deviceidle force-idle

# Trigger app standby bucket
adb shell am set-standby-bucket <package> rare

WorkManager also exposes a built-in diagnostic tool accessible at runtime:

WorkManager.getInstance(context).getWorkInfosByTagLiveData("sync")
// or observe all work:
WorkManager.getInstance(context).getWorkInfosLiveData(WorkQuery.fromStates(WorkInfo.State.RUNNING))

Under the hood

These commands all read or poke system_server state. dumpsys jobscheduler prints the JobSchedulerService's live registry — every app's jobs, their unsatisfied constraints, quota, and last-run reasons — which is the ground truth for why a WorkManager job hasn't run yet. dumpsys deviceidle force-idle drives the DeviceIdleController straight into deep Doze so you can observe deferral immediately, and am set-standby-bucket overrides the UsageStatsService bucket assignment to test throttling. The WorkDiagnosticsProvider and the WorkInfo observation APIs read WorkManager's own Room database, so they reflect the persisted WorkSpec state — state, attempt count, output Data — rather than the framework scheduler's view.

Quick-Reference: Interview Cheat Sheet

Race Condition

Two threads read-modify-write a shared variable without synchronization, so one update is lost.

Thread-Safe

A class is thread-safe if its invariants hold under concurrent access without external synchronization by the caller.

Intrinsic Lock

Every Java object has one. synchronized on that object acquires it and provides both mutual exclusion and visibility.

Deadlock Prevention

Lock ordering: always acquire multiple locks in the same canonical order across all threads.

volatile vs AtomicInteger

volatile gives visibility only — count++ is still a race. AtomicInteger.incrementAndGet() is a single CAS, so it is atomic and visible.

wait() vs sleep()

wait() releases the monitor and parks the thread in the wait set. sleep() does not release any lock.

Why Not GlobalScope?

It is not bound to any lifecycle, so coroutines survive ViewModel and Activity destruction, causing leaks and unexpected behavior.

Structured Concurrency

A parent scope cannot complete until all children complete. Cancellation and exceptions propagate through the parent-child hierarchy automatically.

Job vs SupervisorJob

With a Job, one child failing cancels all siblings. With a SupervisorJob, each child is independent.

StateFlow vs SharedFlow

StateFlow always has a current value, replays it to new collectors, and has distinctUntilChanged built in — use it for state. SharedFlow has configurable replay and no built-in dedup — use it for events and broadcasts.

repeatOnLifecycle vs launchWhenStarted

launchWhenStarted is deprecated: it suspends collection but the coroutine stays alive, leaking resources. repeatOnLifecycle(STARTED) completely cancels and restarts the inner block, actually freeing resources when the UI goes to background.

WorkManager vs Coroutine

If the work must survive process death or device reboot, use WorkManager. Otherwise, a coroutine in the appropriate scope is simpler.

WorkManager vs Foreground Service

WorkManager is deferrable, battery-optimized, and system-scheduled. A Foreground Service is for immediate, ongoing, user-visible work that requires a persistent notification. When you need both persistence and immediacy, use WorkManager's expedited API, which runs as a Foreground Service under the hood on older API levels.
