1. Arrays

Definition

An array is a fixed-size, contiguous block of memory that stores elements of the same type. Each element is addressable directly by its index via pointer arithmetic.

Internal Implementation

Memory is allocated as a single contiguous slab. Given a base address base and element size s, element at index i lives at base + i * s. This is why access is O(1): one multiplication, one memory read.

Index:    0    1    2    3    4
Memory: [42] [17] [99] [ 3] [55]
         ^
         base address (e.g., 0x1000)
         Element[2] = *(0x1000 + 2 * 4) = 0x1008

Big O Summary

Operation Time Complexity Notes
Access by indexO(1)Direct pointer arithmetic
Search (unsorted)O(n)Must scan every element
Search (sorted)O(log n)Binary search
Insert at endO(1)If space exists (fixed-size array)
Insert at middleO(n)Must shift all elements to the right
Delete at middleO(n)Must shift all elements to the left
Delete at endO(1)Just decrement logical size

Space complexity: O(n) — exactly n elements, no overhead per element.

Memory Characteristics

  • Primitive arrays (IntArray, LongArray, BooleanArray): stored as raw JVM primitives — no object header, no boxing. An IntArray(1000) uses exactly 4,000 bytes.
  • Object arrays (Array<Int>, Array<String>): stores references (pointers) to heap objects. Each Int is boxed into a java.lang.Integer object (~16 bytes on most JVMs) plus the reference itself. An Array<Int>(1000) could use 20,000+ bytes.
  • Cache locality: because elements are contiguous, the CPU prefetcher loads neighboring elements into L1/L2 cache automatically. Iterating an array is extremely fast — often the actual bottleneck is memory bandwidth, not instruction count.

Kotlin Specifics

// Primitive array — no boxing, compact memory
val scores: IntArray = IntArray(5) { it * 10 }   // [0, 10, 20, 30, 40]

// Object array — boxed, larger footprint
val names: Array<String> = Array(3) { "item$it" }

// 2D array (array of arrays — NOT a contiguous 2D block)
val matrix: Array<IntArray> = Array(3) { IntArray(3) }
matrix[1][2] = 42

// Iteration — idiomatic Kotlin
for (score in scores) { /* ... */ }
scores.forEachIndexed { index, value -> /* ... */ }

// Binary search on sorted array
val sortedArr = intArrayOf(1, 3, 5, 7, 9)
val idx = sortedArr.binarySearch(5)   // returns 2

When to Use

  • You know the size upfront (fixed collection).
  • Performance-critical numeric computation (avoid boxing).
  • You need O(1) random access and cache-friendly iteration.
  • Backing data structure for other collections (ArrayList uses Object[] internally).

When to Avoid

  • Frequent insertions/deletions in the middle.
  • Unknown or highly variable size.
  • When you need key-value access (use a map instead).

Interview Angles

Why is array access fast?

"Array access is O(1) because the elements live in one contiguous block of memory. So to find any element, the CPU just does a bit of arithmetic — base address plus index times element size — and jumps straight there. There's no traversal and no pointer chasing. And in practice it's even better than O(1) suggests, because the CPU prefetches neighboring elements into cache, so walking an array sequentially is extremely fast."

Why is inserting into an array expensive?

"Inserting in the middle is O(n) because the array has no notion of 'making space' — to open a slot, every element after the insertion point has to physically shift one position to the right. So if I insert at index 0 of an n-element array, all n elements move. Deletion is the mirror image: everything to the right shifts left to close the gap. That's why arrays are great for reads but poor when you're inserting and removing in the middle a lot."

Why are primitive arrays better for memory?

"It comes down to boxing. On the JVM, anything that isn't a primitive is a heap object with a 12-to-16-byte header plus padding. So an Array<Int> doesn't store raw ints — it stores references to boxed Integer objects, which is roughly 24 bytes per element once you count the object and the reference. An IntArray stores the raw 4-byte ints with zero overhead. At 100,000 elements that's about 2.3 MB versus 0.4 MB — and on top of the size difference, all those tiny boxed objects create GC pressure. On Android that matters a lot, because GC pauses translate directly into dropped frames, so for numeric data I always reach for the primitive array."

2. ArrayList / MutableList

Definition

An ArrayList is basically a dynamic array — it behaves like an array but grows itself automatically when it runs out of room. In Kotlin, MutableList is typically backed by Java's ArrayList, which in turn is backed by an Object[].

Internal Implementation

capacity = 8
size     = 5
backing array: [A][B][C][D][E][ ][ ][ ]
                0  1  2  3  4  5  6  7

When you add(F) and size == capacity, a new array is allocated (typically newCapacity = oldCapacity * 1.5 in Java's ArrayList — actually (oldCapacity * 3) / 2 + 1) and all elements are copied via System.arraycopy. The old array is abandoned for GC.

Growth sequence (Java ArrayList): 10 → 16 → 25 → 38 → 58 → 88 → ...

The amortized cost of append is O(1) because the expensive resize happens rarely enough that, averaged across all appends, each append costs a constant amount. Formal proof: with geometric growth factor k, after n appends the total copy work is at most n * k/(k-1) = O(n), so per-element amortized cost is O(1).

Big O Summary

Operation Time Complexity (Amortized) Notes
Access by indexO(1)Direct array access
Search (unsorted)O(n)Linear scan
Append (add at end)O(1) amortizedOccasional O(n) resize
Insert at middleO(n)Shift + possible resize
Delete at middleO(n)Shift elements left
Delete at endO(1)Just decrement size
contains()O(n)Linear scan

Space: O(n) for elements, but capacity ≥ size so some wasted space.

Kotlin Usage

// Create
val list = mutableListOf("Alice", "Bob", "Charlie")
val listWithCapacity = ArrayList<String>(100)  // pre-size if count is known

// Access
val first = list[0]      // O(1)
val last  = list.last()  // O(1)

// Append
list.add("Dave")         // amortized O(1)

// Insert at specific position — O(n) shift!
list.add(1, "Zara")      // shifts Bob, Charlie, Dave right

// Remove by index — O(n) shift!
list.removeAt(2)

// Remove by value — O(n) scan + O(n) shift
list.remove("Bob")

// Capacity control
(list as ArrayList).ensureCapacity(500)   // avoid repeated resizes
(list as ArrayList).trimToSize()           // release excess capacity

// Read-only view (no copy)
val readOnly: List<String> = list

Size vs Capacity

  • size: number of elements currently stored.
  • capacity: size of the backing array (always ≥ size).
  • If you know you'll add 10,000 elements, construct with ArrayList<T>(10_000) to skip all intermediate resizes.

When to Use

  • Default choice for most ordered, variable-size collections.
  • Frequent random access or append.
  • Infrequent insertions/deletions in the middle.

When to Avoid

  • Frequent middle insertions/deletions (consider Deque or a linked structure).
  • When memory is very tight and you know the size won't change (use a fixed array).

Interview Angles

What happens when ArrayList grows?

"When you call add() and the list is already full — so size equals capacity — the ArrayList does a five-step dance. First it computes a new capacity, which is (oldCapacity * 3) / 2 + 1, so roughly one and a half times bigger. Then it allocates a brand-new Object[] of that size. Then it calls System.arraycopy to copy every existing element over, which is the O(n) part. Then it swaps its internal reference to point at the new array, and finally it adds the new element. The old array becomes unreachable and gets garbage-collected. And this is exactly why, if you know roughly how many elements you'll have, you pass that size into the constructor — you skip all those intermediate copies. That matters a lot in Android scroll adapters or when you're building a big list at startup."

Why is ArrayList usually better than LinkedList in real apps?

"For almost any real app I'd pick ArrayList over LinkedList, and there are four reasons. First, cache locality — ArrayList's elements sit contiguously in memory so the CPU prefetches them, whereas LinkedList nodes are scattered across the heap and every hop is potentially a cache miss. In practice that makes iterating a LinkedList 5 to 10 times slower for the same number of elements. Second, memory overhead — every LinkedList node carries two extra pointers, prev and next, plus an object header, which is about 32 extra bytes per element on a 64-bit JVM, while ArrayList adds zero per-element overhead. Third, random access is O(1) on ArrayList but O(n) on LinkedList. And fourth, the one thing LinkedList is supposed to be good at — middle inserts — barely comes up in practice, because that's only fast when you already hold a reference to the node. In real code you search first and then modify, so the search itself is O(n) regardless."

Difference between size and capacity.

"Size is the logical count — how many elements are actually in the list. Capacity is the physical size of the backing array, and it's always at least as big as size. They drift apart because ArrayList never shrinks itself automatically. So if I add a thousand elements and then remove 990, my size is 10 but the capacity is still north of a thousand — that memory is just sitting there. If the content is stable and I want it back, I call trimToSize() to reclaim it."

3. LinkedList

Definition

A LinkedList is a node-based sequence — instead of one contiguous block, every element lives in its own node that holds a value plus a reference to the next node, and in a doubly linked list, a reference back to the previous one too. Java's LinkedList, which Kotlin inherits, is doubly linked and also implements Deque.

Internal Implementation

Head --> [prev=null|42|next] <--> [prev|17|next] <--> [prev|99|next=null] <-- Tail

Each node:

class Node<T>(
    var value: T,
    var prev: Node<T>? = null,
    var next: Node<T>? = null
)

Insert/delete with a node reference: update two pointers = O(1). But finding the node at index i requires traversal from head (or tail if i > size/2) = O(n).

Big O Summary

Operation Time Notes
Access by indexO(n)Traverse from head or tail
Search by valueO(n)Linear scan
Insert at head/tailO(1)Update head/tail pointer + adjacent node
Insert at middleO(n)O(n) to find position, O(1) to link
Delete at head/tailO(1)Update pointer
Delete at middleO(n)O(n) to find node, O(1) to unlink
Insert given node refO(1)When iterating and inserting at ListIterator

Space: O(n) elements + O(n) pointer overhead. Each node ≈ 32–48 bytes on 64-bit JVM vs ~4–8 bytes for an array element reference.

Kotlin Usage

val ll = LinkedList<String>()
ll.addFirst("A")   // O(1)
ll.addLast("B")    // O(1)
ll.add(1, "Mid")   // O(n) — traverses to find position

// Efficient iteration with mid-insertion via ListIterator
val iter = ll.listIterator()
while (iter.hasNext()) {
    val v = iter.next()
    if (v == "B") iter.add("B2")  // O(1) — insert after current
}

// As a stack/deque
ll.push("X")   // addFirst
ll.pop()        // removeFirst

Memory Characteristics

  • No wasted capacity (no pre-allocated slots).
  • But per-node overhead is large: object header (12 bytes) + prev pointer (8 bytes) + next pointer (8 bytes) + value reference (8 bytes) = 36 bytes minimum, padded to 48 bytes. Compare to ArrayList's 8 bytes per reference slot.
  • Nodes are scattered across heap → high GC pressure, poor CPU cache utilization.

When to Use

  • You need O(1) insert/delete at both ends (use ArrayDeque instead — it's faster).
  • You're already holding a ListIterator and need to insert/remove during traversal.
  • Rarely: implementing a true LRU where you relink nodes.

When to Avoid

  • Almost always in Android apps. The combination of cache-unfriendly access patterns, high memory overhead, and O(n) random access makes it the wrong choice in nearly every scenario.

Interview Angles

Why is LinkedList rarely the best choice in Android apps?

"In practice I almost never reach for LinkedList on Android, and there are three reasons. First, memory — every node is a separate heap object with two extra pointers, so a list of 10,000 items is 10,000 little objects the garbage collector has to track. On Android that GC pressure shows up as dropped frames. Second, cache locality — array elements sit next to each other in memory so the CPU prefetches them, but linked-list nodes are scattered, so every hop is a potential cache miss. And third, random access is O(n) instead of O(1). So for almost any real use case, ArrayList or ArrayDeque wins."

Dimension ArrayList LinkedList
Backing structureDynamic arrayDoubly-linked nodes
Random accessO(1)O(n)
AppendO(1) amortizedO(1)
PrependO(n)O(1)

Memory per element~8 bytes (reference)~48 bytes (node object)

Implements Deque?NoYes

4. Stack

Definition

A stack is a Last-In, First-Out structure — whatever you pushed in last is the first thing you pop back out. The classic mental model is a stack of plates: you add to the top and you take from the top.

Internal Implementation

Can be backed by either an array (ArrayDeque is the modern choice) or a linked list. Java's legacy Stack class extends Vector (synchronized array) — avoid it. Prefer ArrayDeque as a stack in Kotlin.

push(A) push(B) push(C) → stack: [A, B, C]   (C is top)
pop()   → returns C,   stack: [A, B]
peek()  → returns B,   stack: [A, B]  (no removal)

Big O Summary

Operation Time Notes
pushO(1)Add to top
popO(1)Remove from top
peekO(1)Read top without removing
searchO(n)Linear scan from top
isEmptyO(1)Check size == 0

Space: O(n).

Kotlin Usage

// Modern: use ArrayDeque
val stack = ArrayDeque<String>()
stack.addLast("A")     // push
stack.addLast("B")
stack.addLast("C")

val top = stack.last()           // peek — O(1)
val popped = stack.removeLast()  // pop  — O(1)

// Avoid legacy java.util.Stack — synchronized overhead, wrong inheritance
// val legacyStack = java.util.Stack<String>()  // Don't use

Common Algorithmic Uses

  • Undo stack: Each action pushes a reversible operation; undo pops and reverses it.
  • Android back stack: Each Activity/Fragment transition pushes a back state.
  • Parentheses/bracket validation.
  • DFS (iterative): Push neighbors, pop to visit.
  • Expression evaluation (Shunting-yard algorithm).
  • Monotonic stack for next-greater-element, histogram, skyline problems.

Classic Problems

Valid Parentheses

fun isValid(s: String): Boolean {
    val stack = ArrayDeque<Char>()
    val pairs = mapOf(')' to '(', ']' to '[', '}' to '{')
    for (ch in s) {
        when {
            ch in "([{" -> stack.addLast(ch)
            ch in ")]}" -> {
                if (stack.isEmpty() || stack.last() != pairs[ch]) return false
                stack.removeLast()
            }
        }
    }
    return stack.isEmpty()
}

Min Stack (O(1) getMin)

class MinStack {
    private val stack = ArrayDeque<Int>()
    private val minStack = ArrayDeque<Int>()

    fun push(val_: Int) {
        stack.addLast(val_)
        // Push new min (or same min if val_ is larger)
        minStack.addLast(minOf(val_, minStack.lastOrNull() ?: val_))
    }

    fun pop() {
        stack.removeLast()
        minStack.removeLast()
    }

    fun top(): Int = stack.last()
    fun getMin(): Int = minStack.last()  // O(1) always
}

Interview Angles

How does Android back stack resemble a stack?

"The Activity back stack is literally a LIFO stack that the Android framework manages for you — it lives in the TaskRecord. When you call startActivity(), the new Activity gets pushed onto the task stack. When the user hits Back or you call finish(), the top Activity is popped and the one underneath resumes. The FragmentManager back stack works the exact same way — addToBackStack() pushes a BackStackRecord, and pressing Back pops it and reverses the transaction. So it maps cleanly onto a stack: you push when you navigate forward and pop when you go back. And the NavController in Jetpack Navigation wraps this same idea behind a typed navigation graph, but underneath it's still a stack of destinations."

5. Queue

Definition

A queue is a First-In, First-Out structure — the first element you put in is the first one to come out. The everyday analogy is a line at a ticket counter: you join at the back and you're served from the front.

Internal Implementation

Best backed by ArrayDeque (circular buffer implementation) for O(1) at both ends. A singly-linked list also gives O(1) enqueue/dequeue but with higher constant factors and GC overhead.

enqueue: A → B → C → D   (D entered last)
dequeue: A ← (A leaves first)

Big O Summary

Operation Time Notes
offer / enqueueO(1)Add to tail
poll / dequeueO(1)Remove from head
peekO(1)Read head without removing
searchO(n)Not a primary use case
isEmptyO(1)

Space: O(n).

Kotlin Usage

// ArrayDeque as a Queue (preferred)
val queue = ArrayDeque<String>()
queue.addLast("Task1")   // enqueue
queue.addLast("Task2")
queue.addLast("Task3")

val next = queue.first()         // peek — O(1)
val processed = queue.removeFirst()  // dequeue — O(1)

// java.util.LinkedList also implements Queue
val linkedQueue: Queue<String> = LinkedList()
linkedQueue.offer("Task1")   // enqueue (returns false if capacity-bounded)
linkedQueue.poll()            // dequeue (returns null if empty)
linkedQueue.peek()            // peek (returns null if empty)

Common Uses

  • BFS traversal: Enqueue root, dequeue-and-process each node, enqueue its children.

  • Producer-consumer: One thread produces, another consumes; queue decouples them.
  • Android MessageQueue: Looper drains Message objects in order.

BFS Example

fun bfs(graph: Map<Int, List<Int>>, start: Int): List<Int> {
    val visited = mutableSetOf(start)
    val queue = ArrayDeque<Int>()
    val order = mutableListOf<Int>()
    queue.addLast(start)
    while (queue.isNotEmpty()) {
        val node = queue.removeFirst()
        order.add(node)
        for (neighbor in graph[node].orEmpty()) {
            if (visited.add(neighbor)) {   // add() returns true if newly inserted
                queue.addLast(neighbor)
            }
        }
    }
    return order
}

How does Android MessageQueue work conceptually?

"The interesting thing is that MessageQueue isn't actually a pure FIFO — it's really a priority queue ordered by time, because every Message carries a when timestamp. 6. Deque

Definition

A deque — short for double-ended queue, and pronounced "deck" — lets you insert and remove from both the front and the back in O(1). It's the generalization of both a stack and a queue, so you can use one type for either job.

Implement sliding window maximum.

Problem: Given nums and window size k, return the maximum in each window.

fun maxSlidingWindow(nums: IntArray, k: Int): IntArray {
    // Deque stores indices; front is always index of max for current window
    val deque = ArrayDeque<Int>()
    val result = IntArray(nums.size - k + 1)

    for (i in nums.indices) {
        // Remove indices that are out of the current window
        while (deque.isNotEmpty() && deque.first() < i - k + 1) {
            deque.removeFirst()
        }
        // Remove indices whose values are less than nums[i]
        // (they can never be the max while nums[i] is in the window)
        while (deque.isNotEmpty() && nums[deque.last()] < nums[i]) {
            deque.removeLast()
        }
        deque.addLast(i)
        // Start recording results once first window is complete
        if (i >= k - 1) {
            result[i - k + 1] = nums[deque.first()]
        }
    }
    return result
}
// Time: O(n) — each element is added and removed at most once
// Space: O(k) — deque holds at most k indices

Why prefer ArrayDeque over legacy Stack?

"There are basically two problems with the old java.util.Stack. The first is that it extends Vector, which is just a synchronized ArrayList, so every single push, pop, and peek grabs a mutex lock — and that's pure overhead in single-threaded code, which is virtually all UI and algorithmic work. The second is that because it's a Vector, it exposes the whole List API, so nothing stops you from accidentally calling get(i) or add(i, x) and quietly breaking the LIFO contract. ArrayDeque has none of that synchronization overhead, it only exposes the operations you actually want, and it's backed by a cache-friendly circular buffer. So the rule I follow is simple: never use java.util.Stack in new code."

7. HashMap / MutableMap

Definition

A HashMap is a key-value store that gives you O(1) average-case lookup, insertion, and deletion. The trick is that it runs each key through a hash function to figure out exactly where the value lives, so it can jump straight to it instead of searching.

Internal Implementation (Java HashMap, which Kotlin's MutableMap uses)

Buckets: An internal array of "buckets" (initially 16). The bucket index for a key is computed as hash(key) & (capacity - 1).

Hash function: hashCode() is called on the key, then a secondary "perturbation" hash is applied to spread bits more evenly: h ^= (h >>> 16) (Java 8+).

Collision handling — chaining: Multiple keys can map to the same bucket. In Java 8, each bucket starts as a linked list of Entry nodes. When a bucket's chain length exceeds 8 and the table has ≥ 64 slots, the chain is converted to a Red-Black tree (treeifying) — worst-case O(log n) per bucket.

Load factor: Default is 0.75. When size > capacity * loadFactor, the table is resized (doubled) and all entries are rehashed — O(n) cost amortized.

capacity=16, loadFactor=0.75 → resize when size > 12

Bucket 0: [key="Alice", val=1] → [key="Bob", val=2]   (collision)
Bucket 1: [key="Charlie", val=3]
Bucket 2: empty
...

equals() and hashCode() contract:

  • If a.equals(b) then a.hashCode() == b.hashCode() (required by spec).
  • If a.hashCode() == b.hashCode(), a.equals(b) may or may not be true (hash collision is allowed).
  • Violating this contract causes keys to "disappear" — you put("key", v) and then get("key") returns null because the map looks in a different bucket.

Interview Angles

How does HashMap work internally?

"Under the hood a HashMap is an array of buckets. When I put(key, value), there are five steps. First, it calls key.hashCode() and runs it through a secondary spread function to mix the bits. Second, it turns that into a bucket index with hash & (capacity - 1). Third, if that bucket is empty, it just drops a new entry node in. Fourth, if the bucket already has something — that's a collision — it walks the chain or tree comparing keys with equals(); if it finds a match it updates the value, otherwise it appends a new node. And fifth, if adding that entry pushes size past capacity * loadFactor, it rehashes — allocates an array twice as big and redistributes everything. A get is just the read-side of that: hash the key, find the bucket, walk the chain or tree until equals() matches or you hit the end."

What happens if two keys have the same hash?

"That's a collision, and it just means both entries land in the same bucket. The map keeps them as a linked list — or a Red-Black tree if that chain gets long. On lookup, it has to compare each entry's key with equals() to find the right one. With a good hash function every bucket holds exactly one entry, so you stay at O(1). But in the degenerate case where every key hashes to the same bucket, lookup degrades to an O(n) list scan — or O(log n) once the bucket treeifies, which Java 8 added. And that degenerate case isn't just theoretical: an attacker can craft inputs that deliberately force it, which is a hash DoS attack, and the treeification is what mitigates it."

Why must equal objects have equal hash codes?

"It comes down to how lookup works in two stages — HashMap uses hashCode() to find the bucket, then equals() to find the exact entry within it. So imagine two objects that are equal but somehow have different hash codes. They'd land in different buckets. When I call get(), it hashes the key, goes to bucket A, doesn't find it there, and returns null — even though an equal key is sitting over in bucket B. The contract exists to guarantee correctness: equal objects produce the same hash, so they go to the same bucket, the same chain, and the equals() check actually gets a chance to succeed."

What happens if a key is mutated after insertion?

"If the key's hashCode() depends on the field you mutate, then mutating it changes the hash. But the entry is still physically sitting in the bucket for the old hash. So now when I call get(), it computes the new hash, goes to a different bucket, and returns null. The entry is still in the map but it's permanently unreachable — a ghost entry — until you rebuild the map. That's exactly why you always use immutable objects, or at least objects with a stable hash code, as map keys."

9. LinkedHashMap

Definition

A LinkedHashMap is a HashMap with one extra trick — it threads a doubly-linked list through all its entries so they have a predictable order, either insertion order or access order. That means when you iterate, you always get that maintained order back instead of HashMap's arbitrary order.

Internal Implementation

Each entry node in LinkedHashMap extends HashMap.Entry with two additional pointers: before and after. These form a doubly-linked list independent of the bucket chains.

HashMap buckets: [bucket0] → Entry("C") → Entry("A") (same hash bucket)
                 [bucket1] → Entry("B")

LinkedList order (insertion): "A" ↔ "B" ↔ "C"   (A was added first)

Access order (enabled by constructor flag): When you get() or put() an existing key, that entry is moved to the tail of the linked list. This is the basis for LRU caching.

Big O Summary

Same as HashMap for all operations. Iteration is O(n) and ordered (unlike HashMap's arbitrary order).

Space overhead vs HashMap: 2 extra pointers per entry (~16 bytes per entry). Practically negligible.

Kotlin Usage

// c=3, a=1, b=2  (insertion order preserved)

LRU Cache Using LinkedHashMap

class LruCache<K, V>(private val maxSize: Int) {
    // accessOrder=true: least recently used is at the head
    private val map = object : LinkedHashMap<K, V>(16, 0.75f, true) {
        override fun removeEldestEntry(eldest: Map.Entry<K, V>): Boolean {
            return size > maxSize  // evict when over capacity
        }
    }

    fun get(key: K): V? = map[key]
    fun put(key: K, value: V) { map[key] = value }
    fun size() = map.size
}

// Note: Android's androidx.collection.LruCache is a battle-tested version
// of this pattern — prefer it in production.

Interview Angles

How would you implement an LRU cache?

"There are really two ways I'd answer this. The simple one is to lean on LinkedHashMap: construct it with accessOrder=true and override removeEldestEntry to return true whenever size exceeds the max capacity. Then every get and put automatically moves the touched entry to the tail, so the head is always the least recently used, and eviction is just removing the head of the linked list — O(1). You end up with O(1) get and put and O(n) space, and the code above shows it.

The deeper answer, the one that shows you really understand it, is to build it from scratch with a HashMap plus a doubly linked list. You keep a HashMap<K, Node<K,V>> for O(1) key-to-node lookup, and the doubly linked list gives you O(1) move-to-front and evict-from-the-back. That's literally what LinkedHashMap is doing internally — implementing it by hand just proves you know that."

class LruCacheFromScratch<K, V>(private val capacity: Int) {
    data class Node<K, V>(val key: K, var value: V) {
        var prev: Node<K, V>? = null
        var next: Node<K, V>? = null
    }

    private val map = HashMap<K, Node<K, V>>()
    private val head = Node<K, V>(null as K, null as V)  // dummy
    private val tail = Node<K, V>(null as K, null as V)  // dummy
    init { head.next = tail; tail.prev = head }

    fun get(key: K): V? {
        val node = map[key] ?: return null
        moveToFront(node)
        return node.value
    }

    fun put(key: K, value: V) {
        val existing = map[key]
        if (existing != null) { existing.value = value; moveToFront(existing); return }
        val node = Node(key, value)
        map[key] = node
        insertAfterHead(node)
        if (map.size > capacity) evictLru()
    }

    private fun moveToFront(node: Node<K, V>) { removeNode(node); insertAfterHead(node) }
    private fun removeNode(node: Node<K, V>) { node.prev!!.next = node.next; node.next!!.prev = node.prev }
    private fun insertAfterHead(node: Node<K, V>) {
        node.next = head.next; node.prev = head
        head.next!!.prev = node; head.next = node
    }
    private fun evictLru() {
        val lru = tail.prev!!
        removeNode(lru)
        map.remove(lru.key)
    }
}

Why is LinkedHashMap useful for caching?

"The reason is that accessOrder=true maintains one really useful invariant for free: the least recently accessed entry is always sitting at the head of the internal linked list, with zero manual bookkeeping on my part. Every get and put stays O(1) even including the reorder, because that's just relinking a couple of pointers. And answering 'what should I evict?' is O(1) too — you just read the head. That combination is what makes it the fastest and simplest correct LRU you can get straight out of the JDK."

10. TreeMap / SortedMap

Definition

A TreeMap is a key-value map that keeps its keys sorted at all times — either by their natural ordering through Comparable, or by a custom Comparator you hand it. The trade-off is that every operation is O(log n) rather than O(1), because it's backed by a Red-Black tree, which is a self-balancing binary search tree.

Internal Implementation: Red-Black Tree

A BST where every node is colored Red or Black with invariants that guarantee the tree height stays O(log n):

  1. Root is Black.
  2. No two adjacent Red nodes (Red node's parent must be Black).
  3. Every path from root to null has the same number of Black nodes.

Insertions and deletions may require "rotations" and "recolorings" to restore invariants, but these are O(1) and at most O(log n) in count — keeping all operations O(log n).

11. PriorityQueue / Heap

Definition

A PriorityQueue is a heap — a min-heap or a max-heap — and its whole job is to give you O(1) access to the smallest or largest element at any moment. It's implemented as a binary heap stored compactly in an array.

Internal Implementation: Binary Heap

A complete binary tree stored as an array:

  • Root at index 0.
  • Node at index i has children at 2i+1 (left) and 2i+2 (right).
  • Node at index i has parent at (i-1)/2.

Min-heap invariant: every parent ≤ both children. Root is always the minimum.

Heap array: [1, 3, 5, 7, 9, 8, 6]
Tree:
        1
       / \
      3   5
     / \ / \
    7  9 8  6

Insert (sift-up): Add at end → swap with parent while parent > child. O(log n). Poll (sift-down): Replace root with last element → swap with smaller child while violating invariant. O(log n). Heapify (build heap from array): O(n) — not O(n log n); bottom-up construction.

Big O Summary

Operation Time Notes
peek (min/max)O(1)Root of heap
poll (remove min/max)O(log n)Sift-down after removal
offer (insert)O(log n)Sift-up
heapifyO(n)Build from array

val maxHeap = PriorityQueue<Int>(compareByDescending { it })
maxHeap.offer(5); maxHeap.offer(1); maxHeap.offer(3)
println(maxHeap.poll())  // 5

// Custom objects — comparator on a field
data class Task(val name: String, val priority: Int)
val taskQueue = PriorityQueue<Task>(compareBy { it.priority })
taskQueue.offer(Task("low", 10)); taskQueue.offer(Task("high", 1))
println(taskQueue.poll().name)  // "high" (priority=1 is smallest)

// Top K frequent elements
fun topKFrequent(nums: IntArray, k: Int): IntArray {
    val freq = mutableMapOf<Int, Int>()
    for (n in nums) freq[n] = freq.getOrDefault(n, 0) + 1

    // Min-heap of size k: keeps the k largest frequencies
    val heap = PriorityQueue<Map.Entry<Int, Int>>(compareBy { it.value })
    for (entry in freq.entries) {
        heap.offer(entry)
        if (heap.size > k) heap.poll()  // evict smallest frequency
    }
    return heap.map { it.key }.toIntArray()
}

fun mergeKSortedLists(lists: Array<IntArray>): IntArray {
    // Min-heap stores (value, listIndex, elementIndex)
    val heap = PriorityQueue<Triple<Int, Int, Int>>(compareBy { it.first })
    val result = mutableListOf<Int>()

    // Seed heap with first element from each list
    for ((i, list) in lists.withIndex()) {
        if (list.isNotEmpty()) heap.offer(Triple(list[0], i, 0))
    }

    while (heap.isNotEmpty()) {
        val (value, listIdx, elemIdx) = heap.poll()
        result.add(value)
        val nextIdx = elemIdx + 1
        if (nextIdx < lists[listIdx].size) {
            heap.offer(Triple(lists[listIdx][nextIdx], listIdx, nextIdx))
        }
    }
    return result.toIntArray()
}
// Time: O(N log K) where N = total elements, K = number of lists
// Space: O(K) for the heap

Difference between heap and binary search tree. See table above. "The distinction I'd lead with is this: a heap gives you O(1) access to the min or max but O(n) to find anything else, whereas a BST gives you O(log n) for basically everything but costs you more complexity. So the rule of thumb is, use a heap when all you care about is the extremes — scheduling, top-k, Dijkstra's — and use a BST when you need general sorted access and range queries."

12. Trie

Definition

A trie is a prefix tree — a tree where each node stands for a single character, so the path from the root down to any node spells out a prefix. Each node holds its children in an array or a map indexed by character, which is what makes prefix lookups so fast.

Internal Implementation

Words: ["app", "apple", "apply", "apt"]

root
 └── 'a'
      └── 'p'
           ├── 'p' [isEnd=true]  ← "app"
           │    ├── 'l'
           │    │    ├── 'e' [isEnd=true]  ← "apple"
           │    │    └── 'y' [isEnd=true]  ← "apply"
           └── 't' [isEnd=true]  ← "apt"

Each node stores:

  • Array (or map) of child pointers — one per possible character.
  • isEndOfWord boolean flag.

For lowercase ASCII: children = arrayOfNulls<TrieNode>(26) — O(1) child lookup by char - 'a'.

Kotlin Implementation

class Trie {
    private class TrieNode {
        val children = arrayOfNulls<TrieNode>(26)
        var isEnd = false
    }

    private val root = TrieNode()

    fun insert(word: String) {
        var node = root
        for (ch in word) {
            val idx = ch - 'a'
            if (node.children[idx] == null) {
                node.children[idx] = TrieNode()
            }
            node = node.children[idx]!!
        }
        node.isEnd = true
    }

    fun search(word: String): Boolean {
        val node = traverse(word) ?: return false
        return node.isEnd
    }

    fun startsWith(prefix: String): Boolean = traverse(prefix) != null

    private fun traverse(prefix: String): TrieNode? {
        var node = root
        for (ch in prefix) {
            node = node.children[ch - 'a'] ?: return null
        }
        return node
    }

    fun getWordsWithPrefix(prefix: String): List<String> {
        val node = traverse(prefix) ?: return emptyList()
        val results = mutableListOf<String>()
        dfs(node, StringBuilder(prefix), results)
        return results
    }

    private fun dfs(node: TrieNode, sb: StringBuilder, results: MutableList<String>) {
        if (node.isEnd) results.add(sb.toString())
        for (i in 0..25) {
            node.children[i]?.let {
                sb.append('a' + i)
                dfs(it, sb, results)
                sb.deleteCharAt(sb.length - 1)
            }
        }
    }
}

  • Autocomplete: Find all words with a given prefix.
  • Spell checker: Dictionary lookup and prefix matching.
  • IP routing tables: Longest prefix match.
  • Word search in a 2D board.
  • Phone number prefix lookup.

13. Graphs

Definition

A graph is just a set of vertices — nodes — connected by edges. The edges can be directed, meaning one-way, or undirected, meaning two-way, and they can be weighted or unweighted, and those choices are what let a graph model almost any kind of relationship.

Graph Representations

Adjacency List (preferred for sparse graphs):

    0 to listOf(1, 2),
    1 to listOf(2, 3),
    2 to listOf(3),
    3 to listOf<Int>()
)
// Space: O(V + E)
// Check edge(u,v): O(degree(u))
// Get neighbors: O(1)

Adjacency Matrix (preferred for dense graphs or when O(1) edge checking is needed):

val n = 4

matrix[0][1] = true  // edge from 0 to 1
// Space: O(V²)
// Check edge(u,v): O(1)
// Get neighbors: O(V)

When to use which:

  • Adjacency list: Most algorithmic problems, sparse graphs, BFS/DFS.
  • Adjacency matrix: Dense graphs, Floyd-Warshall, when O(1) edge lookup is critical.

BFS and DFS

// BFS — explores layer by layer; finds shortest path in unweighted graph
fun bfs(graph: Map<Int, List<Int>>, start: Int): List<Int> {
    val visited = mutableSetOf(start)
    val queue = ArrayDeque<Int>()
    val order = mutableListOf<Int>()
    queue.addLast(start)
    while (queue.isNotEmpty()) {
        val v = queue.removeFirst()
        order.add(v)
        for (neighbor in graph[v].orEmpty()) {
            if (visited.add(neighbor)) queue.addLast(neighbor)
        }
    }
    return order
}

// DFS — iterative (stack-based)
fun dfsIterative(graph: Map<Int, List<Int>>, start: Int): List<Int> {
    val visited = mutableSetOf<Int>()
    val stack = ArrayDeque<Int>()
    val order = mutableListOf<Int>()
    stack.addLast(start)
    while (stack.isNotEmpty()) {
        val v = stack.removeLast()
        if (visited.add(v)) {
            order.add(v)
            for (neighbor in graph[v].orEmpty()) {
                if (neighbor !in visited) stack.addLast(neighbor)
            }
        }
    }
    return order
}

// DFS — recursive
fun dfsRecursive(graph: Map<Int, List<Int>>, v: Int, visited: MutableSet<Int>, order: MutableList<Int>) {
    if (!visited.add(v)) return
    order.add(v)
    for (neighbor in graph[v].orEmpty()) dfsRecursive(graph, neighbor, visited, order)
}

Cycle Detection

// Directed graph cycle detection using DFS with 3-color marking
// WHITE=0 (unvisited), GRAY=1 (in current path), BLACK=2 (fully processed)
fun hasCycle(graph: Map<Int, List<Int>>): Boolean {
    val color = mutableMapOf<Int, Int>()

    fun dfs(v: Int): Boolean {
        color[v] = 1  // GRAY
        for (neighbor in graph[v].orEmpty()) {
            if (color[neighbor] == 1) return true  // back edge → cycle
            if (color[neighbor] == null && dfs(neighbor)) return true
        }
        color[v] = 2  // BLACK
        return false
    }

    return graph.keys.any { color[it] == null && dfs(it) }
}

// Undirected graph cycle detection using Union-Find
class UnionFind(n: Int) {
    private val parent = IntArray(n) { it }
    private val rank   = IntArray(n) { 0 }

    fun find(x: Int): Int {
        if (parent[x] != x) parent[x] = find(parent[x])  // path compression
        return parent[x]
    }

    fun union(x: Int, y: Int): Boolean {
        val px = find(x); val py = find(y)
        if (px == py) return false  // already connected — adding this edge creates a cycle
        if (rank[px] < rank[py]) parent[px] = py
        else if (rank[px] > rank[py]) parent[py] = px
        else { parent[py] = px; rank[px]++ }
        return true
    }
}

Topological Sort

// Kahn's algorithm (BFS-based) — also detects cycles
fun topologicalSort(numNodes: Int, edges: List<Pair<Int, Int>>): List<Int>? {
    val inDegree = IntArray(numNodes)
    val adj = Array(numNodes) { mutableListOf<Int>() }
    for ((u, v) in edges) { adj[u].add(v); inDegree[v]++ }

    val queue = ArrayDeque<Int>()
    for (i in 0 until numNodes) if (inDegree[i] == 0) queue.addLast(i)

    val order = mutableListOf<Int>()
    while (queue.isNotEmpty()) {
        val v = queue.removeFirst()
        order.add(v)
        for (neighbor in adj[v]) {
            if (--inDegree[neighbor] == 0) queue.addLast(neighbor)
        }
    }
    return if (order.size == numNodes) order else null  // null = cycle detected
}

14.1 SparseArray

Definition

SparseArray is Android's answer to HashMap<Int, V>. Instead of a hash table, it keeps two parallel arrays — one of integer keys, one of values — and does lookups by binary search. The big win is that the keys stay as raw ints, so there's no boxing.

Internal Implementation

keys:   [0, 3, 7, 12, 45]      (sorted int[])
values: [A, B, C,  D,  E]      (Object[])
  • get(key): binary search in keys array → O(log n). If found, return values[idx].
  • put(key, value): binary search to find insert position → shift arrays → O(n).
  • Lazy deletion: delete() marks the slot as DELETED (a sentinel) without shifting; garbage-collected on next put or gc() call.

Big O Summary

Operation Time Notes

putO(n)Insert + shift
deleteO(log n)Lazy delete (no shift)
iterationO(n)Sequential array scan

When to Use

  • Mapping integer IDs (view IDs, resource IDs, position indices) to objects.
  • Small-to-medium collections (n < ~1000) where avoiding HashMap boxing overhead matters.
  • Memory-sensitive code: avoids boxing int → Integer.

14.2 LongSparseArray

This is just SparseArray but for Long keys instead of int keys, so it avoids boxing Long into java.lang.Long. You'd use it whenever your keys are timestamps or 64-bit IDs.

14.3 ArrayMap

Definition

ArrayMap is a memory-efficient stand-in for HashMap<K, V>. It also uses two parallel arrays — one holding the key hashes, one holding the key-value pairs — and it's specifically designed for small maps, under roughly 1000 entries, which is the common case on Android.

Internal Implementation

hashes: [hash(C), hash(A), hash(B)]  (sorted int[])
array:  [keyC, valC, keyA, valA, keyB, valB]  (Object[], interleaved)
  • Lookup: binary search on hashes → O(log n). Then linear probe if hash collision.
  • Avoids the 28-byte HashMap.Entry object per entry — only uses the arrays.
  • At small sizes, better cache behavior (contiguous arrays) despite O(log n) vs O(1).

When to Use

  • Small maps (< 100–1000 entries) where memory matters more than raw throughput.
  • Android View system, Bundle extras, configuration maps.
  • When you know the map is small and allocated frequently (e.g., per-frame data).

When NOT to Use

  • Large maps (HashMap wins on throughput at scale due to O(1) vs O(log n)).
  • Hot paths with millions of lookups per second.
val arrayMap = ArrayMap<String, Int>()

arrayMap["level"] = 5

14.4 LruCache

Definition

androidx.collection.LruCache<K, V> is a thread-safe, size-bounded cache that, when it fills up, evicts the Least Recently Used entry to make room. Under the hood it's just a LinkedHashMap with accessOrder=true, which is what makes the eviction order fall out for free.

Big O Summary

All operations O(1): get, put, eviction.

Usage Pattern

// Typical usage: bitmap cache
val maxMemory = Runtime.getRuntime().maxMemory() / 1024  // KB
val cacheSize = (maxMemory / 8).toInt()  // Use 1/8 of available memory

val bitmapCache = object : LruCache<String, Bitmap>(cacheSize) {
    // Tell LruCache the size of each item (in KB)
    override fun sizeOf(key: String, value: Bitmap): Int {
        return value.byteCount / 1024
    }

    // Called when an entry is evicted — release resources
    override fun entryRemoved(evicted: Boolean, key: String, oldValue: Bitmap, newValue: Bitmap?) {
        if (evicted) oldValue.recycle()  // optional, Glide manages this itself
    }
}

// Usage
bitmapCache.put("url_hash", bitmap)
val cached = bitmapCache.get("url_hash")  // null if evicted

Thread safety: LruCache is synchronized. All get() and put() calls acquire an intrinsic lock. Safe from multiple threads but adds overhead in single-threaded contexts.

Interview Angles

Why might Android-specific collections reduce memory overhead?

"There are three mechanisms at play. The first is avoiding boxing — SparseArray and LongSparseArray keep their keys in primitive int[] or long[], whereas a HashMap<Int, V> has to box every Int into a java.lang.Integer, which is about 16 bytes plus an 8-byte reference, so 24 bytes versus SparseArray's 4. Across 10,000 integer keys that's roughly 240KB against 40KB. The second is avoiding Entry objects — a HashMap allocates a HashMap.Entry object per pair, around 28 to 48 bytes, while ArrayMap stores everything in two flat arrays with no per-entry objects at all, so you get lower GC pressure and better cache locality. And the third is a smaller starting footprint — HashMap defaults to a 16-bucket array and wastes slots under the load factor, whereas ArrayMap starts at 4 entries and grows linearly. And the reason all this matters: on memory-constrained Android devices juggling lots of apps, those savings make it less likely the OOM killer comes for your process."

When would you use LruCache?

"I'd reach for LruCache for any in-memory cache where three things are true:

  • The items are expensive to compute or fetch — think bitmap decoding, network responses, database queries.
  • You can't or don't want to cache everything, because unbounded growth eventually means an OOM.
  • And the access pattern is temporal, meaning something you used recently is likely to be needed again soon.

The classic Android example is bitmap loading in a RecyclerView or ListView. Without a cache, every single onBindViewHolder would re-decode the bitmap from disk. With an LruCache, the hot bitmaps stay in memory and the eviction keeps the total cache under whatever limit you set. It's not exotic, either — Glide and Picasso both use LruCache internally."

Why not always replace HashMap with ArrayMap?

"Because the memory win comes at a speed cost — ArrayMap looks up by binary search, which is O(log n), versus HashMap's O(1) average. So once you've got a large collection or you're hammering it with high-throughput lookups, HashMap is simply faster. Google's own docs say ArrayMap is meant for under about 1000 entries, where the memory footprint matters more than raw throughput. If you've got 10,000-plus entries, or you're doing thousands of lookups a second in something like a parser or a scheduler hot loop, HashMap wins by 5 to 10 times on speed. So I think of ArrayMap as a targeted optimization for the common Android case — small maps in activities, adapters, and bundles — not a blanket replacement."

15. Big O Notation

What It Is

Big O notation is how we describe the upper bound on an algorithm's growth rate as the input size n gets large. The point is to capture how time or space scales, while deliberately ignoring constant factors and lower-order terms so we can compare algorithms apples to apples.

Formally: T(n) = O(f(n)) means ∃ constants c, n₀ such that T(n) ≤ c·f(n) for all n ≥ n₀.

15.1 Time Complexity

The number of operations (not seconds) the algorithm performs as a function of input size n.

Why we drop constants: Hardware, compiler optimizations, and JIT make constant factors unreliable. We care about asymptotic scaling. 100n is O(n), not O(100n), because the 100x gap is stable regardless of n.

15.2 Space Complexity

Extra memory the algorithm uses beyond the input itself (auxiliary space). Examples:

  • In-place sort: O(1) auxiliary space.
  • Merge sort: O(n) — needs a temporary array.
  • Recursive DFS: O(V) stack frames.
  • BFS: O(V) queue.

15.3 Best, Average, and Worst Case

Case Notation Meaning
BestΩ(n)Minimum operations on the most favorable input
AverageΘ(n)Expected operations on a random input
WorstO(n)Maximum operations on the most adversarial input

Example — QuickSort:

  • Best case: Θ(n log n) — pivot always splits evenly.
  • Average case: Θ(n log n) — random pivot statistically balanced.
  • Worst case: O(n²) — sorted input with naive pivot selection (always picks smallest/largest).

Why worst case matters: In production, you cannot assume best-case inputs. An API endpoint that processes user data must handle adversarial inputs. For security-sensitive code, worst case = the attack surface.

15.4 Amortized Complexity

Amortized analysis averages the cost of expensive operations over a sequence of operations:

ArrayList.add() example: Most appends cost O(1) (just write to next slot). Occasionally, when capacity is full, a resize costs O(n) (copy all elements). But the resize doubles capacity, so the next resize won't happen for another n appends. Total cost for n appends: O(n) copy work + O(n) write work = O(2n) = O(n). Amortized per append: O(1).

Accounting method intuition: Each O(1) append "deposits" a credit. When the costly resize happens, the accumulated credits pay for it. No individual operation feels expensive in the amortized view.

Other amortized examples:

  • HashMap.put(): amortized O(1) despite occasional O(n) rehash.
  • Splay tree operations: amortized O(log n) per operation.
  • StringBuilder.append(): amortized O(1).

15.5 Recursive Complexity

Use the Master Theorem for recurrences of the form T(n) = a·T(n/b) + f(n):

f(n) = O(n^(logb a - ε))T(n) = Θ(n^logb a)Binary tree traversal
f(n) = Θ(n^logb a)T(n) = Θ(n^logb a · log n)Merge sort

Common examples:

Binary search:     T(n) = T(n/2) + O(1)   → O(log n)
Merge sort:        T(n) = 2T(n/2) + O(n)  → O(n log n)
Binary tree walk:  T(n) = 2T(n/2) + O(1)  → O(n)

Fibonacci naive:   T(n) = T(n-1) + T(n-2) → O(2^n) [exponential!]
Fibonacci memoized:                        → O(n)

Recursion stack space: Each recursive call uses O(1) stack frame space. A recursion of depth d uses O(d) stack space. For DFS on a tree of depth d, stack space is O(d). For a balanced tree, d = O(log n). For a skewed tree, d = O(n) — potential StackOverflowError. Iterative DFS avoids this by using an explicit heap-allocated stack.

15.6 Hidden Constants

Big O hides constant multipliers. O(n) with a constant of 1000 can be slower than O(n log n) with a constant of 1 for all practical input sizes.

Real-world example: Java's Arrays.sort() uses TimSort (O(n log n)) for Object arrays but uses a dual-pivot QuickSort (O(n log n) average but O(n log n) in practice with better constants) for primitives. The choice is driven by benchmarked constants, not just the asymptotic class.

In Android: calling startActivity() is O(1) but has a 50ms+ constant due to process creation, IPC, inflation, measure/layout/draw. Never let algorithmic reasoning alone justify complex navigation strategies.

15.7 Why O(n) Can Beat O(log n) in Practice

Cache locality wins:

  • Modern CPUs load memory in 64-byte cache lines. When accessing an array, neighboring elements load together.
  • A linear scan of a small sorted array (O(n)) may be faster than binary search (O(log n)) because the linear scan accesses memory sequentially — all cache hits — while binary search accesses indices n/2, n/4, n/8... — scattered memory addresses, each potentially a cache miss.

Crossover point: For n ≤ 64 (one cache line), linear scan is almost always faster. For n ≤ 128, often faster. For n ≥ 1000, binary search wins.

Android example: ArrayMap uses binary search (O(log n)) instead of hash lookup (O(1)), yet is faster than HashMap for small maps because the contiguous array fits in cache, while HashMap's scattered Entry objects cause cache misses.

Practical implication: Always benchmark before assuming asymptotic complexity determines real-world speed. Profile with realistic data sizes.

Analyze a piece of code.

"When I'm analyzing code live, I walk through it with a consistent checklist. First, I find the outermost loop, because its bound is the baseline for everything else. Second, for nested loops I multiply their bounds — two loops that each run to n is O(n²). Third, I hunt for hidden inner loops, the sneaky ones like contains(), indexOf(), or string concatenation, because those quietly add a factor of n. Fourth, if there's recursion, I write out the recurrence and apply the Master Theorem or substitution. And fifth, I just recall the complexity of any data structure operations involved — a hash map get is O(1), a TreeMap get is O(log n) — and fold those in."

// Example — what is the complexity?
fun findDuplicates(list: List<Int>): List<Int> {
    val seen = mutableSetOf<Int>()   // HashSet
    val dupes = mutableListOf<Int>()
    for (x in list) {                // O(n)
        if (x in seen) {             // O(1) — HashSet contains
            dupes.add(x)             // O(1) amortized
        } else {
            seen.add(x)              // O(1) amortized
        }
    }
    return dupes
}
// Total: O(n) time, O(n) space

Improve brute force to better complexity.

"The classic example here is Two Sum:"

// Brute force O(n²) — every pair
fun twoSumBrute(nums: IntArray, target: Int): IntArray {
    for (i in nums.indices)
        for (j in i+1 until nums.size)
            if (nums[i] + nums[j] == target) return intArrayOf(i, j)
    return intArrayOf()
}

// Optimized O(n) — HashMap for complement lookup
fun twoSumOptimal(nums: IntArray, target: Int): IntArray {
    val seen = HashMap<Int, Int>()  // value → index
    for ((i, num) in nums.withIndex()) {
        val complement = target - num
        if (complement in seen) return intArrayOf(seen[complement]!!, i)
        seen[num] = i
    }
    return intArrayOf()
}
// Trade-off: O(n) extra space to gain O(n²) → O(n) time

"And there are a handful of patterns I keep in my back pocket for cutting complexity:

  • To go from O(n²) to O(n log n), sort first and then use a two-pointer sweep or binary search.
  • To go from O(n²) all the way down to O(n), replace the inner loop with a HashMap or HashSet so the lookup becomes O(1).
  • To go from O(n) to O(log n), reach for binary search or recursive divide-and-conquer.
  • And to tame an exponential O(2ⁿ) down to O(n²), add memoization — that's top-down dynamic programming."

Explain time vs space trade-off.

"The time-space trade-off is basically that you can usually buy speed with memory, or buy memory savings with slower operations — you rarely get both for free. So the question is always which one you're short on."

Explain why a hash map can improve lookup.

"Without a hash map, asking 'is this value in the collection?' means scanning every element — that's O(n). A hash map gets you to O(1) average, and there are two reasons why. First, the key's hashCode() deterministically maps it straight to a bucket index, so you jump right to the neighborhood instead of searching. And second, once you're in that bucket there are usually only one or two entries to compare with equals(). The classic example is counting word frequencies: the naive approach checks whether each word is already in a list, which is O(n²), but with a hash map you just do freq[word]++, which is O(1) per word and O(n) total. At 100,000 words that's the difference between something like 10¹⁰ operations and 10⁵."

Explain recursion stack space.

"Every function call pushes a stack frame onto the JVM call stack, and on Android that stack is only about 256KB to 512KB. Each frame holds the local variables, the parameters, and the return address — typically 40 to 100 bytes. So the danger with recursion is that if it goes deep enough, you exhaust that stack and get a StackOverflowError."

// Fibonacci recursive — O(n) stack depth → StackOverflowError for large n
fun fib(n: Int): Long = if (n <= 1) n.toLong() else fib(n-1) + fib(n-2)
// Stack depth = n frames. For n = 10,000 → StackOverflowError.

// Iterative — O(1) stack space
fun fibIterative(n: Int): Long {
    if (n <= 1) return n.toLong()
    var a = 0L; var b = 1L
    repeat(n - 1) { val tmp = a + b; a = b; b = tmp }
    return b
}

"So on Android, any time I'm doing DFS over the navigation graph or a large data tree, I think about the maximum depth up front. A file-system DFS, for instance, can blow the stack if the directory nesting is deep. The fix is to convert it to an iterative DFS with an explicit ArrayDeque — that moves the stack onto the heap and eliminates the stack-depth risk entirely."
