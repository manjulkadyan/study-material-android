Data Structures

Explain HashMap internals.

"A HashMap is backed by an array of buckets — 16 by default. When you call put, the key's hashCode() is computed and the bucket index is derived with (n-1) & hash. Collisions are handled with a linked list inside each bucket. The important Java 8 upgrade is that once a bucket's list exceeds 8 entries — that's TREEIFY_THRESHOLD — and the overall array is at least 64 entries wide, the list converts to a red-black tree. That keeps worst-case lookup at O(log n) instead of O(n). The map doubles in size and rehashes everything when it crosses the load factor, which defaults to 0.75. In concurrent contexts you'd reach for ConcurrentHashMap instead, because it stripe-locks individual buckets rather than locking the whole structure."

Key complexities: average O(1) get/put, O(n) worst-case (pre-Java-8 or degenerate hash), O(log n) worst-case Java 8+.

Difference between HashMap and TreeMap.

"The key difference is ordering and performance. A HashMap stores entries in an unordered hash table and gives you O(1) average for get and put. A TreeMap stores entries in a red-black tree sorted by the key's natural order, or a Comparator you supply — so get, put, and remove are O(log n), but when you iterate you always get keys in sorted order. The trade-off is: reach for TreeMap when you need range queries like subMap, headMap, or tailMap, or when sorted iteration matters. Reach for HashMap when you just want raw speed and don't care about order."

Difference between ArrayList and LinkedList.

"An ArrayList is a resizable array, so you get O(1) random access, amortized O(1) append, but O(n) insert or delete in the middle because you have to shift elements. A LinkedList is a doubly-linked list: O(1) insert or delete once you have an iterator at the position, but O(n) to get to that position by index, and it has higher memory overhead because each node carries two pointers plus an object header. In practice, ArrayList wins in almost every Android use case because of CPU cache locality — the elements are contiguous in memory, so the prefetcher loves it. LinkedList is rarely worth it unless you have very frequent arbitrary insertions and deletions and you never need to access elements by index."

Implement LRU Cache.

"The cleanest approach is to combine a LinkedHashMap in access-order mode with a max-size cap. If you need full control — say the interviewer asks you to build it from scratch — you can use a HashMap paired with a doubly-linked list, which gives you the same O(1) guarantees manually."

class LRUCache(private val capacity: Int) {
    private val map = object : LinkedHashMap<Int, Int>(capacity, 0.75f, true) {
        override fun removeEldestEntry(eldest: MutableMap.MutableEntry<Int, Int>?) =
            size > capacity
    }

    fun get(key: Int): Int = map.getOrDefault(key, -1)

    fun put(key: Int, value: Int) {
        map[key] = value
    }
}

"Passing accessOrder = true to LinkedHashMap makes it move the most recently accessed entry to the tail on every get or put. Then overriding removeEldestEntry to return true when size > capacity automatically evicts the head — which is always the least-recently-used entry. All operations are O(1)."

Analyze time complexity of code.

"My framework is to count the loops first — each level of nesting multiplies the complexity. Then I look at recursive calls and set up the recurrence relation. The thing I flag most often is hidden inner loops: calling contains() on a plain List inside another loop is O(n) per call, which makes the whole thing O(n²) without looking like it. I always express the answer in Big-O, and I make sure to clarify whether I mean amortized or worst-case. For Android interviews the patterns that come up most are: two nested loops gives O(n²), sorting gives O(n log n), hash lookups are O(1) average, and tree traversal is O(n)."

Find duplicate elements.

fun findDuplicates(nums: IntArray): List<Int> {
    val seen = HashSet<Int>()
    val dupes = mutableListOf<Int>()
    for (n in nums) if (!seen.add(n)) dupes.add(n)
    return dupes
}
// O(n) time, O(n) space

"If you're allowed to mutate the array and the values are in the range 1 to n, there's a O(1) space trick: negate the value at index abs(val)-1 as you visit each element. If you arrive at an index that's already negative, the value at that index is a duplicate."

Top K frequent items.

"There are two approaches. The standard one is a frequency map combined with a min-heap of size K — you keep evicting the least-frequent element from the heap whenever it grows past K, so only the top K survive. That runs in O(n log k). If you want O(n), you can use bucket sort: build an array of lists indexed by frequency from 0 to n, then read from the high-frequency end until you have K elements."

fun topKFrequent(nums: IntArray, k: Int): IntArray {
    val freq = HashMap<Int, Int>()
    for (n in nums) freq[n] = (freq[n] ?: 0) + 1

    // min-heap keyed by frequency, evict when size > k
    val heap = PriorityQueue<Map.Entry<Int, Int>>(compareBy { it.value })
    for (entry in freq.entries) {
        heap.offer(entry)
        if (heap.size > k) heap.poll()
    }
    return heap.map { it.key }.toIntArray()
}
// O(n log k) time

"The bucket-sort version creates an array of lists indexed by frequency from 0 to n, then iterates in reverse to collect the top K — O(n) time, O(n) space."

Merge intervals.

fun merge(intervals: Array<IntArray>): Array<IntArray> {
    intervals.sortBy { it[0] }
    val result = mutableListOf<IntArray>()
    for (interval in intervals) {
        if (result.isEmpty() || result.last()[1] < interval[0]) {
            result.add(interval)
        } else {
            result.last()[1] = maxOf(result.last()[1], interval[1])
        }
    }
    return result.toTypedArray()
}
// O(n log n) due to sort

"The approach is to sort by start time first, then do a single pass. For each interval, if its start is greater than the last merged interval's end, it doesn't overlap — so you add it as a new interval. Otherwise, you extend the last merged interval's end to the maximum of the two ends. The sort dominates at O(n log n)."

Valid parentheses.

fun isValid(s: String): Boolean {
    val stack = ArrayDeque<Char>()
    val match = mapOf(')' to '(', ']' to '[', '}' to '{')
    for (c in s) {
        if (c in "([{") stack.addLast(c)
        else if (stack.isEmpty() || stack.removeLast() != match[c]) return false
    }
    return stack.isEmpty()
}
// O(n) time, O(n) space

"The idea is: push every opening bracket onto a stack. When you see a closing bracket, pop the top and verify it matches. If the stack is empty when you need to pop, or if it's non-empty when you reach the end, the string is not balanced."

Binary search.

fun binarySearch(arr: IntArray, target: Int): Int {
    var lo = 0; var hi = arr.size - 1
    while (lo <= hi) {
        val mid = lo + (hi - lo) / 2  // avoids overflow vs (lo+hi)/2
        when {
            arr[mid] == target -> return mid
            arr[mid] < target  -> lo = mid + 1
            else               -> hi = mid - 1
        }
    }
    return -1
}
// O(log n)

"One subtlety worth mentioning: I use lo + (hi - lo) / 2 rather than (lo + hi) / 2 to avoid integer overflow when both bounds are large. For variants — finding the first or last occurrence means you keep going after you match instead of returning immediately. For a rotated array, the key insight is that one half is always sorted, so you check which half and decide where to narrow."

BFS / DFS.

// BFS — level order, shortest path in unweighted graph
fun bfs(graph: Map<Int, List<Int>>, start: Int): List<Int> {
    val visited = mutableSetOf(start)
    val queue = ArrayDeque<Int>()
    val order = mutableListOf<Int>()
    queue.addLast(start)
    while (queue.isNotEmpty()) {
        val node = queue.removeFirst()
        order.add(node)
        graph[node]?.forEach { neighbor ->
            if (visited.add(neighbor)) queue.addLast(neighbor)
        }
    }
    return order
}

// DFS — recursive or iterative, path finding, topological sort
fun dfs(graph: Map<Int, List<Int>>, node: Int, visited: MutableSet<Int>, order: MutableList<Int>) {
    if (!visited.add(node)) return
    order.add(node)
    graph[node]?.forEach { dfs(graph, it, visited, order) }
}

"BFS uses a queue and explores level by level, which makes it the right choice for shortest path in an unweighted graph and for level-order problems. DFS uses a stack or recursion and goes deep first — it's better for connectivity checks, path existence, topological sort, and cycle detection."

Detect cycle in graph.

"The approach depends on whether the graph is directed or undirected. For an undirected graph, you run DFS and track the parent node. If you reach a visited node that isn't the parent you came from, there's a cycle. For a directed graph, you need three colour states: WHITE means unvisited, GRAY means currently on the recursion stack, and BLACK means fully processed. If during DFS you encounter a GRAY node, you've found a back edge — that's a cycle."

// Directed cycle detection
fun hasCycle(n: Int, edges: List<Pair<Int,Int>>): Boolean {
    val graph = Array(n) { mutableListOf<Int>() }
    edges.forEach { (u, v) -> graph[u].add(v) }
    val color = IntArray(n) // 0=white,1=gray,2=black

    fun dfs(u: Int): Boolean {
        color[u] = 1
        for (v in graph[u]) {
            if (color[v] == 1) return true   // back edge
            if (color[v] == 0 && dfs(v)) return true
        }
        color[u] = 2
        return false
    }
    return (0 until n).any { color[it] == 0 && dfs(it) }
}

"There's also a Union-Find approach for undirected graphs: if find(u) == find(v) before you call union(u, v), the two nodes are already in the same component, so adding this edge creates a cycle."

Concurrency

What is thread safety?

"A class or operation is thread-safe if it behaves correctly when accessed concurrently from multiple threads, without the caller having to add any extra synchronization themselves. There are three main ways to achieve it: mutual exclusion via synchronized or ReentrantLock, immutability — if the object never changes there's nothing to protect — and lock-free data structures like AtomicInteger or ConcurrentHashMap. The naive approach of making all methods synchronized is the bluntest instrument. It works, but it serializes all access and creates contention under load, so at scale you want to prefer fine-grained locking or lock-free approaches."

What is a race condition?

"A race condition is when the outcome of a computation depends on the non-deterministic ordering of concurrent operations. The classic example is a counter: two threads both read count = 5, both compute 6, both write 6 — so the net result is 6 instead of the correct 7. The fix is to make the read-modify-write sequence atomic, either with an AtomicInteger, a synchronized block, or a Mutex in coroutines."

synchronized vs volatile.

"The critical distinction is that synchronized gives you two guarantees: mutual exclusion — only one thread is in the block at a time — and visibility — changes are flushed to main memory on exit and re-read on entry. volatile gives you visibility only. Reads and writes bypass CPU caches and go straight to main memory, but it does not make compound operations atomic. So volatile is fine for a simple on/off flag, but the moment you have a check-then-act pattern — read the flag, do something, write the flag — you need synchronized or an Atomic* type."

How does a Java monitor work?

"Every Java object has an intrinsic lock called a monitor. When you call synchronized(obj), the calling thread acquires that lock, and any other thread that tries to acquire it blocks until it's released. The monitor also provides condition-based waiting through wait(), notify(), and notifyAll(). When a thread calls wait(), it releases the lock and suspends. When another thread calls notify(), one waiting thread wakes up, re-acquires the lock, and then returns from wait(). This primitive mechanism is the foundation for all the higher-level concurrency utilities in Java."

What causes deadlock?

"Deadlock requires four conditions to be true at the same time — the Coffman conditions. First, mutual exclusion: resources can't be shared. Second, hold-and-wait: a thread holds one lock while waiting for another. Third, no preemption: you can't forcibly take a lock from a thread. Fourth, circular wait: thread A is waiting for something thread B holds, and thread B is waiting for something thread A holds. To prevent deadlock, the most practical approach is to always acquire locks in a consistent global order. You can also use tryLock with a timeout, avoid nested locks altogether, or use higher-level concurrent structures that don't require explicit locking. When detecting a deadlock, thread dumps will show the relevant threads stuck in BLOCKED state with a circular wait chain."

Producer-consumer implementation.

// Using BlockingQueue (Java)
val queue = LinkedBlockingQueue<Int>(10)

val producer = thread {
    var i = 0
    while (true) { queue.put(i++); Thread.sleep(100) }
}
val consumer = thread {
    while (true) { val item = queue.take(); println("Consumed $item") }
}

// Coroutine Channel version
val channel = Channel<Int>(10)
launch { repeat(100) { channel.send(it) } }
launch { for (item in channel) println("Got $item") }

"The BlockingQueue handles backpressure naturally: put blocks when the queue is full, and take blocks when it's empty. On Android the idiomatic equivalent is a coroutine Channel, which integrates with structured concurrency and suspension rather than blocking threads."

Executor vs raw Thread.

"A raw Thread is unmanaged: every creation and teardown is an OS-level operation, there's no pooling, and there's no lifecycle management. An Executor or ExecutorService pools threads, queues tasks, and reuses threads across many work items. Executors.newFixedThreadPool(n) is good for CPU-bound work, and newCachedThreadPool works better for IO-bound work where most threads are waiting. On Android, you'd usually go one level higher still and use coroutine dispatchers — Dispatchers.IO and Dispatchers.Default — which are backed by shared thread pools and integrate with structured concurrency and cancellation."

Coroutine vs Thread.

"The key insight is that coroutines are not threads — they're lightweight and cheap to create, you can have thousands of them. They can suspend at suspension points without blocking the underlying OS thread at all. Threads are OS-level entities: expensive to create, and when they wait for IO they block the thread entirely. The practical implication is that Dispatchers.IO uses a pool of roughly 64 threads but can serve thousands of concurrent coroutines, because most of those coroutines are suspended and not actually executing at any given moment. Coroutines also compose naturally through structured concurrency, which gives you automatic cancellation propagation that threads simply don't have."

launch vs async.

"launch fires a coroutine and returns a Job — use it when you don't need a result back, it's essentially fire-and-forget within a structured lifecycle. async returns a Deferred<T> — use it when you need a result, which you retrieve by calling await(). Both are non-blocking. The classic pattern for parallelism is to start both with async — val a = async { fetchA() }; val b = async { fetchB() } — and then call a.await() + b.await(). They run concurrently, not sequentially."

StateFlow vs SharedFlow.

"StateFlow always holds the latest value — you have to give it an initial value when you create it. When a new collector subscribes, it immediately gets the current value. It also conflates rapid emissions, so only the latest value is delivered. That makes it the right choice for UI state. SharedFlow is more configurable: no initial value by default, a configurable replay cache and buffer, and no conflation. It's better for one-shot events like navigation triggers or toasts, where you either want no value replayed or exactly N values replayed. One nuance in practice: many teams back one-shot events with a Channel-based approach to avoid duplicate delivery on recomposition."

Why avoid GlobalScope?

"GlobalScope ties a coroutine's lifetime to the application process, not to any component lifecycle. So if you launch work in GlobalScope from an Activity, that coroutine keeps running after the Activity is destroyed. That causes three problems: memory leaks because the coroutine holds a reference to the destroyed Activity, wasted CPU doing work nobody will see, and potential crashes if the coroutine tries to update views that are gone. You should always prefer viewModelScope, lifecycleScope, or a custom CoroutineScope that you explicitly cancel in the appropriate lifecycle callback."

How do you cancel background work?

"Coroutine cancellation is cooperative — the coroutine has to participate. Calling Job.cancel() sets a cancellation flag, and the coroutine is actually cancelled at its next suspension point. If you have a tight CPU loop with no suspending calls, you need to check ensureActive() or call yield() periodically, otherwise cancellation is never observed. Structured concurrency propagates cancellation automatically to all children. For cleanup, finally blocks run even when a coroutine is cancelled, and you can also use invokeOnCompletion for non-suspending cleanup. For WorkManager tasks, you cancel by calling WorkManager.cancelWorkById()."

How do you prevent ANRs?

"The rule is that the main thread must never block for more than 5 seconds — or 10 seconds for a broadcast receiver — otherwise the system shows an ANR dialog. The answer is simple in principle: keep all IO, network calls, and heavy computation off the main thread. In practice that means using Dispatchers.IO for IO-bound work and Dispatchers.Default for CPU-bound work, then bringing results back to the main thread with withContext(Dispatchers.Main) to update UI. To catch violations early, I enable StrictMode in debug builds — it will flag any disk or network access on the main thread. I also profile with Android Studio's CPU Profiler to find any main thread work that's taking longer than the frame budget."

Android Threading

Explain main/UI thread.

"Android runs all UI rendering, event dispatch, and lifecycle callbacks on a single main thread. Every view operation — invalidate, layout, text updates — has to happen there. If you block the main thread, you drop frames and eventually trigger an ANR. Under the hood, the main thread is just a Looper attached to a MessageQueue — it sits in an infinite loop dequeuing and processing Messages. You post work to it via Handler(Looper.getMainLooper()), View.post(), runOnUiThread(), or withContext(Dispatchers.Main) in a coroutine."

Explain Handler, Looper, MessageQueue.

"These three work together. A Looper prepares a thread to process messages by creating and attaching a MessageQueue, then Looper.loop() enters an infinite loop reading from that queue. A Handler is bound to a Looper and gives you sendMessage() and post(Runnable) to enqueue work onto that thread. On the main thread, Android sets all of this up for you via Looper.prepareMainLooper() and Looper.loop(). On a background thread you'd have to call Looper.prepare() and Looper.loop() yourself — or just use HandlerThread, which does both and exposes getLooper() so you can attach a Handler to it."

What is HandlerThread?

"HandlerThread is a Thread subclass that sets up a Looper for you and exposes getLooper() after you call start(), so you can attach a Handler to it and post work onto that specific thread. It gives you a sequential background message queue without the overhead of a full thread pool — messages are processed one at a time in order. It's particularly useful for APIs that deliver callbacks on a specific thread, like camera preview callbacks or media player events. One important detail: always call quit() or quitSafely() when you're done with it, to stop the looper and let the thread exit cleanly."

Why can't you update UI from background thread?

"Android's view hierarchy is deliberately not thread-safe. ViewRootImpl checks that modifications come only from the thread that originally created the view hierarchy — the main thread — and throws CalledFromWrongThreadException if they don't. This is a conscious design choice: if views were thread-safe, you'd need synchronization on every single view operation, which would be prohibitively expensive. The contract is simple — create and mutate views on the main thread only, and use any of the standard mechanisms to post back to it from a background thread."

Binder thread pool.

"When your app receives an incoming IPC call — for example through a bound service's AIDL — Android dispatches it on a thread from the app's Binder thread pool. The pool goes up to 16 threads maximum, with at least 1 guaranteed. These threads are managed by the system and run concurrently, which means your AIDL implementation must be thread-safe if it touches any shared state. The other side of the coin is outgoing calls: Binder calls from your app to another process block the calling thread until the remote method returns, because they're synchronous by default. That means you must never make Binder calls from the main thread."

WorkManager vs coroutine.

"The key distinction is durability. WorkManager is for deferrable background work that must survive process death and device reboots — it persists work to a database, handles retries, supports chaining, and respects OS-level constraints like network availability and charging state. Coroutines scoped to viewModelScope or lifecycleScope are tied to the component's lifecycle — they're cancelled when the component is destroyed. My rule of thumb is: if the user could kill the app and the work still has to complete — like uploading logs or syncing data — use WorkManager. If the work is request/response within a single screen session, use coroutines."

Foreground service vs WorkManager.

"A foreground service runs with an ongoing notification visible to the user, which makes it nearly immune to process killing by the OS — that makes it right for long-running user-visible tasks like music playback, GPS navigation, or a large file download. WorkManager is for deferred background tasks that can be queued, rescheduled, and potentially batched — the OS may defer them, especially in Doze mode. The way I choose is: if the user is actively aware the work is happening and needs real-time feedback, use a foreground service. If the task is best-effort and can run whenever conditions are right, use WorkManager."

How do you communicate from worker thread to UI?

"There are a few options, and I'd rank them in preference order. First, withContext(Dispatchers.Main) { updateUI() } inside a coroutine — that's the cleanest and most idiomatic. Second, Handler(Looper.getMainLooper()).post { ... } for non-coroutine callbacks like legacy camera or sensor APIs. Third, Activity.runOnUiThread { ... }, which is just a convenience wrapper around the same thing. Fourth, LiveData.postValue() or StateFlow.emit() from the background, with the UI observing on the main thread. The one thing to avoid is runBlocking on the main thread — that synchronously blocks the UI thread waiting for background work, which is exactly the opposite of what you want."

How can Handler cause memory leak?

"The problem comes from how inner classes work in Java and Kotlin. A non-static inner Handler inside an Activity holds an implicit reference to the enclosing Activity instance. If you post a Runnable with a delay — say 30 seconds — that Runnable stays in the MessageQueue for 30 seconds. The chain is: MessageQueue holds the Message, Message holds the Handler, Handler holds the Activity. So even after the user navigates away and the Activity is destroyed, the GC can't collect it because that live chain is still rooted. The fix is either to call handler.removeCallbacksAndMessages(null) in onDestroy(), switch to lifecycleScope.launch which is cancelled automatically, or use a static inner class with a WeakReference<Activity>."

IPC

What is Binder?

"Binder is Android's high-performance IPC mechanism, implemented as a kernel driver. The key thing it does is let one process call methods on objects in another process as if they were local — you never really see the cross-process boundary in the code. What makes it fast is a single-copy design: the Binder kernel module copies data from the caller's address space directly into the callee's, whereas traditional Unix IPC like pipes or sockets often requires two copies. Binder also supports object identity — remote objects are uniquely identified — transactions, and death notifications so you know when the remote process dies. It's the backbone of essentially all Android system services: Activity Manager, Package Manager, and so on."

What is AIDL?

"AIDL stands for Android Interface Definition Language. It's an IDL that generates the stub and proxy code you need for Binder IPC. You define your interface in a .aidl file, and the build system generates a Stub on the server side that extends Binder, and a Proxy on the client side. When the client calls a method, the proxy marshals the arguments into a Parcel, the Binder kernel transports it, and the server's Stub unmarshals it and invokes the implementation on one of the Binder thread pool threads. AIDL supports primitive types, String, Parcelable objects, List, and Map."

AIDL vs Messenger.

"Messenger wraps a Handler and sends Message objects over Binder. Because it goes through a Handler, calls are sequential — there's no concurrency — which keeps it simple. It's a good fit when you just need to pass simple messages between processes. AIDL is for defining a typed, multi-method interface where calls can arrive concurrently on Binder threads. It's more powerful but also more complex to set up. My decision rule is: use Messenger for simple request/response messaging; use AIDL when you need multiple method signatures, concurrent access, or complex custom data types."

Synchronous vs asynchronous IPC.

"Standard AIDL calls are synchronous — the calling thread blocks until the remote method returns, which makes them dangerous on the main thread because you risk an ANR. There are a few patterns to make IPC asynchronous. First, you can declare a method as oneway in the AIDL file: it becomes fire-and-forget with no return value and no exception propagation. Second, you can use Messenger for sequential message passing. Third, you can implement a callback interface: the client passes an AIDL callback object to the server, and the server calls back on a separate future Binder transaction. On Android 10 and above, android.os.IBinder.FLAG_ONEWAY achieves the same effect programmatically."

Parcelable vs Serializable.

"Parcelable is Android's custom serialization interface — you implement writeToParcel and a CREATOR yourself, which is verbose but fast: it avoids reflection entirely and writes directly to a shared memory Parcel, producing very little garbage. Serializable is Java's standard serialization, which uses reflection, creates a lot of temporary objects, and is significantly slower. The rule is: always use Parcelable for Android IPC and Bundle extras — and in Kotlin you can just annotate with @Parcelize and the plugin generates the boilerplate for you. Serializable is acceptable for in-process persistence like writing an object to a file, but never for high-frequency IPC where the overhead compounds."

How do you handle remote service death?

"You register a DeathRecipient by calling IBinder.linkToDeath(recipient, 0). When the remote process dies, the system fires binderDied() on a Binder thread. Inside that callback you should unlink the recipient, null out your binder reference, and then either attempt to rebind or notify the user that the service is unavailable. For bound services, the system also calls onServiceDisconnected() on your ServiceConnection — I'd use both together for robust handling, because onServiceDisconnected only fires for bound services while DeathRecipient works for any direct Binder handle."

What should not be sent over Binder?

"The main thing to avoid is large data. Binder has a per-process transaction buffer of roughly 1 MB, and if you exceed it by sending a bitmap or a large byte array in a Parcel, you get a TransactionTooLargeException — which can be especially confusing because it can surface in onSaveInstanceState as an apparently unrelated crash. For large payloads, use shared memory via MemoryFile or SharedMemory and pass only the FileDescriptor over Binder. Also, you can only send types that Binder knows how to serialize: primitives, String, Parcelable objects, List, and Map. You cannot send arbitrary Java objects — Binder has no reflection-based serialization."

Memory

How GC works conceptually.

"ART uses a generational garbage collector. New objects are allocated in the Young generation — specifically the Eden space — and most short-lived objects die there quickly in what's called a minor GC, which is fast. Objects that survive multiple GC cycles get promoted to the Old generation, which does major GC less frequently but with more work. ART also has a Large Object Space for objects that exceed a size threshold. GC pauses are minimized by running marking concurrently with the app threads, so the GC doesn't have to stop the world for the full collection. The practical implication for Android development is: allocating a lot of short-lived objects is not free — it increases GC frequency, which can cause jank. That's why I profile with Android Studio's Memory Profiler to catch allocation hot spots."

What causes memory leaks in Android?

"The root cause is always the same: a long-lived object holds a reference to a short-lived one — typically an Activity or Fragment — preventing the GC from collecting it. There are six common sources I watch for. First, static fields that hold a Context or a View — those live as long as the process. Second, non-static inner classes including anonymous Runnables and listeners, which carry an implicit this reference to the enclosing class. Third, a Handler with delayed messages, as I described above. Fourth, unregistered listeners and receivers — broadcast receivers, sensor listeners, and RxJava subscriptions that are never disposed. Fifth, Fragment ViewBinding references held beyond onDestroyView(). And sixth, coroutine scopes that are not cancelled when the lifecycle ends."

Activity context vs Application context.

"Activity context has a shorter lifetime — it's tied to the Activity instance — and it carries the Activity's theming and configuration, which is why you need it for UI operations like inflating layouts and creating dialogs. Application context lives as long as the app process itself, so it's the right choice for singletons, background services, and content providers, or anything that has to outlive a single Activity. The rule I follow is: never store Activity context in a singleton or a static field, because you'll prevent the Activity from being garbage collected. Use Application context in those long-lived places instead."

Handler leak. (also covered under Android Threading)

"Covered in the Android Threading section above. The short version: a non-static inner Handler in an Activity plus any delayed messages means the Activity cannot be GC'd until those messages drain from the queue. Fix it by calling removeCallbacksAndMessages(null) in onDestroy(), or better yet, use lifecycleScope which handles cancellation automatically."

Fragment view binding leak.

"The problem here is that Fragments have two distinct lifetimes: the Fragment instance survives configuration changes and back-stack operations, but the Fragment's view is destroyed in onDestroyView(). ViewBinding holds references to views. So if you store the binding in a field and forget to null it out in onDestroyView(), the binding keeps the entire view hierarchy alive even after the views have been destroyed. The fix is to always set _binding = null in onDestroyView() and access the binding through a non-null delegate backed by that nullable field — so safe access is guaranteed during the view's lifetime and the reference is released when the view is gone."

private var _binding: FragmentFooBinding? = null
private val binding get() = _binding!!

override fun onCreateView(...) = FragmentFooBinding.inflate(inflater, container, false)
    .also { _binding = it }.root

override fun onDestroyView() {
    super.onDestroyView()
    _binding = null
}

Bitmap OOM.

"Bitmaps are large objects stored in native memory under ART. A single 4K photo at 3840 by 2160 pixels in ARGB_8888 format consumes roughly 31 MB. OOM happens when you load full-resolution images without downsampling them first. The fix is to use BitmapFactory.Options.inSampleSize to downsample to the size you actually need before loading into memory — or better yet, use an image loading library like Glide or Coil, which handles downsampling automatically, pools and reuses bitmap memory, and ties the loading lifecycle to the component so it cancels requests when the screen is gone. The other thing to avoid is holding multiple large bitmaps in memory at the same time."

How to debug memory leaks.

"My go-to workflow has four steps. First, I add LeakCanary to the debug build — it automatically detects leaks and fires a notification with the full reference chain leading to the leaking object, which takes most of the guesswork out. Second, I use Android Studio's Memory Profiler to take heap dumps and compare snapshots before and after a suspected leak scenario. Third, for a quick command-line view, adb shell dumpsys meminfo shows PSS, heap usage, and retained objects per process. Fourth, in any of those tools I look for classes with unexpectedly high instance counts — for example, if I see multiple instances of an Activity class that should only ever have one at a time, I have a leak."

How to respond to low-memory conditions.

"The right hook is Application.onTrimMemory(level), or ComponentCallbacks2.onTrimMemory(level) on any component. The system calls this with different severity levels — TRIM_MEMORY_RUNNING_LOW, TRIM_MEMORY_RUNNING_CRITICAL, TRIM_MEMORY_UI_HIDDEN, TRIM_MEMORY_BACKGROUND, and others — and you respond by releasing caches, bitmaps, and any other non-essential memory proportional to the urgency of the level. In a ViewModel, for instance, I'd clear any in-memory caches that can be rebuilt from the DB. For APIs below 14 there's the older onLowMemory() callback, but onTrimMemory is what you'd use in any modern codebase."

Architecture

MVP vs MVVM.

"In MVP, the Presenter handles all UI logic and calls View interface methods directly — the View is passive. The problem is that the Presenter holds a direct reference to the View interface, which means to unit test it you have to mock the View, and the coupling between Presenter and View contract can get tight. In MVVM, the ViewModel exposes observable state through LiveData or StateFlow, and the View just observes and renders. There's no direct reference from ViewModel to View — the ViewModel doesn't even know the View exists. That's what makes it testable without a View mock and what allows it to survive configuration changes. MVVM with Compose is the current Android standard."

MVVM vs MVI.

"Both follow the same general shape, but MVI takes it further. In MVVM, the ViewModel exposes state and events and the View can update individual pieces of state independently — it's easier to set up and works well for most screens. In MVI — Model-View-Intent — there's a single immutable state object. The View sends Intents, which are action objects, to the ViewModel, and the ViewModel reduces the current state plus the Intent into a new state, like Redux. The benefit is a complete audit trail: you can log every state transition, replay them, and debug complex state bugs much more easily. The trade-off is more boilerplate. My rule is: use MVI when screen state is complex and you need strict reproducibility; use MVVM for simpler flows."

What is clean architecture?

"Clean architecture structures the codebase into three concentric layers. The outermost is Data — repositories, network sources, database sources. The middle is Domain — use cases and interactors written in pure Kotlin with no Android dependencies. The innermost is UI or Presentation — ViewModels and Compose. The key rule is that dependencies only point inward: UI depends on Domain, and Domain depends on nothing — it defines repository interfaces, and the Data layer provides the implementations. The payoff is that the Domain layer is completely unit-testable without any Android framework on the test classpath. The trade-off is more files and more indirection, which I think is worth it for medium-to-large apps but may be overkill for a small prototype."

What belongs in ViewModel?

"The ViewModel owns three things. First, UI state — it's the single source of truth, exposed via StateFlow or LiveData. Second, UI events like navigation triggers and snackbars, exposed via SharedFlow. Third, orchestration logic: calling use cases or interactors, handling their results, and transforming them into state. What it must NOT do is hold a reference to a View or a Context — unless it's AndroidViewModel and absolutely needs Application context — and it should never reach directly into a database or make a network call itself. The reason it survives configuration changes is precisely because it has no reference to the Activity that gets destroyed and recreated."

What belongs in use case?

"A use case — or interactor — encapsulates exactly one business operation: get a user profile, book an appointment. It calls one or more repositories, applies any business rules like validation or data mapping, combines data from multiple sources if needed, and returns a result. It's a pure Kotlin class with zero Android dependencies, which makes it trivially unit-testable. The discipline to enforce is Single Responsibility: one use case per business action. If a class starts doing two distinct things, split it."

What belongs in repository?

"The repository abstracts the data layer from the domain. It's the place that decides where data comes from — local database, network, cache — and owns the caching and sync strategy. Critically, it exposes clean domain models, not raw DTOs or database entities. The domain layer has no idea whether data comes from Room, Retrofit, SharedPreferences, or a GraphQL endpoint — that's all hidden behind the repository interface. The domain only calls those interfaces, and the concrete implementations are injected via DI, which is what makes it easy to substitute a fake repository in tests."

What is single source of truth?

"Single source of truth means one authoritative owner for the canonical state of a piece of data. In Android, that's typically either a Room database or a StateFlow in a ViewModel. The pattern for an offline-first app is: write network responses to the DB, and have the UI read exclusively from the DB. That prevents the inconsistency where your UI shows one thing from the in-memory cache and something different from a concurrent network call. In Compose, a single uiState: StateFlow<UiState> in the ViewModel is the SSOT for the entire screen — there's no other place to look for what the screen should be showing."

What is UDF (Unidirectional Data Flow)?

"UDF means state flows in one direction: down from the ViewModel to the UI, and events flow back up from the UI to the ViewModel. The UI never mutates state directly — it fires events, the ViewModel handles them and emits new state, and the UI renders whatever state it receives. Compose naturally enforces this pattern: composables receive state as parameters and call lambdas to signal user actions. The benefits are three-fold — state transitions are predictable, everything is easy to debug because all state changes go through one path, and it's easy to test by simply asserting on the output state given a specific input event."

Why use dependency injection?

"DI decouples class creation from class usage. The benefit is testability: instead of a class creating its own network client or database, you inject them from outside, so in tests you can inject a fake or a mock instead of the real thing. It also makes code reusable — you can swap implementations without touching the classes that use them — and explicit about dependencies, because everything a class needs is declared in its constructor. Without DI, every class that needs a database would new one up internally, making unit tests impossible without a real database. With Dagger, the framework builds and wires the entire object graph at compile time, which means missing bindings become compile errors rather than runtime crashes."

How would you modularize a large app?

"I'd decompose by feature and by layer. The typical shape is: :app as the entry point, which depends on :feature:X modules for each distinct feature, which in turn depend on :core:network, :core:database, and :core:ui shared modules. Each feature module is an independent Android library. There are four main benefits: parallel compilation speeds up builds, internal visibility enforces API boundaries between modules, incremental compilation is faster because changes are isolated, and you get the option of on-demand delivery via Play Feature Delivery. The trade-offs are a more complex Gradle setup and the need to manage inter-module navigation — usually via a shared navigation graph or an interface-based approach. The rule to enforce strictly is no circular module dependencies."

View Rendering

Explain measure/layout/draw.

"Android renders views in three sequential passes, all on the main thread. First, measure: the parent passes MeasureSpec constraints to each child, the child calculates its desired size and reports it back via setMeasuredDimension(). Second, layout: onLayout() assigns the final left, top, right, and bottom coordinates for each child based on those measured sizes. Third, draw: each view renders itself onto a Canvas in onDraw(). The two ways to trigger these passes are requestLayout(), which restarts from the measure pass when a view's size or position might change, and invalidate(), which skips straight to draw when only the visual appearance changes."

invalidate() vs requestLayout().

"invalidate() marks a view as dirty and schedules a new draw pass — nothing more. Use it when only the visual appearance changes, like a color or text content, but the size and position stay the same. requestLayout() marks the view and its entire parent chain as needing a full measure plus layout plus draw pass. Use it when the view's size or position might have changed. The mistake to avoid is calling requestLayout() when invalidate() would have been enough — you're triggering an expensive re-measure and re-layout of the whole parent chain for no reason."

What is jank?

"Jank is the visible stuttering you see when frames are dropped. Android targets 60 fps, which gives you a budget of 16 ms per frame. On 90 or 120 Hz displays the budget is even tighter. A frame is dropped whenever the main thread takes longer than that budget to complete its rendering work. The common causes are: expensive onDraw() implementations, deep or complex view hierarchies that take too long to measure and layout, any blocking operation on the main thread, and excessive allocations that trigger frequent GC pauses. I detect jank with Perfetto for a timeline view, Android Studio's Frame Profiler, or adb shell dumpsys gfxinfo for a quick per-frame breakdown."

How to optimize RecyclerView?

"There are a handful of changes that move the needle most. First, replace notifyDataSetChanged() with DiffUtil or ListAdapter — that gives you efficient, animated, diffed updates instead of rebinding everything. Second, always do a full bind in onBindViewHolder and never skip it. Third, call setHasFixedSize(true) when item count changes don't affect the RecyclerView's own dimensions — it skips an unnecessary parent remeasure. Fourth, share a RecycledViewPool across nested RecyclerViews that use the same view types to improve view reuse. Fifth, avoid nested weights and overly complex ConstraintLayout in list item layouts, because each item's measure is expensive and it happens many times per scroll. Sixth, use Glide or Coil for async image loading — they handle downsampling, caching, and lifecycle binding. Finally, for nested RecyclerViews, set setInitialPrefetchItemCount() on the inner LinearLayoutManager so items are prefetched before they come on screen."

What triggers Compose recomposition?

"Recomposition is triggered when the state that a composable reads changes. Compose's snapshot system tracks exactly which State<T> objects are read during each composable's execution. When a State is written, only the composables that read that specific state are scheduled for recomposition — not the whole tree. The important nuance is stability. For Compose to skip a composable when its parent recomposes, it needs to know that the composable's inputs haven't changed. That requires the parameter types to be stable — either primitives, String, classes annotated with @Stable or @Immutable, or types Compose can infer stability for. Unstable types always cause the composable to recompose when the parent does, regardless of whether the value actually changed. The practical fix is to use derivedStateOf { } for any computed state, and reach for ImmutableList for collections."

remember vs rememberSaveable.

"remember stores a value in the composition, so it survives recompositions, but it is lost when the Activity is recreated — for example on a configuration change like rotation. rememberSaveable goes one step further: it persists the value through configuration changes using the SavedStateRegistry, which is the Compose equivalent of onSaveInstanceState. My decision rule is: use remember for purely transient UI state that doesn't matter after a rotation, like an in-progress animation state. Use rememberSaveable for state the user would expect to still be there after rotating the device, like a text field they were typing in or the selected tab index."

State hoisting.

"State hoisting is the pattern of moving state ownership up the composable hierarchy. Instead of a composable managing its own state internally with remember, it receives the current value as a parameter and emits changes via a lambda. The signature looks like value: T, onValueChange: (T) -> Unit. The parent — or ultimately the ViewModel — holds the state; the child just renders what it's given and fires events when the user interacts. This makes composables stateless, which makes them reusable in different contexts and easy to test. The Compose guideline is to hoist state to the lowest common ancestor of all composables that either read or write it."

Compose side effects.

"Side effects are operations that escape the composition — starting a coroutine, registering a listener, firing an analytics event. Compose provides specific APIs for each pattern. LaunchedEffect(key) starts a coroutine scoped to the composition, re-launches it when the key changes, and cancels it when the composable leaves the composition — use it for one-shot effects like triggering navigation or playing an animation. DisposableEffect(key) handles non-coroutine side effects that need cleanup — you register something and return an onDispose { } block to unregister it. SideEffect runs on every successful recomposition with no key — it's for pushing Compose state out to non-Compose code. And rememberCoroutineScope() gives you a coroutine scope tied to the composable's lifetime for user-triggered effects like button clicks, where you need to launch a coroutine from a non-suspending lambda."

How to debug slow rendering.

"My approach has several layers. First, Perfetto or systrace for a full frame timeline — it shows main thread work, RenderThread, and GPU work per frame so you can see exactly where the budget is being spent. Second, Android Studio's Layout Inspector with recomposition highlights, which shows which composables are recomposing and how often — that surfaces excessive recompositions immediately. Third, adb shell dumpsys gfxinfo <package> for a quick command-line view of janky frame counts and frame time percentiles at the 50th, 90th, 95th, and 99th percentiles. Fourth, StrictMode in debug builds to catch disk or network access on the main thread. Fifth, I look for Baseline Profiles to reduce JIT overhead on startup and critical paths. The patterns I search for specifically are: excessive recompositions from unstable types, deep view hierarchies, invalidate() storms, image loading on the main thread, and any blocking call inside onDraw()."

The Framework

For every interview question, structure your answer with six beats:

2. InternalsExplain how it works under the hood — data structures, kernel mechanisms, runtime behavior.

Worked Example 1 — Handler Memory Leak (from the source doc)

Question: How can a Handler cause a memory leak?

1. Define: "A Handler lets you post Messages and Runnables to a thread's MessageQueue for deferred or repeated execution."

2. Internals: "When you call handler.postDelayed(runnable, 30_000), the system creates a Message object that holds a reference to the Runnable. That Message also holds a reference to the Handler. If the Handler is a non-static inner class of the Activity, it holds an implicit reference back to the Activity instance — that's just how non-static inner classes work in Java and Kotlin."

3. Android implications: "If the Activity is destroyed — the user pressed back, or there was a configuration change — while that delayed message is still sitting in the queue, the GC cannot collect the Activity. The chain is still live: MessageQueue → Message → Handler → Activity. Nothing in that chain can be collected until the message drains."

4. Trade-offs: "Non-static inner Handlers are convenient to write, but they're dangerous for any delay longer than a few milliseconds. The safer pattern is a static inner class with a WeakReference<Activity>, which is verbose but doesn't prevent GC."

5. Failure cases:

  • A leaked Activity retains its entire view hierarchy and all attached bitmaps in memory.
  • If the Runnable accesses destroyed views, it may throw NullPointerException or silently no-op.
  • Multiple leaks accumulate across rotations, inflating heap over time.

6. Debug / test:

  • LeakCanary will surface this immediately with the full reference chain.
  • Memory Profiler: take a heap dump after rotating; filter for your Activity class — multiple instances means a leak.
  • Fix: call handler.removeCallbacksAndMessages(null) in onDestroy(), or replace with lifecycleScope.launch { delay(30_000); updateUI() } which is cancelled automatically when the Activity is destroyed.

Worked Example 2 — Coroutine Structured Concurrency & Cancellation

Question: How does coroutine cancellation work, and what can go wrong?

1. Define: "Structured concurrency means every coroutine belongs to a parent scope, and cancelling the parent automatically cancels all children. The important detail is that cancellation is cooperative — a coroutine has to check for it; it doesn't get interrupted like a thread."

2. Internals: "When you call Job.cancel(), the Job transitions to a Cancelling state and a CancellationException is scheduled to be thrown at the next suspension point. All child coroutines receive the same signal and go through the same process. finally blocks run normally, which is how you do cleanup. The subtle bug to watch for is catching Exception broadly and not rethrowing the CancellationException — the coroutine then swallows the cancellation and keeps running."

3. Android implications: "viewModelScope is cancelled when ViewModel.onCleared() is called — which happens when the Activity or Fragment finishes. lifecycleScope is cancelled on Lifecycle.Event.ON_DESTROY. Both give you automatic cleanup without any manual Job.cancel() calls. Any coroutine launched with GlobalScope is completely outside this hierarchy and ignores both."

4. Trade-offs: "The cooperative model is lightweight — there's no thread interruption signal to send. The cost is that you have to ensure cancellation can actually be observed. Long CPU loops with no suspension points need periodic calls to ensureActive() or yield(). Libraries that use BlockingQueue.take() or other OS-level blocking primitives are not cancellation-aware without wrapping them carefully in withContext plus thread interruption."

5. Failure cases:

  • Catching Exception without rethrowing CancellationException makes the coroutine non-cancellable.
  • runBlocking on the main thread blocks cancellation and can cause ANR.
  • Using GlobalScope means the coroutine outlives the ViewModel and may crash accessing destroyed state.
  • Not cleaning up a CoroutineScope owned by a non-lifecycle object (a custom class) causes coroutine leaks.

6. Debug / test:

  • Use TestCoroutineDispatcher / runTest in tests to control coroutine execution deterministically.
  • In production, monitor for jobs that never complete by logging in invokeOnCompletion.
  • LeakCanary can surface ViewModel leaks caused by GlobalScope coroutines keeping the ViewModel alive.

Worked Example 3 — Compose Recomposition & Stability

Question: What triggers Compose recomposition, and how do you prevent excessive recompositions?

1. Define: "Recomposition is Compose re-executing a composable function when the state it reads has changed. It's the mechanism by which the UI stays in sync with state."

2. Internals: "Compose's snapshot system tracks exactly which State<T> objects are read during each composable's execution. When a State is written, Compose schedules recomposition only for the composables that read that specific state — not the whole tree. For this optimisation to work, Compose has to be able to skip a composable when its inputs haven't changed. That requires all the parameters to be stable — either primitives, String, classes annotated with @Stable or @Immutable, or types whose stability Compose can infer from their definition."

3. Android implications: "A data class from a repository that has a plain List<T> property is treated as unstable by Compose because Compose can't prove the list won't mutate. That means its parent composable will always recompose when the parent recomposes, regardless of whether the data actually changed. The fix is to use kotlinx.collections.immutable.ImmutableList or to annotate the data class with @Immutable."

4. Trade-offs: "@Immutable is a promise — you're telling the compiler the class truly never changes after creation, and you have to keep that promise. @Stable is a looser contract for classes that change only in ways Compose can observe. Using derivedStateOf { } is the right tool for computed values that depend on state — it means the composable only recomposes when the derived value actually changes, not every time the upstream state changes."

5. Failure cases:

  • Lambda captures in composables can inadvertently capture unstable objects, breaking skippability.
  • Reading a StateFlow value directly rather than via collectAsState() bypasses the snapshot system entirely.
  • Excessive recompositions from unstable types cause jank on complex screens — the Layout Inspector's recompose counts will show hot composables recomposing on every keystroke.

6. Debug / test:

  • Android Studio Layout Inspector → Recomposition Counts tab: shows which composables recompose and how often.
  • @Stable / @Immutable plus ImmutableList as the first remediation step.
  • Compose compiler metrics (-P plugin:androidx.compose.compiler.plugins.kotlin:reportsDestination=...) report per-composable stability and skippability.
  • In tests, use composeTestRule.mainClock.autoAdvance and verify UI state without flakiness from recompositions.

Worked Example 4 — Binder Transaction Limits / IPC Design

Question: What are the limits and failure modes of Android IPC via Binder?

1. Define: "Binder is Android's kernel-backed IPC. It lets a process call methods on objects in another process, and it does the data transfer with a single copy through the kernel. Every cross-process call is a Binder transaction."

2. Internals: "Each process has a shared Binder transaction buffer of roughly 1 MB. The kernel copies data from the caller's address space into that buffer, and the callee reads from it. By default, Binder calls are synchronous — the calling thread blocks until the remote method returns. Each process gets up to 16 Binder threads: 15 available for incoming calls and 1 spawning thread."

3. Android implications: "Every call to a system service — ActivityManager, PackageManager, WindowManager — goes over Binder. Calling those on the main thread, or passing large objects like bitmaps or big lists, will cause slow or failed IPC. TransactionTooLargeException is thrown when you exceed the ~1 MB buffer limit. One particularly confusing manifestation of this is in onSaveInstanceState, where a large saved-state bundle silently crosses the limit and causes a crash that looks unrelated to IPC."

4. Trade-offs: "Binder's single-copy design makes it faster than socket-based IPC, but it still has overhead. For large payloads like video frames or audio buffers, the right approach is to use SharedMemory or MemoryFile and pass only the file descriptor over Binder. oneway AIDL declarations avoid the blocking call, but you give up return values and error propagation."

5. Failure cases:

  • Calling synchronous Binder methods on the main thread causes ANR.
  • Sending large Parcelables causes TransactionTooLargeException, which is often hard to debug because the stack trace points to the OS rather than your code.
  • Not registering a DeathRecipient means your app silently loses its remote service handle and all subsequent calls throw DeadObjectException.
  • Binder thread pool exhaustion — if the remote service is slow and all 16 threads are occupied — causes the calling thread to block indefinitely.

6. Debug / test:

  • adb shell dumpsys binder_calls_stats shows per-process IPC call frequency and latency.
  • StrictMode detectCustomSlowCalls() plus a thread policy can flag Binder calls on the main thread in debug builds.
  • For TransactionTooLargeException: log bundle sizes before putExtra, consider splitting large payloads, or switch to a content provider or file-based approach.
  • Unit test AIDL implementations by calling the Stub directly in-process — no real Binder needed. Integration test with an instrumented test that binds to a real service running in a separate process.
