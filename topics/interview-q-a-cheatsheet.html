Data Structures

Explain HashMap internals.

🎤 Say it out loud (~40s): "A HashMap is an array of buckets — 16 by default — and on put it spreads the key's hashCode and masks it with (n-1) & hash to pick a bucket. Collisions chain in a linked list, but the Java 8 upgrade is that once a single bucket passes 8 entries and the table is at least 64 wide, that bucket converts to a red-black tree, capping worst-case lookup at O(log n) instead of O(n). The gotcha an interviewer probes is the load factor: at 0.75 occupancy the table doubles and rehashes everything, so sizing it up front matters for hot paths — and for concurrency you switch to ConcurrentHashMap, which stripe-locks per bucket rather than the whole map."

"A HashMap is backed by an array of buckets — 16 by default. When you call put, the key's hashCode() is computed and the bucket index is derived with (n-1) & hash. Collisions are handled with a linked list inside each bucket. The important Java 8 upgrade is that once a bucket's list exceeds 8 entries — that's TREEIFY_THRESHOLD — and the overall array is at least 64 entries wide, the list converts to a red-black tree. That keeps worst-case lookup at O(log n) instead of O(n). The map doubles in size and rehashes everything when it crosses the load factor, which defaults to 0.75. In concurrent contexts you'd reach for ConcurrentHashMap instead, because it stripe-locks individual buckets rather than locking the whole structure."

Key complexities: average O(1) get/put, O(n) worst-case (pre-Java-8 or degenerate hash), O(log n) worst-case Java 8+.

Under the hood

The table is a Node<K,V>[] where each Node holds the cached hash, key, value, and a next pointer. The lookup index is (n - 1) & hash, which only works because capacity is always a power of two — that turns the modulo into a single bitwise AND. To stop poor high-bit distributions from clustering, HashMap.hash() does h ^ (h >>> 16), XOR-ing the upper 16 bits down into the lower ones so they participate in bucket selection. Treeification swaps the Node chain for TreeNodes ordered by hash (falling back to Comparable or identity hash on ties); if a resize later shrinks a tree bucket below UNTREEIFY_THRESHOLD (6), it reverts to a plain list.

put(k,v):
  h = k.hashCode() ^ (k.hashCode() >>> 16)   // spread bits
  i = (capacity - 1) & h                      // power-of-two => bitwise mask
  walk bucket[i]; if (e.hash==h && e.key.equals(k)) overwrite
  else append; if (binCount >= 8 && capacity >= 64) treeify(bucket[i])
  if (++size > capacity * 0.75) resize(2x) and rehash all nodes

Difference between HashMap and TreeMap.

🎤 Say it out loud (~30s): "HashMap is an unordered hash table giving O(1) average get/put; TreeMap is a red-black tree sorted by the key's natural order or your Comparator, so everything is O(log n) but iteration comes out sorted. I reach for TreeMap when I need ordered iteration or range queries like subMap, headMap, tailMap; otherwise HashMap for raw speed. The subtle point is TreeMap uses compareTo/Comparator for equality, not equals, so an inconsistent comparator silently loses entries."

"The key difference is ordering and performance. A HashMap stores entries in an unordered hash table and gives you O(1) average for get and put. A TreeMap stores entries in a red-black tree sorted by the key's natural order, or a Comparator you supply — so get, put, and remove are O(log n), but when you iterate you always get keys in sorted order. The trade-off is: reach for TreeMap when you need range queries like subMap, headMap, or tailMap, or when sorted iteration matters. Reach for HashMap when you just want raw speed and don't care about order."

Under the hood

TreeMap is a left-leaning-free red-black tree: each node is colored red or black, and the tree maintains the invariants that no red node has a red child and every root-to-leaf path crosses the same number of black nodes. Those invariants bound the height at roughly 2·log₂(n+1), which is what guarantees O(log n). Every insert/delete does the comparison-based BST walk, then runs fixAfterInsertion/fixAfterDeletion to recolor nodes and perform left/right rotations restoring balance. Crucially, TreeMap never calls hashCode() or equals() — two keys are "the same" if and only if the comparator returns 0, which is why a comparator inconsistent with equals makes the map behave incorrectly.

Difference between ArrayList and LinkedList.

🎤 Say it out loud (~35s): "ArrayList is a backing array: O(1) random access, amortized O(1) append, but O(n) middle inserts because elements shift. LinkedList is a doubly-linked list: O(1) insert/delete at a known node but O(n) to walk to an index, plus two pointers and an object header of overhead per node. In practice I almost always pick ArrayList on Android because contiguous memory wins on cache locality and the prefetcher; LinkedList only pays off with very frequent positional mutations and no index access. The gotcha is even LinkedList's add(i, x) is O(n) because it has to traverse to i first."

"An ArrayList is a resizable array, so you get O(1) random access, amortized O(1) append, but O(n) insert or delete in the middle because you have to shift elements. A LinkedList is a doubly-linked list: O(1) insert or delete once you have an iterator at the position, but O(n) to get to that position by index, and it has higher memory overhead because each node carries two pointers plus an object header. In practice, ArrayList wins in almost every Android use case because of CPU cache locality — the elements are contiguous in memory, so the prefetcher loves it. LinkedList is rarely worth it unless you have very frequent arbitrary insertions and deletions and you never need to access elements by index."

Under the hood

ArrayList wraps an Object[] elementData. Append writes to elementData[size++]; when full, grow() allocates a new array of roughly oldCapacity + (oldCapacity >> 1) (1.5×) and System.arraycopys everything over — that occasional O(n) copy is why append is amortized O(1), not strict O(1). A middle insert also uses arraycopy to shift the tail. LinkedList allocates a separate Node object per element, each holding prev/next/item; those nodes are scattered across the heap, so iteration chases pointers and incurs cache misses, whereas the array's elements sit in one contiguous block the CPU can prefetch linearly.

ArrayList:  [a][b][c][d][ ][ ]   one heap block, index = base + i*stride
LinkedList: (a)⇄(b)   (c)⇄(d)    scattered nodes, follow next pointers

Implement LRU Cache.

🎤 Say it out loud (~35s): "The cleanest answer is a LinkedHashMap constructed in access-order mode with removeEldestEntry returning true past capacity — that gives O(1) get/put/evict for free. If they want it from scratch, I pair a HashMap for O(1) lookup with a doubly-linked list for O(1) recency reordering, moving touched nodes to the tail and evicting the head. The nuance is that access-order mode mutates the structure on every get, so the cache isn't safe to share across threads without external synchronization or Collections.synchronizedMap."

"The cleanest approach is to combine a LinkedHashMap in access-order mode with a max-size cap. If you need full control — say the interviewer asks you to build it from scratch — you can use a HashMap paired with a doubly-linked list, which gives you the same O(1) guarantees manually."

class LRUCache(private val capacity: Int) {
    private val map = object : LinkedHashMap<Int, Int>(capacity, 0.75f, true) {
        override fun removeEldestEntry(eldest: MutableMap.MutableEntry<Int, Int>?) =
            size > capacity
    }

    fun get(key: Int): Int = map.getOrDefault(key, -1)

    fun put(key: Int, value: Int) {
        map[key] = value
    }
}

"Passing accessOrder = true to LinkedHashMap makes it move the most recently accessed entry to the tail on every get or put. Then overriding removeEldestEntry to return true when size > capacity automatically evicts the head — which is always the least-recently-used entry. All operations are O(1)."

Under the hood

LinkedHashMap extends HashMap but threads every entry onto a separate doubly-linked list via extra before/after pointers on each Entry, maintaining iteration order independent of bucket placement. With accessOrder=true, get() (and put on an existing key) calls afterNodeAccess(), which unlinks the touched entry and re-links it at the tail — so the head is always the least-recently-used. After every insertion, afterNodeInsertion() consults removeEldestEntry(head); returning true makes it evict the head node. Because both the hash lookup and the linked-list splice are O(1), all operations stay O(1) — the linked list adds order without adding traversal cost.

Analyze time complexity of code.

🎤 Say it out loud (~30s): "My framework is: count nested loops since each level multiplies, write recurrences for recursion, and watch for hidden inner loops — calling contains() on a List inside a loop is a silent O(n²). I always state whether I mean worst-case or amortized. The trap interviewers love is the disguised cost: a String += in a loop is O(n²) because each concat copies the whole string, and ArrayList.add(0, x) is O(n) per call, not O(1)."

"My framework is to count the loops first — each level of nesting multiplies the complexity. Then I look at recursive calls and set up the recurrence relation. The thing I flag most often is hidden inner loops: calling contains() on a plain List inside another loop is O(n) per call, which makes the whole thing O(n²) without looking like it. I always express the answer in Big-O, and I make sure to clarify whether I mean amortized or worst-case. For Android interviews the patterns that come up most are: two nested loops gives O(n²), sorting gives O(n log n), hash lookups are O(1) average, and tree traversal is O(n)."

Under the hood

Big-O describes the asymptotic growth of an abstract operation count, but the constant factors it hides are real hardware costs: a cache miss is ~100× a cache hit, so an O(n) array scan often beats an O(log n) pointer-chasing tree at small n. The "hidden loop" trap is that library calls have their own complexity baked in — List.contains is a linear scan, String concatenation allocates and copies because String is immutable, and divide-and-conquer recursion resolves via the Master Theorem: T(n)=2T(n/2)+O(n) solves to O(n log n) (the merge-sort recurrence), while T(n)=T(n/2)+O(1) solves to O(log n) (binary search).

Find duplicate elements.

🎤 Say it out loud (~30s): "The general solution is a HashSet: add each element, and if add returns false it's already seen, so it's a duplicate — O(n) time, O(n) space. The clever follow-up they want is the O(1)-space trick when values are in 1..n and you can mutate the array: use each value as an index and negate the element there; if you land on an already-negative slot, that index is a duplicate. The gotcha is it destroys the array and only works for that bounded value range."
fun findDuplicates(nums: IntArray): List<Int> {
    val seen = HashSet<Int>()
    val dupes = mutableListOf<Int>()
    for (n in nums) if (!seen.add(n)) dupes.add(n)
    return dupes
}
// O(n) time, O(n) space

"If you're allowed to mutate the array and the values are in the range 1 to n, there's a O(1) space trick: negate the value at index abs(val)-1 as you visit each element. If you arrive at an index that's already negative, the value at that index is a duplicate."

Under the hood

The in-place trick works because the array itself becomes the visited-set: with values constrained to 1..n there's a bijection between each value v and the slot v-1, so the sign bit of nums[v-1] stores one bit of "have I seen v before?" without any extra allocation. You always read the magnitude with abs() before indexing because an earlier step may have flipped the sign of the slot you now need to use as a key. The HashSet version trades that O(1) space for generality — add does a single hash-bucket probe and returns false when an equal element already occupies the bucket, so no separate contains call is needed.

Top K frequent items.

🎤 Say it out loud (~35s): "Two approaches. The standard one builds a frequency map then keeps a min-heap of size K — push everything and poll whenever the heap exceeds K, so only the top K survive, giving O(n log k). If they push for linear, I switch to bucket sort: an array of lists indexed by frequency 0..n, then read from the high-frequency end until I have K — O(n). The nuance is the heap must be a min-heap keyed by frequency, so the smallest survivor is what gets evicted, leaving the largest K behind."

"There are two approaches. The standard one is a frequency map combined with a min-heap of size K — you keep evicting the least-frequent element from the heap whenever it grows past K, so only the top K survive. That runs in O(n log k). If you want O(n), you can use bucket sort: build an array of lists indexed by frequency from 0 to n, then read from the high-frequency end until you have K elements."

fun topKFrequent(nums: IntArray, k: Int): IntArray {
    val freq = HashMap<Int, Int>()
    for (n in nums) freq[n] = (freq[n] ?: 0) + 1

    // min-heap keyed by frequency, evict when size > k
    val heap = PriorityQueue<Map.Entry<Int, Int>>(compareBy { it.value })
    for (entry in freq.entries) {
        heap.offer(entry)
        if (heap.size > k) heap.poll()
    }
    return heap.map { it.key }.toIntArray()
}
// O(n log k) time

"The bucket-sort version creates an array of lists indexed by frequency from 0 to n, then iterates in reverse to collect the top K — O(n) time, O(n) space."

Under the hood

Java's PriorityQueue is a binary min-heap stored in a flat array, where the children of index i live at 2i+1 and 2i+2 — no node objects, just arithmetic. offer appends at the end and "sifts up" swapping with the parent until heap order holds; poll removes index 0, moves the last element to the root, and "sifts down" — each O(log size). Bounding the heap at K is what turns O(n log n) into O(n log k): you only ever hold K elements. The bucket-sort alternative exploits the fact that no frequency can exceed n, so frequencies form a dense bounded integer range — a perfect fit for a counting/bucket pass that skips comparison sorting entirely and hits O(n).

Merge intervals.

🎤 Say it out loud (~30s): "Sort by start time, then sweep once: if the current interval starts after the last merged interval ends, it's disjoint so I append it; otherwise they overlap and I extend the last interval's end to the max of the two ends. The sort dominates at O(n log n). The off-by-one gotcha is deciding whether touching intervals like [1,2] and [2,3] count as overlapping — clarify whether endpoints are inclusive before you pick < versus <=."
fun merge(intervals: Array<IntArray>): Array<IntArray> {
    intervals.sortBy { it[0] }
    val result = mutableListOf<IntArray>()
    for (interval in intervals) {
        if (result.isEmpty() || result.last()[1] < interval[0]) {
            result.add(interval)
        } else {
            result.last()[1] = maxOf(result.last()[1], interval[1])
        }
    }
    return result.toTypedArray()
}
// O(n log n) due to sort

"The approach is to sort by start time first, then do a single pass. For each interval, if its start is greater than the last merged interval's end, it doesn't overlap — so you add it as a new interval. Otherwise, you extend the last merged interval's end to the maximum of the two ends. The sort dominates at O(n log n)."

Under the hood

Sorting by start time establishes the key invariant the single pass relies on: once intervals are start-ordered, any interval that overlaps the running merged interval must overlap it at its right edge — you can never need to revisit an earlier merged interval, which is what collapses the problem to one linear sweep. Arrays.sort on the object array uses TimSort, an adaptive merge sort that detects already-sorted runs and merges them, giving O(n) on nearly-sorted input and a stable O(n log n) worst case. The maxOf on the end is necessary because a later interval can be fully contained in the current merged one, in which case the end must not shrink.

Valid parentheses.

🎤 Say it out loud (~30s): "Push every opening bracket onto a stack; on a closing bracket, pop and check it matches the expected opener. If the stack is empty when I need to pop, or non-empty at the end, it's unbalanced — O(n) time and space. The two edge cases interviewers check are the empty-stack pop on a leading closer like ), and the leftover-openers case like ((( where the final emptiness check is what catches it."
fun isValid(s: String): Boolean {
    val stack = ArrayDeque<Char>()
    val match = mapOf(')' to '(', ']' to '[', '}' to '{')
    for (c in s) {
        if (c in "([{") stack.addLast(c)
        else if (stack.isEmpty() || stack.removeLast() != match[c]) return false
    }
    return stack.isEmpty()
}
// O(n) time, O(n) space

"The idea is: push every opening bracket onto a stack. When you see a closing bracket, pop the top and verify it matches. If the stack is empty when you need to pop, or if it's non-empty when you reach the end, the string is not balanced."

Under the hood

A stack is the natural data structure because bracket nesting is a last-in-first-out relationship: the most recently opened bracket must be the first one closed. Kotlin's ArrayDeque backs this with a growable circular array, so addLast/removeLast are amortized O(1) — no per-element node allocation like a linked stack. The short-circuit evaluation matters: stack.isEmpty() || stack.removeLast() != match[c] checks emptiness first, so removeLast is never called on an empty deque (which would throw NoSuchElementException) — the || guarantees the pop only runs when there's something to pop.

Binary search.

🎤 Say it out loud (~30s): "Maintain lo/hi bounds, compute mid, and halve the search space each step on a sorted array — O(log n). The detail I always call out is computing mid as lo + (hi - lo) / 2 rather than (lo + hi) / 2 to dodge integer overflow when both bounds are large. For variants: first/last occurrence means I don't return on a match but keep narrowing toward that side; for a rotated array, one half is always sorted, so I test which half is sorted and decide whether the target lies in it."
fun binarySearch(arr: IntArray, target: Int): Int {
    var lo = 0; var hi = arr.size - 1
    while (lo <= hi) {
        val mid = lo + (hi - lo) / 2  // avoids overflow vs (lo+hi)/2
        when {
            arr[mid] == target -> return mid
            arr[mid] < target  -> lo = mid + 1
            else               -> hi = mid - 1
        }
    }
    return -1
}
// O(log n)

"One subtlety worth mentioning: I use lo + (hi - lo) / 2 rather than (lo + hi) / 2 to avoid integer overflow when both bounds are large. For variants — finding the first or last occurrence means you keep going after you match instead of returning immediately. For a rotated array, the key insight is that one half is always sorted, so you check which half and decide where to narrow."

Under the hood

The overflow concern is concrete: int is a 32-bit two's-complement value capped at 2,147,483,647, so for two large near-Int.MAX_VALUE bounds, lo + hi silently wraps to a negative number and indexes out of bounds — this exact bug lived in the JDK's own Arrays.binarySearch for nine years. lo + (hi - lo) / 2 is algebraically equal to (lo + hi) / 2 but the intermediate hi - lo can never overflow when both are non-negative. The lo <= hi termination (not <) plus the mid ± 1 updates guarantee the interval strictly shrinks every iteration, so the loop provably halts after ⌈log₂ n⌉ steps with no infinite-loop edge case.

BFS / DFS.

🎤 Say it out loud (~30s): "BFS uses a queue and explores level by level, which makes it the right tool for shortest path in an unweighted graph and level-order traversal. DFS uses a stack or recursion and dives deep first, better for connectivity, path existence, topological sort, and cycle detection. The shared gotcha is the visited set: you must mark a node visited when you enqueue it in BFS, not when you dequeue it, or you'll push the same node many times and blow up the queue."
// BFS — level order, shortest path in unweighted graph
fun bfs(graph: Map<Int, List<Int>>, start: Int): List<Int> {
    val visited = mutableSetOf(start)
    val queue = ArrayDeque<Int>()
    val order = mutableListOf<Int>()
    queue.addLast(start)
    while (queue.isNotEmpty()) {
        val node = queue.removeFirst()
        order.add(node)
        graph[node]?.forEach { neighbor ->
            if (visited.add(neighbor)) queue.addLast(neighbor)
        }
    }
    return order
}

// DFS — recursive or iterative, path finding, topological sort
fun dfs(graph: Map<Int, List<Int>>, node: Int, visited: MutableSet<Int>, order: MutableList<Int>) {
    if (!visited.add(node)) return
    order.add(node)
    graph[node]?.forEach { dfs(graph, it, visited, order) }
}

"BFS uses a queue and explores level by level, which makes it the right choice for shortest path in an unweighted graph and for level-order problems. DFS uses a stack or recursion and goes deep first — it's better for connectivity checks, path existence, topological sort, and cycle detection."

Under the hood

The only structural difference between the two is the frontier data structure: BFS pulls from a FIFO queue so nodes come out in non-decreasing distance from the start — that ordering is exactly why the first time BFS reaches a node it has found a shortest path in an unweighted graph. DFS uses a LIFO stack, which the recursive form gets for free from the JVM call stack; each recursive frame holds the node and its iterator position. That implicit stack is also DFS's hazard — on a deep or skewed graph it can exhaust the thread's stack and throw StackOverflowError, which is why production DFS over untrusted-depth graphs is often rewritten with an explicit ArrayDeque stack on the heap.

Detect cycle in graph.

🎤 Say it out loud (~35s): "It depends on directedness. Undirected: run DFS tracking the parent — if I hit a visited node that isn't the parent I came from, that's a cycle. Directed: I need three colors — white unvisited, gray on the current recursion stack, black fully done — and hitting a gray node means a back edge, which is a cycle. The classic mistake is using a plain visited boolean for directed graphs; that can't distinguish 'currently in progress' from 'already finished,' so you miss back edges. There's also Union-Find for the undirected case."

"The approach depends on whether the graph is directed or undirected. For an undirected graph, you run DFS and track the parent node. If you reach a visited node that isn't the parent you came from, there's a cycle. For a directed graph, you need three colour states: WHITE means unvisited, GRAY means currently on the recursion stack, and BLACK means fully processed. If during DFS you encounter a GRAY node, you've found a back edge — that's a cycle."

// Directed cycle detection
fun hasCycle(n: Int, edges: List<Pair<Int,Int>>): Boolean {
    val graph = Array(n) { mutableListOf<Int>() }
    edges.forEach { (u, v) -> graph[u].add(v) }
    val color = IntArray(n) // 0=white,1=gray,2=black

    fun dfs(u: Int): Boolean {
        color[u] = 1
        for (v in graph[u]) {
            if (color[v] == 1) return true   // back edge
            if (color[v] == 0 && dfs(v)) return true
        }
        color[u] = 2
        return false
    }
    return (0 until n).any { color[it] == 0 && dfs(it) }
}

"There's also a Union-Find approach for undirected graphs: if find(u) == find(v) before you call union(u, v), the two nodes are already in the same component, so adding this edge creates a cycle."

Under the hood

GRAY precisely models "this node is an ancestor on the current DFS path" — it's set when recursion enters the node and flipped to BLACK only after all descendants return. A back edge, by definition, is an edge to an ancestor still on the recursion stack, so encountering GRAY is the textbook back-edge detection and equivalently proves the graph isn't a DAG (no valid topological order exists). Union-Find solves the undirected case with near-constant amortized cost: with path compression (flattening the tree on find) plus union by rank, the total work is O(α(n)) per operation, where α is the inverse Ackermann function — effectively ≤ 4 for any realistic input.

white(0) ──enter──▶ gray(1) ──all children done──▶ black(2)
edge to gray  = back edge = cycle
edge to black = forward/cross edge = safe

Concurrency

What is thread safety?

🎤 Say it out loud (~35s): "Code is thread-safe if it stays correct under concurrent access without callers adding their own synchronization. Three ways to get there: mutual exclusion via synchronized or ReentrantLock, immutability — nothing to protect if state never changes — and lock-free structures like AtomicInteger or ConcurrentHashMap. The gotcha is that blanket-synchronizeding every method is correct but serializes all access and kills throughput under contention, so at scale you prefer fine-grained locks or lock-free designs, and you remember that composing two thread-safe calls isn't itself atomic."

"A class or operation is thread-safe if it behaves correctly when accessed concurrently from multiple threads, without the caller having to add any extra synchronization themselves. There are three main ways to achieve it: mutual exclusion via synchronized or ReentrantLock, immutability — if the object never changes there's nothing to protect — and lock-free data structures like AtomicInteger or ConcurrentHashMap. The naive approach of making all methods synchronized is the bluntest instrument. It works, but it serializes all access and creates contention under load, so at scale you want to prefer fine-grained locking or lock-free approaches."

Under the hood

Thread safety is ultimately defined by the Java Memory Model's happens-before relation, not by intuition about "simultaneous" access. Without a happens-before edge, the compiler, JIT, and CPU are all free to reorder instructions and the CPU may keep writes in per-core store buffers that other cores never see. Each synchronization tool establishes that edge differently: releasing a monitor or lock happens-before any later acquire of the same lock; a volatile write happens-before any later read; and lock-free Atomic* types use CAS (compare-and-swap), which compiles to a single hardware instruction like x86 LOCK CMPXCHG that atomically tests-and-sets while emitting a memory fence — giving atomicity and visibility without ever parking a thread.

What is a race condition?

🎤 Say it out loud (~30s): "A race condition is when the result depends on the non-deterministic interleaving of concurrent operations. Classic case: two threads both read count=5, both compute 6, both write 6 — you lose an increment and get 6 instead of 7. The fix is to make the read-modify-write atomic, with an AtomicInteger, a synchronized block, or a coroutine Mutex. The deeper gotcha is that even volatile doesn't fix this — visibility isn't atomicity, so a volatile counter still races."

"A race condition is when the outcome of a computation depends on the non-deterministic ordering of concurrent operations. The classic example is a counter: two threads both read count = 5, both compute 6, both write 6 — so the net result is 6 instead of the correct 7. The fix is to make the read-modify-write sequence atomic, either with an AtomicInteger, a synchronized block, or a Mutex in coroutines."

Under the hood

count++ is not one operation — the bytecode is a read-modify-write triple that the scheduler can interrupt between any two steps:

getfield count    // thread A reads 5
iconst_1
iadd              // A computes 6   <-- thread B reads 5 here too
putfield count    // A writes 6 ... then B also writes 6  => lost update

AtomicInteger.incrementAndGet() instead loops on a CAS: it reads the current value, computes the next, and atomically swaps only if the value is still what it read — retrying if another thread won the race. Because the entire test-and-set is a single uninterruptible hardware instruction, there's no window for an interleaving to slip in, so no increment is ever lost.

synchronized vs volatile.

🎤 Say it out loud (~30s): "synchronized gives two guarantees — mutual exclusion and visibility (changes flushed on exit, re-read on entry). volatile gives visibility only: reads and writes bypass caches and hit main memory, but it does not make compound operations atomic. So volatile is perfect for a simple on/off flag, but the moment you have a check-then-act or read-modify-write — like a counter or lazy init — you need synchronized or an Atomic* type. The trap is thinking volatile count++ is safe; it isn't."

"The critical distinction is that synchronized gives you two guarantees: mutual exclusion — only one thread is in the block at a time — and visibility — changes are flushed to main memory on exit and re-read on entry. volatile gives you visibility only. Reads and writes bypass CPU caches and go straight to main memory, but it does not make compound operations atomic. So volatile is fine for a simple on/off flag, but the moment you have a check-then-act pattern — read the flag, do something, write the flag — you need synchronized or an Atomic* type."

Under the hood

A volatile read/write compiles to ordinary load/store instructions wrapped in memory barriers (fences): a write emits a StoreStore + StoreLoad fence so it can't be reordered earlier and is globally visible before subsequent operations; a read emits a LoadLoad + LoadStore fence. That guarantees ordering and visibility but touches no lock, so two threads can still interleave a non-atomic ++. synchronized compiles to monitorenter/monitorexit bytecodes that acquire an object's monitor — establishing both exclusion and the same memory-fence semantics at the lock boundaries. The JIT can further optimize uncontended monitors via biased/thin locking, escalating to a heavyweight OS mutex only when threads actually contend.

How does a Java monitor work?

🎤 Say it out loud (~35s): "Every Java object has an intrinsic lock — a monitor. synchronized(obj) acquires it; other threads trying to acquire block until it's released. The monitor also gives condition waiting via wait/notify/notifyAll: wait atomically releases the lock and suspends, notify wakes one waiter which must re-acquire the lock before returning. The gotcha interviewers chase is that you must call wait inside a loop re-checking the condition — never an if — because of spurious wakeups and because another thread can change the state between the notify and your re-acquire."

"Every Java object has an intrinsic lock called a monitor. When you call synchronized(obj), the calling thread acquires that lock, and any other thread that tries to acquire it blocks until it's released. The monitor also provides condition-based waiting through wait(), notify(), and notifyAll(). When a thread calls wait(), it releases the lock and suspends. When another thread calls notify(), one waiting thread wakes up, re-acquires the lock, and then returns from wait(). This primitive mechanism is the foundation for all the higher-level concurrency utilities in Java."

Under the hood

The monitor state lives in the object header's mark word, which the JVM repurposes to point at lock metadata. A monitor conceptually maintains an owner thread, a recursion count (monitors are reentrant — the owner can re-enter without deadlocking, incrementing the count), an entry set of threads blocked on monitorenter, and a wait set of threads parked in wait(). wait() releases the lock and moves the thread into the wait set; notify() moves one thread from the wait set back to the entry set, where it must still win the lock before continuing. Because notify and the actual lock re-acquisition aren't a single step, the awakened thread can observe state changed by some third thread — which is exactly why the condition must be re-tested in a while loop.

What causes deadlock?

🎤 Say it out loud (~35s): "Deadlock needs all four Coffman conditions at once: mutual exclusion, hold-and-wait, no preemption, and circular wait. The most reliable prevention is breaking circular wait by always acquiring locks in one consistent global order; alternatives are tryLock with a timeout, avoiding nested locks, or using lock-free structures. To diagnose one, a thread dump shows the threads stuck in BLOCKED with a circular wait chain. The subtle one is lock ordering across abstraction layers — two code paths that lock A-then-B versus B-then-A will deadlock under load even though each looks fine alone."

"Deadlock requires four conditions to be true at the same time — the Coffman conditions. First, mutual exclusion: resources can't be shared. Second, hold-and-wait: a thread holds one lock while waiting for another. Third, no preemption: you can't forcibly take a lock from a thread. Fourth, circular wait: thread A is waiting for something thread B holds, and thread B is waiting for something thread A holds. To prevent deadlock, the most practical approach is to always acquire locks in a consistent global order. You can also use tryLock with a timeout, avoid nested locks altogether, or use higher-level concurrent structures that don't require explicit locking. When detecting a deadlock, thread dumps will show the relevant threads stuck in BLOCKED state with a circular wait chain."

Under the hood

A deadlock is a cycle in the wait-for graph — a directed graph where an edge T1→T2 means thread T1 is blocked waiting on a lock held by T2; if that graph contains a cycle, no thread in the cycle can ever proceed. Consistent global lock ordering provably eliminates the cycle: if every thread acquires locks in ascending order by some total order (e.g. System.identityHashCode), the wait-for graph can only ever point "upward," and a cycle requires at least one downward edge, so a cycle becomes impossible. The JVM doesn't auto-recover from deadlock — jstack / the ThreadMXBean.findDeadlockedThreads() API can detect it by finding the cycle, but the threads stay parked until the process is killed.

Producer-consumer implementation.

🎤 Say it out loud (~30s): "A bounded BlockingQueue handles producer-consumer cleanly: put blocks when full and take blocks when empty, so backpressure is automatic — no manual wait/notify. On Android the idiomatic version is a coroutine Channel, which suspends instead of blocking the thread and plugs into structured concurrency and cancellation. The gotcha is bounding the buffer: an unbounded queue or Channel.UNLIMITED removes backpressure, so a fast producer can OOM the app when consumers can't keep up."
// Using BlockingQueue (Java)
val queue = LinkedBlockingQueue<Int>(10)

val producer = thread {
    var i = 0
    while (true) { queue.put(i++); Thread.sleep(100) }
}
val consumer = thread {
    while (true) { val item = queue.take(); println("Consumed $item") }
}

// Coroutine Channel version
val channel = Channel<Int>(10)
launch { repeat(100) { channel.send(it) } }
launch { for (item in channel) println("Got $item") }

"The BlockingQueue handles backpressure naturally: put blocks when the queue is full, and take blocks when it's empty. On Android the idiomatic equivalent is a coroutine Channel, which integrates with structured concurrency and suspension rather than blocking threads."

Under the hood

LinkedBlockingQueue uses two separate ReentrantLocks — a putLock and a takeLock — plus two Conditions (notFull, notEmpty), so producers and consumers can largely operate in parallel rather than contending on one lock. put parks the OS thread on notFull.await() when the queue is full; take signals notFull after removing an element. A Channel achieves the same shape without blocking threads: when a coroutine sends into a full rendezvous/buffered channel, the channel suspends the coroutine by capturing its Continuation and storing it in the channel's internal wait queue, then resumes it from receive on the consumer side — so the underlying dispatcher thread is freed to run other coroutines instead of being parked.

Executor vs raw Thread.

🎤 Say it out loud (~30s): "A raw Thread is unmanaged — every start and stop is an OS operation, no pooling, no lifecycle. An ExecutorService pools and reuses threads across tasks: fixed pools for CPU-bound work, cached pools for IO-bound work where threads mostly wait. On Android I usually go a level higher to coroutine dispatchers, which sit on shared pools and add structured cancellation. The gotcha is newCachedThreadPool is unbounded — under a task flood it can spawn thousands of threads and exhaust memory, so for untrusted load you want a bounded pool."

"A raw Thread is unmanaged: every creation and teardown is an OS-level operation, there's no pooling, and there's no lifecycle management. An Executor or ExecutorService pools threads, queues tasks, and reuses threads across many work items. Executors.newFixedThreadPool(n) is good for CPU-bound work, and newCachedThreadPool works better for IO-bound work where most threads are waiting. On Android, you'd usually go one level higher still and use coroutine dispatchers — Dispatchers.IO and Dispatchers.Default — which are backed by shared thread pools and integrate with structured concurrency and cancellation."

Under the hood

Creating a Thread calls down through the JVM to a native pthread_create, which reserves a stack (commonly ~512KB–1MB of address space on Android) and registers the thread with the OS scheduler — expensive enough that thousands of them are infeasible. ThreadPoolExecutor amortizes that by keeping a fixed set of worker threads each looping in getTask(), blocking on the shared BlockingQueue until work arrives. Its behavior is governed by corePoolSize, maximumPoolSize, the queue type, and a RejectedExecutionHandler: newFixedThreadPool pairs a fixed core size with an unbounded LinkedBlockingQueue (tasks queue, threads stay constant), while newCachedThreadPool uses a SynchronousQueue with maximumPoolSize = Integer.MAX_VALUE, so each task that can't hand off to an idle thread spawns a new one — hence the unbounded-growth risk.

Coroutine vs Thread.

🎤 Say it out loud (~35s): "Coroutines aren't threads — they're cheap, you can run thousands, and they suspend at suspension points without blocking the underlying OS thread. Threads are OS entities: costly to create, and when they wait on IO they block the thread outright. So Dispatchers.IO can serve thousands of coroutines on a pool of ~64 threads because most are suspended at any instant. They also compose through structured concurrency with automatic cancellation propagation, which raw threads don't give you. The gotcha is that suspension is cooperative — a blocking call like Thread.sleep inside a coroutine still pins the thread and defeats the whole model."

"The key insight is that coroutines are not threads — they're lightweight and cheap to create, you can have thousands of them. They can suspend at suspension points without blocking the underlying OS thread at all. Threads are OS-level entities: expensive to create, and when they wait for IO they block the thread entirely. The practical implication is that Dispatchers.IO uses a pool of roughly 64 threads but can serve thousands of concurrent coroutines, because most of those coroutines are suspended and not actually executing at any given moment. Coroutines also compose naturally through structured concurrency, which gives you automatic cancellation propagation that threads simply don't have."

Under the hood

The Kotlin compiler transforms each suspend function via CPS (continuation-passing style): it rewrites the function into a state machine where every suspension point is a labeled state, and the function gains a hidden Continuation parameter that captures its local variables and resume label. When a function suspends, it returns the sentinel COROUTINE_SUSPENDED instead of blocking; the dispatcher's thread is released, and the saved Continuation is resumed later — possibly on a different thread. So a "coroutine" is really a heap-allocated state-machine object plus its continuation chain, which is why it costs a few dozen bytes instead of a megabyte of stack. A blocking call like Thread.sleep doesn't hit a suspension point, so the state machine never yields and the dispatcher thread stays parked — that's the leak that exhausts the pool.

launch vs async.

🎤 Say it out loud (~30s): "launch fires a coroutine and returns a Job — fire-and-forget within a structured lifecycle, no result. async returns a Deferred<T> and you call await() for the result. Both are non-blocking. The classic parallel pattern is two asyncs then a.await() + b.await() so they run concurrently. The gotcha interviewers love is exception timing: launch throws into the parent scope immediately, but async defers the exception until you call await(), so an unawaited async can swallow a failure."

"launch fires a coroutine and returns a Job — use it when you don't need a result back, it's essentially fire-and-forget within a structured lifecycle. async returns a Deferred<T> — use it when you need a result, which you retrieve by calling await(). Both are non-blocking. The classic pattern for parallelism is to start both with async — val a = async { fetchA() }; val b = async { fetchB() } — and then call a.await() + b.await(). They run concurrently, not sequentially."

Under the hood

Both are extension functions on CoroutineScope that create a child coroutine and a Job linked into the parent's Job hierarchy — that parent-child link is what structured concurrency is built on. The difference is the returned handle and how results/failures flow: launch returns a bare Job; an uncaught exception propagates immediately up to the parent and (in a normal scope) cancels siblings. async returns a Deferred<T> (a Job subtype) that stores the computed value or the captured exception in its completed state — await() either returns the value or re-throws the stored exception. That storage is exactly why an exception in async stays dormant until awaited: there's nowhere to surface it until someone reads the result.

StateFlow vs SharedFlow.

🎤 Say it out loud (~35s): "StateFlow always holds a single latest value — needs an initial value, new collectors immediately get the current value, and it conflates rapid emissions, which makes it ideal for UI state. SharedFlow is configurable: no initial value, tunable replay and buffer, no conflation — better for one-shot events like navigation or toasts. The big gotcha is StateFlow is equality-conflated: it only emits when the new value != the previous one, so emitting an equal value is dropped — and for events, conflation plus replay can drop or duplicate them, which is why many teams back events with a Channel instead."

"StateFlow always holds the latest value — you have to give it an initial value when you create it. When a new collector subscribes, it immediately gets the current value. It also conflates rapid emissions, so only the latest value is delivered. That makes it the right choice for UI state. SharedFlow is more configurable: no initial value by default, a configurable replay cache and buffer, and no conflation. It's better for one-shot events like navigation triggers or toasts, where you either want no value replayed or exactly N values replayed. One nuance in practice: many teams back one-shot events with a Channel-based approach to avoid duplicate delivery on recomposition."

Under the hood

StateFlow is actually implemented as a SharedFlow with replay = 1, zero extra buffer, and BufferOverflow.DROP_OLDEST — its single slot is the state. Its conflation isn't time-based; it stores the latest value and only notifies collectors when newValue != oldValue by equals, which is why repeated equal emissions are silently coalesced and why it's safe to set from many threads via an atomic update. Both flows track collectors as subscriber slots; the replay cache is a small array that new collectors drain on subscribe. A Channel-backed event differs fundamentally: it's a queue with exactly-once delivery semantics (each element is consumed by one receiver and removed), so it survives configuration-change re-collection without re-emitting stale events the way a replaying flow would.

Why avoid GlobalScope?

🎤 Say it out loud (~30s): "GlobalScope ties a coroutine's life to the whole process, not to any component, so work launched from an Activity keeps running after the Activity is destroyed. That gives you leaks — the coroutine pins the destroyed Activity — wasted CPU, and crashes if it touches dead views. The fix is to use a lifecycle-aware scope: viewModelScope, lifecycleScope, or a custom scope you cancel explicitly. The deeper point is GlobalScope opts out of structured concurrency entirely, so failures and cancellation don't propagate to or from anything."

"GlobalScope ties a coroutine's lifetime to the application process, not to any component lifecycle. So if you launch work in GlobalScope from an Activity, that coroutine keeps running after the Activity is destroyed. That causes three problems: memory leaks because the coroutine holds a reference to the destroyed Activity, wasted CPU doing work nobody will see, and potential crashes if the coroutine tries to update views that are gone. You should always prefer viewModelScope, lifecycleScope, or a custom CoroutineScope that you explicitly cancel in the appropriate lifecycle callback."

Under the hood

A CoroutineScope is just a holder for a CoroutineContext, and the key element in that context is a Job that becomes the parent of every coroutine launched in the scope. viewModelScope and lifecycleScope are scopes whose Job is cancelled in onCleared() / the appropriate lifecycle teardown, so cancellation cascades to all children automatically. GlobalScope's context contains no Job to parent or cancel — its coroutines are top-level orphans tied only to process lifetime. The leak mechanism is concrete: a launched lambda capturing this@Activity compiles to a class holding a strong reference to the Activity; as long as that coroutine object is reachable (and it stays reachable from GlobalScope's living machinery until it completes), the Activity can't be garbage collected.

How do you cancel background work?

🎤 Say it out loud (~35s): "Coroutine cancellation is cooperative — the coroutine has to participate. Job.cancel() sets a flag, and the coroutine actually stops at its next suspension point. A tight CPU loop with no suspending calls never observes it, so you sprinkle ensureActive() or yield(). Structured concurrency propagates cancellation to children automatically, and finally blocks still run for cleanup. The gotcha is that suspending calls in a finally of a cancelled coroutine throw immediately — you need withContext(NonCancellable) to run suspending cleanup. For durable work, WorkManager.cancelWorkById."

"Coroutine cancellation is cooperative — the coroutine has to participate. Calling Job.cancel() sets a cancellation flag, and the coroutine is actually cancelled at its next suspension point. If you have a tight CPU loop with no suspending calls, you need to check ensureActive() or call yield() periodically, otherwise cancellation is never observed. Structured concurrency propagates cancellation automatically to all children. For cleanup, finally blocks run even when a coroutine is cancelled, and you can also use invokeOnCompletion for non-suspending cleanup. For WorkManager tasks, you cancel by calling WorkManager.cancelWorkById()."

Under the hood

cancel() puts the coroutine's Job into a Cancelling state and stores a CancellationException as its cancellation cause. Every suspending function from the library checks isActive on resume; if the job is cancelling, the Continuation is resumed with that CancellationException rather than its normal result, which unwinds the state machine and runs finally blocks on the way out. That's why a non-suspending CPU loop is invisible to cancellation — there's no resume point at which to inject the exception, so ensureActive() (which throws if cancelled) or yield() (which suspends and re-checks) must be inserted manually. CancellationException is special-cased: the machinery treats it as normal cooperative cancellation and does not propagate it as a failure to the parent, which is why catching a broad Exception in a coroutine can accidentally swallow cancellation.

How do you prevent ANRs?

🎤 Say it out loud (~30s): "The rule is the main thread must never block — input dispatch must complete within ~5 seconds (broadcasts ~10) or the system shows an ANR. So I keep all IO, network, and heavy compute off the main thread: Dispatchers.IO for IO, Dispatchers.Default for CPU, then back to Dispatchers.Main to touch UI. I enable StrictMode in debug to flag disk or network on the main thread, and profile frames in the CPU Profiler. The nuance is ANRs aren't only about long work — a deadlock or a contended lock the main thread waits on triggers one just as easily."

"The rule is that the main thread must never block for more than 5 seconds — or 10 seconds for a broadcast receiver — otherwise the system shows an ANR dialog. The answer is simple in principle: keep all IO, network calls, and heavy computation off the main thread. In practice that means using Dispatchers.IO for IO-bound work and Dispatchers.Default for CPU-bound work, then bringing results back to the main thread with withContext(Dispatchers.Main) to update UI. To catch violations early, I enable StrictMode in debug builds — it will flag any disk or network access on the main thread. I also profile with Android Studio's CPU Profiler to find any main thread work that's taking longer than the frame budget."

Under the hood

ANR detection is driven by the system's ActivityManagerService arming timeout timers, most notably through input dispatch: when InputDispatcher delivers a touch event it starts a ~5s timer that the app's main Looper must cancel by finishing the event. If the main thread is stuck in a long callback or blocked on a lock, it can't drain its MessageQueue, the event isn't consumed, the timer fires, and the system collects a trace into /data/anr/traces.txt before showing the dialog. This is why the cause is "main thread didn't make progress," not "a method ran long in isolation" — a 4-second computation that yields between frames is fine, but a 6-second synchronized wait on a lock another thread holds is a textbook ANR even though the main thread is doing "nothing."

Android Threading

Explain main/UI thread.

🎤 Say it out loud (~30s): "Android runs all UI rendering, input dispatch, and lifecycle callbacks on one main thread — every view operation has to happen there, and blocking it drops frames and eventually ANRs. Under the hood the main thread is just a Looper draining a MessageQueue in an infinite loop, and you post work to it via a main-Looper Handler, View.post, runOnUiThread, or withContext(Dispatchers.Main). The subtle point is the main thread isn't special-cased magic — it's an ordinary thread that happens to host the loop, so anything you post simply queues behind the work already there."

"Android runs all UI rendering, event dispatch, and lifecycle callbacks on a single main thread. Every view operation — invalidate, layout, text updates — has to happen there. If you block the main thread, you drop frames and eventually trigger an ANR. Under the hood, the main thread is just a Looper attached to a MessageQueue — it sits in an infinite loop dequeuing and processing Messages. You post work to it via Handler(Looper.getMainLooper()), View.post(), runOnUiThread(), or withContext(Dispatchers.Main) in a coroutine."

Under the hood

ActivityThread.main() — the process entry point — calls Looper.prepareMainLooper() and then Looper.loop(), and that loop() call never returns for the life of the process; everything your app does on the main thread is a Message dispatched from inside it. Frame rendering itself is just a message: Choreographer registers a VSYNC callback that posts the traversal (measure/layout/draw) onto the same queue, so your posted work and the render pass compete for the same ~16.6ms-per-frame budget at 60Hz. That's the mechanical reason main-thread work causes jank — a long Runnable you posted sits ahead of the next doFrame message, delaying the frame past its VSYNC deadline.

Explain Handler, Looper, MessageQueue.

🎤 Say it out loud (~35s): "These three are one system. A Looper prepares a thread to process messages by owning a MessageQueue, and Looper.loop() runs an infinite read loop over it. A Handler is bound to a specific Looper and lets you post Runnables or sendMessage onto that thread's queue. The main thread gets this set up for free; on a background thread you call Looper.prepare() and Looper.loop() yourself, or just use HandlerThread. The gotcha is which Looper a Handler binds to — construct it on the wrong thread and your callbacks run on the wrong thread, which is a classic source of CalledFromWrongThreadException."

"These three work together. A Looper prepares a thread to process messages by creating and attaching a MessageQueue, then Looper.loop() enters an infinite loop reading from that queue. A Handler is bound to a Looper and gives you sendMessage() and post(Runnable) to enqueue work onto that thread. On the main thread, Android sets all of this up for you via Looper.prepareMainLooper() and Looper.loop(). On a background thread you'd have to call Looper.prepare() and Looper.loop() yourself — or just use HandlerThread, which does both and exposes getLooper() so you can attach a Handler to it."

Under the hood

Looper.prepare() stores a Looper in a ThreadLocal, so each thread has at most one — that's why a Handler created on a thread binds to that thread's looper. MessageQueue is not a simple list: it's a priority queue of Messages ordered by their when (target uptime) timestamp, and next() blocks in the native nativePollOnce() (an epoll_wait on a file descriptor) until either the head message is due or the fd is poked by an enqueue. Each Message carries a target (the dispatching Handler), a callback Runnable or what code, and a next pointer; after dispatch, Message.recycle() returns it to a free pool (capped at 50) to avoid per-message allocation. Handler.post(r) just wraps r in a Message with target = this and inserts it by timestamp.

Looper.loop():
  for (;;) {
    Message msg = queue.next();   // blocks in nativePollOnce (epoll) until 'when' is due
    msg.target.dispatchMessage(msg);  // -> handler.handleMessage / runnable.run
    msg.recycleUnchecked();           // back to the pooled free list
  }

What is HandlerThread?

🎤 Say it out loud (~30s): "HandlerThread is a Thread subclass that runs a Looper for you and exposes getLooper() after start(), so you can attach a Handler and post serialized work onto that one thread — messages run one at a time in order, without a thread pool. It's ideal for APIs that must deliver callbacks on a dedicated thread, like camera preview or media events. The gotcha is you must call quit() or quitSafely() when done; otherwise the looper blocks forever and the thread leaks. And getLooper() can return null if you call it before the looper is prepared."

"HandlerThread is a Thread subclass that sets up a Looper for you and exposes getLooper() after you call start(), so you can attach a Handler to it and post work onto that specific thread. It gives you a sequential background message queue without the overhead of a full thread pool — messages are processed one at a time in order. It's particularly useful for APIs that deliver callbacks on a specific thread, like camera preview callbacks or media player events. One important detail: always call quit() or quitSafely() when you're done with it, to stop the looper and let the thread exit cleanly."

Under the hood

HandlerThread.run() calls Looper.prepare(), then inside a synchronized block sets mLooper and calls notifyAll(), then enters Looper.loop(). getLooper() is the matching half: if mLooper is still null it wait()s on the same lock until run() signals it — that handshake is why getLooper() blocks the caller until the looper is actually ready (and returns null only if the thread never started). quitSafely() sets a flag and posts a "remove all future messages but drain already-due ones" instruction so MessageQueue.next() returns null, causing loop() to return and the thread's run() to finish; quit() is the abrupt version that discards even pending due messages. Without either, next() never returns null and the native thread parks in epoll indefinitely.

Why can't you update UI from background thread?

🎤 Say it out loud (~30s): "Android's view system is deliberately not thread-safe. ViewRootImpl records the thread that created the hierarchy and, on any mutation, calls checkThread() — if you're not on that thread it throws CalledFromWrongThreadException. It's a conscious design trade: making views thread-safe would require locking on every view operation, which would be ruinously expensive given how many there are per frame. So the contract is create-and-mutate-on-main only. The subtle gotcha is the check only exists once a view is attached to a window — before attach you can sometimes mutate off-thread and get away with it, which masks the bug."

"Android's view hierarchy is deliberately not thread-safe. ViewRootImpl checks that modifications come only from the thread that originally created the view hierarchy — the main thread — and throws CalledFromWrongThreadException if they don't. This is a conscious design choice: if views were thread-safe, you'd need synchronization on every single view operation, which would be prohibitively expensive. The contract is simple — create and mutate views on the main thread only, and use any of the standard mechanisms to post back to it from a background thread."

Under the hood

When a view is attached to a window, a ViewRootImpl is created on the main thread and stashes mThread = Thread.currentThread(). Any operation that requests a redraw — invalidate(), requestLayout(), setting text — eventually calls ViewRootImpl.checkThread(), which simply does if (mThread != Thread.currentThread()) throw new CalledFromWrongThreadException(...). There's no lock anywhere in the hot path of measure/layout/draw, which is exactly the performance win the single-thread contract buys: thousands of view operations per frame run with zero synchronization overhead. The check is intentionally cheap (one reference comparison) and is the framework's way of converting a silent data-race into a loud, immediate crash.

Binder thread pool.

🎤 Say it out loud (~30s): "Incoming IPC — like a bound service's AIDL call — is dispatched on a thread from the app's Binder thread pool, which is system-managed and capped at 16 threads. Because those run concurrently, my AIDL implementation has to be thread-safe if it touches shared state. The flip side is outgoing Binder calls are synchronous by default — they block the caller until the remote returns — so I must never make them from the main thread. The gotcha people miss is that even a callback you receive over Binder arrives on a Binder thread, so you still have to hop back to the main thread to touch UI."

"When your app receives an incoming IPC call — for example through a bound service's AIDL — Android dispatches it on a thread from the app's Binder thread pool. The pool goes up to 16 threads maximum, with at least 1 guaranteed. These threads are managed by the system and run concurrently, which means your AIDL implementation must be thread-safe if it touches any shared state. The other side of the coin is outgoing calls: Binder calls from your app to another process block the calling thread until the remote method returns, because they're synchronous by default. That means you must never make Binder calls from the main thread."

Under the hood

Each process that hosts Binder objects opens /dev/binder and registers a pool with the kernel driver via ProcessState, capped by DEFAULT_MAX_BINDER_THREADS (15 spawnable + the main caller = effectively 16). Pool threads sit in a BINDER_WRITE_READ ioctl loop blocked in the kernel; when a transaction arrives, the driver picks a thread and hands it the parceled transaction to run the target object's onTransact. A synchronous (non-oneway) outgoing call writes a BC_TRANSACTION command and then blocks the calling thread in the kernel waiting for the matching BR_REPLY — the thread is genuinely parked in the driver, which is precisely why issuing it on the main thread can produce an ANR if the remote is slow.

WorkManager vs coroutine.

🎤 Say it out loud (~30s): "The dividing line is durability. WorkManager is for deferrable work that must survive process death and reboots — it persists jobs to a database, retries with backoff, supports chaining, and honors constraints like network or charging. Coroutines in viewModelScope/lifecycleScope are tied to a component and die when it does. My rule: if the user could kill the app and the work still has to finish — uploads, syncs — use WorkManager; if it's request/response within one screen, use coroutines. The gotcha is people reach for WorkManager for immediate in-screen work, paying DB and scheduling overhead they don't need."

"The key distinction is durability. WorkManager is for deferrable background work that must survive process death and device reboots — it persists work to a database, handles retries, supports chaining, and respects OS-level constraints like network availability and charging state. Coroutines scoped to viewModelScope or lifecycleScope are tied to the component's lifecycle — they're cancelled when the component is destroyed. My rule of thumb is: if the user could kill the app and the work still has to complete — like uploading logs or syncing data — use WorkManager. If the work is request/response within a single screen session, use coroutines."

Under the hood

WorkManager persists every WorkRequest as a row in a Room database (the WorkSpec table) the moment you enqueue it — that durable record is what survives process death and reboot. On modern Android it delegates actual scheduling to JobScheduler, which hands the constraints and persistence to the system's JobSchedulerService; a BOOT_COMPLETED receiver re-reads the database and reschedules surviving work after a reboot. The state machine (ENQUEUED → RUNNING → SUCCEEDED/FAILED/RETRY) and exponential backoff are all driven from that table. A viewModelScope coroutine has no such persistence — it's purely in-memory state tied to a Job cancelled in onCleared(), so it cannot by construction outlive the process.

Foreground service vs WorkManager.

🎤 Say it out loud (~30s): "A foreground service runs with a mandatory ongoing notification, which signals active user-visible work and makes the OS very reluctant to kill it — right for music, navigation, or a large active download. WorkManager is for deferred, best-effort work the OS can batch, defer, or run in Doze. My rule: if the user is actively aware and needs real-time progress, foreground service; if it's 'run when conditions are right,' WorkManager. The modern gotcha is foreground services now require a declared foregroundServiceType and have tightened background-start restrictions, so you can't just start one from anywhere."

"A foreground service runs with an ongoing notification visible to the user, which makes it nearly immune to process killing by the OS — that makes it right for long-running user-visible tasks like music playback, GPS navigation, or a large file download. WorkManager is for deferred background tasks that can be queued, rescheduled, and potentially batched — the OS may defer them, especially in Doze mode. The way I choose is: if the user is actively aware the work is happening and needs real-time feedback, use a foreground service. If the task is best-effort and can run whenever conditions are right, use WorkManager."

Under the hood

A foreground service raises the process's oom_adj score in the kernel's low-memory-killer ranking — the LMK kills processes in priority order under memory pressure, and a foreground-service process sits near the top alongside the visible app, which is the mechanical reason it's "nearly immune" rather than truly immune. The mandatory notification is the OS enforcing a visibility contract: you must call startForeground() within a few seconds of starting or the system throws and may kill the service. WorkManager sits at the opposite end — its jobs run through JobScheduler, which intentionally batches and defers them to align with Doze maintenance windows and other system wake-ups to conserve battery, so they get lower scheduling priority by design. WorkManager can itself run a long task as a foreground service via setForeground() when it needs that immunity.

How do you communicate from worker thread to UI?

🎤 Say it out loud (~30s): "In preference order: withContext(Dispatchers.Main) { ... } inside a coroutine is cleanest; Handler(Looper.getMainLooper()).post { } for non-coroutine callbacks like legacy camera/sensor APIs; runOnUiThread { } as a thin wrapper over the same; or post state through LiveData.postValue/StateFlow with the UI observing on main. The one thing to avoid is runBlocking on the main thread — that synchronously blocks the UI waiting on background work, the exact opposite of the goal. The subtle gotcha is LiveData.postValue conflates rapid updates, so intermediate values can be dropped."

"There are a few options, and I'd rank them in preference order. First, withContext(Dispatchers.Main) { updateUI() } inside a coroutine — that's the cleanest and most idiomatic. Second, Handler(Looper.getMainLooper()).post { ... } for non-coroutine callbacks like legacy camera or sensor APIs. Third, Activity.runOnUiThread { ... }, which is just a convenience wrapper around the same thing. Fourth, LiveData.postValue() or StateFlow.emit() from the background, with the UI observing on the main thread. The one thing to avoid is runBlocking on the main thread — that synchronously blocks the UI thread waiting for background work, which is exactly the opposite of what you want."

Under the hood

Every one of these mechanisms ultimately funnels into the same place — a Message posted to the main Looper's MessageQueue. runOnUiThread literally checks if (Thread.currentThread() != mUiThread) mHandler.post(action); LiveData.postValue posts a runnable to the main thread that then sets the value and notifies active observers; withContext(Dispatchers.Main) resumes the coroutine's Continuation by dispatching it onto Handler(mainLooper). Dispatchers.Main on Android is HandlerDispatcher wrapping exactly that handler, and Dispatchers.Main.immediate skips the post entirely when already on the main thread. runBlocking is the anti-pattern because it parks the current thread in a nested event loop until its body completes — if that thread is the main thread, the real main Looper can't dispatch frames, so the UI freezes.

How can Handler cause memory leak?

🎤 Say it out loud (~30s): "A non-static inner Handler in an Activity captures an implicit reference to the Activity. Post a delayed Runnable — say 30 seconds — and that message sits in the MessageQueue the whole time, forming a chain: queue holds the message, message holds the handler, handler holds the Activity. So even after the user leaves and the Activity is destroyed, it can't be GC'd until the message drains. The fix is removeCallbacksAndMessages(null) in onDestroy(), or lifecycleScope.launch which auto-cancels, or a static handler with a WeakReference."

"The problem comes from how inner classes work in Java and Kotlin. A non-static inner Handler inside an Activity holds an implicit reference to the enclosing Activity instance. If you post a Runnable with a delay — say 30 seconds — that Runnable stays in the MessageQueue for 30 seconds. The chain is: MessageQueue holds the Message, Message holds the Handler, Handler holds the Activity. So even after the user navigates away and the Activity is destroyed, the GC can't collect it because that live chain is still rooted. The fix is either to call handler.removeCallbacksAndMessages(null) in onDestroy(), switch to lifecycleScope.launch which is cancelled automatically, or use a static inner class with a WeakReference<Activity>."

Under the hood

The leak is rooted in a GC root: the main thread is alive, so its Looper and the MessageQueue it owns are reachable, and any Message enqueued there is reachable too. A Java/Kotlin non-static inner (or anonymous) class compiles to a class with a synthetic this$0 field holding the outer Activity, and the Handler stores itself as the message's target — so the reference chain Thread → Looper → MessageQueue → Message.target(Handler) → Handler.this$0(Activity) is fully GC-reachable. The garbage collector traces reachability from roots, so it cannot reclaim the Activity until the message is dispatched or removed. A WeakReference<Activity> breaks the chain because the GC ignores weak references when determining reachability, so the Activity can be collected and the handler simply finds a null referent.

IPC

What is Binder?

🎤 Say it out loud (~35s): "Binder is Android's high-performance IPC, implemented as a kernel driver. It lets one process call methods on objects in another as if they were local — the proxy/stub machinery hides the boundary. What makes it fast is a single-copy design: the kernel copies the marshaled data once, from the caller's buffer directly into the callee's mapped buffer, versus the two copies pipes or sockets typically need. It also carries object identity, transactions, and death notifications. It's the backbone of essentially every system service. The gotcha is the ~1MB per-process transaction buffer — overflow it and you get TransactionTooLargeException."

"Binder is Android's high-performance IPC mechanism, implemented as a kernel driver. The key thing it does is let one process call methods on objects in another process as if they were local — you never really see the cross-process boundary in the code. What makes it fast is a single-copy design: the Binder kernel module copies data from the caller's address space directly into the callee's, whereas traditional Unix IPC like pipes or sockets often requires two copies. Binder also supports object identity — remote objects are uniquely identified — transactions, and death notifications so you know when the remote process dies. It's the backbone of essentially all Android system services: Activity Manager, Package Manager, and so on."

Under the hood

The single-copy trick relies on mmap: when a process opens /dev/binder, the driver maps a receive buffer into that process's address space. On a transaction the kernel does one copy_from_user out of the sender's Parcel straight into the receiver's mapped buffer — the receiver reads it without a second copy, which is the win over the userspace→kernel→userspace double copy of pipes. "Object identity" is enforced by the driver: each Binder object has a kernel node, and a reference handed to another process becomes a handle the driver translates back to the same node, so identity survives crossing the boundary. The userspace side is the IBinder/transact(code, data, reply, flags) interface; everything higher up (AIDL, Messenger, system service proxies) is generated code sitting on top of that single transact primitive.

What is AIDL?

🎤 Say it out loud (~30s): "AIDL — Android Interface Definition Language — is an IDL that generates the stub and proxy boilerplate for Binder IPC. You declare your interface in a .aidl file; the build generates a server-side Stub extending Binder and a client-side Proxy. A client call marshals args into a Parcel, Binder transports it, and the Stub unmarshals and dispatches it on a Binder pool thread. It supports primitives, String, Parcelable, List, and Map. The gotcha is that because methods run on Binder threads concurrently, your Stub implementation must be thread-safe."

"AIDL stands for Android Interface Definition Language. It's an IDL that generates the stub and proxy code you need for Binder IPC. You define your interface in a .aidl file, and the build system generates a Stub on the server side that extends Binder, and a Proxy on the client side. When the client calls a method, the proxy marshals the arguments into a Parcel, the Binder kernel transports it, and the server's Stub unmarshals it and invokes the implementation on one of the Binder thread pool threads. AIDL supports primitive types, String, Parcelable objects, List, and Map."

Under the hood

The AIDL compiler assigns each interface method a stable integer transaction code (TRANSACTION_foo = IBinder.FIRST_CALL_TRANSACTION + n). The generated Proxy.foo() writes an interface token plus each argument into a Parcel in declaration order, calls mRemote.transact(TRANSACTION_foo, data, reply, 0), then reads the result out of the reply Parcel. On the other side, Stub.onTransact(code, data, reply, flags) is a big switch on the code that reads the args back in the same order, calls the real implementation, and writes the return value into reply. Stub.asInterface(binder) is the bridge: if the binder is local it returns the implementation directly (no IPC), otherwise it wraps it in a Proxy. This is why argument read/write order must match exactly and why changing the method order in a shipped .aidl breaks binary compatibility.

AIDL vs Messenger.

🎤 Say it out loud (~30s): "Messenger wraps a Handler and ships Message objects over Binder; because everything funnels through one Handler, calls are serialized — no concurrency — which keeps it simple and inherently thread-safe. AIDL defines a typed, multi-method interface where calls arrive concurrently on Binder threads, so it's more powerful but needs you to handle thread safety. My rule: Messenger for simple sequential request/response, AIDL when you need multiple signatures, concurrency, or rich custom types. The gotcha is people pick AIDL for its 'power' and then forget their implementation now runs on multiple threads."

"Messenger wraps a Handler and sends Message objects over Binder. Because it goes through a Handler, calls are sequential — there's no concurrency — which keeps it simple. It's a good fit when you just need to pass simple messages between processes. AIDL is for defining a typed, multi-method interface where calls can arrive concurrently on Binder threads. It's more powerful but also more complex to set up. My decision rule is: use Messenger for simple request/response messaging; use AIDL when you need multiple method signatures, concurrent access, or complex custom data types."

Under the hood

Messenger is actually built on top of AIDL — internally it holds an IMessenger Binder interface, and Messenger.send(msg) is a single AIDL call that ships the Message (its what, arg1/arg2, Bundle data, and replyTo Messenger) across the boundary. On the receiving side the framework's Stub posts that Message to the target Handler's Looper, which is why delivery is automatically serialized through one queue — the single-thread guarantee is just the Looper contract, so you never write a lock. AIDL exposes the raw multi-method onTransact switch directly, so each method can be dispatched on a different Binder pool thread concurrently. In short: Messenger trades AIDL's concurrency for the safety and simplicity of a single message queue.

Synchronous vs asynchronous IPC.

🎤 Say it out loud (~30s): "Standard AIDL calls are synchronous — the caller blocks until the remote returns, which is dangerous on the main thread because of ANR risk. To make IPC async I have options: mark a method oneway so it's fire-and-forget with no return or exception; use Messenger for sequential message passing; or pass an AIDL callback object the server invokes on a later Binder transaction. The gotcha with oneway is that it not only drops the return value but also swallows exceptions, and oneway calls to the same binder are serialized, so they aren't a free parallelism win."

"Standard AIDL calls are synchronous — the calling thread blocks until the remote method returns, which makes them dangerous on the main thread because you risk an ANR. There are a few patterns to make IPC asynchronous. First, you can declare a method as oneway in the AIDL file: it becomes fire-and-forget with no return value and no exception propagation. Second, you can use Messenger for sequential message passing. Third, you can implement a callback interface: the client passes an AIDL callback object to the server, and the server calls back on a separate future Binder transaction. On Android 10 and above, android.os.IBinder.FLAG_ONEWAY achieves the same effect programmatically."

Under the hood

A normal transaction sets no flags, so the driver writes the caller's command and blocks the caller in the kernel until the BR_REPLY comes back — the synchronous round trip. A oneway call sets FLAG_ONEWAY (== TF_ONE_WAY): the driver enqueues the transaction into the target's work queue and immediately returns control to the caller without waiting for a reply, which is why there's no return value and exceptions can't propagate back. The driver also serializes oneway transactions destined for the same binder node into a per-node async queue (with a smaller async transaction buffer, ~half the ~1MB), so they run one after another in submission order rather than truly in parallel. A callback interface is just the reverse direction — the client's callback object is itself a Binder the server holds a handle to and transacts on, which is why those callbacks arrive on the client's Binder threads, not its main thread.

Parcelable vs Serializable.

🎤 Say it out loud (~30s): "Parcelable is Android's hand-written serialization — you implement writeToParcel and a CREATOR, verbose but fast because it avoids reflection and writes straight into a shared-memory Parcel with little garbage. Serializable is Java's reflection-based serialization: lots of temporary objects, much slower. So always Parcelable for IPC and Bundle extras — and in Kotlin @Parcelize generates the boilerplate. Serializable is fine for in-process file persistence but not high-frequency IPC. The gotcha is a Parcel is a transient transport, not a storage format — never persist one to disk, its layout isn't version-stable."

"Parcelable is Android's custom serialization interface — you implement writeToParcel and a CREATOR yourself, which is verbose but fast: it avoids reflection entirely and writes directly to a shared memory Parcel, producing very little garbage. Serializable is Java's standard serialization, which uses reflection, creates a lot of temporary objects, and is significantly slower. The rule is: always use Parcelable for Android IPC and Bundle extras — and in Kotlin you can just annotate with @Parcelize and the plugin generates the boilerplate for you. Serializable is acceptable for in-process persistence like writing an object to a file, but never for high-frequency IPC where the overhead compounds."

Under the hood

Serializable is a marker interface; the JVM's ObjectOutputStream walks the object graph with reflection, writing class descriptors, field names, and types into a self-describing stream — that metadata and the reflective field access are the cost, and a wrong/missing serialVersionUID makes deserialization throw InvalidClassException across versions. Parcelable does none of that: writeToParcel calls explicit primitive writers (writeInt, writeString, …) that append directly to the Parcel's native byte buffer, and the static CREATOR.createFromParcel reads them back in the same order with no type discovery. Because there's no embedded schema, a Parcel is purely a positional, transient wire format meant to be marshaled into Binder's transaction buffer and immediately unmarshaled — its byte layout can change between OS versions, which is exactly why persisting a Parcel to disk is unsafe.

How do you handle remote service death?

🎤 Say it out loud (~30s): "I register a DeathRecipient via IBinder.linkToDeath. When the remote process dies the system fires binderDied() on a Binder thread, and there I unlink the recipient, null my binder reference, and either rebind or surface unavailability to the user. For bound services I also get onServiceDisconnected() on the ServiceConnection. I use both: onServiceDisconnected only fires for bound services, while DeathRecipient works for any raw binder handle. The gotcha is binderDied runs on a Binder thread, so any UI reaction has to hop back to the main thread."

"You register a DeathRecipient by calling IBinder.linkToDeath(recipient, 0). When the remote process dies, the system fires binderDied() on a Binder thread. Inside that callback you should unlink the recipient, null out your binder reference, and then either attempt to rebind or notify the user that the service is unavailable. For bound services, the system also calls onServiceDisconnected() on your ServiceConnection — I'd use both together for robust handling, because onServiceDisconnected only fires for bound services while DeathRecipient works for any direct Binder handle."

Under the hood

linkToDeath registers the recipient with the kernel Binder driver against the remote binder node. When the owning process dies, the driver detects the closed /dev/binder fd, walks the list of nodes that process owned, and sends a death notification to every process holding a reference with a registered recipient — your side receives it on a Binder pool thread and the framework invokes binderDied(). This is fundamentally more reliable than polling because it's kernel-driven and fires even on an abrupt SIGKILL (e.g. the LMK reaping the process), where the remote never gets a chance to run cleanup code. onServiceDisconnected is a higher-level callback the framework synthesizes only for the bound-service connection it manages, which is why a direct binder handle you obtained some other way needs the lower-level DeathRecipient.

What should not be sent over Binder?

🎤 Say it out loud (~30s): "Mainly large data. Binder's per-process transaction buffer is roughly 1MB, shared across all in-flight transactions, so shipping a bitmap or big byte array in a Parcel throws TransactionTooLargeException — which is sneaky because it often surfaces inside onSaveInstanceState as an unrelated-looking crash. For big payloads I pass a FileDescriptor over Binder via MemoryFile/SharedMemory and share memory instead. And you can only send types Binder can serialize — primitives, String, Parcelable, List, Map — never arbitrary Java objects, since Binder has no reflection-based serialization."

"The main thing to avoid is large data. Binder has a per-process transaction buffer of roughly 1 MB, and if you exceed it by sending a bitmap or a large byte array in a Parcel, you get a TransactionTooLargeException — which can be especially confusing because it can surface in onSaveInstanceState as an apparently unrelated crash. For large payloads, use shared memory via MemoryFile or SharedMemory and pass only the FileDescriptor over Binder. Also, you can only send types that Binder knows how to serialize: primitives, String, Parcelable objects, List, and Map. You cannot send arbitrary Java objects — Binder has no reflection-based serialization."

Under the hood

The ~1MB limit is the size of the mmap'd transaction buffer the driver allocated for the process, and crucially it's shared across every concurrent transaction in that process — so the effective headroom for any single call is smaller than 1MB and depends on what else is in flight, which is why TransactionTooLargeException is intermittent and hard to reproduce. The onSaveInstanceState connection is that the saved Bundle is parceled and sent to the system ActivityManagerService over Binder; stuffing a large bitmap or list into instance state overflows the buffer at save time, far from where the data was created. Passing a FileDescriptor sidesteps the limit because the fd is a tiny handle — the driver duplicates it into the receiving process via the kernel, and the actual bytes live in shared memory (ashmem) that both processes map directly, transferring nothing through the transaction buffer.

Memory

How GC works conceptually.

🎤 Say it out loud (~35s): "ART uses a generational, mostly-concurrent collector. New objects land in the Young generation's Eden space, and most die there fast in a cheap minor GC; survivors get promoted to the Old generation, collected less often but with more work. There's also a Large Object Space for big allocations like bitmaps. Marking runs concurrently with app threads so it mostly avoids stop-the-world pauses. The practical takeaway is that churning short-lived objects isn't free — it raises GC frequency and causes jank — so I profile allocation hot spots in the Memory Profiler. The gotcha is GC reclaims memory but can't fix a leak: a reachable object is never collected no matter how much pressure there is."

"ART uses a generational garbage collector. New objects are allocated in the Young generation — specifically the Eden space — and most short-lived objects die there quickly in what's called a minor GC, which is fast. Objects that survive multiple GC cycles get promoted to the Old generation, which does major GC less frequently but with more work. ART also has a Large Object Space for objects that exceed a size threshold. GC pauses are minimized by running marking concurrently with the app threads, so the GC doesn't have to stop the world for the full collection. The practical implication for Android development is: allocating a lot of short-lived objects is not free — it increases GC frequency, which can cause jank. That's why I profile with Android Studio's Memory Profiler to catch allocation hot spots."

Under the hood

ART's default foreground collector is Concurrent Copying (CC) with a moving, region-based heap: allocation is a near-free bump-the-pointer in a thread-local allocation buffer (TLAB), and the generational variant collects the young region frequently while moving (compacting) survivors, which also eliminates fragmentation. Because objects move, ART uses read barriers — small instrumented reads the JIT/AOT compiler inserts — so application threads can keep running while the collector relocates objects, limiting stop-the-world to brief root-marking and flip phases (sub-millisecond on modern devices). The generational hypothesis it exploits is empirical: most objects die young, so concentrating effort on the young region collects the most garbage for the least work. A leak defeats all of this because reachability, not age, decides collection — an object still reachable from a GC root is live by definition and survives every cycle.

What causes memory leaks in Android?

🎤 Say it out loud (~30s): "The root cause is always one shape: a long-lived object holds a reference to a short-lived one — usually an Activity or Fragment — so the GC can't reclaim it. The usual suspects: static fields holding a Context or View; non-static inner classes and anonymous listeners capturing this; a Handler with delayed messages; unregistered receivers, sensor listeners, or undisposed Rx subscriptions; Fragment ViewBinding kept past onDestroyView; and uncancelled coroutine scopes. The interviewer's follow-up gotcha is that a leak isn't about allocating too much — it's about reachability, which is why GC can't help and tools like LeakCanary trace the retaining chain."

"The root cause is always the same: a long-lived object holds a reference to a short-lived one — typically an Activity or Fragment — preventing the GC from collecting it. There are six common sources I watch for. First, static fields that hold a Context or a View — those live as long as the process. Second, non-static inner classes including anonymous Runnables and listeners, which carry an implicit this reference to the enclosing class. Third, a Handler with delayed messages, as I described above. Fourth, unregistered listeners and receivers — broadcast receivers, sensor listeners, and RxJava subscriptions that are never disposed. Fifth, Fragment ViewBinding references held beyond onDestroyView(). And sixth, coroutine scopes that are not cancelled when the lifecycle ends."

Under the hood

A leak is precisely an unintended path from a GC root to an object you meant to free. The GC roots that matter on Android are static fields (reachable from the class loaded into the permanent class space), live thread stacks (including the main thread's Looper/MessageQueue), JNI global references, and active synchronization monitors. The reachability tracer starts from those roots and marks everything transitively reachable as live; anything not marked is collected. Every listed cause is just a different edge from a root to an Activity: a static field is a direct root edge; an anonymous listener's synthetic this$0 field is an edge from whatever long-lived object registered it; a queued Message is an edge from the main thread's live queue. LeakCanary works by watching destroyed objects with a WeakReference, forcing a GC, and if the referent survives, dumping the heap and computing the shortest strong reference path from a GC root to it — that path is the leak.

Activity context vs Application context.

🎤 Say it out loud (~30s): "Activity context is short-lived — tied to the Activity instance — and carries the Activity's theme and configuration, so it's what you need for UI work like inflating layouts and showing dialogs. Application context lives for the whole process, so it's right for singletons, services, and content providers. The hard rule: never store an Activity context in a singleton or static field, or you pin the Activity and leak it. The gotcha that bites people is using applicationContext to inflate a themed view or show a dialog — it lacks the activity theme, so you get wrong styling or an outright crash."

"Activity context has a shorter lifetime — it's tied to the Activity instance — and it carries the Activity's theming and configuration, which is why you need it for UI operations like inflating layouts and creating dialogs. Application context lives as long as the app process itself, so it's the right choice for singletons, background services, and content providers, or anything that has to outlive a single Activity. The rule I follow is: never store Activity context in a singleton or a static field, because you'll prevent the Activity from being garbage collected. Use Application context in those long-lived places instead."

Under the hood

Both are subclasses of Context, but they're backed by very different objects. The Activity is a Context (it extends ContextThemeWrapper → ContextWrapper), so it holds the full window, the theming Resources.Theme resolved from the activity's android:theme, and a back-reference into the view hierarchy — which is exactly why it can inflate themed layouts and host dialogs, and exactly why retaining it leaks the whole UI tree. The Application context is a single long-lived ContextImpl-backed instance with no activity theme and no window token. A dialog needs a window token from an Activity to attach to, so Dialog(applicationContext) throws BadTokenException; and inflating with the application context resolves only the base application theme, silently dropping activity-level style overrides.

Handler leak. (also covered under Android Threading)

🎤 Say it out loud (~30s): "Same mechanism as before: a non-static inner Handler in an Activity, plus any delayed message, keeps the Activity alive until the message drains, because the live main-thread queue holds message→handler→Activity. Fix it with removeCallbacksAndMessages(null) in onDestroy(), or better, use lifecycleScope which cancels automatically. The gotcha is that even a non-delayed message can leak briefly if it's queued behind a backlog — the window is just usually too short to notice."

"Covered in the Android Threading section above. The short version: a non-static inner Handler in an Activity plus any delayed messages means the Activity cannot be GC'd until those messages drain from the queue. Fix it by calling removeCallbacksAndMessages(null) in onDestroy(), or better yet, use lifecycleScope which handles cancellation automatically."

Under the hood

The retaining chain is identical to the one in the Android Threading section — main Thread → Looper → MessageQueue → Message.target → Handler → outer Activity — and it's GC-reachable because the main thread is a permanent GC root for the life of the process. removeCallbacksAndMessages(null) walks the MessageQueue's singly-linked list and unlinks every Message whose target is this handler (the null argument means "regardless of what/callback"), recycling them to the pool and thereby severing the queue→message edge so the Activity becomes unreachable. lifecycleScope avoids the problem at the source: its Job is cancelled in the destroy callback, which resumes any suspended continuations with CancellationException and lets their captured references — including the implicit Activity reference — be released immediately.

Fragment view binding leak.

🎤 Say it out loud (~30s): "Fragments have two lifetimes: the Fragment instance can outlive its view, since the view is destroyed in onDestroyView() on config changes and back-stack pops. ViewBinding holds references to every view, so if you keep it in a field and don't null it in onDestroyView, you pin the whole destroyed view hierarchy. The fix is _binding = null in onDestroyView() with a non-null delegate over the nullable field. The gotcha is async callbacks firing after onDestroyView — they touch the binding and NPE, which is why you must guard against the view being gone, not just null the field."

"The problem here is that Fragments have two distinct lifetimes: the Fragment instance survives configuration changes and back-stack operations, but the Fragment's view is destroyed in onDestroyView(). ViewBinding holds references to views. So if you store the binding in a field and forget to null it out in onDestroyView(), the binding keeps the entire view hierarchy alive even after the views have been destroyed. The fix is to always set _binding = null in onDestroyView() and access the binding through a non-null delegate backed by that nullable field — so safe access is guaranteed during the view's lifetime and the reference is released when the view is gone."

private var _binding: FragmentFooBinding? = null
private val binding get() = _binding!!

override fun onCreateView(...) = FragmentFooBinding.inflate(inflater, container, false)
    .also { _binding = it }.root

override fun onDestroyView() {
    super.onDestroyView()
    _binding = null
}

Under the hood

A generated ViewBinding is a plain class holding hard references to the root view and every view it found via findViewById during inflate. The two-lifetime mismatch is structural: FragmentManager retains the Fragment instance across onDestroyView/onCreateView cycles (a back-stacked or retained fragment object persists), while the inflated View tree is torn down and a fresh one created on re-display. If the binding field outlives onDestroyView, it keeps the old, detached view tree — and its Context/parent references — reachable from the surviving Fragment, leaking an entire screen's worth of views. Nulling the field in onDestroyView removes that edge. The _binding!! accessor isn't just ergonomics: it converts the dangerous "stale binding after teardown" case into an immediate, traceable NullPointerException instead of a silent reference to dead views — which is why an androidx.lifecycle-aware delegate that clears on onDestroyView is the robust generalization.

Bitmap OOM.

🎤 Say it out loud (~30s): "Bitmaps are huge — a 4K image at 3840×2160 in ARGB_8888 is about 31MB, since it's 4 bytes per pixel. OOM hits when you decode full-resolution images you don't need at that size. The fix is downsampling with BitmapFactory.Options.inSampleSize before decoding, or better, using Glide or Coil, which downsample to the target view, pool and reuse bitmap memory, and cancel requests tied to lifecycle. The gotcha is that since Android 8 bitmap pixel data lives in native memory, so it won't show up in your Java heap dump — you have to look at native/graphics memory to see the real footprint."

"Bitmaps are large objects stored in native memory under ART. A single 4K photo at 3840 by 2160 pixels in ARGB_8888 format consumes roughly 31 MB. OOM happens when you load full-resolution images without downsampling them first. The fix is to use BitmapFactory.Options.inSampleSize to downsample to the size you actually need before loading into memory — or better yet, use an image loading library like Glide or Coil, which handles downsampling automatically, pools and reuses bitmap memory, and ties the loading lifecycle to the component so it cancels requests when the screen is gone. The other thing to avoid is holding multiple large bitmaps in memory at the same time."

Under the hood

A bitmap's memory cost is purely width × height × bytesPerPixel, and the format sets the last term: ARGB_8888 is 4 bytes/pixel (8 bits each for A/R/G/B), so 3840×2160×4 ≈ 31.6MB, while RGB_565 halves that to 2 bytes/pixel at the cost of color depth. inSampleSize works at decode time: a value of n tells the native decoder to read every n-th pixel in each dimension, so inSampleSize=2 produces an image with ¼ the pixels and ¼ the memory — and because the subsampling happens in the decoder, the full image is never fully materialized in memory. Since Android 8.0 (API 26) pixel data moved from the Java heap into native heap under ART, freed via NativeAllocationRegistry when the Bitmap becomes unreachable; this dodges the old OutOfMemoryError-on-a-small-Java-heap problem but means bitmap memory is invisible in a Java heap dump and must be read from the "Native"/"Graphics" categories in the Memory Profiler.

How to debug memory leaks.

🎤 Say it out loud (~30s): "My workflow has four steps. LeakCanary in debug builds auto-detects leaks and gives me the full retaining reference chain — that removes most of the guesswork. Android Studio's Memory Profiler for heap dumps and before/after snapshot diffs around a suspected scenario. adb shell dumpsys meminfo for a quick CLI view of PSS and heap. And in any tool, I hunt for classes with unexpectedly high instance counts — multiple instances of an Activity that should be a singleton is a dead giveaway. The gotcha is forcing a GC before snapshotting, otherwise garbage that's merely uncollected-yet looks like a leak."

"My go-to workflow has four steps. First, I add LeakCanary to the debug build — it automatically detects leaks and fires a notification with the full reference chain leading to the leaking object, which takes most of the guesswork out. Second, I use Android Studio's Memory Profiler to take heap dumps and compare snapshots before and after a suspected leak scenario. Third, for a quick command-line view, adb shell dumpsys meminfo shows PSS, heap usage, and retained objects per process. Fourth, in any of those tools I look for classes with unexpectedly high instance counts — for example, if I see multiple instances of an Activity class that should only ever have one at a time, I have a leak."

Under the hood

LeakCanary hooks the lifecycle (via ObjectWatcher) to wrap each destroyed Activity/Fragment/ViewModel in a KeyedWeakReference tied to a ReferenceQueue. After the object should be dead it triggers a GC and checks the queue: if the weak reference wasn't enqueued, the object is still strongly reachable — a leak — so it dumps the heap (an HPROF file) and runs Shark, which parses HPROF and computes the shortest strong path from a GC root to the retained object. That "shortest path" framing is the key insight every tool shares: a heap dump is a graph of objects and references, and leak analysis is graph traversal from roots. dumpsys meminfo reports at a coarser level — PSS (Proportional Set Size) attributes shared pages fairly across processes — useful for spotting growth trends but not the retaining chain, which is why you escalate to a heap dump to find the actual culprit reference.

How to respond to low-memory conditions.

🎤 Say it out loud (~30s): "The hook is onTrimMemory(level) on Application or any ComponentCallbacks2. The system passes escalating severity levels — RUNNING_LOW, RUNNING_CRITICAL, UI_HIDDEN, BACKGROUND, and so on — and I release caches, bitmaps, and other rebuildable memory proportional to the urgency. In a ViewModel I'd drop in-memory caches I can rebuild from the DB. onLowMemory() is the legacy single-level callback. The gotcha is that onTrimMemory levels signal why — UI_HIDDEN means the app just went to background, while COMPLETE/CRITICAL mean you're next in line to be killed — so you should react differently to each, not treat them uniformly."

"The right hook is Application.onTrimMemory(level), or ComponentCallbacks2.onTrimMemory(level) on any component. The system calls this with different severity levels — TRIM_MEMORY_RUNNING_LOW, TRIM_MEMORY_RUNNING_CRITICAL, TRIM_MEMORY_UI_HIDDEN, TRIM_MEMORY_BACKGROUND, and others — and you respond by releasing caches, bitmaps, and any other non-essential memory proportional to the urgency of the level. In a ViewModel, for instance, I'd clear any in-memory caches that can be rebuilt from the DB. For APIs below 14 there's the older onLowMemory() callback, but onTrimMemory is what you'd use in any modern codebase."

Under the hood

onTrimMemory is driven by the same oom_adj priority machinery the low-memory killer uses. ActivityManagerService tracks every process's adj score (foreground = lowest/safest, empty cached = highest/first-to-die) and, as system memory tightens, dispatches trim callbacks down the list with a level matching each process's current standing — that's why the levels split into two families: the RUNNING_* levels fire while your process is foreground and the whole device is under pressure (trim to stay alive), while UI_HIDDEN/BACKGROUND/MODERATE/COMPLETE fire as your process moves down the cached LRU and signal how close it is to being reaped. Releasing memory in response literally lowers your footprint and your eviction odds: the LMK frees whole processes when trimming isn't enough, so a process that voluntarily shrinks its cache is less likely to be the one killed. onLowMemory() predates this granularity and is roughly equivalent to a single TRIM_MEMORY_COMPLETE.

Architecture

MVP vs MVVM.

🎤 Say it out loud (~35s): "In MVP the Presenter drives a passive View by calling View-interface methods directly and holds a reference to that View — so unit-testing means mocking the View, and the two are tightly coupled. In MVVM the ViewModel exposes observable state via StateFlow/LiveData and the View just observes and renders; the ViewModel has no reference to the View and doesn't know it exists, which makes it testable without a View mock and lets it survive configuration changes. MVVM with Compose is today's standard. The gotcha is the lifecycle reason MVVM survives rotation: the ViewModel is retained by the ViewModelStore, while an MVP Presenter naively wired to an Activity dies with it and leaks if you're not careful."

"In MVP, the Presenter handles all UI logic and calls View interface methods directly — the View is passive. The problem is that the Presenter holds a direct reference to the View interface, which means to unit test it you have to mock the View, and the coupling between Presenter and View contract can get tight. In MVVM, the ViewModel exposes observable state through LiveData or StateFlow, and the View just observes and renders. There's no direct reference from ViewModel to View — the ViewModel doesn't even know the View exists. That's what makes it testable without a View mock and what allows it to survive configuration changes. MVVM with Compose is the current Android standard."

Under the hood

The configuration-change survival isn't a property of the "MVVM pattern" in the abstract — it's the ViewModelStore mechanism. When an Activity is recreated on rotation, onRetainNonConfigurationInstance() hands the ViewModelStore (a map of ViewModels) across to the new Activity instance before the old one is destroyed, so ViewModelProvider returns the same ViewModel object rather than constructing a new one. That's only safe because the ViewModel holds no reference to the View/Activity — if it did (as a naive MVP Presenter does), retaining it across the recreation would pin the destroyed Activity and leak it. Observation closes the loop: LiveData/StateFlow collected with repeatOnLifecycle re-subscribes the new View to the retained ViewModel's current state, so the screen restores instantly without re-fetching.

MVVM vs MVI.

🎤 Say it out loud (~30s): "Same general shape, but MVI is stricter. MVVM exposes state and events and lets the View update individual pieces of state independently — easy to set up, fine for most screens. MVI — Model-View-Intent — has a single immutable state object: the View sends Intents, and a reducer folds current-state + Intent into a new state, Redux-style. The payoff is a full audit trail you can log and replay, which makes complex state bugs tractable; the cost is more boilerplate. My rule: MVI when state is complex and reproducibility matters, MVVM for simpler flows. The gotcha MVI solves is inconsistent partial updates racing each other when multiple StateFlows drive one screen."

"Both follow the same general shape, but MVI takes it further. In MVVM, the ViewModel exposes state and events and the View can update individual pieces of state independently — it's easier to set up and works well for most screens. In MVI — Model-View-Intent — there's a single immutable state object. The View sends Intents, which are action objects, to the ViewModel, and the ViewModel reduces the current state plus the Intent into a new state, like Redux. The benefit is a complete audit trail: you can log every state transition, replay them, and debug complex state bugs much more easily. The trade-off is more boilerplate. My rule is: use MVI when screen state is complex and you need strict reproducibility; use MVVM for simpler flows."

Under the hood

MVI's guarantees come from making state transitions a pure function — reduce(state, intent) -> newState — funneled through a single serialized path, typically a StateFlow updated only inside the reducer. Because the reducer is pure and the state object is immutable, every new state is fully determined by the previous state plus the intent, so you can record the intent stream and deterministically replay it to reach any state — that's the audit/time-travel property. Serializing all intents through one reducer also eliminates a whole class of races: with multiple independent StateFlows in plain MVVM, two concurrent updates can interleave and produce an inconsistent composite screen state, whereas a single-state reducer applies updates one at a time atomically. The cost is real: every change must round-trip through an intent and a full state copy (data class copy()), which is the boilerplate and allocation overhead you trade for that determinism.

What is clean architecture?

🎤 Say it out loud (~35s): "Clean architecture splits the code into concentric layers — Data on the outside (repositories, network, DB), Domain in the middle (use cases in pure Kotlin, no Android), and UI/Presentation innermost (ViewModels, Compose). The cardinal rule is the dependency rule: dependencies point inward, and Domain depends on nothing — it declares repository interfaces and Data provides the implementations. The payoff is a Domain layer that's fully unit-testable with no Android on the classpath; the cost is more files and indirection, worth it for medium-to-large apps. The gotcha is the dependency inversion: Domain owning the interfaces is what lets the inner layer not depend on the outer one despite calling into it."

"Clean architecture structures the codebase into three concentric layers. The outermost is Data — repositories, network sources, database sources. The middle is Domain — use cases and interactors written in pure Kotlin with no Android dependencies. The innermost is UI or Presentation — ViewModels and Compose. The key rule is that dependencies only point inward: UI depends on Domain, and Domain depends on nothing — it defines repository interfaces, and the Data layer provides the implementations. The payoff is that the Domain layer is completely unit-testable without any Android framework on the test classpath. The trade-off is more files and more indirection, which I think is worth it for medium-to-large apps but may be overkill for a small prototype."

Under the hood

The mechanism that makes "Domain depends on nothing while Data implements its needs" possible is the Dependency Inversion Principle realized through DI. The Domain module declares interface UserRepository; the Data module implements UserRepositoryImpl and depends on Domain (not vice versa) to see that interface; at the composition root, the DI graph (Dagger/Hilt) binds the implementation to the interface. So the compile-time dependency arrow points inward (Data → Domain) even though the runtime call flows outward (Domain calls into Data's implementation) — the interface inverts the direction. Concretely, this means the :domain Gradle module has no android dependency at all, so its unit tests run on a plain JVM with no Robolectric or instrumentation, which is both faster and what enforces the boundary: an accidental import android.* in domain code simply won't compile.

What belongs in ViewModel?

🎤 Say it out loud (~30s): "Three things: UI state as the single source of truth via StateFlow/LiveData; one-shot UI events like navigation and snackbars via SharedFlow; and orchestration — calling use cases, handling results, mapping them into state. What it must NOT hold is a View or Context reference (unless it's AndroidViewModel needing Application context), and it shouldn't touch a database or make network calls directly. The reason it survives config changes is precisely that it has no reference to the recreated Activity. The gotcha is leaking via callbacks — passing a View or Activity into a ViewModel method, even transiently, can pin it and defeat the whole point."

"The ViewModel owns three things. First, UI state — it's the single source of truth, exposed via StateFlow or LiveData. Second, UI events like navigation triggers and snackbars, exposed via SharedFlow. Third, orchestration logic: calling use cases or interactors, handling their results, and transforming them into state. What it must NOT do is hold a reference to a View or a Context — unless it's AndroidViewModel and absolutely needs Application context — and it should never reach directly into a database or make a network call itself. The reason it survives configuration changes is precisely because it has no reference to the Activity that gets destroyed and recreated."

Under the hood

A ViewModel is kept alive by a ViewModelStore owned by the Activity/Fragment's ViewModelStoreOwner, and survives configuration changes via onRetainNonConfigurationInstance, as described above. The framework calls ViewModel.onCleared() exactly once — when the owner is finally destroyed (the Activity actually finishing, not just rotating) — which is the lifecycle hook where viewModelScope (a CoroutineScope whose Job is a SupervisorJob bound to the ViewModel) is cancelled. The "no Context/View reference" rule is the load-bearing invariant behind all of this: because the store deliberately outlives the Activity instance across recreation, any Activity reference the ViewModel held would be retained past the Activity's death, producing a textbook leak — the same retained-store mechanism that gives you state survival would silently turn into a memory leak.

What belongs in use case?

🎤 Say it out loud (~30s): "A use case — or interactor — encapsulates exactly one business operation: get a profile, book an appointment. It calls one or more repositories, applies business rules like validation or mapping, combines sources if needed, and returns a result. It's pure Kotlin with zero Android dependencies, so it's trivially unit-testable. The discipline is Single Responsibility — one use case per business action — and if a class starts doing two distinct things, split it. The gotcha interviewers probe is the anti-pattern of anemic pass-through use cases that just forward one repository call with no logic; if there's truly nothing to add, that's a sign the layer may be ceremony rather than value."

"A use case — or interactor — encapsulates exactly one business operation: get a user profile, book an appointment. It calls one or more repositories, applies any business rules like validation or data mapping, combines data from multiple sources if needed, and returns a result. It's a pure Kotlin class with zero Android dependencies, which makes it trivially unit-testable. The discipline to enforce is Single Responsibility: one use case per business action. If a class starts doing two distinct things, split it."

Under the hood

The "single operation" convention is often encoded structurally as a class with one public method — frequently operator fun invoke(...), so the call site reads like a function call (getUserProfile(id)). Because it depends only on repository interfaces injected via the constructor, a test instantiates it with fakes/mocks and asserts on the returned result with no Robolectric and no Android runtime — it's a plain JVM unit test, which is the entire testability payoff. The composability comes from the fact that a use case is just another injectable Kotlin object, so a higher-level use case can depend on lower-level ones and the DI graph wires the tree; this is also where the anemic-wrapper smell shows up — if invoke does nothing but return repository.getThing(), the indirection adds a class and a binding without adding a business rule, so the layer earns its keep only when it actually orchestrates or enforces something.

What belongs in repository?

🎤 Say it out loud (~30s): "The repository abstracts the data layer from the domain. It decides where data comes from — DB, network, cache — and owns the caching and sync strategy. Critically it exposes clean domain models, not raw DTOs or DB entities, so the domain has no idea whether the data is Room, Retrofit, SharedPreferences, or GraphQL behind the interface. The domain calls the interface, concrete impls are injected via DI, and that's what lets you swap a fake repository in tests. The gotcha is leaking persistence types upward — returning a Retrofit DTO or a Room @Entity from the repository defeats the abstraction and couples your UI to your wire format."

"The repository abstracts the data layer from the domain. It's the place that decides where data comes from — local database, network, cache — and owns the caching and sync strategy. Critically, it exposes clean domain models, not raw DTOs or database entities. The domain layer has no idea whether data comes from Room, Retrofit, SharedPreferences, or a GraphQL endpoint — that's all hidden behind the repository interface. The domain only calls those interfaces, and the concrete implementations are injected via DI, which is what makes it easy to substitute a fake repository in tests."

Under the hood

The repository is the seam where DTOs/entities get mapped into domain models — a deliberate, sometimes-tedious translation layer that's the whole point: the Retrofit @SerializedName DTO and the Room @Entity are shaped by the wire and the schema, while the domain model is shaped by the business. Keeping them separate means a backend JSON rename or a database migration changes only the mapping function, not the UI or use cases. The offline-first pattern lives here too — a repository commonly exposes a Flow backed by the Room DAO as the single source of truth and launches network refreshes that write into the DB, so the UI observes one stream and never sees the network and cache disagree. Because the domain depends only on the interface, swapping FakeUserRepository in a test is a one-line DI binding change with no behavioral coupling to how the real one fetches.

What is single source of truth?

🎤 Say it out loud (~30s): "Single source of truth means one authoritative owner for the canonical state of a piece of data — usually a Room database or a StateFlow in a ViewModel. The offline-first pattern is: write network responses into the DB, and have the UI read exclusively from the DB, which kills the inconsistency where the cache shows one thing and a concurrent network call shows another. In Compose a single uiState: StateFlow<UiState> is the SSOT for the whole screen. The gotcha is multiple sources of truth sneaking in — e.g. holding a copy of state in the View as well as the ViewModel — which is exactly the bug SSOT exists to prevent."

"Single source of truth means one authoritative owner for the canonical state of a piece of data. In Android, that's typically either a Room database or a StateFlow in a ViewModel. The pattern for an offline-first app is: write network responses to the DB, and have the UI read exclusively from the DB. That prevents the inconsistency where your UI shows one thing from the in-memory cache and something different from a concurrent network call. In Compose, a single uiState: StateFlow<UiState> in the ViewModel is the SSOT for the entire screen — there's no other place to look for what the screen should be showing."

Under the hood

The mechanism that makes a Room-backed SSOT work is observable queries: a DAO method returning Flow<T> registers an InvalidationTracker on the underlying tables, so any write to those tables — whether from a network sync, a user edit, or a background job — automatically re-runs the query and re-emits, pushing the new value to every collector. That's why "write to the DB, read from the DB" eliminates inconsistency by construction: there is exactly one place state can change and exactly one notification path out of it. A ViewModel StateFlow SSOT works the same way at the screen level — its single conflated slot means there's one canonical current value and compose/observers always render that, so a stale copy held elsewhere (in a View field, or a second flow) is the only way to reintroduce divergence, which is precisely the failure mode the pattern forbids.

What is UDF (Unidirectional Data Flow)?

🎤 Say it out loud (~30s): "UDF means state flows down from the ViewModel to the UI, and events flow up from the UI to the ViewModel — never the reverse. The UI never mutates state directly; it fires events, the ViewModel handles them and emits new state, and the UI renders whatever it receives. Compose enforces this naturally: composables take state as parameters and call lambdas to signal actions. The benefits are predictable transitions, easy debugging since all changes go through one path, and easy testing by asserting output state for a given input event. The gotcha is breaking it with mutable shared state the UI writes to directly, which reintroduces the bidirectional coupling UDF removes."

"UDF means state flows in one direction: down from the ViewModel to the UI, and events flow back up from the UI to the ViewModel. The UI never mutates state directly — it fires events, the ViewModel handles them and emits new state, and the UI renders whatever state it receives. Compose naturally enforces this pattern: composables receive state as parameters and call lambdas to signal user actions. The benefits are three-fold — state transitions are predictable, everything is easy to debug because all state changes go through one path, and it's easy to test by simply asserting on the output state given a specific input event."

Under the hood

UDF is what makes Compose's recomposition model correct and efficient. Compose tracks reads of State<T> objects during composition; when a State value changes, the runtime marks exactly the composables that read it as invalid and reschedules only those for recomposition — a targeted re-run, not a full redraw. "State down" means a composable receives that state as a parameter so the runtime can establish the read-dependency; "events up" via lambdas means the composable never owns or mutates the canonical state, so there's a single writer (the ViewModel) and the read/write directions never form a cycle. A cycle — UI writing state it also reads mid-composition — is exactly what produces Compose's "infinite recomposition" or inconsistent-frame bugs, which is why the discipline of hoisting state up and pushing events up isn't stylistic but load-bearing for the rendering engine.

Why use dependency injection?

🎤 Say it out loud (~30s): "DI decouples constructing a dependency from using it. The headline benefit is testability — instead of a class newing up its own network client or DB, you inject them, so tests inject fakes or mocks. It also makes code reusable, since you can swap implementations without touching consumers, and explicit, since a class's needs are declared in its constructor. With Dagger the framework builds and wires the whole object graph at compile time, so a missing binding is a compile error, not a runtime crash. The gotcha interviewers like is the distinction from a service locator: DI pushes dependencies in, while a locator is pulled from inside the class, which hides dependencies and hurts testability."

"DI decouples class creation from class usage. The benefit is testability: instead of a class creating its own network client or database, you inject them from outside, so in tests you can inject a fake or a mock instead of the real thing. It also makes code reusable — you can swap implementations without touching the classes that use them — and explicit about dependencies, because everything a class needs is declared in its constructor. Without DI, every class that needs a database would new one up internally, making unit tests impossible without a real database. With Dagger, the framework builds and wires the entire object graph at compile time, which means missing bindings become compile errors rather than runtime crashes."

Under the hood

Dagger is an annotation processor: at compile time it reads @Inject, @Provides, @Module, and @Component and generates plain Java factory classes (e.g. Foo_Factory) and a DaggerAppComponent that constructs the entire object graph with hand-written new calls — there's zero runtime reflection, which is why it's fast and why a missing or duplicate binding fails the build rather than crashing in production. Scoping (@Singleton, @ActivityScoped) is implemented by wrapping providers in a DoubleCheck lazy holder so a scoped binding is instantiated once per component instance and cached. The generated code is the literal answer to "who calls the constructor": instead of a class pulling its collaborators from a global locator (hiding them and forcing tests to populate that locator), Dagger pushes them through the constructor, so the dependency set is visible in the signature and a test just calls Foo(fakeRepo, fakeClient) directly with no framework at all.

How would you modularize a large app?

🎤 Say it out loud (~35s): "I decompose by feature and by layer: :app as the entry point depends on :feature:X modules, which depend on shared :core:network, :core:database, :core:ui. Each feature is an independent Android library. Four wins: parallel compilation, internal visibility enforcing API boundaries, faster incremental builds since changes stay isolated, and the option of on-demand delivery via Play Feature Delivery. The costs are a heavier Gradle setup and inter-module navigation, usually solved with a shared nav graph or interface-based approach. The rule I enforce strictly is no circular module dependencies — and the subtle one is that an over-shared :core module that everything depends on becomes a bottleneck that re-triggers everyone's rebuild."

"I'd decompose by feature and by layer. The typical shape is: :app as the entry point, which depends on :feature:X modules for each distinct feature, which in turn depend on :core:network, :core:database, and :core:ui shared modules. Each feature module is an independent Android library. There are four main benefits: parallel compilation speeds up builds, internal visibility enforces API boundaries between modules, incremental compilation is faster because changes are isolated, and you get the option of on-demand delivery via Play Feature Delivery. The trade-offs are a more complex Gradle setup and the need to manage inter-module navigation — usually via a shared navigation graph or an interface-based approach. The rule to enforce strictly is no circular module dependencies."

Under the hood

Gradle models the build as a task DAG, and module boundaries determine its shape. Independent modules with no dependency edge between them can be compiled on separate worker threads in parallel, and Gradle's incremental engine plus the build cache mean that touching :feature:checkout recompiles only that module and its downstream dependents — anything that doesn't depend on it is served from cache untouched. This is also why the api vs implementation distinction matters mechanically: an implementation dependency is hidden from a module's consumers, so changing a transitively-implementation library doesn't recompile the whole tree, whereas api leaks it onto the compile classpath of every dependent and widens the recompilation blast radius. The "no circular dependency" rule isn't just hygiene — Gradle literally cannot topologically order a cyclic task graph and will fail the build; and an over-broad :core that everything depends on sits at the root of the DAG, so any change to it invalidates every downstream module's cache, collapsing the parallelism/incrementality benefits you modularized to get.

View Rendering

Explain measure/layout/draw.

🎤 Say it out loud (~40s): "Android renders in three sequential main-thread passes: measure, where parents hand children MeasureSpec constraints and children report a size back via setMeasuredDimension(); layout, where each view is assigned its final left/top/right/bottom; and draw, where each view paints onto a Canvas. The nuance interviewers probe is the two triggers — requestLayout() restarts from measure when size or position might change, and invalidate() skips to draw when only appearance changes. And measure can run a child more than once, like when a parent uses EXACTLY after a weight pass, which is why deep hierarchies get expensive fast."

"Android renders views in three sequential passes, all on the main thread. First, measure: the parent passes MeasureSpec constraints to each child, the child calculates its desired size and reports it back via setMeasuredDimension(). Second, layout: onLayout() assigns the final left, top, right, and bottom coordinates for each child based on those measured sizes. Third, draw: each view renders itself onto a Canvas in onDraw(). The two ways to trigger these passes are requestLayout(), which restarts from the measure pass when a view's size or position might change, and invalidate(), which skips straight to draw when only the visual appearance changes."

Under the hood

The passes are driven by ViewRootImpl.performTraversals(), which runs once per frame in response to a Choreographer vsync callback. A MeasureSpec is not a struct — it's an int that packs a 2-bit mode (UNSPECIFIED/EXACTLY/AT_MOST) into the high bits and a 30-bit size into the low bits, so a single primitive flows down the tree with no allocation. requestLayout() walks up setting the PFLAG_FORCE_LAYOUT flag on each ancestor and posts a traversal; invalidate() instead unions the view's bounds into a dirty Rect and sets PFLAG_INVALIDATED, so performTraversals() skips straight to performDraw().

Choreographer (vsync) → ViewRootImpl.performTraversals()
   performMeasure()  → view.measure() → onMeasure() → setMeasuredDimension()
   performLayout()   → view.layout()  → onLayout()
   performDraw()     → view.draw()    → onDraw(Canvas)

invalidate() vs requestLayout().

🎤 Say it out loud (~30s): "invalidate() just marks a view dirty and schedules a redraw — same size and position, only the pixels change, like a color swap. requestLayout() marks the whole parent chain as needing measure plus layout plus draw, so you use it only when bounds might change. The classic mistake is calling requestLayout() when invalidate() would do — you've forced an expensive remeasure of the entire ancestor chain for nothing."

"invalidate() marks a view as dirty and schedules a new draw pass — nothing more. Use it when only the visual appearance changes, like a color or text content, but the size and position stay the same. requestLayout() marks the view and its entire parent chain as needing a full measure plus layout plus draw pass. Use it when the view's size or position might have changed. The mistake to avoid is calling requestLayout() when invalidate() would have been enough — you're triggering an expensive re-measure and re-layout of the whole parent chain for no reason."

Under the hood

requestLayout() propagates upward setting PFLAG_FORCE_LAYOUT | PFLAG_INVALIDATED on every parent until it reaches a ViewParent that's already in a layout pass or the ViewRootImpl, which calls scheduleTraversals() — a single posted Runnable per frame guarded by mTraversalScheduled, so N requestLayout() calls in one frame coalesce into one traversal. invalidate() does no upward force-layout walk; it accumulates the damaged region and, in hardware-accelerated rendering, the dirty view's RenderNode display list is re-recorded while clean siblings reuse their cached display lists on the RenderThread.

What is jank?

🎤 Say it out loud (~35s): "Jank is visible stutter from dropped frames. At 60 fps you have a ~16 ms budget per frame, tighter on 90 or 120 Hz panels — blow it and the frame gets skipped. The usual culprits are heavy onDraw(), deep hierarchies that take too long to measure and lay out, main-thread blocking, and allocation churn that triggers GC pauses. The detail I'd add is that the main thread only owns part of the frame — RenderThread and the GPU also have to finish inside that budget — so I profile with Perfetto, the Frame Profiler, or dumpsys gfxinfo to see exactly which stage overran."

"Jank is the visible stuttering you see when frames are dropped. Android targets 60 fps, which gives you a budget of 16 ms per frame. On 90 or 120 Hz displays the budget is even tighter. A frame is dropped whenever the main thread takes longer than that budget to complete its rendering work. The common causes are: expensive onDraw() implementations, deep or complex view hierarchies that take too long to measure and layout, any blocking operation on the main thread, and excessive allocations that trigger frequent GC pauses. I detect jank with Perfetto for a timeline view, Android Studio's Frame Profiler, or adb shell dumpsys gfxinfo for a quick per-frame breakdown."

Under the hood

Choreographer registers for vsync via DisplayEventReceiver and dispatches callbacks in fixed priority order — INPUT, ANIMATION, then TRAVERSAL — each frame. If the UI-thread work plus the RenderThread's display-list playback don't both finish before the next vsync, the previous frame is rescanned out and the system records a skipped frame (the "Skipped N frames!" log fires when Choreographer detects the main thread missed the deadline). Modern devices pipeline the UI thread and RenderThread across frames, and a triple-buffered swap chain absorbs a single late frame, but a sustained overrun starves the buffer queue and the GPU repeats the last completed frame — that repeated scanout is the visible stutter.

How to optimize RecyclerView?

🎤 Say it out loud (~40s): "The biggest wins are diffing instead of notifyDataSetChanged() — DiffUtil or ListAdapter for efficient animated updates — and keeping item layouts flat so each measure is cheap, since binding happens many times per scroll. Then setHasFixedSize(true) to skip parent remeasures, a shared RecycledViewPool for nested lists with the same view types, async image loading with Coil or Glide, and prefetch tuning on nested LinearLayoutManager. The gotcha is that ListAdapter runs its diff on a background thread, so you must submit immutable copies — diffing a list you then mutate gives wrong results or crashes."

"There are a handful of changes that move the needle most. First, replace notifyDataSetChanged() with DiffUtil or ListAdapter — that gives you efficient, animated, diffed updates instead of rebinding everything. Second, always do a full bind in onBindViewHolder and never skip it. Third, call setHasFixedSize(true) when item count changes don't affect the RecyclerView's own dimensions — it skips an unnecessary parent remeasure. Fourth, share a RecycledViewPool across nested RecyclerViews that use the same view types to improve view reuse. Fifth, avoid nested weights and overly complex ConstraintLayout in list item layouts, because each item's measure is expensive and it happens many times per scroll. Sixth, use Glide or Coil for async image loading — they handle downsampling, caching, and lifecycle binding. Finally, for nested RecyclerViews, set setInitialPrefetchItemCount() on the inner LinearLayoutManager so items are prefetched before they come on screen."

Under the hood

RecyclerView recycles via a multi-tier cache inside Recycler: the per-list mAttachedScrap/mChangedScrap (in-pass detach), a small mCachedViews (default capacity 2, holds fully-bound views by position so a quick scroll-back skips rebind), and the shared RecycledViewPool (holds unbound views keyed by viewType for rebinding). DiffUtil runs Myers' O(ND) diff algorithm to compute the shortest edit script, then emits granular notifyItemRange* calls that the ItemAnimator turns into move/fade animations. Prefetch works because GapWorker, a runnable posted at the end of each frame, uses the scroll velocity to predict upcoming positions and inflates/binds those views during the idle time before the next vsync, moving that cost off the critical scroll frame.

What triggers Compose recomposition?

🎤 Say it out loud (~40s): "Recomposition fires when a composable reads a State whose value changes. Compose's snapshot system records exactly which states each composable read, so on a write only the readers are invalidated — not the whole tree. The nuance is stability: for Compose to skip an unchanged composable, its parameters have to be stable — primitives, String, or types marked @Stable/@Immutable. An unstable input, like a bare List, forces recomposition every time the parent recomposes even if the value is identical. The practical fixes are derivedStateOf for computed state and ImmutableList for collections."

"Recomposition is triggered when the state that a composable reads changes. Compose's snapshot system tracks exactly which State<T> objects are read during each composable's execution. When a State is written, only the composables that read that specific state are scheduled for recomposition — not the whole tree. The important nuance is stability. For Compose to skip a composable when its parent recomposes, it needs to know that the composable's inputs haven't changed. That requires the parameter types to be stable — either primitives, String, classes annotated with @Stable or @Immutable, or types Compose can infer stability for. Unstable types always cause the composable to recompose when the parent does, regardless of whether the value actually changed. The practical fix is to use derivedStateOf { } for any computed state, and reach for ImmutableList for collections."

Under the hood

The Compose compiler plugin rewrites every @Composable function to take a synthetic $composer and $changed int parameter and to emit composer.startRestartGroup(key) / endRestartGroup() around the body, where key is a compile-time-generated integer for that call site. State reads go through a SnapshotStateObject; reading inside a composable registers the current RecomposeScope as a reader in the snapshot system's observer set. A mutableStateOf write bumps a snapshot version and notifies those scopes, which enqueue into the Recomposer's invalid-scope set. Skipping is the $changed bitmask check: the generated code compares each parameter's stability-derived "changed" bits and, if a RestartGroup's inputs are all stable-and-equal, calls composer.skipToGroupEnd() to reuse the prior slot-table emission instead of re-running the body. Unstable params can't be proven equal, so their bits force the body to re-run.

remember vs rememberSaveable.

🎤 Say it out loud (~35s): "remember caches a value in the composition's slot table, so it survives recomposition but dies when the Activity is recreated — a rotation wipes it. rememberSaveable additionally writes the value into the SavedStateRegistry, the Compose analog of onSaveInstanceState, so it survives config changes and process death. My rule: remember for throwaway UI state like an animation flag, rememberSaveable for anything the user expects to persist, like text-field input or a selected tab. The gotcha is that whatever you put in rememberSaveable must be Bundle-able, so custom types need a Saver."

"remember stores a value in the composition, so it survives recompositions, but it is lost when the Activity is recreated — for example on a configuration change like rotation. rememberSaveable goes one step further: it persists the value through configuration changes using the SavedStateRegistry, which is the Compose equivalent of onSaveInstanceState. My decision rule is: use remember for purely transient UI state that doesn't matter after a rotation, like an in-progress animation state. Use rememberSaveable for state the user would expect to still be there after rotating the device, like a text field they were typing in or the selected tab index."

Under the hood

remember is sugar over composer.cache(): on first composition it computes the value and stores it in the composition's slot table — a flat gap-buffer (SlotTable) of groups and slots indexed by the composer's positional key path — and on later passes it returns the slot if the keys are unchanged. The slot table is part of the composition and is discarded when the composition is disposed, which is why a config-change Activity recreate loses it. rememberSaveable wraps that with a registration into SaveableStateRegistry: it registers a provider lambda keyed by the call-site key, and when the host emits onSaveInstanceState the registry calls every provider, collects the values (via the type's Saver, defaulting to the autoSaver which requires the value be storable in a Bundle), and writes them into the saved-state Bundle that survives both rotation and system-initiated process death.

State hoisting.

🎤 Say it out loud (~30s): "State hoisting means moving state ownership up out of a composable: instead of holding its own remember, the composable takes value as a parameter and reports changes through an onValueChange lambda. The parent — usually the ViewModel — owns the state; the child is a stateless, reusable, testable render function. The rule of thumb is to hoist to the lowest common ancestor of everything that reads or writes that state, no higher, so you don't over-centralize state that only one subtree cares about."

"State hoisting is the pattern of moving state ownership up the composable hierarchy. Instead of a composable managing its own state internally with remember, it receives the current value as a parameter and emits changes via a lambda. The signature looks like value: T, onValueChange: (T) -> Unit. The parent — or ultimately the ViewModel — holds the state; the child just renders what it's given and fires events when the user interacts. This makes composables stateless, which makes them reusable in different contexts and easy to test. The Compose guideline is to hoist state to the lowest common ancestor of all composables that either read or write it."

Under the hood

Hoisting matters mechanically because of where the read happens in the recompose graph. A State read registers the currently executing RecomposeScope as an observer; when state lives inside a leaf composable, only that leaf re-runs on change. When you hoist, the read moves into the parent's scope and the value is passed down as a parameter — so the parent recomposes, then the child is re-invoked but can be skipped if the passed value is stable-and-equal. This is the "donut hole" / read-deferral idea: by passing a value (or even a lambda that defers the read, like () -> T) you push the actual State read as far down as possible, shrinking the recompose scope to exactly the subtree that depends on it.

Compose side effects.

🎤 Say it out loud (~45s): "Side effects are anything that escapes the composition — launching a coroutine, registering a listener, firing analytics. Compose gives you a tool per pattern: LaunchedEffect(key) runs a coroutine scoped to the composition, restarting on key change and cancelling on leave — good for one-shot work like navigation. DisposableEffect is for callbacks that need teardown via onDispose. SideEffect runs after every successful composition to publish Compose state to non-Compose code. And rememberCoroutineScope() gives a composition-scoped scope you can launch from event callbacks. The classic gotcha is the key: a constant key like Unit means it never restarts, while keying on a frequently changing value relaunches it every recomposition."

"Side effects are operations that escape the composition — starting a coroutine, registering a listener, firing an analytics event. Compose provides specific APIs for each pattern. LaunchedEffect(key) starts a coroutine scoped to the composition, re-launches it when the key changes, and cancels it when the composable leaves the composition — use it for one-shot effects like triggering navigation or playing an animation. DisposableEffect(key) handles non-coroutine side effects that need cleanup — you register something and return an onDispose { } block to unregister it. SideEffect runs on every successful recomposition with no key — it's for pushing Compose state out to non-Compose code. And rememberCoroutineScope() gives you a coroutine scope tied to the composable's lifetime for user-triggered effects like button clicks, where you need to launch a coroutine from a non-suspending lambda."

Under the hood

Each effect is itself a remembered node in the slot table. LaunchedEffect remembers a LaunchedEffectImpl whose onRemembered() callback starts a coroutine in a CoroutineScope whose context is the composition's recomposeCoroutineContext plus a fresh Job; onForgotten() (fired when the call leaves composition) cancels that Job. Because the impl is keyed, supplying new keys makes Compose forget the old node (cancel) and remember a new one (relaunch) — that is the entire "restart on key change" mechanism, not a special code path. DisposableEffect remembers a DisposableEffectImpl that runs your block on onRemembered and your returned DisposableEffectResult.dispose() on onForgotten. SideEffect is the simplest: the composer records it in the change list and the applier invokes it during the apply phase, only after the composition successfully commits — so it never runs for an abandoned/cancelled composition.

How to debug slow rendering.

🎤 Say it out loud (~40s): "I work in layers. Perfetto or systrace first for a full frame timeline across the UI thread, RenderThread, and GPU — that tells me which stage blew the budget. Then Layout Inspector with recomposition counts to catch composables recomposing too often, usually from unstable types. dumpsys gfxinfo gives quick frame-time percentiles, and StrictMode flags disk or network on the main thread. The deeper move is the Compose compiler stability report, which tells me per-composable whether something is skippable or restartable — that's how I find the unstable parameter that's defeating skipping, rather than guessing."

"My approach has several layers. First, Perfetto or systrace for a full frame timeline — it shows main thread work, RenderThread, and GPU work per frame so you can see exactly where the budget is being spent. Second, Android Studio's Layout Inspector with recomposition highlights, which shows which composables are recomposing and how often — that surfaces excessive recompositions immediately. Third, adb shell dumpsys gfxinfo <package> for a quick command-line view of janky frame counts and frame time percentiles at the 50th, 90th, 95th, and 99th percentiles. Fourth, StrictMode in debug builds to catch disk or network access on the main thread. Fifth, I look for Baseline Profiles to reduce JIT overhead on startup and critical paths. The patterns I search for specifically are: excessive recompositions from unstable types, deep view hierarchies, invalidate() storms, image loading on the main thread, and any blocking call inside onDraw()."

Under the hood

These tools read different layers of the same pipeline. dumpsys gfxinfo returns the data the framework already keeps: each ViewRootImpl records per-frame timing into a ring buffer (FrameInfo/FrameMetrics) tagging the cost of each stage — input handling, animation, measure/layout, draw (display-list record), sync+upload to the RenderThread, GPU command issue, and swap-buffers — so "janky frame" counts come straight from comparing total frame duration to the vsync interval. Perfetto goes lower: it ingests ATRACE userspace markers (the Trace.beginSection calls the framework sprinkles through performTraversals) and kernel ftrace scheduling events, so you can see the UI thread descheduled, RenderThread GPU waits, and binder transactions on one timeline. The Compose compiler report is a static artifact emitted at build time: for each composable it prints restartable/skippable and, for each class, stable/unstable with the field that broke stability — no runtime measurement, just the compiler's stability inference made visible.

Worked Example 1 — Handler Memory Leak (from the source doc)

🎤 Say it out loud (~35s): "A delayed Handler message leaks because the chain MessageQueue → Message → Handler → Activity stays live until the message drains — and a non-static inner Handler holds an implicit reference to its enclosing Activity. So if the Activity is destroyed while a 30-second postDelayed is pending, the GC can't reclaim it or its view hierarchy. The fix is either a static inner class with a WeakReference, or just removeCallbacksAndMessages(null) in onDestroy() — or skip Handler entirely and use a lifecycleScope coroutine that auto-cancels."

Question: How can a Handler cause a memory leak?

1. Define: "A Handler lets you post Messages and Runnables to a thread's MessageQueue for deferred or repeated execution."

2. Internals: "When you call handler.postDelayed(runnable, 30_000), the system creates a Message object that holds a reference to the Runnable. That Message also holds a reference to the Handler. If the Handler is a non-static inner class of the Activity, it holds an implicit reference back to the Activity instance — that's just how non-static inner classes work in Java and Kotlin."

3. Android implications: "If the Activity is destroyed — the user pressed back, or there was a configuration change — while that delayed message is still sitting in the queue, the GC cannot collect the Activity. The chain is still live: MessageQueue → Message → Handler → Activity. Nothing in that chain can be collected until the message drains."

4. Trade-offs: "Non-static inner Handlers are convenient to write, but they're dangerous for any delay longer than a few milliseconds. The safer pattern is a static inner class with a WeakReference<Activity>, which is verbose but doesn't prevent GC."

5. Failure cases:

  • A leaked Activity retains its entire view hierarchy and all attached bitmaps in memory.
  • If the Runnable accesses destroyed views, it may throw NullPointerException or silently no-op.
  • Multiple leaks accumulate across rotations, inflating heap over time.

6. Debug / test:

  • LeakCanary will surface this immediately with the full reference chain.
  • Memory Profiler: take a heap dump after rotating; filter for your Activity class — multiple instances means a leak.
  • Fix: call handler.removeCallbacksAndMessages(null) in onDestroy(), or replace with lifecycleScope.launch { delay(30_000); updateUI() } which is cancelled automatically when the Activity is destroyed.

Under the hood

The implicit Activity reference is real bytecode, not an abstraction: the Kotlin/Java compiler gives every non-static inner class a synthetic final field — this$0 — initialized in the constructor to the enclosing instance, so an inner Handler literally has a strong Activity pointer. The pending message sits in MessageQueue as a linked list of Message objects ordered by their when timestamp; postDelayed sets when = SystemClock.uptimeMillis() + delay and links the node in. Message.target is the Handler, and Message.callback is the Runnable, so the GC root chain is the live MessageQueue (reachable from the main thread's Looper, itself a thread-local) holding that node for the full 30 s. removeCallbacksAndMessages(null) walks the queue, unlinks matching nodes, and calls Message.recycle() to return them to the static Message object pool, breaking the chain immediately.

Worked Example 2 — Coroutine Structured Concurrency & Cancellation

🎤 Say it out loud (~40s): "Structured concurrency means every coroutine has a parent Job, and cancelling the parent cancels all children. Cancellation is cooperative — it's not a thread interrupt; a CancellationException is thrown at the next suspension point, and finally blocks still run for cleanup. The bug interviewers love is a broad catch (e: Exception) that swallows that CancellationException, making the coroutine effectively uncancellable. On Android, viewModelScope and lifecycleScope give you cancellation for free at onCleared and ON_DESTROY — GlobalScope is outside the hierarchy and is the classic leak source."

Question: How does coroutine cancellation work, and what can go wrong?

1. Define: "Structured concurrency means every coroutine belongs to a parent scope, and cancelling the parent automatically cancels all children. The important detail is that cancellation is cooperative — a coroutine has to check for it; it doesn't get interrupted like a thread."

2. Internals: "When you call Job.cancel(), the Job transitions to a Cancelling state and a CancellationException is scheduled to be thrown at the next suspension point. All child coroutines receive the same signal and go through the same process. finally blocks run normally, which is how you do cleanup. The subtle bug to watch for is catching Exception broadly and not rethrowing the CancellationException — the coroutine then swallows the cancellation and keeps running."

3. Android implications: "viewModelScope is cancelled when ViewModel.onCleared() is called — which happens when the Activity or Fragment finishes. lifecycleScope is cancelled on Lifecycle.Event.ON_DESTROY. Both give you automatic cleanup without any manual Job.cancel() calls. Any coroutine launched with GlobalScope is completely outside this hierarchy and ignores both."

4. Trade-offs: "The cooperative model is lightweight — there's no thread interruption signal to send. The cost is that you have to ensure cancellation can actually be observed. Long CPU loops with no suspension points need periodic calls to ensureActive() or yield(). Libraries that use BlockingQueue.take() or other OS-level blocking primitives are not cancellation-aware without wrapping them carefully in withContext plus thread interruption."

5. Failure cases:

  • Catching Exception without rethrowing CancellationException makes the coroutine non-cancellable.
  • runBlocking on the main thread blocks cancellation and can cause ANR.
  • Using GlobalScope means the coroutine outlives the ViewModel and may crash accessing destroyed state.
  • Not cleaning up a CoroutineScope owned by a non-lifecycle object (a custom class) causes coroutine leaks.

6. Debug / test:

  • Use TestCoroutineDispatcher / runTest in tests to control coroutine execution deterministically.
  • In production, monitor for jobs that never complete by logging in invokeOnCompletion.
  • LeakCanary can surface ViewModel leaks caused by GlobalScope coroutines keeping the ViewModel alive.

Under the hood

A suspend function is compiled via CPS (continuation-passing style) into a state machine: the compiler generates a synthetic Continuation subclass with an integer label field and slots for locals, and each suspension point is a when(label) case that returns the COROUTINE_SUSPENDED sentinel and stores state. Cancellation works by checking the Job's state at these boundaries — Job.cancel() flips the job to Cancelling, and the framework's suspending primitives (delay, yield, channel/Flow ops) check isActive / the job state on resume and throw CancellationException. That's why a tight non-suspending loop never cancels: it never re-enters the dispatcher, so nothing checks the flag — ensureActive() is a manual state check you insert. viewModelScope is a CoroutineScope whose context carries a SupervisorJob + Dispatchers.Main.immediate, stored as a tagged value on the ViewModel; onCleared() calls coroutineContext.cancel(), which cancels that job and, structurally, every child continuation registered under it.

Worked Example 3 — Compose Recomposition & Stability

🎤 Say it out loud (~40s): "Recomposition is Compose re-running a composable when a State it read changes, tracked precisely by the snapshot system so only readers re-run. To prevent excess recomposition I make inputs stable: a data class exposing a raw List is unstable because Compose can't prove the list won't mutate, so I switch to ImmutableList or annotate @Immutable. The thing interviewers dig into is why a class is unstable — usually a var, a List/Map, or a type from a module the compiler couldn't analyze — and I'll point them at the Compose compiler stability report to prove it rather than guess."

Question: What triggers Compose recomposition, and how do you prevent excessive recompositions?

1. Define: "Recomposition is Compose re-executing a composable function when the state it reads has changed. It's the mechanism by which the UI stays in sync with state."

2. Internals: "Compose's snapshot system tracks exactly which State<T> objects are read during each composable's execution. When a State is written, Compose schedules recomposition only for the composables that read that specific state — not the whole tree. For this optimisation to work, Compose has to be able to skip a composable when its inputs haven't changed. That requires all the parameters to be stable — either primitives, String, classes annotated with @Stable or @Immutable, or types whose stability Compose can infer from their definition."

3. Android implications: "A data class from a repository that has a plain List<T> property is treated as unstable by Compose because Compose can't prove the list won't mutate. That means its parent composable will always recompose when the parent recomposes, regardless of whether the data actually changed. The fix is to use kotlinx.collections.immutable.ImmutableList or to annotate the data class with @Immutable."

4. Trade-offs: "@Immutable is a promise — you're telling the compiler the class truly never changes after creation, and you have to keep that promise. @Stable is a looser contract for classes that change only in ways Compose can observe. Using derivedStateOf { } is the right tool for computed values that depend on state — it means the composable only recomposes when the derived value actually changes, not every time the upstream state changes."

5. Failure cases:

  • Lambda captures in composables can inadvertently capture unstable objects, breaking skippability.
  • Reading a StateFlow value directly rather than via collectAsState() bypasses the snapshot system entirely.
  • Excessive recompositions from unstable types cause jank on complex screens — the Layout Inspector's recompose counts will show hot composables recomposing on every keystroke.

6. Debug / test:

  • Android Studio Layout Inspector → Recomposition Counts tab: shows which composables recompose and how often.
  • @Stable / @Immutable plus ImmutableList as the first remediation step.
  • Compose compiler metrics (-P plugin:androidx.compose.compiler.plugins.kotlin:reportsDestination=...) report per-composable stability and skippability.
  • In tests, use composeTestRule.mainClock.autoAdvance and verify UI state without flakiness from recompositions.

Under the hood

Compose classifies every type into one of three stability buckets and encodes the result as bits the compiler bakes into call sites. A type is stable if all its public properties are val of stable types (and it isn't mutable in a way Compose can't observe); @Stable/@Immutable are programmer assertions that override inference. The snapshot system is an MVCC mechanism: each thread runs inside a Snapshot with a monotonically increasing version; a MutableState keeps a versioned StateRecord linked list, and reads pick the record visible to the current snapshot while writes append a new record and, on apply(), notify global read observers. derivedStateOf is a DerivedState that itself records which states its calculation read; it only notifies its own dependents when a re-evaluation produces a value that fails the equality check — that's why it collapses many upstream changes into the few that actually change the result. At the call site, the generated $changed bitmask carries 3 bits per parameter (uncertain / same / different) so the restart group can decide to skipToGroupEnd() without re-running the body.

Worked Example 4 — Binder Transaction Limits / IPC Design

🎤 Say it out loud (~40s): "Binder is Android's kernel-backed IPC — one process calls methods on another with a single kernel copy, and every cross-process call is a transaction. The hard limit interviewers chase is the ~1 MB per-process transaction buffer: blow past it and you get TransactionTooLargeException, and the nastiest version is a fat onSaveInstanceState bundle that crashes far from where the bug actually is. Calls are synchronous by default with a 16-thread pool per process, so synchronous Binder on the main thread risks ANR. For big payloads you pass a file descriptor over Binder using SharedMemory or MemoryFile instead of the data itself."

Question: What are the limits and failure modes of Android IPC via Binder?

1. Define: "Binder is Android's kernel-backed IPC. It lets a process call methods on objects in another process, and it does the data transfer with a single copy through the kernel. Every cross-process call is a Binder transaction."

2. Internals: "Each process has a shared Binder transaction buffer of roughly 1 MB. The kernel copies data from the caller's address space into that buffer, and the callee reads from it. By default, Binder calls are synchronous — the calling thread blocks until the remote method returns. Each process gets up to 16 Binder threads: 15 available for incoming calls and 1 spawning thread."

3. Android implications: "Every call to a system service — ActivityManager, PackageManager, WindowManager — goes over Binder. Calling those on the main thread, or passing large objects like bitmaps or big lists, will cause slow or failed IPC. TransactionTooLargeException is thrown when you exceed the ~1 MB buffer limit. One particularly confusing manifestation of this is in onSaveInstanceState, where a large saved-state bundle silently crosses the limit and causes a crash that looks unrelated to IPC."

4. Trade-offs: "Binder's single-copy design makes it faster than socket-based IPC, but it still has overhead. For large payloads like video frames or audio buffers, the right approach is to use SharedMemory or MemoryFile and pass only the file descriptor over Binder. oneway AIDL declarations avoid the blocking call, but you give up return values and error propagation."

5. Failure cases:

  • Calling synchronous Binder methods on the main thread causes ANR.
  • Sending large Parcelables causes TransactionTooLargeException, which is often hard to debug because the stack trace points to the OS rather than your code.
  • Not registering a DeathRecipient means your app silently loses its remote service handle and all subsequent calls throw DeadObjectException.
  • Binder thread pool exhaustion — if the remote service is slow and all 16 threads are occupied — causes the calling thread to block indefinitely.

6. Debug / test:

  • adb shell dumpsys binder_calls_stats shows per-process IPC call frequency and latency.
  • StrictMode detectCustomSlowCalls() plus a thread policy can flag Binder calls on the main thread in debug builds.
  • For TransactionTooLargeException: log bundle sizes before putExtra, consider splitting large payloads, or switch to a content provider or file-based approach.
  • Unit test AIDL implementations by calling the Stub directly in-process — no real Binder needed. Integration test with an instrumented test that binds to a real service running in a separate process.

Under the hood

The "single copy" is the key kernel mechanic: the binder driver mmaps a region of the receiving process's address space into kernel space, so a transaction does one copy_from_user from the sender straight into the receiver's mapped buffer — versus the two copies a pipe/socket needs (sender→kernel, kernel→receiver). That mapped region is the ~1 MB pool shared by all concurrent transactions in the process, which is why the limit is per-process-at-a-moment, not per-call. A Parcel marshals arguments into this buffer; object references are written as flat_binder_object entries that the driver translates into the correct handle in the target process. The thread pool is the BC_REGISTER_LOOPER mechanism — ProcessState caps incoming threads (default 15 + the main looper), and when all are busy the driver queues the transaction. linkToDeath registers a DeathRecipient with the driver, which sends a BR_DEAD_BINDER notification when the holding process dies, and any in-flight or subsequent call then surfaces as DeadObjectException (a RemoteException).
