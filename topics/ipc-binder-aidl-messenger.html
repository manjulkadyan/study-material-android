5.1 Android Process Model

Definition

🎤 Say it out loud (~30–45s): "On Android every app runs in its own Linux process, with its own UID, its own ART runtime, and its own heap — they're isolated at the kernel level, so they can't see each other's memory. Each process has a main thread driven by a Looper plus a Binder thread pool for handling incoming IPC. The nuance interviewers like is that this isolation is exactly why IPC exists: you can never pass an object reference across the boundary, only marshalled data."

Every Android app runs in its own Linux process by default, completely isolated from every other app at the OS kernel level. That process hosts a Dalvik/ART VM, a main thread with its own Looper, a Binder thread pool, and the app's heap. The OS assigns each process a unique UID and PID.

Under the hood

A process is created by Zygote: when the system needs a new app process it doesn't spin up a fresh runtime, it fork()s the already-warm Zygote process, which has the core framework classes and shared resources preloaded. Copy-on-write means the child shares those pages until it writes to them, which is why app startup is cheap. After the fork, the child's UID is set, the Binder driver fd is opened (/dev/binder), and ActivityThread.main() installs the main Looper.

init → Zygote (preloads framework, opens shared libs)
        │  fork() + setuid()
        ▼
   app process (UID/PID) → ActivityThread.main() → Looper.prepareMainLooper()
                                                  → Binder thread pool started

How components map to processes

🎤 Say it out loud (~30–45s): "By default all four component types in one APK live in the single process named after the package. I can move a component into another process with android:process in the manifest — a leading colon means a private process scoped to my app, no colon means a globally-named process other apps signed with the same key can share. The catch teams forget: separate processes share nothing — no heap, no statics, no singletons — so any cross-process talk has to go through IPC."

By default, all four component types (Activity, Service, BroadcastReceiver, ContentProvider) declared in a single APK run in the same process — the one named after the app's package. You opt components into a different process via the android:process attribute:

<!-- AndroidManifest.xml -->
<service
    android:name=".AudioPlayerService"
    android:process=":audio" />   <!-- ':' prefix = private process, scoped to this app -->

<service
    android:name=".SyncService"
    android:process="com.example.sync" />  <!-- no ':' = shared process, any app with same UID -->

When components live in different processes, they share no memory at all — not the heap, not static fields, not singletons. The JVM runs a completely separate instance for every process. That's the fundamental reason IPC exists: you cannot pass an object reference across process boundaries.

Under the hood

android:process is read by the PackageManager when it parses the manifest, and the resulting process name is recorded per-component. When you launch a component, ActivityManagerService (AMS) looks up the target process name; if no process with that name is alive under the app's UID, AMS asks Zygote to fork a new one and only then dispatches the component into it. A :-prefixed name is rewritten to packageName + ":" + suffix so it's namespaced to your app; an absolute name with no colon is global, and another app can join it only if it shares your UID via android:sharedUserId and the same signing key. Each forked process gets its own class loader and therefore its own copy of every static initializer.

Memory isolation

🎤 Say it out loud (~30–45s): "Within one process, statics and singletons are shared because there's one class loader and one heap. Across processes nothing is shared — each process re-runs its own static initializers, so a singleton is genuinely two independent instances, and a raw object reference is just a pointer into the wrong address space. For files or prefs you'd go through a ContentProvider or FileProvider rather than assume shared state."
Scope Same process Different processes
Static variablesSharedNot shared — each process has its own copy
Singleton instancesSharedIndependent instances
Object referencesValid pointersMeaningless (different address space)
Files / SharedPreferencesShared if same UID and no MODE_PRIVATENeed ContentProvider or FileProvider

"What happens to static variables across processes?"

"Each process gets its own JVM, so a companion object or @JvmStatic field is initialized independently in every process. Changing the value in process A has zero effect on process B. This is a surprisingly common source of confusion when teams introduce a :remote service without realizing their in-memory cache now has two stale, independent copies."

Under the hood

A static field lives in the runtime representation of its class, and a class is identified by the pair (fully-qualified name, defining class loader). Each process boots its own class loader hierarchy, so the same MySingleton class is loaded twice — two distinct Class objects in two heaps — and ART runs the <clinit> static initializer once per loader. There is no shared-memory segment behind statics, so a write in one process never propagates. SharedPreferences make this worse: the in-memory map is per-process, and concurrent writes from two processes can clobber the backing XML even with the legacy MODE_MULTI_PROCESS flag, which is why modern guidance is a ContentProvider for any genuinely cross-process state.

Process lifecycle and death

🎤 Say it out loud (~30–45s): "Android can kill any of my processes at any time to reclaim memory, ordered by importance — foreground, visible, service, background, then empty — but with no guarantee beyond that ordering. So I treat in-memory state as disposable: anything only in statics or instance fields is gone on death. And because a remote service can die independently of my UI, I handle RemoteException, register a death recipient, and lean on onServiceDisconnected for the binding side."

The Android OS is free to kill any background process at any time to reclaim memory. The kill order follows a priority ladder — foreground, then visible, then service, then background, then empty — but the OS makes no guarantees beyond that ordering. A service running in a separate process can die while the app's UI is still alive, or vice versa.

There are three implications worth internalizing. First, any state stored only in static or instance memory is gone on process death. Second, if you hold a reference to a remote IBinder, the remote can disappear under you at any moment — you must handle RemoteException and register a death recipient (covered in §5.2). Third, bound services get a callback when the remote process dies: ServiceConnection.onServiceDisconnected.

Under the hood

The "priority ladder" is implemented as an oom_adj (now oom_score_adj) value that AMS computes for each process and writes into /proc/<pid>/oom_score_adj. The kernel's low-memory killer — historically the in-kernel LMK, now usually the userspace lmkd daemon watching memory-pressure (PSI) signals — reaps the process with the highest adj score first when memory runs low. AMS recomputes adj scores as components start/stop and as visibility changes, so a process holding only a started service sits around adj 500 while a foreground activity sits near 0. The process is killed with SIGKILL, so there is no chance to run cleanup code — which is exactly why persisted state, not in-memory state, is the only thing you can rely on.

oom_score_adj (lower = harder to kill)
  foreground / persistent   ~   0
  visible                   ~ 100–200
  service                   ~ 500
  cached / background       ~ 700–900
  empty                     ~ 900+   ← killed first by lmkd under pressure

Bound vs remote services

🎤 Say it out loud (~30–45s): "Binding is always bindService(), but the meaning of the returned IBinder depends on where the service lives. In-process, onBind() hands back the real object — you cast it and call methods directly, zero IPC cost. Out-of-process, the framework gives you a proxy: every call on it marshals arguments into a Binder transaction the kernel driver routes to the server. The gotcha is that this is transparent — same API both ways — so it's easy to forget remote calls can block and throw RemoteException."
Type Same process Different process
Started servicestartService()startService() across packages, but still same process unless android:process set
Bound service (local)IBinder returned from onBind() is a direct object reference, no IPC overheadN/A
Bound service (remote)—onBind() returns an AIDL stub or Messenger; every call crosses a Binder transaction

The key insight is that binding to a service in another process is still bindService(), but Android transparently routes the IBinder through the Binder driver. The client receives a proxy object, not the real object.

Under the hood

When onBind() returns a Binder and the client is in the same process, AMS hands the client the identical IBinder object — asInterface() sees a local binder and returns the concrete implementation, so calls are plain virtual dispatch. When the client is in a different process, the binder reference travels through the Binder driver as a handle, and on the client side the driver materializes a BinderProxy. Stub.asInterface() checks queryLocalInterface(), finds nothing local, and wraps the proxy in a generated Stub.Proxy. Each method on that proxy calls transact(), which blocks the calling thread while the driver copies the marshalled Parcel into the target process and wakes one of its Binder pool threads to run onTransact().

// Generated by AIDL — the branch that makes local binding free:
fun asInterface(obj: IBinder): IMyService {
    val local = obj.queryLocalInterface(DESCRIPTOR)  // non-null only same-process
    return if (local is IMyService) local             // direct call, no IPC
           else Stub.Proxy(obj)                        // remote → transact()
}

Interview angles — process model

Q: Process vs thread?

"A process is an OS-level isolation unit — it has its own address space, its own PID, its own UID. A thread, by contrast, shares the address space with all the other threads in the same process. So IPC is what you need when you're crossing process boundaries; thread synchronization handles coordination within a single process."

Q: How do you communicate with a service in another process?

"You return an IBinder from Service.onBind(). The client receives a proxy object rather than the real thing, and each method call on that proxy becomes a Binder transaction that the kernel Binder driver routes over to the server process."

Q: How do you handle remote process death?

"You register an IBinder.DeathRecipient via binder.linkToDeath(recipient, 0). When the remote process dies, the binderDied() callback fires on a Binder thread, and from there you can attempt a rebind, surface an error to the user, or clean up any state you were holding. You should also implement ServiceConnection.onServiceDisconnected to cover the service binding lifecycle side of the same event."

5.2 Binder

Definition

🎤 Say it out loud (~30s): "Binder is Android's core IPC mechanism — it's a kernel driver at /dev/binder that gives you fast, secure RPC between processes. Almost everything system-level rides on it: when I call ActivityManager, PackageManager, or any AIDL service, that's a Binder transaction under the covers. The thing interviewers like to hear is that it's not just sockets — it's a single-copy, capability-based design with kernel-enforced caller identity."

Binder is Android's proprietary IPC mechanism — a Linux kernel driver at /dev/binder that enables lightweight, secure RPC between processes. It underpins virtually every Android API: ActivityManager, WindowManager, PackageManager, and every AIDL or Messenger call all go through Binder.

Under the hood

Binder isn't part of the mainline Linux kernel — it's an Android-specific character driver (drivers/android/binder.c) exposed as a misc device. Each process open()s /dev/binder and mmap()s a region (default ~1 MB minus two pages) that the driver manages. The framework layer on top is libbinder (native C++: IBinder, BBinder, BpBinder), with Java's android.os.IBinder/Binder/BinderProxy as a JNI bridge. Object identity is mediated by the kernel: a real BBinder has a binder_node, and remote references are binder_ref handles — integers scoped per-process, so handle 3 in process A and handle 3 in process B point to entirely different objects.

Java IBinder        ──JNI──►  libbinder (BBinder/BpBinder)  ──ioctl(BINDER_WRITE_READ)──►  binder driver
                                                                                            binder_node / binder_ref

How it works internally

🎤 Say it out loud (~30–45s): "When a client calls transact(), it marshals the args into a Parcel and the thread blocks on an ioctl into the binder driver. The driver copies the data once into a buffer that's already mmap'd into the target process, then wakes a binder thread there to run onTransact(). Two things I always call out: it's a single copy, not the double copy you get with sockets, which is why it's fast for small payloads; and the kernel stamps the real calling UID and PID so the server can trust who's calling without spoofing risk."
Client process                    Kernel (Binder driver)              Server process
──────────────                    ──────────────────────              ──────────────
IBinder.transact()  ─── data ───► /dev/binder                   ◄─── Binder.onTransact()
(blocks thread)                   copies once (shared mem)           (runs on Binder thread)
                    ◄── reply ───  wakes client thread

Unlike traditional UNIX IPC mechanisms like pipes, sockets, or shared memory, Binder achieves a single-copy transfer: data is written into a kernel-mapped buffer that is also mapped into the server's address space, so the kernel only copies once (client to kernel), not twice. This makes it significantly faster than UNIX domain sockets for small-to-medium messages.

There are three key properties worth knowing. First, identity: each Binder object has a unique kernel-level token, and the client holds a proxy rather than the real object (unless both sides are in the same process). Second, security: the kernel records the calling PID and UID via Binder.getCallingUid() and Binder.getCallingPid(), and these cannot be spoofed by userspace. Third, reference counting: the kernel tracks how many proxy holders exist, and when the last proxy is dropped, the Binder is garbage-collected on the server side.

Under the hood

The actual transport is a single ioctl(fd, BINDER_WRITE_READ, ...) carrying a binder_write_read struct. The Parcel's flat object table describes embedded binders and file descriptors via flat_binder_object entries, which the driver translates between processes (a binder_node on the owning side becomes a binder_ref/handle on the receiver). The "single copy" comes from binder_alloc: the driver copy_from_users the payload directly into the target process's mmap'd buffer, so the receiver reads it without a second copy. Caller identity is non-spoofable because the driver records task->cred (the sending thread's real UID/PID) into the transaction; getCallingUid() simply reads what the kernel stamped. Reference counting uses BC_INCREFS/BC_DECREFS commands, and a dying owner triggers binderDied() on registered DeathRecipients via the kernel notifying holders.

struct binder_transaction_data {
  union { size_t handle; void* ptr; } target;  // ref to target node
  uid_t   sender_euid;   // stamped by kernel, trusted
  size_t  data_size;     // marshalled Parcel bytes
  binder_size_t offsets_size;  // table of flat_binder_objects / fds
};

Binder thread pool

🎤 Say it out loud (~30s): "Every process that hosts a binder service gets a thread pool — managed by ProcessState, capped at 15 worker threads by default. Incoming transactions get dispatched to any idle thread, and importantly the main thread is never in that pool; it has its own Looper. The gotcha is contention: if all 15 threads are blocked downstream, callers queue, and if the caller that's blocked is your main thread, that's an ANR."

Every process that uses Binder has a thread pool managed by ProcessState. The default pool size is 15 threads. Incoming transactions are dispatched to any idle thread in the pool. The main thread is never part of this pool — it has its own Looper.

Server process
├── main thread  (Looper — not in Binder pool)
├── Binder thread 1  ← handles incoming IPC call
├── Binder thread 2
└── Binder thread N  (up to 15)

If all Binder threads are busy — say they're all blocked waiting on a downstream service — new transactions queue up and the caller blocks until a thread becomes available. If that blocked caller happens to be the main thread, you get an ANR.

Under the hood

ProcessState::self() is a per-process singleton that calls startThreadPool(), and the cap of 15 comes from DEFAULT_MAX_BINDER_THREADS passed to the driver via ioctl(BINDER_SET_MAX_THREADS, 15) — so the count is 1 (the main pooled thread spawned eagerly) plus up to 15 spawned on demand. The driver, not userspace, decides when to grow the pool: when work arrives and no thread is idle, it sends a BR_SPAWN_LOOPER command up to libbinder, which spawns a PoolThread that loops on IPCThreadState::joinThreadPool() → getAndExecuteCommand(). The driver tracks requested_threads vs max_threads so it never over-spawns. The main/UI thread is excluded because it never calls joinThreadPool; it runs Looper.loop() instead. This is why dispatch is true concurrency — two simultaneous IPCs run on two different binder threads, so your onTransact/AIDL stub methods must be thread-safe.

Synchronous vs asynchronous calls

🎤 Say it out loud (~30s): "By default a Binder call is synchronous — the calling thread blocks until the server replies, which is what you want when you need a return value. If you mark an AIDL method oneway, it becomes fire-and-forget: the call returns as soon as the transaction is queued, and there's no reply or thrown exception path. The trap is doing a synchronous call on the main thread to a slow remote — that's a classic ANR, so I either move it off-thread or make it oneway."
Mode Behaviour Use when
Synchronous (default)Caller blocks until server returnsYou need a return value or confirmation
Asynchronous (oneway in AIDL)Caller returns immediately; server processes laterFire-and-forget; notifications

Synchronous Binder calls from the main thread are an ANR risk if the remote is slow. Always call from a background thread or use oneway.

Under the hood

The mode is a flag bit (TF_ONE_WAY) on the transaction. For a synchronous call, libbinder writes a BC_TRANSACTION and then blocks reading for the matching BR_REPLY, parking the thread inside the ioctl until the driver wakes it — so the caller's thread is genuinely suspended in the kernel, not spinning. For oneway, the driver enqueues the transaction onto the target's work list and immediately returns BR_TRANSACTION_COMPLETE; there's no reply slot, which is why oneway methods must return void and can't surface a RemoteException from server-side logic. One important detail: oneway transactions to the same target binder are serialized by the driver (it won't dispatch the next until the current finishes), and they share a separate, smaller async buffer space — half the per-process buffer — so a flood of oneway calls can still hit TransactionTooLargeException or backpressure.

Transaction size limits and TransactionTooLargeException

🎤 Say it out loud (~30–45s): "Each process gets roughly a 1 MB binder buffer, and crucially it's shared across all in-flight transactions to that process, not per-call. So TransactionTooLargeException can fire even when your individual payload is small — if a bunch of transactions are simultaneously in flight, they collectively blow the budget. The usual culprit is shoving a big Bitmap or list into an Intent or onSaveInstanceState. The fix is to send a reference instead of the bytes: a ParcelFileDescriptor, a content URI, or SharedMemory."

The Binder kernel buffer is roughly 1 MB per process, shared across all simultaneous transactions from and to that process. Each individual transaction payload is practically limited to around 500 KB, but the smaller the better.

// BAD — sending a large Bitmap over Binder
val bundle = Bundle()
bundle.putParcelable("image", largeBitmap)   // could be several MB
intent.putExtras(bundle)
startActivity(intent)                         // throws TransactionTooLargeException at runtime

TransactionTooLargeException is thrown in two situations: when a single transaction exceeds the 1 MB kernel buffer, or when the combined in-flight transactions to a process push past that limit. There are four ways to avoid it: pass file descriptors via ParcelFileDescriptor instead of raw bytes; write large data to disk or a ContentProvider and send a URI reference instead; use shared memory via MemoryFile or the SharedMemory API on API 27 and above; or chunk large payloads if you need to stream them.

Under the hood

The ~1 MB figure is the size of the mmap'd region requested by ProcessState (BINDER_VM_SIZE, defined as ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)) — about 1 MB minus two guard pages. Allocation is handled by the driver's binder_alloc allocator carving buffers out of that region; when binder_alloc_new_buf can't find a free slot large enough, the failure propagates up as FAILED_TRANSACTION, which libbinder maps to a Java TransactionTooLargeException. Because the region is shared and freed only when the receiver calls BC_FREE_BUFFER (i.e., after it finishes handling the transaction), a slow consumer holding buffers makes the effective limit far lower than 1 MB — that's why the "combined in-flight" case bites. ParcelFileDescriptor and SharedMemory sidestep this entirely because they marshal a flat_binder_object of type FD: the driver dups the file descriptor into the receiver (fd_install) and the actual bytes never travel through the binder buffer — they live in a separate ashmem/memfd region.

Parcel payload  ──► binder_alloc region (~1MB, shared, freed on BC_FREE_BUFFER)
ParcelFileDescriptor / SharedMemory  ──► only an fd crosses; bytes stay in ashmem/memfd

What NOT to send over Binder

🎤 Say it out loud (~30s): "The rule of thumb is: send small, marshalled, primitive-ish data — and send references, not payloads, for anything big. So no large bitmaps or byte arrays (use a ParcelFileDescriptor or URI), no Serializable (it's reflection-based and slow — use Parcelable), no live object references since only Binder objects can cross the boundary, and no Cursors directly. And don't ship sensitive credentials until you've checked the caller's UID."
  • Large bitmaps or byte arrays — use ParcelFileDescriptor or a URI instead.
  • Serializable objects — they're slow and fragile; use Parcelable.
  • Database cursors — use the Cursor/ContentProvider API, which wraps them in BulkCursorToCursorAdaptor.
  • References to live objects — non-Binder Java objects simply cannot cross process boundaries.
  • Sensitive credentials in plaintext when you haven't yet validated the caller's UID.

Under the hood

A Parcel can only flatten three kinds of things: raw primitive bytes, file descriptors, and IBinder tokens (flat_binder_object). A plain Java object has no representation in that flat format, so Parcelable exists purely to teach the object how to serialize its fields into the byte stream and reconstruct on the other side via a CREATOR — the object itself doesn't travel; a value-copy does. Serializable "works" because Parcel.writeSerializable falls back to Java's ObjectOutputStream, which uses reflection to walk the object graph at runtime — orders of magnitude slower and producing far larger byte payloads, which makes it both an ANR and a TransactionTooLargeException risk. A Cursor returned across processes is never the real cursor: the framework substitutes a BulkCursorToCursorAdaptor proxy that fetches rows in windowed batches over Binder on demand, so you only pay for the rows you actually read. And a live object reference can't cross because there's no shared address space — only a BBinder/binder_node can be referenced remotely (as a handle), which is exactly why callbacks must themselves be Binder stubs.

RemoteException

🎤 Say it out loud (~30–45s): "Every call on a Binder proxy is really a transact across a process boundary, so it can fail if the other process died — that surfaces as a RemoteException. I always catch RemoteException, not just DeadObjectException, because the dead-object case is only one subclass; there are other transport failures too. And the subtle part is it's a checked exception, so the AIDL-generated proxy forces me to handle it at every call site, which is the framework nudging me to plan for the remote dying mid-call."

Any method call on a remote IBinder proxy can throw RemoteException if the remote process has died. The most common subclass is DeadObjectException, which specifically means the remote Binder object is gone. Always catch RemoteException rather than just DeadObjectException, because other transport errors exist too.

try {
    remoteService.doWork()
} catch (e: RemoteException) {
    // Remote process is dead or unreachable
    Log.e(TAG, "Remote service died", e)
    rebindService()
}

Under the hood

RemoteException is thrown from native code. When BinderProxy.transactNative() issues the ioctl(BINDER_WRITE_READ) syscall, the binder driver returns a status; if the target node is gone the driver returns BR_DEAD_REPLY, and IPCThreadState::waitForResponse maps that to DEAD_OBJECT (a status_t). JNI then throws the matching Java exception. DeadObjectException is a subclass of RemoteException, so catching the base type covers dead objects plus other failures like TransactionTooLargeException (driver returned FAILED_TRANSACTION because the payload exceeded the ~1 MB per-process binder transaction buffer).

client.doWork()
  → Proxy.transact(code, data, reply, 0)
    → BinderProxy.transactNative(...)        // JNI
      → IPCThreadState::transact
        → ioctl(fd, BINDER_WRITE_READ, &bwr)  // kernel
          ← BR_DEAD_REPLY  →  status_t DEAD_OBJECT
      ← jniThrowException("android/os/DeadObjectException")

Death recipients

🎤 Say it out loud (~30–45s): "A death recipient is how I get notified asynchronously that the remote process died, instead of finding out the hard way on my next call. I register it with linkToDeath right after binding, and binderDied fires on a Binder thread — not the main thread — so I bounce any UI or reconnect logic over to a Handler or StateFlow. The gotcha is to unlink in onServiceDisconnected so the recipient doesn't double-fire, and to register before my first transaction since the process can die at any moment."
class RemoteServiceClient {
    private var binder: IMyService? = null

    private val deathRecipient = IBinder.DeathRecipient {
        // Called on a Binder thread when the remote process dies
        binder = null
        mainHandler.post { reconnect() }
    }

    fun onServiceConnected(name: ComponentName, service: IBinder) {
        binder = IMyService.Stub.asInterface(service)
        // Register BEFORE first call — the process could die any time
        service.linkToDeath(deathRecipient, 0)
    }

    fun onServiceDisconnected(name: ComponentName) {
        // Called on main thread — unlink to avoid double-firing
        binder?.asBinder()?.unlinkToDeath(deathRecipient, 0)
        binder = null
    }

    fun reconnect() {
        bindService(intent, connection, Context.BIND_AUTO_CREATE)
    }
}

One critical detail: binderDied() fires on a Binder thread, not the main thread. If you need to update UI from it, post to a Handler or route through LiveData or StateFlow.

Under the hood

linkToDeath only works on a BinderProxy (a remote object) — it tells the kernel binder driver to track the lifetime of the remote node. The driver maintains a binder_ref with a death-notification list; when the owning process's /dev/binder fd is closed (process exits, killed by lowmemorykiller, or crashes), the driver walks every ref with a registered death recipient and queues a BR_DEAD_BINDER work item to that process's binder threads. The receiving process's IPCThreadState reads it and dispatches binderDied() via the JavaDeathRecipient JNI callback — which is why it runs on a Binder thread pool thread, not your main looper. The recipients are stored in a WeakReference-keyed list in native Parcel/BpBinder state, so you must hold a strong reference to the DeathRecipient yourself or it can be collected.

remote process dies → fd closed
  → binder driver iterates death refs
    → enqueues BR_DEAD_BINDER for each subscriber
      → subscriber's binder thread reads it
        → JavaDeathRecipient::binderDied()  // Binder thread, NOT main

Avoid heavy work in Binder callbacks

🎤 Say it out loud (~30–45s): "Incoming IPC runs on a fixed-size Binder thread pool — by default 16 threads per process — so if my onTransact or AIDL method body does network, DB, or heavy compute, I'm holding a thread the whole time and can starve the pool. If the pool is exhausted, every incoming transaction queues, including system calls from ActivityManager, which can stall the whole process. So I hand off heavy work to a coroutine or executor immediately and return from the Binder thread fast, usually delivering the result through a oneway callback interface."

Binder threads are a finite pool. If your onTransact implementation — or any AIDL method body — does heavy work like network I/O, database queries, or complex computation, you starve the pool and block all incoming IPC to that process, including system calls from ActivityManager.

The best practice is to dispatch heavy work to a coroutine or a separate thread pool immediately in the Binder callback, and return from the Binder thread as fast as possible.

// In AIDL Stub implementation — BAD
override fun processLargeData(data: ByteArray): Result {
    val result = database.runSlowQuery()  // blocks Binder thread
    return result
}

// GOOD — return a callback interface, or use oneway + callback pattern
override fun processLargeDataAsync(data: ByteArray, callback: IResultCallback) {
    scope.launch {
        val result = database.runSlowQuery()
        try { callback.onResult(result) } catch (e: RemoteException) { /* client died */ }
    }
}

Under the hood

When a process first uses Binder it calls ProcessState::startThreadPool, which registers the main thread plus spawns up to maxThreads worker threads (set via BINDER_SET_MAX_THREADS, default 15, so 16 total including the main binder thread). Each thread loops in IPCThreadState::getAndExecuteCommand, blocked in ioctl(BINDER_WRITE_READ) waiting for BR_TRANSACTION. When work arrives the driver picks an idle thread; if all are busy it sends BR_SPAWN_LOOPER until the max is reached, after which new transactions simply queue in the driver. A blocking call in onTransact keeps that thread parked, so a burst of slow calls drains the pool and back-pressures every other inbound transaction to the process — including high-priority system calls — until a thread frees up.

inbound transaction → binder driver
  → idle binder thread? → dispatch BR_TRANSACTION → onTransact()
  → all 16 busy?        → queue in driver (BR_SPAWN_LOOPER already maxed)
                          → callers wait → potential ANR upstream

Interview angles — Binder

Q: What is Binder?

"Binder is Android's kernel-level IPC driver. It enables RPC between processes using a single-copy data transfer, it gives you built-in caller identity through UID and PID, and it manages the lifecycle of remote objects with reference counting."

Q: What is a Binder thread?

"A Binder thread is a thread in the server process's pool that sits blocked inside ioctl(/dev/binder), waiting for incoming transactions. When a client calls a remote method, the kernel wakes one idle Binder thread to execute onTransact. Meanwhile, the calling thread on the client side stays blocked until the server returns — that's the synchronous mode."

Q: What happens if a Binder transaction blocks?

"The calling thread blocks indefinitely, or until a timeout if the kernel is using SYNC_WAIT. The critical case is when that blocked thread is the main thread: if the block exceeds 5 seconds for an Activity or 10 seconds for a Service, Android raises an ANR dialog. That's exactly why all synchronous IPC calls must go on a background thread unless the method is marked oneway."

Q: How do you design safe IPC APIs?

"There are six rules I follow. First, mark fire-and-forget calls as oneway in AIDL so the caller doesn't block. Second, use a callback or listener AIDL interface for results that come back from oneway calls. Third, always catch RemoteException — every remote call can throw it. Fourth, link death recipients immediately on bind, before you make any calls. Fifth, validate caller UID with Binder.getCallingUid() and never trust the client's self-reported identity. Sixth, keep transaction payloads small and use file descriptors for any bulk data."

5.3 AIDL

Definition

🎤 Say it out loud (~30–45s): "AIDL is Android's interface definition language — I describe an IPC contract in a .aidl file and the AIDL compiler generates all the Binder plumbing. On the server side it gives me a Stub abstract class extending Binder that I implement, and on the client side a Proxy that wraps transact. The point is it auto-generates the marshalling and unmarshalling so I'm not hand-writing writeInt/readInt against Parcels, and it assigns each method a stable transaction code under the hood."

AIDL — Android Interface Definition Language — is Android's IDL for defining IPC interfaces. The AIDL compiler, either the standalone aidl tool or the Gradle plugin, generates Java and Kotlin boilerplate for you: a Stub abstract class on the server side that extends Binder, and a Proxy class on the client side that wraps IBinder.transact(). You define the contract in a .aidl file and the generated code handles all the marshalling and unmarshalling.

Under the hood

The compiler turns each interface method into a constant transaction code (TRANSACTION_methodName = IBinder.FIRST_CALL_TRANSACTION + n). The generated Proxy writes an interface token plus each argument into a Parcel, calls mRemote.transact(code, data, reply, flags), then reads the result back. The generated Stub.onTransact(code, data, reply, flags) is a big switch on the code: it enforces the interface descriptor with data.enforceInterface(...), unmarshals the arguments, calls your concrete implementation, and writes the return value into reply. Stub.asInterface(binder) does a queryLocalInterface check — if the IBinder is local (same process) it returns your implementation directly with no marshalling; only if it's a remote BinderProxy does it wrap it in the Proxy.

// Generated (simplified)
public boolean onTransact(int code, Parcel data, Parcel reply, int flags) {
    switch (code) {
        case TRANSACTION_doWork:
            data.enforceInterface(DESCRIPTOR);
            int arg = data.readInt();
            int result = this.doWork(arg);   // your impl
            reply.writeNoException();
            reply.writeInt(result);
            return true;
    }
    return super.onTransact(code, data, reply, flags);
}

Supported types in AIDL

🎤 Say it out loud (~30–45s): "AIDL only supports types it knows how to marshal into a Parcel: the primitives, String and CharSequence, List and Map of supported types, IBinder, other AIDL interfaces, and any Parcelable — but a Parcelable has to be declared in its own .aidl file so the compiler knows about it. The big gotcha is that Serializable and arbitrary objects aren't supported, and you never stream bulk data through a transaction — you pass a ParcelFileDescriptor instead, because the transaction buffer is only about a megabyte for the whole process."
Category Types
Primitivesboolean, byte, char, short, int, long, float, double
StringsString, CharSequence
CollectionsList<T> (T must be AIDL-supported), Map (keys/values must be supported)
ParcelableAny class implementing Parcelable (must be declared in its own .aidl file)
Other interfacesOther AIDL interfaces

Not supported natively: Serializable, arbitrary objects, or file streams — for those, use ParcelFileDescriptor.

Under the hood

Every supported type maps to a concrete Parcel.writeX/readX pair that the generated code emits. Primitives use writeInt/writeLong/etc.; String uses writeString (length-prefixed UTF-16); List/Map use writeList/writeMap, which prefix the element count and recursively parcel each entry. A Parcelable is written via writeTypedObject/createFromParcel, which is why the type must implement Parcelable and declare a CREATOR. IBinder is special: writeStrongBinder doesn't copy the object — it writes a flat_binder_object that the kernel binder driver translates into a handle in the receiving process, preserving object identity across the boundary. A ParcelFileDescriptor is marshalled as a flat_binder_object of type BINDER_TYPE_FD; the driver dup()s the file descriptor into the target process rather than copying bytes, which is exactly why it's the right tool for bulk data versus stuffing megabytes into the ~1 MB transaction buffer.

Directional tags: in, out, inout

🎤 Say it out loud (~30–45s): "Directional tags tell aidl which way to marshal a parameter across the Binder transaction. in copies the data from client to server only, out ships an empty container over and copies it back filled, and inout copies in both directions, so it's the most expensive. Primitives and Strings are always implicitly in; the gotcha is that for object parameters the tag isn't optional — you have to specify one explicitly or the build fails, and people who slap inout on everything are paying for two copies they usually don't need."

Parameters in AIDL methods have a directional tag that controls marshalling direction:

Tag Client → Server Server → Client Use when
in (default for primitives)Data copiedNot copied backClient sends, server reads only
outNot copied to serverCopied backClient provides empty container; server fills it
inoutCopied both waysCopied backBidirectional; most expensive

Primitives and String are always implicitly in. Objects require an explicit directional tag.

Under the hood

The directional tag controls the writeToParcel/readFromParcel calls the aidl compiler emits into the generated Proxy and Stub. For an in parameter, the Proxy writes the object into the outgoing _data parcel and the Stub reads it; nothing is read back. For out, the Proxy writes nothing meaningful into _data but, after transact returns, reads the object back from the _reply parcel by calling readFromParcel on the same client-side instance — which is why out/inout Parcelables must implement a readFromParcel(Parcel) method, not just createFromParcel. inout emits both. Because everything is a serialized copy, mutations on the server are only visible to the client when a return path exists.

in    : Proxy.writeToParcel(_data)  --transact-->  Stub.createFromParcel(_data)
out   :                              transact      Stub fills obj -> writeToParcel(_reply)
        Proxy obj.readFromParcel(_reply) <-- reply
inout : both of the above

One-way (oneway) calls

🎤 Say it out loud (~30–45s): "Marking a method oneway makes the call fire-and-forget — the client returns as soon as the transaction is queued in the kernel driver, and the server runs it later on a Binder thread. So no return value and no out/inout params, because there's no reply path. The nuance interviewers want is that oneway calls to the same binder are still ordered, but they go through a much smaller per-process async transaction buffer, so if you flood it you'll hit TransactionTooLargeException-style failures, and the server still processes them serially on the Binder thread pool."

Adding oneway to a method makes the client call non-blocking. The client returns immediately after the transaction is enqueued, and the server processes the call asynchronously on a Binder thread. The trade-offs are that oneway methods cannot have return values, and they cannot have out or inout parameters because there is no return path.

interface IEventService {
    oneway void logEvent(String name, in Bundle params);  // fire and forget
    int getEventCount();                                   // synchronous, blocks caller
}

If you mark an entire interface oneway, all methods in it become non-blocking.

Under the hood

A synchronous call passes the transact flag 0; oneway passes IBinder.FLAG_ONEWAY. With the flag set, the kernel Binder driver copies the transaction into the target process's buffer and immediately returns control to the caller without blocking on a reply. The driver dispatches oneway transactions to a single target one-at-a-time (it serializes them per-binder so ordering is preserved), but they share the limited asynchronous transaction space carved out of the process's ~1MB binder mmap region. Crucially, the caller's own thread does not block, so a oneway call cannot ANR the client — but exceptions thrown on the server side are silently dropped rather than rethrown as RemoteException, which is a common surprise.

Minimal AIDL example

🎤 Say it out loud (~30–45s): "This is the canonical shape: you declare the interface in a .aidl file, the build generates a Stub you subclass on the server and a Proxy you get on the client via Stub.asInterface. The key detail people miss is that every Binder call lands on a thread from the pool, not the main thread, so the server impl must be thread-safe and you should validate the caller's UID inside the method — never trust the client. And on the client side you always call from a background thread because synchronous transactions block."

File: app/src/main/aidl/com/example/ICalculator.aidl

// ICalculator.aidl
package com.example;

interface ICalculator {
    /** Synchronous call — caller blocks until result is returned. */
    int add(int a, int b);

    /** Fire-and-forget — caller returns immediately. */
    oneway void scheduleComputation(int jobId, in int[] operands);

    /** Passes a Parcelable in both directions. */
    ComputeResult compute(inout ComputeRequest request);
}

File: app/src/main/aidl/com/example/ComputeRequest.aidl

// Every Parcelable used in AIDL needs its own declaration file.
package com.example;
parcelable ComputeRequest;

Server-side Stub implementation:

class CalculatorService : Service() {

    private val binder = object : ICalculator.Stub() {
        override fun add(a: Int, b: Int): Int {
            // Binder thread — keep it fast or dispatch to a coroutine scope
            return a + b
        }

        override fun scheduleComputation(jobId: Int, operands: IntArray) {
            // oneway — no return value, caller already unblocked
            scope.launch { processJob(jobId, operands) }
        }

        override fun compute(request: ComputeRequest): ComputeResult {
            // Validate caller — never trust the client
            val callerUid = Binder.getCallingUid()
            require(isAuthorized(callerUid)) { "Unauthorized UID: $callerUid" }
            return performCompute(request)
        }
    }

    override fun onBind(intent: Intent): IBinder = binder
}

Client-side binding and usage:

class ClientActivity : AppCompatActivity() {
    private var calculator: ICalculator? = null

    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName, service: IBinder) {
            calculator = ICalculator.Stub.asInterface(service)
            // Stub.asInterface: returns the Stub directly if same process,
            // or wraps it in a Proxy if cross-process.
            service.linkToDeath(deathRecipient, 0)
        }
        override fun onServiceDisconnected(name: ComponentName) {
            calculator = null
        }
    }

    private val deathRecipient = IBinder.DeathRecipient {
        calculator = null
        runOnUiThread { rebind() }
    }

    fun callRemote() {
        lifecycleScope.launch(Dispatchers.IO) {   // NEVER call from main thread
            try {
                val result = calculator?.add(3, 4) ?: return@launch
                withContext(Dispatchers.Main) { updateUi(result) }
            } catch (e: RemoteException) {
                Log.e(TAG, "Remote call failed", e)
            }
        }
    }
}

Under the hood

The aidl tool generates ICalculator.java containing three nested pieces: the ICalculator interface, an abstract Stub extending Binder and implementing ICalculator, and a private Proxy wrapping an IBinder. Each method gets a TRANSACTION_<name> constant (e.g. Stub.TRANSACTION_add = FIRST_CALL_TRANSACTION + 0) assigned by declaration order. The Proxy method writes args into a _data Parcel, calls mRemote.transact(code, _data, _reply, flags), then reads the result from _reply. The Stub's onTransact(code, data, reply, flags) switch dispatches on that code, unmarshals args, invokes the real method, and writes the return value back. Stub.asInterface calls queryLocalInterface on the IBinder: if the binder lives in the same process it returns the concrete Stub directly (no marshalling, a plain virtual call), otherwise it returns a Proxy. That is why a "remote" call can transparently become an in-process method call.

asInterface(binder):
  local = binder.queryLocalInterface(DESCRIPTOR)
  if (local instanceof ICalculator) return local   // same process, no IPC
  else return new Stub.Proxy(binder)                // cross-process, marshals

Versioning and backward compatibility

🎤 Say it out loud (~30–45s): "The cardinal rule is that method dispatch is positional — IDs are assigned by declaration order — so you can only ever append methods, never remove or reorder them, or you'll silently route calls to the wrong implementation. For evolving Parcelables I write a version integer as the very first field and gate reads of newer fields on it, and on stable AIDL I lean on default method implementations so old clients survive. The gotcha is UNKNOWN_TRANSACTION: an old server hit with a new method code returns it, and your client has to handle that instead of assuming the call succeeded."

Binder is the backbone of platform services across Android versions, so breaking an AIDL interface is extremely disruptive. There are five rules to follow.

First, never remove or reorder methods. Method IDs are assigned by declaration order, so reordering breaks binary compatibility silently — calls dispatch to the wrong method with no compiler warning.

Second, add new methods at the end only. Old clients calling transact with an unrecognized method code receive UNKNOWN_TRANSACTION, which the Stub base class returns as false. Handle that gracefully.

Third, for stable AIDL interfaces you can provide default method bodies, which allows new methods to be added without breaking old clients that haven't implemented them yet.

Fourth, version the interface explicitly. The convention is a getVersion(): Int method, or the @VintfStability and @Backing annotations for HAL-level AIDL.

Fifth, for Parcelable evolution: add new fields with defaults, write a version integer as the first field in writeToParcel, and check that version number in createFromParcel before reading newer fields.

// Robust Parcelable that handles older versions
data class UserProfile(
    val id: String,
    val name: String,
    val email: String = ""   // added in v2 — must default for older senders
) : Parcelable {
    companion object CREATOR : Parcelable.Creator<UserProfile> {
        private const val VERSION = 2

        override fun createFromParcel(source: Parcel): UserProfile {
            val version = source.readInt()
            val id = source.readString()!!
            val name = source.readString()!!
            val email = if (version >= 2) source.readString()!! else ""
            return UserProfile(id, name, email)
        }
        override fun newArray(size: Int) = arrayOfNulls<UserProfile>(size)
    }

    override fun writeToParcel(dest: Parcel, flags: Int) {
        dest.writeInt(VERSION)
        dest.writeString(id)
        dest.writeString(name)
        dest.writeString(email)
    }
    override fun describeContents() = 0
}

Under the hood

The positional dispatch is literal: onTransact is a switch (code) over FIRST_CALL_TRANSACTION + n constants generated in declaration order, so inserting a method in the middle renumbers every method after it. Stable AIDL (the aidl_interface Soong module used for platform/VINTF interfaces) addresses this by hashing the interface and freezing versioned snapshots under aidl_api/; the build fails if you mutate a frozen version. Default method bodies work because stable AIDL generates a getDefaultImpl()/setDefaultImpl() hook and the Proxy falls back to it when transact returns false for an unknown code. For Parcelables, the leading version int is just a plain writeInt/readInt at a known offset — there is no schema in the wire format, so reader and writer must agree on field order, and the version gate is the only thing letting a newer reader skip absent older-sender fields safely.

Interview angles — AIDL

Q: When do you need AIDL?

"You reach for AIDL when you need typed, multi-method RPC between processes — specifically when you need return values, when you have multiple concurrent callers, or when you're passing complex object graphs. Concrete examples are a background processing service that returns results, an inter-app SDK, or a system service extension."

Q: AIDL vs Messenger?

See dedicated section below.

Q: Synchronous vs one-way AIDL?

"Synchronous means the caller blocks until the server returns, and you can have a return value. One-way means the caller returns immediately after enqueuing the transaction, but there's no return value possible. I use oneway for any event or notification call where I don't need a result back, because it completely eliminates the ANR risk on the caller side."

Q: How do you version IPC contracts?

"There are two parts to this. For the interface itself: add new methods at the end only, never remove or reorder existing ones, and add a getVersion(): Int method so callers can check what the server supports before calling new methods. For Parcelable types that go across the wire: write a version integer as the first field, and in createFromParcel check that version before reading any fields that were added after the initial version."

5.4 Messenger

Definition

🎤 Say it out loud (~30–45s): "Messenger is the lightweight cousin of AIDL — it wraps a Handler behind a Binder so a remote process can post Message objects into your handler's queue. You hand the client a Messenger built from your handler, they call send, and the message arrives on whatever thread the handler's Looper runs on. The key trade-off is that it serializes everything onto one queue, so there's no concurrency and no real return value — you reply by having the client pass its own Messenger in Message.replyTo. It's perfect when you just need a serialized command channel and don't want to write an AIDL interface."

Messenger is a simpler IPC mechanism built on top of Binder. It wraps a Handler in a Binder object, letting the remote process send Message objects to that Handler. Under the hood it still uses AIDL — Android ships IMessenger.aidl in the framework — but it hides all the marshalling complexity behind the familiar Message API.

Under the hood

A Messenger holds a single IMessenger binder. On the server side, Messenger(Handler) creates a Handler.MessengerImpl which is an IMessenger.Stub whose send(Message msg) simply calls Handler.sendMessage, enqueuing the Message into the handler's MessageQueue. On the client side, Messenger(IBinder) wraps the binder in IMessenger.Stub.asInterface, and messenger.send(msg) is a oneway Binder transaction that marshals the Message via Message.writeToParcel. Because dispatch funnels through one Looper, all calls are processed serially and there's no per-call reply value — Message.replyTo carries the caller's own Messenger so the server can send back. The Message's obj field can only cross processes if it's a framework Parcelable; arbitrary objects throw, which is why Bundle-based data is the safe payload.

How it works

🎤 Say it out loud (~30–45s): "Messenger is really just a thin, friendly wrapper around a single Binder interface called IMessenger. The service hands the client a Binder, the client wraps it in a Messenger and calls send(), and that message gets marshalled across Binder and dropped onto the server's Handler queue. The key thing to know is everything funnels through one Handler, so messages are processed strictly one at a time — there's no parallelism — and there's no return value, so if you want a reply you attach a replyTo Messenger and the response comes back asynchronously."
Client process                         Server process
──────────────                         ──────────────
Messenger(service IBinder)             Handler handles messages sequentially
   └─ serverMessenger.send(msg)        └─ handleMessage(msg: Message)
        │                                       ▲
        └─── Binder IPC ──────────────────────►─┘
             (IMessenger.send transaction)
  1. The Service returns a Messenger's underlying IBinder from onBind().
  2. The client wraps that IBinder in Messenger(binder).
  3. The client calls serverMessenger.send(message).
  4. The Message is marshalled over Binder and delivered to the server's Handler.handleMessage().
  5. For replies, the client attaches replyTo = Messenger(clientHandler) to the message.

All messages are processed sequentially through the Handler's MessageQueue. There is no parallelism — the server handles one message at a time, by design.

Under the hood

Messenger is built on top of a framework-internal AIDL interface, IMessenger, which has exactly one oneway method: void send(Message msg). The Handler you pass to the constructor exposes a private IMessenger stub via Handler.getIMessenger(); Messenger simply holds that stub's IBinder. When you call send(), the framework writes the Message into the transaction Parcel via Message.writeToParcel() — which only marshals what, arg1, arg2, data (the Bundle), and replyTo, not Message.obj unless it is a Parcelable (and even then only on API 21+). Because the underlying transaction is oneway, send() returns immediately and the kernel enqueues the transaction without blocking the caller.

Client: serverMessenger.send(msg)
   → IMessenger.Stub proxy.transact(send, parcel, null, FLAG_ONEWAY)
   → binder driver copies parcel into server's process
   → server Binder thread: IMessenger.Stub.onTransact()
       → Message.obtain() + readFromParcel()
       → msg.target = the wrapped Handler
       → Handler.sendMessage(msg)  // enqueues on MessageQueue
   → Looper dispatches → Handler.handleMessage(msg)

Service skeleton

🎤 Say it out loud (~30–45s): "On the service side I just create a Handler with my message-handling logic, wrap it in a Messenger, and return messenger.binder from onBind(). The Handler's handleMessage runs on whatever Looper I gave it — by default the main thread, which I have to remember, because if the work is heavy I'll block the UI thread of my own process. The gotcha I always mention is checking msg.replyTo and wrapping the reply send() in a try/catch for RemoteException, since the client process can die between request and reply."
class MessengerService : Service() {

    private val incomingHandler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            when (msg.what) {
                MSG_COMPUTE -> {
                    val input = msg.data.getInt("value")
                    val result = input * 2

                    // Reply to client if replyTo is set
                    msg.replyTo?.let { replyMessenger ->
                        val reply = Message.obtain(null, MSG_RESULT)
                        reply.data = Bundle().apply { putInt("result", result) }
                        try {
                            replyMessenger.send(reply)
                        } catch (e: RemoteException) {
                            // Client died — ignore or clean up
                        }
                    }
                }
                else -> super.handleMessage(msg)
            }
        }
    }

    private val messenger = Messenger(incomingHandler)

    override fun onBind(intent: Intent): IBinder = messenger.binder

    companion object {
        const val MSG_COMPUTE = 1
        const val MSG_RESULT = 2
    }
}

Under the hood

messenger.binder returns the IBinder backing the Handler's internal IMessenger.Stub. That stub is a real Binder object, so the framework registers it with the Binder driver and it gets a node in the kernel; when a remote send() arrives, a thread from this process's Binder thread pool runs IMessenger.Stub.onTransact(), reconstructs the Message, sets msg.target to your incomingHandler, and posts it to that Handler's MessageQueue. The Binder thread does not run handleMessage itself — it just enqueues. Dispatch happens later on the Looper thread, which is why a Looper.getMainLooper()-backed handler serializes all incoming IPC onto the main thread, and why heavy work there can ANR.

Client skeleton

🎤 Say it out loud (~30–45s): "The client binds to the service, and in onServiceConnected I wrap the returned IBinder in a Messenger so I can call send() on it. For replies I create my own Messenger backed by a local Handler and stamp it onto msg.replyTo — that's the only way the server can talk back, because send() is one-way. The thing I'm careful about is that send() can throw RemoteException if the service has died, and that the serverMessenger is null until the connection is established, so every send needs both a null check and a try/catch."
class MessengerClient : AppCompatActivity() {
    private var serverMessenger: Messenger? = null

    private val replyHandler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            if (msg.what == MessengerService.MSG_RESULT) {
                val result = msg.data.getInt("result")
                updateUi(result)
            }
        }
    }
    private val replyMessenger = Messenger(replyHandler)

    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName, service: IBinder) {
            serverMessenger = Messenger(service)
        }
        override fun onServiceDisconnected(name: ComponentName) {
            serverMessenger = null
        }
    }

    fun sendRequest(value: Int) {
        val msg = Message.obtain(null, MessengerService.MSG_COMPUTE)
        msg.data = Bundle().apply { putInt("value", value) }
        msg.replyTo = replyMessenger   // attach reply channel
        try {
            serverMessenger?.send(msg)
        } catch (e: RemoteException) {
            Log.e(TAG, "Service not available", e)
        }
    }
}

Under the hood

Messenger(service) on the client constructs a Messenger whose internal field is IMessenger.Stub.asInterface(service) — i.e. a proxy over the remote Binder, not a local stub. msg.replyTo = replyMessenger works because replyMessenger is itself a Messenger, and Messenger implements Parcelable: when the outgoing Message is written to the transaction Parcel, the reply Messenger's underlying IBinder is flattened via Parcel.writeStrongBinder(). The kernel translates that binder reference into a handle valid in the server process, so when the server later calls replyMessenger.send(), its transaction is routed back across the driver to the client's replyHandler. This binder-handle translation by the driver is what makes bidirectional callbacks possible without either side knowing the other's address.

Key characteristics

🎤 Say it out loud (~30–45s): "The defining trait of Messenger is sequential, single-threaded delivery — one Handler, one MessageQueue, one message at a time — which is great for ordered command processing but a bottleneck for throughput. There's no type safety: you discriminate on an integer msg.what and read untyped Bundle data, unlike AIDL's generated typed methods. And it's fire-and-forget with no return values. The practical gotcha is the Handler runs on its Looper's thread, usually main, so for heavy work you back it with a HandlerThread."
  • Sequential delivery: All messages queue through a single Handler, so there's no concurrent message processing. That's good for ordered operations but bad for high-throughput parallel work.
  • Message payload: Message.obj can hold any Parcelable. Message.data is a Bundle. Message.arg1 and arg2 are int fields for cheap primitives.
  • msg.what: An integer discriminator for the message type. You must define constants for all message types — there is no type safety here, unlike AIDL interfaces.
  • No return values: send() is always fire-and-forget. Replies require the client to attach a separate replyTo Messenger to the message.
  • Thread context: The Handler executes on whatever thread its Looper belongs to — usually the main thread. If message handling is heavy, back it with a HandlerThread instead.
// Using HandlerThread for background message processing
class HeavyMessengerService : Service() {
    private lateinit var handlerThread: HandlerThread

    override fun onCreate() {
        super.onCreate()
        handlerThread = HandlerThread("MessengerWorker").also { it.start() }
    }

    private val incomingHandler by lazy {
        object : Handler(handlerThread.looper) {
            override fun handleMessage(msg: Message) { /* heavy work ok here */ }
        }
    }

    private val messenger by lazy { Messenger(incomingHandler) }
    override fun onBind(intent: Intent): IBinder = messenger.binder

    override fun onDestroy() {
        handlerThread.quitSafely()
        super.onDestroy()
    }
}

Under the hood

The "single-threaded" property is not enforced by Messenger itself but is an emergent consequence of the Handler/Looper/MessageQueue machinery underneath. Multiple Binder threads can call onTransact() concurrently and each enqueues a Message, but a single Looper thread drains that one MessageQueue serially via Looper.loop(). So concurrency exists on the receiving side (Binder pool) yet collapses to a serial pipeline at the dispatch side. Backing the Handler with a HandlerThread only moves that serial dispatch off the main thread — it does not parallelize it; you still get exactly one message handled at a time. True parallel IPC requires AIDL, where each synchronous call occupies its own Binder pool thread inside onTransact.

Interview angles — Messenger

Q: Messenger vs AIDL?

See detailed table in the next section.

Q: When is Messenger enough?

"Messenger is the right call when your IPC is simple, sequential, and fire-and-forget — for example, a background download service where you just send it commands and don't need typed responses back. It's also good for prototyping or when you need cross-process event delivery but don't want to deal with generating and maintaining AIDL stubs."

Q: Why is Messenger simpler but less flexible?

"Because everything goes through a single Handler and MessageQueue. There are no return values, no parallel processing, and no typed method signatures — every message is an integer code in msg.what, which is untyped and error-prone. And it fundamentally can't express 'give me back a result synchronously.' If you need a reply, you have to attach a replyTo Messenger to every message and handle the response asynchronously on the other end. That overhead is fine for simple command-style patterns, but the moment you need a real typed API with return values, you've outgrown Messenger."

One thing worth calling out specifically: Parcelable is not safe for disk persistence. The Parcel binary format is internal to Android and can change between OS versions — a Parcel written on Android 12 might be unreadable on Android 14. For persistence, use Room, DataStore, or JSON/Protobuf.
