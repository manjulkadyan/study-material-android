5.1 Android Process Model

Definition

Every Android app runs in its own Linux process by default, completely isolated from every other app at the OS kernel level. That process hosts a Dalvik/ART VM, a main thread with its own Looper, a Binder thread pool, and the app's heap. The OS assigns each process a unique UID and PID.

How components map to processes

By default, all four component types (Activity, Service, BroadcastReceiver, ContentProvider) declared in a single APK run in the same process — the one named after the app's package. You opt components into a different process via the android:process attribute:

<!-- AndroidManifest.xml -->
<service
    android:name=".AudioPlayerService"
    android:process=":audio" />   <!-- ':' prefix = private process, scoped to this app -->

<service
    android:name=".SyncService"
    android:process="com.example.sync" />  <!-- no ':' = shared process, any app with same UID -->

When components live in different processes, they share no memory at all — not the heap, not static fields, not singletons. The JVM runs a completely separate instance for every process. That's the fundamental reason IPC exists: you cannot pass an object reference across process boundaries.

Memory isolation

Scope Same process Different processes
Static variablesSharedNot shared — each process has its own copy
Singleton instancesSharedIndependent instances
Object referencesValid pointersMeaningless (different address space)
Files / SharedPreferencesShared if same UID and no MODE_PRIVATENeed ContentProvider or FileProvider

"What happens to static variables across processes?"

"Each process gets its own JVM, so a companion object or @JvmStatic field is initialized independently in every process. Changing the value in process A has zero effect on process B. This is a surprisingly common source of confusion when teams introduce a :remote service without realizing their in-memory cache now has two stale, independent copies."

Process lifecycle and death

The Android OS is free to kill any background process at any time to reclaim memory. The kill order follows a priority ladder — foreground, then visible, then service, then background, then empty — but the OS makes no guarantees beyond that ordering. A service running in a separate process can die while the app's UI is still alive, or vice versa.

There are three implications worth internalizing. First, any state stored only in static or instance memory is gone on process death. Second, if you hold a reference to a remote IBinder, the remote can disappear under you at any moment — you must handle RemoteException and register a death recipient (covered in §5.2). Third, bound services get a callback when the remote process dies: ServiceConnection.onServiceDisconnected.

Bound vs remote services

Type Same process Different process
Started servicestartService()startService() across packages, but still same process unless android:process set
Bound service (local)IBinder returned from onBind() is a direct object reference, no IPC overheadN/A
Bound service (remote)—onBind() returns an AIDL stub or Messenger; every call crosses a Binder transaction

The key insight is that binding to a service in another process is still bindService(), but Android transparently routes the IBinder through the Binder driver. The client receives a proxy object, not the real object.

Interview angles — process model

Q: Process vs thread?

"A process is an OS-level isolation unit — it has its own address space, its own PID, its own UID. A thread, by contrast, shares the address space with all the other threads in the same process. So IPC is what you need when you're crossing process boundaries; thread synchronization handles coordination within a single process."

Q: How do you communicate with a service in another process?

"You return an IBinder from Service.onBind(). The client receives a proxy object rather than the real thing, and each method call on that proxy becomes a Binder transaction that the kernel Binder driver routes over to the server process."

Q: How do you handle remote process death?

"You register an IBinder.DeathRecipient via binder.linkToDeath(recipient, 0). When the remote process dies, the binderDied() callback fires on a Binder thread, and from there you can attempt a rebind, surface an error to the user, or clean up any state you were holding. You should also implement ServiceConnection.onServiceDisconnected to cover the service binding lifecycle side of the same event."

5.2 Binder

Definition

Binder is Android's proprietary IPC mechanism — a Linux kernel driver at /dev/binder that enables lightweight, secure RPC between processes. It underpins virtually every Android API: ActivityManager, WindowManager, PackageManager, and every AIDL or Messenger call all go through Binder.

How it works internally

Client process                    Kernel (Binder driver)              Server process
──────────────                    ──────────────────────              ──────────────
IBinder.transact()  ─── data ───► /dev/binder                   ◄─── Binder.onTransact()
(blocks thread)                   copies once (shared mem)           (runs on Binder thread)
                    ◄── reply ───  wakes client thread

Unlike traditional UNIX IPC mechanisms like pipes, sockets, or shared memory, Binder achieves a single-copy transfer: data is written into a kernel-mapped buffer that is also mapped into the server's address space, so the kernel only copies once (client to kernel), not twice. This makes it significantly faster than UNIX domain sockets for small-to-medium messages.

There are three key properties worth knowing. First, identity: each Binder object has a unique kernel-level token, and the client holds a proxy rather than the real object (unless both sides are in the same process). Second, security: the kernel records the calling PID and UID via Binder.getCallingUid() and Binder.getCallingPid(), and these cannot be spoofed by userspace. Third, reference counting: the kernel tracks how many proxy holders exist, and when the last proxy is dropped, the Binder is garbage-collected on the server side.

Binder thread pool

Every process that uses Binder has a thread pool managed by ProcessState. The default pool size is 15 threads. Incoming transactions are dispatched to any idle thread in the pool. The main thread is never part of this pool — it has its own Looper.

Server process
├── main thread  (Looper — not in Binder pool)
├── Binder thread 1  ← handles incoming IPC call
├── Binder thread 2
└── Binder thread N  (up to 15)

If all Binder threads are busy — say they're all blocked waiting on a downstream service — new transactions queue up and the caller blocks until a thread becomes available. If that blocked caller happens to be the main thread, you get an ANR.

Synchronous vs asynchronous calls

Mode Behaviour Use when
Synchronous (default)Caller blocks until server returnsYou need a return value or confirmation
Asynchronous (oneway in AIDL)Caller returns immediately; server processes laterFire-and-forget; notifications

Synchronous Binder calls from the main thread are an ANR risk if the remote is slow. Always call from a background thread or use oneway.

Transaction size limits and TransactionTooLargeException

The Binder kernel buffer is roughly 1 MB per process, shared across all simultaneous transactions from and to that process. Each individual transaction payload is practically limited to around 500 KB, but the smaller the better.

// BAD — sending a large Bitmap over Binder
val bundle = Bundle()
bundle.putParcelable("image", largeBitmap)   // could be several MB
intent.putExtras(bundle)
startActivity(intent)                         // throws TransactionTooLargeException at runtime

TransactionTooLargeException is thrown in two situations: when a single transaction exceeds the 1 MB kernel buffer, or when the combined in-flight transactions to a process push past that limit. There are four ways to avoid it: pass file descriptors via ParcelFileDescriptor instead of raw bytes; write large data to disk or a ContentProvider and send a URI reference instead; use shared memory via MemoryFile or the SharedMemory API on API 27 and above; or chunk large payloads if you need to stream them.

What NOT to send over Binder

  • Large bitmaps or byte arrays — use ParcelFileDescriptor or a URI instead.
  • Serializable objects — they're slow and fragile; use Parcelable.
  • Database cursors — use the Cursor/ContentProvider API, which wraps them in BulkCursorToCursorAdaptor.
  • References to live objects — non-Binder Java objects simply cannot cross process boundaries.
  • Sensitive credentials in plaintext when you haven't yet validated the caller's UID.

RemoteException

Any method call on a remote IBinder proxy can throw RemoteException if the remote process has died. The most common subclass is DeadObjectException, which specifically means the remote Binder object is gone. Always catch RemoteException rather than just DeadObjectException, because other transport errors exist too.

try {
    remoteService.doWork()
} catch (e: RemoteException) {
    // Remote process is dead or unreachable
    Log.e(TAG, "Remote service died", e)
    rebindService()
}

Death recipients

class RemoteServiceClient {
    private var binder: IMyService? = null

    private val deathRecipient = IBinder.DeathRecipient {
        // Called on a Binder thread when the remote process dies
        binder = null
        mainHandler.post { reconnect() }
    }

    fun onServiceConnected(name: ComponentName, service: IBinder) {
        binder = IMyService.Stub.asInterface(service)
        // Register BEFORE first call — the process could die any time
        service.linkToDeath(deathRecipient, 0)
    }

    fun onServiceDisconnected(name: ComponentName) {
        // Called on main thread — unlink to avoid double-firing
        binder?.asBinder()?.unlinkToDeath(deathRecipient, 0)
        binder = null
    }

    fun reconnect() {
        bindService(intent, connection, Context.BIND_AUTO_CREATE)
    }
}

One critical detail: binderDied() fires on a Binder thread, not the main thread. If you need to update UI from it, post to a Handler or route through LiveData or StateFlow.

Avoid heavy work in Binder callbacks

Binder threads are a finite pool. If your onTransact implementation — or any AIDL method body — does heavy work like network I/O, database queries, or complex computation, you starve the pool and block all incoming IPC to that process, including system calls from ActivityManager.

The best practice is to dispatch heavy work to a coroutine or a separate thread pool immediately in the Binder callback, and return from the Binder thread as fast as possible.

// In AIDL Stub implementation — BAD
override fun processLargeData(data: ByteArray): Result {
    val result = database.runSlowQuery()  // blocks Binder thread
    return result
}

// GOOD — return a callback interface, or use oneway + callback pattern
override fun processLargeDataAsync(data: ByteArray, callback: IResultCallback) {
    scope.launch {
        val result = database.runSlowQuery()
        try { callback.onResult(result) } catch (e: RemoteException) { /* client died */ }
    }
}

Interview angles — Binder

Q: What is Binder?

"Binder is Android's kernel-level IPC driver. It enables RPC between processes using a single-copy data transfer, it gives you built-in caller identity through UID and PID, and it manages the lifecycle of remote objects with reference counting."

Q: What is a Binder thread?

"A Binder thread is a thread in the server process's pool that sits blocked inside ioctl(/dev/binder), waiting for incoming transactions. When a client calls a remote method, the kernel wakes one idle Binder thread to execute onTransact. Meanwhile, the calling thread on the client side stays blocked until the server returns — that's the synchronous mode."

Q: What happens if a Binder transaction blocks?

"The calling thread blocks indefinitely, or until a timeout if the kernel is using SYNC_WAIT. The critical case is when that blocked thread is the main thread: if the block exceeds 5 seconds for an Activity or 10 seconds for a Service, Android raises an ANR dialog. That's exactly why all synchronous IPC calls must go on a background thread unless the method is marked oneway."

Q: How do you design safe IPC APIs?

"There are six rules I follow. First, mark fire-and-forget calls as oneway in AIDL so the caller doesn't block. Second, use a callback or listener AIDL interface for results that come back from oneway calls. Third, always catch RemoteException — every remote call can throw it. Fourth, link death recipients immediately on bind, before you make any calls. Fifth, validate caller UID with Binder.getCallingUid() and never trust the client's self-reported identity. Sixth, keep transaction payloads small and use file descriptors for any bulk data."

5.3 AIDL

Definition

AIDL — Android Interface Definition Language — is Android's IDL for defining IPC interfaces. The AIDL compiler, either the standalone aidl tool or the Gradle plugin, generates Java and Kotlin boilerplate for you: a Stub abstract class on the server side that extends Binder, and a Proxy class on the client side that wraps IBinder.transact(). You define the contract in a .aidl file and the generated code handles all the marshalling and unmarshalling.

Supported types in AIDL

Category Types
Primitivesboolean, byte, char, short, int, long, float, double
StringsString, CharSequence
CollectionsList<T> (T must be AIDL-supported), Map (keys/values must be supported)
ParcelableAny class implementing Parcelable (must be declared in its own .aidl file)
Other interfacesOther AIDL interfaces
RawIBinder

Not supported natively: Serializable, arbitrary objects, or file streams — for those, use ParcelFileDescriptor.

Directional tags: in, out, inout

Parameters in AIDL methods have a directional tag that controls marshalling direction:

Tag Client → Server Server → Client Use when
in (default for primitives)Data copiedNot copied backClient sends, server reads only
outNot copied to serverCopied backClient provides empty container; server fills it
inoutCopied both waysCopied backBidirectional; most expensive

Primitives and String are always implicitly in. Objects require an explicit directional tag.

One-way (oneway) calls

Adding oneway to a method makes the client call non-blocking. The client returns immediately after the transaction is enqueued, and the server processes the call asynchronously on a Binder thread. The trade-offs are that oneway methods cannot have return values, and they cannot have out or inout parameters because there is no return path.

interface IEventService {
    oneway void logEvent(String name, in Bundle params);  // fire and forget
    int getEventCount();                                   // synchronous, blocks caller
}

If you mark an entire interface oneway, all methods in it become non-blocking.

Minimal AIDL example

File: app/src/main/aidl/com/example/ICalculator.aidl

// ICalculator.aidl
package com.example;

interface ICalculator {
    /** Synchronous call — caller blocks until result is returned. */
    int add(int a, int b);

    /** Fire-and-forget — caller returns immediately. */
    oneway void scheduleComputation(int jobId, in int[] operands);

    /** Passes a Parcelable in both directions. */
    ComputeResult compute(inout ComputeRequest request);
}

File: app/src/main/aidl/com/example/ComputeRequest.aidl

// Every Parcelable used in AIDL needs its own declaration file.
package com.example;
parcelable ComputeRequest;

Server-side Stub implementation:

class CalculatorService : Service() {

    private val binder = object : ICalculator.Stub() {
        override fun add(a: Int, b: Int): Int {
            // Binder thread — keep it fast or dispatch to a coroutine scope
            return a + b
        }

        override fun scheduleComputation(jobId: Int, operands: IntArray) {
            // oneway — no return value, caller already unblocked
            scope.launch { processJob(jobId, operands) }
        }

        override fun compute(request: ComputeRequest): ComputeResult {
            // Validate caller — never trust the client
            val callerUid = Binder.getCallingUid()
            require(isAuthorized(callerUid)) { "Unauthorized UID: $callerUid" }
            return performCompute(request)
        }
    }

    override fun onBind(intent: Intent): IBinder = binder
}

Client-side binding and usage:

class ClientActivity : AppCompatActivity() {
    private var calculator: ICalculator? = null

    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName, service: IBinder) {
            calculator = ICalculator.Stub.asInterface(service)
            // Stub.asInterface: returns the Stub directly if same process,
            // or wraps it in a Proxy if cross-process.
            service.linkToDeath(deathRecipient, 0)
        }
        override fun onServiceDisconnected(name: ComponentName) {
            calculator = null
        }
    }

    private val deathRecipient = IBinder.DeathRecipient {
        calculator = null
        runOnUiThread { rebind() }
    }

    fun callRemote() {
        lifecycleScope.launch(Dispatchers.IO) {   // NEVER call from main thread
            try {
                val result = calculator?.add(3, 4) ?: return@launch
                withContext(Dispatchers.Main) { updateUi(result) }
            } catch (e: RemoteException) {
                Log.e(TAG, "Remote call failed", e)
            }
        }
    }
}

Versioning and backward compatibility

Binder is the backbone of platform services across Android versions, so breaking an AIDL interface is extremely disruptive. There are five rules to follow.

First, never remove or reorder methods. Method IDs are assigned by declaration order, so reordering breaks binary compatibility silently — calls dispatch to the wrong method with no compiler warning.

Second, add new methods at the end only. Old clients calling transact with an unrecognized method code receive UNKNOWN_TRANSACTION, which the Stub base class returns as false. Handle that gracefully.

Third, for stable AIDL interfaces you can provide default method bodies, which allows new methods to be added without breaking old clients that haven't implemented them yet.

Fourth, version the interface explicitly. The convention is a getVersion(): Int method, or the @VintfStability and @Backing annotations for HAL-level AIDL.

Fifth, for Parcelable evolution: add new fields with defaults, write a version integer as the first field in writeToParcel, and check that version number in createFromParcel before reading newer fields.

// Robust Parcelable that handles older versions
data class UserProfile(
    val id: String,
    val name: String,
    val email: String = ""   // added in v2 — must default for older senders
) : Parcelable {
    companion object CREATOR : Parcelable.Creator<UserProfile> {
        private const val VERSION = 2

        override fun createFromParcel(source: Parcel): UserProfile {
            val version = source.readInt()
            val id = source.readString()!!
            val name = source.readString()!!
            val email = if (version >= 2) source.readString()!! else ""
            return UserProfile(id, name, email)
        }
        override fun newArray(size: Int) = arrayOfNulls<UserProfile>(size)
    }

    override fun writeToParcel(dest: Parcel, flags: Int) {
        dest.writeInt(VERSION)
        dest.writeString(id)
        dest.writeString(name)
        dest.writeString(email)
    }
    override fun describeContents() = 0
}

Interview angles — AIDL

Q: When do you need AIDL?

"You reach for AIDL when you need typed, multi-method RPC between processes — specifically when you need return values, when you have multiple concurrent callers, or when you're passing complex object graphs. Concrete examples are a background processing service that returns results, an inter-app SDK, or a system service extension."

Q: AIDL vs Messenger?

See dedicated section below.

Q: Synchronous vs one-way AIDL?

"Synchronous means the caller blocks until the server returns, and you can have a return value. One-way means the caller returns immediately after enqueuing the transaction, but there's no return value possible. I use oneway for any event or notification call where I don't need a result back, because it completely eliminates the ANR risk on the caller side."

Q: How do you version IPC contracts?

"There are two parts to this. For the interface itself: add new methods at the end only, never remove or reorder existing ones, and add a getVersion(): Int method so callers can check what the server supports before calling new methods. For Parcelable types that go across the wire: write a version integer as the first field, and in createFromParcel check that version before reading any fields that were added after the initial version."

5.4 Messenger

Definition

Messenger is a simpler IPC mechanism built on top of Binder. It wraps a Handler in a Binder object, letting the remote process send Message objects to that Handler. Under the hood it still uses AIDL — Android ships IMessenger.aidl in the framework — but it hides all the marshalling complexity behind the familiar Message API.

How it works

Client process                         Server process
──────────────                         ──────────────
Messenger(service IBinder)             Handler handles messages sequentially
   └─ serverMessenger.send(msg)        └─ handleMessage(msg: Message)
        │                                       ▲
        └─── Binder IPC ──────────────────────►─┘
             (IMessenger.send transaction)
  1. The Service returns a Messenger's underlying IBinder from onBind().
  2. The client wraps that IBinder in Messenger(binder).
  3. The client calls serverMessenger.send(message).
  4. The Message is marshalled over Binder and delivered to the server's Handler.handleMessage().
  5. For replies, the client attaches replyTo = Messenger(clientHandler) to the message.

All messages are processed sequentially through the Handler's MessageQueue. There is no parallelism — the server handles one message at a time, by design.

Service skeleton

class MessengerService : Service() {

    private val incomingHandler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            when (msg.what) {
                MSG_COMPUTE -> {
                    val input = msg.data.getInt("value")
                    val result = input * 2

                    // Reply to client if replyTo is set
                    msg.replyTo?.let { replyMessenger ->
                        val reply = Message.obtain(null, MSG_RESULT)
                        reply.data = Bundle().apply { putInt("result", result) }
                        try {
                            replyMessenger.send(reply)
                        } catch (e: RemoteException) {
                            // Client died — ignore or clean up
                        }
                    }
                }
                else -> super.handleMessage(msg)
            }
        }
    }

    private val messenger = Messenger(incomingHandler)

    override fun onBind(intent: Intent): IBinder = messenger.binder

    companion object {
        const val MSG_COMPUTE = 1
        const val MSG_RESULT = 2
    }
}

Client skeleton

class MessengerClient : AppCompatActivity() {
    private var serverMessenger: Messenger? = null

    private val replyHandler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            if (msg.what == MessengerService.MSG_RESULT) {
                val result = msg.data.getInt("result")
                updateUi(result)
            }
        }
    }
    private val replyMessenger = Messenger(replyHandler)

    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName, service: IBinder) {
            serverMessenger = Messenger(service)
        }
        override fun onServiceDisconnected(name: ComponentName) {
            serverMessenger = null
        }
    }

    fun sendRequest(value: Int) {
        val msg = Message.obtain(null, MessengerService.MSG_COMPUTE)
        msg.data = Bundle().apply { putInt("value", value) }
        msg.replyTo = replyMessenger   // attach reply channel
        try {
            serverMessenger?.send(msg)
        } catch (e: RemoteException) {
            Log.e(TAG, "Service not available", e)
        }
    }
}

Key characteristics

  • Sequential delivery: All messages queue through a single Handler, so there's no concurrent message processing. That's good for ordered operations but bad for high-throughput parallel work.
  • Message payload: Message.obj can hold any Parcelable. Message.data is a Bundle. Message.arg1 and arg2 are int fields for cheap primitives.
  • msg.what: An integer discriminator for the message type. You must define constants for all message types — there is no type safety here, unlike AIDL interfaces.
  • No return values: send() is always fire-and-forget. Replies require the client to attach a separate replyTo Messenger to the message.
  • Thread context: The Handler executes on whatever thread its Looper belongs to — usually the main thread. If message handling is heavy, back it with a HandlerThread instead.
// Using HandlerThread for background message processing
class HeavyMessengerService : Service() {
    private lateinit var handlerThread: HandlerThread

    override fun onCreate() {
        super.onCreate()
        handlerThread = HandlerThread("MessengerWorker").also { it.start() }
    }

    private val incomingHandler by lazy {
        object : Handler(handlerThread.looper) {
            override fun handleMessage(msg: Message) { /* heavy work ok here */ }
        }
    }

    private val messenger by lazy { Messenger(incomingHandler) }
    override fun onBind(intent: Intent): IBinder = messenger.binder

    override fun onDestroy() {
        handlerThread.quitSafely()
        super.onDestroy()
    }
}

Interview angles — Messenger

Q: Messenger vs AIDL?

See detailed table in the next section.

Q: When is Messenger enough?

"Messenger is the right call when your IPC is simple, sequential, and fire-and-forget — for example, a background download service where you just send it commands and don't need typed responses back. It's also good for prototyping or when you need cross-process event delivery but don't want to deal with generating and maintaining AIDL stubs."

Q: Why is Messenger simpler but less flexible?

"Because everything goes through a single Handler and MessageQueue. There are no return values, no parallel processing, and no typed method signatures — every message is an integer code in msg.what, which is untyped and error-prone. And it fundamentally can't express 'give me back a result synchronously.' If you need a reply, you have to attach a replyTo Messenger to every message and handle the response asynchronously on the other end. That overhead is fine for simple command-style patterns, but the moment you need a real typed API with return values, you've outgrown Messenger."

The recommendation is straightforward: always use Parcelable for anything passed over Binder — Intent extras, Bundle contents, AIDL parameters. Use Serializable only when you need cross-JVM disk persistence and performance is not critical.

One thing worth calling out specifically: Parcelable is not safe for disk persistence. The Parcel binary format is internal to Android and can change between OS versions — a Parcel written on Android 12 might be unreadable on Android 14. For persistence, use Room, DataStore, or JSON/Protobuf.
