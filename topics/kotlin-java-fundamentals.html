2.1 Kotlin Fundamentals

val vs var

🎤 Say it out loud (~30s): "val is a read-only reference — once assigned I can't reassign it, like final in Java — while var can be reassigned. The thing people miss is that val is about the reference, not the object: a val list: MutableList still lets me add elements. So val gives you immutability of the binding, not deep immutability of the data. I default to val everywhere and only reach for var when I genuinely need to mutate the reference."

Definition

val is a read-only reference — once you assign it, you cannot reassign it, analogous to final in Java. var is a mutable reference you can reassign freely.

How it works

val compiles to a final field on the JVM. The compiler enforces the single-assignment at the call site, not deep inside the object. The object a val points to can still be mutated (e.g., a val list: MutableList<Int> can have items added to it).

val x = 42          // x = 99 → compile error
var y = 42
y = 99              // OK

val list = mutableListOf(1, 2, 3)
list.add(4)         // Fine — the list is mutable, the reference is not

Under the hood

A top-level or member val backed by a field emits a private final field plus a getter; a var emits a non-final field plus a getter and setter. The single-assignment guarantee for val is largely a compile-time check — the compiler rejects reassignment — but for final fields the JVM also provides a real memory-model guarantee: a value safely published through a final field is visible to other threads without extra synchronization, which is why val is "safer" for shared references. A local val doesn't get a field at all; it's just a slot on the stack frame that the compiler forbids you from re-storing into.

// `val x = 42` (member)  ->  private final int x; public int getX();
// `var y = 42` (member)  ->  private int y; public int getY(); public void setY(int);

Android implications

  • val in a ViewModel is idiomatic for StateFlow, LiveData, or Channel properties. Consumers can only emit via the backing var _state/MutableStateFlow; the public surface is immutable.
  • val in a data class means structural equality works correctly; var fields in a data class can change after construction, breaking contract.

Trade-offs

val var
Thread safetySafer (no race on reference)Risk of torn reads on JVM without synchronization
TestabilityEncourages immutable designHarder to reason about
PerformanceJIT can optimize final fields betterNegligible difference

Failure cases

  • Assuming val means deep immutability. A val users: MutableList<User> is still mutable.
  • val inside a var property delegate: the delegate itself can be reassigned.

Nullable vs Non-Null Types

🎤 Say it out loud (~30s): "Kotlin puts nullability in the type system: String can never be null, String? can, and that's enforced at compile time. What surprises people is that it's not just compiler bookkeeping — Kotlin also emits runtime null checks (intrinsics) on public function parameters, so if Java passes null into a non-null Kotlin parameter, it throws right at the boundary rather than corrupting state later. The weak spot is platform types coming from Java, where Kotlin can't know the nullability and won't force you to check."

Definition

Kotlin bakes nullability directly into the type system. String can never hold null; String? can. That is a compile-time guarantee — the compiler enforces it and backs it with @NonNull/@Nullable annotations in the JVM bytecode.

How it works

The Kotlin compiler inserts null checks at the bytecode level. Calling a method on a non-null type never needs a null check — the compiler has already proven it cannot be null. For nullable types, the compiler forces the developer to handle the null case explicitly.

val name: String = "Alice"     // never null — safe to call .length directly
val nickname: String? = null   // must handle null before using

println(name.length)           // OK
println(nickname.length)       // Compile error: nullable receiver

Under the hood

There's no runtime representation difference between String and String? — both are just a java.lang.String reference on the JVM; nullability is erased like generics. What the compiler adds is twofold. First, it annotates bytecode with @NotNull/@Nullable (org.jetbrains.annotations) so other Kotlin/Java tooling can see the contract. Second, on the entry of any public function it emits a call to Intrinsics.checkNotNullParameter(arg, "name") for each non-null parameter; that throws a NullPointerException immediately if a caller (typically Java, which can ignore the annotations) passes null. So the "guarantee" is enforced by the compiler for Kotlin callers and by inserted runtime guards at the Java interop boundary.

// fun greet(name: String)  ->
//   Intrinsics.checkNotNullParameter(name, "name");
//   ... body ...

Android implications

Most Java SDK callbacks return nullable platform types (e.g., Bundle?, Intent?). Kotlin exposes these as platform types (String!) — see section 2.4 for details.

Failure cases

  • Blindly using !! converts compile-time safety into runtime NullPointerException.
  • Storing a Kotlin non-null reference in Java code and passing null back will throw at the Kotlin boundary (intrinsic null checks).

Safe Call ?.

🎤 Say it out loud (~30s): "?. calls the member only if the receiver is non-null; otherwise the whole expression short-circuits to null instead of throwing. It compiles to a simple null-check branch, and the key consequence is that the result type is always nullable, so it propagates up your chain. The thing I watch for is overusing it — a long a?.b?.c?.d chain silently swallows the failure, and when something's null you can't tell which link broke, so where null is a real bug I'd rather fail fast with requireNotNull."

Definition

?. evaluates the left-hand expression and, if it is non-null, calls the right-hand member. If it is null, the whole expression short-circuits to null without throwing.

How it works

Compiles to an if (x != null) x.member else null check. The result type is always nullable.

val length: Int? = nickname?.length   // null if nickname == null

// Chaining — short-circuits at the first null
val city: String? = user?.address?.city

Under the hood

The compiler lowers x?.foo() into a temporary local plus a conditional: it evaluates x once into a synthetic slot, does an IFNULL branch, and either invokes foo() or pushes null. Evaluating into a temporary matters because the receiver expression is only evaluated a single time even though the byte-level form looks like an if/else. For a chain a?.b?.c, each link adds its own null-check-and-jump, all targeting a common "result is null" label, so the first null jumps straight past the rest of the chain. The static type of the whole expression is the member's type made nullable (Int becomes Int?), even when used on a ?. whose receiver the compiler could otherwise prove non-null.

// nickname?.length  ->
//   ALOAD nickname; DUP; IFNULL Lnull
//   INVOKEVIRTUAL length(); ... ; GOTO Lend
// Lnull: POP; ACONST_NULL
// Lend:

Android implications

Safe calls appear everywhere in lifecycle code where objects may have been destroyed:

binding?.root?.visibility = View.GONE  // if Fragment's view was already destroyed

Failure cases

  • Chaining too many ?. makes NPEs harder to locate. Prefer failing fast with requireNotNull() or checkNotNull() in places where null is truly unexpected.

Elvis Operator ?:

🎤 Say it out loud (~30s): "The Elvis operator gives you a fallback: a ?: b returns a if it's non-null, otherwise it evaluates b. The nice part is the right-hand side can be any expression including throw or return, so I use it for guard clauses — val id = args?.getInt(\"id\") ?: return. Because the right side is only evaluated when the left is null, it's a clean way to either supply a default or bail out. The anti-pattern is using it to paper over a null that actually signals a bug and should propagate."

Definition

?: returns the left-hand value if it is non-null, and if it is null, evaluates and returns the right-hand expression instead.

How it works

val displayName: String = user.name ?: "Anonymous"

// Right side can be a throw or return
val id = arguments?.getInt("id") ?: error("Missing required argument: id")

Under the hood

Elvis compiles to the same shape as a safe call: evaluate the left side into a temporary, DUP, branch on IFNULL; if non-null keep it on the stack, otherwise POP it and evaluate the right side. The right-hand expression is only evaluated on the null path, so it's genuinely lazy — that's what lets ?: return and ?: throw work as control flow. Those work because return, throw, and error(...) have type Nothing, which is a subtype of every type, so the compiler can type the whole a ?: throw ... expression as the non-null type of a. That's also why Elvis can smart-cast away nullability: after val x = a ?: return, x is known non-null.

Android implications

Classic ViewModel pattern:

val currentUser: User
    get() = _currentUser ?: throw IllegalStateException("User not loaded")

Failure cases

  • Using ?: to silently swallow meaningful nulls with a default when null should propagate as an error.
  • Nesting ?: chains without clarity: a?.b ?: c?.d ?: e becomes hard to read and debug.

Not-Null Assertion !!

🎤 Say it out loud (~30s): "!! asserts a nullable value is actually non-null, throwing immediately if it's not. I treat it as a code smell — it's me overriding the type system. The real-world gotcha is the place it tempts you most: a nullable var property where smart-casting fails, because another thread could null it between the check and the use. The fix is to copy it to a local val and check that instead. Our codebase actually bans new !!, which I think is the right call."

Definition

!! converts a nullable type to its non-null equivalent, or throws KotlinNullPointerException at runtime if the value is null. It is essentially telling the compiler "I know better than the type system."

How it works

Bytecode inserts an if (x == null) throw NullPointerException() intrinsic. The JVM stack trace may have poor context without good variable names.

val len = nickname!!.length  // throws KotlinNullPointerException if nickname == null

Under the hood

x!! lowers to a call to Intrinsics.checkNotNull(x) (historically Intrinsics.checkExpressionValueIsNotNull / throwNpe in older compilers), which throws if the value is null and otherwise returns it for the subsequent member access. The thrown type is a NullPointerException (since Kotlin 1.4 a plain java.lang.NullPointerException, not the older KotlinNullPointerException). Crucially the check fires at the !! site, so the stack trace points at where you asserted, not where the null originated — which is why !! deep in a call chain is hard to debug. When the compiler can already prove non-nullability, !! adds no real guard and just resolves to the value.

When to use

Almost never in production code. Acceptable in:

  • Test code where you know the value is present and want a test failure rather than silent skip.
  • Code immediately after a precondition check where the compiler cannot prove non-nullability (e.g., a checked value stored in a field that is mutated on another thread, defeating smart casts).

Failure cases

  • !! on a field: the compiler cannot smart-cast a var property because another thread could null it between the check and the use. Use a local val copy = field pattern.
  • Stack traces from !! show the call site, not the place null was introduced. Hard to debug.
  • Zocdoc CLAUDE.md explicitly prohibits new !! uses in this codebase.

Smart Casts

🎤 Say it out loud (~30s): "A smart cast is the compiler automatically narrowing a type after I've checked it with is or a null check, so I don't write an explicit cast. It works because the compiler does control-flow analysis and knows the type can't have changed between the check and the use. The classic gotcha is that it only works on stable values — vals or local vars — not on mutable var properties, especially open ones or ones with custom getters, because the value could differ between the check and the use; there the fix is to copy into a local val."

Definition

After a type or null check, the Kotlin compiler automatically casts the value to the narrower type within the scope where that check holds — you do not need to write an explicit cast.

How it works

The compiler performs dataflow analysis. After if (x is String), inside that branch x is smart-cast to String. After if (x != null), inside that branch x is smart-cast to its non-null type.

fun process(obj: Any) {
    if (obj is String) {
        println(obj.length)  // Smart cast: obj treated as String here
    }
}

fun printLength(s: String?) {
    if (s != null) {
        println(s.length)    // Smart cast: s is String here
    }
}

Limitations (failure cases)

Smart casts do not work for:

  • var local variables that could be modified by a closure.
  • Mutable (var) class properties, because another thread could change them.
  • Properties that have custom getters (getter could return a different value each call).
class Foo {
    var value: String? = "hello"
    fun len(): Int {
        if (value != null) {
            return value!!.length  // Must use !! — smart cast fails on var property
        }
        return 0
    }
}

Fix pattern

fun len(): Int {
    val v = value  // capture to local val
    return if (v != null) v.length else 0
}

Under the hood

A smart cast is purely a compiler-side narrowing — after an is/null check the compiler tracks the refined type in its dataflow graph and emits a CHECKCAST only at points where the JVM bytecode actually requires the narrower static type (member calls, assignments). There's no runtime wrapper or boxing; for the common null-check case it often emits nothing extra at all. The "stable value" rule exists because the compiler must prove no write happened between the check and the use. For a local val or a local var not captured by a lambda it can prove this; for a mutable member property, an open property, a property with a custom getter, or one from another module, it cannot guarantee a second read returns the same value (a custom getter or another thread could change it), so it refuses the smart cast and tells you to use an explicit cast or a local val copy.

Android implications

Used heavily when processing sealed class branches or when handling when expressions over a type hierarchy (UI state machines, navigation events).

Data Classes

🎤 Say it out loud (~30s): "A data class makes the compiler generate equals, hashCode, toString, copy, and componentN from the primary-constructor properties, so it's the idiomatic value holder — perfect for UI state. The subtle gotcha is that only properties declared in the primary constructor count toward equals/hashCode/toString; anything in the class body is invisible to them. And copy() is a shallow copy, so nested mutable objects are shared. I also keep data-class properties val, because a mutable property whose hashCode changes will silently corrupt a HashSet or HashMap."

Definition

A data class is a class whose compiler automatically generates equals(), hashCode(), toString(), copy(), and componentN() functions for you, based on the properties declared in the primary constructor. The idea is that you are declaring a value-holder, and the compiler handles the boilerplate.

How it works

data class User(val id: Int, val name: String, val email: String)

val u1 = User(1, "Alice", "alice@example.com")
val u2 = User(1, "Alice", "alice@example.com")
println(u1 == u2)   // true — structural equality
println(u1)         // User(id=1, name=Alice, email=alice@example.com)

val u3 = u1.copy(name = "Bob")  // new User(1, "Bob", "alice@example.com")

// Destructuring
val (id, name, email) = u1

Rules and trade-offs

  • Only primary constructor properties participate in equals/hashCode/toString. Properties declared in the body are invisible to these generated methods — this is a subtle gotcha.
  • data class cannot be abstract, open, sealed, or inner.
  • Inheritance: a data class can implement interfaces and extend abstract classes, but not extend another data class.
  • copy() performs a shallow copy. Nested mutable objects are shared between original and copy.
  • componentN() enables destructuring in for loops and assignments.

Under the hood

The compiler synthesizes real methods on the class. equals does a per-field comparison (Intrinsics.areEqual for reference types, primitive == for primitives); hashCode folds the fields with the familiar result = 31 * result + field.hashCode() pattern; toString builds the ClassName(prop=value, ...) string. copy is generated as a method whose parameters default to the current field values (fun copy(id: Int = this.id, ...)), which is why named-argument copies work — it just calls the constructor with the substituted args, hence the shallow copy. Each componentN() is an operator fun returning the Nth constructor property in declaration order, and destructuring val (a, b) = x lowers to positional x.component1(), x.component2() calls — it's positional, not by-name. Body-declared properties get none of this treatment because the generator only walks the primary-constructor parameter list.

// data class User(val id: Int, val name: String) generates:
//   public boolean equals(Object);   // compares id, name
//   public int hashCode();           // 31*id + name.hashCode()
//   public String toString();        // "User(id=..., name=...)"
//   public final User copy(int id, String name);
//   public final int component1(); public final String component2();

Android implications

  • Ideal for UI state holders: data class SearchState(val query: String, val results: List<Result>, val isLoading: Boolean).
  • copy() is the idiomatic way to emit new state from a ViewModel: _state.value = _state.value.copy(isLoading = false).
  • Use in DiffUtil.ItemCallback — equals() is auto-correct for comparing items in RecyclerView.

Failure cases

  • Mutable properties (var) in a data class: hashCode changes over time, breaking HashMap/HashSet contracts.
  • Placing business logic in a data class body — those members are invisible to equals.
  • Large data classes with many properties in the constructor create verbose copy() call sites.

Sealed Classes and Sealed Interfaces

🎤 Say it out loud (~30s): "A sealed class or interface restricts its subclasses to a known set in the same module and package, which gives the compiler complete knowledge of the hierarchy — that's what makes when exhaustive with no else. I lean on this for ViewModel UI state and one-shot navigation events. The deeper point I'd make is that exhaustiveness is a safety feature: when I add a new variant, every when without an else breaks the build and forces me to handle it — so I deliberately avoid adding else branches, because an else throws that safety away."

Definition

A sealed class or sealed interface restricts the class hierarchy so that all direct subclasses must be defined in the same package and compilation unit (Kotlin 1.5+; previously the same file). That constraint gives the compiler complete knowledge of every subclass, which is what enables exhaustive when expressions — you get a compile error if you forget a branch.

How it works

sealed class UiState {
    object Loading : UiState()
    data class Success(val data: List<Item>) : UiState()
    data class Error(val throwable: Throwable) : UiState()
}

fun render(state: UiState) = when (state) {
    is UiState.Loading  -> showSpinner()
    is UiState.Success  -> showData(state.data)
    is UiState.Error    -> showError(state.throwable)
    // No else needed — compiler knows all subclasses
}

Sealed interface (Kotlin 1.5+) enables a type to participate in multiple sealed hierarchies via interface implementation, which sealed classes (single inheritance) cannot do.

sealed interface Result<out T>
data class Ok<T>(val value: T) : Result<T>
data class Failure(val error: Throwable) : Result<Nothing>

Under the hood

A sealed class compiles to an abstract class with a constructor that's effectively non-public, so no subclass outside the sealed scope can extend it; a sealed interface compiles to a regular interface but the compiler enforces the permitted-subclass restriction. On modern toolchains the set of permitted subclasses is recorded in metadata (and, on JVM 17+ targets, can map to the JVM's own PermittedSubclasses attribute), which is how the compiler — and exhaustiveness checking — knows the complete list. Exhaustiveness itself is a compile-time analysis: when a when is used as an expression (or marked exhaustive), the compiler verifies every permitted subtype is covered and errors otherwise; at runtime the when is just a sequence of INSTANCEOF checks with no magic. There's no reflective enumeration of subclasses at runtime — that knowledge lives only in the compiler and metadata.

Android implications

  • ViewModel UI state: The single most common use case. One StateFlow<UiState> drives the entire screen, and the when in Compose or a Fragment is exhaustive.
  • Navigation events: Sealed classes for one-shot navigation side effects via SharedFlow.
  • Network result wrappers: sealed class NetworkResult<out T> — eliminates null checks and boolean flags.

Trade-offs

  • Sealed classes couple all variants into one compilation unit — a large sealed hierarchy can bloat a single file.
  • Adding a new variant to a sealed class is a breaking change for all when statements without an else — the compiler will surface this as an error, which is actually a safety feature.
  • sealed interface solves the file coupling issue and allows subclasses to be data classes or objects simultaneously implementing multiple sealed interfaces.

Failure cases

  • Forgetting to update a when after adding a variant — the compiler forces this only when there is no else branch. If you add an else "just in case," you lose exhaustiveness checking.
  • Nesting sealed classes too deeply — hard to read and test.

Enum vs Sealed Class

🎤 Say it out loud (~30s): "Both model a closed set of alternatives, but the rule of thumb is: use an enum when the variants are uniform and carry no per-instance data, and a sealed class when different variants carry different payloads. An enum constant is a single shared instance with a stable ordinal and name, great for iteration and serialization; a sealed subclass can be a data class with its own fields and even its own subtree. So SortOrder.ASC/DESC is an enum, but Success(data) vs Error(throwable) vs Loading is a sealed class."

Definition

Both model a fixed set of alternatives, but they differ significantly in capability. The short version: use an enum when all your variants have the same shape and carry no extra data; use a sealed class when different variants carry different payloads.

Aspect enum class sealed class
InstancesSingleton per constantAny number of instances per subclass
StateShared state via properties on the constantEach instance carries its own data
PolymorphismLimited (shared interface, properties)Full class hierarchy — each variant can have different fields
ReflectionenumValues<T>(), .ordinal, .nameNo built-in enumeration (use when, sealed itself)
SerializationClean (name or ordinal)Requires polymorphic serializer
MemoryOne instance per constantNew allocation per instance
Exhaustive whenYesYes

When to use enum

  • Constants that are truly identical in shape, only differing by name/identity: Direction.NORTH, Status.ACTIVE.
  • When you need ordinal, iteration over all values, or Enum.valueOf().
  • Flags, simple state machines with no payload.

When to use sealed class

  • States with different payloads: Success(data) vs Error(throwable) vs Loading.
  • Any time variants carry different fields.
  • When a variant needs subclasses of its own.
// enum — right choice
enum class SortOrder { ASC, DESC }

// sealed — right choice
sealed class SearchState {
    object Idle : SearchState()
    data class Results(val items: List<SearchItem>) : SearchState()
    data class Error(val message: String) : SearchState()
}

Under the hood

An enum class compiles to a subclass of java.lang.Enum. Each constant becomes a public static final field initialized in the static initializer (<clinit>), plus a synthetic $VALUES array backing values(); ordinal and name come straight from the Enum base class. Because all constants are created once at class load, every reference to SortOrder.ASC is the same instance — ideal for == comparison and EnumSet/EnumMap, which exploit the dense ordinal. A sealed hierarchy, by contrast, is just ordinary classes: objects are singletons but each data class variant is a normal class you new up per use, so each carries its own fields and allocates per instance. That's the core trade-off the table captures — enums give you cheap interning and built-in reflection (values(), valueOf) but uniform shape, while sealed classes give you heterogeneous payloads at the cost of per-instance allocation and no built-in enumeration.

Android implications

Using a sealed class for ViewModel UI state is standard practice. Using an enum for navigation direction or a fixed set of tab indices is correct. Misapplying enums to state with payloads forces awkward Pair or global state.

Object Declarations and Companion Objects

🎤 Say it out loud (~30s): "object is Kotlin's built-in singleton — one class, one lazily-created instance, thread-safe by virtue of JVM class initialization. A companion object is just an object nested in a class to give you static-like members and factory methods, like a Fragment's newInstance. The interview probe is usually leaks and testing: a singleton's state is global, so holding an Activity Context in an object leaks it — use applicationContext — and because singletons are hard to swap in tests, I prefer DI over object when there's real state."

Definition

object declares a class and its single instance in one expression — it is Kotlin's built-in singleton pattern. A companion object is an object nested inside a class, which gives you "static-like" members scoped to that class.

How it works

// Object declaration — true singleton
object NetworkManager {
    fun get(url: String): Response = TODO()
}

// Usage
NetworkManager.get("https://api.zocdoc.com/doctors")

The object is lazily initialized on first access via a class-level INSTANCE field with double-checked locking (the JVM guarantees this via class initialization).

// Companion object
class MyFragment : Fragment() {

    companion object {
        private const val KEY_USER_ID = "userId"

        fun newInstance(userId: Int): MyFragment {
            return MyFragment().apply {
                arguments = bundleOf(KEY_USER_ID to userId)
            }
        }
    }
}

// Usage
MyFragment.newInstance(42)

Types of objects

Type Syntax Use
Object declarationobject Foo { ... }Singleton
Companion objectcompanion object { ... }Static-like members, factory methods
Object expressionobject : Interface { ... }Anonymous class instance

Under the hood

An object declaration compiles to a final class with a public static final INSTANCE field assigned in the static initializer. Thread safety comes for free from the JVM's class-initialization guarantee: the classloader holds a lock and runs <clinit> exactly once, so the "double-checked locking" is really the JVM's initialization-on-first-use, not handwritten synchronization. A companion object compiles to a nested class (named Companion by default) with its own singleton instance held in a static field on the outer class; "static-like" members are actually instance methods on that Companion object, which is why you sometimes need @JvmStatic or @JvmField to expose true statics to Java. const val is the exception — it's inlined as a real compile-time constant (static final with a ConstantValue), not routed through the companion instance. An object expression (object : Foo {}) compiles to an anonymous class, instantiated where it appears rather than interned as a singleton.

Android implications

  • companion object for Fragment/Activity factory methods (newInstance) is the recommended pattern to keep argument keys private.
  • object for singleton services when DI is overkill (utilities, constants).
  • Object expressions are frequently used to implement RecyclerView.AdapterDataObserver, TextWatcher, etc., inline.

Failure cases

  • Singleton state is global — holding a Context in an object causes memory leaks. Always use applicationContext.
  • Testing singletons is hard; consider passing them as constructor arguments (DI) instead.
  • companion object members with non-trivial initialization cause class-loading delays.

Extension Functions

🎤 Say it out loud (~30s): "Extension functions let me add functions to a type I don't own, without inheritance. The mental model that keeps me out of trouble is that they compile to static methods taking the receiver as the first parameter — so they're resolved statically by the declared type, not dynamically by the runtime type, and they can't access private members or be overridden. The two gotchas: a member with the same signature always wins over an extension, and because they're static they don't play nicely with mocking frameworks in tests."

Definition

Extension functions let you add new functions to a class without modifying it or using inheritance. The type you are extending is called the receiver, and inside the function body you refer to it as this.

How it works

Extension functions compile to static methods that take the receiver as the first parameter. They do not actually modify the class — they cannot access private members.

fun String.isPalindrome(): Boolean {
    return this == this.reversed()
}

"racecar".isPalindrome()  // true

// Compiles to:
// static boolean isPalindrome(String $this) { ... }

Under the hood

An extension function compiles to a plain static method whose first parameter is the receiver (conventionally named $this$<name> / $receiver); the call site "racecar".isPalindrome() lowers to FileKt.isPalindrome("racecar") — an INVOKESTATIC, not a virtual dispatch. That single fact explains every behavioral quirk: there's no entry in any vtable, so no dynamic dispatch and no overriding; the resolved function is chosen at compile time from the static type of the expression, which is why an extension on Animal runs even when the value is actually a Dog. It also can't touch private/protected members because it's compiled outside the class. When a member function and an extension have the same signature, the compiler binds the call to the member (INVOKEVIRTUAL) — the member always wins. Receiver nullability (fun String?.foo()) just means the first static parameter is nullable, so the method itself must null-check this.

Android implications

Extensions are everywhere in Android Kotlin idioms:

fun View.show() { visibility = View.VISIBLE }
fun View.hide() { visibility = View.GONE }
fun Context.dpToPx(dp: Float): Int = (dp * resources.displayMetrics.density).toInt()
fun Fragment.requireArgument(key: String): String =
    arguments?.getString(key) ?: error("Missing argument: $key")

Trade-offs

  • Extensions do not support dynamic dispatch (polymorphism). They are resolved statically at compile time based on the declared type, not the runtime type.
  • Extensions cannot override virtual methods.
  • They can shadow existing members if named the same — the member always wins.

Failure cases

  • Operator extensions can surprise callers: operator fun List<Int>.plus(other: Int) already exists. Defining conflicting operators introduces bugs.
  • Null-safe extensions: the receiver can be null if you declare fun String?.isNullOrBlankCustom().
  • Extension functions in tests that mock the receiver class do not work with standard mocking tools because they're static.

Scope Functions

🎤 Say it out loud (~30s): "The five scope functions all run a block in the context of an object, and I pick between them on two axes: how the object is referenced — this for run/apply/with, it for let/also — and what comes back — the object itself for apply/also, the lambda result for let/run/with. So apply is for configuring and returning an object, let for null-safe transforms, also for side effects like logging in a chain. They're all inline, so there's no lambda allocation overhead. The thing I keep in check is nesting them — more than two deep and readability falls off a cliff."

Scope functions — let, run, apply, also, with — execute a block of code in the context of an object. They all look similar, but they differ on two axes. First, how the context object is referenced inside the block: as this (an implicit receiver) or as it (a lambda argument). Second, what the function returns: the context object itself, or the result of the lambda.

Function Receiver style Returns Typical use
letit (lambda argument)Lambda resultNull-safe operations, transform + use
runthis (implicit receiver)Lambda resultObject initialization + computation
applythis (implicit receiver)Context objectObject configuration / builder pattern
alsoit (lambda argument)Context objectSide effects without changing the object
withthis (implicit receiver)Lambda resultNon-extension, grouping operations on an object

let

// Definition: inline fun <T, R> T.let(block: (T) -> R): R
val result = name?.let {
    it.trim().uppercase()   // it = name
}
// result is null if name was null; otherwise the transformed string

Use let when you want to perform operations on a nullable value, or when you want to transform a value into something else and use the result.

run

// Definition: inline fun <T, R> T.run(block: T.() -> R): R
val service = Service().run {
    connect()        // this = Service instance
    authenticate()
    this             // returns the configured service
}

run is also available as a non-extension — run { ... } — which is useful for creating a local scope when you have no specific context object to work with.

apply

// Definition: inline fun <T> T.apply(block: T.() -> Unit): T
val intent = Intent(context, MainActivity::class.java).apply {
    putExtra("KEY", value)   // this = Intent
    flags = Intent.FLAG_ACTIVITY_NEW_TASK
}
// Returns the Intent itself

apply is the go-to for builder-style object configuration. It returns the receiver itself, so you can chain it in one expression.

also

// Definition: inline fun <T> T.also(block: (T) -> Unit): T
val list = mutableListOf(1, 2, 3)
    .also { log.d("Before sort: $it") }  // it = list
    .sorted()
    .also { log.d("After sort: $it") }

Use also for side effects — logging, validation, debugging — that should not change the object or interrupt the call chain. It returns the original object unchanged.

with

// Definition: inline fun <T, R> with(receiver: T, block: T.() -> R): R
val result = with(user) {
    "$firstName $lastName"   // this = user
}

with is not an extension — it takes the receiver as a parameter. That means there is no null safety: the object you pass in must already be non-null. Use it when you have a confirmed non-null object and want to group several operations on it without repeating the variable name.

Choosing between them — decision tree

Need null safety?
  YES → let (result = transform) or also (side effect)
  NO → does the block configure the object?
         YES → apply (returns object) or run (returns result)
         NO → with (non-null, grouped ops, returns result)

Side effects only (logging, debug)?
  → also (keeps object in chain)

Under the hood

All five are declared inline, so the compiler splices the lambda body directly into the call site — there's no Function object allocated and no extra stack frame, which is why they're effectively zero-cost and can even contain non-local returns. The "this vs it" distinction is just the lambda's declared shape: apply/run/with take a receiver lambda (T.() -> R), so the object becomes the implicit receiver this inside the block; let/also take a parameter lambda ((T) -> R), so the object arrives as the single argument it. The "returns object vs result" distinction is equally mechanical — apply/also end with return this/return the receiver, while let/run/with return whatever the block evaluates to. Because apply/run/with shadow this, referencing the enclosing instance inside them requires a qualified this@OuterClass. After inlining, a with(binding) { ... } block is indistinguishable from writing binding.x = ...; binding.y = ... by hand.

Android implications

// apply for building Bundles/Intents
val bundle = Bundle().apply {
    putInt("userId", userId)
    putString("source", source)
}

// let for safe null-unwrap
viewModel.selectedItem?.let { item ->
    startActivity(ItemDetailActivity.newIntent(this, item.id))
}

// also for logging before API call
val request = buildRequest().also {
    Timber.d("Sending request: $it")
}

// with for grouped UI updates
with(binding) {
    titleTextView.text = title
    subtitleTextView.text = subtitle
    loadingIndicator.isVisible = false
}

Failure cases

  • Nesting scope functions more than two deep creates unreadable code.
  • Forgetting that run/apply/with shadow this — if you need the outer this (e.g., inside a Fragment's with(binding) block), you must qualify it as this@Fragment.
  • let on a var property is not atomic: the property could change between the null check and the let call in a multithreaded context.

Higher-Order Functions

🎤 Say it out loud (~30–45s): "A higher-order function is one that takes a function as a parameter or returns one — Kotlin treats functions as first-class values, so I can pass them around like any other object. This is the backbone of a lot of idiomatic Kotlin: collection operators, scope functions, click listeners, and basically every Compose layout taking a trailing content lambda. The nuance I'd flag is that unless the function is inline, each lambda argument becomes a real heap-allocated Function object, and if that lambda captures a Context or View it can leak — so for hot paths or long-lived lambdas you need to think about allocation and captured references."

Definition

A higher-order function is a function that either takes another function as a parameter, or returns a function as its result. In Kotlin, functions are first-class values, so you can pass them around like any other type.

How it works

fun doWithLogging(operation: () -> Unit) {
    Timber.d("Start")
    operation()
    Timber.d("End")
}

doWithLogging { repository.syncData() }

Lambda type syntax

(ParamType1, ParamType2) -> ReturnType
fun filter(items: List<Int>, predicate: (Int) -> Boolean): List<Int> {
    return items.filter(predicate)
}

val evens = filter(listOf(1,2,3,4)) { it % 2 == 0 }

Under the hood

A function type like (Int) -> Boolean is sugar for the JVM interface kotlin.jvm.functions.Function1<Integer, Boolean> (there are Function0 through Function22, plus FunctionN for larger arities). When you pass a lambda to a non-inline higher-order function, the compiler emits a class implementing the matching FunctionN interface and a synthetic invoke method holding the body; calling the lambda is a virtual invoke dispatch. A lambda that captures no state is emitted as a singleton INSTANCE (allocated once), while a capturing lambda allocates a new object per evaluation with the captured values stored as fields. A method reference like ::myFunction compiles to a similar synthetic class whose invoke forwards to the target, capturing the receiver (this) when the reference is bound.

Android implications

  • Click listeners: fun Button.setThrottledClick(action: () -> Unit).
  • Lifecycle scopes: lifecycleScope.launch { ... } takes a suspend lambda.
  • Compose: almost every layout function (Column, Row, LazyColumn) takes a trailing content: @Composable () -> Unit lambda.

Failure cases

  • Non-inline higher-order functions that capture a coroutine scope can cause memory leaks if the lambda holds a reference to a Context or View.
  • Passing a method reference (::myFunction) captures this, which can prevent garbage collection.

Lambdas

🎤 Say it out loud (~30–45s): "A lambda is an anonymous function you can pass as a value, and in Kotlin it's a real object of a function type unless the enclosing function is inline. The detail interviewers like to probe is capture: a non-capturing lambda is a reused singleton, but a capturing one allocates per use — and unlike Java, Kotlin can capture mutable vars because the compiler boxes them in a Ref wrapper on the heap. That's exactly why capturing an Activity or View in a long-lived lambda leaks, and why capturing a mutable variable that's mutated across threads is a data race."

Definition

A lambda is an anonymous function that can be passed as a value. In Kotlin, lambdas are objects of function types like (Int) -> Boolean, so every lambda is a real object on the heap unless the containing function is inline.

How it works

val multiply: (Int, Int) -> Int = { a, b -> a * b }
println(multiply(3, 4))  // 12

// Trailing lambda syntax (last parameter)
listOf(1, 2, 3).forEach { println(it) }

// Unused parameters → _
listOf(1, 2, 3).mapIndexed { _, value -> value * 2 }

Closures

Lambdas capture variables from their enclosing scope. Unlike Java, Kotlin lambdas can capture mutable variables — the compiler wraps the variable in a small Ref object on the heap so the lambda can read and write it:

var count = 0
val increment = { count++ }
increment()
println(count)  // 1

Under the hood

A non-inlined lambda compiles to a class implementing the appropriate FunctionN interface, with the body in invoke. Captured vals are passed into the synthetic class's constructor and stored as final fields. Captured vars can't be stored by value because the lambda must read and write the same variable the outer scope sees, so the compiler rewrites the variable into a kotlin.jvm.internal.Ref.IntRef (or ObjectRef, etc.) — a tiny mutable box on the heap — and both the outer code and the lambda share that one Ref.element field:

// var count = 0; val increment = { count++ }  decompiles roughly to:
final Ref.IntRef count = new Ref.IntRef();
count.element = 0;
Function0 increment = () -> { count.element++; return Unit.INSTANCE; };

A lambda capturing nothing is emitted as a static singleton and reused across calls; a capturing lambda is a fresh allocation each time the surrounding code runs.

Android implications

Lambdas are the backbone of Compose:

Button(onClick = { viewModel.onConfirm() }) {
    Text("Confirm")
}

Failure cases

  • Capturing Activity/Fragment/View references in long-lived lambdas (stored in singletons, repositories) causes memory leaks.
  • Mutable variable capture in a lambda that runs asynchronously is a data race.
  • Each non-inline lambda creates a new object allocation (important in hot paths like RecyclerView adapter bind).

Inline Functions

🎤 Say it out loud (~30–45s): "An inline function tells the compiler to copy the function body — and the bodies of its lambda arguments — directly into the call site. The win is that the lambda doesn't become a heap-allocated Function object and there's no virtual invoke call, which matters for hot, higher-order code. It's also what unlocks non-local returns and reified generics. The cost is code-size bloat and that it leaks implementation details into callers, so you inline small wrapper functions with lambda params, not big ones — and you reach for noinline when a lambda must be stored, and crossinline when it's invoked from another execution context."

Definition

An inline function has its bytecode copied directly to each call site at compile time. The lambda parameters are inlined too — no lambda object is created, no virtual dispatch happens.

How it works

inline fun measureTime(block: () -> Unit): Long {
    val start = System.currentTimeMillis()
    block()
    return System.currentTimeMillis() - start
}

At compile time, the call measureTime { doWork() } is replaced with the body of measureTime, with block() replaced by doWork(). No lambda object is created, no virtual dispatch.

noinline marks a specific lambda parameter so it is not inlined — use this when you need to store or pass the lambda elsewhere rather than call it immediately:

inline fun foo(inlined: () -> Unit, noinline notInlined: () -> Unit) { ... }

crossinline prevents a return inside the lambda from returning from the enclosing function. You need this when the lambda is invoked in a different execution context — for example, inside another lambda — where a non-local return would not make sense:

inline fun startAsync(crossinline action: () -> Unit) {
    Thread { action() }.start()  // Can't use a non-local return here
}

Benefits

There are three benefits. First, zero overhead for lambdas — no allocation, no virtual dispatch. Second, it enables reified generics, which is covered in the next section. Third, it enables non-local returns from the lambda, so you can return from the calling function inside the lambda body.

When to use

  • Small utility functions that are called frequently.
  • Functions whose sole purpose is to wrap another lambda (like scope functions, resource management, timing).
  • When you need reified.

When NOT to use

  • Large functions — inlining bloats bytecode.
  • Functions called from public APIs (inline leaks implementation details; changes to the function require recompilation of all callers).
  • Functions with many lambda parameters that are stored or invoked later.

Under the hood

Without inline, the lambda compiles to an anonymous class implementing FunctionN, allocated per call (or reused as a singleton if it captures nothing), and each call is a virtual invoke. With inline, the compiler splices the function body into the caller and substitutes each block() call with the lambda's body, so the decompiled Java shows the statements expanded with no extra class and no invoke:

// measureTime { doWork() }  becomes, at the call site:
long start = System.currentTimeMillis();
doWork();                              // lambda body spliced in directly
long elapsed = System.currentTimeMillis() - start;

noinline forces a specific lambda to stay a real FunctionN object so it can be stored or passed onward. A non-local return from an inlined lambda compiles to an actual return out of the caller's frame (because the body is physically there); crossinline forbids that — it keeps the lambda inlined but disallows non-local returns, which is required when the body ends up nested inside another generated class (like a Runnable) where returning from the outer function is impossible.

Android implications

All standard Kotlin scope functions (let, apply, etc.) and most collection operations (map, filter) are inline. Compose's @Composable functions are handled by the Compose compiler plugin (not inline in the standard sense, but similarly rewritten).

Reified Generics

🎤 Say it out loud (~30–45s): "On the JVM, generic type parameters are erased at runtime, so normally you can't write T::class or is T inside a generic function. reified works around that, but only inside inline functions — because inlining substitutes the real type argument into the body at each call site before erasure even applies, so the emitted bytecode literally contains String::class rather than a generic T. That's what powers nice APIs like startActivity<MainActivity>() or viewModel<T>() without passing a Class<T>. The catch is it's tied to inlining, so it carries the same recompilation-of-callers caveat."

Definition

Normally, type parameters are erased at runtime — that is what type erasure means on the JVM. The reified modifier, which is only available in inline functions, works around this by preserving the actual type at each call site, so you can use T as a real type inside the function body — in is checks, ::class references, and reflection.

How it works

// Without reified — doesn't compile
fun <T> List<Any>.filterByType(): List<T> {
    return this.filterIsInstance<T>()  // T is erased — won't work in a normal function
}

// With reified
inline fun <reified T> List<Any>.filterByType(): List<T> {
    return this.filterIsInstance<T>()  // T is available at runtime
}

val strings = listOf(1, "two", 3.0).filterByType<String>()  // ["two"]

Why it works

Because the function is inlined, the compiler substitutes the actual type argument at the call site before erasure ever happens. The bytecode at that call site literally contains String::class — or whatever T actually is — not a generic T.

inline fun <reified T : Activity> Context.startActivity() {
    startActivity(Intent(this, T::class.java))
}

// Usage
context.startActivity<MainActivity>()

Under the hood

There is no runtime type token being passed around — reified is purely a compile-time substitution enabled by inlining. At the call site the inliner copies the body in and replaces every textual use of T with the concrete type argument supplied for that call, so T::class.java becomes a hard-coded class literal:

// context.startActivity<MainActivity>()  expands to:
context.startActivity(new Intent(context, MainActivity.class));

This is also why reified is impossible on a non-inline function: with a single shared compiled body there is nowhere to bake the type token, and the JVM has already erased T to Object. An is T check similarly compiles to a concrete instanceof ConcreteType, and filterIsInstance<T>() resolves the element check against the substituted type.

Android implications

  • startActivity<T>() extension without passing Class<T> explicitly.
  • viewModel<T>() — many DI/ViewModel extension functions use reified.
  • Gson/Moshi type-safe deserialization helpers.

Failure cases

  • reified only works with inline. Attempting to use reified on a normal function is a compile error.
  • The inlined bytecode embeds the exact type — if the inlined code is in a library, the client must recompile when the inline body changes.

Value Classes

🎤 Say it out loud (~30–45s): "A value class wraps a single property and, in the common case, the compiler erases the wrapper entirely so it's represented at runtime as the underlying type — so I get compile-time type safety like distinguishing a UserId from a DoctorId with zero allocation overhead. The nuance interviewers want is when boxing reappears: the wrapper has to materialize as a real object when it's used as a nullable, as a generic type argument, or stored in a collection, or when it's referenced through an interface it implements. So it's free in the hot path of direct calls, but not magic everywhere — and that's why the methods get mangled names under @JvmInline."

Definition

A value class (formerly called an inline class) wraps a single property of another type. At runtime, the JVM represents it as the underlying type directly — no boxing, no wrapper object allocation. You get type safety at compile time and zero overhead at runtime.

How it works

@JvmInline
value class UserId(val id: Int)
@JvmInline
value class Email(val value: String)

fun sendInvite(userId: UserId, email: Email) { ... }

// Correct usage — types are distinct at compile time
sendInvite(UserId(42), Email("alice@example.com"))

// Won't compile — Int and String cannot be confused with UserId/Email
// sendInvite(42, "alice@example.com")  // Error!

At runtime, UserId is just an Int — no heap allocation.

Benefits

There are two benefits. First, type safety: UserId and DoctorId are both Int wrappers but cannot be accidentally swapped — the compiler rejects a raw Int where a UserId is expected. Second, zero cost in normal usage — no boxing. The caveat is that boxing does occur when a value class is stored in a collection or used as a nullable.

Limitations

  • Can have only one property.
  • Cannot extend other classes (but can implement interfaces).
  • Boxing occurs when used as a generic type parameter or nullable.

Under the hood

In the unboxed case the compiler replaces the value class with its underlying type at use sites: a parameter of type UserId is compiled as a plain int, and UserId(42) carries no allocation. To avoid JVM signature clashes (two functions taking UserId and DoctorId would both look like (int) to the JVM), the compiler mangles the function names with a hash suffix — that's what @JvmInline enables and why a value-class-typed function isn't cleanly callable from Java:

fun sendInvite(userId: UserId, email: Email)
// compiles to something like:
public static void sendInvite-<hash>(int userId, String email)

A real wrapper object is generated and boxed only when the value class must be treated as a reference type: when it is nullable (UserId?), used as a generic argument (List<UserId>), or accessed through an implemented interface — because in those positions the JVM needs an Object, not a primitive.

Android implications

Excellent for identifier types, quantities with units (Pixels, Dp, Milliseconds), and domain primitives that prevent primitive obsession.

Delegated Properties

🎤 Say it out loud (~30–45s): "A delegated property hands its get/set logic to a separate delegate object via the by keyword — the compiler routes reads through the delegate's getValue and writes through setValue. Kotlin ships handy ones like lazy, Delegates.observable, and vetoable, and on Android by viewModels() and by viewBinding() are delegated properties. The implementation detail worth knowing is that the compiler generates a hidden backing field holding the delegate instance and rewrites every access to call the operator functions, passing a KProperty reflecting the property — so the delegate can know the property's name without you wiring it up."

Definition

A delegated property offloads its get and set logic to a separate delegate object. The by keyword connects the property to its delegate — you write var name: String by someDelegate and the compiler routes all reads and writes through that delegate's getValue and setValue operator functions.

How it works

class Example {
    var name: String by Delegates.observable("initial") { prop, old, new ->
        println("$old → $new")
    }
}

Built-in delegates:

Custom delegates

class LoggingDelegate<T>(private var value: T) {
    operator fun getValue(thisRef: Any?, property: KProperty<*>): T {
        println("Getting ${property.name}")
        return value
    }
    operator fun setValue(thisRef: Any?, property: KProperty<*>, value: T) {
        println("Setting ${property.name} = $value")
        this.value = value
    }
}

Under the hood

For each delegated property the compiler synthesizes a private final field holding the delegate instance (e.g. name$delegate) and replaces the property's getter/setter with calls to the delegate's getValue/setValue operators. It also emits a KProperty metadata object describing the property, which is passed as the second argument — that's how the delegate gets property.name for free:

// var name: String by observable(...)  generates roughly:
private final ReadWriteProperty name$delegate = Delegates.observable(...);
public String getName()        { return name$delegate.getValue(this, $$delegatedProperties[0]); }
public void   setName(String v){ name$delegate.setValue(this, $$delegatedProperties[0], v); }

val properties use the ReadOnlyProperty/getValue-only contract; var uses ReadWriteProperty. The optional provideDelegate operator, if present, runs once at construction to let the delegate be created with knowledge of the owning instance and property.

Android implications

  • viewModels(), activityViewModels() are delegated properties from Jetpack.
  • by viewBinding() libraries use delegated properties for binding lifecycle management.
  • SharedPreferences delegates: var token: String by prefs.string("token", "").

Lazy Initialization

🎤 Say it out loud (~30–45s): "by lazy defers computing a val until its first access, then caches the result so the initializer never runs again. By default it's SYNCHRONIZED, meaning it does double-checked locking so it's safe to initialize from multiple threads — and you can downgrade to PUBLICATION or NONE if you know the access pattern. The thing I'm careful about is that NONE skips all locking, so using it on a property touched from multiple threads is a data race; and lazy is val-only, so if I genuinely need deferred-but-settable I reach for lateinit or Delegates.notNull() instead."

Definition

lazy defers computing a property's value until the first time it is accessed. After that first access the result is cached, so every subsequent read just returns the stored value — the initializer block never runs again.

How it works

val heavyObject: ExpensiveClass by lazy {
    ExpensiveClass()  // Called once on first access
}

lazy returns a Lazy<T> delegate. By default it uses LazyThreadSafetyMode.SYNCHRONIZED — double-checked locking under the hood.

Thread safety modes

Mode Description
SYNCHRONIZED (default)Thread-safe, but adds synchronization overhead
PUBLICATIONMultiple threads may initialize, first one wins
NONENo locking — use only when single-threaded access is guaranteed

Under the hood

by lazy { } generates a synthetic xxx$delegate field holding a Lazy<T> instance, and the property getter delegates to Lazy.getValue (which returns Lazy.value). The default SYNCHRONIZED mode is implemented by SynchronizedLazyImpl, which stores the initializer lambda and a _value field initialized to a sentinel UNINITIALIZED_VALUE; the first read uses double-checked locking — a volatile read, then synchronized(lock), re-check, run the initializer, publish the result, and drop the lambda reference so it can be GC'd:

public T getValue() {
    if (_value != UNINITIALIZED_VALUE) return (T) _value;   // fast path, volatile read
    synchronized (lock) {
        if (_value == UNINITIALIZED_VALUE) {
            _value = initializer.invoke();
            initializer = null;
        }
        return (T) _value;
    }
}

PUBLICATION uses SafePublicationLazyImpl with an atomic compare-and-set (the initializer may run on several threads but only the first published value wins), and NONE uses UnsafeLazyImpl with no synchronization at all — a plain field check, which is a data race if shared across threads.

Android implications

class MyFragment : Fragment() {
    private val viewModel: MyViewModel by viewModels()  // lazy under the hood
    private val adapter: MyAdapter by lazy { MyAdapter(requireContext()) }
}

Failure cases

  • lazy on a var is not allowed (only val). If you need a lazy var, use Delegates.notNull() or lateinit.
  • lazy(LazyThreadSafetyMode.NONE) in a class that gets accessed from multiple threads causes a data race.

lateinit vs lazy

🎤 Say it out loud (~30–45s): "Both defer initialization but they're for different actors. lateinit var is a non-null var that some external thing — Dagger, the test runner, the framework — sets after construction; it has no thread safety and throws UninitializedPropertyAccessException if read too early, and it can't be a primitive. by lazy is a val you compute yourself once from other state, thread-safe by default, never null. My rule of thumb: lateinit when an external actor sets the value, lazy when I compute it myself, and neither when the value is genuinely nullable or changes over time."

Both lateinit var and by lazy defer initialization, but they serve different purposes and the choice between them is usually clear-cut:

lateinit

class MyActivity : AppCompatActivity() {
    @Inject lateinit var analyticsLogger: AnalyticsLogger
    private lateinit var binding: ActivityMainBinding

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        binding = ActivityMainBinding.inflate(layoutInflater)

The failure case for lateinit is accessing the property before it has been set — that throws UninitializedPropertyAccessException with the property name. Use ::binding.isInitialized in tests or defensive code to guard against this.

lazy

class MyViewModel : ViewModel() {
    val formattedDate: String by lazy {
        DateTimeFormatter.ISO_DATE.format(LocalDate.now())
    }
}

Choosing

The rule of thumb is: use lateinit when an external actor — Dagger, the test runner, the Android framework — sets the value after construction and you cannot set it yourself in the constructor. Use lazy when the value is derived from other state and should be computed at most once. Use neither when the value can genuinely be null or changes over time.

Under the hood

lateinit is not a delegate — it compiles to an ordinary backing field that the compiler simply allows to stay null after construction (skipping the usual non-null initialization requirement). Every read is wrapped with a generated null check that throws UninitializedPropertyAccessException("lateinit property X has not been initialized") if the field is still null, which is why it can't hold a primitive (a primitive field can't be null, so there'd be no "uninitialized" sentinel). The ::property.isInitialized syntax compiles to a direct read of that backing field compared against null:

// access to `binding` becomes:
if (this.binding == null) throw new UninitializedPropertyAccessException("lateinit property binding has not been initialized");
return this.binding;

by lazy, in contrast, generates a separate Lazy<T> delegate field with its own caching and (by default) double-checked locking. So lateinit is a single mutable field plus null guards (zero extra objects, no thread safety), while lazy adds a delegate object and synchronization but guarantees exactly-once computation.

Kotlin Collections

read-only List vs MutableList

🎤 Say it out loud (~30–45s): "Kotlin splits collections into a read-only interface, List<T>, and a mutating one, MutableList<T>, that extends it with add/remove. The key thing is that this is a compile-time distinction only — at runtime both are usually a java.util.ArrayList, and you can cast a List<T> back to MutableList<T> and mutate it. So List<T> is a read-only view, not a deep immutability guarantee; for real immutability you need a defensive copy, Collections.unmodifiableList, or a persistent collection. In practice I expose List<T> from a ViewModel and hold the MutableList<T> privately."

Definition

Kotlin's collection interfaces are split into two layers. List<T> is read-only — it exposes no mutating methods. MutableList<T> extends it with add, remove, and the rest of the mutating API. Both compile to java.util.List on the JVM, so the distinction is purely at the Kotlin type-system level.

val readOnly: List<Int> = listOf(1, 2, 3)
val mutable: MutableList<Int> = mutableListOf(1, 2, 3)

readOnly.add(4)   // Compile error
mutable.add(4)    // OK

Critical caveat: List<T> is a read-only view, not a deeply immutable list. The underlying object may still be a java.util.ArrayList. If you cast readOnly as MutableList<Int>, you can mutate it at runtime — and it might succeed or throw depending on the actual implementation. True immutability requires Collections.unmodifiableList() or a persistent data structure library.

// Dangerous — compiles and runs
val list: List<Int> = mutableListOf(1, 2, 3)
(list as MutableList<Int>).add(4)  // Works at runtime!

Under the hood

kotlin.collections.List and kotlin.collections.MutableList are Kotlin-only interfaces that, through the compiler's "mapped types" mechanism, are both projected onto java.util.List in bytecode — there is no separate runtime class for the read-only version. listOf(...) typically returns a java.util.Arrays.ArrayList (or EmptyList/SingletonList for the 0/1-element cases), and mutableListOf(...) returns a java.util.ArrayList; both are presented to Kotlin code as the appropriate interface. Because the read-only-ness lives only in the Kotlin type system, an as MutableList cast is just a normal unchecked cast that succeeds at runtime whenever the backing object actually implements the mutating methods — hence the mutation "leaking through." Calling a mutator on a genuinely unmodifiable backing (like Collections.unmodifiableList) throws UnsupportedOperationException instead.

Android implications

  • Expose List<T> from ViewModel/repository (read-only surface), hold MutableList<T> internally.
  • StateFlow<List<Item>> — never expose MutableList in public API.

Sequences

🎤 Say it out loud (~30–45s): "A Sequence is the lazy counterpart to a collection: instead of each operator producing a full intermediate list, every element is pulled through the whole pipeline one at a time, and nothing happens until a terminal operation like toList() or first(). That's a big win for large inputs with a short result — filter.map.take(5) over a million elements only touches as many elements as it needs and allocates no intermediate lists. But for small collections the per-element iterator overhead isn't worth it, sequences are stateful so they're not thread-safe, and you have to remember the terminal op or nothing runs."

Definition

A Sequence<T> is a lazily evaluated collection. Instead of creating a full intermediate list after each operation, each element flows through the entire pipeline before the next element starts. The practical effect is that you avoid allocating those intermediate lists entirely.

How it works

// Eager (Collections) — creates 3 intermediate lists
val result = (1..1000000)
    .filter { it % 2 == 0 }   // intermediate list of 500,000
    .map { it * 3 }            // intermediate list of 500,000
    .take(5)                   // final list of 5
    .toList()

// Lazy (Sequences) — processes element-by-element, stops after 5
val result = (1..1000000).asSequence()
    .filter { it % 2 == 0 }
    .map { it * 3 }
    .take(5)
    .toList()                  // triggers evaluation

When to use sequences

  • Large collections where you only need a subset of elements.
  • Multiple chained transformations where intermediate results are not needed.
  • Infinite sequences.

When NOT to use sequences

  • Small collections — the overhead of creating a Sequence object is not worth it.
  • Operations that need random access (sequences are inherently sequential).
  • Android's main thread where even eager collections over small lists are fine.

Under the hood

Each intermediate sequence operator (filter, map, take) returns a new lightweight Sequence object that wraps the previous one and overrides iterator() — so the chain is a stack of decorating iterators, not data. No Function/predicate runs until a terminal operation calls iterator() and pulls elements: each next() on the outermost iterator drives one element down through every stage (TransformingSequence, FilteringSequence, TakeSequence, etc.), and short-circuiting operators like take simply stop requesting more once satisfied. The eager collection operators, by contrast, are inline functions that each allocate and fully populate a new ArrayList before returning — which is why the collection pipeline materializes one list per stage while the sequence pipeline materializes nothing until the terminal call. Because those iterators hold mutable position/state, a sequence is single-use-ish and not thread-safe.

Failure cases

  • Sequences are not thread-safe (they hold state).
  • Forgetting to call a terminal operation (toList(), first(), etc.) — a sequence does nothing until terminated.
  • Mutating the source collection while iterating a sequence.

Flows

🎤 Say it out loud (~30–45s): "A Flow is conceptually a Sequence for the async world — a cold stream of values that integrates with coroutines and can suspend between emissions, so it doesn't run until something collects it. The line I draw is: Sequence is synchronous and pull-based on one thread, while Flow is asynchronous and built on suspend functions, so it can do things like delay or hit the network between emits. And then StateFlow/SharedFlow are the hot variants — they're always active and either hold a current value or multicast to multiple collectors, unlike a cold flow { } that restarts per collector."

Flow<T> is covered in depth in the Coroutines section. Conceptually, a Flow is a cold, asynchronous sequence of values — think of it as a Sequence that integrates with coroutines and supports suspend emitters.

val flow: Flow<Int> = flow {
    emit(1)
    delay(100)
    emit(2)
}

The key distinction from Sequence is: Sequence is synchronous, Flow is asynchronous and supports suspend emitters. StateFlow and SharedFlow are hot flows that additionally carry state or multicast to subscribers.

Under the hood

A cold flow { } builder allocates a SafeCollector-wrapped object whose block isn't executed until collect is called; emission and collection are plain suspend functions, so the whole pipeline compiles through Kotlin's coroutine state-machine transform (each suspend point becomes a continuation, letting delay/IO suspend without blocking a thread). Because it's cold, every collect re-runs the builder block from scratch — there's no shared state across collectors. StateFlow and SharedFlow are hot: they're backed by a long-lived implementation (StateFlowImpl/SharedFlowImpl) holding an atomic current value or a replay/buffer array plus a registry of active collector slots, emitting regardless of whether anyone is collecting and fanning the same emissions out to all subscribers — which is why they don't restart per collector the way a cold flow { } does.

Interview Angles — 2.1

Q: Difference between List and MutableList?

"List<T> is a read-only interface — it exposes no mutating methods. MutableList<T> extends it with add, remove, and the rest. The important thing to understand is that the split is compile-time only — at runtime both are ArrayList by default, and you can cast a List<T> to a MutableList<T> and mutate it. So List<T> is a read-only view, not a deep immutability guarantee. For true immutability you need a defensive copy or an immutable list wrapper. In practice, the convention is to expose List<T> from the ViewModel so call sites cannot accidentally mutate internal state, while you hold MutableList<T> inside the ViewModel."

Q: Difference between data class and normal class?

"A data class auto-generates equals and hashCode from primary constructor properties, a meaningful toString, a copy method for shallow cloning, and componentN functions for destructuring. A normal class inherits reference equality from Any, so two objects that are logically the same will compare as unequal unless you override equals yourself. There are four gotchas to know. First, only primary constructor properties participate in the generated methods — body properties are invisible to them. Second, var properties in a data class break HashSet and HashMap contracts if mutated after insertion. Third, copy is shallow — nested mutable objects are shared. And fourth, data classes cannot be open or abstract, so you cannot subclass them."

Q: Why avoid !!?

"!! converts compile-time null safety into a runtime KotlinNullPointerException. It is saying 'I know better than the type system,' which is almost always wrong. There are two practical problems. First, when it does throw, the stack trace points at the !! site, not where the null was actually introduced, so it is hard to debug. Second, using it becomes contagious — once you start you tend to chain more of them. The alternatives are better in every case: ?. handles null gracefully, ?: provides a fallback or a meaningful error, and requireNotNull() or checkNotNull() throw with a clear message you can read in logs. The Zocdoc codebase explicitly prohibits new !! uses."

Q: When to use sealed class for UI state?

"Use a sealed class for UI state whenever the screen can be in multiple mutually exclusive states with different data payloads. The canonical pattern is a Loading object, a Content data class with the actual data, and an Error data class with a message. The big win is that the when expression on this state in a Composable or Fragment is exhaustive — the compiler forces you to handle every case, so you can never accidentally ship a screen that silently ignores a new state. It also eliminates the alternative of having stranded boolean flags like isLoading, hasError, isSuccess all sitting on the ViewModel, which can get into contradictory combinations."

Q: lateinit vs nullable vs lazy?

"There are three choices and each fits a specific situation. A nullable var field: Type? = null is the right choice when null is a meaningful value in the domain, or when the field may genuinely never be set. The downside is null checks everywhere and it reads like the absence of a decision. lateinit var is for framework-injected properties — things Dagger or the Android lifecycle system will definitely set before first use, like an @Inject field or binding in onCreate. If you access it too early it throws UninitializedPropertyAccessException with the property name, which is a useful failure. You cannot use it with primitives. by lazy is for val properties you compute yourself from other state — the value is derived once and cached. It is thread-safe by default and it can never be null. The rule I follow is: use lateinit when an external actor sets the value, use lazy when you compute it yourself."

Q: Sequence vs collection?

"Collections are eager — every intermediate operation like filter or map produces a full intermediate list before the next step starts. Sequences are lazy — elements flow through the entire pipeline one by one, so no intermediate lists are allocated. The practical difference is most visible on large inputs with a short final result: filter { }.map { }.take(5) on a million elements processes only as many elements as needed to produce 5 results, and allocates nothing in between. For small collections or chains of one or two operations, use collections — the overhead of creating the sequence object is not worth it. Sequences also enable infinite sources, since they only produce elements on demand."

2.2 Kotlin Generics

Type Parameters and Constraints

🎤 Say it out loud (~30–45s): "Type parameters let me write one piece of code that's reusable across many types while staying fully type-safe — the compiler checks every substitution. Constraints, or bounds, narrow what's allowed: an upper bound like T : Comparable<T> tells the compiler T is at least a Comparable, so I can call compareTo on it. If I need more than one bound I use a where clause. The nuance interviewers like is that none of this survives to runtime — on the JVM a type parameter is just its bound, defaulting to Any?/Object, with casts inserted by the compiler."

Definition

Type parameters let you write code that works with multiple types while preserving type safety. Constraints narrow which types are allowed as arguments — an upper bound constraint like T : Comparable<T> lets you call compareTo on T because the compiler knows it is at least a Comparable.

// Unconstrained — T can be anything
fun <T> identity(value: T): T = value

// Upper bound constraint
fun <T : Comparable<T>> max(a: T, b: T): T = if (a > b) a else b

// Multiple constraints — use where clause
fun <T> copy(src: T, dest: T) where T : Cloneable, T : Serializable { ... }

How it works on the JVM

Type parameters exist only at compile time. The bytecode uses Object (or the upper bound) everywhere. The compiler inserts casts as needed.

Under the hood

The JVM has no notion of generics at runtime — they are a compile-time-only feature, so every type parameter is erased to its bound. An unconstrained <T> erases to Object (Kotlin's Any?); a bounded <T : Comparable<T>> erases to Comparable. The compiler keeps the full generic information only in metadata used for type checking, then emits casts at the use sites where erased values flow back into typed positions.

fun <T> identity(value: T): T          // source
  ->  Object identity(Object value)    // erased JVM signature

fun <T : Comparable<T>> max(a, b): T   // source
  ->  Comparable max(Comparable a, Comparable b)  // erased to the bound

Because the parameter is gone at runtime, you cannot ask "what is T?" inside an ordinary generic function — that's the limitation reified later works around.

Android implications

Repository and data-layer generics:

sealed class Result<out T> {
    data class Success<T>(val data: T) : Result<T>()
    data class Error(val exception: Exception) : Result<Nothing>()
}

Variance: out and in

🎤 Say it out loud (~30–45s): "Variance answers when a Container<Sub> can stand in for a Container<Super>. I mark a type parameter out when the class only produces T — returns it, never accepts it — which makes it covariant and safe to substitute a more specific type. I mark it in when the class only consumes T, which makes it contravariant and substitutable in the opposite direction. That's PECS — producer-extends, consumer-super. The key Kotlin point is declaration-site variance: I declare out/in once on the class, instead of repeating Java's wildcards at every use site, though Kotlin also supports use-site variance when I can't touch the class."

Definition

Variance describes how subtyping relationships between generic types relate to subtyping of their type arguments. The core question is: if Dog is a subtype of Animal, what is the relationship between Container<Dog> and Container<Animal>?

Invariance (default)

By default, MutableList<Dog> is not a subtype of MutableList<Animal>, even though Dog is a subtype of Animal. This is invariance.

The reason is type safety. If MutableList<Dog> were assignable to MutableList<Animal>, you could add a Cat to what is actually a Dog list:

val dogs: MutableList<Dog> = mutableListOf(Dog())
val animals: MutableList<Animal> = dogs        // If allowed...
animals.add(Cat())                              // Now dogs contains a Cat!

Covariance: out T (producer)

A type parameter marked out means the class only produces values of T — it returns T from functions but never accepts T as an input. This makes Container<Dog> a safe subtype of Container<Animal>.

interface Producer<out T> {
    fun produce(): T   // Can only return T
}

val dogProducer: Producer<Dog> = DogFactory()
val animalProducer: Producer<Animal> = dogProducer   // Safe — produces Dogs, which are Animals

List<T> in Kotlin is declared as List<out T> — you can only read from it, never add to it — so List<Dog> is safely assignable to List<Animal>.

Contravariance: in T (consumer)

A type parameter marked in means the class only consumes values of T — it accepts T as a parameter but never returns it. This makes Consumer<Animal> a safe subtype of Consumer<Dog>, which is the opposite direction from covariance.

interface Consumer<in T> {
    fun consume(value: T)   // Can only accept T
}

val animalConsumer: Consumer<Animal> = AnimalHandler()
val dogConsumer: Consumer<Dog> = animalConsumer   // Safe — can consume Animals, Dogs are Animals

Mnemonic: Producer is out, which is covariant — read only. Consumer is in, which is contravariant — write only. Comparator<T> is a good example of in T because it consumes two T values to compare them and never produces one.

Use-site vs declaration-site variance

There are two places to declare variance. Declaration-site is out or in on the class or interface definition itself — List<out T> is the example in the standard library. Use-site is out or in on a specific function parameter — useful when you cannot control the class definition.

fun copy(from: List<out Animal>, to: MutableList<in Animal>) {
    for (item in from) to.add(item)
}

Under the hood

Variance is a compile-time contract; at the bytecode level Kotlin's out/in map directly onto Java wildcards. A declaration-site out T is realized in generated signatures as ? extends T wherever the parameter would appear, and in T as ? super T. Use-site variance (List<out Animal>) compiles to the same wildcard at that single position.

Producer<out T>          ->  Producer<? extends T>   (covariant / "extends")
Consumer<in T>           ->  Consumer<? super T>     (contravariant / "super")
fun f(x: List<out Animal>)  ->  void f(List<? extends Animal> x)
fun f(y: MutableList<in Animal>) -> void f(List<? super Animal> y)

The compiler enforces the rules statically — an out parameter may not appear in an in (consuming) position and vice versa — but after erasure the wildcards carry no runtime data; they only inform Java interop and the casts the compiler emits.

Star Projection

🎤 Say it out loud (~30–45s): "List<*> means 'a list of some type I don't know or care about' — it's Kotlin's analogue of Java's List<?>. I use it when I need to accept any generic container regardless of its argument. The nuance is what it projects to: for a covariant out type it behaves like out Any?, so I can read elements as Any? but can't write, since the compiler can't prove what concrete type would be safe to put in. And because of erasure, the star doesn't recover the real argument at runtime — it just safely caps what I'm allowed to do."

Definition

List<*> means "a List of some type I do not know or do not care about." It is analogous to Java's List<?>. You use it when you need to accept any generic container regardless of its type argument.

How it works

  • List<*> is equivalent to List<out Any?> — you can read from it but all elements come out as Any?.
  • MutableList<*> — you can read elements as Any? but cannot add anything (because the compiler doesn't know the actual type).
fun printAll(list: List<*>) {
    for (item in list) println(item)  // item: Any?
}

When to use

  • When you receive a generic type at runtime and don't have the type information.
  • When a function needs to accept any generic container.

Failure cases

  • You cannot write to a MutableList<*> (except null). Attempting to add a value is a compile error.

Under the hood

A star projection is the compiler's way of saying "the safest possible variance for an unknown argument." For a type parameter declared out T (upper bound B), Foo<*> projects to Foo<out B>, so reads yield the bound (Any? when the bound is Any?) and writes are forbidden. For an in T parameter, Foo<*> projects to Foo<in Nothing> — you can't pass anything meaningful in. At the JVM level the star is just Java's unbounded wildcard ?, and since generics are erased, List<*> and List<String> are the very same List class at runtime — the star simply tells the compiler to restrict you, not the runtime.

List<*>        ->  List<out Any?>     // read as Any?, no writes
MutableList<*> ->  effectively writes blocked (in Nothing for the consuming half)
// JVM erased form: just List with wildcard "?"

Type Erasure

🎤 Say it out loud (~30–45s): "Type erasure is the foundational rule of JVM generics: the type arguments exist only at compile time and are gone in the bytecode, so List<String> and List<Int> are both just List at runtime. The compiler uses the arguments for checking and inserts casts, but the parameters never appear in the class file. The practical consequence interviewers probe is that I can't do x is List<String> — the runtime can't tell one parameterization from another — so I reach for reified type parameters, an explicit Class<T>/KClass<T>, or ParameterizedType reflection."

Definition

Generic type information is erased at runtime — that is the fundamental rule of the JVM generics implementation. At the bytecode level, List<String> and List<Int> are both just List. The compiler uses the type arguments for type checking and inserts casts where needed, but the type parameters do not appear in the compiled class file at all.

Implications

fun <T> check(list: List<T>) {
    if (list is List<String>) { }  // Compile error: cannot check for erased type
}

Under the hood

After compilation a parameterized type collapses to its raw class plus the parameter's bound. List<String>, List<Int>, and List<*> are indistinguishable java.util.List instances at runtime — the <...> lives only in the class-file's generic signature metadata, used by the compiler and reflection, never by the bytecode that executes. A plain generic T can't be runtime-checked because there is no Class object representing it: is T would have to compare against a type that was erased to Object/Any (or its bound), so it can't distinguish T from anything else — which is exactly why the compiler rejects is List<String>.

List<String>  ─┐
List<Int>     ─┼─►  (single raw type) java.util.List   // after erasure
List<*>       ─┘
// is List<String>  ✗ — no runtime type to test against
// is List<*>        ✓ — only the raw class can be checked

Workarounds

  • Reified type parameters (inline functions, see section 2.1).
  • Pass Class<T> or KClass<T> explicitly.
  • ParameterizedType reflection (fragile, verbose).

Reified Type Parameters

🎤 Say it out loud (~30–45s): "reified is the escape hatch from type erasure, and it only works on inline functions. Because the function body is inlined into every call site, the compiler can substitute the concrete type argument right there before erasure applies — so inside the function T::class, T::class.java, and is T all work as if T were a real type. Without it, any API needing runtime type info has to take an explicit Class<T>; with it I just write parseResponse<User>(json). And it's free at runtime — the substitution is entirely a compile-time inlining trick."

Already covered in depth in section 2.1. Restatement in generics context:

reified is only available in inline functions. It instructs the compiler to substitute the actual type at each call site, bypassing type erasure for that specific invocation.

inline fun <reified T> parseResponse(json: String): T {
    return Gson().fromJson(json, T::class.java)
}

val user: User = parseResponse(jsonString)

Without reified, you would have to write parseResponse(jsonString, User::class.java).

Under the hood

reified only exists on inline functions because the mechanism is inlining. There is no separate compiled method that carries a runtime type token; instead, at each call site the compiler copies the function body in and replaces every occurrence of T with the actual type argument supplied there. So a T::class.java inside the function becomes a literal User.class reference at the call site, and is T becomes a concrete instanceof User check — both compiling to ordinary bytecode that never needed generic runtime info.

val u: User = parseResponse(json)
// inlined & substituted at the call site:
val u: User = Gson().fromJson(json, User::class.java)   // T -> User, baked in at compile time

This is why a non-reified generic T still can't be checked: only inlining lets the concrete type be known before erasure, and only inline functions can be inlined. The cost is paid entirely at compile time — zero extra runtime overhead, at the price of duplicating the body per call site.

Interview Angles — 2.2

Q: Explain List<out T>.

"List<T> in Kotlin is declared as interface List<out E>. The out makes it covariant in E, which means a List<Dog> is a safe subtype of List<Animal>. That is safe because List is read-only — you can only get elements out of it, never add them in. If the interface allowed mutation, covariance would break type safety, because you could use the List<Animal> reference to add a Cat to what is physically a List<Dog>. The out keyword enforces the restriction at the compiler level: the interface cannot declare any method that consumes E, only methods that produce it. This is declaration-site variance — the class itself makes the promise once and the compiler holds it everywhere."

Q: Why is MutableList<Dog> not safely assignable to MutableList<Animal>?

"MutableList is invariant in T because it both produces and consumes elements — it has both get and add. If the assignment were allowed, the type system would break:"

val dogs: MutableList<Dog> = mutableListOf(Dog())
val animals: MutableList<Animal> = dogs  // Hypothetically allowed
animals.add(Cat())                       // Cat added to dogs!
val dog: Dog = dogs[1]                   // ClassCastException at runtime

"This is the classic array covariance problem. Java arrays are covariant and this exact scenario causes ArrayStoreException at runtime. Kotlin prevents it at compile time for generics by making mutable containers invariant by default — a deliberate improvement over Java."

Q: What problem does reified solve?

"Type erasure means you cannot write T::class.java or is T inside a generic function — the type parameter T simply does not exist at runtime. reified solves this by inlining the function and substituting the concrete type at each call site before erasure can happen. Without reified, any API that needs runtime type information has to accept an explicit Class<T> parameter, which is verbose — you write parseResponse(jsonString, User::class.java) every time. With reified, you just write parseResponse<User>(jsonString) — clean, type-safe, and zero extra runtime overhead because the substitution happens at compile time."

2.3 Java Fundamentals

OOP Basics

🎤 Say it out loud (~30–45s): "Java is class-based and statically typed, organized around encapsulation, inheritance, polymorphism, and abstraction. The nuance interviewers care about is polymorphism via dynamic dispatch — a parent-type reference can hold any subtype, and instance method calls are resolved at runtime against the object's actual class through the vtable, not the declared type. Static methods and fields, by contrast, are bound at compile time, which is why you can't 'override' a static method — you only hide it."

Definition

Java is a class-based, statically typed, object-oriented language built around four pillars. First, encapsulation: internal state is hidden behind methods, with access controlled by private, protected, public, and package-private modifiers. Second, inheritance: a class can extend exactly one parent class with extends. Third, polymorphism: a parent-type reference can hold any subtype, and method calls are dispatched based on the actual runtime type — dynamic dispatch. Fourth, abstraction: interfaces and abstract classes define contracts without providing complete implementations.

Under the hood

Dynamic dispatch is implemented in bytecode by INVOKEVIRTUAL (and INVOKEINTERFACE for interface types), which resolves the target method against the receiver's actual class at runtime via a per-class method table. Private, static, and constructor calls use INVOKESPECIAL/INVOKESTATIC and are statically bound — no runtime lookup — which is why a static method is hidden rather than overridden. On Android, the bytecode is translated to DEX and ahead-of-time/just-in-time compiled by ART, which can devirtualize and inline monomorphic call sites it observes, but the language-level dispatch semantics are identical.

Inheritance

🎤 Say it out loud (~30–45s): "Java is single inheritance — one extends, with Object as the implicit root. Constructors aren't inherited, and a subclass constructor must chain to a parent constructor, either explicitly with super(...) or implicitly to the no-arg one. The thing I'd flag is the fragile base class problem: subclasses bind to the parent's implementation details, so a self-call inside the parent that the subclass has overridden can produce surprising behavior — which is the core argument for composition over inheritance."

Definition

A Java class can extend one other class and thereby inherit all of that class's non-private fields and methods.

class Animal {
    protected String name;
    public void speak() { System.out.println("..."); }
}

class Dog extends Animal {
    @Override
    public void speak() { System.out.println("Woof"); }
}

Key rules

Java has single-class inheritance — one extends only. All classes implicitly extend Object. super accesses parent class members. Constructors are not inherited, but the parent constructor must be called — either explicitly via super(...) or implicitly if the parent has a no-arg constructor.

Under the hood

Every constructor compiles to an <init> method, and the first thing <init> does is invoke the superclass <init> via INVOKESPECIAL — this is the bytecode-level reason the parent constructor always runs first. Instance field initializers and instance-initializer blocks are folded into <init> after the super(...) call, in source order. Because the superclass constructor runs before the subclass's field initializers, an overridden method called from a parent constructor sees the subclass's fields still at their default (zero/null) values — a classic initialization-order trap. There is no implicit chaining for non-constructor methods; only <init> is special.

Failure cases

  • Fragile base class problem: Changing a method in a base class can break subclasses that override it, especially if the override relies on implementation details.
  • Constructor chaining: Forgetting super(args) when the parent has no no-arg constructor causes a compile error.
  • Overriding equals in a subclass breaks the symmetry contract if the parent already overrides it.

Interfaces

🎤 Say it out loud (~30–45s): "An interface is a type contract, and a class can implement many of them — that's how Java gets multiple inheritance of type without the diamond problem on state. Since Java 8 they can carry default and static methods, and Java 9 added private helpers, but they still hold no instance state. The subtlety is the diamond on behavior: if two interfaces supply conflicting default methods, the implementing class is forced to override and disambiguate, often calling Interface.super.method()."

Definition

An interface defines a contract — a set of methods a class promises to implement. A class can implement as many interfaces as needed, which is how Java achieves multiple inheritance of type.

interface Drawable {
    void draw();
    default void drawWithBorder() {  // Default method (Java 8+)
        draw();
        drawBorder();
    }
    static Drawable noOp() { return () -> {}; }  // Static method
}

Java 8+ additions

Java 8 added three things to interfaces. default methods provide a default implementation so existing classes do not need to change. static methods add utility functions scoped to the interface. Java 9 added private methods as helpers for default implementations, keeping the public surface clean.

Under the hood

Interface method calls dispatch via INVOKEINTERFACE, which is slightly more expensive than INVOKEVIRTUAL because the target's method table layout isn't fixed by a single class hierarchy. Interface fields are implicitly public static final constants and live in the interface's <clinit>. default methods are real methods on the interface (not copied into implementors); the JVM resolves them at link time and applies precedence rules — a class implementation wins over a default, and a more specific subinterface's default wins over a superinterface's, with genuine conflicts being a compile error that forces an explicit override. Lambdas implementing a functional interface are wired up at runtime through INVOKEDYNAMIC and LambdaMetafactory rather than generating an anonymous class per lambda.

vs abstract class (see next section)

Abstract Classes

🎤 Say it out loud (~30–45s): "An abstract class can't be instantiated; it mixes abstract methods that subclasses must implement with concrete methods and instance state they inherit. The reason to choose it over an interface is shared state and a constructor — it's the natural home for the template-method pattern, where the base class controls the algorithm skeleton and subclasses fill in the steps. If all I need is a capability contract with no state, I'd use an interface instead because it doesn't burn the single extends slot."

Definition

An abstract class is a class that cannot be instantiated directly. It can declare abstract methods — methods with no body — that every subclass must implement, and it can also have fully concrete methods that subclasses inherit as-is.

abstract class Shape {
    protected String color;

    public abstract double area();  // Must be overridden

    public String describe() {      // Concrete method — can be used as-is
        return color + " shape with area " + area();
    }
}

Under the hood

An abstract class carries the ACC_ABSTRACT flag on the class, and each bodyless method carries ACC_ABSTRACT on the method — the verifier rejects any attempt to NEW an abstract type. It still has a real <init> constructor that subclass <init> chains to via INVOKESPECIAL, and it can declare instance fields, which is exactly what interfaces cannot do. Concrete methods are ordinary virtual methods dispatched by INVOKEVIRTUAL; the template-method pattern works because a concrete base method can call an abstract one and dynamic dispatch routes it to the subclass override.

Composition over Inheritance

🎤 Say it out loud (~30–45s): "Rather than extend a class to reuse it, I hold an instance and delegate. This dodges the fragile base class problem because I'm coupled only to the delegate's public contract, it works even when the target is final, and it lets me swap the delegate at runtime or inject a mock in tests. Inheritance is an is-a relationship and a compile-time, permanent binding; composition is a has-a relationship that's far more flexible — Kotlin even has first-class by delegation for exactly this."

Definition

Instead of extending a class to reuse its behavior, you hold an instance of it as a field and delegate to it. This avoids the fragile base class problem — you are not coupled to the parent's implementation details — and it allows you to swap behavior at runtime by substituting a different delegate.

// Inheritance (fragile)
class LoggingList<T> extends ArrayList<T> {
    @Override public boolean add(T e) {
        log.info("Adding " + e);
        return super.add(e);  // Breaking if ArrayList.add internals change
    }
}

// Composition (robust)
class LoggingList<T> implements List<T> {
    private final List<T> delegate;
    public LoggingList(List<T> delegate) { this.delegate = delegate; }

    @Override public boolean add(T e) {
        log.info("Adding " + e);
        return delegate.add(e);
    }
    // ... other methods delegate to delegate
}

Under the hood

The fragile-inheritance failure is concrete in bytecode: a subclass override that calls super.add() is an INVOKESPECIAL to the parent, but if the parent's other public method (e.g. addAll) internally self-dispatches to add via INVOKEVIRTUAL, that virtual call lands back on the subclass override — causing double-counting or recursion the subclass author never intended. Composition replaces those super/self calls with INVOKEINTERFACE/INVOKEVIRTUAL against a field reference, so you only ever depend on the delegate's published contract. Kotlin's by delegation generates exactly the forwarding methods shown above at compile time, so there's no reflection or runtime cost.

Android implications

  • RecyclerView.Adapter composition — hold a list rather than extending one.
  • Interactors in MVVM — each Interactor is a composed piece of behavior injected into a ViewModel, not a subclass of some BaseInteractor.
  • Kotlin's delegation syntax by automates composition: class LoggingList<T>(private val delegate: List<T>) : List<T> by delegate.

Why prefer composition

There are four reasons to prefer composition. First, it does not couple you to the parent's implementation details — changes to the delegate do not break your class. Second, it works even when the parent class is final. Third, it enables dynamic replacement of behavior at runtime by substituting a different delegate. Fourth, it is far more amenable to dependency injection and testing — you inject a mock instead of the real thing.

final

🎤 Say it out loud (~30–45s): "final means assign-once for variables, no-override for methods, and no-subclass for classes. Beyond the obvious, there's a memory-model guarantee I'd call out: if an object's final fields are fully set in the constructor and the this reference doesn't escape during construction, any thread that sees the object afterward is guaranteed to see those final fields correctly initialized — with no synchronization. That freeze guarantee is why immutable objects built only from final fields can be shared safely."

Definition

final has three distinct uses in Java. A final class cannot be subclassed — String and Integer are final. A final method cannot be overridden in a subclass. A final variable or field can be assigned exactly once, and the compiler enforces this.

final class ImmutablePoint {
    private final int x;
    private final int y;

    public ImmutablePoint(int x, int y) {
        this.x = x;  // Only assignment allowed
        this.y = y;
    }
}

Performance

The JVM can optimize final methods and fields more aggressively — it can inline them and skip virtual dispatch. There is also a thread-safety benefit: final fields in a properly constructed object are guaranteed to be visible to all threads without any synchronization, per the Java Memory Model.

Under the hood

final classes carry ACC_FINAL; the JIT/AOT compiler can treat their methods as non-virtual and inline them. The JMM final-field freeze is the deep part: the end of a constructor that writes final fields acts as a freeze action, and the compiler is forbidden from reordering those writes past the constructor's exit or sinking them below the point where this is published. So a correctly constructed immutable object needs no volatile or lock for readers to see its final fields — provided the constructor doesn't leak this (e.g. registering a listener mid-construction), which breaks the guarantee. final local variables produce no special bytecode; the restriction is purely a compile-time check.

Kotlin equivalent

In Kotlin, classes are final by default. You use open to allow subclassing. This is the inverse of Java's default and it is a deliberate language design choice — if you want to be subclassed, you have to explicitly opt in.

static

🎤 Say it out loud (~30–45s): "static members belong to the class, not an instance — one shared copy, callable without constructing anything. Two nuances I'd raise: initialization is lazy and thread-safe because the JVM runs the class initializer once under a lock the first time the class is used, and static methods are statically bound, so they're hidden, not overridden. On Android the practical hazard is holding a Context, Activity, or View in a static field — that outlives the screen and leaks the whole view hierarchy."

Definition

static members belong to the class, not to any particular instance. A static field is shared across all instances — one copy for the whole class — and a static method can be called without creating an instance at all.

class Counter {
    private static int count = 0;    // One per class
    private int id;                  // One per instance

    public Counter() { this.id = ++count; }
    public static int getCount() { return count; }
}

Under the hood

Static field initializers and static { } blocks are compiled into the synthetic <clinit> class-initializer method; instance initializers go into <init>. The JVM runs <clinit> exactly once, lazily, on first active use of the class (first instance creation, static field/method access, or subclass init), and it holds an initialization lock so this is inherently thread-safe — which is the basis of the lazy-holder singleton idiom. Static methods compile to INVOKESTATIC and are resolved at compile time against the declared type, so they cannot participate in dynamic dispatch — a subclass static of the same signature merely hides the parent's. static final compile-time constants are inlined into callers' bytecode, so changing one requires recompiling dependents.

Android implications

Static constants like static final String TAG = "MyClass" are fine and idiomatic. Static utility methods are fine. The one rule to internalize is: never hold a Context, Activity, or View in a static field — that is the most common Android memory leak. A static Activity reference keeps the entire Activity and its entire View hierarchy alive past onDestroy(), which prevents GC and leaks memory proportional to the screen's complexity.

Kotlin equivalent

Use companion object for class-level members and top-level functions or properties for file-level statics.

equals() and hashCode()

🎤 Say it out loud (~30–45s): "equals() defines value equality and hashCode() gives an int bucket for hash-based collections, and they're contractually linked: equal objects must return equal hash codes — the converse isn't required, collisions are fine. equals must also be reflexive, symmetric, transitive, and consistent. The classic bug is overriding equals but not hashCode: logically equal objects land in different buckets, so a HashMap lookup silently misses. I'd also use mutable fields cautiously, since mutating a key after insertion corrupts the map."

Definition

equals() defines semantic equality — whether two objects represent the same value. hashCode() returns an integer hash used by hash-based data structures to find the right bucket. The two methods are deeply coupled: you must always override both or neither.

Contract (from Object Javadoc)

The equals contract has four requirements: reflexive (x.equals(x) is always true), symmetric (x.equals(y) implies y.equals(x)), transitive, and consistent across multiple calls. The critical linking rule between the two methods is: if x.equals(y), then x.hashCode() must equal y.hashCode(). The converse is not required — hash collisions are allowed.

class User {
    private final int id;
    private final String name;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        User user = (User) o;
        return id == user.id && Objects.equals(name, user.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}

Why override both?

If you override equals but not hashCode, two objects that are logically equal may land in different hash buckets. A HashMap or HashSet looks up by bucket first, so it will never find the entry:

User u1 = new User(1, "Alice");
User u2 = new User(1, "Alice");
u1.equals(u2);  // true (custom equals)
// hashCode not overridden → different hash buckets
Map<User, String> map = new HashMap<>();
map.put(u1, "value");
map.get(u2);  // null — looked in wrong bucket!

Kotlin data class auto-generates a correct, consistent equals/hashCode pair from primary constructor properties — that is one of the main reasons to prefer it over a plain class for value objects.

Under the hood

Object.hashCode() defaults to an identity hash — historically derived from the object's address but in practice a per-object value the JVM lazily computes and stashes in the object header (its mark word), independent of field contents. HashMap doesn't use the raw hashCode; it spreads the bits (h ^ (h >>> 16)) to mix high bits into the low-order bucket index, then masks by capacity - 1. Within a bucket it walks a linked list comparing with equals, and once a bucket exceeds a threshold (8 entries, with table size ≥ 64) it converts that bucket to a red-black tree to bound worst-case lookup at O(log n). This is exactly why a broken hashCode is silent: a wrong bucket index means equals is never even consulted.

Failure cases

  • Using instanceof vs getClass(): instanceof allows subtype equality (often violates symmetry), getClass() enforces exact type match.
  • Mutable fields in equals/hashCode: if the fields change, the contract is broken.

toString()

🎤 Say it out loud (~30–45s): "toString() is the human-readable form; the default from Object is just ClassName@hex, which is useless in logs, so I override it on model types. The hex part is the identity hash code in hex, not the memory address. The one hard rule is to never put PII or secrets in toString(), because it leaks straight into logcat and crash reports — and Kotlin data classes generate toString() for free, which makes accidental PII exposure easy if you're not careful."

Definition

toString() returns a human-readable representation of the object. Without overriding it, the default from Object gives you ClassName@hexHashCode — which is useless in logs.

@Override
public String toString() {
    return "User{id=" + id + ", name='" + name + "'}";
}

Under the hood

Object.toString() returns getClass().getName() + "@" + Integer.toHexString(hashCode()) — so the hex suffix is the identity hash code, not a pointer. String concatenation with + doesn't naively allocate many strings: modern javac compiles + chains to INVOKEDYNAMIC against StringConcatFactory (older bytecode used a StringBuilder chain), so a hand-rolled StringBuilder is rarely needed except in loops. On Android/ART the concat strategy is similar, and the implicit toString() calls in string templates can quietly invoke a custom override that exposes fields — relevant to the PII warning.

Android implications

Always override toString() on model classes so logs are readable. Kotlin data classes auto-generate it from primary constructor properties. The one rule that overrides everything else: do not include sensitive or PII data in toString(), because it will end up in crash logs and logcat.

Immutability

🎤 Say it out loud (~30–45s): "An immutable object can't change after construction — any 'mutation' returns a new instance. In Java I make the class final, fields private final, expose no setters, and defensively copy mutable inputs on the way in and mutable fields on the way out. The payoff is they're inherently thread-safe with zero synchronization and safe as map keys because the hash never changes. The subtle part is that final only freezes the reference — if a field points to a mutable collection, you must copy it or the object is only shallowly immutable."

Definition

An immutable object's state cannot change after construction. Any operation that looks like a mutation actually returns a new object — the original stays unchanged.

How to achieve in Java

There are five steps. First, declare the class final so no subclass can sneak in a mutable field. Second, make all fields private final. Third, provide no setters. Fourth, perform defensive copies of any mutable parameters passed to the constructor. Fifth, return defensive copies of any mutable fields from getters — otherwise callers can reach in and mutate the internal state directly.

public final class ImmutableList<T> {
    private final List<T> items;

    public ImmutableList(List<T> items) {
        this.items = new ArrayList<>(items);  // Defensive copy
    }

    public List<T> getItems() {
        return Collections.unmodifiableList(items);  // Defensive copy on read
    }
}

Benefits

There are four benefits to immutability. It is inherently thread-safe because no thread can mutate the state, so no synchronization is needed. It is safe as a HashMap key because the hash code can never change. It is easier to reason about — no action-at-a-distance mutations. And the JVM can cache and share instances, which is why String is immutable and String.intern() works.

Under the hood

The thread-safety claim rests on the JMM final-field freeze guarantee: because all fields are final and set in the constructor without leaking this, the JMM guarantees a correct initialized view to any thread that later obtains the reference — no volatile or lock required. Note final only makes the reference immutable, not the referent, which is why the defensive copy is mandatory for collection fields. Collections.unmodifiableList returns a view that throws UnsupportedOperationException on mutators but does not copy — so it protects against the caller, while the inbound new ArrayList<>(items) protects against later mutation of the original. String's immutability lets the JVM intern literals into a shared pool and lets the JIT cache the lazily-computed hash in the String object.

Android implications

  • Room entities benefit from immutability; mutable entities cause hidden mutation bugs.
  • Kotlin's data class with val properties provides near-immutability (still requires defensive copies of collection fields).

Checked vs Unchecked Exceptions

🎤 Say it out loud (~30–45s): "Everything descends from Throwable. Error is JVM-fatal and not meant to be caught. Under Exception, checked exceptions — everything except RuntimeException and its subclasses — must be declared with throws or caught, enforced by the compiler; unchecked ones have no such obligation. The nuance is that checked-or-not is purely a compile-time contract — at runtime the JVM treats them identically. In practice checked exceptions pollute APIs and don't compose with lambdas, so modern Java and Kotlin lean unchecked or toward Result-style types."

Definition

Java has two exception hierarchies rooted at Throwable. Error covers JVM-level issues like OutOfMemoryError and StackOverflowError — these are not meant to be caught. Exception splits further into two categories. Checked exceptions — Exception and its subclasses, excluding RuntimeException — must be either declared in the method signature with throws or caught at the call site. Examples are IOException and SQLException. Unchecked exceptions — RuntimeException and its subclasses — have no compile-time obligation to catch or declare. Examples are NullPointerException, IllegalArgumentException, and IndexOutOfBoundsException.

// Checked — must catch or declare
public void readFile(String path) throws IOException {
    Files.readAllBytes(Paths.get(path));
}

// Unchecked — no obligation
public void divide(int a, int b) {
    if (b == 0) throw new ArithmeticException("Division by zero");
}

Under the hood

The checked/unchecked distinction exists only in javac; the JVM has no concept of it and never verifies throws clauses at runtime. The throws clause is recorded as method metadata (and bytecode for try/catch is the Exceptions attribute plus per-method exception tables that map instruction ranges to handler offsets and a catch type). At runtime, ATHROW unwinds the stack frame by frame, consulting each frame's exception table for a handler whose type matches; if none is found the frame is popped and unwinding continues. This is why a class compiled to bypass the checked check (or Kotlin code) can throw a "checked" exception that Java callers never declared — the verifier doesn't care.

The checked-exception controversy

Checked exceptions enforce error handling at compile time, which sounds good, but the practical problems are significant. They pollute APIs with throws declarations that propagate all the way up the call stack. Developers often swallow them or wrap them in RuntimeException just to escape the obligation. And they do not compose well with higher-order functions — a lambda cannot easily throw a checked exception. Modern Java and Kotlin overwhelmingly prefer unchecked exceptions or Result/Either types for error handling.

Kotlin does not have checked exceptions

Kotlin treats all exceptions as unchecked. See section 2.4 for how this affects interop with Java that declares checked exceptions.

Generics and Type Erasure (Java)

🎤 Say it out loud (~30–45s): "Java generics are compile-time only — the compiler type-checks and inserts casts, then erases type parameters to their bounds, so List<String> and List<Integer> are both just List at runtime. That's why you can't do new T(), instanceof List<String>, or have generic arrays. Variance is use-site via wildcards — PECS: producer-extends, consumer-super. And erasure forces the compiler to synthesize bridge methods so overriding across a generic boundary still dispatches correctly."

The fundamental mechanism is the same as Kotlin — same JVM. The key difference is that Java uses wildcards for use-site variance rather than out/in.

Wildcards (Java's use-site variance)

List<? extends Animal> is an upper bounded wildcard — covariant, read-only — and it is equivalent to Kotlin's List<out Animal>. List<? super Dog> is a lower bounded wildcard — contravariant, write-only — and it is equivalent to Kotlin's List<in Dog>. List<?> is an unbounded wildcard equivalent to Kotlin's List<*>.

PECS mnemonic: Producer Extends, Consumer Super — the way I remember it is that if a generic type produces values for you to read, use extends; if it consumes values you hand to it, use super.

// Reading from: use extends
<T> void process(List<? extends T> source) { T item = source.get(0); }
// Writing to: use super
<T> void populate(List<? super T> target, T value) { target.add(value); }

Under the hood

Erasure replaces each type parameter with its leftmost bound — T becomes Object, <T extends Number> becomes Number — and the compiler inserts CHECKCAST instructions at use sites so the runtime stays type-safe. The catch is overriding: when class StringBox implements Comparable<String> overrides compareTo(String), erasure of the interface yields compareTo(Object), so javac generates a synthetic bridge method compareTo(Object) (flags ACC_BRIDGE | ACC_SYNTHETIC) that casts and forwards to the real compareTo(String) — this is what lets polymorphic dispatch through the raw interface type land on your typed override. Because the parameters are gone, the runtime carries no reified type info; Kotlin's reified works only by inline-substituting the concrete type at each call site before bytecode is emitted.

Java Collections

The choices I reason about are access pattern and ordering: ArrayList for O(1) random access, LinkedList/ArrayDeque for ends, HashMap/HashSet for O(1) lookup, the Tree* variants for sorted O(log n), and ConcurrentHashMap when threads share. Under the hood

Java Memory Model Basics

🎤 Say it out loud (~30–45s): "The JMM defines what writes by one thread are visible to reads by another, and in what order. Without synchronization there are no visibility or ordering guarantees — each thread can cache shared variables in registers, and both the compiler and CPU can reorder instructions. The unifying concept is happens-before: if A happens-before B, all of A's effects are visible to B. volatile writes, monitor release/acquire, Thread.start, and Thread.join are the edges that establish it; absent such an edge, a data race is undefined behavior."

Definition

The Java Memory Model — usually called the JMM — defines the rules governing how threads read and write to memory, establishing visibility and ordering guarantees.

Key concepts

There are four things to understand. Working memory: each thread has a local copy — a cache — of shared variables, and it does not necessarily read from main memory on every access. Main memory: the shared store all threads ultimately read from and write to. Visibility: without synchronization, changes made by one thread may never become visible to another. Reordering: the JVM and CPU can reorder instructions for performance, as long as the program appears to execute in order from a single thread's perspective.

Happens-before relationship

The JMM formalizes visibility through the happens-before relation — if action A happens-before action B, then every effect of A is guaranteed to be visible to B. The key rules are: a thread's own actions are happens-before within that thread in program order; a synchronized block releasing a monitor happens-before the next acquisition of the same monitor; a volatile write happens-before all subsequent volatile reads of the same variable; Thread.start() happens-before the new thread's first action; and Thread.join() happens-before the code that follows it.

Under the hood

Happens-before is realized in machine code by memory barriers (fences) the compiler emits at the right places: a volatile store maps to a StoreStore + StoreLoad fence, a volatile load to a LoadLoad + LoadEnsure fence, and monitor exit/enter to release/acquire fences — these stop the compiler and CPU from reordering across them and force cache coherence. The model is defined over actions (reads, writes, locks, unlocks) and "synchronizes-with" edges; happens-before is the transitive closure of program order plus those edges. The crucial subtlety: a program with a data race (conflicting accesses not ordered by happens-before) has effectively undefined behavior — the JMM only promises sequential consistency for correctly synchronized, data-race-free programs. On ARM (most Android devices) the hardware memory model is weakly ordered, so these fences are real CPU instructions, not no-ops as they nearly are on x86.

volatile

🎤 Say it out loud (~30–45s): "volatile guarantees visibility and ordering but not atomicity. A write to a volatile field goes straight to main memory and is immediately visible to other threads, and the JMM forbids reordering around it — so it establishes a happens-before edge — but a compound action like count++ is still read-modify-write and can lose updates. For atomicity I'd use an Atomic class or a lock; I reach for volatile for a simple flag like a running/cancelled boolean, or to safely publish an immutable object's reference."

Definition

A volatile field guarantees visibility and prevents reordering across the access. Every write to a volatile variable is immediately written through to main memory, and every read reads from main memory rather than a thread-local cached copy.

private volatile boolean running = true;

// Thread 1
public void stop() { running = false; }

// Thread 2
public void run() {
    while (running) { doWork(); }
}

Without volatile, Thread 2 might cache running = true forever in its CPU register, never seeing the update from Thread 1.

What volatile does NOT provide

volatile does not provide atomicity for compound operations. i++ on a volatile int is not atomic — it is read, increment, write — three operations — and another thread can slip in between them. Use AtomicInteger instead. It also does not provide mutual exclusion: multiple threads can execute a volatile write simultaneously.

When to use

Use volatile for simple flags that one thread reads and another thread sets. Use it for publishing an immutable object — the volatile write ensures the reference assignment is visible to all threads. The classic example is the double-checked locking singleton pattern, which requires volatile on the instance field to prevent the JVM from returning a partially constructed object.

// Double-checked locking — requires volatile
private static volatile Singleton instance;

public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) {
                instance = new Singleton();
            }
        }
    }
    return instance;
}

The Kotlin equivalent is the @Volatile annotation on a property.

Under the hood

A volatile field is flagged ACC_VOLATILE; field access compiles to ordinary GETFIELD/PUTFIELD, but the JIT/AOT compiler wraps them in memory fences (StoreStore+StoreLoad around a write, LoadLoad+LoadEnsure around a read) so neither compiler nor CPU may reorder or cache across them. The double-checked-locking bug it fixes is concrete: instance = new Singleton() is really allocate, run <init>, publish reference — without volatile the JVM may reorder the publish before <init> finishes, letting another thread's first-check read a non-null but half-constructed object. The volatile write's release semantics forbid that reordering and establish happens-before from construction to the reader. Note volatile provides no read-modify-write atomicity because i++ is still separate GETFIELD/IADD/PUTFIELD opcodes with no lock between them.

synchronized

🎤 Say it out loud (~30–45s): "synchronized gives both mutual exclusion and visibility by acquiring an object's monitor — only one thread holds it at a time, and releasing it happens-before the next acquisition on the same monitor, so changes publish. Monitors are reentrant, so a thread already holding the lock can re-enter without deadlocking itself. I'd warn against locking on this or on boxed Integers (cached -128..127 share a monitor), and against holding a lock across I/O — and note it costs more than volatile under contention because threads block."

Definition

synchronized provides two guarantees: mutual exclusion — only one thread can execute the block at a time — and visibility — all changes made inside the block are visible to the next thread that enters a synchronized block on the same monitor.

private final Object lock = new Object();
private int counter = 0;

public void increment() {
    synchronized (lock) {
        counter++;   // Read-modify-write is now atomic
    }
}

public synchronized int get() {  // Locks on 'this'
    return counter;
}

Under the hood

A synchronized (obj) { } block compiles to a MONITORENTER opcode on entry and MONITOREXIT on exit, with javac emitting an extra MONITOREXIT in a synthetic exception handler so the monitor is released even if the block throws. A synchronized method carries no opcodes — it sets the ACC_SYNCHRONIZED flag and the JVM locks the receiver (this, or the Class object for a static method) on entry. The monitor lives in the object header's mark word and is reentrant: it keeps a hold count, so a thread already owning it can re-enter and only fully releases at count zero. The JVM optimizes uncontended locks via biased/thin (CAS-based) locking, inflating to a heavyweight OS monitor only under real contention. The boxed-Integer hazard is concrete: Integer.valueOf(100) returns a cached shared instance, so two "independent" locks are the same monitor.

Failure cases

There are four common failure cases. Synchronizing on this can cause unintended contention if external code also synchronizes on the same object — prefer a private final lock object instead. Holding locks across I/O or long-running operations starves other threads. Deadlock: Thread A holds Lock 1 and waits for Lock 2 while Thread B holds Lock 2 and waits for Lock 1 — they block each other forever. Synchronizing on a boxed Integer is unsafe because Integer.valueOf() caches values between -128 and 127, so multiple threads may accidentally share the same monitor.

The Kotlin equivalents are the @Synchronized annotation or the synchronized(lock) { } extension function.

wait() / notify() / notifyAll()

🎤 Say it out loud (~30–45s): "These are Object methods for condition signalling, and they only work while you hold that object's monitor — otherwise you get IllegalMonitorStateException. wait() atomically releases the monitor and parks the thread until a notify/notifyAll, then reacquires before returning. The two things I always say: call wait() inside a while loop checking the condition, never an if, because spurious wakeups are explicitly permitted and another thread may have changed state; and in modern code I'd prefer java.util.concurrent primitives like BlockingQueue or Condition."

Definition

These Object methods implement the classic condition variable pattern for inter-thread communication, and they must be called from within a synchronized block on the same object. wait() releases the lock and suspends the current thread until another thread calls notify() or notifyAll() on the same object. notify() wakes one waiting thread — non-deterministically which one. notifyAll() wakes all waiting threads, and they then compete to reacquire the lock.

// Producer-consumer pattern
private final Queue<Task> queue = new LinkedList<>();

public synchronized void produce(Task task) {
    queue.add(task);
    notifyAll();  // Wake any waiting consumers
}

public synchronized Task consume() throws InterruptedException {
    while (queue.isEmpty()) {
        wait();   // Release lock and wait for a produce() call
    }
    return queue.poll();
}

Critical rules

There are three rules to internalize. First, always check the condition in a while loop, not an if — the JVM spec explicitly allows spurious wakeups, so the condition might not actually be true when a thread wakes up. Second, always call wait/notify/notifyAll within a synchronized block on the same object, or you get IllegalMonitorStateException. Third, in modern code, prefer java.util.concurrent primitives like CountDownLatch, Semaphore, BlockingQueue, and Condition over raw wait/notify — they are safer and more readable.

Under the hood

Each Java object's monitor owns a wait set and an entry set. wait() requires the calling thread to own the monitor; it atomically releases the monitor (fully, dropping the entire reentrant hold count), adds the thread to the wait set, and parks it. notify() moves one arbitrary thread from the wait set to the entry set; notifyAll() moves all of them — but none can proceed until the notifier exits its synchronized block and releases the monitor, after which the awakened threads contend via MONITORENTER to reacquire it (restoring the prior hold count) before wait() returns. The JVM is explicitly permitted to return from wait() without any notify (a spurious wakeup), which is the bytecode-level reason the condition must be rechecked in a while. Calling these without owning the monitor throws IllegalMonitorStateException.

Android implications

You will rarely use wait/notify directly in Android code because coroutines and RxJava provide better abstractions. However, understanding them is important for understanding how CountDownLatch and blocking calls work, which do appear in test code.

Interview Angles — 2.3

Q: Explain Java object equality.

"Java has two kinds of equality. Reference equality uses == and asks: are these two variables pointing at the exact same object in memory? Semantic equality uses equals() and asks: do these two objects represent the same value? Object.equals() defaults to reference equality — so without overriding it, two User(1, 'Alice') instances are not equal even though they carry identical data. The contract for equals requires four properties: reflexive, symmetric, transitive, and consistent. There is also a classic gotcha with primitive wrappers: Integer.valueOf(127) == Integer.valueOf(127) returns true because the JVM caches integers from -128 to 127, but Integer.valueOf(128) == Integer.valueOf(128) returns false because those create new objects. The lesson is never use == to compare boxed types."

Q: Why override hashCode() when overriding equals()?

"The hashCode contract says: if a.equals(b), then a.hashCode() must equal b.hashCode(). Hash-based collections like HashMap and HashSet work in two stages — they use hashCode to find the bucket, then use equals to find the exact entry within that bucket. If you override equals but not hashCode, two logically equal objects land in different buckets, so HashMap.get never finds the second one and HashSet.contains returns false even though the element is there. This causes silent data loss and duplicate entries. The rule is simple: always override both together or neither."

Q: What is type erasure?

"Type erasure is the JVM mechanism by which generic type arguments are removed at compile time. List<String> and List<Integer> both become just List in the bytecode. The compiler uses the type information for checking and inserts casts where needed, but the type parameters disappear completely from the class files. The practical consequences are three things you cannot do: you cannot check instanceof List<String> at runtime because the type argument is gone; you cannot write new T() in a generic method for the same reason; and reflection sees only raw types. Kotlin's reified generics are a compile-time workaround — by inlining the function, the compiler substitutes the concrete type at each call site before erasure happens."

Q: Difference between volatile and synchronized?

"volatile provides visibility — reads and writes to a single variable bypass CPU caches and go directly to main memory, so all threads always see the latest value. But it does not provide atomicity: i++ on a volatile int is still three separate operations that can be interleaved. synchronized provides both visibility and mutual exclusion — only one thread can execute the synchronized block at a time, and all changes become visible to the next thread that acquires the lock. The trade-off is that synchronized can block threads and cause contention. The rule I use is: reach for volatile for simple flags or published references; reach for synchronized or java.util.concurrent classes when you need atomicity across multiple operations or need to protect compound state."

Q: Difference between interface and abstract class?

"Abstract classes can have instance state — fields — constructors, and any mix of abstract and concrete methods. Interfaces, since Java 8, can have default, static, and private methods but they still cannot have instance state. The other key difference is inheritance: a class can implement as many interfaces as it wants but can only extend one abstract class. The guidance I follow is: use an abstract class for the template method pattern — shared implementation with customization hooks — or when subclasses genuinely need to share state. Use an interface for contracts and capabilities like Serializable or Drawable. When in doubt, prefer interfaces because they compose better and do not constrain the subclass's inheritance chain."

2.4 Kotlin-Java Interop

Platform Types

🎤 Say it out loud (~30–45s): "Platform types come from Java code that carries no nullability information — Kotlin shows them as String!. The catch is that the compiler doesn't force a null check, so I can freely assign one to a non-null type and it compiles fine — but if Java actually returned null, I get an NPE that surfaces deep inside Kotlin code, far from the Java boundary. The fix is to annotate the Java side with @Nullable/@NonNull, or to immediately pin the value to an explicitly nullable Kotlin type right at the call site."

Definition

When Kotlin calls Java code that has no nullability annotations, the compiler cannot determine whether the value is nullable or non-null. These values get platform types, written as Type! in error messages — for example, String!. Platform types are essentially an escape hatch that bypasses Kotlin's null safety system, and the responsibility for null checking shifts entirely to you.

How it works

// Java
public class UserRepository {
    public User getUser() { return null; }  // No annotation
}
val repo = UserRepository()
val user = repo.getUser()   // user has type User! (platform type)
user.name                   // Compiles — but crashes at runtime if null!

The compiler does not warn you about potential nullability when assigning a platform type to a non-null variable:

val name: String = repo.getUser().name  // Compiles, but can throw NPE at runtime

Why this matters

Platform types are a compatibility escape hatch, not a safety feature. You are responsible for null checking. When a null does come through, the resulting crash looks like a KotlinNullPointerException with a message like "getUser() must not be null," which tells you where the null crossed the boundary but not where it originated.

Under the hood

A platform type is not a real type in the type system — it is a flexible type the compiler tracks internally as the range (Type..Type?), meaning "could be Type or Type?." Because of this flexibility, the compiler emits no parameter or assignment null-check intrinsic when the value is used as a platform type, but the moment you pin it to a non-null Kotlin type, the compiler inserts an Intrinsics.checkNotNullExpressionValue(...) (or a parameter check) that throws if the value is null. That is why the NPE fires at the assignment/use site, not where Java produced the null:

val name: String = repo.getUser().name
  ↓ compiler inserts
  Intrinsics.checkNotNullExpressionValue(getUser(), "getUser()")  // throws here

Best practices

The fix is to add @Nullable and @NonNull annotations to your Java code so Kotlin sees definite types. When calling un-annotated Java APIs in Kotlin, always treat return values as potentially null — use ?. or an explicit null check. Never assign a platform type directly to a non-null val without verifying first.

Nullability Annotations

🎤 Say it out loud (~30–45s): "Nullability annotations on the Java side — @Nullable and @NonNull — give Kotlin enough information to assign a definite nullable or non-null type at the call site instead of a platform type. Kotlin understands a whole family of these from JetBrains, AndroidX, and JSR-305. The thing to flag is that annotations are trusted, not verified: if Java lies and a method annotated @NonNull returns null, Kotlin treats it as non-null and crashes with no warning."

Definition

Adding @Nullable or @NonNull annotations to Java code gives Kotlin the information it needs to assign a definite nullable or non-null type at the call site, rather than a platform type.

Supported annotation packages — Kotlin recognizes all of these:

  • org.jetbrains.annotations.@Nullable / @NotNull
  • androidx.annotation.@Nullable / @NonNull
  • javax.annotation.@Nullable / @Nonnull
  • android.support.annotation.@Nullable / @NonNull
  • JSR-305 (@javax.annotation.Nonnull)
import androidx.annotation.NonNull;
import androidx.annotation.Nullable;

public class UserRepository {
    @Nullable
    public User getUser() { return null; }

    @NonNull
    public String getServerUrl() { return "https://api.zocdoc.com"; }
}
val repo = UserRepository()
val user: User? = repo.getUser()     // Now correctly typed as User?
val url: String = repo.getServerUrl() // Correctly typed as String

Under the hood

When the compiler reads a @NonNull/@NotNull Java return, it drops the platform flexibility and treats the type as a plain non-null Kotlin type — so it generates exactly the same Intrinsics non-null checks it would for native Kotlin non-null types. A @Nullable return becomes a true Type?, forcing the safe-call/null-check discipline at compile time. The compiler does not re-validate the annotation against runtime behavior: the annotation is taken on faith, which is why a @NonNull method that actually returns null produces an NPE at first dereference with no compiler diagnostic.

Android implications

Most AndroidX APIs are well-annotated, so you rarely encounter platform types from them. Third-party Java libraries are often not annotated — treat their return values defensively as nullable until proven otherwise.

SAM Conversion

🎤 Say it out loud (~30–45s): "SAM conversion lets me pass a Kotlin lambda where a Java single-abstract-method interface is expected — like View.OnClickListener — without writing an anonymous object. It only works for Java interfaces automatically; Kotlin interfaces need me to opt in with fun interface, because Kotlin already has function types and the compiler doesn't want ambiguity. The nuance is that it only kicks in with exactly one abstract method — add a second and the lambda stops compiling."

Definition

Single Abstract Method (SAM) conversion lets a Kotlin lambda be automatically converted into a Java interface that has exactly one abstract method. This is what lets you write a lambda where the Java API expects, say, a View.OnClickListener, without any boilerplate object expression.

How it works

// Java SAM interface
public interface OnClickListener {
    void onClick(View v);
}

// Java method taking it
public void setOnClickListener(OnClickListener listener) { ... }
// Without SAM conversion (verbose)
button.setOnClickListener(object : View.OnClickListener {
    override fun onClick(v: View) { handleClick(v) }
})

// With SAM conversion (idiomatic)
button.setOnClickListener { v -> handleClick(v) }

SAM for Kotlin interfaces

For Kotlin interfaces, SAM conversion does not happen automatically — you have to explicitly mark the interface with fun interface to opt in:

fun interface Predicate<T> {
    fun test(value: T): Boolean
}

val isPositive = Predicate<Int> { it > 0 }  // SAM conversion

Under the hood

The compiler wraps the lambda in a synthetic class that implements the target interface and forwards its single method to the lambda body. By default each SAM-converted lambda becomes an anonymous class instance generated at the call site; with invokedynamic-based SAM generation (the modern default on supported targets) the wrapper is created lazily via a bootstrap method rather than emitting a named $1 class. For a Kotlin fun interface, the compiler synthesizes the same kind of adapter that bridges the lambda's FunctionN.invoke to the interface's abstract method:

button.setOnClickListener { v -> handleClick(v) }
  ↓ compiler emits roughly
  setOnClickListener(new OnClickListener() {
      public void onClick(View v) { handleClick(v); }
  })

Failure cases

SAM conversion only works when the Java interface has exactly one abstract method — add a second and the lambda no longer compiles. Kotlin interfaces do not support SAM conversion by default, which is why fun interface exists. If the Java SAM interface has generic type parameters, the Kotlin lambda may need explicit type annotations.

@JvmStatic

🎤 Say it out loud (~30–45s): "@JvmStatic on a companion object member tells the compiler to emit a real static method in the bytecode, alongside the normal instance method on the Companion object. Without it, Java has to go through MyClass.Companion.create(); with it, Java just writes MyClass.create(). It's the right thing to put on factory methods and constants that Java code calls — in Android, things like Fragment.newInstance()."

Definition

@JvmStatic on a companion object method or property tells the Kotlin compiler to generate a real static method or field in the Java bytecode, in addition to the instance method on the companion object. Without it, Java callers have to go through MyClass.Companion.create(), which is awkward. With it, they just write MyClass.create().

Without @JvmStatic

class MyClass {
    companion object {
        fun create(): MyClass = MyClass()
    }
}

From Java: MyClass.Companion.create() — verbose.

With @JvmStatic

class MyClass {
    companion object {
        @JvmStatic
        fun create(): MyClass = MyClass()
    }
}

From Java: MyClass.create() — clean, looks like a static method.

Under the hood

A companion object is, in bytecode, a nested Companion class with a single static instance field on the outer class (public static final MyClass$Companion Companion). A normal companion method lives as an instance method on MyClass$Companion, which is why Java must write MyClass.Companion.create(). @JvmStatic makes the compiler additionally emit a genuine static method on the outer MyClass that simply delegates to the companion instance — both exist, so existing Kotlin callers are unaffected:

public final class MyClass {
    public static final Companion Companion = ...;
    public static MyClass create() { return Companion.create(); }  // emitted by @JvmStatic
    public static final class Companion {
        public final MyClass create() { return new MyClass(); }    // always present
    }
}

When to use

Use @JvmStatic on any public API that will be called from Java. In Android specifically, Fragment.newInstance() and Activity.newIntent() factory methods in companion objects should have it, because they are commonly called from Java Activities.

@JvmOverloads

🎤 Say it out loud (~30–45s): "Kotlin has default parameter values but Java doesn't understand them, so from Java you'd have to pass every argument. @JvmOverloads makes the compiler synthesize a set of telescoping overloads — one per trailing default — so Java callers get the same convenience. The classic Android trap is a custom View: without @JvmOverloads the framework can't find the (Context, AttributeSet) constructor and your view won't inflate from XML."

Definition

Kotlin supports default parameter values, but Java does not understand them. @JvmOverloads tells the compiler to generate a set of Java overloaded methods — one for each combination of trailing default parameters — so Java callers get the same convenience without knowing about defaults.

@JvmOverloads
fun connect(host: String, port: Int = 443, timeout: Int = 5000) { ... }

Generated Java methods:

void connect(String host, int port, int timeout)  // Full
void connect(String host, int port)               // timeout defaults to 5000
void connect(String host)                          // port defaults to 443, timeout to 5000

Under the hood

Without @JvmOverloads, a Kotlin function with defaults compiles to a single method plus a synthetic connect$default(...) helper that takes a bitmask flagging which arguments were omitted — that mechanism is invisible to Java. @JvmOverloads instead synthesizes one real overload per trailing default, each of which forwards to the full method supplying the default expressions. The overloads are generated only by dropping trailing parameters from right to left, so a default in the middle of the list does not produce an overload that skips just that one:

void connect(String h)            -> connect(h, 443, 5000)
void connect(String h, int p)     -> connect(h, p, 5000)
void connect(String h, int p, int t)  // full implementation

Android use case

The canonical example is a custom View constructor. Without @JvmOverloads, the Android framework — which calls View constructors from Java — would fail to find the (Context, AttributeSet) constructor and your view would not inflate from XML. This is one of the most common Android gotchas when writing custom views in Kotlin.

@JvmField

🎤 Say it out loud (~30–45s): "By default a Kotlin property is a private backing field plus a getXxx() (and setXxx() for a var). @JvmField tells the compiler to expose the backing field directly as a public field and suppress the getter/setter entirely, so Java accesses it as config.maxRetries instead of config.getMaxRetries(). It's mainly for constants and frameworks like JUnit @Rule that want a real field — but it can't be used with custom accessors or delegation since there's no field to expose."

Definition

By default, a Kotlin property compiles to a private backing field plus a getXxx() getter — and a setXxx() setter if it is a var. @JvmField exposes the field directly in Java bytecode with no getter or setter wrapper, so Java callers access it as a plain field.

class Config {
    @JvmField
    val maxRetries: Int = 3    // Exposed as a public field in Java
}

Java access: config.maxRetries (direct field access, not config.getMaxRetries()).

Under the hood

Normally the backing field is emitted as private and visibility is mediated by generated accessors. @JvmField changes the field's emitted visibility to match the property (e.g. public final int maxRetries) and instructs the compiler to not generate the getXxx/setXxx accessor methods at all. Because there are no accessors, anything that requires an accessor — custom get()/set(), lateinit with checks, property delegation (by), open/abstract properties — is incompatible and rejected at compile time. On a companion-object constant, @JvmField likewise promotes the value to a static field on the outer class so Java reads MyClass.DEFAULT_TIMEOUT directly:

@JvmField val maxRetries: Int = 3
  ↓
public final int maxRetries = 3;   // no getMaxRetries() emitted

Use cases

There are three common use cases. Constants in companion objects — @JvmField val DEFAULT_TIMEOUT = 5000 — so Java sees MyClass.DEFAULT_TIMEOUT as a direct field access. Avoiding the overhead of getter calls in performance-sensitive Java code, though this is a minor win in practice. And some Java frameworks that expect direct field access, like JUnit's @Rule or certain serialization libraries, require it.

Gotchas

@JvmField bypasses property delegation, custom getters, and visibility modifiers — the field is exposed as-is. It cannot be used on abstract properties or properties that have custom getters or setters.

Calling Suspend Functions from Java

🎤 Say it out loud (~30–45s): "A suspend function has no Java equivalent — the compiler rewrites it via a CPS transform, appending a hidden Continuation parameter and changing the return type to Object because it may return the COROUTINE_SUSPENDED marker instead of the result. So from Java you'd literally have to build and pass a Continuation, which is miserable. The right move is to never expose suspend to Java; instead surface a LiveData, an RxJava Single, or a ListenableFuture from the ViewModel."

Definition

suspend functions are a Kotlin coroutine concept with no direct Java equivalent. The Kotlin compiler transforms them by adding a Continuation<T> parameter — that is what the coroutine machinery uses to resume execution. From Java you can call them, but it requires explicit continuation handling, which is not ergonomic.

What the compiler generates

// Kotlin
suspend fun fetchUser(id: Int): User = withContext(Dispatchers.IO) { api.get(id) }

Becomes in Java bytecode:

Object fetchUser(int id, Continuation<? super User> continuation)

Calling from Java

The cleanest approach is to wrap the suspend call in a coroutine scope:

// Option 1: BuildersKt.launch (fire-and-forget)
BuildersKt.launch(
    CoroutineScopeKt.CoroutineScope(Dispatchers.getMain()),
    EmptyCoroutineContext.INSTANCE,
    CoroutineStart.DEFAULT,
    (scope, continuation) -> viewModel.fetchUser(userId, continuation)
);

// Option 2: Wrap in a ListenableFuture (kotlinx-coroutines-guava)
ListenableFuture<User> future = FutureKt.future(
    scope, EmptyCoroutineContext.INSTANCE, CoroutineStart.DEFAULT,
    (scope2, cont) -> viewModel.fetchUser(userId, cont)
);

Under the hood

The compiler applies a Continuation-Passing Style (CPS) transform: suspend fun fetchUser(id: Int): User becomes Object fetchUser(int id, Continuation<? super User> $completion). The return type is erased to Object because the function may either return the actual User or the sentinel COROUTINE_SUSPENDED (from IntrinsicsKt.getCOROUTINE_SUSPENDED()) when it suspends. The body is compiled into a state machine: each suspension point becomes a labeled state, local variables that must survive suspension are spilled into fields of a generated ContinuationImpl subclass, and resumption re-enters the method via invokeSuspend, switching on the saved label to jump to the next state:

suspend fun fetchUser(id): User
  ↓ CPS + state machine
Object fetchUser(int id, Continuation $completion) {
    switch ($continuation.label) {
        case 0: ... ; $continuation.label = 1; return withContext(...);  // may return COROUTINE_SUSPENDED
        case 1: return $continuation.result;                              // resumed value
    }
}

Best practice

The right approach is to expose a LiveData<T> or an RxJava Single<T> from the ViewModel for Java callers, rather than exposing suspend functions directly. Never surface suspend functions in public APIs that Java code will consume.

// ViewModel with Java-friendly surface
fun loadUserLiveData(id: Int): LiveData<User> = liveData {
    emit(fetchUser(id))
}

Java Checked Exceptions in Kotlin

🎤 Say it out loud (~30–45s): "Kotlin has no checked exceptions — everything is unchecked — so when I call a Java method that declares throws IOException, Kotlin doesn't force a try-catch; the exception can still propagate at runtime, it's just not enforced at compile time. The flip side matters for interop: if a Kotlin function can throw something Java needs to catch, I annotate it with @Throws so the compiler emits a throws clause into the bytecode — otherwise Java callers have no idea and get an unchecked surprise."

Definition

Kotlin does not have checked exceptions — all exceptions are unchecked. When Kotlin code calls a Java method that declares checked exceptions with throws IOException, Kotlin does not require a try-catch at the call site. The exception can still propagate at runtime, it just will not be flagged at compile time.

val bytes = Files.readAllBytes(Paths.get("file.txt"))  // No try-catch required in Kotlin
// But IOException can still propagate at runtime!

Exposing Kotlin to Java with @Throws

If a Kotlin function propagates a checked exception and will be called from Java, annotate it with @Throws to generate a throws clause in the bytecode. Without it, the Java caller has no idea the exception can be thrown — it becomes an unchecked surprise at runtime.

Under the hood

The JVM's checked-exception rule is enforced by javac, not by the bytecode itself — the throws clause is stored as method metadata (the Exceptions attribute in the class file). The Kotlin compiler simply never emits that attribute, so the called Kotlin method can throw anything but advertises nothing, and javac raises no "must be caught" error against it. @Throws(IOException::class) instructs the compiler to write the Exceptions attribute listing those types, which is exactly what javac reads to enforce catch-or-declare on the Java side:

@Throws(IOException::class)
fun read() { ... }
  ↓ emits method with attribute
  void read() throws java.io.IOException   // javac now enforces handling

Failure cases

Forgetting @Throws on Kotlin functions called from Java is the main pitfall — Java callers will not be warned and may not have any error handling in place. Catching blanket Exception in Kotlin just to absorb checked exceptions coming from Java is also a common mistake that masks real bugs.

Kotlin Properties → Getters/Setters

🎤 Say it out loud (~30–45s): "A Kotlin property compiles to a private backing field plus JavaBean-style accessors: getName()/setName() for a var, just the getter for a val. The special case interviewers like is Booleans — a property named isActive keeps the is prefix, so Java sees isActive() and setActive(). A computed property with a custom get() and no stored value has no backing field, and inside an accessor the field keyword is how you touch the backing field without recursing into yourself."

Definition

Kotlin properties compile to a private backing field plus getXxx() and setXxx() accessor methods in Java bytecode. This aligns with JavaBean conventions, so Java code can consume Kotlin properties transparently.

class Person {
    var name: String = "Alice"         // get: getName(), set: setName()
    val age: Int = 30                  // get: getAge() only (val = no setter)
    var isActive: Boolean = true       // get: isActive(), set: setActive()  ← Boolean special case
}

Java:

Person p = new Person();
p.getName();       // → person.name
p.setName("Bob");  // → person.name = "Bob"
p.isActive();      // Boolean: isXxx() convention
p.setActive(false);

Boolean naming

For Boolean properties starting with is, the getter keeps the is prefix — so isActive becomes isActive() in Java. For all other properties, the getter is get plus the capitalized name.

Custom accessors

var firstName: String = ""
var lastName: String = ""
val fullName: String
    get() = "$firstName $lastName"   // Compiles to getFullName(), no backing field

@JvmField to remove accessors

If you annotate a property with @JvmField, no getter or setter is generated — Java sees it as a direct public field. This is most useful for constants.

Backing field

Inside a custom accessor, the field keyword refers to the auto-generated backing field — it is how you read or write the stored value without triggering recursion:

var count: Int = 0
    set(value) {
        require(value >= 0)
        field = value   // 'field' is the backing field
    }

Under the hood

For a var name: String, the compiler emits a private String name field plus public String getName() and public void setName(String) methods; a val omits the setter. The accessor name is derived mechanically — get/set + capitalized property name — except for a Boolean property whose name already starts with is, where the getter reuses the name verbatim (isActive()) and the setter replaces is with set (setActive(...)). A backing field is generated only when the property is actually referenced via the field keyword or has an initializer; a purely computed property (val fullName get() = ...) emits no field — just getFullName(). Inside an accessor, field compiles to a direct read/write of that private field, which is why it avoids the infinite recursion you'd get by calling the property's own getter/setter:

var name: String = "Alice"
  ↓
private String name = "Alice";
public String getName() { return name; }
public void setName(String v) { name = v; }

Interview Angles — 2.4

Q: What are platform types?

"Platform types — denoted Type! in error messages — are types that come from Java code with no nullability annotations. Kotlin cannot determine if they are nullable or non-null, so it makes no guarantee either way and skips null checks. They are the escape hatch in Kotlin's null safety system and the primary source of unexpected NullPointerException in Kotlin codebases that call into Java. There are two fixes: either add @Nullable or @NonNull annotations to the Java code so Kotlin sees a definite type, or defensively treat all unannotated Java return values as potentially null when you consume them in Kotlin."

Q: How can Java nullability cause Kotlin crashes?

"There are three scenarios. First, a platform type assigned to a non-null variable: val user: User = javaRepo.getUser() — if getUser() returns null, the Kotlin intrinsic null check at the assignment throws NullPointerException. Second, a platform type passed to a non-null parameter: processUser(javaRepo.getUser()) — the parameter's intrinsic check throws if the value is null. Third, a lying annotation: if Java annotates a method @NonNull but actually returns null, Kotlin treats the result as non-null and crashes at first use with no warning. The defense strategy is: annotate all Java APIs you own, treat unannotated Java returns as nullable in Kotlin, and use requireNotNull() with a meaningful message at lifecycle boundaries where you expect the value to be present."

Q: How do you expose Kotlin APIs cleanly to Java?

"There is a checklist I work through. First, @JvmStatic on companion object factory methods and constants, so Java callers write MyClass.create() instead of MyClass.Companion.create(). Second, @JvmOverloads on functions with default parameters, so Java sees a set of overloaded methods rather than one method with all parameters required. Third, @JvmField on public constants to expose them as direct fields. Fourth, @Throws(SomeException::class) on functions that propagate checked exceptions, so Java callers know they need to handle them. Fifth, avoid exposing suspend functions — instead expose LiveData, RxJava Observable or Single, or ListenableFuture. Sixth, avoid typealias in public APIs because Java sees the aliased type, not the alias name. Seventh, name is-prefixed Boolean properties carefully since Java sees isActive() and setActive(), which may not match expected conventions. And eighth, if you must expose the companion object itself to Java, give it a meaningful name like companion object Factory."
