2.1 Kotlin Fundamentals

val vs var

Definition

val is a read-only reference — once you assign it, you cannot reassign it, analogous to final in Java. var is a mutable reference you can reassign freely.

How it works

val compiles to a final field on the JVM. The compiler enforces the single-assignment at the call site, not deep inside the object. The object a val points to can still be mutated (e.g., a val list: MutableList<Int> can have items added to it).

val x = 42          // x = 99 → compile error
var y = 42
y = 99              // OK

val list = mutableListOf(1, 2, 3)
list.add(4)         // Fine — the list is mutable, the reference is not

Android implications

  • val in a ViewModel is idiomatic for StateFlow, LiveData, or Channel properties. Consumers can only emit via the backing var _state/MutableStateFlow; the public surface is immutable.
  • val in a data class means structural equality works correctly; var fields in a data class can change after construction, breaking contract.

Trade-offs

val var
Thread safetySafer (no race on reference)Risk of torn reads on JVM without synchronization
TestabilityEncourages immutable designHarder to reason about
PerformanceJIT can optimize final fields betterNegligible difference

Failure cases

  • Assuming val means deep immutability. A val users: MutableList<User> is still mutable.
  • val inside a var property delegate: the delegate itself can be reassigned.

Nullable vs Non-Null Types

Definition

Kotlin bakes nullability directly into the type system. String can never hold null; String? can. That is a compile-time guarantee — the compiler enforces it and backs it with @NonNull/@Nullable annotations in the JVM bytecode.

How it works

The Kotlin compiler inserts null checks at the bytecode level. Calling a method on a non-null type never needs a null check — the compiler has already proven it cannot be null. For nullable types, the compiler forces the developer to handle the null case explicitly.

val name: String = "Alice"     // never null — safe to call .length directly
val nickname: String? = null   // must handle null before using

println(name.length)           // OK
println(nickname.length)       // Compile error: nullable receiver

Android implications

Most Java SDK callbacks return nullable platform types (e.g., Bundle?, Intent?). Kotlin exposes these as platform types (String!) — see section 2.4 for details.

Failure cases

  • Blindly using !! converts compile-time safety into runtime NullPointerException.
  • Storing a Kotlin non-null reference in Java code and passing null back will throw at the Kotlin boundary (intrinsic null checks).

Safe Call ?.

Definition

?. evaluates the left-hand expression and, if it is non-null, calls the right-hand member. If it is null, the whole expression short-circuits to null without throwing.

How it works

Compiles to an if (x != null) x.member else null check. The result type is always nullable.

val length: Int? = nickname?.length   // null if nickname == null

// Chaining — short-circuits at the first null
val city: String? = user?.address?.city

Android implications

Safe calls appear everywhere in lifecycle code where objects may have been destroyed:

binding?.root?.visibility = View.GONE  // if Fragment's view was already destroyed

Failure cases

  • Chaining too many ?. makes NPEs harder to locate. Prefer failing fast with requireNotNull() or checkNotNull() in places where null is truly unexpected.

Elvis Operator ?:

Definition

?: returns the left-hand value if it is non-null, and if it is null, evaluates and returns the right-hand expression instead.

How it works

val displayName: String = user.name ?: "Anonymous"

// Right side can be a throw or return
val id = arguments?.getInt("id") ?: error("Missing required argument: id")

Android implications

Classic ViewModel pattern:

val currentUser: User
    get() = _currentUser ?: throw IllegalStateException("User not loaded")

Failure cases

  • Using ?: to silently swallow meaningful nulls with a default when null should propagate as an error.
  • Nesting ?: chains without clarity: a?.b ?: c?.d ?: e becomes hard to read and debug.

Not-Null Assertion !!

Definition

!! converts a nullable type to its non-null equivalent, or throws KotlinNullPointerException at runtime if the value is null. It is essentially telling the compiler "I know better than the type system."

How it works

Bytecode inserts an if (x == null) throw NullPointerException() intrinsic. The JVM stack trace may have poor context without good variable names.

val len = nickname!!.length  // throws KotlinNullPointerException if nickname == null

When to use

Almost never in production code. Acceptable in:

  • Test code where you know the value is present and want a test failure rather than silent skip.
  • Code immediately after a precondition check where the compiler cannot prove non-nullability (e.g., a checked value stored in a field that is mutated on another thread, defeating smart casts).

Failure cases

  • !! on a field: the compiler cannot smart-cast a var property because another thread could null it between the check and the use. Use a local val copy = field pattern.
  • Stack traces from !! show the call site, not the place null was introduced. Hard to debug.
  • Zocdoc CLAUDE.md explicitly prohibits new !! uses in this codebase.

Smart Casts

Definition

After a type or null check, the Kotlin compiler automatically casts the value to the narrower type within the scope where that check holds — you do not need to write an explicit cast.

How it works

The compiler performs dataflow analysis. After if (x is String), inside that branch x is smart-cast to String. After if (x != null), inside that branch x is smart-cast to its non-null type.

fun process(obj: Any) {
    if (obj is String) {
        println(obj.length)  // Smart cast: obj treated as String here
    }
}

fun printLength(s: String?) {
    if (s != null) {
        println(s.length)    // Smart cast: s is String here
    }
}

Limitations (failure cases)

Smart casts do not work for:

  • var local variables that could be modified by a closure.
  • Mutable (var) class properties, because another thread could change them.
  • Properties that have custom getters (getter could return a different value each call).
class Foo {
    var value: String? = "hello"
    fun len(): Int {
        if (value != null) {
            return value!!.length  // Must use !! — smart cast fails on var property
        }
        return 0
    }
}

Fix pattern

fun len(): Int {
    val v = value  // capture to local val
    return if (v != null) v.length else 0
}

Android implications

Used heavily when processing sealed class branches or when handling when expressions over a type hierarchy (UI state machines, navigation events).

Data Classes

Definition

A data class is a class whose compiler automatically generates equals(), hashCode(), toString(), copy(), and componentN() functions for you, based on the properties declared in the primary constructor. The idea is that you are declaring a value-holder, and the compiler handles the boilerplate.

How it works

data class User(val id: Int, val name: String, val email: String)

val u1 = User(1, "Alice", "alice@example.com")
val u2 = User(1, "Alice", "alice@example.com")
println(u1 == u2)   // true — structural equality
println(u1)         // User(id=1, name=Alice, email=alice@example.com)

val u3 = u1.copy(name = "Bob")  // new User(1, "Bob", "alice@example.com")

// Destructuring
val (id, name, email) = u1

Rules and trade-offs

  • Only primary constructor properties participate in equals/hashCode/toString. Properties declared in the body are invisible to these generated methods — this is a subtle gotcha.
  • data class cannot be abstract, open, sealed, or inner.
  • Inheritance: a data class can implement interfaces and extend abstract classes, but not extend another data class.
  • copy() performs a shallow copy. Nested mutable objects are shared between original and copy.
  • componentN() enables destructuring in for loops and assignments.

Android implications

  • Ideal for UI state holders: data class SearchState(val query: String, val results: List<Result>, val isLoading: Boolean).
  • copy() is the idiomatic way to emit new state from a ViewModel: _state.value = _state.value.copy(isLoading = false).
  • Use in DiffUtil.ItemCallback — equals() is auto-correct for comparing items in RecyclerView.

Failure cases

  • Mutable properties (var) in a data class: hashCode changes over time, breaking HashMap/HashSet contracts.
  • Placing business logic in a data class body — those members are invisible to equals.
  • Large data classes with many properties in the constructor create verbose copy() call sites.

Sealed Classes and Sealed Interfaces

Definition

A sealed class or sealed interface restricts the class hierarchy so that all direct subclasses must be defined in the same package and compilation unit (Kotlin 1.5+; previously the same file). That constraint gives the compiler complete knowledge of every subclass, which is what enables exhaustive when expressions — you get a compile error if you forget a branch.

How it works

sealed class UiState {
    object Loading : UiState()
    data class Success(val data: List<Item>) : UiState()
    data class Error(val throwable: Throwable) : UiState()
}

fun render(state: UiState) = when (state) {
    is UiState.Loading  -> showSpinner()
    is UiState.Success  -> showData(state.data)
    is UiState.Error    -> showError(state.throwable)
    // No else needed — compiler knows all subclasses
}

Sealed interface (Kotlin 1.5+) enables a type to participate in multiple sealed hierarchies via interface implementation, which sealed classes (single inheritance) cannot do.

sealed interface Result<out T>
data class Ok<T>(val value: T) : Result<T>
data class Failure(val error: Throwable) : Result<Nothing>

Android implications

  • ViewModel UI state: The single most common use case. One StateFlow<UiState> drives the entire screen, and the when in Compose or a Fragment is exhaustive.
  • Navigation events: Sealed classes for one-shot navigation side effects via SharedFlow.
  • Network result wrappers: sealed class NetworkResult<out T> — eliminates null checks and boolean flags.

Trade-offs

  • Sealed classes couple all variants into one compilation unit — a large sealed hierarchy can bloat a single file.
  • Adding a new variant to a sealed class is a breaking change for all when statements without an else — the compiler will surface this as an error, which is actually a safety feature.
  • sealed interface solves the file coupling issue and allows subclasses to be data classes or objects simultaneously implementing multiple sealed interfaces.

Failure cases

  • Forgetting to update a when after adding a variant — the compiler forces this only when there is no else branch. If you add an else "just in case," you lose exhaustiveness checking.
  • Nesting sealed classes too deeply — hard to read and test.

Enum vs Sealed Class

Definition

Both model a fixed set of alternatives, but they differ significantly in capability. The short version: use an enum when all your variants have the same shape and carry no extra data; use a sealed class when different variants carry different payloads.

Aspect enum class sealed class
InstancesSingleton per constantAny number of instances per subclass
StateShared state via properties on the constantEach instance carries its own data
PolymorphismLimited (shared interface, properties)Full class hierarchy — each variant can have different fields
ReflectionenumValues<T>(), .ordinal, .nameNo built-in enumeration (use when, sealed itself)
SerializationClean (name or ordinal)Requires polymorphic serializer
MemoryOne instance per constantNew allocation per instance
Exhaustive whenYesYes

When to use enum

  • Constants that are truly identical in shape, only differing by name/identity: Direction.NORTH, Status.ACTIVE.
  • When you need ordinal, iteration over all values, or Enum.valueOf().
  • Flags, simple state machines with no payload.

When to use sealed class

  • States with different payloads: Success(data) vs Error(throwable) vs Loading.
  • Any time variants carry different fields.
  • When a variant needs subclasses of its own.
// enum — right choice
enum class SortOrder { ASC, DESC }

// sealed — right choice
sealed class SearchState {
    object Idle : SearchState()
    data class Results(val items: List<SearchItem>) : SearchState()
    data class Error(val message: String) : SearchState()
}

Android implications

Using a sealed class for ViewModel UI state is standard practice. Using an enum for navigation direction or a fixed set of tab indices is correct. Misapplying enums to state with payloads forces awkward Pair or global state.

Object Declarations and Companion Objects

Definition

object declares a class and its single instance in one expression — it is Kotlin's built-in singleton pattern. A companion object is an object nested inside a class, which gives you "static-like" members scoped to that class.

How it works

// Object declaration — true singleton
object NetworkManager {
    fun get(url: String): Response = TODO()
}

// Usage
NetworkManager.get("https://api.zocdoc.com/doctors")

The object is lazily initialized on first access via a class-level INSTANCE field with double-checked locking (the JVM guarantees this via class initialization).

// Companion object
class MyFragment : Fragment() {

    companion object {
        private const val KEY_USER_ID = "userId"

        fun newInstance(userId: Int): MyFragment {
            return MyFragment().apply {
                arguments = bundleOf(KEY_USER_ID to userId)
            }
        }
    }
}

// Usage
MyFragment.newInstance(42)

Types of objects

Type Syntax Use
Object declarationobject Foo { ... }Singleton
Companion objectcompanion object { ... }Static-like members, factory methods
Object expressionobject : Interface { ... }Anonymous class instance

Android implications

  • companion object for Fragment/Activity factory methods (newInstance) is the recommended pattern to keep argument keys private.
  • object for singleton services when DI is overkill (utilities, constants).
  • Object expressions are frequently used to implement RecyclerView.AdapterDataObserver, TextWatcher, etc., inline.

Failure cases

  • Singleton state is global — holding a Context in an object causes memory leaks. Always use applicationContext.
  • Testing singletons is hard; consider passing them as constructor arguments (DI) instead.
  • companion object members with non-trivial initialization cause class-loading delays.

Extension Functions

Definition

Extension functions let you add new functions to a class without modifying it or using inheritance. The type you are extending is called the receiver, and inside the function body you refer to it as this.

How it works

Extension functions compile to static methods that take the receiver as the first parameter. They do not actually modify the class — they cannot access private members.

fun String.isPalindrome(): Boolean {
    return this == this.reversed()
}

"racecar".isPalindrome()  // true

// Compiles to:
// static boolean isPalindrome(String $this) { ... }

Android implications

Extensions are everywhere in Android Kotlin idioms:

fun View.show() { visibility = View.VISIBLE }
fun View.hide() { visibility = View.GONE }
fun Context.dpToPx(dp: Float): Int = (dp * resources.displayMetrics.density).toInt()
fun Fragment.requireArgument(key: String): String =
    arguments?.getString(key) ?: error("Missing argument: $key")

Trade-offs

  • Extensions do not support dynamic dispatch (polymorphism). They are resolved statically at compile time based on the declared type, not the runtime type.
  • Extensions cannot override virtual methods.
  • They can shadow existing members if named the same — the member always wins.

Failure cases

  • Operator extensions can surprise callers: operator fun List<Int>.plus(other: Int) already exists. Defining conflicting operators introduces bugs.
  • Null-safe extensions: the receiver can be null if you declare fun String?.isNullOrBlankCustom().
  • Extension functions in tests that mock the receiver class do not work with standard mocking tools because they're static.

Scope Functions

Scope functions — let, run, apply, also, with — execute a block of code in the context of an object. They all look similar, but they differ on two axes. First, how the context object is referenced inside the block: as this (an implicit receiver) or as it (a lambda argument). Second, what the function returns: the context object itself, or the result of the lambda.

Function Receiver style Returns Typical use
letit (lambda argument)Lambda resultNull-safe operations, transform + use
runthis (implicit receiver)Lambda resultObject initialization + computation
applythis (implicit receiver)Context objectObject configuration / builder pattern
alsoit (lambda argument)Context objectSide effects without changing the object
withthis (implicit receiver)Lambda resultNon-extension, grouping operations on an object

let

// Definition: inline fun <T, R> T.let(block: (T) -> R): R
val result = name?.let {
    it.trim().uppercase()   // it = name
}
// result is null if name was null; otherwise the transformed string

Use let when you want to perform operations on a nullable value, or when you want to transform a value into something else and use the result.

run

// Definition: inline fun <T, R> T.run(block: T.() -> R): R
val service = Service().run {
    connect()        // this = Service instance
    authenticate()
    this             // returns the configured service
}

run is also available as a non-extension — run { ... } — which is useful for creating a local scope when you have no specific context object to work with.

apply

// Definition: inline fun <T> T.apply(block: T.() -> Unit): T
val intent = Intent(context, MainActivity::class.java).apply {
    putExtra("KEY", value)   // this = Intent
    flags = Intent.FLAG_ACTIVITY_NEW_TASK
}
// Returns the Intent itself

apply is the go-to for builder-style object configuration. It returns the receiver itself, so you can chain it in one expression.

also

// Definition: inline fun <T> T.also(block: (T) -> Unit): T
val list = mutableListOf(1, 2, 3)
    .also { log.d("Before sort: $it") }  // it = list
    .sorted()
    .also { log.d("After sort: $it") }

Use also for side effects — logging, validation, debugging — that should not change the object or interrupt the call chain. It returns the original object unchanged.

with

// Definition: inline fun <T, R> with(receiver: T, block: T.() -> R): R
val result = with(user) {
    "$firstName $lastName"   // this = user
}

with is not an extension — it takes the receiver as a parameter. That means there is no null safety: the object you pass in must already be non-null. Use it when you have a confirmed non-null object and want to group several operations on it without repeating the variable name.

Choosing between them — decision tree

Need null safety?
  YES → let (result = transform) or also (side effect)
  NO → does the block configure the object?
         YES → apply (returns object) or run (returns result)
         NO → with (non-null, grouped ops, returns result)

Side effects only (logging, debug)?
  → also (keeps object in chain)

Android implications

// apply for building Bundles/Intents
val bundle = Bundle().apply {
    putInt("userId", userId)
    putString("source", source)
}

// let for safe null-unwrap
viewModel.selectedItem?.let { item ->
    startActivity(ItemDetailActivity.newIntent(this, item.id))
}

// also for logging before API call
val request = buildRequest().also {
    Timber.d("Sending request: $it")
}

// with for grouped UI updates
with(binding) {
    titleTextView.text = title
    subtitleTextView.text = subtitle
    loadingIndicator.isVisible = false
}

Failure cases

  • Nesting scope functions more than two deep creates unreadable code.
  • Forgetting that run/apply/with shadow this — if you need the outer this (e.g., inside a Fragment's with(binding) block), you must qualify it as this@Fragment.
  • let on a var property is not atomic: the property could change between the null check and the let call in a multithreaded context.

Higher-Order Functions

Definition

A higher-order function is a function that either takes another function as a parameter, or returns a function as its result. In Kotlin, functions are first-class values, so you can pass them around like any other type.

How it works

fun doWithLogging(operation: () -> Unit) {
    Timber.d("Start")
    operation()
    Timber.d("End")
}

doWithLogging { repository.syncData() }

Android implications

  • Click listeners: fun Button.setThrottledClick(action: () -> Unit).
  • Lifecycle scopes: lifecycleScope.launch { ... } takes a suspend lambda.
  • Compose: almost every layout function (Column, Row, LazyColumn) takes a trailing content: @Composable () -> Unit lambda.

Failure cases

  • Non-inline higher-order functions that capture a coroutine scope can cause memory leaks if the lambda holds a reference to a Context or View.
  • Passing a method reference (::myFunction) captures this, which can prevent garbage collection.

Lambdas

Definition

A lambda is an anonymous function that can be passed as a value. In Kotlin, lambdas are objects of function types like (Int) -> Boolean, so every lambda is a real object on the heap unless the containing function is inline.

How it works

val multiply: (Int, Int) -> Int = { a, b -> a * b }
println(multiply(3, 4))  // 12

// Trailing lambda syntax (last parameter)
listOf(1, 2, 3).forEach { println(it) }

// Unused parameters → _
listOf(1, 2, 3).mapIndexed { _, value -> value * 2 }

Closures

Lambdas capture variables from their enclosing scope. Unlike Java, Kotlin lambdas can capture mutable variables — the compiler wraps the variable in a small Ref object on the heap so the lambda can read and write it:

var count = 0
val increment = { count++ }
increment()
println(count)  // 1

Android implications

Lambdas are the backbone of Compose:

Button(onClick = { viewModel.onConfirm() }) {
    Text("Confirm")
}

Failure cases

  • Capturing Activity/Fragment/View references in long-lived lambdas (stored in singletons, repositories) causes memory leaks.
  • Mutable variable capture in a lambda that runs asynchronously is a data race.
  • Each non-inline lambda creates a new object allocation (important in hot paths like RecyclerView adapter bind).

Inline Functions

Definition

An inline function has its bytecode copied directly to each call site at compile time. The lambda parameters are inlined too — no lambda object is created, no virtual dispatch happens.

How it works

inline fun measureTime(block: () -> Unit): Long {
    val start = System.currentTimeMillis()
    block()
    return System.currentTimeMillis() - start
}

At compile time, the call measureTime { doWork() } is replaced with the body of measureTime, with block() replaced by doWork(). No lambda object is created, no virtual dispatch.

noinline marks a specific lambda parameter so it is not inlined — use this when you need to store or pass the lambda elsewhere rather than call it immediately:

inline fun foo(inlined: () -> Unit, noinline notInlined: () -> Unit) { ... }

crossinline prevents a return inside the lambda from returning from the enclosing function. You need this when the lambda is invoked in a different execution context — for example, inside another lambda — where a non-local return would not make sense:

inline fun startAsync(crossinline action: () -> Unit) {
    Thread { action() }.start()  // Can't use a non-local return here
}

Benefits

There are three benefits. First, zero overhead for lambdas — no allocation, no virtual dispatch. Second, it enables reified generics, which is covered in the next section. Third, it enables non-local returns from the lambda, so you can return from the calling function inside the lambda body.

When to use

  • Small utility functions that are called frequently.
  • Functions whose sole purpose is to wrap another lambda (like scope functions, resource management, timing).
  • When you need reified.

When NOT to use

  • Large functions — inlining bloats bytecode.
  • Functions called from public APIs (inline leaks implementation details; changes to the function require recompilation of all callers).
  • Functions with many lambda parameters that are stored or invoked later.

Android implications

All standard Kotlin scope functions (let, apply, etc.) and most collection operations (map, filter) are inline. Compose's @Composable functions are handled by the Compose compiler plugin (not inline in the standard sense, but similarly rewritten).

Reified Generics

Definition

Normally, type parameters are erased at runtime — that is what type erasure means on the JVM. The reified modifier, which is only available in inline functions, works around this by preserving the actual type at each call site, so you can use T as a real type inside the function body — in is checks, ::class references, and reflection.

How it works

// Without reified — doesn't compile
fun <T> List<Any>.filterByType(): List<T> {
    return this.filterIsInstance<T>()  // T is erased — won't work in a normal function
}

// With reified
inline fun <reified T> List<Any>.filterByType(): List<T> {
    return this.filterIsInstance<T>()  // T is available at runtime
}

val strings = listOf(1, "two", 3.0).filterByType<String>()  // ["two"]

Why it works

Because the function is inlined, the compiler substitutes the actual type argument at the call site before erasure ever happens. The bytecode at that call site literally contains String::class — or whatever T actually is — not a generic T.

inline fun <reified T : Activity> Context.startActivity() {
    startActivity(Intent(this, T::class.java))
}

// Usage
context.startActivity<MainActivity>()

Android implications

  • startActivity<T>() extension without passing Class<T> explicitly.
  • viewModel<T>() — many DI/ViewModel extension functions use reified.
  • Gson/Moshi type-safe deserialization helpers.

Failure cases

  • reified only works with inline. Attempting to use reified on a normal function is a compile error.
  • The inlined bytecode embeds the exact type — if the inlined code is in a library, the client must recompile when the inline body changes.

Value Classes

Definition

A value class (formerly called an inline class) wraps a single property of another type. At runtime, the JVM represents it as the underlying type directly — no boxing, no wrapper object allocation. You get type safety at compile time and zero overhead at runtime.

How it works

@JvmInline
value class UserId(val id: Int)
@JvmInline
value class Email(val value: String)

fun sendInvite(userId: UserId, email: Email) { ... }

// Correct usage — types are distinct at compile time
sendInvite(UserId(42), Email("alice@example.com"))

// Won't compile — Int and String cannot be confused with UserId/Email
// sendInvite(42, "alice@example.com")  // Error!

At runtime, UserId is just an Int — no heap allocation.

Benefits

There are two benefits. First, type safety: UserId and DoctorId are both Int wrappers but cannot be accidentally swapped — the compiler rejects a raw Int where a UserId is expected. Second, zero cost in normal usage — no boxing. The caveat is that boxing does occur when a value class is stored in a collection or used as a nullable.

Limitations

  • Can have only one property.
  • Cannot extend other classes (but can implement interfaces).
  • Boxing occurs when used as a generic type parameter or nullable.

Android implications

Excellent for identifier types, quantities with units (Pixels, Dp, Milliseconds), and domain primitives that prevent primitive obsession.

Delegated Properties

Definition

A delegated property offloads its get and set logic to a separate delegate object. The by keyword connects the property to its delegate — you write var name: String by someDelegate and the compiler routes all reads and writes through that delegate's getValue and setValue operator functions.

How it works

class Example {
    var name: String by Delegates.observable("initial") { prop, old, new ->
        println("$old → $new")
    }
}

  • by viewBinding() libraries use delegated properties for binding lifecycle management.
  • SharedPreferences delegates: var token: String by prefs.string("token", "").

Lazy Initialization

Definition

lazy defers computing a property's value until the first time it is accessed. After that first access the result is cached, so every subsequent read just returns the stored value — the initializer block never runs again.

How it works

val heavyObject: ExpensiveClass by lazy {
    ExpensiveClass()  // Called once on first access
}

lazy returns a Lazy<T> delegate. By default it uses LazyThreadSafetyMode.SYNCHRONIZED — double-checked locking under the hood.

Android implications

class MyFragment : Fragment() {
    private val viewModel: MyViewModel by viewModels()  // lazy under the hood
    private val adapter: MyAdapter by lazy { MyAdapter(requireContext()) }
}

Failure cases

  • lazy on a var is not allowed (only val). If you need a lazy var, use Delegates.notNull() or lateinit.
  • lazy(LazyThreadSafetyMode.NONE) in a class that gets accessed from multiple threads causes a data race.

}

Choosing

The rule of thumb is: use lateinit when an external actor — Dagger, the test runner, the Android framework — sets the value after construction and you cannot set it yourself in the constructor. Use lazy when the value is derived from other state and should be computed at most once. Use neither when the value can genuinely be null or changes over time.

Kotlin Collections

read-only List vs MutableList

Definition

Kotlin's collection interfaces are split into two layers. List<T> is read-only — it exposes no mutating methods. MutableList<T> extends it with add, remove, and the rest of the mutating API. Both compile to java.util.List on the JVM, so the distinction is purely at the Kotlin type-system level.

val readOnly: List<Int> = listOf(1, 2, 3)
val mutable: MutableList<Int> = mutableListOf(1, 2, 3)

readOnly.add(4)   // Compile error
mutable.add(4)    // OK

Critical caveat: List<T> is a read-only view, not a deeply immutable list. The underlying object may still be a java.util.ArrayList. If you cast readOnly as MutableList<Int>, you can mutate it at runtime — and it might succeed or throw depending on the actual implementation. True immutability requires Collections.unmodifiableList() or a persistent data structure library.

// Dangerous — compiles and runs
val list: List<Int> = mutableListOf(1, 2, 3)
(list as MutableList<Int>).add(4)  // Works at runtime!

Android implications

  • Expose List<T> from ViewModel/repository (read-only surface), hold MutableList<T> internally.
  • StateFlow<List<Item>> — never expose MutableList in public API.

Sequences

Definition

A Sequence<T> is a lazily evaluated collection. Instead of creating a full intermediate list after each operation, each element flows through the entire pipeline before the next element starts. The practical effect is that you avoid allocating those intermediate lists entirely.

How it works

// Eager (Collections) — creates 3 intermediate lists
val result = (1..1000000)
    .filter { it % 2 == 0 }   // intermediate list of 500,000
    .map { it * 3 }            // intermediate list of 500,000
    .take(5)                   // final list of 5
    .toList()

// Lazy (Sequences) — processes element-by-element, stops after 5
val result = (1..1000000).asSequence()
    .filter { it % 2 == 0 }
    .map { it * 3 }
    .take(5)
    .toList()                  // triggers evaluation

When to use sequences

  • Large collections where you only need a subset of elements.
  • Multiple chained transformations where intermediate results are not needed.
  • Infinite sequences.

When NOT to use sequences

  • Small collections — the overhead of creating a Sequence object is not worth it.
  • Operations that need random access (sequences are inherently sequential).
  • Android's main thread where even eager collections over small lists are fine.

Failure cases

  • Sequences are not thread-safe (they hold state).
  • Forgetting to call a terminal operation (toList(), first(), etc.) — a sequence does nothing until terminated.
  • Mutating the source collection while iterating a sequence.

Flows

Flow<T> is covered in depth in the Coroutines section. Conceptually, a Flow is a cold, asynchronous sequence of values — think of it as a Sequence that integrates with coroutines and supports suspend emitters.

val flow: Flow<Int> = flow {
    emit(1)
    delay(100)
    emit(2)
}

The key distinction from Sequence is: Sequence is synchronous, Flow is asynchronous and supports suspend emitters. StateFlow and SharedFlow are hot flows that additionally carry state or multicast to subscribers.

Interview Angles — 2.1

Q: Difference between List and MutableList?

"List<T> is a read-only interface — it exposes no mutating methods. MutableList<T> extends it with add, remove, and the rest. The important thing to understand is that the split is compile-time only — at runtime both are ArrayList by default, and you can cast a List<T> to a MutableList<T> and mutate it. So List<T> is a read-only view, not a deep immutability guarantee. For true immutability you need a defensive copy or an immutable list wrapper. In practice, the convention is to expose List<T> from the ViewModel so call sites cannot accidentally mutate internal state, while you hold MutableList<T> inside the ViewModel."

Q: Difference between data class and normal class?

"A data class auto-generates equals and hashCode from primary constructor properties, a meaningful toString, a copy method for shallow cloning, and componentN functions for destructuring. A normal class inherits reference equality from Any, so two objects that are logically the same will compare as unequal unless you override equals yourself. There are four gotchas to know. First, only primary constructor properties participate in the generated methods — body properties are invisible to them. Second, var properties in a data class break HashSet and HashMap contracts if mutated after insertion. Third, copy is shallow — nested mutable objects are shared. And fourth, data classes cannot be open or abstract, so you cannot subclass them."

Q: Why avoid !!?

"!! converts compile-time null safety into a runtime KotlinNullPointerException. It is saying 'I know better than the type system,' which is almost always wrong. There are two practical problems. First, when it does throw, the stack trace points at the !! site, not where the null was actually introduced, so it is hard to debug. Second, using it becomes contagious — once you start you tend to chain more of them. The alternatives are better in every case: ?. handles null gracefully, ?: provides a fallback or a meaningful error, and requireNotNull() or checkNotNull() throw with a clear message you can read in logs. The Zocdoc codebase explicitly prohibits new !! uses."

Q: When to use sealed class for UI state?

"Use a sealed class for UI state whenever the screen can be in multiple mutually exclusive states with different data payloads. The canonical pattern is a Loading object, a Content data class with the actual data, and an Error data class with a message. The big win is that the when expression on this state in a Composable or Fragment is exhaustive — the compiler forces you to handle every case, so you can never accidentally ship a screen that silently ignores a new state. It also eliminates the alternative of having stranded boolean flags like isLoading, hasError, isSuccess all sitting on the ViewModel, which can get into contradictory combinations."

Q: lateinit vs nullable vs lazy?

"There are three choices and each fits a specific situation. A nullable var field: Type? = null is the right choice when null is a meaningful value in the domain, or when the field may genuinely never be set. The downside is null checks everywhere and it reads like the absence of a decision. lateinit var is for framework-injected properties — things Dagger or the Android lifecycle system will definitely set before first use, like an @Inject field or binding in onCreate. If you access it too early it throws UninitializedPropertyAccessException with the property name, which is a useful failure. You cannot use it with primitives. by lazy is for val properties you compute yourself from other state — the value is derived once and cached. It is thread-safe by default and it can never be null. The rule I follow is: use lateinit when an external actor sets the value, use lazy when you compute it yourself."

Q: Sequence vs collection?

"Collections are eager — every intermediate operation like filter or map produces a full intermediate list before the next step starts. Sequences are lazy — elements flow through the entire pipeline one by one, so no intermediate lists are allocated. The practical difference is most visible on large inputs with a short final result: filter { }.map { }.take(5) on a million elements processes only as many elements as needed to produce 5 results, and allocates nothing in between. For small collections or chains of one or two operations, use collections — the overhead of creating the sequence object is not worth it. Sequences also enable infinite sources, since they only produce elements on demand."

2.2 Kotlin Generics

Type Parameters and Constraints

Definition

Type parameters let you write code that works with multiple types while preserving type safety. Constraints narrow which types are allowed as arguments — an upper bound constraint like T : Comparable<T> lets you call compareTo on T because the compiler knows it is at least a Comparable.

// Unconstrained — T can be anything
fun <T> identity(value: T): T = value

// Upper bound constraint
fun <T : Comparable<T>> max(a: T, b: T): T = if (a > b) a else b

// Multiple constraints — use where clause
fun <T> copy(src: T, dest: T) where T : Cloneable, T : Serializable { ... }

How it works on the JVM

Type parameters exist only at compile time. The bytecode uses Object (or the upper bound) everywhere. The compiler inserts casts as needed.

Android implications

Repository and data-layer generics:

sealed class Result<out T> {
    data class Success<T>(val data: T) : Result<T>()
    data class Error(val exception: Exception) : Result<Nothing>()
}

Variance: out and in

Definition

Variance describes how subtyping relationships between generic types relate to subtyping of their type arguments. The core question is: if Dog is a subtype of Animal, what is the relationship between Container<Dog> and Container<Animal>?

Invariance (default)

By default, MutableList<Dog> is not a subtype of MutableList<Animal>, even though Dog is a subtype of Animal. This is invariance.

The reason is type safety. If MutableList<Dog> were assignable to MutableList<Animal>, you could add a Cat to what is actually a Dog list:

val dogs: MutableList<Dog> = mutableListOf(Dog())
val animals: MutableList<Animal> = dogs        // If allowed...
animals.add(Cat())                              // Now dogs contains a Cat!

Covariance: out T (producer)

A type parameter marked out means the class only produces values of T — it returns T from functions but never accepts T as an input. This makes Container<Dog> a safe subtype of Container<Animal>.

interface Producer<out T> {
    fun produce(): T   // Can only return T
}

val dogProducer: Producer<Dog> = DogFactory()
val animalProducer: Producer<Animal> = dogProducer   // Safe — produces Dogs, which are Animals

List<T> in Kotlin is declared as List<out T> — you can only read from it, never add to it — so List<Dog> is safely assignable to List<Animal>.

Contravariance: in T (consumer)

A type parameter marked in means the class only consumes values of T — it accepts T as a parameter but never returns it. This makes Consumer<Animal> a safe subtype of Consumer<Dog>, which is the opposite direction from covariance.

interface Consumer<in T> {
    fun consume(value: T)   // Can only accept T
}

val animalConsumer: Consumer<Animal> = AnimalHandler()
val dogConsumer: Consumer<Dog> = animalConsumer   // Safe — can consume Animals, Dogs are Animals

Mnemonic: Producer is out, which is covariant — read only. Consumer is in, which is contravariant — write only. Comparator<T> is a good example of in T because it consumes two T values to compare them and never produces one.

Use-site vs declaration-site variance

There are two places to declare variance. Declaration-site is out or in on the class or interface definition itself — List<out T> is the example in the standard library. Use-site is out or in on a specific function parameter — useful when you cannot control the class definition.

fun copy(from: List<out Animal>, to: MutableList<in Animal>) {
    for (item in from) to.add(item)
}

Star Projection

Definition

List<*> means "a List of some type I do not know or do not care about." It is analogous to Java's List<?>. You use it when you need to accept any generic container regardless of its type argument.

How it works

  • List<*> is equivalent to List<out Any?> — you can read from it but all elements come out as Any?.
  • MutableList<*> — you can read elements as Any? but cannot add anything (because the compiler doesn't know the actual type).
fun printAll(list: List<*>) {
    for (item in list) println(item)  // item: Any?
}

When to use

  • When you receive a generic type at runtime and don't have the type information.
  • When a function needs to accept any generic container.

Failure cases

  • You cannot write to a MutableList<*> (except null). Attempting to add a value is a compile error.

Type Erasure

Definition

Generic type information is erased at runtime — that is the fundamental rule of the JVM generics implementation. At the bytecode level, List<String> and List<Int> are both just List. The compiler uses the type arguments for type checking and inserts casts where needed, but the type parameters do not appear in the compiled class file at all.

Implications

fun <T> check(list: List<T>) {
    if (list is List<String>) { }  // Compile error: cannot check for erased type
}

Workarounds

  • Reified type parameters (inline functions, see section 2.1).
  • Pass Class<T> or KClass<T> explicitly.
  • ParameterizedType reflection (fragile, verbose).

Reified Type Parameters

Already covered in depth in section 2.1. Restatement in generics context:

reified is only available in inline functions. It instructs the compiler to substitute the actual type at each call site, bypassing type erasure for that specific invocation.

inline fun <reified T> parseResponse(json: String): T {
    return Gson().fromJson(json, T::class.java)
}

val user: User = parseResponse(jsonString)

Without reified, you would have to write parseResponse(jsonString, User::class.java).

Interview Angles — 2.2

Q: Explain List<out T>.

"List<T> in Kotlin is declared as interface List<out E>. The out makes it covariant in E, which means a List<Dog> is a safe subtype of List<Animal>. That is safe because List is read-only — you can only get elements out of it, never add them in. If the interface allowed mutation, covariance would break type safety, because you could use the List<Animal> reference to add a Cat to what is physically a List<Dog>. The out keyword enforces the restriction at the compiler level: the interface cannot declare any method that consumes E, only methods that produce it. This is declaration-site variance — the class itself makes the promise once and the compiler holds it everywhere."

Q: Why is MutableList<Dog> not safely assignable to MutableList<Animal>?

"MutableList is invariant in T because it both produces and consumes elements — it has both get and add. If the assignment were allowed, the type system would break:"

val dogs: MutableList<Dog> = mutableListOf(Dog())
val animals: MutableList<Animal> = dogs  // Hypothetically allowed
animals.add(Cat())                       // Cat added to dogs!
val dog: Dog = dogs[1]                   // ClassCastException at runtime

"This is the classic array covariance problem. Java arrays are covariant and this exact scenario causes ArrayStoreException at runtime. Kotlin prevents it at compile time for generics by making mutable containers invariant by default — a deliberate improvement over Java."

Q: What problem does reified solve?

"Type erasure means you cannot write T::class.java or is T inside a generic function — the type parameter T simply does not exist at runtime. reified solves this by inlining the function and substituting the concrete type at each call site before erasure can happen. Without reified, any API that needs runtime type information has to accept an explicit Class<T> parameter, which is verbose — you write parseResponse(jsonString, User::class.java) every time. With reified, you just write parseResponse<User>(jsonString) — clean, type-safe, and zero extra runtime overhead because the substitution happens at compile time."

2.3 Java Fundamentals

OOP Basics

Definition

Java is a class-based, statically typed, object-oriented language built around four pillars. First, encapsulation: internal state is hidden behind methods, with access controlled by private, protected, public, and package-private modifiers. Second, inheritance: a class can extend exactly one parent class with extends. Third, polymorphism: a parent-type reference can hold any subtype, and method calls are dispatched based on the actual runtime type — dynamic dispatch. Fourth, abstraction: interfaces and abstract classes define contracts without providing complete implementations.

Inheritance

Definition

A Java class can extend one other class and thereby inherit all of that class's non-private fields and methods.

class Animal {
    protected String name;
    public void speak() { System.out.println("..."); }
}

class Dog extends Animal {
    @Override
    public void speak() { System.out.println("Woof"); }
}

Key rules

Java has single-class inheritance — one extends only. All classes implicitly extend Object. super accesses parent class members. Constructors are not inherited, but the parent constructor must be called — either explicitly via super(...) or implicitly if the parent has a no-arg constructor.

Failure cases

  • Fragile base class problem: Changing a method in a base class can break subclasses that override it, especially if the override relies on implementation details.
  • Constructor chaining: Forgetting super(args) when the parent has no no-arg constructor causes a compile error.
  • Overriding equals in a subclass breaks the symmetry contract if the parent already overrides it.

Interfaces

Definition

An interface defines a contract — a set of methods a class promises to implement. A class can implement as many interfaces as needed, which is how Java achieves multiple inheritance of type.

interface Drawable {
    void draw();
    default void drawWithBorder() {  // Default method (Java 8+)
        draw();
        drawBorder();
    }
    static Drawable noOp() { return () -> {}; }  // Static method
}

Java 8+ additions

Java 8 added three things to interfaces. default methods provide a default implementation so existing classes do not need to change. static methods add utility functions scoped to the interface. Java 9 added private methods as helpers for default implementations, keeping the public surface clean.

vs abstract class (see next section)

Abstract Classes

Definition

An abstract class is a class that cannot be instantiated directly. It can declare abstract methods — methods with no body — that every subclass must implement, and it can also have fully concrete methods that subclasses inherit as-is.

abstract class Shape {
    protected String color;

    public abstract double area();  // Must be overridden

    public String describe() {      // Concrete method — can be used as-is
        return color + " shape with area " + area();
    }
}

Interface vs Abstract Class

The guideline is: prefer interfaces for defining capabilities like Serializable or Drawable. Use abstract classes when you have shared implementation or shared state that subclasses genuinely should inherit.

Composition over Inheritance

Definition

Instead of extending a class to reuse its behavior, you hold an instance of it as a field and delegate to it. This avoids the fragile base class problem — you are not coupled to the parent's implementation details — and it allows you to swap behavior at runtime by substituting a different delegate.

// Inheritance (fragile)
class LoggingList<T> extends ArrayList<T> {
    @Override public boolean add(T e) {
        log.info("Adding " + e);
        return super.add(e);  // Breaking if ArrayList.add internals change
    }
}

// Composition (robust)
class LoggingList<T> implements List<T> {
    private final List<T> delegate;
    public LoggingList(List<T> delegate) { this.delegate = delegate; }

    @Override public boolean add(T e) {
        log.info("Adding " + e);
        return delegate.add(e);
    }
    // ... other methods delegate to delegate
}

Android implications

  • RecyclerView.Adapter composition — hold a list rather than extending one.
  • Interactors in MVVM — each Interactor is a composed piece of behavior injected into a ViewModel, not a subclass of some BaseInteractor.
  • Kotlin's delegation syntax by automates composition: class LoggingList<T>(private val delegate: List<T>) : List<T> by delegate.

Why prefer composition

There are four reasons to prefer composition. First, it does not couple you to the parent's implementation details — changes to the delegate do not break your class. Second, it works even when the parent class is final. Third, it enables dynamic replacement of behavior at runtime by substituting a different delegate. Fourth, it is far more amenable to dependency injection and testing — you inject a mock instead of the real thing.

final

Definition

final has three distinct uses in Java. A final class cannot be subclassed — String and Integer are final. A final method cannot be overridden in a subclass. A final variable or field can be assigned exactly once, and the compiler enforces this.

final class ImmutablePoint {
    private final int x;
    private final int y;

    public ImmutablePoint(int x, int y) {
        this.x = x;  // Only assignment allowed
        this.y = y;
    }
}

Performance

The JVM can optimize final methods and fields more aggressively — it can inline them and skip virtual dispatch. There is also a thread-safety benefit: final fields in a properly constructed object are guaranteed to be visible to all threads without any synchronization, per the Java Memory Model.

Kotlin equivalent

In Kotlin, classes are final by default. You use open to allow subclassing. This is the inverse of Java's default and it is a deliberate language design choice — if you want to be subclassed, you have to explicitly opt in.

static

Definition

static members belong to the class, not to any particular instance. A static field is shared across all instances — one copy for the whole class — and a static method can be called without creating an instance at all.

class Counter {
    private static int count = 0;    // One per class
    private int id;                  // One per instance

    public Counter() { this.id = ++count; }
    public static int getCount() { return count; }
}

Android implications

Static constants like static final String TAG = "MyClass" are fine and idiomatic. Static utility methods are fine. The one rule to internalize is: never hold a Context, Activity, or View in a static field — that is the most common Android memory leak. A static Activity reference keeps the entire Activity and its entire View hierarchy alive past onDestroy(), which prevents GC and leaks memory proportional to the screen's complexity.

Kotlin equivalent

Use companion object for class-level members and top-level functions or properties for file-level statics.

equals() and hashCode()

Definition

equals() defines semantic equality — whether two objects represent the same value. hashCode() returns an integer hash used by hash-based data structures to find the right bucket. The two methods are deeply coupled: you must always override both or neither.

Contract (from Object Javadoc)

The equals contract has four requirements: reflexive (x.equals(x) is always true), symmetric (x.equals(y) implies y.equals(x)), transitive, and consistent across multiple calls. The critical linking rule between the two methods is: if x.equals(y), then x.hashCode() must equal y.hashCode(). The converse is not required — hash collisions are allowed.

class User {
    private final int id;
    private final String name;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        User user = (User) o;
        return id == user.id && Objects.equals(name, user.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}

Why override both?

If you override equals but not hashCode, two objects that are logically equal may land in different hash buckets. A HashMap or HashSet looks up by bucket first, so it will never find the entry:

User u1 = new User(1, "Alice");
User u2 = new User(1, "Alice");
u1.equals(u2);  // true (custom equals)
// hashCode not overridden → different hash buckets
Map<User, String> map = new HashMap<>();
map.put(u1, "value");
map.get(u2);  // null — looked in wrong bucket!

Kotlin data class auto-generates a correct, consistent equals/hashCode pair from primary constructor properties — that is one of the main reasons to prefer it over a plain class for value objects.

Failure cases

  • Using instanceof vs getClass(): instanceof allows subtype equality (often violates symmetry), getClass() enforces exact type match.
  • Mutable fields in equals/hashCode: if the fields change, the contract is broken.

toString()

Definition

toString() returns a human-readable representation of the object. Without overriding it, the default from Object gives you ClassName@hexHashCode — which is useless in logs.

@Override
public String toString() {
    return "User{id=" + id + ", name='" + name + "'}";
}

Android implications

Always override toString() on model classes so logs are readable. Kotlin data classes auto-generate it from primary constructor properties. The one rule that overrides everything else: do not include sensitive or PII data in toString(), because it will end up in crash logs and logcat.

Immutability

Definition

An immutable object's state cannot change after construction. Any operation that looks like a mutation actually returns a new object — the original stays unchanged.

How to achieve in Java

There are five steps. First, declare the class final so no subclass can sneak in a mutable field. Second, make all fields private final. Third, provide no setters. Fourth, perform defensive copies of any mutable parameters passed to the constructor. Fifth, return defensive copies of any mutable fields from getters — otherwise callers can reach in and mutate the internal state directly.

public final class ImmutableList<T> {
    private final List<T> items;

    public ImmutableList(List<T> items) {
        this.items = new ArrayList<>(items);  // Defensive copy
    }

    public List<T> getItems() {
        return Collections.unmodifiableList(items);  // Defensive copy on read
    }
}

Benefits

There are four benefits to immutability. It is inherently thread-safe because no thread can mutate the state, so no synchronization is needed. It is safe as a HashMap key because the hash code can never change. It is easier to reason about — no action-at-a-distance mutations. And the JVM can cache and share instances, which is why String is immutable and String.intern() works.

Android implications

  • Room entities benefit from immutability; mutable entities cause hidden mutation bugs.
  • Kotlin's data class with val properties provides near-immutability (still requires defensive copies of collection fields).

Checked vs Unchecked Exceptions

Definition

Java has two exception hierarchies rooted at Throwable. Error covers JVM-level issues like OutOfMemoryError and StackOverflowError — these are not meant to be caught. Exception splits further into two categories. Checked exceptions — Exception and its subclasses, excluding RuntimeException — must be either declared in the method signature with throws or caught at the call site. Examples are IOException and SQLException. Unchecked exceptions — RuntimeException and its subclasses — have no compile-time obligation to catch or declare. Examples are NullPointerException, IllegalArgumentException, and IndexOutOfBoundsException.

// Checked — must catch or declare
public void readFile(String path) throws IOException {
    Files.readAllBytes(Paths.get(path));
}

// Unchecked — no obligation
public void divide(int a, int b) {
    if (b == 0) throw new ArithmeticException("Division by zero");
}

The checked-exception controversy

Checked exceptions enforce error handling at compile time, which sounds good, but the practical problems are significant. They pollute APIs with throws declarations that propagate all the way up the call stack. Developers often swallow them or wrap them in RuntimeException just to escape the obligation. And they do not compose well with higher-order functions — a lambda cannot easily throw a checked exception. Modern Java and Kotlin overwhelmingly prefer unchecked exceptions or Result/Either types for error handling.

Kotlin does not have checked exceptions

Kotlin treats all exceptions as unchecked. See section 2.4 for how this affects interop with Java that declares checked exceptions.

Generics and Type Erasure (Java)

The fundamental mechanism is the same as Kotlin — same JVM. The key difference is that Java uses wildcards for use-site variance rather than out/in.

Wildcards (Java's use-site variance)

List<? extends Animal> is an upper bounded wildcard — covariant, read-only — and it is equivalent to Kotlin's List<out Animal>. List<? super Dog> is a lower bounded wildcard — contravariant, write-only — and it is equivalent to Kotlin's List<in Dog>. List<?> is an unbounded wildcard equivalent to Kotlin's List<*>.

PECS mnemonic: Producer Extends, Consumer Super — the way I remember it is that if a generic type produces values for you to read, use extends; if it consumes values you hand to it, use super.

// Reading from: use extends
<T> void process(List<? extends T> source) { T item = source.get(0); }
// Writing to: use super
<T> void populate(List<? super T> target, T value) { target.add(value); }

Java Memory Model Basics

Definition

The Java Memory Model — usually called the JMM — defines the rules governing how threads read and write to memory, establishing visibility and ordering guarantees.

Key concepts

There are four things to understand. Working memory: each thread has a local copy — a cache — of shared variables, and it does not necessarily read from main memory on every access. Main memory: the shared store all threads ultimately read from and write to. Visibility: without synchronization, changes made by one thread may never become visible to another. Reordering: the JVM and CPU can reorder instructions for performance, as long as the program appears to execute in order from a single thread's perspective.

Happens-before relationship

The JMM formalizes visibility through the happens-before relation — if action A happens-before action B, then every effect of A is guaranteed to be visible to B. The key rules are: a thread's own actions are happens-before within that thread in program order; a synchronized block releasing a monitor happens-before the next acquisition of the same monitor; a volatile write happens-before all subsequent volatile reads of the same variable; Thread.start() happens-before the new thread's first action; and Thread.join() happens-before the code that follows it.

volatile

Definition

A volatile field guarantees visibility and prevents reordering across the access. Every write to a volatile variable is immediately written through to main memory, and every read reads from main memory rather than a thread-local cached copy.

private volatile boolean running = true;

// Thread 1
public void stop() { running = false; }

// Thread 2
public void run() {
    while (running) { doWork(); }
}

Without volatile, Thread 2 might cache running = true forever in its CPU register, never seeing the update from Thread 1.

What volatile does NOT provide

volatile does not provide atomicity for compound operations. i++ on a volatile int is not atomic — it is read, increment, write — three operations — and another thread can slip in between them. Use AtomicInteger instead. It also does not provide mutual exclusion: multiple threads can execute a volatile write simultaneously.

When to use

Use volatile for simple flags that one thread reads and another thread sets. Use it for publishing an immutable object — the volatile write ensures the reference assignment is visible to all threads. The classic example is the double-checked locking singleton pattern, which requires volatile on the instance field to prevent the JVM from returning a partially constructed object.

// Double-checked locking — requires volatile
private static volatile Singleton instance;

public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) {
                instance = new Singleton();
            }
        }
    }
    return instance;
}

The Kotlin equivalent is the @Volatile annotation on a property.

synchronized

Definition

synchronized provides two guarantees: mutual exclusion — only one thread can execute the block at a time — and visibility — all changes made inside the block are visible to the next thread that enters a synchronized block on the same monitor.

private final Object lock = new Object();
private int counter = 0;

public void increment() {
    synchronized (lock) {
        counter++;   // Read-modify-write is now atomic
    }
}

public synchronized int get() {  // Locks on 'this'
    return counter;
}

synchronized vs volatile

Failure cases

There are four common failure cases. Synchronizing on this can cause unintended contention if external code also synchronizes on the same object — prefer a private final lock object instead. Holding locks across I/O or long-running operations starves other threads. Deadlock: Thread A holds Lock 1 and waits for Lock 2 while Thread B holds Lock 2 and waits for Lock 1 — they block each other forever. Synchronizing on a boxed Integer is unsafe because Integer.valueOf() caches values between -128 and 127, so multiple threads may accidentally share the same monitor.

The Kotlin equivalents are the @Synchronized annotation or the synchronized(lock) { } extension function.

wait() / notify() / notifyAll()

Definition

These Object methods implement the classic condition variable pattern for inter-thread communication, and they must be called from within a synchronized block on the same object. wait() releases the lock and suspends the current thread until another thread calls notify() or notifyAll() on the same object. notify() wakes one waiting thread — non-deterministically which one. notifyAll() wakes all waiting threads, and they then compete to reacquire the lock.

// Producer-consumer pattern
private final Queue<Task> queue = new LinkedList<>();

public synchronized void produce(Task task) {
    queue.add(task);
    notifyAll();  // Wake any waiting consumers
}

public synchronized Task consume() throws InterruptedException {
    while (queue.isEmpty()) {
        wait();   // Release lock and wait for a produce() call
    }
    return queue.poll();
}

Critical rules

There are three rules to internalize. First, always check the condition in a while loop, not an if — the JVM spec explicitly allows spurious wakeups, so the condition might not actually be true when a thread wakes up. Second, always call wait/notify/notifyAll within a synchronized block on the same object, or you get IllegalMonitorStateException. Third, in modern code, prefer java.util.concurrent primitives like CountDownLatch, Semaphore, BlockingQueue, and Condition over raw wait/notify — they are safer and more readable.

Android implications

You will rarely use wait/notify directly in Android code because coroutines and RxJava provide better abstractions. However, understanding them is important for understanding how CountDownLatch and blocking calls work, which do appear in test code.

Interview Angles — 2.3

Q: Explain Java object equality.

"Java has two kinds of equality. Reference equality uses == and asks: are these two variables pointing at the exact same object in memory? Semantic equality uses equals() and asks: do these two objects represent the same value? Object.equals() defaults to reference equality — so without overriding it, two User(1, 'Alice') instances are not equal even though they carry identical data. The contract for equals requires four properties: reflexive, symmetric, transitive, and consistent. There is also a classic gotcha with primitive wrappers: Integer.valueOf(127) == Integer.valueOf(127) returns true because the JVM caches integers from -128 to 127, but Integer.valueOf(128) == Integer.valueOf(128) returns false because those create new objects. The lesson is never use == to compare boxed types."

Q: Why override hashCode() when overriding equals()?

"The hashCode contract says: if a.equals(b), then a.hashCode() must equal b.hashCode(). Hash-based collections like HashMap and HashSet work in two stages — they use hashCode to find the bucket, then use equals to find the exact entry within that bucket. If you override equals but not hashCode, two logically equal objects land in different buckets, so HashMap.get never finds the second one and HashSet.contains returns false even though the element is there. This causes silent data loss and duplicate entries. The rule is simple: always override both together or neither."

Q: What is type erasure?

"Type erasure is the JVM mechanism by which generic type arguments are removed at compile time. List<String> and List<Integer> both become just List in the bytecode. The compiler uses the type information for checking and inserts casts where needed, but the type parameters disappear completely from the class files. The practical consequences are three things you cannot do: you cannot check instanceof List<String> at runtime because the type argument is gone; you cannot write new T() in a generic method for the same reason; and reflection sees only raw types. Kotlin's reified generics are a compile-time workaround — by inlining the function, the compiler substitutes the concrete type at each call site before erasure happens."

Q: Difference between volatile and synchronized?

"volatile provides visibility — reads and writes to a single variable bypass CPU caches and go directly to main memory, so all threads always see the latest value. But it does not provide atomicity: i++ on a volatile int is still three separate operations that can be interleaved. synchronized provides both visibility and mutual exclusion — only one thread can execute the synchronized block at a time, and all changes become visible to the next thread that acquires the lock. The trade-off is that synchronized can block threads and cause contention. The rule I use is: reach for volatile for simple flags or published references; reach for synchronized or java.util.concurrent classes when you need atomicity across multiple operations or need to protect compound state."

Q: Difference between interface and abstract class?

"Abstract classes can have instance state — fields — constructors, and any mix of abstract and concrete methods. Interfaces, since Java 8, can have default, static, and private methods but they still cannot have instance state. The other key difference is inheritance: a class can implement as many interfaces as it wants but can only extend one abstract class. The guidance I follow is: use an abstract class for the template method pattern — shared implementation with customization hooks — or when subclasses genuinely need to share state. Use an interface for contracts and capabilities like Serializable or Drawable. When in doubt, prefer interfaces because they compose better and do not constrain the subclass's inheritance chain."

2.4 Kotlin-Java Interop

Platform Types

Definition

When Kotlin calls Java code that has no nullability annotations, the compiler cannot determine whether the value is nullable or non-null. These values get platform types, written as Type! in error messages — for example, String!. Platform types are essentially an escape hatch that bypasses Kotlin's null safety system, and the responsibility for null checking shifts entirely to you.

How it works

// Java
public class UserRepository {
    public User getUser() { return null; }  // No annotation
}
val repo = UserRepository()
val user = repo.getUser()   // user has type User! (platform type)
user.name                   // Compiles — but crashes at runtime if null!

The compiler does not warn you about potential nullability when assigning a platform type to a non-null variable:

val name: String = repo.getUser().name  // Compiles, but can throw NPE at runtime

Why this matters

Platform types are a compatibility escape hatch, not a safety feature. You are responsible for null checking. When a null does come through, the resulting crash looks like a KotlinNullPointerException with a message like "getUser() must not be null," which tells you where the null crossed the boundary but not where it originated.

Best practices

The fix is to add @Nullable and @NonNull annotations to your Java code so Kotlin sees definite types. When calling un-annotated Java APIs in Kotlin, always treat return values as potentially null — use ?. or an explicit null check. Never assign a platform type directly to a non-null val without verifying first.

Nullability Annotations

Definition

Adding @Nullable or @NonNull annotations to Java code gives Kotlin the information it needs to assign a definite nullable or non-null type at the call site, rather than a platform type.

Supported annotation packages — Kotlin recognizes all of these:

  • org.jetbrains.annotations.@Nullable / @NotNull
  • androidx.annotation.@Nullable / @NonNull
  • javax.annotation.@Nullable / @Nonnull
  • android.support.annotation.@Nullable / @NonNull
  • JSR-305 (@javax.annotation.Nonnull)
import androidx.annotation.NonNull;
import androidx.annotation.Nullable;

public class UserRepository {
    @Nullable
    public User getUser() { return null; }

    @NonNull
    public String getServerUrl() { return "https://api.zocdoc.com"; }
}
val repo = UserRepository()
val user: User? = repo.getUser()     // Now correctly typed as User?
val url: String = repo.getServerUrl() // Correctly typed as String

Android implications

Most AndroidX APIs are well-annotated, so you rarely encounter platform types from them. Third-party Java libraries are often not annotated — treat their return values defensively as nullable until proven otherwise.

SAM Conversion

Definition

Single Abstract Method (SAM) conversion lets a Kotlin lambda be automatically converted into a Java interface that has exactly one abstract method. This is what lets you write a lambda where the Java API expects, say, a View.OnClickListener, without any boilerplate object expression.

How it works

// Java SAM interface
public interface OnClickListener {
    void onClick(View v);
}

// Java method taking it
public void setOnClickListener(OnClickListener listener) { ... }
// Without SAM conversion (verbose)
button.setOnClickListener(object : View.OnClickListener {
    override fun onClick(v: View) { handleClick(v) }
})

// With SAM conversion (idiomatic)
button.setOnClickListener { v -> handleClick(v) }

SAM for Kotlin interfaces

For Kotlin interfaces, SAM conversion does not happen automatically — you have to explicitly mark the interface with fun interface to opt in:

fun interface Predicate<T> {
    fun test(value: T): Boolean
}

val isPositive = Predicate<Int> { it > 0 }  // SAM conversion

Failure cases

SAM conversion only works when the Java interface has exactly one abstract method — add a second and the lambda no longer compiles. Kotlin interfaces do not support SAM conversion by default, which is why fun interface exists. If the Java SAM interface has generic type parameters, the Kotlin lambda may need explicit type annotations.

@JvmStatic

Definition

@JvmStatic on a companion object method or property tells the Kotlin compiler to generate a real static method or field in the Java bytecode, in addition to the instance method on the companion object. Without it, Java callers have to go through MyClass.Companion.create(), which is awkward. With it, they just write MyClass.create().

Without @JvmStatic

class MyClass {
    companion object {
        fun create(): MyClass = MyClass()
    }
}

From Java: MyClass.Companion.create() — verbose.

With @JvmStatic

class MyClass {
    companion object {
        @JvmStatic
        fun create(): MyClass = MyClass()
    }
}

From Java: MyClass.create() — clean, looks like a static method.

When to use

Use @JvmStatic on any public API that will be called from Java. In Android specifically, Fragment.newInstance() and Activity.newIntent() factory methods in companion objects should have it, because they are commonly called from Java Activities.

@JvmOverloads

Definition

Kotlin supports default parameter values, but Java does not understand them. @JvmOverloads tells the compiler to generate a set of Java overloaded methods — one for each combination of trailing default parameters — so Java callers get the same convenience without knowing about defaults.

@JvmOverloads
fun connect(host: String, port: Int = 443, timeout: Int = 5000) { ... }

Generated Java methods:

void connect(String host, int port, int timeout)  // Full
void connect(String host, int port)               // timeout defaults to 5000
void connect(String host)                         // port defaults to 443, timeout to 5000

Android use case

The canonical example is a custom View constructor. Without @JvmOverloads, the Android framework — which calls View constructors from Java — would fail to find the (Context, AttributeSet) constructor and your view would not inflate from XML. This is one of the most common Android gotchas when writing custom views in Kotlin.

@JvmField

Definition

By default, a Kotlin property compiles to a private backing field plus a getXxx() getter — and a setXxx() setter if it is a var. @JvmField exposes the field directly in Java bytecode with no getter or setter wrapper, so Java callers access it as a plain field.

class Config {
    @JvmField
    val maxRetries: Int = 3    // Exposed as a public field in Java
}

Java access: config.maxRetries (direct field access, not config.getMaxRetries()).

Use cases

There are three common use cases. Constants in companion objects — @JvmField val DEFAULT_TIMEOUT = 5000 — so Java sees MyClass.DEFAULT_TIMEOUT as a direct field access. Avoiding the overhead of getter calls in performance-sensitive Java code, though this is a minor win in practice. And some Java frameworks that expect direct field access, like JUnit's @Rule or certain serialization libraries, require it.

Gotchas

@JvmField bypasses property delegation, custom getters, and visibility modifiers — the field is exposed as-is. It cannot be used on abstract properties or properties that have custom getters or setters.

Calling Suspend Functions from Java

Definition

suspend functions are a Kotlin coroutine concept with no direct Java equivalent. The Kotlin compiler transforms them by adding a Continuation<T> parameter — that is what the coroutine machinery uses to resume execution. From Java you can call them, but it requires explicit continuation handling, which is not ergonomic.

What the compiler generates

// Kotlin
suspend fun fetchUser(id: Int): User = withContext(Dispatchers.IO) { api.get(id) }

Becomes in Java bytecode:

Object fetchUser(int id, Continuation<? super User> continuation)

Calling from Java

The cleanest approach is to wrap the suspend call in a coroutine scope:

// Option 1: BuildersKt.launch (fire-and-forget)
BuildersKt.launch(
    CoroutineScopeKt.CoroutineScope(Dispatchers.getMain()),
    EmptyCoroutineContext.INSTANCE,
    CoroutineStart.DEFAULT,
    (scope, continuation) -> viewModel.fetchUser(userId, continuation)
);

// Option 2: Wrap in a ListenableFuture (kotlinx-coroutines-guava)
ListenableFuture<User> future = FutureKt.future(
    scope, EmptyCoroutineContext.INSTANCE, CoroutineStart.DEFAULT,
    (scope2, cont) -> viewModel.fetchUser(userId, cont)
);

Best practice

The right approach is to expose a LiveData<T> or an RxJava Single<T> from the ViewModel for Java callers, rather than exposing suspend functions directly. Never surface suspend functions in public APIs that Java code will consume.

// ViewModel with Java-friendly surface
fun loadUserLiveData(id: Int): LiveData<User> = liveData {
    emit(fetchUser(id))
}

Java Checked Exceptions in Kotlin

Definition

Kotlin does not have checked exceptions — all exceptions are unchecked. When Kotlin code calls a Java method that declares checked exceptions with throws IOException, Kotlin does not require a try-catch at the call site. The exception can still propagate at runtime, it just will not be flagged at compile time.

val bytes = Files.readAllBytes(Paths.get("file.txt"))  // No try-catch required in Kotlin
// But IOException can still propagate at runtime!

Exposing Kotlin to Java with @Throws

If a Kotlin function propagates a checked exception and will be called from Java, annotate it with @Throws to generate a throws clause in the bytecode. Without it, the Java caller has no idea the exception can be thrown — it becomes an unchecked surprise at runtime.

Failure cases

Forgetting @Throws on Kotlin functions called from Java is the main pitfall — Java callers will not be warned and may not have any error handling in place. Catching blanket Exception in Kotlin just to absorb checked exceptions coming from Java is also a common mistake that masks real bugs.

Kotlin Properties → Getters/Setters

Definition

Kotlin properties compile to a private backing field plus getXxx() and setXxx() accessor methods in Java bytecode. This aligns with JavaBean conventions, so Java code can consume Kotlin properties transparently.

class Person {
    var name: String = "Alice"         // get: getName(), set: setName()
    val age: Int = 30                  // get: getAge() only (val = no setter)
    var isActive: Boolean = true       // get: isActive(), set: setActive()  ← Boolean special case
}

Java:

Person p = new Person();
p.getName();       // → person.name
p.setName("Bob");  // → person.name = "Bob"
p.isActive();      // Boolean: isXxx() convention
p.setActive(false);

Boolean naming

For Boolean properties starting with is, the getter keeps the is prefix — so isActive becomes isActive() in Java. For all other properties, the getter is get plus the capitalized name.

Custom accessors

var firstName: String = ""
var lastName: String = ""
val fullName: String
    get() = "$firstName $lastName"   // Compiles to getFullName(), no backing field

@JvmField to remove accessors

If you annotate a property with @JvmField, no getter or setter is generated — Java sees it as a direct public field. This is most useful for constants.

Backing field

Inside a custom accessor, the field keyword refers to the auto-generated backing field — it is how you read or write the stored value without triggering recursion:

var count: Int = 0
    set(value) {
        require(value >= 0)
        field = value   // 'field' is the backing field
    }

Interview Angles — 2.4

Q: What are platform types?

"Platform types — denoted Type! in error messages — are types that come from Java code with no nullability annotations. Kotlin cannot determine if they are nullable or non-null, so it makes no guarantee either way and skips null checks. They are the escape hatch in Kotlin's null safety system and the primary source of unexpected NullPointerException in Kotlin codebases that call into Java. There are two fixes: either add @Nullable or @NonNull annotations to the Java code so Kotlin sees a definite type, or defensively treat all unannotated Java return values as potentially null when you consume them in Kotlin."

Q: How can Java nullability cause Kotlin crashes?

"There are three scenarios. First, a platform type assigned to a non-null variable: val user: User = javaRepo.getUser() — if getUser() returns null, the Kotlin intrinsic null check at the assignment throws NullPointerException. Second, a platform type passed to a non-null parameter: processUser(javaRepo.getUser()) — the parameter's intrinsic check throws if the value is null. Third, a lying annotation: if Java annotates a method @NonNull but actually returns null, Kotlin treats the result as non-null and crashes at first use with no warning. The defense strategy is: annotate all Java APIs you own, treat unannotated Java returns as nullable in Kotlin, and use requireNotNull() with a meaningful message at lifecycle boundaries where you expect the value to be present."

Q: How do you expose Kotlin APIs cleanly to Java?

"There is a checklist I work through. First, @JvmStatic on companion object factory methods and constants, so Java callers write MyClass.create() instead of MyClass.Companion.create(). Second, @JvmOverloads on functions with default parameters, so Java sees a set of overloaded methods rather than one method with all parameters required. Third, @JvmField on public constants to expose them as direct fields. Fourth, @Throws(SomeException::class) on functions that propagate checked exceptions, so Java callers know they need to handle them. Fifth, avoid exposing suspend functions — instead expose LiveData, RxJava Observable or Single, or ListenableFuture. Sixth, avoid typealias in public APIs because Java sees the aliased type, not the alias name. Seventh, name is-prefixed Boolean properties carefully since Java sees isActive() and setActive(), which may not match expected conventions. And eighth, if you must expose the companion object itself to Java, give it a meaningful name like companion object Factory."
