9.1 Activity

Full Lifecycle: onCreate → onDestroy

An Activity's lifecycle is the set of callbacks the Android system invokes as it creates, runs, pauses, stops, and destroys the Activity. The thing that matters in an interview — and in production — is knowing exactly what each callback guarantees and what it does not, because getting that wrong is the source of almost every lifecycle bug.

         App launched
              │
         onCreate()        ← One-time setup: inflate layout, init ViewModel
              │
         onStart()         ← Activity becomes visible (not yet interactive)
              │
         onResume()        ← Activity is in foreground, user can interact
              │
         ┌───┴────────────────────────────────────────────────────┐
         │              Activity is running                       │
         └───┬────────────────────────────────────────────────────┘
              │
         onPause()         ← Partially obscured (dialog, multi-window), or leaving
              │
         onStop()          ← No longer visible
              │
     ┌────────┴───────────┐
     │                    │
onRestart()          onDestroy()       ← Finishing or system reclaim
     │
 onStart() ──► ...

onCreate(savedInstanceState: Bundle?)

  • Called once per Activity instance lifetime — when first created or after process death recreation.
  • Receives savedInstanceState: null on a fresh launch, non-null on recreation after a system kill or configuration change.
  • Do here: setContentView/Compose setup, ViewModel retrieval, binding observer setup, one-time initializations.
  • Do NOT do here: long operations, network calls on the main thread, or anything that requires the view to be measured or laid out — view sizes are 0 at this point.
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContentView(R.layout.activity_main)
    val viewModel: MyViewModel by viewModels()
    viewModel.uiState.observe(this) { state -> render(state) }
    // Safe: savedInstanceState?.getString("MY_KEY") to restore transient UI state
}

onStart()

  • Activity transitions from "stopped" to "visible but not yet in the foreground."
  • Called after onCreate and also after onRestart when returning from a stopped state.
  • The Activity can receive UI updates at this point, but the user cannot interact yet.
  • Typical use: re-register lightweight listeners that should only be active while the Activity is visible (e.g., a BroadcastReceiver for UI updates).

onResume()

  • Activity is at the top of the stack and fully interactive.
  • Called after onStart and also after returning from any partial-cover state — for example, after a dialog is dismissed.
  • Typical use: start animations, acquire camera or audio resources, resume media playback.
  • This is the steady state for a running Activity — the one it spends most of its time in.

onPause()

  • Called when the Activity is losing the foreground but may still be visible — for example, in multi-window mode, with a transparent dialog over it, or as a new Activity is starting.
  • Must be fast — the new Activity's onResume is not called until onPause returns, so any long work here causes the transition to stutter.
  • Typical use: save lightweight unsaved data (not heavy database writes), stop animations, release camera or audio resources that must not run in the background.
  • After onPause, the Activity may be killed by the system without onStop or onDestroy ever being called — a low-memory scenario that is rare in modern Android but worth knowing.

onStop()

  • Called when the Activity is no longer visible — either another Activity has fully covered it, or the user pressed Home.
  • Typical use: release resources not needed while invisible (heavy database writes, unregister receivers), stop location updates.
  • The Activity object is still alive in memory at this point and its state is preserved.
  • The system can kill the process after onStop without ever calling onDestroy.

onDestroy()

  • Called when the Activity is permanently finishing — either finish() was called or the system decided to reclaim it.
  • Also called on configuration changes such as rotation, before the new instance is created.
  • Not guaranteed during process death — the system kills the process without calling this.
  • Typical use: cancel coroutines not tied to a lifecycle scope, release any remaining resources. For anything that needs to survive configuration changes, use ViewModel instead.

onRestart()

  • Called only when an Activity is returning to the foreground after being stopped — not after being killed and recreated.
  • The path is: onStop → onRestart → onStart → onResume.

Configuration Changes

A configuration change is any change to the device environment that could require the Activity to rebuild its UI: screen rotation, locale change, font scale change, keyboard availability, dark/light mode toggle, or a screen size change from a multi-window resize.

Default behavior: The system destroys and recreates the Activity.

  1. onPause → onStop → onSaveInstanceState → onDestroy (old instance)
  2. onCreate(savedInstanceState) → onStart → onResume (new instance)

Key fact: ViewModel survives this destruction and recreation because it is stored in a ViewModelStore owned by the ViewModelStoreOwner — the Activity's backing store — which the framework passes across the configuration change via NonConfigurationInstance under the hood.

Handling configuration changes manually

You can tell the system to not recreate the Activity for certain config changes by declaring configChanges in the manifest:

<activity
    android:name=".MyActivity"
    android:configChanges="orientation|screenSize|keyboardHidden" />

Then override:

override fun onConfigurationChanged(newConfig: Configuration) {
    super.onConfigurationChanged(newConfig)
    // Manually handle the configuration change, e.g., update layout
    if (newConfig.orientation == Configuration.ORIENTATION_LANDSCAPE) {
        // adjust UI
    }
}

Trade-off: Handling config changes manually bypasses the standard lifecycle recreation, which means any layout that differs between orientations must be updated programmatically. That is fragile and hard to maintain. The better default is ViewModel plus saved instance state. Reserve configChanges for genuinely performance-sensitive cases — a video player that must not rebuffer on rotation is the classic example.

Lifecycle during rotation (the classic interview question)

User rotates device:
  Old instance: onPause → onStop → onSaveInstanceState → onDestroy
  New instance: onCreate(bundle) → onStart → onResume

ViewModel: NOT destroyed — survives the entire sequence.
savedInstanceState Bundle: saved before destroy, restored in new onCreate.

Process Death

The Android system can kill an app's process when memory is low. This happens after onStop is called on the visible Activity — the system never calls onDestroy. The process simply ceases to exist.

From the user's perspective: they can background the app, do memory-intensive work, then come back and expect to see the app in exactly the state they left it. That is Android's "apparent continuity" contract.

How Android restores:

  1. The system stores the Activity back stack — which Activities and Fragments were in which state — in a separate system process.
  2. When the user returns, the system recreates the top Activity (and the back stack) from that stored state.
  3. The Activity's onCreate is called with the saved Bundle.
  4. The ViewModel is NOT restored — it lived in the killed process. You must reinitialize it.
  5. SavedStateHandle in the ViewModel can survive process death, because the framework serializes it alongside the instance state.
class MyViewModel(
    private val savedStateHandle: SavedStateHandle
) : ViewModel() {
    // This value survives process death AND configuration changes
    var searchQuery: String
        get() = savedStateHandle["query"] ?: ""
        set(value) { savedStateHandle["query"] = value }
}

Saved Instance State

onSaveInstanceState(outState: Bundle) is called:

  • Before the Activity may be destroyed for a configuration change.
  • When the Activity is stopped and the system may kill the process — since Android 3.0+, this is called after onStop; before 3.0, it was called before onStop.

What to save: Small, serializable UI state — scroll position, selected tab, text field content, checked radio buttons, and so on.

What NOT to save: Large objects such as bitmaps or data lists, objects that hold a reference to the Activity context (that is a memory leak waiting to happen), or data that lives in a database or repository — that should be restored from the source of truth.

override fun onSaveInstanceState(outState: Bundle) {
    super.onSaveInstanceState(outState) // important: super saves view hierarchy state
    outState.putString("search_query", searchInput.text.toString())
    outState.putInt("selected_tab", currentTabIndex)
}

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    savedInstanceState?.let {
        searchInput.setText(it.getString("search_query"))
        currentTabIndex = it.getInt("selected_tab", 0)
    }
}

Bundle size limits: The Bundle is serialized via a Binder transaction, which has a total limit of roughly 1 MB. Storing large data in it causes a TransactionTooLargeException. Use the database or a file for anything large.

Bundle vs Database decision:

  • Bundle: ephemeral UI state that is only meaningful on the current screen — scroll position, form input, selected item. Cheap to serialize and small in size.
  • Database / Repository: persistent domain data that should survive app uninstall/reinstall cycles, is shared across screens, or is large. Restore it from the repository inside the ViewModel.

ViewModel

ViewModel is an Architecture Component designed to hold and manage UI-related data in a lifecycle-conscious way. It survives configuration changes but not process death — unless you are using SavedStateHandle, in which case the parts you put in the handle can survive both.

Internals: The ViewModelStore is retained by the NonConfigurationInstance mechanism in ComponentActivity. When a configuration change occurs, ActivityThread calls retainNonConfigurationInstances() before destroying the Activity, and passes the returned objects to the new instance.

class ProfileViewModel(
    private val savedStateHandle: SavedStateHandle,
    private val profileRepo: ProfileRepository
) : ViewModel() {
    
    // Survives both config change AND process death
    val userId: String = savedStateHandle.get<String>("userId") ?: ""
    
    private val _uiState = MutableStateFlow<ProfileUiState>(ProfileUiState.Loading)
    val uiState: StateFlow<ProfileUiState> = _uiState.asStateFlow()
    
    init {
        loadProfile()
    }
    
    private fun loadProfile() {
        viewModelScope.launch {
            try {
                _uiState.value = ProfileUiState.Success(profileRepo.getProfile(userId))
            } catch (e: Exception) {
                _uiState.value = ProfileUiState.Error(e.message ?: "Unknown error")
            }
        }
    }
    
    override fun onCleared() {
        super.onCleared()
        // viewModelScope is automatically cancelled — no need to cancel manually
    }
}

ViewModel vs savedInstanceState:

  • ViewModel: great for large data like lists and bitmaps, can hold non-serializable objects, cleared only when the user explicitly finishes the Activity.
  • savedInstanceState: serialized to disk, survives process death, but limited to roughly 50 KB of serializable data.
  • Best practice: combine both — the ViewModel holds the full data set, and savedInstanceState (via SavedStateHandle) holds just enough to re-query it after process death.

Back Stack

The task back stack is a stack of Activities maintained by the system. Each task has its own stack, and pressing the system Back button pops the top Activity and resumes the one beneath it.

  • startActivity(intent) pushes a new Activity onto the current task's back stack.
  • finish() pops the current Activity.
  • The home screen is a separate task; navigating to it moves your task to the background rather than destroying it.

Task affinity: Activities have a taskAffinity attribute that defaults to the app's package name. Activities with the same affinity are naturally grouped in the same task, and this interacts with certain launch modes.

Launch Modes

Launch modes control whether a new instance of an Activity is created when it is started, or whether an existing instance is reused. They can be declared in the manifest or set dynamically via Intent flags.

standard (default)

  • A new instance is created every time the Activity is started, even if an instance already exists in the stack.
  • Multiple instances of the same Activity can coexist in the stack at the same time.

singleTop

  • If the Activity is already at the top of the current task's back stack, no new instance is created — instead, onNewIntent(intent) is called on the existing instance.
  • If the Activity exists somewhere in the stack but is not at the top, a new instance is created.
  • Use case: notification target Activity, search Activity — avoids duplicates when the user taps a notification while the Activity is already open.
override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent) // important: update the intent so getIntent() returns the new one
    handleDeepLink(intent)
}

singleTask

  • Only one instance of this Activity exists in its task. If it already exists anywhere in the back stack, all Activities stacked on top of it are popped and onNewIntent is called on the existing instance.
  • Creates a new task if one does not already exist.
  • Use case: main or home screen of an app.
  • Gotcha: Activities on top of it are destroyed when it comes to the foreground, which can be surprising if you're not expecting it.

singleInstance

  • Like singleTask but more isolated: the Activity is the only Activity in its task, and any Activities it starts go into a different task.
  • Use case: system-level shared UIs such as a dialer or alarm screen. Rarely needed in typical apps.

Intent flags (runtime alternative to manifest modes)

Flag Effect
FLAG_ACTIVITY_NEW_TASKStart Activity in a new task (required from non-Activity contexts)
FLAG_ACTIVITY_CLEAR_TOPIf Activity already in stack, pop everything above it
FLAG_ACTIVITY_SINGLE_TOPSame as singleTop mode at runtime
FLAG_ACTIVITY_NO_HISTORYActivity is not added to back stack

// Useful for "go home and clear everything"
val intent = Intent(this, HomeActivity::class.java).apply {
    flags = Intent.FLAG_ACTIVITY_CLEAR_TASK or Intent.FLAG_ACTIVITY_NEW_TASK
}
startActivity(intent)

Deep Links

A deep link is an Intent that brings the user directly to a specific screen within your app from an external source — a notification, a web page, or another app.

Manifest declaration:

<activity android:name=".ProfileActivity">
    <intent-filter>
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <data
            android:scheme="myapp"
            android:host="profile"
            android:pathPrefix="/user" />
    </intent-filter>
</activity>

Handling in Activity:

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val uri: Uri? = intent.data
    if (uri != null) {
        val userId = uri.lastPathSegment
        // navigate to the correct screen
    }
}

Back stack for deep links: When a deep link launches your Activity, the back stack should contain a synthetic back stack so the user can navigate "up" naturally. Jetpack Navigation handles this automatically when you use <deepLink> declarations in the nav graph. If you are doing it manually, use TaskStackBuilder.

val deepLinkIntent = Intent(this, ProfileActivity::class.java).apply {
    data = uri
}
val stackBuilder = TaskStackBuilder.create(this).apply {
    addNextIntentWithParentStack(deepLinkIntent)
}
stackBuilder.startActivities()

Multi-Window

Android 7.0 and above support multi-window (split-screen) mode. In multi-window:

  • Both Activities can be visible simultaneously, but only one is resumed at a time — that is the pre-Android 10 behavior.
  • Android 10 and above: multiple Activities can be in the resumed state simultaneously, which is called multi-resume. This matters most for camera, audio, and other exclusive resources that you may need to share.

Lifecycle impact:

  • Entering split-screen triggers onPause if the Activity loses the top position, and onResume for the Activity that stays resumed (on Android 10+).
  • Resizing the window triggers a configuration change — similar to rotation — if screenSize is not listed in configChanges.
override fun onMultiWindowModeChanged(isInMultiWindowMode: Boolean, newConfig: Configuration) {
    super.onMultiWindowModeChanged(isInMultiWindowMode, newConfig)
    if (isInMultiWindowMode) {
        // release exclusive resources if needed
    }
}

Declaring support: Activities are multi-window-enabled by default. You can opt out with android:resizeableActivity="false", but that is not recommended.

Activity Result API

The Activity Result API is the modern replacement for the deprecated startActivityForResult/onActivityResult pattern. It is lifecycle-safe and uses a contract-based approach where you declare what you want upfront and get a typed result back.

// 1. Register the launcher in the Activity/Fragment (at class level, before lifecycle)
private val pickImageLauncher = registerForActivityResult(
    ActivityResultContracts.PickVisualMedia()
) { uri: Uri? ->
    if (uri != null) {
        imageView.setImageURI(uri)
    }
}

// 2. Launch when needed
fun onPickPhotoClicked() {
    pickImageLauncher.launch(
        PickVisualMediaRequest(ActivityResultContracts.PickVisualMedia.ImageOnly)
    )
}

Built-in contracts:

  • StartActivityForResult — generic, takes an Intent, returns an ActivityResult
  • RequestPermission / RequestMultiplePermissions
  • PickVisualMedia (Photo Picker)
  • TakePicture, TakeVideo
  • GetContent, OpenDocument, CreateDocument
  • StartIntentSenderForResult

Custom contract:

class MyContract : ActivityResultContract<String, Boolean>() {
    override fun createIntent(context: Context, input: String): Intent =
        Intent(context, MyActivity::class.java).apply { putExtra("key", input) }
    
    override fun parseResult(resultCode: Int, intent: Intent?): Boolean =
        resultCode == Activity.RESULT_OK
}

Why better than onActivityResult:

  • Input and output are type-safe via the contract.
  • The launcher can be registered before the Activity is fully started, decoupled from the lifecycle.
  • No more managing integer request codes.
  • Works cleanly with Fragments without any extra plumbing.

Activity Interview Angles

Q: Walk me through the Activity lifecycle during device rotation.

"When the user rotates the device, the system detects a configuration change and walks through a fixed sequence. On the old instance: onPause, then onStop, then onSaveInstanceState — since API 28 that's called after onStop — and then onDestroy. Then the new instance is created: onCreate with the bundle, onStart, onResume. The key thing to call out is that the ViewModel's onCleared is never called — the ViewModel survives the whole sequence completely intact. The Bundle carries the saved UI state. The ViewModel holds the data that is too large or not serializable to fit in a Bundle."

Q: What is the difference between a configuration change and process death?

"The two feel similar but they're quite different under the hood. With a configuration change, the system follows the normal lifecycle — onDestroy is called, but the ViewModel survives because it's held in a store that gets passed to the new instance. With process death, the system issues a SIGKILL — onDestroy is never called, and the ViewModel is gone because the entire process is gone. What both share is the Bundle: onSaveInstanceState was called while the Activity was alive, so that Bundle exists for both cases. The difference is what you do with it — after a config change the ViewModel already has your data, so the Bundle is mostly a cross-check; after process death, you need to use SavedStateHandle in the ViewModel or re-query from your repository in onCreate."

Q: What should go in Bundle vs in the database?

"The rule I follow is: Bundle for ephemeral UI state, database or repository for everything else. Ephemeral UI state means things that are only meaningful on this screen right now — scroll position, form text, which tab is selected, whether a dialog was open. It's transient, screen-specific, and cheap to serialize. The other bucket is persistent domain data — user profiles, search results, appointments. That data has a canonical home in the database or a remote API, it may be needed by multiple screens, and it's often too large for a Bundle. The practical reason the size limit matters is that the Bundle goes over a Binder transaction, which has a total cap of roughly 1 MB — put a large list in there and you'll get a TransactionTooLargeException."

Q: Why is onDestroy() not guaranteed for process death?

"The system kills the process at the OS level with a SIGKILL signal when memory is critical. At that point there is no opportunity to call any Java or Kotlin methods — the process just stops. onDestroy is only called when the system follows the normal lifecycle: an explicit finish(), a configuration change, or a controlled shutdown. That's why critical state has to be saved in onStop or earlier — onSaveInstanceState is called while the process is still alive. Any cleanup that lives only in onDestroy is fine for non-critical resource release, but you can never rely on it for data integrity."

9.2 Fragment

Fragment Lifecycle

A Fragment has its own lifecycle that is coupled to — but distinct from — its host Activity. The key word is "distinct": a Fragment's lifecycle has more phases than an Activity's, and getting them confused is one of the most common sources of Android bugs. Each Fragment instance goes through these callbacks:

onAttach(context)       ← Fragment associated with Activity; safe to access Context
    │
onCreate(savedState)    ← Initialize non-view resources; do NOT access views
    │
onCreateView(...)       ← Inflate/create the Fragment's view hierarchy; return root view
    │
onViewCreated(view, ...) ← View hierarchy created; safe to find/bind views
    │
onViewStateRestored(...) ← Restore state from savedInstanceState
    │
onStart()               ← Fragment becomes visible
    │
onResume()              ← Fragment is interactive
    │
[Fragment active]
    │
onPause()               ← Fragment loses foreground
    │
onStop()                ← Fragment no longer visible
    │
onSaveInstanceState()   ← Save UI state
    │
onDestroyView()         ← View hierarchy being destroyed; CLEAR view binding here
    │
onDestroy()             ← Fragment instance being destroyed
    │
onDetach()              ← Fragment disassociated from Activity

Key insight: onCreateView and onDestroyView can be called multiple times on the same Fragment instance — for example, when a Fragment is placed on the back stack its view is destroyed, but the Fragment object itself lives on. onCreate and onDestroy, by contrast, happen exactly once per Fragment instance lifetime.

View Lifecycle vs Fragment Lifecycle

This is one of the most important distinctions in Android development and a very common interview topic.

Fragment lifecycle: tied to the Fragment instance. The Fragment object can exist long after its view is destroyed — that happens whenever the Fragment is on the back stack.

View lifecycle (viewLifecycleOwner): tied specifically to the Fragment's view. It starts in onCreateView and ends in onDestroyView.

Fragment instance lifetime:  onAttach ──────────────────────────────────────── onDetach
Fragment view lifetime:                 onCreateView ──── onDestroyView
                                         (repeated every time fragment returns to foreground)

Practical consequence: If you observe a LiveData or collect a Flow using this — the Fragment as LifecycleOwner — the observer lives until the Fragment is destroyed. If the Fragment goes to the back stack and comes back, a new view is created but the old observer is not re-registered because it never died. This seems harmless at first, but if that observer references a view directly, you now have a stale reference to a destroyed view — a use-after-free bug on a destroyed view hierarchy.

The fix: Always use viewLifecycleOwner when observing data that needs to update the UI:

// WRONG — observer may reference destroyed views, or may register duplicate observers
viewModel.uiState.observe(this) { state -> render(state) }

// CORRECT — observer is tied to the view's lifecycle
viewModel.uiState.observe(viewLifecycleOwner) { state -> render(state) }

viewLifecycleOwner

viewLifecycleOwner is a LifecycleOwner that mirrors the lifecycle of the Fragment's view, running from onCreateView through to onDestroyView.

When to use this vs viewLifecycleOwner:

  • this (the Fragment as LifecycleOwner): for operations that should survive view destruction — loading data, non-UI work.
  • viewLifecycleOwner: for everything that interacts with views — observing LiveData or Flow for UI updates, registering view-bound callbacks.

In Compose fragments: If the Fragment hosts a ComposeView, use viewLifecycleOwner.lifecycleScope to launch coroutines that collect flows for Compose:

viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state -> /* update Compose */ }
    }
}

Fragment Transactions

Fragment transactions are operations that add, remove, replace, or show and hide Fragments. They are batched together and committed atomically, which means either all operations in the transaction happen or none of them do.

supportFragmentManager.commit {
    setCustomAnimations(R.anim.slide_in, R.anim.slide_out, R.anim.slide_in, R.anim.slide_out)
    replace(R.id.container, DetailFragment.newInstance(id), "detail_tag")
    addToBackStack("detail") // null = anonymous, named = can pop to by name
}

Transaction operations:

  • add: Adds a Fragment to the container; any existing Fragments stay in place.
  • remove: Removes a Fragment; onDestroyView and onDestroy are called.
  • replace: Removes all existing Fragments in the container and adds the new one.
  • hide/show: Hides or shows a Fragment without triggering lifecycle callbacks; the view stays in the hierarchy.
  • detach/attach: Detaches (destroys the view but the Fragment instance lives on) and attaches (recreates the view).

Pending transactions: Transactions are not immediately executed — they are scheduled on the main thread's message queue. Use executePendingTransactions() to force immediate, synchronous execution on the main thread. Never call this from a background thread.

Fragment Back Stack

addToBackStack(name) records the transaction on the Fragment back stack. Pressing Back reverses it — restoring the previous state.

// Add to back stack — Back press will reverse this replace
fragmentManager.commit {
    replace(R.id.container, DetailFragment())
    addToBackStack("detail")
}

// Pop back stack programmatically
fragmentManager.popBackStack()                          // async
fragmentManager.popBackStackImmediate()                 // sync (main thread)
fragmentManager.popBackStack("detail", 0)              // pop to "detail" inclusive
fragmentManager.popBackStack("detail", FragmentManager.POP_BACK_STACK_INCLUSIVE) // pop "detail" too

Gotcha: If you call replace without addToBackStack, the replaced Fragment is destroyed and its instance is gone — pressing Back will not bring it back. With addToBackStack, the Fragment's view is destroyed but the instance is retained, so Back can restore it.

Navigation Component

Jetpack Navigation abstracts Fragment transactions into a graph-based navigation system, so you navigate by destination rather than by manually writing replace/add transactions.

// Navigate
findNavController().navigate(R.id.action_home_to_detail, bundleOf("userId" to id))

// Navigate with NavDirections (type-safe, requires Safe Args plugin)
val action = HomeFragmentDirections.actionHomeToDetail(userId = id)
findNavController().navigate(action)

// Navigate up
findNavController().navigateUp()

// Pop to a destination
findNavController().popBackStack(R.id.homeFragment, inclusive = false)

Benefits over manual transactions:

  • Type-safe argument passing with Safe Args.
  • Deep links handled automatically via <deepLink> declarations in the nav graph.
  • Back stack managed automatically — no manual addToBackStack calls.
  • Transition animations declared in the graph.
  • Visual editor in Android Studio for seeing the whole flow at a glance.

NavHostFragment: The Fragment that hosts the navigation graph. Declared in the layout:

<FragmentContainerView
    android:name="androidx.navigation.fragment.NavHostFragment"
    app:navGraph="@navigation/nav_graph"
    app:defaultNavHost="true" />

View Binding Cleanup

The problem: View binding references (and findViewById references) hold a strong reference to views. Views are destroyed in onDestroyView, but the Fragment instance may live on in the back stack. If the binding property is not cleared, the old destroyed view hierarchy is held in memory — a memory leak.

The solution: Always null out the binding reference in onDestroyView.

class MyFragment : Fragment(R.layout.fragment_my) {
    
    private var _binding: FragmentMyBinding? = null
    private val binding get() = _binding!! // safe to use only between onCreateView and onDestroyView
    
    override fun onCreateView(
        inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?
    ): View {
        _binding = FragmentMyBinding.inflate(inflater, container, false)
        return binding.root
    }
    
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        binding.button.setOnClickListener { /* ... */ }
    }
    
    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null // CRITICAL: prevents memory leak
    }
}

Why this is a leak: The Fragment instance — which holds _binding — is retained on the back stack. The _binding field holds a reference to the now-destroyed view hierarchy, including all View objects and their Context. That chain of references prevents the garbage collector from reclaiming any of those views.

Fragment Result API

The Fragment Result API is the modern way for Fragments to communicate results back to their parent or sibling Fragments, without requiring direct Fragment-to-Fragment references or casting the parent as an interface.

// In the child Fragment (sender)
setFragmentResult("requestKey", bundleOf("selected_date" to date))

// In the parent Fragment (receiver) — registered in onCreate or onViewCreated
setFragmentResultListener("requestKey") { key, bundle ->
    val date = bundle.getString("selected_date")
    // handle result
}

Key properties:

  • Results are delivered to the listener when the receiving Fragment is at least in the STARTED state.
  • If the Fragment is not started when the result is set, the result is held and delivered once it becomes STARTED.
  • Only one active listener per key — the last registered listener wins.
  • Works between a child and its parent by using childFragmentManager on the parent side.

Alternative (legacy pattern): interface callbacks from Fragment to Activity or parent Fragment. This is fragile because it requires casting and creates tight coupling between the two.

Child Fragments

A Fragment can host its own childFragmentManager to manage nested Fragments. This is the right approach for view pagers, tab layouts inside a Fragment, and any case where you need modular, reusable screen segments.

class TabContainerFragment : Fragment() {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        childFragmentManager.commit {
            replace(R.id.tab_container, FirstTabFragment())
        }
    }
}

Gotchas with child fragments:

  • Always use childFragmentManager for Fragments nested inside a Fragment — never supportFragmentManager, which attaches to the Activity's manager and breaks the lifecycle hierarchy.
  • A DialogFragment shown from inside a Fragment should use show(childFragmentManager, tag).
  • The system Back button does not automatically pop childFragmentManager. You must manually intercept Back and call childFragmentManager.popBackStack(), or wire it up through OnBackPressedDispatcher.

commit vs commitNow

commit(): Schedules the transaction asynchronously on the main thread's message queue. The actual transaction executes on the next frame or message dispatch.

commitNow(): Executes the transaction immediately on the calling thread, which must be the main thread. Does NOT work with addToBackStack — it throws IllegalStateException if you try.

commitAllowingStateLoss(): Behaves like commit() but suppresses the IllegalStateException that occurs when the Activity's state has already been saved — that is, after onSaveInstanceState. Use with caution: if the Activity is killed after a state loss, your transaction will not be restored.

// Typical — async, safe
fragmentManager.commit { replace(R.id.container, SomeFragment()) }

// Immediate execution — no back stack possible
fragmentManager.commitNow { replace(R.id.container, SomeFragment()) }

// After onSaveInstanceState (e.g., from a callback) — UI inconsistency risk
fragmentManager.commitAllowingStateLoss { replace(R.id.container, SomeFragment()) }

When to use commitNow: When subsequent code in the same method depends on the transaction having already completed — for example, you immediately find the new Fragment by tag. This is rare; most cases do not need synchronous execution.

Fragment Interview Angles

Q: Fragment lifecycle vs view lifecycle — why does it matter?

"The Fragment instance can outlive its views when it is on the back stack. If I observe LiveData or collect a Flow using this — the Fragment as LifecycleOwner — those observers are tied to the Fragment's lifetime, not the view's. When the Fragment goes to the back stack and comes back, a brand-new view is created but the observer is never re-registered because it never died. And if that observer references view objects directly, it is now pointing at destroyed views. The fix is to always use viewLifecycleOwner for anything that touches UI — that ensures each observer is created fresh with the new view and torn down with it."

Q: Why clear binding in onDestroyView()?

"The Fragment instance lives on in the back stack, but the view hierarchy is destroyed. If I don't null out _binding, the binding field is still holding a reference to all those destroyed View objects and their Context. That chain of references prevents garbage collection of the entire view tree — all the Drawables, bitmaps, and whatever else the views were holding on to. The _binding = null in onDestroyView is the idiomatic way to break that reference and let the GC do its job."

Q: Common Fragment memory leaks.

  1. Not clearing view binding in onDestroyView.
  2. Using this instead of viewLifecycleOwner for LiveData observers.
  3. Storing a reference to the Activity or Fragment in a companion object or static field.
  4. Registering callbacks — for example, ViewPager2.registerOnPageChangeCallback — without unregistering them in onDestroyView.
  5. Passing this (the Fragment) as a listener to a view that outlives the Fragment.
  6. Child Fragments holding a strong reference back to the parent via parentFragment.

Q: commit vs commitNow.

"commit() is asynchronous — it gets scheduled on the main thread's message queue, and it works fine with addToBackStack. commitNow() is synchronous — it executes immediately on the calling thread, but it cannot be combined with addToBackStack at all. The rule is: use commit() by default, and only reach for commitNow() when the code immediately following depends on the transaction having already completed."

9.3 Services

Started Service

A started Service is launched by startService(intent) or startForegroundService(intent) and runs independently of the caller. Even if the starting component is destroyed, the service keeps running until it stops itself or is stopped externally.

// Start
startService(Intent(this, DownloadService::class.java).apply {
    putExtra("url", downloadUrl)
})

// Stop from outside
stopService(Intent(this, DownloadService::class.java))

// Stop itself (preferred)
class DownloadService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val url = intent?.getStringExtra("url") ?: return START_NOT_STICKY
        serviceScope.launch {
            download(url)
            stopSelf(startId) // stops only if no new starts have come in
        }
        return START_REDELIVER_INTENT
    }
    override fun onBind(intent: Intent?): IBinder? = null
}

Bound Service

A bound Service is connected to by one or more clients via bindService(intent, connection, flags). It lives as long as at least one client is bound — when all clients unbind, the service is destroyed, unless it was also started independently.

class MusicService : Service() {
    inner class MusicBinder : Binder() {
        fun getService(): MusicService = this@MusicService
    }
    private val binder = MusicBinder()
    override fun onBind(intent: Intent?): IBinder = binder
    fun play(songId: String) { /* ... */ }
}

// In Activity
private var musicService: MusicService? = null
private val connection = object : ServiceConnection {
    override fun onServiceConnected(name: ComponentName?, service: IBinder?) {
        val binder = service as MusicService.MusicBinder
        musicService = binder.getService()
    }
    override fun onServiceDisconnected(name: ComponentName?) {
        musicService = null
    }
}

override fun onStart() {
    super.onStart()
    bindService(Intent(this, MusicService::class.java), connection, Context.BIND_AUTO_CREATE)
}

override fun onStop() {
    super.onStop()
    unbindService(connection)
    musicService = null
}

Cross-process binding: For services running in different processes, use AIDL (Android Interface Definition Language) or Messenger to communicate across the process boundary.

Foreground Service

A foreground Service performs work that is noticeable to the user and must show a persistent notification while it runs. It has elevated priority and is much less likely to be killed by the system than a background service.

Required since Android 8.0 (API 26):

  • Must call startForeground(notificationId, notification) within 5 seconds of being started, or the system will crash the app.
  • The caller must use startForegroundService() instead of startService().
class LocationService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = buildNotification()
        startForeground(NOTIFICATION_ID, notification)
        startLocationUpdates()
        return START_STICKY
    }
    
    private fun buildNotification() = NotificationCompat.Builder(this, CHANNEL_ID)
        .setContentTitle("Tracking your location")
        .setSmallIcon(R.drawable.ic_location)
        .setOngoing(true)
        .build()
    
    override fun onBind(intent: Intent?): IBinder? = null
}

Android 14+ foreground service types: You must declare foregroundServiceType in the manifest and request the appropriate type-specific permissions:

<service
    android:name=".LocationService"
    android:foregroundServiceType="location" />

Available types: camera, connectedDevice, dataSync, health, location, mediaPlayback, mediaProjection, microphone, phoneCall, remoteMessaging, shortService, specialUse, systemExempted.

Background Service Restrictions

Android 8.0 (API 26) introduced severe restrictions on background Services:

  • Apps in the background — meaning they have no visible Activity — cannot start background services. Calling startService() in that state throws IllegalStateException.
  • The solution is to use startForegroundService() for work that genuinely needs to be a Service, or WorkManager for deferrable background work.
  • The system will kill background services aggressively to reclaim memory.

Android 12+ (API 31): Exact alarm restrictions. Apps must request the SCHEDULE_EXACT_ALARM permission. Android 13+ (API 33): Posting notifications requires the POST_NOTIFICATIONS permission. Android 14+ (API 34): Further restrictions on starting foreground services from the background.

Service Lifecycle

Started service lifecycle:

startService() / startForegroundService()
    │
onCreate()       ← called once; initialize resources
    │
onStartCommand() ← called for every startService() call
    │
[Service running]
    │
stopSelf() / stopService()
    │
onDestroy()      ← cleanup

Bound service lifecycle:

bindService()
    │
onCreate()
    │
onBind()         ← return IBinder
    │
[Clients connected]
    │
onUnbind()       ← called when last client unbinds; override to allow re-binding
    │
onDestroy()

Combined (started + bound): The service stays alive until it has been both stopped and unbound — both conditions must be satisfied.

onStartCommand and Return Values

onStartCommand(intent: Intent?, flags: Int, startId: Int): Int

  • Called on the main thread for every startService() call.
  • intent: the Intent passed to startService(). Can be null if the system recreates the service after a kill with START_STICKY.
  • flags: START_FLAG_RETRY if a previous start attempt failed, or START_FLAG_REDELIVERY for redelivered intents from START_REDELIVER_INTENT.
  • startId: a unique identifier for this specific start request. Pass it to stopSelf(startId) to avoid stopping the service prematurely if multiple starts have come in.

Return values:

Constant Behavior after system kill
START_NOT_STICKYService is NOT recreated. Good for tasks where data can be re-fetched later.
START_STICKYService IS recreated, but intent will be null. Good for ongoing services that do not depend on the original intent.
START_REDELIVER_INTENTService IS recreated with the last Intent redelivered. Good for download/upload tasks where the intent carries the work spec.
override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
    when (intent?.action) {
        ACTION_DOWNLOAD -> startDownload(intent.getStringExtra("url"))
        ACTION_CANCEL -> cancelDownload()
    }
    return START_REDELIVER_INTENT // safe: if killed mid-download, redelivers URL
}

Service vs WorkManager

This is one of the most common design-decision questions in Android interviews, and the answer is not "always use WorkManager."

Concern Service WorkManager
Battery optimizationCan drain battery; bypasses Doze by defaultRespects Doze, battery saver, device idle
Persistence across rebootsNo (by default)Yes (WorkInfo is persisted to DB)
Guaranteed executionNot guaranteed (can be killed)Guaranteed (retried with backoff)

Chaining / sequencingManualWorkContinuation chains
CancellationstopService()workManager.cancelWorkById(id)
ObservabilityManual (broadcast, etc.)LiveData<WorkInfo> / Flow<WorkInfo>

Use Service when: work must run right now, potentially indefinitely, and the user should be aware of it via a foreground service notification. Examples: music playback, VoIP, live location sharing.

Use WorkManager when: work can be deferred, must survive process death and device reboots, depends on constraints like waiting for Wi-Fi, or is a one-shot or periodic background task. Examples: syncing the database, uploading photos, sending analytics.

When to run in another process: declare android:process=":myservice" in the manifest. There are three reasons to do this — first, crash isolation: a crash in the service process won't kill the main app process. Second, a separate memory budget so the service doesn't push the main app out of memory. Third, enforcing architectural separation. The downsides are IPC overhead for every call and the fact that you cannot share in-memory singletons across processes.

Services Interview Angles

Q: Service vs WorkManager — when do you choose each?

"The question is really: does this work need to happen right now, and does the user need to know about it? If yes — music playback, VoIP, live location — that's a foreground Service. If the work is deferrable, needs to survive process death and device reboots, or depends on constraints like waiting for Wi-Fi, that's WorkManager. And for Android 8.0 and above, background Services are so heavily restricted that WorkManager is the right default for almost any background task that doesn't need to be immediate."

Q: Started vs bound service.

"There are two fundamental shapes a Service can take. A started Service runs independently — you fire it off with startService and it keeps going until it stops itself or you call stopService. There's no ongoing connection; it's fire-and-forget. A bound Service is different — it exposes an IBinder interface and lives only as long as at least one client is bound to it. When all clients unbind, it gets destroyed. The interesting case is when you combine them: a Service that is both started and bound will outlive its clients and only die when it's stopped. Use started for work that needs to run to completion; use bound for any situation where you need a live client-server interaction, either within the same process or across processes."

Q: Foreground service restrictions.

"There are several layers here. At the basics: the service must show a persistent notification and must call startForeground() within 5 seconds of being started or the system crashes it. Since Android 14, you also must declare foregroundServiceType in the manifest — for example, location, camera, mediaPlayback — and you must hold the appropriate permissions for that type. And since Android 12, apps generally cannot start foreground services from the background at all; the main exemption is high-priority FCM notifications, which can grant a brief window to start a foreground service."

9.4 BroadcastReceiver

A BroadcastReceiver responds to system-wide or app-specific broadcast messages delivered as Intents. The defining constraint is that it has a very short execution window — roughly 10 seconds on the main thread — and the process may be killed immediately after onReceive() returns.

Manifest-Registered vs Context-Registered

Manifest-registered (static receiver):

  • Declared in AndroidManifest.xml.
  • The app does not need to be running to receive the broadcast — the system can launch it just to deliver the Intent.
  • Since Android 8.0 (API 26): cannot receive most implicit broadcasts via manifest declaration, due to background execution limits. Only a small set of system broadcasts are exempt — and even ACTION_BOOT_COMPLETED has its own restrictions on newer APIs.
<receiver android:name=".BootReceiver" android:exported="false">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>

Context-registered (dynamic receiver):

  • Registered in code via context.registerReceiver(receiver, intentFilter).
  • Active only while the registering component — Activity, Service — is alive.
  • Not affected by the Android 8.0 implicit broadcast restrictions.
  • Must be unregistered in the matching lifecycle callback to avoid leaks — register in onStart, unregister in onStop.
private val networkReceiver = object : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        updateNetworkStatus()
    }
}

override fun onStart() {
    super.onStart()
    registerReceiver(
        networkReceiver,
        IntentFilter(ConnectivityManager.CONNECTIVITY_ACTION),
        RECEIVER_NOT_EXPORTED // API 33+ requirement for non-exported receivers
    )
}

override fun onStop() {
    super.onStop()
    unregisterReceiver(networkReceiver)
}

Ordered Broadcasts

Normal broadcasts are delivered to all receivers asynchronously, in no guaranteed order, potentially concurrently. Ordered broadcasts are different — they are delivered to one receiver at a time, in priority order.

  • Each receiver can call setResult*() to pass data along to the next receiver in the chain.
  • A receiver can call abortBroadcast() to prevent delivery to any lower-priority receivers.
  • They are sent via sendOrderedBroadcast(intent, receiverPermission).
sendOrderedBroadcast(intent, null) // null = no permission restriction

// In a receiver (highest priority processes first)
override fun onReceive(context: Context, intent: Intent) {
    val previousResult = resultData
    setResultData("processed_$previousResult")
    // abortBroadcast() // would stop propagation
}

Use case: In-app notification interception, where a foreground Activity intercepts a notification broadcast before it reaches the notification manager. Rarely needed in modern apps.

Explicit vs Implicit Broadcasts

Implicit broadcast: The Intent specifies an action but no specific component. Any registered receiver with a matching intent filter can receive it. Examples include ACTION_BATTERY_LOW and ACTION_AIRPLANE_MODE_CHANGED.

Explicit broadcast: Targets a specific component by package and class name. Because it is explicit, it bypasses the Android 8.0 restrictions:

// Explicit — bypasses Android 8.0+ restrictions
val intent = Intent(this, MyReceiver::class.java).apply {
    action = "com.example.MY_ACTION"
}
sendBroadcast(intent)

// To send to another app explicitly
val intent = Intent().apply {
    setClassName("com.other.app", "com.other.app.MyReceiver")
    action = "com.other.app.MY_ACTION"
}
sendBroadcast(intent)

Security: implicit broadcasts sent without a permission can be received by any app that has a matching intent filter. For sensitive data, there are three options — first, sendBroadcast(intent, permission), which restricts delivery to receivers that hold the specified permission. Second, an in-process alternative like SharedFlow (or the deprecated LocalBroadcastManager). Third, an explicit broadcast that targets a specific package.

Background Execution Limits

Android 8.0 prohibits apps from registering receivers for most implicit broadcasts in the manifest. The motivation is that apps were being woken up by system broadcasts they did not actually need, which was a significant source of battery drain.

Exempted broadcasts (can still be registered in the manifest):

  • ACTION_BOOT_COMPLETED — though it has its own restrictions on newer APIs
  • ACTION_LOCKED_BOOT_COMPLETED
  • ACTION_MY_PACKAGE_REPLACED
  • ACTION_PACKAGE_REPLACED (for self)
  • CONNECTIVITY_CHANGE is no longer exempt

Migration path for apps targeting Android 8.0+:

  • Replace CONNECTIVITY_CHANGE receivers with JobScheduler or WorkManager using network constraints.
  • Replace polling via broadcasts with FCM for remote triggers.
  • Use context-registered receivers for anything that only needs to work at runtime.

Short Execution and Follow-Up Work

onReceive() runs on the main thread with a hard execution time limit of approximately 10 seconds — exceed that and the app will ANR. After onReceive() returns, the BroadcastReceiver is considered dead and the system may kill the process immediately.

You cannot:

  • Launch an async coroutine and expect it to keep running after onReceive() returns — the process may die before it gets a chance to run.
  • Start a background thread and rely on it completing.
  • Bind to a Service from onReceive() and use it asynchronously.

You can:

  • Do fast, synchronous work.
  • Update SharedPreferences.
  • Post a notification.
  • Schedule follow-up work with WorkManager.
  • Start a Service — a foreground service, if the context is a foreground context.
  • Use goAsync() to get a PendingResult that extends the deadline to roughly 30 seconds; but this is still not truly asynchronous — you must call pendingResult.finish() or the system will eventually ANR anyway.
// Pattern 1: Schedule work with WorkManager
override fun onReceive(context: Context, intent: Intent) {
    val workRequest = OneTimeWorkRequestBuilder<SyncWorker>().build()
    WorkManager.getInstance(context).enqueue(workRequest)
}

// Pattern 2: goAsync() for slightly longer synchronous work
override fun onReceive(context: Context, intent: Intent) {
    val pendingResult = goAsync()
    CoroutineScope(Dispatchers.Default).launch {
        try {
            doQuickWork()
        } finally {
            pendingResult.finish() // MUST call or ANR
        }
    }
}

BroadcastReceiver Interview Angles

Q: Why should BroadcastReceiver work be short?

"There are two reasons. First, onReceive() runs on the main thread — if it takes more than roughly 10 seconds the system raises an ANR. Second, and this is the sneaky one: after onReceive() returns, the process has no active components left, so the system may kill it immediately. Any background threads you started in onReceive() will die with it. There is no lifecycle object protecting them. So the rule is: do only the minimum in onReceive(), then hand off to something with a lifecycle — WorkManager, a foreground Service, or goAsync() if you need a short extension."

Q: How do you continue work after receiving a broadcast?

"There are three options depending on the urgency and duration of the work. For deferrable background work — syncing data, uploading something — use WorkManager. It persists across process death, respects battery constraints, and will retry if it fails. If the work must start immediately and the user should be aware of it, start a foreground Service. And for work that just barely exceeds the 10-second window but is still short — say, up to about 30 seconds — you can call goAsync() to get a PendingResult that keeps the process alive, do the work on a coroutine, and call pendingResult.finish() when done. Skip that last call and you'll ANR."

Q: Static vs dynamic receiver.

"Static receivers — manifest-registered — have the advantage that the app doesn't need to be running to receive the broadcast. But since Android 8.0 they're restricted to explicit broadcasts and a small whitelist of implicit ones. Dynamic receivers — context-registered — are not subject to that restriction but they're only alive while the registering component is alive. The rule I follow: use dynamic receivers for things that should only matter while the app is in the foreground, and static receivers for app startup or self-targeted explicit broadcasts."

9.5 ContentProvider

A ContentProvider is an Android component that provides structured, URI-addressed access to data, enabling data sharing across application boundaries with fine-grained permission control. It is the standard mechanism for apps to expose data to other apps or to the system.

Cross-App Data Sharing

ContentProvider is the standard mechanism for one app to expose its data to another app or to the system. The system's contacts, media store, and calendar are all ContentProviders.

Why not just use a file? There are four reasons. First, a ContentProvider enforces permission checks on every access — not just when the file is first opened. Second, it provides a uniform SQL-like query interface that callers already know how to use. Third, it allows granting temporary URI-level permissions to specific apps without giving broad file system access. Fourth, the Cursor-based streaming model avoids loading large data sets into memory all at once.

URI-Based Access and ContentResolver

Every piece of data in a ContentProvider is addressed by a Uri:

content://com.example.app.provider/users/42
           └─────── authority ──────┘ └─ path ┘
  • Scheme: always content://
  • Authority: unique identifier for the ContentProvider, typically the package name plus .provider
  • Path: identifies the type of data and optionally a specific record by ID

ContentResolver is the client-side API for accessing ContentProviders. It routes calls to the correct provider process transparently, whether that provider is in the same app or another app entirely.

val contentResolver = context.contentResolver

// Query
val cursor = contentResolver.query(
    Uri.parse("content://com.example.app.provider/users"),
    arrayOf("_id", "name", "email"), // projection (columns)
    "age > ?",                       // selection
    arrayOf("18"),                   // selectionArgs
    "name ASC"                       // sortOrder
)

// Insert
val values = ContentValues().apply {
    put("name", "Alice")
    put("email", "alice@example.com")
}
val newUri = contentResolver.insert(
    Uri.parse("content://com.example.app.provider/users"),
    values
)

// Update
val rowsUpdated = contentResolver.update(uri, values, null, null)

// Delete
val rowsDeleted = contentResolver.delete(uri, "_id = ?", arrayOf("42"))

MIME Types

ContentProviders must return MIME types for their data so that clients know how to interpret what they receive.

override fun getType(uri: Uri): String? {
    return when (uriMatcher.match(uri)) {
        USERS -> "vnd.android.cursor.dir/vnd.com.example.app.user"   // collection
        USER_ID -> "vnd.android.cursor.item/vnd.com.example.app.user" // single item
        else -> throw IllegalArgumentException("Unknown URI: $uri")
    }
}

Convention:

  • Collection (multiple rows): vnd.android.cursor.dir/vnd.<authority>.<type>
  • Single item: vnd.android.cursor.item/vnd.<authority>.<type>
  • File-based: standard MIME types such as image/jpeg or application/pdf

ContentProvider Permissions

Permissions are the primary mechanism for controlling who can access your ContentProvider:

<provider
    android:name=".MyContentProvider"
    android:authorities="com.example.app.provider"
    android:exported="true"
    android:readPermission="com.example.app.permission.READ"
    android:writePermission="com.example.app.permission.WRITE">
</provider>

URI permissions: Grant temporary access to a specific URI to another app without requiring that app to hold the broad provider permission:

// Grant read permission to the receiving app for a specific URI
val intent = Intent(Intent.ACTION_VIEW).apply {
    data = photoUri
    addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
}
startActivity(intent)

The receiving app can access that specific URI until the task ends or you call revokeUriPermission to revoke it early.

Cursor

Cursor is the object returned by ContentResolver.query() — a pointer into a row set that you iterate over, one row at a time.

cursor?.use { c ->
    if (c.moveToFirst()) {
        do {
            val id = c.getLong(c.getColumnIndexOrThrow("_id"))
            val name = c.getString(c.getColumnIndexOrThrow("name"))
            results.add(User(id, name))
        } while (c.moveToNext())
    }
}
// cursor.use{} automatically closes it — never forget to close!

Cursor operations:

  • moveToFirst(), moveToNext(), moveToPrevious(), moveToLast(), moveToPosition(n)
  • getColumnIndex("name") — returns -1 if the column is not found; use getColumnIndexOrThrow if you want an exception instead of a silent -1
  • getString, getInt, getLong, getFloat, getBlob
  • isNull(columnIndex) — check for null before reading to avoid unexpected crashes

Memory: Cursors backed by SQLite are lazy — data is fetched row by row as you iterate. Close cursors promptly to release the underlying SQLite statement and free resources. The idiomatic Kotlin way is cursor.use {}, which closes it automatically even if an exception is thrown.

FileProvider

FileProvider is a specialized ContentProvider that grants temporary access to files in your app's private storage to other apps, replacing direct file:// URIs which are dangerous and now blocked.

Why: Since Android 7.0 (API 24), the system blocks file:// URIs in Intents between apps and throws a FileUriExposedException. Apps must instead use content:// URIs generated by FileProvider, which applies permission checks and grants only the specific URI requested.

Setup:

  1. Declare in manifest:
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_provider_paths" />
</provider>
  1. Define paths in res/xml/file_provider_paths.xml:
<paths>
    <files-path name="images" path="images/" />
    <cache-path name="camera" path="camera_photos/" />
    <external-files-path name="downloads" path="Downloads/" />
</paths>
  1. Use in code:
val file = File(context.cacheDir, "camera_photos/photo.jpg")
val uri = FileProvider.getUriForFile(
    context,
    "${context.packageName}.fileprovider",
    file
)
val intent = Intent(MediaStore.ACTION_IMAGE_CAPTURE).apply {
    putExtra(MediaStore.EXTRA_OUTPUT, uri)
    addFlags(Intent.FLAG_GRANT_WRITE_URI_PERMISSION)
}
startActivity(intent)

ContentProvider Interview Angles

Q: When would you use a ContentProvider?

"There are three situations where a ContentProvider makes sense. First, when you need to expose structured data to other apps or to the system — for example, making your app's contact data readable by the system contacts app. Second, when you need fine-grained URI-level permission grants to share individual files with other apps, which is what FileProvider does. Third, when you want a uniform data access interface within your own app and need ContentObserver for reactive change notifications. Outside of those cases, for internal-only data, a Room database accessed through a repository is simpler and more idiomatic."

Q: Why use FileProvider instead of a file URI?

"file:// URIs expose your app's internal storage path directly to other apps. Since Android 7.0 the system blocks them outright with a FileUriExposedException. FileProvider generates content:// URIs instead and applies a permission check on every access. The receiving app gets access to only the specific URI you grant — not broad access to your file system — and it does not need READ_EXTERNAL_STORAGE to receive it. So it's both more secure and more compatible."

Q: How do permissions apply to ContentProviders?

"There are two layers. The first is the broad provider-level permission: you declare readPermission and writePermission on the <provider> element, and any caller that tries to query must hold the read permission, while any caller that tries to insert, update, or delete must hold the write permission. The second layer is URI-level grants: if you set grantUriPermissions=true on the provider, you can attach FLAG_GRANT_READ_URI_PERMISSION or FLAG_GRANT_WRITE_URI_PERMISSION to an Intent and hand it to another app. That app gets temporary access to just that URI, bypassing the broad provider permission entirely. This is the standard mechanism for sharing an individual file or record without permanently giving the other app a broad permission."

9.6 Intents and PendingIntents

Explicit vs Implicit Intents

Explicit Intent: Directly specifies the target component — Activity, Service, or BroadcastReceiver — by its class name. Used for communication within your own app, where you know exactly what you want to start.

// Start a specific Activity in your app
val intent = Intent(this, ProfileActivity::class.java).apply {
    putExtra("userId", userId)
}
startActivity(intent)

// Start a specific service
val serviceIntent = Intent(this, DownloadService::class.java)
startService(serviceIntent)

Implicit Intent: Does not name a specific component. Instead it declares an action — and optionally data and a category — and lets the system find a matching component from any installed app. Used for inter-app communication.

// Open a URL in a browser
val intent = Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com"))
startActivity(intent)

// Share text
val shareIntent = Intent(Intent.ACTION_SEND).apply {
    type = "text/plain"
    putExtra(Intent.EXTRA_TEXT, "Check this out!")
}
startActivity(Intent.createChooser(shareIntent, "Share via"))

// Make a phone call
val dialIntent = Intent(Intent.ACTION_DIAL, Uri.parse("tel:+15551234567"))
startActivity(dialIntent)

Security: Always use explicit intents for starting Services. Implicit intents to start a Service have been blocked since Android 5.0 — the system throws IllegalArgumentException: Service Intent must be explicit. The reason is that an implicit service intent is a security risk: any app with a matching intent filter could intercept it.

Intent Filters

Declared in the manifest, intent filters specify what Intents an Activity, Service, or Receiver is willing to handle. The system uses them to match implicit intents to the right component.

<activity android:name=".ShareActivity">
    <intent-filter>
        <action android:name="android.intent.action.SEND" />
        <action android:name="android.intent.action.SEND_MULTIPLE" />
        <category android:name="android.intent.category.DEFAULT" />
        <data android:mimeType="image/*" />
    </intent-filter>
</activity>

Matching rules: An implicit Intent matches a filter if three conditions hold — first, its action matches at least one <action> in the filter. Second, its category matches all <category> elements (note that the DEFAULT category is automatically added to Intents started with startActivity). Third, its data — URI plus MIME type — satisfies the filter's data rules.

android:exported: Activities with an intent-filter are exported by default, meaning any app can start them. Since Android 12, you must explicitly declare android:exported="true" or android:exported="false" for any Activity, Service, or Receiver that has an intent-filter; omitting it causes a build or install failure.

Deep Links (Intents)

Deep links route external URLs and URIs into specific app screens. They are declared as intent filters with ACTION_VIEW, CATEGORY_DEFAULT, and CATEGORY_BROWSABLE — the BROWSABLE category is what allows the link to be opened from a web browser.

<activity android:name=".ArticleActivity">
    <intent-filter>
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <data android:scheme="myapp" android:host="article" />
        <!-- HTTP/HTTPS deep link -->
        <data
            android:scheme="https"
            android:host="www.example.com"
            android:pathPrefix="/articles" />
    </intent-filter>
</activity>
// Handle in Activity
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val uri = intent.data
    val action = intent.action
    if (action == Intent.ACTION_VIEW && uri != null) {
        val articleId = uri.lastPathSegment
        loadArticle(articleId)
    }
}

Testing deep links:

adb shell am start -W -a android.intent.action.VIEW -d "myapp://article/123" com.example.app

App Links

App Links are a stricter form of deep link that use the https:// scheme and require verified domain ownership. When verified, Android routes matching links directly to your app without showing the disambiguation dialog.

Requirements:

  1. An intent filter with android:autoVerify="true".
  2. A /.well-known/assetlinks.json file served from your domain, containing your app's SHA-256 certificate fingerprint.
<intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data android:scheme="https" android:host="www.example.com" />
</intent-filter>
// https://www.example.com/.well-known/assetlinks.json
[{
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
        "namespace": "android_app",
        "package_name": "com.example.app",
        "sha256_cert_fingerprints": ["14:6D:E9:83:..."]
    }
}]

Difference from deep links:

  • Deep links show the disambiguation dialog if multiple apps can handle the URI, or offer to open it in a browser.
  • App links open directly in your app with no dialog — but only after domain ownership is verified. If your app is not installed, the system falls back to the browser.

PendingIntent

A PendingIntent is a token representing an Intent that another application or the system can fire on your app's behalf at some point in the future, using your app's identity and permissions. It is essentially a pre-authorized capability you hand to someone else.

Use cases:

  • Notification taps and action buttons.
  • AlarmManager scheduled tasks.
  • Widget click handlers.
  • App shortcuts.
  • Any situation where an external process needs to launch a component in your app.
// For a Notification
val intent = Intent(context, MainActivity::class.java).apply {
    flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK
    putExtra("notification_id", notificationId)
}
val pendingIntent = PendingIntent.getActivity(
    context,
    requestCode,        // unique integer to distinguish PendingIntents
    intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)
val notification = NotificationCompat.Builder(context, channelId)
    .setContentIntent(pendingIntent)
    .build()

Four factory methods:

  • PendingIntent.getActivity(context, requestCode, intent, flags) — starts an Activity
  • PendingIntent.getService(context, requestCode, intent, flags) — starts a Service
  • PendingIntent.getBroadcast(context, requestCode, intent, flags) — sends a Broadcast
  • PendingIntent.getActivities(context, requestCode, intents, flags) — starts a synthetic stack of Activities (useful for deep-link back stacks)

PendingIntent Mutability

Since Android 12 (API 31), apps must specify mutability explicitly:

  • FLAG_IMMUTABLE: The system cannot modify the Intent inside the PendingIntent. The receiving component gets exactly the Intent you specified. Preferred and required for almost every use case.
  • FLAG_MUTABLE: Allows the system to modify certain Intent fields such as extras. Required only when the PendingIntent is meant to be filled in by the system — for example, inline reply from notifications, AlarmManager.setAlarmClock() show-intent, bubble Intents, or MediaSessionCompat.
// Immutable — preferred, for notification tap, alarm callbacks
PendingIntent.getActivity(context, 0, intent, PendingIntent.FLAG_IMMUTABLE)

// Mutable — only when the system needs to fill in extras
PendingIntent.getBroadcast(context, 0, intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_MUTABLE)

Before API 31: FLAG_IMMUTABLE was available but not required. Omitting both flags defaulted to mutable behavior. Apps targeting API 31 and above will crash at PendingIntent creation if neither flag is specified.

Security Implications

PendingIntent security risks:

  1. Mutable PendingIntent with implicit base Intent: This is extremely dangerous. A mutable PendingIntent wrapping an implicit Intent can be received by a malicious app that then modifies the Intent fields — action, component, extras — and redirects it to any component, including private ones in your app. The rule is simple: if you use FLAG_MUTABLE, the base Intent must be explicit.
  1. Confused deputy attack: Your PendingIntent fires with your app's identity and permissions. A malicious app that receives it can exploit whatever elevated permissions your app holds — for example, accessing a protected ContentProvider or starting a non-exported Activity — using your credentials.
  1. Intent interception: Implicit broadcasts sent without a receiverPermission argument can be received by any installed app. Use explicit targeting or sendBroadcast(intent, permission) for any broadcast carrying sensitive data.
// DANGEROUS: mutable + implicit
val badIntent = Intent(Intent.ACTION_VIEW) // implicit
val dangerousPendingIntent = PendingIntent.getActivity(
    context, 0, badIntent, PendingIntent.FLAG_MUTABLE
) // any receiver can redirect this to any Activity with your app's identity!

// SAFE: immutable or mutable with explicit intent
val safeIntent = Intent(context, MyActivity::class.java) // explicit
val safePendingIntent = PendingIntent.getActivity(
    context, 0, safeIntent, PendingIntent.FLAG_IMMUTABLE
)
  1. Exported components without permission checks: Any Activity with android:exported="true" and no permission requirement can be started by any app on the device. Add android:permission on the element or do manual permission checks in onCreate if you need to restrict access.

Task Stack Behavior

Intents can manipulate the task back stack in significant ways. There are a few key scenarios to know:

Notification tap: Tapping a notification should open the app in a sensible state — not just drop the user onto a detail screen with no way to navigate up. Use TaskStackBuilder to create a synthetic back stack that mirrors what the user would have seen if they had navigated there naturally:

val resultIntent = Intent(context, DetailActivity::class.java).apply {
    putExtra("id", itemId)
}
val stackBuilder = TaskStackBuilder.create(context).apply {
    addNextIntentWithParentStack(resultIntent) // reads parentActivityName from manifest
}
val pendingIntent = stackBuilder.getPendingIntent(0,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)

FLAG_ACTIVITY_NEW_TASK: Required when starting an Activity from a non-Activity context such as a Service or BroadcastReceiver. It creates a new task if none exists, or brings an existing task with the same affinity to the foreground.

FLAG_ACTIVITY_CLEAR_TOP: If the target Activity already exists anywhere in the current task's back stack, all Activities above it are destroyed and onNewIntent is called on the existing instance. This is the standard "navigate to home and clear" pattern.

// Go to HomeActivity and clear everything above it
val intent = Intent(context, HomeActivity::class.java).apply {
    flags = Intent.FLAG_ACTIVITY_CLEAR_TOP or Intent.FLAG_ACTIVITY_SINGLE_TOP
}
startActivity(intent)

FLAG_ACTIVITY_NO_HISTORY: The Activity is not added to the back stack. When the user leaves it — via Back or by starting another Activity — it finishes immediately and cannot be recovered by pressing Back. Useful for splash screens or short-lived intermediary screens.

Intents Interview Angles

Q: Explicit vs implicit intent — when do you use each?

"The rule is: explicit when you know exactly what you're talking to, implicit when you want the system to find the right handler. Inside my own app I always use explicit intents — I know the Activity, Service, or Receiver by name and I'm not trying to let any other app intercept it. Implicit intents are for inter-app work: opening a URL in a browser, sharing text, capturing an image — situations where I care about the action but not which app performs it. One important exception: implicit intents for starting Services are blocked on API 21 and above, because any app could intercept them. Service intents must always be explicit."

Q: What is a PendingIntent?

"A PendingIntent is a pre-authorized token you hand to another process — the system, AlarmManager, NotificationManager, a widget host — that lets them fire a specific Intent on your app's behalf at some point in the future, even if your process is not running. The system holds the description of the Intent, not the Intent object itself, and recreates it when it needs to fire. The critical thing is that it fires with your app's identity and permissions, not the caller's, which is why the security choices you make when creating it really matter."

Q: Why does PendingIntent mutability matter?

"Mutability determines whether the process that receives the PendingIntent can modify the Intent before firing it. If the base Intent is implicit and the PendingIntent is mutable, a malicious app can receive it and overwrite the target component — redirecting it to any Activity in your app, including private ones — while still running under your app's identity and permissions. That's the 'confused deputy' attack. FLAG_IMMUTABLE prevents any modification and should be the default choice. FLAG_MUTABLE is only for cases where the system legitimately needs to inject data — like filling in the reply text for an inline notification reply."

Q: How do deep links work?

"Deep links go through Android's Intent resolution system. You declare an <intent-filter> with ACTION_VIEW, CATEGORY_DEFAULT, and CATEGORY_BROWSABLE, plus a <data> element that specifies the scheme, host, and path pattern you want to handle. When the user taps a matching link in a browser, email, or another app, the system queries all installed apps for a matching intent filter. If multiple apps match, it shows the disambiguation dialog. If you've set up App Links with verified domain ownership, it routes directly to your app with no dialog. Either way, the matching Activity receives the Intent and reads the URI from intent.data to navigate to the right screen."
