9.1 Activity

Full Lifecycle: onCreate → onDestroy

🎤 Say it out loud (~30–45s): "The Activity lifecycle is a set of callbacks the framework drives as the Activity moves between created, started, resumed, paused, stopped, and destroyed. What I really care about is what each callback guarantees: onCreate runs exactly once per instance, onResume means I'm interactive, and onStop/onDestroy are not guaranteed to run because the system can kill my process outright. So I never put persistence-critical work in onDestroy — I save in onPause/onStop and lean on ViewModel plus saved state for survival."

An Activity's lifecycle is the set of callbacks the Android system invokes as it creates, runs, pauses, stops, and destroys the Activity. The thing that matters in an interview — and in production — is knowing exactly what each callback guarantees and what it does not, because getting that wrong is the source of almost every lifecycle bug.

         App launched
              │
         onCreate()        ← One-time setup: inflate layout, init ViewModel
              │
         onStart()         ← Activity becomes visible (not yet interactive)
              │
         onResume()        ← Activity is in foreground, user can interact
              │
         ┌───┴────────────────────────────────────────────────────┐
         │              Activity is running                       │
         └───┬────────────────────────────────────────────────────┘
              │
         onPause()         ← Partially obscured (dialog, multi-window), or leaving
              │
         onStop()          ← No longer visible
              │
     ┌────────┴───────────┐
     │                    │
onRestart()          onDestroy()       ← Finishing or system reclaim
     │
 onStart() ──► ...

Under the hood

The lifecycle isn't a set of virtual methods the OS calls directly across the process boundary. The system server (ActivityManagerService) sends transactions over Binder to the app process, where ActivityThread (running the main Looper) receives them as messages. Each transition is modeled as a ClientTransaction carrying lifecycle items and a target state; TransactionExecutor computes the path between the current and requested lifecycle state and replays the intermediate callbacks in order. Activity.dispatchActivityResult / performCreate / performStart etc. are the internal hooks that ultimately invoke your onX() overrides and flip the mCalled flag — which is why forgetting super.onCreate() throws SuperNotCalledException.

system_server (AMS) ──Binder──► app process main thread
                                  ActivityThread.mH (Handler/Looper)
                                  └─ ClientTransaction
                                       └─ TransactionExecutor
                                            ├─ cycleToPath(...)   // replays onStart→onResume etc.
                                            └─ performLifecycleSequence(...) → your onX()

onCreate(savedInstanceState: Bundle?)

🎤 Say it out loud (~30s): "onCreate runs once per instance — savedInstanceState is null on a fresh launch and non-null when I'm being recreated after rotation or a process kill. It's where I inflate the layout, grab my ViewModel, and wire observers. The gotcha is the views aren't measured yet — width and height are zero — so anything that needs layout dimensions has to wait for a layout pass, not run here."
  • Called once per Activity instance lifetime — when first created or after process death recreation.
  • Receives savedInstanceState: null on a fresh launch, non-null on recreation after a system kill or configuration change.
  • Do here: setContentView/Compose setup, ViewModel retrieval, binding observer setup, one-time initializations.
  • Do NOT do here: long operations, network calls on the main thread, or anything that requires the view to be measured or laid out — view sizes are 0 at this point.
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContentView(R.layout.activity_main)
    val viewModel: MyViewModel by viewModels()
    viewModel.uiState.observe(this) { state -> render(state) }
    // Safe: savedInstanceState?.getString("MY_KEY") to restore transient UI state
}

Under the hood

setContentView only attaches your inflated hierarchy to the Activity's DecorView; it does not measure or lay anything out. The actual measure/layout/draw traversal happens later, on the first ViewRootImpl.performTraversals() after the window is added to the WindowManager (around onResume/makeVisible). That's why view dimensions are 0 in onCreate — getWidth()/getHeight() read fields that layout() hasn't populated yet. If you need real sizes, post to the view's handler or use a OnGlobalLayoutListener/doOnLayout, which fire after the traversal. The savedInstanceState Bundle, when present, is the deserialized result of an earlier onSaveInstanceState that the system unparceled from the activity record.

onStart()

🎤 Say it out loud (~30s): "onStart is the visible-but-not-interactive state — the Activity is on screen but not yet at the top accepting touches. It runs both after onCreate and after onRestart when I come back from stopped. I use it to re-register lightweight, visibility-scoped listeners like a UI BroadcastReceiver, because anything registered here pairs cleanly with onStop to release it."
  • Activity transitions from "stopped" to "visible but not yet in the foreground."
  • Called after onCreate and also after onRestart when returning from a stopped state.
  • The Activity can receive UI updates at this point, but the user cannot interact yet.
  • Typical use: re-register lightweight listeners that should only be active while the Activity is visible (e.g., a BroadcastReceiver for UI updates).

Under the hood

Internally onStart is where the framework marks the Activity as part of the visible set and the LifecycleRegistry (the Lifecycle backing the LifecycleOwner) advances to the STARTED state, moving any STARTED-gated LifecycleObservers and repeatOnLifecycle(STARTED) collectors into their active phase. The window has been added but mStopped/mVisibleFromClient bookkeeping in Activity flips such that the surface becomes eligible to be shown. Symmetry with onStop matters: the framework guarantees a matching stop for every start that completes, so listeners registered here are safe to unregister there.

onResume()

🎤 Say it out loud (~30s): "onResume means I'm at the top of the stack and fully interactive — touch events flow to me. It's also called when I come back from a partial cover, like dismissing a dialog, without onStart running again. So I acquire foreground-only resources here — camera, sensors, media playback — and release the mirror image in onPause."
  • Activity is at the top of the stack and fully interactive.
  • Called after onStart and also after returning from any partial-cover state — for example, after a dialog is dismissed.
  • Typical use: start animations, acquire camera or audio resources, resume media playback.
  • This is the steady state for a running Activity — the one it spends most of its time in.

Under the hood

onResume returning is not the same instant the user can touch the screen. After handleResumeActivity, ActivityThread calls WindowManager.addView on the DecorView, which creates the ViewRootImpl and registers the window/input channel with the system. Only once the surface is created and the first frame is drawn and the input channel is wired does touch dispatch actually begin. The LifecycleRegistry advances to RESUMED here. There's also onTopResumedActivityChanged (added for multi-window) which is the true "I uniquely own focus" signal when several visible activities exist side by side.

onPause()

🎤 Say it out loud (~30s): "onPause fires when I'm losing the foreground but might still be visible — a transparent dialog, multi-window, or the next Activity starting. It has to be fast, because the incoming Activity's onResume won't run until my onPause returns, so heavy work here janks the transition. I release foreground-only resources and do light saves here, never blocking DB writes."
  • Called when the Activity is losing the foreground but may still be visible — for example, in multi-window mode, with a transparent dialog over it, or as a new Activity is starting.
  • Must be fast — the new Activity's onResume is not called until onPause returns, so any long work here causes the transition to stutter.
  • Typical use: save lightweight unsaved data (not heavy database writes), stop animations, release camera or audio resources that must not run in the background.
  • After onPause, the Activity may be killed by the system without onStop or onDestroy ever being called — a low-memory scenario that is rare in modern Android but worth knowing.

Under the hood

The "onPause must be fast" rule comes from the historical handshake in ActivityManagerService: when starting a new Activity, AMS would pause the current one and wait on the completePaused callback (with an ActivityManagerService timeout, classically ~500ms) before resuming the next. Modern Android relaxes some of this, but the dependency is real — your onPause is on the critical path of the next screen's appearance. The OS uses your process's adj (out-of-memory adjustment score, managed via oom_adj) to decide kill priority; once paused-and-stopped your process climbs to a cached/background adj and the Linux low-memory killer can reap it with no further callbacks.

onStop()

🎤 Say it out loud (~30s): "onStop means I'm fully off-screen — another Activity covered me or the user hit Home. The object is still alive and its state is preserved, so this is where I do the heavier teardown: flush DB writes, unregister receivers, stop location updates. The key caveat is the system can kill my process after onStop without ever calling onDestroy, so onStop is my last reliable chance to persist."
  • Called when the Activity is no longer visible — either another Activity has fully covered it, or the user pressed Home.
  • Typical use: release resources not needed while invisible (heavy database writes, unregister receivers), stop location updates.
  • The Activity object is still alive in memory at this point and its state is preserved.
  • The system can kill the process after onStop without ever calling onDestroy.

Under the hood

At onStop the WindowManager is told the window is no longer visible, so the surface is released back to SurfaceFlinger and the Activity stops consuming GPU/compositor resources — but the Java object graph (the Activity instance, its view tree, your ViewModel) stays resident in the heap. The framework keeps an ActivityClientRecord referencing it. Crucially, the saved state has already been parceled (onSaveInstanceState ran around this point) and handed to system_server, which holds it in the TaskRecord/ActivityRecord in a different process. That's why a process kill after onStop loses your in-memory objects but not your Bundle — the Bundle lives outside your process.

onDestroy()

🎤 Say it out loud (~30s): "onDestroy runs when the Activity is genuinely finishing — either I called finish() or the system is reclaiming it — and also on config changes before the new instance is built. The big trap interviewers want is that it's not guaranteed: on process death the OS just kills the process and onDestroy never runs. So for anything that must survive, I use ViewModel and saved state, not cleanup code in onDestroy."
  • Called when the Activity is permanently finishing — either finish() was called or the system decided to reclaim it.
  • Also called on configuration changes such as rotation, before the new instance is created.
  • Not guaranteed during process death — the system kills the process without calling this.
  • Typical use: cancel coroutines not tied to a lifecycle scope, release any remaining resources. For anything that needs to survive configuration changes, use ViewModel instead.

Under the hood

You can distinguish a real finish from a config-change destroy with isFinishing() and isChangingConfigurations(). Internally, on a config change the framework calls retainNonConfigurationInstances() before performDestroy() to snapshot the NonConfigurationInstances (which wraps the ViewModelStore), then destroys the old Activity and hands that snapshot to the new one — so the ViewModel object literally survives by reference, never serialized. On process death there is no performDestroy call at all: the kernel reaps the process when the OOM killer fires, so any onDestroy cleanup (closing files, cancelling raw threads) simply never executes — only the externally-held saved state remains.

onRestart()

🎤 Say it out loud (~20s): "onRestart only fires when a stopped Activity is coming back to the foreground — not when it was killed and recreated. The exact path is onStop → onRestart → onStart → onResume. It's a hook for re-preparing state that was torn down in onStop but where the object itself was never destroyed."
  • Called only when an Activity is returning to the foreground after being stopped — not after being killed and recreated.
  • The path is: onStop → onRestart → onStart → onResume.

Under the hood

onRestart exists because the framework distinguishes a stopped-but-alive Activity from a destroyed one. The ActivityClientRecord still holds the live instance, so TransactionExecutor.cycleToPath computes a transition from ON_STOP back up to ON_RESUME and inserts the restart callback as the entry point — it is never part of the create path. There is no onRestart after recreation because that path goes through a brand-new instance and onCreate, not through the retained object.

Configuration Changes

A configuration change is any change to the device environment that could require the Activity to rebuild its UI: screen rotation, locale change, font scale change, keyboard availability, dark/light mode toggle, or a screen size change from a multi-window resize.

Default behavior: The system destroys and recreates the Activity.

  1. onPause → onStop → onSaveInstanceState → onDestroy (old instance)
  2. onCreate(savedInstanceState) → onStart → onResume (new instance)

Key fact: ViewModel survives this destruction and recreation because it is stored in a ViewModelStore owned by the ViewModelStoreOwner — the Activity's backing store — which the framework passes across the configuration change via NonConfigurationInstance under the hood.

🎤 Say it out loud (~30–45s): "By default a config change like rotation destroys and recreates the whole Activity — full onPause through onDestroy, then a fresh onCreate with the saved Bundle. The reason that's safe is the resource system: the new config may map to different resources, so the framework rebuilds to re-resolve them. ViewModel survives that because it's held outside the Activity instance via the non-configuration-instance mechanism, while transient view state rides along in the Bundle. I only opt into configChanges for narrow performance cases like a video player."

Under the hood

The deeper reason Android recreates rather than just notifying is the resource system. Each Configuration maps to a set of qualified resource directories (values-land, values-night, drawable-xxhdpi, etc.); on a config change the framework builds a new Resources/AssetManager context so that getString, getDrawable, layout inflation, and so on resolve against the new qualifiers. Recreation guarantees every cached resource reference is re-fetched consistently. The ViewModel's survival is implemented in ComponentActivity.onRetainNonConfigurationInstance(), which packs the ViewModelStore into a NonConfigurationInstances holder; ActivityThread stashes that on the ActivityClientRecord and injects it into the new instance, so getLastNonConfigurationInstance() returns the same store and ViewModelProvider hands back the same ViewModel objects.

Handling configuration changes manually

🎤 Say it out loud (~30s): "I can declare configChanges in the manifest to tell the system not to recreate for those specific changes — instead it calls onConfigurationChanged and hands me the new config to react to manually. The downside is I now own all the resource-swapping the framework would've done for free, so any layout that differs by orientation has to be updated in code. It's fragile; I reserve it for cases like a video player that mustn't rebuffer on rotation."

You can tell the system to not recreate the Activity for certain config changes by declaring configChanges in the manifest:

<activity
    android:name=".MyActivity"
    android:configChanges="orientation|screenSize|keyboardHidden" />

Then override:

override fun onConfigurationChanged(newConfig: Configuration) {
    super.onConfigurationChanged(newConfig)
    // Manually handle the configuration change, e.g., update layout
    if (newConfig.orientation == Configuration.ORIENTATION_LANDSCAPE) {
        // adjust UI
    }
}

Trade-off: Handling config changes manually bypasses the standard lifecycle recreation, which means any layout that differs between orientations must be updated programmatically. That is fragile and hard to maintain. The better default is ViewModel plus saved instance state. Reserve configChanges for genuinely performance-sensitive cases — a video player that must not rebuffer on rotation is the classic example.

Under the hood

When you list a flag in configChanges, the framework compares the changed config bits against your declared mask. If every changed bit is one you claimed to handle, it skips the relaunch path entirely and instead calls Activity.onConfigurationChanged(newConfig) plus the resource update — your Resources object's configuration is updated in place rather than rebuilt. If even one changed bit is not in your mask, the framework falls back to a full relaunch regardless. A common bug: declaring orientation but not screenSize, so on modern API levels (where rotation also changes the smallest-width/screen-size config) the Activity still gets recreated because screenSize wasn't claimed.

Lifecycle during rotation (the classic interview question)

User rotates device:
  Old instance: onPause → onStop → onSaveInstanceState → onDestroy
  New instance: onCreate(bundle) → onStart → onResume

ViewModel: NOT destroyed — survives the entire sequence.
savedInstanceState Bundle: saved before destroy, restored in new onCreate.

Process Death

🎤 Say it out loud (~30–45s): "Process death is when the OS reclaims my app's process for memory while it's backgrounded — it happens after onStop, and onDestroy is never called; the process just disappears. When the user returns, Android recreates the top Activity and back stack from saved state and calls onCreate with the Bundle. The trap is that ViewModel is gone — it lived in the dead process — but SavedStateHandle survives because the framework serializes it alongside the instance state. So I design recovery around the Bundle plus a re-query from my repository, not around in-memory ViewModel fields."

The Android system can kill an app's process when memory is low. This happens after onStop is called on the visible Activity — the system never calls onDestroy. The process simply ceases to exist.

From the user's perspective: they can background the app, do memory-intensive work, then come back and expect to see the app in exactly the state they left it. That is Android's "apparent continuity" contract.

How Android restores:

  1. The system stores the Activity back stack — which Activities and Fragments were in which state — in a separate system process.
  2. When the user returns, the system recreates the top Activity (and the back stack) from that stored state.
  3. The Activity's onCreate is called with the saved Bundle.
  4. The ViewModel is NOT restored — it lived in the killed process. You must reinitialize it.
  5. SavedStateHandle in the ViewModel can survive process death, because the framework serializes it alongside the instance state.
class MyViewModel(
    private val savedStateHandle: SavedStateHandle
) : ViewModel() {
    // This value survives process death AND configuration changes
    var searchQuery: String
        get() = savedStateHandle["query"] ?: ""
        set(value) { savedStateHandle["query"] = value }
}

Key difference: config change vs process death

Aspect Configuration Change Process Death
ViewModel survives?YESNO
onDestroy called?YESNO
savedInstanceState?YESYES (system serialized it)
In-memory objects?Survive (in ViewModel)Lost
onSaveInstanceState?Called before destroyCalled when Activity is stopped

Under the hood

The kill itself is performed by the Linux Low Memory Killer (historically the in-kernel LMK driver, now usually the userspace lmkd daemon) acting on the oom_adj score system_server assigns each process based on its component states. A foreground Activity sits near adj 0 (effectively unkillable); once your task is cached/background it climbs to a high adj and is among the first reaped under pressure. Because the kill is SIGKILL at the kernel level, no Java finalizers, onDestroy, or shutdown hooks run — that's why onDestroy and process death are fundamentally asymmetric. The saved-state survival works because onSaveInstanceState parcels your Bundle and ships it over Binder to system_server, which persists it in the ActivityRecord; SavedStateHandle plugs into this same pipeline via the SavedStateRegistry, so its contents are written into the same Bundle and replayed on recreation.

Backgrounded app process              system_server (survives)
  onStop ─► onSaveInstanceState ──Binder──► Bundle stored in ActivityRecord
        adj raised → lmkd SIGKILL                     │
  (heap, ViewModel, threads gone)                     │
  user returns → recreate top activity ◄──────────────┘
        onCreate(savedBundle)  // ViewModel rebuilt fresh; SavedStateHandle rehydrated

Saved Instance State

🎤 Say it out loud (~30–45s): "onSaveInstanceState gives me a Bundle to stash small, transient UI state — scroll position, form text, selected tab — right before the Activity might be destroyed for a config change or process kill. The hard limit people forget is that the Bundle goes through a Binder transaction capped around 1MB, so dropping a bitmap or a big list in there throws TransactionTooLargeException. The rule of thumb: Bundle for ephemeral screen state, database or repository for anything large or authoritative."

onSaveInstanceState(outState: Bundle) is called:

  • Before the Activity may be destroyed for a configuration change.
  • When the Activity is stopped and the system may kill the process — since Android 3.0+, this is called after onStop; before 3.0, it was called before onStop.

What to save: Small, serializable UI state — scroll position, selected tab, text field content, checked radio buttons, and so on.

What NOT to save: Large objects such as bitmaps or data lists, objects that hold a reference to the Activity context (that is a memory leak waiting to happen), or data that lives in a database or repository — that should be restored from the source of truth.

override fun onSaveInstanceState(outState: Bundle) {
    super.onSaveInstanceState(outState) // important: super saves view hierarchy state
    outState.putString("search_query", searchInput.text.toString())
    outState.putInt("selected_tab", currentTabIndex)
}

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    savedInstanceState?.let {
        searchInput.setText(it.getString("search_query"))
        currentTabIndex = it.getInt("selected_tab", 0)
    }
}

Bundle size limits: The Bundle is serialized via a Binder transaction, which has a total limit of roughly 1 MB. Storing large data in it causes a TransactionTooLargeException. Use the database or a file for anything large.

Bundle vs Database decision:

  • Bundle: ephemeral UI state that is only meaningful on the current screen — scroll position, form input, selected item. Cheap to serialize and small in size.
  • Database / Repository: persistent domain data that should survive app uninstall/reinstall cycles, is shared across screens, or is large. Restore it from the repository inside the ViewModel.

Under the hood

super.onSaveInstanceState(outState) walks the view hierarchy and calls View.onSaveInstanceState() on every view that has an id, collecting each Parcelable into a SparseArray keyed by view id — that's how an EditText's text or a RecyclerView's scroll position restore automatically without you writing code (and why an id is required). The Bundle is then parceled — flattened into a Parcel, a contiguous native buffer — and transmitted to system_server over Binder. The ~1MB ceiling is the per-process Binder transaction buffer shared across all in-flight transactions, so the real safe budget is well under 1MB and exceeding it surfaces as TransactionTooLargeException (sometimes asynchronously, making it tricky to attribute). Note putParcelable doesn't serialize at call time — the flattening happens lazily when the Bundle is actually parceled for the transaction.

ViewModel

🎤 Say it out loud (~30–45s): "ViewModel holds UI state in a lifecycle-aware way and survives configuration changes because it's scoped to the ViewModelStore, not the Activity instance — the store is retained across recreation via the non-configuration-instance mechanism. It does not survive process death by itself; for that I inject SavedStateHandle, whose contents are serialized into the saved-state Bundle. The other thing I rely on is viewModelScope — it's a CoroutineScope that's automatically cancelled in onCleared, so I never leak coroutines."

ViewModel is an Architecture Component designed to hold and manage UI-related data in a lifecycle-conscious way. It survives configuration changes but not process death — unless you are using SavedStateHandle, in which case the parts you put in the handle can survive both.

Internals: The ViewModelStore is retained by the NonConfigurationInstance mechanism in ComponentActivity. When a configuration change occurs, ActivityThread calls retainNonConfigurationInstances() before destroying the Activity, and passes the returned objects to the new instance.

class ProfileViewModel(
    private val savedStateHandle: SavedStateHandle,
    private val profileRepo: ProfileRepository
) : ViewModel() {
    
    // Survives both config change AND process death
    val userId: String = savedStateHandle.get<String>("userId") ?: ""
    
    private val _uiState = MutableStateFlow<ProfileUiState>(ProfileUiState.Loading)
    val uiState: StateFlow<ProfileUiState> = _uiState.asStateFlow()
    
    init {
        loadProfile()
    }
    
    private fun loadProfile() {
        viewModelScope.launch {
            try {
                _uiState.value = ProfileUiState.Success(profileRepo.getProfile(userId))
            } catch (e: Exception) {
                _uiState.value = ProfileUiState.Error(e.message ?: "Unknown error")
            }
        }
    }
    
    override fun onCleared() {
        super.onCleared()
        // viewModelScope is automatically cancelled — no need to cancel manually
    }
}

ViewModel vs savedInstanceState:

  • ViewModel: great for large data like lists and bitmaps, can hold non-serializable objects, cleared only when the user explicitly finishes the Activity.
  • savedInstanceState: serialized to disk, survives process death, but limited to roughly 50 KB of serializable data.
  • Best practice: combine both — the ViewModel holds the full data set, and savedInstanceState (via SavedStateHandle) holds just enough to re-query it after process death.

Under the hood

ViewModelStore is just a HashMap<String, ViewModel> keyed by a provider-generated key. ViewModelProvider.get() looks up the key and either returns the existing instance or builds one via the Factory. The "survives config change" magic is purely that the store map outlives the Activity instance: ComponentActivity.onRetainNonConfigurationInstance() returns a holder containing that map, the framework reattaches it, and the new Activity's getViewModelStore() finds the same map with the same ViewModel objects — no serialization, same heap references. viewModelScope is a lazily-created CoroutineScope backed by SupervisorJob() + Dispatchers.Main.immediate, stored as a tagged field on the ViewModel; onCleared() is invoked when the store calls clear() (on genuine finish, not config change), and the framework cancels that scope's Job, which cancels every child coroutine. SavedStateHandle is a MutableMap whose savedStateProvider() is registered with the SavedStateRegistry, so its entries get written into the same instance-state Bundle that survives process death.

Back Stack

🎤 Say it out loud (~30–45s): "The back stack is a per-task LIFO stack of Activities the system maintains — startActivity pushes, finish() and the Back button pop and resume what's underneath. Each task has its own stack, and pressing Home doesn't destroy your task, it just moves it to the background. The subtle part interviewers probe is taskAffinity and launch modes — affinity defaults to the package name and determines which task an Activity prefers to land in, which is what makes singleTask and friends behave the way they do."

The task back stack is a stack of Activities maintained by the system. Each task has its own stack, and pressing the system Back button pops the top Activity and resumes the one beneath it.

  • startActivity(intent) pushes a new Activity onto the current task's back stack.
  • finish() pops the current Activity.
  • The home screen is a separate task; navigating to it moves your task to the background rather than destroying it.

Task affinity: Activities have a taskAffinity attribute that defaults to the app's package name. Activities with the same affinity are naturally grouped in the same task, and this interacts with certain launch modes.

Under the hood

The back stack isn't stored in your process — it lives in system_server as a Task (historically TaskRecord) holding an ordered list of ActivityRecords, managed by the activity task subsystem (ActivityTaskManagerService / ActivityStack / Task). When you startActivity, the launch flows through AMS, which consults the Intent flags and the target's launchMode/taskAffinity to decide which task receives the record and whether to reuse an existing instance. standard always creates a new record; singleTop reuses the top if it matches (routing through onNewIntent instead of a new instance); singleTask finds or creates a task by affinity and clears records above the existing instance; singleInstance isolates the Activity as the sole member of its own task. Because the records and their saved Bundles live in the system process, the entire stack can be reconstructed after your app's process is killed — the system replays it Activity by Activity on return.

Launch Modes

🎤 Say it out loud (~30–45s): "Launch modes decide whether starting an Activity creates a fresh instance or reuses an existing one, and whether it lives in the current task or a new one. The four manifest modes are standard, singleTop, singleTask, and singleInstance, and you can layer runtime overrides with Intent flags like CLEAR_TOP or NEW_TASK. The gotcha interviewers love is that singleTask and singleTop reuse the instance and route through onNewIntent instead of onCreate — so if you parse your data in onCreate, deep links into an already-running Activity silently break unless you also handle onNewIntent."

Launch modes control whether a new instance of an Activity is created when it is started, or whether an existing instance is reused. They can be declared in the manifest or set dynamically via Intent flags.

standard (default)

🎤 Say it out loud (~30s): "Standard is the default: every start creates a brand-new instance and pushes it onto the task, so you can end up with several copies of the same Activity stacked on top of each other. It doesn't care whether an instance already exists — that's both its simplicity and its footgun if you launch the same screen repeatedly."
  • A new instance is created every time the Activity is started, even if an instance already exists in the stack.
  • Multiple instances of the same Activity can coexist in the stack at the same time.

Under the hood

In the framework, ActivityStarter resolves a target and, for standard, always allocates a new ActivityRecord and pushes it onto the top TaskFragment of the resolved task. There's no reuse check — the record's lifecycle begins at onCreate. Each ActivityRecord is a distinct token in the ActivityManagerService (AMS), so two "identical" standard Activities are completely separate objects with separate saved states.

Task: [ A ] -> startActivity(A) -> Task: [ A, A' ]   // A' is a new ActivityRecord

singleTop

🎤 Say it out loud (~30s): "singleTop only reuses the instance if it's already sitting at the very top of the task — in that case you get onNewIntent instead of a new onCreate. If it's lower in the stack, you still get a fresh instance. I reach for it on notification and search targets so tapping again doesn't stack duplicates, and I always remember to call setIntent() inside onNewIntent or getIntent() keeps returning the stale one."
  • If the Activity is already at the top of the current task's back stack, no new instance is created — instead, onNewIntent(intent) is called on the existing instance.
  • If the Activity exists somewhere in the stack but is not at the top, a new instance is created.
  • Use case: notification target Activity, search Activity — avoids duplicates when the user taps a notification while the Activity is already open.
override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent) // important: update the intent so getIntent() returns the new one
    handleDeepLink(intent)
}

Under the hood

When AMS resolves the start, it compares the requested component against the top ActivityRecord of the task. On a match it skips creating a record and instead schedules a NewIntentItem through the ClientTransaction pipeline, which the ActivityThread delivers as onNewIntent. Because no new record is created, getIntent() still points at the original launch Intent — setIntent() mutates the record's stored intent so subsequent reads see the new one.

Task: [ X, A ]  startActivity(A) -> top is A -> onNewIntent(A)   // no new instance
Task: [ A, X ]  startActivity(A) -> top is X -> new A pushed     // not top, so created

singleTask

🎤 Say it out loud (~30s): "singleTask guarantees a single instance within its task — if it already exists anywhere in the stack, the system pops everything above it and delivers onNewIntent rather than making a new one. It's the classic home/root-screen mode. The surprise is that those Activities sitting on top really do get destroyed when it surfaces, so any unsaved state up there is gone."
  • Only one instance of this Activity exists in its task. If it already exists anywhere in the back stack, all Activities stacked on top of it are popped and onNewIntent is called on the existing instance.
  • Creates a new task if one does not already exist.
  • Use case: main or home screen of an app.
  • Gotcha: Activities on top of it are destroyed when it comes to the foreground, which can be surprising if you're not expecting it.

Under the hood

AMS scans the task's ActivityRecord list for an existing match. On a hit it performs a "clear top" operation, finishing every record above the target (each goes through onDestroy), then schedules onNewIntent on the survivor. The task affinity (taskAffinity, defaulting to the package name) decides which task it belongs to; if no task with that affinity exists, AMS creates a new Task and roots the Activity there.

Task: [ Home, B, C ]  startActivity(Home) -> finish C, finish B -> Home.onNewIntent()
                       -> Task: [ Home ]

singleInstance

🎤 Say it out loud (~30s): "singleInstance is singleTask taken to the extreme: the Activity is the only thing in its task, and anything it launches gets shoved into a different task. It's really for system-style surfaces like a dialer or alarm screen where you want hard isolation. In a normal app it's almost always the wrong tool and causes weird back-stack behavior."
  • Like singleTask but more isolated: the Activity is the only Activity in its task, and any Activities it starts go into a different task.
  • Use case: system-level shared UIs such as a dialer or alarm screen. Rarely needed in typical apps.

Under the hood

AMS marks the task as exclusive to this single ActivityRecord and refuses to add any other record to it. When this Activity calls startActivity, the launcher routes the new record into a separate task (creating one by affinity if needed), so the singleInstance task never grows beyond one entry. This is why "up"/back navigation across these boundaries is non-intuitive — two distinct Task objects are involved, each with its own back stack.

Intent flags (runtime alternative to manifest modes)

🎤 Say it out loud (~30s): "Intent flags let me override or approximate launch-mode behavior at the call site without touching the manifest, which is handy when the same Activity needs different behavior from different entry points. The common combo is CLEAR_TASK or NEW_TASK to wipe the stack and land on Home. The catch is that some flags only make sense together — CLEAR_TASK is a no-op without NEW_TASK — and launching from a non-Activity Context requires NEW_TASK."
Flag Effect

FLAG_ACTIVITY_CLEAR_TOPIf Activity already in stack, pop everything above it
FLAG_ACTIVITY_SINGLE_TOPSame as singleTop mode at runtime
FLAG_ACTIVITY_NO_HISTORYActivity is not added to back stack

val intent = Intent(this, HomeActivity::class.java).apply {
    flags = Intent.FLAG_ACTIVITY_CLEAR_TASK or Intent.FLAG_ACTIVITY_NEW_TASK
}
startActivity(intent)

Under the hood

Flags are packed as a bitmask into the Intent's mFlags int and travel with the Intent across the Binder call to AMS. The starter (ActivityStarter.setInitialState / computeLaunchingTaskFlags) reads them to decide reuse and task placement — they're effectively merged with the manifest launchMode to produce a final disposition. A subtlety: CLEAR_TOP without SINGLE_TOP destroys and recreates the matched Activity (new onCreate), whereas CLEAR_TOP or SINGLE_TOP delivers onNewIntent to the existing one instead.

mFlags = NEW_TASK | CLEAR_TASK  ->  AMS finishes all records in the target task,
                                    then roots HomeActivity as the new base record

Deep Links

🎤 Say it out loud (~30–45s): "A deep link is just an Intent — usually an ACTION_VIEW with a URI — that drops the user straight onto a specific screen from outside the app. The manifest intent-filter does the routing, and I read the target from intent.data. The part people forget is the synthetic back stack: if the user arrives via a deep link, pressing back should walk them up through your app hierarchy, not kick them out. Jetpack Navigation builds that automatically from <deepLink> nodes; doing it by hand means TaskStackBuilder with addNextIntentWithParentStack."

A deep link is an Intent that brings the user directly to a specific screen within your app from an external source — a notification, a web page, or another app.

Manifest declaration:

<activity android:name=".ProfileActivity">
    <intent-filter>
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <data
            android:scheme="myapp"
            android:host="profile"
            android:pathPrefix="/user" />
    </intent-filter>
</activity>

Handling in Activity:

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val uri: Uri? = intent.data
    if (uri != null) {
        val userId = uri.lastPathSegment
        // navigate to the correct screen
    }
}

Back stack for deep links: When a deep link launches your Activity, the back stack should contain a synthetic back stack so the user can navigate "up" naturally. Jetpack Navigation handles this automatically when you use <deepLink> declarations in the nav graph. If you are doing it manually, use TaskStackBuilder.

val deepLinkIntent = Intent(this, ProfileActivity::class.java).apply {
    data = uri
}
val stackBuilder = TaskStackBuilder.create(this).apply {
    addNextIntentWithParentStack(deepLinkIntent)
}
stackBuilder.startActivities()

Under the hood

At install time PackageManagerService parses every <intent-filter> into an IntentFilter object indexed by action, category, scheme, host, and path. When an ACTION_VIEW Intent fires, AMS asks PackageManager to match it against these filters — the URI's scheme/host/path are tested with the filter's matching rules, and BROWSABLE is required for links arriving from a browser. addNextIntentWithParentStack walks the manifest's parentActivityName chain (or getParentActivityIntent()) upward, building an array of Intents; startActivities then hands that whole array to AMS, which materializes the synthetic stack bottom-up so each parent ActivityRecord exists before the leaf.

URI myapp://profile/user/42
   matched filter -> ProfileActivity
TaskStackBuilder: [ HomeIntent, ProfileIntent ]  // parent chain resolved
   -> AMS creates Home (paused) then Profile (resumed) as one task

Multi-Window

🎤 Say it out loud (~30–45s): "Multi-window lets two apps share the screen in split mode since Android 7. The lifecycle wrinkle is visibility versus focus: before Android 10 only the focused Activity was RESUMED and the other dropped to PAUSED, so people used to put 'stop the camera' logic in onPause. Android 10 introduced multi-resume, where both Activities can be RESUMED at once, so that assumption breaks — now the focused one is signalled via onTopResumedActivityChanged, and that's where exclusive resources like the camera or mic should be acquired and released."

Android 7.0 and above support multi-window (split-screen) mode. In multi-window:

  • Both Activities can be visible simultaneously, but only one is resumed at a time — that is the pre-Android 10 behavior.
  • Android 10 and above: multiple Activities can be in the resumed state simultaneously, which is called multi-resume. This matters most for camera, audio, and other exclusive resources that you may need to share.

Lifecycle impact:

  • Entering split-screen triggers onPause if the Activity loses the top position, and onResume for the Activity that stays resumed (on Android 10+).
  • Resizing the window triggers a configuration change — similar to rotation — if screenSize is not listed in configChanges.
override fun onMultiWindowModeChanged(isInMultiWindowMode: Boolean, newConfig: Configuration) {
    super.onMultiWindowModeChanged(isInMultiWindowMode, newConfig)
    if (isInMultiWindowMode) {
        // release exclusive resources if needed
    }
}

Declaring support: Activities are multi-window-enabled by default. You can opt out with android:resizeableActivity="false", but that is not recommended.

Under the hood

Pre-Android 10, the WindowManager/AMS scheduler enforced a single globally-resumed Activity by pausing whichever Activity lost top focus, so RESUMED implied "focused". Android 10's multi-resume relaxed this: the scheduler can keep several ActivityRecords in the RESUMED lifecycle state across different windows/displays, and it tracks the focused one separately via the onTopResumedActivityChanged(isTopResumedActivity) callback (delivered through the same ClientTransaction pipeline). A window resize doesn't go through that path at all — it produces a new Configuration whose diff includes screenSize/smallestScreenSize, and unless those bits are in android:configChanges AMS relaunches the Activity exactly like a rotation.

< API 29:  split-screen -> non-focused Activity forced to onPause (only one RESUMED)
>= API 29: both RESUMED; focus moves via onTopResumedActivityChanged(true/false)
resize:    new Configuration (screenSize bit set) -> relaunch unless in configChanges

Activity Result API

🎤 Say it out loud (~30–45s): "The Activity Result API replaced startActivityForResult/onActivityResult. You register a launcher with a typed contract — input and output are strongly typed — and the framework hands you the result in a callback. The big win is lifecycle safety: because you register at construction time, not at launch time, the callback is correctly re-wired across configuration changes and even process death, so you don't lose the result like the old request-code pattern could. That's also the one rule interviewers check — you must register unconditionally at class init, never inside a click handler or after STARTED, or it throws."

The Activity Result API is the modern replacement for the deprecated startActivityForResult/onActivityResult pattern. It is lifecycle-safe and uses a contract-based approach where you declare what you want upfront and get a typed result back.

// 1. Register the launcher in the Activity/Fragment (at class level, before lifecycle)
private val pickImageLauncher = registerForActivityResult(
    ActivityResultContracts.PickVisualMedia()
) { uri: Uri? ->
    if (uri != null) {
        imageView.setImageURI(uri)
    }
}

// 2. Launch when needed
fun onPickPhotoClicked() {
    pickImageLauncher.launch(
        PickVisualMediaRequest(ActivityResultContracts.PickVisualMedia.ImageOnly)
    )
}

Built-in contracts:

  • StartActivityForResult — generic, takes an Intent, returns an ActivityResult
  • RequestPermission / RequestMultiplePermissions
  • PickVisualMedia (Photo Picker)
  • TakePicture, TakeVideo
  • GetContent, OpenDocument, CreateDocument
  • StartIntentSenderForResult

Custom contract:

class MyContract : ActivityResultContract<String, Boolean>() {
    override fun createIntent(context: Context, input: String): Intent =
        Intent(context, MyActivity::class.java).apply { putExtra("key", input) }
    
    override fun parseResult(resultCode: Int, intent: Intent?): Boolean =
        resultCode == Activity.RESULT_OK
}

Why better than onActivityResult:

  • Input and output are type-safe via the contract.
  • The launcher can be registered before the Activity is fully started, decoupled from the lifecycle.
  • No more managing integer request codes.
  • Works cleanly with Fragments without any extra plumbing.

Under the hood

registerForActivityResult is backed by an ActivityResultRegistry owned by the ComponentActivity. At registration it generates (or restores) an integer request code, hashes the key, and stores the contract + callback in maps; the registry's state is itself saved and restored via onSaveInstanceState, which is why results survive configuration changes and process death. launch() calls the contract's createIntent, then dispatches via the platform startActivityForResult under that generated code. When the result returns, ComponentActivity.onActivityResult forwards to ActivityResultRegistry.dispatchResult, which runs the contract's parseResult and invokes your callback — but only if the registering LifecycleOwner is at least STARTED, otherwise the result is held until it is. Registering after STARTED throws IllegalStateException, which enforces the "register at init" rule.

register -> rc=0x0001 stored {key -> (contract, callback)}, persisted in saved state
launch   -> createIntent() -> startActivityForResult(intent, rc)
return   -> onActivityResult(rc, code, data) -> parseResult() -> callback (if >= STARTED)

Activity Interview Angles

Q: Walk me through the Activity lifecycle during device rotation.

"When the user rotates the device, the system detects a configuration change and walks through a fixed sequence. On the old instance: onPause, then onStop, then onSaveInstanceState — since API 28 that's called after onStop — and then onDestroy. Then the new instance is created: onCreate with the bundle, onStart, onResume. The key thing to call out is that the ViewModel's onCleared is never called — the ViewModel survives the whole sequence completely intact. The Bundle carries the saved UI state. The ViewModel holds the data that is too large or not serializable to fit in a Bundle."

Q: What is the difference between a configuration change and process death?

"The two feel similar but they're quite different under the hood. With a configuration change, the system follows the normal lifecycle — onDestroy is called, but the ViewModel survives because it's held in a store that gets passed to the new instance. With process death, the system issues a SIGKILL — onDestroy is never called, and the ViewModel is gone because the entire process is gone. What both share is the Bundle: onSaveInstanceState was called while the Activity was alive, so that Bundle exists for both cases. The difference is what you do with it — after a config change the ViewModel already has your data, so the Bundle is mostly a cross-check; after process death, you need to use SavedStateHandle in the ViewModel or re-query from your repository in onCreate."

Q: What should go in Bundle vs in the database?

"The rule I follow is: Bundle for ephemeral UI state, database or repository for everything else. Ephemeral UI state means things that are only meaningful on this screen right now — scroll position, form text, which tab is selected, whether a dialog was open. It's transient, screen-specific, and cheap to serialize. The other bucket is persistent domain data — user profiles, search results, appointments. That data has a canonical home in the database or a remote API, it may be needed by multiple screens, and it's often too large for a Bundle. The practical reason the size limit matters is that the Bundle goes over a Binder transaction, which has a total cap of roughly 1 MB — put a large list in there and you'll get a TransactionTooLargeException."

Q: Why is onDestroy() not guaranteed for process death?

"The system kills the process at the OS level with a SIGKILL signal when memory is critical. At that point there is no opportunity to call any Java or Kotlin methods — the process just stops. onDestroy is only called when the system follows the normal lifecycle: an explicit finish(), a configuration change, or a controlled shutdown. That's why critical state has to be saved in onStop or earlier — onSaveInstanceState is called while the process is still alive. Any cleanup that lives only in onDestroy is fine for non-critical resource release, but you can never rely on it for data integrity."

9.2 Fragment

Fragment Lifecycle

🎤 Say it out loud (~30–45s): "A Fragment's lifecycle is coupled to its host Activity but has extra phases, and the crucial split is the Fragment instance versus its view. The Fragment object runs onCreate/onDestroy once, but onCreateView/onDestroyView can fire many times — every time it goes on and off the back stack the view is torn down and rebuilt while the instance lives on. That's exactly why you bind views in onViewCreated and null out your binding in onDestroyView; if you hold a view reference past onDestroyView you leak the entire view hierarchy. It's also why you observe LiveData with viewLifecycleOwner, not the Fragment itself."

A Fragment has its own lifecycle that is coupled to — but distinct from — its host Activity. The key word is "distinct": a Fragment's lifecycle has more phases than an Activity's, and getting them confused is one of the most common sources of Android bugs. Each Fragment instance goes through these callbacks:

onAttach(context)       ← Fragment associated with Activity; safe to access Context
    │
onCreate(savedState)    ← Initialize non-view resources; do NOT access views
    │
onCreateView(...)       ← Inflate/create the Fragment's view hierarchy; return root view
    │
onViewCreated(view, ...) ← View hierarchy created; safe to find/bind views
    │
onViewStateRestored(...) ← Restore state from savedInstanceState
    │
onStart()               ← Fragment becomes visible
    │
onResume()              ← Fragment is interactive
    │
[Fragment active]
    │
onPause()               ← Fragment loses foreground
    │
onStop()                ← Fragment no longer visible
    │
onSaveInstanceState()   ← Save UI state
    │
onDestroyView()         ← View hierarchy being destroyed; CLEAR view binding here
    │
onDestroy()             ← Fragment instance being destroyed
    │
onDetach()              ← Fragment disassociated from Activity

Key insight: onCreateView and onDestroyView can be called multiple times on the same Fragment instance — for example, when a Fragment is placed on the back stack its view is destroyed, but the Fragment object itself lives on. onCreate and onDestroy, by contrast, happen exactly once per Fragment instance lifetime.

Under the hood

The FragmentManager drives each Fragment through an integer state machine (Fragment.mState, e.g. INITIALIZING, CREATED, VIEW_CREATED, ACTIVITY_CREATED, STARTED, RESUMED), and FragmentStateManager.moveToExpectedState() steps the Fragment up or down one state at a time toward the target the manager computes from the Activity's state and the transaction. Critically, the Fragment owns two LifecycleOwners: the Fragment itself (lives onCreate→onDestroy) and a separate viewLifecycleOwner whose LifecycleRegistry is recreated on each onCreateView and moved to DESTROYED on each onDestroyView. That second registry is what makes back-stack reuse safe — observers bound to viewLifecycleOwner are automatically removed when the view dies, so a recreated view doesn't accumulate duplicate observers, and a stale binding reference held past onDestroyView keeps the whole detached view tree alive (the classic Fragment view leak).

Fragment instance state:   CREATED ─────────────────────────── DESTROYED   (once)
view lifecycle state:      [INITIALIZED→RESUMED→DESTROYED]  [INITIALIZED→...]  (per view)
                            └ onCreateView..onDestroyView ┘  └ recreated on back-stack pop ┘

View Lifecycle vs Fragment Lifecycle

🎤 Say it out loud (~30–45s): "The key is that a Fragment outlives its view. The Fragment instance runs from onAttach to onDetach, but its view only exists from onCreateView to onDestroyView — and when a Fragment goes onto the back stack, its view gets destroyed while the instance survives. So when it comes back, you get a brand-new view but the same Fragment. The gotcha interviewers love is that if you observe LiveData or collect a Flow against this instead of viewLifecycleOwner, the observer never dies with the view, so you can end up with a stale reference to a destroyed view or duplicate observers piling up."

This is one of the most important distinctions in Android development and a very common interview topic.

Fragment lifecycle: tied to the Fragment instance. The Fragment object can exist long after its view is destroyed — that happens whenever the Fragment is on the back stack.

View lifecycle (viewLifecycleOwner): tied specifically to the Fragment's view. It starts in onCreateView and ends in onDestroyView.

Fragment instance lifetime:  onAttach ──────────────────────────────────────── onDetach
Fragment view lifetime:                 onCreateView ──── onDestroyView
                                         (repeated every time fragment returns to foreground)

Practical consequence: If you observe a LiveData or collect a Flow using this — the Fragment as LifecycleOwner — the observer lives until the Fragment is destroyed. If the Fragment goes to the back stack and comes back, a new view is created but the old observer is not re-registered because it never died. This seems harmless at first, but if that observer references a view directly, you now have a stale reference to a destroyed view — a use-after-free bug on a destroyed view hierarchy.

The fix: Always use viewLifecycleOwner when observing data that needs to update the UI:

// WRONG — observer may reference destroyed views, or may register duplicate observers
viewModel.uiState.observe(this) { state -> render(state) }

// CORRECT — observer is tied to the view's lifecycle
viewModel.uiState.observe(viewLifecycleOwner) { state -> render(state) }

Under the hood

A Fragment holds two separate LifecycleRegistry objects. mLifecycleRegistry is the instance lifecycle owned by the Fragment itself. The view lifecycle lives in a distinct FragmentViewLifecycleOwner that the FragmentManager creates inside performCreateView and exposes via getViewLifecycleOwner(). When the view is created, the manager moves the view registry to RESUMED; in performDestroyView it drives that view registry to DESTROYED and then nulls out the reference, so the next onCreateView builds a fresh FragmentViewLifecycleOwner with a fresh registry. That is why a back-stack Fragment can have multiple sequential view-lifecycle owners over the life of one instance.

Fragment instance ──► mLifecycleRegistry (LifecycleRegistry)   // lives onAttach..onDetach
       │
       └─ getViewLifecycleOwner() ──► FragmentViewLifecycleOwner
                                          └─ own LifecycleRegistry  // recreated each onCreateView

LiveData.observe(owner, observer) wraps the observer in a LifecycleBoundObserver registered against whichever registry you pass. Pass the view owner and the binding auto-detaches at onDestroyView; pass the Fragment and it survives until onDestroy, which is exactly how duplicate/stale observers accumulate.

viewLifecycleOwner

🎤 Say it out loud (~30–45s): "viewLifecycleOwner is a LifecycleOwner whose lifecycle exactly mirrors the Fragment's view — alive from onCreateView to onDestroyView. My rule of thumb is: anything that touches a view goes on viewLifecycleOwner, and anything that should survive view recreation, like a data load, goes on the Fragment itself. The classic trap is accessing viewLifecycleOwner before onCreateView or after onDestroyView — it throws because there's no current view lifecycle to give you."

viewLifecycleOwner is a LifecycleOwner that mirrors the lifecycle of the Fragment's view, running from onCreateView through to onDestroyView.

When to use this vs viewLifecycleOwner:

  • this (the Fragment as LifecycleOwner): for operations that should survive view destruction — loading data, non-UI work.
  • viewLifecycleOwner: for everything that interacts with views — observing LiveData or Flow for UI updates, registering view-bound callbacks.

In Compose fragments: If the Fragment hosts a ComposeView, use viewLifecycleOwner.lifecycleScope to launch coroutines that collect flows for Compose:

viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state -> /* update Compose */ }
    }
}

Under the hood

getViewLifecycleOwner() returns the FragmentViewLifecycleOwner stored in the Fragment's mViewLifecycleOwner field; if that field is null it throws IllegalStateException("Can't access the Fragment View's LifecycleOwner ... when getView() is null"). There is also a viewLifecycleOwnerLiveData that emits the new owner each time a view is created and null when it's destroyed, which is how libraries observe view-owner transitions safely. The lifecycleScope you get from it is a LifecycleCoroutineScope backed by a SupervisorJob plus Dispatchers.Main.immediate; when the view registry reaches DESTROYED, the lifecycle's coroutine cancels that scope's job, so any collect launched there is automatically cancelled at onDestroyView. repeatOnLifecycle(STARTED) further suspends the body and cancels the inner block on each STOP, restarting it on the next START — so it pauses collection while backgrounded without tearing down the outer scope.

Fragment Transactions

🎤 Say it out loud (~30–45s): "A Fragment transaction is a batch of operations — add, remove, replace, hide/show, detach/attach — that the FragmentManager applies atomically. The subtlety is that commit doesn't run synchronously; it posts the work to the main thread's message queue, so the views aren't actually swapped until that runs. If I need them applied right now I call executePendingTransactions, but never from a background thread, and I avoid commit after onSaveInstanceState unless I deliberately allow state loss."

Fragment transactions are operations that add, remove, replace, or show and hide Fragments. They are batched together and committed atomically, which means either all operations in the transaction happen or none of them do.

supportFragmentManager.commit {
    setCustomAnimations(R.anim.slide_in, R.anim.slide_out, R.anim.slide_in, R.anim.slide_out)
    replace(R.id.container, DetailFragment.newInstance(id), "detail_tag")
    addToBackStack("detail") // null = anonymous, named = can pop to by name
}

Transaction operations:

  • add: Adds a Fragment to the container; any existing Fragments stay in place.
  • remove: Removes a Fragment; onDestroyView and onDestroy are called.
  • replace: Removes all existing Fragments in the container and adds the new one.
  • hide/show: Hides or shows a Fragment without triggering lifecycle callbacks; the view stays in the hierarchy.
  • detach/attach: Detaches (destroys the view but the Fragment instance lives on) and attaches (recreates the view).

Pending transactions: Transactions are not immediately executed — they are scheduled on the main thread's message queue. Use executePendingTransactions() to force immediate, synchronous execution on the main thread. Never call this from a background thread.

Under the hood

A FragmentTransaction is really a BackStackRecord — an ordered list of Op objects, each holding a command code (OP_ADD, OP_REPLACE, OP_HIDE, etc.) and the target Fragment. commit() doesn't touch any views; it calls FragmentManager.enqueueAction, which appends a runnable to mPendingActions and posts mExecCommit to the main Handler. When that runnable runs, execPendingActions pops the records and FragmentManager "optimizes" them by reordering and cancelling out redundant ops (the reordered-transactions behavior), then moves each affected Fragment through the state machine via moveToState. executePendingTransactions() just drains that queue inline on the calling thread — which must be the main thread, since it manipulates views. commit() checks mStateSaved/mStopped and throws IllegalStateException: Can not perform this action after onSaveInstanceState unless you used commitAllowingStateLoss().

commit() ──► enqueueAction(BackStackRecord) ──► mPendingActions.add(...)
        └──► mHost.handler.post(mExecCommit)
                                   │  (main-thread message)
                                   ▼
                       execPendingActions() ──► optimize/reorder Ops ──► moveToState(fragment)

Fragment Back Stack

🎤 Say it out loud (~30–45s): "addToBackStack records a transaction so that pressing Back reverses it and restores the prior state. The thing to be precise about: with addToBackStack the replaced Fragment's view is destroyed but the instance survives on the back stack, so Back can rebuild it; without it, the Fragment is gone for good. I also keep the popBackStack variants straight — the async one posts to the queue, popBackStackImmediate runs synchronously, and the INCLUSIVE flag controls whether the named entry itself gets popped."

addToBackStack(name) records the transaction on the Fragment back stack. Pressing Back reverses it — restoring the previous state.

// Add to back stack — Back press will reverse this replace
fragmentManager.commit {
    replace(R.id.container, DetailFragment())
    addToBackStack("detail")
}

// Pop back stack programmatically
fragmentManager.popBackStack()                          // async
fragmentManager.popBackStackImmediate()                 // sync (main thread)
fragmentManager.popBackStack("detail", 0)              // pop to "detail" inclusive
fragmentManager.popBackStack("detail", FragmentManager.POP_BACK_STACK_INCLUSIVE) // pop "detail" too

Gotcha: If you call replace without addToBackStack, the replaced Fragment is destroyed and its instance is gone — pressing Back will not bring it back. With addToBackStack, the Fragment's view is destroyed but the instance is retained, so Back can restore it.

Under the hood

The back stack is FragmentManager.mBackStack, an ArrayList<BackStackRecord>. Calling addToBackStack(name) flips mAddToBackStack = true on the record and stores the optional name; on commit the record is pushed onto that list and assigned an index. A Fragment referenced by a record kept on the back stack is moved only down to CREATED (view destroyed at onDestroyView) rather than removed, and its mSavedFragmentState/saved-instance bundle is retained so the view can be rebuilt on pop. popBackStack() enqueues a PopBackStackState action processed on the next main-thread loop, while popBackStackImmediate() enqueues it and then immediately calls execPendingActions. The integer flags select named-pop semantics: 0 pops everything above the entry, and POP_BACK_STACK_INCLUSIVE (value 1) also removes the named entry itself. Popping replays each Op in reverse — an OP_REPLACE is undone by re-adding the previous Fragment and re-tearing-down the current one.

Navigation Component

🎤 Say it out loud (~30–45s): "Jetpack Navigation sits on top of Fragment transactions and lets me navigate by destination ID against a graph instead of hand-writing replace calls. I get type-safe args through Safe Args, automatic back-stack management, declarative deep links and animations. Under the hood it's still a NavHostFragment delegating to a FragmentNavigator that runs the same transactions — so the FragmentManager rules still apply, and one gotcha is that calling navigate twice fast can throw or double-navigate if you don't guard the current destination."

Jetpack Navigation abstracts Fragment transactions into a graph-based navigation system, so you navigate by destination rather than by manually writing replace/add transactions.

// Navigate
findNavController().navigate(R.id.action_home_to_detail, bundleOf("userId" to id))

// Navigate with NavDirections (type-safe, requires Safe Args plugin)
val action = HomeFragmentDirections.actionHomeToDetail(userId = id)
findNavController().navigate(action)

// Navigate up
findNavController().navigateUp()

// Pop to a destination
findNavController().popBackStack(R.id.homeFragment, inclusive = false)

Benefits over manual transactions:

  • Type-safe argument passing with Safe Args.
  • Deep links handled automatically via <deepLink> declarations in the nav graph.
  • Back stack managed automatically — no manual addToBackStack calls.
  • Transition animations declared in the graph.
  • Visual editor in Android Studio for seeing the whole flow at a glance.

NavHostFragment: The Fragment that hosts the navigation graph. Declared in the layout:

<FragmentContainerView
    android:name="androidx.navigation.fragment.NavHostFragment"
    app:navGraph="@navigation/nav_graph"
    app:defaultNavHost="true" />

Under the hood

findNavController() walks up the view tree (via a tag set on the NavHostFragment's view) to find the NavController. The controller owns a NavBackStackEntry deque — each entry pairs a NavDestination with its arguments and its own Lifecycle, ViewModelStore, and SavedStateRegistry, which is why nav-scoped ViewModels work. navigate() resolves the action/destination, then delegates to the registered Navigator for that destination type; FragmentNavigator.navigate ultimately issues a normal FragmentTransaction (replace + addToBackStack) against the NavHostFragment's child FragmentManager. Safe Args is a Gradle plugin that code-generates Directions and Args classes at build time, packing/unpacking a Bundle so there's no runtime reflection. defaultNavHost="true" registers an OnBackPressedCallback with the host Activity's OnBackPressedDispatcher so system Back pops the nav back stack first.

findNavController() ─► NavController
   └─ mBackQueue: ArrayDeque<NavBackStackEntry>   // each entry = destination + Lifecycle + ViewModelStore
        navigate(id) ─► Navigator<Destination> ─► FragmentNavigator
                                                      └─ childFragmentManager.commit { replace(...); addToBackStack(...) }

View Binding Cleanup

🎤 Say it out loud (~30–45s): "View binding holds strong references to the inflated view tree, and because a Fragment can outlive its view on the back stack, holding that binding past onDestroyView leaks the entire destroyed view hierarchy and its Context. So the pattern is a nullable backing field that I set in onCreateView and explicitly null out in onDestroyView. The non-obvious part is that even though the views are gone, the surviving Fragment instance keeps the field alive, so GC can't reclaim anything until I clear it."

The problem: View binding references (and findViewById references) hold a strong reference to views. Views are destroyed in onDestroyView, but the Fragment instance may live on in the back stack. If the binding property is not cleared, the old destroyed view hierarchy is held in memory — a memory leak.

The solution: Always null out the binding reference in onDestroyView.

class MyFragment : Fragment(R.layout.fragment_my) {
    
    private var _binding: FragmentMyBinding? = null
    private val binding get() = _binding!! // safe to use only between onCreateView and onDestroyView
    
    override fun onCreateView(
        inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?
    ): View {
        _binding = FragmentMyBinding.inflate(inflater, container, false)
        return binding.root
    }
    
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        binding.button.setOnClickListener { /* ... */ }
    }
    
    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null // CRITICAL: prevents memory leak
    }
}

Why this is a leak: The Fragment instance — which holds _binding — is retained on the back stack. The _binding field holds a reference to the now-destroyed view hierarchy, including all View objects and their Context. That chain of references prevents the garbage collector from reclaiming any of those views.

Under the hood

The generated FragmentMyBinding is a plain class holding a strong field for the root View plus one strong field per id-bearing view, produced at build time by the View Binding annotation-processor-equivalent step in AGP. Each View in turn references its parent and its mContext, so a single retained binding root keeps the whole inflated tree — and the Activity Context it was inflated with — reachable through the GC root graph. A Fragment kept on the back stack is itself reachable from the FragmentManager's mActive/back-stack structures, so it acts as a live GC root for whatever _binding points at. Nulling _binding in onDestroyView cuts the only remaining strong edge from the surviving instance to the dead view tree, letting ART's concurrent collector reclaim it; tools like LeakCanary detect the failure mode by watching destroyed Fragment views with a WeakReference and forcing a GC to confirm they were not collected.

FragmentManager (GC root)
   └─► MyFragment instance (on back stack, survives)
          └─► _binding ──► root View ──► child Views ──► Context   // leaked if not nulled

Fragment Result API

🎤 Say it out loud (~30–45s): "The Fragment Result API lets two fragments pass a result Bundle through their shared FragmentManager using a string key, so neither needs a direct reference to the other or a casted interface. The sender calls setFragmentResult, the receiver registers a setFragmentResultListener, and the framework holds the result until the receiver is at least STARTED. The gotcha is scoping: a child talking to its parent has to use the parent's childFragmentManager, and there's only one listener per key, so the last registration wins."

The Fragment Result API is the modern way for Fragments to communicate results back to their parent or sibling Fragments, without requiring direct Fragment-to-Fragment references or casting the parent as an interface.

// In the child Fragment (sender)
setFragmentResult("requestKey", bundleOf("selected_date" to date))

// In the parent Fragment (receiver) — registered in onCreate or onViewCreated
setFragmentResultListener("requestKey") { key, bundle ->
    val date = bundle.getString("selected_date")
    // handle result
}

Key properties:

  • Results are delivered to the listener when the receiving Fragment is at least in the STARTED state.
  • If the Fragment is not started when the result is set, the result is held and delivered once it becomes STARTED.
  • Only one active listener per key — the last registered listener wins.
  • Works between a child and its parent by using childFragmentManager on the parent side.

Alternative (legacy pattern): interface callbacks from Fragment to Activity or parent Fragment. This is fragile because it requires casting and creates tight coupling between the two.

Under the hood

The FragmentManager keeps two maps keyed by requestKey: one of stored results (Map<String, Bundle>) and one of registered listeners (Map<String, LifecycleAwareResultListener>). setFragmentResult either dispatches immediately if a STARTED listener exists, or parks the Bundle in the results map. setFragmentResultListener wraps your callback in a LifecycleEventObserver attached to the owner's Lifecycle; on the ON_START event it checks the results map, fires any pending result, and on ON_DESTROY it removes itself — which is why each key holds only one live listener and why the Bundle survives configuration changes (it lives in the FragmentManager's saved state, not the Fragment instance).

setFragmentResult(key, bundle)
   ├─ listener registered & STARTED? → invoke now
   └─ else → mResults[key] = bundle  (held)

setFragmentResultListener(key) {...}
   └─ register LifecycleEventObserver
        on ON_START → if mResults[key] != null → invoke, then clear
        on ON_DESTROY → unregister

Child Fragments

🎤 Say it out loud (~30–45s): "A Fragment can host its own nested fragments through its childFragmentManager, which is the right tool for tab containers, ViewPagers, or any reusable sub-screen. The key discipline is to always use childFragmentManager, never the Activity's supportFragmentManager, or you break the lifecycle and save-state hierarchy. And the back button doesn't automatically pop the child back stack — the dispatcher only knows about the Activity's manager — so I have to wire that up myself through OnBackPressedDispatcher."

A Fragment can host its own childFragmentManager to manage nested Fragments. This is the right approach for view pagers, tab layouts inside a Fragment, and any case where you need modular, reusable screen segments.

class TabContainerFragment : Fragment() {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        childFragmentManager.commit {
            replace(R.id.tab_container, FirstTabFragment())
        }
    }
}

Gotchas with child fragments:

  • Always use childFragmentManager for Fragments nested inside a Fragment — never supportFragmentManager, which attaches to the Activity's manager and breaks the lifecycle hierarchy.
  • A DialogFragment shown from inside a Fragment should use show(childFragmentManager, tag).
  • The system Back button does not automatically pop childFragmentManager. You must manually intercept Back and call childFragmentManager.popBackStack(), or wire it up through OnBackPressedDispatcher.

Under the hood

Each Fragment owns a FragmentManager instance created lazily via getChildFragmentManager(), distinct from the host Activity's supportFragmentManager. They form a tree: the child manager is initialized with a FragmentHostCallback pointing at the parent Fragment, so child lifecycle states are clamped to the parent's — a child can never be RESUMED while its parent is only STARTED. State save/restore walks this tree: the parent serializes its child manager's FragmentManagerState (back stack records, saved fragment states) into the parent's own saved-state Bundle, which is why mixing in supportFragmentManager corrupts restoration — the child fragments get attached to the wrong manager and the parent has nothing to restore. The back stack itself is just an ArrayList<BackStackRecord> per manager, and OnBackPressedDispatcher only registers a callback for the Activity-level manager automatically.

commit vs commitNow

🎤 Say it out loud (~30–45s): "commit() is asynchronous — it enqueues the transaction onto the main thread's message queue and runs on a later dispatch, and it supports addToBackStack. commitNow() runs the transaction synchronously, right then on the main thread, which is useful when the next line of code needs the fragment to already exist, but it deliberately forbids addToBackStack because synchronous execution would reorder the back stack unpredictably. There's also commitAllowingStateLoss, which swallows the after-onSaveInstanceState crash but risks losing your transaction if the process dies, so I treat it as a last resort."

commit(): Schedules the transaction asynchronously on the main thread's message queue. The actual transaction executes on the next frame or message dispatch.

commitNow(): Executes the transaction immediately on the calling thread, which must be the main thread. Does NOT work with addToBackStack — it throws IllegalStateException if you try.

commitAllowingStateLoss(): Behaves like commit() but suppresses the IllegalStateException that occurs when the Activity's state has already been saved — that is, after onSaveInstanceState. Use with caution: if the Activity is killed after a state loss, your transaction will not be restored.

// Typical — async, safe
fragmentManager.commit { replace(R.id.container, SomeFragment()) }

// Immediate execution — no back stack possible
fragmentManager.commitNow { replace(R.id.container, SomeFragment()) }

// After onSaveInstanceState (e.g., from a callback) — UI inconsistency risk
fragmentManager.commitAllowingStateLoss { replace(R.id.container, SomeFragment()) }

When to use commitNow: When subsequent code in the same method depends on the transaction having already completed — for example, you immediately find the new Fragment by tag. This is rare; most cases do not need synchronous execution.

Under the hood

commit() calls FragmentManager.enqueueAction, which appends a Runnable (a Op-list executor) to mPendingActions and posts mExecCommit onto the main thread Handler. On the next loop iteration execPendingActions drains the queue and moveToState walks each affected fragment through its lifecycle. commitNow() skips the queue: it calls execSingleAction, which first flushes any already-pending actions, then executes this transaction's ops inline on the current (main) thread. The addToBackStack prohibition is structural — a back stack entry is identified by an index assigned at commit time (mBackStack), and reentrant synchronous commits would interleave indices nondeterministically, so the API asserts !mAddToBackStack. The state-loss check is the boolean mStateSaved/mStopped: commit() throws when it's set after onSaveInstanceState, and commitAllowingStateLoss simply passes allowStateLoss = true to bypass that guard.

commit()      → mPendingActions.add(op); handler.post(execCommit)  [later dispatch]
commitNow()   → execPendingActions(); execSingleAction(op)         [inline, sync]
addToBackStack + commitNow → IllegalStateException (checkStateLoss / assert)

Fragment Interview Angles

Q: Fragment lifecycle vs view lifecycle — why does it matter?

"The Fragment instance can outlive its views when it is on the back stack. If I observe LiveData or collect a Flow using this — the Fragment as LifecycleOwner — those observers are tied to the Fragment's lifetime, not the view's. When the Fragment goes to the back stack and comes back, a brand-new view is created but the observer is never re-registered because it never died. And if that observer references view objects directly, it is now pointing at destroyed views. The fix is to always use viewLifecycleOwner for anything that touches UI — that ensures each observer is created fresh with the new view and torn down with it."

Q: Why clear binding in onDestroyView()?

"The Fragment instance lives on in the back stack, but the view hierarchy is destroyed. If I don't null out _binding, the binding field is still holding a reference to all those destroyed View objects and their Context. That chain of references prevents garbage collection of the entire view tree — all the Drawables, bitmaps, and whatever else the views were holding on to. The _binding = null in onDestroyView is the idiomatic way to break that reference and let the GC do its job."

Q: Common Fragment memory leaks.

  1. Not clearing view binding in onDestroyView.
  2. Using this instead of viewLifecycleOwner for LiveData observers.
  3. Storing a reference to the Activity or Fragment in a companion object or static field.
  4. Registering callbacks — for example, ViewPager2.registerOnPageChangeCallback — without unregistering them in onDestroyView.
  5. Passing this (the Fragment) as a listener to a view that outlives the Fragment.
  6. Child Fragments holding a strong reference back to the parent via parentFragment.

Q: commit vs commitNow.

"commit() is asynchronous — it gets scheduled on the main thread's message queue, and it works fine with addToBackStack. commitNow() is synchronous — it executes immediately on the calling thread, but it cannot be combined with addToBackStack at all. The rule is: use commit() by default, and only reach for commitNow() when the code immediately following depends on the transaction having already completed."

9.3 Services

Started Service

🎤 Say it out loud (~30–45s): "A started service runs independently of whoever launched it — once it's going it survives the caller's death and keeps running until it calls stopSelf or someone calls stopService. The return value of onStartCommand controls restart behavior: START_STICKY, START_NOT_STICKY, or START_REDELIVER_INTENT. The modern gotcha is background limits — on Oreo and up you can't just startService from the background; you have to use startForegroundService and then call startForeground with a notification within about five seconds or the system crashes you with an ANR-style exception."

A started Service is launched by startService(intent) or startForegroundService(intent) and runs independently of the caller. Even if the starting component is destroyed, the service keeps running until it stops itself or is stopped externally.

// Start
startService(Intent(this, DownloadService::class.java).apply {
    putExtra("url", downloadUrl)
})

// Stop from outside
stopService(Intent(this, DownloadService::class.java))

// Stop itself (preferred)
class DownloadService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val url = intent?.getStringExtra("url") ?: return START_NOT_STICKY
        serviceScope.launch {
            download(url)
            stopSelf(startId) // stops only if no new starts have come in
        }
        return START_REDELIVER_INTENT
    }
    override fun onBind(intent: Intent?): IBinder? = null
}

Under the hood

startService doesn't run the service in your process directly — it sends a Binder transaction to the ActivityManagerService (AMS) in system_server, which looks up the <service> in the target package, forks/binds the hosting process if needed, and schedules onStartCommand via the app's ApplicationThread back on its main-thread Handler (H). Each delivery gets a monotonically increasing startId; stopSelf(startId) only tears down if that id matches the most recent start, which prevents a stale stop from killing a service that received newer work. The onStartCommand return value is recorded by AMS in the ServiceRecord and consulted on process death: START_NOT_STICKY discards the record, START_STICKY re-creates with a null intent, and START_REDELIVER_INTENT re-delivers the last intent. For startForegroundService, AMS starts a watchdog timer (~5s) and throws a ForegroundServiceDidNotStartInTimeException / RemoteServiceException if startForeground() isn't called in time.

Bound Service

🎤 Say it out loud (~30–45s): "A bound service exposes an IBinder interface to clients that connect with bindService, and it lives only as long as at least one client is bound — when the last one unbinds, it's destroyed, unless it was also started. Same-process binding is cheap because onServiceConnected hands you the actual Binder object and you just cast it. The gotcha is lifecycle hygiene: bind in onStart and unbind in onStop, and remember the connection callbacks aren't symmetric — onServiceDisconnected only fires on an unexpected crash, not on a normal unbindService."

A bound Service is connected to by one or more clients via bindService(intent, connection, flags). It lives as long as at least one client is bound — when all clients unbind, the service is destroyed, unless it was also started independently.

class MusicService : Service() {
    inner class MusicBinder : Binder() {
        fun getService(): MusicService = this@MusicService
    }
    private val binder = MusicBinder()
    override fun onBind(intent: Intent?): IBinder = binder
    fun play(songId: String) { /* ... */ }
}

// In Activity
private var musicService: MusicService? = null
private val connection = object : ServiceConnection {
    override fun onServiceConnected(name: ComponentName?, service: IBinder?) {
        val binder = service as MusicService.MusicBinder
        musicService = binder.getService()
    }
    override fun onServiceDisconnected(name: ComponentName?) {
        musicService = null
    }
}

override fun onStart() {
    super.onStart()
    bindService(Intent(this, MusicService::class.java), connection, Context.BIND_AUTO_CREATE)
}

override fun onStop() {
    super.onStop()
    unbindService(connection)
    musicService = null
}

Cross-process binding: For services running in different processes, use AIDL (Android Interface Definition Language) or Messenger to communicate across the process boundary.

Under the hood

bindService routes through AMS, which tracks each binding as a ConnectionRecord and reference-counts how many clients are bound; the service is destroyed when that count hits zero (and it wasn't started). Within the same process, the IBinder delivered to onServiceConnected is the literal Binder instance returned by onBind — no marshalling happens, so the cast to MusicBinder works directly. Across processes it's a BinderProxy: AMS hands the client a proxy whose method calls become transact() Binder kernel-driver IPC, which is exactly why AIDL exists — it generates Stub/Proxy classes that marshal arguments into a Parcel, copy them across the kernel binder buffer (capped around 1MB per transaction), and unmarshal on the other side. onServiceDisconnected is invoked by the binder DeathRecipient mechanism: it only fires when the remote process dies unexpectedly, never on an orderly unbindService.

same process : onServiceConnected(binder)  → binder IS the MusicBinder (no IPC)
cross process: onServiceConnected(proxy)   → BinderProxy → transact() → Parcel → kernel → Stub
death        : remote crash → linkToDeath → onServiceDisconnected()

Foreground Service

🎤 Say it out loud (~30–45s): "A foreground service is for work the user is actively aware of — music, navigation, a live workout — so it shows a mandatory ongoing notification and the system treats it as high priority, almost as if there's a visible Activity. The gotcha interviewers love is the contract: once you call startForegroundService() you have a hard five-second window to call startForeground() with a notification, or the system throws an ANR-style crash. And since Android 14 you also have to declare a foregroundServiceType and hold the matching permission, or the start is rejected outright."

A foreground Service performs work that is noticeable to the user and must show a persistent notification while it runs. It has elevated priority and is much less likely to be killed by the system than a background service.

Required since Android 8.0 (API 26):

  • Must call startForeground(notificationId, notification) within 5 seconds of being started, or the system will crash the app.
  • The caller must use startForegroundService() instead of startService().
class LocationService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = buildNotification()
        startForeground(NOTIFICATION_ID, notification)
        startLocationUpdates()
        return START_STICKY
    }
    
    private fun buildNotification() = NotificationCompat.Builder(this, CHANNEL_ID)
        .setContentTitle("Tracking your location")
        .setSmallIcon(R.drawable.ic_location)
        .setOngoing(true)
        .build()
    
    override fun onBind(intent: Intent?): IBinder? = null
}

Under the hood

When you call startForegroundService(), ActivityManagerService (AMS) in system_server records the start and arms a watchdog. The ServiceRecord is flagged as requiring a foreground transition, and AMS posts a delayed message (the 5-second timer) onto its own handler. The component's process is told to run onCreate/onStartCommand via the ApplicationThread binder. When your code calls startForeground(), that routes back through ActivityManager.getService().setServiceForeground(...), which cancels the pending timeout and asks NotificationManagerService to post the ongoing notification. If the timer fires first, AMS calls into the app to crash it with a ForegroundServiceDidNotStartInTimeException (a RemoteServiceException subtype).

startForegroundService()
  └─> AMS.startService() → ServiceRecord(fgRequired=true)
        ├─ schedule TIMEOUT msg (+5s) on AMS handler
        └─ schedule onCreate/onStartCommand on app process
app: startForeground(id, notif)
  └─> AMS.setServiceForeground() → cancel TIMEOUT, NMS posts notification
[if 5s elapses first] → AMS posts crash to app's main thread

On Android 14+ the foregroundServiceType is verified at this transition: AMS checks the manifest-declared type bits and the runtime permission grant for that type (e.g. ACCESS_FINE_LOCATION for location); a mismatch throws SecurityException or MissingForegroundServiceTypeException.

Android 14+ foreground service types: You must declare foregroundServiceType in the manifest and request the appropriate type-specific permissions:

<service
    android:name=".LocationService"
    android:foregroundServiceType="location" />

Available types: camera, connectedDevice, dataSync, health, location, mediaPlayback, mediaProjection, microphone, phoneCall, remoteMessaging, shortService, specialUse, systemExempted.

Background Service Restrictions

🎤 Say it out loud (~30–45s): "Starting with Android 8, the OS stopped letting backgrounded apps spin up arbitrary background services — if your app has no visible UI and you call startService(), you get an IllegalStateException. The reasoning is battery and memory: free-running background services were a top cause of drain. So the modern answer is to use startForegroundService() if the user genuinely needs to know about the work, or WorkManager for anything deferrable. There's a layered set of follow-on restrictions too — exact alarms need a permission on 12, posting notifications needs POST_NOTIFICATIONS on 13, and 14 tightens background foreground-service starts further."

Android 8.0 (API 26) introduced severe restrictions on background Services:

  • Apps in the background — meaning they have no visible Activity — cannot start background services. Calling startService() in that state throws IllegalStateException.
  • The solution is to use startForegroundService() for work that genuinely needs to be a Service, or WorkManager for deferrable background work.
  • The system will kill background services aggressively to reclaim memory.

Android 12+ (API 31): Exact alarm restrictions. Apps must request the SCHEDULE_EXACT_ALARM permission. Android 13+ (API 33): Posting notifications requires the POST_NOTIFICATIONS permission. Android 14+ (API 34): Further restrictions on starting foreground services from the background.

Under the hood

AMS tracks every app's process state on a numeric importance scale (ActivityManager.RunningAppProcessInfo.IMPORTANCE_*, internally ProcessRecord.setProcState). When startService() is invoked, AMS consults the caller's current proc-state. If the caller is below the foreground threshold — roughly anything weaker than a visible/foreground process and outside a temp-allowlist window — ActiveServices.startServiceLocked() rejects the start and the binder call surfaces an IllegalStateException in the calling process. A short temporary allowlist is granted by certain triggers (a high-priority FCM message, a notification action, an exact alarm firing), which briefly bumps the proc-state so a start is permitted.

app.startService(i)
  → AMS.ActiveServices.startServiceLocked(caller)
      procState = caller.setProcState
      if (procState worse than FOREGROUND && !inTempAllowlist)
          throw IllegalStateException("Not allowed to start service ...")

WorkManager sidesteps this entirely: instead of holding a live process, it persists a WorkSpec row in its Room DB and schedules execution through JobScheduler (API 23+), so JobSchedulerService in system_server — not your process — owns the timing and constraint evaluation (Doze, network, charging), waking your app only when the job is actually dispatchable.

Service Lifecycle

🎤 Say it out loud (~30–45s): "A Service has two distinct lifecycles depending on how it's used. Started services go onCreate once, then onStartCommand for every startService call, and they keep running until something calls stopSelf or stopService. Bound services go onCreate, onBind, and live only while clients are connected — when the last one unbinds, they're destroyed. The subtle part interviewers probe is the combined case: if a service is both started and bound, it won't die until it's both stopped AND fully unbound — both conditions have to be satisfied, otherwise you leak a running service."

Started service lifecycle:

startService() / startForegroundService()
    │
onCreate()       ← called once; initialize resources
    │
onStartCommand() ← called for every startService() call
    │
[Service running]
    │
stopSelf() / stopService()
    │
onDestroy()      ← cleanup

Bound service lifecycle:

bindService()
    │
onCreate()
    │
onBind()         ← return IBinder
    │
[Clients connected]
    │
onUnbind()       ← called when last client unbinds; override to allow re-binding
    │
onDestroy()

Combined (started + bound): The service stays alive until it has been both stopped and unbound — both conditions must be satisfied.

Under the hood

AMS represents each service with a ServiceRecord and decides destruction in ActiveServices.bringDownServiceIfNeededLocked(). That method ANDs two pieces of state: startRequested (set true by startServiceLocked, cleared when the last startId is stopped) and the connection set connections (populated per bindService, drained per unbindService). The service is only torn down when startRequested == false AND there are no remaining bindings — which is exactly why the combined service survives until both conditions hold.

ServiceRecord {
  startRequested : Boolean   // started path
  connections    : Map<IBinder, ConnectionRecord>  // bound path
}
bringDownServiceIfNeededLocked():
  if (!startRequested && connections.isEmpty())  → bringDownServiceLocked() → onDestroy()

Each lifecycle callback is not invoked directly — AMS sends scheduling commands over the IApplicationThread binder interface to your process, where ActivityThread's main-thread Handler (H) processes messages like CREATE_SERVICE, SERVICE_ARGS, BIND_SERVICE, UNBIND_SERVICE, and STOP_SERVICE, calling the matching method on your Service instance on the main thread.

onStartCommand and Return Values

🎤 Say it out loud (~30–45s): "onStartCommand runs on the main thread for every startService call, and its return value tells the system what to do if the process gets killed. START_NOT_STICKY means don't bother recreating; START_STICKY recreates but hands you a null intent — good for ongoing services like music; and START_REDELIVER_INTENT recreates and redelivers the last intent, which is what you want for transactional work like a download so you don't lose the work spec. The detail people forget is startId: you should call stopSelf(startId) rather than bare stopSelf(), so you don't kill the service out from under a newer start request that arrived while you were working."

onStartCommand(intent: Intent?, flags: Int, startId: Int): Int

  • Called on the main thread for every startService() call.
  • intent: the Intent passed to startService(). Can be null if the system recreates the service after a kill with START_STICKY.
  • flags: START_FLAG_RETRY if a previous start attempt failed, or START_FLAG_REDELIVERY for redelivered intents from START_REDELIVER_INTENT.
  • startId: a unique identifier for this specific start request. Pass it to stopSelf(startId) to avoid stopping the service prematurely if multiple starts have come in.

Return values:

Constant Behavior after system kill
START_NOT_STICKYService is NOT recreated. Good for tasks where data can be re-fetched later.
START_STICKYService IS recreated, but intent will be null. Good for ongoing services that do not depend on the original intent.
START_REDELIVER_INTENTService IS recreated with the last Intent redelivered. Good for download/upload tasks where the intent carries the work spec.
override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
    when (intent?.action) {
        ACTION_DOWNLOAD -> startDownload(intent.getStringExtra("url"))
        ACTION_CANCEL -> cancelDownload()
    }
    return START_REDELIVER_INTENT // safe: if killed mid-download, redelivers URL
}

Under the hood

AMS keeps a list of ServiceRecord.StartItem entries — one per startService call, each tagged with the monotonically increasing startId it issued. Your return code is stored as ServiceRecord.lastStartId's disposition and dictates the restart policy. For START_REDELIVER_INTENT, AMS retains the StartItem (including its intent) in a "delivered but not finished" state until you call stopSelf(startId), which invokes serviceDoneExecuting/stopServiceTokenLocked and lets AMS discard that item. If the process dies first, AMS re-launches the service and replays the retained intents with START_FLAG_REDELIVERY set.

startService(A) → AMS issues startId=1, StartItem{id=1, intent=A}
startService(B) → AMS issues startId=2, StartItem{id=2, intent=B}
service finishes work for A → stopSelf(1)  // removes only StartItem 1
   → StartItem 2 still pending ⇒ AMS keeps service alive
stopSelf() with no id ⇒ would clear ALL items ⇒ B's work lost

This is the mechanism behind the stopSelf(startId) guidance: bare stopSelf() clears every outstanding StartItem regardless of startId, so a concurrent start that arrived after you began processing gets silently dropped.

Service vs WorkManager

🎤 Say it out loud (~30–45s): "I frame it as two questions: does the work need to run right now, and does the user need to be aware of it? If yes — music, VoIP, live location — it's a foreground Service. If the work is deferrable, must survive process death and reboots, or depends on constraints like Wi-Fi or charging, it's WorkManager, because WorkManager persists its queue to a database and delegates scheduling to JobScheduler so it respects Doze and guarantees retried execution. Given how locked-down background services are since Android 8, WorkManager is my default for anything that isn't genuinely immediate and user-visible."

This is one of the most common design-decision questions in Android interviews, and the answer is not "always use WorkManager."

Use Service when: work must run right now, potentially indefinitely, and the user should be aware of it via a foreground service notification. Examples: music playback, VoIP, live location sharing.

Use WorkManager when: work can be deferred, must survive process death and device reboots, depends on constraints like waiting for Wi-Fi, or is a one-shot or periodic background task. Examples: syncing the database, uploading photos, sending analytics.

When to run in another process: declare android:process=":myservice" in the manifest. There are three reasons to do this — first, crash isolation: a crash in the service process won't kill the main app process. Second, a separate memory budget so the service doesn't push the main app out of memory. Third, enforcing architectural separation. The downsides are IPC overhead for every call and the fact that you cannot share in-memory singletons across processes.

Under the hood

A Service holds a live ProcessRecord in your app process for as long as it runs; AMS only knows it's "alive" while the process exists, so an OOM-kill or reboot wipes it. WorkManager decouples the intent to do work from the process that does it: enqueue() writes a WorkSpec row (state, constraints, backoff policy, input Data) into its bundled Room database, then registers the job with a scheduler. On modern Android that scheduler is JobScheduler, living in system_server; it persists job records and evaluates constraints (network, idle, charging, Doze maintenance windows) independently of your app. When constraints are met, JobScheduler binds to WorkManager's SystemJobService, which spins up the WorkerFactory, runs your Worker.doWork(), and writes the result back to the DB.

workManager.enqueue(req)
  └─> WorkSpec row → Room DB (survives kill/reboot)
  └─> Scheduler.schedule() → JobScheduler (system_server) persists job
[reboot] → system re-reads jobs; WorkManager re-syncs DB ↔ JobScheduler
constraints met → JobScheduler binds SystemJobService → Worker.doWork()
  └─> result (SUCCESS/RETRY/FAILURE) written back to WorkSpec row

Because the DB row is the source of truth, a RETRY result re-applies the BackoffPolicy to compute the next WorkSpec.calculateNextRunTime(), giving the "guaranteed, retried with backoff" property the table claims — something a raw Service has no equivalent of.

Services Interview Angles

Q: Service vs WorkManager — when do you choose each?

"The question is really: does this work need to happen right now, and does the user need to know about it? If yes — music playback, VoIP, live location — that's a foreground Service. If the work is deferrable, needs to survive process death and device reboots, or depends on constraints like waiting for Wi-Fi, that's WorkManager. And for Android 8.0 and above, background Services are so heavily restricted that WorkManager is the right default for almost any background task that doesn't need to be immediate."

Q: Started vs bound service.

"There are two fundamental shapes a Service can take. A started Service runs independently — you fire it off with startService and it keeps going until it stops itself or you call stopService. There's no ongoing connection; it's fire-and-forget. A bound Service is different — it exposes an IBinder interface and lives only as long as at least one client is bound to it. When all clients unbind, it gets destroyed. The interesting case is when you combine them: a Service that is both started and bound will outlive its clients and only die when it's stopped. Use started for work that needs to run to completion; use bound for any situation where you need a live client-server interaction, either within the same process or across processes."

Q: Foreground service restrictions.

"There are several layers here. At the basics: the service must show a persistent notification and must call startForeground() within 5 seconds of being started or the system crashes it. Since Android 14, you also must declare foregroundServiceType in the manifest — for example, location, camera, mediaPlayback — and you must hold the appropriate permissions for that type. And since Android 12, apps generally cannot start foreground services from the background at all; the main exemption is high-priority FCM notifications, which can grant a brief window to start a foreground service."

9.4 BroadcastReceiver

A BroadcastReceiver responds to system-wide or app-specific broadcast messages delivered as Intents. The defining constraint is that it has a very short execution window — roughly 10 seconds on the main thread — and the process may be killed immediately after onReceive() returns.

Manifest-Registered vs Context-Registered

🎤 Say it out loud (~30–45s): "A manifest-registered receiver is static — it's declared in the manifest and the system can cold-start my process just to deliver the broadcast, even if the app isn't running. A context-registered receiver is dynamic — I register it in code and it's only alive while the registering component is, so I must unregister it or I leak. The big gotcha is Android 8.0: static receivers can no longer get most implicit broadcasts because of background execution limits, so for runtime-only signals like connectivity I use a dynamic receiver, and for app-startup work I lean on the small exempt whitelist or explicit broadcasts."

Manifest-registered (static receiver):

  • Declared in AndroidManifest.xml.
  • The app does not need to be running to receive the broadcast — the system can launch it just to deliver the Intent.
  • Since Android 8.0 (API 26): cannot receive most implicit broadcasts via manifest declaration, due to background execution limits. Only a small set of system broadcasts are exempt — and even ACTION_BOOT_COMPLETED has its own restrictions on newer APIs.
<receiver android:name=".BootReceiver" android:exported="false">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>

Context-registered (dynamic receiver):

  • Registered in code via context.registerReceiver(receiver, intentFilter).
  • Active only while the registering component — Activity, Service — is alive.
  • Not affected by the Android 8.0 implicit broadcast restrictions.
  • Must be unregistered in the matching lifecycle callback to avoid leaks — register in onStart, unregister in onStop.
private val networkReceiver = object : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        updateNetworkStatus()
    }
}

override fun onStart() {
    super.onStart()
    registerReceiver(
        networkReceiver,
        IntentFilter(ConnectivityManager.CONNECTIVITY_ACTION),
        RECEIVER_NOT_EXPORTED // API 33+ requirement for non-exported receivers
    )
}

override fun onStop() {
    super.onStop()
    unregisterReceiver(networkReceiver)
}

Under the hood

Both kinds of receiver are ultimately tracked by the system's ActivityManagerService (AMS) and routed through your process's ActivityThread. The difference is where the IntentFilter lives. For a static receiver, the filter is parsed at install time by the PackageManager from the manifest and stored persistently, so AMS can match a broadcast against an app that has no running process — it then forks/cold-starts the process via Zygote, instantiates the BroadcastReceiver class fresh, and hands it a short-lived Context. For a dynamic receiver, registerReceiver does a Binder call into AMS that stores a live ReceiverList keyed by an IIntentReceiver Binder token tied to your process; the filter only exists in RAM, so it vanishes if the process dies and isn't subject to the manifest-broadcast policy gate that AMS applies at install/dispatch time.

sendBroadcast(intent)
   └─ Binder → ActivityManagerService.broadcastIntent()
        ├─ match against static filters (from PackageManager, persisted)   ──> may cold-start process
        └─ match against dynamic ReceiverLists (in-memory, per-process)     ──> only if process alive
              └─ schedules onReceive() onto the receiver's Handler (main thread)

The leak with dynamic receivers is concrete: AMS holds your IIntentReceiver Binder, and the Context (often an Activity) holds the receiver object — forget unregisterReceiver and the Activity can't be GC'd, plus AMS logs a "leaked IntentReceiver" warning when the ContextImpl is finalized.

Ordered Broadcasts

🎤 Say it out loud (~30–45s): "An ordered broadcast is delivered to receivers one at a time, in descending priority order, instead of fanning out to everyone concurrently like a normal broadcast. Because it's serialized, each receiver can mutate a shared result that the next one sees with setResult*, or it can call abortBroadcast to stop the chain entirely. The trade-off is latency — every receiver blocks the next, so a slow one stalls the whole pipeline, which is why it's rarely worth it in modern apps."

Normal broadcasts are delivered to all receivers asynchronously, in no guaranteed order, potentially concurrently. Ordered broadcasts are different — they are delivered to one receiver at a time, in priority order.

  • Each receiver can call setResult*() to pass data along to the next receiver in the chain.
  • A receiver can call abortBroadcast() to prevent delivery to any lower-priority receivers.
  • They are sent via sendOrderedBroadcast(intent, receiverPermission).
sendOrderedBroadcast(intent, null) // null = no permission restriction

// In a receiver (highest priority processes first)
override fun onReceive(context: Context, intent: Intent) {
    val previousResult = resultData
    setResultData("processed_$previousResult")
    // abortBroadcast() // would stop propagation
}

Use case: In-app notification interception, where a foreground Activity intercepts a notification broadcast before it reaches the notification manager. Rarely needed in modern apps.

Under the hood

AMS keeps two separate queues per BroadcastQueue: a parallel list (normal broadcasts, dispatched to all receivers back-to-back without waiting) and an ordered list. For an ordered broadcast, AMS builds a single BroadcastRecord containing the sorted receiver list and an index pointer, then dispatches strictly one receiver at a time. After scheduling onReceive on a receiver, AMS waits for that receiver to "finish" — for a synchronous receiver that's the return of onReceive, for one that called goAsync() it's the PendingResult.finish() call — before advancing the index to the next receiver. The result fields (resultCode, resultData, resultExtras) live on the BroadcastRecord itself, which is why each receiver reads what the previous one wrote; abortBroadcast() just sets a flag on that record that makes AMS skip the remaining indices.

BroadcastRecord(ordered=true)
  receivers = [P=1000 R_a, P=500 R_b, P=0 R_c]   // sorted by android:priority
  resultCode / resultData / resultExtras          // carried across the chain
  nextReceiver = 0  ──► dispatch R_a ──► wait finish() ──► nextReceiver=1 ──► ...
                                            └─ abortBroadcast() sets abort flag → stop

Because AMS waits between receivers, each one is also subject to the broadcast timeout (the same ~10s/~60s ANR window), and a hung high-priority receiver can deny delivery to everyone below it.

Explicit vs Implicit Broadcasts

🎤 Say it out loud (~30–45s): "An implicit broadcast names only an action, so the system matches it against any registered intent filter — that's powerful but it's exactly what Android 8.0 clamped down on for manifest receivers, and it's a data-leak risk since any app with a matching filter can receive it. An explicit broadcast targets a specific package and class, so it bypasses the 8.0 manifest restriction and is inherently safer. When I send sensitive data I either make it explicit, attach a receiver permission, or keep it in-process with something like a SharedFlow."

Implicit broadcast: The Intent specifies an action but no specific component. Any registered receiver with a matching intent filter can receive it. Examples include ACTION_BATTERY_LOW and ACTION_AIRPLANE_MODE_CHANGED.

Explicit broadcast: Targets a specific component by package and class name. Because it is explicit, it bypasses the Android 8.0 restrictions:

// Explicit — bypasses Android 8.0+ restrictions
val intent = Intent(this, MyReceiver::class.java).apply {
    action = "com.example.MY_ACTION"
}
sendBroadcast(intent)

// To send to another app explicitly
val intent = Intent().apply {
    setClassName("com.other.app", "com.other.app.MyReceiver")
    action = "com.other.app.MY_ACTION"
}
sendBroadcast(intent)

Security: implicit broadcasts sent without a permission can be received by any app that has a matching intent filter. For sensitive data, there are three options — first, sendBroadcast(intent, permission), which restricts delivery to receivers that hold the specified permission. Second, an in-process alternative like SharedFlow (or the deprecated LocalBroadcastManager). Third, an explicit broadcast that targets a specific package.

Under the hood

The dividing line is whether the Intent carries a resolved component (ComponentName). When setComponent/setClassName/the Intent(context, Class) constructor is used, AMS skips intent resolution entirely and routes straight to that one component — which is why the 8.0 manifest policy (enforced inside AMS's broadcast-matching path for implicit manifest receivers) never trips. For an implicit broadcast, AMS calls into PackageManagerService.queryBroadcastReceivers(), which walks every installed app's persisted IntentFilter set and scores matches by action, data type/scheme, and category. The permission form, sendBroadcast(intent, permission), attaches a requiredPermission string to the BroadcastRecord; before scheduling each receiver AMS checks that the receiving app holds that permission via checkComponentPermission, dropping non-holders. LocalBroadcastManager sidestepped all of this by never touching AMS at all — it kept filters in a process-local HashMap and dispatched via the main-thread Handler, which is exactly the model a SharedFlow replaces today.

Background Execution Limits

🎤 Say it out loud (~30–45s): "Starting in Android 8.0, apps can't register manifest receivers for most implicit broadcasts, because the OS was waking thousands of processes for system events they didn't really need — connectivity changes were the worst battery offender. Only a tiny whitelist like BOOT_COMPLETED and self-package-replaced survives in the manifest. The migration is to move that logic to WorkManager or JobScheduler with constraints for deferrable work, FCM for remote triggers, and context-registered receivers for anything that only matters while the app is running."

Android 8.0 prohibits apps from registering receivers for most implicit broadcasts in the manifest. The motivation is that apps were being woken up by system broadcasts they did not actually need, which was a significant source of battery drain.

Exempted broadcasts (can still be registered in the manifest):

  • ACTION_BOOT_COMPLETED — though it has its own restrictions on newer APIs
  • ACTION_LOCKED_BOOT_COMPLETED
  • ACTION_MY_PACKAGE_REPLACED
  • ACTION_PACKAGE_REPLACED (for self)
  • CONNECTIVITY_CHANGE is no longer exempt

Migration path for apps targeting Android 8.0+:

  • Replace CONNECTIVITY_CHANGE receivers with JobScheduler or WorkManager using network constraints.
  • Replace polling via broadcasts with FCM for remote triggers.
  • Use context-registered receivers for anything that only needs to work at runtime.

Under the hood

The limit is enforced inside AMS, not by the compiler — when a broadcast is dispatched, AMS evaluates candidate manifest receivers and, for implicit broadcasts, filters out any whose target app targetSdkVersion >= 26 unless the action is on the system's hardcoded exemption list (defined alongside the broadcast-queue logic). The exemptions exist because those broadcasts are tied to lifecycle events the OS must deliver for correctness (boot, package replacement) and can't be polled. The reason WorkManager/JobScheduler is the sanctioned replacement is that constraints (network type, charging, idle) are evaluated centrally by JobSchedulerService, which batches wakeups across all apps and coalesces them into maintenance windows — instead of N apps each spinning up a process on every connectivity flip, the framework wakes one batch when the constraint is genuinely satisfied.

CONNECTIVITY_CHANGE fires
   pre-O:  AMS → every manifest receiver with matching filter → N process cold-starts  (battery drain)
   O+:     AMS drops implicit manifest matches for targetSdk≥26
           → app instead registers a JobScheduler job with NETWORK_TYPE constraint
           → JobSchedulerService batches & fires one wakeup when constraint is met

Short Execution and Follow-Up Work

🎤 Say it out loud (~30–45s): "onReceive runs on the main thread and has a hard ANR deadline around 10 seconds, but the subtler killer is that once it returns the receiver is dead and the OS can reap the whole process — so any coroutine or thread you spawned dies with it because nothing keeps the process priority elevated. The rule is do only fast synchronous work, then hand off to something with a real lifecycle: WorkManager for deferrable work, a foreground service for immediate user-visible work, or goAsync() for a short extension where I absolutely must call finish() or I'll ANR anyway."

onReceive() runs on the main thread with a hard execution time limit of approximately 10 seconds — exceed that and the app will ANR. After onReceive() returns, the BroadcastReceiver is considered dead and the system may kill the process immediately.

You cannot:

  • Launch an async coroutine and expect it to keep running after onReceive() returns — the process may die before it gets a chance to run.
  • Start a background thread and rely on it completing.
  • Bind to a Service from onReceive() and use it asynchronously.

You can:

  • Do fast, synchronous work.
  • Update SharedPreferences.
  • Post a notification.
  • Schedule follow-up work with WorkManager.
  • Start a Service — a foreground service, if the context is a foreground context.
  • Use goAsync() to get a PendingResult that extends the deadline to roughly 30 seconds; but this is still not truly asynchronous — you must call pendingResult.finish() or the system will eventually ANR anyway.
// Pattern 1: Schedule work with WorkManager
override fun onReceive(context: Context, intent: Intent) {
    val workRequest = OneTimeWorkRequestBuilder<SyncWorker>().build()
    WorkManager.getInstance(context).enqueue(workRequest)
}

// Pattern 2: goAsync() for slightly longer synchronous work
override fun onReceive(context: Context, intent: Intent) {
    val pendingResult = goAsync()
    CoroutineScope(Dispatchers.Default).launch {
        try {
            doQuickWork()
        } finally {
            pendingResult.finish() // MUST call or ANR
        }
    }
}

Under the hood

When AMS dispatches a broadcast it posts the onReceive invocation onto the receiver's main-thread Handler (via ActivityThread's H handler) and starts a timeout alarm — the broadcast-timeout watchdog. If the receiver hasn't reported "finished" before the deadline (~10s foreground / ~60s background), AMS files an ANR against the process. Crucially, while a broadcast is being processed AMS temporarily bumps the process's OOM-adjust / scheduling group so it isn't killed mid-delivery; the instant onReceive returns (or PendingResult.finish() is called), AMS marks the BroadcastRecord done, lowers the process priority back to a cached/empty state, and the LMK (low-memory killer) is then free to reap it under memory pressure. That priority drop is exactly why a detached coroutine evaporates — there's no longer any component holding the process "important," so the kernel can reclaim it.

AMS.processNextBroadcast()
  ├─ set process oom_adj high  (protected during delivery)
  ├─ schedule onReceive on main Handler + arm broadcast-timeout
  ├─ goAsync()? → BroadcastRecord stays "open" until PendingResult.finish()
  └─ on finish/return:
        ├─ cancel timeout
        ├─ restore oom_adj → cached/empty  ← background work now unprotected
        └─ advance queue

goAsync() works by telling AMS not to treat the synchronous return as completion: it hands back a PendingResult (a token referencing the BroadcastRecord) and keeps the record open — and the elevated priority — until you call finish(), but the timeout alarm is still armed, so it buys time, not unbounded life.

BroadcastReceiver Interview Angles

Q: Why should BroadcastReceiver work be short?

"There are two reasons. First, onReceive() runs on the main thread — if it takes more than roughly 10 seconds the system raises an ANR. Second, and this is the sneaky one: after onReceive() returns, the process has no active components left, so the system may kill it immediately. Any background threads you started in onReceive() will die with it. There is no lifecycle object protecting them. So the rule is: do only the minimum in onReceive(), then hand off to something with a lifecycle — WorkManager, a foreground Service, or goAsync() if you need a short extension."

Q: How do you continue work after receiving a broadcast?

"There are three options depending on the urgency and duration of the work. For deferrable background work — syncing data, uploading something — use WorkManager. It persists across process death, respects battery constraints, and will retry if it fails. If the work must start immediately and the user should be aware of it, start a foreground Service. And for work that just barely exceeds the 10-second window but is still short — say, up to about 30 seconds — you can call goAsync() to get a PendingResult that keeps the process alive, do the work on a coroutine, and call pendingResult.finish() when done. Skip that last call and you'll ANR."

Q: Static vs dynamic receiver.

"Static receivers — manifest-registered — have the advantage that the app doesn't need to be running to receive the broadcast. But since Android 8.0 they're restricted to explicit broadcasts and a small whitelist of implicit ones. Dynamic receivers — context-registered — are not subject to that restriction but they're only alive while the registering component is alive. The rule I follow: use dynamic receivers for things that should only matter while the app is in the foreground, and static receivers for app startup or self-targeted explicit broadcasts."

9.5 ContentProvider

A ContentProvider is an Android component that provides structured, URI-addressed access to data, enabling data sharing across application boundaries with fine-grained permission control. It is the standard mechanism for apps to expose data to other apps or to the system.

Cross-App Data Sharing

🎤 Say it out loud (~30–45s): "A ContentProvider is Android's standard way for one app to expose structured data to another app or the system — Contacts, MediaStore, and Calendar are all ContentProviders. I reach for it over just handing out a file because it enforces permission checks on every call, gives callers a uniform query/insert/update/delete interface, and lets me grant temporary URI-level access to a single record instead of opening up my whole file system. The thing interviewers probe is that it's the only one of the four components designed for cross-process data access, and access checks happen per-call, not just at open time."

ContentProvider is the standard mechanism for one app to expose its data to another app or to the system. The system's contacts, media store, and calendar are all ContentProviders.

Why not just use a file? There are four reasons. First, a ContentProvider enforces permission checks on every access — not just when the file is first opened. Second, it provides a uniform SQL-like query interface that callers already know how to use. Third, it allows granting temporary URI-level permissions to specific apps without giving broad file system access. Fourth, the Cursor-based streaming model avoids loading large data sets into memory all at once.

Under the hood

A ContentProvider's cross-process magic is Binder IPC. When app A queries app B's provider, ContentResolver.acquireProvider() asks ActivityManagerService to resolve the authority to a process, cold-starting that process if needed, and hands back an IContentProvider Binder proxy (ContentProviderProxy). Each call marshals its arguments across the Binder transaction; the system stamps the caller's uid/pid into the transaction so the provider's enforceReadPermission/enforceWritePermission can check it on every single call via Binder.getCallingUid().

App A                         system_server                 App B (provider process)
ContentResolver.query() ──► AMS.getContentProvider() ──► (cold start if needed)
        │                    returns IContentProvider proxy
        └── Binder txn (uid of A stamped) ──────────────► Transport.query()
                                                          enforceReadPermission(uid A)
                                                          ◄── CursorWindow (shared memory) ──

The returned Cursor is not a copy of the rows — its data lives in a CursorWindow backed by ashmem (anonymous shared memory). Only the shared-memory file descriptor crosses Binder, so large result sets aren't serialized through the 1 MB Binder transaction buffer.

URI-Based Access and ContentResolver

🎤 Say it out loud (~30–45s): "Every row in a ContentProvider is addressed by a content URI — content:// scheme, then an authority that uniquely identifies the provider, then a path that points at a collection or a specific record. Clients never touch the provider directly; they go through ContentResolver, which resolves the authority and routes the call to the right process, whether that's in my app or someone else's. The detail worth mentioning is that the resolver is the single choke point — it's where I register observers and where the system applies the URI-permission grants."

Every piece of data in a ContentProvider is addressed by a Uri:

content://com.example.app.provider/users/42
           └─────── authority ──────┘ └─ path ┘
  • Scheme: always content://
  • Authority: unique identifier for the ContentProvider, typically the package name plus .provider
  • Path: identifies the type of data and optionally a specific record by ID

ContentResolver is the client-side API for accessing ContentProviders. It routes calls to the correct provider process transparently, whether that provider is in the same app or another app entirely.

val contentResolver = context.contentResolver

// Query
val cursor = contentResolver.query(
    Uri.parse("content://com.example.app.provider/users"),
    arrayOf("_id", "name", "email"), // projection (columns)
    "age > ?",                       // selection
    arrayOf("18"),                   // selectionArgs
    "name ASC"                       // sortOrder
)

// Insert
val values = ContentValues().apply {
    put("name", "Alice")
    put("email", "alice@example.com")
}
val newUri = contentResolver.insert(
    Uri.parse("content://com.example.app.provider/users"),
    values
)

// Update
val rowsUpdated = contentResolver.update(uri, values, null, null)

// Delete
val rowsDeleted = contentResolver.delete(uri, "_id = ?", arrayOf("42"))

Under the hood

ContentResolver is abstract; the concrete instance you get from context.contentResolver is ApplicationContentResolver, which delegates to ActivityThread.acquireProvider(). Authority resolution is a lookup in the package manager's registry of <provider> declarations — an authority must be globally unique on the device, so two installed apps declaring the same authority causes an install conflict (INSTALL_FAILED_CONFLICTING_PROVIDER).

The resolver also maintains the ContentObserver machinery: registerContentObserver(uri, ...) records your observer in a Transport tied to that URI tree, and a provider's notifyChange(uri) walks the system's observer node tree to dispatch onChange callbacks. The internal URI representation is a parsed Uri object (an immutable, lazily-parsed Uri.HierarchicalUri), not the raw string, so repeated Uri.parse of the same string allocates fresh objects — cache them on hot paths.

MIME Types

🎤 Say it out loud (~30–45s): "Every provider has to answer getType() with a MIME type so callers know how to interpret the data without parsing it. The Android convention is two custom vendor types — vnd.android.cursor.dir/... for a collection of rows and vnd.android.cursor.item/... for a single row — and standard types like image/jpeg for file-backed data. The practical reason it matters is intent resolution: the system matches an intent's MIME type against <intent-filter> data types, so a wrong dir vs item means the wrong activity gets offered to handle the URI."

ContentProviders must return MIME types for their data so that clients know how to interpret what they receive.

override fun getType(uri: Uri): String? {
    return when (uriMatcher.match(uri)) {
        USERS -> "vnd.android.cursor.dir/vnd.com.example.app.user"   // collection
        USER_ID -> "vnd.android.cursor.item/vnd.com.example.app.user" // single item
        else -> throw IllegalArgumentException("Unknown URI: $uri")
    }
}

Convention:

  • Collection (multiple rows): vnd.android.cursor.dir/vnd.<authority>.<type>
  • Single item: vnd.android.cursor.item/vnd.<authority>.<type>
  • File-based: standard MIME types such as image/jpeg or application/pdf

Under the hood

getType() is special among provider methods: since Android allows querying a URI's type without holding read permission, the call is routed and resolved against the provider's declared structure. When the system needs to match an intent against intent filters, IntentResolver compares the resolved MIME type using the type/subtype grammar where * wildcards match — image/* matches image/jpeg. The vnd.android.cursor.dir/vnd.android.cursor.item prefixes are just a platform convention encoded as ordinary MIME strings; nothing in the kernel treats them specially, but CursorAdapter-style framework code and intent filters keying on android:mimeType="vnd.android.cursor.dir/..." rely on the exact string. UriMatcher itself is a small trie of path segments built by addURI; match() walks segments, treating # as a numeric wildcard and * as a text wildcard, returning the registered integer code.

ContentProvider Permissions

🎤 Say it out loud (~30–45s): "I control provider access with manifest permissions — separate read and write permissions, plus exported to decide whether other apps can reach it at all. But the powerful piece is temporary URI permissions: I can hand another app a content URI with FLAG_GRANT_READ_URI_PERMISSION so it reads just that one record without ever holding my broad provider permission, and the grant evaporates when the receiving task finishes. The gotcha interviewers like is that grantUriPermissions=true is what enables those temporary grants, and that grants survive only as long as the task — for longer-lived access you take a persistable grant."

Permissions are the primary mechanism for controlling who can access your ContentProvider:

<provider
    android:name=".MyContentProvider"
    android:authorities="com.example.app.provider"
    android:exported="true"
    android:readPermission="com.example.app.permission.READ"
    android:writePermission="com.example.app.permission.WRITE">
</provider>

URI permissions: Grant temporary access to a specific URI to another app without requiring that app to hold the broad provider permission:

// Grant read permission to the receiving app for a specific URI
val intent = Intent(Intent.ACTION_VIEW).apply {
    data = photoUri
    addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
}
startActivity(intent)

The receiving app can access that specific URI until the task ends or you call revokeUriPermission to revoke it early.

Under the hood

Permission enforcement lives in ActivityManagerService, which holds the authoritative table of active URI grants (UriGrantsManagerService in newer releases). When you launch an intent carrying FLAG_GRANT_READ_URI_PERMISSION, AMS records a grant entry keyed by (sourceUid, targetUid, Uri, modeFlags). On each subsequent provider call, the provider's enforceReadPermission first checks whether the calling uid holds the static permission; if not, it asks AMS checkUriPermission() for a matching transient grant. This is why a uid with no declared permission can still read a single granted URI.

grant record:  src=uid(A)  tgt=uid(B)  uri=content://.../photo/7  mode=READ
lifetime:      tied to target's task stack — cleared when task finishes
persisted:     only via takePersistableUriPermission() (survives reboot,
               stored in /data/system/urigrants.xml)

A subtle point: the grant is per exact URI (or a tree, for DocumentsProvider tree URIs). A grant on .../users/42 does not extend to .../users/43. Persistable grants are the exception that survive process death and reboot, and the device caps how many an app may hold.

Cursor

🎤 Say it out loud (~30–45s): "A Cursor is a movable pointer into a result set — you call moveToFirst, loop with moveToNext, and pull columns by index for the current row. The two things I'm careful about: column lookups can return -1 silently if the name's wrong, so I use getColumnIndexOrThrow; and I always close the cursor, ideally with Kotlin's use {}, because a SQLite-backed cursor holds a native statement and a shared-memory window that leak if I don't. It's lazy too — rows are paged in from the window as I iterate, not all up front."

Cursor is the object returned by ContentResolver.query() — a pointer into a row set that you iterate over, one row at a time.

cursor?.use { c ->
    if (c.moveToFirst()) {
        do {
            val id = c.getLong(c.getColumnIndexOrThrow("_id"))
            val name = c.getString(c.getColumnIndexOrThrow("name"))
            results.add(User(id, name))
        } while (c.moveToNext())
    }
}
// cursor.use{} automatically closes it — never forget to close!

Cursor operations:

  • moveToFirst(), moveToNext(), moveToPrevious(), moveToLast(), moveToPosition(n)
  • getColumnIndex("name") — returns -1 if the column is not found; use getColumnIndexOrThrow if you want an exception instead of a silent -1
  • getString, getInt, getLong, getFloat, getBlob
  • isNull(columnIndex) — check for null before reading to avoid unexpected crashes

Memory: Cursors backed by SQLite are lazy — data is fetched row by row as you iterate. Close cursors promptly to release the underlying SQLite statement and free resources. The idiomatic Kotlin way is cursor.use {}, which closes it automatically even if an exception is thrown.

Under the hood

A SQLite-backed cursor is a SQLiteCursor, and its rows live in a CursorWindow — a fixed-size block of ashmem shared memory (default ~2 MB). The cursor doesn't hold all rows; it fills the window with a page of rows around the current position, and moveToPosition past the window edge triggers a re-query (onMove) that re-runs the compiled statement and refills the window from a new offset. That's the laziness.

SQLiteCursor ──► SQLiteQuery (compiled statement, sqlite3_stmt*)
            └──► CursorWindow (ashmem) ── holds page of rows ──► getString reads from window

Across process boundaries the cursor becomes a BulkCursorToCursorAdaptor/CrossProcessCursorWrapper: the provider fills a CursorWindow and passes only the shared-memory fd over Binder, so the client reads rows directly from shared memory without copying. close() releases the CursorWindow (decrementing its ref count to free the ashmem) and finalizes the native sqlite3_stmt. If you leak it, StrictMode / the CloseGuard finalizer logs "Cursor finalized but not deactivated" and the statement stays pinned — under load this exhausts SQLite's cursor pool and you get SQLiteException: too many open cursors.

FileProvider

🎤 Say it out loud (~30–45s): "FileProvider is a ready-made ContentProvider from AndroidX that wraps a file in your private storage as a content:// URI you can safely share. I need it because since Android 7 the system throws FileUriExposedException if you put a raw file:// URI in an intent to another app — sharing private file paths is a security hole. So I declare FileProvider with an XML paths config, call getUriForFile, and add a grant-URI flag on the intent. The catch is the paths file: the file you hand it must live under one of the declared roots, or getUriForFile throws IllegalArgumentException."

FileProvider is a specialized ContentProvider that grants temporary access to files in your app's private storage to other apps, replacing direct file:// URIs which are dangerous and now blocked.

Why: Since Android 7.0 (API 24), the system blocks file:// URIs in Intents between apps and throws a FileUriExposedException. Apps must instead use content:// URIs generated by FileProvider, which applies permission checks and grants only the specific URI requested.

Setup:

  1. Declare in manifest:
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_provider_paths" />
</provider>
  1. Define paths in res/xml/file_provider_paths.xml:
<paths>
    <files-path name="images" path="images/" />
    <cache-path name="camera" path="camera_photos/" />
    <external-files-path name="downloads" path="Downloads/" />
</paths>
  1. Use in code:
val file = File(context.cacheDir, "camera_photos/photo.jpg")
val uri = FileProvider.getUriForFile(
    context,
    "${context.packageName}.fileprovider",
    file
)
val intent = Intent(MediaStore.ACTION_IMAGE_CAPTURE).apply {
    putExtra(MediaStore.EXTRA_OUTPUT, uri)
    addFlags(Intent.FLAG_GRANT_WRITE_URI_PERMISSION)
}
startActivity(intent)

Under the hood

The FileUriExposedException is enforced by StrictMode.VmPolicy's file-uri-exposure check, which is on by default for apps targeting API 24+. Uri.checkFileUriExposed() runs whenever a file:// URI leaves the app via Intent.migrateExtraStreamToClipData() and similar paths.

FileProvider itself is a real ContentProvider subclass. At init it parses the <paths> XML into a SimplePathStrategy — a map from a path name to a concrete root File (resolved from Context.getFilesDir(), getCacheDir(), getExternalFilesDir(), etc.). getUriForFile() canonicalizes the target file's path, finds the longest matching root prefix, and rewrites it into content://<authority>/<name>/<relative-path>; if no root contains the file it throws IllegalArgumentException("Failed to find configured root...").

file:  /data/data/pkg/cache/camera_photos/photo.jpg
root:  <cache-path name="camera" path="camera_photos/">  → getCacheDir()/camera_photos
uri:   content://pkg.fileprovider/camera/photo.jpg

On the read side, openFile() reverses the mapping back to the real File and returns a ParcelFileDescriptor — the actual kernel fd is duplicated and passed over Binder, so the receiving app reads the bytes directly without ever learning the real path. The FLAG_GRANT_*_URI_PERMISSION is what makes the receiver's open succeed, since exported="false" means it holds no static permission.

ContentProvider Interview Angles

Q: When would you use a ContentProvider?

"There are three situations where a ContentProvider makes sense. First, when you need to expose structured data to other apps or to the system — for example, making your app's contact data readable by the system contacts app. Second, when you need fine-grained URI-level permission grants to share individual files with other apps, which is what FileProvider does. Third, when you want a uniform data access interface within your own app and need ContentObserver for reactive change notifications. Outside of those cases, for internal-only data, a Room database accessed through a repository is simpler and more idiomatic."

Q: Why use FileProvider instead of a file URI?

"file:// URIs expose your app's internal storage path directly to other apps. Since Android 7.0 the system blocks them outright with a FileUriExposedException. FileProvider generates content:// URIs instead and applies a permission check on every access. The receiving app gets access to only the specific URI you grant — not broad access to your file system — and it does not need READ_EXTERNAL_STORAGE to receive it. So it's both more secure and more compatible."

Q: How do permissions apply to ContentProviders?

"There are two layers. The first is the broad provider-level permission: you declare readPermission and writePermission on the <provider> element, and any caller that tries to query must hold the read permission, while any caller that tries to insert, update, or delete must hold the write permission. The second layer is URI-level grants: if you set grantUriPermissions=true on the provider, you can attach FLAG_GRANT_READ_URI_PERMISSION or FLAG_GRANT_WRITE_URI_PERMISSION to an Intent and hand it to another app. That app gets temporary access to just that URI, bypassing the broad provider permission entirely. This is the standard mechanism for sharing an individual file or record without permanently giving the other app a broad permission."

9.6 Intents and PendingIntents

Explicit vs Implicit Intents

🎤 Say it out loud (~30–45s): "An explicit intent names the exact component class I want to start — that's what I use inside my own app. An implicit intent only declares an action, data, and category, and lets the system resolve which installed component can handle it — that's how I hand work off to other apps, like opening a URL or sharing text. The gotcha is services: implicit service intents have been illegal since Android 5.0 because any app could intercept them, so a service intent must always be explicit."

Explicit Intent: Directly specifies the target component — Activity, Service, or BroadcastReceiver — by its class name. Used for communication within your own app, where you know exactly what you want to start.

// Start a specific Activity in your app
val intent = Intent(this, ProfileActivity::class.java).apply {
    putExtra("userId", userId)
}
startActivity(intent)

// Start a specific service
val serviceIntent = Intent(this, DownloadService::class.java)
startService(serviceIntent)

Implicit Intent: Does not name a specific component. Instead it declares an action — and optionally data and a category — and lets the system find a matching component from any installed app. Used for inter-app communication.

// Open a URL in a browser
val intent = Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com"))
startActivity(intent)

// Share text
val shareIntent = Intent(Intent.ACTION_SEND).apply {
    type = "text/plain"
    putExtra(Intent.EXTRA_TEXT, "Check this out!")
}
startActivity(Intent.createChooser(shareIntent, "Share via"))

// Make a phone call
val dialIntent = Intent(Intent.ACTION_DIAL, Uri.parse("tel:+15551234567"))
startActivity(dialIntent)

Security: Always use explicit intents for starting Services. Implicit intents to start a Service have been blocked since Android 5.0 — the system throws IllegalArgumentException: Service Intent must be explicit. The reason is that an implicit service intent is a security risk: any app with a matching intent filter could intercept it.

Under the hood

An Intent is a Parcelable bundle of fields (action string, data Uri, categories set, component name, type, flags, and an extras Bundle). When you call startActivity, the intent is marshalled across a Binder transaction to the ActivityManagerService (now ActivityTaskManagerService) in the system_server process. For an explicit intent, AMS reads the embedded ComponentName and dispatches directly. For an implicit intent, AMS hands it to PackageManagerService, which runs IntentResolver over every component's parsed <intent-filter> set — matching action, then categories, then data (scheme/host/path/MIME) — and returns ranked ResolveInfo results. Resolution scans only manifest-declared filters, which is why an implicit service intent throws: the framework refuses to let multiple matching services be silently chosen.

startActivity(intent)
  → Instrumentation.execStartActivity()
  → Binder txn → ActivityTaskManagerService (system_server)
  → explicit? dispatch by ComponentName
  → implicit? PackageManagerService.queryIntentActivities()
      → IntentResolver.queryIntent() over parsed manifest filters
      → match(action) && match(all categories) && matchData(uri, mime)

Intent Filters

🎤 Say it out loud (~30–45s): "An intent filter is a manifest declaration that advertises which implicit intents a component can handle — the system matches on action, category, and data. The subtlety interviewers love is the three-part matching rule: the action has to match one entry, the intent's categories must all be present in the filter, and the data has to satisfy the scheme and MIME rules. And since Android 12, any component with a filter must explicitly set android:exported, or the build fails."

Declared in the manifest, intent filters specify what Intents an Activity, Service, or Receiver is willing to handle. The system uses them to match implicit intents to the right component.

<activity android:name=".ShareActivity">
    <intent-filter>
        <action android:name="android.intent.action.SEND" />
        <action android:name="android.intent.action.SEND_MULTIPLE" />
        <category android:name="android.intent.category.DEFAULT" />
        <data android:mimeType="image/*" />
    </intent-filter>
</activity>

Matching rules: An implicit Intent matches a filter if three conditions hold — first, its action matches at least one <action> in the filter. Second, its category matches all <category> elements (note that the DEFAULT category is automatically added to Intents started with startActivity). Third, its data — URI plus MIME type — satisfies the filter's data rules.

android:exported: Activities with an intent-filter are exported by default, meaning any app can start them. Since Android 12, you must explicitly declare android:exported="true" or android:exported="false" for any Activity, Service, or Receiver that has an intent-filter; omitting it causes a build or install failure.

Under the hood

At install time, PackageManagerService parses every <intent-filter> in the manifest into an IntentFilter object and registers it in the package's parsed component data. Each IntentFilter holds arrays for actions, categories, schemes, authorities, paths, and MIME types. Matching is performed by IntentFilter.match(), which runs four ordered checks — matchAction(), matchCategories(), matchData(), and the implicit DEFAULT requirement — and returns a match constant or a negative NO_MATCH_* code (e.g. NO_MATCH_ACTION, NO_MATCH_CATEGORY, NO_MATCH_DATA). Filters never make an intent broader: an intent's categories must be a subset of the filter's, not vice versa. The exported flag is also resolved here — if a component has a filter, an unset exported historically defaulted to true, which is why Android 12 (targetSdk 31) makes the attribute mandatory at manifest-merge/parse time.

IntentFilter.match(action, type, scheme, data, categories)
  → matchAction()      // intent action ∈ filter actions
  → matchCategories()  // filter categories ⊇ intent categories
  → matchData()        // scheme + authority + path + MIME
  → returns MATCH_CATEGORY_* | NO_MATCH_ACTION | NO_MATCH_DATA ...

Deep Links (Intents)

🎤 Say it out loud (~30–45s): "A deep link is just an intent filter on ACTION_VIEW with the BROWSABLE category, which is what makes a URI launchable from a browser or another app into a specific screen. I read the data off intent.data in the target component. The thing to call out is that a plain deep link with a custom scheme isn't verified — if more than one app can handle the URI the user sees a disambiguation chooser, which is exactly what App Links solve."

Deep links route external URLs and URIs into specific app screens. They are declared as intent filters with ACTION_VIEW, CATEGORY_DEFAULT, and CATEGORY_BROWSABLE — the BROWSABLE category is what allows the link to be opened from a web browser.

<activity android:name=".ArticleActivity">
    <intent-filter>
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <data android:scheme="myapp" android:host="article" />
        <!-- HTTP/HTTPS deep link -->
        <data
            android:scheme="https"
            android:host="www.example.com"
            android:pathPrefix="/articles" />
    </intent-filter>
</activity>
// Handle in Activity
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val uri = intent.data
    val action = intent.action
    if (action == Intent.ACTION_VIEW && uri != null) {
        val articleId = uri.lastPathSegment
        loadArticle(articleId)
    }
}

Testing deep links:

adb shell am start -W -a android.intent.action.VIEW -d "myapp://article/123" com.example.app

Under the hood

When a browser or another app fires an ACTION_VIEW intent for a URI, the system resolves it the same way as any implicit intent — through PackageManagerService and IntentResolver — but with the extra requirement that the matching component carry CATEGORY_BROWSABLE. Browsers add BROWSABLE to the intents they build, so a filter lacking that category is invisible to web-originated navigation. The <data> elements are decomposed into scheme, host (authority), and path attributes, and matchData() compares them piecewise; pathPrefix, pathPattern, and path map to different PatternMatcher match types (PATTERN_PREFIX, PATTERN_SIMPLE_GLOB, PATTERN_LITERAL). If multiple components match and none is a verified App Link, ResolverActivity is launched to present the disambiguation chooser. The URI itself arrives parsed lazily — Uri.parse builds an opaque/hierarchical Uri whose lastPathSegment and query parts are decoded on demand.

App Links

🎤 Say it out loud (~30–45s): "App Links are deep links over HTTPS that prove I own the domain, so Android routes the URL straight into my app with no chooser dialog. I set android:autoVerify on the filter, and I host an assetlinks.json at /.well-known/ containing my signing cert's SHA-256 fingerprint. The verifier checks that file against my package, and the catch is that verification is fragile — a wrong fingerprint, a redirect, or a non-200 on that file silently drops you back to opening the link in the browser."

App Links are a stricter form of deep link that use the https:// scheme and require verified domain ownership. When verified, Android routes matching links directly to your app without showing the disambiguation dialog.

Requirements:

  1. An intent filter with android:autoVerify="true".
  2. A /.well-known/assetlinks.json file served from your domain, containing your app's SHA-256 certificate fingerprint.
<intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data android:scheme="https" android:host="www.example.com" />
</intent-filter>
// https://www.example.com/.well-known/assetlinks.json
[{
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
        "namespace": "android_app",
        "package_name": "com.example.app",
        "sha256_cert_fingerprints": ["14:6D:E9:83:..."]
    }
}]

Difference from deep links:

  • Deep links show the disambiguation dialog if multiple apps can handle the URI, or offer to open it in a browser.
  • App links open directly in your app with no dialog — but only after domain ownership is verified. If your app is not installed, the system falls back to the browser.

Under the hood

At install (and on package updates) the DomainVerificationManagerService / IntentFilterVerificationAgent collects every autoVerify filter's host and issues an HTTPS fetch of https://<host>/.well-known/assetlinks.json. It parses the JSON, looks for a delegate_permission/common.handle_all_urls relation whose package_name matches and whose sha256_cert_fingerprints includes the hash of the APK's signing certificate (the same fingerprint computed from your keystore / Play App Signing key). On success the domain's verification state is persisted as STATE_VERIFIED, and the framework promotes that filter above the generic resolver so ACTION_VIEW for the host bypasses ResolverActivity entirely. Any failure — non-200, redirect to a different host, malformed JSON, or fingerprint mismatch — leaves the state unverified, so the link falls through to the chooser or browser. On Android 12+ this state is inspectable via adb shell pm get-app-links <package> and re-triggerable with pm verify-app-links.

install/update
  → DomainVerificationManagerService.verify(host)
  → HTTPS GET https://host/.well-known/assetlinks.json   (must be 200, no cross-host redirect)
  → match package_name && sha256 fingerprint ∈ list
  → STATE_VERIFIED → filter wins over ResolverActivity
  → any failure → STATE_NO_RESPONSE / unverified → chooser/browser

PendingIntent

🎤 Say it out loud (~30–45s): "A PendingIntent is a token I hand to the system or another app that lets them fire an intent later using my app's identity and permissions — it's a pre-authorized capability, used for notification taps, alarms, and widgets. The big modern gotcha is mutability: since Android 12 / target 31 I must pass FLAG_IMMUTABLE or FLAG_MUTABLE explicitly, and FLAG_UPDATE_CURRENT matters because PendingIntents that are 'equal' are deduplicated by the system — same requestCode and matching intent fields return the same token."

A PendingIntent is a token representing an Intent that another application or the system can fire on your app's behalf at some point in the future, using your app's identity and permissions. It is essentially a pre-authorized capability you hand to someone else.

Use cases:

  • Notification taps and action buttons.
  • AlarmManager scheduled tasks.
  • Widget click handlers.
  • App shortcuts.
  • Any situation where an external process needs to launch a component in your app.
// For a Notification
val intent = Intent(context, MainActivity::class.java).apply {
    flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK
    putExtra("notification_id", notificationId)
}
val pendingIntent = PendingIntent.getActivity(
    context,
    requestCode,        // unique integer to distinguish PendingIntents
    intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)
val notification = NotificationCompat.Builder(context, channelId)
    .setContentIntent(pendingIntent)
    .build()

Four factory methods:

  • PendingIntent.getActivity(context, requestCode, intent, flags) — starts an Activity
  • PendingIntent.getService(context, requestCode, intent, flags) — starts a Service
  • PendingIntent.getBroadcast(context, requestCode, intent, flags) — sends a Broadcast
  • PendingIntent.getActivities(context, requestCode, intents, flags) — starts a synthetic stack of Activities (useful for deep-link back stacks)

Under the hood

A PendingIntent is just a thin wrapper around an IIntentSender Binder handle whose real object — a PendingIntentRecord — lives inside system_server, not your process. When you create one, AMS interns it in a HashMap keyed by a PendingIntentRecord.Key built from your package, the target type (activity/service/broadcast), the requestCode, and the intent's "filter equality" fields (action, data, type, component, categories — but not extras). If a record with an equal key already exists, AMS returns the same underlying record, which is exactly why FLAG_UPDATE_CURRENT exists: it refreshes the extras on that shared record, and FLAG_CANCEL_CURRENT tears the old one down first. Because the token carries your app's UID, whoever holds it fires the intent with your identity — that is the security surface FLAG_IMMUTABLE protects: without it, a holder could use send() with a fill-in Intent to mutate unfilled fields. Targeting SDK 31+ throws IllegalArgumentException if neither FLAG_IMMUTABLE nor FLAG_MUTABLE is supplied.

PendingIntent.getActivity(ctx, requestCode, intent, flags)
  → ActivityManager.getIntentSender()  (Binder → system_server)
  → key = {package, type=ACTIVITY, requestCode, intent.filterEquals(), flags}
  → existing record for key? reuse (UPDATE_CURRENT refreshes extras)
  → else new PendingIntentRecord (holds caller UID/identity)
  → return PendingIntent wrapping IIntentSender token

PendingIntent Mutability

🎤 Say it out loud (~30–45s): "Since Android 12 you have to declare a PendingIntent as either immutable or mutable — there's no implicit default anymore, and if you specify neither on API 31+ creation throws. I reach for FLAG_IMMUTABLE by default because the receiver gets exactly the Intent I described and can't tamper with it. I only use FLAG_MUTABLE for the narrow cases where the system legitimately fills fields in — inline notification replies, setAlarmClock show-intents, bubbles — and even then the base Intent must be explicit."

Since Android 12 (API 31), apps must specify mutability explicitly:

  • FLAG_IMMUTABLE: The system cannot modify the Intent inside the PendingIntent. The receiving component gets exactly the Intent you specified. Preferred and required for almost every use case.
  • FLAG_MUTABLE: Allows the system to modify certain Intent fields such as extras. Required only when the PendingIntent is meant to be filled in by the system — for example, inline reply from notifications, AlarmManager.setAlarmClock() show-intent, bubble Intents, or MediaSessionCompat.
// Immutable — preferred, for notification tap, alarm callbacks
PendingIntent.getActivity(context, 0, intent, PendingIntent.FLAG_IMMUTABLE)

// Mutable — only when the system needs to fill in extras
PendingIntent.getBroadcast(context, 0, intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_MUTABLE)

Before API 31: FLAG_IMMUTABLE was available but not required. Omitting both flags defaulted to mutable behavior. Apps targeting API 31 and above will crash at PendingIntent creation if neither flag is specified.

Under the hood

A PendingIntent isn't a heap object you own — it's a token backed by a record (PendingIntentRecord) held inside system_server's ActivityManagerService. When you call getActivity/getBroadcast/getService, the framework binders over to AMS, which stores the description of the Intent (action, component, extras, the requesting uid/package) keyed by a Key that hashes the requestCode, target type, and Intent's filterEquals fields. What you get back is a remotable handle (an IIntentSender Binder proxy). The mutability and UPDATE_CURRENT/CANCEL_CURRENT flags are stored as bits on that record. When the holder later calls send(), AMS looks up the record, optionally merges a fill-in Intent (only if FLAG_MUTABLE), and dispatches under the original creator's uid — which is why it carries your identity, not the sender's.

your app ──getActivity()──▶ AMS.getIntentSender()
                              └─ creates/finds PendingIntentRecord{ key, uid, flags }
                              └─ returns IIntentSender Binder token
holder  ──send(fillIn)────▶ AMS  ──(merge only if MUTABLE)──▶ startActivity() as creator uid

Because filterEquals ignores extras, two getActivity calls with the same action/component but different extras resolve to the same record unless you vary the requestCode or pass FLAG_UPDATE_CURRENT — a classic source of "my notification opens the wrong screen" bugs.

Security Implications

🎤 Say it out loud (~30–45s): "The headline risk is the confused-deputy attack: a PendingIntent fires with my app's identity and permissions, so if it's mutable and wraps an implicit Intent, a malicious app can receive it, rewrite the target component, and redirect it at a private component of mine while running as me. The fix is the rule that mutable PendingIntents must carry an explicit base Intent, plus keeping components non-exported or permission-guarded. I also avoid sending sensitive data over implicit broadcasts without a receiver permission."

PendingIntent security risks:

  1. Mutable PendingIntent with implicit base Intent: This is extremely dangerous. A mutable PendingIntent wrapping an implicit Intent can be received by a malicious app that then modifies the Intent fields — action, component, extras — and redirects it to any component, including private ones in your app. The rule is simple: if you use FLAG_MUTABLE, the base Intent must be explicit.
  1. Confused deputy attack: Your PendingIntent fires with your app's identity and permissions. A malicious app that receives it can exploit whatever elevated permissions your app holds — for example, accessing a protected ContentProvider or starting a non-exported Activity — using your credentials.
  1. Intent interception: Implicit broadcasts sent without a receiverPermission argument can be received by any installed app. Use explicit targeting or sendBroadcast(intent, permission) for any broadcast carrying sensitive data.
// DANGEROUS: mutable + implicit
val badIntent = Intent(Intent.ACTION_VIEW) // implicit
val dangerousPendingIntent = PendingIntent.getActivity(
    context, 0, badIntent, PendingIntent.FLAG_MUTABLE
) // any receiver can redirect this to any Activity with your app's identity!

// SAFE: immutable or mutable with explicit intent
val safeIntent = Intent(context, MyActivity::class.java) // explicit
val safePendingIntent = PendingIntent.getActivity(
    context, 0, safeIntent, PendingIntent.FLAG_IMMUTABLE
)
  1. Exported components without permission checks: Any Activity with android:exported="true" and no permission requirement can be started by any app on the device. Add android:permission on the element or do manual permission checks in onCreate if you need to restrict access.

Under the hood

The "fires with your identity" property is enforced in the binder/AMS layer, not in your process. When IIntentSender.send() reaches AMS, the kernel binder driver has already stamped the call with Binder.getCallingUid() for the sender, but AMS deliberately uses the uid/packageName captured in the PendingIntentRecord at creation time to perform permission checks and dispatch — that's the deputy. For a mutable record, AMS calls Intent.fillIn() to merge the sender's supplied Intent into the stored one; fillIn will overwrite the component, action, data, and unset extras only on fields the creator left null/unguarded, which is exactly how redirection happens when the base Intent had no explicit component. An immutable record skips the merge entirely. Exported-component enforcement happens earlier, during Intent resolution in PackageManagerService: each component's exported bit and optional android:permission are checked against the caller's granted permissions before AMS will even resolve the target, so a non-exported component is unreachable from another uid regardless of the Intent.

Task Stack Behavior

🎤 Say it out loud (~30–45s): "The back stack is owned by the system per task, and Intent flags are how you reshape it from outside an Activity. From a Service or Receiver I need FLAG_ACTIVITY_NEW_TASK because there's no Activity task to attach to. CLEAR_TOP plus SINGLE_TOP is my go-to for 'jump home and clear everything above' — it delivers onNewIntent to the existing instance instead of recreating it. And for notifications I build a synthetic parent stack with TaskStackBuilder so Up navigation makes sense even though the user landed deep."

Intents can manipulate the task back stack in significant ways. There are a few key scenarios to know:

Notification tap: Tapping a notification should open the app in a sensible state — not just drop the user onto a detail screen with no way to navigate up. Use TaskStackBuilder to create a synthetic back stack that mirrors what the user would have seen if they had navigated there naturally:

val resultIntent = Intent(context, DetailActivity::class.java).apply {
    putExtra("id", itemId)
}
val stackBuilder = TaskStackBuilder.create(context).apply {
    addNextIntentWithParentStack(resultIntent) // reads parentActivityName from manifest
}
val pendingIntent = stackBuilder.getPendingIntent(0,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)

FLAG_ACTIVITY_NEW_TASK: Required when starting an Activity from a non-Activity context such as a Service or BroadcastReceiver. It creates a new task if none exists, or brings an existing task with the same affinity to the foreground.

FLAG_ACTIVITY_CLEAR_TOP: If the target Activity already exists anywhere in the current task's back stack, all Activities above it are destroyed and onNewIntent is called on the existing instance. This is the standard "navigate to home and clear" pattern.

// Go to HomeActivity and clear everything above it
val intent = Intent(context, HomeActivity::class.java).apply {
    flags = Intent.FLAG_ACTIVITY_CLEAR_TOP or Intent.FLAG_ACTIVITY_SINGLE_TOP
}
startActivity(intent)

FLAG_ACTIVITY_NO_HISTORY: The Activity is not added to the back stack. When the user leaves it — via Back or by starting another Activity — it finishes immediately and cannot be recovered by pressing Back. Useful for splash screens or short-lived intermediary screens.

Under the hood

Tasks and the back stack live entirely in system_server, inside the ActivityTaskManager (split out from AMS in API 29). A task is a Task object holding a stack of ActivityRecords, each with a taskAffinity derived from your package/manifest. When you call startActivity, AMS runs ActivityStarter, which interprets the launch flags against the target's manifest launchMode to decide whether to reuse an existing record or push a new one. FLAG_ACTIVITY_CLEAR_TOP makes ActivityStarter scan the task for a matching ActivityRecord; if found and the activity is singleTop/you also passed SINGLE_TOP, it finishes everything above and routes the Intent to onNewIntent on the surviving instance — otherwise it destroys and recreates the matched activity. NEW_TASK triggers an affinity lookup: AMS finds an existing task whose affinity matches and reparents/foregrounds it, or allocates a fresh Task. TaskStackBuilder.getPendingIntent doesn't create real activities up front — it serializes the array of synthetic Intents (each tagged with NEW_TASK on the root) into one PendingIntent, and AMS replays them in order as a single startActivities call when fired.

Task(affinity=com.app) ─ ActivityRecord[Home]
                        └ ActivityRecord[List]
                        └ ActivityRecord[Detail]  ◀── CLEAR_TOP+SINGLE_TOP to Home:
                                                       finish Detail & List, onNewIntent(Home)

Intents Interview Angles

Q: Explicit vs implicit intent — when do you use each?

"The rule is: explicit when you know exactly what you're talking to, implicit when you want the system to find the right handler. Inside my own app I always use explicit intents — I know the Activity, Service, or Receiver by name and I'm not trying to let any other app intercept it. Implicit intents are for inter-app work: opening a URL in a browser, sharing text, capturing an image — situations where I care about the action but not which app performs it. One important exception: implicit intents for starting Services are blocked on API 21 and above, because any app could intercept them. Service intents must always be explicit."

Q: What is a PendingIntent?

"A PendingIntent is a pre-authorized token you hand to another process — the system, AlarmManager, NotificationManager, a widget host — that lets them fire a specific Intent on your app's behalf at some point in the future, even if your process is not running. The system holds the description of the Intent, not the Intent object itself, and recreates it when it needs to fire. The critical thing is that it fires with your app's identity and permissions, not the caller's, which is why the security choices you make when creating it really matter."

Q: Why does PendingIntent mutability matter?

"Mutability determines whether the process that receives the PendingIntent can modify the Intent before firing it. If the base Intent is implicit and the PendingIntent is mutable, a malicious app can receive it and overwrite the target component — redirecting it to any Activity in your app, including private ones — while still running under your app's identity and permissions. That's the 'confused deputy' attack. FLAG_IMMUTABLE prevents any modification and should be the default choice. FLAG_MUTABLE is only for cases where the system legitimately needs to inject data — like filling in the reply text for an inline notification reply."

Q: How do deep links work?

"Deep links go through Android's Intent resolution system. You declare an <intent-filter> with ACTION_VIEW, CATEGORY_DEFAULT, and CATEGORY_BROWSABLE, plus a <data> element that specifies the scheme, host, and path pattern you want to handle. When the user taps a matching link in a browser, email, or another app, the system queries all installed apps for a matching intent filter. If multiple apps match, it shows the disambiguation dialog. If you've set up App Links with verified domain ownership, it routes directly to your app with no dialog. Either way, the matching Activity receives the Intent and reads the URI from intent.data to navigate to the right screen."
