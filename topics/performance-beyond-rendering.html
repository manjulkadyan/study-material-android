14.1 Startup Performance

Cold Start

🎤 Say it out loud (~30–45s): "A cold start is the worst case: the process doesn't exist, so the system has to fork it from zygote, run my Application class, then build and render the first Activity. Everything in Application.onCreate() is on the critical path because the main thread is blocked until it returns. The nuance interviewers probe is the difference between TTID — the first frame drawn — and TTFD, which is when the screen is actually usable; I report the latter with reportFullyDrawn() so my metrics reflect real perceived performance, not just a skeleton."

Definition: A cold start is what happens when the app process does not exist in memory at all and the system has to spin up a brand-new process from scratch.

How it works:

  1. The system forks a new process from zygote (the pre-forked Android runtime).
  2. The app's Application class is instantiated and Application.onCreate() runs.
  3. The target Activity is created: onCreate() → onStart() → onResume().
  4. The first frame is rendered and delivered to SurfaceFlinger.

Timeline breakdown:

  • Time To Initial Display (TTID): Time until the first frame is drawn. This is what Displayed in logcat measures.
  • Time To Full Display (TTFD): Time until the app's content is fully loaded and interactive (can be reported with reportFullyDrawn()).

Under the hood

The zygote process is started by init at boot and preloads the core framework classes and shared resources, then sits blocked in a select/socket loop. When ActivityManagerService needs a new app, it asks zygote to fork() — the child inherits the already-warmed heap via copy-on-write memory pages, which is why apps don't pay to reload android.* classes. After the fork, ActivityThread.main() sets up the main Looper, calls bindApplication (which instantiates your Application), then drives the activity lifecycle through the H handler. The "Displayed" log is emitted by ActivityManagerService when it receives the first dispatchWindowsDrawn callback from the window's ViewRootImpl after the first Choreographer frame completes.

init → zygote (preloaded classes, blocked on socket)
         │ fork() + COW pages
         ▼
ActivityThread.main() → Looper.prepareMainLooper()
         │ bindApplication → new Application(); onCreate()
         ▼
handleLaunchActivity → Activity onCreate/onStart/onResume
         │ ViewRootImpl.performTraversals → first Choreographer frame
         ▼
dispatchWindowsDrawn → AMS logs "Displayed"

Android implications:

  • Cold start is measured from when the user taps the launcher icon to when the first frame appears.
  • The system displays a splash screen window (preview window) immediately from windowBackground theme attribute, providing visual feedback before any app code runs.
  • All Dagger component initialization, third-party SDK initialization, and database schema migrations that run in Application.onCreate() add directly to cold start time.
  • Pre-Android 12, apps controlled the splash screen entirely. Android 12+ enforces a system-managed splash screen.

Optimizing cold start:

  • Defer initialization that is not needed immediately (lazy init, background threads).
  • Use App Startup library to sequence and parallelize initializer dependencies.
  • Use Baseline Profiles so the ART JIT compiler has pre-compiled hot paths.
  • Avoid disk I/O or network calls on the main thread during startup.
  • Minimize the depth and breadth of the Dagger object graph that is constructed eagerly.

Measuring cold start:

# Force a cold start by killing the process first
adb shell am force-stop com.example.app
adb shell am start-activity -W com.example.app/.MainActivity

# Output:
# ThisTime: 847
# TotalTime: 1203
# WaitTime: 1210
  • ThisTime: Time for the last activity to start.
  • TotalTime: Time from process creation to onResume() of the first activity.
  • WaitTime: Total time including the system overhead before am start returns.

Also watch logcat for:

I/ActivityManager: Displayed com.example.app/.MainActivity: +1s203ms

Warm Start

🎤 Say it out loud (~30–45s): "A warm start is when the process is still alive but the Activity was destroyed — so Application.onCreate() is skipped, but the Activity gets fully recreated from onCreate through onResume, restoring any saved Bundle. It's typically two to three times faster than cold because class loading and the app graph are already warm. The gotcha is that it lulls you into assuming your in-memory state is always there; in production a user can always hit a true cold start after process death, so my code has to render correctly from null or empty initial state."

Definition: A warm start is when the app process is already alive in memory, but the Activity itself was destroyed — for example, the user navigated away and the system reclaimed it, or the user killed the Activity without killing the whole process.

How it works:

  • The Application object already exists — Application.onCreate() is NOT called again.
  • The system recreates the Activity from scratch: onCreate() → onStart() → onResume().
  • Saved instance state (Bundle) is restored if available.

Under the hood

In a warm start the process's main Looper is still running and the JVM has already loaded and verified the relevant classes, so there's no zygote fork or class-loading cost. ActivityManagerService simply schedules a new LaunchActivityItem on the existing ActivityThread's H handler. The saved Bundle was captured earlier in onSaveInstanceState (which serializes via Parcel into native memory held by the system_server's ActivityRecord, not your process), and it's handed back into onCreate/onRestoreInstanceState. Because that state lives in system_server, it survives the Activity object being garbage-collected — but it does NOT survive the process being killed, since the ActivityRecord is also torn down.

Android implications:

  • Warm starts are typically 2–3x faster than cold starts because process + class loading is already done.
  • Any initialization in Application.onCreate() is not repeated, but Activity.onCreate() still runs.
  • Retained ViewModel instances survive warm starts (across configuration changes), but do NOT survive process death — which triggers a cold start.

Common warm-start failure mode: Assuming ViewModel data is always populated because warm start is common during development. In production, users can always encounter a cold start; code must handle null/empty initial state gracefully.

Hot Start

🎤 Say it out loud (~30–45s): "A hot start is the best case — both the process and the Activity are still in memory, the app was just backgrounded, so the system only runs onRestart → onStart → onResume and brings the existing window forward. No object creation happens, so it's usually under a hundred milliseconds and isn't really an optimization target. What I do watch for is staleness: in-memory caches can be old if the user was gone a while, and memory pressure while backgrounded can get the process killed, silently demoting the next launch to a cold start."

Definition: A hot start is the best case — the app process and the Activity both already exist in memory, and the user has simply backgrounded the app and come back.

How it works:

  • The system simply brings the existing Activity to the foreground: onRestart() → onStart() → onResume().
  • No new object creation occurs for the Application or Activity.

Under the hood

On a hot start the Activity's Window, ViewRootImpl, and the whole decor view hierarchy are still attached and the rendered surface is still allocated in SurfaceFlinger — nothing needs re-inflation or re-measure unless something changed. The system_server's WindowManagerService just changes the window's visibility and z-order, and the existing Surface's buffers can often be composited straight away. The lifecycle callbacks fire through the same H handler, but no performTraversals re-layout is forced, which is why the cost is dominated by callback dispatch rather than rendering work.

Android implications:

  • Hot starts are extremely fast (< 100 ms typically) and are not a meaningful startup optimization target.
  • The primary concern for hot starts is state freshness: data cached in memory may be stale if the user was gone for a long time.
  • Memory pressure while backgrounded can cause the system to kill the process and degrade the next start to cold.

Application.onCreate()

🎤 Say it out loud (~30–45s): "Application.onCreate() runs exactly once when the process is created, and the main thread is blocked until it returns — so every millisecond here is paid on every cold start. The discipline is to only do work that genuinely must be ready before any code runs, like crash reporting, and defer everything else: no disk reads, no network, no eager Dagger graph. The trap interviewers love is multi-process apps — onCreate runs once per process, so a background :remote process for push or Bluetooth will redundantly build your whole UI graph unless you guard it by checking the process name."

Definition: Application.onCreate() is the single entry point that runs once when the app process is first created. It's the place every library, SDK, and framework gravitates toward for global initialization, which is exactly what makes it the most important location for startup optimization.

What happens here (and why it matters):

  • The main thread is blocked until Application.onCreate() returns.
  • Everything inside it adds directly to cold start time.
  • This is the most impactful single location for startup optimization.

What MUST happen in Application.onCreate():

  • Crash reporting initialization (Crashlytics, Sentry) — needs to be active before any crash can occur.
  • Strict mode setup (debug builds only).
  • Process-name-specific initialization (multi-process apps must guard with ProcessUtils.getProcessName() to avoid initializing UI dependencies in background processes).

What should NOT happen in Application.onCreate():

  • Database schema migration or opening database connections.
  • SharedPreferences.getSharedPreferences() calls (triggers disk read on main thread).
  • Network calls of any kind.
  • Heavy Dagger graph construction (e.g., constructing a component that transitively initializes dozens of dependencies).
  • Analytics SDK full initialization if it can be deferred.
  • Image loading library disk cache setup (Glide/Coil manage this lazily).
  • Feature flag synchronization from network.

Multi-process trap: In apps with :remote or other background processes (e.g., push notification services, Bluetooth services), Application.onCreate() runs once per process. If you initialize your Dagger component unconditionally, you're paying full initialization cost in every process. Guard with:

class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        if (isMainProcess()) {
            initializeMainProcessComponents()
        }
        // crash reporting is OK for all processes
        initializeCrashReporting()
    }

    private fun isMainProcess(): Boolean =
        packageName == getProcessName()
}

Under the hood

Application.onCreate() is invoked synchronously by ActivityThread.handleBindApplication(), which runs as message BIND_APPLICATION on the main Looper before any Activity launch message is processed. Crucially, ContentProvider.onCreate() for every provider declared in the manifest runs even earlier — between Application instantiation (the constructor and attachBaseContext) and Application.onCreate() — which is exactly the hook auto-init libraries exploit. Each process gets its own forked copy of the runtime, so static initializers and the Application singleton are per-process; getProcessName() reads the process name the system assigned at fork time (backed by ActivityThread.currentProcessName() on API 28+, or /proc/self/cmdline historically).

ActivityThread.handleBindApplication():
   makeApplication()        → new Application(); attachBaseContext()
   installContentProviders() → every <provider>.onCreate()   ← auto-init runs here
   mInstrumentation.callApplicationOnCreate(app) → onCreate()  ← main thread blocked
   ... only now can ActivityThread process LAUNCH_ACTIVITY ...

Lazy Initialization

🎤 Say it out loud (~30–45s): "Lazy initialization means I defer constructing an expensive object until the first access, so I keep it off the startup critical path. In Kotlin by lazy is thread-safe by default — it synchronizes the first read — and I can drop to LazyThreadSafetyMode.NONE for single-threaded access to skip that locking. The nuance is that lazy doesn't make the cost disappear, it just moves it; if that first access lands on the main thread during a user interaction it becomes jank or even an ANR, so for things I know I'll need I preload them on a background thread after startup."

Definition: Lazy initialization means deferring object construction or expensive operations until the first time they are actually needed, rather than paying the cost upfront at startup.

How it works in Kotlin:

// Property-level lazy — thread-safe by default (SYNCHRONIZED mode)
val database: AppDatabase by lazy {
    Room.databaseBuilder(context, AppDatabase::class.java, "app.db").build()
}

// LazyThreadSafetyMode.NONE — fastest, only safe if accessed from one thread
val cache: LruCache<String, Bitmap> by lazy(LazyThreadSafetyMode.NONE) {
    LruCache(maxSize)
}

Dagger lazy injection:

// Dagger provides Lazy<T> — the object is constructed on first .get() call
@Inject lateinit var expensiveService: Lazy<AnalyticsService>

fun trackEvent(event: String) {
    expensiveService.get().track(event)  // constructed only here
}

Under the hood

by lazy desugars to a synthetic backing field holding a Lazy<T> instance — by default SynchronizedLazyImpl. Its value getter checks a field against a sentinel (UNINITIALIZED_VALUE); on a miss it acquires a lock (double-checked locking) and runs your initializer lambda exactly once, then caches the result so subsequent reads are a plain field read. LazyThreadSafetyMode.NONE uses UnsafeLazyImpl, which is just an unsynchronized field check with no lock and no volatile — fast, but two threads racing can both run the initializer and see torn state. Dagger's Lazy<T> is a different mechanism: it generates a DoubleCheck provider wrapper that memoizes the result of the underlying Provider.get() factory, also via double-checked locking.

// Conceptually, what SynchronizedLazyImpl.value does:
val v1 = _value
if (v1 !== UNINITIALIZED) return v1 as T   // fast path: already set
return synchronized(lock) {
    if (_value === UNINITIALIZED) { _value = initializer() }
    _value as T
}

Android implications:

  • by lazy is ideal for singletons that are expensive to construct but used infrequently.
  • The trade-off: the first access has the full construction cost. If this happens on the main thread during a user interaction, it causes jank. Move first access to a background thread or preload on a background thread after startup.
  • Avoid lazy init for objects required immediately on every cold start — the cost is identical, just deferred.

Failure modes:

  • Lazy init on main thread during first user interaction causing dropped frames or ANR.
  • Thread-safety issues with LazyThreadSafetyMode.NONE when multiple threads access the same lazy property.
  • Circular initialization: lazy A depends on lazy B which depends on lazy A.

App Startup Library

🎤 Say it out loud (~30–45s): "App Startup is the Jetpack library that replaces the old per-library ContentProvider auto-init trick with a single shared InitializationProvider. I write Initializer<T> classes that declare their dependencies, and the library topologically sorts them into a DAG and runs them in order. The key trade-off interviewers want me to name is that everything still runs on the main thread before the first frame by default — so it's about ordering and de-duplicating ContentProviders, not about moving work off the critical path; anything not needed at first frame I'd lazily initialize instead."

Definition: The App Startup library (androidx.startup) is a Jetpack library that gives you a structured, dependency-aware way to initialize components at startup, replacing the scattered ContentProvider initialization tricks that libraries historically relied on.

Background — the ContentProvider trick: Many libraries (WorkManager, Firebase, etc.) historically used a ContentProvider to auto-initialize without requiring app code. A ContentProvider with android:initOrder runs before Application.onCreate(). The problem: each ContentProvider is a separate process boundary hook, they run sequentially, and they bloat startup time invisibly.

How App Startup works:

  1. A single InitializationProvider (one ContentProvider total, shared across all initializers) is registered in the manifest.
  2. You define Initializer<T> classes for each component.
  3. Each initializer declares its dependencies via dependencies(), forming a DAG.
  4. The library topologically sorts the DAG and runs initializers in order, on the main thread by default.
class WorkManagerInitializer : Initializer<WorkManager> {
    override fun create(context: Context): WorkManager {
        WorkManager.initialize(
            context,
            Configuration.Builder()
                .setMinimumLoggingLevel(Log.ERROR)
                .build()
        )
        return WorkManager.getInstance(context)
    }

    override fun dependencies(): List<Class<out Initializer<*>>> = emptyList()
}

class AnalyticsInitializer : Initializer<Analytics> {
    override fun create(context: Context): Analytics {
        // depends on WorkManager being ready
        return Analytics.init(context)
    }

    override fun dependencies() = listOf(WorkManagerInitializer::class.java)
}

Manifest registration:

<provider
    android:name="androidx.startup.InitializationProvider"
    android:authorities="${applicationId}.androidx-startup"
    android:exported="false"
    tools:node="merge">
    <meta-data
        android:name="com.example.WorkManagerInitializer"
        android:value="androidx.startup" />
    <!-- AnalyticsInitializer is discovered transitively via dependencies() -->
</provider>

Lazy/manual initialization: Remove the <meta-data> entry and call manually:

AppInitializer.getInstance(context)
    .initializeComponent(WorkManagerInitializer::class.java)

Trade-offs:

  • Pro: Centralizes and makes startup dependencies explicit and auditable.
  • Pro: Eliminates redundant ContentProviders.
  • Con: All initializers still run on the main thread by default; async initializers require careful handling.
  • Con: Dependency cycles produce a runtime exception at startup.

Under the hood

InitializationProvider is an ordinary ContentProvider, so the framework calls its onCreate() during ActivityThread.installContentProviders() — before Application.onCreate(). In that callback AppInitializer.discoverAndInitialize() reads the <meta-data> entries from the provider's ProviderInfo via PackageManager, then for each entry recursively resolves dependencies(), doing a depth-first traversal while tracking an "initializing" set to detect cycles (which throw IllegalStateException). Results are memoized in a mInitialized map keyed by initializer class, so a dependency shared by several initializers is only constructed once. Because the whole walk happens on the provider's onCreate on the main thread, the DAG is effectively executed sequentially in topological order — there is no built-in threading.

installContentProviders()
   InitializationProvider.onCreate()
      AppInitializer.discoverAndInitialize()
         read <meta-data> → list of Initializer classes
         for each: doInitialize(clazz, initializing=set)
            if clazz in initializing → throw (cycle)
            for dep in dependencies(): doInitialize(dep, ...)
            result = initializer.create(context)   // memoized in mInitialized

Android implications:

  • Use to replace library ContentProvider auto-init patterns (disable with tools:node="remove" in manifest merger).
  • Prefer lazy initialization over eager App Startup for anything not needed at first frame.

Baseline Profiles

🎤 Say it out loud (~30–45s): "Baseline Profiles are AOT compilation hints I ship in the APK that tell ART to natively compile my hot startup paths the moment the app installs, so I skip the JIT warm-up that normally makes the first few launches sluggish. I write a Macrobenchmark that drives the critical path, it captures which methods and classes matter, and ProfileInstaller applies it on device. The gotcha interviewers love is that the profile is useless without the profileinstaller dependency, and it goes stale as code changes — so I regenerate it in CI on a cadence."

Definition: Baseline Profiles are pre-compiled ART profiles that you ship inside your APK or AAB. The key idea is that they let the system AOT-compile your hot code paths on install, so you get native-speed execution from the very first launch instead of waiting for the JIT compiler to warm up over several runs.

Background — ART compilation modes:

  • Interpreted mode: Bytecode run directly. Slowest but requires no compilation time.
  • JIT (Just-In-Time): Code is profiled at runtime; hot methods are compiled to native. After ~10 minutes of use, the system compiles the profile in the background. This means new installs are slow for the first few app starts.
  • AOT (Ahead-Of-Time): Code compiled to native before execution. Fastest at runtime but compilation takes time and space.

Baseline Profiles give you AOT compilation of critical paths on first launch, eliminating the JIT warm-up period.

How to create a Baseline Profile:

  1. Add the androidx.benchmark:benchmark-macro and androidx.profileinstaller:profileinstaller dependencies.
  2. Write a BaselineProfileGenerator (a Macrobenchmark test) that exercises your startup path:
@RunWith(AndroidJUnit4::class)
class BaselineProfileGenerator {
    @get:Rule
    val rule = BaselineProfileRule()

    @Test
    fun generate() = rule.collect(
        packageName = "com.example.app",
        profileBlock = {
            // navigate the critical startup path
            pressHome()
            startActivityAndWait()
            // interact with the home screen
            device.findObject(By.text("Search")).click()
            waitForIdle()
        }
    )
}
  1. Run the test on a rooted device or emulator — it produces a baseline-prof.txt in src/main/.
  2. The profile is packaged into the APK and read by the ProfileInstaller library on device.

AGP integration (AGP 8.x):

// build.gradle.kts
android {
    defaultConfig {
        // enables ProfileInstaller to install profile at first run
    }
}

The Baseline Profile plugin (com.android.tools.baselineprofile) automates generation and inclusion.

Measured impact: Google reports 30–40% startup improvement for apps with comprehensive Baseline Profiles. The improvement is most visible on cold starts on lower-end devices.

Trade-offs:

  • Pro: Dramatic cold start improvement, especially on first run post-install.
  • Pro: Works at the library level too — Jetpack libraries ship their own baseline profiles.
  • Con: Requires a connected rooted device for profile generation (CI setup is non-trivial).
  • Con: Profiles go stale if code changes significantly — need periodic regeneration.
  • Con: APK size increases slightly.

Failure mode: Forgetting to add profileinstaller dependency — the profile ships in the APK but is never installed on the device.

Under the hood

The human-readable baseline-prof.txt is a list of method and class descriptors in the HRF (Human-Readable Format), e.g. HSPLcom/example/MyClass;->myMethod(I)V, where the leading flags mean Hot, Startup, and Post-startup. AGP compiles this into a binary .prof/.profm file embedded under assets/dexopt/ in the APK. On first run, ProfileInstaller copies that profile into ART's reference profile location (/data/misc/profiles/ref/<pkg>). ART's dex2oat then performs AOT compilation of exactly those flagged methods into the .odex/.art files, rather than waiting for the runtime interpreter+JIT to discover them across many sessions. Without the embedded profile, ART starts cold: methods run interpreted, the JIT samples execution counts, and only after thresholds are crossed (and during idle bg-dexopt maintenance) does it compile them — which is why the first several launches are slow.

Splash Screen

🎤 Say it out loud (~30–45s): "Since Android 12 the system owns the splash screen — it draws your themed icon over a window background on every cold and warm start, and dismisses it the instant your first frame is ready. I use the AndroidX core-splashscreen library so the behavior backports to API 23, and installSplashScreen() must run before super.onCreate(). The thing interviewers probe is setKeepOnScreenCondition — it's evaluated every single frame on the main thread, so it has to be a cheap StateFlow read, never a blocking call, and it must eventually return false or the app looks frozen."

Definition: The splash screen is the initial visual shown while the app loads. Starting with Android 12, the system enforces a standardized splash screen API rather than letting apps roll their own.

Pre-Android 12 (legacy):

  • Apps set windowBackground on the launch theme to a drawable/color, giving the appearance of instant launch.
  • The "splash screen" was actually the window background visible before the Activity drew its first frame.
  • Common pattern: theme switch — launch with SplashTheme (sets windowBackground), then setTheme(R.style.AppTheme) in onCreate() before setContentView().

Android 12+ SplashScreen API:

  • The system always shows a splash screen on cold and warm starts.
  • Composed of: icon (adaptive icon), icon background, window background.
  • The splash screen is dismissed when the app draws its first frame (or when you call splashScreen.setKeepOnScreenCondition { true } to hold it longer).

Jetpack SplashScreen library (androidx.core:core-splashscreen) — backports to API 23:

// In Activity.onCreate(), BEFORE super.onCreate()
val splashScreen = installSplashScreen()

// Keep splash visible until data is ready
splashScreen.setKeepOnScreenCondition {
    viewModel.isLoading.value
}

// Animate the exit
splashScreen.setOnExitAnimationListener { splashScreenView ->
    val slideUp = ObjectAnimator.ofFloat(
        splashScreenView.view, View.TRANSLATION_Y, 0f, -splashScreenView.view.height.toFloat()
    )
    slideUp.doOnEnd { splashScreenView.remove() }
    slideUp.start()
}

Theme setup:

<style name="Theme.App.Starting" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@color/colors_background_white</item>
    <item name="windowSplashScreenAnimatedIcon">@drawable/ic_launcher_foreground</item>
    <item name="windowSplashScreenAnimationDuration">300</item>
    <item name="postSplashScreenTheme">@style/Theme.App</item>
</style>

Under the hood

The system splash is not a separate Activity — it's a window the framework adds in the same window as your starting Activity, using the attributes resolved from your launch theme (windowSplashScreenBackground, windowSplashScreenAnimatedIcon, etc.). The WindowManager/StartingSurface machinery in system_server constructs this "starting window" before your process even finishes drawing, which is why it appears instantly. installSplashScreen() must run before super.onCreate() because it swaps your Activity's theme from Theme.App.Starting to postSplashScreenTheme and registers the keep-on-screen predicate; after setContentView, the framework hooks the ViewTreeObserver.OnPreDrawListener on the content root. On each frame the pre-draw listener evaluates your keepOnScreenCondition — returning true consumes the draw (returns false from the listener so the frame is suspended), and once it finally returns false the listener removes itself and the exit animation runs. That per-frame evaluation is exactly why the condition must be O(1).

cold start
  ├─ system_server adds starting window (theme attrs) ── shown immediately
  ├─ app process: onCreate -> installSplashScreen() swaps theme + sets predicate
  ├─ setContentView -> OnPreDrawListener attached to decor/content root
  └─ every frame: keepOnScreenCondition?  true -> suspend draw
                                          false -> remove listener, exit anim, draw

Android implications:

  • setKeepOnScreenCondition is checked on every frame; keep it cheap (read a StateFlow value, not a blocking call).
  • The splash screen duration should be minimized — it's loading time from the user's perspective.
  • Do not use the splash screen to hide a slow startup; use it to bridge the inevitable gap.
  • On Android 12+, showing a custom splash screen Activity before the system splash screen will result in a double-splash flicker.

Failure modes:

  • Forgetting installSplashScreen() before super.onCreate() — the splash screen is dismissed immediately.
  • setKeepOnScreenCondition that never returns false — app appears frozen.
  • Custom animated icon not respecting adaptive icon safe zone — icon appears clipped.

Dependency Graph Initialization

🎤 Say it out loud (~30–45s): "Dependency graph init is the cost of building every object that has to exist before the first user interaction — and with Dagger, calling DaggerAppComponent.create() eagerly constructs all your unscoped singletons, including any that do I/O in their constructors. My playbook is to keep the singleton component truly global, defer feature subcomponents until those features open, and wrap expensive singletons in Lazy<T> so they're built on first access. The subtle gotcha is transitive I/O hiding in constructors — like a SharedPreferences inject that silently parses an XML file off disk on the main thread — so I instrument each initializer with Trace.beginSection to find them."

Definition: Dependency graph initialization is the cost of constructing all the objects and their interdependencies that have to exist before the app can serve its first user interaction.

The problem: Dependency injection frameworks like Dagger construct an entire object graph eagerly when you call DaggerAppComponent.create(). If the component includes dozens of singletons — each with their own @Inject constructor doing I/O or computation — the graph construction cost is paid at startup.

Strategies:

  1. Scoped components: Don't build the entire graph in Application.onCreate(). Use a SingletonComponent with only truly global singletons, and defer feature-scoped components (booking, search) until those features are accessed.
  1. Lazy bindings: Use Lazy<T> in Dagger for singletons that are needed globally but not immediately:
@Singleton
class MyRepository @Inject constructor(
    private val db: Lazy<AppDatabase>,  // DB constructed on first access
    private val api: MyApi
)
  1. Background graph construction: For large sub-graphs, construct on a background thread and block only when the UI actually needs the result:
class Application : Application() {
    val appComponent: Deferred<AppComponent> by lazy {
        CoroutineScope(Dispatchers.Default).async {
            DaggerAppComponent.factory().create(this@Application)
        }
    }
}

This is risky — any code that calls runBlocking { appComponent.await() } on the main thread defeats the purpose. Use carefully.

  1. Tracing initialization: Use Trace.beginSection("DaggerInit") / Trace.endSection() around each initializer to see cost in Perfetto/systrace.

Failure modes:

  • Cyclical dependency in Dagger graph — compile-time error (good).
  • Transitive I/O in constructor: @Inject constructor(prefs: SharedPreferences) — SharedPreferences reads from disk on first getSharedPreferences().
  • SDK init() methods that internally call Dagger-provided singletons before the graph is ready.

Under the hood

Dagger is a fully compile-time framework — the annotation processor (KAPT/KSP) generates concrete *_Factory classes and a DaggerAppComponent implementation, so there is no runtime reflection. Each @Provides/@Inject binding becomes a Provider<T> field. The distinction that drives startup cost is how those providers are wired: an unscoped binding generates a factory whose get() allocates a fresh instance every call, while a @Singleton (scoped) binding is wrapped in DoubleCheck — a memoizing provider that lazily allocates on the first get() and then caches, using double-checked locking for thread safety. Lazy<T> is backed by that same DoubleCheck, which is why it defers construction until first access. So DaggerAppComponent.create() itself is cheap — the expense appears when the graph's initialization (or your own eager get() calls) walks transitive DoubleCheck providers and triggers constructor bodies, some of which call into the framework (getSharedPreferences, opening Room) and hit disk on the main thread.

// Generated shape (simplified)
private Provider<MyRepository> myRepositoryProvider; // = DoubleCheck.provider(MyRepository_Factory.create(dbProvider, apiProvider))

// DoubleCheck: first get() runs the factory, subsequent ones return cached instance
public T get() {
    Object result = instance;                 // volatile
    if (result == UNINITIALIZED) {
        synchronized (this) { /* double-checked */ result = delegate.get(); instance = result; }
    }
    return (T) result;
}

Avoiding Main-Thread I/O

🎤 Say it out loud (~30–45s): "The rule is that disk reads, disk writes, and network calls never touch the main thread — not at startup, not ever — because storage latency swings from a couple milliseconds on a flagship to hundreds on a low-end device under I/O contention, and the main thread is your 16ms frame budget. I catch violations early with StrictMode in debug builds, using penaltyDeath so they can't slip by. The classic trap is that the offending I/O is invisible at the call site — SharedPreferences parses its XML file synchronously on first access — so I migrate to DataStore and push anything synchronous behind withContext(Dispatchers.IO)."

Definition: Avoiding main-thread I/O means making sure disk reads, disk writes, and network calls never block the main UI thread — not during startup, not during any user interaction, ever.

Why it matters:

  • Disk read speed varies enormously across devices — what takes 2 ms on a Pixel 8 may take 200 ms on a low-end device with NAND flash.
  • eMMC/UFS storage is shared across all apps; I/O contention on a busy device makes latencies unpredictable.
  • Network I/O on the main thread can block for seconds.

Detection: StrictMode:

// In Application.onCreate() for debug builds
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectDiskReads()
            .detectDiskWrites()
            .detectNetwork()
            .penaltyLog()    // logcat warning
            .penaltyDeath()  // crash on violation — catch all before shipping
            .build()
    )
    StrictMode.setVmPolicy(
        StrictMode.VmPolicy.Builder()
            .detectLeakedSqlLiteObjects()
            .detectLeakedClosableObjects()
            .penaltyLog()
            .build()
    )
}

Common sources of main-thread I/O at startup:

  • PreferenceManager.getDefaultSharedPreferences(context) — triggers an XML file parse from disk.
  • Room.databaseBuilder(...).build() (not the query, but schema validation on first access).
  • Any File.exists() or File.read() in an initializer.
  • ClassLoader loading many new classes for the first time (inherent, but can be mitigated by Baseline Profiles).
  • Some third-party SDK init() methods that read license files or configuration from assets.

Solutions:

  • Move all SharedPreferences access to a DataStore (which is coroutines-based and async by design).
  • Wrap synchronous I/O in withContext(Dispatchers.IO) { ... }.
  • Preload critical preferences on a background thread immediately after startup and cache them in memory.

Under the hood

StrictMode doesn't watch your code — it instruments the framework's actual I/O entry points. The runtime sets a per-thread policy mask (stored in thread-local state and mirrored into a system property the native layer reads), and low-level methods like BlockGuard.getThreadPolicy().onReadFromDisk() / onWriteToDisk() / onNetwork() are called from inside libcore's file and socket primitives (e.g. posix.read, FileInputStream, the network stack). When one of those callbacks fires on a thread whose policy has the matching detect bit set, it walks the configured penalties — logging a stack trace, flashing the screen, or throwing for penaltyDeath. That's why it catches I/O you never see at the call site: getSharedPreferences() returns immediately but spawns/awaits a background load that getString() blocks on, and the actual read() syscall trips BlockGuard. The reason main-thread I/O is fatal to smoothness is structural: the main thread runs the Looper, and a blocking read() parks it in the kernel so it can't service the Choreographer VSYNC callback — the frame is missed and you jank.

      ▼                                                 │

Interview Angles: Startup

Q: How do you improve cold start?

"I think about this in eight layers. First, measure — I run adb shell am start-activity -W, pull a Perfetto trace, or use Macrobenchmark. I never optimize what I haven't measured. Second, I audit Application.onCreate(): add StrictMode in debug builds to catch any disk I/O, and defer SDK initializations using the App Startup library or lazy init. Third, I look at the Dagger graph — I instrument expensive singleton constructors with Trace.beginSection() to find the slow ones, then make them lazy or scope-delayed. Fourth, I generate and ship a Baseline Profile to eliminate the JIT warm-up on the very first run. Fifth, I verify the splash screen's window background is set correctly so the user sees a pixel of UI instantly. Sixth, I kick off above-the-fold network calls on a coroutine right in onCreate() so data is arriving by the time the first frame paints. Seventh, I make sure R8 is enabled for release because it can inline and dead-strip code paths, which helps the class-loading cost. And eighth, I call reportFullyDrawn() when the content is actually ready, because TTID isn't enough — TTFD is what the user actually experiences."

Q: What should NOT happen in Application.onCreate()?

"The short answer is: anything that blocks the main thread or initializes more than you need right now. Specifically — disk reads like SharedPreferences access or opening a database, any network request, any blocking call. I also don't want to build the full Dagger component if it transitively initializes dozens of singletons. And SDKs that are only needed in specific flows — payment SDKs, camera SDKs — shouldn't be eagerly initialized here at all. The rule of thumb I use is: if it shows up as more than 5 ms in a Perfetto trace, it needs to move."

Q: How do you measure startup?

"There are six tools I reach for, depending on how much detail I need. For a quick sanity check, adb shell am start-activity -W gives me TTID on the command line in seconds. Logcat also automatically prints Displayed com.example/.MainActivity: +1s203ms — that's TTID with zero instrumentation. When the content itself is ready — not just the first frame — I call reportFullyDrawn(), which surfaces TTFD in logcat and Perfetto. For CI and regression tracking I use the Macrobenchmark library, which runs repeated cold starts on a real device and gives me p50, p90, p99 distributions. For understanding what's happening inside a specific startup — which method is taking 80 ms — I pull a Perfetto trace and instrument critical blocks with Trace.beginSection() and endSection(). And when I want a visual overview without setting up Perfetto, Android Studio Profiler's App Startup view shows the phase breakdown."

14.2 Battery and Resource Usage

Wake Locks

🎤 Say it out loud (~30–45s): "A wake lock keeps the CPU running even when the screen is off, which I reach for only when work absolutely must finish without the device suspending — like a critical chunk of processing after a push arrives. For almost everything deferrable I use WorkManager instead, because it manages wake locks internally and respects Doze. The two gotchas I always call out: always pass a timeout to acquire() so a crash can't pin the CPU on until reboot, and always release in a finally block — a partial wake lock blocks every CPU power-saving state, so a leaked one is a battery disaster."

Definition: A wake lock is a mechanism that prevents the CPU — and optionally the screen or keyboard backlight — from going to sleep for as long as the app holds it.

How it works:

val powerManager = getSystemService(Context.POWER_SERVICE) as PowerManager
val wakeLock = powerManager.newWakeLock(
    PowerManager.PARTIAL_WAKE_LOCK,
    "MyApp::MyWakeLock"
)
wakeLock.acquire(10 * 60 * 1000L) // 10-minute timeout — ALWAYS specify timeout
try {
    doLongRunningWork()
} finally {
    wakeLock.release()
}

Wake lock types:

  • PARTIAL_WAKE_LOCK: CPU on, screen/keyboard can sleep. Most common for background work.
  • SCREEN_DIM_WAKE_LOCK / SCREEN_BRIGHT_WAKE_LOCK: Deprecated in API 17. Use WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON or View.setKeepScreenOn(true) instead.
  • FULL_WAKE_LOCK: Deprecated. Used to keep screen bright.

When a wake lock is necessary:

  • Downloading a large file that must complete even if the screen turns off.
  • Receiving a push notification and doing critical processing before the CPU sleeps.
  • Audio playback (though MediaSession manages this internally via AudioFocus + WifiLock).
  • Sensors that require CPU to process data as it arrives.

When NOT to use a wake lock:

  • For anything that can be deferred — use WorkManager with appropriate constraints instead.
  • For periodic background tasks — use JobScheduler/WorkManager which handle wake lock management internally.
  • For network calls — WorkManager + NetworkType.CONNECTED constraint is almost always correct.

Trade-offs:

  • Pro: Guarantees work completes without CPU suspension.
  • Con: Terrible for battery. A partial wake lock prevents all CPU power-saving states.
  • Con: Requires WAKE_LOCK permission in manifest.
  • Con: If not released (e.g., exception before release()), the lock is held until the timeout or process death.

Failure modes:

  • Wake lock not released due to missed finally block — CPU stays awake indefinitely, draining battery.
  • No timeout specified — acquire() without a timeout holds the lock until explicitly released; process crash = locked until reboot.
  • WifiLock forgotten — CPU wakes up but WiFi radio sleeps, causing network timeouts.

Android 13+ restrictions: Background apps requesting WAKE_LOCK are increasingly restricted. WorkManager is the right abstraction.

Under the hood

PowerManager.newWakeLock() is a thin client handle; the real state lives in system_server's PowerManagerService. Calling acquire() makes a Binder IPC that registers the lock, and the service aggregates all held locks across all apps to compute a "wakefulness" decision. For a PARTIAL_WAKE_LOCK it tells the kernel — historically by writing the lock's tag to /sys/power/wake_lock (the kernel wakeup_sources / suspend-blocker mechanism) — which prevents the SoC from entering deep suspend (autosleep), even though the display pipeline can still power down. This is why a partial lock is so costly: suspend is all-or-nothing for the application processor, so a single held lock keeps the whole CPU in an active idle state, defeating the low-power states that dominate battery savings. The acquire(timeout) overload schedules a Handler message in the service that auto-releases after the deadline — that's your safety net against a leaked lock surviving a process crash. WorkManager builds on the same primitive: its internal WakeLockHolder acquires a PARTIAL_WAKE_LOCK around a worker's execution and releases it deterministically when the worker finishes, so you get the guarantee without managing lifecycle by hand. Doze/App Standby layer on top by having PowerManagerService ignore or defer many wake locks during maintenance windows.

app                          system_server (PowerManagerService)        kernel
 newWakeLock() ── handle
 acquire(t) ──Binder──►  add to held-lock set, aggregate wakefulness ──► /sys/power/wake_lock
                          schedule auto-release at t (Handler msg)        (blocks autosleep)
 release() ──Binder──►   remove from set; if none -> allow suspend ────► /sys/power/wake_unlock

Doze Mode

🎤 Say it out loud (~30–45s): "Doze kicks in when the device is unplugged, screen off, and stationary — the system batches deferred work into periodic maintenance windows instead of letting apps wake the device whenever they want. There are two tiers: light Doze starts quickly even while moving, deep Doze adds stricter limits after the device sits still for a while. The big gotcha is that wake locks, jobs, and setExact alarms are all suspended, so the only reliable way to get urgent work through is a high-priority FCM message, which has a system exemption."

Definition: Doze Mode is a battery-saving state introduced in Android 6.0 (API 23) that aggressively restricts background CPU and network activity whenever the device is unplugged, stationary, and has its screen off.

How Doze works — two stages:

Stage 1 (Light Doze — API 24+): Triggered when screen off + unplugged, even while device is moving.

  • Network access is restricted.
  • JobScheduler jobs are deferred.
  • AlarmManager setExact() alarms are deferred (unless setExactAndAllowWhileIdle()).
  • Wake locks are ignored.
  • Sync adapters are paused.

Stage 2 (Deep Doze): Triggered after Stage 1 + device stationary for ~1 hour.

  • Same restrictions as Stage 1, but stricter.
  • The system allows brief "maintenance windows" (a few minutes every hour or so) where restrictions are lifted and deferred work runs.

Maintenance window: Work scheduled via JobScheduler or WorkManager is queued and executed during these windows. This is why WorkManager's constraint-based scheduling is battery-friendly — it piggybacks on maintenance windows.

What still works in Doze:

  • High-priority FCM (Firebase Cloud Messaging) push notifications — FCM has a special exemption to wake the device and deliver urgent notifications.
  • AlarmManager.setAlarmClock() — used for calendar alarms, user-visible.
  • Foreground services (but the device CPU is still sleeping; a foreground service notification doesn't prevent Doze itself).

Testing Doze:

# Force device into Doze
adb shell dumpsys deviceidle force-idle

# Check current Doze state
adb shell dumpsys deviceidle

# Disable Doze for testing
adb shell dumpsys deviceidle disable

Under the hood

Doze is driven by DeviceIdleController in system_server, a state machine fed by sensors: SensorManager's significant-motion / stationary detection, the screen-on signal, and the charging signal. As the device stays idle it walks through states — ACTIVE → INACTIVE → IDLE_PENDING → SENSING → LOCATING → IDLE → IDLE_MAINTENANCE — with widening backoff between maintenance windows. While idle, AlarmManagerService holds non-ALLOW_WHILE_IDLE alarms in a deferred list and the JobSchedulerService won't grant new job slots; the maintenance window briefly releases them so queued work drains in a burst. FCM high-priority messages arrive over Google Play Services' persistent connection and the framework grants the receiving app a short temporary power-allowlist (a few seconds to ~minutes) so it can run despite Doze.

                                                  IDLE_MAINTENANCE
                                                          ↓  (re-enter idle, longer interval)
                                                        IDLE

Android implications:

  • Never use AlarmManager.setRepeating() for background sync — use WorkManager.
  • Never use Handler.postDelayed() as a background schedule mechanism — it stops in Doze.
  • Legitimate use of setExactAndAllowWhileIdle() is limited: calendar/clock alarms, critical security-related timers.

App Standby

🎤 Say it out loud (~30–45s): "App Standby is per-app, not device-wide like Doze — the system sorts each app into a usage bucket from active down to restricted based on how recently and how often the user opens it. The bucket controls how often your jobs, alarms, and network access get to run, so an app the user hasn't touched in weeks might only get one job a day. The thing to remember is that the bucket changes dynamically behind your back, so you can't promise a sync cadence — you design for eventual delivery and lean on FCM for anything that has to land promptly."

Definition: App Standby is a battery-saving mechanism that progressively restricts an app's background activity based on how recently and how often the user has opened it.

How App Standby works (API 23+): The system categorizes apps into buckets based on recency and frequency of use:

  • An app the user hasn't opened in a week may only be allowed to run WorkManager jobs once per day.
  • Background sync, push notification processing, and analytics uploads are all affected.

Under the hood

Bucketing lives in AppStandbyController (part of UsageStatsService). It maintains a per-app "idle" score derived from usage events — ACTIVITY_RESUMED, notification interactions, sync usage, and "active timeout" windows — and on a periodic check elevates or demotes the bucket as elapsed-since-last-use thresholds are crossed (defaults roughly: working set ~hours, frequent ~2 days, rare ~8 days, restricted weeks). Each bucket maps to quota tables that JobSchedulerService (QuotaController) and AlarmManagerService consult: the bucket determines how many jobs/alarms an app may fire per rolling time window and the minimum gap between them. App Standby and Doze are independent gates — work must satisfy both — and UsageStatsManager.getAppStandbyBucket() reads the same controller's current value.

Background Restrictions

🎤 Say it out loud (~30–45s): "Background restrictions are a stack of independent limits, not one switch. On Oreo and up you can't freely start background services or rely on most implicit broadcasts; you move that work to startForegroundService or WorkManager. On top of that the user can flip an app to 'restricted' in battery settings, which kills essentially all background execution except FCM. The mistake I watch for is assuming a foreground service is a free pass — it isn't; it still has to be started legally and justified, and on newer APIs there are foreground-service-type and while-in-use restrictions layered on as well."

Definition: Background restrictions are additional per-app limits on background activity — either ones the user enables manually (Android 9+) or ones the system applies automatically on Android 12+ and on low-RAM devices.

Layers of background restrictions:

  1. Implicit broadcast restrictions (API 26+): Most implicit broadcasts (e.g., CONNECTIVITY_CHANGE) no longer delivered to manifest-registered receivers. Must use JobScheduler with network constraints or runtime-registered receivers.
  2. Background service restrictions (API 26+): startService() throws IllegalStateException if called while app is in background. Must use startForegroundService() (and call startForeground() within 5 seconds) or WorkManager.
  3. User-triggered battery restriction: User can mark an app as "restricted" in Settings → Battery → Background usage. This stops background execution entirely except for FCM.
  4. PROCESS_CAPABILITY_* flags: Apps declaring certain capabilities must justify them.

Best practices:

  • Use WorkManager for all deferrable background work.
  • Use FCM for server-to-device push; never poll.
  • Declare foreground services only when truly needed (GPS tracking, music playback, file download with user awareness).

Under the hood

These limits are enforced by ActivityManagerService (AMS), which tracks each process's lifecycle through the OOM-adjustment / process-state machine (foreground, visible, service, cached, etc.). When startService() is called and AMS sees the caller is not in an allowed state, it throws BackgroundServiceStartNotAllowedException (a subclass of IllegalStateException); startForegroundService() instead enters a grace state and arms a ~5s timer — miss the startForeground() call and AMS raises an ANR-style RemoteServiceException. Implicit broadcast filtering happens when the package is parsed: manifest-declared receivers for most implicit actions are simply not registered in AMS's BroadcastQueue dispatch tables (an allowlist of exempt actions survives). The "restricted" toggle sets an AppOpsManager op (RUN_ANY_IN_BACKGROUND) that AMS checks before granting any background process state.

// API 26+ : illegal because AMS sees the process is in a background/cached state
context.startService(intent)        // throws BackgroundServiceStartNotAllowedException

// Legal: AMS grants a short-lived foreground grace window
context.startForegroundService(intent)
// ...must call within ~5s or AMS kills the service:
startForeground(NOTIF_ID, notification)

Network Batching

🎤 Say it out loud (~30–45s): "Network batching matters because of the cellular radio's tail-power problem — after any transmission the radio stays in its high-power state for several seconds before stepping down, so a tiny 1 KB ping can cost nearly as much energy as a big transfer. The win is coalescing requests so the radio powers up once and does everything: batch analytics, defer non-urgent syncs, and let WorkManager align your work with other apps' wakeups. The nuance interviewers like is that this is a state machine — RRC states with promotion and demotion timers set by the carrier — so frequent dribs and drabs are the worst possible pattern."

Definition: Network batching is the practice of grouping multiple small network requests together so the radio is activated as few times as possible.

Why it matters — radio state machine: The cellular radio transitions through states:

  • Idle: Radio off. No power.
  • Low power (FACH): Radio partially active. ~40 mW on LTE.
  • Full power (DCH/Connected): Radio fully active. ~600 mW on LTE.

After a network request, the radio stays in "full power" for a "tail time" (~10 seconds on LTE) before dropping back to idle. This means a single 1 KB request uses as much power as a 100 KB request — the tail time dominates.

Batching strategy:

  • Combine multiple small requests into one (e.g., batch analytics events, batch API calls).
  • Use JobScheduler / WorkManager with setRequiredNetworkType(NetworkType.CONNECTED) — the system batches work from multiple apps, sharing radio activation.
  • Use HTTP/2 multiplexing — multiple requests over a single connection reduce overhead.
  • Implement request coalescing in your network layer: buffer events for 30 seconds, then flush.

Under the hood

The "state machine" is the modem's RRC (Radio Resource Control) protocol negotiated with the carrier's network, not something the OS sets — on LTE the relevant states are RRC_IDLE and RRC_CONNECTED, gated by network-side inactivity timers and the cRPT/DRX (discontinuous reception) configuration that defines the tail. The app never touches RRC directly; it issues sockets, the kernel hands packets to the rild/modem, and the modem requests a promotion to RRC_CONNECTED. That promotion itself costs a signaling round-trip (and energy), which is why scattered requests are doubly expensive — each may re-promote from idle. The OS-side lever is JobScheduler's coalescing: the framework holds eligible jobs and fires a batch together (often aligned with maintenance windows or setRequiresDeviceIdle/network constraints) so one radio promotion serves many apps' work.

RRC_IDLE ──(packet to send: promotion + signaling)──► RRC_CONNECTED
   ▲                                                         │
   └──────────── inactivity timer expires (tail) ◄───────────┘
   tail time = energy spent with nothing transmitting → batch to amortize it

Android implications:

  • WorkManager.enqueueUniquePeriodicWork() with a 15-minute interval (minimum) is the correct pattern for periodic sync.
  • OkHttp connection pooling helps amortize connection setup across sequential requests.
  • Consider ConnectivityManager.registerNetworkCallback() to detect when WiFi is available and batch Wi-Fi-only uploads then.

Job Constraints

🎤 Say it out loud (~30–45s): "Job constraints are the conditions all of which must be true before WorkManager or JobScheduler will run a job — network type, charging, battery-not-low, device idle, storage-not-low. They're how you make background work battery-friendly: the system waits for a cheap moment and batches everyone's eligible work together. The trap is over-constraining — if I require unmetered plus charging plus idle, a user who only has cellular and never charges overnight may have that work never run, so I pick the loosest constraints that still meet the requirement, and use exponential backoff for retries."

Definition: Job constraints are the conditions that must all be satisfied before a scheduled job — whether via WorkManager or JobScheduler — is allowed to execute.

WorkManager constraints:

val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.CONNECTED)     // any network
    .setRequiredNetworkType(NetworkType.UNMETERED)     // WiFi only
    .setRequiresBatteryNotLow(true)                    // battery above threshold
    .setRequiresCharging(true)                         // plugged in
    .setRequiresDeviceIdle(true)                       // device not actively used
    .setRequiresStorageNotLow(true)                    // internal storage not low
    .build()

val uploadWork = OneTimeWorkRequestBuilder<UploadWorker>()
    .setConstraints(constraints)
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.MINUTES)
    .build()

WorkManager.getInstance(context).enqueue(uploadWork)

Constraint trade-offs:

  • More constraints = better for battery/user, but work may never run for users on metered connections or old devices that never charge.
  • setRequiresDeviceIdle(true) combined with setRequiresCharging(true) is ideal for very heavy background tasks (large data migrations) but may only run at night.
  • UNMETERED is too strict for critical syncs; CONNECTED is generally correct.

PeriodicWork minimum interval: 15 minutes. The system may run it less frequently based on App Standby bucket. Do not use PeriodicWork for anything requiring precision timing.

Failure mode: Job that has setRequiresCharging(true) + setRequiresDeviceIdle(true) + UNMETERED on a user who only has cellular data and never uses their phone while charging — work never runs.

Under the hood

WorkManager persists each request and its constraints into its Room database (WorkSpec rows) so they survive process death and reboot. At runtime it observes constraints through ConstraintTracker subclasses — NetworkStateTracker (via ConnectivityManager callbacks), BatteryChargingTracker / BatteryNotLowTracker and StorageNotLowTracker (via sticky ACTION_* broadcasts) — and the WorkConstraintsTracker only marks a WorkSpec runnable when every tracker reports satisfied. On API 23+ WorkManager doesn't actually poll; it delegates to JobScheduler by translating the WorkSpec into a JobInfo with the matching setRequiredNetworkType/setRequiresCharging/setRequiresDeviceIdle flags, so the real gating and cross-app batching happen inside JobSchedulerService's controllers. Exponential backoff is stored on the WorkSpec (backoffPolicy + backoffDelayDuration) and recomputed on each failed attempt, then re-handed to JobScheduler as the next minimum latency.

enqueue ─► WorkSpec persisted (Room)
             │
   ConstraintTrackers (network, charging, battery, storage, idle)
             │ all satisfied?
             ▼
   JobInfo built ─► JobSchedulerService (cross-app batch + final gate) ─► Worker.doWork()

Location Updates

🎤 Say it out loud (~30–45s): "Location is one of the biggest battery sinks, so I always start from the question 'what's the loosest accuracy and longest interval that still satisfies the feature?' I use the Fused Location Provider with a priority — high-accuracy turns the GPS chip on and is only for turn-by-turn, balanced uses cell and WiFi for a fraction of the power, and passive is essentially free because it just piggybacks on other apps' requests. The classic bug is forgetting to call removeLocationUpdates when the screen goes away, which leaves GPS running in the background — and on Android 10+ that also trips the separate background-location permission."

Definition: Location updates are the mechanism by which apps receive position data from GPS, network, or passive providers — and the way you configure them has a dramatic impact on battery life.

Location providers:

  • GPS: High accuracy, high battery drain. Requires clear sky view.
  • Network (Fused): Cell towers + WiFi. Lower accuracy, lower power.
  • Passive: Receives location updates only when another app requests them. Zero additional battery cost.
  • Fused Location Provider (FLP): Google Play Services API that automatically selects the best provider based on requested accuracy and power constraints.

Power levels:

LocationRequest.Builder(Priority.PRIORITY_HIGH_ACCURACY, intervalMillis = 1000)  // GPS on, max battery
LocationRequest.Builder(Priority.PRIORITY_BALANCED_POWER_ACCURACY, 5000)         // network location
LocationRequest.Builder(Priority.PRIORITY_LOW_POWER, 60_000)                     // city-level accuracy
LocationRequest.Builder(Priority.PRIORITY_PASSIVE, Long.MAX_VALUE)               // passive only

Battery impact guidelines:

  • PRIORITY_HIGH_ACCURACY at 1-second intervals: GPS active, ~200 mW. Only for turn-by-turn navigation.
  • PRIORITY_BALANCED_POWER_ACCURACY at 5 seconds: ~10 mW. Reasonable for location-aware search.
  • PRIORITY_PASSIVE: ~0 mW overhead.

Best practices:

  • Request the lowest accuracy that meets your feature requirements.
  • Use the longest interval that is acceptable.
  • Remove location updates when not needed (removeLocationUpdates() in onStop()).
  • Use geofencing APIs instead of polling for "is the user near location X" use cases.
  • Android 10+ background location requires ACCESS_BACKGROUND_LOCATION permission and user justification.

Under the hood

The Fused Location Provider lives in Google Play Services, not the app process — your LocationRequest is marshalled over Binder to the GMS LocationManagerService/fused engine, which fuses GPS (the hardware GNSS chip via the HAL), network location (cell + WiFi RTT/scan, partly server-assisted), and onboard sensors. The fused engine deduplicates demand system-wide: it runs the GNSS hardware at the highest accuracy any client currently requests and fans the results out to every registered callback — that's literally why PRIORITY_PASSIVE is "free," it only delivers fixes the chip was already producing for someone else, and it's also why one app's HIGH_ACCURACY request raises everyone's effective power cost. Requested interval becomes a hint to the GNSS duty cycle (how often the chip wakes); a leaked callback keeps that duty cycle alive across the Binder boundary even after your Activity is gone. On Android 10+, the ACCESS_BACKGROUND_LOCATION check is enforced in the system when delivering fixes to a process that isn't in a foreground/while-in-use state.

App: LocationRequest(priority, interval)
        │  Binder IPC
        ▼
GMS Fused engine ── fuses ──► GNSS HAL (chip) + WiFi/cell scan + sensors
        │ runs chip at MAX accuracy across all clients
        ▼  fan-out to callbacks
   your onLocationResult()   (PASSIVE = only gets fixes others already triggered)

Failure mode: Forgetting to removeLocationUpdates() when the Activity pauses — GPS stays active in the background, draining battery and triggering background location access in Android 10+.

Sensor Usage

🎤 Say it out loud (~30–45s): "Sensors are read through SensorManager by registering a listener with a sampling delay, and that delay is the single biggest lever on battery — FASTEST pegs the hardware at full rate while NORMAL is fine for most cases. The gotcha interviewers love is lifecycle: you have to unregister in onStop, because the framework keeps the sensor hardware powered as long as any listener is registered, even if your activity is in the background. I also reach for batch mode with a max report latency so the SoC sensor hub buffers events and lets the application processor stay asleep between deliveries."

Definition: Sensor usage covers how apps read hardware sensors — accelerometer, gyroscope, heart rate, barometer, and so on — via SensorManager, and the sampling rate you choose directly determines how much battery the sensor hardware consumes.

How it works:

val sensorManager = getSystemService(Context.SENSOR_SERVICE) as SensorManager
val accelerometer = sensorManager.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)

sensorManager.registerListener(
    listener,
    accelerometer,
    SensorManager.SENSOR_DELAY_NORMAL  // ~200ms updates
)

Sampling rates and battery:

  • SENSOR_DELAY_FASTEST (~1 ms): Maximum rate, maximum battery.
  • SENSOR_DELAY_GAME (~20 ms): For gaming.
  • SENSOR_DELAY_UI (~60 ms): For UI interactions.
  • SENSOR_DELAY_NORMAL (~200 ms): Most background use cases.

Power guidelines:

  • Unregister listeners in onStop() or whenever the data is not needed.
  • Use batch mode (SensorManager.registerListener() with maxReportLatencyUs) to buffer sensor events and deliver them in batches, keeping the CPU in low-power states between batches.
  • On Wear OS and health apps, use the Health Services API which manages sensor duty cycling.

Failure mode: Registering a SENSOR_DELAY_FASTEST accelerometer listener and forgetting to unregister it — sensor hardware stays active at full rate, draining battery significantly.

Under the hood

The SensorManager you get from getSystemService is a SystemSensorManager that talks to the native sensorservice over Binder. The delay constant isn't a guarantee — it's a hint converted to a sampling period in microseconds and passed down to the kernel sensor driver / hardware sensor hub. The HAL multiplexes all registered listeners for a given physical sensor and runs the hardware at the fastest requested rate, then fans events out, which is why one stray FASTEST listener anywhere costs everyone. Batch mode (maxReportLatencyUs > 0) enables a hardware FIFO in the sensor hub: events accumulate in that buffer so the main application processor can stay in a deep idle state and is only woken when the FIFO fills or the latency window elapses.

      ▼

      │

Foreground Service Impact

🎤 Say it out loud (~30–45s): "A foreground service is how you tell the system 'I'm doing ongoing work the user knows about' — it shows a persistent notification and in exchange the system won't kill it or doze the CPU out from under it. The thing that trips people up now is that since Android 14 you must declare a specific foregroundServiceType in both the manifest and the startForeground call, and several types need a runtime permission, with dataSync capped at six hours a day. And the classic crash: if you call startForegroundService you have a five-second window to call startForeground, or the system kills you with ForegroundServiceDidNotStartInTimeException."

Definition: A foreground service is a service with a persistent, user-visible notification that signals to both the user and the system that the app is doing ongoing, intentional work.

Why foreground services exist: Android 8.0+ prevents background services. Foreground services are the approved mechanism for long-running work that the user must be aware of: music playback, navigation, file downloads, health tracking.

Battery impact:

  • The CPU is kept from deep sleep while a foreground service runs.
  • Network radios may be prevented from sleeping.
  • The persistent notification consumes notification shade space.
  • Heavy foreground services (GPS + network + database writes) can consume 10–30% battery per hour.

Foreground service types (API 29+): Must declare type in manifest and in startForeground():

// Manifest
<service android:name=".MyService"
    android:foregroundServiceType="location|mediaPlayback" />

// Code
startForeground(NOTIFICATION_ID, notification,
    ServiceInfo.FOREGROUND_SERVICE_TYPE_LOCATION)

Types: camera, connectedDevice, dataSync, health, location, mediaPlayback, mediaProjection, microphone, phoneCall, remoteMessaging, shortService, specialUse, systemExempted.

Android 14+ restrictions: Most foreground service types require a runtime permission grant before starting. dataSync foreground services are limited to 6 hours total per app per day.

When to use vs. WorkManager:

  • Use foreground service: music playback, turn-by-turn navigation, screen recording, active health session — user-visible, ongoing.
  • Use WorkManager: background sync, image upload, data migration, analytics flush — deferrable, doesn't need UI.
  • Never use foreground service as a workaround to bypass WorkManager's 15-minute periodic interval — Google Play policies prohibit this.

Failure mode: Starting a foreground service with startForegroundService() but not calling startForeground() within 5 seconds — the system throws an ANR-like ForegroundServiceDidNotStartInTimeException.

Under the hood

startForegroundService() routes through ActivityManagerService, which puts the app into a temporary "while-in-use"-style allowlist and arms a 5-second timer. When you call startForeground(), AMS promotes the service's process to the foreground service process state (PROCESS_STATE_FOREGROUND_SERVICE), which raises its oom_adj score so the low-memory killer treats it almost like a visible app, and it registers the notification with NotificationManagerService. If the timer fires first, AMS posts a crash via ActivityThread.throwRemoteServiceException, surfacing as ForegroundServiceDidNotStartInTimeException. The elevated process state is also what keeps the CPU out of Doze and exempts the process from background execution limits — the battery cost is a direct consequence of holding that state. On Android 14+ AMS additionally validates the declared foregroundServiceType bitmask against the manifest and the corresponding runtime permission, and dataSync time is accounted against a rolling 24-hour budget tracked per UID.

Interview Angles: Battery

Q: How do you reduce battery drain?

"I work through this in seven areas. First, I audit all background work and replace any manual Service plus AlarmManager patterns with WorkManager, using appropriate constraints so the system can batch work efficiently. Second, network batching — I combine analytics events and API calls, use HTTP/2, and schedule uploads when the device is on WiFi or charging. Third, location: I use the lowest priority that the feature actually needs, I always remove the listener in onStop(), and I prefer geofencing over polling for 'is the user near X' use cases. Fourth, sensors: I default to SENSOR_DELAY_NORMAL, unregister in onStop(), and use batch mode to let the CPU sleep between deliveries. Fifth, I measure — Android Studio Energy Profiler and Battery Historian from adb bugreport both show me exactly where time in wake state is being spent. Sixth, I audit every WAKE_LOCK usage: anything that could be WorkManager should be WorkManager, every remaining lock must have a timeout and be released in a finally block. And seventh, I design for Doze and App Standby: I test under adb shell dumpsys deviceidle force-idle, and I make sure any work that genuinely must run in Doze uses FCM high-priority or setExactAndAllowWhileIdle()."

Q: Why batch background work?

"There are two reasons. The first is the radio tail-time effect: once the LTE radio activates, it stays in full-power mode for roughly 10 seconds, regardless of how much data actually goes over the wire. So ten individual 1 KB requests spread over 10 seconds cost exactly the same as ten requests fired in one burst — the tail time dominates. Batching collapses all those tail times into one.

The second reason is that the system already does batching for you during Doze maintenance windows and when multiple apps share a WiFi connection moment. By scheduling work through WorkManager, you're opting into that system-level batching instead of fighting it. Your jobs piggyback on other apps' radio activations, and you share the cost."

Q: When is a wake lock necessary?

"Honestly, in modern Android the answer is almost never — WorkManager handles its own wake lock internally, so most of the time you should just use that. But there are three situations where a raw wake lock is genuinely the right tool. First, when work must complete without interruption even if the screen turns off and the CPU would otherwise sleep, and you can't afford to wait for a Doze maintenance window. Second, when the work is time-critical enough that Doze scheduling is truly unacceptable. And third, when WorkManager isn't the right abstraction — for example, the work is user-initiated and must finish right now, like an active file transfer.

The most legitimate real-world examples I'd give are: a media download the user explicitly started that must not be paused, an active health-monitoring foreground service that needs continuous CPU, or a critical security operation triggered by a high-priority FCM message. Outside those cases, if I see a raw wake lock I treat it as a code smell and look for the WorkManager equivalent."

14.3 ANR and Crash Debugging

Main-Thread Blocking

🎤 Say it out loud (~30–45s): "Main-thread blocking is anything on the UI thread that runs past the system's budget — five seconds for an input event, ten for a broadcast, twenty for a service lifecycle call — and because that one thread drives input, the message loop, and every Choreographer frame, blocking it freezes the whole app and eventually triggers an ANR. The classic culprits are disk I/O like the first SharedPreferences read, database queries, or runBlocking waiting on a slow coroutine. My go-to is StrictMode with penaltyDeath in debug builds so violations crash immediately and never reach production."

Definition: Main-thread blocking is any operation on the Android UI thread that consumes more time than the allowed budget, causing an ANR — Application Not Responding. The main thread owns input event processing, UI updates, and every Choreographer frame, so blocking it freezes the entire app.

Time budgets:

  • Input dispatch: 5 seconds to handle a touch/key event.
  • Broadcast receiver: 10 seconds to return from onReceive().
  • Service onCreate/onStartCommand/onBind: 20 seconds.

Common causes:

  • Database queries on main thread (pre-Room's enforced coroutine-based API).
  • SharedPreferences.getSharedPreferences() on first access (disk read).
  • Network call on main thread (throws NetworkOnMainThreadException on API 11+, but Binder calls to network-capable services do not throw this).
  • Thread.sleep() in UI code.
  • Heavy RecyclerView.Adapter.onBindViewHolder() doing computation.
  • Synchronous IPC (Binder call) to a slow service.
  • runBlocking { } on the main thread awaiting a slow coroutine.

Detection:

  • StrictMode ThreadPolicy.detectAll().penaltyDeath() in debug builds catches most main-thread violations.
  • Systrace/Perfetto shows main-thread slices and their duration.
  • Android Studio Profiler → CPU → main thread timeline.

Under the hood

The ANR mechanism lives in system_server. When the framework dispatches an input event or starts a broadcast/service, it posts a delayed "timeout" message to a watchdog handler (for input, this is tracked by the InputDispatcher in native code via anrTracker). If the responsible component acknowledges completion before the timeout fires, the message is cancelled; if not, AMS gathers stack traces from the offending process plus a few others and writes them to /data/anr/, then shows the "App isn't responding" dialog. Crucially, the budget is not CPU time — it's wall-clock time on the main Looper. The main thread's MessageQueue processes messages serially, so a long-running onBindViewHolder or a blocking disk read simply prevents the next queued input/lifecycle message from being dispatched in time. StrictMode hooks instrument BlockGuard policy callbacks on disk and network primitives, so a flagged operation is detected the moment it executes on a thread whose policy forbids it.

input event ──► InputDispatcher posts 5s ANR timer
                main Looper busy in onBindViewHolder...
                timer fires first  ──► AMS dumps traces ──► ANR dialog

Deadlock

🎤 Say it out loud (~30–45s): "A deadlock is when two or more threads each hold a lock the other needs, so nobody can make progress — they wait forever. The Android-flavored version that bites people is runBlocking on the main thread awaiting a coroutine that needs to post back to the main thread to finish: the main thread is blocked waiting, so the continuation can never run. I diagnose it from the ANR trace by finding threads in BLOCKED state and following the lock-ownership chain, and I prevent it by enforcing a consistent global lock-acquisition order."

Definition: A deadlock is the situation where two or more threads are each waiting for the other to release a lock — so all of them end up permanently blocked, waiting forever.

Classic deadlock pattern:

// Thread A holds lockA, waiting for lockB
// Thread B holds lockB, waiting for lockA
val lockA = ReentrantLock()
val lockB = ReentrantLock()

// Thread A
lockA.lock()
Thread.sleep(10) // context switch happens here
lockB.lock()     // Thread A waits for Thread B to release lockB

// Thread B
lockB.lock()
lockA.lock()     // Thread B waits for Thread A to release lockA — DEADLOCK

Android-specific deadlocks:

  • Main thread waiting on a coroutine (runBlocking) that internally posts back to the main thread — the coroutine can never resume because the main thread is blocked.
  • synchronized blocks in a ViewModel accessed from both a coroutine (Dispatchers.IO) and the main thread.
  • ContentProvider accessing a database while holding a lock that a background migration thread is waiting on.

Detection:

  • ANR traces (/data/anr/traces.txt or anr_<pid>.txt) show thread states. Look for threads in BLOCKED state and trace the lock ownership chain.
  • jstack equivalent: adb shell kill -3 <pid> dumps thread state to logcat.

Under the hood

On ART, a Kotlin synchronized block compiles to monitor-enter/monitor-exit bytecode, and each Java object carries a lock word in its header. Uncontended locks use a thin-lock fast path (a CAS storing the owning thread's id into the lock word). Under contention the lock inflates into a fat Monitor object held by the runtime, and waiting threads transition to the kBlocked thread state, recorded with the monitor and owning thread. That ownership metadata is exactly what SIGQUIT (kill -3) dumps: ART's SignalCatcher walks every thread, and for each blocked thread prints - waiting to lock <addr> ... held by thread N, letting you reconstruct the cycle. A deadlock is a cycle in this wait-for graph; ART doesn't break it automatically, so the threads stay kBlocked indefinitely until the process is killed. ReentrantLock is pure-Java (AbstractQueuedSynchronizer) rather than a monitor, so it parks threads via LockSupport.park instead — the cycle is the same, but the trace shows them parked rather than monitor-blocked.

Lock Contention

🎤 Say it out loud (~30–45s): "Lock contention is when many threads compete for the same lock and serialize behind it — there's no cycle like a deadlock, just a bottleneck where everyone queues. It won't ANR on its own, but if the main thread is one of the waiters and it stalls past five seconds it can become one, and even short of that it tanks throughput. My fixes are to shrink the critical section to the bare minimum, swap coarse synchronized blocks for concurrent or atomic structures like ConcurrentHashMap or AtomicInteger, and use a ReadWriteLock when reads vastly outnumber writes."

Definition: Lock contention happens when multiple threads compete for the same lock, causing them to queue up and wait serially even though no deadlock exists — they're just all fighting over a single bottleneck.

How it harms performance:

  • Lock contention does not cause ANR by itself, but if the main thread is one of the contending threads and must wait > 5 seconds, it becomes an ANR.
  • High contention on a lock used frequently by background threads causes throughput degradation.

Identifying lock contention:

  • Perfetto CPU trace shows main-thread slices with status Sleeping or Blocked on a monitor lock.
  • monitor_contention events in systrace output.

Solutions:

  • Replace synchronized with ConcurrentHashMap, AtomicInteger, StateFlow where appropriate.
  • Use lock-free data structures (e.g., java.util.concurrent classes).
  • Minimize lock scope — acquire lock, do minimal work, release.
  • Use ReadWriteLock when reads are far more frequent than writes.

Under the hood

When a monitor inflates under contention, ART emits a monitor_contention ATrace event whenever a thread blocks long enough — this is the slice Perfetto surfaces, and it carrys the owner thread and the line/method where the lock is held. Each contended acquisition that misses the thin-lock CAS fast path forces a kernel transition (a futex wait), so the cost isn't just waiting — it's the context switches and scheduler overhead of parking and waking threads. Lock-free structures like ConcurrentHashMap avoid this by partitioning state (per-bin CAS updates) so threads touching different keys never serialize; AtomicInteger reduces a whole critical section to a single CAS loop on a volatile field. A ReadWriteLock helps read-heavy workloads because multiple readers share the lock concurrently and only writers are exclusive — but its own bookkeeping adds overhead, so for short critical sections a plain lock or an atomic is often faster.

Slow Binder Call

🎤 Say it out loud (~30–45s): "A slow Binder call is a synchronous IPC into a system service — like PackageManager or ActivityManager — that blocks the calling thread until the remote process replies. If I make that call on the main thread, it's a direct path to an ANR, because the thread is parked in a kernel wait, not doing UI work. The gotcha interviewers probe is that it's not just my latency: the system server runs a fixed Binder thread pool, so under load all threads can be busy and my call queues behind everyone else's. So I move these off the main thread and cache results aggressively."

Definition: A slow Binder call is a synchronous IPC call through Android's Binder mechanism that takes longer than expected — and because it blocks the calling thread, if that thread is the main thread, it becomes a direct path to ANR.

How Binder works:

  • Every system service call (e.g., ActivityManager, WindowManager, PackageManager) goes through Binder IPC.
  • The call blocks the calling thread until the remote process processes the request and returns.
  • Under system load, Binder thread pools can be exhausted, causing callers to wait.

Common slow Binder calls:

  • PackageManager.queryIntentActivities() — queries all installed packages; can take 50–500 ms on devices with many apps.
  • ActivityManager.getRunningAppProcesses() — deprecated but still used in legacy code.
  • ContentResolver.query() — goes through Binder if the ContentProvider is in another process.
  • AccountManager.getAccounts() — blocked by other account operations.
  • WifiManager.getScanResults() — can be slow under radio contention.

Detection:

  • Perfetto: main-thread slice labeled with binder transaction in SLEEPING state.
  • systrace with -a com.example.app shows Binder call chains.
  • ANR trace shows main thread in Object.wait() or nativePollOnce waiting for Binder reply.

Solutions:

  • Move Binder calls to background threads (Dispatchers.IO).
  • Cache results: call once, cache, serve from cache.
  • Use async Binder APIs where available.

Under the hood

Binder is a kernel driver (/dev/binder) reached via ioctl(BINDER_WRITE_READ). The proxy marshals arguments into a Parcel, the driver copies that buffer once into the target process's mapped Binder memory region, picks a thread from the target's Binder thread pool, and the caller's thread blocks inside the kernel until a reply transaction arrives. Each process's pool is capped (default 15 threads via setMaxThreads), so an exhausted pool means callers wait for a free thread before their transaction is even serviced. The transaction buffer is also bounded (~1 MB shared per process), which is why large payloads throw TransactionTooLargeException.

caller thread          binder driver (kernel)        target Binder thread
  transact() --------->  copy Parcel into target's
  (BLOCKED)              mmap'd region, enqueue
                         pick free pool thread ------> onTransact()
  (still BLOCKED) <----- reply transaction <---------- return Parcel

BroadcastReceiver Timeout

🎤 Say it out loud (~30–45s): "A manifest-registered BroadcastReceiver runs onReceive on the main thread, and the system gives it about 10 seconds to return — overrun that and you get a broadcast ANR. The key thing is onReceive should finish fast: hand real work off to WorkManager or a coroutine. If I genuinely need a bit more time inline, I call goAsync(), which holds the broadcast 'live' and keeps the process at a higher priority, but I still must call finish() within the window or I leak the receiver and risk a kill. Foreground broadcasts get a shorter timeout than background ones, which trips people up."

Definition: A BroadcastReceiver's onReceive() must return within 10 seconds — exceed that budget and the system fires an ANR.

How it works:

  • onReceive() is called on the main thread for manifest-registered receivers.
  • Runtime-registered receivers can be dispatched on a custom handler/executor (API 33+).
  • The 10-second window is for onReceive() to return. Background work must be handed off and onReceive() must return quickly.

Correct pattern for long work in onReceive():

class MyReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        // Do NOT do any I/O or long work here
        // Hand off to WorkManager
        WorkManager.getInstance(context)
            .enqueue(OneTimeWorkRequestBuilder<MyWorker>().build())
        // onReceive() returns immediately
    }
}

Ordered broadcasts: If you call goAsync(), you get up to 10 seconds of async processing, but the PendingResult.finish() must be called within that window:

override fun onReceive(context: Context, intent: Intent) {
    val pendingResult = goAsync()
    CoroutineScope(Dispatchers.IO).launch {
        try {
            doWork() // max 10 seconds total
        } finally {
            pendingResult.finish()
        }
    }
}

Failure mode: Doing network I/O or database access directly in onReceive() without goAsync() — causes ANR on slow devices or under load.

Under the hood

Broadcasts are dispatched by the ActivityManagerService (AMS), which maintains broadcast queues and arms a timeout alarm when it delivers an intent to a receiver. AMS sends the intent to the app process over Binder; ApplicationThread posts it to the main thread Looper, which invokes onReceive. When onReceive returns (or PendingResult.finish() is called for goAsync), the app sends finishReceiver back to AMS, which cancels the timeout and proceeds to the next receiver. If the timeout fires first, AMS records an ANR. goAsync() simply tells AMS "I'm not done yet" by deferring that finishReceiver call — and while pending, AMS bumps the process's oom_adj so it isn't killed mid-work.

AMS: scheduleReceiver(intent) ---Binder---> app main Looper -> onReceive()
AMS: start timeout (e.g. 10s fg / 60s bg)
app: finishReceiver() --------Binder------> AMS: cancel timeout, dispatch next
(timeout fires before finishReceiver -> ANR)

Service Timeout

🎤 Say it out loud (~30–45s): "A Service's lifecycle callbacks run on the main thread, so onStartCommand, onCreate, and onBind have to return quickly — the system arms a timeout, around 20 seconds for a foreground service, and a hang there is a service ANR. The sharp edge is the foreground-service promotion contract: if I call startForegroundService(), I have roughly 5 seconds to call startForeground() with a notification, or on Android 12+ I get a ForegroundServiceDidNotStartInTimeException crash. So I post the notification first thing and do the actual work on a background scope."

Definition: Service lifecycle callbacks — onCreate, onStartCommand, and onBind — must complete within 20 seconds, and onDestroy must return promptly; hanging in any of these causes a service ANR.

Foreground service not started in time: When startForegroundService() is called, the service must call startForeground() within 5 seconds:

class MyService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // Must call startForeground() within 5 seconds of startForegroundService()
        startForeground(NOTIF_ID, buildNotification())
        
        // Start coroutine for actual work
        serviceScope.launch {
            doWork()
            stopSelf(startId)
        }
        return START_NOT_STICKY
    }
}

API 34+ ForegroundServiceDidNotStartInTimeException: System throws this if startForeground() isn't called in time. Treat it like an ANR.

Under the hood

startForegroundService() tells AMS to start the service and grants the app a short temporary allowlist so it can run even from the background. AMS posts a delayed timeout message (the ~5s window) before delivering onStartCommand over Binder. When the app calls startForeground(), it Binders back into AMS, which cancels that timeout and registers the service as foreground with an active notification. If the timeout message executes first, AMS throws ForegroundServiceDidNotStartInTimeException into the app process. Separately, the broader service-lifecycle timeout (~20s foreground / ~200s background) is the SERVICE_TIMEOUT watchdog AMS uses to detect a wedged callback and file a service ANR.

app: startForegroundService() --Binder--> AMS: temp-allowlist, arm 5s timeout
AMS: scheduleServiceArgs ------Binder----> app main Looper -> onStartCommand()
app: startForeground(notif) ---Binder----> AMS: cancel timeout, mark FG
(5s elapses first -> AMS throws ForegroundServiceDidNotStartInTimeException)

Input Dispatch Timeout

🎤 Say it out loud (~30–45s): "Input dispatch ANRs come from the system's InputDispatcher: it sends each touch or key event to the focused window and expects an acknowledgement within about 5 seconds. If my main thread is blocked on I/O or a lock, ViewRootImpl never reads and finishes the event, the dispatcher's deadline passes, and the user sees the 'app isn't responding' dialog. The nuance is that the timeout isn't about how long the touch handler runs — it's the gap until the event is consumed, so a main thread stuck on something completely unrelated still triggers it."

Definition: The input dispatch timeout is the 5-second window the system gives the focused window to acknowledge each touch or key event. If the window misses that deadline — because the main thread is blocked — the user sees the ANR dialog.

How it works:

  • The input dispatcher sends an event to the app's ViewRootImpl.
  • ViewRootImpl dispatches it on the main thread.
  • If the main thread is blocked (doing I/O, waiting on a lock, in a long computation), it cannot acknowledge the event.
  • After 5 seconds, the system logs an ANR and shows the dialog.

Input ANR vs. other ANRs:

  • Input ANR: "App is not responding. Do you want to close it?" — triggered by touch/key timeout.
  • Broadcast ANR: less visible to users but still logged.
  • Service ANR: logged and potentially killed.

Diagnosing input dispatch ANR: The ANR trace shows:

"main" prio=5 tid=1 Blocked
  | group="main" sCount=1 dsCount=0 obj=0x... self=0x...
  | sysTid=1234 nice=-10 cgrp=default sched=0/0 handle=0x...
  | state=S schedstat=( 0 0 0 ) utm=0 stm=0 core=0 HZ=100
  | stack=0x... stackSize=8MB
  | held mutexes=
  at com.example.DatabaseHelper.query(DatabaseHelper.java:47)   ← BLOCKING CALL
  - waiting to lock <0x...> (a java.lang.Object)
  held by thread 12

The main thread is Blocked waiting for a lock. Thread 12 holds the lock — look it up in the same file to see what it's doing.

Under the hood

In system_server, InputDispatcher (native, in libinputflinger) writes each event into an InputChannel — a socket pair shared with the app. On the app side, ViewRootImpl's WindowInputEventReceiver reads the event, runs it through the view hierarchy, and calls finishInputEvent, which writes a finished signal back over the channel. InputDispatcher tracks outstanding events per connection and arms an ANR timer (mAnrTracker); if no finish signal arrives before the deadline, it calls back into AMS to raise the ANR. Because the deadline is measured from dispatch to acknowledgement, any main-thread block — even one unrelated to input — starves the Looper and prevents the finishInputEvent write.

InputDispatcher (system_server)        app process
  publish event --InputChannel(socket)--> WindowInputEventReceiver.onInputEvent
  arm ANR timer (~5s)                      -> main thread dispatch -> view handling
  receive 'finished' <--InputChannel------ finishInputEvent()
  (timer expires first -> notify AMS -> ANR dialog)

Tombstones

🎤 Say it out loud (~30–45s): "A tombstone is the native crash dump Android writes when a process dies on a fatal signal like SIGSEGV or SIGABRT — it's the native-world equivalent of a Java stack trace. It captures the faulting signal, register state, the native backtrace, and memory maps, written by debuggerd. The thing to know is that pure Kotlin/Java crashes don't produce tombstones — those show up as a FATAL EXCEPTION in logcat. And the raw backtrace is just hex addresses, so I have to symbolicate it with ndk-stack against my unstripped .so files to get real function names."

Definition: A tombstone is a crash dump file written by Android's native crash handler (debuggerd) whenever a native process terminates with a fatal signal — SIGSEGV, SIGABRT, and so on.

Location: /data/tombstones/tombstone_XX (requires root) or via adb bugreport.

Tombstone contents:

  • Build fingerprint and timestamp.
  • Process name, PID, thread ID.
  • Signal that caused the crash (e.g., SIGSEGV = null pointer dereference in native code).
  • Register dump at the time of crash.
  • Full native stack trace (with symbols if mapping files are available).
  • Memory maps.
  • Log output near the time of crash.

When tombstones occur:

  • Native code bug (JNI code, NDK libraries, system libraries).
  • OOM with oom_adj killing the process.
  • Calling a null function pointer.
  • Stack overflow in native code.

Symbolication: Raw tombstones contain hex addresses. Use ndk-stack or the Android Studio tombstone parser to resolve to function names:

adb logcat | ndk-stack -sym /path/to/app/obj/local/arm64-v8a

Java crashes produce a FATAL EXCEPTION log in logcat, not tombstones. Tombstones are specifically native crashes.

Under the hood

When a process receives a fatal signal, the kernel runs the signal handler that Bionic (libc) installs at startup via debuggerd_init. That handler doesn't unwind in-process; instead it forks a helper and hands off to the debuggerd daemon (tombstoned), which ptrace-attaches to the crashing process so it can read registers and walk the stack from outside, unaffected by the corrupted state. It unwinds using the binaries' .eh_frame/unwind tables, formats the report, and tombstoned writes it to /data/tombstones/ with a rotating ring of up to ~10 files. Addresses are file offsets into mapped .so files; symbolication just maps lib + offset back to a symbol using the unstripped binary's symbol table.

fatal signal (SIGSEGV) -> Bionic signal handler -> debuggerd daemon
   ptrace_attach(crashing_pid)
   read registers + unwind stack via .eh_frame
   tombstoned -> /data/tombstones/tombstone_NN
backtrace frame: #00 pc 0001a2b4  libfoo.so   (offset, not symbol)
   ndk-stack: libfoo.so + 0x1a2b4 -> Foo::crash() at foo.cpp:88

Stack Traces

🎤 Say it out loud (~30–45s): "A stack trace is the snapshot of the call chain that was live when a crash or ANR happened — newest frame on top, entry point at the bottom. When I read one I scan for the topmost frame that's in my code, not framework code, because that's usually where the real problem is. For ANRs the trick is different: the file dumps every thread, so I find the main/tid=1 thread and look at what it's blocked on, then follow the held by thread N pointer to whatever is actually holding the lock it's waiting for."

Definition: A stack trace is the ordered list of method calls that were active at the moment of a crash or ANR, with the most recent call at the top and the root invocation at the bottom — it's the primary artifact you read to find the actual cause.

Multiple thread traces: ANR files include ALL threads. The main thread is labeled "main" or tid=1. Other threads show their pool names (e.g., "OkHttp Dispatcher", "DefaultDispatcher-worker-1").

Under the hood

A Java/Kotlin stack trace is captured when a Throwable is constructed: fillInStackTrace() walks ART's interpreter/JIT call frames and records, per frame, the ArtMethod and the dex PC. The dex PC is mapped back to a source line via the line_number debug info embedded in the dex file; the MyClass.kt:42 you read comes from that table, which is why an obfuscated build needs the ProGuard/R8 mapping file to deobfuscate. ANR traces are different — they're produced by the ART runtime's SIGQUIT handler: AMS sends SIGQUIT (signal 3) to the process, the signal catcher thread suspends all threads at a safepoint and dumps each one's native + managed stack, lock ownership (held by thread N), and scheduler state into the trace file. That cross-thread lock-ownership annotation is exactly what lets you trace a Blocked main thread to its holder.

                dex PC --(debug line table)--> "MyClass.kt:42"
ANR:  AMS --SIGQUIT(3)--> signal catcher thread
      suspend all threads at safepoint
      dump per-thread: state, managed+native frames, monitor owners
      -> /data/anr/anr_<ts>.txt

Crashlytics

🎤 Say it out loud (~30–45s): "Crashlytics installs its own uncaught-exception handler on top of the JVM's and signal handlers for native code, so when the app dies it serializes a report to disk and uploads it on the next launch — that asynchronous-on-next-launch model is the key detail, because reports aren't sent at crash time when the process is already unwinding. It groups crashes by stack-trace signature and gives me crash-free rate, velocity alerts, and custom keys for segmentation. The gotcha interviewers love is that Crashlytics does NOT capture ANRs — those only show up in Android Vitals — and non-fatals are rate-limited, so you can't rely on it for high-volume handled-exception telemetry."

Definition: Firebase Crashlytics is a real-time crash reporting service that aggregates crash data from every app instance in the field so you can see, group, and prioritize production failures without needing to wait for user reports.

How it works:

  • FirebaseCrashlytics.getInstance() installs exception handlers for both the JVM (Thread.UncaughtExceptionHandler) and native code (signal handlers).
  • On crash, the report is written to disk and uploaded on next app launch.
  • Reports include: stack trace, device info (model, OS version, RAM), custom logs, custom keys, breadcrumbs (recent log calls).

Best practices:

// Log breadcrumbs for context before crashes
FirebaseCrashlytics.getInstance().log("User tapped checkout button")

// Set custom keys for crash segmentation
FirebaseCrashlytics.getInstance().apply {
    setCustomKey("user_type", "premium")
    setCustomKey("screen", "checkout")
    setCustomKey("cart_items", cartSize)
}

// Log non-fatal exceptions (handled exceptions you want visibility on)
try {
    riskyOperation()
} catch (e: IOException) {
    FirebaseCrashlytics.getInstance().recordException(e)
    showUserError()
}

// Set user identifier (anonymized — NEVER use real email/name for GDPR)
FirebaseCrashlytics.getInstance().setUserId(anonymizedId)

Prioritizing crashes:

  • Crash-free rate: Target > 99.5% for production apps. Google Play Console flags apps below 99%.
  • Velocity alerts: Crashlytics alerts when a crash issue suddenly spikes — key for catching regressions in new releases.
  • Impact score: Number of affected users × severity. Fix issues affecting many users first.
  • Grouping: Crashlytics groups crashes by stack trace. If a crash is grouped incorrectly (different root cause, same stack), use custom keys to segment.

Limitations:

  • Does not capture ANRs (use Android Vitals for ANR rate).
  • Non-fatal recording has rate limiting — not every non-fatal is uploaded.
  • Large .so files require uploading symbol maps for native stack trace symbolication.

Under the hood

At init the Crashlytics SDK chains itself onto the existing handler: it captures the current Thread.getDefaultUncaughtExceptionHandler(), installs its own, and on a fatal it serializes the crash then delegates to the previous handler. JVM exceptions arrive through UncaughtExceptionHandler; native crashes (SIGSEGV, SIGABRT, etc.) are caught by a registered sigaction signal handler that runs on a pre-allocated alternate signal stack (sigaltstack) so it can still record even when the normal stack is corrupted. Because the process is in the middle of dying, the SDK only writes a minimal binary record to disk — it does not do a network upload at crash time — and a background job (via WorkManager / the crashlytics startup component) reads and uploads pending reports on the next clean launch.

Grouping is server-side: the backend normalizes each frame, hashes the trace into a "signature," and buckets identical signatures into one issue. Native traces ship as raw addresses; symbolication happens on the server using the uploaded symbol files (.symbols), mapping addresses in your stripped .so back to function/line via the debug info.

app start ─► FirebaseCrashlytics.getInstance()
              └─ saves prevHandler = Thread.getDefaultUncaughtExceptionHandler()
              └─ Thread.setDefaultUncaughtExceptionHandler(crashlyticsHandler)
              └─ sigaction(SIGSEGV/SIGABRT/…) on alternate signal stack

crash ─► handler/signal fires
          └─ write minimal session record + keys + logs to disk
          └─ delegate to prevHandler  (process still terminates)

next launch ─► background worker uploads pending reports
                └─ server normalizes frames → hash → group into issue
                └─ symbolicate native frames via uploaded symbol map

Under the hood

Android Vitals data is collected by the platform, not by an in-app SDK. ANRs are detected by system_server: components like ActivityManagerService/AnrHelper arm watchdog timers around dispatched work — input events (the InputDispatcher has its own ~5s timeout when an app fails to consume an input event), Service lifecycle calls, BroadcastReceiver.onReceive, and ContentProvider operations. When the app fails to make progress within the deadline, the system signals the process (SIGQUIT / kill -3) and the app's runtime dumps every thread's stack into an ANR trace, capturing the main thread's exact blocked state. The platform then reports these — along with crash signals it observes — through the Play Services / system metrics pipeline, which is why it only covers users opted into "usage and diagnostics."

On the server side the pipeline batches and aggregates per app version / OS / device over rolling windows, which is the source of the ~24h delay; rates are computed as affected-DAU over total-DAU, and the percentile/"bad behavior" thresholds are evaluated against user-perceptible buckets (e.g., ANRs in the foreground / while the user is interacting).

Interview Angles: ANR and Crashes

Q: How do you debug an ANR?

"I work through this in seven steps. First, reproduce — I identify the user flow, run it in a debug build with StrictMode enabled, and attach Android Studio Profiler to trigger the scenario. Second, pull the ANR trace: either adb pull /data/anr/ if I have root, or adb bugreport and extract the anr_*.txt from the zip. Third, find the main thread — I search for "main" or tid=1 and look at the topmost non-framework frame in my own code.

Fourth, identify the blocking pattern. There are four signatures I look for: if the main thread is Blocked with waiting to lock <0x...> held by thread N, that's lock contention — I then look up thread N in the same file to see what it's doing. If the main thread is in Native state at epoll_wait or nativePollOnce, it's actually idle, which means the ANR was probably a slow Binder call rather than a pure CPU block. If I see a frame at Object.wait(), the main thread is waiting for a signal from another thread — potential deadlock or a runaway background operation. And if I see a frame directly in my own code doing disk or network I/O, that's just a missing withContext(Dispatchers.IO).

Fifth, I scan all the other threads looking for any that are BLOCKED and hold the lock the main thread is waiting for. Sixth, I fix — move blocking work off the main thread, reduce lock scope, or restructure to avoid contention. And seventh, I verify with Macrobenchmark on the specific interaction path that triggered the ANR, and add a StrictMode or tracing check so a regression would be caught before it ships again."

Q: What is the difference between a crash and an ANR?

"The core distinction is cause and timing. A crash is an unhandled exception — a NullPointerException, an OutOfMemoryError, or a native signal — and the process dies immediately. An ANR is not a crash; the process is still running, but the main thread is blocked so long that the system decides the app has stopped responding.

From the user's perspective: a crash closes the app instantly with an 'App has stopped' dialog. An ANR freezes the app, and after 5 seconds the user sees 'App is not responding' with a choice to wait or close. Crucially, if the main thread unblocks before the user acts, an ANR can self-resolve — a crash never can.

For diagnosis: crashes go to Crashlytics via the FATAL EXCEPTION logcat tag, and the stack trace points to the throw site. ANRs go into /data/anr/ traces and Android Vitals, and the stack trace points to whatever blocking call the main thread is stuck on. They need different debugging strategies."

Q: How do you prioritize production stability issues?

"I use a seven-factor framework. First, impact — users affected times frequency. A crash hitting 10,000 users a day is always higher priority than one hitting 10, regardless of how easy either is to fix. Second, bad behavior thresholds: Android Vitals flags ANR rate above 0.47% and crash rate above 1.09% as bad behavior, and those directly hurt your Play Store ranking — anything above the threshold is immediate. Third, recency: a crash that appears for the first time in the latest release is a P0 because it's a regression and you have a clear rollback option. An old crash with a flat rate is lower urgency. Fourth, Crashlytics velocity alerts — a sudden spike on an existing issue means a new trigger just appeared, whether a new OS version, a new device model, or a user behavior change. Fifth, business impact: a crash in the checkout or payment flow is P0 regardless of volume, because it directly blocks revenue. A crash in the settings screen can wait. Sixth, reproducibility: an issue I can reproduce locally is cheaper to fix than one that only shows up on obscure devices in the field — give reproducible issues a priority boost. And seventh, user feedback correlation: if app store reviews start mentioning a specific crash, cross-reference with Crashlytics — that signal often surfaces issues before the volume numbers look alarming.
