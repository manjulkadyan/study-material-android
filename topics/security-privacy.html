13.1 Android Security Basics

App Sandbox and UID Isolation

Definition

Every Android app runs in its own Linux process with a unique User ID assigned at install time. The key insight is that the Linux kernel enforces the boundary — one app's process literally cannot read or write another app's memory or files unless you go through an explicit sharing mechanism.

How it works

  1. The Package Manager assigns a unique UID (e.g., u0_a123) per app at install time. This UID is permanent for the life of the installation.
  2. Each app process runs under that UID. The kernel denies cross-UID file access by default.
  3. App data is stored in /data/data/<package.name>/ with permissions rwx------ (owner = app's UID). Other UIDs cannot traverse this path.
  4. Apps can share a UID by declaring android:sharedUserId in the manifest (deprecated since API 29; use explicit content sharing instead). Both APKs must be signed with the same key.
  5. The Dalvik/ART VM provides a second layer: each app has its own VM instance, so a crash in one app does not corrupt another app's heap.

Android implications

  • Storage: Internal storage is private by default. External storage (SD card, getExternalFilesDir) is world-readable pre-API 19 and scoped-storage-restricted from API 29+.
  • IPC: To share data across apps you must use defined IPC surfaces: ContentProvider, BroadcastReceiver, Service, Activity — all subject to permission checks.
  • Root breaks the sandbox: A rooted device grants a process UID 0 (root), which the kernel allows to bypass all UID-based checks.

Trade-offs

Benefit Cost
Strong default isolation — no extra code neededApps cannot directly read each other's data even for legitimate use cases
Kernel-enforced — can't be bypassed in userspaceSharing requires explicit APIs (ContentProvider, FileProvider) with their own complexity
Process crash is containedShared UID pattern (sharedUserId) breaks isolation and is deprecated

Failure modes

  • Declaring android:sharedUserId with an untrusted or compromised partner app gives that partner full read/write access to your private files.
  • World-readable files set programmatically via openFileOutput(name, MODE_WORLD_READABLE) break sandbox — this mode was deprecated in API 17.
  • Leaving files in external storage without scoped storage protection allows any app with READ_EXTERNAL_STORAGE to read them.

Debug/test

# Verify your app's UID
adb shell ps | grep com.yourapp

# Confirm private files are not world-readable
adb shell ls -la /data/data/com.yourapp/

Permissions

Definition

Android permissions are a gating mechanism — every sensitive capability an app needs must be declared upfront in AndroidManifest.xml, and the OS or the user decides whether to grant it.

How it works

Permissions are categorized by protection level:

Level Description Example
normalAuto-granted at install; no user promptINTERNET, VIBRATE
dangerousRequires runtime user approval (API 23+)CAMERA, READ_CONTACTS
signatureGranted only to apps signed with the same key as the defining appCustom permissions between your own apps
signatureOrSystemsignature OR pre-installed system appInternal OEM APIs
appopManaged through AppOps; toggled in SettingsMANAGE_EXTERNAL_STORAGE

Declaring permissions in the manifest

<!-- Declaring a permission your app uses -->
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.READ_CONTACTS" />

<!-- Defining a custom permission (protect your own components) -->
<permission
    android:name="com.yourapp.permission.ACCESS_DATA"
    android:protectionLevel="signature" />

<!-- Requiring it on a component -->
<activity
    android:name=".SensitiveActivity"
    android:permission="com.yourapp.permission.ACCESS_DATA" />

Android implications

  • From API 23+, declaring a dangerous permission in the manifest is necessary but not sufficient — the user must grant it at runtime.
  • Permissions are granted per group (e.g., READ_CONTACTS and WRITE_CONTACTS belong to the CONTACTS group). Granting one may implicitly grant others in the group, but this behavior changed in API 26+ — always request each permission explicitly.
  • From Android 11 (API 30), if the user denies a permission twice, future calls to requestPermissions are silently ignored and you must redirect to Settings.

Failure modes

  • Requesting permissions you do not use: Google Play policy violation, and Play Store may flag your app.
  • Not handling the denial path: app crashes or shows a broken state.
  • Assuming a previously-granted permission is still granted — users can revoke permissions at any time in Settings.

Runtime Permissions

Definition

Runtime permissions, introduced in API 23, require apps to explicitly ask the user for dangerous permissions while the app is running — at install time the user sees nothing; the ask happens in context, at the moment the feature actually needs it.

How it works

  1. Check if permission is already granted: ContextCompat.checkSelfPermission().
  2. If not granted, optionally show rationale with shouldShowRequestPermissionRationale().
  3. Request it via the ActivityResultContracts.RequestPermission API (preferred over the older requestPermissions).
  4. Handle the result.
// Modern approach using Activity Result API (preferred)
private val requestPermissionLauncher = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { isGranted ->
    if (isGranted) {
        openCamera()
    } else {
        // Check if we should show rationale or go straight to settings
        if (!shouldShowRequestPermissionRationale(Manifest.permission.CAMERA)) {
            // User selected "Don't ask again" — redirect to settings
            showGoToSettingsDialog()
        } else {
            showPermissionDeniedExplanation()
        }
    }
}

fun checkAndRequestCameraPermission() {
    when {
        ContextCompat.checkSelfPermission(
            this, Manifest.permission.CAMERA
        ) == PackageManager.PERMISSION_GRANTED -> {
            openCamera()
        }
        shouldShowRequestPermissionRationale(Manifest.permission.CAMERA) -> {
            // Show UI explaining why you need the permission
            showCameraRationaleDialog {
                requestPermissionLauncher.launch(Manifest.permission.CAMERA)
            }
        }
        else -> {
            requestPermissionLauncher.launch(Manifest.permission.CAMERA)
        }
    }
}

Multiple permissions at once

private val requestMultiplePermissions = registerForActivityResult(
    ActivityResultContracts.RequestMultiplePermissions()
) { permissions ->
    val allGranted = permissions.values.all { it }
    if (allGranted) {
        proceedWithFeature()
    } else {
        handlePartialDenial(permissions)
    }
}

Key API 30+ changes

  • One-time permissions: ACCESS_FINE_LOCATION, READ_MEDIA_* can be granted just for this session.
  • Auto-reset: permissions are auto-revoked for apps unused for months.
  • Background location requires a separate two-step flow: foreground first, then background.

Failure modes

  • Calling requestPermissions on a non-resumed Activity — can cause silent drops.
  • Not re-checking after returning from background — permission may have been revoked while the app was paused.
  • Requesting permissions in onCreate before the user has context for why they're needed.

Least Privilege

Definition

Least privilege means requesting only the permissions your feature genuinely needs right now — never speculatively acquiring them "in case we need them later." The trade-off is that extra permissions are pure attack surface with no benefit.

How it works in practice

  1. Audit your manifest before each release: remove any uses-permission that no longer corresponds to an active code path.
  2. Use scoped alternatives before reaching for broad permissions:
    • Instead of READ_EXTERNAL_STORAGE: use ActivityResultContracts.GetContent() (user picks file, you get a URI — no permission needed).
    • Instead of READ_CONTACTS: use ACTION_PICK on the contacts URI.
    • Instead of CAMERA: use ACTION_IMAGE_CAPTURE — the camera app handles it.
  3. Request permissions only when the user triggers the action that needs them, not upfront.

Android implications

  • Google Play requires a Privacy Policy and justification for sensitive permissions (location, contacts, SMS, camera).
  • ACCESS_BACKGROUND_LOCATION, MANAGE_EXTERNAL_STORAGE, USE_EXACT_ALARM: require additional Play Store review.
  • Unused permissions are a security surface: a supply-chain attack on a library you ship can exploit them.

Trade-offs

Using intents to delegate to system apps (camera, contacts, file picker) means you lose control over the UX, but gain zero permission overhead and a narrower attack surface.

Exported Components

Definition

An Android component — Activity, Service, BroadcastReceiver, or ContentProvider — is exported when it can be reached by components in other apps. You control this with android:exported in the manifest, and getting it wrong is one of the most common Android security mistakes.

How it works

  • android:exported="true": any app can interact with this component.
  • android:exported="false": only components within the same app (same UID or shared UID) can use it.
  • Default behavior (pre-API 31): if an <intent-filter> is present, exported defaults to true. Without an intent-filter, it defaults to false.
  • API 31+ (Android 12) breaking change: every Activity, Service, and BroadcastReceiver that has an <intent-filter> MUST explicitly declare android:exported. The build will fail if you omit it.

Securing exported components

Three layers of defence:

Layer 1: Don't export unless you have to.

<activity
    android:name=".InternalActivity"
    android:exported="false" />

Layer 2: Require a permission for access.

<!-- Define the permission -->
<permission
    android:name="com.yourapp.permission.LAUNCH_INTERNAL"
    android:protectionLevel="signature" />

<!-- Require it on the component -->
<activity
    android:name=".SensitiveActivity"
    android:exported="true"
    android:permission="com.yourapp.permission.LAUNCH_INTERNAL" />

Layer 3: Validate inputs inside the component.

// In the Activity/Service — never trust incoming Intent data
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val action = intent.action ?: run {
        finish()
        return
    }
    // Whitelist allowed actions
    if (action !in setOf(ACTION_SHOW_DETAIL, ACTION_OPEN_FROM_NOTIFICATION)) {
        finish()
        return
    }
    val id = intent.getLongExtra(EXTRA_ID, -1L)
    if (id < 0) {
        finish()
        return
    }
}

ContentProvider specifics

<provider
    android:name=".InternalDataProvider"
    android:authorities="com.yourapp.internal"
    android:exported="false" />

<!-- If you need to share with specific apps, use grantUriPermissions -->
<provider
    android:name=".ShareProvider"
    android:authorities="com.yourapp.share"
    android:exported="false"
    android:grantUriPermissions="true" />

Failure modes

  • Exported Activity that accepts a URL extra and opens it in a WebView → open redirect / JavaScript injection.
  • Exported Service that performs privileged operations without permission checks → privilege escalation.
  • BroadcastReceiver exported without permission that triggers sensitive actions → any app can trigger it.
  • ContentProvider exported with no read/write permissions → full database readable by any app.

Debug/test

# List all exported components of your app
adb shell dumpsys package com.yourapp | grep -A 2 "ActivityResolver"

# Drozer (security testing framework) to enumerate exported components
dz> run app.activity.info -a com.yourapp
dz> run app.service.info -a com.yourapp
dz> run app.provider.info -a com.yourapp

Intent Spoofing

Definition

Intent spoofing is when a malicious app sends a crafted Intent to an exported component of your app, either impersonating a legitimate caller or injecting malicious data to trigger behaviour you didn't intend. The root cause is that Android Intents carry no built-in caller authentication.

How it works

Android Intents carry no built-in authentication. When a component is exported, any app on the device can send it an Intent — including setting arbitrary action strings, extras, and URI data. The receiving component cannot verify that the sender is who it claims to be (there is no trusted sender field that can't be spoofed from user space).

Attack scenarios

  1. Fake login callback: Your app registers an exported Activity to receive OAuth redirect Intents. An attacker app sends a spoofed Intent with a stolen authorization code.
  2. Data injection: Your exported Service accepts a URL extra and fetches it. An attacker passes an internal URL (http://localhost/admin).
  3. UI spoofing: An attacker launches your exported Activity with crafted extras to display misleading UI.

How to defend

// 1. Check the calling package (for Activities called via startActivityForResult)
override fun onActivityResult(requestCode: Int, resultCode: Int, data: Intent?) {
    // Note: callingPackage is set by Android; not spoofable from user space
    // but only available for startActivityForResult flows, not plain startActivity
}

// 2. Use LocalBroadcastManager for in-process broadcasts (deprecated; use Flow/LiveData instead)
// 3. Use explicit Intents for internal communication — don't rely on implicit Intents
val intent = Intent(this, MyInternalService::class.java)
startService(intent)

// 4. Require a signature-level permission on your exported component
// <activity android:permission="com.yourapp.permission.INTERNAL" ... />

// 5. Validate all data from Intents as untrusted input
val amount = intent.getDoubleExtra("amount", 0.0)
require(amount > 0 && amount <= MAX_TRANSFER_LIMIT) { "Invalid amount" }

Key rules

  • Never trust Intent.getStringExtra() or any extras from exported components without validation.
  • Prefer android:exported="false" + explicit Intents for all internal communication.
  • For broadcast Intents you need to receive from the system (e.g., ACTION_BOOT_COMPLETED), use android:permission to limit who else can send you broadcasts.

PendingIntent Mutability

Definition

A PendingIntent is a token you hand to another app or the system so it can launch one of your components using your app's identity. Mutability controls whether the recipient is allowed to modify the Intent that's wrapped inside — and getting this wrong is a privilege-escalation vulnerability.

How it works

Flag Meaning
FLAG_IMMUTABLEThe PendingIntent's Intent cannot be modified by the recipient
FLAG_MUTABLEThe recipient can fill in unspecified fields of the Intent

The vulnerability

A mutable PendingIntent with empty or partially-specified wrapped Intent can be hijacked. The receiver fills in the action, component, or extras and your app executes the attacker's Intent under your app's identity (with your permissions).

// DANGEROUS — mutable with no action/component specified
val badPendingIntent = PendingIntent.getActivity(
    context, 0, Intent(), PendingIntent.FLAG_UPDATE_CURRENT
    // Missing FLAG_IMMUTABLE — attacker can specify any Action/Component
)

// CORRECT — immutable for all cases where you don't need the recipient to fill fields
val safePendingIntent = PendingIntent.getActivity(
    context,
    requestCode,
    Intent(context, MyActivity::class.java).apply {
        action = ACTION_SHOW_NOTIFICATION
        putExtra(EXTRA_ID, notificationId)
    },
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)

When FLAG_MUTABLE is legitimate

The primary case is AlarmManager.setAlarmClock() and MediaSession where the system framework needs to write the ClipData or fill in a FILL_IN_COMPONENT. Even then, always specify as much of the Intent as possible.

// Mutable only when genuinely needed (e.g., inline reply notifications)
val replyPendingIntent = PendingIntent.getService(
    context,
    requestCode,
    Intent(context, ReplyService::class.java),
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_MUTABLE
)

Android 12+ enforcement

From API 31, creating a PendingIntent without explicitly setting either FLAG_IMMUTABLE or FLAG_MUTABLE throws IllegalArgumentException — you have to make a deliberate choice. The right default is FLAG_IMMUTABLE; reach for FLAG_MUTABLE only when you have a specific framework reason and can document it.

Failure modes

  • Mutable PendingIntent given to a notification manager → if a malicious app intercepts the notification before the system, it can modify the wrapped Intent to launch its own component with your app's permissions.
  • Passing a mutable PendingIntent to a third-party SDK — the SDK (or its dependencies) could be compromised.

Deep Link Validation

Definition

Deep links are URIs — HTTP/HTTPS or a custom scheme — that launch your app directly to a specific screen. Without proper validation they become a vector for open redirects, parameter injection, and data theft, so treating every deep link as untrusted external input is non-negotiable.

Types of deep links

Type Definition Security Level
Custom schememyapp://pathLow — any app can intercept or send
HTTP/HTTPS Intent filterhttp://yourapp.com/pathMedium — multiple apps may handle the same URL
App Links (verified)HTTPS with android:autoVerify="true"High — only your app handles your domain

How App Links work

  1. Declare intent-filter with android:autoVerify="true" in manifest.
  2. Host a Digital Asset Links file at https://yourapp.com/.well-known/assetlinks.json.
  3. Android verifies the association at install time. If verified, your app is the exclusive handler for those URLs — no disambiguation dialog, no other app can intercept.
<!-- AndroidManifest.xml -->
<activity
    android:name=".DeepLinkActivity"
    android:exported="true">
    <intent-filter android:autoVerify="true">
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <data
            android:scheme="https"
            android:host="www.yourapp.com"
            android:pathPrefix="/appointments" />
    </intent-filter>
</activity>

Validating deep link parameters in code

// In DeepLinkActivity.onCreate or handleIntent()
private fun handleDeepLink(intent: Intent) {
    val uri = intent.data ?: return

    // 1. Validate scheme and host — never trust them blindly even with autoVerify
    if (uri.scheme != "https" || uri.host != "www.yourapp.com") {
        finish()
        return
    }

    // 2. Whitelist known paths
    val allowedPrefixes = listOf("/appointments/", "/profile/", "/search")
    val path = uri.path ?: run { finish(); return }
    if (allowedPrefixes.none { path.startsWith(it) }) {
        finish()
        return
    }

    // 3. Sanitize and range-check parameters
    val appointmentId = uri.getQueryParameter("id")?.toLongOrNull() ?: run {
        finish()
        return
    }
    if (appointmentId <= 0) { finish(); return }

    // 4. Never pass raw URI strings to WebView
    navigateToAppointment(appointmentId)
}

Custom scheme risks

Custom schemes like myapp:// have no verification step, which means any other app can declare the same scheme and intercept your links. For any sensitive flow — authentication, payment — avoid custom schemes entirely. Always prefer App Links, which are cryptographically verified at install time.

OAuth redirect validation

// OAuth callback: validate state parameter to prevent CSRF
private fun handleOAuthCallback(uri: Uri) {
    val code = uri.getQueryParameter("code") ?: return
    val state = uri.getQueryParameter("state") ?: return

    // Compare against the state you generated and stored before launching the flow
    val expectedState = prefs.getString(KEY_OAUTH_STATE, null) ?: return
    if (state != expectedState) {
        // CSRF attack — discard
        return
    }
    exchangeCodeForToken(code)
}

Failure modes

  • Loading uri.toString() directly in a WebView → open redirect to phishing site.
  • Not validating the state parameter in OAuth flows → CSRF token theft.
  • Using custom scheme for payment redirects → any app can intercept the payment callback.

FileProvider

Definition

FileProvider is a ContentProvider subclass that lets you share files from your app's private directories with other apps through temporary URI grants, without ever exposing the actual filesystem path.

Why avoid direct file paths

  • file:// URIs reference absolute filesystem paths. If you pass a file:// URI to another app, that app must have filesystem access to that path — which violates the sandbox.
  • From API 24 (Android 7), passing file:// URIs via Intents to other apps throws FileUriExposedException. The OS enforces this.
  • Even if no exception occurs (e.g., you're targeting < API 24), exposing the path lets any app that can read the intent know where your private files are stored.

How FileProvider works

  1. Declare it in the manifest.
  2. Define accessible paths in an XML resource.
  3. Generate a content:// URI using FileProvider.getUriForFile().
  4. Grant temporary read/write permission on that URI to the receiving app.
  5. The receiving app uses ContentResolver.openInputStream() to access the file — it never sees the path.

Setup

<!-- AndroidManifest.xml -->
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_provider_paths" />
</provider>
<!-- res/xml/file_provider_paths.xml -->
<paths>
    <!-- App's private files dir: /data/data/com.yourapp/files/ -->
    <files-path name="private_files" path="." />

    <!-- App's cache dir: /data/data/com.yourapp/cache/ -->
    <cache-path name="cache" path="." />

    <!-- External files dir: /sdcard/Android/data/com.yourapp/files/ -->
    <external-files-path name="external_files" path="." />

    <!-- Avoid <external-path> (maps to root of external storage) unless truly needed -->
</paths>

Sharing a file

fun shareFile(file: File) {
    val uri = FileProvider.getUriForFile(
        context,
        "${context.packageName}.fileprovider",
        file
    )

    val shareIntent = Intent(Intent.ACTION_SEND).apply {
        type = "application/pdf"
        putExtra(Intent.EXTRA_STREAM, uri)
        // Grant read permission to whichever app the user picks
        addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
    }

    context.startActivity(Intent.createChooser(shareIntent, "Share file"))
}

Camera capture example

private var photoUri: Uri? = null

private val takePictureLauncher = registerForActivityResult(
    ActivityResultContracts.TakePicture()
) { success ->
    if (success) {
        photoUri?.let { processPhoto(it) }
    }
}

fun launchCamera() {
    val photoFile = File(context.cacheDir, "photo_${System.currentTimeMillis()}.jpg")
    val uri = FileProvider.getUriForFile(
        context,
        "${context.packageName}.fileprovider",
        photoFile
    )
    photoUri = uri
    takePictureLauncher.launch(uri)
}

Failure modes

  • Using <external-path path="."> in file_provider_paths.xml — exposes the entire external storage root. Scope paths as tightly as possible.
  • Not setting android:exported="false" on the FileProvider — other apps could enumerate or access files directly.
  • Forgetting FLAG_GRANT_READ_URI_PERMISSION — the receiving app gets a URI it can't open.
  • Retaining content:// URIs beyond the activity lifecycle — grants expire.

WebView Security

Definition

WebView embeds a full browser engine inside your app. The reason misconfigured WebViews show up on so many security audit reports is that they can expose your app's Java and Kotlin interfaces directly to web content — and if that content is untrusted, that's essentially remote code execution.

Key security settings

webView.settings.apply {
    // JavaScript: disable unless your own trusted content requires it
    javaScriptEnabled = false // default; only enable for your own URLs

    // Never allow file access — prevents file:// scheme injection
    allowFileAccess = false          // API 29+ default; set explicitly for older targets
    allowContentAccess = false

    // Disable universal access from file URLs
    // (prevents file:// pages from fetching http:// resources)
    allowFileAccessFromFileURLs = false    // deprecated but set for older targets
    allowUniversalAccessFromFileURLs = false

    // Prevent mixed content (http:// loaded in https:// WebView)
    mixedContentMode = WebSettings.MIXED_CONTENT_NEVER_ALLOW

    // Disable geolocation (enable only if feature requires it)
    setGeolocationEnabled(false)

    // Disable saving form data
    saveFormData = false
    savePassword = false
}

JavaScript Interface (addJavascriptInterface)

This is the highest-risk WebView API. It exposes Kotlin/Java methods to JavaScript running in the WebView.

// DANGEROUS if webView loads untrusted content
webView.addJavascriptInterface(MyBridge(), "AndroidBridge")

class MyBridge {
    @JavascriptInterface // REQUIRED annotation — without it, methods are not exposed
    fun getUserToken(): String {
        // If untrusted JS can call this, it can steal the token
        return secureStore.getToken()
    }
}

Rules for safe JavaScript interfaces:

  1. Never add a JS interface if the WebView loads any untrusted URL.
  2. Annotate only with @JavascriptInterface — this is required from API 17+ for methods to be callable (pre-17 all public methods were exposed — a major attack surface).
  3. Never expose sensitive data (tokens, PII) through the bridge.
  4. Validate all parameters passed from JS as untrusted input.

URL interception — prevent open redirects

webView.webViewClient = object : WebViewClient() {
    override fun shouldOverrideUrlLoading(view: WebView, request: WebResourceRequest): Boolean {
        val url = request.url
        // Whitelist: only allow navigations within your domain
        if (url.scheme == "https" && url.host == "www.yourapp.com") {
            return false // let WebView handle it
        }
        // External URLs — open in system browser, not your WebView
        if (url.scheme == "https" || url.scheme == "http") {
            startActivity(Intent(Intent.ACTION_VIEW, url))
        }
        return true // block in WebView
    }

    override fun onReceivedSslError(view: WebView, handler: SslErrorHandler, error: SslError) {
        // NEVER call handler.proceed() — that ignores TLS errors
        handler.cancel()
        showTlsErrorToUser()
    }
}

Safe Browsing

// Enable Safe Browsing (checks URLs against Google's list of known bad URLs)
WebView.startSafeBrowsing(context) { success ->
    // success = false means Safe Browsing is unavailable on this device
}

webView.settings.safeBrowsingEnabled = true // API 26+

Additional hardening

  • Disable setWebContentsDebuggingEnabled(true) in production builds (it's only valid in debug). It exposes the WebView to Chrome DevTools over ADB.
  • Never load file:// URLs that the user or an external source controls.
  • Use WebResourceResponse to serve sensitive content from code rather than from files, when possible.
// Only enable debugging in debug builds
if (BuildConfig.DEBUG) {
    WebView.setWebContentsDebuggingEnabled(true)
}

Failure modes

  • onReceivedSslError calling handler.proceed() → app silently accepts invalid/expired certificates → MITM possible.
  • javaScriptEnabled = true with untrusted content + addJavascriptInterface → remote code execution equivalent.
  • allowFileAccess = true + allowUniversalAccessFromFileURLs = true → XSS in a local file can exfiltrate all app files.

13.2 Data Security

Android Keystore

Definition

The Android Keystore System is a hardware-backed — or on older devices, OS-isolated — key storage facility. The defining property is that keys stored in the Keystore can never be extracted from the device in plaintext; all cryptographic operations happen inside the secure hardware, whether that's a StrongBox secure element, a TEE, or the isolated Keystore daemon.

What it is

  • Not a file on disk. It is a system service backed by hardware security where available.
  • Keys are bound to the app (via UID) — another app cannot use your Keystore keys.
  • Supports key usage policies: require biometric authentication, time-based expiry, user presence check.

How it works

// 1. Generate an AES key in the Keystore
fun generateAesKey(alias: String) {
    val keyGenerator = KeyGenerator.getInstance(
        KeyProperties.KEY_ALGORITHM_AES,
        "AndroidKeyStore" // This is the Keystore provider name
    )
    keyGenerator.init(
        KeyGenParameterSpec.Builder(
            alias,
            KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
        )
            .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
            .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
            .setKeySize(256)
            .setUserAuthenticationRequired(false) // set true to require biometrics
            .build()
    )
    keyGenerator.generateKey()
}

// 2. Encrypt data using the Keystore key
fun encrypt(alias: String, plaintext: ByteArray): Pair<ByteArray, ByteArray> {
    val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    val secretKey = keyStore.getKey(alias, null) as SecretKey

    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    cipher.init(Cipher.ENCRYPT_MODE, secretKey)
    val iv = cipher.iv
    val ciphertext = cipher.doFinal(plaintext)
    return Pair(iv, ciphertext)
}

// 3. Decrypt
fun decrypt(alias: String, iv: ByteArray, ciphertext: ByteArray): ByteArray {
    val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    val secretKey = keyStore.getKey(alias, null) as SecretKey

    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    val spec = GCMParameterSpec(128, iv)
    cipher.init(Cipher.DECRYPT_MODE, secretKey, spec)
    return cipher.doFinal(ciphertext)
}

Key generation for asymmetric (RSA/EC)

fun generateRsaKeyPair(alias: String) {
    val keyPairGenerator = KeyPairGenerator.getInstance(
        KeyProperties.KEY_ALGORITHM_RSA, "AndroidKeyStore"
    )
    keyPairGenerator.initialize(
        KeyGenParameterSpec.Builder(
            alias,
            KeyProperties.PURPOSE_SIGN or KeyProperties.PURPOSE_VERIFY
        )
            .setDigests(KeyProperties.DIGEST_SHA256)
            .setSignaturePaddings(KeyProperties.SIGNATURE_PADDING_RSA_PKCS1)
            .setKeySize(2048)
            .setUserAuthenticationRequired(true) // require biometric/PIN before signing
            .setUserAuthenticationValidityDurationSeconds(-1) // per-use auth (not time-based)
            .build()
    )
    keyPairGenerator.generateKeyPair()
}

StrongBox vs TEE

  • TEE (Trusted Execution Environment): An isolated processor within the main SoC. Keys cannot be extracted even with root, but a sophisticated hardware attack on the SoC could theoretically succeed.
  • StrongBox: A dedicated secure element (separate chip, e.g., Titan M on Pixel). Higher assurance — keys are isolated even from the main SoC.
// Request StrongBox (API 28+), fallback to TEE
val spec = KeyGenParameterSpec.Builder(alias, ...)
    .setIsStrongBoxBacked(true) // throws StrongBoxUnavailableException if not available
    .build()

When Keystore keys are invalidated

  • setInvalidatedByBiometricEnrollment(true) (default): adding a new fingerprint after key creation invalidates it. The app must re-generate the key.
  • Factory reset: Keystore is wiped.
  • Root: Keystore may be wiped as a security measure on stock ROMs.

Android implications

  • Keys cannot be exported (by design). You cannot back up a Keystore key to a server.
  • On low-end devices pre-API 18, there is no hardware-backed Keystore — the software fallback is less secure.
  • Keystore keys survive app updates but are deleted on app uninstall.

Trade-offs

Benefit Cost
Key material never leaves secure hardwareCannot back up keys; if device is wiped, keys are gone
Per-app UID isolationSetup is complex (Cipher/KeyStore boilerplate)
Biometric auth binding availableStrongBox not available on all devices

EncryptedSharedPreferences

Definition

EncryptedSharedPreferences is a Jetpack Security wrapper around SharedPreferences that transparently encrypts both keys and values — AES-256-GCM for values, AES-256-SIV for keys — with the master key living in the Android Keystore. From the outside it's a drop-in replacement; underneath, nothing touches disk in plaintext.

How it works

  1. A master key is created in (or retrieved from) the Keystore.
  2. The master key wraps a data encryption key stored in the encrypted prefs file.
  3. Every key and value is encrypted before being written to the XML file.

Setup

Add dependency:

// build.gradle.kts
implementation("androidx.security:security-crypto:1.1.0-alpha06")
import androidx.security.crypto.EncryptedSharedPreferences
import androidx.security.crypto.MasterKey

fun createEncryptedPrefs(context: Context): SharedPreferences {
    val masterKey = MasterKey.Builder(context)
        .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
        .build()

    return EncryptedSharedPreferences.create(
        context,
        "secure_prefs",                              // filename (stored in app's data dir)
        masterKey,
        EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
        EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
    )
}

// Usage — exactly like regular SharedPreferences
val prefs = createEncryptedPrefs(context)
prefs.edit()
    .putString("auth_token", token)
    .putLong("token_expiry", expiryMs)
    .apply()

val token = prefs.getString("auth_token", null)

What it protects against

  • ADB backup extraction of SharedPreferences XML files.
  • Physical access to the device storage (if the device is encrypted and locked).
  • Other apps reading your prefs (they can't, due to UID isolation, but encryption provides defence in depth).

What it does NOT protect against

  • Root: a root process can extract the Keystore keys on devices without StrongBox, allowing decryption.
  • A running process with the same UID (e.g., a malicious SDK in your own process) — it calls the same API you do.
  • Memory scraping of a live process — plaintext values exist in memory after decryption.

Trade-offs

Benefit Cost
Drop-in replacement for SharedPreferencesSlower (encryption on every read/write)
Master key in Keystore — hardware-backedAlpha/beta API — can have migration issues between versions
Protects against offline storage accessDoes not protect a rooted live device

Migration from plain SharedPreferences

There is no automatic migration. You must read old plain prefs, write to encrypted prefs, and delete the old file. Do this once at app startup.

EncryptedFile

Definition

EncryptedFile from Jetpack Security gives you AES-256-GCM file encryption backed by the Android Keystore. Use it whenever you need to store sensitive files — PDFs, images, large JSON blobs — that must stay unreadable even if someone extracts the device storage or pulls an ADB backup.

How it works

Internally uses Tink's StreamingAead — the file is split into 4KB segments, each encrypted with AES-256-GCM. The key is derived from the master Keystore key.

fun writeEncryptedFile(context: Context, filename: String, data: ByteArray) {
    val masterKey = MasterKey.Builder(context)
        .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
        .build()

    val file = File(context.filesDir, filename)

    val encryptedFile = EncryptedFile.Builder(
        context,
        file,
        masterKey,
        EncryptedFile.FileEncryptionScheme.AES256_GCM_HKDF_4KB
    ).build()

    encryptedFile.openFileOutput().use { outputStream ->
        outputStream.write(data)
    }
}

fun readEncryptedFile(context: Context, filename: String): ByteArray {
    val masterKey = MasterKey.Builder(context)
        .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
        .build()

    val file = File(context.filesDir, filename)

    val encryptedFile = EncryptedFile.Builder(
        context,
        file,
        masterKey,
        EncryptedFile.FileEncryptionScheme.AES256_GCM_HKDF_4KB
    ).build()

    return encryptedFile.openFileInput().use { inputStream ->
        inputStream.readBytes()
    }
}

When to use EncryptedFile vs EncryptedSharedPreferences

  • EncryptedSharedPreferences: key-value pairs, configuration, tokens, flags.
  • EncryptedFile: arbitrary binary data — PDFs, user documents, large JSON blobs, offline cache of sensitive content.

Failure modes

  • Passing a non-empty existing file to EncryptedFile.Builder where the file was NOT written by EncryptedFile → IOException on read.
  • Creating two EncryptedFile instances with different master keys for the same file → decryption failure.

Token Storage

Definition

Where and how you store authentication tokens — session tokens, OAuth access and refresh tokens, JWTs — is one of the highest-impact security decisions you make in a mobile app, because a stolen token is often equivalent to a stolen identity.

Storage options ranked by security

Option Security Notes
Android Keystore (key only)HighestKey never leaves hardware; use to encrypt the token
EncryptedSharedPreferencesHighAES-256-GCM, master key in Keystore
Internal storage (plain)MediumUID-isolated, but readable with root or ADB backup
SharedPreferences (plain)MediumSame as internal storage; XML readable with ADB backup on pre-M devices
External storageLowWorld-readable; avoid entirely for tokens
Hardcoded in code/resourcesNoneDecompilable; never do this

Best practice recommendation

// Pattern: store auth token in EncryptedSharedPreferences
class TokenRepository(context: Context) {

    private val prefs: SharedPreferences by lazy {
        val masterKey = MasterKey.Builder(context)
            .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
            .build()

        EncryptedSharedPreferences.create(
            context,
            "token_store",
            masterKey,
            EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
            EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
        )
    }

    fun saveToken(token: String) {
        prefs.edit().putString(KEY_AUTH_TOKEN, token).apply()
    }

    fun getToken(): String? = prefs.getString(KEY_AUTH_TOKEN, null)

    fun clearToken() {
        prefs.edit().remove(KEY_AUTH_TOKEN).apply()
    }

    companion object {
        private const val KEY_AUTH_TOKEN = "auth_token"
    }
}

For ultra-sensitive tokens: Keystore-encrypted

// Store the token encrypted with a Keystore key
// The raw token never persists to disk — only ciphertext + IV do
class KeystoreTokenRepository(context: Context) {
    private val prefs = context.getSharedPreferences("ks_token_store", Context.MODE_PRIVATE)
    private val keyAlias = "token_key"

    init {
        if (!KeyStore.getInstance("AndroidKeyStore").apply { load(null) }.containsAlias(keyAlias)) {
            generateAesKey(keyAlias)
        }
    }

    fun saveToken(token: String) {
        val (iv, ciphertext) = encrypt(keyAlias, token.toByteArray(Charsets.UTF_8))
        prefs.edit()
            .putString("iv", Base64.encodeToString(iv, Base64.DEFAULT))
            .putString("ct", Base64.encodeToString(ciphertext, Base64.DEFAULT))
            .apply()
    }

    fun getToken(): String? {
        val ivB64 = prefs.getString("iv", null) ?: return null
        val ctB64 = prefs.getString("ct", null) ?: return null
        val iv = Base64.decode(ivB64, Base64.DEFAULT)
        val ct = Base64.decode(ctB64, Base64.DEFAULT)
        return try {
            decrypt(keyAlias, iv, ct).toString(Charsets.UTF_8)
        } catch (e: Exception) {
            null // Key invalidated (e.g., new biometric enrolled)
        }
    }
}

Interview answer: "Where do you store auth tokens?"

"I store auth tokens in EncryptedSharedPreferences backed by a Keystore master key. That gives AES-256-GCM encryption at rest, with the key never leaving the secure hardware on supported devices. For extremely sensitive flows — like a private signing key — I go a level lower and use the Keystore directly, storing only the ciphertext and IV on disk. I never use plain SharedPreferences, external storage, or hardcoded values."

Biometrics

Definition

The BiometricPrompt API in the Jetpack Biometric library gives you a single, unified interface for fingerprint, face, and iris authentication. It is the right API to use — the older FingerprintManager is deprecated and broken on many Android 10+ devices.

Two modes

  1. Authentication only (no Keystore key): verify the user is present; you handle what happens after.
  2. Crypto-bound authentication: tie a Keystore key to biometric auth — the key is only unlocked after biometric passes.

Authentication only

val executor = ContextCompat.getMainExecutor(this)
val biometricPrompt = BiometricPrompt(this, executor, object : BiometricPrompt.AuthenticationCallback() {
    override fun onAuthenticationSucceeded(result: BiometricPrompt.AuthenticationResult) {
        // User authenticated — proceed
        unlockFeature()
    }
    override fun onAuthenticationError(errorCode: Int, errString: CharSequence) {
        // Permanent error (lockout, no hardware, etc.)
        showError(errString.toString())
    }
    override fun onAuthenticationFailed() {
        // Single attempt failed (wrong finger) — prompt stays open automatically
    }
})

val promptInfo = BiometricPrompt.PromptInfo.Builder()
    .setTitle("Authenticate")
    .setSubtitle("Use your biometric to access the app")
    .setNegativeButtonText("Use PIN instead")
    .setAllowedAuthenticators(
        BiometricManager.Authenticators.BIOMETRIC_STRONG or
        BiometricManager.Authenticators.DEVICE_CREDENTIAL // API 30+
    )
    .build()

biometricPrompt.authenticate(promptInfo)

Crypto-bound biometric — strongest pattern

// Step 1: Generate a key that requires per-use biometric auth
fun generateBiometricKey(alias: String) {
    val keyGenerator = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
    keyGenerator.init(
        KeyGenParameterSpec.Builder(alias, KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
            .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
            .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
            .setUserAuthenticationRequired(true)
            .setUserAuthenticationValidityDurationSeconds(-1) // per-use, not time-window
            .setInvalidatedByBiometricEnrollment(true)
            .build()
    )
    keyGenerator.generateKey()
}

// Step 2: Create a Cipher initialized with the key — this triggers biometric prompt
fun getCipher(alias: String): Cipher {
    val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    val secretKey = keyStore.getKey(alias, null) as SecretKey
    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    cipher.init(Cipher.ENCRYPT_MODE, secretKey) // This doesn't fail yet
    return cipher
}

// Step 3: Show biometric prompt with the crypto object
fun authenticateWithCrypto(cipher: Cipher) {
    val cryptoObject = BiometricPrompt.CryptoObject(cipher)
    biometricPrompt.authenticate(promptInfo, cryptoObject)
    // In onAuthenticationSucceeded, result.cryptoObject?.cipher is the unlocked cipher
}

Checking biometric availability

val biometricManager = BiometricManager.from(context)
when (biometricManager.canAuthenticate(BiometricManager.Authenticators.BIOMETRIC_STRONG)) {
    BiometricManager.BIOMETRIC_SUCCESS -> { /* available */ }
    BiometricManager.BIOMETRIC_ERROR_NO_HARDWARE -> { /* no biometric hardware */ }
    BiometricManager.BIOMETRIC_ERROR_HW_UNAVAILABLE -> { /* temporarily unavailable */ }
    BiometricManager.BIOMETRIC_ERROR_NONE_ENROLLED -> {
        // Prompt user to enroll
        val enrollIntent = Intent(Settings.ACTION_BIOMETRIC_ENROLL)
        startActivity(enrollIntent)
    }
}

Failure modes

  • Using deprecated FingerprintManager — broken on many Android 10+ devices.
  • Not handling BIOMETRIC_ERROR_LOCKOUT and BIOMETRIC_ERROR_LOCKOUT_PERMANENT — user gets locked out with no path forward.
  • Using time-based auth validity (setUserAuthenticationValidityDurationSeconds(30)) for sensitive operations — a compromised app could use the unlocked window.
  • Ignoring setInvalidatedByBiometricEnrollment(true) — a new biometric added by an attacker (after stealing the device) would give them access.

TLS

Definition

Transport Layer Security (TLS) encrypts all data in transit between your app and your servers. Android enforces it by default from API 28 onwards — cleartext traffic is blocked unless you explicitly opt in, which you should almost never do in production.

Network Security Config

Android's Network Security Config (XML) lets you declaratively configure TLS behavior without code changes.

<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <!-- Production: require TLS, no cleartext, no user CAs -->
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
            <!-- Do NOT include: <certificates src="user" /> in production -->
        </trust-anchors>
    </base-config>

    <!-- Debug-only: allow user-installed CAs for proxy tools like Charles -->
    <debug-overrides>
        <trust-anchors>
            <certificates src="system" />
            <certificates src="user" />
        </trust-anchors>
    </debug-overrides>

    <!-- Allow cleartext for specific domains (legacy API, avoid in new code) -->
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="false">legacy.internal.api.com</domain>
    </domain-config>
</network-security-config>
<!-- AndroidManifest.xml -->
<application
    android:networkSecurityConfig="@xml/network_security_config"
    ...>

Key defaults by API level

API Default cleartext User CAs trusted
< 24PermittedYes
24–27PermittedNo (debug builds: yes)
28+Not permittedNo

Retrofit + OkHttp TLS

// Retrofit respects the system TLS config automatically.
// Override TLS version/cipher suites if you need stricter control:

    .tlsVersions(TlsVersion.TLS_1_3, TlsVersion.TLS_1_2)

Failure modes

  • cleartextTrafficPermitted="true" in production Network Security Config → credentials sent in plaintext.
  • <certificates src="user" /> in production config → man-in-the-middle trivially possible with a user-installed CA (the exact scenario proxy tools exploit).
  • Calling setSSLSocketFactory with a trust-all TrustManager → completely disables certificate validation.
// NEVER DO THIS — it defeats all TLS security
val trustAll = object : X509TrustManager {
    override fun checkClientTrusted(chain: Array<X509Certificate>, authType: String) {}
    override fun checkServerTrusted(chain: Array<X509Certificate>, authType: String) {}
    override fun getAcceptedIssuers(): Array<X509Certificate> = emptyArray()
}

Certificate Pinning

Definition

Certificate pinning makes your app reject any TLS certificate that doesn't match a specific public key or certificate you've embedded in the app — even if that certificate was signed by a trusted CA. The key insight is that it defends against scenarios where the CA itself is compromised, rogue, or coerced: a nation-state MITM, a rogue CA issuing a fraudulent cert for your domain, or a corporate proxy intercepting traffic.

How it works

Instead of trusting the entire CA chain, you embed a hash of the server's public key (or certificate) in your app. At connection time, you compare the server's presented public key against your pinned hash.

Network Security Config pinning (recommended)

<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <domain-config>
        <domain includeSubdomains="true">api.yourapp.com</domain>
        <pin-set expiration="2027-01-01">
            <!-- SHA-256 hash of the Subject Public Key Info (SPKI) -->
            <!-- Primary pin (current certificate) -->
            <pin digest="SHA-256">abc123...base64hash...</pin>
            <!-- Backup pin (next certificate, ready for rotation) -->
            <pin digest="SHA-256">def456...base64hash...</pin>
        </pin-set>
    </domain-config>
</network-security-config>

Getting the pin value:

# Extract SPKI hash from a certificate
openssl x509 -in cert.pem -pubkey -noout | \
  openssl pkey -pubin -outform DER | \
  openssl dgst -sha256 -binary | \
  openssl enc -base64

OkHttp CertificatePinner (programmatic)

val certificatePinner = CertificatePinner.Builder()
    .add("api.yourapp.com", "sha256/abc123...base64...")  // primary
    .add("api.yourapp.com", "sha256/def456...base64...")  // backup
    .build()

val client = OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build()

Pin rotation strategy

Pin rotation is the hardest operational challenge with certificate pinning. If you deploy a new certificate without a backup pin already shipped in the app, users on old versions lose connectivity to your server, and you have to support the old pins until the whole userbase has updated.

Best practice:

  1. Always include a backup pin — the next certificate's SPKI hash — so you can rotate without a blackout window.
  2. Set an expiration date in Network Security Config — after expiry, pinning is disabled and the app falls back to standard CA validation, which prevents a permanent hard lockout for old app versions that can't be updated.
  3. Pin the SPKI (the public key hash) rather than the full certificate — that way the pin survives certificate renewal as long as the same key pair is reused.

When to use certificate pinning

  • Financial apps, health apps, any app handling highly sensitive data where a rogue CA attack is a realistic threat.
  • Apps that communicate with a small number of known, controlled API endpoints.
  • Do NOT pin if: your API is behind a CDN that rotates certificates frequently, or if you can't guarantee app updates before certificate expiry.

Trade-offs

Benefit Cost
Defeats rogue CA / MITM attacksCertificate rotation can hard-break old app versions
Visible in code reviewBlocks legitimate corporate TLS inspection proxies
Works with Network Security Config (no code)Harder to test — requires debug bypass

Debug bypass for testing with Charles/mitmproxy

<debug-overrides>
    <!-- In debug: disable pinning so you can inspect traffic -->
    <trust-anchors>
        <certificates src="system" />
        <certificates src="user" />
    </trust-anchors>
</debug-overrides>

The <debug-overrides> block only applies to debuggable="true" builds — pinning remains enforced in production.

Failure modes

  • Pinning only the leaf certificate (not SPKI) → broken at every certificate renewal.
  • No backup pin → any certificate rotation causes connection failures.
  • No expiry date → old unpatchable app versions are permanently broken.
  • Pinning in an app with a very long tail of old versions → operational nightmare.

Rooted Device Limitations

Definition

A rooted Android device makes UID 0 (root) access available to user-space processes. Root breaks the foundational assumption of the Android security model — that the app UID boundary is inviolable — which means every defence you've built on top of that boundary becomes weaker or irrelevant.

What root access enables (threat model)

Attack Mechanism
Read private filesRoot bypasses filesystem permissions
Extract Keystore keysOn devices without StrongBox, root can access the Keystore daemon's memory or storage
Read process memoryRoot can ptrace your app process and dump the heap
Modify app code at runtimeFrida/JDWP hooking, method swizzling

What you can do (and their limits)

1. Detect root (defense in depth, not a hard barrier)

// Using RootBeer library (or implement manually)
val rootBeer = RootBeer(context)
if (rootBeer.isRooted) {
    // Warn the user or limit functionality
    // Do NOT silently stop working — that's a bad UX with no explanation
}

Manual checks (can each be individually bypassed by a determined attacker):

fun isDeviceRooted(): Boolean {
    // Check 1: su binary present
    val suPaths = listOf("/system/bin/su", "/system/xbin/su", "/sbin/su")
    if (suPaths.any { File(it).exists() }) return true

    // Check 2: Test Tags (build props on production ROMs)
    if (Build.TAGS?.contains("test-keys") == true) return true

    // Check 3: Can we execute su?
    return try {
        Runtime.getRuntime().exec(arrayOf("/system/xbin/su", "-c", "id"))
        true
    } catch (e: IOException) {
        false
    }
}

2. Use StrongBox-backed keys

On Pixel and other StrongBox-equipped devices, keys are in a separate secure element — root on the application processor cannot extract them.

3. Integrity checks: Google Play Integrity API

val integrityManager = IntegrityManagerFactory.create(context)
val request = StandardIntegrityManager.StandardIntegrityTokenRequest.builder()
    .setRequestHash(requestHash)
    .build()
integrityManager.requestIntegrityToken(request)
    .addOnSuccessListener { response ->
        // Send response.token() to your backend for verification
        // Backend verifies: device integrity, app integrity, account details
    }

The Play Integrity API verdict distinguishes: MEETS_DEVICE_INTEGRITY, MEETS_BASIC_INTEGRITY, NO_INTEGRITY.

4. SafetyNet Attestation (deprecated — prefer Play Integrity)

SafetyNet was deprecated in June 2023. Existing integrations continue to work until further notice, but migrate to Play Integrity.

Honest interview answer on the limits

"No mobile app can be fully secured against a rooted device with physical access and unlimited time — that's just the reality of running on hardware you don't control. The goal of root detection isn't to make attack impossible; it's to raise the cost. So the right layered approach is: use Keystore keys, preferably StrongBox-backed, so the key material is hardware-isolated even from a root process; use the Play Integrity API to get a server-verifiable attestation of device and app state; and do root detection to fail gracefully — warn the user and log the event server-side — rather than pretending you can stop a determined attacker."

Avoiding Hardcoded Secrets

Definition

Hardcoded secrets are API keys, tokens, passwords, or cryptographic keys embedded directly in source code, resource files, or compiled bytecode. The problem is not theoretical — Android APKs are trivially decompilable, and any string literal in your code is recoverable in minutes.

Why it's a problem

Android APKs are trivially decompilable with tools like jadx, apktool, or even online services. Any string in your code, BuildConfig, or res/values/ is recoverable from the APK in minutes — even with ProGuard/R8 obfuscation applied, because R8 renames identifiers but does not encrypt string literals.

What counts as a secret

  • API keys for third-party services (Firebase, Maps, Stripe).
  • Server-side credentials.
  • Cryptographic keys (symmetric keys, private keys).
  • Hardcoded passwords or salts that are meaningful without context.

What does NOT need protection

  • Public keys (by definition public).
  • API keys for client-side-only services designed to be public (like a public Maps embed key with domain restrictions) — though even these should be restricted on the server side.

Mitigations

Approach Use case
Backend proxyThe mobile app calls your backend, which holds the API key and proxies to the third-party service. The mobile app never sees the key.
Runtime key deliveryKey is fetched from your server at runtime (over TLS + authenticated) and stored in EncryptedSharedPreferences. Never in the APK.
Firebase Remote Config / AWS SSMKey is stored server-side and fetched at runtime.
Android KeystoreFor keys generated on-device — they never exist outside the device, so there's nothing to hardcode.
Restricted API keysSome services (Google Maps) allow domain/package/certificate restrictions on the key. Even if extracted, the key is unusable from another app or server.

ProGuard/R8 does NOT protect secrets

A common misconception is that obfuscation hides secrets. R8 renames identifiers but leaves string literals intact, so jadx will find "sk_live_abc123" in your code regardless of how thoroughly you've obfuscated everything else.

Detecting hardcoded secrets in code review

# Search for common patterns
grep -rn "api_key\|apikey\|secret\|password\|passwd\|token" app/src/ --include="*.kt" --include="*.java"

# Tools: truffleHog, gitleaks, GitHub secret scanning

Build-time injection (acceptable for non-sensitive config)

// build.gradle.kts — value comes from environment variable, not committed
android {
    buildTypes {
        release {
            buildConfigField("String", "API_BASE_URL", "\"${System.getenv("API_BASE_URL")}\"")
        }
    }
}

This is acceptable for non-secret config values (base URLs, feature flag service URLs). Still visible in the APK via BuildConfig, but not a secret per se. Never use this pattern for API keys or tokens.

Logging Sensitive Data

Definition

Android's Logcat is a system-wide, unencrypted log buffer. Any app with READ_LOGS permission — or root — can read every line in it, and crash-reporting SDKs routinely capture recent log output and ship it to their servers. That means sensitive data written to Logcat doesn't just sit on the device; it can travel off it.

The problem

Before API 19, any app could read Logcat. From API 19 onwards, only apps with READ_LOGS — a signature-level permission granted to some system apps — or root can read other apps' logs. But that still leaves three real exposure paths. First, developer devices with ADB enabled expose the entire Logcat to anyone with USB access. Second, crash reporting SDKs like Sentry and Firebase Crashlytics may capture recent Logcat output and send it to their servers. And third, some OEM apps ship with READ_LOGS, so production Logcat is not private even without root.

Rules

// NEVER LOG:
Log.d("Auth", "Token: $authToken")              // token in log
Log.d("User", "Password: $password")             // password
Log.d("Profile", "SSN: ${user.ssn}")             // PII
Log.d("Payment", "Card: ${card.number}")         // card number

// OK IN DEBUG, NEVER IN RELEASE:
if (BuildConfig.DEBUG) {
    Log.d("Network", "Response: $responseBody")  // may contain PII
}

// SAFE:
Log.d("Auth", "Token refreshed successfully")    // no token value
Log.d("Network", "Request failed with code: $code")
Log.e("Payment", "Payment failed: ${error.code}")

Using ProGuard/R8 to strip debug logs

# Strip Log.d and Log.v calls in release builds
-assumenosideeffects class android.util.Log {
    public static int d(...);
    public static int v(...);
}

Timber (logging library) pattern

// Plant debug tree only in debug builds
if (BuildConfig.DEBUG) {
    Timber.plant(Timber.DebugTree())
} else {
    Timber.plant(CrashReportingTree()) // custom tree that filters PII
}

class CrashReportingTree : Timber.Tree() {
    override fun log(priority: Int, tag: String?, message: String, t: Throwable?) {
        if (priority < Log.WARN) return // only warn+ in production
        // Scrub before sending to crash reporter
        val scrubbed = message.replace(TOKEN_REGEX, "[TOKEN]")
        Sentry.captureMessage(scrubbed)
    }
}

Crash reporter configuration

Configure your crash reporting SDK to exclude certain fields:

// Sentry example — scrub sensitive breadcrumbs
SentryAndroid.init(context) { options ->
    options.beforeBreadcrumb = BeforeBreadcrumbCallback { breadcrumb, _ ->
        if (breadcrumb.category == "auth") null // drop auth breadcrumbs
        else breadcrumb
    }
    options.beforeSend = BeforeSendCallback { event, _ ->
        // Strip request bodies from network events
        event.request?.data = null
        event
    }
}

Failure modes

  • Debug logging left in release builds (ProGuard didn't strip it, or ProGuard not configured).
  • Exception messages containing sensitive data being sent to crash reporters.
  • Using toString() on data classes that include token fields in the generated output.
// Data class: toString() includes all fields — be careful
data class UserSession(
    val userId: String,
    val token: String // this will appear in any Log.d("Session", session.toString())
)

// Safer: override toString to exclude sensitive fields
data class UserSession(
    val userId: String,
    @Transient val token: String
) {
    override fun toString() = "UserSession(userId=$userId, token=[REDACTED])"
}

Interview Q&A Master List

13.1 Security Basics

Q: How do you secure an exported component?

"There are three layers. First, don't export unless you genuinely have to — set android:exported='false' or remove intent-filters from anything that's internal to your app. Second, if it must be exported, require a signature-level custom permission so only apps signed with the same key as yours can call it. And third, treat every piece of Intent data that arrives as untrusted input: whitelist expected actions, sanitize extras, and reject anything with an unexpected shape. I also avoid doing any privileged work in response to externally-triggered Intents without first validating the caller's identity."

Q: What is intent spoofing?

"Intent spoofing is when a malicious app sends a crafted Intent to one of your exported components, either impersonating a legitimate caller or injecting malicious data to trigger behaviour you didn't intend. The root of the problem is that Android Intents carry no built-in caller authentication — any app on the device can send any Intent to any exported component. So the defence has three parts: don't export components unnecessarily, require signature-level permissions on components that must be exported, and treat every Intent extra as untrusted user input regardless of what action string it declares."

Q: Why avoid exposing file paths directly (file:// URIs)?

"There are two reasons. First, from API 24 onwards, passing a file:// URI to another app via an Intent throws FileUriExposedException — it literally crashes the app. And second, more fundamentally, a file:// URI reveals the absolute filesystem path to a private file, so any app that sees that Intent now knows where your app stores its data. FileProvider solves both problems at once: it generates a content:// URI that the OS routes through your ContentProvider, granting the receiving app temporary read access without ever exposing the underlying path. The other app calls ContentResolver.openInputStream() and gets the bytes — it never learns where those bytes came from on disk."

Q: How do you validate deep links?

"There are four steps. First, use App Links — HTTPS with android:autoVerify='true' and an assetlinks.json file — so only your app handles your domain's URLs. Custom schemes are a problem because any app can register the same scheme and intercept your links. Second, even with App Links in place, validate the scheme and host in code before you act on the link, because App Links can be bypassed on some older devices. Third, whitelist known paths and reject anything unexpected. And fourth, sanitize and range-check all query parameters as untrusted input. For OAuth deep links there's an extra step: always validate the state parameter against the one you generated before launching the flow, or you're open to CSRF."

Q: What is PendingIntent mutability and why does it matter?

"FLAG_IMMUTABLE prevents the recipient of a PendingIntent from modifying the wrapped Intent's action, component, or extras. The vulnerability with a mutable PendingIntent is that if you leave the action or component unspecified, the receiver can fill in whatever it wants — and it executes under your app's identity and your app's permissions, not theirs. That's a privilege escalation. Since API 31, omitting both flags entirely throws an IllegalArgumentException, so you have to be explicit. My rule is to default to FLAG_IMMUTABLE everywhere, and only reach for FLAG_MUTABLE in the specific cases where a system framework genuinely needs to fill in fields — for example, inline reply notifications."

13.2 Data Security

Q: Where do you store auth tokens?

"I store auth tokens in EncryptedSharedPreferences, which uses AES-256-GCM for values and AES-256-SIV for keys, with the master key living in the Android Keystore. On supported hardware that key never leaves the secure element. For extremely sensitive operations — like a private signing key — I go one level lower and use the Keystore directly: only ciphertext and the IV go to disk, and the raw key material never exists outside the Keystore. The things I never do are plain SharedPreferences — its XML is exposed in ADB backups on pre-Marshmallow devices — external storage, or any form of hardcoded value."

Q: Can you fully secure secrets in a mobile app?

"No, not fully. A mobile app runs on hardware you don't control, in the user's hands. With physical access and a rooted device, an attacker with enough time can extract almost anything from user space — they can read process memory, bypass TLS pinning with Frida, and on devices without StrongBox they can potentially access Keystore key material too. So the goal is not to make attack impossible; it's to raise the cost high enough that it's not worth it. You do that by using hardware-backed Keystore keys — preferably StrongBox-backed — so the key material is isolated even from root, by never hardcoding secrets anywhere in the APK, by using the Play Integrity API to detect compromised device states at the server level, and by architecting your backend so that a compromised client has a limited blast radius: short-lived tokens, scope-limited keys, and server-side rate limiting."

Q: What is Android Keystore and how does it work?

"Android Keystore is a system service that stores cryptographic keys in hardware-isolated storage — ideally a TEE, which is a Trusted Execution Environment within the main SoC, or a StrongBox, which is a dedicated secure element on a separate chip. Keys are bound to the app's UID, so another app can't use yours. The defining property is that key material never leaves the secure hardware in plaintext — every cryptographic operation happens inside the Keystore service, not in your process. From your code's perspective you just reference a key by alias and call standard JCE APIs like KeyGenerator and Cipher; the implementation quietly routes those operations to the hardware. You can optionally bind a key to biometric authentication, a time-based validity window, or a user presence check. Keys survive app updates but are wiped on uninstall, factory reset, and — if you set setInvalidatedByBiometricEnrollment(true) — whenever new biometrics are enrolled."

Q: When should you use certificate pinning?

"I use it in high-value apps where a rogue or compromised CA is a realistic threat — financial, health, or any app handling highly sensitive data. The conditions I need before pinning are: I control the API endpoints so I know the certificate in advance, the API doesn't rotate certificates frequently, and I can guarantee app updates before the pin expiry date. The operational discipline around it is non-negotiable. There are three rules. First, always include a backup pin for the next certificate's SPKI hash, so you can rotate without breaking users. Second, set an expiration date in Network Security Config so old app versions that can't be updated fail open — back to standard CA validation — rather than being permanently broken. Third, pin the public key hash, the SPKI, rather than the full certificate, so key reuse across renewals doesn't invalidate your pin. The cases where I wouldn't pin: APIs behind a CDN with frequent certificate rotation, or any situation where I can't control when the certificate changes."

Q: What is the difference between EncryptedSharedPreferences and using the Keystore directly?

"EncryptedSharedPreferences is a high-level drop-in replacement for SharedPreferences. It uses the Keystore to hold a master key, which in turn wraps a data encryption key that's stored alongside the prefs file. From your code's perspective, all the cipher, IV, and key management is abstracted away — you just call putString and getString like normal. The ciphertext ends up in an XML file on internal storage, protected by UID isolation plus AES-256 encryption. Using the Keystore directly means generating your own AES key, calling Cipher.init() yourself, managing the IV, and storing the ciphertext wherever you choose. The trade-off is that you get much more control: you can require biometric authentication per encryption operation, request StrongBox backing, or use an asymmetric key pair — but you're writing substantially more boilerplate. For most token storage scenarios, EncryptedSharedPreferences is the right level of abstraction. The Keystore-directly approach makes sense when you need per-operation biometric binding or you're handling something unusually sensitive."
