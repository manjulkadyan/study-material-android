15.1 Android App Architecture Design

Senior and staff design interviews are not about memorizing a pattern. They are about showing that you can drive decisions across the full stack of a feature — from network protocol to UI rendering, from data persistence to security model, from rollout strategy to monitoring.

Use this framework for every design:

Architecture → Modules → State Management → Data Flow → Offline Strategy →
Error Handling → Threading → Caching → Security → Performance → Testing →
Monitoring → Rollout

Worked Designs

Chat App

Scenario: Design the Android client for a consumer chat application (think WhatsApp/Signal scale). Real-time messaging, media sharing, read receipts, message status, group chats.

Architecture

MVVM with a single-direction data flow per conversation screen. Each open conversation has its own ConversationViewModel. A global ChatSessionManager (singleton, process-scoped) owns the WebSocket lifecycle. Repository layer mediates between the remote (WebSocket/REST) and local (Room) sources.

UI (Compose ConversationScreen)
   ↑ UiState
   ViewModel (ConversationViewModel)
   ↑ Flow<List<Message>>
   Repository (MessageRepository)
   ↑                   ↑
Room (MessageDao)   WebSocket / REST

Modules

:app                          — entry, DI wiring
:feature:chat                 — conversation list + open chat screens
:feature:media                — media picker, upload, preview
:data:chat                    — MessageRepository, ConversationRepository
:data:network                 — WebSocketClient, ChatApiService
:data:db                      — Room DB, DAOs
:domain:chat                  — Message, Conversation domain models, use cases
:core:crypto                  — end-to-end encryption utilities
:core:push                    — FCM token registration, notification routing
:core:ui                      — shared Compose components (Bubble, Avatar, etc.)

State Management

ConversationViewModel exposes a single StateFlow<ConversationUiState>. That state includes:

  • messages: List<MessageUiModel> (paginated, sorted by timestamp)
  • typingIndicators: Set<UserId>
  • sendStatus: SendStatus (idle / sending / failed)
  • scrollToPosition: Int?

Side-effects (scroll triggers, attachment picker opening) use SharedFlow<ConversationEvent>.

Data Flow

  1. App opens → ChatSessionManager.connect() opens a persistent WebSocket.
  2. Incoming frame decoded → MessageRepository.handleIncoming(frame) → persisted to Room → Room

emits new Flow<List<Message>> → ViewModel picks up → UI re-renders.

  1. User sends message → ViewModel calls SendMessageUseCase → message inserted into Room with

status=PENDING → Room emission updates UI immediately (optimistic) → background coroutine sends over WebSocket → on ACK update status=SENT → on server push update status=DELIVERED / status=READ.

  1. Pagination: ViewModel uses Pager + PagingSource backed by `MessageDao.getMessages(threadId,

limit, offset)`. Load older messages on scroll-to-top.

Offline Strategy

  • Messages typed while offline are inserted into Room with status=PENDING.
  • A WorkManager PeriodicWorkRequest (PendingMessageSyncWorker) processes the queue when

connectivity is restored.

  • Conversation list and last messages are always served from Room; staleness is acceptable

because the WebSocket reconciles on reconnect.

  • Media uploads are queued via WorkManager with NetworkType.CONNECTED constraint.

Error Handling

  • WebSocket disconnection: exponential back-off reconnect (1s, 2s, 4s, 8s, cap at 60s).

ChatSessionManager emits ConnectionState (CONNECTED / RECONNECTING / OFFLINE) into a StateFlow; the UI shows a subtle banner.

  • Send failure: the PENDING message stays in the local DB. UI shows a retry icon. User can

tap to retry or swipe to cancel.

  • Media upload failure: WorkManager retries up to 3 times; on final failure emit an event toast.
  • Decryption failure: show a placeholder "This message could not be decrypted" rather than

crashing.

Threading

  • WebSocket callbacks arrive on an IO dispatcher thread. Parsing and DB writes are on

Dispatchers.IO. ViewModel collects on Dispatchers.Main.

  • Media compression is on Dispatchers.Default (CPU-bound).
  • Never block the main thread; use launch(Dispatchers.IO) for all persistence.
  • Use structured concurrency: ConversationViewModel creates its own `CoroutineScope(

SupervisorJob() + Dispatchers.Main) cancelled in onCleared()`.

Caching

  • Room is the single source of truth. No in-memory cache for messages — paging handles this.
  • Avatar/profile images: Coil's disk cache (LRU, 50 MB limit). HTTP Cache-Control headers

drive eviction. Coil uses an in-memory LRU for recently seen avatars.

  • Attachments (images, videos): cached on disk under getCacheDir()/attachments/, max 200 MB

with LRU eviction managed by a custom AttachmentCacheManager.

Security

  • End-to-end encryption: Signal Protocol (libsignal-client). Keys stored in Android Keystore.
  • Message DB encrypted via SQLCipher; the SQLCipher key is stored in Keystore and only accessible

with user auth (biometric/pin).

  • TLS pinning on the WebSocket and REST endpoints.
  • No message content in notifications on locked screen (show "New message" only); configurable

per user setting.

  • Media sent to S3 via pre-signed URLs; the URL is only valid for 24 hours.
  • Prevent screenshots in sensitive screens using FLAG_SECURE.

Performance

  • LazyColumn for message list; use key { message.id } for stable recomposition.
  • Avatar Composables use remember { painter } to avoid re-loading on every recompose.
  • Diff in PagingData uses DiffUtil keyed on message ID; only changed items re-render.
  • Use stateIn(SharingStarted.WhileSubscribed(5000)) to avoid re-fetching from DB during

screen rotation.

  • Incoming WebSocket frames are batched (100ms debounce) before triggering DB writes to avoid

thrashing.

Testing

  • MessageRepository unit tested with FakeMessageDao (in-memory) and FakeWebSocketClient.
  • ConversationViewModel tested with MainCoroutineTestRule and fake repository.
  • SendMessageUseCase unit tested independently with mocked repository.
  • UI tests with Espresso/Compose test: verify message appears in list after sendMessage(),

verify retry button appears on simulated network failure.

  • WorkManager tested with TestWorkerBuilder.

Monitoring

  • Sentry: capture ConversationCrash events; tag with conversationId (not participant names).
  • Custom metric: message_send_latency_ms from user tap to status=SENT; tracked via DataDog.
  • connection_drop_rate = drops per session, alerted if > 2%.
  • Media upload success rate (target > 99%).
  • pending_message_count gauge: rising queue means sync worker is broken.

Rollout

  1. Ship behind AB flag chat_v2_enabled.
  2. 1% → 5% → 20% → 100% rollout over two weeks.
  3. Monitor crash-free rate, message delivery rate, latency p95.
  4. Kill-switch: flag off returns users to previous chat implementation.

Offline-First Feed

Scenario: Design a social/news feed that works fully offline. Think Twitter timeline, Reddit feed, or an internal news app with periodic content.

Architecture

Repository pattern with Room as the single source of truth. The UI always reads from local DB. A FeedSyncManager (tied to WorkManager) is the only component that writes from network to DB. This is a strict local-first pattern.

UI (Compose FeedScreen)
   ↑ PagingData<FeedItemUiModel>
   FeedViewModel
   ↑ PagingSource (Room)
   FeedRepository
          ↑ write only
   FeedSyncManager (WorkManager PeriodicWork)
          ↑
   FeedApiService (Retrofit)

Modules

:feature:feed          — FeedScreen, FeedViewModel
:data:feed             — FeedRepository, FeedSyncManager
:data:db               — FeedItemEntity, FeedDao
:data:network          — FeedApiService, NetworkMonitor
:domain:feed           — FeedItem domain model, GetFeedUseCase
:core:sync             — BaseSyncWorker, SyncResult, retry policy

State Management

ViewModel exposes:

  • PagingData<FeedItemUiModel> via Pager backed by FeedDao.getFeedItems().
  • feedStatus: StateFlow<FeedStatus> (SYNCED / SYNCING / STALE / ERROR) — this comes from a

metadata table feed_sync_meta (last sync timestamp, sync result).

  • Pull-to-refresh triggers FeedRepository.requestSync() which starts an expedited WorkManager

request.

Data Flow

Read path: FeedDao → PagingSource → PagingData → ViewModel → Compose LazyColumn. Write path: FeedSyncWorker.doWork() calls FeedApiService.getFeed(cursor), maps to entities, calls FeedDao.upsertAll(entities), updates feed_sync_meta. The DB write wakes up the PagingSource observer automatically.

Offline Strategy

  • Feed is always readable — Room has all previously fetched items.
  • NetworkMonitor (wraps ConnectivityManager.NetworkCallback) emits isOnline: StateFlow<Bool>.
  • When offline: show a banner "Showing cached content from X minutes ago". Use

feed_sync_meta.lastSyncTimestamp for the time.

  • WorkManager constraint NetworkType.CONNECTED — sync only happens with connectivity.
  • Pagination cursor stored in feed_sync_meta so sync resumes from last known position after

re-connect.

  • Read articles are stored; user can explicitly save articles for permanent offline.

Error Handling

  • Network error during sync: WorkManager returns Result.retry() with exponential back-off.

After 3 retries, Result.failure() updates feed_sync_meta.lastSyncStatus = ERROR. UI shows "Could not refresh" with a retry button.

  • Partial sync: if the API returns 50 items but fails mid-write, use a DB transaction

(@Transaction) to ensure atomicity — all or nothing.

  • Parse error for a single item: skip that item, log to Sentry, continue.

Threading

  • All DB reads via Dispatchers.IO (Room automatically uses IO dispatcher for suspending

functions).

  • WorkManager doWork() is called on a background thread pool; no extra dispatchers needed.
  • ViewModel collects PagingData on Dispatchers.Main.

Caching

  • Room IS the cache. No additional in-memory layer.
  • Image caching: Coil with disk cache; staleWhileRevalidate header support.
  • Cache eviction: a nightly CleanupWorker deletes FeedItemEntity rows older than 7 days,

except those marked saved = true.

  • Article body (HTML/markdown): stored in a separate article_body table with its own 24-hour

TTL.

Security

  • API auth via bearer token (stored in EncryptedSharedPreferences).
  • HTTPS-only; certificate pinning in OkHttp interceptor.
  • Saved articles: no PII in local DB (user IDs stored as hashed tokens).

Performance

  • PagingSource with pageSize = 20, prefetchDistance = 5.
  • Pager cached in ViewModel with cachedIn(viewModelScope) so rotation does not re-fetch.
  • Images: use AsyncImage with crossfade, avoid loading full-res in feed (request thumbnail

variant from CDN with ?w=400).

  • DB indices on FeedItemEntity: index on (timestamp DESC) for the main sort, index on

(saved, timestamp) for saved filter.

Testing

  • FeedSyncWorker tested with TestWorkerBuilder and a FakeFeedApiService.
  • FeedRepository tested with an in-memory Room DB.
  • FeedViewModel tested with TestCoroutineDispatcher and fake repository.
  • UI: screenshot tests of feed in CACHED state vs SYNCING state.

Monitoring

  • feed_sync_success_rate per WorkManager run.
  • feed_load_time_ms from screen open to first item visible.
  • stale_content_shown_rate — how often users see cached content older than 1 hour.

Rollout

  • Feature flag offline_first_feed_enabled.
  • Shadow mode: new sync path runs alongside old network-then-cache path; compare outputs.
  • Gradual rollout; watch stale_content_shown_rate and crash rate.

Video Streaming App

Scenario: Design an Android client for a video streaming service (Netflix/YouTube scale). Browse catalog, search, play video, download for offline.

Architecture

Feature-modular MVVM. ExoPlayer is the media engine, wrapped in a VideoPlayerController singleton. Download management via DownloadManager (ExoPlayer's download module) backed by WorkManager.

Modules

:feature:home          — catalog browse
:feature:player        — playback screen + mini-player
:feature:downloads     — download list, download management
:feature:search        — search screen
:data:catalog          — CatalogRepository (GraphQL + Room)
:data:playback         — PlaybackSessionRepository, DRM license fetching
:data:download         — DownloadRepository (ExoPlayer DownloadManager + Room)
:core:player           — VideoPlayerController, ExoPlayer factory, DRM
:core:analytics        — playback telemetry (QoE events)

State Management

PlayerViewModel exposes:

  • playbackState: StateFlow<PlaybackState> (IDLE / BUFFERING / PLAYING / PAUSED / ENDED / ERROR)
  • currentPosition: StateFlow<Long> (updated every 500ms via ExoPlayer.addListener)
  • videoMetadata: StateFlow<VideoMetadata>
  • qualityLevel: StateFlow<Quality> (for adaptive bitrate display)

Data Flow

  1. User taps video → PlayerViewModel.loadVideo(videoId) → PlaybackSessionRepository

fetches manifest URL + DRM license URL → construct MediaItem with DRM config → hand to ExoPlayer.

  1. ExoPlayer handles HLS/DASH ABR internally.
  2. Player listener events → StateFlow updates → UI reacts.
  3. Resume position: on pause/stop, persist (videoId, position) to Room → on next open, seek

to that position.

Offline Strategy

  • ExoPlayer DownloadManager with SegmentDownloader for HLS/DASH.
  • Download request added via DownloadService (foreground service required by ExoPlayer).
  • DRM offline license fetched and stored alongside segments.
  • DownloadRepository exposes Flow<List<DownloadState>> backed by ExoPlayer's DownloadIndex

(SQLite-backed).

  • Expired downloads: check license expiry on app open; prompt user to re-download if needed.

Error Handling

  • Playback error → PlaybackException from ExoPlayer → map to user-friendly error + retry button.
  • DRM license fetch failure: surface "Content not available in your region / retry".
  • Download failure: WorkManager retry; notify user with NotificationCompat progress notification.
  • Network interruption mid-playback: ExoPlayer buffers 30s; auto-resumes when connectivity

returns; show "Reconnecting..." indicator after 5s buffer exhausted.

Threading

  • ExoPlayer must run on main thread. All ExoPlayer calls from Dispatchers.Main.
  • Manifest/license fetches: OkHttp on IO dispatcher.
  • Download: ExoPlayer DownloadService runs in its own process with foreground service

notification.

Caching

  • SimpleCache (ExoPlayer) for in-memory HLS segment cache (100 MB default).
  • LeastRecentlyUsedCacheEvictor with configurable max size.
  • Catalog metadata: Room with 24-hour TTL via catalog_meta.fetchedAt column.
  • Thumbnails: Coil disk cache.

Security

  • Widevine DRM (L1 on supported hardware, L3 fallback).
  • FLAG_SECURE on player Activity to prevent screen recording.
  • Offline DRM licenses: keystore-backed encrypted storage via ExoPlayer's DefaultDrmSessionManager.
  • API tokens in EncryptedSharedPreferences.
  • Certificate pinning for CDN and license server endpoints.

Performance

  • Thumbnail loading: use low-resolution variants from CDN; full-res only on detail screen.
  • Pre-fetch next episode: when 80% through current episode, start buffering next episode's first

30s in background (ConcatenatingMediaSource).

  • ABR: ExoPlayer AdaptiveTrackSelection with custom DefaultBandwidthMeter calibrated to

streaming profile.

  • Reduce startup latency: pre-warm ExoPlayer instance on app cold start.

Testing

  • VideoPlayerController unit tested with FakeExoPlayer (ExoPlayer test utilities).
  • PlaybackSessionRepository mocked with MockK; test DRM license fetch path.
  • Integration test: mock API server + ExoPlayer playing test HLS stream.
  • Manual QA checklist: seek behavior, background playback, download flow, resume after kill.

Monitoring

  • QoE metrics: startup time, buffering ratio, average bitrate, error rate per stream.
  • video_start_failure_rate alerted if > 0.5%.
  • rebuffering_ratio alerted if > 2%.
  • Download success rate (target > 98%).
  • Crash-free rate on Player Activity (target > 99.9%).

Rollout

  • ExoPlayer version upgrades: shadow A/B, compare QoE metrics before full rollout.
  • New DRM configuration: 1% → 5% → 20% with crash rate monitoring at each step.

Payments Flow

Scenario: Design a payments flow in an Android app — add card, select payment method, confirm purchase. Security and reliability are paramount.

Architecture

A dedicated PaymentsActivity hosts a single-flow NavHost. Each step is a Compose screen. PaymentViewModel is scoped to the Activity (not individual screens) to maintain state across steps. All payment data handling is strictly in the data:payments module behind an interface.

PaymentsActivity (NavHost)
  ├── SelectPaymentMethodScreen
  ├── AddCardScreen (delegates to PCI-compliant SDK)
  ├── ConfirmPurchaseScreen
  └── PaymentResultScreen

PaymentViewModel (Activity-scoped)
   ↑ PaymentUiState
   PaymentRepository
   ↑
   PaymentApiService (Retrofit)
   StripeSDK / BraintreeSDK (PCI-compliant card tokenization)

Modules

:feature:payments       — UI screens, PaymentViewModel, navigation
:data:payments          — PaymentRepository, PaymentApiService
:domain:payments        — PaymentMethod, Order, PaymentResult domain models
:core:security          — BiometricHelper, EncryptedPreferences

State Management

PaymentUiState is a sealed class:

  • SelectingMethod(methods: List<PaymentMethod>)
  • AddingCard
  • Confirming(orderSummary: OrderSummary, selectedMethod: PaymentMethod)
  • Processing
  • Success(receipt: Receipt)
  • Failure(error: PaymentError)

One-way flow: state emitted from ViewModel → UI renders. User action → ViewModel event → new state. No state stored in individual screen Composables.

Data Flow

  1. Screen opens → PaymentViewModel.loadPaymentMethods() → REST call → StateFlow updated.
  2. User selects saved card → proceed to Confirm step.
  3. User adds new card → Stripe SDK tokenizes (card number never leaves the SDK) → token returned

to app → sent to backend for association with account.

  1. User taps "Pay" → PaymentViewModel.confirmPayment(orderId, methodToken) → REST call →

idempotency key sent with request → result updates state.

Offline Strategy

Payments must NOT proceed offline. If NetworkMonitor.isOnline == false:

  • Disable "Pay" button.
  • Show "No internet connection — payment not processed."
  • Queue no payment attempts offline (risk of double-charge).

Error Handling

  • Network timeout: show "Something went wrong" + retry. Do NOT assume payment succeeded.
  • Idempotency keys: every payment request includes a UUID generated client-side and stored in

Room. If the same request is retried, the same key is sent — backend deduplicates.

  • Card declined: show specific error from backend (insufficient funds, expired card, etc.).
  • 3DS challenge: launch a Chrome Custom Tab for the challenge URL; handle redirect back to app

via deep link.

  • Crash during payment: on next app open, query backend with the idempotency key to determine

payment status. Never assume a crash means failure.

Threading

  • All payment API calls on Dispatchers.IO.
  • Stripe SDK operations on the thread Stripe requires (usually main thread for their UI components).
  • Never make payment calls on main thread.

Caching

  • Payment methods list: cached in Room for 15 minutes. Show stale data with "Refresh" button.
  • Never cache raw card data.
  • Order summary: not cached — always fresh from backend to prevent stale price display.

Security

  • PCI DSS: card data never touches app servers — Stripe/Braintree SDK handles tokenization.
  • Biometric confirmation before payment: BiometricPrompt required for purchases > threshold.
  • FLAG_SECURE on payment Activity — no screenshots, no recents thumbnail.
  • No card numbers in logs, analytics, crash reports.
  • Token storage: payment method tokens in EncryptedSharedPreferences.
  • Jailbreak/root detection: warn user, optionally block (policy decision).
  • Certificate pinning on payment API endpoints.
  • Tamper detection: use SafetyNet/Play Integrity API before confirming payment.

Performance

  • Payment method list pre-fetched when user enters checkout funnel (not just when they tap the

payment button).

  • Optimistic UI only for non-payment steps; never for the actual charge (wait for server ACK).

Testing

  • PaymentRepository tested with mock Retrofit + idempotency key verification.
  • PaymentViewModel state machine tested exhaustively: every transition.
  • Stripe SDK integration: use Stripe test mode with test card numbers.
  • Test double-submit prevention by rapid-tapping the Pay button.
  • Test network drop at the exact moment of payment confirmation.

Monitoring

  • Payment success rate (target > 99.5%).
  • payment_start_to_success_latency_ms p95.
  • Idempotency key collision rate (should be ~0).
  • 3DS challenge completion rate.
  • Alert on any payment error spike (> 1% error rate triggers page).

Rollout

  • Never ship payment changes without QA sign-off on test mode + staging environment.
  • Shadow mode: run new payment path alongside old for 24 hours, compare success rates.
  • Feature flag with instant kill-switch.
  • Gradual rollout: 1% for 48 hours minimum, watching payment error rate.

Ride Tracking App

Scenario: Design the Android client for a ride-hailing app. Real-time driver location, ETA, fare calculation, trip state machine.

Architecture

Real-Time Collaborative App

Scenario: Design a real-time collaborative editing app (Google Docs/Figma style). Multiple users editing a shared document simultaneously on Android.

Architecture

MVVM + event sourcing. The document is represented as a sequence of operations (OT or CRDT). Local operations are applied immediately (optimistic), sent to server, and server broadcasts merged operations to all clients.

Modules

:feature:editor         — EditorScreen, EditorViewModel, Compose rich text editor
:data:document          — DocumentRepository, OperationQueue, WebSocket channel
:domain:collab          — Operation, Document, ConflictResolver (OT/CRDT logic)
:core:realtime          — WebSocketClient, ReconnectManager
:core:presence          — CollaboratorPresence (cursors, selection state)

State Management

EditorViewModel exposes:

  • documentState: StateFlow<DocumentContent> — the current rendered content.
  • collaborators: StateFlow<List<CollaboratorPresence>> — other users' cursors.
  • syncState: StateFlow<SyncState> (SYNCED / PENDING / CONFLICTED / OFFLINE).

Data Flow

  1. User makes edit → LocalOperation created → applied to local document immediately (optimistic

→ documentState updates) → enqueued in OperationQueue.

  1. OperationQueue.flush() sends operations over WebSocket.
  2. Server applies OT/CRDT, broadcasts merged operation to all clients.
  3. Remote operation received → ConflictResolver.transform(localPending, remoteOp) → apply to

local document → update state.

  1. On full sync (reconnect): fetch full document snapshot from REST; replay pending local ops on top.

Offline Strategy

  • Continue editing offline; operations buffered in OperationQueue (Room-backed for persistence

across process death).

  • On reconnect: send buffered operations in order with version vector for server-side OT.
  • Show "Editing offline" badge; other collaborators' changes not visible until reconnect.

Error Handling

  • Conflict resolution failure: fall back to "last write wins" at field granularity with a toast

"Some of your changes may have been overridden."

  • Persistent sync failure: prompt user to save a local copy and try again.
  • WebSocket disconnect: foreground service keeps connection alive while editing; app background

pauses collaboration session after 30s.

Threading

  • WebSocket on IO dispatcher.
  • OT/CRDT conflict resolution on Dispatchers.Default (CPU-bound).
  • UI updates on Dispatchers.Main.
  • Operations are sequential (use Channel with UNLIMITED capacity to serialize them).

Caching

  • Document snapshots: Room. Fetch on first open; subsequent opens use local + delta sync.
  • Collaborator presence: in-memory only (ephemeral).

Security

  • Document access control enforced server-side; client trusts server's rejection.
  • Operations signed with session token to prevent forgery.
  • End-to-end encryption option for private documents (keys exchanged out-of-band).

Performance

  • Rich text rendering: avoid re-rendering unchanged paragraphs. Use Compose key {} at paragraph

level.

  • Presence cursors: debounce cursor position sends (50ms) to reduce WebSocket traffic.
  • Operation batch: batch up to 10 ops or 100ms into one WebSocket frame.

Testing

  • ConflictResolver unit tested extensively with known OT scenarios (concurrent inserts, deletes,

reorders).

  • OperationQueue tested for correct ordering and replay behavior.
  • Integration test: two DocumentRepository instances on a fake WebSocket server, verify eventual

consistency.

Monitoring

  • Operation round-trip time (client send → server broadcast → client receive).
  • Conflict resolution rate.
  • Sync failure rate.
  • Presence latency (cursor position latency).

Rollout

  • Beta with controlled set of collaborative documents.
  • Monitor conflict rate; high conflict rate may indicate OT implementation bugs.

SDK Used by Many Apps

Scenario: You are designing an Android SDK that will be embedded in dozens of third-party apps. The SDK provides analytics, identity, or feature-flag capabilities.

Architecture

The SDK is a library module (AAR). It must have zero opinion about the host app's architecture. No forced DI framework. Minimal transitive dependencies. Exposes a simple public API surface.

Design Principles

  1. No forced dependencies: Do not pull in Hilt, Dagger, or large libraries. Use manual DI

internally. If using OkHttp, shade it (jarjar) or make it optional.

  1. Single entry point: MySDK.init(context, config) — one call to start.
  2. Thread-safe: All public methods safe to call from any thread. Internally uses a

dedicated CoroutineScope(SupervisorJob() + Dispatchers.IO) that the host can optionally replace.

  1. No crash propagation: Catch all exceptions internally; never let SDK bugs crash the host app.

Log internally, report to own backend silently.

  1. Minimal permissions: Only request permissions the SDK absolutely needs; document them.
  2. ProGuard-friendly: Ship a proguard-rules.pro file. Annotate public API with @Keep.
  3. Small binary size: Every KB counts when embedding in a host app. Use R8 full-mode.

Modules (internal)

sdk-api/          — public interfaces + data classes (no implementation)
sdk-core/         — SdkCore, initialization, config
sdk-network/      — SdkHttpClient (shaded OkHttp or HttpURLConnection)
sdk-storage/      — SdkPreferences, SdkDatabase (scoped, named with SDK prefix)
sdk-analytics/    — event batching, flush scheduler

Public API Surface

// Keep it minimal. Every method added is API debt.
object MySDK {
    fun init(context: Context, apiKey: String, config: SdkConfig = SdkConfig())
    fun logEvent(name: String, properties: Map<String, Any> = emptyMap())
    fun identify(userId: String)
    fun reset()
    fun setLogLevel(level: SdkLogLevel) // debug only
}

State Management

SDK maintains internal state in a thread-safe AtomicReference<SdkState>. Public state is exposed via a simple callback interface (not Kotlin Flow — host apps may be Java or non-coroutine).

Data Flow

  1. Host calls logEvent() → event queued in in-memory CircularBuffer.
  2. Flush triggered by: buffer full (100 events), time interval (30s), app going to background.
  3. Flush sends batched events to SDK backend via HTTP POST with retry.
  4. On failure: events persisted to SdkDatabase (Room, SDK-namespaced); retried next flush.

Offline Strategy

All events queued in Room until connectivity available. WorkManager optional (do not force it). SDK can use ConnectivityManager and schedule its own flush on network available via ConnectivityManager.registerNetworkCallback.

Error Handling

  • Wrap every public method in try/catch; log internally; never throw to caller.
  • If initialization fails (e.g., invalid API key), put SDK in NO-OP mode — all calls are safe

no-ops. Never crash.

  • If backend rejects events (400): drop them (don't fill up disk). If 500: retry.

Security

  • API key validated on backend; not embedded in SDK binary.
  • Event data: no PII by default; document clearly what the SDK collects.
  • Certificate pinning: opt-in only (host apps may have their own pinning; forcing SDK pinning

causes conflicts).

  • No reflection access into host app.

Performance

  • SDK startup: < 10ms in init(). No network calls in init(). Defer all I/O.
  • Event logging: < 1ms per call (just a queue append).
  • Flush on IO thread; never block the calling thread.
  • SDK memory: < 5 MB RSS overhead.
  • No StrictMode violations in init().

Testing

  • SDK tested as a standalone module (no host app in tests).
  • Unit tests for event queuing, batching, flush logic.
  • Integration tests against a mock HTTP server.
  • Compatibility test matrix: API 21–34, AGP versions, Kotlin/Java host apps.
  • Binary size test: fail build if AAR exceeds size budget.

Monitoring (SDK's own telemetry)

  • SDK health endpoint: reports SDK version, init success rate, event delivery rate.
  • SDK crash reporting: SDK-internal Sentry project (separate from host's Sentry).

Rollout

  • Semantic versioning. MAJOR version for breaking public API changes.
  • Changelog for every release.
  • Minimum 30-day deprecation notice before removing public API.
  • Ship beta releases (1.2.0-beta01) for host app partners to validate before stable release.
  • Provide a migration guide for every MAJOR version bump.

Multi-Process App

Scenario: Design an Android app that uses multiple processes — e.g., an app with a persistent background service (music player, VPN, location tracker) that must survive the main process being killed.

Architecture

Main process: UI + ViewModel + normal app logic. Service process (:remote): foreground service owning the long-running operation. Communication via AIDL (for structured IPC) or Messenger (for simple message passing). Alternatively, broadcast intents for fire-and-forget signaling.

When Multi-Process is Warranted

  • The background operation must outlive the UI process.
  • The operation uses significant memory and you want the OS to manage its lifecycle separately

(lower OOM priority for the service process).

  • You are implementing an accessibility service, input method, or VPN — which Android mandates

run in separate processes.

Modules

:app                    — UI, main process
:service                — MusicPlayerService (separate process), foreground notification
:ipc-api                — AIDL interfaces, Parcelable data classes (shared by both processes)
:core:notification      — NotificationBuilder (used by service process)

State Management

  • Service process owns the authoritative state (e.g., PlaybackState).
  • UI process subscribes to state changes via AIDL callback interface.
  • PlaybackServiceConnection in the UI process wraps ServiceConnection and exposes a

StateFlow<PlaybackState> by bridging AIDL callbacks to coroutine channels.

IPC Data Flow

UI Process                     Service Process
PlaybackControls               MusicPlayerService
   │ AIDL call (play/pause)         │
   └──────────────────────────────► │
                                    │ updates state
   ◄────────────────────────────────┘
   AIDL callback (PlaybackStateChanged)

Offline Strategy

The service process does not depend on network for playback of downloaded content. Network for streaming handled within the service process independently.

Error Handling

  • Service process crash: ServiceConnection.onServiceDisconnected() fires → UI shows

"Service disconnected, reconnecting..." → rebind with exponential back-off.

  • AIDL RemoteException: wrap all AIDL calls in try/catch. RemoteException = binder dead.

Trigger reconnect.

  • Process OOM kill of UI while service alive: service continues playing; notification controls

remain functional.

Threading

  • AIDL binder callbacks arrive on a binder thread pool (not main thread). Marshal to main thread

or appropriate dispatcher before UI updates.

  • Service process: Dispatchers.IO for all I/O, Dispatchers.Main for Service lifecycle

methods.

Caching

  • Shared data between processes: do NOT use in-memory cache (separate heap). Use:
    • ContentProvider for structured data.
    • SharedPreferences (multi-process mode is deprecated; prefer a DB-backed ContentProvider

or AIDL for live state).

  • Room with WRITE_AHEAD_LOGGING mode (WAL) is safe for multi-process read (one writer, many

readers).

Security

  • AIDL service should check caller's UID (Binder.getCallingUid()) to reject unauthorized clients.
  • Use android:process to set a custom process name; the process has the same UID as the app

(unless using sharedUserId which is deprecated).

  • Parcelable data: validate all incoming Parcelable data in the service process (treat as

untrusted if the IPC is exposed to other apps).

Performance

  • Minimize IPC frequency: batch state updates rather than calling AIDL per frame.
  • Large data (e.g., album art bitmap): do NOT pass through Binder (1 MB Binder transaction limit).

Pass a URI; UI process loads separately.

  • Service process memory: profile separately; it has its own heap.

Testing

  • AIDL interfaces tested with a mock binder in unit tests.
  • Integration: instrumented test that binds to the service, sends commands, verifies state

callbacks.

  • Simulate UI process death while service is running; verify graceful recovery.

Monitoring

  • Binder transaction failure rate.
  • Service crash rate (separate from UI crash rate).
  • RemoteException frequency.
  • Service foreground notification persistence (OEM-specific issues).

Rollout

  • Foreground service behavior varies dramatically by OEM (Samsung, Xiaomi, Huawei kill services

aggressively). Test on top 10 OEM device configurations before release.

  • Gradual rollout; monitor service crash rate per device brand.

Interview Angles — Architecture

"Design a scalable Android app architecture"

"I'd anchor the whole thing on eight principles. First, feature modules with clear ownership boundaries — each team owns its module and you enforce that with Dependency Guard. Second, unidirectional data flow with MVVM or MVI, so the UI is purely a function of state and there are no hidden side-channel updates. Third, the Repository pattern as the single gatekeeper between data sources and business logic — the ViewModel never talks directly to the network or the database. Fourth, define contracts as interfaces between layers and depend on abstractions, not concretions, so you can swap implementations and test in isolation. Fifth, Compose with StateFlow for the UI layer — reactive and lifecycle-safe. Sixth, WorkManager for any background work that must complete reliably, even if the process is killed. Seventh, Baseline Profiles measured with Macrobenchmark so performance is a tracked metric, not a guess. And eighth, monitoring from day one: crash-free session rate, ANR rate, and the business metrics that actually matter for your feature."

"How would you migrate legacy MVP to MVVM/Compose?"

"The approach is incremental, feature by feature — never rewrite everything at once. There are six steps. First, identify a small, well-tested screen as the pilot so you have a contained blast radius. Second, add a ViewModel alongside the existing Presenter and move the state there, keeping the Presenter delegating to the ViewModel temporarily so nothing breaks. Third, replace the Fragment's XML with a Compose screen inside an AndroidViewBinding stub, then remove the stub once it's stable. Fourth, retire the Presenter once the screen is fully ViewModel-driven — at that point it's dead code. Fifth, measure code coverage, crash rate, and rendering frame times before and after per screen so you can prove the migration is paying off. And sixth, get team buy-in early with a concrete before/after comparison on the pilot screen — once they see the difference, the rest of the migration is much easier to drive."

"How would you introduce modularization gradually?"

"I'd do it in six steps, ordered by risk and impact. First, extract the :core modules — networking, database, and UI tokens — because they have no upward dependencies and immediately unlock parallel builds for everything that depends on them. Second, start writing all new features as :feature:X modules from day one; no rework of existing code yet. Third, introduce Dependency Guard and module ownership rules so the new model is enforced automatically, not just by convention. Fourth, extract existing features one at a time, starting with the most isolated ones that touch the fewest shared files. Fifth, be deliberate about api versus implementation dependencies to prevent transitive leakage from bleeding your module boundaries. And sixth, measure build time at every step with Gradle build scans — if a module extraction doesn't move the needle on compile scope, question whether it was worth the overhead."

"How do you handle offline mode?"

"My framework has five pieces. First, Room as the single source of truth — the UI always reads from the local database, never directly from the network. Second, the Repository decides whether to serve local or remote data based on a freshness policy, so that decision is centralized and not scattered across the codebase. Third, a NetworkMonitor wrapping ConnectivityManager that exposes an isOnline: StateFlow<Boolean> in :core:network, so any component can react to connectivity changes. Fourth, WorkManager for background sync with a NetworkType.CONNECTED constraint, so writes queue up and flush automatically when connectivity returns. Fifth, the UI reflects sync state explicitly — SYNCED, STALE, or OFFLINE — so users always know what they're looking at. And the one thing I always call out separately is conflict resolution, because the right strategy varies: for most data it's last-write-wins, for collaborative data you need a merge strategy, and for some things you have to prompt the user."

"How do you support multiple teams in the same codebase?"

"There are seven things I'd put in place. First, module ownership with CODEOWNERS so every module has a designated team responsible for it. Second, :api modules that define public contracts and :impl modules that are private to the owning team, so teams program to interfaces and never depend on each other's internals. Third, no cross-feature direct dependencies — all cross-feature navigation goes through :core:navigation, which keeps features genuinely isolated. Fourth, shared infrastructure in :core:* owned by a platform team, with any changes requiring a platform team review. Fifth, the Dependency Guard plugin to automatically enforce that no circular or cross-feature imports sneak in. Sixth, module-level lint rules so each team can have their own code-style preferences without polluting the whole codebase. And seventh, parallel builds per feature module so teams aren't blocking each other on the critical path at compile time."

15.2 Trade-Off Thinking

For every comparison, run through the same five questions: what problem does it solve, what are the benefits, what are the costs, when would I use it, and when would I avoid it.

MVVM vs MVI

MVVM (Model-View-ViewModel)

  1. Problem it solves: Separates UI rendering from business logic; ViewModel survives config changes.
  2. Benefits:
    • Simpler mental model; most Android developers familiar with it.
    • Less boilerplate for straightforward screens.
    • StateFlow + SharedFlow maps naturally to Compose.
    • Well supported by Android Jetpack; viewModels() delegation, SavedStateHandle.
  3. Costs:
    • Multiple state fields (separate StateFlows) can get out of sync if not careful.
    • Side effects (navigation, toasts) require extra SharedFlow<Event> pattern.
    • Bidirectional data binding (if used with XML) causes hidden coupling.
  4. When to use: Most CRUD screens, standard forms, list-detail flows. When team is familiar with MVVM and the feature complexity is low-to-medium.
  5. When to avoid: Screens with complex, interdependent state where multiple events must be processed in strict order. Large screens where state fields proliferate and become hard to track.

MVI (Model-View-Intent)

  1. Problem it solves: Strict unidirectional data flow; all state changes are explicit and testable; time-travel debugging possible.
  2. Benefits:
    • Single sealed UiState class — state is always consistent (no partial updates).
    • All events are explicit Intent/Action objects — easy to log, replay, test.
    • Reducer function is pure: reduce(currentState, action) → newState. Easy to unit test.
    • Easier to reason about complex state machines (payments, multi-step flows).
  3. Costs:
    • More boilerplate: Intent sealed class, Reducer, Effect channel.
    • Slight learning curve for teams unfamiliar with the pattern.
    • Can be over-engineering for simple screens.
  4. When to use: Complex screens with many interdependent state fields; payment flows; multi-step wizards; collaborative editors; any feature that benefits from action logging/replay.
  5. When to avoid: Simple screens (a list with a loading state). When team has no MVI experience and delivery timeline is short.

The rule of thumb is: start with MVVM, and upgrade to MVI when the ViewModel becomes hard to reason about because multiple state fields are interacting with each other.

Compose vs XML Views

Compose

  1. Problem it solves: Declarative UI — UI is a function of state; no manual view synchronization.
  2. Benefits:
    • Less boilerplate: no ViewBinding, no notifyDataSetChanged().
    • Animations and theming are first-class.
    • Easier testing via Compose test APIs (onNodeWithText, performClick).
    • Strong recomposition model — Compose only re-renders what changed.
    • Single language (Kotlin) for both logic and UI.
  3. Costs:
    • Learning curve for teams trained in XML.
    • Compose compiler adds to build time.
    • Some edge cases in performance require understanding recomposition (stability, remember, derivedStateOf).
    • Interop with existing XML views adds complexity (but works via AndroidView/ComposeView).
  4. When to use: All new screens. Teams building greenfield apps or migrating screen by screen.
  5. When to avoid: Screens that use complex custom View subclasses not yet Compose-compatible; teams under tight deadline with no Compose experience; SurfaceView-based features (maps, cameras, video — use AndroidView).

XML Views

  1. Problem it solves: Standard declarative UI layout with view hierarchy inflated at runtime.
  2. Benefits: Large existing ecosystem; every Android developer knows it. Mature tooling (Layout Inspector, Layout Editor).
  3. Costs: Manual synchronization between UI and data model; boilerplate ViewBinding; adapter pattern required for lists; poor animation ergonomics.
  4. When to use: Only when maintaining existing XML code or when a specific custom view is not yet Compose-portable.
  5. When to avoid: Any new screen or feature.

Room vs Raw SQLite

Room

  1. Problem it solves: Type-safe compile-time verified SQL on Android without boilerplate.
  2. Benefits:
    • @Entity, @Dao, @Query — SQL verified at compile time, not runtime.
    • Built-in coroutine and Flow support.
    • Database migrations with Migration objects; version checked at open.
    • @TypeConverter for custom types.
    • Easy to test with in-memory Room DB.
  3. Costs:
    • Kapt/KSP annotation processing adds build time.
    • Some complex SQL (window functions, CTEs) requires raw query workarounds.
    • Adds ~200 KB to APK.
  4. When to use: Almost always. Any structured local data storage in an Android app.
  5. When to avoid: Extremely simple key-value storage (use DataStore instead). Embedding a database in an SDK where you want to minimize transitive dependencies. Apps that require complex SQL features Room doesn't cleanly support (rare).

Raw SQLite

  1. Problem it solves: Direct low-level database access.
  2. Benefits: No dependencies, no annotation processing.
  3. Costs: No type safety, no compile-time query verification, manual cursor management, no built-in migration system, no reactive support.
  4. When to use: SDK where pulling Room is unacceptable. Very simple use case (one table, five columns).
  5. When to avoid: Any app with non-trivial data model.

WorkManager vs Foreground Service

WorkManager

  1. Problem it solves: Guaranteed deferred background work that survives process death and device reboots.
  2. Benefits:
    • Constraint-based scheduling (network, battery, storage).
    • Chaining, parallelism, backoff built-in.
    • Works across all Android versions (no doze/battery optimization issues).
    • Progress observation via WorkInfo LiveData/Flow.
    • Expedited work requests for near-immediate execution.
  3. Costs:
    • Not for real-time or low-latency work (15-minute minimum interval for periodic).
    • No user-visible progress notification built-in (you add it manually).
    • Debugging scheduled work is harder (use WorkManager.getWorkInfosForUniqueWork()).
  4. When to use: Uploads, syncs, cleanup jobs, notification scheduling, any work that must complete "eventually" but not immediately.
  5. When to avoid: Work that needs to run immediately and continuously (use foreground service). Work where sub-second latency matters.

Foreground Service

  1. Problem it solves: Long-running operations that the user is aware of and that must not be interrupted.
  2. Benefits:
    • Runs indefinitely while foregrounded (persistent notification).
    • User-visible progress.
    • Required for real-time operations (location, media playback, calls, downloads).
  3. Costs:
    • Must show a persistent notification (Android 8+).
    • Foreground service types required (Android 14+) — must declare type in manifest.
    • OEM battery optimizations can kill even foreground services on some devices.
    • More complex lifecycle management.
  4. When to use: Music/podcast playback, navigation, ongoing call, real-time location tracking, file download/upload requiring user progress.
  5. When to avoid: Short background tasks (use WorkManager or coroutines). Anything that doesn't need to be running while the user is actively watching.

Coroutines vs RxJava

Coroutines

  1. Problem it solves: Asynchronous and concurrent programming without callback hell; structured concurrency.
  2. Benefits:
    • Sequential-looking code for async operations (no nesting).
    • Structured concurrency: CoroutineScope ties coroutine lifetime to component lifecycle.
    • Cancellation propagates automatically.
    • First-class Kotlin support: suspend, async/await, Flow.
    • Smaller runtime overhead than RxJava.
    • Official Google/Jetpack recommendation.
  3. Costs:
    • Requires Kotlin. Java code cannot call suspend functions directly.
    • Flow is less feature-rich than RxJava Observable for exotic operators.
    • Debugging: coroutine stack traces less readable (use -Dkotlinx.coroutines.debug).
  4. When to use: All new async code. Any Kotlin codebase.
  5. When to avoid: When the codebase is Java-only (use RxJava). When complex reactive pipelines use operators not in Flow (rarely true).

RxJava

  1. Problem it solves: Reactive programming model: compose streams of events with rich operators.
  2. Benefits:
    • Rich operator set (flatMap, zip, combineLatest, throttle, etc.).
    • Works in Java codebases.
    • Mature ecosystem, large community.
  3. Costs:
    • Steep learning curve.
    • Verbose code.
    • Easy to forget to dispose subscriptions → memory leaks.
    • Heavier runtime than coroutines.
    • No longer the Android-recommended approach.
  4. When to use: Maintaining existing RxJava code. Java-only modules. Complex observable pipelines with operators that have no good coroutine equivalent.
  5. When to avoid: All new Kotlin code. Any greenfield feature.

Flow vs LiveData

Flow (StateFlow/SharedFlow)

  1. Problem it solves: Reactive data streams that integrate with coroutines and support backpressure.
  2. Benefits:
    • Works outside Android (ViewModel, Repository, even pure Kotlin modules can use Flow).
    • Richer operator set than LiveData (map, filter, combine, flatMapLatest, etc.).
    • StateFlow is always consistent (no "missed emissions" on config change).
    • Better for UI layer with Compose (collectAsStateWithLifecycle).
    • Testable with turbine library.
  3. Costs:
    • Requires explicit lifecycle-aware collection (repeatOnLifecycle or collectAsStateWithLifecycle) — forgetting this leaks.
    • No built-in null-value semantics for initial state (use a nullable or wrapper type).
  4. When to use: All new code. Repository → ViewModel → UI data flow. Any stream that needs operators.
  5. When to avoid: Very simple one-shot data that doesn't change. Cases where LiveData lifecycle integration is already well-tested and working.

LiveData

  1. Problem it solves: Lifecycle-aware observable that automatically stops/resumes with the lifecycle owner.
  2. Benefits:
    • Automatic lifecycle handling (no repeatOnLifecycle needed).
    • Simple API.
  3. Costs:
    • Main thread only (value is always posted to main thread).
    • Weak operator set.
    • Tied to Android framework (not usable in non-Android modules like :domain:).
    • MediatorLiveData is verbose compared to Flow operators.
  4. When to use: Maintaining existing LiveData code.
  5. When to avoid: All new code. Any code in domain/data layers (non-Android modules).

Hilt vs Manual DI

Hilt

  1. Problem it solves: Boilerplate-free DI on Android using annotation-based code generation on top of Dagger 2.
  2. Benefits:
    • Standard component hierarchy tied to Android lifecycle (Application, Activity, ViewModel, etc.).
    • Less boilerplate than raw Dagger 2.
    • @HiltViewModel integrates ViewModel injection seamlessly.
    • Good documentation and tooling.
    • Testing support: @HiltAndroidTest, @UninstallModules.
  3. Costs:
    • Build time: Hilt/Dagger annotation processing (KAPT/KSP) is the single largest build time contributor.
    • Hard to use outside Android (not suitable for pure Kotlin SDK).
    • Opaque compile errors when DI graph is incomplete.
  4. When to use: All standard Android apps. Greenfield apps. When team is willing to invest in DI setup upfront.
  5. When to avoid: SDKs (no framework dependency). Apps where build time is critical and team is small (consider Koin or manual DI). Apps targeting very low API levels where Hilt adds unexpected overhead.

Manual DI (Pure Kotlin)

  1. Problem it solves: Dependency injection without annotation processing — create factories and pass dependencies by hand.
  2. Benefits:
    • Zero build time overhead.
    • Works in any Kotlin/Java code (SDK, non-Android modules).
    • No magic; easier to reason about.
  3. Costs:
    • Boilerplate: factories, constructor call sites.
    • Scope management is manual (you manage singleton vs scoped vs transient).
    • Hard to maintain at scale (100+ classes).
  4. When to use: SDKs. Small apps. Non-Android modules in a larger project.
  5. When to avoid: Large apps with many injection points — the boilerplate becomes unmanageable.

Monolith vs Modular Architecture

Monolith (Single App Module)

  1. Problem it solves: Simple app structure where all code lives in :app.
  2. Benefits:
    • Simple setup; fast to get started.
    • No inter-module dependency management.
    • Single DI component graph.
  3. Costs:
    • Build time: any change recompiles everything.
    • No ownership boundaries — any team can modify any code.
    • Harder to enforce clean architecture.
    • Difficult to extract to modular later (becomes a big bang rewrite risk).
  4. When to use: Small apps (1 team, <5 engineers). Prototype/MVP. Short-lived apps.
  5. When to avoid: Multi-team codebases. Apps that plan to grow. Apps where build time is already a concern.

Modular Architecture

  1. Problem it solves: Parallel builds, clean ownership boundaries, faster incremental compilation.
  2. Benefits:
    • Build: only changed modules recompile.
    • Ownership: teams own specific modules.
    • Testability: modules tested in isolation.
    • Enables dynamic feature modules.
    • Enforces clean architecture (import rules).
  3. Costs:
    • Complex Gradle setup.
    • Inter-module communication needs explicit contracts (:api modules).
    • Easy to make circular dependencies if not managed.
    • Higher ramp-up for new engineers.
  4. When to use: Any app with > 2 teams. Any app targeting aggressive build time reduction. Any app planning DFMs.
  5. When to avoid: Small teams where the overhead exceeds the benefit.

Single Activity vs Multiple Activities

Single Activity

  1. Problem it solves: One Activity hosts all screens; NavController/NavHost handles navigation within.
  2. Benefits:
    • Shared ViewModel scope across the navigation graph.
    • Smooth transitions (shared element, slide) across all screens.
    • Single back stack managed by NavController.
    • Less Intent boilerplate.
  3. Costs:
    • Complex flows may need navigation sub-graphs.
    • Shared ViewModels can become large if not decomposed.
    • Screen state from deep in the graph may be complex to save/restore.
  4. When to use: Linear, single-flow apps. Apps where cross-screen animation is important. Greenfield apps.
  5. When to avoid: Super-apps where features are completely independent and should have separate task stacks. When entry points from external intents require different Activities for proper Android back-stack behavior.

Multiple Activities

  1. Problem it solves: Each flow or feature has its own Activity with its own task stack and lifecycle.
  2. Benefits:
    • Proper Android task management (each Activity can be a task root).
    • Clear isolation between features.
    • Easier to support multiple deep-link entry points.
  3. Costs:
    • More Intent/Parcelable boilerplate.
    • Harder to share state across Activities.
    • Activity transitions are heavier than Compose navigation transitions.
  4. When to use: Flows with independent entry points. Multi-process apps. Feature modules that should be isolated.
  5. When to avoid: Within a single linear flow (use NavController for that).

Repository per Feature vs Shared Repository

Repository per Feature

  1. Problem it solves: Each feature owns its data access layer; no shared state.
  2. Benefits:
    • Clear ownership.
    • Feature modules have no cross-module data dependencies.
    • Easier to mock in tests.
  3. Costs:
    • Data duplication: two features may have their own copy of UserProfile data.
    • Cache coherence: two repositories caching the same entity may get out of sync.
  4. When to use: Features with truly independent data (e.g., health feature and food feature in a super-app).
  5. When to avoid: When multiple features display the same data (user profile, cart, session) — you want a single source of truth.

Shared Repository

  1. Problem it solves: Single source of truth for data shared across features (e.g., UserRepository, CartRepository).
  2. Benefits:
    • Cache coherence: all readers see the same state.
    • One network call for shared data.
  3. Costs:
    • Creates a dependency from feature modules to :data:shared — careful with ownership.
  4. When to use: User identity, session, cart — anything that must be consistent across features.
  5. When to avoid: Feature-specific data that no other feature needs.

Domain Layer vs No Domain Layer

Domain Layer

  1. Problem it solves: Business logic in pure Kotlin use-case classes, independent of Android framework and UI.
  2. Benefits:
    • Pure Kotlin: no Android imports → fast unit tests, reusable across platforms (KMP).
    • Single responsibility: each use case does one thing.
    • ViewModel is thin: delegates to use cases.
    • Logic testable without mocking Android framework.
  3. Costs:
    • Extra layer → more files, more indirection.
    • For simple screens, use cases are trivial pass-throughs (wasted abstraction).
  4. When to use: Complex business logic (payment rules, eligibility checks, booking constraints). Multi-step transformations. Code shared across multiple ViewModels. KMP targeting.
  5. When to avoid: Simple CRUD screens where the "use case" would just call one repository method.

No Domain Layer

  1. Problem it solves: Simplify architecture for straightforward screens.
  2. Benefits: Less boilerplate; faster to write.
  3. Costs: Business logic bleeds into ViewModel or Repository. Hard to test complex logic in isolation.
  4. When to use: Simple screens. Prototype code.
  5. When to avoid: Any non-trivial business logic. Multi-team codebases where logic ownership matters.

Local-First vs Network-First

Local-First

  1. Problem it solves: App works offline; UI always responsive (reads from local DB first).
  2. Benefits:
    • Zero latency reads.
    • Works offline by default.
    • User experience consistent regardless of network quality.
  3. Costs:
    • Stale data risk: local data may be outdated.
    • Complex sync and conflict resolution needed.
    • More implementation effort (Room + sync logic).
  4. When to use: Feed apps, todo/note apps, offline-capable enterprise apps. Any feature where showing stale data is better than showing nothing.
  5. When to avoid: Real-time critical data (stock prices, live seat availability). Data that must be fresh for correctness (payment confirmation, order status).

Network-First

  1. Problem it solves: Always show the latest data from the server.
  2. Benefits:
    • Always fresh.
    • No conflict resolution needed.
    • Simpler implementation.
  3. Costs:
    • Fails offline.
    • Higher latency (must wait for network).
  4. When to use: Real-time data (prices, inventory, live scores). Data that is wrong if stale.
  5. When to avoid: Data that changes infrequently. Poor network conditions.

Synchronous vs Asynchronous IPC

Synchronous IPC (AIDL blocking call)

  1. Problem it solves: Caller waits for the result from another process; simpler sequential code.
  2. Benefits:
    • Simple to reason about: call returns result.
    • No callback management.
  3. Costs:
    • Blocks the calling thread (which is a binder thread, not main thread — but still counts).
    • Risk of ANR if the callee is slow.
    • Deadlock risk if callee calls back into the caller synchronously.
  4. When to use: Quick IPC calls with guaranteed low latency (< 1ms). Status queries where the caller NEEDS the answer immediately.
  5. When to avoid: Any call that involves I/O or computation in the remote process. Any call from a UI-critical context.

Asynchronous IPC (Messenger, callbacks, AIDL with callback)

  1. Problem it solves: Non-blocking IPC; caller continues while waiting for result.
  2. Benefits:
    • Non-blocking; no ANR risk.
    • Callback arrives on binder thread (can be marshalled to main).
  3. Costs:
    • More complex code (callbacks/channels).
    • State management more complex.
  4. When to use: All IPC involving I/O or computation. State subscription (register callback, receive updates over time).
  5. When to avoid: When synchronous result is required and the call is guaranteed fast.

HashMap vs TreeMap

HashMap

  1. Problem it solves: O(1) average-case key lookup, insertion, deletion.
  2. Benefits: Fastest for most lookups; no ordering overhead.
  3. Costs: No ordering; iteration order not guaranteed; worst-case O(n) with hash collisions.
  4. When to use: Lookup/cache tables where insertion order or sorted order is not needed. The default choice for most Maps.
  5. When to avoid: When you need sorted iteration (e.g., range queries, sorted display of entries). When key ordering matters for correctness.

TreeMap

  1. Problem it solves: Sorted key ordering with O(log n) operations.
  2. Benefits: Keys always sorted; supports headMap, tailMap, subMap, firstKey, lastKey.
  3. Costs: O(log n) for all operations vs O(1) for HashMap.
  4. When to use: Range queries. Ordered iteration. Implementing a priority queue-like structure where keys have natural ordering.
  5. When to avoid: Simple lookup where ordering is irrelevant. Hot paths where O(log n) is slower than O(1).

One Android-specific point worth adding: also consider ArrayMap for small maps with fewer than about 100 entries (lower memory than HashMap), and SparseArray when your keys are Int values (avoids boxing entirely).

ArrayList vs LinkedList

ArrayList

  1. Problem it solves: Ordered, indexed, random-access list backed by an array.
  2. Benefits:
    • O(1) random access by index.
    • Good cache locality (contiguous memory).
    • Efficient iteration.
  3. Costs:
    • O(n) insertion/deletion in the middle (array shift).
    • Amortized O(1) add-at-end; occasional resize copies.
  4. When to use: The default choice for lists. Any list where you read by index or iterate often. Compose LazyColumn data model.
  5. When to avoid: Frequent insertion/deletion in the middle of large lists.

LinkedList

  1. Problem it solves: O(1) insertion/deletion at head/tail without array resizing.
  2. Benefits: O(1) add/remove at head or tail (as a Deque).
  3. Costs:
    • O(n) random access.
    • High memory overhead: each node has two pointers.
    • Poor cache locality.
  4. When to use: Implementing a queue or deque. Frequent insertion at head (e.g., prepend to a list repeatedly). Producer-consumer buffers where you add to one end and remove from the other.
  5. When to avoid: Any list where you access by index. Any list that will be iterated many times. Any list that will be displayed in a UI (use ArrayList).

In practice, LinkedList is rarely the right answer on Android. ArrayDeque is almost always preferable for queue and deque use cases because of its better cache locality and lower per-element overhead.

15.3 Legacy Code and Migration

When an interviewer asks about migration, what they are really asking is: can you drive a complex multi-month engineering project without stopping feature work, without breaking production, and while bringing the whole team along? Every answer here needs to demonstrate three things — discipline, incrementalism, and measurement.

Java to Kotlin

Goal: Incrementally replace Java files with idiomatic Kotlin without breaking existing tests or callers.

Approach:

  1. Interop first: Kotlin and Java interop seamlessly. Start calling Kotlin from Java and vice

versa. No big-bang needed.

  1. IntelliJ auto-conversion: Use IntelliJ's "Convert Java file to Kotlin" as a starting point,

then review for idiomatic improvements (null safety, data classes, extension functions).

  1. Prioritize new code: All new files are written in Kotlin. Legacy Java is converted

opportunistically when touching a file for other reasons.

  1. Nullability contracts: Add @NonNull/@Nullable annotations to Java before converting.

Kotlin will respect them and emit correct null-safety checks.

  1. Platform types: Eliminate all ! (platform types) in converted code. Make nullability

explicit.

  1. Kotlin idioms: Replace if (x != null) x.foo() with x?.foo(). Replace getters with

properties. Use data classes where appropriate.

  1. Test coverage before and after: Run existing tests after conversion. Conversion should be

behavior-neutral.

Metrics to prove success:

  • % of files in Kotlin tracked over time.
  • NullPointerException rate in Sentry (should decrease as null safety improves).
  • Code review time per PR (should decrease as Kotlin is more concise).

Common pitfalls:

  • companion object vs top-level functions — prefer top-level unless the function is tied to

a class.

  • @JvmStatic, @JvmOverloads, @JvmField needed when Kotlin code is called from Java.
  • data class copy() misuse — the copy is shallow; mutable references inside are shared.

XML to Compose

Goal: Migrate screens from XML layouts to Jetpack Compose incrementally.

Approach:

  1. Interop layer: Use ComposeView inside an existing XML layout to embed Compose in a

Fragment. Use AndroidView inside Compose to embed XML views in Compose. Either direction works.

  1. Start with new screens: All new screens written in Compose.
  2. Pilot an existing screen: Choose a simple, well-covered screen. Replace its XML with

Compose. Keep the Fragment temporarily; it becomes a thin wrapper hosting ComposeView.

  1. Migrate Fragment to Composable function: Once the screen is Compose, the Fragment is

just a one-liner (setContent { ScreenComposable() }). Eventually the Fragment can be removed if navigation is migrated to NavController.

  1. Theme migration: Ensure MezzanineTheme (or the app's design system) is properly

integrated before migration (colors, typography, shapes).

  1. Remove XML files only after the Compose equivalent is shipped and stable.

Metrics:

  • % of screens in Compose tracked in a migration tracker.
  • Rendering frame times per screen (Compose should improve jank on complex screens).
  • Screenshot test parity (before/after visual comparison).
  • APK size delta (Compose adds ~1.5 MB to APK; acceptable for most apps).

Common pitfalls:

  • Missing LocalLifecycleOwner in Compose-in-Fragment setups (use ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed).
  • remember used incorrectly when rememberSaveable is needed for config change survival.
  • Recomposition storms from unstable lambdas (use remember for callbacks, stable data classes).

MVP to MVVM/MVI

Goal: Replace Presenter + View interface pattern with ViewModel + StateFlow, without stopping feature work.

Approach:

  1. Identify the Presenter contract: The View interface is already a contract. The Presenter

updates the View. Map each View.showX() call to a corresponding state field.

  1. Create a parallel ViewModel: The ViewModel replicates the Presenter's state logic in a

StateFlow<ScreenUiState>. Both Presenter and ViewModel exist simultaneously.

  1. Thin Presenter → ViewModel delegation: Gradually move logic from Presenter to ViewModel.

Presenter becomes a thin bridge that just calls ViewModel.

  1. Replace View interface with Compose: Once ViewModel has all logic, replace the XML

Fragment with a Compose screen observing ViewModel.uiState.

  1. Delete the Presenter and View interface.

Key challenge — RxJava in Presenter: Presenters often use RxJava. Migrate RxJava subscriptions to coroutines using rxObservable.asFlow() or Single.await() from kotlinx-coroutines-rx2. This lets you migrate incrementally — the interop layer translates.

Metrics:

  • Presenter files remaining (tracked in migration backlog).
  • Test coverage before and after (ViewModel tests should cover same paths as Presenter tests).

AsyncTask/RxJava to Coroutines

AsyncTask Migration:

AsyncTask is deprecated in API 30 and removed in API 33. Migration is straightforward:

// Before: AsyncTask
class FetchDataTask : AsyncTask<Void, Void, Result>() {
    override fun doInBackground(vararg p0: Void?) = fetchFromNetwork()
    override fun onPostExecute(result: Result) { updateUI(result) }
}

// After: coroutine in lifecycleScope
lifecycleScope.launch {
    val result = withContext(Dispatchers.IO) { fetchFromNetwork() }
    updateUI(result) // back on Main
}

The mental model is one-to-one: each AsyncTask becomes one launch { withContext(IO) { } } block.

RxJava Migration:

Use kotlinx-coroutines-rx2 bridge:

  • Single<T>.await() → suspend fun T.
  • Observable<T>.asFlow() → Flow<T>.
  • Completable.await() → suspend fun Unit.

Migrate one subscription at a time. Start with leaf-level utilities that have no callers depending on Observable return types. Work inward.

Disposing subscriptions — moving to structured cancellation: Replace CompositeDisposable.clear() in onDestroy with simply letting the CoroutineScope cancel in onCleared(). Cancellation propagates automatically to all child coroutines.

Introducing Dependency Injection

Goal: Add Hilt (or Dagger) to a codebase that uses manual construction (e.g., MyClass(MyDep())).

Approach:

  1. Identify construction sites: Every new MyClass(...) or MyClass(...) in Activities,

Fragments, or ViewModels is a construction site to migrate.

  1. Extract constructor injection: Change classes to receive their dependencies via constructor

rather than constructing them internally. This is the key step and can be done without Hilt.

  1. Add Hilt incrementally:
    • Add @HiltAndroidApp to Application.
    • Add @AndroidEntryPoint to Activities and Fragments one by one.
    • Add @Inject constructor() to classes being injected.
    • Add @Module / @Provides for third-party classes.
  2. Migrate ViewModel injection: Add @HiltViewModel + @Inject constructor(). Remove

ViewModelFactory boilerplate.

  1. Test modules: Add @UninstallModules + fake @TestInstallIn modules for testing.

Risk: Adding @HiltAndroidApp changes Application initialization. Test thoroughly.

Introducing Modularization

See also 15.1 Interview Angles — "How would you introduce modularization gradually?"

Step-by-step:

  1. Create :core:network, :core:db, :core:ui — pure infrastructure, no circular deps.
  2. Run a build scan (./gradlew build --scan) before and after each extraction to measure

improvement.

  1. Extract :feature:X for new features — no rework of existing code.
  2. Add Dependency Guard (com.dropbox.dependency-guard) — enforce no circular dependencies.
  3. Extract existing features one at a time, starting with the most isolated.
  4. Define :api:X interfaces for cross-feature contracts.

Common mistake: Extracting too many modules too fast. Each extracted module that doesn't reduce compile scope is just overhead. Measure before and after.

Reducing Build Time

Diagnosis first:

./gradlew assembleDebug --scan   # Gradle build scan
./gradlew assembleDebug --profile  # HTML profile report

The three metrics to look for are annotation processing time, configuration time, and the number of tasks that were not up-to-date — those last ones tell you exactly how much incremental caching is being wasted.

Strategies (roughly ordered by impact):

  1. Migrate KAPT → KSP: KSP is 2x faster for most annotation processors (Room, Moshi, Hilt).
  2. Modularization: Parallel builds; only changed modules recompile.
  3. Avoid transitive api dependencies: Use implementation unless the type is in the public API.
  4. Build caching: org.gradle.caching=true in gradle.properties. Use remote build cache

(Gradle Enterprise or custom) in CI.

  1. Configuration cache: org.gradle.configuration-cache=true (Gradle 8+).
  2. Incremental annotation processing: Ensure all annotation processors support incremental mode.
  3. Avoid @JvmStatic + @JvmOverloads overuse — generates extra methods.
  4. Reduce unused dependencies: Run Dependency Analysis Gradle Plugin to find unused deps.
  5. R8 full mode in debug: Speeds up debug build dex step (trade-off: slower first build, faster incremental).
  6. Avoid resource merging overhead: Keep resources in the correct module; do not put all resources in :app.

Measurement: Track ./gradlew assembleDebug time in CI over time. Set a regression budget (e.g., max 10% increase per PR).

Removing Memory Leaks

Detection:

  • LeakCanary: mandatory in debug builds. Every new leak generates a LeakCanary notification.
  • Sentry: track OutOfMemoryError events.
  • Android Studio Profiler: heap dumps to find retained objects.

Common sources and fixes:

Source Fix
Activity/Fragment in a static fieldNever store Context in static fields. Use WeakReference if unavoidable.
Registered listener not unregisteredRegister in onStart, unregister in onStop.
Handler with anonymous RunnableUse Handler(Looper.getMainLooper()) + remove callbacks in onDestroy.
Anonymous class/lambda capturing outer classUse a named class or WeakReference.
ViewModel holding View/Context referenceViewModels must not hold View or Activity references. Use Application context if needed.
Bitmap not recycled (pre-API 26)Use Glide/Coil which manage bitmap lifecycle.
Subscription not disposedUse CoroutineScope.cancel() or CompositeDisposable.clear().

Process:

  1. Fix leak identified by LeakCanary.
  2. Write a test that detects the leak (using LeakCanary's LeakAssert).
  3. Run the test in CI to prevent regression.

Improving Test Coverage

Approach:

  1. Measure current state: Run ./gradlew testWithCoverage. Generate JaCoCo report. Find

the bottom 20% (files with < 20% coverage).

  1. Prioritize by risk: Focus on high-churn, high-complexity classes with low coverage first.

Use git log --numstat to identify high-churn files.

  1. Add tests when fixing bugs: Every bug fix must include a failing test that proves the bug.
  2. Add tests when refactoring: Refactoring without tests is dangerous. Write tests first,

then refactor.

  1. Coverage gates: Add a JaCoCo coverage gate in CI (jacocoTestCoverageVerification).

Set minimum coverage (e.g., 70%) per module. Ratchet it up over time.

  1. Testing pyramid:
    • 70% unit tests (fast, cheap)
    • 20% integration tests (medium)
    • 10% UI/E2E tests (slow, fragile)
  2. Mock at boundaries: MockK for external dependencies. Fake implementations for internal

boundaries.

Common coverage antipatterns:

  • Testing implementation details (test behavior, not internals).
  • Testing only the happy path (add error and edge cases).
  • Brittle tests that test too much at once.

Stabilizing Crashy Features

Framework for investigating and fixing crashes:

  1. Triage: Group Sentry events by root cause, not by crash type. Sort by volume × user impact.
  2. Reproduce: Every crash must be reproducible before fixing. If you can't reproduce, you

can't verify the fix.

  1. Add logging: Add ZLog.logErrorWithTeamTag() breadcrumbs before the crash site to capture

context.

  1. Fix conservatively: Add null checks, default values, and fallback states rather than

aggressive refactors. The goal is stability, not elegance.

  1. Feature flag: If a feature is causing 1%+ crash rate, flag it off immediately.
  2. Test the fix: Unit test the specific crash scenario. Integration test the flow.
  3. Monitor after fix: Set a Sentry alert for the specific crash grouping. Verify crash rate

drops in the next 24-48 hours after rollout.

Common crash types:

Type Fix
NPE on API response fieldAdd null-safety; use nullable types; default values for missing fields.
ArrayIndexOutOfBoundsExceptionBounds check before access; guard adapter positions.
IllegalStateException in FragmentCheck isAdded() before using requireContext().
ClassCastException in RecyclerViewVerify viewType in onCreateViewHolder/onBindViewHolder.
SQLiteExceptionValidate SQL migrations; test DB upgrade paths in unit tests.
ANRMove I/O off main thread; use StrictMode in debug to catch violations early.

Incremental Refactoring

Principles:

  1. Boy scout rule: Leave code slightly cleaner than you found it in every PR. Accumulates

without a big-bang refactor.

  1. Strangler fig pattern: Build the new implementation alongside the old. Gradually route

callers to the new one. Once all callers are migrated, delete the old one.

  1. Wrap then replace: Wrap the legacy class in an interface. New code uses the interface.

Replace the implementation later without touching new code.

  1. Never mix refactoring and feature work in the same PR. Reviewers can't tell what is

behavior change vs refactoring. Keep them separate.

  1. Test coverage as a prerequisite: Do not refactor code without a test baseline. Tests

are the safety net. If coverage is low, write tests first.

  1. Measure impact: Refactoring should improve measurable metrics (build time, test time,

crash rate, code complexity score). If no metric improves, question the value.

Interview Angles — Migration

"How do you migrate without stopping feature development?"

"There are four things I rely on. First, feature flags — the new code runs alongside the old code and you switch at runtime, so nothing is ever all-or-nothing. Second, parallel implementation — you build the new system, wire it in incrementally, and delete the old one only after all callers are migrated. Third, module boundaries — by migrating one module at a time you completely avoid touching other teams' code in the same PR. And fourth, the practical time allocation: I dedicate 20% of every sprint to migration, never zero and never a hundred percent. The anti-pattern I always call out explicitly is 'we'll freeze features for three months and do a full rewrite' — that always fails because scope grows, the team loses context, and you end up integrating everything at once right at the deadline."

"How do you avoid big-bang rewrites?"

"Big-bang rewrites fail for four interconnected reasons. First, scope always grows — the new system needs to match every edge case of the old one, most of which are undocumented and only discovered mid-rewrite. Second, the team loses context halfway through because the rewrite takes months. Third, integration happens all at once at the very end, which is when you're most exhausted and least able to absorb surprises. And fourth, there's no working app to ship if the deadline moves. The alternative I use is incremental, verifiable steps — the app must be in a deployable state at every commit. The pattern for this is the strangler fig: the old and new systems coexist, you gradually route callers to the new one, and the migration is reversible at any point. And critically, I define 'done' per unit — per screen, per module, per class — not for the migration as a whole."

"How do you prove migration success?"

"I use six categories of metrics. Crash rate before and after — if migration introduced regressions you need to know immediately. Build time before and after — this is often the primary driver of modularization migrations and you need hard numbers. Test coverage before and after — migration should never reduce coverage. Code complexity metrics like cyclomatic complexity and file length — these confirm the code is actually getting simpler, not just different. PR review time as a proxy for code readability — if reviews are faster, the code is easier to understand. And finally a developer survey: self-reported confidence and onboarding time, because if engineers feel less confident after the migration than before, something went wrong even if the hard metrics look fine."

"How do you get team adoption?"

"There are six things that actually move the needle. First, lead by example — write the first idiomatic implementation yourself, because people will copy the pattern they see in the codebase more than anything they read in a doc. Second, make the right way the easy way by adding Live Templates in IntelliJ so the correct pattern takes less keystrokes than the old way. Third, in code review, point people to the pattern without blocking PRs on style — block only when it's a correctness or production issue. Fourth, document it, link the guide in every relevant PR description, and present it at a tech talk so there's a shared canonical reference. Fifth, pair on the first migration of each new type — doing it together once is worth ten documentation pages. And sixth, never mandate, always persuade: show the concrete benefits in terms engineers care about — minutes shaved off the build, tests that no longer need a full emulator. When people see the benefit themselves, adoption follows."

15.4 Engineering Leadership

Staff-level interviews assess not just technical knowledge but how you use it to influence teams and organizations. Every answer here needs to demonstrate three things: judgment — knowing when to apply a technique and when not to; scale — impact that extends beyond yourself; and craft — the quality of execution once you decide to act.

Use the STAR framework to structure every answer: Situation, Task, Action, Result.

STAR Templates

Each template below gives you the structure to follow. Fill in the specifics from your own experience — the brackets mark what you need to replace.

Leading Architecture Decisions

Situation: [The codebase had grown to X engineers on a single :app module. Build times were N minutes. Different teams had conflicting patterns in the same files. There was no clear owner for shared components.]

Task: [I was asked to lead the architectural modernization effort: define a module structure, migration plan, and team ownership model.]

Action:

  • Surveyed the codebase (dependency graph, build scan) to understand current state.
  • Interviewed tech leads from each team to understand pain points.
  • Drafted a design doc with three options (monolith, feature modules, full clean architecture

with DFMs), each with trade-offs, timelines, and risks.

  • Facilitated a design review with all tech leads; incorporated feedback.
  • Identified the lowest-risk, highest-impact first step (extract :core:network).
  • Created a migration tracker with module owners and milestones.
  • Wrote the first migration to serve as a reference implementation; held a live coding session

to walk the team through it.

  • Established Dependency Guard and CODEOWNERS to enforce the new model.

Result: [Build time reduced by X%. Teams can now work independently on feature modules. New engineers onboard faster. The pattern has been adopted by all teams without mandating.]

Mentoring Engineers

Situation: [A junior engineer on my team was delivering code that worked but was consistently hard to review — large PRs, no tests, unclear naming.]

Task: [Help them grow to mid-level quality without damaging their confidence or autonomy.]

Action:

  • Set up a weekly 1:1 with a technical focus: walk through one thing to improve each week (not everything at once).
  • Pair-programmed on their next PR: not to write it for them, but to model the thought process.
  • Gave feedback in code review in questions ("What would happen if X is null here?") not

directives ("Add null check").

  • Connected them with resources: pointed to specific internal examples of well-structured code.
  • Celebrated improvements publicly in the team channel.

Result: [Within two quarters, their PRs were consistently smaller, well-tested, and faster to review. They now mentor newer engineers the same way.]

Handling Disagreement

Situation: [Another senior engineer and I disagreed on whether to use Flow or LiveData for our ViewModel state. They wanted to maintain LiveData for consistency; I wanted to migrate to Flow for the testability and KMP compatibility benefits.]

Task: [Resolve the disagreement and move forward — ideally with the better technical decision and without a fractured team.]

Action:

  • Acknowledged their concern (consistency is a real cost, not a trivial objection).
  • Prepared a written comparison (the same 5-question framework from 15.2) shared asynchronously.
  • Proposed a time-boxed experiment: migrate one screen to Flow, measure build time, test time,

and code lines. Let the data drive the decision.

  • Set an explicit decision deadline: we will decide by end of sprint.
  • When the experiment favored Flow, proposed a gradual migration plan with a transitional adapter

for existing LiveData callers.

Result: [We adopted Flow. The other engineer became a co-author of the migration guide because I incorporated their concerns about the transition plan. Disagreement became collaboration.]

Writing Design Docs

A strong design doc has nine sections. First, the problem statement — what breaks if you don't solve this? Second, goals and non-goals — explicit boundaries are what prevent scope creep. Third, background and constraints — what decisions are already made and what is non-negotiable? Fourth, options considered — at least three, and one of them should always be "do nothing." Fifth, the recommended option with its rationale. Sixth, trade-offs — what the recommended option gives up. Seventh, the migration plan — how you get from the current state to the target state. Eighth, open questions that need resolution before implementation starts. And ninth, success metrics — how will you know it worked?

One practical note: a design doc that gets no comments in review was probably too safe. Good design docs should generate discussion. Invite disagreement explicitly — add a section that says "I am uncertain about X, here is my current thinking, what am I missing?"

Reviewing Large PRs

Framework:

  1. First pass: understand the intent. Read the PR description and linked ticket. Don't read code yet.
  2. Second pass: high-level structural review. Are there missing modules? Is the design sound?
  3. Third pass: correctness review. Look for crash risks, data races, incorrect API usage.
  4. Fourth pass: code quality. Naming, simplifications, test coverage.
  5. Leave comments in priority order (P1: must-fix, P2: should-fix, P3: nit/suggestion).

The practical rules: never approve a PR you haven't fully read. Never block a PR on P3 nits unless the author explicitly asks for that level of feedback. And when a PR is too large to review well, tell the author what to extract first rather than trying to review an unmanageable diff.

Creating Coding Standards

The key principle is that a standard engineers helped write gets adopted, while one handed down from above gets ignored.

The process has six steps. First, identify a recurring inconsistency — logging, error handling, null handling — something you can point to concretely. Second, survey existing code and count how many different ways it's currently done; three or more different approaches in the same codebase is the signal it's a real problem. Third, propose a standard with the rationale and share it as a draft, not a decree. Fourth, hold an RFC period of one to two weeks and genuinely incorporate the feedback. Fifth, codify it — write it in the team guide and add a lint rule where possible, because automated enforcement is far more reliable than code review. And sixth, apply it to new code only; backfilling is optional and tracked separately so it doesn't become an unbounded obligation.

Driving Performance Improvements

Framework:

  1. Measure first: Macrobenchmark for startup and scroll. Perfetto traces for specific UI threads. Profiler for CPU and memory. Never optimize without a baseline.
  2. Identify the top bottleneck — Amdahl's law: fix the biggest constraint first.
  3. Fix, measure, compare.
  4. Automate the measurement in CI: a performance regression is a build failure.
  5. Publish the results: post a before/after in the team channel. Performance wins motivate the team.

Typical wins to name with concrete numbers: Baseline Profiles reduce startup by 20–30%. Lazy initialization eliminates blocking I/O from Application.onCreate(). Modularization reduces incremental build time (the exact number varies by codebase, so always measure yours). And removing synchronous SharedPreferences reads from the main thread eliminates a class of jank that is surprisingly common in older codebases.

Reducing Crash/ANR Rate

Process:

  1. Triage: open Sentry (or Crashlytics) and sort by user-affected count, not total event count — a crash that hits 10,000 users once each outranks one that hits 1 user 10,000 times.
  2. Target the top 5 issues — fixing the top 5 almost always moves the crash-free rate measurably.
  3. For each issue: reproduce it, add logging breadcrumbs, fix it, test it, and then monitor it specifically after rollout.
  4. For ANRs: use Android Vitals in Play Console, add StrictMode in debug builds to surface violations early, and profile with Perfetto to find exactly what is blocking the main thread.
  5. Prevent regression: add a CI gate so that crashFreeSessionsTarget > 99.5% is a hard requirement, and set a Sentry alert to page if crash rate spikes after any release.

Improving Release Quality

Strategies: A staging environment where all changes must pass before they ever touch production. Phased rollout at 1% then 5% then 20% then 100%, with explicit monitoring at each gate before advancing. Feature flags on every risky change with an instant kill-switch. A release train on a predictable weekly or bi-weekly cadence so engineers plan to the schedule and there are no emergency rushes. A 24-hour code freeze before each cut where only critical fixes are allowed in. QA sign-off on P0 flows before each release. And automated regression tests — Espresso and Compose tests — running in CI so regressions are caught before they reach QA at all.

Coordinating Across Backend, Product, Design, QA

Practical patterns: API contracts first — before writing a line of code, agree on the API schema with the backend team, write a mock server from that schema, and let frontend and backend develop in parallel against it. Design handoff via Figma and code connect — get a design walkthrough before implementation starts, not after the first PR is opened. QA involvement early — invite QA to the design doc review, define acceptance criteria together, and have QA write test cases before implementation is done. Clear owners — every cross-functional dependency has exactly one owner with a deadline, because ambiguity in ownership is the most common cause of delays. And status visibility — post a weekly async update to Slack or Confluence so stakeholders can find status themselves; they should never need to ask.

Making Trade-Offs Under Deadlines

Framework: There are five steps I run through. First, understand the real constraint — is it a hard business deadline like a product launch, or a soft one where someone just wants it sooner? Those require very different responses. Second, scope reduction before quality reduction — the question to ask is whether we can ship 80% of the feature that delivers 100% of the value. Third, quality gates are non-negotiable: no shipping without passing automated tests, and no crash-rate increases allowed under any deadline. Fourth, technical debt is explicit — if we take a shortcut, a ticket for the cleanup gets written immediately so it doesn't silently become a permanent decision. Fifth, communicate early: the message is "we can hit the deadline if we cut X, is that acceptable?" — not "we need more time" delivered at the last minute.

"How do you maintain code quality across teams?"

"There are seven things I rely on. First, automated gates — lint, detekt, coverage thresholds, Dependency Guard. Computers enforce standards; humans provide judgment. The key insight is that if it can be automated, automate it, because code review is too inconsistent and too expensive to be the only mechanism. Second, a code review culture where PRs are about knowledge sharing and finding bugs, not gatekeeping, with a 24-hour response time SLA so reviews don't become a bottleneck. Third, a shared standards document that is a living doc, version-controlled, and updated via an RFC process so engineers own it rather than feel subjected to it. Fourth, rotation on shared infrastructure — engineers rotating ownership of :core modules spreads knowledge and prevents single points of failure. Fifth, blameless quality metrics: track crash rate, ANR rate, and coverage per team not to blame anyone but to identify where a team needs support or resources. Sixth, an explicit prioritized tech debt backlog with 20% of sprint capacity reserved for it, because debt that isn't tracked and scheduled never gets paid down. And seventh, lead by example — the quality of your own PRs sets the actual bar, regardless of any written standard. If your PRs have thorough tests and clear descriptions, others will match that."
