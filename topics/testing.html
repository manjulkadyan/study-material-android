11.1 Unit Testing

JUnit 4 / JUnit 5 Basics

🎤 Say it out loud (~30–45s): "JUnit is the harness that discovers test methods by annotation and runs each one in isolation with a fresh test-instance and a defined lifecycle. On Android we mostly stick with JUnit 4 because the Android Gradle plugin and Robolectric integrate against it natively — JUnit 5 needs the vintage engine to bridge. The gotcha most people hit is that JUnit 4 creates a brand-new instance of the test class for every @Test, so you can't lean on instance state surviving between tests, and you wire shared cross-cutting behavior through @Rules instead of inheritance."

JUnit is the standard Java/Kotlin framework for running deterministic, isolated tests against a single unit of code — a class or a function.

How it works:

Test lifecycle (JUnit 4):
  @BeforeClass → @Before → @Test → @After → @AfterClass

Android projects historically use JUnit 4 (@RunWith(JUnit4::class)) because the Android Gradle plugin and Robolectric both integrate against it. JUnit 5 (Jupiter) requires an additional adapter — junit-vintage-engine — and is less common on Android, though adoptable.

Key annotations:

Annotation Purpose
@TestMarks a test method
@Before / @AfterSetup / teardown per test
@BeforeClass / @AfterClassOne-time setup per class
@IgnoreSkip a test with a reason
@RuleAttach JUnit rules (e.g., InstantTaskExecutorRule)
@RunWithChoose a test runner

Rules in Android:

  • InstantTaskExecutorRule — makes LiveData operations synchronous by swapping the background executor for an instant one. Essential for any ViewModel test that uses LiveData.
  • MainCoroutineTestRule — installs a TestCoroutineDispatcher or UnconfinedTestDispatcher as Dispatchers.Main. Required for any coroutine that runs on Main.
@RunWith(JUnit4::class)
class MyViewModelTest {

    @get:Rule val instantTaskRule = InstantTaskExecutorRule()
    @get:Rule val coroutineRule = MainCoroutineTestRule()

    // ...
}

Under the hood

A JUnit 4 runner (BlockJUnit4ClassRunner, the default behind @RunWith(JUnit4::class)) reflects over the class for @Test-annotated methods, builds a Description tree, and for each test constructs a new instance of the test class — that's why per-test isolation is automatic but instance fields reset every method. Each method is wrapped into a chain of Statement objects: the runner composes @Before/@After/@Rule as nested decorators around the actual invocation. A @Rule is really a TestRule.apply(Statement, Description) that returns a wrapping Statement, so rules execute outside @Before/@After — which is exactly why InstantTaskExecutorRule can install its executor before your setup runs and tear it down after.

RunRules( ruleN ... rule1,
  RunAfters(
    RunBefores(
      InvokeMethod(@Test)   ← fresh test instance
    , @Before methods)
  , @After methods))

Android implications:

  • Tests in /app/src/test/ run on the JVM — fast, no emulator needed.
  • Tests in /app/src/androidTest/ run on a device or emulator — slow, but gives you the full Android framework.
  • Prefer JVM tests wherever possible; push to instrumented only when you genuinely need real Android APIs.

Failure modes:

  • Forgetting InstantTaskExecutorRule means LiveData observers never fire and assertions fail silently — it's a common "why is my test always passing?" trap.
  • If @Before init throws with a Kotlin lateinit var, the test is skipped without a clear error message.

Test Doubles: Mock, Fake, Stub, Spy, Dummy

🎤 Say it out loud (~30–45s): "These are Meszaros's five categories of test doubles, and the distinction that matters is state versus behavior versus verification. A dummy just fills a parameter slot, a stub returns canned data so a code path can run, a fake is a real-but-simplified working implementation like an in-memory repo, and a mock is a stub that also records and verifies interactions. The nuance interviewers probe is that mock and spy are about verifying calls — they couple your test to how the code collaborates — whereas stubs and fakes only care about what comes back, so I reach for fakes when I want refactor-resistant tests."

These are Gerard Meszaros's canonical vocabulary. Interviewers love asking candidates to distinguish them precisely — knowing all five cold is a signal of real testing experience.

Double Definition Behavior State
DummyPassed but never usedNoneNone
StubReturns canned responsesFixed, pre-programmedNone
SpyWraps real object, records callsDelegates to real implPartial
MockPre-programmed with expectations; verifies callsDefined per testNone
FakeLightweight working implementationReal logic, simplifiedIn-memory

Dummy example:

// The function signature requires a Context but the code path under test never uses it.
val dummyContext: Context = mockk(relaxed = true)
sut.doSomethingThatIgnoresContext(dummyContext)

Stub example:

val stubRepo: UserRepository = mockk()
every { stubRepo.getUser(any()) } returns User(id = 1, name = "Alice")

Spy example:

val realLogger = AnalyticsLogger()
val spyLogger = spyk(realLogger)
sut.logEvent("tap")
verify { spyLogger.logEvent("tap") }  // verifies call happened on real object

Mock example (with verification):

val mockRepo: UserRepository = mockk()
every { mockRepo.saveUser(any()) } just Runs
sut.createAccount(email = "a@b.com")
verify(exactly = 1) { mockRepo.saveUser(match { it.email == "a@b.com" }) }

Fake example:

class FakeUserRepository : UserRepository {
    private val users = mutableListOf<User>()

    override suspend fun getUser(id: Int): User =
        users.find { it.id == id } ?: throw NoSuchElementException("User $id not found")

    override suspend fun saveUser(user: User) { users.add(user) }

    fun seedUser(user: User) { users.add(user) }
}

Under the hood

A mock object isn't your real class — it's a dynamically generated subclass/proxy whose every method is overridden to consult a recorded "answer" table instead of running real logic. Frameworks build these proxies at runtime via bytecode generation (ByteBuddy) and load them through an agent; the proxy's overridden method looks up a matcher → answer entry, records the invocation into a list for later verification, and returns the stubbed value (or a type-appropriate default). A spy is the same proxy but its default answer delegates to the real method via super/the wrapped instance. A fake, by contrast, involves none of this machinery — it's just a hand-written class implementing the interface, so calls are ordinary virtual dispatch with real fields and real control flow.

mock.getUser(1)
  → proxy.getUser(1)
      → invocationStore.record(getUser, [1])      // for verify()
      → answerTable.match(getUser, eq(1)) ?: default
fake.getUser(1)
  → ordinary method: users.find { it.id == 1 }    // no proxy, no recording

Fake vs Mock — Interview Deep Dive

🎤 Say it out loud (~30–45s): "My rule of thumb is fakes for domain logic, mocks for verifying side effects. A fake gives real behavior — an in-memory store that actually filters and sorts — so I can test collaboration without over-specifying, and it only breaks when the contract changes. A mock is best when I genuinely need to assert that a call happened, like an analytics event or a network write. The trap interviewers want you to name is that mocks couple tests to implementation: rename a method and every mocked test breaks even though behavior didn't, which is why over-mocking produces brittle, low-value tests."

The core question: "When do you use a fake over a mock?"

Use a Fake when:

  1. The real behavior is needed to validate complex interactions — for example, a repository that must correctly filter and sort.
  2. Multiple tests reuse the same double, because writing every { ... } for every combination gets tedious and error-prone fast.
  3. You want to test the collaboration between two classes where one drives the other's state.
  4. The interface is large — mocking every method becomes a maintenance burden.
  5. The dependency has internal state that matters, like an in-memory database.

Use a Mock when:

  1. You need to verify a specific call happened — interaction testing.
  2. The dependency is an external side-effectful system like analytics or the network.
  3. You want to control exactly what's returned without writing an entire implementation.
  4. The test only cares about one or two methods on the interface.

Trade-offs:

Criterion Fake Mock
MaintenanceHigh (keep in sync with interface)Low (change per test)
ReadabilitySelf-documenting behaviorVerbose every/coEvery setup
Over-specificationNone (tests behavior)Risk (tests implementation details)
Parallel test safetyCareful with shared stateSafe (fresh per test)
Refactoring resistanceHighLow (breaks on rename)

The key insight for interviews is that mocks couple tests to implementation details. If you rename a method, every mocked test that calls it breaks — even if the behavior is unchanged. Fakes only break when the contract itself changes. So the rule I follow is: use fakes for domain logic, use mocks for verifying side effects.

Under the hood

The brittleness difference is structural, not stylistic. A mock's stub/verify clauses are keyed on a method reference plus argument matchers captured at record time; the framework resolves that reference against the proxy's method table. Rename or re-signature the method and the matcher no longer binds to any invocation, so verification fails or the stub silently returns a default — the test breaks even though behavior is identical. A fake reaches the method only through normal virtual dispatch behind the interface, so as long as the interface contract holds, the compiler rewrites call sites automatically on a rename (it's still just a super/interface call in bytecode). That's the mechanical reason fakes are "refactoring-resistant": there's no out-of-band string/reference table that can drift out of sync with the code.

MockK — Android's Preferred Mocking Library

🎤 Say it out loud (~30–45s): "MockK is the Kotlin-first mocking library, and the reason we prefer it over Mockito on Android is that Kotlin classes and methods are final by default — MockK mocks them out of the box via a JVM agent and bytecode generation, whereas plain Mockito needs the inline extension to do the same. The non-negotiable gotcha is unmockkAll() in teardown: mockkStatic and mockkObject patch global classloader state, and because Gradle reuses the test-worker JVM across classes, a leaked static mock silently corrupts completely unrelated tests later in the run."

MockK is designed for Kotlin and handles final classes and methods natively. Mockito, by contrast, can't mock Kotlin finals without pulling in the mockito-inline extension, which adds friction. On Android, MockK is the default choice.

Setup:

@Before
fun setUp() {
    MockKAnnotations.init(this, relaxed = true)
}

@After
fun tearDown() {
    unmockkAll()  // MANDATORY — prevents mock leaks across test classes
}

Why unmockkAll() is non-negotiable:

  • MockK registers static and object mocks directly in the JVM classloader.
  • Without cleanup, every subsequent test class in the same JVM worker inherits that polluted state.
  • This is especially dangerous with mockkStatic and mockkObject — they mutate global singletons and can silently corrupt tests that run later.
  • In CI, the Gradle test worker JVM is reused across test classes, so leaked mocks accumulate and cause unpredictable failures in completely unrelated tests.

Core DSL:

// Annotations
@MockK lateinit var repo: UserRepository
@RelaxedMockK lateinit var analytics: AnalyticsService  // auto-returns defaults
@SpyK val logger = RealLogger()
@InjectMockKs lateinit var sut: UserViewModel

// Stubbing
every { repo.getUser(1) } returns User(1, "Alice")
every { repo.getUser(any()) } throws RuntimeException("Not found")
coEvery { repo.getUserAsync(1) } returns User(1, "Alice")  // for suspend funs

// Verification
verify { repo.getUser(1) }
verify(exactly = 2) { repo.getUser(any()) }
verify(inverse = true) { analytics.logError(any()) }  // assert NOT called
coVerify { repo.getUserAsync(1) }

// Capturing arguments
val slot = slot<User>()
coEvery { repo.saveUser(capture(slot)) } just Runs
sut.createAccount("alice@test.com")
assertEquals("alice@test.com", slot.captured.email)

// Static mocking
mockkStatic(Log::class)
every { Log.d(any(), any()) } returns 0
// ... test ...
unmockkStatic(Log::class)

// Object mocking
mockkObject(MyObject)
every { MyObject.getInstance() } returns fakeInstance

relaxed = true makes MockK automatically return empty, zero, null, or false for any call you haven't explicitly stubbed. It's good for dependencies that are invoked but whose return value isn't relevant to the test under examination.

Under the hood

The every { ... } block isn't a normal lambda — it runs in "recording" mode. MockK generates a proxy subclass with ByteBuddy, and when your lambda calls repo.getUser(1), the proxy is in a recording state where matchers like any()/eq(1) push onto a thread-local matcher stack; MockK reconstructs the call signature from that stack and binds it to the answer you supply after returns/throws/just Runs. At verify time it replays recorded invocations against those matchers. coEvery/coVerify exist because suspend functions compile to methods with an extra Continuation parameter — MockK intercepts that and drives the suspension inside a runBlocking-style harness so you write the stub as if it were synchronous. mockkStatic/mockkObject are the dangerous ones: they don't create a new object, they re-transform an already-loaded class in place (static method dispatch is patched, and Kotlin object singletons get their INSTANCE behavior redirected), which mutates global classloader/JVM state — exactly why unmockkAll() must reverse it before the next test class reuses the worker JVM.

every { repo.getUser(1) } returns u
  1. enter recording mode (thread-local)
  2. proxy.getUser(1): eq(1) pushed to matcher stack
  3. signature = getUser(eq(1))  → answerTable[signature] = StubAnswer(u)
verify { repo.getUser(1) } → replay invocationLog against matcher

Testing ViewModels

🎤 Say it out loud (~30–45s): "A ViewModel is pure presentation logic — state transformation, event routing, coordinating interactors — so I test it entirely on the JVM with constructor-injected fakes or mocks, never through ViewModelProvider. The two rules that make it deterministic are InstantTaskExecutorRule for LiveData and swapping Dispatchers.Main for a TestDispatcher. The subtle part interviewers chase is asserting the sequence of state emissions — loading then success or error — which means collecting the flow and controlling virtual time with advanceTimeBy/advanceUntilIdle rather than just reading .value at the end."

A ViewModel's job is presentation logic — state transformation, event routing, and coordinating interactors. That logic should be tested entirely on the JVM, with no Activity or emulator involved.

Setup requirements:

  1. InstantTaskExecutorRule — if you're using LiveData.
  2. MainCoroutineTestRule — replaces Dispatchers.Main with a test dispatcher.
  3. Inject all dependencies via constructor — never go through ViewModelProvider in tests.

Pattern:

@RunWith(JUnit4::class)
class UserProfileViewModelTest {

    @get:Rule val instantTaskRule = InstantTaskExecutorRule()
    @get:Rule val coroutineRule = MainCoroutineTestRule()

    @MockK private lateinit var getUserInteractor: GetUserInteractor
    @MockK private lateinit var analyticsLogger: AnalyticsLogger

    private lateinit var sut: UserProfileViewModel

    @Before
    fun setUp() {
        MockKAnnotations.init(this, relaxed = true)
        sut = UserProfileViewModel(getUserInteractor, analyticsLogger)
    }

    @After
    fun tearDown() {
        unmockkAll()
    }

    @Test
    fun `loading state is emitted before data arrives`() = runTest {
        coEvery { getUserInteractor(1) } coAnswers {
            delay(100)
            User(1, "Alice")
        }

        val states = mutableListOf<UiState>()
        val job = launch { sut.uiState.toList(states) }

        sut.loadUser(1)
        advanceTimeBy(50)
        assertTrue(states.last() is UiState.Loading)

        advanceUntilIdle()
        assertTrue(states.last() is UiState.Success)

        job.cancel()
    }

    @Test
    fun `error state is emitted when interactor throws`() = runTest {
        coEvery { getUserInteractor(any()) } throws IOException("Network error")

        sut.loadUser(1)
        advanceUntilIdle()

        val state = sut.uiState.value
        assertTrue(state is UiState.Error)
        assertEquals("Network error", (state as UiState.Error).message)
    }
}

What to assert on a ViewModel:

  • Initial state is correct.
  • Loading, success, and error transitions are emitted in the right order.
  • Side-effect events emitted via SharedFlow fire when expected.
  • Analytics or logging is called with the right arguments.
  • Launching the same action twice cancels the first job.

What NOT to test on a ViewModel:

  • The ViewModel doesn't own actual network or database calls — test those on the interactor.
  • Don't test Android framework concerns like the Activity lifecycle — that belongs in UI tests.

Under the hood

runTest installs a TestCoroutineScheduler backed by a StandardTestDispatcher whose work queue is keyed by virtual time, not wall-clock time. When a coroutine hits delay(100), the dispatcher doesn't sleep a real thread — it parks a resume callback at virtual-time 100 in the scheduler's priority queue. advanceTimeBy(50) and advanceUntilIdle() simply pop and run those callbacks up to the target virtual time, which is why a "100ms" delay tests instantly and deterministically. The MainCoroutineTestRule calls Dispatchers.setMain(testDispatcher) so any viewModelScope.launch (which defaults to Dispatchers.Main.immediate) lands on that same single-threaded scheduler — giving you a serial, reproducible execution order. Collecting the StateFlow/SharedFlow into a list in a child coroutine works because emissions are dispatched on that controlled scheduler too, so you observe every intermediate state rather than only the final conflated value.

runTest scheduler (virtual clock = 0)
  loadUser(1) → launch → enqueue(getUser) 
  getUser hits delay(100) → park resume @ t=100
  advanceTimeBy(50)  → clock=50, nothing due → state == Loading
  advanceUntilIdle() → clock jumps to 100 → resume → state == Success

Testing Use Cases (Interactors)

🎤 Say it out loud (~30–45s): "Interactors are the easiest thing in the codebase to test because they're single-responsibility — usually one operator fun invoke — so it's input in, output asserted, with a fake or mock for whatever they call. I lean on a fake repository here so I'm testing the real transformation and mapping logic rather than re-stating it in stubs. The cases I always cover are the happy path, an edge or empty case, and error propagation — making sure an exception from the repo bubbles through unchanged rather than getting swallowed."

Use cases are single-responsibility classes — typically an operator fun invoke. They're the easiest thing to test in the whole codebase: give them an input, check the output, and use a fake or mocked dependency for anything they call.

class GetUserInteractorTest {

    private val fakeRepo = FakeUserRepository()
    private val sut = GetUserInteractor(fakeRepo)

    @Test
    fun `returns user when found`() = runTest {
        fakeRepo.seedUser(User(id = 1, name = "Alice"))
        val result = sut(userId = 1)
        assertEquals("Alice", result.name)
    }

    @Test
    fun `throws when user not found`() = runTest {
        assertFailsWith<NoSuchElementException> {
            sut(userId = 99)
        }
    }
}

Canonical interactor tests:

  1. Happy path — the correct transformation is applied.
  2. Empty or edge case — empty list, zero value, null input.
  3. Error propagation — an exception from the repo bubbles through correctly.
  4. Mapping — a data-layer model maps correctly to the domain model.
  5. Caching behavior, if the interactor wraps a cache.

Under the hood

operator fun invoke is plain Kotlin sugar: the compiler emits a regular JVM method named invoke, and the call site sut(userId = 1) is compiled to sut.invoke(1) — there's no reflection or special dispatch, so an interactor is as cheap to call and test as any method. Because the function is suspend, the compiler applies the Continuation-Passing-Style transform: it gains a hidden Continuation parameter and the body becomes a state machine class whose invokeSuspend advances across suspension points. Inside runTest, that continuation is resumed on the test scheduler, so a suspending interactor completes synchronously in virtual time. Error propagation "just works" because a thrown exception is captured by the state machine and delivered through Continuation.resumeWith(Result.failure(e)), which rethrows at the awaiting call site — no special wrapping unless you explicitly catch it, which is exactly the behavior assertFailsWith relies on.

Testing Repositories

🎤 Say it out loud (~30–45s): "A repository sits between the network and the local cache, so when I unit-test it I fake both data sources and verify the orchestration logic — does it return the cache when it's warm, does it fall back to the network and write back on a miss. The thing an interviewer wants to hear is that I'm testing the policy, not the sources themselves; if I want to validate the real wire format or schema I'd swap in MockWebServer and an in-memory Room DB and call that an integration test instead."

Repositories orchestrate data sources — network plus local cache. The key is to substitute both ends: use a fake or mock for the remote source and a fake or mock for the local source. If you want a true integration test, swap those for a real MockWebServer and an in-memory Room database respectively.

Unit test approach (all mocked):

class UserRepositoryImplTest {

    @MockK private lateinit var remoteSource: UserRemoteDataSource
    @MockK private lateinit var localSource: UserLocalDataSource

Under the hood

MockK's relaxed = true mocks are generated at runtime via bytecode — MockK uses ByteBuddy to subclass the interface/class and route every call through a MockKStub that records invocations into a CallRecorder. A relaxed mock returns a type-appropriate zero value (0, false, empty collection, or a chained relaxed mock for non-primitive returns) unless you override with coEvery. coEvery/coVerify are the suspend-aware variants: under the hood the suspend function's hidden Continuation parameter (the result of Kotlin's CPS transform) is matched too, so MockK intercepts the call before it actually suspends. coVerify(inverse = true) replays the recorded invocation list and asserts the matcher found zero matches.

  └─ (remoteSource never invoked) → recorded-call list has 0 entries for fetchUser

Coroutine Testing

🎤 Say it out loud (~30–45s): "Coroutines are async, so naive tests are flaky — they depend on wall-clock timing. The fix is runTest, which runs the body on a TestScope backed by a virtual clock: delay doesn't actually wait, it just advances a scheduler, so a test with a five-second retry backoff finishes in microseconds. The big gotcha is the dispatcher choice — StandardTestDispatcher queues child coroutines so you must advanceUntilIdle(), whereas UnconfinedTestDispatcher runs them eagerly inline. And on the JVM you have to swap Dispatchers.Main with a test rule because the real Main needs Android's Looper, which doesn't exist off-device."

The core challenge with coroutine testing is that coroutines run asynchronously. Without explicit control over time and dispatchers, your tests become non-deterministic — they pass or fail depending on timing. The solution is a stack of test utilities that give you that control.

Solution stack:

Component Purpose

TestCoroutineDispatcher (deprecated)Old API for controlling dispatch
StandardTestDispatcherNew (1.6+): doesn't auto-advance; requires explicit advance
UnconfinedTestDispatcherEagerly executes coroutines inline; simpler but less control
advanceTimeBy(ms)Fast-forwards virtual clock

runTest block:

@Test
fun `delay is skipped in runTest`() = runTest {
    var result: String? = null
    launch {
        delay(5_000)  // Virtual time; completes instantly
        result = "done"
    }
    advanceUntilIdle()
    assertEquals("done", result)
}

runTest uses virtual time by default, so delay() calls don't actually wait — the test finishes as fast as the CPU can execute.

MainCoroutineTestRule:

class MainCoroutineTestRule(
    val dispatcher: TestDispatcher = UnconfinedTestDispatcher()
) : TestWatcher() {
    override fun starting(description: Description) {
        Dispatchers.setMain(dispatcher)
    }
    override fun finished(description: Description) {
        Dispatchers.resetMain()
    }
}

This ensures Dispatchers.Main is available on the JVM test runner — normally it isn't, because Dispatchers.Main requires Android's Looper, which doesn't exist on the JVM.

StandardTestDispatcher vs UnconfinedTestDispatcher:

// UnconfinedTestDispatcher: launches run eagerly in-line
@Test
fun unconfinedExample() = runTest(UnconfinedTestDispatcher()) {
    val results = mutableListOf<Int>()
    launch { results.add(1) }  // runs immediately
    launch { results.add(2) }  // runs immediately
    assertEquals(listOf(1, 2), results)  // passes without advanceUntilIdle()
}

// StandardTestDispatcher: launches are queued; must advance manually
@Test
fun standardExample() = runTest {  // StandardTestDispatcher by default
    val results = mutableListOf<Int>()
    launch { results.add(1) }  // queued, not yet run
    assertTrue(results.isEmpty())
    advanceUntilIdle()
    assertEquals(listOf(1), results)
}

When to use which:

  • UnconfinedTestDispatcher — simple cases where you don't care about interleaving order.
  • StandardTestDispatcher — when testing race conditions, ordering, or cancellation.

Testing withContext(Dispatchers.IO):

The right approach is to inject dispatchers so tests can substitute them:

class UserRepository(
    private val api: UserApi,
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {

Virtual time and delay:

@Test
fun `retries after delay`() = runTest {
    var callCount = 0
    coEvery { mockApi.fetchUser(1) } coAnswers {
        callCount++
        if (callCount < 3) throw IOException("Retry me")
        User(1, "Alice")
    }

    val result = sut.getUserWithRetry(1)  // internally delays 1s between retries

    advanceUntilIdle()  // skips all delays
    assertEquals("Alice", result.name)
    assertEquals(3, callCount)
}

Failure modes:

  • Using Thread.sleep() instead of delay() breaks virtual time — the test either hangs or becomes genuinely slow.
  • Calling blockingGet() (RxJava) inside a coroutine uses a CountDownLatch that coroutine cancellation cannot interrupt — the test hangs for 90+ minutes in CI.
  • Forgetting advanceUntilIdle() with StandardTestDispatcher means assertions run before the coroutines have completed.
  • Not cleaning up a CoroutineScope owned by the system under test leaves leaked coroutines that keep the Gradle worker JVM alive indefinitely.

Under the hood

Virtual time is implemented by TestCoroutineScheduler, which all test dispatchers share within a single runTest. There's no real clock — the scheduler keeps a priority queue of TestDispatchEvents keyed by a currentTime (a Long of virtual milliseconds). When a coroutine calls delay(5000), the dispatcher doesn't Thread.sleep; it schedules a resume event at currentTime + 5000 and suspends the continuation. advanceUntilIdle() repeatedly pops the earliest event, jumps currentTime to it, and resumes that continuation until the queue is empty. The Standard-vs-Unconfined difference is purely dispatch policy: StandardTestDispatcher always enqueues the resumed continuation (so launch bodies wait), while UnconfinedTestDispatcher overrides isDispatchNeeded to return false, resuming the continuation on the current call stack immediately. Dispatchers.setMain works because Dispatchers.Main is resolved lazily through a MainDispatcherFactory ServiceLoader; setMain swaps the delegate field so the Android-backed factory is bypassed entirely.

runTest body ──┐
               ├─ shares one TestCoroutineScheduler (virtual clock = Long ms)
launch {...} ──┘
delay(5000) → scheduler.registerEvent(at = currentTime + 5000); suspend
advanceUntilIdle() → while(queue not empty){ currentTime = peek.time; resume() }

Flow Testing

🎤 Say it out loud (~30–45s): "Flows are cold and lazy — nothing runs until a terminal operator collects them — so the first decision is whether the Flow is finite or infinite. For a finite Flow I just toList() it. For a StateFlow or any hot/infinite Flow I have to launch a collector in the background and cancel it, and I deliberately collect on an UnconfinedTestDispatcher so it starts eagerly while the test body keeps StandardTestDispatcher to drive the producer's timing. The classic trap is forgetting that StateFlow always replays its current value, so the first awaitItem is the initial state, not the update you triggered."

Flows are lazy — nothing happens until something collects them. That means testing a Flow requires an active coroutine scope, and you have to pick the right approach depending on whether the Flow is finite or infinite.

Approach 1: toList() — simplest, blocks until completion

@Test
fun `emits three values`() = runTest {
    val flow = flowOf(1, 2, 3)
    val result = flow.toList()
    assertEquals(listOf(1, 2, 3), result)
}

Approach 2: launch + collect — for StateFlow / infinite flows

@Test
fun `stateflow emits initial then updated state`() = runTest {
    val states = mutableListOf<UiState>()
    val collectJob = launch(UnconfinedTestDispatcher()) {
        sut.uiState.collect { states.add(it) }
    }

    assertEquals(UiState.Idle, states[0])
    sut.loadUser(1)
    advanceUntilIdle()
    assertEquals(UiState.Success(User(1, "Alice")), states[1])

    collectJob.cancel()
}

Why UnconfinedTestDispatcher for collection? With StandardTestDispatcher, collect is queued and never starts unless you call advanceUntilIdle(). Using UnconfinedTestDispatcher for the collector launch means it starts collecting eagerly, while the test body on StandardTestDispatcher can still control time precisely for the producer side. The two dispatchers work together.

Approach 3: Turbine (preferred for Flow testing) See next section.

Testing SharedFlow (events):

@Test
fun `navigation event emitted on successful login`() = runTest {
    coEvery { loginInteractor(any(), any()) } returns LoginResult.Success

    val events = mutableListOf<NavigationEvent>()
    val job = launch(UnconfinedTestDispatcher()) {
        sut.navigationEvents.collect { events.add(it) }
    }

    sut.login("user@test.com", "password")
    advanceUntilIdle()

    assertEquals(listOf(NavigationEvent.GoToHome), events)
    job.cancel()
}

Under the hood

A cold Flow is just a Flow object wrapping a suspend block; collect is what actually invokes the builder lambda, which is why nothing emits until collection — each collector re-runs the producer from scratch on its own. toList() is a terminal operator that suspends the calling coroutine until the upstream completes, appending each emit into a MutableList. StateFlow and SharedFlow are hot and implemented differently: internally StateFlowImpl holds a single volatile _state slot plus an array of slot objects, one per collector, and uses a conflated emission strategy — a new collector immediately gets the current value (replay = 1), and intermediate values can be dropped under back-pressure. That conflation is exactly why a StateFlow test sees the latest state but not necessarily every transition, and why the first awaitItem/index [0] is always the seeded initial value. SharedFlow instead keeps a replay buffer and emission counters and never signals completion, so a collector on it suspends forever waiting for the next slot to fill.

StateFlowImpl
  _state : volatile Any?      ← single conflated slot (replay = 1)
  slots[]: per-collector resume handles
  emit(x): if (x != _state) { _state = x; resume each waiting slot }
  new collector → immediately handed current _state, then awaits next change

Turbine

🎤 Say it out loud (~30–45s): "Turbine is Cash App's Flow-testing DSL — its test {} block launches the collector for me and gives me awaitItem, awaitComplete, and awaitError so I can interleave emissions and assertions linearly instead of doing a collect-then-assert two-phase dance. The reason I reach for it over hand-rolled collection is that awaitItem has a built-in timeout, so a hung Flow fails fast instead of spinning forever, and there's no job.cancel() I can forget. The one gotcha: SharedFlow never completes, so I end with cancelAndIgnoreRemainingEvents() — calling awaitComplete() on it would hang."

Turbine is a testing library by Cash App that wraps Flow collection in a clean DSL. It eliminates all the boilerplate of manually launch-ing a collector, converting to a list, and remembering to cancel the job.

Testing multiple concurrent Flows with Turbine:

@Test
fun `multiple flows`() = runTest {
    turbineScope {
        val flowA = flowOf("a1", "a2").testIn(backgroundScope)
        val flowB = flowOf("b1").testIn(backgroundScope)

        assertEquals("a1", flowA.awaitItem())
        assertEquals("b1", flowB.awaitItem())
        assertEquals("a2", flowA.awaitItem())
        flowA.awaitComplete()
        flowB.awaitComplete()
    }
}

Why Turbine over manual collection: There are four reasons. First, awaitItem() has an automatic timeout — it fails fast if the Flow hangs rather than letting the test spin forever. Second, there's no job.cancel() you can forget. Third, expectNoEvents() is impossible to express cleanly with toList(). And fourth, interleaving emissions and assertions inside a single test {} block reads much more naturally than a separate collect phase followed by a separate assert phase.

Turbine + SharedFlow gotcha: SharedFlow has no completion event. Always end with cancelAndIgnoreRemainingEvents() rather than awaitComplete(), or the test will hang waiting for a termination that never comes.

Under the hood

test {} launches a collecting coroutine that funnels every signal — items, completion, and errors — into an unbounded Channel<Event>. Each awaitItem() is a suspending channel.receive() wrapped in withTimeout (default 3s via turbineTimeout); if the timeout elapses with no event, Turbine throws an AssertionError rather than hanging, which is the fail-fast property. Completion and exceptions are sent as distinct Event.Complete / Event.Error sentinels, so awaitItem() can detect "Flow finished when I expected a value" and fail with a clear message. turbineScope + testIn(backgroundScope) launch each collector into a child scope tied to the test; on block exit Turbine cancels those collectors and, unless you consumed everything, asserts no unconsumed events remain — that "unconsumed events" check is what catches accidentally-dropped emissions.

flow.test { } ──launch──► collector coroutine
   onEach emit  → channel.send(Event.Item(value))
   onCompletion → channel.send(Event.Complete | Event.Error)
awaitItem() = withTimeout(3s) { channel.receive() }   // sentinel → AssertionError
block end   → cancel collector + assert channel drained

What Should Be Unit Tested?

🎤 Say it out loud (~30–45s): "I unit-test the things that are pure logic and fast — ViewModels, use cases, mappers, repository cache policy, validators — because they run in milliseconds on the JVM with no device. I deliberately don't unit-test framework behavior like View inflation, lifecycle transitions, Room schema, or wire format; those need instrumentation, an in-memory database, or MockWebServer respectively. My mental checklist is FIRST: fast, isolated, repeatable, self-validating, and timely — if a 'unit' test needs a device or shared state, it's miscategorized."

Good candidates:

  • ViewModels — state transitions, event routing, error handling.
  • Use cases / Interactors — business logic, input validation, data transformation.
  • Mappers — conversions between data-layer, domain, and UI models.
  • Repositories — cache strategy, network fallback, error propagation.
  • Utility functions — formatters, validators, parsers.
  • Extension functions that contain logic.

Poor candidates (push these to integration or UI tests):

  • XML inflation and View measurement.
  • Activity and Fragment lifecycle transitions.
  • Database schema correctness — that needs Room's in-memory database.
  • Network wire format — that needs MockWebServer.
  • Animations and transitions.

The FIRST principles — good tests are:

  • Fast — unit tests should complete in milliseconds.
  • Isolated — no shared state between tests.
  • Repeatable — same result on every run, every machine.
  • Self-validating — explicit pass or fail, no manual inspection.
  • Timely — written alongside or before the code they cover.

Under the hood

The fast/slow split is a real runtime distinction, not a stylistic one. JVM unit tests run under the testDebugUnitTest task on your host JVM via JUnit's BlockJUnit4ClassRunner, which reflectively instantiates the test class and invokes each @Test method — no dex, no APK, no device. By default Android framework classes are stubbed to throw RuntimeException("Method ... not mocked") (the android.jar "mockable" stub), which is exactly why touching real Views or Looper fails off-device. Instrumentation tests instead compile a separate test APK, install both it and the app via adb, and run inside the app's own ART process under AndroidJUnitRunner, so they pay dexing, install, and boot costs — typically seconds-to-minutes versus milliseconds. Room's in-memory database (Room.inMemoryDatabaseBuilder) and MockWebServer exist precisely to give the database and network slices a real implementation without the rest of the device.

JVM unit test  : Gradle → testDebugUnitTest → host JVM (android.jar stubs) → ms
instrumentation: Gradle → assemble test APK → adb install → ART on device   → s–min
                 (AndroidJUnitRunner drives @Test inside the app process)

Espresso

🎤 Say it out loud (~30–45s): "Espresso is Google's instrumentation framework for driving real Views on a device or emulator, and its whole model is match-a-view, perform-an-action, check-an-assertion. The reason it's more reliable than Thread.sleep is that it auto-synchronizes — before each interaction it waits for the main thread's message queue to go idle, so it acts only when the UI is settled. The catch every interviewer probes: it only knows about the main thread and explicitly registered Idling Resources, so anything on a background thread or a custom executor is invisible and you get flaky races unless you wire up an IdlingResource."

Espresso is Google's instrumentation testing framework for interacting with Android Views. It runs on-device or on an emulator — not on the JVM.

How it works: Every test follows a three-step pattern.

  1. Find a View using a ViewMatcher.
  2. Perform an action on it using a ViewAction.
  3. Assert its state with a ViewAssertion.
@Test
fun loginButtonSavesCredentials() {
    onView(withId(R.id.email_field))

    onView(withId(R.id.password_field))
        .perform(typeText("secret"), closeSoftKeyboard())

    onView(withId(R.id.login_button))
        .perform(click())

    onView(withId(R.id.welcome_message))
        .check(matches(isDisplayed()))
        .check(matches(withText(containsString("Welcome"))))
}

Under the hood

Espresso's synchronization is built on UiController plus a set of IdlingResources polled through an IdlingRegistry. onView(...).perform(...) doesn't run immediately; it posts the action to the main thread and first loops loopMainThreadUntilIdle(), which drains the MessageQueue and blocks while the queue's IdleHandler reports work pending. Out of the box Espresso registers resources for the main Looper's message queue and for AsyncTask's thread pools, which is why it can't see arbitrary background work — a raw Thread, a custom Executor, OkHttp's dispatcher, or a coroutine on Dispatchers.IO never touches those queues, so Espresso believes the app is idle and proceeds early, causing flakiness. A ViewMatcher is a Hamcrest Matcher<View> evaluated by walking the view hierarchy from the root via ViewFinder, throwing NoMatchingViewException/AmbiguousViewMatcherException on 0 or >1 matches. The fix for invisible async work is registering a custom IdlingResource whose isIdleNow() returns false until the work completes, which re-couples that work to Espresso's idle loop.

perform(click())
  └─ loopMainThreadUntilIdle():
        while (mainQueue not idle || any IdlingResource.isIdleNow()==false)
            pump messages / wait
  └─ then inject the click MotionEvents
(background thread work not on main queue & not an IdlingResource → invisible)

Android implications:

  • Requires a real device or emulator — roughly 10× slower than unit tests.
  • Espresso auto-synchronizes with the main thread: it waits for the message queue to drain before executing the next action. That's what makes it more stable than raw Thread.sleep approaches. The catch is it only understands the main thread and explicitly registered Idling Resources — anything on a background thread is invisible to it.

Idling Resources

🎤 Say it out loud (~30–45s): "Espresso auto-syncs with the main thread's message queue, but it has no idea about work happening off that thread — a network call, a coroutine, an Rx chain. So it fires the next action before the data lands and the test flakes. An IdlingResource is the bridge: it tells Espresso 'I'm busy' and only reports idle once that background work completes, so Espresso parks until then. The nuance is that registering one is increasingly unnecessary — fully Compose UIs sync via the compose clock, and with MockWebServer the latency is deterministic, so I reach for idling resources mainly with legacy Views doing real async."

Espresso synchronizes with the main thread, but async operations — network calls, coroutines, RxJava chains — run on background threads. Without help, Espresso proceeds before those operations finish, producing flaky tests. The solution is to register an IdlingResource that signals "the app is idle" only when all background work is done.

class CountingIdlingResource(name: String) : IdlingResource {
    private val counter = AtomicInteger(0)
    private val name = name
    private var callback: IdlingResource.ResourceCallback? = null

    fun increment() { counter.incrementAndGet() }

    fun decrement() {
        val count = counter.decrementAndGet()
        if (count == 0) callback?.onTransitionToIdle()
    }

    override fun getName() = name
    override fun isIdleNow() = counter.get() == 0
    override fun registerIdleTransitionCallback(cb: IdlingResource.ResourceCallback) {
        callback = cb
    }
}

// Usage in test:
@Before
fun registerIdlingResource() {
    IdlingRegistry.getInstance().register(myIdlingResource)
}

@After
fun unregisterIdlingResource() {
    IdlingRegistry.getInstance().unregister(myIdlingResource)
}

Under the hood

Espresso's UiController.loopMainThreadUntilIdle() doesn't sleep — it drains the main thread Looper's MessageQueue and then checks two things: that the queue has no immediately-runnable messages, and that every registered IdlingResource reports isIdleNow() == true. The IdlingResourceRegistry polls resources and also listens for the onTransitionToIdle() callback so it can re-check without spinning. Crucially, idling state is sampled between UI events, not continuously — so a resource that flickers busy→idle→busy in a single drain can let Espresso slip through, which is the classic source of residual flakiness with hand-rolled counters.

performClick()
  └► UiController.loopMainThreadUntilIdle()
        ├─ drain MessageQueue (run due messages)
        ├─ all IdlingResources.isIdleNow()?  ── no ─┐
        │                                            │ park, await onTransitionToIdle()
        └─ yes ► proceed to next action  ◄───────────┘

The OkHttp idling resource simply wires the Dispatcher's runningCallsCount() to isIdleNow(), so Espresso treats "in-flight HTTP calls > 0" as busy.

ActivityScenario

🎤 Say it out loud (~30–45s): "ActivityScenario is the AndroidX replacement for the old ActivityTestRule. It launches an Activity, lets me drive it through arbitrary lifecycle states, and hands me the instance safely on the main thread via onActivity. It implements Closeable, so I close it or wrap it in use { } to guarantee teardown. The subtlety interviewers probe is the threading rule: the onActivity block runs on the main thread, so I never touch the Activity directly from the test thread, and I copy out anything I need rather than leaking the reference."

ActivityScenario is Jetpack Test's replacement for the old ActivityTestRule. It launches an Activity and gives you fine-grained lifecycle control without coupling your test class to the test runner.

@Test
fun activityDisplaysUserName() {
    val scenario = ActivityScenario.launch(UserProfileActivity::class.java)

    scenario.onActivity { activity ->
        // Access Activity on main thread
        assertNotNull(activity.binding.nameTextView)
    }

    onView(withId(R.id.name_text_view))
        .check(matches(withText("Alice")))

    scenario.close()  // triggers onDestroy
}

Passing extras:

    .putExtra("USER_ID", 1)

Lifecycle control:

scenario.moveToState(Lifecycle.State.CREATED)   // onCreate called, not started
scenario.moveToState(Lifecycle.State.STARTED)   // onStart called
scenario.moveToState(Lifecycle.State.RESUMED)   // onResume called (default)
scenario.recreate()                              // simulate rotation

Under the hood

ActivityScenario drives lifecycle through real framework plumbing, not reflection hacks. It registers an ActivityLifecycleCallbacks monitor on the Application (via Instrumentation.ActivityMonitor) so it can observe the true Stage (CREATED/STARTED/RESUMED/etc.) of the launched Activity. moveToState posts an InstrumentationActivityInvoker command to the main thread that issues the actual lifecycle transitions — and it works synchronously, blocking the test thread on a latch until the target stage is reached. recreate() invokes Activity.recreate(), the same path a configuration change uses, so it genuinely tears down and rebuilds the instance including saved-state restoration.

test thread                          main thread
   │ moveToState(RESUMED)
   ├─ post command ───────────────►  invoker drives onStart→onResume
   │ await CountDownLatch            ActivityLifecycleCallbacks fires
   ◄──────────────────────────────  latch.countDown() at Stage.RESUMED
   │ continue

onActivity { } posts its ActivityAction onto the main Looper and blocks until it returns — that's why the block sees a consistent Activity and why you must not stash the reference for use back on the test thread.

ActivityScenario.launch vs launchActivity:

  • launch returns an ActivityScenario<T> for direct lifecycle control.
  • Use it with a use { } block for automatic close: ActivityScenario.launch<MyActivity>(...).use { scenario -> ... }.

🎤 Say it out loud (~30–45s): "FragmentScenario does for Fragments what ActivityScenario does for Activities — it spins up a Fragment in isolation without needing the host Activity that normally owns it. launchFragmentInContainer adds it to a real container view so I can run Espresso assertions, while launchFragment hosts it headlessly. The catch is the theme: the empty host Activity has no theme, so if my Fragment relies on theme attributes I have to pass themeResId, otherwise it crashes or renders wrong. FragmentScenario is built on top of ActivityScenario: it launches an empty, themeless host Activity (EmptyFragmentActivity / EmptyFragmentActivityWithLayout) and then uses that Activity's real FragmentManager to perform a transaction that adds your Fragment — via a supplied FragmentFactory so constructor-injected Fragments work. Screenshot Testing

🎤 Say it out loud (~30–45s): "Screenshot testing renders UI and diffs it pixel-by-pixel against a committed golden image, so unintended visual regressions — a stray padding, a wrong color token, a font change — fail the build. On Android I lean toward Paparazzi or Roborazzi because they render on the JVM via LayoutLib or Robolectric, so they're fast and need no emulator in CI. The trade-off the interviewer will push on: JVM rendering isn't pixel-identical to a real device — font metrics and shadow rounding drift — and goldens are binary blobs that bloat PRs, so I scope them to stable design-system components, not content-heavy screens."

Screenshot testing catches unintentional visual regressions by rendering UI and comparing the output pixel-by-pixel against a committed golden baseline image. If anything changes — a color, a padding value, a font — the test fails.

Options for Android:

  1. Paparazzi (Cash App) — renders Compose/Views on the JVM without an emulator using

LayoutLib. Fast, runs in CI without device.

  1. Roborazzi — screenshot tests using Robolectric on JVM.
  2. Shot (Karumi) — device-based screenshot comparisons via instrumentation.
  3. Percy / Browserstack — cloud-based visual diffing.

Paparazzi example:

@get:Rule
val paparazzi = Paparazzi(
    deviceConfig = DeviceConfig.PIXEL_5,
    theme = "Theme.MyApp"
)

@Test
fun userCardLooksCorrect() {
    paparazzi.snapshot {
        UserCard(
            user = User(id = 1, name = "Alice", avatarUrl = null),
            onClick = {}
        )
    }
}

Workflow:

  1. First run: ./gradlew recordPaparazziDebug → creates golden images.
  2. Future runs: ./gradlew verifyPaparazziDebug → fails if diff exceeds threshold.
  3. On intentional changes: re-record.

Under the hood

Paparazzi runs the actual Android framework's UI toolkit on the JVM by loading LayoutLib — the same rendering engine Android Studio's layout preview uses — which is a repackaged layoutlib.jar plus native font/graphics libraries (libandroid_runtime-equivalents). It bootstraps a fake Resources/AssetManager from your merged resources and a stub Context, measures and lays out the view (or composes the tree into a View via ComposeView), then draws into an in-memory BufferedImage and PNG-encodes it. Verification decodes the golden PNG and computes a per-pixel delta against a configurable threshold. Roborazzi differs by using Robolectric's shadow framework and the real ART-on-JVM Robolectric environment, capturing from the Robolectric-rendered canvas instead of LayoutLib.

snapshot { UserCard(...) }
  ├─ LayoutLib: inflate fonts/resources → measure → layout
  ├─ draw to Bitmap/BufferedImage (software canvas, no GPU)
  └─ verify: |goldenPixels − renderedPixels| > threshold ? FAIL

The reason device and JVM renders diverge is subpixel: software (no-GPU) rasterization, host vs device freetype font hinting, and shadow/elevation blur math are not bit-identical — hence the diff threshold rather than exact match.

Trade-offs:

  • JVM rendering can differ subtly from a real device — font metrics and shadow rounding in particular can diverge.
  • Golden images live in the repo and must be updated intentionally when a visual change is intentional — PR diffs with image files are large.
  • Most useful for design-system components that should be visually stable; less useful for data-driven screens that change content often.

Accessibility Testing

🎤 Say it out loud (~30–45s): "Accessibility testing verifies that TalkBack, Switch Access, and large-text users can actually use the app — missing content descriptions, low contrast, and undersized touch targets are real bugs. In Espresso I enable Google's Accessibility Test Framework so any action automatically throws if the element fails a check; in Compose I assert on semantics like assertHasClickAction and assertContentDescriptionEquals. The nuance is that automated checks catch only the mechanical stuff — minimum 48dp targets, 4.5:1 contrast, presence of a label — they can't judge whether a screen is actually navigable or labeled meaningfully, so I still do a manual TalkBack pass."

Accessibility is not optional. TalkBack, Switch Access, and large-text users depend on correct semantics — broken content descriptions and undersized touch targets are real bugs, not nice-to-haves.

Espresso Accessibility Checks (Google's Accessibility Test Framework):

@Before

    AccessibilityChecks.enable().setRunChecksFromRootView(true)
}

Once enabled, Espresso throws AccessibilityViewCheckException if any action — like click() — is performed on an element that fails a check: missing content description, contrast ratio too low, or touch target too small.

Compose accessibility:

    .assertHasClickAction()
    .assertContentDescriptionEquals("Add new item")

Manual checks:

  • Every icon-only button must have a contentDescription.
  • Touch targets must be at least 48×48 dp.
  • Text contrast must be at least 4.5:1 — that's the WCAG AA threshold.
  • Interactive elements must have a semantic role like button, checkbox, and so on.

TalkBack testing: Run the app with TalkBack enabled and navigate entirely by swipe. Every screen must be fully navigable without vision.

Under the hood

The Accessibility Test Framework (ATF) runs a set of AccessibilityHierarchyCheck rules against a snapshot of the accessibility hierarchy — for Views it reads the AccessibilityNodeInfo tree (the same data the framework hands to TalkBack), and for contrast it actually samples the rendered bitmap to compute the luminance ratio. When you call AccessibilityChecks.enable(), Espresso installs a ViewAssertion-style hook into its ViewActions pipeline so every action captures the hierarchy and runs the checks, throwing AccessibilityViewCheckException with the failing AccessibilityCheckResults. In Compose, the equivalent assertions read the SemanticsNode properties (OnClick, ContentDescription, Role) — and Compose's own accessibility bridge translates those same semantics into AccessibilityNodeInfo for TalkBack at runtime, so testing the semantics tree is testing what assistive tech will see.

TalkBack / Switch Access
        ▲  AccessibilityNodeInfo tree
        │
   ┌────┴──────────────┐
   View hierarchy   Compose SemanticsNode tree
   (createAccessibilityNodeInfo)   (AndroidComposeViewAccessibilityDelegate)
        ▲                    ▲
        └── ATF checks ──────┘   contrast = sample bitmap luminance ratio

The reason automated checks are necessary-but-not-sufficient: ATF can verify a label exists and meets size/contrast minimums, but it cannot evaluate whether the label is correct or whether focus order is sensible — those require the manual TalkBack pass.

Flaky Tests

🎤 Say it out loud (~30–45s): "A flaky test passes sometimes and fails other times with no code change — and the root cause is always non-determinism leaking in: timing, async work that isn't synchronized, shared state from a prior test, or wall-clock and random seeds. The biggest gotcha interviewers probe is the retry instinct — retries and @FlakyTest hide the symptom, they don't fix it. I treat a flake as a real bug: reproduce it by looping the test 50 times, find the unsynchronized async or the leaked singleton, and fix the determinism rather than quarantining it forever."

A flaky test is one that produces different results — passing sometimes, failing other times — on different runs with no code changes. The root cause is always some form of non-determinism leaking into the test.

Root causes in Android UI tests:

Cause Mechanism
Timing / animationTest proceeds before animation completes
Async operationsBackground work not synchronized with Espresso
Order-dependent stateShared state from a previous test bleeds over
Emulator instabilityLow memory, GPU rendering differences
Network callsReal network in test → latency variability
Date/timeTests that depend on Date.now() or wall clock
Random seedsNon-deterministic ordering in collections

Reducing flakiness: There are eight concrete tactics.

  1. Disable animations in test runner:
   // In test setup:
   val instrumentation = InstrumentationRegistry.getInstrumentation()
   val uiDevice = UiDevice.getInstance(instrumentation)
   uiDevice.executeShellCommand("settings put global animator_duration_scale 0")
   uiDevice.executeShellCommand("settings put global transition_animation_scale 0")
   uiDevice.executeShellCommand("settings put global window_animation_scale 0")

Or via adb shell settings put global animator_duration_scale 0 in CI setup.

  1. Use Idling Resources for async operations (see above).
  1. Mock all network calls — never make real network requests in instrumented tests.

Use MockWebServer or a fake backend.

  1. Isolate test data — each test creates its own data; tests do not share Room databases

or SharedPreferences. ``kotlin @Before fun setUp() { db = Room.inMemoryDatabaseBuilder(...).build() } @After fun tearDown() { db.close() } ``

  1. Use ActivityScenario over ActivityTestRule — ActivityTestRule launches before @Before runs, which creates timing issues.
  1. Inject clocks — inject a Clock or TimeProvider so tests can control time:
   class FakeClock(var now: Long = 0L) : Clock {
       override fun currentTimeMillis() = now
   }
  1. Retry on CI conservatively — @FlakyTest(bugId = ...) and test-runner retry logic are a workaround, not a fix. Always investigate the root cause and never leave a quarantined test indefinitely.
  1. Compose-specific: awaitIdle() — after performing an action, call composeRule.awaitIdle() before asserting to let recomposition settle.

Debugging flaky tests:

  • Run the test 50 times locally: ./gradlew connectedAndroidTest --tests "*.MyFlaky*" -Pandroid.testInstrumentationRunnerArguments.repeat=50
  • Add logging at each step to identify which specific assertion is flaking.
  • Check for static singletons that aren't reset between tests — those are a common source of cross-test contamination.

Under the hood

Most UI-test flakiness traces back to how Espresso synchronizes with the app. Espresso doesn't sleep; before each perform/check it calls Looper.myQueue().isIdle() on the main thread and blocks until the MessageQueue has no due messages, the AsyncTask thread pool is idle, and every registered IdlingResource reports isIdleNow() == true. Work that escapes those three signals — a raw background thread, an OkHttp dispatcher thread, or a coroutine on Dispatchers.IO — is invisible to Espresso, so the assertion races the result. That's the structural origin of "async not synchronized."

Espresso UiController loop (simplified):
  loopMainThreadUntilIdle():
    while (!queueIsEmpty || !allIdlingResourcesIdle || !asyncPoolIdle):
        process next main-thread Message
  -> only THEN run the ViewAction / ViewAssertion

Animations are a second source: a 0→1 interpolator posts frames via Choreographer, so the view's final bounds aren't settled when Espresso reads them. Setting the three *_animation_scale globals to 0 makes the platform skip the animator entirely rather than fast-forward it. Order-dependence comes from JVM reuse — instrumentation runs all tests in one process, so a static/object field or an un-reset Dispatcher carries state across tests; JUnit also doesn't guarantee method order unless you set @FixMethodOrder, which is why hidden coupling surfaces randomly.

Espresso vs Compose Testing

🎤 Say it out loud (~30–45s): "Both run on a device and both auto-synchronize, but they look at different trees. Espresso matches against the Android View hierarchy with ViewMatchers, while Compose has no Views — it asserts against the semantics tree using SemanticsMatchers. The nuance I call out is that Compose's test rule ties its idle-waiting to the same clock that drives recomposition, so it knows when the UI has settled in a way Espresso can't for arbitrary async. On a mixed screen I use createAndroidComposeRule so onView and onNode work in the same test."

When to use Compose testing over Espresso:

  • Any screen built with Compose — don't use Espresso for those.
  • When you want to test a single composable in isolation without launching a full Activity.
  • When you need fine-grained semantic assertions.

Mixed screens (Views + Compose): Use both frameworks in the same test — onView() for the View parts, composeRule.onNode() for the Compose parts. createAndroidComposeRule<Activity>() supports both in one test class.

Under the hood

The two frameworks find elements through completely different data structures. Espresso walks the live View tree returned by getRootView(), applying Matcher<View> predicates against fields like getText() and getContentDescription(). Compose has no Views to walk — instead each composable that calls Modifier.semantics { } (or a higher-level component that does) contributes a SemanticsNode to a merged/unmerged SemanticsTree, a parallel structure built specifically for accessibility and testing. onNodeWithText runs a SemanticsMatcher over SemanticsProperties (e.g. Text, Role, OnClick), not over any rendered pixels.

Espresso:  View tree  --ViewMatcher-->  matched View   --> perform/check
Compose:   Composition --produces-->  SemanticsTree
                                   --SemanticsMatcher--> SemanticsNode --> action/assert

Synchronization also differs. Compose's ComposeTestRule swaps in a TestMonotonicFrameClock and pauses the automatic frame clock, so waitForIdle()/awaitIdle() deterministically drain pending recompositions, layout, and LaunchedEffect work driven by that clock — there's no separate IdlingResource registry. With createAndroidComposeRule, the underlying AndroidComposeView is just another View in Espresso's hierarchy, which is why the two query mechanisms coexist in one process and one test.

What Not to Test in UI Tests

🎤 Say it out loud (~30–45s): "UI tests are the slowest, most expensive, and most brittle layer, so I keep them thin: they verify wiring and the critical happy/error paths, not logic. Business rules, exhaustive state permutations, and AB-variant selection belong in fast ViewModel and interactor unit tests. The thing I'm careful about is not re-testing the platform or third-party SDKs — I don't write a UI test that Retrofit parses JSON or that the back button works; that's framework behavior, and asserting on it just buys flakiness with no confidence."
  1. Business logic — that belongs in ViewModel and interactor unit tests. UI tests are expensive; don't replicate your unit test coverage at the UI layer.
  2. All permutations of state — test the happy path and the critical error paths; exhaustive combinatorial state testing belongs in unit tests.
  3. Platform behavior — the back button, system dialogs, keyboard behavior. These are Android framework concerns, not your app's behavior.
  4. Specific layout metrics — pixel-perfect positioning is fragile across devices. Test that content is visible, not that it's at exactly pixel (320, 480).
  5. Third-party SDKs — don't test that Retrofit parses JSON correctly. That's not your code.
  6. Animations themselves — disable them for test stability and test that the end state is correct.
  7. A/B test variants exhaustively — pick the most critical variant; the variant selection logic belongs in unit tests.

Under the hood

The cost asymmetry is mechanical, not philosophical. A UI test boots the full instrumentation process: it installs two APKs (app + test), spins up an ActivityThread, inflates the real view tree or runs a full Compose composition, and drives everything through Instrumentation IPC to the device — startup and teardown alone dominate. A JVM unit test for the same logic instantiates one class and runs in milliseconds with no Binder, no Looper, no rendering. So each assertion you push up to the UI layer multiplies real wall-clock and exposes you to every device-level non-determinism (GPU rendering, IPC timing, system dialogs racing your activity).

Unit test:  new ViewModel() -> call method -> assert            ~ms, in-process
UI test:    install APKs -> ActivityThread -> inflate/compose
            -> Instrumentation IPC -> assert on device tree      ~seconds–minutes

Testing platform behavior is wasteful for the same reason it's flaky: the back button, IME, and system dialogs are implemented in system_server/the framework and dispatched over Binder, so you're exercising AOSP code you don't own and can't make deterministic. Third-party SDK internals (Retrofit's converter, an analytics SDK's batching) are likewise already covered by their own suites — your contract is the boundary, which a fast fake or a unit-level verification can pin down without paying the instrumentation tax.

Repository Integration Tests

🎤 Say it out loud (~30–45s): "A repository integration test wires the real collaborators together but stubs the edges of the system — a real Room in-memory DB, MockWebServer for the network, and zero mocked business logic — so I exercise the full data path: parse the response, map it, persist it, and read it back. The value over unit tests is that it catches the seams unit tests mock away, like a wrong column mapping or a serialization mismatch. The gotcha I watch is teardown — I must shutdown() MockWebServer and close() the DB in @After, or the dispatcher thread and the in-memory DB leak across tests in the reused JVM."

Integration tests wire real components together but substitute external dependencies like the network and hardware. For a repository, the concrete recipe is: a real Room in-memory database, MockWebServer for the network layer, and no mocked business logic. The result is a test that exercises the full data path through real code.

@RunWith(JUnit4::class)
class UserRepositoryIntegrationTest {

    private lateinit var db: AppDatabase
    private lateinit var mockWebServer: MockWebServer
    private lateinit var sut: UserRepositoryImpl

    @Before
    fun setUp() {
        db = Room.inMemoryDatabaseBuilder(
            ApplicationProvider.getApplicationContext(),
            AppDatabase::class.java
        ).allowMainThreadQueries().build()

        mockWebServer = MockWebServer()
        mockWebServer.start()

        val retrofit = Retrofit.Builder()
            .baseUrl(mockWebServer.url("/"))
            .addConverterFactory(GsonConverterFactory.create())
            .build()

        sut = UserRepositoryImpl(
            remoteSource = retrofit.create(UserApi::class.java),
            localSource = db.userDao()
        )
    }

    @After
    fun tearDown() {
        db.close()
        mockWebServer.shutdown()
    }

    @Test
    fun `fetches from network and persists to database`() = runTest {
        mockWebServer.enqueue(
            MockResponse()
                .setResponseCode(200)
                .setBody("""{"id":1,"name":"Alice","email":"alice@test.com"}""")
        )

        val user = sut.getUser(1)

        assertEquals("Alice", user.name)
        assertEquals("Alice", db.userDao().getUser(1)?.name)  // verify persisted
    }
}

Under the hood

MockWebServer isn't a mock object — it's a real HTTP server. On start() it binds an actual ServerSocket on localhost:0 (the OS assigns a free port), and url("/") returns that loopback address. When the test points Retrofit at it, OkHttp opens a genuine TCP socket and writes a real HTTP/1.1 (or HTTP/2) request; the server pulls the next queued MockResponse off an internal BlockingQueue (FIFO, set via enqueue) and writes real response bytes back. So the path under test includes OkHttp's connection pool, the converter factory, and Gson actually parsing the JSON — the only thing faked is what's on the wire.

sut.getUser(1)
  -> Retrofit proxy -> OkHttp -> TCP socket -> 127.0.0.1:<port>
       MockWebServer dequeues MockResponse (FIFO) -> writes real bytes
  -> GsonConverterFactory deserializes -> UserEntity
  -> Room DAO INSERT into in-memory SQLite -> SELECT verifies

This is also why ordering and teardown matter: responses are consumed in enqueue order regardless of which endpoint is called, so a mismatched count silently feeds the wrong body to the wrong call. And because start() leaves an accept thread parked on the socket, skipping shutdown() leaks both the thread and the port across the reused test JVM.

Database Tests (Room)

🎤 Say it out loud (~30–45s): "Room DAO tests run against a real in-memory SQLite database, which is fast and self-cleaning since it vanishes on close. The catch interviewers look for is why they need instrumentation: Room generates code that calls Android's bundled SQLite via JNI, and that native library isn't on the plain JVM — so the test lives in androidTest, or I bring in Robolectric to shim the Android runtime and run it on the JVM at the cost of a few seconds of startup. I also test the Flow queries with Turbine to confirm they re-emit when the underlying table changes."

Room tests use an in-memory database, which is fast — but they require instrumentation because Room uses Android's SQLite bindings, which aren't available on the plain JVM. The alternative is Robolectric, which emulates enough of the Android runtime to run them on the JVM.

Robolectric adds roughly 5 to 10 seconds of startup overhead, but removes the device requirement entirely.

Under the hood

Room is an annotation-processor (KSP/kapt) framework: at compile time it generates a UserDao_Impl and an AppDatabase_Impl containing the actual SQL strings and the cursor-to-entity binding code. None of that is reflection at runtime — db.userDao() just returns the generated impl. The reason these can't run on a bare JVM is that the generated code ultimately drives SQLiteDatabase/SQLiteConnection, whose query execution is implemented in native code (libsqlite) reached through JNI. The desktop JVM has no such library loaded, so you either run on a device/emulator or let Robolectric load its shadow + bundled native SQLite.

@Dao interface -> KSP -> UserDao_Impl (raw SQL + cursor binding)
in-memory builder -> SQLiteDatabase(":memory:") -> JNI -> native libsqlite
                                                   (absent on plain JVM)

The observeUsers() Flow re-emits because Room registers an InvalidationTracker: each table maintains a flag in a room_table_modification_log temp table updated by triggers Room installs, and after a write transaction commits the tracker checks those flags and notifies registered observers, which re-run the query. An in-memory database (:memory:) lives entirely in the connection's heap and is discarded the instant the last connection closes — that's why db.close() in @After gives perfect isolation with no file cleanup.

Room Migration Tests

🎤 Say it out loud (~30–45s): "Migration tests matter because a migration runs exactly once on a real device, and if it corrupts data the user can never recover it. So I seed a database at the old schema version, run the actual migration, and assert that existing rows survived and new columns got their defaults. The gotcha interviewers love is NOT NULL without a DEFAULT — that crashes on any populated table — and the other one is forgetting MigrationTestHelper validates the resulting schema against Room's exported JSON, which is why you have to commit those schema files."

Migrations are critical because they run exactly once on a user's real device. A bad migration corrupts data that the user can never get back. Migration tests verify that the schema transition is correct, that existing data survives, and that new columns have the right defaults.

Setup:

androidTestImplementation "androidx.room:room-testing:$room_version"
@RunWith(AndroidJUnit4::class)
class MigrationTest {

    @get:Rule
    val migrationTestHelper = MigrationTestHelper(
        InstrumentationRegistry.getInstrumentation(),
        AppDatabase::class.java
    )

    @Test
    fun migrate1to2() {
        // Create DB at version 1
        var db = migrationTestHelper.createDatabase(TEST_DB_NAME, 1)

        // Insert data in version-1 schema
        db.execSQL("INSERT INTO users (id, name) VALUES (1, 'Alice')")
        db.close()

        // Run migration from 1 to 2
        db = migrationTestHelper.runMigrationsAndValidate(
            TEST_DB_NAME,
            2,
            true,  // validateDroppedTables
            MIGRATION_1_2
        )

        // Verify data survived migration
        val cursor = db.query("SELECT * FROM users WHERE id = 1")
        assertTrue(cursor.moveToFirst())
        assertEquals("Alice", cursor.getString(cursor.getColumnIndex("name")))
        // Verify new column added by migration
        assertNotEquals(-1, cursor.getColumnIndex("email"))
        cursor.close()
        db.close()
    }

    companion object {
        private const val TEST_DB_NAME = "migration_test_db"
    }
}

Migration definition:

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE users ADD COLUMN email TEXT NOT NULL DEFAULT ''")
    }
}

What migration tests verify:

  1. The schema at version N matches what Room expects.
  2. Existing data is preserved — not dropped or corrupted.
  3. New columns have correct defaults.
  4. New tables exist after migration.
  5. Old tables are dropped where specified.

Common migration bugs:

  • Adding a NOT NULL column without a DEFAULT value — the migration crashes on any non-empty table.
  • A column type mismatch between the migration SQL and the Room entity annotation.
  • A missing migration path — for example, providing 1→2 and 2→3 individually but no direct 1→3 path for users skipping versions.

Under the hood

createDatabase uses Room's exported schema JSON (the files emitted by the room.schemaLocation annotation-processor argument, committed under schemas/) to physically build a SQLite file whose CREATE TABLE statements exactly match version N — it does not run your entity definitions. runMigrationsAndValidate then applies your Migration.migrate() SQL against that real SQLite database, and afterward reads SQLite's own catalog (PRAGMA table_info, PRAGMA foreign_key_list, PRAGMA index_list) and diffs it against the expected version-N+1 schema JSON. A mismatch throws IllegalStateException — this is why a column type that differs between your migration SQL and your @Entity (e.g. you ADD COLUMN email TEXT but annotate the field non-null with a different affinity) fails validation even when the SQL itself succeeds.

exported schema JSON (v1) ──► createDatabase ──► real .db file at v1
                                                      │
                          your Migration(1,2).migrate(SupportSQLiteDatabase)
                                                      ▼
                              PRAGMA table_info / index_list  ──diff──►  expected schema JSON (v2)
                                                      │
                                          mismatch → IllegalStateException

SupportSQLiteDatabase here is the framework SQLite binding (FrameworkSQLiteDatabase wrapping android.database.sqlite.SQLiteDatabase), so execSQL goes straight through JNI to the device's bundled SQLite engine — the test exercises the same C library that runs in production.

API Contract Tests with MockWebServer

🎤 Say it out loud (~30–45s): "MockWebServer spins up a real HTTP server on localhost in the test process, so my Retrofit client does actual socket I/O against it — real headers, real status codes, real JSON parsing. That catches things a mock can't: a misspelled JSON field, a broken interceptor, wrong serialization. I point Retrofit at mockWebServer.url('/'), enqueue canned responses, and then call takeRequest() to assert on what my client actually sent. The trade-off is it's milliseconds-per-call slower than a pure mock and it doesn't validate the real backend — that's still E2E's job."

OkHttp's MockWebServer runs a real HTTP server in-process. Your Retrofit client makes actual HTTP requests to it — real serialization, real headers, real status codes — which means these tests verify the contract between your app and the API in a way that pure mocks cannot.

Dependency:

testImplementation "com.squareup.okhttp3:mockwebserver:4.x.x"

Full example:

@RunWith(JUnit4::class)
class UserApiContractTest {

    private val mockWebServer = MockWebServer()

    private lateinit var api: UserApi

    @Before
    fun setUp() {
        mockWebServer.start()
        val retrofit = Retrofit.Builder()
            .baseUrl(mockWebServer.url("/"))
            .addConverterFactory(GsonConverterFactory.create())
            .build()
        api = retrofit.create(UserApi::class.java)
    }

    @After
    fun tearDown() {
        mockWebServer.shutdown()
    }

    @Test
    fun `GET user returns parsed User`() = runTest {
        mockWebServer.enqueue(
            MockResponse()
                .setResponseCode(200)
                .addHeader("Content-Type", "application/json")
                .setBody("""{"id":1,"name":"Alice","email":"alice@test.com"}""")
        )

        val user = api.getUser(1)

        assertEquals(1, user.id)
        assertEquals("Alice", user.name)

        val request = mockWebServer.takeRequest()
        assertEquals("GET", request.method)
        assertEquals("/users/1", request.path)
    }

    @Test
    fun `401 response throws AuthException`() = runTest {
        mockWebServer.enqueue(MockResponse().setResponseCode(401))

        assertFailsWith<AuthException> {
            api.getUser(1)
        }
    }

    @Test
    fun `network timeout propagates as IOException`() = runTest {
        mockWebServer.enqueue(
            MockResponse()
                .setBodyDelay(5_000, TimeUnit.MILLISECONDS)
                .setBody("{}")
        )

        assertFailsWith<IOException> {
            api.getUser(1)  // client timeout < 5s
        }
    }

    @Test
    fun `request includes authorization header`() = runTest {
        mockWebServer.enqueue(MockResponse().setResponseCode(200).setBody("{}"))

        api.getUser(1)

        val request = mockWebServer.takeRequest()
        assertTrue(request.getHeader("Authorization")?.startsWith("Bearer ") ?: false)
    }
}

What MockWebServer enables that mocks cannot:

  • It exercises OkHttp interceptors — auth, logging, retry — which pure mocks skip entirely.
  • It tests the JSON deserialization path: if a field name has a typo, a mock wouldn't catch it, but MockWebServer would.
  • It tests HTTP error code handling end-to-end.
  • It lets you inspect the actual request — headers, query params, body — to verify the client is constructing it correctly.

Trade-offs:

  • Slower than pure mocks, roughly 50ms per request versus microseconds.
  • More fragile to API shape changes — you have to keep test JSON in sync with the actual API.
  • Doesn't test the real backend — that's what E2E tests are for.

Under the hood

MockWebServer.start() binds a real ServerSocket on 127.0.0.1 at an OS-assigned ephemeral port (port 0 → kernel picks a free one), spins up a dispatcher thread to accept connections, and url("/") returns an HttpUrl pointing at that loopback port. Enqueued MockResponse objects sit in a BlockingQueue; the default QueueDispatcher pops one per incoming request and writes raw HTTP/1.1 (or HTTP/2) bytes back over the socket. Your Retrofit call therefore goes through the full OkHttp stack — interceptor chain, connection pool, Okio buffered socket source/sink, and the converter's JsonReader parsing the response body — none of which is stubbed. Each received request is parsed into a RecordedRequest and pushed onto another queue that takeRequest() drains (blocking up to a timeout), which is how you can assert on the method, path, headers, and body bytes the client actually transmitted.

api.getUser(1)
  └─ Retrofit invocation handler builds Request
       └─ OkHttp interceptor chain (auth/logging/retry)
            └─ TCP connect to 127.0.0.1:<ephemeral>  ◄─── MockWebServer ServerSocket
                 └─ QueueDispatcher pops next MockResponse → writes HTTP bytes
            └─ converter parses body → User
  takeRequest() ◄── RecordedRequest (method, path, headers, body) recorded on accept

Hilt Test Injection

🎤 Say it out loud (~30–45s): "Hilt owns the whole dependency graph, so for tests I don't hand-build fakes — I swap bindings inside the graph. @HiltAndroidTest plus HiltAndroidRule regenerates the components against a HiltTestApplication, and I replace a production module with @TestInstallIn(replaces = ...), or for a one-off I use @BindValue to push a field straight into the graph. The classic gotcha is rule ordering: the Hilt rule has to be order = 0 so injection finishes before ActivityScenarioRule launches the Activity, otherwise the component isn't ready when the Activity asks for its dependencies."

Hilt manages the entire dependency graph in production. The testing challenge is that you need to swap out specific components with fakes — without touching any production wiring. Hilt provides dedicated annotations for exactly that.

Hilt testing annotations:

// Marks a test class to use Hilt injection
@HiltAndroidTest
@RunWith(AndroidJUnit4::class)
class UserRepositoryHiltTest {

    @get:Rule
    val hiltRule = HiltAndroidRule(this)

    @Inject
    lateinit var userRepository: UserRepository  // real binding from graph

    @Before
    fun setUp() {
        hiltRule.inject()
    }
}

Replacing modules with test fakes:

// Production module
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides
    fun provideUserApi(): UserApi = Retrofit.Builder()...build().create(UserApi::class.java)
}

// Test replacement
@Module
@TestInstallIn(
    components = [SingletonComponent::class],
    replaces = [NetworkModule::class]
)
object FakeNetworkModule {
    @Provides
    fun provideUserApi(): UserApi = FakeUserApi()
}

@UninstallModules — removes a module for a specific test class without a replacement:

@HiltAndroidTest
@UninstallModules(AnalyticsModule::class)
class SomeTest {
    // AnalyticsModule is gone; inject your own fake manually or via @BindValue
}

@BindValue — injects a field directly into Hilt's binding graph from test:

@HiltAndroidTest
class SomeTest {
    @BindValue
    @JvmField
    val fakeUserApi: UserApi = FakeUserApi()
}

Testing Activities/Fragments with Hilt:

@HiltAndroidTest
class MainActivityTest {

    @get:Rule(order = 0)
    val hiltRule = HiltAndroidRule(this)

    @get:Rule(order = 1)
    val activityRule = ActivityScenarioRule(MainActivity::class.java)

    // ...
}

Note: @HiltAndroidTest requires that a @HiltAndroidApp Application exists. For tests, use HiltTestApplication — Hilt provides it — as the test application class. Configure it in the AndroidManifest.xml for the androidTest source set.

HiltAndroidRule order matters when combining multiple rules. Set order = 0 for the Hilt rule so Hilt injects before any Activity launches.

Under the hood

These annotations are processed at compile time by Hilt's annotation processor (running on top of Dagger). @HiltAndroidTest makes the processor generate a per-test Dagger component (e.g. a test variant of SingletonComponent) instead of relying on the app's single generated graph, which is why each test class can have a different binding set. @TestInstallIn and @UninstallModules work by altering which @Module classes are aggregated into that generated component: replaces tells the processor to drop the named production module's @Provides methods and substitute the test module's, all resolved statically — no runtime reflection or bytecode rewriting. @BindValue is the one runtime-ish piece: the processor generates a synthetic @Module whose @Provides method returns the field value read from your test instance, so the binding is created when hiltRule.inject() runs and reads that field. Rule ordering is enforced by JUnit's RuleChain: @get:Rule(order = 0) makes JUnit wrap the Hilt rule as the outermost statement, so its before() (which builds the component and performs field injection) executes before ActivityScenarioRule.before() launches the Activity via ActivityScenario, guaranteeing the graph exists when the Activity's onCreate triggers member injection.

JUnit RuleChain (outer → inner):
  HiltAndroidRule(order=0).before()   → build test component, inject @Inject/@BindValue fields
    ActivityScenarioRule(order=1).before() → ActivityScenario.launch(...) → Activity.onCreate
                                              → Hilt member-injects Activity from ready graph

CI Strategy

A well-structured CI test strategy has three goals. First, fast feedback on every PR — under 10 minutes for blocking checks. Second, full regression coverage before any release. And third, a quarantine system so flaky tests don't block the pipeline while they're being investigated.

🎤 Say it out loud (~30–45s): "My CI strategy maps directly onto the test pyramid: unit and integration tests gate every PR because they're fast and deterministic, UI smoke tests cover only the critical flows on the PR, and the slow full UI and device-farm suites run pre-release where a longer runtime is acceptable. To keep PR feedback under ten minutes I shard instrumentation tests across parallel emulators and merge the results. The discipline part is flaky-test quarantine — I tag and exclude a flake with a linked bug, but with a hard fix-or-delete policy so the quarantine list doesn't quietly become a graveyard of untrusted tests."

Recommended layer allocation:

  -Pandroid.testInstrumentationRunnerArguments.numShards=4 \
  -Pandroid.testInstrumentationRunnerArguments.shardIndex=0

Run on 4 parallel emulators and combine results.

Flaky test quarantine:

  • Tag with @FlakyTest(bugId = "ZD-123") to exclude a test from the blocking suite while it's under investigation.
  • Never leave quarantined tests sitting indefinitely — set a policy of fix or delete within 2 sprints.

Test result aggregation: Use allure or junit-merge to combine results across parallel shards into a single report.

Under the hood

numShards/shardIndex are consumed by AndroidJUnitRunner, not Gradle: the runner enumerates every discovered test method, computes a stable hash of each, and runs only those where hash % numShards == shardIndex. That partition is deterministic and disjoint, so N machines each running a different shardIndex collectively run every test exactly once with no coordination — which is why merging is just concatenating each shard's TEST-*.xml JUnit reports. @FlakyTest is a JUnit filter annotation: the runner's -e annotation/-e notAnnotation arguments (or a CI filter) drop annotated methods from the run set before execution, so a quarantined test never even instantiates. Each shard typically targets its own emulator/device instance to avoid contention on the single ADB/instrumentation channel per device.

   for each test:  shard = stableHash(testName) % numShards
   run if shard == shardIndex            ── disjoint partition, no overlap
emulator 0 → shard 0 ─┐
emulator 1 → shard 1 ─┤ each emits TEST-*.xml
emulator 2 → shard 2 ─┤
emulator 3 → shard 3 ─┘ → junit-merge / allure → single aggregated report

How to Test a Login Flow

🎤 Say it out loud (~30–45s): "I'd answer this as three tests at three layers, not one. Unit tests on the ViewModel and interactor cover validation and the success/error mapping — blank email, token returned. A repository integration test with MockWebServer proves the 200 actually persists the token and a 401 maps to invalid-credentials. Then one or two UI tests with a FakeAuthRepository bound via Hilt verify that a success navigates to home and a failure shows the error. The key principle I'd state out loud: never hit the real backend — the server isn't my system under test, my app's behavior is."

This is the canonical multi-layer testing interview question. The right answer isn't one test — it's three tests at three different layers, each catching a different class of bug.

The flow covers: email input, password input, submit, API call, token storage, and navigation to home.

Layer 1: Unit tests (fastest)

// ViewModel unit test
@Test

    advanceUntilIdle()
    val state = sut.uiState.value
    assertTrue(state is LoginUiState.ValidationError)
    assertEquals("Email is required", (state as LoginUiState.ValidationError).message)

// Use case unit test
@Test

}

@Test

What NOT to do: Never test login with real network calls. The backend is not your system under test — you're testing your app's behavior, not the server's.

Under the hood

The three layers run on entirely different machinery, which is why they catch different bug classes. Layer 1 runs on a local JVM (no Android framework) under runTest, whose TestCoroutineScheduler virtualizes the clock — advanceUntilIdle() drains all queued coroutine continuations on the test dispatcher instantly rather than waiting real time, so there is no actual concurrency and assertions are deterministic. Layer 2 still runs on the JVM but adds real socket I/O to a loopback MockWebServer, exercising serialization and HTTP status mapping. Layer 3 runs on a device/emulator inside an instrumentation APK; Espresso's value-add is its UiController, which loops on the main thread's MessageQueue and only proceeds when the app is idle — no pending main-thread messages and all registered IdlingResources reporting idle — which is what makes onView(...).check(...) reliable instead of racing the UI. The @BindValue FakeAuthRepository is wired in by Hilt's generated test component so the production network path is never touched, and Espresso ViewMatchers/ViewActions resolve views by walking the view hierarchy from the activity's decor view.

Layer 2  JVM + loopback  Retrofit ↔ MockWebServer socket → real JSON + status mapping
Layer 3  emulator        Espresso UiController waits for MessageQueue idle + IdlingResources
                         FakeAuthRepository bound via Hilt test component (no real network)

How to Test Network Error Handling

🎤 Say it out loud (~30–45s): "Network error handling isn't one scenario — it's a matrix: timeouts, no connectivity, 4xx, 5xx, malformed JSON, and cancellation, each tested at the right layer. At the ViewModel layer I make the interactor throw an IOException and assert the UI goes to a retryable error state. At the integration layer MockWebServer is the star: SocketPolicy lets me simulate a connection refused, a mid-response disconnect, or a never-responding server for timeouts, and a setBodyDelay to force a SocketTimeoutException. The nuance is matching the exception type the layer below actually surfaces — a timeout is a SocketTimeoutException, a bad body is a parse exception — not just catching a generic Exception."

Network error handling is a broad category — it covers timeouts, no connectivity, HTTP 4xx and 5xx responses, malformed JSON, and cancelled requests. Each of these requires a different test at a different layer.

MockWebServer SocketPolicy options:

  • DISCONNECT_AT_START — connection refused (simulates no network)
  • DISCONNECT_AFTER_REQUEST — disconnects before sending response
  • DISCONNECT_DURING_RESPONSE_BODY — partial response
  • NO_RESPONSE — server accepts connection but never responds (timeout)
  • RESET_STREAM_AT_START — TCP RST

Retry logic test:

@Test
fun `repository retries 3 times on 503`() = runTest {
    repeat(2) {
        mockWebServer.enqueue(MockResponse().setResponseCode(503))
    }
    mockWebServer.enqueue(MockResponse().setResponseCode(200).setBody("""{"id":1,"name":"Alice"}"""))

    val user = retryableRepository.getUser(1)

    assertEquals(3, mockWebServer.requestCount)
    assertEquals("Alice", user.name)
}

Under the hood

Each SocketPolicy maps to a concrete manipulation of the TCP socket by MockWebServer's dispatcher thread, which is why the resulting exception types differ. DISCONNECT_AT_START closes (or refuses) the socket before any bytes flow, surfacing in OkHttp as a connection failure (ConnectException/IOException). NO_RESPONSE accepts the connection but writes nothing, so OkHttp's read on the Okio source eventually trips the configured readTimeout and throws SocketTimeoutException — the same mechanism setBodyDelay exploits by stalling the body write past the client's timeout. DISCONNECT_DURING_RESPONSE_BODY writes a partial body then drops the connection, so the OkHttp source hits EOF before the declared/expected length and throws an IOException. Malformed JSON gets through the socket layer intact and only fails deeper in the stack, when the converter's streaming parser (Gson's JsonReader / Moshi's JsonReader) encounters an unexpected token. Crucially, OkHttp does not automatically retry HTTP 5xx responses — retryOnConnectionFailure only covers transport-level failures — so the "retries 3 times on 503" test is exercising your application-level retry interceptor or repository loop, which is exactly why requestCount is the right assertion.

SocketPolicy            socket action                     exception surfaced
DISCONNECT_AT_START     refuse/close before bytes      →  ConnectException / IOException
NO_RESPONSE             accept, never write            →  SocketTimeoutException (readTimeout)
setBodyDelay > timeout  stall body write               →  SocketTimeoutException
DISCONNECT_DURING_BODY  partial body then close        →  IOException (unexpected EOF)
malformed body (200)    full bytes delivered           →  JsonReader parse exception (in converter)
5xx (200-level socket)  clean response, status 503     →  no OkHttp auto-retry → app-level retry loop

Under the hood

runTest builds a TestScope backed by a TestCoroutineScheduler — a virtual-time clock, not the wall clock. Both test dispatchers share that single scheduler; they differ only in when they dispatch. StandardTestDispatcher enqueues every resumption into the scheduler's task queue and runs nothing until you call advanceUntilIdle(), advanceTimeBy(), or runCurrent(), which drain the queue in when-timestamp order. UnconfinedTestDispatcher resumes coroutines eagerly on the current thread up to their first real suspension point, so child coroutines execute as soon as they're launched. Crucially, delay() does not sleep — the dispatcher intercepts it and registers a when timestamp on the scheduler, so advanceTimeBy(10_000) advances "10 seconds" instantly. runTest also installs an auto-advancing mechanism and asserts at the end that no coroutines were left uncompleted, throwing UncompletedCoroutinesError if a launched job never finished.

MockK's unmockkAll() matters because mockkStatic/mockkObject install a JVM-wide bytecode/objenesis transformation on the class — the test JVM worker is reused across classes (Gradle's forkEvery is not 1), so an un-reset static mock stays patched into the shared classloader and silently corrupts later, unrelated tests.

Under the hood

Espresso's core guarantee is synchronization: every onView(...).perform/check posts work onto the main thread's MessageQueue and then blocks until the app is idle. It does this through a UiController that watches three things — the MessageQueue (via the Looper's IdleHandler and an internal queue interrogation), the AsyncTask thread pool, and any registered IdlingResources. Only when all report idle does Espresso dispatch the next interaction, which is why custom async work (custom thread pools, OkHttp dispatchers) is invisible to Espresso unless you wrap it in an IdlingResource whose isIdleNow() returns false while busy and calls back via ResourceCallback when done. Animations break this because a running Animator/ValueAnimator keeps posting frame callbacks through the Choreographer, so the queue never appears idle (or the view's final state isn't settled) — hence disabling them at the system level.

Compose has no View hierarchy, so it can't be walked by Espresso. Instead each composable can attach a SemanticsConfiguration (via Modifier.semantics, testTag, content descriptions), and these merge into a SemanticsTree. ComposeTestRule matchers like onNodeWithText query that tree, and synchronization runs through the Compose Recomposer / Snapshot system: waitForIdle()/awaitIdle() pumps the test clock and blocks until there are no pending recompositions, layout, or draw passes. Under Espresso interop, Compose registers itself as an IdlingResource so the two frameworks stay coordinated.

Under the hood

MockWebServer is a real HTTP server: it binds a ServerSocket on localhost, accepts connections on a background thread, and serves responses you enqueue() from a FIFO BlockingQueue. Because the client connects over an actual socket, the entire OkHttp/Retrofit stack runs for real — DNS to localhost, the connection pool, every Interceptor, the converter factory (Moshi/Gson/kotlinx) deserializing the byte stream — which a mocked ApiService skips entirely. SocketPolicy lets you inject failures at the transport layer: DISCONNECT_AT_START closes the socket before sending bytes, NO_RESPONSE hangs to trigger read timeouts, and you can return malformed bodies to exercise converter-level parse failures — fault modes a return-stubbed mock can never reproduce.

Room's MigrationTestHelper is a JUnit TestRule that reads the schema JSON Room exports at compile time (the room.schemaLocation annotation-processor arg). createDatabase(name, version) materializes a real SQLite file using the exported schema for that version so you can insert legacy rows; runMigrationsAndValidate(name, newVersion, validateDroppedTables, migration) then opens that file with SupportSQLiteOpenHelper, applies your Migration.migrate() SQL, and diffs the resulting live schema (via PRAGMA table_info / PRAGMA foreign_key_list) against the exported schema for newVersion — throwing if columns, indices, or types don't match, while your own assertions confirm the data survived.

Hilt's test machinery rewrites the dependency graph at compile time: @HiltAndroidTest makes the annotation processor generate a per-test ApplicationComponent against a HiltTestApplication; HiltAndroidRule.inject() performs members-injection into the test instance. @TestInstallIn generates a replacement module that uninstalls the production module from the component, and @BindValue binds a field's runtime value straight into the graph — so you swap fakes without touching production wiring, all resolved by Dagger's generated factory code, not reflection.
