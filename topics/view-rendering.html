8.1 Traditional View System Rendering

View Hierarchy

🎤 Say it out loud (~30–45s): "The View system is a tree — ViewGroups are branches, leaf Views are the nodes — all rooted at a DecorView that the Window owns. The framework walks it top-down to measure and lay things out, then bottom-up to draw, so children paint over their parents. The thing an interviewer wants me to know is that every frame traverses this whole tree, so deep nesting hurts — and worst case, nested wrap_content can blow measurement up to O(n²), which is why flat hierarchies and ConstraintLayout matter."

The View system organizes UI as a tree of View and ViewGroup objects rooted at a DecorView. A ViewGroup is itself a View that contains children, forming a parent-child tree. The tree is traversed top-down for measurement and layout, and bottom-up for drawing — children paint over parents.

Internals:

  • Activity.setContentView(layoutRes) inflates XML into View objects and attaches them under the DecorView.
  • DecorView is a FrameLayout subclass managed by the Window. It holds the status bar, title bar, and the user's content area.
  • The Window is an abstraction over the display surface (Surface). A Surface is a raw buffer the GPU composites.

Under the hood

LayoutInflater.inflate() parses the compiled XML (binary XmlResourceParser, not text) and for each tag calls createView(), which uses reflection — or a registered LayoutInflater.Factory2 — to instantiate the View via its (Context, AttributeSet) constructor. The AttributeSet is backed by a TypedArray pulled from a pooled Resources cache, which is why attribute lookups are index-based, not string-based.

setContentView(R.layout.x)
  └─ PhoneWindow.setContentView()
       └─ LayoutInflater.inflate()  ── reads binary XML, reflects out View instances
            └─ attaches inflated root under DecorView's content FrameLayout (android.R.id.content)

Android Implications:

  • Every pixel rendered must traverse this tree. A deep or wide tree means more nodes visited per frame.
  • Flat hierarchies (fewer nesting levels) render faster because traversal is O(nodes) and measurement can be O(n²) in the worst case (when MeasureSpec.UNSPECIFIED or WRAP_CONTENT is used in nested WRAP_CONTENT parents).

Failure Modes:

  • InflateException when a referenced attribute or style is missing.
  • Memory leaks when a Context (often an Activity) is held by a static View reference after the Activity is destroyed.

ViewRootImpl

🎤 Say it out loud (~30–45s): "ViewRootImpl is the hidden glue between the View tree and the windowing system — there's exactly one per Window, created when WindowManager.addView runs around onResume. It owns the Choreographer subscription and runs the measure/layout/draw passes in performTraversals, and it talks to SurfaceFlinger through the Surface. The gotcha interviewers chase is the threading rule: ViewRootImpl records the thread that created the view, so any off-thread mutation throws CalledFromWrongThreadException — and invalidate/requestLayout don't render immediately, they just post a message that gets coalesced into the next frame."

ViewRootImpl is the bridge between the View tree and the display system. It is an internal Android class (android.view.ViewRootImpl) that implements ViewParent and View.AttachInfo. Every Window — and therefore every Activity — has exactly one ViewRootImpl.

Internals:

  • Created when WindowManager.addView() is called (which happens during Activity.onResume()).
  • It holds a Choreographer subscription and drives the measure/layout/draw passes in performTraversals().
  • It communicates with SurfaceFlinger (the system compositor) via a Surface object.
  • It manages the main-thread Handler that processes input events, configuration changes, and invalidation/relayout requests.

Under the hood

The thread check is just a stored reference comparison: ViewRootImpl captures Thread.currentThread() at construction into mThread, and checkThread() compares it on every requestLayout()/invalidate(). requestLayout() sets the PFLAG_FORCE_LAYOUT flag up the parent chain and schedules a traversal via Choreographer.postCallback(CALLBACK_TRAVERSAL, ...); the VSYNC tick then fires doTraversal() → performTraversals(), which runs measure, layout, and draw in sequence under one frame.

view.requestLayout()
  └─ checkThread()                      // throws CalledFromWrongThreadException if off main
  └─ scheduleTraversals()
       └─ Choreographer.postCallback(TRAVERSAL)   // waits for next VSYNC
            └─ doTraversal() → performTraversals()
                 ├─ performMeasure()
                 ├─ performLayout()
                 └─ performDraw()

Android Implications:

  • All View operations (measure, layout, draw, touch) must happen on the thread that created the View — the main thread. Off-thread mutations cause CalledFromWrongThreadException.
  • requestLayout() and invalidate() ultimately send a message to ViewRootImpl's handler, which coalesces them into the next frame traversal.

Trade-off: The synchronous traversal model means every frame is bounded by how much work the main thread can complete — roughly 16ms at 60 Hz or 8ms at 120 Hz.

Measure Pass

🎤 Say it out loud (~30–45s): "The measure pass walks the tree top-down asking each view how big it wants to be. The key data structure is MeasureSpec — a single packed int that crams a mode (EXACTLY, AT_MOST, UNSPECIFIED) and a size together; the parent derives a child spec from its own spec plus the child's layout params. The nuance interviewers like is double measurement: LinearLayout with weights, and RelativeLayout, measure twice, while ConstraintLayout usually does it in one pass — and wrap_content inside an UNSPECIFIED parent like a ScrollView can trigger repeated re-measuring."

The measure pass determines the desired size of every View in the tree. It begins at ViewRootImpl.performMeasure() and propagates down via View.measure().

Internals — MeasureSpec: MeasureSpec encodes both a mode and a size in a single int:

Mode Meaning
EXACTLYParent dictates exact size (match_parent or dp value)
AT_MOSTView may be up to this size (wrap_content in bounded parent)
UNSPECIFIEDParent imposes no constraint (scrollable containers)

The measure pass is recursive: a parent calls child.measure(widthSpec, heightSpec) for each child, passing down constrained MeasureSpec values derived from its own MeasureSpec and the child's layout params.

Performance: Re-measurement is expensive. A LinearLayout with layout_weight attributes forces two measure passes per weighted child. RelativeLayout also performs two passes. ConstraintLayout performs one pass in most cases.

Under the hood

MeasureSpec packs the mode into the top 2 bits and the size into the low 30 bits of an int, so there's no allocation — makeMeasureSpec(size, mode) is just size + mode with the mode shifted to bit 30, and getMode/getSize are bitmask reads. View.measure() short-circuits with a measurement cache keyed on the spec ints (PFLAG_MEASURED_DIMENSION_SET plus a LongSparseLongArray of cached results), so re-measuring with an unchanged spec skips onMeasure() entirely — unless forceLayout() invalidated the cache.

MeasureSpec int layout (32 bits):
 ┌─ 2 bits ─┬──────── 30 bits ────────┐
 │  MODE    │          SIZE           │
 └──────────┴─────────────────────────┘
 EXACTLY = 0x40000000, AT_MOST = 0x80000000, UNSPECIFIED = 0x00000000

Interview: "WRAP_CONTENT in a ScrollView with a ListView" used to be a classic O(n²) trap — ScrollView passes UNSPECIFIED, the ListView re-measures every child for each onMeasure() call.

Layout Pass

🎤 Say it out loud (~30–45s): "The layout pass takes the sizes from the measure pass and assigns each view its final position — the four coordinates left, top, right, bottom — relative to its parent. ViewGroup.onLayout is where a container positions each child by calling child.layout. The practical gotcha is timing: getWidth/getHeight return 0 before layout runs, so calling them in onCreate gives you zero — you defer with view.post {} or doOnLayout {} until after the first traversal completes."

The layout pass assigns the final position — left, top, right, bottom — to every View, given the sizes determined by the measure pass. It begins at ViewRootImpl.performLayout() and calls View.layout(), which in turn calls onLayout().

Internals:

  • View.layout(l, t, r, b) stores the four coordinates and calls onLayout() if the size or position changed.
  • ViewGroup.onLayout() is where the group positions each child by calling child.layout().
  • View.getLeft(), getTop(), getRight(), getBottom() are only valid after layout.

Under the hood

layout() calls setOpticalFrame()/setFrame(), which compares the new l/t/r/b against the stored mLeft/mTop/mRight/mBottom fields. If they changed it sets PFLAG_HAS_BOUNDS, fires onSizeChanged(), and only then invokes onLayout(). The coordinates are stored as raw int pixel offsets relative to the parent — getWidth() is literally mRight - mLeft — so before the first traversal those fields are all 0, which is exactly why early reads return zero. view.post {} works because the Runnable is queued on the main Looper behind the traversal message that WindowManager.addView scheduled.

Failure Modes:

  • Calling getWidth() or getHeight() in onCreate() before layout completes returns 0. Use View.post { } or doOnLayout { } (KTX) to defer.

Draw Pass

🎤 Say it out loud (~30–45s): "The draw pass renders each view onto a Canvas, walking the tree so backgrounds and parents draw first and children on top. The big thing to mention is hardware rendering, default since API 14: instead of painting pixels immediately, each view records its draw commands into a RenderNode display list, and the RenderThread — a separate thread since API 21 — replays those lists on the GPU. The payoff is that an invalidate() only re-records the dirty nodes; everything else is replayed straight from its cached display list, which is why properties like translation and alpha animate cheaply without a relayout."

The draw pass traverses the tree and renders each View to a Canvas. It begins at ViewRootImpl.performDraw().

Internals (Software rendering):

  • ViewRootImpl locks a Canvas from the Surface buffer.
  • View.draw(canvas) is called; it:
    1. Draws the background.
    2. Saves the canvas and fades edges if needed.
    3. Calls onDraw(canvas) — View's own content.
    4. Calls dispatchDraw(canvas) — children.
    5. Draws decorators (scrollbars, foreground).

Internals (Hardware rendering — default since API 14):

  • Instead of writing directly to a software buffer, each View records drawing commands into a RenderNode (a display list).
  • The RenderNode is replayed on the RenderThread (a separate thread introduced in API 21) via the GPU, using OpenGL ES or Vulkan.
  • Only invalidated nodes are re-recorded; others are replayed from the cached display list.

Under the hood

In hardware mode the Canvas handed to onDraw() is a RecordingCanvas (formerly DisplayListCanvas): its draw calls don't rasterize — they append opcodes into the native RenderNode's display list buffer. invalidate() sets PFLAG_INVALIDATED so only that node's list is re-recorded; the rest are reused. The UI thread then ships the updated tree of RenderNodes to the RenderThread, which builds a GPU command stream (OpenGL ES / Vulkan) and submits it. Because RenderNode properties like translationX, scale, and alpha live on the node itself, mutating them via setTranslationX() just updates the node and triggers a cheap replay — no onDraw, no measure, no layout.

View.invalidate()        → mark RenderNode dirty (re-record only this node)
View.requestLayout()     → mark FORCE_LAYOUT  (full measure + layout + draw)
View.setTranslationX()   → update RenderNode property only (RenderThread replay)

onMeasure()

🎤 Say it out loud (~30–45s): "onMeasure is where a custom view computes its size from the incoming width and height specs. The one hard rule is you must call setMeasuredDimension before you return, or the framework throws IllegalStateException — and you typically resolve your desired size against the spec with resolveSize so you honor the parent's constraints. For a custom ViewGroup, I have to measure my children first with measureChildWithMargins, otherwise they collapse to zero dimensions because nobody ever set their measured size."
override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
    val desiredWidth = 200
    val desiredHeight = 200
    val width = resolveSize(desiredWidth, widthMeasureSpec)
    val height = resolveSize(desiredHeight, heightMeasureSpec)
    setMeasuredDimension(width, height)  // MUST be called
}

Rules:

  • Must call setMeasuredDimension() — failing to do so throws IllegalStateException.
  • Use View.resolveSize() or MeasureSpec.getSize() / MeasureSpec.getMode() helpers.
  • For ViewGroup, call measureChildren() or measureChildWithMargins() before calling setMeasuredDimension().

Under the hood

setMeasuredDimension() stores the result into mMeasuredWidth/mMeasuredHeight and sets the PFLAG_MEASURED_DIMENSION_SET flag. After onMeasure() returns, View.measure() asserts that flag is set — if it isn't, it throws IllegalStateException("View ... onMeasure() did not set the measured dimension"). resolveSize() collapses your desired size against the spec: for EXACTLY it returns the spec size verbatim, for AT_MOST it returns min(desired, specSize), and for UNSPECIFIED it returns your desired size unchanged — which is exactly how wrap_content versus match_parent semantics get enforced at the view level.

resolveSize(desired, spec):
  EXACTLY     → specSize
  AT_MOST     → min(desired, specSize)
  UNSPECIFIED → desired

Trade-off: Overriding onMeasure() in a ViewGroup without properly measuring children causes those children to end up with zero dimensions.

onLayout()

🎤 Say it out loud (~30–45s): "onLayout() is where a ViewGroup positions its already-measured children by calling child.layout(l, t, r, b) with absolute coordinates relative to the parent. By the time it runs, measurement is done, so I'm just placing things — I should never re-measure or trigger a new pass here. The gotcha is that the size you assign must come from measuredWidth/measuredHeight; if onMeasure and onLayout disagree, children get clipped or stretched."
override fun onLayout(changed: Boolean, l: Int, t: Int, r: Int, b: Int) {
    // For a ViewGroup: position each child
    var currentTop = paddingTop
    for (child in children) {
        if (child.visibility == View.GONE) continue
        val childWidth = child.measuredWidth
        val childHeight = child.measuredHeight
        child.layout(paddingLeft, currentTop, paddingLeft + childWidth, currentTop + childHeight)
        currentTop += childHeight
    }
}

Rules:

  • Only called on ViewGroup subclasses (or Views that need to arrange things — rare).
  • changed is true if the size or position changed since the last layout.

Under the hood

View.layout(l, t, r, b) calls setFrame(), which stores the four coordinates into the View's mLeft/mTop/mRight/mBottom fields and returns whether the frame changed. If it changed, the framework fires onSizeChanged() and sets the PFLAG_LAYOUT_REQUIRED flag so onDraw will run. The public layout() is what dispatches to your overridable onLayout(). Coordinates are integer pixels in the parent's coordinate space, and getWidth()/getHeight() are simply derived as mRight - mLeft and mBottom - mTop.

ViewGroup.layout(l,t,r,b)
  └─ View.setFrame() → writes mLeft/mTop/mRight/mBottom, detects change
       └─ if changed → onSizeChanged(), invalidate(), set PFLAG_LAYOUT_REQUIRED
  └─ onLayout(changed, ...)  → you call each child.layout(...)

onDraw()

🎤 Say it out loud (~30–45s): "onDraw() hands me a Canvas and I issue drawing commands against it — circles, text, paths. The golden rule is zero allocation in here: Paint, Path, and formatted strings get created once as fields, because onDraw can run every frame and allocating triggers GC pressure that causes jank. The other thing interviewers probe is save/restore balance — every transform or clip I push has to be popped, or state leaks into later draw calls."
override fun onDraw(canvas: Canvas) {
    super.onDraw(canvas)
    canvas.drawCircle(width / 2f, height / 2f, radius, paint)
    canvas.drawText(label, x, y, textPaint)
}

Rules:

  • Never allocate objects here (no Paint(), no Path(), no String formatting with +).
  • All Paint and Path objects are created once in init {} or a field initializer.
  • canvas.save() / canvas.restore() bracket transformations and clips.

Under the hood

In hardware-accelerated mode the Canvas passed to onDraw is a RecordingCanvas (historically DisplayListCanvas). Your drawCircle/drawText calls don't paint pixels immediately — they append serialized drawing operations into the View's RenderNode display list. That recorded list is later replayed on the RenderThread and translated into GPU draw calls. This is why allocation hurts so much: the recording happens on the main thread inside the frame budget (~16ms at 60Hz), and a GC pause there blows the frame. save() pushes the current matrix+clip onto a stack maintained by the canvas; restore() pops it. drawText is comparatively expensive because it resolves glyphs through the font engine and caches rendered glyphs in a GPU texture atlas.

invalidate() vs requestLayout()

🎤 Say it out loud (~30–45s): "invalidate() says 'my pixels are stale, redraw me' — it only re-runs the draw pass. requestLayout() says 'my size or position may have changed' — it re-runs measure, layout, and draw for the affected subtree, so it's much more expensive. Rule of thumb: color or animation-frame changes call invalidate(); anything that changes dimensions calls requestLayout(). The classic gotcha is calling requestLayout() inside onLayout() and creating an infinite traversal loop."
invalidate() requestLayout()
What it doesMarks the View as needing to be redrawnMarks the View as needing a new measure + layout + draw pass
ScopeOnly the draw pass (onDraw) is repeatedFull traversal: onMeasure → onLayout → onDraw
CostCheaper — only redraws dirty regionMore expensive — re-measures and re-lays out the subtree
When to useVisual change only (color, text, animation frame) — size/position unchangedSize or position of the View has changed
Thread safetypostInvalidate() for off-main-threadrequestLayout() is safe to call on any thread (posts to main handler)

Both methods ultimately schedule a traversal in ViewRootImpl. Multiple requestLayout() calls within a single frame are coalesced into one traversal. One important gotcha: calling requestLayout() from within onLayout() — unless guarded — creates an infinite loop.

The failure modes to watch for: calling requestLayout() when only a color changes wastes a full measure/layout pass unnecessarily. On the flip side, calling invalidate() when a text string that changes the View's width is updated causes the View to draw at the old size.

Under the hood

requestLayout() sets PFLAG_FORCE_LAYOUT on the View and walks mParent upward, each parent calling its own requestLayout() until it reaches ViewRootImpl.requestLayout(). That schedules a traversal via Choreographer (a mTraversalRunnable posted on the next VSYNC callback) and sets mLayoutRequested = true. On the next frame performTraversals() runs measure → layout → draw. invalidate() instead sets PFLAG_INVALIDATED/PFLAG_DIRTY, marks the dirty rectangle, propagates up via invalidateChildInParent(), and schedules a traversal that runs only performDraw() — re-recording just that View's RenderNode display list. Because both funnel through one Choreographer frame callback, N calls in the same frame collapse to a single traversal.

requestLayout() → flag PFLAG_FORCE_LAYOUT → bubble up parents
       → ViewRootImpl.scheduleTraversals() → Choreographer (next VSYNC)
       → performTraversals(): measure → layout → draw
invalidate()    → flag dirty + dirty rect → bubble up
       → scheduleTraversals() → performTraversals(): draw only

Canvas and Paint

🎤 Say it out loud (~30–45s): "Canvas is the drawing-surface abstraction — in software mode it wraps a Bitmap, in hardware mode it records commands into a RenderNode. Paint is the 'how' — color, stroke width, typeface, anti-aliasing, shaders, color filters. The thing I'm careful about is state: save()/restore() bracket every transform and clip, and I wrap them in try/finally so an exception can't leave the matrix corrupted for the rest of the draw."

Canvas is the drawing surface abstraction. It wraps a Bitmap in software mode or records commands to a RenderNode in hardware mode. The key operations you reach for are drawRect, drawCircle, drawPath, drawBitmap, drawText, drawLine, save/restore, clipRect, clipPath, translate, scale, and rotate. canvas.save() pushes the current matrix-and-clip state; canvas.restore() pops it back. Always balance saves and restores — wrapping them in a try/finally is the safe pattern.

Paint describes how drawing operations render: it carries color, stroke width, typeface, anti-aliasing flag, shader, mask filter, and more. A few things to know: Paint.setAntiAlias(true) smooths edges at a small GPU cost; setStyle controls whether you fill, stroke, or do both; setShader(LinearGradient(...)) gives you gradient fills; and setColorFilter(PorterDuffColorFilter(...)) handles tinting.

// Create once in init, never in onDraw
private val circlePaint = Paint(Paint.ANTI_ALIAS_FLAG).apply {
    color = Color.BLUE
    style = Paint.Style.FILL
}

Under the hood

Canvas and Paint are thin Java wrappers over native objects: each holds a long native pointer (mNativeCanvasWrapper, mNativePaint) into a C++ Skia object (SkCanvas/SkPaint). Almost every method is a JNI call that mutates Skia state. The current transform is a 3×3 SkMatrix; translate/scale/rotate post-multiply into it, and save()/restore() push/pop entries on Skia's internal save stack (matrix + clip together). Paint carries the anti-alias flag, an SkShader for gradients, an SkColorFilter, and an SkMaskFilter for blurs. Anti-aliasing costs more because Skia computes fractional edge coverage instead of a hard binary mask. This native backing is also why allocating a Paint in onDraw is doubly bad — you pay both Java GC pressure and native object construction.

Hardware Acceleration

🎤 Say it out loud (~30–45s): "Hardware acceleration moves drawing from the CPU onto the GPU, and it's been the default since API 14. The model is that each View records its drawing into a RenderNode display list once, and a separate RenderThread replays those on the GPU. The big win is partial invalidation — when one View changes, only its RenderNode is re-recorded and everything else replays from cache. The gotcha is that a handful of operations aren't GPU-supported and silently fall back to software, so I sometimes have to force LAYER_TYPE_SOFTWARE."

Hardware acceleration redirects drawing commands from the CPU to the GPU. It has been the default since API 14, enabled at the Application level in the manifest or overridden per-Window or per-View.

Internals:

  • Every hardware-accelerated View has a RenderNode that stores a DisplayList — a serialized sequence of drawing commands.
  • When invalidate() is called on a View, only that View's RenderNode is re-recorded. The RenderThread replays all non-dirty RenderNodes from cache.
  • The RenderThread (a background GPU thread) handles actual GPU command submission independently from the main thread, reducing jank when the main thread is briefly busy.

Not all Canvas operations are hardware-accelerated:

  • Some Paint operations (e.g., certain Xfermodes) may fall back to software rendering.
  • View.setLayerType(View.LAYER_TYPE_SOFTWARE, null) forces software rendering for a subtree (useful for unsupported operations but costs performance).

The key trade-off with hardware layers (LAYER_TYPE_HARDWARE): they cache a View's rendered output as a GPU texture, which is great for animations that don't change the View's content — translates, scales, alpha fades. But the layer must be explicitly invalidated when content changes, or it shows stale pixels. ViewPropertyAnimator manages this automatically during animations, which is one reason to prefer it over manual hardware layer management.

Under the hood

The pipeline runs in two stages across two threads. On the main thread, performDraw() records each dirty View's display list into its native RenderNode (a tree mirroring the View hierarchy). Then the recorded tree is handed to the RenderThread, which uses Skia's GPU backend (hwui, talking to OpenGL ES or Vulkan) to issue actual draw calls and swap buffers in sync with VSYNC. Because the tree is retained, an unchanged View's RenderNode is replayed without re-recording — and RenderNode properties like translation, scale, and alpha can be updated and re-replayed entirely on the RenderThread without any main-thread work, which is exactly how ViewPropertyAnimator and RenderNodeAnimator stay smooth even when the main thread is busy. A software layer (LAYER_TYPE_SOFTWARE) detours through an off-screen Bitmap rendered with the CPU rasterizer, which is why unsupported Xfermodes/MaskFilters land there.

Main thread:  performTraversals → performDraw
                → RenderNode.recordingCanvas → record DisplayList (per dirty View)
RenderThread: replay RenderNode tree → Skia (GL/Vulkan) → GPU → buffer swap @ VSYNC
              (translate/scale/alpha replayed here with NO main-thread cost)

Overdraw

🎤 Say it out loud (~30–45s): "Overdraw is painting the same pixel more than once in a single frame — usually stacked opaque backgrounds, like a window background plus a layout background plus a card background. It wastes GPU fill-rate, which matters most on cheap, fill-rate-bound devices. I diagnose it with the 'Debug GPU Overdraw' overlay, then strip redundant backgrounds, clip to the visible region, and set willNotDraw(true) on ViewGroups that don't draw anything themselves."

Overdraw occurs when the same pixel is drawn more than once per frame. Every extra draw cycle wastes GPU fill-rate and can cause thermal throttling on lower-end devices.

Detection: Enable "Debug GPU Overdraw" in Developer Options. The overlay colors pixels:

  • No color: drawn once (ideal)
  • Blue: 2x overdraw
  • Green: 3x overdraw
  • Pink: 4x overdraw
  • Red: 5+ overdraw (problematic)

Causes:

  • Opaque View background + opaque Window background both rendering.
  • CardView background + content View background.
  • Drawing transparent regions.

Fixes:

  • Remove redundant backgrounds: activity.window.setBackgroundDrawableResource(android.R.color.transparent) if the Activity's root View already sets a background.
  • Use canvas.clipRect() to skip drawing outside a region.
  • Use View.setWillNotDraw(true) on ViewGroups that don't draw themselves.

Under the hood

Overdraw is a fill-rate cost: every fragment the GPU shades and blends into the framebuffer counts, even if a later opaque draw completely hides it. Traditional desktop GPUs would use a depth/Z-buffer to early-reject hidden fragments, but mobile UI compositing draws back-to-front in painter's-algorithm order with alpha blending enabled, so the GPU can't trivially skip covered pixels — it shades and blends each layer. The "Debug GPU Overdraw" overlay works by incrementing a per-pixel counter in the GPU's stencil buffer on each draw and mapping the count to a tint. clipRect/clipPath install a clip in the RenderNode so Skia rejects ops outside the region before rasterizing, and setWillNotDraw(true) sets the PFLAG_SKIP_DRAW flag so the framework omits the onDraw call entirely for that ViewGroup. Modern hwui also applies some automatic backdrop/overlap culling, but stacked opaque backgrounds it can't prove are fully covered still get drawn.

Clipping

🎤 Say it out loud (~30s): "Clipping restricts the drawable region of a Canvas so anything outside the clip just doesn't get touched — I use it to cut overdraw or to mask shapes like rounded corners. The gotcha is that clipPath with a non-rectangular path forces a software fallback on a hardware layer, so for rounded corners in production I reach for setClipToOutline with a ViewOutlineProvider, which the GPU can clip natively."

Clipping restricts drawing to a region of the Canvas, preventing pixels outside the clip from being modified.

override fun onDraw(canvas: Canvas) {
    canvas.save()
    canvas.clipRect(left, top, right, bottom)
    // Only pixels within the rect are affected
    canvas.drawBitmap(bitmap, 0f, 0f, null)
    canvas.restore()
}

Uses:

  • Reducing overdraw by skipping drawing behind opaque regions.
  • Rounded corners: canvas.clipPath(roundRectPath) (software only — on hardware, use View.setClipToOutline(true) with ViewOutlineProvider).
  • Compositing effects.

One trade-off to keep in mind: clipPath() disables hardware acceleration for that draw call, falling back to software. For hardware-accelerated clipping, prefer Outline-based clipping via View.setClipToOutline(true) with a ViewOutlineProvider.

Under the hood

Canvas.save() pushes the current clip and transform matrix onto a save stack; restore() pops it. On a hardware-accelerated canvas (which is really a RecordingCanvas recording into a RenderNode's display list), clipRect is cheap because rectangular clips map directly to GPU scissor-rect state. A clipPath with an arbitrary path can't be expressed as a scissor or simple stencil, so the framework historically rendered that draw through a software path — the path is rasterized to a mask and composited. setClipToOutline(true) instead stores the rounded-rect geometry on the RenderNode itself, and the GPU clips at composite time using the outline (anti-aliased rounded rects are a fast path the renderer special-cases), avoiding any software detour.

clipRect      -> GPU scissor rect (fast, free)
clipPath(rrect) on SW canvas -> rasterize mask -> composite (slow)
RenderNode.setOutline + clipToOutline -> GPU-side rounded-rect clip (fast)

Touch Dispatch

🎤 Say it out loud (~30–45s): "Touch events flow top-down from the Activity through ViewRootImpl into the view tree: each ViewGroup gets a shot at onInterceptTouchEvent before the event descends to a hit-tested child, and whoever returns true from onTouchEvent consumes it. The key invariant is that the ACTION_DOWN target is locked in for the rest of that gesture — if nothing consumes the DOWN, that view sees nothing else. The two gotchas interviewers love are that a parent stealing the gesture mid-stream sends the child an ACTION_CANCEL, which you must treat like an UP, and that a child can call requestDisallowInterceptTouchEvent(true) to stop its parent from intercepting — that's how nested scrollables coexist."

Touch events follow a dispatch chain from the root ViewGroup down through children, and each level in the hierarchy has the opportunity to intercept the event before it reaches the target.

The three-method pattern:

Method Purpose Returning true
dispatchTouchEvent(ev)Entry point; routes to intercept or childEvent is consumed by this View's tree
onInterceptTouchEvent(ev)ViewGroup only; can steal an ongoing gestureThis ViewGroup will handle subsequent events
onTouchEvent(ev)Handles the event in this ViewEvent is consumed

Dispatch flow for ACTION_DOWN:

  1. Activity.dispatchTouchEvent() → ViewRootImpl → root ViewGroup.
  2. Each ViewGroup calls onInterceptTouchEvent(). If it returns false, the event descends to children.
  3. Children are hit-tested (largest z-order child first). A matching child's dispatchTouchEvent() is called.
  4. If no child consumes it, the ViewGroup's own onTouchEvent() is called.
  5. If nothing consumes ACTION_DOWN, subsequent events are not sent to that View.

ACTION_CANCEL is sent to a child when a parent intercepts mid-gesture. Always handle ACTION_CANCEL the same way you handle ACTION_UP in custom Views — it signals "the gesture you were tracking is no longer yours."

requestDisallowInterceptTouchEvent(true) is called by a child on its parent to block onInterceptTouchEvent() from being called — the classic use case is a horizontal ViewPager nested inside a vertical RecyclerView, where the inner scroll view needs to own horizontal swipes.

Under the hood

When a child consumes ACTION_DOWN, the parent ViewGroup records it in an internal TouchTarget linked list (keyed by pointer id), so subsequent MOVE/UP events skip hit-testing and route straight to that child — this is why the DOWN target is sticky for the gesture. onInterceptTouchEvent is consulted on every event except once a child is already the target and the parent hasn't intercepted; if the parent later returns true, the framework synthesizes an ACTION_CANCEL to the captured child and clears the TouchTarget. requestDisallowInterceptTouchEvent simply sets the FLAG_DISALLOW_INTERCEPT bit on the ViewGroup's mGroupFlags, which short-circuits the intercept call; that flag is reset automatically on the next ACTION_DOWN. Multi-touch is handled by MotionEvent packing several pointers, with ACTION_POINTER_DOWN/ACTION_POINTER_UP carrying a pointer index in the action's high bits.

ViewGroup.mFirstTouchTarget --> TouchTarget{ child, pointerIdBits } --> ...
  null  => no captured child; intercept consulted, hit-test runs each event
  set   => events routed to captured child until UP/CANCEL or parent intercept

Nested Layouts

🎤 Say it out loud (~30–45s): "Every level of nesting is more nodes to measure and lay out, but the real trap is that some parent/child combos blow up to exponential measurement — the classic is a WRAP_CONTENT LinearLayout inside a WRAP_CONTENT ScrollView, which is O(n²) because the ScrollView measures children with UNSPECIFIED and the LinearLayout can't cache under UNSPECIFIED, so each parent measure re-measures the whole subtree. My fix is to flatten with ConstraintLayout. I'd also flag RelativeLayout, which always does a double measure pass to resolve relative dependencies, so nesting those compounds the cost."

Every extra level of nesting adds nodes to the traversal. The really dangerous case is when certain combinations cause exponential measurement: a LinearLayout with WRAP_CONTENT inside a ScrollView with WRAP_CONTENT produces O(n²) measurement passes. The reason is that ScrollView passes UNSPECIFIED to its children, and with UNSPECIFIED, LinearLayout cannot cache measurement results for its own WRAP_CONTENT children — so every call to measure() propagates all the way back down the tree.

The fix is to use ConstraintLayout to flatten the hierarchy — replace three levels of LinearLayout and RelativeLayout with a single flat ConstraintLayout.

One thing interviewers like to ask about is RelativeLayout's double-measure pass: it measures children twice — once to gather relative constraints and once to resolve them.

Under the hood

View.measure() has a cache: it stores the last MeasureSpec pair and the resulting measured dimensions, and if measure() is called again with the same specs (and no forceLayout/PFLAG_FORCE_LAYOUT), it returns the cached size without re-running onMeasure. The catch is that the cache key includes the MeasureSpec mode, and UNSPECIFIED measure passes are treated as non-cacheable for the optimized path because the parent is "probing" for desired size. So when a LinearLayout (especially with weights) measures each child once with UNSPECIFIED to find natural sizes and again with EXACTLY to distribute leftover space, and its own parent (ScrollView) is also doing an UNSPECIFIED probe, the multiplicative effect cascades down each nesting level — hence the O(n²) (or worse) behavior. ConstraintLayout avoids this by solving positions analytically in a single solver pass rather than recursive remeasuring.

ScrollView (WRAP, UNSPECIFIED)
  └ LinearLayout (WRAP) measures child twice (probe + exact)
      └ each child measured again per parent probe  => passes multiply per level

ConstraintLayout

🎤 Say it out loud (~30–45s): "ConstraintLayout lets me express positions as a system of constraints — anchor edges to the parent, to siblings, or to guidelines — and a solver resolves them in one pass, which is how it replaces deeply nested LinearLayout/RelativeLayout trees with a single flat level. Under the hood it runs a Cassowary linear-constraint solver, the same family as Apple's Auto Layout. The nuance is that flat doesn't always beat nested for free: it adds a dependency and slightly more inflation cost, and chains or ratios can still trigger extra solver work, so I don't blindly assume one flat ConstraintLayout always wins."

ConstraintLayout is a ViewGroup that positions children using a system of horizontal and vertical constraints. The key benefit is that it replaces deeply nested LinearLayout/RelativeLayout trees with a single flat level.

Internals:

  • Uses the Cassowary constraint-solving algorithm (same as Apple's Auto Layout).
  • Each View has constraints anchoring it to parent edges, other Views' edges, or guidelines.
  • Resolves all constraints in O(n) for a well-formed layout (no circular dependencies).
  • Barrier, Group, Guideline, and Flow are virtual helpers (zero-size Views) that assist positioning.

Key features:

  • layout_constraintDimensionRatio for aspect ratio.
  • layout_constraintPercent* for percentage-based sizing.
  • ConstraintSet for programmatic constraint manipulation (useful for animations).
  • MotionLayout (a ConstraintLayout subclass) for declarative keyframe animations.

Trade-offs: It adds a dependency (implementation "androidx.constraintlayout:constraintlayout") and slightly longer inflation time compared to a simple FrameLayout. XML authoring can also be verbose for complex layouts — the Layout Editor helps with that.

Under the hood

ConstraintLayout builds an internal graph of ConstraintWidget objects and feeds them to a LinearSystem — an implementation of the Cassowary simplex algorithm that solves systems of linear equalities and inequalities. Each anchor (left/right/top/bottom/baseline) becomes a variable, and constraints become equations the solver minimizes. For layouts without chains or ratio dependencies, the solver runs effectively linearly; chains, match_constraint (0dp) with ratios, and bidirectional dependencies add iterations because the solver must converge on the leftover space. The Barrier/Guideline/Group helpers don't draw and aren't laid out as real views — they only contribute variables/anchors to the solver. MotionLayout reuses this by interpolating two ConstraintSet end states (start/end constraints) per animation frame and re-solving.

XML constraints -> ConstraintWidget graph -> LinearSystem (Cassowary)
   variables: each edge anchor; equations: each constraint
   solve() -> resolved x/y per widget -> setMeasuredDimension/layout

RecyclerView Rendering (View-system level)

🎤 Say it out loud (~30s): "At the view-system level a RecyclerView is just a ViewGroup whose onMeasure/onLayout delegate to the LayoutManager — the LayoutManager decides which item views exist and where they go. RecyclerView itself draws almost nothing beyond item decorations; each item view still runs the full measure/layout/draw cycle inside dispatchLayout. The key rendering point is that only visible items (plus a small prefetch window) are actually in the view tree, so the cost is bounded by what's on screen, not by the dataset size."

At the View-system level, RecyclerView is just a ViewGroup. Its onMeasure() and onLayout() delegate to the attached LayoutManager, which measures and positions item Views. RecyclerView itself draws nothing other than item decorations. Each item View goes through the full measure/layout/draw cycle during RecyclerView.dispatchLayout().

The important rendering distinction: only visible items are measured and laid out. Off-screen items (beyond prefetch distance) are not in the tree.

Under the hood

dispatchLayout runs in up to three phases (dispatchLayoutStep1/2/3): step 1 records pre-layout positions of currently-attached views (for predictive item animations), step 2 asks the LayoutManager to actually lay out children for the post-change state, and step 3 records post-layout positions and fires ItemAnimator animations to bridge the two. The LayoutManager pulls views from the Recycler, which is backed by a RecycledViewPool (scrap + cache tiers); a recycled ViewHolder skips inflation and only gets onBindViewHolder called. Prefetch is driven by GapWorker, which during the UI thread's idle time after a frame uses the deadline before the next vsync to pre-create/bind items just off-screen, so scrolling doesn't stall on a synchronous bind. Children added by the LayoutManager are real child views, so each still gets measureChildWithMargins → its own onMeasure/onLayout/draw.

RecyclerView.dispatchLayout
  step1: save pre-layout bounds (predictive anim)
  step2: LayoutManager.onLayoutChildren -> Recycler.getViewForPosition -> bind
  step3: record post-layout bounds -> ItemAnimator.animate
GapWorker: post-frame idle -> prefetch next item into RecycledViewPool

Custom View

🎤 Say it out loud (~30–45s): "For a custom view I extend View, allocate all my Paint/Path objects up front in init — never in onDraw, since that runs on every frame — read custom attributes with obtainStyledAttributes, implement onMeasure honoring the MeasureSpec via resolveSize, and draw in onDraw. The decision interviewers probe is invalidate versus requestLayout: if only the appearance changed I call invalidate to redraw; if the size or position could change I call requestLayout, which re-triggers measure and layout up the tree. For a custom ViewGroup I'd also override onLayout and generateLayoutParams."

Complete template:

class CircleView @JvmOverloads constructor(
    context: Context,
    attrs: AttributeSet? = null,
    defStyleAttr: Int = 0
) : View(context, attrs, defStyleAttr) {

    private var radius = 50f
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG).apply {
        color = Color.RED
        style = Paint.Style.FILL
    }
    // Path and other objects also created here, never in onDraw

    init {
        // Read custom attributes
        context.obtainStyledAttributes(attrs, R.styleable.CircleView, defStyleAttr, 0).use { ta ->
            radius = ta.getDimension(R.styleable.CircleView_circleRadius, 50f)
        }
    }

    override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
        val desired = (radius * 2).toInt()
        setMeasuredDimension(
            resolveSize(desired, widthMeasureSpec),
            resolveSize(desired, heightMeasureSpec)
        )
    }

    override fun onDraw(canvas: Canvas) {
        canvas.drawCircle(width / 2f, height / 2f, radius, paint)
    }

    fun setRadius(newRadius: Float) {
        radius = newRadius
        requestLayout() // size changed
    }

    fun setColor(color: Int) {
        paint.color = color
        invalidate() // only redraw needed
    }
}

For ViewGroup: also override onLayout() and generateLayoutParams().

Custom attributes: Define in res/values/attrs.xml:

<declare-styleable name="CircleView">
    <attr name="circleRadius" format="dimension" />
</declare-styleable>

Under the hood

invalidate() sets the PFLAG_INVALIDATED/PFLAG_DIRTY flags on the view and walks invalidateChildInParent up to ViewRootImpl, which schedules a traversal via Choreographer for the next vsync; on a hardware-accelerated tree only that view's RenderNode display list is re-recorded (its onDraw re-runs), while sibling render nodes are reused by the GPU — that's why invalidate is cheap. requestLayout() instead sets PFLAG_FORCE_LAYOUT and propagates up the parent chain so the whole branch is re-measured and re-laid-out before the next draw, which also clears the measurement cache for affected views. The @JvmOverloads constructor exists so the framework's XML inflater can call the (Context, AttributeSet) overload reflectively during LayoutInflater.createView. obtainStyledAttributes resolves attributes through the style resolution chain (explicit XML attrs → style → theme defStyleAttr → defaults) into a TypedArray backed by a shared int[] pool, which is why you must recycle() it (the .use { } block handles that). resolveSize reconciles your desired size against the parent's MeasureSpec mode so EXACTLY is honored and AT_MOST is clamped.

// invalidate(): repaint only — re-records THIS view's display list
// requestLayout(): re-measure + re-layout this branch, then draw
fun setColor(c: Int) { paint.color = c; invalidate() }   // size unchanged
fun setRadius(r: Float) { radius = r; requestLayout() }   // size may change

Why onDraw() Avoids Allocations

🎤 Say it out loud (~30–45s): "onDraw() runs on the main thread on every dirty frame — potentially 60, 90, or 120 times a second — so anything you allocate in there gets allocated at that same rate. That builds up garbage fast, and when the GC kicks in to reclaim it you get a pause on the main thread, which is exactly the thread that's trying to render, so you drop a frame. The fix is dead simple: hoist your Paint, Rect, and Path objects to fields and reuse them. The gotcha interviewers like is that it's not just GC pauses — constant allocation also fills the young generation and triggers more frequent minor collections even when each one is fast."

onDraw() is called up to 60–120 times per second — every frame where the View is dirty. Allocating objects inside it causes three problems. First, it creates GC pressure: the garbage collector must periodically run to reclaim those short-lived allocations, and a GC pause on the main thread stalls the render loop, which means a dropped frame. Second, it defeats JIT optimization: hotspot allocation in tight loops inhibits JIT inlining and escape analysis. Third, it creates heap churn: even if GC is fast in the generational sense, frequent allocation fills the young generation and triggers more frequent minor GCs.

// BAD — allocates a Paint object every frame
override fun onDraw(canvas: Canvas) {
    val p = Paint().apply { color = Color.RED } // allocated 60+ times/sec
    canvas.drawRect(0f, 0f, 100f, 100f, p)
}

// GOOD — reuses pre-allocated object
private val paint = Paint().apply { color = Color.RED }
override fun onDraw(canvas: Canvas) {
    canvas.drawRect(0f, 0f, 100f, 100f, paint)
}

Tools to detect: Android Studio Memory Profiler, StrictMode (not for GC directly, but for disk/network on main thread). For GC pauses specifically: Android Vitals / Perfetto trace showing GC events.

Under the hood

Every Paint() allocation runs a Java/Kotlin new (a new-instance bytecode plus <init>), which on ART carries a JNI hop because Paint wraps a native SkPaint via a long mNativePaint handle — so each allocation is both a Java heap object and a native peer. ART's default collector (Concurrent Copying / CC, generationally configured) tracks Java objects in a bump-pointer region space; short-lived frame allocations land in the young region and survive only until the next minor GC. The collector is mostly concurrent, but it still imposes brief stop-the-world pauses to mark roots and flip references, and those pauses can land mid-frame on the UI thread.

onDraw() allocates Paint
  → ART bump-pointer alloc in young region (+ native SkPaint via NewGlobalRef-style handle)
  → young region fills after N frames
  → minor GC: brief STW root-mark + concurrent copy
  → if STW lands inside the 16.67ms budget → Choreographer#doFrame overruns → dropped frame

8.2 Choreographer, VSync, and Frame Rendering

Frame Deadlines

🎤 Say it out loud (~30–45s): "A frame deadline is the wall-clock budget you have to get all the CPU and GPU work done before the next display refresh. At 60 Hz that's about 16.7 milliseconds; at 90 it's 11.1; at 120 it's 8.3 — the faster the panel, the tighter the budget. The thing people miss is that this budget is split: the main thread does measure, layout, and records the draw list, then the RenderThread turns that into GPU commands, and both have to finish in time. So even if your main-thread work is fast, a heavy RenderThread or GPU stage can still blow the deadline."

A frame deadline is the time by which all CPU and GPU work for a frame must complete so the frame can be delivered to the display at the next refresh cycle.

  • At 60 Hz: ~16.67 ms per frame.
  • At 90 Hz: ~11.11 ms per frame.
  • At 120 Hz: ~8.33 ms per frame.

The frame deadline budget is split across the main thread (measure/layout/draw call recording) and the RenderThread (GPU command submission). Both must finish within the deadline.

Android "jank budget" breakdown:

  • Main thread: builds the display list (calls onDraw, composites layers, handles input). Target: < 4–6 ms.
  • RenderThread: translates display list to GPU commands, uploads textures. Target: < 4–6 ms.
  • GPU: executes the commands. Target: < remaining time.

If any stage misses the deadline, the frame is dropped and the previous frame is shown again.

Under the hood

The deadline isn't a single thread racing a clock — it's a pipeline. Since Project Butter (Android 4.1) the system pipelines stages across VSync intervals: the main thread records its work into a DisplayList, hands it to the RenderThread, and immediately starts the next frame while the RenderThread submits GPU commands. With triple buffering this means the main thread, RenderThread, and SurfaceFlinger can each be working on a different frame at the same time. The "16.67 ms" budget therefore applies per stage per VSync — a stage that consistently overruns one VSync interval pushes the whole pipeline back and SurfaceFlinger re-scans the previous buffer.

VSync N:    Main thread frame A ─┐
VSync N+1:  Main thread frame B  └→ RenderThread frame A ─┐
VSync N+2:  Main thread frame C    RenderThread frame B   └→ SurfaceFlinger composites A → display

VSync

🎤 Say it out loud (~30–45s): "VSync is the hardware pulse from the display that marks when it starts scanning out a new frame. Apps don't actually get the raw hardware signal — SurfaceFlinger subscribes to it and re-distributes a software VSync to each app through Choreographer, and that software signal is usually phase-offset so CPU and GPU work can be pipelined. The detail worth dropping is that Android uses triple buffering, so the app can start rendering the next frame right after submitting the current one without waiting for the compositor to finish."

VSync — short for Vertical Synchronization — is a hardware signal from the display that fires at the display's refresh rate. It marks the moment when the display starts scanning out a new frame.

Android doesn't hand the raw hardware VSync directly to apps. Instead, SurfaceFlinger (the system compositor) subscribes to the hardware signal and then distributes a software VSync signal via Choreographer to applications. This software VSync may be phase-offset from the hardware signal to pipeline CPU and GPU work. Apps are synchronized to this software VSync so frame rendering stays aligned with display refresh.

Android also uses triple buffering — three frame buffers: one being displayed, one being composited by SurfaceFlinger, and one being rendered by the app. This lets the app start the next frame immediately after submitting the current one, even if SurfaceFlinger hasn't finished compositing yet.

Under the hood

The hardware VSync arrives from the display driver into HWComposer; SurfaceFlinger maintains a DispSync model that predicts VSync timing and emits two offset software signals — VSYNC-app (which Choreographer listens to) and VSYNC-sf (which wakes SurfaceFlinger to composite). The offsets are deliberately staggered so the app gets a head start before the compositor needs the buffer. Buffers move between the app and SurfaceFlinger through a BufferQueue: the app dequeues a buffer, draws, and queues it; SurfaceFlinger acquires it for compositing; then it's released back. Synchronization uses fences rather than CPU blocking, so the GPU signals completion to the consumer without stalling the thread.

HW VSync → HWComposer → SurfaceFlinger DispSync
                              ├─ VSYNC-app (offset) → Choreographer → app renders → BufferQueue.queue()
                              └─ VSYNC-sf  (offset) → SurfaceFlinger.acquire() → composite → scanout

Choreographer and Frame Callbacks

🎤 Say it out loud (~30–45s): "Choreographer is the main-thread coordinator that receives the software VSync and fans it out to callbacks in a fixed order: input, then animation, then insets, then traversal — which is measure/layout/draw — then commit. The reason that ordering matters is that animation runs before traversal, so an animated property change is picked up in the very same frame's draw pass; there's no one-frame lag. Almost nobody posts frame callbacks directly — ValueAnimator, ViewPropertyAnimator, and Compose's withFrameNanos all sit on top of Choreographer for you."

Choreographer is the Android class that coordinates frame timing on the main thread. It receives VSync signals and dispatches them to registered callbacks.

// Low-level frame callback (rarely used directly in app code)
Choreographer.getInstance().postFrameCallback { frameTimeNanos ->
    // frameTimeNanos: timestamp in nanoseconds of the VSync that triggered this frame
    // Perform animation updates here
    if (animating) {
        Choreographer.getInstance().postFrameCallback(this)
    }
}

Frame callback types (in order of execution within a frame):

  1. CALLBACK_INPUT — processes input events.
  2. CALLBACK_ANIMATION — ValueAnimator, ObjectAnimator, view animations.
  3. CALLBACK_INSETS_ANIMATION — window inset animations.
  4. CALLBACK_TRAVERSAL — ViewRootImpl.performTraversals() (measure/layout/draw).
  5. CALLBACK_COMMIT — post-draw work.

The ordering has an important implication: input is processed before traversal, and animation updates happen before traversal too. That means if an animation updates a View property, the updated value is reflected in the same frame's draw pass — there is no one-frame lag.

ValueAnimator, ObjectAnimator, and View.animate() — the ViewPropertyAnimator — all drive themselves through Choreographer internally. In Compose, the withFrameNanos suspend function is the Compose-side equivalent.

Under the hood

Choreographer registers a FrameDisplayEventReceiver (a native DisplayEventReceiver) that listens for VSYNC-app on the main thread's Looper. When VSync fires, the receiver posts a message whose target invokes Choreographer.doFrame(frameTimeNanos, ...). doFrame first checks for a missed-VSync skip (logging "Skipped N frames!" when the main thread was busy), then walks the internal CallbackQueue[] — one queue per callback type — and runs each due CallbackRecord in the fixed INPUT → ANIMATION → INSETS_ANIMATION → TRAVERSAL → COMMIT order. Each posted callback is one-shot, which is why a running animation re-posts itself every frame. All callbacks for a frame share the same frameTimeNanos, so every animation in that frame samples from an identical timestamp and stays perfectly in sync.

VSYNC-app → DisplayEventReceiver.onVsync()
         → Handler message on main Looper
         → Choreographer.doFrame(frameTimeNanos):
              [skip check: "Skipped N frames!"]
              run CALLBACK_INPUT      queue
              run CALLBACK_ANIMATION  queue   (ValueAnimator.animateBasedOnTime)
              run CALLBACK_INSETS_ANIMATION
              run CALLBACK_TRAVERSAL  queue   (ViewRootImpl.performTraversals → measure/layout/draw)
              run CALLBACK_COMMIT     queue

Main-Thread Work and Frame Rendering

🎤 Say it out loud (~30–45s): "Every frame the main thread has a fixed to-do list: drain pending input, run animation callbacks, execute performTraversals for measure/layout/draw recording, and service any Handler messages that landed between frames. Anything that blocks that thread — disk reads, a synchronous commit(), a Room query on the main thread, decoding a big bitmap — eats into the frame budget and causes jank. My rule of thumb is that anything over roughly 4 milliseconds on the main thread is a real risk, so I push I/O and computation to Dispatchers.IO or Dispatchers.Default."

Every frame, the main thread must handle pending input events, run animation callbacks, execute ViewRootImpl.performTraversals() — which covers measure, layout, and draw recording — and respond to any Handler messages posted between frames.

What blocks the main thread and causes jank: network I/O (never do this — StrictMode.ThreadPolicy detects it); disk reads and writes (avoid them, use coroutines with Dispatchers.IO); long computation (move it to Dispatchers.Default); synchronous SharedPreferences commits (apply() is async, commit() is sync); database queries on the main thread (Room's allowMainThreadQueries() is a trap); overdone onDraw() or deeply nested measure passes; and large Bitmaps decoded synchronously.

The rule of thumb: any work taking more than roughly 4 ms on the main thread risks missing the frame deadline.

Under the hood

The main thread is a single Looper spinning MessageQueue.next(), and frame work is just one more message on that queue. Choreographer's VSync callback, your View.post{} runnables, Handler messages, and input dispatch all compete for the same serialized loop — there is no preemption. If a message's handleMessage/runnable runs long, the queue can't reach the next doFrame message until it returns, so the frame starts late and Choreographer reports skipped frames. This is why StrictMode works by wrapping I/O calls to detect when they execute on the thread tagged as the UI thread, and why moving work off-thread isn't optional — the loop literally cannot dispatch the frame callback while it's busy executing your code.

// Conceptually, the main thread is:
while (true) {
    val msg = messageQueue.next()   // blocks on nativePollOnce when idle
    msg.target.dispatchMessage(msg) // your work AND doFrame run here, serially
    msg.recycleUnchecked()
}
// A 30ms disk read inside one dispatchMessage() delays the next doFrame by 30ms → ~2 dropped frames at 60Hz.

Dropped Frames and Jank

🎤 Say it out loud (~30–45s): "A dropped frame happens when the app misses the VSync deadline, so the display just re-scans the previous buffer — at 60 Hz that's a 33 millisecond gap, two refresh cycles, and that visible stutter is what we call jank. I'd debug it with a Perfetto system trace, find the Choreographer#doFrame slice on the main thread, and see which phase — measure, layout, draw, or input — is over budget, then check the RenderThread for GPU-side stalls. The number to know is Google Play's bar: frozen frames over 700 ms should stay under 0.1 percent of frames."

A dropped frame occurs when the app fails to submit a rendered frame before the VSync deadline, so the previous frame repeats on screen. Jank is the perceptible stuttering that results from dropped frames — a single dropped frame at 60 Hz creates a 33 ms gap, two display cycles, between visual updates.

Threshold (Android Vitals):

  • "Slow frames": frames that take > 16 ms to render (at 60 Hz).
  • "Frozen frames": frames that take > 700 ms.
  • Google Play's core vitals threshold: < 0.1% frozen frames.

Debug approach:

  1. Reproduce the jank scenario.
  2. Capture a system trace with Android Studio Profiler → CPU → System Trace (Perfetto backend).
  3. Look at the Choreographer#doFrame slice on the main thread.
  4. Identify which phase (measure, layout, draw, input) is taking too long.
  5. Look at RenderThread for GPU-side bottlenecks.

Under the hood

A "dropped frame" is concretely a missed buffer swap: the app's buffer wasn't queued to the BufferQueue before SurfaceFlinger's acquire deadline, so HWComposer re-scans the buffer already on screen. Choreographer detects this after the fact by comparing the intended frameTimeNanos against the wall-clock time when doFrame actually ran; if the gap exceeds whole VSync intervals it logs Skipped N frames!. Modern measurement uses FrameMetrics / JankStats, which read per-phase nanosecond timings the framework records during traversal — UNKNOWN_DELAY, INPUT_HANDLING, ANIMATION, LAYOUT_MEASURE, DRAW, SYNC, COMMAND_ISSUE, SWAP_BUFFERS, TOTAL_DURATION — so you can attribute jank to a specific stage rather than guessing. Android Vitals aggregates these TOTAL_DURATION values across the install base to compute the slow/frozen-frame percentages.

FrameMetrics phases (ns) summed → TOTAL_DURATION
  UNKNOWN_DELAY  → main thread was busy with non-frame work before doFrame started
  INPUT_HANDLING + ANIMATION + LAYOUT_MEASURE + DRAW  → main-thread cost
  SYNC + COMMAND_ISSUE + SWAP_BUFFERS                 → RenderThread / GPU cost
TOTAL_DURATION > 16.7ms (60Hz) → slow frame ;  > 700ms → frozen frame

Frozen Frames

🎤 Say it out loud (~30–45s): "A frozen frame is any frame that takes more than 700 milliseconds to produce — that's the threshold Android Vitals uses for severe jank, and it usually means the main thread was effectively stuck. In practice these are ANR-adjacent: a blocking disk write, decoding a huge bitmap on the UI thread, or too much work crammed into the first Activity's onCreate. The gotcha interviewers want is that frozen frames are a Play Store ranking signal — if the rate goes above 0.1% it hurts your store visibility, so we treat it as a hard budget, not a nice-to-have."

A frozen frame is one where the app's main thread does not produce a new frame for more than 700 ms. That 700 ms number is the threshold Android Vitals uses to flag severe jank.

Common causes:

  • ANR-adjacent conditions (deadlocks, long synchronous operations).
  • Blocking SharedPreferences.commit() on a slow disk.
  • Cold-start work pushed into the first Activity's onCreate().
  • Synchronous Bitmap.decodeFile() on large images on the main thread.

Impact: Android Vitals reports frozen frames. A rate above 0.1% negatively affects Play Store ranking and user retention.

Under the hood

Frozen frames are detected the same way slow frames are: the framework's Choreographer schedules a VSYNC callback for each display refresh, and FrameMetrics/gfxinfo record the wall-clock duration between when input/animation/layout/draw begins and when the GPU buffer is queued. When the main thread blocks (e.g. inside a synchronous binder call to the SharedPreferences storage, or a long Bitmap.decodeFile), the Choreographer's doFrame callback simply doesn't run until the thread is free, so VSYNC pulses are missed and the recorded frame duration spans every missed interval. The 700 ms cutoff is a classification applied by the Android Vitals aggregation pipeline over the per-frame durations uploaded via Play services — it is the same telemetry an ANR watchdog consumes, which is why frozen frames so often correlate with ANRs.

VSYNC:   |----16.6ms----|----16.6ms----|---- ... ----|
main:    [====== blocking decodeFile (720ms) ======] queueBuffer
                                                      ^ one frame, duration ≈ 720ms → FROZEN

Slow Rendering

🎤 Say it out loud (~30–45s): "Slow rendering means a frame missed its refresh deadline — that's 16 milliseconds at 60Hz, or about 8.3 at 120Hz. Android Vitals buckets these into slow frames over the deadline and frozen frames over 700ms. The key nuance is that the deadline is refresh-rate dependent: a frame that's fine on a 60Hz device can be jank on a 120Hz panel, so I always measure on representative hardware. My loop is measure with Macrobenchmark, find the root cause in Perfetto, fix it, then re-measure to prove the win rather than eyeball it."

Android defines slow rendering as frames that exceed the per-refresh-cycle deadline — more than 16 ms at 60 Hz, or more than 8.33 ms at 120 Hz. The official developer documentation calls these "skipped frames perceived as jank."

Categories in Android Vitals:

  • Slow frames: > 16 ms (or refresh-rate deadline).
  • Frozen frames: > 700 ms.

Detection: adb shell dumpsys gfxinfo <package> outputs frame timing statistics:

Janky frames: 42 (3.50%)
50th percentile: 6ms
90th percentile: 14ms
95th percentile: 20ms
99th percentile: 88ms

Optimization loop:

  1. Measure baseline with Macrobenchmark.
  2. Profile with Perfetto to find root cause.
  3. Fix (flatten hierarchy, move work off main thread, use Baseline Profiles).
  4. Measure again to confirm improvement.

Under the hood

dumpsys gfxinfo reads from a ring buffer the framework maintains in the rendering pipeline. With profile graphics enabled, RenderThread records timestamps at each stage of the frame — VSYNC arrival, input handling, animation, traversal (measure/layout/draw recording on the UI thread), sync of the display list to RenderThread, GPU command issue, and buffer swap. Each frame's total is compared against the display's reported refresh period (queried from Display.getRefreshRate() / the DisplayManager), so the "deadline" is not a hardcoded 16 ms — it's 1000 / refreshRate. A frame is counted "janky" when its duration exceeds that period. The percentile histogram is computed over the recorded frames (default ring buffer of 120 frames), and the newer framestats block exposes the per-stage nanosecond timestamps so you can attribute a slow frame to UI-thread layout versus GPU-bound draw.

Frame stages (must all finish within ~16.6ms at 60Hz):
  VSYNC → Input → Animation → Layout/Measure/Draw(UI) → Sync → GPU issue → swap
  If sum > refresh period  ⇒ janky frame (slow render)

8.3 RecyclerView Performance

ViewHolder Pattern

🎤 Say it out loud (~30–45s): "The ViewHolder pattern caches the view references for one list row so we don't call findViewById on every bind — those lookups walk the view tree and add up fast during scroll. RecyclerView makes the pattern mandatory: createViewHolder inflates and caches references once, then bindViewHolder just pushes data into them as rows are recycled. I pair it with ViewBinding because that's null-safe and replaces the per-view map lookup with a direct field reference generated at compile time."

ViewHolder is a cache object that holds references to the Views within a single list item layout, eliminating repeated findViewById() calls on every bind.

Internals:

  • RecyclerView.ViewHolder is an abstract class. Each Adapter defines a concrete subclass.
  • Adapter.createViewHolder() inflates the item layout and stores View references in the ViewHolder.
  • Adapter.bindViewHolder() populates the stored Views with item data.
  • RecyclerView manages a pool of ViewHolder objects and calls bindViewHolder when recycling.
class MyAdapter : RecyclerView.Adapter<MyAdapter.VH>() {

    class VH(val binding: ItemMyBinding) : RecyclerView.ViewHolder(binding.root)

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): VH {
        val binding = ItemMyBinding.inflate(LayoutInflater.from(parent.context), parent, false)
        return VH(binding)
    }

    override fun onBindViewHolder(holder: VH, position: Int) {
        val item = items[position]
        holder.binding.title.text = item.title
        // Load image — see image cancellation section
    }

    override fun getItemCount() = items.size
}

ViewBinding — used in the template above — is preferred over findViewById() because it is null-safe and avoids a map lookup per view access.

Under the hood

findViewById is not free: it does a depth-first recursive walk of the View tree comparing each child's integer id field until it finds a match, so its cost scales with hierarchy depth and breadth and would otherwise repeat on every onBindViewHolder. The ViewHolder eliminates that by storing the resolved View references as fields on the holder once at inflation time. ViewBinding takes it further: the Android Gradle plugin's data-binding/view-binding compiler parses each layout XML at build time and generates a *Binding Java class whose constructor performs the findViewById calls exactly once and assigns them to final, typed, non-null fields — so at runtime holder.binding.title is a plain field load (a single getfield bytecode) rather than a tree search. Each row's View is also tagged with its ViewHolder via setTag, which is how RecyclerView maps a recycled View back to its holder.

// Generated by the view-binding compiler (simplified):
public final class ItemMyBinding {
    @NonNull public final TextView title;
    private ItemMyBinding(View root, TextView title) { this.title = title; }
    static ItemMyBinding bind(View root) {
        TextView title = root.findViewById(R.id.title); // resolved ONCE
        return new ItemMyBinding(root, title);
    }
}

Recycling Mechanics

🎤 Say it out loud (~30–45s): "When a row scrolls off, RecyclerView doesn't destroy it — it tries to reuse a holder from three tiers in order: the scrap heap for views that just detached and can be rebound cheaply, then the RecycledViewPool for views recycled from anywhere that need a full rebind, and only if both miss does it call onCreateViewHolder. The pool is partitioned by view type from getItemViewType, so a header holder never gets handed to an item slot — which is why each distinct type needs its own integer and its own onCreateViewHolder branch."

RecyclerView maintains a RecycledViewPool per view type. When a ViewHolder scrolls off screen, it is returned to the pool or to a scrap heap. When a new item needs to be displayed, RecyclerView tries to obtain a ViewHolder from three places in order: first the scrap heap, where ViewHolders that just detached may be rebound cheaply or reused as-is if stable IDs match; then the RecycledViewPool, where ViewHolders recycled from any position must be fully rebound; and finally onCreateViewHolder(), if both caches are empty.

getItemViewType(position) returns an int identifying the layout type. RecyclerView maintains separate pools per view type, so ViewHolders are only recycled within their type. When you have multiple view types — headers, items, footers, ads — return different integers from getItemViewType, and each type needs its own ViewHolder subclass and onCreateViewHolder branch.

override fun getItemViewType(position: Int): Int = when (items[position]) {
    is Header -> TYPE_HEADER
    is Item -> TYPE_ITEM
    else -> TYPE_FOOTER
}

Under the hood

The "three places" are managed by RecyclerView.Recycler, which actually holds several tiers: the mAttachedScrap and mChangedScrap lists (holders detached during the current layout pass), the mCachedViews list (a small LRU, default capacity 2, keyed by position so an item scrolled off and immediately back can be reused with no rebind at all), and finally the shared RecycledViewPool. The pool is a SparseArray<ScrapData> keyed by view type, each bucket capped at 5 holders by default, which is exactly why holders are confined to their type — a getItemViewType mismatch would mean handing a holder whose cached View references point at the wrong layout. Each ViewHolder carries a bitmask of flags (FLAG_BOUND, FLAG_UPDATE, FLAG_INVALID, etc.); the recycler consults these to decide whether a fetched holder can skip rebinding (clean, same position) or must go through bindViewHolder again. setHasStableIds(true) lets the changed-scrap path match holders by id so they survive a notifyDataSetChanged.

getViewForPosition() resolution order:
  1. mChangedScrap / mAttachedScrap   (in-layout detach, often no rebind)
  2. mCachedViews (LRU, by position)  (off-and-back, no rebind)
  3. RecycledViewPool[viewType]       (any position, FULL rebind)
  4. onCreateViewHolder()             (all caches missed → inflate)

DiffUtil

🎤 Say it out loud (~30–45s): "DiffUtil computes the minimal edit script between two lists with the Myers diff algorithm and dispatches granular notify calls — insert, remove, move, change — instead of nuking everything. That matters because notifyDataSetChanged rebinds every visible row and kills item animations, whereas DiffUtil only touches what actually changed and keeps the animations. The gotcha is cost: Myers is O(N + D²) in the edit distance, so for big lists I run calculateDiff off the main thread and post the result back, and I make sure areContentsTheSame is a real equality check, not just an id check."

DiffUtil computes the minimal set of updates — insertions, deletions, moves, and changes — between two lists using the Myers diff algorithm, then dispatches precise notifyItemInserted, notifyItemRemoved, notifyItemMoved, and notifyItemChanged calls. The key advantage over notifyDataSetChanged() is that notifyDataSetChanged() invalidates the entire list: every item is rebound, no add/remove/move animations play, and unchanged items are needlessly re-rendered. DiffUtil preserves those animations and avoids rebinding unchanged items.

class ItemDiffCallback : DiffUtil.ItemCallback<Item>() {
    override fun areItemsTheSame(old: Item, new: Item): Boolean = old.id == new.id
    override fun areContentsTheSame(old: Item, new: Item): Boolean = old == new
    // Optional: return partial update payload
    override fun getChangePayload(old: Item, new: Item): Any? {
        return if (old.title != new.title) "TITLE_CHANGED" else null
    }
}

The Myers diff algorithm is O(N + D²) where N is the list size and D is the edit distance. For large lists — thousands of items — you should run DiffUtil.calculateDiff() off the main thread via Dispatchers.Default and post the result back.

Under the hood

calculateDiff runs the Myers algorithm in two passes. First it calls areItemsTheSame to identify which entries represent the same logical item (by stable identity), producing the structural insertions, deletions, and moves; then for surviving items it calls areContentsTheSame to decide which need a content update, and getChangePayload to attach a partial-update token. The algorithm explores an edit graph and records the diagonal/snake of each "d-contour" in integer arrays (it doesn't build a full O(N×M) matrix), which is what gives the O(N + D²) bound — cheap when lists are similar, quadratic when they diverge heavily. The result is a DiffResult holding compact int arrays of operations; dispatchUpdatesTo(adapter) replays them as the granular notifyItem* calls. The payload returned by getChangePayload is delivered to the onBindViewHolder(holder, position, payloads) overload, letting you mutate just the changed view (e.g. one TextView) instead of rebinding the whole row — and a non-null payload also tells RecyclerView's ItemAnimator to skip the cross-fade change animation.

Pass 1 (areItemsTheSame): build edit graph → Myers snakes → INSERT/REMOVE/MOVE
Pass 2 (areContentsTheSame): for matched items → CHANGE (+ getChangePayload token)
DiffResult.dispatchUpdatesTo(adapter) → notifyItemInserted/Removed/Moved/Changed

ListAdapter

🎤 Say it out loud (~30–45s): "ListAdapter is a RecyclerView.Adapter that wraps AsyncListDiffer, so it runs DiffUtil on a background thread for me — I just call submitList with a new list and it computes the diff and dispatches the updates. Two traps I always call out: it compares by reference, so mutating the same list instance in place is invisible — you must pass a fresh copy. And submitList is serialized; a new submission cancels the in-flight diff, so rapid back-to-back submits without debouncing can drop an intermediate update."

ListAdapter<T, VH> is a RecyclerView.Adapter subclass that wraps AsyncListDiffer, automatically running DiffUtil on a background thread so you don't have to manage that yourself.

class MyListAdapter : ListAdapter<Item, MyListAdapter.VH>(ItemDiffCallback()) {

    class VH(val binding: ItemMyBinding) : RecyclerView.ViewHolder(binding.root)

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int) =
        VH(ItemMyBinding.inflate(LayoutInflater.from(parent.context), parent, false))

    override fun onBindViewHolder(holder: VH, position: Int) {
        holder.binding.title.text = getItem(position).title
    }
}

// In Fragment/Activity:
adapter.submitList(newList) // diff computed on background thread

Two trade-offs to know: submitList() with the same list object mutated in place will not detect changes — always pass a new list copy. And if submitList() is called again before the previous diff completes, the second call cancels the first, which can cause a "lost update" if rapid submissions are not debounced.

Under the hood

ListAdapter delegates to an AsyncListDiffer, which holds the current list and an AsyncDifferConfig carrying the ItemCallback and two executors: the main-thread executor and a background executor (a shared single-thread pool by default). Each submitList increments an internal mMaxScheduledGeneration counter, snapshots the old and new lists, and posts DiffUtil.calculateDiff to the background executor. When the diff finishes it re-checks that its generation still equals the latest counter before posting back to the main thread — if a newer submitList arrived meanwhile, the stale result is discarded, which is exactly the "lost update" / cancellation behavior. The reference-equality trap comes from the fast path: submitList first checks newList === mList and returns immediately if they're the same object, so an in-place mutation never even reaches the differ. The final dispatch happens on the main thread via the same DiffResult.dispatchUpdatesTo mechanism, and getItem(position) always reads from the differ's committed snapshot, keeping adapter reads consistent with what's currently laid out.

submitList(new):
  if (new === current) return            // ← in-place mutation ignored
  gen = ++maxScheduledGeneration
  bgExecutor: result = calculateDiff(old, new)
  mainExecutor: if (gen == maxScheduledGeneration)   // newer submit cancels this
                  commit(new); result.dispatchUpdatesTo(adapter)
                else drop                              // ← lost update

Stable IDs

🎤 Say it out loud (~30–45s): "Stable IDs let me give RecyclerView a durable identity per item via getItemId(), so when I call notifyDataSetChanged() it can match old and new ViewHolders by ID and animate or reuse the ones that didn't move instead of blindly rebinding everything. The gotcha is that the IDs must be truly unique and consistent — if two items collide or an ID changes for the same logical item, you get swapped content and flickering animations. In practice I reach for DiffUtil/ListAdapter instead, which computes precise diffs and is harder to get wrong."

When setHasStableIds(true) is set and getItemId() returns a unique, consistent ID per item, RecyclerView can use those IDs to match old and new ViewHolders without rebinding.

init { setHasStableIds(true) }
override fun getItemId(position: Int) = items[position].id.toLong()

When you use notifyDataSetChanged(), stable IDs let RecyclerView reuse and animate ViewHolders that didn't change. Without them, notifyDataSetChanged() always rebinds everything regardless. That said, stable IDs are mostly superseded by DiffUtil/ListAdapter, which is generally more powerful and correct. Misuse — returning non-unique IDs — causes visual artifacts.

Under the hood

When notifyDataSetChanged() fires, RecyclerView invalidates all attached ViewHolders. With stable IDs enabled, instead of treating every position as dirty it builds a mapping keyed by item ID. The ViewInfoStore records each ViewHolder's pre-layout and post-layout ItemHolderInfo, and the layout pass matches them by mItemId rather than by adapter position. A matched holder is moved/reused (and can run a change/move animation via the ItemAnimator) instead of being rebound. Internally each ViewHolder carries mPosition, mItemId, and a mFlags bitset; with stable IDs the FLAG_UPDATE/FLAG_INVALID handling consults the ID map so unchanged holders skip onBindViewHolder.

notifyDataSetChanged() + hasStableIds:
  for each old ViewHolder: key by mItemId
  match new positions by ID  -> reuse holder, run move/change anim
  no ID match                -> recycle to pool, bind fresh holder
(without stable IDs: every holder marked invalid -> full rebind)

Payload Updates

🎤 Say it out loud (~30–45s): "A payload is an arbitrary object I pass to notifyItemChanged(position, payload) so the adapter knows what changed, not just that it changed. In onBindViewHolder I get the payload list and can update just the title, skipping an expensive image reload. The key nuance is that the payloads list being empty means a full rebind is required — that happens after a recycle or when any partial-update consumer is missing — so I always handle the empty case by falling back to the full bind, otherwise I end up with stale or blank views."

Payloads are optional objects you attach to notifyItemChanged(position, payload) calls that allow partial rebinding — updating only the changed portion of a ViewHolder without triggering a full rebind.

// Dispatch with payload
adapter.notifyItemChanged(position, "TITLE_CHANGED")

// Handle in onBindViewHolder
override fun onBindViewHolder(holder: VH, position: Int, payloads: MutableList<Any>) {
    if (payloads.isEmpty()) {
        super.onBindViewHolder(holder, position, payloads)
        return
    }
    for (payload in payloads) {
        if (payload == "TITLE_CHANGED") {
            holder.binding.title.text = getItem(position).title
            // Skip reloading image, etc.
        }
    }
}

The benefit is avoiding canceled and restarted expensive image loads when only a text field changed.

Under the hood

Each payload is appended to a per-ViewHolder list. Internally ViewHolder holds an mPayloads List<Object> (lazily backed by an unmodifiable view); successive notifyItemChanged calls with payloads accumulate into it as long as the holder hasn't been rebound or recycled. During layout, AdapterHelper coalesces update ops into UpdateOp entries that carry the payload. If at dispatch time any update on that position arrives with a null payload, RecyclerView clears mPayloads and forces a full bind — that's why the list can come back empty. DiffUtil participates by returning a change payload from getChangePayload(), which AdapterListUpdateCallback forwards into notifyItemRangeChanged(position, count, payload).

notifyItemChanged(pos, "TITLE_CHANGED")  -> holder.mPayloads += "TITLE_CHANGED"
notifyItemChanged(pos, "AVATAR_CHANGED") -> holder.mPayloads += "AVATAR_CHANGED"
notifyItemChanged(pos) /* null */        -> holder.mPayloads cleared -> full rebind

Item Decoration

🎤 Say it out loud (~30–45s): "An ItemDecoration is how I draw dividers, spacing, or badges around items without polluting the item views or layouts themselves. I override getItemOffsets to reserve space — that feeds into the item's measured bounds — and onDraw/onDrawOver to paint behind or in front of the items on the RecyclerView's own canvas. The gotcha is that decorations are queried during layout and drawn on every frame, so heavy work in onDraw is a scroll-jank risk; I keep Paint and Drawable objects allocated once, not per call."

RecyclerView.ItemDecoration lets you draw additional content around or between items — dividers, spacing, badges — without modifying the item views themselves.

class DividerItemDecoration : RecyclerView.ItemDecoration() {
    private val divider = DividerDrawable()

    override fun onDraw(c: Canvas, parent: RecyclerView, state: RecyclerView.State) {
        for (i in 0 until parent.childCount - 1) {
            val child = parent.getChildAt(i)
            divider.setBounds(child.left, child.bottom, child.right, child.bottom + divider.intrinsicHeight)
            divider.draw(c)
        }
    }

    override fun getItemOffsets(outRect: Rect, view: View, parent: RecyclerView, state: RecyclerView.State) {
        outRect.bottom = divider.intrinsicHeight  // reserve space for divider
    }
}
recyclerView.addItemDecoration(DividerItemDecoration())

Key methods:

  • onDraw() — draws behind item views.
  • onDrawOver() — draws in front of item views (overlays).
  • getItemOffsets() — adds padding around items for layout.

Under the hood

Decorations are stored in RecyclerView's mItemDecorations list. During measurement/layout, LayoutManager.measureChildWithMargins calls getItemDecorInsetsForChild, which sums every decoration's getItemOffsets into a cached Rect stored on the child's LayoutParams (mDecorInsets); these insets are added to the child's measured dimensions so the item view physically reserves room. At draw time, RecyclerView.onDraw iterates the list calling each onDraw(c, parent, state) before the children are drawn (super.draw paints the items), and RecyclerView.draw calls onDrawOver after, so over-draws land on top. The insets are recomputed only when mDecorInsetsDirty is set, which is why adding/removing a decoration calls markItemDecorInsetsDirty() to invalidate them.

layout:  child.measured += Σ getItemOffsets()   (cached in LayoutParams.mDecorInsets)
draw:    for d in decorations: d.onDraw()        // behind
         drawChildren()
         for d in decorations: d.onDrawOver()    // in front

LayoutManager

🎤 Say it out loud (~30–45s): "The LayoutManager owns measuring and positioning of item views and decides which positions are visible, so it's really what drives recycling — it asks the Recycler for a view at a position and detaches/scraps views as they leave the viewport. RecyclerView gives me Linear, Grid, and StaggeredGrid out of the box. A custom one is doable but genuinely hard: you have to implement onLayoutChildren, the scroll methods, and recycle off-screen views yourself, and getting state restoration and predictive animations right is where most people get burned."

LayoutManager is responsible for measuring and positioning item Views within RecyclerView. It drives the recycling mechanism by telling RecyclerView which positions are currently visible.

Built-in implementations:

You must implement generateDefaultLayoutParams(), onLayoutChildren(), canScrollVertically()/canScrollHorizontally(), and scrollVerticallyBy()/scrollHorizontallyBy(), and you have to handle recycling correctly throughout.

Under the hood

The LayoutManager never creates views directly — it calls Recycler.getViewForPosition(position), which walks a tiered cache: the attached scrap (views detached this layout pass), the mCachedViews one-/two-deep cache (kept fully bound), the optional ViewCacheExtension, then the RecycledViewPool (bind required), and finally onCreateViewHolder on a miss. During scroll, scrollVerticallyBy offsets children via offsetChildrenVertical, fills newly exposed space, and calls recycleViewsFromStart/End to scrap views that scrolled off, returning them to the pool. onLayoutChildren runs in two passes when predictive animations are on (supportsPredictiveItemAnimations()): a pre-layout pass capturing ItemHolderInfo, then a real layout, and the diff feeds the ItemAnimator. LinearLayoutManager drives this with an internal LayoutState (current position, available space, scroll direction) and an AnchorInfo that fixes the reference child for layout and state restoration.

Prefetch

🎤 Say it out loud (~30–45s): "Prefetch is RecyclerView's GapWorker using the idle time between frames to pre-create and pre-bind ViewHolders for items it predicts will scroll into view during a fling, so they're ready in the cache instantly. The LayoutManager reports how many to fetch — two by default for linear — and during nested lists I bump initialPrefetchItemCount on the inner LayoutManager so the inner rows are warmed too. The trade-off is it spends CPU during what would be slack time; if onBindViewHolder is genuinely heavy, the deadline before the next frame can lapse and the prefetch simply doesn't land, so it's an optimization, not a guarantee."

RecyclerView's prefetch mechanism — part of GapWorker, introduced in API 25 — predicts which items will become visible during a fling and pre-creates and pre-binds their ViewHolders on the RenderThread during idle time, before they are actually needed.

There are three parts to how it works. LayoutManager tells RecyclerView how many items to prefetch via setInitialPrefetchItemCount() — the default for LinearLayoutManager is 2. During a fling, GapWorker runs on the RenderThread in the gap between frames, performing onCreateViewHolder() and onBindViewHolder() for off-screen items. Those pre-bound ViewHolders are then placed in the RecycledViewPool or a prefetch cache, ready to be shown instantly.

For nested RecyclerViews, call setInitialPrefetchItemCount() on the inner LinearLayoutManager:

innerLayoutManager.initialPrefetchItemCount = 4 // pre-bind 4 items per inner list

The trade-off is that prefetch consumes CPU during what would otherwise be idle time. For very heavy onBindViewHolder() calls, prefetch may not complete in time to actually help.

Under the hood

GapWorker is a thread-local Runnable posted to the main Handler via the Choreographer frame callback chain. After a frame's traversal, RecyclerView posts the worker with a deadline equal to the start of the next frame (frameTimeNanos + frameIntervalNanos). The worker collects prefetch requests from every active RecyclerView through LayoutManager.collectAdjacentPrefetchPositions (which uses fling velocity to predict direction) and collectInitialPrefetchPositions for nested lists, then sorts tasks so views needed soonest and most likely go first. Each task calls Recycler.tryGetViewHolderForPositionByDeadline; the holder is created and bound only if it estimates it can finish before the deadline (mCreateRunningAverageNs/mBindRunningAverageNs track per-type timing). Successfully prefetched holders are parked in mCachedViews flagged so they aren't recycled away before being displayed. Despite the older "RenderThread" framing, the actual create/bind work runs on the UI thread during the inter-frame gap.

frame N traversal done -> post GapWorker with deadline = frameStart(N+1)
GapWorker:
  collect prefetch positions (adjacent + nested), sort by viewVelocity/distance
  for task: if estimatedBindTime < timeRemaining -> create + bind -> park in mCachedViews
            else -> defer

Nested RecyclerViews

🎤 Say it out loud (~30–45s): "The classic shelf UI is a horizontal RecyclerView inside each row of a vertical one, and two things bite you: by default each inner list has its own RecycledViewPool, so identical item types get recreated per row, and inner scroll position resets when a row is recycled. I fix the first by sharing one RecycledViewPool across all the inner lists, and the second by saving the inner LayoutManager's state into a map keyed by a stable item ID in onViewRecycled and restoring it in onBindViewHolder. The subtle part is keying by item ID, not adapter position — position shifts on inserts, so position-keyed state ends up restored onto the wrong row."

The pattern is a horizontal RecyclerView inside each row of a vertical RecyclerView — common in "shelf" UIs like Netflix. There are two challenges to solve. First, the RecycledViewPool is not shared: by default each row's horizontal RecyclerView has its own pool, so on rebind it destroys and recreates ViewHolders. Second, scroll state is not preserved: when a row is recycled and rebound, its horizontal scroll position resets.

Solutions:

// Share RecycledViewPool across all inner RecyclerViews
val sharedPool = RecyclerView.RecycledViewPool()
sharedPool.setMaxRecycledViews(TYPE_ITEM, 20)

// In onBindViewHolder for the outer adapter:
holder.innerRecyclerView.setRecycledViewPool(sharedPool)
holder.innerRecyclerView.layoutManager?.also { lm ->
    (lm as LinearLayoutManager).initialPrefetchItemCount = 4
}
// Preserve scroll state in a map keyed by item ID
private val scrollStates = HashMap<Long, Parcelable?>()

override fun onBindViewHolder(holder: VH, position: Int) {
    val itemId = getItemId(position)
    val state = scrollStates[itemId]
    holder.innerRecyclerView.layoutManager?.onRestoreInstanceState(state)
}

override fun onViewRecycled(holder: VH) {
    val itemId = getItemId(holder.absoluteAdapterPosition)
    scrollStates[itemId] = holder.innerRecyclerView.layoutManager?.onSaveInstanceState()
}

Under the hood

A RecycledViewPool is internally a SparseArray<ScrapData> keyed by view type, each ScrapData holding an ArrayList<ViewHolder> plus its max size and the running create/bind timing averages prefetch consults. Because it's owned per-RecyclerView by default, sharing one instance via setRecycledViewPool lets every inner list draw from the same warmed pool — but it only helps when the inner lists use the same view types and the same adapter view-type IDs, otherwise the type buckets don't overlap. The pool also stores an "attach count" so it isn't cleared while any RecyclerView still references it. For scroll state, LinearLayoutManager.onSaveInstanceState serializes a SavedState parcelable capturing the anchor position and offset; restoring sets mPendingSavedState, applied on the next onLayoutChildren. Keying the map by getItemId (requiring stable IDs) survives reordering because the map entry tracks the logical item, whereas position is reassigned whenever rows are inserted or removed.

shared pool: every inner RV pulls/returns holders to the same buckets (same viewType ids required)

  onViewRecycled -> save under itemId ; onBindViewHolder -> restore under itemId

Avoiding Heavy Bind Work

🎤 Say it out loud (~30–45s): "onBindViewHolder runs on the main thread for every item that scrolls into view, so it has to finish in roughly a millisecond or it eats into the frame budget and causes jank. My rule is that binding should be pure assignment — just plug pre-computed values into views. Anything expensive, like decoding bitmaps, building Spannables, or formatting strings, I do upfront in the ViewModel and pass down ready-to-use. The gotcha interviewers probe is that even the work feels cheap, like a single SpannableString with a dozen spans, adds up when it runs sixty times a second during a fling."

onBindViewHolder() must complete in under roughly 1 ms to avoid contributing to frame jank. Heavy work that can blow that budget includes synchronous image decoding, complex string formatting, SpannableString creation with many spans, and deserializing data in-place.

The fixes: pre-process data in the ViewModel before passing it to the adapter — format strings, build Spannables, decode thumbnails there, not in onBindViewHolder. Use Glide or Coil for async image loading, since they handle decoding off the main thread. And cache SpannableStrings in the data model if they don't change.

Under the hood

onBindViewHolder is invoked synchronously by RecyclerView from inside tryGetViewHolderForPositionByDeadline, which itself runs during the measure/layout pass on the main thread. The deadline parameter is the key mechanism: RecyclerView computes a per-frame deadline from Choreographer's frame timing and will skip prefetching new holders if binding is predicted to exceed it. Because bind happens inline with layout, any blocking call (a synchronous BitmapFactory.decodeStream, a String.format with locale lookup, a regex compile) directly extends the time before Choreographer's doFrame can hand the frame to the render thread, so a 16.6 ms (or 8.3 ms at 120 Hz) wall-clock window is missed and the frame is dropped.

Choreographer.doFrame
  └─ View.measure/layout
       └─ RecyclerView.onLayoutChildren
            └─ LayoutManager.fill → next()
                 └─ tryGetViewHolderForPositionByDeadline
                      └─ bindViewHolder → onBindViewHolder  ← your code, on the clock

Image Loading Cancellation

🎤 Say it out loud (~30–45s): "When a ViewHolder is recycled it can still have an image request in flight for the old URL, and once it's rebound to a new item you've got two requests racing for the same ImageView. If the older one resolves last, you see the wrong image — that's the classic recycling flicker. Glide and Coil solve this by keying the request to the target view, so starting a new load automatically cancels the prior one on that view. I still call clear() in onViewRecycled to release the in-flight request and avoid leaking work for views that scrolled off and never got rebound."

When a ViewHolder is recycled, it may still have an in-flight image load request. If that recycled ViewHolder is rebound with a different URL, two requests compete for the same ImageView. The earlier request may finish last and show the wrong image — the classic "image flicker" bug. The solution with Glide:

override fun onBindViewHolder(holder: VH, position: Int) {
    Glide.with(holder.itemView)
        .load(item.imageUrl)
        .into(holder.binding.image) // Glide automatically cancels the previous request on this ImageView
}

override fun onViewRecycled(holder: VH) {
    Glide.with(holder.itemView).clear(holder.binding.image) // explicit cancel on recycle
}

Glide tracks requests by ImageView instance and automatically cancels the previous request when a new one is started on the same target. Coil behaves similarly.

Under the hood

Glide stores the active request on the target ImageView itself using View.setTag(id, request) with a Glide-internal view-tag id, retrievable via getTag. When you call .into(view), Glide reads the existing tag, calls clear() on the previous Request (which transitions it to a cancelled state and removes its callbacks from the engine's job queue), and then sets the new request as the tag. The decode/network work runs on Glide's executor pools; cancellation flips an isCancelled flag that the EngineJob checks before delivering the bitmap to the main-thread callback, so a late-finishing decode is dropped instead of being set on the view. Coil uses the same view-tag pattern via ViewTargetRequestManager and ties the request's Job to the view, cancelling it when a new request attaches.

view tag ──▶ Request_A (URL_A, running)
.into(view) with URL_B:
  read tag → Request_A.clear()  (cancel, detach callbacks)
  view tag ──▶ Request_B (URL_B, running)
Request_A finishes late → isCancelled == true → bitmap discarded

Pagination

🎤 Say it out loud (~30–45s): "Pagination means loading data in pages as the user scrolls instead of pulling the whole dataset into memory upfront, which keeps memory flat and the first screen fast. I reach for Paging 3 because it owns the hard parts — it dedupes in-flight requests, retries on error, exposes a unified LoadState for spinners and retry buttons, and caches pages across config changes with cachedIn. The nuance interviewers like is getRefreshKey: when the list refreshes you want to reload around the user's current anchor position, not jump back to page one."

Pagination loads data incrementally as the user scrolls, preventing the app from loading the entire dataset upfront.

Paging 3 library (recommended):

// DataSource
class ItemPagingSource : PagingSource<Int, Item>() {
    override suspend fun load(params: LoadParams<Int>): LoadResult<Int, Item> {
        val page = params.key ?: 1
        return try {
            val response = api.getItems(page = page, size = params.loadSize)
            LoadResult.Page(
                data = response.items,
                prevKey = if (page == 1) null else page - 1,
                nextKey = if (response.items.isEmpty()) null else page + 1
            )
        } catch (e: Exception) {
            LoadResult.Error(e)
        }
    }
    override fun getRefreshKey(state: PagingState<Int, Item>) = state.anchorPosition?.let { anchor ->
        state.closestPageToPosition(anchor)?.prevKey?.plus(1)
            ?: state.closestPageToPosition(anchor)?.nextKey?.minus(1)
    }
}

// ViewModel
val pager = Pager(PagingConfig(pageSize = 20)) { ItemPagingSource() }
    .flow.cachedIn(viewModelScope)

// Adapter
class ItemPagingAdapter : PagingDataAdapter<Item, VH>(ItemDiffCallback()) { ... }

// Fragment
lifecycleScope.launch {
    viewModel.pager.collectLatest { pagingData ->
        adapter.submitData(pagingData)
    }
}

LoadStateAdapter displays loading spinners and retry buttons at the list head or foot based on PagingDataAdapter.loadStateFlow.

Under the hood

Pager.flow emits a new PagingData each time the PagingSource is invalidated; each PagingData wraps a single-shot cold flow of PageEvents (Insert, Drop, LoadStateUpdate). PagingDataAdapter connects to it through an internal AsyncPagingDataDiffer, which holds a PagePresenter snapshot and runs DiffUtil on a background Dispatcher to translate page inserts/drops into notifyItemRangeInserted/Removed calls — that's why you never call notifyDataSetChanged yourself. Loading is triggered by access: when the adapter binds a position near the end of the loaded window, differ.getItem(position) calls back into the presenter, which schedules the next load() on the PagingSource via the PageFetcher. cachedIn(scope) inserts a multicast/replay operator so the most recent PagingData survives configuration changes and is shared among collectors instead of re-fetching from page one. getRefreshKey is consulted only on invalidation-driven refresh to pick the new initial key from the anchorPosition the user was viewing.

8.4 Jetpack Compose Rendering

Compose's rendering pipeline has three phases per frame — analogous to but distinct from the View system. Composition is what to display: Compose calls @Composable functions and builds the slot table. Layout is where to display it: it measures and positions layout nodes. Drawing is how to render it: it executes draw commands on Canvas.

The key insight is that state changes restart from the earliest affected phase. A state change in a DrawModifier only re-runs drawing. A state change that affects size triggers layout plus drawing. A state change that adds or removes composables triggers full recomposition.

Composition

🎤 Say it out loud (~30–45s): "Composition is the first phase where Compose runs your @Composable functions and records the UI they describe into a structure called the slot table. The crucial detail is that it's positional — remember and state are keyed by where the call happens in the call tree, not by a name or map key. That's why calling composables inside a non-keyed loop or a conditional can shuffle that positional identity and make remembered state attach to the wrong element. So composition isn't building a View tree directly; it's writing into a gap-buffer-like table the runtime later uses to emit and update layout nodes."

Composition is the process of executing @Composable functions to build the UI tree — called the "slot table" internally, which is a data structure of groups and nodes.

Internals:

  • The Compose runtime maintains a Composer that tracks the current position in the slot table.
  • When a @Composable function executes, it "emits" nodes — layout nodes, effect nodes — into the slot table at its current position.
  • remember keys store values in the slot table at a specific position — it's positional, not a map lookup.
  • The slot table is a compact array-based tree, not a DOM. It is private to the Compose runtime.

Composition runs on first composition when a ComposeView or setContent {} is called, and then again as recomposition whenever a state value read during composition changes.

Under the hood

The Compose compiler plugin rewrites every @Composable function to take an extra synthetic Composer parameter plus a changed bitmask, and wraps the body in composer.startRestartGroup(key) / endRestartGroup(), where key is a compile-time hash of the source position. The SlotTable itself is two parallel arrays — an IntArray (groups) holding group metadata (parent, size, key, node count, data-anchor offsets) and an Array<Any?> (slots) holding the actual values (remembered objects, parameters, LayoutNode references). A SlotWriter mutates it via a gap buffer: the runtime moves a "gap" to the edit position so inserts/removes are amortized O(1) instead of shifting the whole array. remember { ... } compiles to composer.cache(invalid, factory), which checks the slot at the current position and either returns the stored value or evaluates the lambda and writes it. "Positional memoization" means identity is the path of group keys from the root, which is exactly why key(id) { ... } exists — to inject an explicit key so reordering doesn't corrupt slot alignment.

groups: [ key | nodes | size | parentAnchor | dataAnchor ] ...   (IntArray)
slots:  [ remembered, params, LayoutNode, RememberObserver ... ] (Array<Any?>)
        ▲ SlotWriter gap buffer moves the gap to the edit cursor

Recomposition

🎤 Say it out loud (~30–45s): "Recomposition is Compose re-running only the composables whose observed state actually changed, rather than rebuilding the whole tree. It rests on three guarantees: it's selective so unchanged, stable inputs get skipped; it's idempotent because the runtime may re-run a composable many times, out of order; and it's restartable because the compiler generates a restart lambda per composable. The gotcha is that 'selective' depends on stability and reading state at the right scope — an unstable parameter or reading state too high in the tree forces a parent to recompose and drags its children along, which is the root of most over-recomposition bugs."

Recomposition is the process of re-executing @Composable functions whose inputs have changed, to update the UI tree to reflect new state.

It has three key properties. First, it is selective: only composables whose read state has changed are re-executed; composables with unchanged inputs are skipped if they are stable and skippable. Second, it is idempotent: composables should produce the same output for the same inputs, because they may be re-executed multiple times, out of order, or in parallel in future Compose versions. Third, it is restartable: the Compose compiler generates restart lambdas so the runtime can re-execute any composable from its entry point.

What triggers recomposition: a mutableStateOf, mutableStateListOf, or mutableStateMapOf value that was read during composition is written to; a StateFlow, LiveData, or Flow collected with collectAsState() emits a new value; or a remember block's keys change.

What does not trigger recomposition: writing to state that was not read in the current composition scope, or calling a function that does not read any state.

Under the hood

State reads are tracked by Snapshot observation. A MutableState created by mutableStateOf is a StateObject backed by SnapshotMutableStateImpl; reading its .value calls readable(), which invokes the current snapshot's readObserver. During composition the Recomposer installs an observer that records, for each RecomposeScope (the restartable region created by startRestartGroup), exactly which state objects it read. When you write .value, the new value is recorded against the current snapshot and, on Snapshot.apply(), an applyObserver fires; the Recomposer looks up every RecomposeScope that read that object and marks it invalid. On the next frame (driven by withFrameNanos/Choreographer), only those invalidated scopes are re-run by invoking their stored restart lambda. "Skippable" is a separate compiler decision: if every parameter type is @Stable/@Immutable, the generated code compares each argument against the value stored in the slot table using the changed bitmask and equals, and short-circuits the body when nothing changed. Unstable types (e.g., a plain List, or a class the compiler can't prove stable) are assumed changed every time, forcing re-execution.

// Conceptually, the compiler turns this:
@Composable fun Greeting(name: String) { Text(name) }

// into roughly this:
fun Greeting(name: String, $composer: Composer, $changed: Int) {
    $composer.startRestartGroup(0xKEY)
    // skip if param unchanged AND scope not invalidated
    if ($changed and 0b0110 == 0b0010 && $composer.skipping) {
        $composer.skipToGroupEnd()
    } else {
        Text(name, $composer, ...)        // reads name; Text reads no observed state here
    }
    $composer.endRestartGroup()?.updateScope { c, _ -> Greeting(name, c, $changed or 1) }
}

Layout Phase

🎤 Say it out loud (~30–45s): "After composition produces a tree of LayoutNodes, the layout phase measures and places them in a single pass: each node gets Constraints from its parent, measures its children once, decides its own size, then positions them. That single-pass model is O(n) and forbids measuring a child twice, which is why Compose throws if you try — it's a deliberate guard against the exponential double-measure blowup you can hit with nested wrap_content in the View system. The escape hatch when you genuinely need multi-pass measurement, like matching two children's heights, is intrinsic measurements or SubcomposeLayout."

In Compose, the layout phase is handled by LayoutNodes — internal nodes in the composition tree. Composable functions like Box, Column, Row, and Layout emit LayoutNodes.

The key design difference from the View system is that Compose uses a single-pass measurement approach. Each LayoutNode receives Constraints — min/max width and height — from its parent, measures its children, and returns its own size. This is O(n) per composable, which avoids the exponential worst case you can hit with nested WRAP_CONTENT in the View system.

Custom Layout:

@Composable
fun MyLayout(content: @Composable () -> Unit) {
    Layout(content = content) { measurables, constraints ->
        val placeables = measurables.map { it.measure(constraints) }
        val width = placeables.maxOf { it.width }
        val height = placeables.sumOf { it.height }
        layout(width, height) {
            var y = 0
            placeables.forEach { placeable ->
                placeable.placeRelative(0, y)
                y += placeable.height
            }
        }
    }
}

Under the hood

Each LayoutNode owns a MeasurePassDelegate and is the unit of layout. Measurement and placement are scheduled, not run eagerly: when a node is invalidated (requestRemeasure), the owner (AndroidComposeView) adds it to a MeasureAndLayoutDelegate that holds a DepthSortedSet keyed by tree depth, so parents are always processed before children in one top-down sweep during the dispatchOnGlobalLayout/measure pass. Calling measurable.measure(constraints) returns a Placeable; the runtime asserts each Measurable is measured exactly once per pass and throws IllegalStateException if you call measure twice — that invariant is what guarantees the O(n) single pass. Constraints is a packed inline class over a single Long, encoding min/max width and height in bit fields to avoid allocation. Intrinsics work by running a separate synthetic measurement against an IntrinsicMeasureScope (max/min width/height queries) so a parent can ask "how big would you be?" without violating the measure-once rule; SubcomposeLayout goes further by deferring composition of children until measure time, composing them inside the measure lambda once the constraints are known.

invalidate → requestRemeasure(node)
   └─ MeasureAndLayoutDelegate.relayoutNodes (DepthSortedSet, shallow→deep)
        └─ node.remeasure(constraints)
             └─ MeasurePolicy.measure(measurables, constraints)
                  ├─ measurable.measure(c) → Placeable   (exactly once)
                  └─ layout(w, h) { placeable.place(x, y) }   (placement deferred)

Drawing Phase

🎤 Say it out loud (~30–45s): "The drawing phase is where Compose records the actual paint commands — circles, text, images — into a RenderNode, which is the same display-list primitive the View system uses for hardware acceleration. The key thing I emphasize is that drawing is the cheapest phase to invalidate: if only a color changes, Compose can re-record the draw without re-running composition or layout, which is exactly why Modifier.drawBehind with a lambda reading state is so much cheaper than recomposing."

Compose drawing works similarly to the View system's hardware-accelerated path: drawing commands are recorded into a RenderNodeLayer, which wraps android.graphics.RenderNode. Compose composables that use Modifier.drawBehind, Modifier.drawWithContent, Canvas {}, and similar drawing modifiers all record commands in this phase.

@Composable
fun BlueDot() {
    Box(
        modifier = Modifier
            .size(50.dp)
            .drawBehind {
                drawCircle(color = Color.Blue) // records into RenderNode — no allocation needed here per se
            }
    )
}

Under the hood

A RenderNodeLayer holds a native RenderNode, which is a GPU-friendly display list — a serialized buffer of drawing operations (drawCircle, drawText, transforms, clips). When Compose draws, it records these ops into the RenderNode's buffer once; on subsequent frames where nothing in that layer changed, the system replays the existing display list directly on the render thread via HardwareRenderer, never re-executing your DrawScope lambda. A draw-only invalidation just re-records that one node's buffer; properties like translation, alpha, and rotation live on the RenderNode itself and can be mutated without re-recording at all, so the render thread reuses the same display list.

DrawScope lambda  ──record──▶  RenderNode (native display list buffer)
                                   │
   transform/alpha/clip  ─────────┤ (mutable props, no re-record)
                                   ▼
                          HardwareRenderer (render thread) ──▶ GPU

State Reads and Snapshot State

🎤 Say it out loud (~30–45s): "Snapshot state is Compose's version of MVCC — each mutableStateOf keeps versioned records of its value, and a snapshot is a consistent, isolated view of all of them. During composition Compose installs a read observer, so any .value read gets recorded against the composable that read it; when you write that state, the affected scopes are marked invalid and scheduled for recomposition. The subtle part interviewers probe is isolation: because composition can be snapshotted and even rolled back, composables must be side-effect free, since a re-run inside a discarded snapshot would lose those effects."

Compose's state system is built on the snapshot abstraction. A Snapshot is a consistent view of all MutableState objects at a point in time.

Read tracking works like this: when composition runs, the Compose runtime installs a global ReadObserver on the current Snapshot. Any state.value read within a composable is recorded by that observer, binding the composable to that state object. When the state is written, the Snapshot system marks affected composables as invalid and schedules them for recomposition on the next frame.

Three kinds of state containers:

val counter = mutableStateOf(0)          // single value
val list = mutableStateListOf<Item>()    // observable list (structural changes trigger recomposition)
val map = mutableStateMapOf<K, V>()      // observable map

Snapshot isolation is also why composables must be side-effect free: Compose can make a snapshot of all state, run composition in a background thread — planned for future versions — and then apply changes atomically. A composable may be re-executed in a snapshot that is later discarded, so any side effects would be lost.

Under the hood

Each SnapshotMutableState is a StateObject holding a linked list of StateRecords, each tagged with the snapshot id that wrote it — this is multi-version concurrency control (MVCC). A read returns the record valid for the current snapshot's id and invalid set; a write in a mutable snapshot creates a new record rather than overwriting, so other snapshots still see the old value. Snapshot.takeSnapshot { readObserver } installs the observer thread-locally; SnapshotStateObserver maps each observed StateObject to the scope that read it. On apply(), the global snapshot version advances, write notifications fire, and the recomposer marks the dependent scopes invalid. If two snapshots wrote the same record, apply runs an optional merge policy or throws a conflict.

// conceptual shape
class StateRecord { var snapshotId: Int; var next: StateRecord? }
// read  -> newest record with id <= currentSnapshot.id, not in invalid set
// write -> append a new record tagged currentSnapshot.id (copy-on-write)

remember and rememberSaveable

🎤 Say it out loud (~30–45s): "remember caches a value in the composition's slot table keyed by the call site's position, so it survives recomposition but dies when the composable leaves the tree or on a config change. rememberSaveable adds persistence by registering the value with the SavedStateRegistry — the same Bundle mechanism as onSaveInstanceState — so it survives rotation and process death, which is why the value has to be Parcelable or you have to supply a Saver. The gotcha I call out is that remember keys aren't identity — if you don't pass a key, the value is positional, so moving the composable can reset it."

remember:

@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) { Text("Count: $count") }
}
  • Stores the value in the composition tree's slot table at the call site's position.
  • The value is retained across recompositions.
  • The value is lost when the composable leaves the composition (e.g., navigated away, removed from UI).
  • The value is lost on configuration change (rotation) unless wrapped with rememberSaveable.

rememberSaveable:

var count by rememberSaveable { mutableStateOf(0) }
  • Like remember, but persists through configuration changes by saving to the SavedStateRegistry (the same mechanism as onSaveInstanceState).
  • The value must be Parcelable, Serializable, or a supported primitive type.
  • For custom types, use a Saver:
val saver = Saver<MyState, Map<String, Any>>(
    save = { mapOf("key" to it.value) },
    restore = { MyState(it["key"] as Int) }
)
var state by rememberSaveable(stateSaver = saver) { mutableStateOf(MyState(0)) }

The interview distinction: remember survives recomposition. rememberSaveable survives recomposition, configuration change, and process recreation.

Under the hood

The Compose compiler plugin assigns every call site a stable integer "group key" and the runtime stores remember'd values in the slot table — a flat gap-buffer of Any? slots that mirrors the composition tree in execution order. remember works by emitting a currentComposer.cache(keysChanged) { calculation }: on first pass it runs the lambda and writes the result into the next slot; on recomposition it compares the stored keys and, if unchanged, reads the existing slot and skips the lambda. rememberSaveable layers on a SaveableStateRegistry (provided down the composition) — at registration it adds a registerProvider entry; when the host's onSaveInstanceState fires, the registry walks its providers, invokes each Saver.save, and writes the resulting Bundle. On restore, the registry hands the saved value back to rememberSaveable, which uses it as the initial value instead of running the producer.

slot table (gap buffer):
[ group#A | rememberedValue | group#B | mutableState(0) | ... ]
            └ read on recompose if keys unchanged, else recompute

derivedStateOf

🎤 Say it out loud (~30–45s): "derivedStateOf is for when a value is computed from other state but changes far less often than its inputs — like firstVisibleItemIndex > 0 from a scroll position. It tracks the state you read inside its block, recomputes when those change, but only invalidates downstream readers when the result actually differs by equals. So it acts as a recomposition filter: it collapses many noisy upstream changes into the few that matter. The mistake interviewers look for is using it where there's no over-recomputation to dampen — there it's just overhead."

derivedStateOf creates a derived state that is only recomputed — and only triggers recomposition in its readers — when its dependencies change and the computed value actually changes. Use it when a composable should only recompose when a derived computation result changes, not every time an upstream state changes.

// BAD: list changes on every keystroke, but showButton only changes at the boundary
val list = remember { mutableStateListOf<Item>() }
val showButton = list.size > 5  // reads list.size directly — any list change recomposes this

// GOOD: showButton only recomposes consumers when the derived value changes
val showButton by remember { derivedStateOf { list.size > 5 } }

The derived state object reads its dependencies during its computation. When a dependency changes, it re-runs the computation. Crucially, it only invalidates downstream readers if the computed value actually changed, as determined by equals().

LazyList scroll example:

val listState = rememberLazyListState()
val showScrollToTop by remember { derivedStateOf { listState.firstVisibleItemIndex > 0 } }
// showScrollToTop only changes when crossing 0 boundary, not on every scroll pixel

Under the hood

derivedStateOf returns a DerivedSnapshotState, itself a StateObject. The first time its .value is read, it runs the calculation under a nested readObserver, recording every StateObject it touched along with that object's current snapshot version into a dependency map cached in its StateRecord. On later reads it first checks whether any dependency's recorded version changed; if none did, it returns the cached result with zero recomputation. If a dependency did change, it re-runs the block and compares the new result to the cached one using the policy's equivalence (structuralEqualityPolicy by default) — only a non-equal result bumps the derived state's own version, which is what wakes its readers. Because it is a StateObject, reading a derived state inside composition registers a dependency on it, not on the underlying inputs, so the upstream churn is absorbed at this node.

list.size churns 1→2→3...   read each time
            │
   derivedStateOf { size > 5 }   recompute, but result false==false
            │                     → no version bump → no downstream invalidation
   reader recomposes only when result flips false→true

LaunchedEffect

🎤 Say it out loud (~30–45s): "LaunchedEffect launches a coroutine tied to the composition's lifecycle: it starts when the composable enters, cancels automatically when it leaves, and — critically — cancels and relaunches whenever any key changes. So the keys are effectively your dependency array for async work. The classic bug is passing Unit or no meaningful key when the effect actually depends on a parameter like userId — then you fetch once and show stale data when the id changes. Conversely, passing a key that changes too often restarts the coroutine constantly."

LaunchedEffect launches a coroutine scoped to the composition. The coroutine is cancelled and re-launched whenever the keys change.

@Composable
fun FetchData(userId: String) {
    var data by remember { mutableStateOf<Data?>(null) }
    LaunchedEffect(userId) {  // key: userId
        // Runs when userId changes. Cancelled if userId changes again before completion.
        data = repository.fetchUser(userId)
    }
    // ...
}

You can pass any number of keys. If any key changes, the previous coroutine is cancelled and a new one is launched. Use Unit or a constant when you want a one-time effect that only runs on first composition.

The common failure mode is forgetting to pass the right key: if a key that should cause re-launch is omitted, you'll show stale data after the key conceptually changes.

Under the hood

LaunchedEffect is itself a composable that remembers a LaunchedEffectImpl keyed on the passed keys. That impl is a RememberObserver: when it enters the composition (onRemembered) it creates a child CoroutineScope from the composition's recomposeCoroutineContext (whose dispatcher is AndroidUiDispatcher.Main, frame-aligned) and calls scope.launch { block() }. When it leaves the composition (onForgotten) or the keys change — which makes remember discard the old impl and create a new one — the runtime calls job.cancel(), propagating cancellation into your suspending body. So "key changed" is just "the remembered object was replaced," and lifecycle cancellation is just onForgotten firing.

// conceptual
val effect = remember(key) { LaunchedEffectImpl(coroutineContext, block) }
// RememberObserver:
//   onRemembered -> scope.launch { block() }
//   onForgotten  -> job.cancel()   // leave composition OR key replaced

DisposableEffect

🎤 Say it out loud (~30–45s): "DisposableEffect is for side effects that need an explicit teardown — registering and unregistering a listener, observer, or callback. Its body runs on enter and on key change, and the onDispose block runs right before the body re-runs and when the composable leaves the composition, so the register/unregister always stay balanced. The rule of thumb I give is: if the work is a coroutine, use LaunchedEffect; if it's a paired subscribe/unsubscribe with non-suspending cleanup, use DisposableEffect. The bug to watch for is forgetting that a key change disposes and re-registers, which can double-register if your cleanup is wrong."

DisposableEffect is for non-coroutine side effects that need cleanup. It runs onDispose when keys change or when the composable leaves the composition.

@Composable
fun LifecycleObserver(lifecycle: Lifecycle, onStart: () -> Unit, onStop: () -> Unit) {
    DisposableEffect(lifecycle) {
        val observer = LifecycleEventObserver { _, event ->
            when (event) {
                Lifecycle.Event.ON_START -> onStart()
                Lifecycle.Event.ON_STOP -> onStop()
                else -> {}
            }
        }
        lifecycle.addObserver(observer)
        onDispose {
            lifecycle.removeObserver(observer)  // cleanup
        }
    }
}

The distinction from LaunchedEffect: use DisposableEffect for register/unregister pairs — listeners, observers, callbacks. Use LaunchedEffect for coroutine-based work.

Under the hood

Like LaunchedEffect, DisposableEffect remembers a DisposableEffectImpl keyed on its keys, and that impl is a RememberObserver. On onRemembered it runs your effect lambda inside a DisposableEffectScope; the onDispose { } you return is captured as a DisposableEffectResult and stored. On onForgotten — triggered when the composable leaves the tree or when a key change replaces the remembered impl — the runtime invokes that stored onDispose. There is no coroutine and no dispatcher involved: the body and the cleanup run synchronously on the applier (main) thread during the apply/compose phase, which is why the cleanup must be non-suspending. Because key change is "forget old impl, remember new one," the framework always disposes the previous registration before running the new body, guaranteeing balanced register/unregister.

key change:  oldImpl.onForgotten() → onDispose() runs  ┐
             newImpl.onRemembered() → effect{} runs     ┘ (always in this order)
leave tree:  impl.onForgotten() → onDispose() runs

SideEffect

🎤 Say it out loud (~30–45s): "SideEffect is how I push Compose state out to code that Compose doesn't manage — analytics, an ad SDK, a non-Compose view. It runs after every successful recomposition, so if the composition aborts it won't fire with half-applied state. The gotcha interviewers probe is that it has no cleanup block and no keys — it just runs every time the composition commits — so it's only safe for fire-and-forget publishing, not for anything you need to tear down. For that you'd reach for DisposableEffect instead."

SideEffect publishes Compose state to non-Compose code. It runs after every successful recomposition — not cancelled if recomposition fails — and has no cleanup mechanism.

@Composable
fun AnalyticsTracker(screenName: String, analytics: Analytics) {
    SideEffect {
        analytics.setCurrentScreen(screenName)  // non-Compose side effect
    }
}

The right use case for SideEffect is synchronizing Compose state to an external mutable object that Compose doesn't own — analytics, an ad SDK, or a non-Compose view bridge.

Under the hood

SideEffect isn't a node in the slot table the way remember is — it registers its lambda with the current Composer as a "side effect" that the runtime queues and runs only when the composition/recomposition is applied (committed) to the tree. The Recomposer collects these in a list during the apply phase and invokes them after the change list has been executed, which is why a composition that throws or is discarded never runs them. Because it carries no key state and no onDispose, the runtime makes no attempt to dedupe or unwind it — every commit re-enqueues and re-runs the block.

recompose() -> build change list -> applyChanges() (mutate node tree)
            -> drain recordedSideEffects -> invoke each SideEffect lambda

rememberUpdatedState

🎤 Say it out loud (~30–45s): "rememberUpdatedState solves the stale-closure problem in long-lived effects. Say I have a LaunchedEffect(Unit) that I deliberately never want to restart, but it captures a callback that changes across recompositions — without help it'd call the old lambda. rememberUpdatedState stores the value in a MutableState and reassigns it on every recomposition, so the effect reads the current value through that state holder while its own coroutine keeps running uninterrupted. The key thing is I use it precisely when I don't want the changing value in the effect's key list."

rememberUpdatedState captures the latest value of a lambda or value that may change, for use inside a long-lived effect that should not be restarted when that value changes.

@Composable
fun Timer(onTimeout: () -> Unit) {
    val currentOnTimeout by rememberUpdatedState(onTimeout)
    LaunchedEffect(Unit) {  // key = Unit: never restarts
        delay(5000L)
        currentOnTimeout()  // always calls the latest lambda, not the one captured at launch
    }
}

Why you need it: if onTimeout were captured directly in the LaunchedEffect lambda, it would capture a stale closure whenever onTimeout changed — a new lambda from a recomposition. rememberUpdatedState ensures the effect always calls the latest version of the lambda without restarting the effect.

Under the hood

rememberUpdatedState(x) is essentially remember { mutableStateOf(x) }.apply { value = x } — it remembers a single MutableState slot once, then writes the newest x into it on every recomposition. The effect's coroutine closes over the state holder object (which is stable across recompositions), not over x itself, so reading currentOnTimeout goes through MutableState.value and observes whatever was last written. Because the slot identity never changes, LaunchedEffect(Unit) sees no change in its key and is never torn down.

@Composable
fun <T> rememberUpdatedState(newValue: T): State<T> = remember {
    mutableStateOf(newValue)
}.apply { value = newValue }  // overwrite on each recomposition

Stability and Skippability

🎤 Say it out loud (~30–45s): "Stability is a contract the Compose compiler reasons about to decide whether it can skip a composable when its inputs are unchanged. A type is stable if Compose can trust that equals reflects real change and that it'll be notified when an observed value mutates — primitives, @Stable/@Immutable types, and MutableState. The classic gotcha is List<T>: it's an interface, so the compiler can't prove the implementation is immutable and marks it unstable, which kills skipping. I fix that with ImmutableList or an @Immutable wrapper — and I confirm with the compiler metrics report rather than guessing."

Stability determines whether Compose can skip recomposing a composable when its inputs haven't changed.

Stable types:

  • Primitive types (Int, String, Boolean, etc.)
  • @Stable or @Immutable annotated classes.
  • MutableState<T> (Compose knows to read it and track changes).
  • Classes where all public properties are themselves stable.

Unstable types (by default):

  • List<T>, Map<K,V>, Set<T> (interface types — Compose cannot guarantee they are immutable).
  • Any class with a var public property.
  • Mutable data classes.

Skippability: a composable is skippable if all its parameters are stable. When a parent recomposes, Compose compares the new parameter values with the old ones using equals(). If all are equal, the composable is skipped entirely.

// Unstable — List<T> is not stable
@Composable
fun ItemList(items: List<Item>) { ... }  // recomposes even if items content hasn't changed

// Fix: wrap in a stable class
@Immutable
data class ItemList(val items: List<Item>)

@Composable
fun ItemList(items: ImmutableList<Item>) { ... }  // kotlinx.collections.immutable — stable

Making classes stable:

@Stable  // I promise to notify Compose of changes
class MyState {
    var value by mutableStateOf(0)  // MutableState — Compose can track
}

@Immutable  // I promise this will never change
data class Config(val theme: String, val fontSize: Int)

Compose Compiler Metrics: Run ./gradlew assembleDebug -PcomposeCompilerReports=true to generate reports that show which composables are skippable or restartable and explain why specific parameters are considered unstable.

Under the hood

The Compose compiler plugin rewrites every @Composable function to accept an extra $changed: Int bitmask parameter. At each call site the caller encodes, per argument, whether the value is the same as last time and whether its type is stable (this is the "comparison" the compiler bakes in). Inside the generated body, if the function is skippable and every input's changed-bits say "unchanged," the body short-circuits and calls composer.skipToGroupEnd() instead of re-executing. Stable types get this static comparison; unstable types are treated as "changed" every time, forcing re-execution. @Stable/@Immutable are promises the compiler trusts without proof — violating them produces a correctness bug (stale UI), not a crash. ImmutableList carries the @Immutable marker so the inference treats it as stable.

// Lowered call site (conceptual)
MyComposable(item, $composer, $changed = stabilityBits(item) or sameAsLast(item))
  -> if ($changed and 0b0110 == 0 && $composer.skipping) $composer.skipToGroupEnd()
     else <run body>

Modifier Order

🎤 Say it out loud (~30–45s): "Modifier order matters because the chain is an ordered list where each element wraps the next — the first modifier is the outermost. So padding().background() paints the background inside the padding, while background().padding() pads inside a full-bleed background. The same logic decides hit-test area: clickable().padding() makes the padding clickable, padding().clickable() doesn't. Under the hood each modifier becomes a wrapping layout/draw node, so reordering literally rebuilds the chain of nodes the layout and draw passes walk."

Modifiers in Compose are applied in the order they are chained. The order matters because each modifier wraps the one after it.

// Padding THEN background: padding is outside the background
Modifier.padding(8.dp).background(Color.Blue)

// Background THEN padding: padding is inside the background
Modifier.background(Color.Blue).padding(8.dp)

Think of modifiers as nesting — the first modifier in the chain is the outermost wrapper.

clickable + padding:

// Click area includes the padding (padding is inside clickable)
Modifier.clickable { }.padding(16.dp)

// Click area is the content only (padding is outside clickable)
Modifier.padding(16.dp).clickable { }

From a performance angle, modifiers that read state restrict recomposition, layout, and drawing to the minimal scope. Modifiers that draw — drawBehind, drawWithContent — only re-run the drawing phase when their state changes, not a full recomposition.

Under the hood

A Modifier chain is a left-associative linked structure (CombinedModifier) folded into an ordered list of Modifier.Elements. In the modern node system, that list materializes as a chain of Modifier.Node instances on the LayoutNode. During layout, measurement flows outermost-to-inner: an outer padding node measures its child with a shrunk constraint, so the inner content sees less space; placement adjusts the offset accordingly. During draw, the outermost node draws first and then delegates inward, which is why a background drawn early sits under everything after it. Pointer-input nodes like clickable only register hit regions over the bounds they occupy in the chain — so a padding placed before clickable enlarges the clickable node's bounds, while one placed after it shrinks them.

Modifier.a().b().c()  ==  a wraps (b wraps (c wraps content))
measure:  a -> b -> c -> content   (constraints shrink going in)
draw:     a -> b -> c -> content   (outer paints first / underneath)

LazyColumn Keys

🎤 Say it out loud (~30–45s): "A key gives each item in a LazyColumn a stable identity so Compose matches items across list updates instead of matching by position. Without keys, inserting at the top shifts every position, so Compose thinks every item is new and throws away their remember state — text input, animations, scroll. With keys it can diff by identity and preserve and animate state through inserts, deletes, and moves. The constraints I call out: keys must be unique within the list, stable for the same logical item, and Parcelable/primitive if I want rememberSaveable inside items to survive."

A key in LazyColumn is a stable identifier for each item that allows Compose to match items across list updates and preserve state, animations, and focus correctly.

LazyColumn {
    items(items = list, key = { item -> item.id }) { item ->
        ItemRow(item = item)
    }
}

Without keys, items are matched by position. If an item is inserted at the top, all items below it are considered "new" and their state is lost — text field input, animation state, all of it.

With keys, items are matched by key, so the list can animate insertions, deletions, and moves correctly, and Compose can restore item state — scroll position, rememberSaveable — correctly.

Keys must be stable across recompositions — consistent for the same logical item — unique within the lazy list, and of primitive types or Parcelable for rememberSaveable to work correctly.

Under the hood

Each lazy item's content is wrapped in a key(...)-style movable content group identified by the key you supply. Internally Compose stores composition state in a slot table keyed by a "compound key" derived from call-site position; the explicit item key overrides position so the runtime can recognize "this is the same logical group, it just moved." When the dataset changes, LazyListItemProvider builds a map from key to index; the runtime detaches the saved slot-table group for a key and re-inserts it at the new index rather than disposing and recreating it — which is precisely how remember and rememberSaveable values survive a reorder. With no key, identity falls back to the structural position, so a top insert renumbers every position and the groups are torn down and rebuilt. rememberSaveable additionally serializes into a Bundle-backed registry, which is why the key must be Parcelable/primitive.

keys: [A,B,C]  -> insert X at top -> [X,A,B,C]
 with key():  A,B,C groups *moved* down, state retained; X freshly composed
 no key():    positions 0..2 reused as X,A,B -> A,B,C see "new" slots, state lost

State Hoisting

🎤 Say it out loud (~30–45s): "State hoisting means lifting state out of a composable and up to a caller, so the composable becomes stateless — it takes state in as parameters and emits changes as event lambdas. That buys me a single source of truth, easy testing because I can feed any value in, and reusability since any state source can drive it. The subtle win interviewers like is that a stateless composable with stable params becomes skippable. The rule of thumb is to hoist only to the lowest common ancestor that needs the state — hoisting higher than necessary just causes broader recomposition."

State hoisting is the pattern of moving state up the composable tree so that a composable becomes stateless — it receives state as parameters and emits events as lambdas.

// Stateful composable (hard to test, hard to reuse)
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) { Text("Count: $count") }
}

// Hoisted state — stateless composable
@Composable
fun Counter(count: Int, onIncrement: () -> Unit) {
    Button(onClick = onIncrement) { Text("Count: $count") }
}

// Caller owns the state
@Composable
fun CounterScreen() {
    var count by remember { mutableStateOf(0) }
    Counter(count = count, onIncrement = { count++ })
}

The benefits are: testability — you can pass any count value to Counter in tests; reusability — Counter can be driven by any state source; a single source of truth since only one place owns the count; and the composable becomes stateless, which means it can be skippable and recomposition is more efficient.

Hoist state to the lowest common ancestor of all composables that need to read or modify it.

Under the hood

Hoisting is a consequence of how Compose tracks reads via snapshot state. Whichever composable reads count (via State.value/getValue) is the one the snapshot system records as a subscriber; when that MutableState is written, the Recomposer invalidates and re-runs only the smallest recompose scope that read it. Moving the remember { mutableStateOf } up to CounterScreen and passing count: Int down means the child Counter reads a plain stable Int parameter — so when the value is unchanged the compiler's skippability check lets it skipToGroupEnd, and when it changes only the reading scope re-executes. The event lambda travels the other way as a normal function reference; keeping it stable (e.g. a method reference) avoids it itself becoming an unstable parameter that defeats skipping.

write count.value -> snapshot apply -> notify readers
   reader = lowest scope that called State.getValue -> only that scope re-runs
hoist too high -> the reading scope is large -> more of the tree recomposes

Stateless vs Stateful Composables

🎤 Say it out loud (~30–45s): "A stateless composable takes its state in as parameters and reports changes back through event lambdas — it owns nothing, so it's trivially testable and skippable. A stateful one holds its own state with remember, which is convenient but harder to test and to reuse. The pattern I reach for is to write the stateless version as the source of truth and add a thin stateful overload on top that does the hoisting — that way I get reusability and a one-line convenience API. The gotcha interviewers probe is that 'stateful' isn't bad — it's about where you draw the hoisting line: hoist state to the lowest common ancestor that needs it, no higher."

A common pattern is to provide both a stateful and a stateless overload:

@Composable
fun TextField(value: String, onValueChange: (String) -> Unit) { ... }  // stateless

    var text by remember { mutableStateOf("") }
    TextField(value = text, onValueChange = { text = it })
}

Under the hood

remember is not magic storage — it's a call into the slot table (the gap buffer the Compose runtime uses to persist composition state). On first composition the lambda runs and its result is stored in the slot reserved at that call site; on every subsequent recomposition the runtime reads the existing slot instead of re-running the lambda (unless a key changed). mutableStateOf returns a SnapshotMutableStateImpl whose value getter records a read against the current snapshot's read-observer, which is what lets the runtime know that a given composable scope depends on that state. So "stateful" really means "this call site owns slots plus a snapshot state object," while "stateless" means the slots and state object live in an ancestor's slot table.

                       ^ persists across recompositions; read getter registers the enclosing scope as a reader

Compose Interop with Views

🎤 Say it out loud (~30–45s): "AndroidView lets me drop a classic View into a composition — factory runs once to inflate it, update runs on every recomposition where a captured state changed, and onRelease is my cleanup hook when it leaves the tree. Going the other way, ComposeView is a View I can put in XML and call setContent on. The subtle thing I watch for is lifecycle and saved-state ownership: ComposeView hooks into the View tree's LifecycleOwner and SavedStateRegistryOwner, so in a Fragment I have to wire it to viewLifecycleOwner and set the right ViewCompositionStrategy, otherwise the composition gets disposed at the wrong time or leaks."

AndroidView (embedding View in Compose):

@Composable
fun MapView(mapboxOptions: MapOptions) {
    AndroidView(
        factory = { context ->
            MapboxMapView(context, mapboxOptions)  // inflated once
        },
        update = { view ->
            view.setOptions(mapboxOptions)  // called on recomposition when mapboxOptions changes
        },
        onRelease = { view ->
            view.onDestroy()  // cleanup when composable leaves composition
        }
    )
}

ComposeView (embedding Compose in View):

<androidx.compose.ui.platform.ComposeView

    android:layout_width="match_parent"
    android:layout_height="wrap_content" />

        MyComposableScreen()
    }
}

AbstractComposeView is a class you can subclass to create a custom View that hosts Compose content and exposes Compose properties as View XML attributes, which is useful for design systems.

One lifecycle detail to be aware of: ComposeView integrates with ViewTreeLifecycleOwner and ViewTreeSavedStateRegistryOwner. In a Fragment, make sure the ComposeView is re-used across configuration changes to preserve composition — use Fragment.onCreateView() and store the ComposeView, or use viewLifecycleOwner.

Under the hood

AndroidView works because Compose's layout tree is ultimately backed by a single host View — AndroidComposeView (created by setContent on the Activity/Fragment). Composables don't emit Views; they emit LayoutNodes into the runtime's node tree. AndroidView is the bridge: it emits a special LayoutNode whose measure/layout/draw delegate to a real android.view.View instance, parenting it under an internal ViewFactoryHolder (itself an AbstractComposeView subclass). The factory lambda fills that holder once; update is stored and invoked whenever a State read inside it is invalidated; onRelease fires when the node is removed from the slot table. ComposeView.setContent does the inverse — it lazily creates an AndroidComposeView child, attaches a Recomposer and CompositionContext, and resolves the LifecycleOwner/SavedStateRegistryOwner from the View tree. The ViewCompositionStrategy (e.g. DisposeOnViewTreeLifecycleDestroyed) is just a registered observer that decides when to call dispose() on that composition.

🎤 Say it out loud (~30–45s): "Compose tests don't poke at pixels — they query the semantics tree, which is the accessibility-style description Compose builds alongside the UI. I grab a node with a matcher like onNodeWithText or onNodeWithTag, assert on it, and perform actions. The big difference from Espresso is synchronization: the test rule controls a virtual clock and auto-advances it, so by default the test waits until the app is idle before each assertion. Setup:

// or for Activity-level:
@get:Rule

Under the hood

The test rule swaps in a TestMonotonicFrameClock and registers the composition with an IdlingResource-style registry. Matchers like onNodeWithTag don't search the View hierarchy — they walk the merged/unmerged SemanticsNode tree, which the runtime produces from Modifier.semantics blocks attached to LayoutNodes. That's why assertions are deterministic without Thread.sleep. The escape hatches matter: mainClock.autoAdvance = false lets you step frame-by-frame for animations, and waitUntil polls because work on a non-Compose dispatcher (a raw thread, OkHttp callback, etc.) isn't visible to the idling registry, so the framework can't know to wait for it.

What Triggers Recomposition

🎤 Say it out loud (~30–45s): "Recomposition is driven by the snapshot system — when I read a State object during composition, the runtime records that this composable scope read that object, and when something writes a new value, it invalidates exactly those scopes and schedules them to re-run. So it's not 'parent changed, re-run everything' — it's targeted invalidation based on observed reads. The nuance interviewers push on is that writing to state nobody read during composition does nothing, and derivedStateOf only invalidates when the computed result actually changes, which is how you stop a high-frequency source from thrashing the tree."

Here is a comprehensive list of what triggers recomposition and what does not:

Trigger Mechanism
mutableStateOf value changesSnapshot system invalidates readers
mutableStateListOf / mutableStateMapOf structural changeObservable list/map notifies snapshot
collectAsState() emits new valueStateFlow/Flow → MutableState bridge
observeAsState() emits new valueLiveData → MutableState bridge
remember key changesRuntime discards remembered value, re-runs block
Parent recomposes and parameter changes (unstable params)Parent calls composable with new arg
ProduceState updatesCoroutine updates the produced state
AnimationState / Animatable tickAnimation updates state each frame

What does NOT trigger recomposition:

  • Writing to state that is not read within a composition scope.
  • Changes to derivedStateOf where the derived value did not change.
  • Parameter changes where the composable is skippable and all params are equal — that is, equals() returns true for all of them.

Under the hood

The mechanism is the snapshot state system plus the Compose compiler. State objects implement StateObject and hold a versioned record per snapshot (MVCC-style), so reads and writes are isolated and conflicts are detected at Snapshot.apply(). During composition, a Snapshot read observer captures every StateObject touched by a given RecomposeScope and stores those dependencies in the scope. When a write commits, the global snapshot apply-observer fires, the Recomposer collects the invalid scopes, and marks them dirty. The compiler's role is what makes this efficient: it rewrites every @Composable to take a $composer and a $changed bitmask, inserts composer.changed(param) comparisons, and wraps skippable bodies so the runtime can short-circuit (composer.skipToGroupEnd()) when no observed input changed. derivedStateOf adds a layer — it caches its result and only notifies downstream readers if the recomputed value differs by its policy's equivalent check, so a noisy upstream (scroll offset) that doesn't change the derived boolean produces zero recompositions.

read phase:   State.value getter -> snapshot.readObserver -> RecomposeScope records dependency
write phase:  State.value = x -> new StateRecord version -> apply observer -> Recomposer marks scope dirty
recompose:    only dirty scopes re-run; compiler $changed bitmask skips unchanged children

Avoiding Unnecessary Recomposition

🎤 Say it out loud (~30–45s): "My playbook is: keep parameters stable so composables stay skippable, scope state reads as low as possible so a change invalidates the smallest subtree, and use derivedStateOf to absorb high-frequency sources. The single most impactful trick is deferring state reads into the layout or draw phase — passing a lambda to Modifier.offset { } instead of reading scrollState.value in composition means a scroll only re-runs layout, never recomposition. And I profile before optimizing — the compiler's stability inference is usually the real culprit, so I check the compiler metrics rather than guessing."

There are several techniques. First, use stable types for parameters — wrap List<T> with ImmutableList<T> from kotlinx.collections.immutable or a custom @Immutable wrapper. Second, use derivedStateOf for computed values so that upstream state changes don't propagate when the result doesn't actually change. Third, hoist state to the right level — don't read high-frequency state like scroll position or animation progress in composables that have expensive subtrees. Fourth, use key { } in LazyColumn — without keys, structural list changes recompose items by position unnecessarily. Fifth, stabilize lambdas — lambdas that capture unstable values are themselves unstable, so use remember { lambda } to stabilize lambdas that reference stable values:

val onClickStable = remember(item.id) { { viewModel.onClick(item.id) } }

Or use the Compose compiler's @NonSkippableComposable annotation strategically.

Sixth, move state reads to the lowest composable — if only a leaf composable needs a frequently-updating state, read it only there, not in a parent that would recompose a large subtree. Seventh, read state in a DrawModifier or LayoutModifier, which restricts the effect of a state change to only the drawing or layout phase rather than triggering a full recomposition.

// Full recomposition on scroll
val scrollState = rememberScrollState()
Text(modifier = Modifier.offset(y = scrollState.value.dp), ...)

// Only layout phase re-runs (more efficient)
Text(modifier = Modifier.offset { IntOffset(0, scrollState.value) }, ...)

Finally, profile first — use Android Studio's Composition Tracing on API 30+ to see exactly which composables recompose and why, before spending time on speculative optimizations.

Under the hood

"Stable" and "skippable" are decided by the Compose compiler plugin, not at runtime. The compiler infers a type as stable if it's a primitive/String/function type, is annotated @Stable/@Immutable, or is a class whose public properties are all stable and val. Crucially, List<T> is treated as unstable because the interface could be backed by a mutable implementation — that's why ImmutableList (annotated stable) flips it. A composable becomes skippable only when all its params are stable; the compiler then generates the composer.changed()/skipToGroupEnd() short-circuit described above. The deferred-read trick works because Compose runs in three phases — composition, layout, draw — each able to read state independently. Passing a lambda to Modifier.offset { } registers the scrollState.value read inside the layout phase's MeasureScope, so a change invalidates only the layout pass (requestRelayout) and never re-enters composition. The remember(item.id) { lambda } idiom matters because a lambda capturing an unstable receiver is itself unstable; remembering it keys it to a stable id so the same instance is reused and downstream changed() checks pass.

Compiler metrics (build/compose_metrics) report per function:
  restartable skippable  fun FooRow(...)     <- ideal
  restartable            fun BarRow(...)      <- not skippable: has an unstable param
And per class:           stable / unstable    <- explains why a param breaks skippability

Under the hood

The recording modes use fundamentally different machinery. Callstack sampling installs a periodic timer that walks the stack of the app's threads at a fixed interval (e.g. every 1ms), so cost is attributed statistically — it never sees a method that runs entirely between samples, but it barely perturbs timing. Method tracing instruments method entry/exit (ART writes a trace record on every enter/return), giving exact call counts and durations but adding real per-call overhead that disproportionately inflates many small methods. System Trace is different again: it's a thin wrapper over Perfetto/atrace, reading the kernel's ftrace ring buffer over scheduler events plus userspace Trace.beginSection() markers the framework emits — so tracks like Choreographer#doFrame, RenderThread, and inflate are literally atrace slices the platform code already writes, and you can see thread state (Running/Runnable/Sleeping) and CPU core assignment. That kernel visibility is why System Trace is the tool for jank: a dropped frame caused by lock contention or being descheduled is invisible to a sampler but obvious in the scheduling track.

CPU Profiler

🎤 Say it out loud (~30–45s): "The CPU Profiler has three modes and choosing the right one matters. Sampling is cheap, around a few percent, so it's safe for longer or production-like runs, but being statistical it can miss short methods. Method tracing instruments every entry and exit, which is exact for call sequences but slows you down by orders of magnitude, so I never trust its timings. For jank I reach for System Trace through Perfetto, because that's the only mode that shows the frame timeline, RenderThread, and Choreographer alongside my own Trace sections."

The CPU Profiler records CPU usage and call stacks for the selected process. There are three recording modes to know.

Callstack Sampling periodically captures the stack of all threads. It has low overhead — about 2–5% CPU cost — but it is statistical, so short-lived method calls may be missed. Use it for long recordings or production-like profiling.

Method Tracing records every method entry and exit using Debug.startMethodTracing() under the hood. The overhead is high — 5 to 100 times slowdown — so performance results are not representative of real usage. Use it only to trace exact call sequences, not to measure timings.

System Trace via Perfetto records kernel scheduler events, Binder calls, GPU events, and custom trace sections. It is the best mode for jank analysis — you can see frame timelines, RenderThread, and Choreographer. Add custom sections with Trace.beginSection("MyWork") and Trace.endSection().

Trace.beginSection("BindViewHolder")
try {
    // expensive bind work
} finally {
    Trace.endSection()
}

Under the hood

The three modes use fundamentally different mechanisms. Sampling parks a timer/profiler thread that periodically suspends threads and walks their stacks, so cost scales with sample rate, not with how many methods run — that's why it's cheap but probabilistic. Method tracing injects a hook at every method entry/return (via Debug.startMethodTracing, which ART implements by routing through interpreter/instrumentation entrypoints), writing a record per event into a .trace buffer — exact, but the per-call bookkeeping is what produces the huge slowdown. System Trace is different again: it doesn't instrument your methods at all; it reads kernel ftrace scheduler events plus atrace/Perfetto userspace events, so Trace.beginSection just emits a marker into the same ftrace ring buffer that the kernel scheduler is writing to, giving you userspace slices time-aligned with on-CPU/off-CPU state.

Sampling      → periodic stack walk        → statistical, low overhead
Method trace  → per entry/exit record      → exact calls, large slowdown
System trace  → kernel ftrace + atrace tags → frame/scheduler timeline

Memory Profiler

🎤 Say it out loud (~30–45s): "The Memory Profiler lets me watch the heap over time and capture heap dumps to find what's actually retained — leaked Activities, oversized bitmaps, lingering listeners. The detail interviewers love is that since API 26 bitmap pixel data lives in native memory, not the Java heap, so a leak can be invisible in the Java allocation view and you need the native allocation recorder to see it. For day-to-day leak detection I'd pair this with LeakCanary, which automates the 'should this have been collected?' check rather than me eyeballing dumps."

The Memory Profiler shows heap usage over time and captures heap dumps for analysis.

The three key operations: record native allocations to track C++ heap allocations; record Java/Kotlin allocations to track JVM heap allocations with stack traces on API 26 and above; and capture a heap dump, which is a snapshot of all live objects on the heap.

When analyzing a heap dump, look for large objects, Activity instances that should have been garbage-collected (leaked Activities), Bitmap objects and their sizes, and filter by class name — for example, searching "Listener" to find leaked listeners.

For memory leak detection in general, use LeakCanary, which automatically detects leaked Activity, Fragment, and ViewModel references. It hooks into the GC and checks whether objects that should be collected are actually collected.

One important detail about Bitmaps: on API 26 and above, Bitmap pixels are allocated in native memory, not the JVM heap. You need the Memory Profiler's native allocation recorder to track bitmap memory on those versions.

Under the hood

A heap dump triggers ART to walk every live object reachable from GC roots and serialize them into an HPROF-format snapshot: each object's class, instance fields, and references. Tools like the profiler and LeakCanary's Shark parser then build the object graph and compute the shortest strong reference path from a GC root to a suspected-leaked object — that path is exactly the chain you read to find what's holding the leak. LeakCanary specifically wraps destroyed objects in a WeakReference tied to a ReferenceQueue; after gcRoot collection runs, anything still absent from the queue is "retained" and triggers a dump. Native allocation tracking is separate because those bytes never live in the ART managed heap — bitmap pixels post-API-26 are malloc'd natively and only referenced by a small Java handle, so the native recorder hooks the allocator (malloc) to attribute size and stack.

Perfetto

🎤 Say it out loud (~30–45s): "Perfetto is the modern system-tracing platform — it replaced Systrace and it's what Studio's System Trace runs under the hood. I capture a trace during a janky interaction, find a red dropped frame on the frame timeline, then expand Choreographer#doFrame to see which phase — measure, layout, bind, draw — ate the budget, and drill into RenderThread for GPU stalls. What makes it powerful at the senior level is that the trace is queryable: it's backed by a SQL engine, so I can write queries over the trace database instead of just eyeballing slices."

Perfetto is the open-source system-level tracing platform used on Android and Chrome. It replaced Systrace as the recommended tracing tool, and Android Studio's System Trace recording uses Perfetto under the hood.

You can access it three ways: via Android Studio's CPU Profiler → System Trace, which is the easiest and stays within the Studio UI; with adb shell perfetto ... for command-line capture and viewing at ui.perfetto.dev; or with the adb shell record_android_trace wrapper script for a simpler CLI.

The key features: the Flamegraph visualizes CPU call stacks over time; Thread tracks show each thread's scheduled and sleeping state, making blocking operations visible; the Frame timeline shows doFrame slices and highlights dropped frames in red; and you can add custom trace points with Trace.beginSection/Trace.endSection or the Perfetto SDK for C++. The Perfetto UI also supports SQL queries on the trace database for custom analysis.

The jank debugging workflow: capture a system trace during a jank-inducing interaction such as a fast scroll; find a dropped frame — a red segment on the Frame track; expand the main thread track for that frame and locate the Choreographer#doFrame slice; identify which sub-slice took the most time — inflate, bindViews, custom measure, and so on; then drill into the RenderThread to check for GPU bottlenecks.

Under the hood

Perfetto runs a traced daemon that owns a central ring buffer; data sources — the kernel's ftrace for scheduler/IRQ events, traced_probes for system stats, and userspace atrace/track-event producers — write into shared-memory buffers that get committed to that ring buffer. Your Trace.beginSection/endSection calls become begin/end track events on a per-thread track, time-correlated with the same clock the kernel uses, which is how a userspace slice can be lined up against on-CPU/off-CPU scheduling state. The recorded trace is a stream of protobuf TracePackets; the Perfetto UI loads it into an in-browser SQLite-backed engine (Trace Processor) and exposes the data as relational tables like slice and sched, which is what powers the SQL query interface.

                                                   Trace Processor (SQLite tables)

Systrace is the predecessor to Perfetto. It captures the same kernel-level events — scheduler, interrupts, hardware counters — plus Android-specific events, and outputs an HTML file viewable in Chrome's chrome://tracing.

In terms of current status: Systrace's Python tool (systrace.py) is deprecated and Perfetto is the recommended replacement. That said, the term "Systrace" is still widely used when referring to the concept of system-level tracing. And the custom trace event API is still valid and appears in both old Systrace output and the new Perfetto UI:

import android.os.Trace

} finally {

}

Under the hood

Both Systrace and Perfetto sit on the same lower layer: the kernel ftrace subsystem plus Android's atrace userspace tags. The kernel interleaves those markers with its own scheduler events in one ring buffer. Macrobenchmark

🎤 Say it out loud (~30–45s): "Macrobenchmark measures end-to-end performance like startup and scroll jank, and the key thing is that it runs from a separate instrumentation process that drives my app through UiAutomation — so a COLD start really does spawn the process from scratch. That makes the numbers realistic. The gotcha is that compilation mode matters enormously: if I benchmark with Full() AOT I'm measuring a best case no user ever sees, so I usually use None() for first-install or Partial() with warmup to model a real user who's launched the app a few times."

MacrobenchmarkRule — from androidx.benchmark:benchmark-macrobenchmark — measures end-to-end performance of multi-process interactions: startup time, scroll performance, compile modes. It does this from the perspective of a separate instrumentation process.

The reason for the separate process is important: Macrobenchmark runs as a separate app that controls the app under test via UiAutomation. This accurately simulates real-world cold, warm, and hot starts because the app's process is actually started from scratch.

@RunWith(AndroidJUnit4::class)
class StartupBenchmark {
    @get:Rule
    val benchmarkRule = MacrobenchmarkRule()

    @Test
    fun startup() = benchmarkRule.measureRepeated(
        packageName = "com.example.myapp",
        metrics = listOf(StartupTimingMetric()),
        compilationMode = CompilationMode.None(),  // cold start without AOT
        startupMode = StartupMode.COLD,
        iterations = 5
    ) {
        pressHome()
        startActivityAndWait()  // measures time to first full draw
    }
}

Metrics available:

  • StartupTimingMetric — timeToInitialDisplay, timeToFullDisplay.
  • FrameTimingMetric — P50, P90, P99 frame durations, jank count.
  • TraceSectionMetric("MySection") — timing of a custom Trace.beginSection.
  • MemoryUsageMetric — RSS, PSS.

CompilationMode:

  • None() — no pre-compilation (slowest, simulates cold first install).
  • Partial(warmupIterations = 3) — partial AOT from profile (simulates real user after a few runs).
  • Full() — full AOT (maximum performance baseline).

Results are printed to logcat and the test report with statistical summaries — min, median, max. Continuous integration should fail if medians regress beyond a threshold.

Under the hood

Macrobenchmark resets compilation state between runs by invoking cmd package compile against ART for the target package: None() clears the odex with compiler-filter=verify (no native code, methods run interpreted/JIT), Full() recompiles with compiler-filter=speed, and Partial() uses speed-profile driven by the collected profile plus warmup iterations. Metrics are not sampled by polling — they are extracted from Perfetto/atrace traces captured during each iteration. StartupTimingMetric reads the reportFullyDrawn and Activity lifecycle trace slices; FrameTimingMetric parses the FrameTimeline / actual frame events that SurfaceFlinger and Choreographer emit, computing per-frame CPU and GPU duration against the deadline. Because the harness lives in its own process and talks to the system UiAutomation over Binder, the app process can be force-stopped and re-launched cleanly each iteration without the test framework's own state contaminating the measurement.

Baseline Profiles

🎤 Say it out loud (~30–45s): "A Baseline Profile is a list of classes and methods I ship with the app so ART can AOT-compile the hot startup and scroll paths at install time instead of JIT-ing them during the first few launches. Without it the user pays warmup jank on early runs. I generate it with a BaselineProfileRule test that walks my critical journeys, commit the baseline-prof.txt, and rely on ProfileInstaller so it's active even off Play. The thing people forget is the profile only covers the journeys you actually exercise in the generator — so if I don't navigate into search, search never gets pre-compiled."

A Baseline Profile is a human-readable file — baseline-prof.txt — listing class names, method names, and field names that the Android Runtime (ART) should ahead-of-time (AOT) compile when the app is installed. This speeds up startup and eliminates JIT compilation latency for those critical code paths.

The way it works: at app install time — or after a Play update — ART reads the Baseline Profile and AOT-compiles the listed methods into native code. On first launch, those methods execute at full native speed instead of being JIT-compiled. Without Baseline Profiles, JIT compilation happens on the first few launches, causing warmup jank.

Generating a Baseline Profile:

@RunWith(AndroidJUnit4::class)
class BaselineProfileGenerator {

    @Test
    fun generate() = rule.collect(
        packageName = "com.example.myapp"
    ) {
        pressHome()
        startActivityAndWait()
        // Navigate through critical user journeys
        device.findObject(By.text("Search")).click()

    }
}

Run with ./gradlew generateBaselineProfile. The output baseline-prof.txt is committed to app/src/main/.

ProfileInstaller is a library that installs the Baseline Profile at app startup on Android 7 and above, even without Play, ensuring the profile is active from the very first launch.

Startup Profiles are a variant that marks specific methods as "startup" — these are compiled even more aggressively. Use the @StartupProfile annotation or the Macrobenchmark plus StartupMode.COLD workflow.

Impact: Google reports 10 to 40% startup time improvement for typical apps. Compose-heavy apps see larger gains because Compose's own runtime is also profiled.

Under the hood

The human-readable baseline-prof.txt (HRF) is compiled by the androidx.baselineprofile Gradle plugin into the binary ART profile format and packaged as assets/dexopt/baseline.prof (plus a baseline.profm metadata file that maps profile entries across the specific dex layout of that build). The HRF line syntax encodes flags per method: H = "hot" (called often), S = "startup" (touched during launch), P = "post-startup", followed by the JVM descriptor, e.g. HSPLcom/example/MyClass;->onCreate()V. At install, Package Manager hands this profile to dex2oat, which runs with compiler-filter=speed-profile — meaning ART only AOT-compiles the listed methods into the .odex/native code and leaves everything else to be verified-only and JIT-compiled lazily. This is why coverage is bounded by what the generator exercised: a method that never appears in the profile is never in the speed-profile set. ProfileInstaller performs this same install when Play isn't the installer by copying the bundled profile into the app's cur/ref profile files that ART's background dexopt job consumes.

HSPLcom/ex/App;->onCreate()V ─▶ baseline.prof + .profm ─▶ dex2oat --compiler-filter=speed-profile
                                                          └─▶ AOT-compile only listed methods

StrictMode

🎤 Say it out loud (~30–45s): "StrictMode is a debug-only instrument that flags accidental slow or risky work — disk reads, network, leaked cursors and Activities — right where it happens. I set a ThreadPolicy to catch main-thread I/O and a VmPolicy to catch leaked closables and Activity leaks, and in CI I sometimes use penaltyDeath() so a violation fails the build. The big caveat is you never ship it to production with death penalties, and you'll get false positives from the framework and even Compose font loading, so I scope those away with permitDiskReads rather than disabling detection wholesale."

StrictMode is a developer tool that detects accidentally performed slow or risky operations on the main thread — and VM-wide — and either logs a warning, shows a dialog, or crashes the app when they occur.

ThreadPolicy — main-thread violations:

StrictMode.setThreadPolicy(
    StrictMode.ThreadPolicy.Builder()
        .detectDiskReads()
        .detectDiskWrites()
        .detectNetwork()
        .detectCustomSlowCalls()  // triggered by StrictMode.noteSlowCall("name")
        .detectUnbufferedIo()
        .penaltyLog()             // logcat warning (safest for development)
        .penaltyDeath()           // crash the app (strict CI enforcement)
        .build()
)

VmPolicy — heap/resource violations:

StrictMode.setVmPolicy(
    StrictMode.VmPolicy.Builder()
        .detectLeakedSqlLiteObjects()
        .detectLeakedClosableObjects()  // unclosed Cursor, InputStream, etc.
        .detectLeakedRegistrationObjects()  // Activity leaked via BroadcastReceiver
        .detectActivityLeaks()
        .detectFileUriExposure()
        .detectCleartextNetwork()         // HTTP instead of HTTPS
        .penaltyLog()
        .build()
)

Where to enable:

// In Application.onCreate() or Activity.onCreate(), only in debug builds:
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(...)
    StrictMode.setVmPolicy(...)
}

"What is StrictMode useful for?" — detecting disk and network access on the main thread, which are jank causes; leaked database cursors or streams, which are crash and memory causes; and unencrypted network traffic, which is a security cause. Enable it in debug builds only — never in production, because the penalties can crash the app.

One gotcha: Compose itself performs file I/O for font loading on the main thread in some versions. If you see spurious violations, use StrictMode.allowThreadDiskReads() in a try/finally around Compose initialization.

Under the hood

ThreadPolicy is stored in a thread-local bitmask, so detection has near-zero cost when nothing is happening. The "detect" hooks are wired into low-level framework chokepoints: BlockGuard installs a per-thread Policy callback that methods like libcore's file and socket operations call (onReadFromDisk, onWriteToDisk, onNetwork) before performing the syscall, and noteSlowCall is what powers detectCustomSlowCalls. When a hook fires, StrictMode captures a stack trace and applies the configured penalties — penaltyLog writes to logcat, penaltyDialog posts to the main Handler, and penaltyDeath throws to crash the process. VmPolicy detection is different: leaks like unclosed Closeables or finalized SQLite objects are caught at GC/finalization time via CloseGuard, which records an allocation-site stack when the object is opened and reports it if the object is garbage-collected without being closed. allowThreadDiskReads() simply swaps in a temporarily relaxed thread-local policy and returns the old one for you to restore in finally — it doesn't disable the policy globally.

                        │ (thread-local bitmask check)
                        ▼
                   capture stack ──▶ penaltyLog / Dialog / Death

open Cursor ──▶ CloseGuard.open(stack)   ...   close() ──▶ CloseGuard.close()
                                              GC without close ──▶ report leak + stack

Interview Cheat Sheet

Section 8.1 — Quick Answers

Q: Explain measure/layout/draw. A: "There are three sequential passes. Measure: each View reports its desired size given parent constraints encoded in a MeasureSpec. Layout: each ViewGroup positions its children using left, top, right, and bottom coordinates. Draw: each View records drawing commands to a Canvas or RenderNode. ViewRootImpl drives all three in performTraversals()."

Q: invalidate() vs requestLayout()? A: "invalidate() only triggers a redraw — onDraw reruns. requestLayout() re-runs the full measure, layout, and draw pipeline. I use invalidate() for visual-only changes like color or animation frames, and requestLayout() when the View's size or position has actually changed."

Q: Why are deeply nested layouts bad? A: "Every extra nesting level adds nodes to traverse. The dangerous case is certain combinations — like WRAP_CONTENT inside WRAP_CONTENT — that cause O(n²) measurement passes. The fix is to use ConstraintLayout to flatten the hierarchy."

Q: How do you create a custom View? A: "Extend View, override onMeasure() and call setMeasuredDimension(), and override onDraw(). Create Paint and Path objects in init{} — never in onDraw. Call invalidate() for visual changes and requestLayout() when size changes."

Q: Why should onDraw() avoid allocations? A: "It gets called up to 120 times per second. Allocating objects there creates GC pressure, and a GC pause on the main thread drops a frame. Pre-allocate everything in init {}."

Section 8.2 — Quick Answers

Q: What is jank? A: "Jank is the visible stuttering you see when the app drops a frame — the display repeats the same frame for two or more VSync cycles, so the user perceives a stutter."

Q: Why does main-thread blocking cause dropped frames? A: "The main thread has to finish measure, layout, and draw recording before the VSync deadline — about 8 to 16 ms depending on refresh rate. Any blocking work — disk, network, long computation — delays that, and if the deadline is missed the frame is dropped."

Q: How would you debug jank? A: "I'd reproduce the scenario, capture a System Trace in Android Studio, find the dropped frames shown in red on the Frame track, then drill into the Choreographer#doFrame slice on the main thread to find which sub-slice is too slow. Once I know the root cause — too much work on the main thread, overly deep hierarchy, a missing Baseline Profile — I fix it and measure again to confirm the improvement."

Section 8.3 — Quick Answers

Q: Why use DiffUtil? A: "It computes the minimal diff between the old and new lists using the Myers algorithm, then dispatches precise notifyItemInserted, notifyItemRemoved, and notifyItemMoved calls. That means correct item animations and no unnecessary rebinding. notifyDataSetChanged() by contrast rebinds the entire list and kills all animations."

Q: How does RecyclerView recycle views? A: "When a ViewHolder scrolls off screen, it goes into the RecycledViewPool, bucketed by view type. When a new position becomes visible, RecyclerView pulls a matching ViewHolder from the pool and rebinds it via onBindViewHolder(). If the pool is empty, it calls onCreateViewHolder() to inflate a new one."

Q: What causes RecyclerView jank? A: "The main causes are heavy onBindViewHolder() work — synchronous image decoding, building complex SpannableStrings — too many view types with pool sizes that are too small, not using DiffUtil so everything gets rebound on update, and missing prefetch setup for nested RecyclerViews."

Section 8.4 — Quick Answers

Q: What triggers recomposition? A: "A MutableState value that was read during composition gets written to; a StateFlow or Flow collected with collectAsState() emits a new value; or a parent recomposes with changed parameters when the composable is not skippable."

Q: What is state hoisting? A: "State hoisting is moving state up the composable tree so the composable becomes stateless — it receives state as parameters and emits events as lambdas. The benefits are testability, reusability, and a single source of truth."

Q: Why does stability matter? A: "Stable composables can be skipped during parent recomposition if none of their parameters changed. Unstable parameter types — plain List, mutable classes — prevent that skipping, so even if the data hasn't changed, the composable reruns unnecessarily."

Q: remember vs rememberSaveable? A: "remember survives recomposition but not configuration change. rememberSaveable also survives configuration change and process recreation via the SavedStateRegistry. I use rememberSaveable for user input or any transient UI state that must survive rotation."

Q: LaunchedEffect vs DisposableEffect? A: "LaunchedEffect is for coroutine-based side effects — data fetches, delays — and it relaunches when keys change. DisposableEffect is for register/unregister pairs like listeners and observers; it calls onDispose when keys change or the composable leaves composition."

Q: How do you avoid unnecessary recomposition? A: "There are a few levers: use stable or immutable parameter types; use derivedStateOf for computed values so upstream changes don't propagate when the result is the same; read high-frequency state at the lowest composable level so only a small subtree reruns; use key in lazy lists; and stabilize lambdas with remember."

Section 8.5 — Quick Answers

Q: How do you debug slow startup? A: "I start with Macrobenchmark and StartupTimingMetric to get a quantified baseline. Then I capture a System Trace and look at the bindApplication, activityStart, and inflate slices to find what's taking the time. The usual fixes are moving heavy initialization off the main thread and adding Baseline Profiles to eliminate JIT warmup."

Q: How do you debug jank? A: "Capture a System Trace, find the dropped frame shown in red, identify the slow sub-slice inside Choreographer#doFrame, and fix the root cause. If it's a Compose screen, I also check the Layout Inspector for recomposition counts to see if a composable is recomposing too frequently."

Q: What are Baseline Profiles? A: "A Baseline Profile is a text file listing critical code paths that ART AOT-compiles at install time, eliminating JIT warmup on first launch. You generate them with Macrobenchmark's BaselineProfileRule, commit the output baseline-prof.txt to the repo, and ship it with the app. The typical improvement is 10 to 40% on startup, and Compose-heavy apps tend to see larger gains."

Q: What is StrictMode useful for? A: "Detecting disk and network I/O on the main thread — which are jank causes; leaked database cursors or streams — which cause crashes or memory waste; leaked Activity references; and cleartext HTTP, which is a security issue. You enable it in debug builds only, because penalties like penaltyDeath() will crash the app."
